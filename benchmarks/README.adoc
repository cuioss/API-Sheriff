= API Sheriff Integration Benchmarks
:toc: left
:toclevels: 3
:toc-title: Table of Contents
:sectnums:
:source-highlighter: highlight.js

k6-based HTTP benchmarks for API Sheriff, run against the native container over the
integration-test infrastructure.

Two lanes share one set of k6 scripts:

* the *CI baseline lane* (`-Pbenchmark`) measures API Sheriff alone and publishes to the
  benchmark pages;
* the *on-demand comparison lane* (`scripts/run-comparison.sh`) re-runs the same aspect scripts
  against a second gateway (Apache APISIX) and is deliberately wired into no workflow.

== Lane composition

The two lanes run deliberately different sets, so a number is always attributable to a lane.

[cols="1,1,3", options="header"]
|===
|Lane |Executions |Contents

|CI baseline (`-Pbenchmark`)
|12
|The eight cross-gateway matrix aspects, the two retained non-matrix benchmarks `healthLiveCheck`
 and `gatewayHealth`, *plus* the two API-Sheriff-only passthrough-relay executions (`mapped` relay
 throughput and the `empty`-mode no-regression run).

|On-demand comparison (`run-comparison.sh`)
|8
|The eight matrix aspects only.
|===

The two health benchmarks are excluded from the comparison lane on purpose: both measure the
Quarkus management port, which APISIX does not expose — `apisix.yaml` declares routes for the eight
matrix aspects only, and no management or health route at all. Driving them against APISIX would
still label their summaries `gateway_target: apisix`
while actually measuring API Sheriff — mislabelled data that reads as correct. `run-comparison.sh`
closes its aspect list to the eight comparable aspects so that is unreachable.

== The aspect matrix

The first eight aspects exist route-for-route on both gateways and are the *comparable set*: the
first six ride the single static fairness backend and measure pure gateway overhead, and the next
two (`ws`, `grpc`) ride protocol-appropriate backends instead — see the fairness caveat below the
table. The final `passthrough` aspect is *API-Sheriff-only* — the opaque L4 relay has no APISIX
route in this lane — so it runs in the CI baseline lane but never in the on-demand cross-gateway
comparison; see the passthrough methodology note under _Methodology_.

[cols="1,1,3", options="header"]
|===
|Aspect |Script |What it measures

|`unauth`
|`proxied_static.js`
|Plain proxy overhead: `k6 -> gateway -> nginx`, no authentication. The baseline every other
 aspect is read against.

|`bearer`
|`bearer_proxied.js`
|The added cost of offline bearer-token validation on the hot path. The token is minted once from
 the Keycloak `benchmark` realm and replayed, so the run measures per-request validation rather
 than token issuance.

|`http2`
|`http2.js`
|The same proxied static route over an ALPN-negotiated HTTP/2 connection. The delta against
 `unauth` isolates the protocol's effect.

|`graphql`
|`graphql.js`
|A JSON-bodied POST on a method-restricted anchor: method matching, body admission and the
 upstream path rewrite.

|`upload-1MB`
|`upload_small.js`
|The streaming request-body path at full concurrency — per-byte admission cost, separated from
 the per-request cost `unauth` already covers.

|`upload-50MB`
|`upload_large.js`
|The transfer-bound body path at *reduced* concurrency. Reports throughput (MBps) alongside
 latency.

|`ws`
|`websocket_echo.js`
|The WebSocket upgrade handshake and opaque frame relay: per-message echo round-trip through the
 gateway to go-httpbin's `/websocket/echo`. Reports round-trips/second and round-trip latency.

|`grpc`
|`grpc_unary.js`
|A unary gRPC call over the forced-HTTP/2 relay on the bare service path, against the in-repo
 `grpc-echo` service. Reports calls/second and call latency. (Per Clarification 1 this k6 gRPC
 benchmark supersedes the plan doc's `ghz` proposal, keeping the whole matrix on one load generator.)

|`passthrough`
|`passthrough_relay.js`
|The opaque L4 TCP relay path (`mapped` mode): `k6 -> gateway public TLS port with a mapped SNI ->
 L4 relay -> TLS-enabled backend`, measuring relay throughput/latency through the active passthrough
 path. Its `empty` mode re-measures the same proxied static route with `passthrough_sni` empty (D1's
 zero-overhead default) for a no-regression check against the `unauth` baseline. *API-Sheriff-only*;
 like `ws`/`grpc` it rides a real backend — see the passthrough methodology note.
|===

[NOTE]
====
*Fairness caveat for `ws` and `grpc`.* The first six aspects all ride the single static `nginx`
fairness backend, so they measure *pure gateway overhead* (see the fairness invariant under
Methodology). The `ws` and `grpc` aspects cannot: no static HTTP backend speaks WebSocket or gRPC.
They ride *protocol-appropriate* backends instead — go-httpbin's WebSocket echo for `ws` and the
in-repo `grpc-echo` service for `grpc` — and both gateways target the *same* two backends, so the
two rows stay symmetric across gateways. The consequence, accepted deliberately: these two rows
fold a real protocol backend's echo cost into the number, so they are *protocol-relay comparisons*,
not backend-free gateway-overhead measurements like the other six. Read them as "aspect X costs N%
more on gateway A than on gateway B", never as an absolute relay-throughput claim.
====

=== Retained non-matrix benchmarks

[cols="1,2,3", options="header"]
|===
|Name |Path |What it measures

|`healthLiveCheck`
|`https://api-sheriff:9000/q/health/live`
|Management-interface *liveness* throughput over TLS — the liveness probe only. Still the lightest
 path in the stack (no routing, no pipeline, no upstream), so it remains the harness-health
 indicator: a run whose numbers collapse here indicates a host or container problem, not a gateway
 regression. It is no longer a plain-HTTP floor — see the note below.

|`gatewayHealth`
|`https://api-sheriff:9000/q/health`
|Management-interface *aggregate* health throughput over TLS — `/q/health` runs every registered
 health check, including the token-sheriff JWKS readiness check, so it is the heavier of the two.
|===

Both are retained so their existing badge / history / trend series are not orphaned.

The two health benchmarks share a scheme and a port; they are distinguished by *work done*
(liveness probe vs aggregate check), not by transport. They can no longer differ by TLS: the Quarkus
management interface has exactly one port — its config declares no `ssl-port` and no
`insecure-requests` — so activating management TLS converted port 9000 itself to HTTPS. No
plain-HTTP surface remains anywhere in the stack.

=== Which goals actually run

The CI baseline lane declares twelve goals. Until PLAN-25 it had never executed all of them: the
job died at goal 4 (`passthroughRelay`, whose target hostname resolved nowhere) and Maven's
fail-fast discarded goals 5-12, which had therefore never run in CI even once. Being declared in
`pom.xml` is not evidence that a goal produces a number.

Current disposition — the CI end-of-job coverage step (see `.github/workflows/benchmark.yml`)
enforces this table, so a goal that silently stops running fails the job:

[cols="2,1,4", options="header"]
|===
|Benchmark |State |Notes

|`healthLiveCheck`, `gatewayHealth`, `proxiedStatic`
|runs
|Already executing before PLAN-25.

|`passthroughRelay`, `passthroughRelayEmpty`
|runs
|Repaired by PLAN-25: the relay target now resolves, and the `mapped`/`empty` selector actually
 reaches the container, so the two modes are genuinely distinct runs.

|`bearerProxied`, `http2`, `graphql`, `uploadSmall`, `grpcUnary`
|runs
|First execution in CI under PLAN-25. Their trend series start empty here.

|`uploadLarge`
|runs
|Skipped until the framework body-size floor was declared: the `upload` anchor declares
 `max_body_bytes: 67108864`, but `quarkus.http.limits.max-body-size` was left at the Quarkus 10 MiB
 default, so the declared 64 MiB cap was unreachable and the 50MB body was refused with `413` before
 the security filter ran. `application.properties` now declares that floor at `64M`, matching the
 largest declared cap, so the goal measures upload throughput instead of the rejection path. Its
 trend series starts empty. `skip.benchmark.upload.large` is retained (now `false`) so the goal stays
 individually suppressible.

|`websocketEcho`
|runs
|Skipped until the edge admission permit leak was fixed: every WebSocket upgrade stranded a permit,
 so a sustained load run exhausted the pool and the gateway rejected *all* traffic with `503` until
 restarted, poisoning every goal sequenced after it. The relay now releases its permit from its own
 teardown funnel and takes a bounded relay sub-budget on top, so the goal measures relay throughput
 instead of the exhaustion path. Its trend series starts empty. `skip.benchmark.websocket.echo` is
 retained (now `false`) so the goal stays individually suppressible.

|`sessionMediated`
|*unwired*
|Backs no Maven goal on purpose — see below.
|===

*Skipped means not executed.* A goal suppressed by a `<skip>` element in `benchmarks/pom.xml` — bound
to its own property — is not run at all: it consumes no wall time and cannot abort the suite. No k6
goal is suppressed today; every declared goal executes. The two states are kept distinct rather than
collapsed: the CI coverage step gates on the twelve goals that execute and would name any suppressed
goal, its skip property and its reason in the job summary. When Maven fails, that step also states in
words whether the failure truncated the suite. Silence is never the signal.

The per-goal properties are retained even when `false`, so a single goal can be suppressed for a
local run without editing its execution:

[source,bash]
----
./mvnw clean verify -pl benchmarks -Pbenchmark -Dskip.benchmark.upload.large=true
----

=== Deliberately unwired scripts

`session_mediated.js` (benchmark name `sessionMediated`) is present in `k6-scripts/` but is wired to
*no* Maven execution, **on purpose**: BFF session mediation belongs to PLAN-07A, which shipped the
server-session variant and explicitly deferred its per-variant benchmark additions because
`benchmarks/**` is PLAN-25's surface. The script is therefore ready but unclaimed, not forgotten.

It is listed in the CI end-of-job coverage summary under its own skip section, so its absence from a
run is stated in every job rather than reading as a silent omission. Do not treat a missing
`sessionMediated-summary.json` as a regression, and do not wire the script to a Maven goal without
the owning plan.

./mvnw clean verify -pl benchmarks -Pbenchmark
----

For quick runs (shorter duration, assumes containers already running):

[source,bash]

== Methodology

The comparison is designed so that the only intended difference between the two sides is the
gateway itself.

Single node, same host::
Both gateways run as containers on the same machine, on the same `api-sheriff` bridge network,
under identical CPU and memory limits (512M / 4.0 CPU). A run in which the two gateways get
different budgets measures the budget, not the gateways.

Same TLS material::
API Sheriff, APISIX and Keycloak all mount the same certificate bundle, so every edge presents one
certificate and the load generator needs no per-target trust handling. TLS termination cost is
therefore common to both sides.

Identical routes, one upstream (six HTTP aspects)::
Every *HTTP* benchmarked route on *both* gateways targets the same fast static nginx backend
(`nginx-static`). This is the *fairness invariant*: pointing one gateway's `graphql` / `upload`
routes at the JSON-serializing `go-httpbin` while the other hit `nginx-static` would fold the
backend's serialization cost into one side's number only. The accepted consequence is that the
`graphql` and `upload` aspects measure *gateway processing* — method matching, body-cap
enforcement, path rewriting — rather than real JSON or echo upstream work. That is the benchmark's
stated intent, not a limitation to work around.

Protocol-appropriate backends (`ws`, `grpc`)::
The `ws` and `grpc` aspects are the deliberate exception to the single-backend invariant: no static
HTTP backend speaks WebSocket or gRPC. Each rides a protocol backend shared by *both* gateways —
go-httpbin's `/websocket/echo` for `ws`, the in-repo `grpc-echo` service for `grpc` — so the two
sides stay symmetric even though these rows are not backend-free. See the fairness caveat under
_The aspect matrix_ for how to read the two rows.

Passthrough relay, two modes (API-Sheriff-only)::
The `passthrough` aspect drives the opaque L4 TCP relay. Like `ws` and `grpc`, it folds a real
backend's cost into the number rather than being backend-free — so it is a *protocol-relay
measurement*, not a pure gateway-overhead figure. It is *distinct* from `ws` and `grpc` in one way:
for those the gateway still owns TLS termination, whereas passthrough's backend is *TLS-enabled* and
terminates its own TLS — completing the handshake and presenting its own certificate — while the
gateway relays the still-encrypted stream at L4. Read it as relay overhead versus the terminated
baseline within one run, never as an absolute throughput claim.
It runs in two modes selected by `PASSTHROUGH_SNI`. In `mapped` mode the ClientHello names a
`tls.passthrough_sni` host, so the gateway relays the still-encrypted byte stream at L4 without
terminating and the run measures throughput/latency through the active relay path. In `empty` mode
`passthrough_sni` is empty — D1's zero-overhead default, where the accept-time front listener is
never created and the single terminated Quarkus HTTPS listener owns the public port directly — so
the run re-measures exactly the same proxied static route as the PLAN-04 `unauth` (`proxiedStatic`)
baseline. `PassthroughBaselineComparator` reads the empty-mode summary against that stored baseline
and fails the run if throughput dropped, or either latency percentile rose, beyond a fixed
percentile-band noise tolerance (k6 omits `latency_ms.stdev`, so a standard-deviation gate is not
available — see _Known fidelity limit_). A metric a run did not measure renders `n/a`, never `0`.

Readiness, not warm-up discard::
`pre-benchmark-health-check.sh` gates every run on the stack actually serving, so no run starts
against a cold or half-started gateway. It gates both halves of the lane: the management interface
(the target of the two health benchmarks) *and* a data-plane benchmark target — `/proxy/static`,
the matrix baseline whose failure would invalidate every other data-plane number. A target that is
not served therefore fails at pre-flight, naming the target, rather than 60 seconds later as an
opaque k6 threshold breach. There is no separate warm-up phase whose samples are discarded: the
first seconds of each 60-second window are included. Because the gateway is a native
(AOT-compiled) image rather than a JIT-warming JVM, and because both sides are treated
identically, this is a symmetric effect rather than a bias.

Dedicated load-generator capacity::
k6 runs as its own container rather than in-process, so the load generator's CPU time is not taken
from the gateway's budget. The `upload-50MB` aspect additionally runs at reduced concurrency
because each virtual user holds its own 50MB payload — at full concurrency the generator would be
measuring its own memory pressure and link saturation rather than the gateway.

Relative, not absolute::
*Cross-gateway numbers are meaningful only as ratios within a single run.* These are
single-node, containerized, local-network measurements, not a tuned production deployment or a
certified throughput claim. Compare "aspect X costs N% more on gateway A than on gateway B in this
run"; do not quote an absolute requests-per-second figure as either gateway's capability, and do
not compare figures across runs taken on different hosts.

=== Known fidelity limit: `latency_ms.stdev`

The k6 summaries deliberately omit `latency_ms.stdev`, and this is an *accepted, permanent*
consequence of the toolchain swap rather than a defect to fix.

k6 exposes only `avg` / `min` / `med` / `max` and the configured percentiles for a trend metric; it
reports no standard deviation, and the individual samples are not reachable from
`handleSummary()`. Emitting a derived-looking number would be a fabricated statistic, so the field
is omitted and the converter treats it as absent.

Consequence: the report's *error*, *variability-coefficient* and *confidence-band* columns are
permanently zero-width for k6 runs, where the wrk pipeline populated them from wrk's own stdev.
The percentiles (P50/P75/P90/P99) remain the measured spread signal and are what the comparison
reports on.

=== Reproducibility dependencies

Two production capabilities the benchmark configuration relies on (see ADR-0011) affect whether a
run reproduces:

* `jwks.tls_profile` — the bearer aspect's JWKS fetch verifies Keycloak's self-signed certificate
  against the stack's own trust anchors. Without it the key set never loads, every bearer request
  is rejected 401, and the aspect would measure the *rejection* path while reporting it as bearer
  throughput.
* `jwks.allowed_egress_hosts` — the SSRF egress guard otherwise refuses a JWKS URL resolving to a
  private address, which is exactly what a compose service name resolves to. The allowlist is
  host-exact and names only the benchmark-local IdP.

Both are why `bearer_proxied.js` carries an explicit HTTP-200 check: a misconfiguration that
breaks token validation fails the run instead of reporting the fast rejection path as an excellent
result.

== Comparative runs

Comparison runs are *on-demand only* and are wired into no workflow and no Maven profile that CI
invokes. Running them in CI would multiply benchmark wall time by the number of targets and would
publish comparison numbers into the baseline trend series.

Start the comparison stack — this is one three-file merge, in this exact order:

[source,bash]
----
docker compose -f docker-compose.yml \
               -f docker-compose.benchmark.yml \
               -f docker-compose.apisix.yml \
               --profile comparison up -d --build
----

The order matters and the overlay is not self-contained: `nginx-static` is defined only in
`docker-compose.benchmark.yml`, and the `api-sheriff` network is Compose-project-scoped, so the
APISIX overlay cannot be launched as its own project. "Standalone" refers only to APISIX's own
declarative (etcd-free) runtime mode.

NOTE: Always pass `--build` when Java or configuration has changed. `up -d` without it silently
runs a stale image.

Then run the comparison from `benchmarks/`:

[source,bash]
----
# Full matrix against both gateways
scripts/run-comparison.sh --target both

# A named aspect subset
scripts/run-comparison.sh --target both --aspects bearer,http2

# One side only
scripts/run-comparison.sh --target apisix
----

[cols="1,3", options="header"]
|===
|Flag |Meaning

|`--target`
|`api-sheriff` (default), `apisix`, or `both`.

|`--aspects`
|Comma-separated subset of the eight matrix aspects. Default: all eight. An unknown aspect fails
 before any run starts.

|`--output`
|Results root. Default `target/comparison-results`.

|`--duration` / `--vus`
|Per-aspect window and concurrency. `upload-50MB` keeps its reduced concurrency regardless.

|`--no-dashboard`
|Skip the supplementary HTML report (see below).
|===

=== Where results land

[source,text]
----
target/comparison-results/
  api-sheriff/<benchmark>-summary.json
  api-sheriff/<aspect>-dashboard.html
  apisix/<benchmark>-summary.json
  apisix/<aspect>-dashboard.html
  comparison-summary.md
----

This directory is segregated from both the CI baseline results and the gh-pages deployment tree, so
a comparison run can never overwrite a baseline artifact or leak into the published history/trend
series.

Render the side-by-side table:

[source,bash]
----
./mvnw -pl benchmarks exec:java \
  -Dexec.mainClass=de.cuioss.sheriff.gateway.k6.benchmark.ComparisonSummaryWriter \
  -Dexec.args="target/comparison-results api-sheriff apisix"
----

Each aspect is reported on the figure that characterises it: `uploadLarge` on throughput (MBps),
every other aspect on requests/second, with P50 and P99 per gateway. A metric a run did not measure
renders `n/a`, never `0` — a zero would read as a measured collapse rather than an absent
measurement.

== Dashboard reports

The comparison lane additionally emits a supplementary HTML report per aspect, produced by the
`xk6-dashboard` output extension.

* *Where*: `target/comparison-results/<target>/<aspect>-dashboard.html`, beside the summary JSON.
* *Offline*: each file is self-contained — every asset is inlined, with no external CDN and no
  served endpoint — so it opens directly in a browser after the stack is torn down.
* *Disabling*: pass `--no-dashboard`, which also routes the run through the stock baseline k6
  image.

The report is *purely additive*. Every aspect emits its `handleSummary()` JSON in the generic
cuioss benchmark format either way, and that JSON is what `K6BenchmarkConverter` and
`ComparisonSummaryWriter` consume. Disabling the dashboard changes what a person can browse, never
what the comparison artifact is computed from.

=== Versions

`xk6-dashboard` is a k6 *output extension*, and k6 loads output extensions only when they are
compiled into the binary — there is no runtime plugin path. `Dockerfile.k6-dashboard` therefore
rebuilds k6 with the extension linked in, as a second image beside the untouched `Dockerfile.k6`.

The k6 version built there *must track* the version behind the digest-pinned `grafana/k6` image in
`Dockerfile.k6` (currently *2.1.0*): a dashboard run and a baseline run measured by different
engines are not comparable. The runtime stage reuses that exact digest-pinned image and replaces
only the binary, so everything but the linked-in extension is byte-identical to the baseline
environment. All three build versions (k6, `xk6`, `xk6-dashboard`) are explicit pins; no floating
`latest`. When bumping k6, bump the `FROM` digest in `Dockerfile.k6` and `K6_VERSION` in
`Dockerfile.k6-dashboard` together.

== The wrk-to-k6 swap

The benchmark toolchain was migrated from wrk to k6. What changed, and what a maintainer needs to
know:

. *Scripts*: the `wrk-scripts/` Lua and shell runners were removed in favour of `k6-scripts/`
  JavaScript. Aspect scripts import `lib/target.js` (target -> base URL) and `lib/summary.js`
  (the shared `handleSummary()` helper), so one script body measures whichever gateway a run
  targets.
. *Gates*: the `WRK_MAX_ERROR_RATE` Lua gate is replaced by native k6 thresholds
  (`http_req_failed`, `checks`). A breach exits non-zero, so a gateway that starts rejecting every
  request can never benchmark as an improvement.
. *Post-processing*: `WrkBenchmarkConverter` / `WrkResultPostProcessor` are replaced by
  `K6BenchmarkConverter` / `K6ResultPostProcessor`. The downstream report pipeline (badges,
  10-run history, trends, GitHub Pages) consumes an identically-shaped model and is unchanged.
. *Coverage*: the lane grew from three wired executions to twelve *declared* goals, all of which
  execute and are expected to produce a CI result. Two of them reached that state late: `websocketEcho`
  once its blocking edge admission-permit leak was fixed, and `uploadLarge` once the framework
  body-size floor was declared under the `upload` anchor's `max_body_bytes`. `bearer`
  is genuinely new CI coverage — the wrk-era bearer runner existed on disk but was registered in no
  Maven execution. Being *wired* is not the same as *executing*, and *executing* is not the same as
  *producing a result*: until PLAN-25 the job died at the fourth goal and goals 5-12 had never run
  in CI even once. See _Which goals actually run_ above.

=== One-time gh-pages baseline restart

The published history and trend series are keyed by benchmark name and carry wrk-era numbers
measured by a different engine. Because engine change is exactly the thing that makes two numbers
incomparable, the k6 series starts fresh rather than continuing the wrk series:

* `healthLiveCheck` and `gatewayHealth` keep their names — and therefore their series — by
  deliberate choice, so the badges and trend pages are not orphaned. Expect a *visible one-time
  discontinuity* at the swap commit that is a toolchain artifact, not a regression.
* The `error` / variability / confidence-band columns go permanently zero-width from that point
  (see the `latency_ms.stdev` limit above).
* Every benchmark that writes a summary document for the first time begins with *no history* and
  needs ten runs before its trend series is meaningful. Under PLAN-25 that is most of the lane:
  eight of the twelve declared goals had never executed in CI, and all eight are expected
  to produce a result and so start their series empty — six at the PLAN-25 commit,
  `websocketEcho` once its blocking permit leak was fixed, and `uploadLarge` once the framework
  body-size floor was declared. The workflow's end-of-job coverage step
  (`.github/workflows/benchmark.yml`) is the record of which goals produced a result in a given run.
  A flat or short trend line on a name that *did* run is an absence of history, not a regression.

*Two further discontinuities are coming, and they are distinct causes — do not conflate them:*

. *First execution under PLAN-25* (this commit): goals that had never run and now produce a result
  begin their series here. The cause is coverage — data that never existed now exists.
. *PLAN-31 D6/D7 (`%it` elimination)*: that work will change the measured configuration itself, so
  the numbers before and after are measurements of different things on the *same* names. The cause
  is configuration, not coverage, and it will break continuity again at a later commit.

A reader comparing across either boundary is comparing incomparable eras. Compare only within one.

==== A second, target-change discontinuity

Both health benchmarks carry a *second* discontinuity, distinct from and later than the wrk->k6
engine swap above, at the commit that repointed them:

* `gatewayHealth` previously drove `https://api-sheriff:8443/api/health`. That data-plane endpoint
  was deleted by the pre-1.0 clean break in PR #76, so the benchmark had been measuring a
  deny-by-default `404` rather than a health surface. It now drives the management port's aggregate
  health check.
* `healthLiveCheck` previously drove the same endpoint over plain HTTP. Its numbers now include TLS
  handshake and record-layer cost.

Both names are again retained deliberately to preserve the series. Neither benchmark's post-change
numbers are comparable to its pre-change history, so compare only within the current target era.

Do not investigate either discontinuity as a performance regression.
