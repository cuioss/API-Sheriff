# benchmark.yml Performance Benchmark workflow pins JDK 21 but project baseline is Java 25 — release version 25 not supported

## Problem

`.github/workflows/benchmark.yml` (the "Performance Benchmark" workflow, job
"Run Integration Benchmarks") provisions **JDK 21** in its setup-java step:

```yaml
- name: Set up JDK 21
  uses: actions/setup-java@... # v5.2.0
  with:
    java-version: '21'
    distribution: 'temurin'
```

The project's runtime/compile baseline is **Java 25** (ADR-0001 java25-runtime-baseline;
the root pom sets `<release>25`). So the workflow's `./mvnw clean install` compiles
with `--release 25` on a JDK-21 toolchain and fails at the compiler:

```
[ERROR] Failed to execute goal ...maven-compiler-plugin:3.15.0:compile ... on project
api-sheriff: Fatal error compiling: error: release version 25 not supported
```

This is pre-existing and repo-wide — it is not introduced by any particular PR;
any PR that triggers this workflow hits it. The workflow was simply not bumped
when the project moved to Java 25.

## Observed

PR #64 (plan `fix-plan-02-landing-gaps`). After the SonarCloud outage cleared and
all required checks went green, the only remaining red check was
`Run Integration Benchmarks` (Performance Benchmark), failing with `release
version 25 not supported`. Confirmed the cause by reading `benchmark.yml`: JDK 21
vs the Java 25 baseline.

Context that made it non-blocking:
- The repo's merge rulesets require only `build / conclusion` and
  `integration-tests / conclusion` — both green. `Run Integration Benchmarks` is
  NOT a required check, so it does not block merge.
- The benchmark job is `if`-guarded (`github.event.pull_request.merged == true`)
  and triggers on `pull_request: [closed]` / tags / manual dispatch — it is
  effectively a post-merge deploy job (it deploys results to cuioss.github.io),
  not a per-commit PR gate. On `main` it has only ever run via `workflow_dispatch`.

## Directive

Bump the benchmark workflow's setup-java to the Java 25 baseline:

```yaml
- name: Set up JDK 25
  uses: actions/setup-java@... # keep the pinned SHA / bump as needed
  with:
    java-version: '25'
    distribution: 'temurin'
```

Sweep every `.github/workflows/*.yml` for the same drift — any workflow still on
`java-version: '21'` (or any pre-25 value) while the project baseline is Java 25
will fail identically the moment it compiles. The `build.yml` matrix already runs
25 + 26 (it is green), so only the peripheral workflows (benchmark, and any
release/deploy workflow) are candidates for the stale pin.

Note on fix placement: `pull_request`-triggered workflows execute the workflow
definition from the PR's BASE branch, so fixing `benchmark.yml` inside a feature
PR does not retroactively fix that PR's own benchmark run — the fix takes effect
for subsequent PRs once merged to `main`. Land it as its own small change (or fold
into a PR that is separately gated), not as a fix expected to green the current PR.

## Scope note

Out of scope for a config-validation-focused plan; this is CI-workflow
maintenance. Recorded here so the stale JDK pin is fixed deliberately rather than
rediscovered on the next PR.
