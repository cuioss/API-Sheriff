# A documentation-only footprint removes the gate that would catch a false claim - trace every runtime assertion to the implementing symbol at authoring time

## Observation

PLAN-10 (PR #257, ADR-0039) shipped a **documentation-only** footprint — two `.adoc` files — which
per this project's CLAUDE.md legitimately skips both the quality gate and full verify. The ADR twice
asserted a deployment remedy: that a deployment moving `quarkus.management.port` "must override the
image's `HEALTHCHECK` to match".

That remedy does not exist. Verified against the implementing source:

- `HealthProbe.PROBE_PORT` is a compiled-in `private static final int PROBE_PORT = 9000`.
- `HealthProbe.probe()` takes no port argument and reads no configuration.
- It connects to a hardcoded `new InetSocketAddress("127.0.0.1", PROBE_PORT)`.
- The distroless image carries no executable other than `/app/application`, so an overridden
  `HEALTHCHECK` can only re-invoke the same binary and still probes 9000.

The real consequence is the opposite of the documented one: moving the management port makes the
baked-in check fail closed — never healthy — until the image is rebuilt with a matching constant.

The claim survived outline, planning, execution and the phase-5 verification sweep. The only thing
that caught it was an automated reviewer reading the ADR against the source.

## The general shape

A build gate verifies claims about code by executing them. A prose deliverable asserting **runtime
or deployment behaviour** makes exactly that kind of claim — and a documentation-only footprint is
precisely the case where no gate runs. The skip is correct: a Maven run over two `.adoc` files proves
nothing. But it means the class of error that ships is a *factual* one, and nothing downstream trips
over it.

⛔ The asymmetry is the point. A wrong claim in code fails a test. A wrong claim in an ADR becomes
the documented recovery path an operator follows at 3am, and it is wrong in the direction that
matters: it names an action that cannot work.

## Directive

1. **Every prose assertion about runtime or deployment behaviour names its implementing symbol
   before it is written** — the constant, the method, the image layer that enacts it. Not the
   directory, not a sibling document, not the brief's own earlier prose.
2. **Read the symbol, do not recall it.** The claim here was plausible: overriding a `HEALTHCHECK`
   *is* the normal remedy for most images. It failed on a specific fact — a compiled-in constant and
   a single-executable image — that only a read would surface.
3. **Treat a documentation-only skip as a reason for more authoring care, not less.** The skip
   removes the verifier; it does not remove the obligation the verifier was discharging.
4. **When a reviewer refutes a prose claim, verify the refutation against the source too** — then
   fix it. Accepting the correction on the reviewer's word replaces one unverified claim with
   another. In this run the correction was verified first, which is the right disposition.
5. **A correction that cannot ride the same commit is a follow-up you must record, not a residue you
   may drop.** The identical wrong claim in `HealthProbe.java`'s own Javadoc could not be fixed in
   that PR — a single `.java` file would have made the whole commit gate-requiring — so prose and
   source now disagree until it is landed separately.

## 🔄 RECURRENCE 2026-09-05 — the SAME class, one plan later, and this time the claim contradicted ITSELF

PLAN-15 (PR #267, `558a38b`) is the plan that *shipped the fix* for the defect above. In the same
run it authored a new paragraph in `doc/user/environment-variable-overrides.adoc:94` stating that
moving `QUARKUS_MANAGEMENT_PORT` *"also moves the target of the image's baked HEALTHCHECK, which does
not follow it"* — and the **next three sentences of that same paragraph say the opposite**, correctly:
the probe is hard-coded to `9000`, reads no configuration, and follows the management port nowhere.

CodeRabbit caught it as a functional-correctness issue (finding `b8f5e6`, resolution `fixed`,
remediated on-branch by TASK-005). It survived the plan's own verification sweep.

⛔ **The plan applied Directive 1 to code and not to the prose beside it.** It traced the
`HEALTHCHECK` claim to `PROBE_PORT` — correctly, across six sites — and then wrote a fresh paragraph
whose first sentence contradicted the mechanism it had just verified.

## What the recurrence adds

Directive 1 checks prose **against the source**. This case would have passed that check on three of
its four sentences and still shipped a falsehood, because the defect was *internal to the paragraph*.
So a second, cheaper check belongs beside it:

6. **A paragraph that states a consequence AND explains its mechanism contains two claims — check
   them against each other, not only against the source.** Read the passage whole before calling it
   done. Sentence-by-sentence review passes this defect: every sentence is individually plausible and
   only the pair is contradictory.
7. **No build, test, or link check can observe this class.** It is not a typo, a broken reference, or
   a stale citation — the tooling that guards documentation cannot see a self-contradiction, so the
   read is the only guard there is.

⚠ **Recurrence risk is elevated for `deployment-configurability` specifically**: that epic's
deliverables are largely *statements about what a knob does*, so every plan in it authors prose of
exactly this shape.
