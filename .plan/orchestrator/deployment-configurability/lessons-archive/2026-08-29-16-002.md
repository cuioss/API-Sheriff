# api-sheriff edge/tls suite is flaky on fixed wall-clock awaits; the -T1 pin reduced but did NOT close it (3/3 red with -T1 in effect, reproduced on pristine main)

The quality gate (`verify -Ppre-commit`) failed **5 runs out of 5**, a *different* single
test each time, all in `de.cuioss.sheriff.gateway.edge` (`WebSocketRelayStageTest`,
`GatewayEdgePipelineTest.rejectsDisallowedVerb`, others), and every one of them passed 12/12
in isolation. The branch under test touched no file in that package.

## Fix (2026-08-29) — and its later refutation

`.mvn/maven.config` now pins `-T1` (serial) instead of `-T1C` (one thread per core). The
reactor runs serially; the edge suite goes green.

> **Superseded as a cure — see "## Recurrence (2026-08-31)" below.** The `-T1` pin is still
> in place and is still correct to keep, but it has since been **measured insufficient**: the
> same suite went 3/3 red *with* `-T1` in effect. Do not read this section as "solved".

## How the diagnosis was reached — and what it does NOT claim

This is the reusable part. The method was **controlled comparison**, not mechanism-guessing:

1. **Two plausible mechanisms were hypothesized and then REFUTED against the source.**
   Leaked Vert.x servers between tests: checked, not present. `Map.of()` iteration-order
   randomization changing dispatch order: checked, not the cause. Neither was assumed away
   and neither was assumed true — each was checked and discarded.
2. **Isolate the variable "is this the branch?"** The identical gate was run on clean `main`
   and reproduced the failures. That established the flakiness as **pre-existing**, not
   introduced by the branch — which also means "my branch is red" was the wrong framing from
   the start.
3. **Isolate the variable "is this concurrency?"** `-T1` vs `-T1C` at *identical wall-clock*
   and identical everything else: 5/5 red under `-T1C`, 4/4 green under `-T1`. That is the
   measurement the fix rests on.

**What is measured:** the causal link between reactor parallelism and the failures. That
link is established by step 3 and is the whole basis of the fix.

**What is inferred and remains uninstrumented:** the underlying mechanism — most likely
ephemeral port reuse while a previous socket sits in `TIME_WAIT`, since concurrent modules
racing for ports is the obvious differentiator. **No instrumentation was added to confirm
this.** It is a hypothesis that fits, not a finding.

> **Refuted 2026-09-01 — see "## Outcome (2026-09-01)" below.** The TIME_WAIT / ephemeral-port-reuse
> hypothesis is no longer merely uninstrumented; it is **contradicted**. The stall reproduces in
> fixtures that bind with `listen(0)` and **hold** the port for the whole fixture lifetime, so there
> is no released port and no re-bind window to race.

## The rule

Separate what you **measured** from what you **inferred**, and say which is which in the
commit message, the PR body and the lesson. A fix grounded in a measured causal link is
sound even when the mechanism stays unknown; a fix grounded in a plausible mechanism that
was never measured is a guess wearing a fix's clothes. Writing "port reuse under TIME_WAIT"
as if it were established would have made the next person debugging this trust a claim
nobody ever tested.

## Recurrence (2026-08-31) — the `-T1` mitigation is measured INSUFFICIENT

Observed during plan `configurable-context-path` (TASK-001 verification,
`verify -pl api-sheriff -am`). The failure class returned **with `-T1` still pinned**:

- `.mvn/maven.config` was verified to contain `-T1` in the plan worktree **and** at
  `origin/main` (`git show origin/main:.mvn/maven.config`), so the serial reactor was in
  effect for every run below. This is the check the 2026-08-29 entry's operational note
  said to make ("will resurface the moment anything reintroduces parallelism") — and
  **nothing reintroduced parallelism**. The pin held and the suite failed anyway.
- **3 runs, 3 disjoint failure sets**, same controlled-comparison method as before:
  - run 1 (with the branch change): `ReservedBodyCeilingTest.retiresConnectionAfterStreamedRejection` — `TimeoutException`
  - run 2 (byte-identical code, no edits between runs): `GatewayEdgePipelineTest.rejectsMissingBearerToken` + `PassthroughRelayTest.propagatesAbortToBackend`
  - run 3 (**pristine `origin/main`**, throwaway worktree, none of the branch changes): `WebSocketRelayStageTest.rejectsForeignOriginBeforeDial` + `TlsEdgeProducerTest.skipsUnresolvedAlias`
- 1883 of 1886 tests passed on every run; `ReservedBodyCeilingTest` passed 7/7 in isolation.
- Run 3 is the decisive one and re-establishes step 2 of the original method: reproduced on
  a trusted green baseline, so still **pre-existing, not branch-introduced**.

### What this changes

**What is now measured:** `-T1` does not close the failure class. The 2026-08-29 entry's
"4/4 green under `-T1`" was a 4-run sample against a probabilistic race, and a larger sample
refutes it as a cure. Keep the pin — it demonstrably reduced the rate — but stop treating it
as the close-out.

**What the failure signature now points at:** every failing test stands up a live Vert.x
server and blocks on a **fixed wall-clock await** (10 s or 15 s, via `CompletableFuture.get`),
and every observed failure is a `TimeoutException` on that await rather than a wrong-value
assertion. That is a *deadline* failure, not a port collision — so the still-owed close-out
from the original operational note (bind ephemeral ports, assert on the bound port) is
necessary but likely **not sufficient** on its own.

### The still-owed close-out, restated

1. Replace every fixed `CompletableFuture.get(10, SECONDS)` / `(15, SECONDS)` await in the
   live-server tests with Awaitility-style polling on a generous ceiling, so the assertion
   measures **behaviour** rather than machine load. **LANDED** — `Awaits` and its two tiers
   (`CONNECT_CEILING_SECONDS = 30`, `TEARDOWN_CEILING_SECONDS = 5`) are on `main`.
2. Bind ephemeral ports and assert on the bound port rather than racing for a fixed one
   (carried over from 2026-08-29). **Already satisfied for every server** in the surveyed
   fixtures: they bind with `listen(0)` and read back `actualPort()`, which is exactly this
   item. The residual gap is the narrower **bind-then-close** idiom — a port bound only to
   learn its number, then released and used unheld. A sweep at 2026-09-01 HEAD finds it in
   **two** places, not one, and they are ruled on separately because they differ in the way
   that matters:

   | Instance | Post-release treatment | Failure signature if the port is stolen | Ruling |
   |----------|------------------------|-----------------------------------------|--------|
   | `WebSocketRelayStageTest` lines 121-125 | port assumed **permanently dead**; dials to it are asserted to fail | an *unexpected status* — the symptom that was under investigation | IN scope as a **measurement target**; OUT of scope as a **fix** |
   | `TlsEdgeProducerTest.freePort()` lines 247-259 | port handed back as **free to bind** | the producer's bind fails **loudly** | IN scope as a **survey target** only; OUT of scope as a **fix** |

   Only `WebSocketRelayStageTest` releases the port and then *asserts it stays dead*; that
   distinction, not the shared idiom, is why the two receive different dispositions.
   `TlsEdgeProducerTest.freePort()` additionally already narrows its own window with a bounded
   re-probe-and-retry (`FREE_PORT_ATTEMPTS` + `isListening`), and its Javadoc records the
   residual window as irreducible for the positive case, which needs a genuinely free port so
   the front listener can really bind it. **"Fix both instances because both match the idiom"
   is an explicitly rejected outcome.** (`HealthProbeTest` matches a closed-port sweep but is
   an instance of neither: it binds the *fixed* management port and already asserts genuine
   closure before its refusal case.)

   ⚠️ Neither instance is any longer a *leading* candidate: the 2026-09-01 outcome below
   contradicts port theft as the mechanism outright.
3. Or serialise the live-server tests into their own non-parallel surefire group. Out of scope
   and untouched.

Until one of these lands, expect a red `verify -pl api-sheriff -am` at an unpredictable
point in **any** plan, on `main` as much as on a branch.

### The rule this recurrence adds

**A mitigation that reduces a probabilistic failure rate will read as a cure for exactly as
long as the sample stays small.** State the sample size next to the green claim ("4/4 green
under `-T1`"), because that is what tells the next reader how much the claim is worth — and
re-open the lesson rather than filing a duplicate when a later, larger sample refutes it.
When a red build reproduces on a pristine baseline, the finding is about the **suite**, and
triaging it as the branch's defect is the wrong framing every time.

## Outcome (2026-09-01) — plan `macos-loopback-hang-investigation`

Ran a **pre-registered, non-extensible** budget of **31 runs** (26 with only
`WebSocketRelayStageTest` selected; 5 whole-module), with `-T1` re-read from
`.mvn/maven.config` and confirmed in effect **before the first run** — the provenance check
this lesson prescribes. **Disposition: (c) document-only. No production and no test code was
changed.**

**Provenance labelling.** Everything in this section is **first-hand** unless marked. The
`p = 1/9` and `p = 0.50` reproduction rates that sized the budget are **MEASURED-but-second-hand**:
they come from the `stabilize-edge-suite-awaits` artifacts, which no longer exist (that plan
directory was deleted), so nothing here can re-verify them.

### MEASURED

- A **30-second stall reproduced in 8 of 31 runs (25.8%)** — 5 of 26 on the single-class arm,
  3 of 5 on the whole-module arm.
- It struck **ten distinct methods across five classes** (`WebSocketRelayStageTest`,
  `GatewayEdgePipelineTest`, `GatewayEdgeRouteBffWiringTest`, `GatewayEdgeRouteTest`,
  `PassthroughRelayTest`), always hitting the 30000 ms `Awaits` ceiling essentially exactly
  (30004–30010 ms elapsed) — **no progress at all**, not slow progress.
- **Not reactor parallelism**: `-T1` was in effect for all 31 runs.
- **Not cross-class co-tenancy or machine load**: five stalls occurred on the arm that selected
  a **single** test class in a **single** Surefire fork.
- **Not connection establishment alone**: `PassthroughRelayTest.propagatesHalfCloseToBackend`
  stalled on a half-close over an **already-established** connection, and the stall also strikes
  plain HTTP request/response exchanges, not only WebSocket upgrades.
- **Thread dumps, two independent occurrences in two different fixtures**: the awaiting thread is
  parked in `Awaits` while the Vert.x acceptor thread **and all three event-loop threads** sit
  simultaneously at `sun.nio.ch.KQueue.poll` via `KQueueSelectorImpl.doSelect`. Every Vert.x
  thread idle, with nothing to do.
- **Zero reproductions**, in 31 runs, of the separate *unexpected-upgrade-status* symptom the
  budget was actually sized against.

### INFERRED

All-threads-idle rules out saturation, deadlock and a blocked handler: the work **never arrived**
rather than arriving late. The reading that fits is a **loopback readiness event the macOS kqueue
selector never delivered**. `KQueue` is the macOS-only selector, which is what makes this
**platform-local**; the Linux CI lane has not reproduced it.

> **Refuted 2026-09-03 — see "## Close-out (2026-09-03)" below.** The kqueue-readiness reading is
> now **contradicted by measurement**, not merely superseded. Nothing was ever queued on the
> fixture's listener, so no notification was available to be lost.

### What this outcome changes

- The **TIME_WAIT / ephemeral-port-reuse hypothesis is contradicted**, not merely uninstrumented:
  the stall reproduces against ports that are **held** for the whole fixture lifetime.
- The condition is **not a defect in any fixture and not a defect in the gateway**. That is why
  disposition (c) was selected and why close-out item 2's two bind-then-close sites were both
  left unmutated: fixing a mechanism the evidence excludes would have been an unmeasured fix.
- The zero-reproduction arm is reported as **inconclusive with stated power** — never an
  all-clear. Its power figures derive from the second-hand `p = 0.50`, and an unknown share of
  that historical `5 RED / 10` tally may have been **this** 30-second stall rather than the
  unexpected-status symptom; the destroyed artifacts can no longer separate the two.

> **Corrected 2026-09-03.** "Not a defect in any fixture" was what the 31-run budget observed, and
> it did not survive instrumentation of the bind call. The defect was in the fixtures: a
> dual-stack wildcard ephemeral bind, dialled on loopback. The disposition was right on the
> evidence then available; the conclusion was not the whole answer.

### Operator guidance until this is closed

- A single red edge-suite run **on macOS** is not evidence of a branch defect — roughly a
  quarter of local runs carry the stall. Establish provenance before acting.
- Establish that provenance **against CI (Linux)**, not against a local re-run.
- **Do not** widen the `Awaits` ceilings, and do not retry-wrap or quarantine the affected
  fixtures: the 30-second ceiling is what makes the condition visible and measurable.
- **Do not** change `-T1`. It is a measured rate reduction worth keeping — it is simply not a cure.

### The rule this outcome adds

**A budget that finds nothing measures its own power, not the absence of the defect** — so report
the `N` and the power with every green claim, and never as an all-clear. And when a soak turns up a
*different* reproducible phenomenon than the one it was sized for, record it as its own finding
rather than folding it into the target's tally: conflating the two is exactly what left the
inherited `p = 0.50` uninterpretable here.

## Close-out (2026-09-03) — plan `loopback-stall-fix-and-instrumentation`

The mechanism is no longer inferred. It was **MEASURED** on 2026-09-03 (macOS 26.6.2 / darwin
25.6.0, JDK 25.0.1), and the fix that follows from it has **landed** under this plan. This section
closes the owed work; it does not retire the lesson.

### The measured mechanism

`.listen(0)` with no host argument binds the **dual-stack wildcard** `*:P`. Netty sets
`SO_REUSEADDR=true`, and macOS then permits that wildcard bind to take an ephemeral port another
process already holds as a `127.0.0.1`-specific listener. Both bindings coexist and neither call
fails. A client dialling `127.0.0.1:P` is routed by BSD most-specific-match to the **other**
process, which accepts the connection and never answers it. The Vert.x acceptor sits in
`KQueue.poll` because nothing was ever queued on its listener — **idle correctly, not stuck**.

Four controls, each with its scope stated:

- **Live capture.** At the ceiling the JVM held only its own listener and its client socket, with
  **no server-side accepted socket**. A **system-wide** `lsof -iTCP:65034` named the owner: a VS
  Code helper holding `127.0.0.1:65034 (LISTEN)` and the accepted connection at
  `rxbytes=146 / txbytes=0` — the request arrived and nothing came back. A **per-process** `lsof`
  shows the same absence and cannot name the owner; that difference is why four earlier passes had
  nothing to aim at.
- **Deterministic reproduction (E1).** Squat `127.0.0.1:P` with a loopback-specific listener, then
  wildcard-bind Vert.x on the same `P`: the bind succeeds and the request stalls, **1 of 1**. A
  demonstration that it reproduces on demand — at `N=1`, not a rate estimate.
- **Matched negative control (E2).** `listen(P, "127.0.0.1")` on that same squatted port is refused
  with `BindException`. The loopback-specific bind **collides** exactly where the wildcard bind
  silently coexists, which is what makes the fix a fix.
- **Rate, with its denominator.** 179 foreign `127.0.0.1` listeners sat inside the 16384-port
  ephemeral range (49152–65535), predicting **1.0925 %** per `listen(0)`. A positive control over
  **20 000** ephemeral allocations measured **1.0931 %**: the wildcard arm was handed all 179
  occupied ports, the loopback-bound arm was handed **0**. The three ports the bare reproducer
  stalled on — 61547, 62911, 65034 — are all inside that set.

**INFERRED.** A ~1.09 % per-`listen(0)` rate and the ~26 % per-run rate above are consistent
rather than in tension, because a run performs many ephemeral binds and one collision stalls it.
Nobody counted binds per run, so that is a consistency check between two measured figures, not a
derivation of either.

**Provenance.** The 2026-09-03 probes, run logs and population counts were working material under
`.plan/temp/`, not a committed artifact. While they exist this section is re-checkable; once they
are cleared it becomes recorded-but-not-re-checkable — the same class as the destroyed
`stabilize-edge-suite-awaits` figures.

### What landed

- All **20** `.listen(0)` sites across **9** test files now bind through `LoopbackHost.ADDRESS`
  (`de.cuioss.sheriff.gateway.testsupport`).
- `SocketSnapshot` folds the kernel's own view — `lsof` for this pid plus `netstat -anv -p tcp` —
  into every `Awaits` timeout message, so a future occurrence carries its evidence instead of
  requiring a fifth investigation to obtain it.
- An ArchUnit fitness function (`LoopbackEphemeralBindArchTest`) fails the build on a bare
  ephemeral wildcard bind in either spelling — the single-int `listen(int)` overload and the
  single-int `ServerSocket(int)` constructor — with the four `TlsEdgeProducerTest` sites carried as
  an explicit, documented carve-out. Those sites hold a port precisely so a **wildcard** production
  bind is refused, they are never dialled, and binding them to loopback would invert the assertion
  they exist to make.
- `doc/development/build-gate-discipline.adoc` is rewritten around the measured mechanism, with the
  superseded readings kept and labelled rather than deleted.
- **No ceiling was widened.** `CONNECT_CEILING_SECONDS` is still 30, `TEARDOWN_CEILING_SECONDS`
  still 5.

### The still-owed close-out, resolved

All three items are **SUPERSEDED**. None is owed any longer:

1. Awaitility-style polling on a generous ceiling — **superseded and LANDED**. `Awaits` and its two
   tiers were already on `main`; this plan kept them unchanged and hung the socket capture off the
   same ceiling.
2. The bind-then-close idiom, both instances — **superseded, and explicitly NOT implemented**. The
   2026-09-01 outcome had already ruled port theft out; the measured mechanism is a *coexisting*
   foreign listener, not a stolen released port, so neither instance is implicated. The standing
   rejection of "fix both because both match the idiom" holds, and now rests on a measurement
   rather than on an inference.
3. A non-parallel Surefire group for the live-server tests — **superseded and unnecessary**. It was
   already out of scope; the condition was never a concurrency effect, and serialising would have
   lowered the exposure per unit time while leaving the per-bind hazard exactly where it was.

### Explicitly still open — this close-out does not close these

- The **5 s TEARDOWN-tier** occurrence,
  `ReservedBodyCeilingTest.retiresConnectionAfterDeclaredLengthRejection`, elapsed **5.036 s**
  against the 5000 ms ceiling. A half-close against a connection a foreign process holds would
  plausibly produce it — a conjecture with no measurement behind it. That class is one of the fix
  sites, so its listener is now loopback-bound, which changes nothing here: binding the listener
  does not measure the teardown tier.
- **Why CI is clean.** The reading is that Linux runners hold no such `127.0.0.1`-specific
  listeners in the ephemeral range. That is **INFERRED**, and it is directly testable by running
  the population probe on a runner. Nobody has.
- **Whether the mechanism accounts for every historical occurrence**, including the
  possibly-contaminated second-hand `p = 0.50` full-suite tally. Those artifacts are destroyed, so
  the question is not merely unanswered — it is unanswerable from the record that survives.

No post-fix rate has been measured. The ~26 % figure is a **pre-fix** rate, and a post-fix green
streak is to be read the way this lesson has already had to learn to read one: as absence of
evidence at some unstated `N`.

### Lifecycle

This lesson stays **active** and is deliberately **not** retired or deleted. Its value is the
narrative record of how four passes converged on the mechanism, and that record is precisely what
would be lost by retiring it. Only the owed work is closed.

### The rules this close-out adds

**Refuting one form of a hypothesis does not clear the location it named.** The TIME_WAIT listener
form was contradicted correctly and for the right reason — those fixtures hold the socket, so there
is no release window to race. The passes that followed then instrumented the client, the accepted
socket and the selector: everything except the one bind call that decided the outcome. A refuted
sub-case is not a refuted case; it is also not a cleared **location**.

**A component that appears in every stack trace of a stall is not thereby at fault.** `KQueue` was
in both thread dumps because it is where an idle acceptor waits on macOS — not because it lost a
notification. That the platform-local selector matched a platform-local symptom read as
corroboration; the platform-local property was really BSD most-specific-match routing and what
macOS permits `SO_REUSEADDR` to do.

**The evidence that settles a collision is system-wide, not per-process.** A per-process view can
only show what is *missing* — no accepted socket. Naming the process that took the port needs a
query the investigated process is not the subject of. Four passes had the suggestive half of that
evidence and none of the conclusive half.
