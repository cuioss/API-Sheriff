# ConfigValue.getSourceName() cannot prove a Quarkus build-time key is declared

- **id**: 2026-09-01-15-001
- **component**: java-testing
- **category**: anti-pattern
- **status**: active

## Context

A key declared in the shipped `application.properties` **at its framework default** is invisible to a
value-only assertion: delete `quarkus.http.root-path=/` and the container still answers `/`, because
`@WithDefault` supplies the identical string. The test stays green while the declaration it guards has
silently evaporated. Some discriminator beyond the value is genuinely needed.

## The anti-pattern

The natural reach is the config **provenance** API — resolve the key through `ConfigProvider` and
assert the acting source names the shipped `application.properties` rather than the `@WithDefault`
fallback:

```java
ConfigValue v = ConfigProvider.getConfig().getConfigValue("quarkus.http.root-path");
assertTrue(v.getSourceName().contains("application.properties"));   // does NOT work
```

**It does not discriminate, and the reason is structural.** `quarkus.http.root-path`,
`quarkus.http.non-application-root-path` and `quarkus.management.root-path` all sit on Quarkus
`*BuildTimeConfig` interfaces. Each is fixed at *augmentation* and replayed at runtime from the
synthetic `BuildTime RunTime Fixed` config source, which carries `Integer.MAX_VALUE` ordinal and so
outranks every properties file. All three therefore report:

```
getSourceName() == "BuildTime RunTime Fixed"
```

**whether the value was read from the shipped file or fell through to the framework default** —
augmentation resolves both into that same recorded source. The assertion is green in exactly the case
it was added to catch, which is worse than no assertion at all.

Observed, not theorised: the first form of `ContextPathDefaultsTest` asserted on the source name and
all three parameterized cases failed against that literal.

## What works instead

Assert the **packaged artifact** directly — the same "assert the artifact, not the harness" technique
`ShippedApplicationPropertiesTest` already uses — and pair it with the effective runtime value:

```java
private static final Path PACKAGED = Path.of("target/classes/application.properties");
// declaration: turns RED on deletion
assertEquals(expected, packagedProperties().getProperty(key));
// effective value: proves the declaration is the ACTING one, nothing overrides it
assertEquals(expected, ConfigProvider.getConfig().getValue(key, String.class));
```

Resolve `target/classes/...` **by path**, never via `getResourceAsStream("/application.properties")`:
on the Surefire classpath `target/test-classes` precedes `target/classes`, so the resource call returns
the *test* properties file and the guard passes green against the wrong artifact.

## Generalisation

Two rules worth carrying:

1. **A provenance API answers "which source won", not "which file declared it".** Where a framework
   collapses many sources into one recorded source — any build-time/augmentation-fixed config — those
   two questions come apart, and only the second one detects a deletion.
2. **Run the deletion as an explicit negative control.** Delete the key, watch the test go red, restore
   it. That single run is what separates a real guard from one that merely looks like one — and here it
   is also the thing that exposes the failure above. In the control run the *declaration* assertion went
   red while the *runtime value* assertion stayed green, which is the whole finding in one line.

This is the concrete instance of the CLAUDE.md rule "a configuration key that parses is not a
configuration key that acts": ask whether deleting the key entirely would turn any test red, and do not
settle for an assertion that merely looks provenance-aware.

## Recurrence — 2026-09-02 (configurable-context-path)

The same root cause reappeared one level further out: not a test that cannot detect a deletion, but a
**build seam that was inert while every build stayed green**.

The proposed design mapped a Maven POM property directly onto a Quarkus build-time key. It was measured
inert, and the mechanism is the ordinal ladder that the augmentation story above already introduces:

- POM properties reach augmentation as a SmallRye config source at **ordinal 100**;
- the packaged `application.properties` declares the same keys at **ordinal 250** and therefore wins;
- a system property sits at **ordinal 400** and does win.

So the POM property was silently outranked by the project's own shipped file at every build, in every
profile, with no warning anywhere. The decision is recorded as **ADR-0038**; what belongs here is the
detection habit, not the decision.

**How it was detected — and the habit worth carrying.** Build with the seam set to a distinctive value
and then **grep the produced artifact for that value**, with a control that is known to work:

```
-Dsheriff.context-path=/gw   ->  0 occurrences of "/gw" in generated-bytecode.jar   (POM property: inert)
system property at ordinal 400 ->  4 occurrences                                    (positive control: live)
```

Generalising the two rules above by one step:

3. **A green build is not evidence that a build-time seam is in effect.** Nothing fails when a lower
   ordinal loses; the value is simply not the one baked in. The only thing that observes the outcome is
   the produced artifact.
4. **Measure the artifact, and always pair the measurement with a positive control.** "Zero occurrences"
   alone is ambiguous — it could equally mean the grep was wrong. A control path that yields a non-zero
   count on the same artifact turns the zero into a finding. This is the artifact-side twin of the
   negative-control rule in point 2: point 2 proves an assertion *can* fail, point 4 proves a
   measurement *can* find.
