# verify -Ppre-commit strips the Java unnamed-variable underscore, mangling ~180 files into uncompilable source

> **RESOLVED 2026-09-02 by PR #242 (`82e44cc`).** The destructive rewrite no longer occurs and
> the gate is satisfiable locally. See `## Resolution` at the foot of this lesson. The record
> below is preserved as filed, because the diagnosis trail and the exit-code trap it documents
> remain instructive; read the opening claim as historical.

Running the mandated pre-commit quality gate (`verify -Ppre-commit`) on this macOS machine
**rewrites ~180 source files into uncompilable Java** and then fails the build it was run to
satisfy. The gate cannot currently be satisfied locally.

## MEASURED (first-hand, 2026-09-01, worktree at `5f9630f`)

The OpenRewrite pass strips the Java unnamed-variable `_` from catch parameters:

```diff
-        } catch (UrlSecurityException _) {
+        } catch (UrlSecurityException ) {
```

`catch (X )` is not valid Java, so compilation then fails with a wall of
`<ID> erwartet` ("identifier expected") errors. Measured extent: **~180 files** dirty across
`api-sheriff/src/main/**` and `api-sheriff/src/test/**`; the build failed in
`maven-compiler-plugin:compile` at `default-compile`. The Maven log carries
`There were problems parsing …` warnings for several sources immediately before, which is the
tell that the rewrite pass could not parse what it then re-emitted.

`git checkout -- .` restores every file and the `_` returns, so the damage is confined to the
working tree — but the gate leaves it there, dirty and broken, on exit.

## The trap that makes this worse than an ordinary red build

The harness reported the backgrounded gate as **"completed (exit code 0)"** while the build's own
payload said `status: error, exit_code: 1`. That is the wrapper-exit-vs-build-verdict split the
project's own contract warns about: an operation failure exits 0 and carries its verdict only in
the stdout TOON. **A caller that trusted the exit code would have concluded the gate passed, on a
tree the gate had just broken.** Read the payload, never the exit status.

This is also a live instance of `CLAUDE.md` § "A gate that exits 0 can still have changed your
files": run the gate, then `git status --porcelain`, and attribute the dirty tree before reverting.

## INFERRED (not established)

The likely mechanism is that the OpenRewrite Java parser does not support the unnamed-variable `_`
(finalised in Java 22) at the source level this project compiles at, so it drops the token when
re-emitting. This was **not instrumented** — no OpenRewrite version was pinned, isolated or
bisected, and no minimal reproduction was cut. It is a story that fits the evidence, which is
exactly the category that has burned this repository before.

A second, separate environment fault was measured in the same session and may or may not interact
with this one: a JetBrains-installed **JDK 24.0.2 shadows sdkman's `current` (25.0.1-tem) on
`PATH`**, while `JAVA_HOME` correctly points at 25. `mvnw` prefers `JAVA_HOME`, so ordinary
in-process builds get Java 25 and succeed (31/31 during a soak in this session) — but any build
path that resolves `java` from `PATH` gets 24 and fails on `--release 25`. Appending a PATH
prepend to `~/.zshrc` and `~/.zshenv` did **not** fix it: something re-prepends the JetBrains entry
after the profile runs. Note that `~/.zshenv` had no trailing newline, so a naive `>>` append
concatenates onto the last line and corrupts it.

## Rule

Do not treat `verify -Ppre-commit` as safe to run on this machine until the underscore-stripping is
fixed or the OpenRewrite step is pinned to a parser that understands the project's source level.
Before relying on any gate result: read the build payload rather than the exit code, then
`git status --porcelain` and attribute the churn. A gate that reports success while holding your
tree in a state it cannot compile is worse than one that simply fails.

## Resolution — 2026-09-02, PR #242 (`82e44cc`)

The precondition stated in the Rule above is now satisfied: the underscore-stripping is fixed.
The gate is safe to run and `verify -Ppre-commit` is green with the tree clean on exit.

**The cause, traced rather than inferred.** The INFERRED section above guessed at a parser-level
source-compatibility problem. That guess was wrong in its mechanism, and the real cause was found
by walking the recipe graph (`rewrite-migrate-java` 3.42.1):

```
UpgradeToJava25 -> UpgradeToJava21 -> UpgradeToJava17 -> Java8toJava11
                -> lang.RenameUnderscoreIdentifier
```

`RenameUnderscoreIdentifier` is a **Java-9-era repair** that renames single-underscore identifiers
because `_` became a reserved keyword in Java 9. Since Java 22 `_` is legal again as an unnamed
variable, so the recipe fires on correct modern source and destroys it. Not a parser limitation —
a migration recipe doing exactly what it was written to do, ~15 years too late.

**Two further findings that only surfaced by tracing the graph:**

- **The existing guard never worked.** A comment claimed that swapping `UpgradeToJava21` →
  `UpgradeToJava25` avoided the Java-21 build-config migration that downgrades the compiler release
  to 21. But `UpgradeToJava25` **contains** `UpgradeToJava21` — both ran the whole time. This is
  the direct explanation for why lesson `2026-07-16-09-002`'s `<release>` downgrade kept recurring
  despite a documented fix. A composite recipe's transitive closure is not visible at the call
  site; assume nothing about what a `UpgradeToJavaNN` pulls in without walking it.
- **`JavaUtilAPIs` was active** although `cui-java-parent` 1.5.10 deliberately comments it out for
  producing "broken, non-compiling output". An override header asserted its list was identical to
  the parent's except for one substitution. It was not.

**The fix:** both composites dropped rather than patched (OpenRewrite offers no per-sub-recipe
exclusion, and this follows the parent's own precedent), plus the formatter's 178-file fixed point
landed. `main` had been sitting 178 files away from the fixed point, so *every* gate run rewrote
those files and every developer had to attribute and revert churn they did not author.

**Accepted tradeoff:** the one-time modernization migrations (`UseTextBlocks`,
`InstanceOfPatternMatch`, `SwitchExpressions`, `SequencedCollection`, …) no longer run. On a
codebase authored at Java 25 (ADR-0001) they are near-no-ops, and are not worth a formatter that
can emit source which does not parse.

**What carries forward now that the bug is closed** — the durable part of this lesson is not the
defect but the three habits that found and survived it:

1. Read the build payload, never the wrapper exit code (the trap section above stands unchanged).
2. Run the gate, then `git status --porcelain`, and attribute the churn before reverting.
3. When a documented fix keeps not taking, suspect the fix never applied rather than that the bug
   is stubborn — here, a guard everyone believed in had been a no-op from the start.
