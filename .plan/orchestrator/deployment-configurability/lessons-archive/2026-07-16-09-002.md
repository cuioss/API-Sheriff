# -Ppre-commit profile churns 13 files including a build-breaking pom.xml release downgrade to 21

## Problem

Running the canonical quality-gate command
(`build-maven:maven run --command-args "verify -Ppre-commit"`) mutates 13
tracked source files as a side effect of its formatter/OpenRewrite passes. The
churn is **non-gating** (the build still passes) but must be reverted before
every commit, and one of the mutations is actively dangerous:

1. **Root `pom.xml` `${maven.compiler.release}` is downgraded to a literal
   `21`.** The project's baseline is Java 25 (`CLAUDE.md`: *"Java 25 (compile +
   runtime; CI matrix 25 + 26)"*). Committing this downgrade would **break the
   build** — the source uses Java 25 features (records, sealed classes, pattern
   matching, virtual threads).
2. **`config-model` record classes are de-indented** by the formatter pass.
3. **Imports are reordered** across several files.

## Why it keeps costing time

The mutations are silent — the command reports `status: success`, so an agent
that does not diff the worktree after every quality-gate run will carry the
churn into the commit. On `fix-plan-02-landing-gaps` this forced a **manual
`git checkout` revert on every quality-gate invocation across three separate
execute passes**. The pom.xml downgrade in particular is a latent build-break
waiting for the one pass where the revert is forgotten.

## Directive

Fix the profile, do not keep working around it:

1. **Root cause** — the `-Ppre-commit` profile (formatter / compiler-plugin
   config in the project poms) is rewriting `${maven.compiler.release}` to a
   hard-coded `21` and re-indenting `config-model` records. The correct fix is
   to align the `-Ppre-commit` profile's compiler `<release>` with the Java 25
   baseline and stop the record de-indentation, so the profile is idempotent
   against a clean tree.
2. **Until the profile is fixed** — treat `-Ppre-commit` as tree-mutating:
   `git diff --stat` after every quality-gate run and `git checkout -- <files>`
   the churn before staging. NEVER commit the `pom.xml` `<release>` change — it
   downgrades the Java baseline and breaks the build.
3. A quality-gate command that mutates the tree it is validating is a profile
   defect, not an accepted cost; the standing workaround is a stopgap, not the
   resolution.

## Workaround applied

Reverted the churned files (`git checkout`) after each of the three
quality-gate passes before committing, taking special care that the root
`pom.xml` `<release>` never entered a commit. The plan's own commits stayed
clean, but every pass paid the manual-revert tax.
