# A gate red on one machine is not a branch defect - check CI history before attributing it

When a quality gate goes red locally, the default reflex is to treat it as a defect in the
branch under work. That reflex is expensive and, on this plan, it was wrong: substantial effort
went into hunting a suite defect before anyone asked whether CI saw the same failure.

## The check that reframes the problem

One query settles it, and it costs minutes rather than hours:

```bash
gh run list --workflow <workflow> --limit 100 --json conclusion,headSha,createdAt
```

On this plan the answer was **zero occurrences of the failure across 100 CI runs**, against a
locally-measured failure rate of roughly 50%. That single fact reframes the whole
investigation:

- **Wrong frame** (assumed): "the test suite is broken; fix the suite."
- **Right frame** (measured): "one machine reproduces something CI never does; characterise the
  environment difference."

They lead to entirely different work. Under the wrong frame you rewrite production and test
code chasing a defect that is not there, and every local green reads as a fix.

## Rule

Before attributing a locally-red gate to the branch, establish whether it is red in CI.
State the disposition explicitly, with the evidence:

- **Red in CI too** -> a branch/repository defect. Proceed with the fix.
- **Green in CI, red locally** -> an environment-conditioned failure. The branch is not
  automatically exonerated (a real race can be timing-exposed only on one host), but the
  hypothesis space and the acceptance criterion both change: you are now characterising a
  host-dependent condition, not fixing a deterministic bug, and "it passes locally now" is a
  much weaker signal than it looks.

## Related discipline

This is the *measured versus inferred* discipline applied to failure attribution: the
frequency claim ("this always fails") must be measured over a stated sample and a stated
population, not inferred from the two runs you happened to watch. The originating flake lesson
for this plan (`stabilize-edge-suite-awaits` / lesson `2026-08-29-16-002`) owns that discipline
for the flake class itself; this lesson is the attribution step that precedes it.
