# A same-file path rule: decide which layer is authoritative, and do not grow lexical normalization to chase filesystem semantics


# A "these two paths name the same file" rule: decide which layer is authoritative, and do not grow lexical normalization to chase filesystem semantics

Source: PLAN-V02-20 (#527), candidate lesson 006; code-review findings 3d53bb and 20794f, closed by operator override.

## Observation

The rule that refuses one file for both the client-authentication key and the DPoP key (`OidcClientRules.nameSameFile`) first compared `normalize()`d paths. Review found that collapsing `..` lexically disagrees with the filesystem when a parent is a symlink. The first fix (`Files.isSameFile` when both files exist) left the absent-file fallback still collapsing `..`, which the next round flagged again. Each round produced a new edge case on the same predicate and the operator closed the review after the second fix.

The residue is real: the `nameSameFile` Javadoc and `doc/user/offline-config-validation.adoc` still say the offline verdict "never differs" from the boot verdict, although a pair that locates one file through `..` or a link can pass offline and be refused at boot.

## Rule

- For a same-file check, use `Files.isSameFile` when both files exist, refuse lexically only what is provable without collapsing `..`, and leave the rest to the runtime check that reads the key material (here the boot key-id comparison).
- Record the division of labour in the ADR so a reviewer can see where the edge cases are handled.
- Word the pre-boot check as a subset of the boot check, never as equal to it.

## Apply

Any pre-boot validation rule that predicts a runtime refusal from paths or names.
