The fail-fast rules the gateway applies to its configuration at boot. A configuration that breaks any rule below does not start.

Part of the link:../configuration.adoc[Configuration Model]; the annotated link:../configuration.adoc#_gateway_configuration_gateway_yaml[`gateway.yaml` skeleton] shows every block in place.

== Configuration Validation Rules (summary)

* `version` must be a known value.
* Every `endpoint.id` is unique across all endpoint files (in one file or across files); a
  duplicate endpoint `id` fails the boot.
* Every route has a unique `id` (across all endpoint files).
* An enabled endpoint declares `base_url` *exactly when* it carries at least one proxy route (a route
  declaring neither `asset` nor `redirect`); an endpoint with a proxy route and no `base_url` fails the
  boot. A declared `base_url` must resolve whether or not a route uses it.
* An endpoint is *enabled* unless its resolved `enabled` value is `false` (file literal, or a
  `${ENDPOINT_<ID>_ENABLED:-...}` placeholder resolved against the environment --
  link:../adr/0004-topology-indirection.adoc#_topology_override_placeholder[ADR-0004]). A *disabled* endpoint is schema-validated but otherwise inert: its routes are
  not merged into the table, its `base_url` alias is *exempt* from the resolution requirement
  below, and it takes no part in the disjointness / passthrough-collision checks.
* Every `base_url` alias *of an enabled endpoint* resolves (after placeholder substitution)
  to a well-formed URL; otherwise boot fails.
* Every endpoint file declares an `auth` block (the default posture for its routes) *unless*
  its anchor declares one (see link:../user/anchors.adoc#_anchors[Anchors]); an endpoint with neither fails the
  boot. Routes may override it per route (see
  link:../user/endpoint-routes.adoc#_defaults_for_omitted_blocks[Defaults for omitted blocks]).
* Anchor `path_prefix` values are pairwise disjoint -- no anchor prefix is a prefix of another;
  overlap fails the boot.
* When an `anchors` block is configured: every enabled route's match key (`match.path_prefix`, or the
  exact `match.path`) lies inside its *declared* anchor's `path_prefix`, and every enabled route whose
  path lies inside any anchor's namespace declares exactly that anchor -- a route outside *every*
  anchor namespace declares no anchor. A membership/namespace mismatch, a missing declaration inside
  an anchor namespace, or a reference to an undefined anchor fails the boot. `protocol: grpc` routes
  are exempt from *these two containment checks only* (a service-rooted gRPC method path cannot nest
  inside a gateway path namespace) and stay subject to every other anchor rule (see
  link:../user/anchors.adoc#_anchors[Anchors]).
* [[anchor-coverage-rule]]*Namespace coverage (validator rule 4b).* This is the one statement of the
  rule; every other page links here. A *prefix* route whose namespace strictly contains an anchor's
  `path_prefix`, and which does not declare that anchor, fails the boot *unless* the anchor covers its
  namespace with a prefix route of its own. A route covers the namespace only when it declares the
  anchor, its normalized `match.path_prefix` equals the anchor prefix, *and* it narrows on no further
  `match` dimension (`methods`, `host` or `headers`); a narrowed candidate is not coverage. Exact
  routes are not judged by this rule (the previous rule covers them). `protocol: grpc` routes are
  *not* exempt. Rationale and how to cover a nested anchor:
  link:../adr/0007-anchor-scoped-policy.adoc[ADR-0007] and link:../user/anchors.adoc#_anchors[Anchors].
* Where a route's anchor declares `auth.require` of `bearer` or `session`, the route's
  *effective* auth must not resolve to `require: none` -- the anchor floor cannot be weakened;
  violation fails the boot. An endpoint or route block replacing an anchor block of a policy block
  that opts into the override WARN -- the Override WARN column of
  link:../user/anchors.adoc#_policy_block_scopes[the scope table] lists them -- is logged as the
  `ApiSheriff-101` boot WARN (see
  link:../user/anchors.adoc#_policy_block_override_warn[The override WARN]).
* Every policy block is resolved by the one nearest-declared-scope rule and is declarable only at
  its own scopes; the bundled schemas refuse it anywhere else (see
  link:../user/anchors.adoc#_policy_block_scopes[Where each policy block is declarable]).
* A `forward` block declaring both lists of one dimension (`headers_allow` with `headers_deny`, or
  `query_allow` with `query_deny`) fails the boot -- on an endpoint exactly as on a route.
* A `forward.headers_allow`, `forward.headers_deny` or `forward.set_headers` naming `Cookie`, in any
  letter case, fails the boot -- on an endpoint exactly as on a route. Which cookies cross is decided
  by the `cookies` block alone.
* A `cookies` block fails the boot, at whichever of its four scopes it is declared, when: it
  declares `allow: all` at the gateway scope; a listed name is not an RFC 6265 cookie name, or is one
  of the gateway's own cookies; it declares `same_origin_check` or `additional_origins` while its
  `allow` is `none`; or an `additional_origins` entry is not a serialized origin. A route-level
  `cookies` block on an asset or redirect route fails the boot, and so does a `protocol: websocket`
  route whose effective block forwards any cookie without a non-empty `websocket.allowed_origins`.
  A declared `allow: []` is refused at load. A cookie-forwarding route with `same_origin_check: false`
  emits the `ApiSheriff-139` boot WARN (see link:routing-and-forwarding.adoc#_cookies_boot_rules[Boot refusals and WARNs]).
* A route whose *effective* auth is `require: bearer` requires a `token_validation` block with
  at least one issuer.
* A route whose *effective* auth is `require: session` requires an `oidc` block.
* An `auth` block (anchor, endpoint or route) declaring `session_fallback: true` must declare
  `require: bearer`, and the gateway must declare an `oidc` block; each violation fails the boot
  (see xref:authentication-and-oidc.adoc#_auth_session_fallback[`auth.session_fallback`]).
* A route's `match` declares exactly one of `path_prefix` and `path` (enforced by the schema).
* Any two routes with an identical `match.path_prefix` (compared normalized), or any two exact routes
  with an identical `match.path` (compared verbatim, so `/a` and `/a/` never collide) -- same file or
  not -- must be statically disjoint, or the boot fails. Disjoint means one of: different `host`
  values; non-overlapping `methods`; header matchers on the same name (compared after `Locale.ROOT`
  lower-casing) with different exact values; or one matcher requiring the header (`present: true` or
  a `value`) while the other forbids it (`present: false`). `value` vs `present: false` is disjoint;
  `value` vs `present: true` is not; a lone `present: true` establishes nothing. An exact route never
  collides with a prefix route (see link:../user/endpoint-routes.adoc#_route_ordering[Route ordering]).
* A `match.headers` matcher declaring `present: false` together with `value` fails the boot, naming
  the route and the header (the matcher could never match). Every such matcher is reported in the
  same pass (see link:routing-and-forwarding.adoc#_match[`match`]).
* A route declaring two `match.headers` matchers on the same header name (compared after
  `Locale.ROOT` lower-casing) that can never both hold -- two different `value`s, or one requiring
  the header (`present: true` or a `value`) while the other forbids it (`present: false`) -- fails
  the boot, naming the route and both matchers. One error is reported per conflicting pair, all in
  the same pass. Redundant but compatible pairs (`value` with `present: true`, identical values,
  identical presence flags) are valid. Across two *different* routes the same `value` vs
  `present: false` pair stays disjoint and valid.
* A route resolves *exactly one* terminal action: a `redirect` block together with an `asset` block or
  an `upstream` block fails the boot. A route under a `type: asset` anchor declares an `asset` or a
  `redirect` block; an `asset` block under any other anchor type, or on an unanchored route, fails the
  boot. A `redirect` is refused on any `protocol` other than `http`.
* A `redirect.location` without `allow_external: true` must be a gateway path: exactly one leading
  `/`, no backslash, no percent-encoded `/` or `\`, no dot-segment, printable ASCII without
  whitespace, and no `#` when `keep_query` is `true`. With `allow_external: true` it may instead be an
  absolute `http`/`https` URI with a non-empty host and no user-info. Any other value fails the boot;
  a route opting into `allow_external` emits the `ApiSheriff-128` boot WARN. `redirect.status` must be
  one of `301`, `302`, `303`, `307`, `308` (enforced by the schema).
* `upstream.rewrite_location: true` is refused on `grpc` and `websocket` routes.
* `asset.index` and `asset.fallback` are refused on a `source: upstream` asset block, and each value
  must be a single file-name segment (no `/`, `\`, `..` or control character, not empty).
* `portal.path` must be canonical (a single leading `/`, no `//`, no dot segment, no `?` or `#`, no
  percent-encoded separator, admitted by the URL path review), must not equal a reserved OIDC path
  (compared host-independently), and must not equal the exact `match.path` of an enabled endpoint's
  route; a prefix route covering it is admitted. Each violation fails the boot (see
  link:../configuration.adoc#_portal[`portal`]).
* Every enabled endpoint's `catalog.entry` must be an origin-relative path on the gateway's own
  origin: a single leading `/`, no scheme or authority, no backslash, no percent-encoded `/` or `\`,
  and a path part the URL path review admits. A violation fails the boot without echoing the value
  (see link:../configuration.adoc#_endpoint_catalog[`endpoint.catalog`]).
* A `portal.template_dir` whose `portal.html` is missing, unreadable or unparseable, or that uses
  `raw`, `safe` or a namespaced expression, aborts startup with `ApiSheriff-202` (a template refusal,
  reported separately from the collected `ApiSheriff-200` violations).
* `allowed_methods` (global, anchor, or endpoint) may list only `GET`, `HEAD`, `POST`, `PUT`,
  `PATCH`, `DELETE`, `OPTIONS`; listing `TRACE` or `CONNECT` fails the boot.
* Every method in a route's `match.methods` must be a member of that route's *effective*
  `allowed_methods` (resolved by the one policy-block rule); a route matching a verb its endpoint
  forbids fails the boot (see link:routing-and-forwarding.adoc#_allowed_methods[`allowed_methods`]).
* A route whose `match.host` equals (case-insensitively) a key in `tls.passthrough_sni`
  fails the boot (see the link:tls-and-egress.adoc#_tls[`tls`] field reference).
* Every `tls.passthrough_sni` alias resolves via the topology, and the resolved URL carries no
  base-path; otherwise the boot fails.
* The `forwarded` block is optional; when present, `forwarded.trusted_proxies` must be present
  within it (may be empty = forwarding headers are never trusted); the trust-all CIDRs `0.0.0.0/0`
  *and* `::/0` are rejected as unsafe.
* A `forwarded.trusted_proxies` entry shorter than `/16` (IPv4) or `/48` (IPv6) emits the
  `ApiSheriff-102` boot WARN -- it does *not* fail the boot. An IPv4 `/16` and an IPv6 `/48` boot
  without a WARN, as a chosen exposure rather than a safe one. A range supplied through a `${VAR}`
  placeholder meets exactly these rules and no stricter one (see the
  link:routing-and-forwarding.adoc#_forwarded_headers[`trusted_proxies`] field reference and
  link:../adr/0044-Trusted-proxy_breadth_is_warned_beyond_one_provisioned_network_and_refused_only_at_the_whole_address_space.adoc[ADR-0044]).
* A `${VAR}` written at a *list-valued* key supplies the whole list: the placeholder is typed from
  the destination's declared `array` and split on `,`, each element stripped. An *empty resolution*
  at such a key -- a value resolving to empty, the defaulted `${VAR:-}` shape, or any empty
  comma-separated element -- *fails the boot*, reported at the value's own pointer and never
  echoing the resolved value. An explicit `[]` written in the file stays valid; the refusal happens
  at substitution because these keys declare no `minItems`. A `${VAR}` resolving to empty at a
  *scalar* key is not affected by this rule.
* *The list-valued rule applies by declared type alone.* It reaches *every* `array`-typed key of
  `schema/gateway.schema.json` (over `gateway.yaml`) and `schema/endpoint.schema.json` (over each
  `endpoints/*.yaml`), on identical terms. The enumerations below are checked against those schemas
  by a contract test. A key defined once and referenced from several places -- `allowed_methods` at
  the global and anchor level, the `security_filter`, `security_headers`, `forward` and `cookies`
  blocks -- is one key, named by the block it is declared under; an endpoint document's keys are
  named relative to its `endpoint` block.
+
--
In `gateway.yaml` the schema declares 20 such keys, of which 19 declare string items and are the
usable set: `allowed_methods` (global and anchor), `security_filter.allowed_paths`, `security_filter.allowed_header_names`,
`security_filter.blocked_header_names`, `security_filter.allowed_content_types`,
`security_headers.cors.allowed_origins`, `security_headers.cors.allowed_methods`,
`security_headers.cors.allowed_headers`, `tls.cipher_suites`, `tls.alpn`,
`forwarded.trusted_proxies`, `token_validation.issuers[].jwks.allowed_egress_hosts`, `oidc.scopes`,
`oidc.allowed_egress_hosts`,
`oidc.session.csrf.trusted_origins`, `oidc.user_info.allowed_claims`,
`oidc.user_info.default_view`, `cookies.allow` (global and anchor) and `cookies.additional_origins`.

An `endpoints/*.yaml` document declares the same-named `allowed_methods`, four
`security_filter` lists and the two `cookies` lists (at the endpoint and on a route), and adds 7 further string-item keys of its
own: `scopes`, `routes[].match.methods`, `forward.headers_allow`, `forward.headers_deny`,
`forward.query_allow`, `forward.query_deny` (the forward block, at the endpoint and on a route) and
`routes[].websocket.allowed_origins`.
--
+
*`cookies.allow` takes a `${VAR}` only in part.* Its node is a scalar-or-list `oneOf` with no `type`,
so a placeholder written as its whole value resolves to one scalar: `none` or `all` binds that mode,
and a comma-separated value such as `SESSIONID,theme` is refused at load. To take cookie names from
the environment, write one placeholder per list element, for example
`allow: ["${APP_SESSION_COOKIE}", theme]`. `cookies.additional_origins` takes the whole-list form.
+
Of the reachable keys, 3 are arrays of *objects* rather than strings (`token_validation.issuers`,
`routes`, `routes[].match.headers`): the first in `gateway.yaml`, the other two in an endpoint
document. At each the mechanism *reaches* the key rather than silently skipping it, produces scalars
where the schema requires objects, and the schema-validation pass then *refuses the document* -- a
loud failure, not a wrong value. That refusal is deliberate and is *preserved* by the map rule
below: the `object` arm is reachable only from a key's own declared type and never from an array's
item type, so an array-of-objects key keeps failing loudly instead of binding an array of
single-entry objects.
* *A `${VAR}` written at a map-valued key supplies the whole map.* Where the destination declares
  `object`, the placeholder is split on `,` exactly as a list is, and each element is then split on
  its *first* `=` into a key and a string value (so a value may contain `=`). Example:
  `tls.passthrough_sni: "${SHERIFF_PASSTHROUGH_SNI}"` with
  `SHERIFF_PASSTHROUGH_SNI=legacy.example.com=legacy-tier,vault.example.com=vault-tier` binds a
  two-entry map.
+
A *malformed* input (an element without `=`, or an empty key) or an *empty resolution* leaves the
value a string, which the schema-validation pass refuses as `expected object, got string` at the
key's own pointer, naming the types and never the value.
+
*A `${VAR}` at an object-typed key that contains a secret-classified field anywhere beneath it is
refused at boot.* Today that is `oidc` (it holds `client_secret`); `oidc.session` holds no secret
and is admitted. The error names the pointer and the rule and never echoes the resolved value. Write
the bare `${VAR}` at the secret field itself (see the `client_secret` rule below). The refusal runs
at substitution because the whole-map form could otherwise synthesise a `client_secret` after the
bare-reference check has read the document.
* *Reachable is not recommended.* `forwarded.trusted_proxies` is deployment-bound and is the
  intended user of the list mechanism. `tls.cipher_suites`, `tls.alpn` and the endpoint-document
  security lists (`forward` allow/deny lists, `cookies.allow`, `cookies.additional_origins`,
  `routes[].websocket.allowed_origins`) are policy: they are reachable by a `${VAR}`, which can
  widen or empty them, but belong in the committed document
  (link:../adr/0025-The_whole_server-TLS_surface_is_neutral_in_gatewayyaml_and_bound_by_exactly_two_seams.adoc[ADR-0025]).
  An empty resolution at any of them fails the boot.
* The one secret in `oidc`, `client_secret`, must be a *bare* `${ENV_VAR}` reference -- not a
  literal, and not the defaulted `${ENV_VAR:-...}` form, whose default would itself be a literal
  secret in a committed document. Both shapes fail the boot. The three `key_file` values
  (`client_authentication.key_file`, `sender_constraint.key_file`, `session.key_file`) are
  locations, not secrets, and are not held to this rule: a literal path and a defaulted placeholder
  are both accepted.
* `oidc.client_secret` together with `oidc.client_authentication.key_file` fails the boot. The two
  select different client authentications, so at most one of them may be configured; declaring
  neither is valid and selects `private_key_jwt` with a generated key. A declared
  `oidc.client_secret` that resolves to a blank value fails the boot as well. Both are reported at
  `/oidc/client_secret` with a fixed text that names the keys and carries neither the secret nor the
  configured path (see link:authentication-and-oidc.adoc#_oidc_client_authentication[Client authentication]).
* The client JWKS path -- a declared `oidc.client_authentication.jwks_path`, or the default
  `/bff/jwks` when the key is omitted -- must not be the path of another reserved OIDC endpoint: the
  `redirect_uri` callback, `logout.path`, `logout.post_logout_redirect_uri`,
  `logout.backchannel_path`, `user_info.path`, `login.path` or `step_up.path`. A collision fails the
  boot at `/oidc/client_authentication/jwks_path`, naming both keys. A path that is not a canonical
  gateway path fails the boot at the same pointer. Both refusals hold in both client-authentication
  modes (see link:authentication-and-oidc.adoc#_oidc_client_jwks[The client JWKS endpoint]).
* A `key_file` the gateway cannot use -- absent, unreadable, not holding exactly one unencrypted
  PKCS#8 `PRIVATE KEY` block and one `PUBLIC KEY` block, holding a key that is neither RSA of at
  least 2048 bits nor EC on P-256, or holding two halves that do not match -- fails the boot. This
  refusal is raised when the BFF runtime reads the key, not by the validator, so it is reported on
  its own rather than with the collected `ApiSheriff-200` violations (see
  link:authentication-and-oidc.adoc#_oidc_signing_keys[Signing keys]).
* `session.mode: cookie` does *not* require `session.key_file` -- omitting it selects the
  generate-on-startup key mode (sessions are dropped on restart and the key is not shareable
  across replicas). A declared `session.key_file` the gateway cannot use fails the boot when the
  BFF runtime reads it, naming the key and the defect and never the path (see the
  link:authentication-and-oidc.adoc#_oidc[`session.key_file`] field reference). `session.mode: server` requires an explicit
  `session.store` (only `memory` is valid), reads no sealing key, and refuses a declared
  `session.key_file` at `/oidc/session/key_file`.
* A declared `oidc.session.cookie_name` -- in either session mode -- must start with the
  case-sensitive `+__Host-+` prefix followed by a name, be a non-empty RFC 9110 token, and differ
  from the gateway-owned `+__Host-sheriff-binding+` and `+__Host-sheriff-logout+` cookies; otherwise
  the boot fails, naming every requirement the name misses and echoing the value escaped. An
  omitted key resolves to `+__Host-sheriff-session+` and is never refused (see the
  link:authentication-and-oidc.adoc#_oidc[`session.cookie_name`] field reference).
* A declared `oidc.user_info.path`, `oidc.login.path` or `oidc.step_up.path` must be an absolute
  gateway path starting with a single `/` and carrying no query (`?`), no fragment (`#`), no
  backslash (`+\+`), no control character and no whitespace; a blank, relative or scheme-relative
  (`//host`) value, or one holding any of those characters, fails the boot at the key's own pointer,
  echoing the value escaped. A value that passes that check must also be canonical -- no `//`, no dot
  segment, no matrix parameter (`;`) and no percent-encoded character, the review the client JWKS
  path is held to -- or the boot fails at the same pointer. The path is matched by exact equality
  with the canonical request path (see the link:authentication-and-oidc.adoc#_oidc[`oidc`] field
  reference).
* `egress_tls.oidc_verify_hostname: false` together with a named `egress_tls.oidc_tls_profile`
  fails the boot with a configuration error naming both keys, and a named `oidc_tls_profile` that is
  unbound, `trust-all`, anchor-free or unloadable fails it too. Both are raised when the BFF runtime
  builds its identity-provider client, before any dial (see
  link:tls-and-egress.adoc#_oidc_back_channel_posture[The BFF OIDC back-channel]).
* An `oidc.allowed_egress_hosts` entry that is blank, whitespace-only or carries a `:port` suffix
  fails the boot at `/oidc/allowed_egress_hosts`, naming the entry (escaped); a bare IPv6 literal is
  admitted. An omitted or empty list is admitted and exempts no host: the token engine's SSRF egress
  guard then refuses every IdP call to a loopback or private address at runtime (see the
  link:authentication-and-oidc.adoc#_oidc_allowed_egress_hosts[`allowed_egress_hosts`] field reference).
* A `token_validation.issuers[].jwks.allowed_egress_hosts` entry of an `http`-sourced issuer that is
  blank, whitespace-only or carries a `:port` suffix fails the boot, naming the entry (a bare IPv6
  literal is admitted). An `http`-sourced issuer that declares no list must name a host in its
  `jwks.url`, because that host is the derived egress allowance; a `jwks.url` without a host fails
  the boot with `CONFIG_INVALID`, naming the issuer but never the URL (see the
  link:authentication-and-oidc.adoc#_token_validation[`allowed_egress_hosts`] field reference).

* A declared `token_validation.issuers[].jwks.refresh_interval_seconds` outside `60`-`86400` fails
  the boot at `/token_validation/issuers/<index>/jwks/refresh_interval_seconds`, naming the issuer,
  the key and the admitted range but never the JWKS URL.

* A declared `token_validation.issuers[].jwks.key_rotation_grace_period_seconds` outside `0`-`3600`
  fails the boot at its own pointer, with the same message shape.

* A declared `token_validation.issuers[].jwks.unknown_kid_refresh_window_seconds` outside `5`-`3600`
  fails the boot at its own pointer, with the same message shape.

* Each of those keys declared on a `source: file` issuer fails the boot at its own pointer,
  whatever value it holds: a file source is read once and never re-fetched, so the key would parse
  and never act. Every violation of every issuer is reported in one pass (see
  link:authentication-and-oidc.adoc#_jwks_key_rotation[Key rotation and the refresh cadence]).

* `security_headers.cors` with a wildcard origin and `allow_credentials: true` is rejected. `cors`
  is accepted in the global `security_headers` block only; a `cors` key inside an anchor's
  `security_headers` block fails the boot at schema load.
* A `security_headers.content_security_policy` value -- global or anchor -- that is blank or carries
  a CR, LF or any other control character fails the boot.
* A `security_headers.header_modes` entry -- global or anchor -- naming a header its own block does
  not enable fails the boot.
* A `protocol: websocket` route whose *effective* auth is `require: bearer` or `require: session`
  must declare a *non-empty* link:routing-and-forwarding.adoc#_allowed_origins[`websocket.allowed_origins`] list; an absent or
  empty allowlist *fails the boot* (there is no "any origin" default). A `require: none` WebSocket
  route may omit it. Each declared entry, on any route, is an exact origin (`scheme://host[:port]`,
  host compared case-insensitively, scheme and port exact); wildcards, suffix forms, and regular
  expressions are rejected. `allowed_origins` written as a route-level sibling of `websocket` fails
  the boot as an unknown key. A `websocket` block on a non-`websocket` route fails the boot.
* `websocket.idle_timeout_seconds`, when declared, must be a *positive integer* (default `300`
  when omitted); it is valid only on a `protocol: websocket` route.
* The `edge_hardening` block is optional, and so is each of its members. An omitted `admission_cap`
  resolves to `2048`; an omitted `websocket_relay_cap` resolves to a *quarter of the effective*
  `admission_cap` (never below `1`), which is `512` at the default `admission_cap`. When declared,
  each cap must be at least `1`.
* `edge_hardening.websocket_relay_cap` must not exceed `edge_hardening.admission_cap` (a relay takes a
  permit from both, so a larger value could never bind). The comparison uses the *effective* values,
  so only an *explicitly declared* relay cap can trip it.
* `security_defaults.max_authorization_header_value_length`, when declared, must not be *below* the
  resolved baseline `max_header_value_length` (1024 under `strict`, 8192 under `lenient`). The key
  only *raises* the pre-route cap for `Authorization` values; neither a route's `security_filter` nor
  `security_defaults.profile` can lower that cap. The comparison uses the *resolved* profile, so it is
  a boot rule; the schema owns only the `integer` / `minimum: 1` range. An omitted key is never
  refused -- it resolves to the default `8192`.
* `asset_defaults.content_types` is *add-only*: an entry naming one of the gateway's 21 built-in
  asset extensions is *refused at boot*, with the message naming the offending extension (remapping a
  built-in -- `svg` away from `image/svg+xml`, or any built-in to `text/html` -- is a stored-XSS
  lever). Entries for extensions the gateway does *not* map are always accepted, and an omitted or
  empty block is never refused. See link:routing-and-forwarding.adoc#_asset_defaults[`asset_defaults`].
