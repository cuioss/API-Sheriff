[[_tls_edge_accept_time_sni_split]]
== TLS Edge (Accept-Time SNI Split)

A Vert.x `NetServer` *front listener* owns the public TLS port. It reassembles the TLS ClientHello,
reads the cleartext Server Name Indication (RFC 6066) and splits each connection at accept time:

* *SNI listed in `tls.passthrough_sni`* -> an *opaque L4 TCP relay*. The intact byte stream
  (ClientHello included) reaches the topology-resolved backend, which presents *its own*
  certificate. The gateway never terminates and sees no L7 detail.

* *any other SNI, or none* -> an *internal handoff to the terminated L7 listener*, which completes
  the handshake with the gateway's certificate (`min_version`, `alpn`, `mtls`) and runs the full
  pipeline.

image::../resources/diagrams/tls-sni-split-and-seams.svg[Accept-time SNI split between the opaque L4 relay and the terminated HTTPS listener, the two server-TLS policy seams, and the management interface, align=center]

Two guards keep the split unambiguous: boot fails when a route's `match.host` equals a passthrough
SNI, and a runtime *Host-vs-SNI smuggle guard* answers a terminated request whose `Host` names a
passthrough SNI with `404` (`PASSTHROUGH_HOST_SMUGGLED`) *before route selection*. Selection is
*fail-closed* (link:../security-threat-model.adoc#gw-06[GW-06]): anything not positively matched as
passthrough is terminated, never relayed. Internals are in the
link:../development/tls-edge.adoc[developer TLS-edge topic].

[[_server_tls_policy_binding]]
== Server-TLS Policy Binding (Two Seams)

`gateway.yaml` is the single effective source of server-TLS *policy* across both listeners
(link:../adr/0025-The_whole_server-TLS_surface_is_neutral_in_gatewayyaml_and_bound_by_exactly_two_seams.adoc[ADR-0025]):

* *Terminated main HTTPS listener* -- bound at server startup via an options customizer that applies
  `tls.min_version`, `tls.cipher_suites`, `tls.alpn` and `tls.mtls`.

* *Management interface* -- bound before CDI startup via a single-ordinal configuration source that
  projects `management.tls.enabled: false` onto the management listener without exposing deployment
  ports or trust material.

See link:../development/tls-edge.adoc#_server_tls_policy_binding[Contributor Guide -- Server-TLS
Policy Binding] for the Quarkus hook mechanics and
link:../adr/0010-YAML_expansion_limits_enforced_in_a_compose-only_pre-pass_before_bind.adoc[ADR-0010]
for the pre-pass expansion limits.

[[_inbound_security_filter]]
== Inbound Security Filter

The inbound filter is the "basic HTTP security filtering -- not a WAF" layer, delivered by
`cui-http`'s security module (see link:../technical_aspects.adoc#_http_security_validation[Technical
Aspects -- HTTP Security Validation]). It runs synchronously on the request's virtual thread (< 1 ms
target, no I/O) and is split across route selection into a non-skippable pre-route floor and an
always-dispatched post-route stage whose validation half is profile-gated
(link:../development/README.adoc#_inbound_validation_where_the_code_lives_and_why[Contributor Guide
-- Inbound Validation]):

image::../resources/diagrams/inbound-filter-and-framing.svg[Inbound filter split across route selection: the pre-route floor with the framing gate, route selection and profile resolution, and the post-route stage with its always-enforced and profile-gated checks, align=center]

The parameter *count* cap stays in the floor although the values it bounds are validated
post-route: a collection limit is a DoS guard that does not depend on a per-route policy.

*Profiles.* The mode set is `strict` / `paranoid` / `lenient` / `minimal`, on the gateway-wide
`security_defaults` block and on any `security_filter` block. An omitted block or `profile` resolves
to `strict`, the fail-closed choice. `minimal` is refused at boot on any effectively-authenticated
or `type: bff` route and takes its retained limits (`max_body_bytes`) from the nearest non-`minimal`
profile in its fallback chain (`strict` when the whole chain is `minimal`; see
link:README.adoc#_component_model[Component Model] and
link:../adr/0024-Inbound_filter_modes_minimal_is_a_partial_disable_retaining_the_body_cap_and_path_allowlist_and_is_refused_on_authenticated_and_BFF_routes.adoc[ADR-0024]).

*The query is validated in the form it is forwarded in.* The post-route stage receives the query
pairs raw and still percent-encoded, split on `&` in wire order -- never grouped by name -- and
validates names and values with `cui-http`'s parameter pipelines (each decoding once). The forward
path appends the pairs in the same order, rewriting every raw `;` in a forwarded name or value as
`%3B` on every route so an upstream that splits on `;` cannot read a second parameter out of one
pair (CWE-235;
link:../adr/0047-The_security_filter_validates_the_raw_query_it_forwards.adoc#semicolon-exception[ADR-0047]).

Path allowlisting is enforced at the gateway from the route's `allowed_paths`. Which client headers
and query parameters reach the upstream is answered later by the route's `forward` block (see
link:routing-and-forwarding.adoc#_forward_policy[Forward Policy] and
link:../configuration.adoc#_security_filtering[Configuration -- Security Filtering]).

=== Framing Gate

A stateless anti-request-smuggling *framing gate* runs once at stage 1, before route selection,
independent of the profile. It rejects five desync and framing vectors with `400` (see
link:../security-threat-model.adoc#gw-02[GW-02]):

. `Content-Length` + `Transfer-Encoding` coexistence;
. a `Content-Length` that is repeated, comma-listed, not strictly decimal ASCII digits (`1*DIGIT`),
  or overflows `long`;

. a `Transfer-Encoding` that is repeated or is not exactly `chunked`;
. a body on a bodyless method (`GET` or `HEAD`);

. a `Connection` header naming a framing or trust header.

On HTTP/1.x a framing rejection carries `Connection: close` and closes the connection once written,
discarding any pipelined request behind it. On HTTP/2 it ends the offending stream alone, resetting
an open request body with `NO_ERROR` once written (<<_http2_post_response_reset>>).

*One operator-relaxable leg.* The gateway-wide `security_defaults.allow_get_with_content_length_body`
(default `false`) relaxes only the declared-`Content-Length` check on `GET` (for upstreams such as
Elasticsearch `_search`,
link:../adr/0029-The_GET-with-body_opt-in_relaxes_only_the_Content-Length_leg_and_is_necessarily_gateway-wide.adoc[ADR-0029]);
every other leg stays unconditionally rejected.

[[_http2_post_response_reset]]
== HTTP/2 Post-Response Reset and Connection Window

image::../resources/diagrams/http2-reset-and-body-timers.svg[HTTP/2 post-response reset and connection window bounds, dispatch body framing with abortive HTTP/1.1 close, and the four request-body and stream timers, align=center]

*An HTTP/2 response answered while the request body is still open is ended once request data stops
arriving or a time cap passes, and its stream is then reset with `NO_ERROR`*
(link:../adr/0066-An_HTTP2_response_answered_while_its_request_body_is_open_is_ended_once_request_data_stops_arriving_or_a_time_cap_passes_and_its_stream_is_then_reset_with_NO_ERROR.adoc[ADR-0066]).
This single rule governs every response the edge ends -- relayed responses, pre-upgrade WebSocket
rejections, and every gateway-authored answer (problem documents, HTML error pages, portal, reserved
paths, assets, redirects, short-circuits, gRPC trailers-only statuses, and admission `503`s). Only a
completed WebSocket upgrade and L4 passthrough bypass it:

. *Stop the body at once.* Reset any in-flight upstream request and pause the inbound stream,
  returning no further flow-control window.

. *Wait until request data settles.* Hold `END_STREAM` until the stream or connection window is
  exhausted (or the stream ended), the window is quiet for 50 ms, or the 1 s cap elapses --
  preventing client-triggered `STREAM_CLOSED` resets from counting against the Rapid-Reset limit.

. *Emit end and `NO_ERROR` reset together.* Write `END_STREAM` followed immediately by `RST_STREAM
  (NO_ERROR)` (RFC 9113 §8.1) so other streams on the connection continue unaffected.

*Abortive upstream close on HTTP/1.1.* Resetting an HTTP/1.1 upstream request once body transfer has
begun closes that upstream connection with `SO_LINGER 0` (TCP `RST`), freeing the local ephemeral
port immediately instead of holding it in `TIME_WAIT` (if the reset fires before the first body chunk
is written, the clean connection returns to the pool; see
link:terminal-actions-and-protocols.adoc#_downstream_client[Downstream Client] and
link:../adr/0066-An_HTTP2_response_answered_while_its_request_body_is_open_is_ended_once_request_data_stops_arriving_or_a_time_cap_passes_and_its_stream_is_then_reset_with_NO_ERROR.adoc#abortive-upstream-close[ADR-0066]).

[[_http2_connection_window]]
[[_http2_connection_window_measurement]]
*Inbound HTTP/2 connection window.* An inbound request returns no flow-control window until its
dispatch obtains an upstream connection and subscribes to the body. The edge caps concurrent streams
per connection at 100 and sizes the connection window to `100 × 65,535` bytes (6,553,500 bytes), so
paused or queued streams cannot starve active uploads on the same connection (see
link:../adr/0060-Dispatch_sends_a_bodyless_method_no_body_and_frames_every_declared-length_body_by_exactly_that_length.adoc[ADR-0060]
for the benchmark comparison against a fixed 2 MiB window).

[[_http2_transport_bounds]]
*Per-connection HTTP/2 transport bounds* (link:../security-threat-model.adoc#gw-08[GW-08]):

* *Header block (`SETTINGS_MAX_HEADER_LIST_SIZE`).* Capped at 16 KiB across the whole decoded block
  (`CONTINUATION` frames included); exceeding it ends the connection with `GOAWAY`.

* *Rapid-Reset.* Pinned at 200 client-sent `RST_STREAM` frames per 30-second window (`GOAWAY
  ENHANCE_YOUR_CALM` on breach). Gateway-issued `NO_ERROR` resets do not count.

[[_http2_unread_upload_release]]
*Unread upload credit release.* An HTTP/2 upload refused `503` at admission returns its stream credit
to the connection window once ended (having never acquired an admission permit), and an admitted
upload reset by its client while awaiting a pooled upstream connection returns its stream credit and
releases its admission permit immediately
(link:../adr/0060-Dispatch_sends_a_bodyless_method_no_body_and_frames_every_declared-length_body_by_exactly_that_length.adoc#unread-upload-bodies[ADR-0060]).

== Request Body Framing and Timeouts

[[_dispatch_body_framing]]
*Dispatch body framing.* A `GET` or `HEAD` without a positive declared `Content-Length` is sent
upstream with no body; its first inbound body byte refuses the request with `400`
(`SECURITY_FILTER_VIOLATION`) before upstream response handover, or resets the HTTP/2 stream with
`CANCEL` (and closes HTTP/1.x) if it arrives after handover. Every other request declaring
`Content-Length` is framed by that exact byte count: a byte beyond it refuses the request (`400`
before handover, or stream reset after handover), and a body ending short of it resets the upstream
request (`INBOUND_BODY_ABORTED`). Requests without a declared length keep chunked/streamed framing.

[[_aborted_inbound_body]]
*Aborted inbound body.* When the inbound body stream fails after dispatch began (client disconnect
or broken chunk framing), the upstream request is reset and the gateway records
`INBOUND_BODY_ABORTED` (`400`, `INPUT_VALIDATION`). A body exceeding `max_body_bytes` remains
`CONTENT_TOO_LARGE` (`413`). Client-ended dispatches are never retried and do not trip the upstream
circuit breaker.

[[_request_body_idle_timeout]]
*Request-body idle timeout (10 s).* Once a proxied dispatch holds an upstream connection and is
reading the body, 10 s without a forwarded body byte resets the upstream request and answers `408`
(`REQUEST_BODY_TIMEOUT`;
link:../adr/0060-Dispatch_sends_a_bodyless_method_no_body_and_frames_every_declared-length_body_by_exactly_that_length.adoc#request-body-idle-timeout[ADR-0060]).
Waiting for a pooled upstream connection, upstream backpressure pauses, bodyless requests, and
`protocol: grpc` routes do not arm or advance this clock.

[[_request_body_deadline]]
*Request-body deadline (25 s).* A slow sender that drips chunks faster than every 10 s is bounded by
a fixed 25 s deadline from the start of the upstream attempt (including pool wait;
link:../adr/0060-Dispatch_sends_a_bodyless_method_no_body_and_frames_every_declared-length_body_by_exactly_that_length.adoc#request-body-deadline[ADR-0060]).
Expiry before the upstream response head answers `408` (`REQUEST_BODY_TIMEOUT`); expiry after the
response head preserves the upstream status and resets/closes the stream.

[[_grpc_stream_idle_bound]]
*gRPC stream-idle bound (5 min).* Because streaming RPCs legitimately pause between messages,
`protocol: grpc` routes use the 30 s upstream head timeout until response headers arrive and then a
5-minute bidirectional frame-idle timer (HTTP/2 `PING` excluded). Expiry resets the upstream request
and ends the client stream with trailers `grpc-status: 4` (`DEADLINE_EXCEEDED`) and `grpc-message:
stream-idle-timeout`
(link:../adr/0060-Dispatch_sends_a_bodyless_method_no_body_and_frames_every_declared-length_body_by_exactly_that_length.adoc#grpc-stream-idle-bound[ADR-0060]).

[[_per_source_detection]]
== Per-Source Detection (Enumeration Detection)

The gateway counts pre-trust reconnaissance rejections per source in a framework-free, per-instance
in-memory leaky-bucket substrate (thresholds apply per gateway instance and reset on restart) and
answers tripped sources according to `enumeration_detection`. The full substrate contract is in
link:../development/source-detection-substrate.adoc[Per-Source Detection Substrate -- Contract] and
the design decision in
link:../adr/0076-One_per-source_detection_substrate_counts_pre-trust_rejections_and_answers_a_tripped_source.adoc[ADR-0076].

image::../resources/diagrams/per-source-detection-and-threat.svg[Per-source key and rejection feed into the enumeration-detection tier and the threat-classification tier, align=center]

* *Keying and bounds.* Requests are keyed by `(source, host)`: client IPv4, IPv6 `/64` prefix, or
  `unknown` (honouring `forwarded.trusted_proxies`), paired with a declared `match.host` or `*`. The
  ledger tracks at most 65,536 keys, draining linearly at `threshold / window` per second and
  transitioning `CLEAR -> TRIPPED` (and `-> BLOCKED` when `action` is `block`) at most once per
  `CLEAR` period.

* *Feed.* Pre-trust rejections in the closed recon set add weight `1` (tagged by their true
  `EventType`, even when rendered as the uniform `404`). Post-trust rejections, upstream/boot
  events, aborted/timed-out bodies, `PRE_TRUST_INTERNAL_FAILURE`, asset routes, and browser-ambient
  fetches (`/favicon.ico`, `/robots.txt`, touch icons) are excluded.

[cols="1,4", options="header"]
|===
| Action | Effect on the wire

| `observe` (default)
| Records `SOURCE_TRIPPED`, increments `sheriff_source_trips_total{action}`, and logs a warning;
  responses are unchanged. `observe` is the default so shared NAT or untrusted-proxy addresses are
  not blocked without operator opt-in.

| `delay`
| Holds recon rejections of a tripped source until at least `admission + delay_millis` (or the
  uniform-`404` floor, whichever is later) on the held-answer permit sub-budget. Served requests are
  never delayed; requests exceeding the source's sub-budget share are answered `429` with
  `Retry-After` before admission.

| `block`
| Blocks a tripped source for `block_seconds`, answering `429` (`SOURCE_BLOCKED`) with
  `Retry-After` and the `rate-limiting` problem document on the event loop before admission or route
  selection.
|===

See link:../configuration.adoc#_enumeration_detection[Configuration -- `enumeration_detection`] and
link:../user/endpoint-routes.adoc#_enumeration_detection_operator_note[Endpoint Routes].

[[_threat_classification]]
== Per-Source Threat Classification

A second `observe`-only ledger sits beside enumeration detection, scoring weighted rejections before
and after the trust boundary and raising one structured ECS ALERT per episode when a source crosses
the `threat_classification` threshold
(link:../development/source-detection-substrate.adoc#_second_consumer[Substrate -- Second Consumer],
link:../adr/0078-Per-source_threat_classification_raises_one_ECS_alert_per_episode_from_its_own_ledger.adoc[ADR-0078]):

[cols="2,1,3", options="header"]
|===
| Category / Signal | Default weight | Rationale

| `input-validation` | `10` | Malformed or injection-shaped requests are the clearest probe signal (scored even on static/asset paths; `REQUEST_BODY_TIMEOUT` and `INBOUND_BODY_ABORTED` are excluded with fixed weight `0` so network stalls alone cannot raise an ALERT).
| `routing` | `1` | Crawlers or stale links also draw unrouted answers (`PRE_TRUST_INTERNAL_FAILURE` is excluded with weight `0`).
| `authentication` / `authorization` | `2` | Expired tokens behind a shared address stay below the drain rate.
| `recon_trip` (`SOURCE_TRIPPED`) | `50` | Each enumeration-detection trip feeds into the threat score.
| `upstream`, `rate-limiting`, `configuration` | fixed `0` | Not caller behaviour or boot-only.
|===

Threat classification never alters responses on the wire. Each trip increments
`sheriff_threat_alerts_total` and logs one ECS-formatted ALERT document
(link:observability-and-errors.adoc#_threat_alert_document[The Threat ALERT Document]). See
link:../configuration.adoc#_threat_classification[Configuration -- `threat_classification`] and
link:../user/endpoint-routes.adoc#_threat_classification_operator_note[Endpoint Routes].
