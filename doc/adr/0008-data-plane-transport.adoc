== Status

Accepted

== Decision

link:0006-body-streaming-vs-httpresult.adoc[ADR-0006] split the gateway's HTTP surface into two planes but did not name the client on each side. The configuration model also promises per-route `304` behaviour through `upstream_defaults.not_modified.enabled`, default enabled. The record settles the client per plane, what `not_modified` means, and where resilience lives.

=== The client per plane

*The data-plane transport is the Vert.x `HttpClient`.* Proxied request and response bodies are piped as streams with backpressure in both directions, directly between the edge and upstream Vert.x streams. One shared client and connection pool serves each distinct upstream target (`EgressClients`). gRPC needs HTTP trailers, WebSocket proxying needs the raw upgrade stream, and upstream HTTP/2 multiplexing is expected. All three are native to this client.

*The control plane stays on `cui-http`.* `HttpHandler`, `ResilientHttpAdapter`, `ETagAwareHttpAdapter` and `HttpResult<T>` serve the gateway's own small, bounded JSON calls, chiefly inside `token-sheriff-validation` and `token-sheriff-client`. On the data plane, `cui-http` supplies the inbound security pipelines and the forwarded-header resolver.

=== `not_modified` is end-to-end conditional pass-through

`not_modified.enabled` gates both halves of one exchange: the validators the client sends and the validators the upstream answers with. Forwarding a validator whose answer is then stripped makes the gateway ask a question it discards the answer to.

* *Enabled (the default).* The `304` validators `If-None-Match` and `If-Modified-Since` cross to the upstream. Upstream `304` responses and the validator response headers (`ETag`, `Last-Modified`) relay untouched. A `304` carries no body, so the exchange is streaming-compatible and needs no gateway state.
* *Disabled.* The gateway withholds those two validators from `GET` and `HEAD` and strips the response-direction `ETag` and `Last-Modified`, which forces full `200` exchanges. This is the hardening setting for upstreams whose ETags are inconsistent across nodes or leak inode or version information.

The validators are the gated tier of the gateway-understood protocol set, the names that cross without an operator entry (link:0037-The_gateway-owned_header_sets_are_enumerated_per_direction_and_bounded_by_knowledge.adoc[ADR-0037]). They reach the upstream under every link:0036-Forward_filtering_is_a_three-mode_policy_inside_an_authorised_route.adoc[forward mode], and the toggle decides whether that tier is admitted at all. With the toggle off, the gateway removes them from the client's headers of a `GET` or `HEAD` after the mode copy. A forward-all, negative-list or positive-list route therefore carries none of them upstream there, and no route forwards a validator whose answering `ETag` the response half strips.

Only `GET` and `HEAD` are answered `304` (RFC 9110 sections 13.1.2 and 13.1.3). On every other method the two cross in either state: `If-None-Match` is a write precondition answered `412`, and the origin ignores `If-Modified-Since`, which is defined only for `GET` and `HEAD`. `If-Match`, `If-Unmodified-Since` and `If-Range` always cross with the unconditional tier. `set_headers` is operator configuration and stays ungated.

=== Upstream identity headers do not reach the client

Every path that relays upstream response headers strips the upstream identity headers `Server` and `X-Powered-By`: the HTTP relay, the gRPC relay and the upstream asset action. A route keeps them with `keep_identity_headers: true`. link:0037-The_gateway-owned_header_sets_are_enumerated_per_direction_and_bounded_by_knowledge.adoc[ADR-0037] records the set and the opt-out.

=== Resilience

*Resilience uses SmallRye Fault Tolerance's programmatic API* (`quarkus-smallrye-fault-tolerance`), without annotations or CDI interception on the hot path. `UpstreamGuards` builds the guards at boot in the edge layer, and the dispatch call runs inside its guard. Breaker state transitions surface as WARN records and metrics.

The breaker is a fixed policy of the gateway, and one guard serves every route dialing the same upstream target with the same retry setting. link:0064-The_upstream_guard_is_fixed_in_the_gateway_and_a_route_declares_no_circuit_breaker_settings.adoc[ADR-0064] records that policy and removes the `upstream.circuit_breaker` block. ADR-0064 also lists the upstream timeout and retry keys that parse and act on nothing, and it leaves them open.

*Retry is stream-aware gateway policy.* The retry predicate retries a failed attempt only when the method is idempotent *and no attempt has taken up the one-shot request body*. Once an attempt has subscribed the body stream no retry follows, even when none of its bytes reached the upstream; a request without a body never subscribes it. No replay buffering in the initial release.

*The upstream timeout is the guard's.* The shared Vert.x client of an upstream target sets no connect or idle timeout of its own, so the Vert.x defaults apply: a 60 s connect timeout, which the guard's timeout ends first, and no idle timeout. Each upstream attempt is bounded by the guard's fixed 30 s SmallRye Fault Tolerance timeout, and a request the retry predicate allows is retried, each retry with its own 30 s timeout (link:0064-The_upstream_guard_is_fixed_in_the_gateway_and_a_route_declares_no_circuit_breaker_settings.adoc[ADR-0064]). The guarded call returns when the upstream's response headers arrive. The response body is streamed after it, so the 30 s bound is not a deadline on the response stream.

*No whole-second timeout rule applies.* That rule existed only because the `cui-http` `HttpHandler` builder takes whole seconds. The Vert.x client takes milliseconds.

== Alternatives rejected

=== `HttpHandler` and the `cui-http` adapters on the data plane

The Architecture "Downstream Client" section once said upstream calls use `HttpHandler`, with one pooled JDK `HttpClient` per upstream tuple.

*Rejected because* the `cui-http` client adapters are materializing by construction, a type-level fact. `ResilientHttpAdapter<T>` and `ETagAwareHttpAdapter<T>` implement `HttpAdapter<T>`, which returns `CompletableFuture<HttpResult<T>>`, a fully deserialized body. Neither can carry a streamed body, and neither was designed for a multi-user proxy path. The JDK `HttpClient` also exposes no HTTP trailers, and `grpc-status` lives there. `cui-http`'s `RetryConfig` presupposes a replayable materialized body, so it is unusable on the data plane.

=== Gateway-side response caching, including ETag revalidation from cache

The ETag adapter on the data plane would serve a cached body on an upstream `304`.

*Rejected because* a shared response cache keyed by anything less than the full authorization context is a cross-user data leak. Keyed by the full context, it is memory-unbounded per user. Either way it materializes proxied bodies and adds a cache-poisoning surface. The adapter also uses a `cacheKeyHeaderFilter` designed to exclude headers such as `Authorization` from the cache key. `ETagAwareHttpAdapter` is control-plane only, permanently.

=== The validators as part of the route's effective `forward.headers_allow`

*Rejected because* `headers_allow` is one of three forward modes, so that mechanism would not reach the other two (link:0036-Forward_filtering_is_a_three-mode_policy_inside_an_authorised_route.adoc[ADR-0036]).

=== Gate all five RFC 9110 section 13 validators on the toggle

*Rejected because* only `If-None-Match` and `If-Modified-Since` are answered by a `304`. Withholding the other three would change the request rather than discard an answer. Without `If-Match` or `If-Unmodified-Since` a conditional write becomes unconditional, a lost update. Without `If-Range` a `Range` request is answered with a `206` slice of a newer representation instead of the full `200`.

=== Name the validators in `headers_deny` to withhold them under a permissive mode

*Rejected because* the two halves are one decision in every mode, so the toggle carries it. link:0037-The_gateway-owned_header_sets_are_enumerated_per_direction_and_bounded_by_knowledge.adoc[ADR-0037] records why narrowing forward-all for this class of client headers is deliberate.

=== Fault-tolerance annotations on the hot path

*Not adopted.* The decision applies the programmatic API "without annotations or CDI interception on the hot path" and records no further reason.

=== A hand-rolled breaker

*Not adopted.* The decision names the same policy as a small gateway-side component only as the fallback if the shipped SmallRye surface lacked a needed hook. It records no other reason against it.

=== Replay buffering for retry

*Not adopted.* The decision says only "No replay buffering in the initial release" and records no further reason.

== Consequences

=== Properties of the design

* gRPC and WebSocket get trailers, upgrade streams and HTTP/2 natively, with no transport swap.
* The breaker has a Quarkus-supported home.
* `HttpHandler` is nearly invisible in API Sheriff's own code, because it lives behind the token-sheriff libraries. `cui-http` stays the standard for inbound security filtering, forwarded-header resolution and control-plane calls, and is not generalized to opaque byte relay.

=== Accepted costs

* `quarkus-smallrye-fault-tolerance` is one more Quarkus extension dependency, with its version from the Quarkus BOM.
* The exact SmallRye programmatic surface (`Guard`, `TypedGuard`, `CircuitBreakerMaintenance` state callbacks) is used as the shipped extension version provides it.
