== Status

Accepted

== Decision

`forwarded.trusted_proxies` lists the machines granted the right to assert client identity. Under link:0003-forwarded-headers.adoc[ADR-0003]'s trust model, a request whose immediate TCP peer lies inside a trusted range has its forwarded chain believed. Every host inside a trusted range that can reach the gateway directly can use that right to spoof the client address. The breadth of a range is therefore the security property.

The boot already refuses a malformed entry, and it refuses a set of ranges that trusts everyone. The check merges the ranges of one family, so complementary halves such as `0.0.0.0/1` plus `128.0.0.0/1` are caught like a single `0.0.0.0/0`. The decision concerns every range between those two refusals, and three facts shape it:

* *The correct answer is itself a broad range.* A container bridge, a cloud VPC and an RFC 1918 site block are each a considered trust decision when the operator provisioned that network for the proxy tier. A guard that fires on a routine configuration teaches operators to read past it.
* *The wrong answer is usually a block pasted in whole.* The realistic mistake is `172.16.0.0/12` or `10.0.0.0/8`, an entire private allocation copied from a reference. A threshold at `/8` would stay silent for exactly those ranges.
* *The value often arrives from the environment, where no review sees it.* Placeholder substitution happens before validation, so the rule receives the substituted value and nothing else.

*The decision:* the boot refuses a `trusted_proxies` entry only when the ranges of its family cover the whole address space. Any single entry spanning more than one operator-provisioned network, broader than an IPv4 `/16` or an IPv6 `/48`, boots with the `ApiSheriff-102` boot WARN. A range supplied through an environment variable is treated exactly like a literal one. `EdgeRules.validateForwardedTrust` realises this.

=== One principle behind both thresholds

The two thresholds encode one rule: warn when a single entry spans more than one network an operator deliberately provisioned.

* *IPv4: warn below `/16`.* `/16` is the widest single IPv4 network in routine use: the largest VPC a major cloud provider allocates, the shape of a container runtime's default bridge (`172.17.0.0/16`), the RFC 1918 `192.168.0.0/16` block. The boot WARN starts one bit broader, at `/15`, and catches `172.16.0.0/12` and `10.0.0.0/8`.
* *IPv6: warn below `/48`.* `/48` is the canonical IPv6 site allocation and the direct analogue, with `/64` the standard single subnet inside it.

=== The un-warned residual is chosen, not safe

An IPv4 `/16`, 65,536 addresses, and an IPv6 `/48` boot with no signal. That is a real exposure. It stays un-warned because it is a legible exposure an operator chose, a range whose size matches the network they provisioned, not because it is harmless. Wherever the threshold appears, the residual is recorded as an accepted exposure with a stated size, so an operator who needs a tighter trust boundary knows to write one.

=== Trust-all is the only breadth refusal

Every narrower range still has a legitimate reading: some deployment provisions that network for its proxy tier. A range set covering the entire family has none. It makes every client on the internet a trusted proxy, so forwarded headers become attacker-controlled input with no boundary at all. That configuration has no coherent meaning, and the boot refuses it.

=== An environment-sourced range meets no stricter refusal

Two reasons each suffice:

* *The distinction is not expressible where the rule runs.* A range written literally and a range substituted from the environment arrive as the same string, and nothing in the bound configuration records which one it was.
* *A source-blind stricter refusal breaks correct deployments and catches nothing new.* It would refuse legitimate pod-network trust, because an orchestrator's pod network is commonly a `10.0.0.0/8`. Every range it would stop already produces a signal.

The residual applies unchanged: an environment-supplied IPv4 `/16` or IPv6 `/48` boots with no signal at all, the same chosen exposure with no review behind it.

=== Matched controls prove the thresholds

A parameterised test in `EdgeRulesTest` holds the claim. Each family carries a range past the boundary, which must warn, and a range exactly at it, which must not. The IPv4 set also carries a very broad `/4` that must warn and boot, so the far end of the band is never mistaken for the trust-all refusal. The test asserts the boot WARN by its identifier and the offending range. Reverting either constant alone turns at least one row red.

== Alternatives rejected

=== Warn at anything broader than an IPv4 `/24` or an IPv6 `/64`

A trust list would be treated as a set of individual peers, and the boot WARN would fire as soon as an entry spans more than a single subnet.

*Rejected because* it fires on the correct configuration. Trusting a provisioned proxy network is the routine case, and those are `/16`-shaped. A threshold at `/24` would warn on most deployments configured exactly right, the guard-trained-into-noise failure the principle exists to avoid. The argument that a trust list is not a routing prefix is the reason the threshold is anchored to provisioned networks at all. It does not make a single subnet the right anchor.

=== An unconditional INFO naming the effective address count

The boot would report every trusted range with its address count.

*Rejected because* it moves the judgement to every reader of every boot log. An unconditional line carries the same weight for a correct `/32` proxy host and a pasted `/8`. The boot WARN already names the range and its prefix length for the cases that cross the principle.

=== A second, stricter refusal threshold

The boot WARN stays and a refusal is added at some wider prefix, for every range or only for ranges from the environment.

*Rejected because* the environment-only variant is not expressible, and the source-blind variant refuses legitimate pod-network trust while stopping no range that is not already surfaced. A second threshold would also create a band in which a range warns and boots and a wider band in which the same kind of mistake fails the deployment: two outcomes for one principle.

A breadth guard earns its place by staying silent on the configuration an operator should write and speaking on the one they should not. Each rejected option either speaks on correct configurations or turns a visible, sometimes-legitimate posture into a refusal it cannot justify.

== Consequences

=== Properties of the design

* A whole private allocation pasted in produces a boot WARN naming the range, also when the value came from an environment no review saw.
* The routine configuration stays silent, so the boot WARN keeps its meaning.
* The only refusal is the one configuration with no legitimate reading.
* The literal and environment paths behave identically.
* The thresholds rest on a stated principle and on controls on both sides of each boundary, so drift breaks a test.

=== Accepted costs

* *A `/16` or `/48` is trusted in full with no signal.* An operator who meant to trust one proxy host and wrote the whole network gets no boot WARN.
* *An environment-supplied range has one signal, and it is a log line.* A deployment that ships an overly broad range boots and serves traffic. The boot WARN records the exposure and does not stop it.
* *The principle is a judgement about typical networks.* A deployment whose single provisioned network is genuinely broader than `/16` gets a boot WARN on a correct configuration and cannot acknowledge it short of narrowing the range.

=== Risks

* *The residual is read as a safe default.* Mitigated by recording the `/16` and `/48` residual as an accepted exposure wherever the threshold is documented: the validator's Javadoc, the operator configuration reference, the security threat model and here.
* *The boot WARN is trained into noise.* Mitigated by anchoring the threshold to the widest single provisioned network and by the at-the-boundary rows that go red if a routine range starts warning.
* *An environment-supplied range is assumed to have been reviewed.* A `gateway.yaml` reads identically whether its range is literal or substituted. Mitigated by stating in the validator's Javadoc and the operator documentation that the boot WARN is then the only signal.
