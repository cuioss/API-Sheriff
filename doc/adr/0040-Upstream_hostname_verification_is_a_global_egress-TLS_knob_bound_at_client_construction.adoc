== Status

Accepted

== Decision

A gateway that terminates TLS on the way out must be told which upstream certificates it accepts.
Two independent questions hide in that sentence:

* *Does the certificate chain to an anchor the gateway trusts?* This is certificate-chain validation.
  The trust anchors the client holds answer it.
* *Does the certificate name the host the gateway dialled?* This is hostname verification. A
  comparison of the dialled name against the certificate's subject alternative names answers it.

Both are on by default and both stay on wherever a deployment can satisfy them. But a gateway often
sits next to upstreams that satisfy the first and not the second: an internal service reached by a
container name, a cluster DNS name, or an address its certificate was never issued for. Conflating
the two questions is the failure this record prevents.

Three facts about the runtime fix the shape of the answer.

* *The two questions are implemented separately.* On Vert.x, `setVerifyHost(false)` becomes an empty
  `hostnameVerificationAlgorithm`. The only effect is that the SSL engine is configured without
  `setEndpointIdentificationAlgorithm`. Chain trust uses other fields, `trustAll` and `trustOptions`,
  and the hostname flag never touches the `X509TrustManager`. Relaxing one cannot relax the other.
* *The setting is fixed at client construction.* The per-request option types the dispatch path and
  the WebSocket relay build declare no hostname-verification field. Only the HTTP client options and
  the WebSocket client options carry it, and both are consumed once, when the client is built. A
  surface scoped narrower than a client is a surface the runtime cannot honour.
* *One client is edge-wide.* Proxy-path egress leaves through three Vert.x construction sites: the
  default HTTP client, the forced-HTTP/2 client that gRPC routes require, and one WebSocket client for
  the whole edge. A setting that reaches all three cannot be scoped per route.

The record settles where egress TLS posture lives, how the proxy path binds it, and the rule every
egress leg follows.

*Egress TLS posture lives in one global `egress_tls` block. For the proxy path,
`upstream_verify_hostname` and `upstream_tls_profile` bind once at each of the three Vert.x
construction sites, and at those only. The hostname key relaxes hostname verification only; the trust
profile is the answer to a chain-trust problem, and the two ship together. Every egress leg follows the
egress-TLS principle below.*

This applies the neutral-name rule of
link:0011-gatewayyaml_exposes_JWKS_trust_and_egress_as_neutral_names_bound_by_the_deployment.adoc[ADR-0011]
to the outbound direction, as
link:0025-The_whole_server-TLS_surface_is_neutral_in_gatewayyaml_and_bound_by_exactly_two_seams.adoc[ADR-0025]
applies it to the inbound one.

[[egress-tls-principle]]
=== The egress-TLS principle

Every egress leg the gateway dials over TLS follows four rules. This record states them once;
link:0041-The_JWKS_hostname-verification_knob_is_the_librarys_own_passthrough_and_its_sslContext_collision_is_refused_at_boot.adoc[ADR-0041]
applies them to the JWKS back channel and
link:0045-The_BFF_OIDC_back-channel_posture_is_pinned_through_the_librarys_own_passthrough_under_peer_egress-TLS_keys.adoc[ADR-0045]
to the BFF back channel.

. *A hostname relaxation never relaxes chain trust.* Each leg's hostname key turns off the name
  comparison and nothing else. An untrusted chain is still refused with the key off. Each leg also
  carries a separate trust answer, so the relaxation is never the only lever an operator with a
  private-CA peer can reach. A PKIX path-building failure is not a name mismatch; a gateway that
  ships only the relaxation builds an incentive to misuse it.
. *A library's own passthrough is preferred over a locally built trust manager.* Where the client
  library that owns the connection offers the posture setting, the gateway passes its value through.
  The gateway writes no delegating `X509TrustManager` of its own. Such code fails invisibly in review,
  because a forwarded overload that validates nothing looks correct.
. *The one combination a library refuses is refused at boot first.* When the library refuses a
  combination of two gateway keys, the gateway checks the combination itself before it builds the
  client. The boot refusal (`CONFIG_INVALID`) names the gateway's own keys, never the library's
  builder methods. Diagnostics stay concrete and in the operator's vocabulary.
. *Every TLS-client construction site declares its posture explicitly.* The site passes the resolved
  value on the default path as well as on the relaxed one. A site that sets nothing follows the
  library's default, and an upstream default change would then move the gateway's posture silently,
  which
  link:0022-Upstream_security-hardening_default_changes_are_adopted_and_documented_never_locally_reverted.adoc[ADR-0022]
  forbids. `EgressTlsPostureArchTest` holds the rule for every construction site, named or not.

Three surface rules go with the principle:

* *One block, a peer key pair per leg.* Every key carries the prefix of the leg it governs:
  `upstream_`, `jwks_`, `oidc_`. A bare `verify_hostname` beside a prefixed one would read as "the
  general rule plus an exception", which is the wrong model. `upstream_tls_profile` is not
  `tls_profile`, because a per-issuer `jwks.tls_profile` already exists and an unprefixed name would
  invite the reading that it covers the JWKS leg too.
* *An omitted flag resolves to `true`.* A boolean bound by the configuration mapper's ordinary rules is
  `false` when absent. A block that names only a trust profile would then silently turn hostname
  verification off. `ConfigLoader`'s `EgressTlsDeserializer` resolves each absent flag to `true` and
  each absent profile to "none", so an omitted block and a partial block both keep verification on.
* *A named profile replaces the anchors; it does not add to them.* An operator who names a profile
  holding only a private CA stops trusting public certificate authorities on that leg.

A relaxed posture the gateway can honour is a boot WARN, not a boot refusal. A disabled hostname check
and a named trust profile are legitimate deployments that must be visible in the log, like the
broad-trusted-proxy and plain-HTTP-management warnings. A posture the gateway cannot honour is a boot
refusal instead: the combination a leg's library refuses, under rule (3), and a trust profile the
resolver fails closed on, below.

=== The proxy path binds at the three Vert.x construction sites

`EgressClients` binds `upstream_verify_hostname` and `upstream_tls_profile` at the default HTTP client,
the forced-HTTP/2 client and the edge-wide WebSocket client. WebSocket relays do not dial through the
route's HTTP client. Left unbound, every `wss://` relay would keep default verification while the
operator believed the key applied gateway-wide. A key bound at two of three sites is the
partial-binding defect
link:0026-A_security_bound_declared_at_one_inbound-validation_stage_is_re-asserted_at_every_later_stage_that_re-validates_the_same_input.adoc[ADR-0026]
prevents on the inbound side, and it fails in the dangerous direction.

The per-request option types take no edit. They declare no hostname-verification field, so no
per-request override exists to expose.

The key cannot affect SNI passthrough. A connection relayed at L4 by the front listener of
link:0017-Accept-time_SNI_split_at_a_dedicated_front_listener_passthrough_relays_opaquely_at_L4_everything_else_terminates_internally.adoc[ADR-0017]
is never decrypted, and the gateway never inspects its certificate.

*The trust profile sits on ADR-0011's seam.* `upstream_tls_profile` names a logical trust profile and
carries no material. `EgressTrustProfileResolver` maps the name onto the anchors the runtime holds and
returns the runtime's own `TrustOptions`, which the Vert.x options consume directly. The resolver fails
closed:

* an omitted key is never resolved, and the clients keep the JVM default trust store;
* a name the deployment does not bind is a boot refusal, never a fallback to default trust;
* a profile that trusts everything is refused, and refused ahead of the anchor-free check, because it
  carries trust options and would otherwise pass that check;
* a profile with no trust material is refused, because it would verify against the default store
  instead of the anchors the name promises.

*The asset-origin fetch is not governed.* An asset route with an `https` origin is fetched by
`UpstreamAssetSource.httpFetcher` on a JDK `java.net.http.HttpClient`. That client carries neither
Vert.x setting; binding the block there needs `SSLParameters` plumbing, a different seam. The limit
cuts in a known direction. Hostname verification is fail-safe there: the JDK client always verifies.
Trust fails closed: a private-CA asset origin fails, and its anchors go into the JVM trust store.

The full set of TLS-terminating egress legs, and which key governs each, is re-derived from source in
link:../user/tls-edge.adoc#_egress_tls[TLS Edge -- Egress TLS]. `EgressTlsConfig` carries the same
enumeration in its documentation. Neither list holds the set closed; the fitness function does.

*The scope claim is proven by a handshake.* The integration stack runs a matched pair of gateway
instances that differ in exactly `upstream_verify_hostname`, plus a third dial that reaches an untrusted
upstream with the key off and must still fail. That third dial would refute the scope claim if the two
mechanisms were coupled. A wiring guard asserts that the pair's documents differ in that one key only.

== Alternatives rejected

*Put the key in the existing `tls` block.* This is the smallest change. Rejected because `tls` is the
server-TLS surface. Its keys are inbound policy (protocol floor, cipher allowlist, ALPN, SNI
passthrough, inbound mTLS), and ADR-0025 classifies exactly that surface with a per-key verdict table.
An egress key there would merge two opposite traffic directions into one block and falsify that table.

*Put the key on the per-upstream or `upstream_defaults` surface.* This is the more precise surface and
was seriously considered. Rejected on two grounds. It cannot be bound: the edge-wide WebSocket client
is one instance, so a per-route value means nothing there, and honouring it would force one WebSocket
client per route. And it is a silent-reset trap: `upstream_defaults` is declarable at gateway and
endpoint scope, and an endpoint declaration replaces the gateway one wholesale. An endpoint that
declares `upstream_defaults` for retry alone would silently reset a security key it never mentions.

*Expose a per-request hostname-verification override.* Each dial would decide, which gives per-route
precision without a per-route block. Rejected because there is nothing to call. The per-request option
types declare no such field, and the setting is consumed when the client is built.

*Ship `upstream_verify_hostname` alone and defer the trust profile.* Deliver the narrower change first.
Rejected because it is actively harmful. Without a trust key, the hostname key is the only lever an
operator with a private-CA upstream can reach. It does not solve the problem, and reaching for it
disables a control that was working.

*Name `jwks_verify_hostname` only once it has a reader.* Declare only the key this record binds.
Rejected because the outbound vocabulary is defined once, across every egress leg. A key named later
risks a different name, and the keys' peerhood, which the prefixes express, is visible only when the
peers exist together. The cost was one declared key with no reader until ADR-0041 bound it; the schema
description, the model documentation and this record said so while it lasted.

*Declare a reserved key in the schema only, without a model field.* Rejected because it does not work
here. The schema refuses unknown properties and the binder refuses unknown fields, so a schema-only key
validates and then fails to bind. The gateway would advertise a document as valid and refuse to boot on
it. A name is declared in both places or in neither.

The rejected options fail in one of two directions. A relaxation earns its place by being narrow and by
shipping with the control that makes it unnecessary; each option above either widens it or ships it
without that control.

== Consequences

*Positive.*

* An operator whose upstream certificate does not name the dialled address has a narrow, supported
  answer. Chain trust stays untouched.
* An operator whose upstream presents a private-CA certificate has a different answer, so the hostname
  key is not misused as one.
* The key reaches every proxy-path egress dial, WebSocket relays included.
* A partial block cannot silently disable a security control.
* Neither relaxed posture is silent: `EgressClients` logs a boot WARN for a disabled hostname check and
  for a named trust profile.
* Trust material stays out of the document operators commit. The same `gateway.yaml` moves across
  environments that bind one profile name to different anchors.
* Every egress leg follows one stated principle, so a new leg's record applies it instead of
  re-deriving it.

*Negative.*

* The setting is global with no per-route override. A gateway with one name-mismatched upstream relaxes
  hostname verification for all proxy-path egress or not at all. The runtime fixes this, not a
  simplification.
* A private-CA upstream needs two edits: the profile name in `gateway.yaml` and its binding in the
  deployment. That indirection is the price of portability, the same one ADR-0011 pays.
* A named profile's anchors are exclusive, so naming one is a wider act than it looks.
* A named but unbound profile is a hard boot refusal, so every instance that names a profile must also
  load its binding.
* "Global" is true of the three Vert.x clients, not of every `https` connection the gateway opens.

*Accepted failure modes.*

* *The relaxation is read as a general TLS disable.* "Verification off" is broader than what the key
  does. The schema description, the model documentation, the operator pages and the boot WARN state the
  hostname-only scope, and the untrusted-upstream dial proves it.
* *"Global" is read as covering the asset-origin fetch.* The operator pages and the boot WARN state the
  limit and its fail-safe and fail-closed directions.
* *The fitness function reads per class.* A class that pins one client of a family and builds a second
  of the same family without its posture is not caught. Every class builds at most one client per family
  today. The rule also reads calls, not values: `setVerifyHost(false)` is a posture call.

*Constraints on later change.*

* A new egress leg follows the principle above, and its record links here instead of restating it.
* The three per-client assertions stay beside the fitness function, because the function cannot tell
  which value was bound.
* Bringing the asset-origin fetch under the block is a separate decision.
