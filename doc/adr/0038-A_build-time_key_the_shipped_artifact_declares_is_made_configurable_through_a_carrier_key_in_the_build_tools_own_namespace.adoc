= ADR-0038: A build-time key the shipped artifact declares is made configurable through a carrier key in the build tool's own namespace
:toc: left
:toclevels: 2
:sectnums:

// adr-metadata
// summary: A build-time configuration key that the shipped artifact declares is made build-configurable by declaring it as an EXPRESSION over a carrier key in the build tool's own namespace, never by having the build seam set the framework key directly -- because the artifact's own declaration outranks the forwarded build property and would silently override it, and because the forwarding path keeps only prefixed names.

== Status

Accepted

== Decision

=== The question

The shipped artifact declares its own configuration explicitly, so a reader of the packaged file sees what the artifact asks for. Some declared keys are *build-time fixed*: augmentation resolves them once and bakes them into the executable, and no environment variable moves them afterwards. Making such a key operator-configurable therefore happens at build time, through the build tool.

Three properties make that dangerous:

* *The artifact's own declaration outranks the build tool.* A property forwarded from the build into augmentation and the packaged configuration file are two sources for one key, and the packaged file has the higher ordinal. A build seam that sets the framework key directly is overridden by the declaration it exists to change.
* *The forwarding path filters by namespace.* The build plugin forwards only names in its own namespace. It drops an operator-facing property named in the project's vocabulary before that property reaches the configuration. The seam therefore has two independent ways to be inert, and only one is about ordinals.
* *Both failures are invisible.* A default build produces identical output whether the seam works or not. Nothing at runtime differs, and no test of the default path changes colour. Only someone who exercises the seam and inspects the augmented output finds it inert.

This record settles the shape of the seam, so that it acts, the artifact keeps its explicit declaration, and a later reader cannot silently disable it.

*The decision:* a build-time configuration key the shipped artifact declares is made configurable by declaring it as an expression over a carrier key in the build tool's own namespace, never by having the build seam set the framework key directly.

=== The declaration becomes a delegation

The packaged file still declares the key and owns its default, but as an expression with an inline default: `quarkus.http.root-path=${quarkus.sheriff-context-path:/}` and `quarkus.management.root-path=${quarkus.sheriff-mgmt-path:/q}`. The higher-ordinal declaration still wins, and what it wins with is a reference. The carrier resolves from the forwarded build property when the seam is active, and from the inline default otherwise. The ordinal contest is not fought but inverted. A winning literal ends the resolution, while a winning expression re-opens it against a source the project controls.

=== The carrier lives in the build tool's namespace

The build profile maps the operator-facing project property (`sheriff.context-path`, `sheriff.management-context-path`) onto a carrier name carrying the framework prefix, because that prefix survives the forwarding filter. The operator-facing vocabulary stays the project's own. The prefix is an implementation detail of the transport.

=== The carrier is a pure carrier

The carrier never gets a configuration mapping, is never documented as a settable key and is never claimed as a configuration surface. It exists only to be referenced by the expression. A construct added to make it look official would assert a surface that does not exist.

=== The shape is asserted

A default build behaves identically either way, so prose cannot defend the shape. Two guards do. `ContextPathDefaultsTest` reads the raw declared value out of the packaged artifact and asserts the expression. `BuildParentContractTest` fails when a declaration is not an expression over its carrier. Flattening either declaration to a literal turns both red. The state they protect is the shape of the declaration, not any observable behaviour, so only an assertion over the declaration detects its loss.

The inline default and the assertion are also the two conditions for reusing the technique on another key. The default keeps the artifact stating its shipped value, and the assertion catches a delegation flattened back to a literal.

== Alternatives rejected

=== Have the build seam set the framework key directly

The obvious shape: a profile that sets the framework key from the operator's property.

*Rejected because* it cannot work. The artifact's own declaration is the higher-ordinal source and overrides it. The failure is silent: the build succeeds and the artifact is unchanged.

=== Drop the declaration from the shipped artifact and let the build seam be the sole source

This removes the conflict by removing one of the two sources.

*Rejected because* the effective default then comes from the framework's own annotation default rather than from the artifact, which is the implicitness the explicit-declaration posture exists to remove. It also deletes the packaged-declaration assertions, the only place the shipped configuration surface is pinned.

=== Declare the expression with an empty inline default

This is cosmetically tidier, because it avoids the normalisation artefact under the accepted costs.

*Rejected for the same reason as the previous option.* The packaged artifact then records the empty string, and the effective default returns to the framework. That trades an explicit declaration for a cosmetic improvement in a test read-back.

=== Document the framework key as the operator-facing knob

Tell operators to set the framework property directly and drop the project-owned name.

*Rejected because* it surrenders the vocabulary boundary: the configurable surface would be whatever the framework calls things this release. It also makes a downstream single-property promise impossible, because a consumer would have to know and restate framework keys.

=== Move the knob into the runtime configuration language

*Rejected by construction, not on preference.* A build-time key is resolved before any runtime source is read, so a runtime source cannot project it. The same classification boundary keeps build-time knobs out of the neutral configuration vocabulary.

=== A container build argument

*Rejected because* the image build copies a pre-built executable and therefore runs strictly after augmentation. It carries no build-time configuration and cannot reach the key.

The rejected options fall into two classes. One lets a source that cannot win try to win anyway. The other buys a working seam by surrendering the artifact's explicit declaration. The chosen shape alone keeps both the declaration and the seam.

== Consequences

=== Properties of the design

* The seam acts through a property in the project's own vocabulary, so the operator-facing knob is a surface the project owns and can keep stable across framework changes.
* An unconfigured build still ships the default from the artifact's own file.
* Because the mechanism is ordinal inversion, a lower-ordinal source can drive the key. A downstream build that inherits a parent model supplies the carrier through ordinary property inheritance, which makes a one-property customisation promise achievable.
* The two invisible failure modes become build failures, because the guards assert the declared form.

=== Accepted costs

* The carrier names occupy the framework's namespace without being owned by it. They get no validation, documentation, tooling completion or guarantee that a typo is reported. A test holds the coupling between the declaration and the carrier.
* The packaged file no longer shows the effective value at a glance. Reading a declaration means following one indirection to the inline default.
* Framework normalisation of the raw declared string can produce a cosmetically different read-back of `quarkus.http.root-path` in a test harness that reads the key through the configuration API. The augmentation path expands before it normalises, so the packaged artifact and the running router are unaffected. The divergence stays in the harness and is asserted as observed.

=== Risks

* A later reader will want to simplify this shape. The literal form reads more obviously, a default build is unchanged and nothing at runtime protests. Only the two guards turn that edit into a red build, so removing them as redundant with the prose removes the only defence.
* The absence of an unrecognized-key report for the carriers is measured, not guaranteed. A future framework release that reports them is the accepted cost materialising, not a regression. The response is to accept the noise, not to add a construct whose only purpose is to silence it.
