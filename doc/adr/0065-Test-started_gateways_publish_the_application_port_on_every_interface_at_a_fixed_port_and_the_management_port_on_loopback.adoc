== Status

Accepted

== Context

Some integration suites cannot run against a service of the Compose stack. They need a gateway whose
readiness is `DOWN` by design, a gateway they restart under a live session, a gateway over a
configuration no Compose instance may load, or a stub or proxy standing in for the identity provider.
Those suites start containers of their own through one shared harness and remove them on every exit
path.

Each such gateway publishes two ports to the host: the application listener the test drives, and the
management interface whose readiness the test polls. Two constraints decide how.

The application port of a BFF gateway has to be known before the container exists. The descriptor
names the gateway's own origin -- the redirect URI and the post-login targets are built from it --
and it is read at boot, so a port docker assigns after the container starts cannot be written into
it. That port is therefore a fixed host port, allocated above the range the Compose stack publishes.

The second constraint is a defect of the container runtime on the development host. On Rancher
Desktop under WSL 2 a host port number can be left dead: a container that publishes it afterwards
starts normally, and a connection to the number is accepted and reset a few seconds later. A number
goes dead when a container is removed that either carried two publications on a loopback address, or
carried one loopback publication while attached to two networks. A publication on every interface
counts towards neither shape, and a number once dead stays dead however it is published afterwards.
A harness that removes containers on every test run turns either shape into a steadily growing set
of unusable port numbers.

The question this decision settles is where a test-started container's ports are published, and on
how many networks it may sit, so that the harness never produces either shape.

== Decision

*A gateway a test starts publishes its application listener on every interface at a fixed host port,
and its management interface on loopback at a fixed host port derived from the first. It joins
exactly one network.*

* The application listener is published as `<port>:8443`, on every interface, at a fixed port taken
  from the test-started range. This is the form the Compose stack publishes its own gateway ports in.
* The management interface is published as `127.0.0.1:<port + 9000>:9000`, on loopback, at the
  application port plus 9000 -- `10464` pairs with `19464`. Distinct application ports therefore give
  distinct management ports, and the one allocation covers both. The suite reads the published port
  back before it polls readiness.
* The container joins one network: the Compose network, or a dedicated network of the rig it belongs
  to.
* A container that must be attached to a second network -- a proxy that dials the Compose Keycloak
  from a rig's own network, or a late identity provider -- publishes no port at all.
* A stub that is not a gateway publishes at most its admin port, on loopback, and joins one network.

The harness enforces the rule before any docker call: `OneOffGatewayContainers.assertLeavesNoDeadHostPort`
refuses both dead-port shapes in every argument builder, and `OneOffGatewayContainersTest` holds the
rule without a docker daemon, including a scan of the integration-test sources that confines publish
options and network attachments to a named set of files. Because readiness on the management port says
nothing about the application port, each suite makes one request to the application port once the
gateway answers, so a dead number fails the start with a message naming it.

The fixed ports, the containers that take them and the port numbers retired by the defect are listed
in the integration-test topology note, whose table is read by `OneOffGatewayContainersTest` and
compared with the ports the sources assign and, for the management column, with the port the harness
derives.

*Amendment -- the management port is fixed.* The decision first published the management interface
as `127.0.0.1::9000`, on a loopback port docker assigned. A full integration run on the Rancher
Desktop/WSL 2 host then failed `BffReservedPathPrecedenceIT` at its start: the gateway's log reported
the management interface listening, and every readiness request to the assigned loopback port was
refused for the whole 90-second budget, while every fixed application port of the run answered and
the suite was green on its own. The assigned number came from the host's ephemeral range, which the
earlier containers of the run had been drawing from in sequence. The management port was moved to a
fixed number for that reason. The shape the dead-port rule governs is unchanged: one loopback
publication on one network.

== Consequences

=== Positive

* Removing a test-started container leaves no host port number dead, so the suites can be run
  repeatedly on the development host without exhausting their fixed ports.
* The rule is a property of the harness, checked before any container starts, rather than a
  convention each suite has to remember.
* A test gateway's application port is published the way a Compose gateway's is, so a suite reaches
  both kinds of gateway the same way.

=== Negative

* While a test runs, its gateway's application listener is reachable from the network the host is
  on, at a fixed port, as the Compose gateways are. This is accepted: the gateway carries only
  committed test material -- descriptors, certificates and signing keys that exist for the tests and
  protect nothing -- and it lives only as long as the test that started it.
* A container attached to two networks cannot be reached from the host at all. A rig that needs to
  observe such a container does so from a one-shot container on its own network.

=== Risks

* The dead-port defect was observed on one host and one runtime. Whether restarting the runtime clears
  a dead number, and whether another runtime behaves the same way, was not measured; the rule may be
  stricter than another host needs.
* A fixed port in the test-started range can collide with a Compose instance added later. The
  topology note's table is the allocator for this range, and the Compose file is the allocator for
  its own. The derived management ports (`19459` and up) lie above the Compose stack's management
  ports (`19000` to `19011`); a Compose instance published there would collide in the same way.
* Which property of the docker-assigned number refused the connection was not established. Fixing
  the number removes the assignment from the path; it does not explain the refusal.

== Alternatives Considered

*Publishing both ports on loopback.* Binding every test-started port to `127.0.0.1` would keep a test
gateway off the host's network entirely. It is exactly the first dead-port shape: every container
removed would leave both of its port numbers dead, and the suites that ran on such ports lost them for
good. Rejected because the harness would consume host port numbers faster than any allocation
scheme could hand them out, and a dead number fails a run in a way that looks like a gateway defect.

*Running these gateways as Compose instances.* A Compose service is reached the same way and needs
no harness of its own. It cannot carry what these gateways exist for. A gateway that is `DOWN` by
design would be refused by the stack's readiness gate, which asserts every instance `UP` before the
suite runs. A gateway restarted under a live session takes every other suite's sessions on that
instance with it. A gateway over a configuration of its own -- a route under an anchor no shared
document declares -- would force that anchor into every gateway document, or its endpoint file into
the directory every instance loads. Rejected because each of these properties belongs to one test
and has to end with it.

*Publishing the application port on a port docker assigns.* Letting docker pick the application port
as well would leave no fixed numbers to allocate and none to retire. A BFF's descriptor names its own
origin and is read at boot, so the port must be known before the container is created. Rejected for
the BFF gateways; the bearer-only gateways keep the same fixed form so that every test-started
gateway publishes alike.

*Publishing the management port on a loopback port docker assigns.* This was the decision's first
form: the management port needs no fixed number, since nothing reads it before the container exists,
and an assigned number needs no allocation. Rejected after the run recorded in the amendment above,
in which the assigned number refused every connection to a gateway that was up. A number derived
from the application port costs no allocation of its own.
