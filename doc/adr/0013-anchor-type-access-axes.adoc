== Status

Accepted

== Decision

=== The question

link:0007-anchor-scoped-policy.adoc[ADR-0007] made the anchor the owner of a URL namespace and the carrier of a non-weakenable policy floor. It left two facts implicit: what an anchor is (a plain reverse proxy, a Backend-For-Frontend surface or a static-asset surface) and who may reach it. Those facts were inferred from `auth.require`, the presence of an `oidc` block and the terminal action behind the route. That costs a security gateway twice:

* *Fail-open by omission.* An anchor's intended audience lives in the operator's head. A surface meant to require authentication that is configured with `require: none` reads as a deliberate public surface. There is no declared expectation for the validator to contradict, so the boot succeeds and the surface is open.
* *Overloaded auth semantics.* Tying the kind of surface to the auth mechanism couples anchor classification to OAuth and OIDC. A deployment that fronts a network-authenticated backend, or serves public assets, has no natural place to state its posture.

*The decision:* every anchor carries two required, orthogonal axes.

* `type` (`proxy`, `bff` or `asset`): what the anchor is. This value space is separate from the `tls.passthrough_sni` surface, and `passthrough` is not a `type` value.
* `access` (`public` or `authenticated`): who may reach the anchor.

=== The boot matrix

A missing axis is a boot refusal. `AnchorRules.validateAccessAuthMatrix` enforces the matrix, and all violations are collected in one pass (link:0009-asymmetric-alias-resolution-failure.adoc[ADR-0009]):

* `access: authenticated` requires an effective non-`none` `require` with its backing block present.
* `access: public` together with an auth block is a boot refusal.
* `type: bff` requires `access: authenticated`.

=== Why two axes

* *Non-OAuth extensibility.* A `type` axis lets the gateway grow new terminal behaviours without overloading auth semantics. An `access` axis expresses audience independently of the mechanism.
* *Fail-closed declaration.* A surface's intended audience is a declared expectation the validator can contradict. An authenticated surface left open no longer boots. This extends the ADR-0007 namespace guarantee to the audience and kind dimensions.
* *Linear growth.* Adding a `type` or `access` value is one new enum constant.

== Alternatives rejected

=== Type a route implicitly and positionally

Infrastructure proxies (NGINX, Traefik, HAProxy, APISIX) type a route by what it holds: a `proxy_pass`, an `upstream` or a `root` directive makes it a proxy or a file server. Access control is a plugin, frequently optional, so a route with no auth plugin is open.

*Rejected because* API Sheriff is a security gateway, not a general-purpose proxy. The application-security tradition (Spring Security, Jakarta Security, the OWASP access-control guidance) fits better: every URL pattern declares its access, and the default for an undeclared pattern is deny. The audience of a surface should be a declared fact the gateway enforces, not an emergent property of which filters are wired.

=== A single fused mode axis

One axis naming every type and access combination.

*Rejected because* it grows combinatorially and re-entangles the two concerns: every type and access pair needs its own named mode.

== Consequences

=== Properties of the design

* The audience of every surface is structural and boot-enforced. An authenticated surface cannot be silently public, and a `bff` surface cannot be public by construction.
* The `type` axis gives the asset terminal action (link:0014-asset-serving-terminal-action.adoc[ADR-0014]) a declared home without overloading the proxy and BFF vocabulary.
* `passthrough` cannot be confused with an anchor `type`, because the two are separate concerns.

=== Accepted costs

* Every anchor carries two required fields. That was a breaking configuration change, accepted under the pre-1.0 rules.
