== Status

Accepted

== Decision

=== The question

The token-validation engine exposes one public validation entry point per token type: access token, ID token, refresh token. Each
entry point imposes that type's mandatory claims. That is correct for the types it names.

It leaves a gap. A gateway that speaks more of OAuth and OIDC than bearer authentication eventually verifies a JWT of neither type. The
same identity provider mints it, the same keys sign it, and the same JWKS publishes it. It is cryptographically as far inside the trust
boundary as a bearer token. Its claim set differs: its specification prescribes other mandatory claims and the absence of some the exposed
types require.

The OIDC back-channel logout token forces the question. It carries `iss`, `aud`, `iat`, `exp`, `jti` and `events`, plus `sub` and/or `sid`. It
need not carry `sub`. `azp` is not part of its claim set. It must not carry `nonce`. The first two collide with the ID-token rules, so the
ID-token entry point rejects a valid `sid`-only token.

The engine's pipeline already separates signature verification from claim validation. Only the public entry points fuse them. This record
settles how the gateway uses that separation.

=== The decision

A JWT whose type the engine exposes no entry point for is verified signature-only, and its claim set is the caller's authority.
`SignatureOnlyTokenVerifier` runs the engine's own ID-token pipeline minus its final claim-validation stage, over the same per-issuer
collaborators the bearer path uses:

. Decode the token, with size, structure and base64 bounds from the engine's parser.
. Resolve the configured issuer by the token's `iss`, and reject an unknown or disabled issuer.
. Run the engine's header validator: algorithm posture and issuer agreement in the JWT header.
. Run the engine's signature validator: the cryptographic check against that issuer's JWKS.
. Run the engine's token builder, which maps the verified body into claims and validates nothing.

Construction resolves the per-issuer collaborators once, so a request allocates none of them. The path increments the same shared
security-event counter as the bearer path, so a rejection here counts exactly as one there.

=== The caller owns everything the omitted stage enforced

Issuer equality, audience, freshness and the token's own required claims move to the component that knows the token's specification. That
component becomes the single authority over its type's claim set. This is the property the decision buys: one place to read the back-channel
logout claim rules, and one place a specification revision lands. For the logout token that component is `LogoutTokenValidator`. It also judges
the `typ` header value the verifier returns beside the claims.

=== The trust boundary does not move

This path rejects a token that fails signature verification, names an issuer the gateway does not configure, names a disabled issuer, or carries
an algorithm the issuer's key does not support, exactly as the bearer path does. The only checks dropped encode ID-token claim semantics: rules
about a different token type.

=== The verifier is signature-only by construction

Its returned value carries the mapped claims and the `typ` header value, and no verdict on either, so a caller cannot mistake it for a validated
token. The name states what the type states.

=== The gateway sanitizes the issuer before it reaches a diagnostic

The unknown-issuer rejection echoes the issuer identifier. Without it an operator cannot tell a typo in the gateway configuration from a token minted
elsewhere. At that moment the value is unverified and caller-supplied, and the message reaches a log on an unauthenticated path. The gateway therefore
strips control characters and bounds the value before interpolation. That closes the log-injection vector (CWE-117) and keeps the diagnostic.

=== The issuer collaborators stay the gateway's own

The gateway owns its issuer configuration and the per-issuer JWKS loaders this path's collaborators come from.
link:0074-The_token-validation_extensions_metrics_collector_observes_the_gateway_validator_and_its_health_probes_stay_excluded.adoc[ADR-0074] states
that ownership.

== Alternatives rejected

=== Drive the foreign token through the ID-token entry point

The smallest change: no new component, no new seam, and the engine's full verdict applies.

*Rejected because* the verdict is wrong. It enforces a claim set the specification never prescribed and rejects the specification's own normal form: a
valid `sid`-only logout token fails before any gateway-owned check runs. A conformance failure that presents as a security check reads as strictness while
being incorrectness.

=== Relax the ID-token entry point so its mandatory claims become optional

This keeps one entry point and needs no new path.

*Rejected because* it degrades the check for every caller to accommodate one. A real ID token must satisfy the dropped rules. A validator whose strictness is
set by its loosest consumer defends none of them.

=== Reimplement decode-and-verify locally for the foreign type

This gives complete control over the claim set, with no dependence on the engine's stage boundaries.

*Rejected because* it duplicates the one thing duplication is least acceptable in. Issuer resolution, algorithm posture and signature verification would exist
twice and drift silently, and nobody would see the drift until a token the two disagreed about arrived. It also answers a claim-semantics question by rewriting
cryptography.

=== Ask upstream for a per-type entry point

The cleanest long-run shape: the engine would own the logout-token claim set as it owns the others.

*Rejected as an answer to this question because* it relocates the decision. The gateway still has to decide what it does with a foreign token type, independently of
any upstream release. This seam stays correct whether or not such an entry point later exists.

=== Validate the claims inside the verifier, parameterised by token type

This keeps verification and validation fused and gives the caller a single call.

*Rejected because* the verifier becomes a registry of every token type the gateway will handle, with a conditional per type. That knowledge belongs to the component
that consumes each type. Fusing is what made the engine's entry points unusable here, and re-fusing them locally reproduces the problem one layer down.

The rejected alternatives divide cleanly. One group answers a claim-semantics question with a cryptography mechanism, and pays in duplication or in defence lost for
every caller. The other refuses to separate the two concerns. The chosen position keeps cryptography singular and upstream-owned, and makes claim authority explicit and
local.

== Consequences

=== Properties of the design

* The gateway speaks the protocol as the identity provider spells it. It accepts a valid `sid`-only logout token, because nothing rejects it on rules from another type.
* One implementation answers "is this signed by a configured issuer". The cryptography, issuer resolution and algorithm posture are the engine's, so an upstream hardening
  of any of them reaches this path with no local change.
* Claim authority is singular and legible. Each foreign token type has one component that owns its claim rules.
* Rejections on this path are observable through the same security-event counter as the bearer path, with no second metrics vocabulary.
* The seam generalises. A second foreign token type needs a claim-validating caller, not a second verification path.

=== Accepted costs

* The verifier returns claims nothing has validated. Its safety is a property of its callers, and the type system cannot enforce that a caller validates.
* The split is a maintenance obligation in two places. A change to the engine's pipeline stages must be reflected here, and the "ID-token pipeline minus its last stage"
  equivalence holds by construction, not by derivation from the engine.
* The gateway carries the back-channel logout claim rules itself. A specification revision is a gateway change, not a dependency upgrade.

=== Risks

* *The verifier is reused as if it validated.* The name and the return type say otherwise, but a future caller could still take it. Naming and documentation mitigate this,
  not the compiler.
* *Claim rules drift between callers.* With several foreign types, a rule that ought to be common, such as an issuer-equality check or a replay window, can diverge. Each caller's
  rules are enumerable and reviewable, not shared.
* *The dropped stage reads as "no claim validation happens".* It happens elsewhere. A reviewer reading only this path sees an unvalidated token and must follow the call. That is the
  cost of relocating authority rather than removing it.
