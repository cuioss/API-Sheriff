= ADR-0056: Session routes obtain their declared scopes by refreshing inside the grant and widening the live session outside it

== Status

Proposed

== Context

A session outlives the route that started it. The login that established it requested one route's
scope set, and the same session is later presented to routes that need other scopes.
link:0049-Route_scope_policy_bearer_routes_enforce_oidcscopes_union_endpointscopes_session_routes_only_request_them.adoc[ADR-0049]
derives one set per route at boot, `neededScopes = oidc.scopes ∪ endpoint.scopes`, and lets a session
route use it only to decide what its login requests. A live session is never compared against it.

That leaves a declared requirement the gateway does not hold its own sessions to:

* *Under-check.* A session that logged in on a route needing fewer scopes reaches a route needing
  more, and its token is relayed without them. Whether the request is refused depends on an upstream
  that may not check.
* *Two answers for one route.* A bearer caller whose token lacks the scope is refused `403` before any
  upstream contact. A browser session lacking the same scope is relayed. On a `session_fallback`
  route the two outcomes sit on one route and differ only by the kind of caller.

ADR-0049 considered a session pre-check and deferred it, because a pre-check needs a way to widen a
*live* session. A new login replaces the session rather than adding to it, and RFC 6749 §6 forbids a
refresh grant from widening the original grant. A pre-check that can only refuse turns every scope
mismatch into a dead end.

Two facts about a session's tokens make the mismatch recoverable, and they are different facts:

* the *active scope set* `A`: the scopes the mediated access token was granted. A refresh response
  can narrow it.
* the *granted scope set* `S`: every scope the user has authorized for this session. It equals `A`
  at login, grows only when the user authorizes more, and a refresh never changes it.

A scope missing from `A` but inside `S` needs no user: a refresh grant may name any subset of what
was originally granted. A scope outside `S` needs a new authorization. The question this ADR settles
is what a session route does when `A` lacks a scope the route needs, given that both recoveries
exist.

== Decision

*A session route never relays a session that lacks a scope the route needs. It compares on every
request, obtains what is missing -- by one refresh when the user already granted it, by widening the
live session when not -- and refuses when the identity provider does.*

* *The comparison runs on every session request.* After the session is resolved and the near-expiry
  refresh has run, `SessionAuthenticationStage` computes `missing = neededScopes − A`. It does so
  whatever `auth.token_relay` says and before any bearer is recorded, so `token_relay: false` withholds
  the token from the upstream but not the check from the request. With nothing missing the request
  continues and no identity-provider call is made.
* *Inside the grant, one refresh.* When every missing scope lies inside `S`, the stage makes exactly
  one call through the scope-driven leg of `TokenRefreshCoordinator`, requesting `A ∪ missing`. The
  leg shares the near-expiry leg's per-session single-flight, re-checks the re-resolved session under
  that exclusion, and leaves `S` unchanged. The stage compares the returned session again, so no
  outcome of the refresh can cause an under-scoped session to be relayed. Navigations and API calls
  take this path alike.
* *Outside the grant, the live session is widened.* When a missing scope lies outside `S`, or the
  refresh did not obtain the set, the answer depends on what the caller can do with it:
** A *navigation* (its `Accept` offers `text/html`) is redirected `302` into an authorization request
   for `S ∪ neededScopes` that returns to the requested URL. The first attempt carries `prompt=none`.
   If the identity provider answers `login_required`, `interaction_required` or `consent_required`,
   exactly one interactive attempt follows.
** Every other request is refused `403` `application/problem+json`, with two RFC 9457 extension
   members. `missing_scopes` lists the missing names, sorted and taken from the route's
   boot-configured set, never from a token. `step_up_url` is the same-origin URL a browser follows to
   widen the session for the refused request; it is present only when `oidc.step_up.path` is
   configured. The answer carries no `WWW-Authenticate` challenge, which belongs to the bearer
   posture.
* *A widening merges into the session it started from.* The widening callback is bound to the
  browser exactly like a login callback: a pending record, the binding cookie and the `state` are
  checked before anything else, an identity-provider error included, so a forged error can never
  start a re-drive. A successful grant is merged only when the new ID token's subject, the live
  session's subject and the subject recorded when the widening started are the same. The merge keeps
  the session's identity, its `sid`, its authentication time and its absolute expiry, takes the new
  tokens, sets `A` to the granted scope and `S` to `S` united with it. It never mints a second
  session and never moves a session to another identity.
* *A refusal is terminal.* Any other identity-provider error, any error on the interactive attempt,
  a subject mismatch, a missing live session, and a grant that still lacks a scope sought beyond `S`
  all answer `403`. The session is left unchanged and stays usable on every route it satisfies. No
  further redirect follows, so a scope the identity provider will not grant cannot loop the browser.
* *The step-up path is a reserved path that serves a live session only.* `oidc.step_up.path` is
  registered from the key's presence and matched like the other browser-facing reserved paths.
  Without a live session it answers `401` with no identity-provider redirect and no pending record.
  Its `returnUrl` is same-origin-validated and falls back to the configured default. When the target
  route's needed scopes already lie inside `S` it redirects straight back, because the route then
  refreshes by itself; otherwise it starts the same silent-first widening a navigation gets.
* *The session carries `S` in both session modes.* The session record and the sealed cookie payload
  hold the granted set next to the active set. A sealed cookie without the field belongs to an older
  format version and is refused at the version gate, so its browser re-authenticates.

One case skips the refresh although everything missing lies inside `S`. When the near-expiry refresh
has just re-bound the session under a new cookie, the request's own `Cookie` header still names the
binding that refresh rotated away, and a second exchange started from it would present a refresh
token the identity provider has already retired. Such a request takes the widening branch. The next
request carries the new cookie and is refreshed normally.

With transparent refresh switched off, the scope-driven leg is bound to a pass-through that hands the
session back unchanged, and the stage goes straight to widening.

=== How this relates to earlier decisions

* *ADR-0049.* This decision supersedes its session half. The precondition that decision deferred its
  session pre-check on, a way to widen a live session, is met by the merge described above. The
  `neededScopes` derivation, the bearer check, and the boot refusal of `endpoint.scopes` on an
  endpoint with only `none` routes stand. Requesting and checking still read one set; a session route
  now does both.
* *ADR-0055.* The SESSION branch of a `session_fallback` route is exactly a session route, so it
  inherits all of the above. Both branches of such a route now enforce the same set, each with its
  own posture's answer.
* *ADR-0046.* The scope-driven leg keeps every per-kind refusal disposition and adds one outcome that
  is not a refusal: the session is kept but does not carry the requested set, because the identity
  provider granted a narrower scope, the session holds no refresh token, or the request coalesced
  with a refresh that did not ask for it. That outcome records no back-off and no warning, and the
  stage widens. An outright `invalid_scope` answer is *not* part of it; see the Negative
  consequences.
* *ADR-0048.* The widening authorization flow is built on `ScopedEngineFlows` per call and never
  cached. The login-flow cache is bounded because a login set is always fixed at boot;
  `S ∪ neededScopes` contains scopes that come from the identity provider, so caching it would remove
  that bound. `prompt=none` is added to the rendered authorization URL by a parameter-aware rewrite on
  the gateway side, which leaves the engine unchanged.

== Consequences

=== Positive

* The under-check is closed on session routes. A scope declared on an endpoint is enforced for every
  authenticated caller of its routes, and no token lacking it reaches the upstream.
* A satisfied route costs nothing. The comparison is a set containment check on values the session
  already holds: no identity-provider call, no rotated token, no `Set-Cookie`.
* A mismatch is recoverable. A user reaches a scoped route from any session with at most one consent,
  and with none when the scope was granted before.
* The session stays the same session across a widening. Its identifier, `sid`, authentication time
  and absolute expiry are kept, so a widening neither creates a second session to track nor extends
  how long the session lives.
* Logins stay minimal. A login still requests only the scope set of the route it is for, and further
  scopes are requested when a route first needs them.
* One route gives one answer about a scope, whichever authentication branch the request takes.

=== Negative

* *An API client cannot recover by retrying.* A widening needs a browser navigation to the identity
  provider. A script that receives the `403` has to send the browser to `step_up_url`, and when no
  step-up path is configured the response names the missing scopes and nothing to follow.
* *An `invalid_scope` refresh answer arms the refresh back-off.* The engine surfaces that answer as a
  transport failure without the OAuth error code, so it is classified `PRE_REDEMPTION` like an outage
  and takes that kind's back-off and warning. The request is still never relayed short of a scope,
  because the stage compares the session again whichever outcome it receives. The cost is that the
  session's next near-expiry refresh waits out the same back-off window. Telling the two apart needs
  the error code from the engine.
* *The first request for a new scope is slower.* It pays one token-endpoint round trip inside the
  grant, or a redirect through the identity provider outside it.
* *The sealed cookie format is not migrated.* A cookie-mode session sealed without the granted set
  is refused, and its browser logs in again.

=== Risks

* *Session-wide scope growth is larger, not smaller.* ADR-0049 accepts that every scope a session
  holds is relayed to every session-route upstream. Widening adds scopes to a live session, so a
  session that visited a scoped route presents that route's scopes everywhere afterwards. The bounds
  are unchanged: the identity provider grants only what is requested, a widening can only request a
  route's boot-declared set united with what was already granted, and `token_relay: false` withholds
  the token from origins that need none. It stays tracked as BFF-15.
* *A cross-site navigation can start a widening.* A link to a scoped route or to the step-up path
  makes the browser request more scopes for the user's session. It cannot choose them: the set is the
  target route's boot-declared set, the return URL is same-origin-validated, and consent stays with
  the identity provider.
* *A widening merge and a concurrent refresh race.* Both resolve the session, then persist it, and the
  last writer wins. Either result is an identity-provider-fresh token set of the same identity, and
  the subject is re-checked on the resolved session, not taken from the pending record. The loss is
  one abandoned refresh token.
* *A refresh inside the grant depends on the identity provider honouring it.* A provider that
  declines to restore a previously granted scope returns a narrower grant or refuses the request, and
  the session is widened instead. The outcome is slower, not wrong.

== Alternatives Considered

*Relay and let the upstream refuse.* This is the session half of ADR-0049. It needs no extra
mechanism and never interrupts a request. It also leaves the enforcement of a gateway-declared scope
to a component the gateway does not control, and gives a bearer caller and a browser session
different answers on the same route. Rejected now that a live session can be widened.

*Narrow the token per endpoint.* Relaying each route a token restricted to that route's scopes,
through a scope-restricted refresh or RFC 8693 token exchange, is ADR-0049's third alternative. It
addresses session-wide scope growth, which is a different problem: a session that lacks a scope
still lacks it after narrowing. It also still costs a token-endpoint round trip per route or
per-route token caching, and needs identity-provider support that cannot be assumed. Still excluded.

*Probe with a refresh instead of tracking `S`.* The stage could request `A ∪ missing` on every miss
and treat a failure as "outside the grant". That removes the second scope set from the session. It
replaces a local set comparison with a token-endpoint round trip for every request on a scope the
user never granted, and it cannot read the answer reliably: a refused scope and an unreachable
provider arrive as the same failure kind, and the back-off for the second would throttle the first.
Rejected.

*Reuse the RFC 9470 step-up coordinator.* `StepUpCoordinator` already re-drives an authorization
request for a live session. It is the `acr` leg: it builds its request from the static `oidc.scopes`
through the engine's step-up handler, and its re-drive lands as a new session. A widening needs a
per-request scope set and a merge into the session it started from, which is the login re-drive's
shape -- pending record, binding cookie, callback -- with a different landing. Rejected; the two legs
stay separate.

The rejected alternatives either leave the decision to someone else, or learn what the user granted
by asking the identity provider each time. The decision keeps the answer in the session: what the
token carries, what the user granted, and one comparison that decides which of the two recoveries
applies.
