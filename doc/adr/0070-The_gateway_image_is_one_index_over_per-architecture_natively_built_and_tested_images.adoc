== Status

Proposed

== Context

The gateway ships as a GraalVM native executable on a distroless base
(link:0042-JVM_over_native_and_UBI-minimal_over_distroless_are_considered_and_declined.adoc[ADR-0042]).
A native executable is machine code for one instruction-set architecture, and for one minimum
level of that architecture. An image that carries it therefore runs on exactly the hosts that
architecture and level describe, and nowhere else: not on another architecture, and not on an older
CPU of the same architecture. Docker's emulation of a foreign architecture does not widen that set
in practice, because the emulators do not provide the vector extensions a modern target assumes.

A release lane that publishes such an image has to answer three questions together, and the
answers constrain one another:

* *Which hosts does one published tag serve?* A tag that names one image serves one architecture.
  Serving more than one under the same tag needs an image index whose entries the registry and the
  container runtime select per host.
* *How is each architecture's image built?* GraalVM native-image cannot cross-compile: the
  executable is built on a machine of the target architecture. A native build under QEMU emulation
  is possible but runs several times slower than a native one, and the native compile is already
  the dominant term of the lane's time budget.
* *Which guarantees survive the split?* The lane's existing guarantees are per-image: the image
  pushed is the image the integration-test suite ran against; its pushed digest is unique; the
  pulled image is identical to the tested one; it is scanned at HIGH and CRITICAL before any push;
  an SBOM describes it; its digest is signed. Every one of these has to hold for each architecture,
  and the multi-architecture artifact must not weaken any of them — in particular it must not
  become possible to publish one architecture's release while the other's failed.

The second structural choice point is the CPU baseline inside each architecture. A higher baseline
lets the compiler use newer instructions on every host; a lower one serves more, older hosts. The
choice is made at build time and fixed in the executable, so it is a property of the published
artifact, and it decides which operators can run the published image and which have to build their
own.

== Decision

*The published image is one image index over two natively built, fully integration-tested
per-architecture images, `linux/amd64` and `linux/arm64`. Release tags name only the index, and are
written only after both architectures passed every check. No `-march` is configured, so each
architecture keeps GraalVM's default target.*

=== One leg per architecture, each on its own architecture

The image job of `.github/workflows/release.yml` (`publish-image`) is a two-leg matrix:
`linux/amd64` on an amd64 runner and `linux/arm64` on an arm64 runner. Each leg builds natively,
because native-image cannot cross-compile and an emulated build does not fit the time budget.

Each leg keeps the single-image guarantees intact, for its own architecture:

* The full `-Pintegration-tests` suite runs on the leg's runner. That run is the leg's one and only
  image build, so the image the leg pushes is the image the suite ran against by construction.
* An SBOM is generated per architecture, because the two images carry different executables over
  different variants of the base image.
* The HIGH and CRITICAL Trivy gate runs per architecture. The two base-image variants are separate
  package sets that can carry different CVEs, so a clean scan of one says nothing about the other.
* The leg pushes with `docker tag` and `docker push` under a leg-local tag,
  `leg-<release-tag sha>-<arch>`, never under a release tag, asserts exactly one pushed digest, and
  asserts that the digest addresses a plain image manifest rather than an index.
* The leg pulls its digest back on its own runner and checks it: the pulled image ID equals the
  tested ID, the version and revision labels match, the OS and architecture match the leg, and the
  image answers its liveness probe. Only a host of the image's own architecture can boot it.

A leg signs nothing and writes no release tag.

=== One join, the only writer of release tags

A join job runs only when the matrix as a whole succeeded. It assembles the index with
`docker buildx imagetools create` from exactly the two digests the legs handed over — no attestation
entry, no third platform, no tag lookup — and points `<version>` and `sha-<release-tag sha>` at it.
It then reads the tags back from the registry and asserts that both resolve to one index digest,
that the index lists exactly `linux/amd64` and `linux/arm64`, each pointing at its own leg's tested
digest, and that pulling the index for `linux/amd64` yields the image the amd64 leg tested.

*A failed or cancelled leg publishes no release tag.* The legs run with `fail-fast`, so a failing
leg cancels the other, and a matrix that did not fully succeed leaves the join skipped. Either both
architectures ship under the release tags or neither does. A failed run leaves at most a leg-local
tag behind, which no consumer is pointed at.

The run/skip guard that keeps a guard-declined merge from re-pushing and re-signing an already
released tag sits on the legs and on the join alike.

=== Three signatures per release

Cosign keyless signing moves from the image job to the join and signs three digests: the index
digest the release tags name, and both platform digests. A consumer can pull a platform digest
directly, bypassing the index, and an unsigned platform digest would verify as nothing. All three
are verified in the same job under the identity and issuer operators are given, which are
unchanged:

* identity regexp `^https://github\.com/cuioss/API-Sheriff/\.github/workflows/release\.yml@refs/heads/main$`
* OIDC issuer `https://token.actions.githubusercontent.com`

The join is a caller-local job of the same workflow file and is reached by the same two events as
before, so the certificate SAN names the same single ref.

=== The CPU baseline: GraalVM's default on both architectures

No `-march` is configured anywhere — not in `quarkus.native.additional-build-args` in
`api-sheriff/src/main/resources/application.properties`, and not in the `native` profiles of
`api-sheriff/pom.xml` or `build-parent/pom.xml`. The shipped build arguments carry no
architecture-specific flag, so the same configuration builds on both legs unchanged. Each
architecture therefore compiles for GraalVM's default target:

* *amd64: `x86-64-v3`.* The executable needs AVX2, BMI2 and FMA. It runs on Intel cores from
  Haswell on and AMD cores from Excavator on, including every current server and desktop part.
* *arm64: GraalVM's AArch64 default, which GraalVM documents as `armv8.1-a`.* Graviton 2
  (Neoverse N1, Armv8.2-A) and every later Graviton generation implement it, as does Apple Silicon.
  Apple Silicon under Docker runs it: this project's own arm64 native images are built with the
  same configuration on Apple Silicon hosts, and one of them brought the compose sample up healthy
  on an arm64 host
  (link:0069-The_BFF_keeps_one_issuer_identity_and_reaches_the_identity_provider_through_a_configured_back-channel_origin.adoc[ADR-0069],
  "Verified on"). Graviton 2 is covered by instruction-set inclusion; no Graviton 2 host has booted
  the image.

Each leg's native-image build log states the target machine on its `Graal compiler:` line. The
lane's dry run (workflow run 39588321108, 2026-10-21) shows `target machine: x86-64-v3` on the
amd64 leg and `target machine: armv8.1-a` on the arm64 leg, so both defaults are observed and not
only documented.

The hosts *below* either baseline are not served by the published image, and are named rather than
left to be discovered:

* x86-64 CPUs without AVX2, BMI2 or FMA — Intel cores before Haswell, AMD cores before Excavator,
  and low-end Atom-class parts that omit AVX2;
* AArch64 cores older than the arm64 default, such as the Cortex-A72 of Graviton 1 and the
  Raspberry Pi 4.

They are served by Route B, a locally built image
(link:../user/compose-sample.adoc[the compose sample]): a build on such a host compiles for that
host. The same applies to an amd64 image forced onto an arm64 host with `--platform linux/amd64`,
which the index no longer requires.

`-march=compatibility` was considered and *declined*; see Alternatives Considered. Because the
decision keeps the default, no cost of a broader target was measured, and no performance figure is
claimed in either direction.

=== A dry run proves the lane without a release

A `workflow_dispatch` input, `dry_run`, runs both legs, the join and the three signatures without
a release: the release job refuses it on every ref, so no Maven publication, SCM tag or GitHub
release can result. Every tag a dry run pushes is `dryrun-<run_id>[-<arch>]`, asserted before the
push; the images carry the version label `dryrun-<run_id>`; signatures are verified under an
identity derived from the dispatching ref; and a cleanup job deletes, by the digests the run
recorded, every package version the run created. A dry run may be dispatched from a non-`main`
ref, because it publishes nothing a consumer pulls by a release tag and its signatures do not
satisfy the published identity unless it was dispatched from `main`.

=== What this record does not change

The release trigger and the centrally owned version-changed decision
(link:0035-A_release_is_cut_by_a_guarded_version-bump_merge_or_a_deliberate_dispatch_and_the_version-changed_decision_is_centrally_owned.adoc[ADR-0035])
are unchanged. The release stays non-atomic: the Maven artifacts publish before the image lane
runs, so a failed leg leaves a jars-only release with no release tag, recovered by re-running the
image jobs (link:../development/release-process.adoc[Release process]). The native-on-distroless artifact and its trust-material
posture (ADR-0042) are unchanged; each platform image is that same artifact for its architecture.

== Consequences

=== Positive

* One tag serves `linux/amd64` and `linux/arm64` hosts, including Apple Silicon and Graviton, and
  each host pulls an image built and tested on its own architecture.
* Every single-image guarantee — tested equals published, unique digest, pulled equals tested,
  gating scan, SBOM, signature — holds per architecture, and the index adds the guarantee that it
  points each platform at the image that platform's leg tested.
* There is no half release. A release tag names an index over both platforms or does not exist.
* Every artifact a consumer can pull by digest is signed and verifiable under one published
  identity.
* The lane can be exercised end to end before a release depends on it, and a dry run leaves no
  package version behind.

=== Negative

* A release costs two native builds and two full integration-test runs instead of one; the legs
  run in parallel, so the wall time grows less than the compute.
* A failure on one architecture blocks the release for both. An arm64-only defect withholds a
  release from amd64 consumers too; that is the price of the no-half-release rule, paid
  deliberately.
* Hosts below either CPU baseline still cannot run the published image and need a local build.

=== Risks

* *arm64 is proven at release time, not on every pull request.* The pull-request integration lane
  runs on amd64 only, so a change that breaks arm64 alone surfaces at the next release or dry run,
  not at review.
* *Leg-local tags persist.* Each release leaves its `leg-<sha>-<arch>` tags on the two platform
  manifests in the package. They name images that are part of a signed release, so they are
  harmless, but they accumulate, and a version badge or tag listing has to ignore them.
* *The arm64 target is the builder image's default, not a pinned setting.* The dry run observed
  `armv8.1-a`, but should a builder-image update change the AArch64 default, the supported arm64
  population changes with it; the build log line names the target, and nothing else asserts it.
* *The runner label is an external dependency.* The arm64 leg needs GitHub's arm64 Linux runner;
  losing access to it stops every release, not only arm64.

== Alternatives Considered

*Build the arm64 image under QEMU on an amd64 runner.* Keeps one runner type and lets one job
build both images. Rejected because an emulated native compile does not fit the lane's time budget,
and because it could not test what it builds: the integration suite would run emulated or not at
all, so "the published image is the tested image" would hold for one architecture only.

*Cross-compile the arm64 executable on the amd64 runner.* GraalVM native-image does not support
cross-compilation, so this option does not exist for this artifact.

*Build and push both platforms in one `docker buildx build --platform ... --push`.* Produces an
index in one step. Rejected because the image would be built outside the integration-test harness,
so what is pushed is no longer what was tested; and because buildx's default attestations push a
manifest list that wraps the image with provenance and SBOM entries, which changes what a
pull-by-digest resolves to and what Cosign signs.

*Publish a separate tag per architecture* (for example `<version>-arm64`) and no index. Avoids the
join. Rejected because every consumer then has to know its host's architecture to name the tag, a
deployment manifest stops being portable between hosts, and there is still no single artifact for
a release to sign.

*Let each leg publish its own release tag as soon as it is green.* Simpler, and amd64 consumers
would not wait on arm64. Rejected because it makes a half release reachable: a release whose tags
serve one architecture while the other failed, which no consumer can distinguish from a complete
one.

*Sign only the index digest.* One signature per release, as before. Rejected because a consumer who
pins a platform digest — which is how one fixes an architecture deliberately — would hold an
artifact no signature covers.

*`-march=compatibility` on both architectures.* Lowers amd64 to the baseline x86-64 instruction
set and arm64 to the plain Armv8-A one, so the published image would also run on the hosts listed
above. Declined because it trades code-generation quality on every supported host for a population
of old or low-end CPUs that a locally built image already serves: the cost would fall on every
deployment, the benefit only on those few, and those few already have a working route. Measuring
the cost on this gateway's workload would be the first step of a reversal, not a step this decision
needs.

*Run the integration suite on arm64 on every pull request.* Would move the arm64 proof from release
time to review time. Not adopted here: it doubles the cost of the most expensive pull-request lane
for a platform whose image is built by the same configuration as the amd64 one. It remains the
natural next step if an arm64-only defect ever reaches a release.

The rejected options share one flaw: each either publishes something other than what was tested,
or lets a release reach consumers in a shape that is not complete.
