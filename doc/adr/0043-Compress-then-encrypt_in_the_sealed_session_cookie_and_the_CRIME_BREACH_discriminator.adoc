== Status

Accepted

== Decision

=== The question

In the cookie-based BFF the sealed session cookie is the session. No server-side store exists, so every
component a later request needs travels in that cookie. The payload carries three credentials and six
small identity and bookkeeping fields. The credentials are the mediated access token, the refresh token
where the identity provider granted one, and the raw ID token kept for the logout `id_token_hint`.

That set must fit one cookie. RFC 6265 section 6.1 obliges a user agent to keep only about 4096 bytes for
the whole `Set-Cookie` header: name, value and attributes together. A browser that decides otherwise drops
the header silently, and the session never exists. The budget is therefore a cliff, and the server cannot
see the failure.

Two facts set the size to defeat. JWTs are already base64 text, so their entropy per byte is low. An earlier
wire format also armoured every field with base64 inside the plaintext and base64url-encoded the sealed value
again, compounding two expansions of about 33 %. A session with all three tokens could not fit.

This record settles what may be done to the plaintext before it is sealed. Length-prefixed raw UTF-8 framing
removes the inner armouring, which raises no security question. Compression does raise one. Compressing before
encrypting is the construction behind CRIME and BREACH. An attacker who can force many samples and place chosen
plaintext next to a secret in one compression context reads the secret from the result lengths, byte by byte.

=== The payload is deflated before it is sealed

The pipeline encodes the nine fields as length-prefixed raw UTF-8, deflates them, seals with AES-256-GCM and
base64url-encodes once for transport. `SealedSessionCookieCodec` implements it. The decision applies here and only
here, because both halves of the CRIME/BREACH discriminator answer no.

=== Half one: sample count

*Can an attacker force additional seals? No, not without already holding the session.*

The gateway writes the sealed value on exactly two events: a completed login, and a token refresh that rotates
the material. Both are outcomes of authentication, not of a request an unauthenticated party can drive.

* An attacker who triggers a login authenticates as themselves and seals their own payload. That teaches nothing
  about a victim's.
* An attacker who triggers a victim's refresh must already send the victim's session cookie. That attacker holds
  the session and has no reason to attack its length.

Compression-oracle attacks need thousands of samples of the same secret under attacker-varied input. This
construction admits one seal per session change, all behind authentication. The attacker has no lever that
increases the count.

=== Half two: chosen-plaintext influence

*Can an attacker vary the plaintext next to the secret? No.* The identity provider issues or the gateway mints each
of the nine components. None is echoed from the request that produced it.

[cols="2,2,3"]
|===
| Component | Who controls it | Can an attacker vary it within a session whose secrets they do not hold?

| `accessToken`
| The identity provider
| No. The IdP mints it for the authenticated subject. The realm's client and mapper configuration set its claims,
  and the operator controls that configuration, not the request.

| `refreshToken`
| The identity provider
| No. Opaque IdP-issued material, present only when the IdP granted one.

| `idToken`
| The identity provider
| No. A JWT the IdP signs. The gateway keeps it because a stateless gateway has nowhere else to keep the
  `id_token_hint` logout needs.

| `sub`
| The identity provider
| No. The subject identifier of the authenticated principal.

| `sid`
| The identity provider
| No. The IdP's session identifier, absent when the IdP mints none.

| `acr`
| The identity provider
| No. The authentication context class the IdP reports.

| `authTime`
| The identity provider
| No. The IdP's authentication instant, as epoch seconds.

| `loginInstant`
| The gateway
| No. The gateway's own clock when the session was created. An attacker who influences when a victim logs in still
  cannot choose the value, and one second of drift is not chosen plaintext.

| `sessionNonce`
| The gateway
| No. 32 bytes of `SecureRandom`, base64url-encoded. It is incompressible by construction, so it sets a floor on any
  compression level. It also guarantees two sessions of one subject never deflate identically.
|===

No request populates a field, so a probe string has no place to go. Attacker-varied bytes sharing a compression
context with the secret are absent structurally, not by a validation a later change could relax.

=== The claim is scoped

This record does not establish that compress-then-encrypt is safe. It establishes that it is safe for this payload,
on these two grounds. A change that removes either ground reverses the decision
(<<_what_would_reverse_this_decision>>).

== Alternatives rejected

=== Refuse compression outright

A blanket rule, never compress before encrypting, is simple, needs no threat model and cannot be got wrong later.

*Rejected because* the cookie-based BFF could then not carry a refreshing session. The three-token payload does not fit
the browser-safe budget without compression. The cost is a real capability. The benefit is a rule the two structural
properties above already satisfy.

=== Raise the cookie size budget

A larger `max_cookie_size` lets the seal-time check pass and changes nothing in the browser.

*Rejected because* the failure moves from a loud server-side rejection to a silent client-side drop. The gateway then
believes it established a session the browser never kept. That converts a diagnosable failure into an undiagnosable one.

=== Split the session across several cookies

The budget is per cookie, so chunks reassembled on read could carry a large session.

*Rejected because* it is a structural cost paid to avoid a bounded threat analysis. It multiplies the state the browser
must keep consistent. It introduces a partial-arrival failure with no clean answer. It also interacts badly with the
`__Host-` prefix discipline the session cookie relies on.

=== Drop the ID token from the payload

The seal holds the ID token only to supply `id_token_hint` on logout. Dropping it would reclaim many bytes and remove a
credential from the browser.

*Rejected because* it degrades logout. Without the hint the IdP cannot reliably identify the session to end, so the round
trip becomes best-effort. It trades a security-relevant behaviour for bytes the packaging supplies without that trade. It
stays the first thing to reconsider if the payload ever stops fitting.

=== The server-session BFF

Keeping the session server-side removes the size question and is the right answer for a deployment that can hold state.

*Rejected as out of scope here.* It is a different variant with different operational properties, not an alternative
packaging for this one. The cookie-based BFF exists for deployments that will not hold session state. The server-session
BFF stays the standing recommendation for an operator whose token set does not fit after packaging.

The alternatives fall into two classes. The first is a rule that costs a capability to avoid an analysis. The rest shrink
or relocate the payload. Only compression addresses the size without giving up a property the design relies on.

== Consequences

=== Properties of the design

* A session with access, refresh and ID tokens fits one browser-safe cookie. This makes the cookie-based BFF viable for an
  identity provider that issues refresh tokens.
* The compression cost falls once per session change, never per request, so the codec can ask for `BEST_COMPRESSION`.
  Unsealing inflates per request, and inflation is cheap beside the AES-GCM operation on that path.
* Inflation runs only on bytes the GCM tag has authenticated, so this is not untrusted-input decompression. The expansion is
  still bounded, so a corrupt-but-authenticated buffer cannot drive an unbounded allocation. A malformed stream takes the
  ordinary "no session" path rather than raising.

=== Accepted costs

* *The compressed length is visible.* Anyone who can see the cookie can observe the sealed size: the browser, an intermediary
  that logs header sizes, and the client. After compression that size depends on the payload's content. A markedly smaller seal
  carries less material, most legibly no refresh token. The signal is not actionable. It distinguishes classes of session, not
  a bit of a secret. It is one observation per session, not a series an attacker can drive. A client that can read the cookie's
  length already holds the cookie. This record keeps the residual, and it is no path to token material.
* *The wire format has no migration path.* An explicit version gate refuses a value sealed under an earlier format before it
  constructs a cipher. Earlier cookie sessions end at the change, and the browser re-authenticates.
* *The payload is not readable at rest, even with the key,* until it is inflated. This is a diagnostic cost, not a security
  property.

[[_what_would_reverse_this_decision]]
=== What would reverse this decision

Either of these restores an enabling condition and makes compress-then-encrypt unsafe here:

. *A payload component an attacker can influence.* A field populated from the request puts chosen plaintext into the compression
  context next to three credentials. Examples are a returned URL, a client-supplied correlation id, a header echo, or an IdP claim
  a downstream party can set. The deflate step must go in the same change.
. *A route that re-seals on demand.* A path that produces a fresh seal without a completed authentication or a due refresh hands
  the attacker the sample count. Examples are a "refresh my cookie" endpoint, a re-seal on every request, or a re-seal a client
  parameter triggers. The other half may still hold, which is the case a reader most likely waves through.

Both reduce to one question: can a party who does not hold this session cause a seal, or choose bytes inside one? While the answer
stays no on both, the decision stands.

=== Other risks

* *A future high-entropy component changes the arithmetic.* The session nonce already is one. Another such field means compression
  buys less, and a session that fits today may stop fitting. That surfaces as a seal-time budget failure rather than a silent browser
  drop: a loud failure, but a capability regression.
* *The deflate step reads like an optimisation*, so a later change may move, generalise or reuse it. It is a security-relevant
  construction whose safety rests on the two properties above, and it belongs to this payload alone.
