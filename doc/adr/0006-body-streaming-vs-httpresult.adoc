== Status

Accepted

== Decision

The `cui-http` client stack is typed and materializing by construction. `HttpHandler` wraps the JDK `HttpClient`, and `ResilientHttpAdapter` and `ETagAwareHttpAdapter` return `HttpResult<T>`, a sealed `Success` or `Failure` carrying the fully materialized response body as an in-memory `T` (link:../technical_aspects.adoc#_httpresult_pattern[Technical Aspects, HttpResult]). The adapters' retry and ETag caching work because the body is a replayable, cacheable `T`.

That shape suits a response that is small, bounded and wanted as an object. The proxy data plane forwards arbitrary client traffic: large responses, file downloads, Server-Sent Events, chunked and long-lived streams, and WebSocket upgrades. The record settles which shape each plane uses.

*The decision:* the two planes are split explicitly.

=== Control plane: `HttpResult<T>`

Small, bounded, single-shot JSON the gateway itself consumes uses `HttpResult<T>`: OIDC discovery, JWKS fetch, the token-endpoint exchange and revocation. Here materialization is a feature: a deserialized object, ETag and `304` caching, a typed `HttpErrorCategory`, and fallback content for graceful degradation. These calls live inside `token-sheriff-validation` and `token-sheriff-client`.

=== Data plane: stream, never materialize

The proxy path forwards request and response bodies as streams with backpressure, in both directions. It pipes the client `ReadStream` to the upstream `WriteStream` and the upstream `ReadStream` to the client `WriteStream`. The source pauses when the sink's write queue is full and resumes on drain.

`HttpResult` does not appear on the data plane. link:0008-data-plane-transport.adoc[ADR-0008] names the transport and the resilience mechanism. The gateway's own event types drive the `502`, `503` and `504` mapping, not `HttpErrorCategory`.

=== The body cap is a streaming counter

The gateway enforces `security_filter.max_body_bytes` (link:../configuration.adoc#_security_filtering[Configuration, security filtering]) by counting bytes as they flow through the pipe and aborting once the cap is exceeded. It never holds the whole body to measure it. There are two cases:

* A request whose `Content-Length` already exceeds the cap is rejected before the upstream connection opens.
* A chunked or streaming request body with no usable `Content-Length` can breach the cap only mid-stream. The upstream connection may already be open and some bytes forwarded, so the breach aborts the in-flight upstream call and tears down the connection.

Both paths reject through the input-validation edge and never complete the forward.

=== Streaming responses pass through untouched

SSE (`text/event-stream`), chunked transfer and long-lived responses relay with immediate flush and no buffering. A WebSocket upgrade becomes a byte relay after the authenticated handshake. None of these is ever materialized.

== Alternatives rejected

=== Materialize proxied bodies

A proxied body could pass through `HttpResult<byte[]>` or `HttpResult<String>`. The early interim proxy did this with `HttpResponse.BodyHandlers.ofByteArray()`, which was acceptable for a scaffold only.

*Rejected because* it holds the whole body in heap or direct memory before a single byte reaches the client. It runs out of memory under concurrency, because N concurrent large bodies each sit whole in memory. It breaks SSE, chunked and infinite streams, because an object carrying a completed `T` cannot exist until the stream ends. It destroys backpressure, and it forces time-to-first-byte up to time-to-last-byte.

The surveyed proxies agree. Each streams the proxied body by default, with bounded buffers and backpressure, and full materialization is off by default, opt-in, or the documented cause of failure:

* *nginx* buffers within bounds and spills to a temp file. `proxy_buffering off` is the documented fix for SSE.
* *Envoy* streams by default and backpressures through watermark buffers. Full-body buffering is an opt-in filter.
* *Traefik* and *Go `httputil.ReverseProxy`* stream through a 32 KB window. Full buffering is a separate opt-in middleware.
* *HAProxy* streams through a bounded per-connection buffer. Whole-body buffering is opt-in.
* *Spring Cloud Gateway* streams by default. Its body-materializing filter is the documented source of `OutOfDirectMemoryError`, broken SSE and direct-memory leaks.
* *Vert.x*, this gateway's runtime, recommends `ReadStream.pipeTo(WriteStream)`. Its documentation warns that reading faster than writing can grow the write queue without bound until it exhausts available RAM.

== Consequences

=== Properties of the design

* Per-request memory is the pipe window, not the body size, so a thousand concurrent large downloads do not multiply into the heap.
* SSE, streaming and large downloads work: the first byte leaves immediately, matching every surveyed proxy's default.
* The `HttpResult<T>` ergonomics stay where they help, the small control-plane JSON calls, without their materialization cost on the data plane.

=== Accepted costs

* A body-cap breach on a chunked request can abort an upstream call that already started, so the upstream may see a partial body.
