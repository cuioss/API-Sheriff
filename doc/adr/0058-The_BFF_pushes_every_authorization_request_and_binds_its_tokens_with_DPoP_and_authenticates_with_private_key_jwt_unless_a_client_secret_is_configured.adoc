== Status

Accepted

== Decision

=== The question

The BFF is a confidential OAuth client. It holds a credential the browser never sees, starts authorization requests on the browser's
behalf and keeps the tokens the identity provider issues. Each duty has a weak form that needs no key material:

* *A shared client secret.* The identity provider stores it and the gateway configuration carries it. Whoever reads either can
  authenticate as the client.
* *Authorization parameters on the front channel.* A request that travels through the browser as a URL can be read and altered there.
* *Bearer tokens.* Whoever holds a copy of an unbound access token can use it.

The FAPI 2.0 Security Profile closes the three with asymmetric client authentication, pushed authorization requests (PAR) and
sender-constrained tokens. It leaves two routes open: mutual TLS, or `private_key_jwt` with DPoP. It does not say where a client's keys
come from, how the IdP learns the public half, or how far behind the client a binding reaches. This record settles those questions.

*The decision:* the BFF pushes every authorization request through PAR, binds its access tokens to one DPoP key, and accepts a token
response only if it is bound to that key. It authenticates with `private_key_jwt`, unless the operator configures `oidc.client_secret`,
which selects `client_secret_basic`. Each of the two signing keys is generated at startup or read from a PEM file that `gateway.yaml` names
by path. The front-channel request and the bearer token have no remaining mode. Client-secret authentication stays an operator choice.

xref:../fapi_status.adoc[FAPI 2.0 Status] states what these decisions let the gateway claim against the profile, and the limit of that
claim. Nineteen decisions realise this. The operator decides one thing, a client secret, a key file or nothing, and the gateway derives the
rest.

=== 1. The route is DPoP with private_key_jwt

The gateway takes the DPoP route: client authentication by a signed assertion, token binding by a DPoP proof. Both are wired on the pinned
confidential-client engine, `token-sheriff-client`, through its types `PrivateKeyJwtAuth` and `SenderConstraint`.

=== 2. Two optional key blocks, and the client secret as an operator choice

The `oidc` block has two sub-blocks, `client_authentication` and `sender_constraint`, each with one optional `key_file`. The two must name
different files that hold different keys, because FAPI 2.0 section 6.8 asks for single-purpose keys. The configuration validator refuses one
file named by both. Where a file is missing, it refuses only a pair equal after normalisation with no `..` segment. The boot also refuses one
key in two files. Neither boot refusal names a path or a key id. The cookie sealing key of ADR-0072 is a sibling: it shares the bounded key-file
read and not the PEM parser.

`oidc.client_secret` is a supported key, and its presence selects the client authentication. There is no switch:

* With `oidc.client_secret`, the gateway authenticates with `client_secret_basic`.
* With no secret and a key file, it authenticates with `private_key_jwt` and the provided key.
* With neither, it generates a key and authenticates with `private_key_jwt`. The default is therefore key-based.

The boot refuses a descriptor that declares `oidc.client_secret` together with `oidc.client_authentication.key_file`. The message names both
keys and no value.

Only client authentication changes with the secret. In both modes every authorization request is pushed (decision 11), every token request carries
a DPoP proof, and every token response must be bound (decision 19). The gateway handles `oidc.sender_constraint.key_file` identically in both.

In client-secret mode the gateway warns at every boot that client-secret authentication is not FAPI 2.0 conformant. The record cannot carry the
secret. xref:../user/bff-session.adoc#client-secret[The operator page] has its wording.

=== 3. A key is either provided or generated

Each purpose has at most one key, in one of two modes:

* *Provided:* `key_file` names a PEM file on a mount.
* *Generated:* no key is configured. The gateway generates an EC P-256 key from `SecureRandom` at boot and logs the purpose and the mode, never the
  material.

The generated mode is this project's own choice, not common practice. It follows the gateway's cookie sealing key, so a single-node gateway starts
without key provisioning. The client implementations surveyed provision or persist their key. One product generated a key at startup, on low-confidence
sources, so this record cites no precedent. A generated key lives in one process and cannot be shared across replicas.

=== 4. A key is referenced by a file path in gateway.yaml

`key_file` is a file path, written literally or through a `+${VAR}+` or `+${VAR:-default}+` placeholder. The gateway reads the file itself, once, at boot.

ADR-0011 rejected trust material in `gateway.yaml`, and it is not engaged here. None of its three grounds holds for an unencrypted PEM path:

* A trust-store path came with a password. An unencrypted PEM path carries no password and is not a secret, so the document stays committable.
* Naming a runtime TLS-registry construct was rejected on layering grounds. A file path names no runtime construct.
* Reading stores in the gateway would have re-implemented what the runtime provides. The runtime offers no facility for a JWS signing key. The gateway adds
  one bounded read of one format through the JDK key factories: no key store, no encrypted PEM, no reload.

`gateway.yaml` has a second class of path-carrying keys next to `tls.mtls.client_ca`, `jwks.file` and `portal.template_dir`.

=== 5. A key-file pointer is a location, not a secret

The gateway treats the pointer exactly as a topology value. It is not among the configuration loader's secret pointers, and it may be written literally. The
secret is the key material, which never enters a descriptor, a log line or an error message. Boot refusals name the purpose's configuration field and the defect,
never the configured path.

=== 6. One file holds a private block and a public block

For every key type, a provided key file holds exactly one unencrypted PKCS#8 `PRIVATE KEY` block and exactly one `PUBLIC KEY` block, and nothing else but whitespace.
The gateway reads it bounded to 16 KiB. At boot, one sign-and-verify round proves the two halves belong together, and a mismatch is a boot refusal.

The JWKS endpoint, the DPoP proof header and the key id all need the public half. The JDK's public API yields it from a PKCS#8 private key for RSA only. For EC P-256
the derivation sits in packages the platform does not export, and its one public entry point is a preview API. The same rule holds for RSA: one file shape gives one
documentation paragraph and one test matrix. An RSA operator therefore supplies a block the gateway could compute.

=== 7. The key id is the RFC 7638 thumbprint

The `kid` is always the RFC 7638 thumbprint of the public key. A PEM file carries none. An identity provider is documented to cache a client key by `kid` and to fetch again
only on an unknown one. The id must therefore change exactly when the key does, and a thumbprint cannot do otherwise.

=== 8. The algorithm follows the key type

The gateway holds both modes to the floors of FAPI 2.0 section 5.4.1 at boot. An RSA key of at least 2048 bits signs `PS256`. An EC key on P-256 signs `ES256`. The `RS256`
family is unreachable by construction.

=== 9. The client-assertion audience is the issuer identifier

The `aud` of the client assertion is the issuer identifier, as a single string (FAPI 2.0 section 5.3.3.1 item 5). The engine renders `aud` as one JSON string, and the gateway
passes the configured issuer. One authentication instance serves the pushed request, the code exchange, the refresh grant and RFC 7009 revocation, so each leg carries the same
audience. The rule applies in key mode. In client-secret mode the gateway sends no assertion.

=== 10. The client key is published at an unauthenticated JWKS endpoint

In key mode the gateway always publishes the client-authentication public key, generated or provided. The endpoint is the single distribution path: the identity provider is
configured with its URL.

* *Path.* `oidc.client_authentication.jwks_path`, default `/bff/jwks`. The boot refuses a path that collides with another reserved path, the step-up path of ADR-0057 included, and
  a non-canonical path no request spelling it as configured would match.
* *Host.* The path matches on every host, as the back-channel logout path of ADR-0018 does, because the identity provider dials it server-to-server at an often internal name.
* *Method.* `GET` only.
* *Content.* Exactly one key, with `use: sig` and no `key_ops`. The gateway never publishes a separate DPoP proof key there: it travels in every proof.
* *TLS.* FAPI 2.0 section 5.4.2 asks for `jwks_uri` over TLS only. The gateway does not refuse the path on a plain listener, because a deployment behind a TLS terminator is
  supported and cannot see how the request reached the terminator. The documentation requires an `https` URL at the identity provider.

In client-secret mode there is nothing to publish. The path stays reserved on every host, answers `404` to every method and never reaches the route table. Moving from the secret to
a key therefore changes no routing and meets no new boot refusal. The back-channel logout path of ADR-0018 sets the precedent, with its deliberate `404` in the cookie-based BFF.

=== 11. Every authorization request is pushed

Every authorization-request seam goes through one adapter, `PushedAuthorizationRequests`, over the engine's flow-agnostic `ParClient`: the login, the session widening of
link:0057-Session_routes_obtain_their_declared_scopes_by_refreshing_inside_the_grant_and_widening_the_live_session_outside_it.adoc[ADR-0057] (its silent attempt and its one interactive
re-drive) and the RFC 9470 step-up re-drive. The adapter composes no parameter itself. It pushes what the engine's builder rendered, so `response_mode=query` (ADR-0018), the per-request
scope set (ADR-0048) and the `prompt=none` of a silent widening travel inside the pushed request. The browser gets exactly two parameters, `client_id` and `request_uri`. The push is dialled
under the back-channel posture of ADR-0045.

The failure contract is one rule. An identity provider that advertises no PAR endpoint and a push that fails both refuse the login or the widening with `502`. The gateway stores nothing and
sets no cookie, and a live session stays as it was. The refusal is recorded under the ADR-0051 discipline, because the login path is reachable without a credential.

=== 12. The step-up re-drive is pushed but has no live caller

The RFC 9470 step-up re-drive has no caller at the edge. PAR on that leg is wired at the seam and proven at unit level only. "Every authorization request" is therefore a property of the seams,
not an observed property of every running flow. The re-drive is not the step-up path of ADR-0057: that path is live and starts a session widening, which decision 11 pushes. The PAR row of
xref:../fapi_status.adoc[FAPI 2.0 Status] states which seams the suites reach.

=== 13. The binding ends at the gateway

The access token carries `cnf.jkt`. The gateway forwards it upstream as `Authorization: Bearer`, with no proof. An upstream must not check `cnf`, and `auth.token_relay: false` is the per-route
opt-out that forwards no token at all. The gateway checks the binding when it receives a token (decision 19). No party downstream of the identity provider checks a proof when the token is used.

=== 14. A key rotates by restart, with no overlap

A generated key rotates on every restart. A provided key rotates by replacing the file and restarting, with no change at the identity provider, which should fetch the new key when it meets the
new `kid`. The documented worst case is the baseline: a session bound to the old key fails its next refresh and follows `oidc.session.refresh.on_failure`. That a session survives on Keycloak is an
observation with stated limits (decision 18), not a guarantee.

=== 15. The DPoP server nonce is supported through the engine's single retry

FAPI 2.0 section 5.3.3.1 item 8 requires a client to support the server-provided nonce. The engine retries a token request once when a non-success response carries `DPoP-Nonce`. Two gaps stay open:

* The retry resends the same request. In key mode that includes the same client assertion, and an authorization server that enforces single use refuses the retry. In client-secret mode it resends
  the same Basic credential, which is not single-use.
* A nonce on a successful response does not carry into later requests (RFC 9449 section 8.2), so the next request pays the retry again.

=== 16. The authorization code is not bound to the DPoP key

The gateway sends no `dpop_jkt`. FAPI 2.0 section 5.3.3.1 NOTE 2 does not require it of clients, and the engine's PAR transport attaches no proof.

=== 17. Findings and unverified premises are accepted residuals

The decision rests on findings from the sources of the pinned engine, the JDK and the identity provider's documentation, and on premises no source settled.
xref:../development/bff-session.adoc#adr-0058-residuals[Server-Session BFF: Accepted residuals] lists each. The residuals an operator meets are the consequences below.

=== 18. Facts only the running stack can show are kept apart

Facts no source can show are not decisions. xref:../development/bff-session.adoc#observed-on-the-integration-stack[Observed on the integration stack] holds each, with its verdict and limits.

=== 19. A token response must be bound to the proof key

After the code exchange and after every refresh, in both client-authentication modes, the gateway accepts a token response only if both of these hold:

* Its token type is `DPoP`.
* The `cnf.jkt` of the access token equals the RFC 7638 thumbprint of the gateway's own proof key.

The gateway refuses a response that fails either:

* *At login:* `400`, and no session is created.
* *At a session widening (ADR-0057):* `400` on the callback, and nothing merges into the live session.
* *At refresh:* the refresh ends the session, and `oidc.session.refresh.on_failure` applies. The near-expiry and scope-driven refreshes share one exchange seam.
* *In the log:* one `WARN` record, with a closed set of reasons and no token material.

`BoundTokenEndpointClient`, a gateway subclass of the engine's token-endpoint client, holds the check. It overrides the one engine method every token response passes, the only place the token type is visible.
Four properties follow:

* *The check reads `cnf` from the token payload,* before the engine validates the signature over the same bytes. A token needs both the check and the engine's validation, so the early read can only refuse.
* *A non-JWT access token is refused.* It has no `cnf` to read.
* *The check judges token responses only,* never a token a session holds, so a key change ends no session through it.
* *A refresh token issued with a refused response is discarded,* not revoked at the identity provider.

== Alternatives rejected

The rejected alternatives are of three kinds. The first keeps a weak form reachable without anyone choosing it. The second takes away a choice the decision leaves with the operator. The third adds a setting, a file, a
dependency or code for something the key, the engine or the identity provider already settles, or relies on something the pinned engine does not offer.

Decision 1:

* *The mutual-TLS route.* The pinned engine cannot construct it: `MtlsClientAuth` throws in its constructor.
* *A gateway-side abstraction over the two routes.* The engine's `SenderConstraint` is the only seam a binding passes through, so a second abstraction would have one implementation and nothing to select.

Decision 2:

* *Removing the secret.* Key-based authentication, and an identity provider that can reach the gateway's key set, would become a precondition of every BFF deployment. The choice stays with the operator and is made visible instead.
* *A mode switch next to the secret.* It is a second key that can contradict the first.
* *Accepting a secret and a key file together and preferring one.* It is a silent choice between two credentials.
* *One key for both purposes.* It saves one file. The DPoP key would also sign client assertions, and FAPI 2.0 section 6.8 asks for one key per purpose.

Decision 3:

* *A retiring companion key.* A second published key would let a replacement overlap. One key per purpose keeps the key set, the assertion signer and the proof signer in step by construction, and replacement is a clean break.

Decision 4:

* *A Quarkus TLS-registry profile name.* It is the operator's stated non-preference. It would name a runtime construct for a key that is not TLS material, and add a second two-place edit of the kind ADR-0011 lists as a cost.
* *A `+${VAR}+` carrying the key itself.* The configured value would become the secret, which the configuration loader would have to classify and redact. A path discloses only a location.

Decision 5:

* *Classifying the pointer as a secret.* It would forbid the literal form and the defaulted placeholder for a value that discloses only a mount location.
* *A per-message judgement on naming the path.* A path is not a secret, but one rule for every refusal of this type is simpler to hold than a decision per message.

Decision 6:

* *Deriving the EC public key in the gateway's own code.* It removes the second block at the price of P-256 point multiplication in a security gateway: hand-written, variable-time curve arithmetic, or an unusual use of key agreement against the curve generator. The project would own either as cryptography.
* *Provided keys are RSA only.* One block and a public-API derivation, but provided deployments would sign `PS256` only, with larger assertions and proofs, while the generated mode stays EC: two key types depending on the mode.
* *A library that derives.* It needs a new dependency.
* *Two files instead of one.* It doubles the configuration keys to four and adds a way to mount the halves apart or mix them between purposes. The boot check is needed either way.

Decision 7:

* *A configurable key id.* An id an operator sets can stay the same across a key replacement, and an identity provider that caches by `kid` would keep verifying against the old key.

Decision 8:

* *An algorithm setting.* A setting can be set wrong. Without one, an operator cannot pick `PS384` or `ES384`.
* *Offering `EdDSA`.* The engine's `PrivateKeyJwtAuth` does not sign it, and supporting it for the proof key alone would add a third key type for one purpose.

Decision 9:

* *The endpoint URL of each leg as audience, or an array of audiences.* The profile excludes both, and a per-leg audience needs one authentication instance per leg.

Decision 10:

* *Static registration as the documented route.* Every key replacement becomes a second edit at the identity provider, and it cannot serve the generated mode.
* *A fixed path.* Every other gateway-owned path is a key of the `oidc` block, and a path the operator cannot move could shadow an equal proxied path.
* *`/.well-known/jwks.json` as the default.* It is conventionally an upstream's or an identity provider's own key set.
* *An empty key set in client-secret mode.* The endpoint would work, and it would state that the client has no key.
* *Releasing the path in client-secret mode.* A proxied upstream could answer under a URL an identity provider may still hold as the client's key-set URL, the key-substitution path the threat model names. A later move to a key could also meet a collision refusal.

Decision 11:

* *Falling back to a front-channel request when the push is unavailable.* A fallback an attacker or a misconfigured identity provider can trigger is the weak form with an extra step.
* *A new event type for a failed push.* It answers through the existing upstream-error event. The metric counts it in the upstream category, and the log record carries the attribution.

Decision 12:

* *Leaving the step-up seam on a front-channel request until it has a caller.* The first caller would ship the weak form unnoticed.

Decision 13:

* *A proof made by the gateway for each upstream call.* Not built. The gateway presents its DPoP key to the identity provider only, so a copy of the token taken on the upstream hop is as usable there as a bearer token.

Decision 14:

* *Overlapping-key support.* It is the companion key of decision 3 from the lifecycle side, rejected for the same reason.

Decision 15:

* *Nonce handling in the gateway.* Not built. Both gaps sit inside the engine's token client, below the seam the gateway wires.

Decision 19:

* *Recording the gap as a risk.* An identity provider that ignores the proof would be served while the gateway reports the sender constraint as in effect.
* *Checking the token type alone, or `cnf` alone.* The type alone is a label without a binding. `cnf` alone ignores that RFC 9449 section 5 marks a bound token by its type as well.
* *A check at each call site, or on the validated token content.* It needs several copies, and the token type is not visible at either place.
* *Re-checking the stored token on every request.* It would end every session at a key change.
* *Leaving it to the engine.* The check is not available at the pinned version.

== Consequences

=== Properties of the design

* In key mode the gateway holds and presents no symmetric client credential. `gateway.yaml` holds a path only. The identity provider needs the public key only, and what it stores beside that key is outside the gateway's control (decision 18).
* The authorization request does not travel through the browser. The redirect discloses a client id and an opaque reference.
* A party that checks proofs refuses, without the proof key, a token taken between the identity provider and the gateway. No party downstream of the identity provider does (decision 13).
* A key replacement is one action at the gateway. The key id changes with the key, and the endpoint is where the identity provider finds the new key.
* A single-node gateway starts with no key provisioned.
* PAR and the sender constraint have no weaker form. Client authentication has one, selected by an explicit key and announced at every boot.

=== Accepted costs

* Every BFF deployment needs an identity provider with a PAR endpoint. One without PAR refuses every login with `502`. A descriptor with `oidc.client_secret` keeps booting.
* The FAPI statement holds in key mode only. A deployment with `oidc.client_secret` does not implement the profile's client authentication.
* An identity provider that does not bind the access token to the proof key, or that issues opaque access tokens, cannot serve a BFF deployment.
* In key mode the identity provider must reach the gateway's JWKS endpoint server-to-server.
* A multi-replica deployment must provision key files and keep them identical across instances.
* An operator cannot choose the signature algorithm or use an `EdDSA` key.
* A provided RSA key file carries a public block the gateway could have derived.
* `gateway.yaml` has a second class of path-carrying keys, and the gateway reads private key material itself.
* The gateway's own bearer routes accept a bound token presented without a proof, because the gateway configures no DPoP check for any issuer.

=== Risks

* *The binding stops at the gateway.* An upstream cannot tell the forwarded token from a bearer token and must not try. The control is transport security on the upstream hop.
* *An unauthenticated endpoint on every host.* It publishes a public key and nothing else, reads no input and logs nothing above `DEBUG`. A proxied path equal to the JWKS path is shadowed, and the path is a key so an operator can move it.
* *A restart changes a generated key.* Logins after a restart depend on the identity provider fetching the new key on the unknown `kid`.
* *A key file is as protected as its mount.* The gateway checks content, not permissions.
* *The nonce gaps of decision 15.* An authorization server that issues nonces and enforces single use of assertions would refuse the engine's retry.
* *A copied descriptor selects the weaker authentication.* A descriptor with a client secret selects `client_secret_basic` without anyone deciding it. The boot warning and the documentation are the controls.
