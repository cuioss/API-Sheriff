== Status

Accepted

== Decision

The topology resolver runs before the configuration validator and turns configured aliases into a resolved topology. Two classes of alias reach it: the `base_url` aliases of enabled endpoints, which routing requires, and the additional aliases of the `tls.passthrough_sni` keys. Any alias may be unresolvable. The record settles which stage owns the resolvability judgement for each class.

*The decision:* resolution applies an asymmetric failure policy keyed to the alias class.

* An unresolvable *enabled-endpoint `base_url`* alias aborts boot. `TopologyResolver` collects the failure and ends its pass with one `TopologyResolutionException` carrying every failure of the pass. Routing cannot proceed without the alias, and no validator rule owns this class.
* An unresolvable *additional* alias is *skipped silently*. Resolution records only what resolves. `EdgeRules.validatePassthroughAliasResolvable` owns the rule and reports it with every other configuration violation in one aggregated pass.

A disabled endpoint's alias is exempt from resolution. An unresolvable placeholder or a malformed URL is collected from either class, because no validator rule owns those.

The governing principle: an earlier pipeline stage must not pre-empt a validation concern the configuration validator owns by throwing on the same condition. The validator is the single reporter of configuration-validation violations. The resolver supplies structured facts and does not adjudicate validator-owned rules.

== Alternatives rejected

=== Symmetric throw

The resolver would abort on any unresolvable alias. This is uniform and simple.

*Rejected because* it makes the validator's passthrough-alias rule unreachable dead code and aborts boot with a less precise, non-aggregated message. It destroys single-reporter ownership and degrades diagnostics.

=== Symmetric skip

The resolver would never throw, and the validator would own all alias resolvability.

*Rejected because* it defers routing-critical enabled-endpoint failures to a later stage and lets boot proceed further into an unroutable state before failing. Enabled-endpoint aliases are structurally required and have no validator rule, so failing at resolution is correct for them.

Both alternatives force one uniform policy on two alias classes whose ownership differs.

== Consequences

=== Properties of the design

* Every violation for additional aliases surfaces through one reporter, in a single pass with precise messages. The validator rule stays live.
* Routing-critical failures still fail at resolution, which keeps the boot-refusal property of link:0004-topology-indirection.adoc[ADR-0004] for the enabled-endpoint class.

=== Accepted costs

* Resolution's failure behaviour is deliberately non-uniform. A reader must know the class distinction to predict whether an unresolvable alias aborts or is skipped.

=== Risks

* A future alias class inherits neither policy automatically. Its author must decide which stage owns its resolvability and wire the abort or the skip accordingly.
