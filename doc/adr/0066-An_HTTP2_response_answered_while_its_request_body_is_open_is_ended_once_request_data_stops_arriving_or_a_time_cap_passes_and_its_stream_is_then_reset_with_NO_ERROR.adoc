== Status

Accepted

== Decision

An HTTP/2 server may answer a request before it has read the request body. An upstream does this when
it decides from the headers alone. The gateway does it for every answer it writes itself to an
upload: a problem document, an HTML error page, the portal page, a reserved-path answer, an asset, a
redirect, a short-circuit, a gRPC trailers-only status, an admission `503`, a framing rejection and a
reserved-body `413`. RFC 9113 §8.1 permits the server to send the complete response and then reset
the stream with `NO_ERROR`. The reset asks the client to stop sending without signalling an error.

A stream left half-open after a complete response puts the decision on the client. A client that
sees `END_STREAM` while it still uploads typically resets the stream itself. The HTTP/2 transport
counts those resets per connection against its Rapid-Reset limit. A burst of ordinary early answers
then looks like a reset flood: the transport closes the connection with `GOAWAY ENHANCE_YOUR_CALM`,
and every sibling stream fails with it.

The moment of the gateway's own reset matters in three ways:

* *Too late*, after the client has seen the complete response, and the client resets first.
* *Too early*, while request DATA frames are still on the way. The transport answers each such frame
  with its own `RST_STREAM(STREAM_CLOSED)` and counts those resets against the same limit.
* *Before the final frame is written*, while flow control holds it back. The reset discards the end
  of the response, and the client receives the status without the body.

Stopping the body has a second cost on the upstream leg. HTTP/1.1 cannot cancel one message, so a
reset of an HTTP/1.1 upstream request closes its connection. A gateway that closes first holds the
local port in `TIME_WAIT` for 60 s on Linux.

The record settles one question: *where does the decision to end a response live, at which moment are
the end and the reset written, and how does the gateway close the upstream connection it gives up?*

*Every response end on the edge passes one seam. An HTTP/2 response answered while its request body
is open stops reading the body at once. It holds its final frame until the client can send nothing
more, has stopped sending for a quiet period, or a hard time cap has passed. It then writes the end
and a `NO_ERROR` reset together. A gateway-closed HTTP/1.1 upstream connection is closed abortively.
The Rapid-Reset guard is left as it is.*

*The boundary with ADR-0060.*
link:0060-Dispatch_sends_a_bodyless_method_no_body_and_frames_every_declared-length_body_by_exactly_that_length.adoc[ADR-0060]
owns what crosses to the upstream and the request-body bounds. This record owns how a response ends
and how the upstream connection closes. The answers ADR-0060 produces end through the seam below, and
the upstream resets it makes close their connections as decided below.

=== One seam for every response end

A writer that has composed a response does not end it. It hands the call that ends it to the edge's
response-end seam (`ResponseEnd`, applied by `ResponseEnds.endResponse`). The edge decides when that
call runs. The relay and the gRPC trailers-only status writer end their responses through the same
seam as every answer the edge writes itself. A new writer inherits the rule by using the seam. The
decision has exactly two branches:

* *HTTP/1.x, or a request body that has already ended.* The seam ends the response at once and does
  nothing else. It never resets an HTTP/1.x request. Where the bytes behind a rejected request cannot
  be trusted, the connection is retired instead (`ConnectionRetirement`).
* *HTTP/2 with the request body still open.* The three steps below run.

There is no per-case mark. A framing rejection and a reserved-body `413` are early answers to an open
body and take the same branch.

=== Step 1 -- the body is stopped at once

As soon as the answer is decided, the gateway stops receiving the body. The seam marks the armed
inbound body as reset by the gateway. The upstream request still receiving the body is reset, so
nothing more is forwarded. The inbound stream is paused for good. A paused HTTP/2 stream returns no
flow-control window, so the client can send no more than the window it already holds. "Is request
data still on the way?" becomes a bounded question.

=== Step 2 -- the end waits until request data stops arriving

The seam holds the final frame back until the first of three conditions:

. the client can send nothing more: the smaller of the stream's and the connection's receive window
  is used up, or the client has ended or lost the stream;
. what the client may send has not changed for a quiet period;
. a hard time cap has passed since the wait began.

Only the first condition shows that no more request data can arrive. The quiet period infers it from a
client that is not sending. The cap ends the wait even while data may still be on the way.

Both windows count. Every stream draws from the shared connection window. A stream whose own window is
open can send nothing once the connection window is exhausted. And a sibling stream that the gateway
reads can refill the connection window.

The poll interval (`EarlyResponseEnd`), the 50 ms quiet period and the 1 s cap are gateway constants.
Vert.x exposes no per-stream flow-control state, so `InboundStreamWindow` reads the windows from the
Netty HTTP/2 codec underneath. It uses exactly one Vert.x internal and otherwise public Netty API,
read-only, on the connection's event loop. When that view cannot be attached, the seam ends the
response at once and resets the stream after the end has been written.

=== Step 3 -- the reset goes out right behind the end

The seam writes the end and the reset in the same event-loop turn as the look that allowed them. No
connection window that another stream returns in between can let the client send on this stream
before the reset arrives. Only when flow control holds the final frame back does the reset wait until
the frame has been written. A stream the client has ended in the meantime is complete and is not
reset.

=== The gateway's reset is the gateway's

The mark of step 1 lives in one place, the inbound body decorator `DispatchStage.InboundBody`. It
delivers one fixed gateway-reset cause to the body consumer and swallows any later transport failure
of the same stream. The streaming body counter recognises that cause. It resets the upstream request
once, but it records no client abort. A gateway-made reset is therefore never counted, metered or
logged as `INBOUND_BODY_ABORTED`. A client that drops its body before the response was decided still
is.

=== The admission `503` keeps the `NO_ERROR` reset

An upload rejected `503` by the admission cap is an early answer like any other. The one end rule
resets its stream with `NO_ERROR`, which also returns the credit its unread body held
(link:0060-Dispatch_sends_a_bodyless_method_no_body_and_frames_every_declared-length_body_by_exactly_that_length.adoc#unread-upload-bodies[ADR-0060]).
No reset code is chosen per case.

=== What the rule does not cover

The late rejection of a body on a bodyless method stays a `CANCEL` reset taken before any end
(link:0060-Dispatch_sends_a_bodyless_method_no_body_and_frames_every_declared-length_body_by_exactly_that_length.adoc#bodyless-method[ADR-0060]),
because that response is deliberately not completed. The WebSocket upgrade and the L4 passthrough
relay are not HTTP/2 response ends. No `quarkus.http.limits.rst-flood-*` key is set or changed.

[[abortive-upstream-close]]
=== A gateway-closed HTTP/1.1 upstream connection is closed abortively

Four triggers close a gateway-dialled HTTP/1.1 upstream connection while its request is still open.
An unauthenticated client can drive each of them at rate on a public upload route:

* *the early upstream answer*: the upstream answers before reading the body, and step 1 resets the
  upstream request;
* *the client abort*: the client drops its upload mid-body, and the dispatch ends as
  `INBOUND_BODY_ABORTED`;
* *the request-body idle timeout*: a partly sent body makes no progress for 10 s, and the dispatch
  ends as `REQUEST_BODY_TIMEOUT`
  (link:0060-Dispatch_sends_a_bodyless_method_no_body_and_frames_every_declared-length_body_by_exactly_that_length.adoc#request-body-idle-timeout[ADR-0060]);
* *the request-body deadline*: the body is still arriving 25 s after its attempt started, and the
  dispatch ends as `REQUEST_BODY_TIMEOUT`
  (link:0060-Dispatch_sends_a_bodyless_method_no_body_and_frames_every_declared-length_body_by_exactly_that_length.adoc#request-body-deadline[ADR-0060]).

The idle timeout and the deadline close the connection only when a body chunk had been forwarded.
`DispatchStage` sends the request head together with the first chunk, so a reset before that chunk
leaves the connection reusable. The other resets of the dispatch close the connection the same way: a body over the route
cap, a body beyond its declared length, a body on a bodyless method, an abandoned attempt and a relay
that fails to start.

Closed in order, each such connection held one of the gateway's local ports in `TIME_WAIT` for a
minute. The Linux default ephemeral range holds about 28,000 ports, so about 470 such closes a second
hold all of them. New connections to the upstream then fail. The per-upstream breaker counts those
genuine connect failures and opens, and every client of that upstream is answered `503`.

. *The close is abortive.* The default upstream client, used for every upstream not forced to HTTP/2,
  sets `SO_LINGER 0` (`EgressClients`). A connection it closes ends with a TCP reset and holds no
  local port. The option is client-wide: every connection this client closes ends this way, idle-pool
  evictions included. It is the client's public option, set once, for all four triggers. There is no
  drain, no half-close and no per-trigger exception. The forced-HTTP/2 client and the WebSocket client
  are unchanged, because an HTTP/2 reset ends one stream and leaves the connection open.
. *The breaker does not count the reset.* The guarded call
  (link:0064-The_upstream_guard_is_fixed_in_the_gateway_and_a_route_declares_no_circuit_breaker_settings.adoc[ADR-0064])
  returns as soon as the attempt's response head has been handed back. The relay, the end of the
  response and the reset of the upstream request after a complete response all run outside the
  guarded call. The breaker has recorded the call as a success and never sees the reset. No exclusion
  is added: the property holds by the structure of the dispatch, and a test pins it. Connect failures
  stay counted, because they are failures to reach the upstream.
. *The reset is not an error record.* A reset hands a `StreamResetException` to the upstream request's
  exception handler. Without a handler, Vert.x logged it as an unhandled exception at `ERROR`, once
  per reset. Every attempt's upstream request now carries a handler from the moment it is obtained.
  On HTTP/1.x a `StreamResetException` can only come from the gateway's own reset, so the handler
  drops it. Any other failure also reaches the send future or the response stream and is mapped
  there, so the handler logs it at `DEBUG` only.

Neither close keeps the connection for reuse. The connection is gone either way; the choice is only
how it ends.

== Alternatives rejected

*Raise or disable the Rapid-Reset limits.* Rejected because it weakens a connection-level protection
for every client to accommodate a stream shape the gateway itself leaves behind. The defect is the
half-open stream, not the limit. A higher limit only moves the burst size at which the connection is
lost.

*Have the upstream read the body before answering.* Rejected because an early answer is legitimate
HTTP. The gateway writes such answers itself on every rejection of an upload, so it has to end these
streams correctly whatever the upstream does.

*Keep reading the body to its end.* Drain or forward the rest of the body after the answer. Rejected
because it consumes bytes the answer has made pointless, for as long as the client takes to send
them, and leaves the stream's lifetime under the client's control. A `NO_ERROR` reset is the
protocol's own way of declining the rest of the body.

*Drain the upstream message instead of closing the connection.* Declining the body costs more on the
upstream leg, because HTTP/1.1 has no message-scoped cancel. Rejected all the same. The bytes that
would complete the upstream message are the client's; the gateway has no other source for them.
Draining the upstream message therefore means reading the inbound stream to its end, the alternative
rejected above. Completing it with invented bytes would hand the upstream a body nobody sent. The
outage came from the `TIME_WAIT` of an orderly close, not from the extra connection, so the abortive
close removes the cause and keeps every property of this decision.

*Reset only marked cases.* Keep a reset for selected rejections, the framing rejection and the
reserved-body `413`, and leave every other answer alone. Rejected because every answer to an open
body leaves a half-open stream. A mark each writer must remember is the per-copy rule that drifts.

*Reset right after the end has been written.* Rejected because the client may still have request data
in flight then. Each such frame draws a `STREAM_CLOSED` reset from the transport that counts against
the same limit. The trip moves from the client's resets to the server's own.

*Bound by the stream window alone.* Rejected because the connection window is shared. Once it is
exhausted, the stream's window says nothing. When a sibling refills it, the client can send on a
stream already judged quiet.

*Make the wait parameters configurable.* Rejected because they encode a protocol timing property, not
a deployment choice. No operator decision makes a longer hold-back correct, and a configurable cap
invites trading the property for latency per deployment.

*Reset an admission-refused upload with `REFUSED_STREAM`.* Rejected. The one end rule resets every
answered stream whose body is open with `NO_ERROR` and rejects a reset code per case. A separate code
for one answer would reopen that decision. `REFUSED_STREAM` also does not fit: RFC 9113 §8.7 uses it
for a stream closed before any processing took place, and a stream answered with a written `503` has
been answered.

*Confine the abortive close to the reset paths.* Rejected because a per-connection linger on a pooled
HTTP/1.1 client connection reaches a Vert.x internal.
link:0062-Platform_mechanisms_are_preferred_over_hand-rolled_equivalents_and_the_framework-agnostic_core_rule_is_retired.adoc[ADR-0062]
prefers the platform mechanism, and the client-wide option is that mechanism.

[[fin-first-rejected]]
*Close FIN-first.* Shut down the write side, drain the connection for about one second with a byte
cap, and fall back to `SO_LINGER 0` only when the drain fails. The motive is the upstream's view: a
`FIN` is retransmitted until acknowledged, while a reset is sent once. An upstream that does not
process the reset, because it was lost or because RFC 5961 makes the upstream answer an out-of-order
reset with a challenge ACK, might hold its side open. Rejected for three reasons:

* *A drain that succeeds brings `TIME_WAIT` back.* In a FIN-first close the gateway sends the first
  `FIN`. When the drain completes, the gateway holds its local port in `TIME_WAIT` for 60 s. That is
  the port-exhaustion mechanism this record closes. Each of the four triggers is in a client's hands,
  so every completed drain is a port a client can hold for a minute.
* *A drain that cannot complete adds only delay.* The `FIN` is queued behind the body bytes already
  sent. An upstream that has stopped reading holds those bytes behind a zero window, so the `FIN`
  does not leave before the drain budget is spent. The close then ends abortively anyway.
* *A per-connection close needs a Vert.x internal.* Vert.x exposes neither a half-close nor a
  per-connection linger on a pooled HTTP/1.1 client connection. The sequence would have to reach the
  Netty channel underneath, the internal ADR-0062 steers away from.

A Linux reproduction tested the upstream's side of the abortive close on four network variants. The
upstream reset at once on loopback, after one round trip with delay, and after one challenge ACK when
the reset overtook data in flight. Only when every reset segment was dropped did the upstream hold its
socket until its own idle timeout. FIN-first would not have changed that case: the upstream had
stopped reading, so its `FIN` would have stayed queued behind the body. The method, the variants and
the figures are in
link:../security-threat-model.adoc#gw-07-fin-first-reproduction[the threat model (GW-07)]. No
FIN-first variant was built or benchmarked. The pin test fails under an orderly close by construction,
so it cannot measure port exhaustion, and no test observes the gateway's own `TIME_WAIT` sockets.

The rejected options either change the wrong component, the guard, the upstream or the client's
upload, or place the reset at a moment the protocol does not make safe. The chosen design puts the
decision at the one seam every response end passes. It times the reset by what the transport knows
about the data in flight, and it closes the upstream connection the one way that costs no local port.

== Consequences

*Positive.*

* An early-answered HTTP/2 upload ends with one reset, written by the gateway. The client's own resets
  no longer accumulate against the Rapid-Reset limit. When the wait ends because the client can send
  nothing more, the transport writes no `STREAM_CLOSED` resets either. A burst of early answers no
  longer costs the connection and its sibling streams. The time cap gives no such assurance.
* The guard keeps its limits and its meaning. The gateway stops producing traffic that looks like a
  flood instead of making the detector more tolerant of floods.
* The rule is stated once and every writer passes it. A new writer cannot reintroduce a half-open
  stream.
* The rest of the body is never forwarded to an upstream that has answered. The stop does not depend
  on how, or whether, the transport surfaces the gateway's own reset.
* `INBOUND_BODY_ABORTED` keeps its meaning: a client-caused abort.
* A stream of early answers, aborted uploads, stalled bodies or trickling bodies no longer uses up the
  gateway's ephemeral ports, so it cannot open the per-upstream breaker for every client. The
  benchmark evidence is recorded with
  link:../security-threat-model.adoc#gw-07-upstream-ports[the threat (GW-07)].
* An early answer leaves no `ERROR` record in the log.

*Negative.*

* The final frame of an early answer on an open upload is delayed: by at most the quiet period for a
  client that has stopped sending, and by at most the cap for one that keeps sending. Every other
  response ends as it is written.
* The transport view reaches one Vert.x internal. A Vert.x upgrade that changes it degrades the rule to
  "end at once, reset after the write" rather than failing. That build then writes the in-flight
  `STREAM_CLOSED` resets again.
* Resetting an HTTP/1.1 upstream request costs the upstream connection. The next request to that
  upstream opens a new one.
* The upstream sees a TCP reset instead of a `FIN` for every connection the gateway closes, idle-pool
  evictions included, and on TLS no `close_notify`. An upstream that alerts on resets sees one per
  early answer.
* An upstream whose copy of the reset is lost keeps its side of the connection `ESTABLISHED` until its
  own idle timeout. The cost lands on the upstream's socket table, is bounded by the upstream's own
  timeout, and needs a lost segment on the gateway-to-upstream path, which a client cannot cause. It is
  accepted with link:../security-threat-model.adoc#gw-07-upstream-ports[GW-07].
* The response-end seam changes the contract of every writer: a writer hands over the call that ends
  the response. The relay and the gRPC status writer carry the seam in their signatures.

*Constraints on later change.* Each of the following reintroduces a defect this record removes:

* bounding sendable bytes by the stream window alone;
* writing the reset in a later event-loop turn than the end, for instance by always waiting for the
  write future;
* moving the reset back to the writers, or into a mark set only by selected paths;
* treating the time cap as the normal exit, or tuning it down to shorten the delay;
* moving the relay or the end of the response into the guarded call, which makes every early answer a
  breaker failure a client can drive. The pin test drives the reset after the dispatch has returned,
  so a change to where the edge ends the response has to be judged against this record;
* removing the client-wide `SO_LINGER 0` without a replacement, which brings the port exhaustion back;
* adding a drain to be polite to the upstream, which brings `TIME_WAIT` back;
* rewriting `GatewayEdgeEarlyResponseResetTest.earlyAnsweredUpstreamConnectionsAreClosedByReset` to
  accept an orderly close, which removes the guard on the abortive close.

The abortive close is pinned for the early answer and the client abort. It is not pinned by a test
for the request-body idle timeout or the request-body deadline. Those two triggers rely on the same
client-wide option.
