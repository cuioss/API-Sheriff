== Status

Accepted

== Decision

Inbound validation is a sequence of stages either side of route selection. The pre-route floor
(`BasicChecksStage`) runs before any route is known, so it measures every request against the
gateway-wide baseline. The post-route stage (`ThoroughChecksStage`) re-validates the same request under
the route's own configuration whenever that configuration diverges from the baseline. Both stages
measure the same properties of the same request. They differ only in the configuration they measure
against.

The shape is deliberate and stays. Route selection must decide on canonical, validated input, so some
validation precedes it. A route's declared posture must be applied to it, so some validation follows
it.

The shape has a failure mode with no natural detector. An exception is granted at a stage: a carve-out
admits a longer value for one header name, or a bound is stated as a guarantee. That stage is
reviewed and documented. A later stage that derives its own configuration from another source is not
obviously part of the decision. It reaches a stricter answer on its own. The stage that was reasoned
about admits the request, and the stage that was not rejects it.

Nothing about this is loud. Each stage is correct against its own configuration, and no validator is
missing. The defect lives only in the relationship between stages, and no single stage's code, tests
or documentation describes that relationship. Derivation fails the same way: when two stages each
build their own copy of a multi-component configuration, the copies agree only while someone
remembers both. A component added to one is silently dropped by the other.

The record settles what a validation stage owes a bound that another stage declared.

*A bound declared at one inbound-validation stage is either re-asserted at every later stage that
re-validates the same input, or explicitly delegated to a named later stage. Silence is not a third
option. One shared seam owns the derivation that realises the bound; no stage reconstructs it.*

Three obligations make the property hold.

=== Re-assert or delegate, never assume

A stage that re-validates an input inherits every bound declared about that input. Either it applies
the bound under its own configuration, or the declaring record names the stage the check moves to and
what that stage validates instead. Delegation is legitimate and in use. A request that ends at a
reserved path never reaches the post-route stage, and its parameter validation moves to the reserved
handler, which knows each parameter's grammar. That check is stricter than the generic one. What is
not legitimate is a bound that stops at a stage boundary because nobody asked where it stopped.

A gate whose bound holds only because of what its caller passes has outsourced its bound. Such a gate
re-checks the condition itself, so its stated bound is true of the gate under any input.

=== One derivation seam, not one per stage

Where several stages derive the same policy from different configurations, the derivation is written
once and takes the configuration as a parameter. The shared seam,
`SecurityConfigurations.builderSeededFrom`, copies every component of a stage's resolved configuration
into a builder. The caller then overrides only the dimension its exception changes: `SecurityPostures`
before route selection, `ThoroughChecksStage` after it. Each stage's answer then differs in exactly the way the stages differ, the
configuration it was handed, and in no other way. That is what makes a bound like "only the length cap
changes" structurally true rather than asserted in a comment. A seeding that carries every component
forward cannot drop one. A per-stage copy of a component list must be maintained twice, and will not
be.

=== A relaxation relaxes in the same direction at every site

A relaxation must relax at every site that honours it. A site that derives a stricter value than the
bound it implements inverts the exception. That happens most easily where the site's configuration
differs from the one the bound was reasoned against, so each site states its direction. Where a value
below the baseline is a legitimate input from another subsystem, the site clamps. Where it is an
operator error, the site is a boot refusal, so the diagnostic is not traded for a uniform mechanism.

*The diagnostic question.* Wherever one input is validated more than once against different
configurations, an exception granted at one point is a statement about the input, not about the
point. Before granting one, ask: which other component re-examines this input, and under which
configuration? Each answer is either "it applies the same exception, derived from its own
configuration" or "the exception is delegated to it, and it validates the input another way". A
component that gives neither answer is where the exception ends, quietly.

*Boundaries.* This record owns the principle. The records that apply it own their bounds:

the reserved-path delegation and the two header carve-outs, with their per-site directions;
link:0029-The_GET-with-body_opt-in_relaxes_only_the_Content-Length_leg_and_is_necessarily_gateway-wide.adoc[ADR-0029]

the map of which check lives at which stage.

== Alternatives rejected

*Let each stage derive its own policy from its own configuration, and document the relationship.* This
is the smallest arrangement and keeps each stage independently understandable. Rejected because
documentation is the mechanism already seen to fail in exactly this position. A bound stated as a
guarantee in prose, with nothing structural behind it, diverged from the shipped behaviour and no check
noticed. Prose cannot enforce a relationship between two components that never reference each other.

*Collapse validation into a single stage so no relationship exists.* This removes the failure class
instead of managing it. Rejected because it cannot be built. Route selection must decide on validated
input, and a route's declared posture must be applied to it. So at least one check must precede route
selection and at least one must follow it. Deferring all validation until after route selection means selecting a
route on unvalidated input, a strictly worse exposure.

*Make the later stage skip inputs an earlier stage already accepted.* This makes the first decision
final and needs no shared derivation. Rejected because it discards per-route posture. A route stricter
than the gateway would no longer be stricter, and the route-level configuration would silently stop
meaning anything for every property the floor also checks. It fixes the disagreement by deleting one
side of it.

*Enforce the property with a test per carve-out rather than a structural seam.* Tests are cheap and name
the invariant. Rejected as the primary mechanism because a test asserts the cases someone thought to
write. This failure mode is precisely a stage or a component nobody thought about. Tests stay valuable
as controls, but they detect a known instance; they do not prevent the class.

The rejected options fall into two kinds. One kind removes the relationship by removing a capability
the architecture needs: per-route posture, or validation ahead of route selection. The other kind keeps the
relationship and relies on someone remembering it. The chosen position keeps both stages and both
capabilities, and makes the relationship a component with a name.

== Consequences

*Positive.*

* A relaxation's stated blast radius is its actual blast radius at every stage, so the list a reviewer
  reads is the one the gateway enforces.
* A defect in the relationship between stages becomes a defect in one shared seam, where it can be
  reviewed and tested.
* Adding a validation stage, or a carve-out to an existing one, carries an explicit obligation: list
  the stages that re-validate the same input and state each one's position.
* A configuration component added to the model reaches every derived policy, instead of reverting to a
  default at the site nobody updated.

*Negative.*

* A new carve-out costs more than its declaring site. The author walks the pipeline and states a
  position per stage, even where the position is "unchanged".
* The shared seam couples the stages that use it. A change to the seam is a change to every stage. That
  is the intended trade, but it constrains changing one stage alone.
* The direction is uniform, the mechanism is not. Clamping at one site and a boot refusal at another
  is deliberate, and each site must state it or it reads as an inconsistency.

*Accepted failure modes.*

* *Stage inventory drift.* The obligation is only as good as the list of stages that re-validate a
  given input. A new stage that derives its own policy brings back exactly this failure, silently.
* *Delegation without a receiver.* Delegation moves a check; it does not remove it. It holds only
  while the named receiver performs the check. A delegation whose receiver never implements it looks,
  from the pipeline, like an omission.

*Constraints on later change.*

* A stage under pressure to differ "just slightly" from the shared derivation is the first step back
  to per-stage copies. The seam has no per-stage branch, and that is its value.
