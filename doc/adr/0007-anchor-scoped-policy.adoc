== Status

Accepted

== Decision

=== The question

The configuration model groups routes into endpoint files that share one `base_url` alias and an endpoint-level `auth` default. No policy scope sits above the endpoint, and nothing owns a URL namespace. As the route population grows, two problems follow:

* *Duplication.* An invariant like "every call under `/api` presents a valid bearer token from the configured identity provider" must be restated in every endpoint file under `/api`. The same holds for the inbound-filter profile and the response-header posture of a surface like `/bff`.
* *No namespace guarantee.* Nothing stops a new endpoint file from placing a route under `/api` with a weaker posture. The invariant lives in the operator's head, which is a fail-open risk for a security gateway.

*The decision:* an anchor is a named policy scope declared in the gateway configuration. It owns a URL path namespace (`path_prefix`) and may carry policy blocks. The boot enforces the namespace, and anchors are gone by the time a request arrives.

=== Namespace ownership

* *Prefixes are pairwise disjoint.* No anchor prefix is a prefix of another. The boot refuses an overlap.
* *Exactly one anchor per route.* A route declares membership at the endpoint level (`anchor:`) and may override it per route, and the gateway never derives it. A route exposed on two surfaces, such as one upstream under `/api` with bearer and under `/bff` with session, is two routes.
* *Namespace enforcement.* When an `anchors` block is configured, every enabled route's `match.path_prefix` must fall inside its declared anchor's `path_prefix`, and every route whose path falls inside any anchor's namespace must declare that anchor. The boot refuses a mismatch and an undeclared squatter. Without an `anchors` block nothing changes.
* *Namespace coverage, the mirror of the squatter rule.* The two rules above judge a route by where its own match key sits. A route outside and above an anchor is judged by neither, while route selection still lets it serve addresses inside the namespace. The boot therefore refuses a prefix route whose namespace strictly contains an anchor's `path_prefix` and which does not declare that anchor, unless a prefix route declared at the anchor's own `path_prefix` covers the namespace. Longest-prefix selection then gives every address inside it to that member. Covering means matching the whole namespace: a candidate that narrows on `match.methods`, `match.host` or `match.headers` serves only part of it, so the boot does not accept it as coverage. This rule became load-bearing with exact routes: an anchor whose only member is `path: /admin` claims one address and leaves `/admin/` and `/admin/x` to the enclosing route. The rule does not judge exact routes, because an exact route serves one address, which is the squatter rule's case.

=== gRPC routes and the two containment directions

A `protocol: grpc` route is exempt from the containment rule and the squatter rule, and from those two only. It rides the service-rooted `/{package}.{Service}/{Method}` path, whose service component is a single opaque path segment. No non-root anchor prefix can contain such a path on a segment boundary, and a stock gRPC client cannot be told to prepend a gateway namespace prefix.

The coverage rule still applies to a gRPC route, because it reads the other way. The exempt rules judge a route by where its match key sits, which is what the service-rooted argument is about. The coverage rule judges what the route's `path_prefix` contains, and nothing constrains a gRPC route's match key to a bare service path. Route selection is protocol-blind, so a gRPC route with a broad `path_prefix` answers plain HTTP requests inside a swallowed namespace with its own auth posture and `security_headers` block. Exempting it would reopen the bypass the coverage rule closes.

Only the path-prefix geometry is exempt. A gRPC route still declares an anchor for its link:0013-anchor-type-access-axes.adoc[ADR-0013] classification and its auth floor, and every other anchor rule stays enforced. `websocket` and `http` routes keep full containment enforcement.

=== The auth floor cannot be weakened

If an anchor declares `auth.require` of `bearer` or `session`, the boot refuses a member whose effective auth resolves to `require: none`. Overriding between non-`none` postures, such as anchor `bearer` and route `session`, is a replacement, not a weakening, and the boot allows it. A non-auth override that relaxes an anchor limit is a replacement announced by a boot WARN, as described below.

Endpoint `auth` is optional for an anchored endpoint whose anchor declares `auth`. An endpoint without an anchor-provided posture must still declare it. Every route has a non-ambiguous effective auth from route, endpoint or anchor, or the boot refuses it.

[[amendment-a2]]
=== One declared rule, resolved by `PolicyBlock`

*One rule, declared once per block.* Every policy block is a `PolicyBlock` descriptor naming the policy scopes it is declarable at, along the chain `gateway -> anchor -> endpoint -> route`. The nearest declared scope wins and replaces every broader declaration whole, never merged. `null` and an empty list both count as not declared. With no scope declaring the block, its fallback applies: a value, no block or a boot refusal. The route-table builder and the configuration validator both resolve through the descriptors.

The live inventory is `PolicyBlock.ALL`, and link:../user/anchors.adoc#_policy_block_scopes[its operator-facing scope table] is the list a contract test binds to the descriptors. link:0067-Every_policy_block_is_one_declaration_resolved_nearest_declared_scope_wins_with_whole-block_replacement.adoc[ADR-0067] records why each set stops where it does and the two field-level fallbacks kept as exceptions.

*The override WARN is derived, not listed.* A block whose descriptor opts in is announced when the route's anchor declares it and the route's endpoint or the route itself declares it too. The Override WARN column of the live scope table marks the blocks that opt in. The auth floor stays a boot refusal.

=== Anchors vanish at runtime

`RouteTable` assembly resolves anchors into the materialized per-route effective values. The request pipeline never sees an anchor and performs no runtime lookup, and the boot log can print the effective posture per route.

[[amendment-a1]]
=== `security_headers` apply after route selection; CORS stays global and pre-auth

An anchor's `security_headers` block must take effect on the wire, and a CORS preflight must be answered before authentication, which runs after route selection. The stage therefore splits in two positions:

* *Stage 0* keeps CORS: the preflight short-circuit and the `Access-Control-Allow-*` headers of an actual request. It also seeds the gateway-owned response security headers (`Strict-Transport-Security`, `X-Content-Type-Options`, `X-Frame-Options`) from the global block.
* *Stage 2a* runs after route selection and before the verb gate. It removes every gateway-owned security-header name from the response and seeds the selected route's resolved block.

*Pre-route responses keep the global block.* A stage-1 rejection, a `404` for an unrouted path and the CORS preflight carry the global block, because no anchor is known yet. Every other response after stage 2a carries the route's block.

*The anchor block replaces the global block whole.* An anchor block declaring only `frame_deny` drops the global `Strict-Transport-Security` for its routes. An operator who wants both declares both on the anchor.

*CORS is global only.* It is evaluated before route selection, so an anchor cannot scope it. The bundled schema accepts `cors` in the global `security_headers` block only, so the boot refuses an anchor-level `cors` block.

Stage 2a never touches CORS headers or other accumulated non-security headers, such as `Allow` or `WWW-Authenticate`.

[[amendment-adr-0073]]
=== A rejection before the trust boundary carries the global block

On the shipped default, a rejection raised after route selection and before the trust boundary is answered as the unrouted `404` (link:0073-Untrusted_callers_get_the_unrouted_404_for_every_rejection_raised_before_the_trust_boundary.adoc[ADR-0073]). The gateway restores the response headers the request had before its route was selected, so that answer carries the global block, as an unrouted `404` does. The verb gate's rejection is one such case. With `security_defaults.uniform_not_found: false`, those rejections carry the route's block.

== Alternatives rejected

=== Keep duplicating everything per endpoint

KrakenD has no inheritance and keeps everything flat per endpoint, which is viable because its configurations are typically machine-generated.

*Rejected because* it scales poorly for hand-authored files and leaves the fail-open risk open: the policy floor exists in N places, and one omission is an open endpoint.

=== Group by named reference instead of URL prefix

APISIX bundles plugin settings in named Plugin Config objects that routes reference by ID. Traefik composes named middlewares as an explicit ordered list per router. Most surveyed products group this way.

*Rejected because* reference-based grouping cannot express "nothing may appear under `/api` without this posture". For a security gateway, binding policy to a namespace the anchor owns buys boot-time namespace enforcement, which the reference model cannot.

=== Merge a nearer block into a broader one

Key-level merging would let a nearer block override only the keys it declares.

*Rejected because* nobody who survived does it. Kong's most specific scope replaces the whole plugin configuration, APISIX overrides per plugin wholesale, and OpenAPI overrides `security` by replacement. NGINX's array directives silently replace rather than merge at lower levels, the canonical cautionary tale for implicit merge expectations. Whole-block replacement is the rule the model already had.

=== Hierarchical policies with separate defaults and overrides

The Kubernetes Gateway API (GEP-713) attaches hierarchical policies with separate defaults and overrides semantics.

*Rejected because* it was widely criticised for a discoverability problem ("why does my route behave this way?") that needed extra status machinery. The hierarchy stays shallow here, and the boot log prints the effective result.

=== A child that places its parent's policy explicitly

Azure API Management's child policy places a `<base/>` element marking where the parent chain executes, so the child sees and controls its inheritance.

*Not adopted.* The survey records no failure of this design. The gateway answers the same visibility need with the boot log of effective postures, and the auth floor must hold whether or not a member asks for it.

=== Allow a route to belong to several anchors

A route exposed on two surfaces would declare both.

*Rejected because* it reintroduces the merge-order ambiguity every surveyed product avoids. The two surfaces need different auth anyway, so two routes cost little.

== Consequences

=== Properties of the design

* Namespace invariants become structural. "Everything under `/api` presents a bearer token" is declared once and enforced at boot, and a forgotten declaration is a boot refusal, not an open endpoint.
* Endpoint files shed repeated posture blocks and keep locality: an override is declared in the endpoint file, and the boot log shows the result.
* The boot validator and the route table cannot resolve a block differently, because there is one resolution.
* A contract test binds a block's descriptor scopes, both bundled schemas and the user-documentation scope table, so a scope added in one place and not the others fails the build.
* Anchor-scoped response headers take effect on routed responses, so the posture the boot log prints is the one served.
* A browser preflight never reaches route selection, authentication or an upstream.

=== Accepted costs

* The chain has one more rung, four levels with one override rule. Forbidding merge and multi-membership and erasing anchors before runtime keep the complexity below what the Gateway API reached.
* The same upstream on two surfaces costs one extra route entry per surface.
* A configuration that places `cors` under an anchor is a boot refusal. The fix is to move the block to the global `security_headers`.

=== Risks

* A boot rule that enumerates declarations instead of resolving the block must be widened by hand when a block gains a scope. link:../development/README.adoc#_adding_a_policy_block[The contributor guide] lists that obligation.
