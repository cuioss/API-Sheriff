== Status

Accepted

== Decision

The edge admits work through a counting semaphore. A request acquires one permit before a virtual thread is dispatched, and a request that cannot acquire one is rejected with `503`. The permit is released from the request's completion hook. That accounting is exact for the request and response shape.

A WebSocket upgrade breaks the shape. The upgrade takes the connection over, the completion hook never fires for an established relay, and the connection outlives the exchange by an unbounded interval. Two failure modes follow. If the permit is released at the upgrade, occupancy under-counts. If it is held for the lifetime, a modest population of long-lived relays occupies a pool sized for short turns. No release point avoids both. The record settles what a relay is with respect to admission, and which second bound that answer needs.

*The decision:* a WebSocket relay holds its general admission permit for the connection's entire lifetime and additionally acquires a dedicated relay sub-budget. Both budgets are operator-facing configuration, because a cap sized against a deployment's memory limit, traffic mix and connection lifetimes cannot be a compile-time constant. The relay budget's implicit value is derived from the general budget.

=== Lifetime-scoped release

The general permit is released when the relay closes, not when the upgrade completes. `TerminalDispatch.dispatchWebSocket` hands the relay a release callback over the request's admission guard, and every relay teardown path invokes it. `EdgeAdmission.releaseAdmission` returns each permit behind its own latch, so each returns exactly once whichever teardown path runs, including an upstream-dial failure that ends the response.

=== A sub-budget acquired in addition

`websocket_relay_cap` bounds how many in-flight requests may be established relays. A relay holds two permits: the general one, which keeps occupancy exact, and the relay one, which keeps relay pressure from consuming the general pool. The gateway rejects an upgrade beyond the relay cap with `503` and releases the general permit on the way out. A relay cap above the admission cap can never bind, so the boot refuses that pair (`LimitRules.validateEdgeHardening`).

=== Proportional defaulting

Both members of the `edge_hardening` block are independently omissible. An omitted block resolves to the documented defaults. An omitted `websocket_relay_cap` resolves to a quarter of the effective admission cap, floored at one (`EdgeHardeningConfig.effectiveWebsocketRelayCap`). The ratio is what the default preserves. Declaring only a small `admission_cap` yields a correspondingly small relay cap, not an implicit constant the boot then refuses. At the shipped admission default the derived quarter equals the documented relay default.

An explicitly declared relay cap is honoured verbatim, including one above the admission cap, which stays a boot refusal. Derivation fills a gap and never overrides an operator.

== Alternatives rejected

=== Release the admission permit when the upgrade succeeds

The minimal shape treats the upgrade as the end of the HTTP exchange.

*Rejected because* it makes the counter lie in the direction that matters. Established relays consume connections, threads and buffers while invisible to admission, so the cap no longer bounds concurrency and an operator reading the gauge is misled. It converts an over-counting bug into an under-counting one.

=== Hold the permit and add no second bound

Accounting stays exact and relays draw from the general pool alone.

*Rejected because* it trades an accounting defect for a starvation defect. Long-lived relays would occupy a pool sized for short turns and reject HTTP traffic that has nothing to do with them.

=== Clamp the implicit relay cap at `min(fixed_default, admission_cap)`

This stops a partially declared block from resolving to a self-rejecting pair.

*Rejected because* the clamp collapses the two budgets into one at any admission cap below the fixed default. The relay cap equals the admission cap, the sub-budget can never bind, and relays may again consume the entire pool. That reintroduces the starvation in the small-deployment configurations that can least absorb it. A proportional derivation preserves the separation the clamp destroys.

=== Move the cap accessors onto the class that consumes them

The caps are read where the semaphores open, so hosting them there would shorten the path from configuration to use.

*Rejected because* the caps do not travel alone. The reserved-body ceiling derives its worst-case bound from the admission cap, and the drain timeout is sized against the same in-flight population. Splitting the group would put a derived bound in one owner and its input in another. The inbound-bound group stays under one owner, `EdgeHardeningOptions`, because its members are defined in terms of each other.

An admission counter must count the resource it claims to count, for the whole time that resource is held. Where that lets one class of work monopolise a shared budget, the answer is a second bound on that class. Where a bound's implicit value must stay consistent with another bound, it derives from that bound.

== Consequences

=== Properties of the design

* Admission occupancy is exact for every shape of work the edge admits, so the cap bounds the resource it is meant to bound.
* WebSocket pressure and HTTP pressure are bounded independently. Relay saturation rejects further upgrades and leaves the remaining general headroom to ordinary traffic.
* The budget is sized in the deployment, where the knowledge lives. An operator who never writes the block keeps the shipped behaviour.
* A partially declared block is internally consistent by construction.

=== Accepted costs

* A relay occupies a general permit for its whole life, so the general cap must be sized with the relay population in mind. This is the reason the cap became configurable in the same decision.
* Two budgets exist where one did, and an upgrade acquires and releases two permits.
* The derived default couples the two members: changing `admission_cap` changes the implicit relay cap. The coupling keeps the pair consistent, and the relay bound is stable only when declared.

=== Risks

* A change that releases the general permit at upgrade time restores the under-counting with no signal beyond the admission-exhaustion regression coverage. That regression runs against the deployed container with a deliberately low cap, so it exercises the real accounting.
* A relay that leaks its close signal leaks two permits. The latches bound double release, not non-release. Non-release stays bounded only by the transport's own idle reaping.
