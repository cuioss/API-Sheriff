== Status

Accepted

== Decision

=== The question

A BFF session holds a refresh token. When the mediated access token nears expiry, the gateway redeems it
through the confidential-client engine. It persists the rotated tokens through the `SessionBinding` seam of
link:0018-BFF_session_mode_is_one_SessionBinding_seam_behind_a_fixed_reserved-path_and_CSRF_model.adoc[ADR-0018].
That redemption can fail in five ways, and what the gateway may safely do depends on what the identity provider did
with the presented token:

* *The identity provider never processed the grant:* a connection or DNS failure, a `5xx`, or a `4xx` it did not
  attribute to the credential. The presented token is still valid. Destroying the session turns every blip into a mass
  logout.
* *The identity provider rejected the credential:* `invalid_grant`. The token is unusable, and keeping the session
  keeps serving a withdrawn grant.
* *The identity provider redeemed the grant, but the gateway refused the response.* The presented token is spent, and a
  successor may now be live that no session holds.
* *The redemption succeeded, but the rotated session could not be persisted.* The presented token is spent and the
  returned one is orphaned.
* *The redemption succeeded, but the session was terminated meanwhile.* A logout or a back-channel logout destroyed the
  session while the exchange was in flight. Writing the rotated session would bring a logged-out session back.

A second question sits beside the first. RFC 9700 §4.14 asks for refresh-token rotation with reuse detection: a replayed,
already-rotated token revokes the grant. That detection must live somewhere. A confidential client only sees the refresh
tokens it presents, and the instances of the cookie-based BFF share nothing. The replay is also reachable there: an older
sealed session cookie still unseals after a refresh, so a copied cookie makes the gateway present a spent token. Ending a
cookie-based session destroys nothing server-side. A client that keeps presenting an ended cookie would therefore make the
gateway present that token on every near-expiry request.

*The decision:* the engine's failure kind disposes a refused refresh, through a default-free switch. The session's fate
follows from the kind, not from configuration. `oidc.session.refresh.on_failure` decides only how a request left without a
token is answered. Reuse detection is the identity provider's job. The shipped control is strict refresh-token rotation at
the identity provider, and the gateway builds no token family.

=== The per-kind dispositions

`TokenRefreshCoordinator` switches over the kind `RefreshFlow.classify` returns, with no `default` branch. A new kind in the
engine therefore fails compilation rather than inheriting a disposition.

[cols="2,2,2,2", options="header"]
|===
| Kind | Session | Revoked (best-effort) | Record

| `PRE_REDEMPTION`
| Kept. The gateway mediates the current access token while it is valid. Once it expires, the request fails and the session
  stays. The next attempt waits out a fixed five-second back-off.
| Nothing. The presented token is still valid.
| `ApiSheriff-127`

| `CREDENTIAL_REJECTED`
| Ended.
| Nothing. Nothing was redeemed.
| `ApiSheriff-111` `credential-rejected`

| `REDEEMED`
| Ended.
| The one live refresh token the gateway can name: the successor when rotated, the presented token when not rotated, none when
  rotation is unknown.
| `ApiSheriff-111` `redeemed-response-refused`

| Persist failure
| Ended.
| The refresh token the exchange returned.
| `ApiSheriff-111` `persist-failure`

| Session terminated at the persist (server-session BFF)
| Stays ended. A logout or a back-channel logout destroyed it while the refresh was in flight. The gateway does not write the
  rotated session.
| The refresh token the exchange returned.
| `ApiSheriff-111` `session-terminated`
|===

The engine classifies neither of the last two rows: in both, the exchange succeeded. They differ in what the `SessionBinding`
seam answered when the gateway wrote the rotated session:

* A *persist failure* is the binding raising an error. It could not hold a session that was still there, for example a sealed
  session cookie past its size budget. This is a fault to investigate, and the record carries the causing exception.
* *Session terminated at the persist* is the binding reporting the session gone. The seam's updating write never creates a
  session (ADR-0018), so the gateway does not write back a session a logout destroyed. A logout overtook a refresh, and the
  record carries no exception.

Only a binding that holds server-side state can report the second, so that row applies to the server-session BFF. A stateless
binding cannot observe a logout and re-seals the rotated session.

Both refresh legs share all five rows: the near-expiry refresh and the scope-driven one of
link:0057-Session_routes_obtain_their_declared_scopes_by_refreshing_inside_the_grant_and_widening_the_live_session_outside_it.adoc[ADR-0057].
A request coalesced on the session's single-flight receives the leader's outcome in each.

Revocation goes through the engine's RFC 7009 `RevocationClient`, built from the same back-channel client configuration the
refresh uses. It is best-effort. The gateway records a failed revocation at `DEBUG`, and it never changes the disposition,
because destroying the local session is what ends the session. Every session-ending disposition clears the session cookie on
the response.

The revocation runs after the disposition:

. The gateway destroys the session and records `ApiSheriff-111` synchronously.
. It publishes the session-ended outcome to the failing request and to every request coalesced on the single-flight.
. Only then does it dispatch the revocation, off the request path, on the virtual-thread executor.

A slow or hanging revocation endpoint therefore delays the revocation and nothing else. A fixed limit bounds concurrent
revocations. When the limit is saturated the gateway skips the revocation and records it at `DEBUG`, and it swallows a refused
dispatch the same way.

=== The back-off

The back-off is fixed rather than exponential. It is bounded in the number of sessions it tracks, read and written under the
per-session single-flight, and per instance. Below that bound it limits engine calls and `ApiSheriff-127` records to one per
session per window during an outage.

Once unexpired windows saturate the bound (expired ones are pruned first), the gateway no longer tracks a session without its
own window individually. One coarse overflow window governs all such sessions:

* The first untracked session at the saturated bound atomically claims the window before its engine call. So does the first one
  after the window elapses.
* Every other untracked session makes no engine call and records nothing until the claimed window closes.
* The claim is released once the identity provider processes the probe's grant, or once the failing probe can be tracked on its
  own window. It is kept while the bound stays saturated.

The throttle therefore degrades to one attempt per overflow window rather than disappearing under the largest outages. The
accepted trade: a session that has not failed itself may see its refresh deferred for up to the fixed back-off while the bound
is saturated. The gateway mediates its still-valid access token meanwhile. With a healthy identity provider the same claim
serialises untracked refreshes to one in flight, only until the saturating windows expire.

=== `on_failure` answers the request, not the session

The coordinator's outcome reaches `SessionAuthenticationStage` as a sealed result with four members: *mediate*, *session ended*
(clear the cookie, then respond), *request failed* (respond and keep the cookie, because the session is live) and *no session*
(respond and keep the cookie). The last one means the refresh leader resolved no session from this request's own cookie. The
coordinator destroyed nothing, and the browser may already hold a cookie a step-up has just re-issued. The stage answers all three
failure members through the effective `on_failure` value:

* `reauthenticate`, the default also when the key is omitted, re-drives the login negotiation for navigations and answers `401`
  problem+json otherwise.
* `reject` answers `401` problem+json for every request.

The boot refuses an unrecognised value with `CONFIG_INVALID`. An operator who wrote `reject` and got `reauthenticate` would never
find out.

=== Reuse detection belongs to the identity provider (option D)

The gateway builds no `RefreshTokenFamily`, no `TokenLifecycleManager` and no shared family store, and it does not ask the engine to.
A confidential client cannot tell a replayed token from a fresh one without remembering every token it ever presented. A stateless
instance cannot remember what a sibling did. The party that can recognise a replay is the one that minted the token.

The shipped control is strict refresh-token rotation at the identity provider: on Keycloak, `revokeRefreshToken: true` with
`refreshTokenMaxReuse: 0`. Both the integration realm and the compose-sample realm enable it. The identity provider rejects a replayed
token with `invalid_grant`, the engine classifies that as `CREDENTIAL_REJECTED`, and the gateway ends the session. No gateway code decides
whether a token is a replay: the replay path is the credential-rejected path.

=== The gateway refuses an ended cookie-based token locally

Detection stays with the identity provider, but the gateway does not re-ask an answered question. In the cookie-based BFF an ended sealed
session cookie still unseals. Without a guard, every near-expiry request carrying it would drive another refresh grant and another
`ApiSheriff-111` warning until the absolute TTL.

When `TokenRefreshCoordinator` ends a cookie-based session, for any reason
link:../LogMessages.adoc#apisheriff-111[`ApiSheriff-111`] records, it marks the presented refresh token in `EndedRefreshTokens` until the
session's absolute lifetime. The mark is a salted, non-reversible SHA-256 digest with a per-instance random salt, never the token or the
cookie. A later request presenting a marked token is disposed as session-ended: the cookie is cleared and `on_failure` negotiated, with no
engine call, no revocation and only a `DEBUG` line.

The key is the token, not the session. Every cookie of one cookie-based session derives the same session identity, so a session-keyed marker
would also refuse the legitimate successor cookie. With the token as key the gateway refuses the exact ended cookie locally. A successor
still reaches the identity provider once, is rejected there, and is then marked.

The marker is bounded, in memory and per instance. RP logout does not set it. It is inert in the server-session BFF, where destroying the
stored session already ends every copy. It is a negative cache of tokens the gateway has seen ended, not a token family: it recognises no
replay the identity provider has not already rejected.

=== Keycloak's verdict is observed and pinned

`BffRefreshReuseIT` records what Keycloak does on a detected replay and asserts it. An upgrade that changes the verdict turns the suite red
rather than silently changing what an operator relies on:

* *The successor grant is revoked too.* After a replayed pre-refresh cookie is rejected, the successor cookie's own refresh is rejected as
  well, answered `401` with a clearing cookie and its own `credential-rejected` record. A replay burns the grant, not only the copy.
* *The Keycloak user session survives.* The session the login created still exists after the replay, with the client attached. The revocation
  covers the refresh grant, not the whole SSO session.

The same suite proves two adjacent claims. Deleting one Keycloak session ends exactly the server-session gateway session behind it, while a
sibling session of the same user keeps refreshing. Deleting the session behind a sealed session cookie ends that cookie session on its next
refresh.

== Alternatives rejected

=== A. Keep destroy-on-every-failure

One rule for every failure, and `on_failure` left as documentation.

*Rejected because* it conflates a blip with a withdrawn credential, logging users out during outages. It also leaves the spent-but-live tokens
of the redeemed and persist-failure cases unrevoked. The engine's classification exists, and ignoring it discards information the safe
disposition depends on.

=== B. A gateway-side in-memory token family

Track each session's refresh-token lineage in the gateway and revoke the family on a superseded token.

*Rejected because* the gateway only sees tokens it presents. A token stolen and redeemed directly at the identity provider never passes through
the family. Stateless instances cannot share it either, so a cookie replayed against a sibling instance is invisible to the instance that rotated
it. It would cover the one path strict rotation already covers, less completely, at the cost of per-session state in a variant that exists to have
none.

=== C. A shared family store for the stateless variant

Back the family with a store every instance reads.

*Rejected because* it reintroduces the external dependency the cookie-based BFF exists to avoid, and it still sees only gateway-presented tokens. The
identity provider already holds the authoritative lineage.

=== D. Strict rotation at the identity provider (chosen)

The one place that sees every redemption of a refresh token is the identity provider that minted it, and every mainstream one offers rotation with
reuse detection. The gateway disposes the refusal correctly and proves, against a real identity provider, that it does.

A control belongs to the party that holds the state it needs. The gateway holds the session, so it owns what happens to the session. The identity
provider holds the refresh-token lineage, so it owns reuse detection.

== Consequences

=== Properties of the design

* An outage no longer logs every user out: sessions survive pre-redemption failures and retry on a bounded schedule.
* The gateway revokes a spent-but-orphaned refresh token where it can name it.
* `on_failure: reject` exists, and a misspelling gets a boot refusal.
* Reuse detection works for both BFF variants, across stateless instances, with no gateway-side state. A cookie-based replay, the one case reachable
  through the gateway, is rejected end to end.
* A live identity provider asserts the documented behaviour, including the parts the gateway does not control.
* A retained ended cookie no longer amplifies into one call and one warning per near-expiry request on the instance that ended the session.

=== Accepted costs

* *Strict rotation makes a duplicate refresh fatal to the session.* Each instance single-flights per session. Two parallel requests with one cookie on
  different instances inside the refresh window still present the token twice, and the second ends the session. The effect is a rare forced re-login. A
  provider-side reuse count or grace window buys it back at the price of the detection.
* *The control lives outside the gateway.* Without strict rotation neither side detects reuse: the identity provider refreshes a replayed token and a
  copied cookie becomes a working session. The gateway cannot see the setting or warn about its absence.
* *The ended-token guard is partial.* It is per instance (each other instance makes one call before marking), in memory (a restart forgets every marker)
  and bounded (a full store records nothing, so replays degrade to one call per request).
* *The back-off is per instance.* With several stateless instances an outage costs one attempt per session per instance per window. On an instance whose
  back-off map is saturated, it costs one attempt per overflow window for its untracked sessions together.

=== Risks

* *An operator skips the identity provider setting.* Both BFF operator guides, the configuration reference and the compose sample state it as an explicit
  step together with the residual. Both project realms ship it on, so a copied realm carries it.
* *An identity provider answers a replay differently.* One that rejects a replay with a `4xx` other than `invalid_grant` could classify as `PRE_REDEMPTION`,
  keeping the session and retrying. The pinned verdict covers Keycloak only, and other identity providers are the operator's to verify.
* *A future gateway- or engine-side family would surface in the wrong kind.* A family check raised inside the engine arrives as a `ClientProtocolException`,
  which classifies as `PRE_REDEMPTION`, so the gateway would keep the session and retry. Any such mechanism belongs in Token-Sheriff with its own
  classification, not in a gateway wrapper.
