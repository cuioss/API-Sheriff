== Status

Accepted

== Decision

=== The question

A route carries one authentication posture: `none`, `bearer` or `session`. An upstream path serving API clients with their own bearer token and browsers logged in through the BFF therefore needs two routes on one prefix, told apart by an
`Authorization` header matcher, often under two anchors. Every such path is declared twice, and the pair depends on the matcher semantics. Nothing in the configuration says the two routes are one resource.

Folding the pair into one route moves the choice between the mechanisms inside the gateway. Whenever one route accepts two credentials, the rule that picks between them is an attack surface:

* If what a client sends can steer the rule, an attacker picks the weaker or more ambient branch. The classic form is *fallback on failure*: the gateway retries an invalid bearer token as a session, so a cross-site request with garbage in
  `Authorization` rides the victim's cookie.
* If the CSRF gate and the authentication stage each decide the branch, they can disagree. A request can be authenticated on the session branch after the CSRF gate judged it a bearer request and skipped the check.
* If the combined route accepts anything a plain bearer route or a plain session route would not, the fold creates a new posture with unreviewed acceptance rules.

This record settles how the branch is chosen and what each branch may be.

=== Two branches, chosen by header presence

A `require: bearer` route may declare `auth.session_fallback: true`. It then carries two authentication branches. One input alone chooses the branch per request: whether the request carries an `Authorization` header.

* *Selection by presence, never by content.* A request with an `Authorization` header, any scheme, any value, an empty value included, takes the BEARER branch. A request without one takes the SESSION branch. The resolver (`AuthBranch.resolve`) never reads the
  credential, so no value a client sends can move a request onto the session branch. The only way onto it is to send no `Authorization` at all, which gains nothing a `require: session` route does not offer.
* *The BEARER branch is exactly a bearer route.* It validates offline, applies the `403 insufficient_scope` check over the route's `neededScopes` (ADR-0049), and rejects a missing, malformed, non-`Bearer` or empty credential. A failed bearer is terminal (RFC 6750 §3.1): no login
  redirect, no session lookup, no `Set-Cookie`, and a valid session cookie sent alongside never rescues it.
* *The SESSION branch is exactly a session route.* It applies the fixed CSRF defence on unsafe methods (ADR-0018), session resolution and transparent refresh, a login redirect for a navigation and a `401` for everything else, a login requesting the route's `neededScopes`, and `token_relay`.
* *One resolver for both decisions.* The edge resolves the branch once, directly after the post-route stage, and runs the CSRF defence for the SESSION branch only. The authentication stage dispatches on the same resolver, so the two cannot disagree. A plain `require: session` route keeps its CSRF defence,
  because its branch is always SESSION.
* *The validated client token crosses through the mediated-bearer seam.* On the BEARER branch the gateway records the validated token as the mediated bearer, which the forward policy writes last, as it writes a session's token. The route needs no `forward.headers_allow: [Authorization]` entry (ADR-0037), and the
  upstream receives the token that was validated, not whatever inbound header crossed. `token_relay` governs the SESSION branch only, and the BEARER branch always forwards. `Cookie` is treated alike on both branches: the gateway's own cookies never reach the upstream, and the others cross only as the route's `cookies`
  policy block admits them (link:../configuration.adoc#_never_forward_set[the never-forward set]). A plain `require: bearer` route records no mediated bearer.
* *Refused where it cannot act, visible where it does.* The key rides the `auth` block's whole-block replacement (ADR-0007). The boot refuses `session_fallback: true` on a posture other than `require: bearer` and on a gateway without an `oidc` block, with two fixed detail texts on the existing configuration-error record. The route
  still needs `token_validation` for its bearer posture, so it needs both backing blocks. The anchor floor keeps comparing `require` only. The per-route boot posture line reports the flag for every route. A counter `sheriff_auth_branch_total{route,branch}` records the selected branch once per request, on `session_fallback` routes only.

=== The answers before the trust boundary

The BEARER branch's terminal rejection and the SESSION branch's CSRF rejection both lie before the trust boundary of
link:0073-Untrusted_callers_get_the_unrouted_404_for_every_rejection_raised_before_the_trust_boundary.adoc[ADR-0073]. On the shipped default the gateway answers a failed bearer as an unrouted address: `404`, with no `WWW-Authenticate` challenge, metering the true event (`TOKEN_MISSING` or `TOKEN_INVALID`). A CSRF rejection is answered the same way.
With `security_defaults.uniform_not_found: false` the BEARER branch answers `401` with `WWW-Authenticate: Bearer`. The SESSION branch keeps its own login negotiation either way, because a browser must reach the login.

== Alternatives rejected

=== Select the branch from the token's shape

Inspect `Authorization` and take the BEARER branch only for something that looks like a `Bearer` JWT.

*Rejected because* selection then depends on attacker-controlled content. A `Basic` credential or a malformed value would fall through to the session branch and ride the cookie. Every change to the heuristic would change which requests are exposed to CSRF.

=== Fall back to the session on a failed bearer

Try the bearer and, on failure, retry with the session cookie.

*Rejected because* this is the downgrade above. An invalid token plus an ambient cookie would authenticate, and the CSRF decision would come after authentication rather than before it. RFC 6750 makes a failed bearer terminal.

=== Reuse `forward.headers_allow: [Authorization]` for the bearer branch

Re-admit the inbound header instead of recording the validated token.

*Rejected in favour of the mediated-bearer seam both branches share.* It forwards whatever crossed, not the validated token. It ties a security property to a forward-list entry an operator can remove or mistype. It also conflicts with `token_relay: false`, whose boot rule refuses that re-admission.

All three let the credential's content or a forward-list entry decide which security mechanism applies. The decision keeps the choice structural: a credential's presence decides the branch, and each branch is an existing, reviewed posture.

== Consequences

=== Properties of the design

* One route serves both callers. The configuration declares a shared upstream path once and says it is one resource with two ways in.
* No downgrade by construction. Selection reads presence, so the requests that can reach the session branch are exactly those that send no credential: the population a `require: session` route already serves.
* No new acceptance rules. The route admits a request only if a plain bearer route or a plain session route would, so the reviews of both postures carry over.
* The CSRF gate and the authentication stage share one decision, so they cannot disagree.
* The branch in use is observable: at boot through the posture line, at runtime through the counter.

=== Accepted costs

* A bearer client that omits its header by mistake is treated as a browser. It gets a login redirect for a navigation-shaped request, or a session `401`. The counter's `session` series is the signal on a route expected to serve mostly API clients.
* The route needs both an `oidc` block and a `token_validation` block, so a bearer-only gateway cannot use the key.

=== Risks

* The branch rule depends on browsers never attaching `Authorization` by themselves and on cross-origin scripts needing a CORS preflight to set it. These are platform guarantees, not gateway controls. A gateway CORS policy that allow-lists the `authorization` request header for an untrusted origin would weaken the second. CORS stays a separate operator decision.
* The counter's `route` label is bounded only because route ids are fixed by configuration, as for every other per-route meter.
