== Status

Proposed

== Context

A route carries one authentication posture: `none`, `bearer` or `session`. A backend path that must
serve two kinds of caller -- API clients presenting their own bearer token, and browsers logged in
through the gateway's BFF session -- therefore needs two routes on one prefix, told apart by an
`Authorization` header matcher, often under two anchors. Every such path is declared twice, the pair
depends on the matcher semantics staying exactly right, and nothing in the configuration says that
the two routes are one resource.

Folding the pair into one route moves the choice between the two mechanisms inside the gateway, and
that choice is the security question. Whenever one route accepts two credentials, the rule that
picks between them is an attack surface:

* If the rule can be steered by what a client sends, an attacker can pick the weaker or more ambient
  branch. The classic form is *fallback on failure*: an invalid bearer token is retried as a session,
  so a cross-site request carrying garbage in `Authorization` rides the victim's cookie.
* If the CSRF gate and the authentication stage each decide the branch on their own, they can
  disagree. A request can then be authenticated on the session branch after the CSRF gate judged it
  to be a bearer request and skipped the check.
* If the combined route accepts anything that neither a plain bearer route nor a plain session route
  would accept, the fold has created a new posture with its own, unreviewed acceptance rules.

The question this ADR settles is how the branch is chosen, and what each branch is allowed to be,
so that none of the three happens.

== Decision

*A `require: bearer` route may declare `auth.session_fallback: true`. It then carries two
authentication branches, and the branch is chosen per request from one input only: whether the
request carries an `Authorization` header.*

* *Selection by presence, never by content.* A request that carries an `Authorization` header --
  any scheme, any value, an empty value included -- takes the BEARER branch. A request without one
  takes the SESSION branch. The resolver (`AuthBranch.resolve`) never reads the credential, so no
  value a client sends can move a request onto the session branch. The only way onto it is to send
  no `Authorization` at all, which gains nothing a `require: session` route does not already offer.
* *The BEARER branch is exactly a bearer route.* Offline validation, the `403 insufficient_scope`
  check over the route's `neededScopes` (ADR-0049), and a `401` with `WWW-Authenticate: Bearer` for a
  missing, malformed, non-`Bearer` or empty credential. A failed bearer is terminal (RFC 6750 §3.1):
  no login redirect, no session lookup, no `Set-Cookie`, and a valid session cookie sent alongside it
  never rescues it.
* *The SESSION branch is exactly a session route.* The fixed CSRF defence on unsafe methods
  (ADR-0018), session resolution and transparent refresh, a login redirect for a navigation and a
  `401` for everything else, a login requesting the route's `neededScopes`, and `token_relay`.
* *One resolver for both decisions.* The edge resolves the branch once, directly after the per-route
  thorough checks, and runs the CSRF defence for the SESSION branch only. The authentication stage
  dispatches on the same resolver, so the CSRF gate and authentication cannot disagree. A plain
  `require: session` route keeps its CSRF defence unchanged, because its branch is always SESSION.
* *The validated client token is forwarded through the mediated-bearer seam.* On the BEARER branch
  the validated token is recorded as the request's mediated bearer, which the forward policy writes
  last, exactly as it writes a session's token. It is not re-admitted through
  `forward.headers_allow: [Authorization]` (ADR-0037), so the route needs no forward-list entry for it,
  and the upstream receives the token that was validated, not whatever inbound header crossed.
  `token_relay` governs the SESSION branch only; the BEARER branch always forwards. The browser
  `Cookie` stays withheld by the gateway-owned never-forward set on both branches. A plain
  `require: bearer` route is unchanged: it records no mediated bearer.
* *Refused where it cannot act, visible where it does.* The key rides the `auth` block's wholesale
  cascade (ADR-0007). The boot refuses `session_fallback: true` on a posture other than
  `require: bearer`, and on a gateway without an `oidc` block, with two fixed detail texts on the
  existing configuration-error record. The route stays held to `token_validation` for its bearer
  posture, so it needs both backing blocks. The anchor floor keeps comparing `require` only. The
  per-route boot posture line reports the flag for every route, and a counter
  `sheriff_auth_branch_total{route,branch}` records the selected branch once per request, on
  `session_fallback` routes only.

== Consequences

=== Positive

* One route serves both callers. A shared backend path is declared once, and the configuration says
  that it is one resource with two ways in.
* No downgrade by construction. Because selection reads presence rather than content, the set of
  requests that can reach the session branch is exactly the set that sends no credential. That is
  the population a `require: session` route already serves.
* No new acceptance rules. A request is admitted on a `session_fallback` route only if a plain bearer
  route or a plain session route would admit it, so the existing reviews of both postures carry
  over unchanged.
* The CSRF gate and the authentication stage share one decision, so the class of defect in which
  they disagree cannot occur.
* The branch in use is observable: at boot through the posture line, at runtime through the
  counter.

=== Negative

* A bearer client that omits its header by mistake is treated as a browser. It receives a login
  redirect for a navigation-shaped request, or a session `401`, instead of a bearer `401`. The
  counter's `session` series is the signal to watch on a route expected to serve mostly API clients.
* The route needs both an `oidc` block and a `token_validation` block, so a bearer-only gateway cannot
  use the key.

=== Risks

* The branch rule depends on browsers never attaching `Authorization` by themselves and on
  cross-origin scripts needing a CORS preflight to set it. Both are platform guarantees rather than
  gateway controls. A gateway CORS policy that allow-lists the `authorization` request header for an
  untrusted origin would weaken the second; the CORS policy stays a separate operator decision.
* The counter's `route` label is bounded only because route ids are config-fixed, as for every other
  per-route meter.

== Alternatives Considered

*Select the branch from the token's shape.* The gateway could inspect `Authorization` and take the
BEARER branch only for something that looks like a `Bearer` JWT, sending everything else to the
session. That makes selection depend on attacker-controlled content: a `Basic` credential or a
malformed value would fall through to the session branch and ride the cookie, and every change to
the shape heuristic would change which requests are exposed to CSRF. Rejected.

*Fall back to the session on a failed bearer.* A route could try the bearer and, on failure, retry
with the session cookie. That is exactly the downgrade the Context describes. An invalid token plus
an ambient cookie would authenticate, and the CSRF decision would have to be made after
authentication, not before it. RFC 6750 makes a failed bearer a terminal `401`. Rejected.

*Reuse `forward.headers_allow: [Authorization]` for the bearer branch.* The route could re-admit the
inbound header instead of recording the validated token. That forwards whatever crossed, not the
token that was validated, ties a security property to a forward-list entry an operator can remove
or mistype, and would conflict with `token_relay: false`, whose boot rule refuses exactly that
re-admission. Rejected in favour of the mediated-bearer seam that both branches share.

All three alternatives let either the credential's content or a forward-list entry decide which
security mechanism applies. The decision keeps that choice structural: whether a credential is
present decides the branch, and each branch is an existing, already reviewed posture.
