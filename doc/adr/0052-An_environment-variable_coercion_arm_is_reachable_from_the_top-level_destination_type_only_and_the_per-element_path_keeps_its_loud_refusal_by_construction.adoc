== Status

Accepted

== Decision

A value supplied through a placeholder arrives as a string, so something must decide its type before the document is bound. Inferring it from the value's shape makes the destination type depend on what the deployment put in the variable. A port that reads `8080` becomes a number, one that reads `08080` a string, and the difference surfaces as a bind failure far from its cause.

`ConfigLoader.coerce` therefore re-types a substituted scalar from the schema-declared destination type at the value's own pointer. Shape inference survives only for pointers the schema pins no type for. Each declared type gets an arm.

The coercion is two-level. A list-valued destination is re-typed into the whole list: one resolved variable splits on a separator, and each element is typed in turn by the declared item type. So the same arm table is consulted once for the value and again for each element.

The list arm reaches every array-typed pointer the schemas declare, deliberately, including arrays whose items are objects. At such a pointer each element falls through to shape inference, and schema validation refuses the resulting array of scalars with a diagnostic naming the expected and actual types and never the value. That refusal is the designed behaviour.

A map-valued arm, which lets one variable supply a map as comma-separated `key=value` pairs, collides with that. It answers to the same type name an array-of-objects pointer declares for its items. Reachable from the item position, it would type each element as a single-entry object, and the array might then satisfy the schema. The loud refusal would become a silent bind of a shape the operator never described. The record settles where an arm's reachability is decided when a coercion table is consulted from two positions.

*The decision:* a coercion arm is reachable from the position its semantics are defined for, and the boundary is enforced at the delegation site, not by the arm declining to act.

The map-valued arm is reachable from the top-level destination type only. `ConfigLoader.coerceList` maps an object item type to no declared type before delegating, so an element at an array-of-objects pointer falls through to shape inference, and the schema's refusal stands.

=== The exclusion lives at the one delegation site

The item type is forwarded into the arm table in exactly one place, and that place enforces the boundary. The arm is unconditional and has no position-dependent branch. An arm that policed its own caller would spread the boundary across every arm.

=== The exclusion says "this position declares no type"

The item path carries no rule that forbids the map arm. It carries the true statement that an object-items pointer has no scalar item type to pin. What follows, shape inference and then the schema's refusal, is the table's ordinary behaviour for an unpinned type. A future non-scalar arm needs the same shape.

=== The preserved refusal is a contract

Reaching an array-of-objects pointer and refusing it with a type-naming diagnostic is a contract. Admitting the map arm to the item path is a decision to convert a refusal into an acceptance, and it must be argued as one.

Where a change to a shared table can turn a loud refusal into a silent acceptance, the burden falls on the change. A silent bind of a shape the operator never wrote is strictly worse than a boot refusal naming the expected type. The boot refusal is discovered in seconds, the silent bind by a request that behaves wrongly.

== Alternatives rejected

=== Let the map arm reach the per-element path too

This is the smallest change: one table, consulted uniformly from both positions.

*Rejected because* it silently converts a documented loud refusal into an acceptance. Each element of an array-of-objects pointer would bind as a single-entry object, and the deployment would boot on a shape nobody described. A change whose failure mode is a successful boot with wrong data must not be made by default.

=== Have the arm detect and decline the item position

This keeps the delegation site uniform and localises the rule inside the arm that needs it.

*Rejected because* it inverts responsibility. The arm would have to know about a caller it cannot see, every future arm would need the same rule, and the boundary would hold only as long as each one remembered. One enforced site beats N remembered ones.

=== Teach the schema to forbid substitution at array-of-objects pointers

This moves the boundary into the declaration where types live.

*Rejected because* the schema declares what a valid document looks like, not what the substitution pass may do to a document on its way there. A second vocabulary inside the schema is a second thing to keep in sync with the arms, with the usual failure mode that the looser copy silently wins.

=== Give the item path its own arm table

This makes the two positions explicitly different.

*Rejected as* disproportionate. The tables would be identical but for one arm, and duplicating a type table is how two positions come to disagree about what `integer` means. The one-line mapping expresses the same difference.

=== Support arrays of objects from a single variable with a richer wire format

This would deliver the capability the exclusion declines.

*Rejected as* answering a different question. A nested wire format needs escaping rules, a nesting bound and its own diagnostics, and the requirement behind the map arm needs none of that. The capability stays available through the mounted document, where a structured value belongs.

One group of these options dissolves the distinction between the positions and pays with a silent acceptance or with drift between two copies. The other keeps the distinction and pays too much for it. The chosen position states the difference once, at the site where the recursion happens.

== Consequences

=== Properties of the design

* An operator can supply a map-valued key from one environment variable, with no change at any other pointer.
* The refusal at array-of-objects pointers holds by construction, not by a test that would have to anticipate each new arm.
* A reader auditing what a variable can turn into has one place to look.
* The arms stay position-agnostic, so an arm can be reviewed in isolation.
* The next non-scalar arm inherits the same question and the same answer shape.
* Failures at unreachable-by-design pointers stay loud and type-named, so a diagnostic never carries a resolved secret.

=== Accepted costs

* The two positions differ, and the arm's own code does not show it. The knowledge lives at the delegation site and in this record.
* An operator cannot supply an array of objects from one environment variable, even where the wire format would be unambiguous. That capability is declined, not merely unimplemented.
* One line of mapping carries the constraint. Nothing in the type system prevents a change from forwarding the item type unmapped, and the regression is silent at the loader.

=== Risks

* *Erosion by plausible local change.* "Just forward the item type" reads as a simplification and removes the boundary. The delegation site names the reason at the point of the mapping, and this record is the argument behind it.
* *Silent regression.* Losing the boundary produces an acceptance, not an error. Only a test that asserts the refusal detects it, and such a test is the kind most easily deleted as an obstacle.
* *A future arm.* A third arm added without reading this record inherits nothing automatically. The delegation site pins the behaviour of the arm it names.
