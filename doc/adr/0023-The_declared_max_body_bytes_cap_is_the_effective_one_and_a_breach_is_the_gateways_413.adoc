== Status

Accepted

== Decision

A gateway with a per-route body cap owns two limits. The configuration declares one: the body cap,
`security_filter.max_body_bytes`. The HTTP framework beneath the gateway enforces the other:
`quarkus.http.limits.max-body-size`. The lower of the two applies.

That creates a class of defect in which a documented key is inert. The gateway parses, models and
enforces the declared cap. But when the framework limit is lower, the framework answers every request
that would exercise the cap first. Nothing fails visibly: the framework's answer is a well-formed
response. Unit tests do not see it either. They exercise the filter directly, below the layer where
the framework cuts the request.

The record settles two questions. Which component sets the effective cap? And how does a reader tell
the gateway's rejection from the framework's?

*The declared cap is the effective cap.* The framework limit is a floor under the declared caps, not
an independent knob. The shipped `application.properties` sets it to 64 MiB, the largest body cap the
shipped configuration declares. The boot checks the relationship fail-closed. `ConfigBootPipeline`
reads every declared `max_body_bytes`, at every policy scope that can declare it. When the largest
one exceeds the framework limit, the boot refuses and names the key to raise. A deployment whose
stated cap cannot be honoured does not start. It never starts with a quietly smaller cap.

The enforcement predicates do not change. The post-route stage (`ThoroughChecksStage`) still rejects
a declared `Content-Length` above the cap before it reads the body. The streaming byte counter still
caps a chunked body. The decision only makes both reachable.

*A body-cap breach is the gateway's own 413.* The gateway renders a breach as `CONTENT_TOO_LARGE`. That
event maps to HTTP 413 in the `INPUT_VALIDATION` category, in the RFC 9457
`application/problem+json` envelope. On gRPC the same event maps to `RESOURCE_EXHAUSTED`, not to
`UNKNOWN`. A breach is therefore one outcome on both protocols.

The status alone does not tell the two rejecting components apart, because the framework also answers
413. The envelope does. The gateway's rejection carries `application/problem+json` with a problem
type and title. The framework's carries no body. A test that means to prove the gateway enforced the
cap asserts on the envelope, not on the status alone.

The operator-facing statement of the floor is in
link:../configuration.adoc[Configuration Reference]. The status and category tables are in
link:../architecture.adoc[Architecture].

== Alternatives rejected

*Leave the framework limit at its default and enforce only in the gateway.* This is the state the
record replaces. It needs no derivation and no boot check. Rejected because it is why the declared
cap was unreachable. The gateway's enforcement sits behind the framework's, so the lower limit wins
whatever the configuration says. It fails not because it is complex. It fails because it makes the
effective cap an accident of which limit is smaller.

*Require the operator to set the framework key by hand, with no check.* This is the cheapest option,
and it makes the declared cap reachable when the operator gets it right. Rejected because it fails on
the same axis as the status quo. A deployment that omits the key, or sets it too low, looks like a
correct one until a large request arrives. The defect class survives, with a manual step added.

*Raise the framework limit to a fixed safe value unrelated to the declared caps.* This makes the
gateway the rejecting component without any check, and it is simple. Rejected because the constant
is arbitrary. Either it is lower than some deployment's declared cap, which brings the defect back
for that deployment. Or it is so high that it means nothing as a limit, which removes the framework's
own backstop and puts nothing in its place.

All three leave the effective cap implicit. The decision makes it explicit and refuses to boot when
it cannot be honoured. It is the only variant in which the documented configuration and the enforced
behaviour cannot diverge.

== Consequences

*Positive.*

* A declared `max_body_bytes` is honoured, or the boot refuses. No third state exists in which the key
  is documented, parsed and inert.
* The component that rejects an oversize body is the one whose configuration declared the cap. The
  rejection is attributable and carries the gateway's envelope, not a bare framework status line.
* A misconfiguration fails at boot, at the layer that owns it, with the offending key named. It does
  not surface at request time as a smaller cap than the operator asked for.
* Body-cap semantics are the same on the proxy and gRPC paths.

*Negative.*

* The framework limit and the declared caps are coupled. Raising a cap above the shipped floor is a
  two-part change, and doing only half of it is a boot refusal, not a warning.
* Every deployment inherits the shipped floor. It must be low enough to be safe and high enough that
  the common case is not a boot refusal.

*Accepted failure modes.*

* *Shadowing at equality.* When the framework limit equals the largest declared cap, the framework's
  pre-router check rejects an over-cap request before the gateway pipeline runs. The client then gets
  the bare framework 413, not the RFC 9457 envelope. The boot check permits this, because the
  declared cap is still honoured for every request at or below it. Only the renderer of an over-cap
  rejection changes. A deployment that wants the gateway's envelope sets the floor strictly above its
  largest cap. The configuration reference documents this instead of forbidding it, because
  forbidding it would refuse a configuration whose stated cap is in fact honoured.
* *Chunked requests take another path.* A request with no `Content-Length` skips the framework's
  pre-check. The gateway's streaming counter then enforces the cap, and the envelope is always
  rendered. The two transports differ in which component rejects, not in the effective cap.

*Constraints on later change.*

* Raising the framework floor must not widen an uncapped path. Every proxy route falls back to a
  default body size when it declares none, and reserved paths carry their own ceiling. A change that
  made the framework floor the only ceiling for some route would silently reopen the risk this record
  closes.
* The boot check reads every scope that can declare `security_filter`. A new policy scope must be
  mapped there, or the check fails loudly; it must never skip that scope's caps.
