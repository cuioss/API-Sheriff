= ADR-0024: Inbound filter modes — `minimal` is a partial disable retaining the body cap and path allowlist, and is refused on authenticated and BFF routes

== Status

Accepted

== Decision

The `profile` key selects an inbound-filter profile. An operator declares it on the gateway-wide
`security_defaults` block and in every `security_filter` policy block. Two things about it were
underspecified.

*The mode set had a member that promised nothing.* Besides `strict`, `paranoid` and `lenient`, each
backed by a cui-http preset, the set carried `default`. Its meaning was "whatever the library's
builder defaults are". A name that resolves to an incidental value names a deferral, not a policy.
An omitted `security_defaults` block resolved to that same value. So the most common configuration,
one with no gateway-wide posture, got the loosest-by-accident policy.

*"Turn the filter off" had no defined meaning.* Operators need an escape hatch. A partner route may
receive parameters with structure the anti-injection policy treats as suspicious: a path-shaped
callback target, or an opaque token with separators. The operator needs "stop validating these
parameter values", not "stop defending this route". No vocabulary existed for that. An undefined off
switch is the dangerous answer, because nobody can say afterwards what it disabled.

Two structural facts constrain the answer. First, the pre-route floor (`BasicChecksStage`) cannot be
skipped. It yields the canonical path that route selection consumes. The profile is a per-route
setting, and no route exists until the floor has run, so no profile can reach the floor.
link:0019-Reserved_BFF_paths_bypass_the_url-parameter_value_pipeline_and_the_cookie-header_length_relaxation_is_gateway-wide.adoc[ADR-0019]
states the same property from the side of the header carve-outs. Second, a `minimal` route can be an
authenticated route. The profile sits in a policy block, and the auth floor can come from another
policy scope. Nothing structural stops an operator from disabling parameter validation in front of a
session or a bearer token.

*The mode set is `strict` / `paranoid` / `lenient` / `minimal`. `minimal` is a bounded partial
disable with a closed list of what it turns off, and the boot refuses it on effectively-authenticated
and BFF routes.* `SecurityProfile` holds the set, `ThoroughChecksStage` the closed list and
`LimitRules.validateSecurityProfileMinimal` the refusal.

=== (1) The mode set, and the default

`default` is removed from the value space. Each remaining mode names a policy a reader can look up.
`strict`, `paranoid` and `lenient` are backed by their cui-http presets. Decision (3) defines
`minimal`.

`paranoid` is `strict` plus the content detection no lower mode performs: the sensitive-path and
suspicious-parameter-name block-lists. It is tighter than `strict` on every axis and looser on none.
It does not move the default. The tightest available mode and the default mode are different
questions. `paranoid` block-lists ordinary REST names such as `file`, `path` or `url`, so it has a
real false-positive profile. It suits a surface whose paths and parameters reach a filesystem.

An omitted `security_defaults` block, or one without `profile`, resolves to `strict`. The common
configuration gets the fail-closed posture by construction. A deployment that wants a looser baseline
must declare it.

The value range stays in the JSON Schema. The schema enumerates the mode set at each of its three
declaration sites, so an out-of-range value fails the boot there. The configuration validator does
not repeat it.

=== (2) `minimal` is a partial disable, with two bounds

`minimal` disables validation. It is not a statement about limits, and it is not a bypass.

*The structural bound.* The pre-route floor runs for every request whatever the profile: path
canonicalisation, header name and value validation, and the parameter- and header-count caps. A
`minimal` route is still rejected for an encoded path separator, an over-cap parameter count or an
oversized header value, exactly like a `strict` route.

*The policy bound.* The body cap (`max_body_bytes`) and `allowed_paths` stay in force under
`minimal`. The post-route stage enforces both, so they could have sat behind the profile gate. They
deliberately do not. Neither is an injection defence. A body cap guards against exhaustion, and a path
allowlist restricts the reachable surface. An operator who asks to stop validating parameter values
does not ask to remove either.

`minimal` names no preset, but the kept body cap needs a number. A `minimal` route therefore takes
its limits from the nearest non-`minimal` profile in its fallback chain, and from `strict` when the
whole chain is `minimal`.

=== (3) The closed list of what `minimal` disables is normative

`minimal` disables exactly two things:

. the url-parameter name and value validation, which runs in the post-route stage under the route's
  own configuration and behind this gate;
. the per-route pipeline re-run: the second pass of the path and header pipelines that a route whose
  configuration diverges from the gateway baseline would otherwise perform.

Nothing else. The list defines the mode; it does not describe an implementation. Adding a third item
is a change to this record, not a refactor. Everything absent from the list keeps running: the
pre-route floor, the body cap, the path allowlist, authentication, the method gate, the
terminal-action rules and the response-side envelope. Item (2) skips only the route's divergent
second pass. The floor's baseline path and header validation has already run.

=== (4) `minimal` is a boot refusal on effectively-authenticated and BFF routes

The boot refuses a route whose effective inbound-filter profile is `minimal` when either

* its effective access level is `authenticated`, or
* its anchor's type is `bff`.

The refusal joins the shared all-violations pass and never fails fast, per
link:0009-asymmetric-alias-resolution-failure.adoc[ADR-0009]. The message names the route, the refusing
dimension and the remedy. It echoes no configured value.

The refusal reads the route's resolved `security_filter` policy block. A `minimal` from any policy
scope, endpoint scope included
(link:0067-Every_policy_block_is_one_declaration_resolved_nearest_declared_scope_wins_with_whole-block_replacement.adoc[ADR-0067]),
is therefore refused exactly like one the route declares. A `security_defaults.profile: minimal` that
reaches an authenticated or BFF route through the fallback chain is refused the same way.

*The access level is derived, not read.* The check resolves the effective access level through the
seam the route table uses (`RouteTableBuilder.effectiveAccessLevel`). It does not read the anchor's
declared `access`.
link:0007-anchor-scoped-policy.adoc[ADR-0007] lets a route or an endpoint strengthen a `public`
anchor's auth floor. A route that adds `require: bearer` under a `public` anchor is effectively
authenticated while its anchor still reads `access: public`. A check that read the anchor would let
exactly that route through.

The anchor-type dimension is independent. Per
link:0013-anchor-type-access-axes.adoc[ADR-0013] a `bff` anchor must be `access: authenticated`, so the
first dimension already covers it today. It is named separately so the refusal survives a later
relaxation of that rule.

*Boundaries.* This record composes with ADR-0007, ADR-0013 and ADR-0019 and supersedes none of them.
It consumes ADR-0007's strengthening rule and ADR-0013's axes. ADR-0019 owns the reserved-path
relaxation and the header carve-outs; the post-route position of the parameter validation set here
is what makes ADR-0019's reserved-path exemption structural.
link:0023-The_declared_max_body_bytes_cap_is_the_effective_one_and_a_breach_is_the_gateways_413.adoc[ADR-0023]
owns the body cap this record keeps in force.
link:0026-A_security_bound_declared_at_one_inbound-validation_stage_is_re-asserted_at_every_later_stage_that_re-validates_the_same_input.adoc[ADR-0026]
owns the principle that a bound declared at one stage holds at every later stage that re-validates
the same input; this record fixes which check lives at which stage.

== Alternatives rejected

*Keep `default` in the mode set.* It needs no change and breaks nothing. Rejected because a posture
whose meaning is "whatever the builder defaults are" cannot be reasoned about or reviewed. It names a
deferral, not a policy. It also became the baseline for every configuration without a gateway-wide
posture, which put the loosest-by-accident value where the safest one belongs.

*Keep the `none` spelling and correct it in prose.* The mode was first named `none`, and the record
first named that over-promise as a negative consequence. Rejected because a name that every reader
must be told to disbelieve is a defect in the name. The correction has to reach the schema
description, the configuration reference, the user guide and every configuration comment. A reader
who misses one guesses wrong in the unsafe direction. `minimal` costs one breaking rename and needs no
correction.

*Make `minimal` a wholesale skip of the post-route stage.* This is the simplest semantics: one branch,
no closed list, and what the original name suggested. Rejected because it over-delivers. An operator
who asks to stop validating parameter values does not ask to remove the body cap or widen the
reachable surface. A mode that grants all three is not a bounded relaxation. Its residual exposure is
"everything the stage would have done", which is not enumerable. The closed list costs a maintenance
obligation and buys a reviewable blast radius.

*Let `minimal` reach the pre-route floor too.* Rejected as not achievable. Route selection consumes
the canonical path the floor produces. A request whose profile suppressed the floor would have no path
to select a route with, and without a route there is no profile to read. The record states this
because "make the off switch turn everything off" is the obvious next request.

*Warn instead of refusing `minimal` on authenticated and BFF routes.* This keeps operator autonomy
and breaks no configuration. Rejected because a boot WARN on a security posture is a signal nobody
reads. The deployment serves weakened traffic in the meantime, and the combination has no legitimate
use that would justify it.

*Read the anchor's declared `access` instead of deriving the effective level.* This is simpler and
needs no shared seam. Rejected because it under-refuses the case that most needs refusal: a route that
strengthens a `public` anchor's floor with `require: bearer`. A guard that misses the subtle instance
reads as coverage, which is worse than no guard.

*Duplicate the profile value range into the configuration validator.* This would put both gates in
one component. Rejected because a second copy of an enumeration must be kept in sync, and when two
range gates drift the looser one silently wins. The schema validates the document where it is bound;
that is the one home for a range check.

The rejected options fall into two kinds. One kind widens the escape hatch past the need: the
wholesale skip, reaching the floor, keeping `default`. The other kind refuses to commit to a bound:
warning instead of refusing, checking a weaker predicate, or keeping a misleading name. The chosen
position is the narrowest disable that meets the operator's need, under a name that states what it
keeps, with a closed list and a boot refusal on the one combination that is never deliberate.

== Consequences

*Positive.*

* Every mode name resolves to a policy a reader can look up, and the escape hatch has an enumerable
  definition.
* The default is safe by construction: a configuration with no gateway-wide posture gets `strict`.
* The escape hatch fits the need. An operator who needs a path-shaped parameter accepted gets exactly
  that, and keeps the body cap, the path allowlist and the whole pre-route floor.
* The worst misconfiguration the key permits cannot boot. Disabling parameter validation in front of a
  token- or session-bearing surface is a boot refusal.
* The closed list is a specification an implementation can be checked against.
* The name `minimal` states the residual posture: the least validation this gateway performs.

*Negative.*

* The `strict` default is a behaviour change for existing deployments. The caps on body size,
  parameter count, header-value length, parameter-value length and path length all drop, and
  suspicious-pattern rejection turns on. A deployment that relied on the incidental values must now
  declare `lenient`. It is a break without a deprecation window, consistent with the pre-1.0 posture.
* The rename from `none` is a breaking configuration change. The schema no longer admits `none` at any
  of its three profile sites, so `profile: none` is a boot refusal. `auth.require: none` is a
  different key in a different value space and is unaffected.
* The closed list is a maintenance obligation. Moving a check across the profile gate is a change to
  this record, and the type system does not enforce that.
* Two gates govern one key: the schema owns the value range, the validator owns the posture refusal.
  A reader must know which gate refused a configuration to know why.

*Accepted failure modes.*

* *Misreading the residual posture.* An operator may still under-estimate how much `minimal` keeps.
  That surprise runs in the safe direction: the mode enforces more than expected, never less.
* *A permitted `minimal` route is really unvalidated.* The refusal covers authenticated and BFF routes.
  On a genuinely public surface `minimal` is permitted and its parameter values are not validated. The
  operator owns that decision.
* *Baseline drift between the floor and a route.* The floor runs under the gateway-wide profile. A
  deployment that lowers that profile to `lenient` loosens the floor for every route, `strict` routes
  included, because the floor precedes route selection.

*Constraints on later change.*

* Each request to move "just one more" check behind the profile gate is plausible alone. Together they
  turn the partial disable into the wholesale one this record rejects. The list is the limit.
