== Status

Accepted

== Decision

Every proxied dispatch runs inside a SmallRye Fault Tolerance guard that `UpstreamGuards` builds at boot: a circuit breaker, an upstream timeout and, on a route that enables it, a retry. The configuration model let a route declare the breaker's shape, `upstream.circuit_breaker.failures` and `reset_ms`, and nothing that builds the guard read either value.

A configuration key that parses and acts on nothing is worse than an absent key on a security gateway. An operator who declares `failures: 3` reads a tighter breaker into the deployment than the one in force, and no boot message, test or metric says otherwise. The record settles where the breaker's shape is decided, by the gateway or by each route, and where the `Retry-After` of an open circuit comes from.

=== The breaker is a fixed policy of the gateway

*The circuit breaker in front of an upstream is the gateway's own fixed policy. A route declares no circuit-breaker settings.*

[cols="1,1,3", options="header"]
|===
| Property | Value | Meaning

| Rolling window
| 20 calls
| The breaker judges the most recent 20 dispatches to the upstream (SmallRye `requestVolumeThreshold`). Below that volume it does not open.

| Failure ratio
| 0.5
| It opens when half or more of the calls in the window failed.

| Open delay
| 5 s
| It stays open for `BREAKER_RESET_SECONDS` = 5 seconds, then lets trial calls through.

| Close threshold
| 2 successes
| Two successful trial calls close it. A failed trial opens it for another delay.
|===

Only an upstream failure counts as a failure. A dispatch the client itself ended (a body-cap breach, an aborted inbound body, a body on a bodyless method, a body that disagrees with its declared length) is a gateway rejection the breaker skips and records as a success, because SmallRye has no neutral outcome. State transitions surface as WARN records and metrics.

One guard serves every route that dials the same upstream target with the same retry setting, so the breaker's state is per upstream target on this node, not per route. Gateway nodes share nothing.

The `upstream.circuit_breaker` block, its model record and its native-image reflection registration are removed. A descriptor that declares the block is a boot refusal, because the schema admits no unknown member in an `upstream` block. That refusal is the intended answer to a deployment that relied on the key, because the key never acted.

=== The `Retry-After` of an open circuit is the breaker's delay, without jitter

The `503` an open circuit answers carries `Retry-After: 5`. One constant, `BREAKER_RESET_SECONDS`, is both the breaker's open delay and the header's value, so the hint cannot drift from the window the breaker applies.

The header carries no jitter. It states the breaker's real window on this node. Spreading retries out is the client's responsibility: RFC 9110 section 10.2.3 defines `Retry-After` as the minimum time the client is asked to wait and permits a client to wait longer. The security-audit finding that the header carries no jitter is accepted on this basis.

=== Amendment 2026-10-26: the timeout and retry keys are removed

The first version of this record left four more per-route upstream keys undecided. Each one parsed and acted on nothing:

* `connect_timeout_ms` and `read_timeout_ms` were bound into the model and read by nothing.
* `retry.max_attempts` and `retry.idempotent_only` were bound and read by nothing. Only `retry.enabled` acted.

On 2026-10-26 the operator decided to remove all four, for the reason the breaker block was removed.

*A route declares no timeout and no retry shape. It keeps one retry toggle, `retry.enabled`.*

The four keys, their model fields and their schema entries are removed. The schema admits no unknown member in an `upstream` block or in its `retry` block. A descriptor that declares one of the four keys is therefore a boot refusal.

The behaviour the keys appeared to configure is a fixed policy of the gateway. `UpstreamGuards` builds it. This record names the policy and does not restate the code.

[cols="1,1,3", options="header"]
|===
| Property | Value | Meaning

| Timeout per attempt
| 30 s
| `UPSTREAM_TIMEOUT_SECONDS`. The guard ends an attempt the upstream holds up for 30 seconds. The timeout sits inside the retry, so it bounds each attempt, not the whole dispatch.

| Retry
| 2 retries, 100 ms apart
| SmallRye `maxRetries(2)`, only on a route whose effective `retry.enabled` is `true`. A retried dispatch runs up to three attempts, about 90 s in all (#582).

| Retried methods
| `GET`, `HEAD`, `OPTIONS`, `PUT`, `DELETE`
| The idempotent method set. The stream-aware retry predicate also refuses a retry once an attempt has subscribed the request body. `POST` and `PATCH` are never retried.

| Connect timeout
| 60 s
| The Vert.x default. The upstream client sets no connect timeout of its own, and the guard's 30 s timeout ends the attempt first.

| Idle timeout
| None
| The upstream client sets no idle timeout. The guard's timeout bounds an upstream that stops answering.

| Request-body bounds
| 10 s idle, 25 s deadline
| Unchanged from #506. Both are shorter than the guard's timeout. A body that stops arriving ends as the request's failure, not the upstream's.
|===

== Alternatives rejected

=== Wire the keys

`failures` and `reset_ms` would be read when the guard is built, and a route could tune its breaker.

*Rejected here because* nothing currently needs a breaker shape other than the gateway's. It changes runtime behaviour: it introduces per-route breaker shapes, needs a decision on how `failures`, a count, maps onto a ratio-based rolling window, and makes the `Retry-After` value per route. It belongs in a plan of its own if a deployment ever needs it.

=== Keep the keys and leave them inert

The schema and the model would stay, with documentation stating that the keys have no effect.

*Rejected because* a key that parses but does not act is exactly the false-security class this decision removes, and documentation is not read where a descriptor is written.

=== Add jitter to `Retry-After`

A randomised value around the delay would spread clients that retry exactly when told.

*Rejected because* the header would then misstate the breaker's window, and because the clients that need spreading are the ones that implement their own backoff anyway.

=== Wire the timeout and retry keys

`connect_timeout_ms` and `read_timeout_ms` would set the upstream client's timeouts. `retry.max_attempts` and `retry.idempotent_only` would shape the guard's retry.

*Rejected because* no deployment needs a timeout or a retry shape other than the gateway's, and wiring the keys changes runtime behaviour for every route that declares them. Each key also needs a decision of its own:

* A per-route timeout must stay longer than the request-body bounds. Otherwise a stalled body ends as the upstream's failure, and the breaker counts it.
* `read_timeout_ms` has no single meaning on the Vert.x client. It could be an idle timeout or a bound on the whole response.
* `retry.idempotent_only: false` would let the guard retry a `POST` or a `PATCH`. A retried write can apply twice on the upstream.

It belongs in a plan of its own if a deployment ever needs it.

=== Keep the four keys parsed and warn at boot, as ADR-0077 does for `rate_limit`

The schema and the model would keep the keys. A boot WARN would name every route that declares one.

*Rejected because* the reason ADR-0077 keeps `rate_limit` does not apply here. Per-route rate limiting is a planned feature, and the `rate_limit` block is where it will be declared. No feature is planned for these four keys: the timeout and the retry policy are decided as fixed, as the breaker is. A kept key would stay a configuration surface that no feature fills, and its WARN would fire at every boot without end.

== Consequences

=== Properties of the design

* Every key left in the `upstream` block acts. An operator can no longer declare a breaker shape, a timeout or a retry shape that the gateway does not run.
* The breaker's shape is stated once, in the code that builds it, and documented as the gateway's policy.
* A client reading `Retry-After` on an open circuit is told the window the breaker applies, by construction.

=== Accepted costs

* A route cannot have a breaker more or less sensitive than the gateway's. An upstream that needs a different shape needs a code change and a new decision.
* A descriptor that declares `upstream.circuit_breaker` is a boot refusal. The key never acted, so the refusal changes no runtime behaviour, but it is a breaking change to the accepted configuration surface.
* A descriptor that declares `connect_timeout_ms`, `read_timeout_ms`, `retry.max_attempts` or `retry.idempotent_only` is a boot refusal. The keys never acted, so the refusal changes no runtime behaviour either. It is a second breaking change to the same surface.

=== Risks

* Many clients honouring the same `Retry-After` can retry together when the delay ends. The half-open state admits trial calls and opens again on a failed one, so a synchronised retry wave meets a breaker that still protects the upstream. Spreading the wave is left to the clients.
* Breaker state is per node. A fleet of gateways in front of one upstream opens and closes its breakers independently, and the `Retry-After` each node sends describes its own breaker only.
