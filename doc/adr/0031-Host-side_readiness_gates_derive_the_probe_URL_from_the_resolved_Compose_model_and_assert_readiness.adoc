= ADR-0031: Host-side readiness gates derive the probe URL from the resolved Compose model and assert readiness

:toclevels: 2

== Status

Proposed

== Context

A host-side script that brings a container stack up must decide when the stack may
be driven. That decision has two independent failure modes, and both are quiet.

**Waiting on the wrong signal.** A liveness probe answers as soon as the process is
up. Readiness answers when the instance can serve. The window between them is
exactly the window in which a test suite's first request reaches an instance whose
bindings are not yet resolved. A suite gated on liveness therefore has a
nondeterministic failure surface that grows with the instance's boot cost, and the
resulting failures present as flakes rather than as a gate defect.

**Restating the model in the gate.** A probe URL embeds a scheme and a published
port. Both are already declared in the Compose model. Restating them in the script
creates two authorities for one fact: republishing a service on a different host
port, adding an instance, or changing an instance's management scheme silently
desynchronises the gate. The failure is asymmetric -- the gate keeps passing while
probing the wrong endpoint, or fails against a healthy container.

A third consideration constrains the remedy. Switching a gate from liveness to
readiness changes *when* it clears, so its retry budget must be re-derived rather
than carried over. A budget adopted from a neighbouring wait, or picked as a round
number, is not evidence; and a budget derived from an uncontended local run
measures the wrong machine.

== Decision

A host-side readiness gate is built on three rules.

**Gate on readiness, not liveness.** The wait probes the readiness endpoint. The
probe must fail closed: the HTTP client is configured to treat a non-2xx response
as failure, so a service answering "not ready" while starting does not clear the
gate at port-accept time.

This rule survived the amendment below unchanged, and is in fact the reason the
amendment is safe. The single-shot readiness assertion both bring-up scripts now
run *is* this rule: it hits the readiness endpoint, with the client configured to
fail closed on a non-2xx answer. What changed is only where the *waiting* happens,
never what is finally asserted.

**Derive the whole probe target from the resolved Compose model.** The script
resolves the service set, each service's published management port, and the scheme
its management interface speaks, from the model -- the scheme via an explicit
per-service label rather than by inferring it from a name or a port number. No
host and no *published* host port is restated in the script. The container-side
management port remains a fixed literal, used as the selector that picks the
management binding out of each service's port list; that is a stable
platform-level contract rather than a per-instance fact, so it is not a
derivation target. Adding, removing, or renumbering an instance requires no
script edit.

Deriving the scheme structurally is what makes a *deliberate* exception free: an
instance whose management interface serves plain HTTP by design is probed over
plain HTTP because its label says so, not because the probe carries a branch on
its service name. The exception costs one label, not one special case.

This rule also survived unchanged, and it now carries one more consumer. The
`compose up --wait` layer described below is *scoped* from the same derivation:
the integration stack passes it exactly the service-name column of the derived
rows, so the set of services the wait gates on and the set the assertion probes
are the same set, from the same source. Scoping matters because an unscoped
`--wait` gates on every service in the model, including the IdP and the upstream
backends, which have their own waits and no baked probe. The operator sample waits
unscoped on purpose -- each of its three services is either health-checked or
correctly satisfied by "running" -- and that is a property of that stack, not a
different rule.

**Delegate the waiting to the image's container health check; the host keeps only a
bound.** *(Amends the original "Derive the retry budget from measurement, and record
the measurement". The rule below replaces it for the two stacks named in the scope
note; see that note for where the original still governs.)*

There is no host-side retry budget. The waiting is performed by
`compose up --wait`, which blocks on the `HEALTHCHECK` baked into the gateway
image, so the cadence that used to live as a host-side loop -- `--interval`,
`--retries`, `--start-period` -- is declared once, in the Dockerfile, and is an
image-level artifact every consumer of that image inherits. Restating it in a
Compose `healthcheck:` key does not extend the image's declaration; it *overrides*
it, which is why a copy is a mirror to be kept in step rather than a second
authority.

The host retains exactly one number, and it is a bound rather than a budget: the
`--wait-timeout`. It is 180s for the integration stack and 120s for the operator
sample, both derived from the same measured worst-case time-to-live of 9.14s
recorded in the integration-test topology document -- roughly a 13x and a 20x
headroom. The two differ because the stacks differ: the integration stack brings up
seven gateway instances concurrently alongside Keycloak and three backends, the
sample brings up one gateway and two supporting services. Neither is consumed on a
healthy run, so the headroom costs nothing; both must survive a loaded CI runner,
which is why they are sized against a measured figure rather than an observed one.

The readiness assertion behind that wait needs no budget at all, and this is the
substantive simplification. A retry budget exists to absorb the interval between
"asked too early" and "ready". By the time the assertion runs, the runtime has
already reported the instance healthy -- so a non-UP readiness answer is not an
early ask, it is a defect, and retrying would only delay reporting it. Single-shot
is therefore not a shortcut; it is what the layering makes correct.

One nuance belongs to the rationale rather than the rule. When a readiness check
reports a *boot-time constructibility* fact read from a cached instance, the
network cost sits in boot, ahead of readiness, not inside the probe. That is why
readiness lands at effectively the same moment liveness does on this gateway, and
why delegating the wait to a liveness-shaped container check costs no additional
delay over the host-side readiness loop it replaced.

**Scope note.** These amendments describe the integration stack's
`start-integration-container.sh` and the operator sample's `start-sample.sh`.
`demo-client/scripts/start-dev-environment.sh` is **unchanged** and still
implements the original three-rule shape, retry budget included -- its services do
not all run an image carrying a baked health check, so it has nothing to delegate
the waiting to. The `affects: demo-client` metadata above therefore remains
correct, and the measured-and-recorded retry-budget rule still governs there in its
original form.

== Consequences

=== Positive

* The suite cannot start against a half-initialised instance, removing a class of
  failure that presents as flakiness rather than as a gate defect.
* Topology changes -- new instances, republished ports, a changed management scheme
  -- propagate to the gate with no script edit, so the model stays the single
  authority.
* A deliberate per-instance exception is expressed as data on the service rather
  than as a branch in the probe, so one loop covers every instance.
* The bound is auditable: its origin is a recorded measurement, not a convention.
* The probe cadence is an image-level artifact, so every consumer of the image --
  the integration stack, the operator sample, an orchestrator -- inherits one
  declaration instead of re-deriving a host-side budget of its own.

=== Negative

* The gate now depends on the model being resolvable at bring-up time, and on each
  service carrying its scheme label. A service that omits the label is not probed
  correctly, so the discovery step must fail loudly rather than degrade.
* Re-deriving the bound requires an instrumented run under contention, which is
  more work than adopting a neighbouring value.
* **The container health check is a bare TCP accept, so the health state it feeds is
  a liveness signal, not a readiness one.** It must be: the management interface's
  scheme is deployment-bound (ADR-0025), so a probe that spoke HTTP would have to
  know which scheme the deployment configured and would fail against the other. The
  consequence is that everything consuming the container's health state --
  `compose up --wait`, `depends_on: condition: service_healthy`, an orchestrator's
  liveness probe, a `docker ps` health column -- is reading liveness however
  "healthy" reads. Readiness remains asserted in exactly two places: the host-side
  single shot against `/q/health/ready`, and `GatewayReadinessCheck` itself. A reader
  who takes a healthy container as a ready one has drawn a conclusion the signal does
  not support.

=== Risks

* The recorded measurement ages. It bounds the live-to-ready delta on the machine
  measured, not absolute container start on slower hosts, so the bound must carry
  headroom rather than track the observed figures.
* Where two bring-up scripts derive from the same model independently, both the
  derivation logic and the timeout constant are duplicated. Duplicated derivation is
  materially safer than a duplicated literal -- both stay correct when the model
  changes -- but the `--wait-timeout` value is a genuine duplicate: the two can be
  re-tuned apart, and only a shared library would make them one. The amendment
  shrinks this rather than removing it -- one bound per script instead of a whole
  retry budget per script -- and the third script, demo-client's, still carries the
  original budget.
* The image's health-check cadence and any Compose `healthcheck:` block mirroring it
  are two spellings of one contract, and Compose resolves the conflict by *replacing*
  rather than merging. A drifted mirror is therefore not a documentation defect but a
  silent substitution of the real probe, which is why the operator sample's copy
  names the Dockerfile as its authority in-line.

== Alternatives Considered

**Keep gating on liveness and accept the window.** Costs nothing and keeps the wait
fast. Rejected because the window is exactly where the suite's first request lands;
the resulting failures are attributed to the tests rather than to the gate, which
is the worst property a failure can have.

**Keep the probe URL hardcoded and correct it when it drifts.** Simple to read at
the call site. Rejected because the drift is silent in the dangerous direction: the
gate keeps passing against a stale endpoint, and the model change that caused it is
elsewhere.

**Branch the probe on the service name for the plain-HTTP instance.** Localises the
exception to one conditional. Rejected because it moves a property of the service
into the prober, so every future exception costs another branch and the prober
accumulates knowledge the model already holds.

**Adopt a neighbouring wait's retry budget.** Removes the need to measure. Rejected
because a budget without a derivation is indistinguishable from a guess, and cannot
be re-evaluated when the boot profile changes.

**Size the budget from an uncontended local run.** Cheap and green. Rejected
because it measures the wrong machine: the budget must survive a loaded CI runner,
and a fast local observation provides no evidence about that.

The rejected options share one shape: each keeps a fact in the gate that the model
already owns, or keeps a number whose origin cannot be reconstructed.
