== Status

Accepted

Supersedes link:0034-Publication_is_triggered_only_by_a_deliberate_standalone_invocation_never_by_a_repository_event_or_an_automated_lifecycle_step.adoc[ADR-0034].

== Decision

=== The question

ADR-0034 decided that an irreversible publication is fired only by a person deciding to fire it. It realised that decision with one mechanism: `workflow_dispatch` as the release workflow's only trigger. This record states what replaced that mechanism and why the replacement does not reverse ADR-0034's reasoning.

*What ADR-0034 was defending against.* On 2026-07-12 a `pull_request: {types: [closed], paths: ['.github/project.yml']}` trigger fired a real Maven Central release. Merging a pull request that touched the version-declaration file published `de.cuioss.sheriff.api:*:1.0.0`. Central artifacts are superseded, never withdrawn. That version was therefore abandoned and relocation-stubbed at 1.0.1, the coordinates moved to `de.cuioss.sheriff.gateway`, and the version line restarted. The defect was not that an event fired the workflow. The defect was that the event fired on merged-ness. Every merge touching that file was a publication, because nothing in the lane asked whether the declared version had changed. A path filter cannot answer that question. `.github/project.yml` carries `name`, `description`, `maven-build`, `sonar`, `pages` and `github-automation`, and that list is open. Editing any of them matched the filter and cut a release.

*What changed.* The pinned `cuioss-organization` reusable release workflow owns a version-changed guard. The guard refuses to release when the declared version did not move against the parent commit, or when a tag for that version already exists. The first condition is the discrimination the 2026-07-12 trigger lacked. It lives one level up, in a versioned, centrally maintained workflow that every project in the organisation consumes, not in each caller's own YAML.

*Why this reopens the trigger question.* An upstream guard is only as good as the caller's discipline in consuming it. A caller that re-implements the comparison locally gets two answers that can disagree, and the local copy is the one that rots. A caller that treats its `paths:` filter as the decision reproduces the 2026-07-12 defect under a new name. A guard that decides correctly also leaves ADR-0034's other residual risks untouched: nothing rejects a change that both removes a trigger and edits the paths it watches, and nothing enforces a merge hold while a release run is in flight.

The choice is therefore narrower than ADR-0034's, and different in kind: given that the release decision can be made correctly and centrally, where does that decision live, and what must the caller refrain from doing?

*The decision:* a release is cut by either of two paths, and the question "is this merge a release?" is answered centrally, never locally.

=== Two triggers, deliberately asymmetric

`.github/workflows/release.yml` declares `workflow_dispatch` and a `pull_request` event narrowed by `types: [closed]`, `branches: [main]` and `paths: ['.github/project.yml']`.

The merge path is conditional. It publishes only when the central guard lets the release through. The image jobs read the guard's verdict through the reusable workflow's `released-version` output.

The dispatch path is unconditional once it reaches the `release` job. It publishes whatever the version declaration says on `main`, including a re-declaration of an unchanged version. The asymmetry is the design. The merge path is the ordinary route and is guarded. The dispatch is the operator-gated fallback for when the ordinary route cannot or did not fire, and its lack of a guard is what makes it a fallback.

The `release` job's `if:` narrows the dispatch path twice. It refuses a dispatch from any ref but `refs/heads/main`, because `workflow_dispatch` offers no branch filter and the signing identity accepts only that ref. It also refuses a dispatch with `dry_run: true` on every ref. A dry run exercises the image lane and cuts no release (link:../development/release-process.adoc#dry-run[Release Process]).

=== The version-changed decision is consumed, never re-implemented

The caller declares the trigger and delegates the decision. The repository has no local version comparison and no local "did the version move" step, and none may be added. A second implementation of a security-relevant decision is a second answer, and the local copy is the one that drifts out of sync with its upstream.

=== The `paths:` filter is a prefilter and never the decision

The filter matches every edit to `.github/project.yml`, not just a version bump. A merge arriving at the workflow therefore proves nothing about the version. The filter's only job is to keep unrelated merges from spending a runner. Reading it as the release condition is the 2026-07-12 defect restated, and the workflow says so in-file at the trigger.

=== The `branches: [main]` filter bounds who may ask

`branches:` filters on the pull request's base, so only a pull request merging into the main line can reach the release job. Without it, a merge into any long-lived branch that touched the declaration file would enter the workflow. The central guard's comparison against that branch would then decide, which could cut a release from a non-main line. This is a base filter, not the version discriminator. It narrows what may ask, never what is answered.

=== `merged == true` is defence in depth, not the guard's substitute

The release job additionally refuses any `pull_request` close that was not a merge. The central guard checks merged-ness too, so this gate is not here because the guard is blind to it. Its merit is not spending a runner on a close without a merge, and one more independent refusal on the path to an irreversible act.

=== Both reachable paths sign under the same ref

A pull request closed by being merged runs against the branch it was merged into, so `GITHUB_REF` is `refs/heads/main` on the merge path exactly as on the dispatch path. This is read off the project's own signing certificates, not inferred from the trigger configuration. Both 0.1.0 (`workflow_dispatch`) and 0.1.1 (`pull_request`) carry `job_workflow_ref = .../release.yml@refs/heads/main`. The accepted Cosign identity is therefore a single anchored ref. Widening it to admit a merge ref would accept a ref no release has ever used.

=== ADR-0034's carried-forward rules stand unchanged

A change that removes or weakens an event-driven trigger still merges on its own, ahead of any change that would fire that trigger. GitHub evaluates a `pull_request` workflow from the base branch, so a mixed change fires the old definition on the very merge that removes it. The post-dispatch merge hold and the "exactly one of each" verification carry forward likewise. Re-arming a trigger does not retire the rules that make changing one safe. It makes them load-bearing again.

== Alternatives rejected

=== Keep `workflow_dispatch` as the only trigger

This is ADR-0034 as it stood. The 2026-07-12 failure mode stays closed by construction, and no upstream is trusted with the release decision.

*Rejected because* the reason for the ban has been addressed at its root. The trigger fired on merged-ness, and now something asks whether the version moved. Retaining the ban would preserve the remedy after the defect was fixed. Its standing cost is a manual act on every release and a runbook whose pre-dispatch gate asserts a trigger shape that is no longer true. A prohibition kept past its cause becomes folklore.

=== Re-implement the version-changed check locally, in this repository's workflow

The release condition becomes inspectable in the file that carries the trigger, with no dependency on an upstream for a security-relevant decision.

*Rejected because* it produces two implementations of one decision. They agree on the day the copy is made and diverge silently afterwards. The divergence surfaces only during a release, either as a release that should not have happened or as one that mysteriously did not. Central ownership is the point: consuming one answer is what makes the answer improvable.

=== Trigger on the merge but require a separate confirmation before publishing

The merge starts the lane and an approval gate holds it short of the irrevocable act. This restores a deliberate human decision without losing the automatic path.

*Rejected as the worst of both.* It reintroduces the manual act ADR-0034's critics find costly, while the reviewer of the version bump stays unsure whether their approval was the decision. It also adds a second place a release can stall unnoticed. An approval that always follows a merge degenerates into a formality, which is the same substitution of a proxy for a decision that ADR-0034 rejected.

=== Drop the `paths:` prefilter and let the central guard decide every merge to the main line

One less filter to reason about, and the guard is the decision anyway.

*Rejected because* the prefilter is cheap and its job is real. It keeps unrelated merges from spending a runner and from appearing in the release workflow's run history, where a long list of no-op runs would make a genuine one harder to notice.

== Consequences

=== Properties of the design

* *The publication decision is made where it can be made correctly.* Whether a version moved is a fact about the declaration. The organisation maintains the guard that reads it once, not once per repository, and fixes a defect in it in one place.
* *The ordinary release path costs no separate act.* Landing the version bump is the release. This re-merges the step ADR-0034 deliberately kept separate, but only because the thing that makes the merge safe is now checked rather than assumed.
* *Mechanism closes the 2026-07-12 failure mode, not prohibition.* ADR-0034 closed it by forbidding the trigger. This record closes it by answering the question the trigger could not. The earlier defence depended on nobody re-adding an event. This one survives the event being present.
* *A fallback exists when the guarded path does not fire.* An operator whose merge cut no release has a documented, unconditional route. The two paths differ in one respect, so the explanation of why the merge did nothing is short.

=== Accepted costs

* *Reviewing a version bump is again reviewing a publication.* The merge of a version-changing `.github/project.yml` pull request is the irrevocable act. ADR-0034 rejected this shape outright. This record accepts it, and accepts that the safety now rests on the guard and not on the reviewer's framing of what they are approving.
* *The safety of the ordinary path depends on an upstream this repository does not own.* The repository consumes the guard from a pinned `cuioss-organization` workflow. Pinning bounds the exposure to a deliberate bump, but the decision itself is no longer inspectable in this repository's own YAML.
* *Two paths mean two behaviours to document and to keep in agreement.* The runbook, the process narrative, the workflow's own comments and the operator-facing verification command all state the posture. Nothing mechanical keeps them all in sync.

=== Risks

Every entry below is a residual risk, not a closed safeguard. As in ADR-0034, they are listed separately so that nobody reads the mechanisms above as covering them.

* *Nothing rejects a mixed trigger-removal change.* This is unchanged from ADR-0034 and now more likely to matter. An event-driven trigger exists again, so a future change that both weakens it and edits the paths it watches fires the old definition on the merge that removes it. Closing this needs an executable check under `.github/workflows/`. Until one exists the merges-on-its-own rule is operator discipline.
* *Nothing enforces the post-dispatch merge hold.* This is unchanged from ADR-0034. No branch policy, merge freeze or workflow check prevents a merge landing between the trigger and the run's completion, so a queue landing can race the release's force-push to the protected branch. The merge path narrows the window rather than closing it, because the run starts at the merge and not at a separate operator act. Nothing bounds the far end.
* *A later reader can mistake the `paths:` prefilter for the guard.* The two are adjacent in the same `on:` block and the prefilter is the visible one. The decision is in a workflow this repository only references. The defence is the in-file comment at the trigger and this record. A future change that narrows or widens the prefilter to tune the release condition would be tuning nothing.
* *A local re-implementation of the version check would stay invisible until it disagreed.* Nothing rejects a caller-local version comparison. The prohibition is normative prose, and a second answer is detectable only at the moment it differs from the first, during a release.
* *The run itself still cannot verify post-publication actions outside the repository.* This is unchanged from ADR-0034, and registry package visibility remains the standing case.

=== The general rule

When a mechanism is banned because it produced a bad outcome, distinguish the mechanism from the missing discrimination that let it misfire. A ban is the right immediate response and the wrong permanent one. It is cheap, verifiable and total, but it fixes the symptom by removing capability. It also survives its own justification, because nothing forces a re-examination when the underlying gap is later closed.

Two questions decide whether a ban may be lifted:

* Has something been added that answers the question the banned mechanism could not answer, and not merely narrowed the circumstances in which it fires?
* Is that answer owned somewhere it can be maintained and corrected, rather than copied into each consumer?

Where both hold, a guard may replace the ban. The ban's residual rules, the ones about operating the mechanism safely, must then be carried forward explicitly, because lifting the ban is exactly when they start mattering again. Where either fails, a filter that narrows when the mechanism fires is no substitute for a check on whether it should. Narrowing reduces the frequency of the bad outcome while leaving it reachable, and a rare irreversible failure is harder to catch than a common one.
