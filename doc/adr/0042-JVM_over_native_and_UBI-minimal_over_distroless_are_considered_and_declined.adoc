== Status

Accepted

== Decision

=== The question

Trust material is deployment-bound. The gateway configuration names TLS policy in neutral terms, while the deployment supplies certificate, key and trust material (link:0025-The_whole_server-TLS_surface_is_neutral_in_gatewayyaml_and_bound_by_exactly_two_seams.adoc[ADR-0025]). That ruling settles who supplies the material. It does not settle how the artifact lets them, and on this artifact the answer is unusually narrow.

The published image is a GraalVM native executable on a distroless base. Two properties of that combination bound the operator's options, and no configuration file shows either:

* *The base carries no `update-ca-trust`, and nothing else that could extend an OS trust store.* It carries no package manager and no shell at all, the same property link:0039-The_distroless_images_health_check_is_answered_by_the_application_binary_before_boot.adoc[ADR-0039] had to design around for the health check. The image has no writable system anchor directory to drop a PEM into, and no command that would rebuild the bundle if it had.
* *A native image captures its trust material at build time.* Nothing at container start extends what the executable was built with.

The consequence is a single supported runtime route: the JDK's `-Djavax.net.ssl.trustStore` triple, passed as command-line arguments to the native runner. A native executable does not honour `JAVA_TOOL_OPTIONS`, so it silently ignores the one variable an operator would reach for first.

*That route replaces the whole trust bundle and does not add to it.* An operator who needs one private certificate authority must assemble a store that also contains every public root they still want, because naming a store discards the platform bundle wholesale. A store built from the private CA alone works against that CA and stops trusting everything else. This happens silently and surfaces later as an opaque handshake failure. The link:../configuration.adoc#_default_trust_store_replaces[configuration reference] holds the full operator route and the recipe that keeps the public roots.

An obvious remedy has to be weighed: ship a JVM artifact on a UBI-minimal base. That base has a package manager and `update-ca-trust`, so trust becomes an extendable OS store. An operator drops a PEM into the anchors directory and runs one command, and the private CA joins the public roots. It is the shape every operator already knows, and it removes the replacement hazard at its root.

This record therefore does not ask whether the current operator experience is good. It is not. It asks whether that experience is worth the artifact change that would fix it.

*The decision:* the native executable stays on the distroless base. Documentation and boot-time reporting close the trust-material gap, not an artifact change. The JVM-on-UBI-minimal alternative is considered and declined for now, not rejected on principle.

=== Three supports carry the decision

*The attack surface is the property the base exists to provide.* A UBI-minimal base restores a package manager and a shell into every running production container, permanently, to serve a change an operator makes rarely. ADR-0039 declined the same trade when it needed a health probe. Declining it twice for the same reason is consistency, not repetition.

*The self-answering health check rests on the current base.* ADR-0039's mechanism, the application binary answering its own `HEALTHCHECK` before the framework boots, exists because the image carries exactly one executable. Changing the base does not break it, but it removes the constraint that made it the right answer. The artifact change is therefore not confined to the artifact, because it reopens a delivered decision. A change with that reach is not one to make as a side effect of a trust ergonomics fix.

*The `-D` route is the runtime's own documented one, and no launch of the native artifact in this repository passes the triple as command-line `-D` arguments.* The triple on the runner's command line, appended to the exec-form `ENTRYPOINT`, is how a native executable takes a runtime default trust store. The integration stack does not take that route. No gateway instance there passes a `-D` argument. Each binds its private certificate authority through named trust profiles instead: `jwks.tls_profile` for the JWKS fetch and `egress_tls.oidc_tls_profile` for the BFF's own back channel to the identity provider. JVM tests set the same `javax.net.ssl.trustStore*` properties, but in-process, and they launch no native artifact with them. The route therefore rests on the runtime's documented behaviour, not on a test of the real artifact. The boot-time reporting below keeps "document it" an answer and not a deferral: the log of every deployment that takes the route names the store actually in force.

=== What the documentation-and-reporting answer consists of

The gap is an operator-knowledge gap, and it is closed where operator knowledge lives:

* The configuration reference states the hazard before the recipe, and the TLS-edge topic repeats it as an operator-facing pointer. The recipe is the `keytool` sequence that starts from the platform bundle, so the public roots survive.
* The gateway reports the effective trust source at boot, so nobody has to derive it. `ApiSheriff-17` names the store in force per tier. `ApiSheriff-122` fires whenever an operator-supplied store is in effect. It states the replacement hazard, and it names which half of the egress surface was left behind when the two tiers disagree.

Reporting is what makes the decision defensible. The replacement is still silent in the sense that nothing refuses it. It is no longer unobserved, and the log names the split-tier state an operator could not have computed, in the one place they will look.

=== This record contradicts neither record it depends on

ADR-0025's ruling is unchanged. Material stays deployment-supplied and is never promoted into the gateway configuration. This record is about the mechanism the deployment uses, not about who owns the material. ADR-0039's mechanism is unchanged, and keeping the base preserves its constraint.

== Alternatives rejected

=== Ship a JVM artifact on a UBI-minimal base

This is the remedy this record is about. It restores an extendable OS trust store, makes `update-ca-trust` available, and removes the replacement hazard at its root.

*Declined for now* on the three supports above: the permanent attack-surface cost paid for a rare operation, the reach into ADR-0039's delivered decision, and the current route being the runtime's own documented one. It is the alternative most likely to be adopted later, so Consequences enumerates its reversal conditions.

=== Keep the native executable but move it to UBI-minimal

This buys `update-ca-trust` without giving up the native format's start-up and footprint properties. It is a strictly smaller change than switching artifact format.

*Declined because* it pays the surface cost in full while buying less than it appears to. A native image still captures trust material at build time, so an OS store extended after the image was built is not automatically what the executable's default `TrustManager` resolves. The route that reaches it would still be the `-D` triple, which is the route the current artifact already offers.

=== Bake the private CA into the image at build time

This removes the runtime question entirely, and the native build already captures trust material at that point.

*Rejected because* it contradicts ADR-0025 directly. It makes trust material an artifact property and not a deployment-supplied one. Every deployment with a different CA would need its own image, and the published artifact would carry an anchor specific to whoever built it.

=== Add a small trust-assembly step to the entry point

The binary would read a mounted anchors directory and build the store itself. This keeps the base and gives the operator the additive experience they expect.

*Rejected because* it puts trust-chain assembly inside the security-critical binary, at start-up, on a path that would have to fail closed and that only the deployments using it would exercise. It also invents a second trust-configuration surface alongside the JDK's own, which is the divergence ADR-0025's single-source rule exists to prevent.

=== Do nothing and leave the gap undocumented

This was the state before this record.

*Rejected because* it is the option under which the hazard is both silent and unwritten. An operator following the one-line instruction to "bind those anchors into the JVM default trust store" produces the failing store and has nothing that says why.

== Consequences

=== Properties of the design

* The attack surface the distroless base provides is unchanged: no shell, no package manager, no second binary. The property survives this requirement.
* ADR-0039's health-check mechanism keeps the constraint that made it correct, so this decision reopens no delivered decision as a side effect.
* The trade-off is written down. A future contributor who proposes a JVM artifact argues against a recorded position with stated reversal conditions and does not have to rediscover the question.

=== Accepted costs

* *The operator experience for trust material stays worse than the industry norm.* Everyone else adds an anchor, and here an operator assembles a bundle. That is the whole cost of the decision.
* *The replacement hazard survives.* Documentation and a boot record make it observable. Neither makes it impossible. An operator who reads neither can still ship a store that removed the public roots.
* *The two trust tiers remain independently settable,* so a half-moved posture is reachable. The gateway reports it when it happens, and nothing refuses it.
* *No launch of the native artifact in this repository takes the route the operator is told to use.* The integration stack binds its trust through named profiles and passes no `-D` argument. The JVM tests that set the same properties do so in-process and launch no native artifact. The documentation therefore describes the runtime's documented behaviour, not a measured one.

=== Risks

* Boot-time reporting is only as good as the log an operator reads. In a deployment that ships container output nowhere, `ApiSheriff-122` is emitted into nothing, and the control degrades to the documentation alone.
* Someone has to notice the reversal conditions below. Nothing fires when one is met, and the most likely way this record goes stale is the first condition accumulating quietly.

=== What would reverse this decision

The decision is declined for now, so the reversal conditions are recorded and not left to judgement. Any one of the following makes the trade come out the other way:

. *A second operator-visible defect traced to the same root.* The base's absent trust tooling is currently one documented hazard. A second independent operator problem caused by the reduced base, not by the native format generally, means the documentation answer is patching symptoms.
. *The `-D` route stops being sufficient.* If a leg appears that the default `TrustManager` does not reach, or a runtime change makes the triple unreliable on a native executable, the one supported route is gone and nothing is left to document.
. *A trust change becomes routine rather than rare.* The acceptance rests on the change being infrequent enough that a documented, replacement-shaped procedure is tolerable. A deployment pattern that rotates anchors on a schedule inverts that.
. *The ADR-0039 constraint is retired for an independent reason.* If the health check stops depending on the single-executable property, one of the three supports is gone, and the remaining two are weaker than they read here.
. *The attack-surface cost of UBI-minimal falls materially.* An example is a variant with the anchor tooling but no shell and no package manager. That would let the extendable store be bought without the surface it currently comes bundled with.

A reversal on any of these is an artifact change, so it needs its own record superseding this one.

=== The general rule

When a deliberately reduced runtime makes a legitimate operation awkward, the choice is between restoring the capability and making the awkwardness legible. Restoring it is right when the operation is frequent or the reduced form is unreliable. Making it legible is right when the operation is rare and the narrow route is one the runtime documents.

"Make it legible" counts as an answer only when it is paid for in full: the hazard stated before the recipe, and the resulting state reported at runtime and not left to be derived. Documentation alone would be a deferral wearing a decision's clothes. The boot record is what turns it into a control.

The second half is the reversal conditions. A decision declined for now without written conditions is indistinguishable a year later from one declined on principle. Whoever next has to argue the question from scratch pays the cost of that confusion.
