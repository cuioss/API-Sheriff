= ADR-0041: The JWKS hostname-verification knob is the library's own passthrough, and its sslContext collision is refused at boot

== Status

Accepted

== Decision

link:0040-Upstream_hostname_verification_is_a_global_egress-TLS_knob_bound_at_client_construction.adoc[ADR-0040]
defines the `egress_tls` block, names `jwks_verify_hostname` as the JWKS peer of
`upstream_verify_hostname`, and states the egress-TLS principle every leg follows
(link:0040-Upstream_hostname_verification_is_a_global_egress-TLS_knob_bound_at_client_construction.adoc#egress-tls-principle[the egress-TLS principle]).
This record applies that principle to the JWKS back channel. The question it settles is the
mechanism, and a property of the JWKS leg forces the answer.

*The JWKS back channel is not a Vert.x client.* The token-validation library reaches it. The library
builds a JDK `java.net.http.HttpClient` behind its own HTTP-handler abstraction, so none of ADR-0040's
three construction sites is involved.

Three facts about that library settle the mechanism.

* *The library carries the passthrough.* Its JWKS loader-config builder (`HttpJwksLoaderConfig`) and
  its well-known discovery-config builder each carry `verifyHostname(boolean)`. Both forward the value
  to the shared HTTP-handler builder, which implements the relaxation.
* *The relaxation substitutes a trust manager on a context the handler derives.* With the flag off,
  the handler builds an SSL context from `TrustManagerFactory.init((KeyStore) null)`, the JVM default
  trust store. It wraps each `X509ExtendedTrustManager` in a delegating one that forwards chain
  validation and drops the overloads that check endpoint identity. Chain validation is untouched.
* *The library refuses the relaxation on a caller-supplied context.* Both builders raise
  `IllegalArgumentException` from `build()` when `verifyHostname(false)` is combined with
  `sslContext(...)`, ahead of the endpoint-source check. The guard is sound: the relaxation swaps the
  trust manager of a context the handler derived, so a context the caller built has nothing to relax.
  Honouring the flag there would mean silently rebuilding the caller's context.

That refusal collides with a gateway feature. Under
link:0011-gatewayyaml_exposes_JWKS_trust_and_egress_as_neutral_names_bound_by_the_deployment.adoc[ADR-0011]
an issuer may name a per-issuer `jwks.tls_profile`. The gateway resolves that name to an `SSLContext`
and hands it to exactly the builder method the library refuses to combine with the relaxation. So the
global hostname flag and a per-issuer trust profile are mutually exclusive per issuer, by a property of
the library.

*`egress_tls.jwks_verify_hostname` is passed straight through to the library's own
`verifyHostname(boolean)`, on every `http` JWKS source, on both the `true` and the `false` path. The one
combination the library refuses, the relaxation together with a per-issuer `jwks.tls_profile`, is a
boot refusal first: `TokenValidatorProducer` reports `CONFIG_INVALID` naming both keys, the profile
and the issuer.*

=== The passthrough is called unconditionally

`TokenValidatorProducer` resolves the flag once, at bean construction, and passes the value to
`verifyHostname` for every `http` JWKS source it builds. One resolution matches the key's scope: it is
gateway-global with no per-issuer override. A `file`-sourced issuer opens no TLS connection, so the
flag does not apply to it and no collision arises there. Passing the value on the `true` path is
principle (4) of ADR-0040.

=== The collision is refused in the gateway's own vocabulary

An `http`-sourced issuer that names `jwks.tls_profile` while `egress_tls.jwks_verify_hostname` is
`false` is a boot refusal. `TokenValidatorProducer` checks the combination before it touches the builder. Left to the
library, the operator would see an `IllegalArgumentException` in terms of `sslContext(...)` and
`verifyHostname(false)`, two symbols that appear nowhere in `gateway.yaml`. That is principle (3) of
ADR-0040.

It is a refusal, not a warning, because ADR-0040 makes a posture the gateway cannot honour a boot
refusal. A relaxed hostname check on its own is a legitimate deployment that must merely be visible,
and ADR-0040 reports it as a boot WARN. This combination is not a deployment at all: the library rejects
it one layer down whatever the gateway does. The only choice is which error the operator sees.

=== The two controls stay orthogonal

`jwks.tls_profile` answers chain trust; `jwks_verify_hostname` answers hostname verification. The mutual
exclusion is a per-issuer constraint on combining them, never a merge into one control. ADR-0011's
trust-profile resolver keeps its fail-closed refusals unchanged, and the new key reaches none of them.
An issuer that needs private-CA anchors names a profile and keeps verifying hostnames. An issuer that
needs the hostname relaxation reaches its anchors through the JVM default trust store.

=== The scope claim is proven by a dial

The proof runs at unit level, against a local HTTPS server, through the public producer path:

* a *matched control* runs the same server, certificate, issuer and key material twice, differing only
  in the flag; chain trust succeeds on both legs, so hostname verification is the only discriminator;
* an *omitted-block leg* proves that a document with no `egress_tls` resolves to verification on;
* an *untrusted-chain leg* dials a server whose certificate names the dialled address under a root that
  is not an anchor, with the flag off, and must still be refused;
* a *falsification check*: deleting the `verifyHostname` call turns the relaxed leg red.

The collision refusal has its own matched control: the same `false` flag without a profile must
assemble cleanly.

== Alternatives rejected

*Hand-roll a delegating `X509ExtendedTrustManager` in the gateway.* Derive a context, wrap each trust
manager so it forwards chain validation and drops the identity check, and pass the result to
`sslContext(...)`. The library does exactly this internally, so it would work, and it would sidestep the
builder guard. Rejected, and the reason it would work is the reason it must not be done. Passing a
caller-built context is what the guard exists to refuse, so this defeats a safety check by satisfying
its letter. The gateway would then own a security-critical trust manager whose defect mode, a
forwarded overload that validates nothing, is invisible in review. It would have to stay correct
against every JDK and library change, and it would diverge from the library's own version the moment
that one is corrected. Writing TLS verification code to avoid calling a method that does it for you is
the wrong trade in a security gateway.

*Derive a relaxed `SSLContext` from the named profile's trust material.* Answer the collision instead of
refusing it: resolve the profile's anchors, build a context from them, wrap its trust managers, and pass
that. Both controls would then apply to one issuer. Rejected for the reasons above, plus one: it makes
the gateway's behaviour diverge from the library's contract, not merely bypass a check. Two issuers
configured alike would verify hostnames differently depending on which code path built their context.
The combination is rare: it needs an IdP that presents a private-CA certificate and is reached at an
address that certificate does not name. The right answer there is to fix the certificate or the name.

*Petition the library to lift the guard.* Ask the token-validation library to allow
`verifyHostname(false)` with a caller-supplied `sslContext`. Rejected because the guard is correct. The
library cannot relax a context it did not build without rebuilding it, silently discarding the caller's
key managers, protocols and parameters. ADR-0022 adopts an upstream hardening decision instead of arguing
it down, and the same posture applies to a guard. Requesting the change would also make the gateway's
correctness depend on a third party accepting a weakening.

Every rejected option moves security-critical TLS code into the gateway to widen the relaxation's reach.
A relaxation the library implements on a context it controls stays the library's to implement, and the
collision refusal is the smaller price.

== Consequences

*Positive.*

* The key is an active control, and a dial proves its behaviour.
* The gateway holds no trust-manager code. The relaxation is the library's own, so the gateway inherits
  any correction the library makes.
* ADR-0011's trust-profile seam and its refusals are untouched, and `jwks.tls_profile` means what it
  meant.
* The incoherent combination fails at boot, naming keys the operator wrote, not at the first bearer
  request.
* The gateway's posture is independent of the library's default.

*Negative.*

* *The flag is global and the profile is per issuer, so the exclusion is felt at the finer grain.* A
  gateway with several issuers, one of which needs the relaxation, must turn the flag off globally. Every
  other issuer that names a `jwks.tls_profile` then fails the boot. There is no per-issuer hostname
  override, because ADR-0040 placed the key at block scope.
* *The refusal names two keys at two scopes.* The operator must understand a block key and a per-issuer
  key to act on it. Naming only one would be worse, because the collision is between them.
* The gateway carries a check whose only reason is a constraint one layer down. If the library lifts the
  restriction, the refusal becomes a gateway-imposed limit and must be removed deliberately.

*Accepted failure modes.*

* *The relaxation is read as a general TLS disable.* The schema description, the model documentation,
  the operator pages and the boot WARN (`ApiSheriff-120`, once per boot) state the hostname-only scope,
  and the untrusted-chain leg proves it.
* *The exclusion is found at boot, not at authoring time.* The schema cannot express a constraint
  between a block key and a per-issuer key, so a document with the collision validates and then fails
  to start. The refusal names both keys and the issuer, and the schema description and the operator
  pages state the constraint.
* *The hostname check is relaxed when chain trust was the real problem.* `jwks.tls_profile` is the
  chain-trust answer, and the collision refusal turns reaching for the wrong lever while the right one
  is configured into a boot refusal.

*Constraints on later change.*

* *The discovery branch is not bound.* The library's discovery-config builder carries the same
  passthrough, but the gateway's issuer model has no discovery source. Adding one is a decision to
  extend this binding. A discovery source without it would leave one branch of the JWKS leg on the
  library default, the partial-binding class
  link:0026-A_security_bound_declared_at_one_inbound-validation_stage_is_re-asserted_at_every_later_stage_that_re-validates_the_same_input.adoc[ADR-0026]
  prevents. `EgressTlsPostureArchTest` maps `HttpJwksLoaderConfig#builder()` today.
