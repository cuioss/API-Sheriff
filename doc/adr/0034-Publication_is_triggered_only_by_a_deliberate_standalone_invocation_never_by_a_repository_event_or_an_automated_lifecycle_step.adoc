== Status

Superseded

Superseded by link:0035-A_release_is_cut_by_a_guarded_version-bump_merge_or_a_deliberate_dispatch_and_the_version-changed_decision_is_centrally_owned.adoc[ADR-0035]. This record states the decision as it was made, and the release workflow no longer has this shape.

== Decision

=== The question

Some acts a repository performs are irreversible outside the repository. Publishing a GA coordinate to a public Maven repository and pushing a signed image to a public registry both leave this project's control the moment they succeed. A published coordinate can be superseded, never withdrawn. Abandoning one costs a fresh patch version and a set of relocation stubs, and the abandoned coordinate stays visible forever.

Every irreversible act needs a trigger, and the trigger's shape decides who can fire it and on what evidence. Four structural properties make that choice non-obvious:

* *The convenient trigger already exists.* A release needs a version declaration to land somewhere in the repository, so the natural-seeming design is to let that merge also publish. It removes a step and needs no new mechanism. It also makes every merge touching that file a publication. Review of a declaration becomes review of an irrevocable act, without anyone involved framing it that way.
* *An event trigger on an irreversible act is hazardous to remove, not merely hazardous to have.* For a `pull_request` event, including `types: [closed]`, GitHub evaluates the workflow definition from the base branch, not from the pull request's head. A pull request that both deletes such a trigger and edits the paths that trigger watches is therefore still evaluated against the old definition. The very merge that removes the trigger fires it one last time. Retreat from this design is a trap the design itself lays.
* *Part of the safety evidence is a property of a moment, not of the repository.* Whether the trigger is still dispatch-only, whether the shared branch is quiesced, and whether a tag for the version already exists are all true at an instant. A record of any of them looks exactly like a record of a durable fact, and it ages the moment it is written.
* *The publication lane is not atomic.* The artifact publication completes before any image step runs. A failure anywhere downstream (a scan gate, a registry push, a signature) leaves a partial release whose published half is already irrevocable. The lane cannot be reordered to fix this, because the released version does not exist until the publication has happened.

Together these produce one choice: where does the authority to fire an irreversible act live, and what has to be true at the instant it fires?

*The decision:* an irreversible publication is fired only by a person deciding to fire it, and the evidence that makes it safe is established at that instant. Automation prepares a release. It never triggers one.

=== Dispatch is the only trigger

The release workflow declares `workflow_dispatch` and nothing else. No merge of any pull request, touching any path, can cut a release. The scope of that guarantee is deliberately narrow. A merge to the main branch is not inert, because the main-branch build publishes a snapshot. What a merge cannot do is reach the irrevocable act.

=== A trigger removal merges on its own

A change that removes or weakens an event-driven trigger merges by itself, ahead of any change that would fire that trigger. The trigger's absence is verified on the base branch before anyone relies on it. This is one normative rule, stated once, because base-branch evaluation makes the naive ordering actively wrong. Only human ordering carries this rule: no check rejects a change that both removes a trigger and edits the paths it watches. Consequences records it as a residual operator risk, not a closed safeguard.

=== The procedure is a standalone runbook, not a lifecycle step

The steps that perform the dispatch live in a user-invocable runbook carried in the repository. The runbook is deliberately not a step of any automated delivery pipeline, and no pipeline configuration registers it. Whoever decides to release follows it from start to finish. It reads correctly whether it is executed as a skill or followed as a document.

=== Time-varying evidence is re-established, never inherited

At cut time the runbook re-asserts four things:

* The trigger is still dispatch-only. The assertion names the commit it read the trigger at, because a claim that names no commit is unverifiable later.
* The release workflow remains the only invocation of the reusable release workflow.
* The shared branch is quiesced.
* No tag for the version already exists.

Recorded evidence from earlier work supplies the method, never the fact.

=== The check-then-act window is bounded at the instant of the act

The publication force-pushes to the protected branch as a queue-bypass actor, so a force push racing a queue landing can discard commits. The runbook therefore asserts quiescence immediately before dispatching, and nothing merges until the run completes. This is a bound at the instant of the act rather than a structural adjacency to some other event. The two halves are not equally strong, and this record does not claim they are:

* *Pre-dispatch is mechanically checked.* The runbook re-reads the shared branch immediately before dispatching. It aborts non-zero unless the branch still equals the commit the green-branch gate proved. A landing between the gate and the dispatch stops the release rather than publishing an unverified commit. The dispatch itself names the branch, not that commit, because the signature identity, the release plugin's push target and the documented shape of the dispatch reference are all bound to the branch. Re-assertion closes the drift, not a pinned reference.
* *Post-dispatch is unenforced.* No mechanism stands behind "nothing merges until the run completes". No branch policy, merge freeze or workflow check rejects a merge inside that window. It is an operator obligation, and Consequences records it as a residual risk.

=== Verification is "exactly one of each"

Verification asserts one tag, one release entry, one repository deployment and one image digest carrying both published tags. "It worked" is not enough. A force-pushed tag and a re-runnable workflow both make duplication a genuine outcome, and a duplicate is far harder to notice than an absence.

== Alternatives rejected

=== Event-driven trigger on the version-declaration file

Publication fires when a pull request touching the release-version declaration merges. It collapses two steps into one and introduces no new mechanism, and it is the shape a sibling project in the same ecosystem uses.

*Rejected because* it makes every merge touching that file an irrevocable publication and relocates the publication decision into ordinary code review, where it is invisible. The failure mode is a GA coordinate that cannot be withdrawn. The rejection compounds rather than balances. GitHub evaluates such a trigger from the base branch, so adopting it also makes it hazardous to remove later. The option is not merely risky to operate. It is difficult to retreat from.

=== A publication step inside an automated delivery lifecycle

The publication runs as a step of the same automated pipeline that lands the work, firing when that pipeline reaches its end. It places the release adjacent to the change being released. That adjacency can close a check-then-act window on the shared branch by ordering alone.

*Rejected because* it makes an irreversible external act a consequence of an unrelated pipeline succeeding. The trigger degenerates into "the automation got this far", which is a statement about the automation rather than a decision to publish. It further requires registering the step in the pipeline's configuration, so the authority to publish becomes a configuration entry that any later configuration change can relocate or drop. The ordering benefit it buys is real but replaceable. A procedure can close a check-then-act window at the instant of the act, whereas nothing can close a misplaced trigger.

=== Inheriting recorded pre-dispatch evidence

The evidence that makes a cut safe is established once, recorded, and simply read at cut time. It moves verification off the critical path and yields an auditable artefact.

*Rejected because* most of that evidence describes a moment rather than the repository, and a record of a momentary property is shaped exactly like a record of a durable one. Inheriting it substitutes a confident claim for a check, in the one place where a wrong answer is unrecoverable. The recorded baseline keeps its full value as a statement of method: what to check, and how to check it soundly.

Each rejected option substitutes a proxy for the decision to publish: a file edit, a pipeline's success, an earlier moment's observation. An irreversible act admits no proxy. The trigger must be the decision itself, and the evidence must be contemporaneous with it.

== Consequences

=== Properties of the design

* *Publication is unreachable by accident.* No path leads from a merge to a GA coordinate. Reviewing a version declaration is reviewing a declaration, not silently authorising a publication.
* *The safety evidence is contemporaneous with the act.* The runbook re-derives the time-varying items instead of reading a baseline, so a stale record cannot be mistaken for a live guarantee.
* *The procedure outlives the work that produced it.* Anyone can invoke a standalone runbook at any time, with no pipeline in flight and no lifecycle slot to occupy. Nothing has to be scheduled for a release to become possible, and nothing expires.
* *Retreat stays possible.* The merge-on-its-own rule is normative, not folklore, so a future trigger change has a known-safe ordering and does not spring the base-branch trap. Knowing the ordering is not the same as being held to it, as the risks below state. A written rule can still be followed and reviewed against, where folklore cannot.

=== Accepted costs

* *Releasing costs a deliberate human act and cannot be scheduled.* There is no automatic release lane, and none can be added without reversing this decision.
* *The evidence is re-established by hand at every cut.* That cost is paid every time, by design.
* *The runbook restates operative facts that also live in the process narrative,* so the two can drift. The duplication is deliberate, because a runbook must be followable cold. The narrative remains canonical, and the drift is a maintenance obligation this decision accepts.

=== Risks

Every entry below is a residual risk, not a closed safeguard. The first three are residual operator risks: human ordering or human restraint carries the rule, and no check rejects the violating action. They are listed here so that nobody reads the mechanisms above as covering them.

* *The dispatch-only guarantee is one commit from regressing.* It is a property of a workflow file, not a mechanically enforced invariant. The defence is the normative rule plus an in-file instruction, and a determined change overwrites both. The runbook therefore re-reads the guarantee at a named commit on every cut and does not assume it.
* *Nothing rejects a mixed trigger-removal change.* The merges-on-its-own rule is normative prose. No pull-request check inspects whether a change both removes or weakens an event-driven trigger and edits the paths that trigger watches. GitHub evaluates such a workflow from the base branch, so a mixed change still fires the old definition on the very merge that removes it. The failure stays invisible until the trigger it was supposed to have removed fires an irreversible act. Closing this needs an executable check under `.github/workflows/`. Until one exists the rule is operator discipline, and a reviewer approving such a change is the only thing standing in the way.
* *Nothing enforces the post-dispatch merge hold.* No branch protection rule, merge-queue freeze or workflow check prevents a merge from landing between the dispatch and the run's completion. A queue landing can still race the release's force-push to the protected branch and discard commits. The quiescence assertion bounds only the pre-dispatch half, and only because the runbook aborts non-zero on branch drift. After the dispatch the bound is a request to the team. Closing this needs an enforced merge freeze or an equivalent branch-policy control.
* *A step performed from memory instead of from the runbook silently loses the checks that make the act safe.* The loss stays invisible until the failure those checks exist to prevent occurs.
* *The release run itself cannot verify post-publication actions outside the repository.* Registry package visibility is the standing case. The in-workflow smoke step pulls with the run's own credentials, so an unfinished visibility change leaves every check green while consumers outside the organisation cannot pull at all.

=== The general rule

An operation whose effects escape the system's control is bounded by when its trigger fires and by when its preconditions were last observed. Those two instants must coincide. Two diagnostic questions separate such an operation from an ordinary one:

* Can the system undo the effect using only its own mechanisms? A "no" forbids an event or a pipeline outcome as the trigger, because both fire on something other than the decision.
* Is any precondition true at an instant rather than true of the system? A "yes" forbids inheriting a recorded observation, because a record cannot distinguish a momentary property from a durable one.

Where both hold, the trigger belongs to a deliberate, separately invocable procedure that re-establishes the momentary preconditions as its own first act.
