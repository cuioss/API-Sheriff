== Status

Accepted

== Decision

The application portal is an optional HTML page on one reserved path. It lists the enabled applications behind the gateway and shows the browser's signed-in state. With `portal.error_pages` the same template also renders an HTML page for a gateway-originated error a browser navigates into. Two properties make HTML different from every JSON body the gateway emits:

* *What the gateway writes is interpreted in the gateway's origin.* The page carries catalog values, a `notice` query parameter (attacker-controlled), the signed-in user's `preferred_username` and an error status. A value written without escaping runs as script with the gateway's credentials.
* *The markup is operator-authored.* A template is a program. Whatever the engine lets a template reach, the template author reaches, and so does anyone who can write to the configuration volume.

The choice of engine is therefore a security boundary. The record settles which engine renders, how escaping is enforced, what a template sees, where the portal sits in the request flow, and when an error becomes HTML.

*The decision:* the portal renders through one standalone Qute engine that the gateway builds and constrains itself, over a fixed map of plain values. The boot refuses a template that could bypass that engine's escaping or reach beyond the data model.

=== A standalone engine

`quarkus-qute` is a dependency of the application module, approved by the operator for this feature, with its version managed by the Quarkus platform BOM. The portal never injects or renders through the Quarkus-managed `Engine`. `PortalRenderer` builds its own `io.quarkus.qute.Engine`:

* the default value resolvers except the raw resolver, so `raw` and `safe` never resolve to an unescaped value;
* `HtmlEscaper` as the result mapper for the `text/html` variant every template is parsed with;
* no namespace resolver, no template locator and no reflection resolver;
* only the `if`, `for`/`each`, `let`/`set` and `when`/`switch` sections, because `eval` would parse a model value as template code and `include`/`insert` have no locator. Any other section is a parse error;
* strict rendering, so a key outside the data model fails and prints nothing.

The built-in template lives under `portal/` on the classpath, not `templates/`, so the managed engine's build-time discovery never claims it. It is included in the native image explicitly.

=== A map-only data model

`PortalPageModel` is the single definition of the template contract. It produces a map whose keys are always all present, an absent value being `null`, and whose values are limited to `String`, `Boolean`, `Integer`, `List` and `Map`. No domain object reaches a template. A template has nothing to call, and rendering needs no reflection registration for the native image.

=== Two-layer escape-bypass enforcement

The missing raw resolver is the first layer. The second is independent of it. Building a renderer parses the template and walks every expression, including section parameters and virtual-method arguments. Any expression part naming `raw` or `safe`, in any spelling including a filter-style `x|raw`, and any namespaced expression refuses the template with the file and line. A missing, unreadable or unparseable template is refused the same way.

The refusal aborts startup through the structured `ApiSheriff-202` record, so a gateway serves a template that was found, parsed and cleared, or does not start. The walk does not check the keys a template references against the data model. A reference to a key the model does not carry parses cleanly and fails at render time under strict rendering. The boot reads the template once and never reloads it.

=== A reservation seam of its own

`PortalEndpoint` answers `portal.path`, consulted after the reserved OIDC paths and before the route table, by exact string equality with the canonical request path on every host. The path is not added to the OIDC `ReservedPathRegistry`, a closed set derived from the `oidc` block and matched on the OIDC host only.

`PortalRules` refuses the collisions at boot: a non-canonical path, a path equal to a reserved OIDC path, or a path equal to an enabled endpoint's exact route. A prefix route covering the path is admitted, which is how the portal can claim the context root. Without a `portal` block an inert endpoint that never matches stands in, and the edge is unchanged. One CDI producer, `PortalProducer`, wires the package.

=== Explicit-`text/html` negotiation

The gateway renders an HTML error page only when error pages are enabled, the exit is classified `HTML_ELIGIBLE`, and the request's `Accept` lists `text/html` explicitly with a quality above zero. Wildcards never qualify. `ErrorPageClassifier` classifies every event type and every non-event exit in a default-free `switch`, so a new one fails compilation until it is classified. Only gateway-originated errors are eligible. A response relayed from an origin is never replaced. The status is the same for the HTML and the problem-document answer.

=== Fixed response headers

Every portal response carries a fixed, hardened `Content-Security-Policy: default-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'` and `X-Content-Type-Options: nosniff`, set in place of whatever the resolved `security_headers` block declares for those names (`SecurityHeadersStage.applyPortalHeaders`). The other gateway-owned headers keep their block (link:0007-anchor-scoped-policy.adoc[ADR-0007]).

== Alternatives rejected

=== Render through the Quarkus-managed Qute engine

This is the idiomatic Quarkus choice, with type-safe templates, build-time validation and hot reload in development.

*Rejected because* the managed engine carries the `cdi:`, `config:` and `inject:` namespaces. Every operator template could reach application beans and configuration properties, including resolved secrets. Removing the namespaces from the managed engine would change behaviour for every other template the application might render. Build-time validation also cannot see an operator template supplied at deployment time. The configuration boundary would reach the application's internals.

=== Rely on default escaping and document that templates must not use `raw` or `safe`

Escaping is on by default, so a well-behaved template is safe.

*Rejected because* the guarantee would rest on every operator template, forever, and on review a gateway cannot perform at boot. One `{title.raw}` would turn a catalog label or the username into stored XSS. A security property the gateway can enforce should not be delegated to documentation.

=== Hand the template the configuration and session objects

Passing `PortalConfig`, the catalog records and a session object would spare the map assembly and allow convenience methods.

*Rejected in favour of* one explicit, documented model. It would expose every accessor to templates, require reflection registration for each type in the native image, and make the template contract whatever the Java types expose.

=== A different template engine, or string substitution

A logic-less engine or placeholder substitution would remove the section surface entirely.

*Rejected because* it would bring a dependency the platform does not manage and its own escaping rules to audit, or it would give operators too little to brand a page (no conditionals for signed-in state, no loop over applications). The Quarkus BOM already manages Qute, and Qute runs in native images. Constraining it costs less than adopting and auditing another engine.

=== Add the portal path to the OIDC reserved-path registry

One registry for every gateway-owned path is tidier.

*Rejected in favour of* a second, explicitly ordered seam with its own boot-time collision checks. The OIDC set is closed, derived from the `oidc` block and matched on the OIDC host only, while the portal must work without `oidc` and on every host. Merging them would change the OIDC matching rule or special-case one member.

=== Negotiate HTML on any `Accept` that admits it, including wildcards

This would show more users an HTML page.

*Rejected because* every `fetch()` and REST client sends `+*/*+` by default and would start receiving HTML instead of the problem body its error handling parses, and a script could insert that markup into a page. Only an explicit `text/html` range is a browser navigation asking for a page.

Each rejected option lets something outside the gateway's control decide a security property: a template's choice of expression, an engine's default resolver set, a Java type's accessor list, or a wildcard `Accept` header. The decision keeps each property in code the gateway owns and verifies at boot.

== Consequences

=== Properties of the design

* Escaping does not depend on template authors. A missing resolver and a boot refusal both enforce it, and either layer alone would hold.
* A template reaches nothing but the data model: no beans, no configuration, no class loader. Server-side template injection has no target, and a model value containing template syntax is only text.
* A missing, unparseable or escape-bypassing template surfaces at boot with a file and line. A reference to an unknown key surfaces at render time.
* Rendering is native-image safe without reflection registration.
* The portal is additive. A deployment without a `portal` block reserves nothing, and the OIDC reserved-path set keeps its closed, host-scoped definition.
* API clients are unaffected by error pages: `fetch()`, XHR and REST clients keep the problem document and status, and origin responses always pass through.

=== Accepted costs

* *A restricted Qute.* Operators get no includes, no layouts, no `eval`, no custom extensions and no namespaces. A template repeats its markup.
* *Strict rendering is unforgiving.* A misspelled key fails the render. On an error page the gateway falls back to the plain error response. On the overview page the failure is visible.
* *One more dependency.* `quarkus-qute` enters the application module even though the managed engine is unused. Its build-time processing must keep ignoring the portal template.
* *No hot reload.* A template change needs a restart, consistent with the immutable, boot-validated configuration everywhere else.

=== Risks

* *Operator markup is trusted.* The template can link to any origin and present the page misleadingly. It cannot execute code or unescape a value, and the portal CSP confines what the page loads and where its forms submit. Write access to the configuration directory already amounts to control of the gateway.
* *Engine drift.* A future Qute release could add a default resolver or a section that reintroduces an escape bypass. The engine is built from an explicit resolver and section list, and the boot-time walk refuses the known bypass names independently.
