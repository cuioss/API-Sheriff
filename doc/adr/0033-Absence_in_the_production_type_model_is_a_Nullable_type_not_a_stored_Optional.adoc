== Status

Accepted

== Decision

=== The question

A codebase that models "this value may be absent" has two vocabularies available in modern Java. Using both without a rule produces an internally inconsistent type model.

`java.util.Optional` was designed as a return-type vocabulary. It lets a method say "I may have nothing for you" at the one point where the caller must confront that. JSpecify's `@NullMarked` package plus `@Nullable` is a declaration-site vocabulary. It lets a type say "this reference may be null" in a form the compiler's null analysis and static tooling can check everywhere the reference appears.

Applying `Optional` in storage positions (a field, a declared parameter, a record component) borrows the return-type vocabulary for a job it was not designed for. The costs are structural, not stylistic:

* *It doubles the object graph.* Every absent value allocates a wrapper that exists only to say "nothing is here", on a request path where the gateway handles the value on every route evaluation.
* *It forces normalization ceremony into constructors.* A record whose components are `Optional` needs a compact constructor that rewrites every incoming `null` into `Optional.empty()`, purely to keep the wrapper invariant intact. That ceremony is bookkeeping the type choice created, not domain logic.
* *It is unenforceable without a rule.* Nothing distinguishes a deliberate `Optional` field from one added by habit. The two vocabularies drift into the same package, and a reader cannot tell which contract a given type asserts.
* *It becomes expensive to change once published.* Turning a record component from `Optional<T>` into `@Nullable T` changes both the canonical constructor and the accessor return type, so every call site changes with it. Pre-1.0 that is free. After a published-API cut it is a break.

An opposite failure is also available: banning `Optional` outright. `Optional` earns its keep at a computed boundary, such as a lookup that may find nothing or an accessor that returns a derived value, where the wrapper is created and consumed at the point of use and not held. A rule that removes it everywhere loses that expressiveness for no gain.

The architecture therefore needs a discriminator sharp enough to apply mechanically at every site and to enforce automatically thereafter.

*The decision:* absence is a `@Nullable` type wherever it is stored, and an `Optional` only where it is computed.

=== Storage versus computation

The discriminator is storage versus computation, not nullability versus optionality:

* *Stored: converts.* A field, a declared constructor or method parameter, and a record component all hold a value. These are declared `@Nullable T` under the package's `@NullMarked` default.
* *Computed: stays.* A method return type and a local variable produce a value at the point of use. These may remain `Optional<T>`.

The rule closes its own obvious loophole. A stored `Optional` that exists in order to generate an `Optional`-returning accessor is still storage. The accessor's return shape does not reclassify the field behind it.

=== A `@NullMarked` package default

The production packages declare `@NullMarked` in `package-info.java`, so a bare reference type is non-null by default and `@Nullable` is the explicit, checkable exception. The `config/model` package documentation states the contract in the same place the compiler reads the default from.

=== Removal of the normalization ceremony

With the wrapper gone, a compact constructor that existed solely to rewrite `null` into `Optional.empty()` has nothing left to do and is deleted. A compact constructor survives only where it performs genuine work: a `requireNonNull` on a mandatory component, or a defensive copy of a collection. At the consuming end, an equivalent null-checked expression replaces an `orElse` fallback, so a fail-closed default is preserved exactly.

=== A standing fitness function

`NoStoredOptionalArchTest` forbids `Optional` in the stored positions and runs with every build, so the decision holds against future code and not only against the sweep that established it. The rule carries the three-part shape the surrounding harness already models:

* the positive rule,
* a non-vacuity guard asserting that every protected package resolves to at least one class,
* a matched positive and negative control, so an emptied specimen fails loudly and does not pass silently.

The parameter rule is phrased positively, as `codeUnits().should(notDeclare…)`, not with the negating `noCodeUnits()` form. Under the negating form ArchUnit inverts event polarity, so a condition that emits violation events reports nothing, and the rule passes while checking nothing. A fitness function that cannot fail is worse than none, because it also removes the reviewer's suspicion.

=== Two carve-outs, both recorded in the rule's own rationale

*Framework-imposed `Optional` is exempt.* Where a third-party API's signature dictates the type, the gateway does not fight it. MicroProfile Config uses `Optional<T>` natively to express an absent property, and a Quarkus TLS-registry lookup takes an `Optional` argument directly. Converting either would change deployment behaviour: an absent property would become a boot failure and not an absent value. The type-model rule has no mandate to make that behavioural change. The guard exempts parameters whose type an external API dictates, minimally those carrying the configuration-property annotation.

*Lombok `@Getter`-backed fields are exempt, and this is a known gap.* Lombok annotations are source-retention and absent from bytecode, so a bytecode-level rule cannot see `@Getter` at all. The available proxy is the presence of a matching public accessor on a non-record class. That proxy is imprecise, so the guard does not police that class of field. The guard checks records unconditionally, never exempt, precisely so the accessor proxy cannot swallow them. The negative control sits on a surface the guard actually covers, so the exemption cannot render the control vacuous.

== Alternatives rejected

=== Keep `Optional` in stored positions and standardise on it everywhere

Use one vocabulary, `Optional`, for both storage and computation, and drop `@Nullable` from the model.

*Rejected because* it makes the wrapper a permanent part of the persisted shape. Every absent value allocates, every record needs its normalization ceremony, and the null-analysis tooling that reads `@NullMarked` and `@Nullable` has nothing to work with. It also cannot be honoured at the framework boundary in reverse. Third-party APIs would still hand the codebase plain nullable references, so the "one vocabulary" claim is false in practice.

=== Ban `Optional` outright

Remove `Optional` from the codebase entirely, including method returns.

*Rejected because* it discards the one position where the wrapper is the right tool. A lookup that may find nothing communicates that better by returning an empty `Optional` than by returning a `@Nullable` reference the caller may dereference without thinking. Banning it trades a real expressiveness gain for uniformity that no failure mode demanded.

=== Convert opportunistically, without a census

Fix stored `Optional` occurrences as they are encountered during other work.

*Rejected because* the parameter surface's size is not knowable without enumerating it, and a partial conversion is strictly worse than none. It leaves the two vocabularies mixed inside the same package while consuming the breaking-change budget. It also makes the standing guard unsatisfiable. A rule cannot be switched on over a partly converted surface, and switching it on with suppressions added to make it pass is a guard that enforces nothing.

=== Enforce by convention and code review rather than a fitness function

Document the storage-versus-computation rule and rely on reviewers.

*Rejected because* the rule's whole value is that it holds against code written later. A convention decays at exactly the rate reviewers' attention does, and its violations are invisible in a diff, because a new `Optional` field looks locally reasonable. An automated rule converts a matter of vigilance into a build outcome.

=== Implement the guard as a source-level recipe rather than a bytecode rule

Use an OpenRewrite recipe, which reads source and therefore sees Lombok annotations directly, instead of an ArchUnit rule.

*Considered and held in reserve.* It is the one option that closes the `@Getter` gap, because source-retention annotations are visible to it. It was not chosen first because an ArchUnit harness with a non-vacuity guard and matched controls already exists in the project and runs on every build. The bytecode rule therefore reaches parity for the record and plain-field cases at a fraction of the cost. The source-level recipe remains the sanctioned path if the accessor proxy proves unworkable.

The rejected options fall into one class: each removes either the discriminator or its enforcement. Without the discriminator the two vocabularies mix. Without enforcement the discriminator decays. The decision keeps both.

== Consequences

=== Properties of the design

* One vocabulary per position. A reader can tell from the declaration site which contract a type asserts, without consulting a convention document.
* Absence is visible to the compiler's null analysis and to static tooling everywhere the reference appears, not only where a wrapper is unwrapped.
* Absent stored values allocate no wrapper on the request path.
* Constructors carry only genuine work. Normalization bookkeeping is gone, and several compact constructors disappear entirely.
* The rule is machine-checked, so it holds without reviewer vigilance.

=== Accepted costs

* Every accessor whose component changed also changed shape, so every call site changed with it. The conversion is a breaking change by construction and is only affordable before a published-API cut.
* The `Optional`-returning accessor is no longer free. A caller that genuinely wants wrapper semantics now constructs the wrapper itself.
* The exemption set is a permanent part of the rule's surface. The rule's own rationale must justify each carve-out, or the rule accumulates unexplained holes.

=== Risks

* *The `@Getter` gap is real and deliberately accepted.* A builder-and-getter class can reintroduce a stored `Optional` field, and the guard stays silent. The rule's rationale documents the gap, so it is auditable and not implicit. Closing it requires a source-level tool, because an OpenRewrite recipe sees `@Getter` directly and a bytecode rule does not.
* *A vacuous guard is worse than none.* A rule whose protected packages resolve to zero classes, or whose negative control sits on an exempted surface, passes green while checking nothing. The non-vacuity guard and the matched controls exist for exactly this failure mode.
* *A type-model refactor can silently move behaviour.* Where a null check replaces an `orElse` fallback, the fallback must be preserved exactly. A test whose asserted value changes is evidence that behaviour moved, not evidence that the test needed updating.
* *A static analyser's model of a helper is not the helper's semantics.* Replacing `orElse` with a null-coalescing helper can light up a null-safety rule across every call site, because the analyser may propagate the first argument's nullness to the result. Binding the nullable read to an explicit local before the guard keeps the analyser's view aligned with the code's actual contract. This is preferred over suppressing the rule, because a suppression blinds the enclosing method to precisely the rule this decision relies on.

=== The general rule

When a language offers two vocabularies for the same concept, one designed for a value in flight and one for a value at rest, the durable rule is not "prefer A" or "prefer B" but a discriminator over position. Ask where the value lives. A value that is held wants the declaration-site vocabulary, because its contract must be legible everywhere the reference appears. A value that is produced and immediately consumed wants the expression-level vocabulary, because its contract only has to hold at one point.

A discriminator stated but not enforced is a preference, not a rule. Pair it with an automated check, and write every exemption the check needs into the check's own rationale. An unexplained carve-out is indistinguishable from a bug in the check.
