== Status

Accepted

== Decision

A BFF that acts as an OIDC confidential client has to settle several structural questions at once.
Each admits a tempting per-deployment or per-route answer that fragments the security model.

* *Gateway-owned paths beside proxied traffic.* The BFF serves its own OIDC endpoints on the host
  that also carries proxied routes. If the route table resolves them, a broad prefix route captures
  the callback, and the login fails silently.
* *CSRF as a setting.* A cookie-authenticated session is exposed to cross-site request forgery, and
  a defence for it could be made a setting.
* *Two session modes.* Tokens can be held server-side behind an opaque cookie, or sealed into the
  cookie itself. The modes differ in state and failure modes. They do not differ in what the login,
  the refresh, the CSRF defence or the reserved paths must do.
* *Key material for cookie mode.* Sealing needs a key. Requiring one blocks the simplest
  deployment. Generating one silently breaks a multi-replica deployment.
* *Session identity without a store.* Per-session coordination, such as single-flight refresh, needs
  a stable identity. Cookie mode has no store and must derive it, and a derived identity must be
  both stable across re-seals and unique across sessions.
* *Writes that race a logout.* A refresh and a widening resolve the session, call the identity
  provider (IdP) and write back. A logout in between must not be undone.
* *Lifetime.* A session that ends only at its absolute lifetime stays usable on an unattended
  device.

*Session mode selects only which `SessionBinding` is assembled. Reserved-path resolution, the CSRF
model, the authorization-response transport, the session writes, the two deadlines and the
session-identity contract are fixed, mode-neutral models behind that one seam.*

*The boundary with ADR-0019.* This record owns the BFF's structure: the seam, the reserved-path and
CSRF models, the session writes and lifetime, and the key and identity contract.
link:0019-Reserved_BFF_paths_bypass_the_url-parameter_value_pipeline_and_the_cookie-header_length_relaxation_is_gateway-wide.adoc[ADR-0019]
owns the two inbound-validation relaxations this structure needs.

[[reserved-paths]]
=== (i) Reserved paths resolve before the route table

The gateway carves its own exact paths out of the route table. `ReservedPathRegistry` holds up to
eight: the callback, login initiation, the RP-initiated logout and its return leg, the back-channel
logout receiver, the user-info view, the step-up path and the client JWKS path. The edge consults the
registry before the route table. A matched reserved path ends at its handler, and no prefix route or
route ordering can shadow it. Each path is configured in the `oidc` block, so an operator can move
one out of a namespace. No configuration makes a reserved path proxyable.

Every path is matched exactly. Six are matched on the OIDC host only, the host of
`oidc.redirect_uri`, because a browser reaches them at the origin the gateway published.

[[backchannel-host]]
*The back-channel logout path and the client JWKS path are matched on every host.* No browser
reaches them. The IdP dials them server-to-server, at whatever address the relying party registered.
In a container or internal-network deployment that address is a service name, while the OIDC host
is the public name. The two are expected to differ, and no configuration can make them coincide.
With an OIDC-host gate, a logout token sent to the service name fell through to the route table and
got a `404`. The session it should have destroyed stayed alive, and neither side reported an error.
The widening grants no authorization. The receiver acts only on a logout token whose signature
verifies against the IdP's JWKS and whose `iss` and `aud` match the client. The client JWKS path
joined the set for the same reason
(link:0058-The_BFF_pushes_every_authorization_request_and_binds_its_tokens_with_DPoP_and_authenticates_with_private_key_jwt_unless_a_client_secret_is_configured.adoc[ADR-0058]).

[[csrf]]
=== (ii) The CSRF model is fixed

Every `require: session` route verifies the origin of an unsafe request, and the session cookie
carries `SameSite=Lax`. Both are fixed properties with no switch. The only configuration is the
allowlist of trusted origins an SPA is served from. The operator declares who may call, never
whether the check happens. The proof and the allowlist are in
link:../variants/02-bff-session.adoc#_csrf_defence[Variant 2 -- CSRF Defence].

[[response-mode]]
*The fixed `Lax` policy decides the authorization-response transport.* The gateway binds an
in-flight login to the browser that started it with a short-lived binding cookie. That cookie also
carries `SameSite=Lax`, and a `Lax` cookie is sent on a top-level `GET` navigation but not on a
cross-site `POST`. Under `response_mode=form_post` the IdP returns the code by a cross-site `POST`.
The browser drops the binding cookie, the callback finds no pending login, and every real-browser
login ends in `403`. The cookie side cannot move, so the transport moves.

*The gateway selects `response_mode=query`.* `QueryResponseModeAuthorizationRequestBuilder` replaces
the engine's `form_post` and copies every other parameter unchanged, in order and encoding. It is
wired into every seam that builds an authorization request: the login, the session widening and the
RFC 9470 step-up re-drive. The URL it builds is the parameter source of the pushed authorization
request (ADR-0058), so the mode travels to the IdP inside the push. The mode has no configuration
key, because its other value cannot produce a working login.

*The accepted trade-off.* `query` places the authorization code in the callback URL. The code is
then exposed to the `Referer` header, to intermediary access logs and to browser history. This is the
standard reason `form_post` is preferred, and nothing here removes the exposure. It is accepted
because it is what makes the browser-facing login work. It stays acceptable only while all four of
the following hold:

. *The binding cookie keeps `SameSite=Lax` and every other attribute.*
. *The response mode stays `query`*, on every seam that builds an authorization request, also after
  an engine upgrade.
. *PKCE stays mandatory with the verifier held by the gateway.* The flow refuses an IdP that does not
  advertise `S256`. A code read from a log is not redeemable without the verifier.
. *The pending login stays single-use, and the `state` check stays.* The callback resolves the
  pending record by the binding cookie, consumes it, and compares `state` in constant time. A code
  replayed from another browser is rejected `403` while the code is still live.

The code's lifetime is the IdP's default, which the gateway does not widen. The TTL the gateway owns
is the pending record's, a separate quantity. A `query` callback reads no body, so the callback path
is not in the edge's reserved-body allowlist. An IdP configured to `form_post` to this gateway is not
supported. The mechanics are in
link:../architecture.adoc#_oidc_callback_response_mode[Architecture -- OIDC callback response mode].

[[seam]]
=== (iii) Server and cookie mode sit behind one `SessionBinding` seam

The BFF binds to `SessionBinding`, never to a store. The configured mode selects only which binding
`BffRuntimeProducer` assembles: `ServerSessionBinding` over a session store, or `CookieSessionBinding`
over the sealed-cookie codec. The login flow, the CSRF defence, the refresh and step-up
coordinators, the reserved handlers and the session stage are written against the seam.

Where the modes differ, they differ by declared capability, not by mode name. A binding reports
whether it can honour IdP-driven destruction (`idpDestruction()`). The back-channel logout endpoint
is gated on that signal and answers `404` when it is unsupported. It never claims a destruction that
did not happen.

[[updating-write]]
*One creating write and two updating writes.*

* `bind` creates a session. It is the login's write.
* `persist` updates a session that already exists, and never creates one. It is the refresh's write.
* `persistReissuingCookie` updates the session as `persist` does and also re-issues the value the
  browser holds. It is the write of a step-up or a widening
  (link:0057-Session_routes_obtain_their_declared_scopes_by_refreshing_inside_the_grant_and_widening_the_live_session_outside_it.adoc[ADR-0057]).

Neither updating write extends the absolute lifetime. A binding that can observe that the session was
destroyed since the caller resolved it writes nothing and reports the session gone. In server mode
the store checks for the session and replaces its record in one atomic step, under the lock every
destroy takes. A logout therefore precedes the check, and nothing is written, or it follows the
write and removes the result. Both callers treat a session reported gone as ended. The widening
callback answers its terminal `403` and stores nothing. The refresh coordinator ends the request as
session-ended and revokes, best-effort, the refresh token the exchange returned
(link:0046-Refresh_failures_are_disposed_by_the_engines_failure_kind_and_refresh-token_reuse_detection_is_the_identity_providers_job.adoc[ADR-0046]).

*Cookie mode cannot observe a termination.* `CookieSessionBinding` holds no server-side state. Its
`destroy` removes nothing; a logout clears the browser's cookie. Its updating writes always re-seal
and never report the session gone. This difference has no capability flag: the result of `persist`
carries it. The residual is in the Consequences.

[[cookie-reissue]]
*Server mode re-issues a handle, not an identity.* In server mode the session cookie carries a random
handle that the store maps to the session. The handle is separate from the session identity. A
re-issue mints a new handle and makes the previous one stop resolving in the same atomic step as the
record's replacement. The session's identity, its authentication time, its absolute expiry, its
`sid` and `sub` index entries and the refresh coordinator's single-flight key stay. The session
identity is never the cookie value, in either mode, and it is never emitted. The re-issued cookie
carries the session's remaining absolute lifetime as its `Max-Age`. A request still in flight with
the previous handle resolves no session and gets one "no session" answer without a clearing cookie,
so it cannot remove the cookie the re-issue just set. In cookie mode every update already produces a
new sealed value, so the variant re-seals exactly as `persist` does, and the nonce is not re-minted.
The store side is described in link:../development/bff-session.adoc#session-store[the server-session
contributor guide].

[[key-material]]
=== (iv) Cookie mode has one sealing key, and it is optional

Cookie mode accepts a configured sealing key or, when none is configured, generates one at startup.
Boot does not require a key, so the simplest deployment needs no key management. The trade-off is
explicit: a generated key cannot be shared with another replica and does not survive a restart, so
its sessions end on restart and a peer cannot serve them. The gateway holds exactly one sealing key
and no decrypt-only companion. Replacing the key is a clean break: a cookie sealed under the
withdrawn key carries a key id the gateway does not hold, resolves as "no session", and its user logs
in again. The operator view, including the removed `previous_key`, is in
link:../user/bff-cookie.adoc#_key_material[Operator setup -- cookie-based BFF].

[[session-identity]]
=== (v) The cookie-mode identity is a keyed digest with a per-session nonce

The derived cookie-mode identity is a salted digest over the login instant, `sub` and a random nonce
minted once at login. The nonce is sealed with the session, re-sealed verbatim on every update and
never re-minted. The raw nonce is never used as the identity, and the identity is never emitted to the
browser. Every input is fixed for the session's life, so a re-seal reproduces the identity: it is
stable. The nonce separates two logins by one subject within one clock granule: it is unique.

The sealed-cookie format version is bound into the cookie's authenticated data. Any change to the
sealed field set raises the version, and an older format is not accepted. Admitting one would mean
inventing the missing input, which would change the derived identity. The wire format is in
link:../development/bff-cookie.adoc[the cookie-based contributor guide].

[[idle-deadline]]
=== (vi) A session has an absolute and an idle deadline

A session ends at its absolute lifetime (`oidc.session.ttl_seconds`), and earlier when
`oidc.session.idle_timeout_seconds` pass without a request that was let through on a session route.
This holds in both modes.

* `resolve` enforces both deadlines and extends neither. A caller that only reads a session, such as
  a reserved handler or the portal, does not keep it alive.
* `recordAccess` is the only operation that moves the idle deadline. The session stage calls it once
  for each request it lets through. A rejected, challenged or redirected request is not an access.
* No access moves the absolute lifetime.

A session past either deadline is no session. *Server mode* keeps the last access in the store beside
the record. The store removes an expired session when it is next looked up, and otherwise a periodic
sweep removes it.

*Cookie mode* keeps the last access in a separate *activity cookie*, not in the sealed session. The
activity cookie is authenticated with HMAC-SHA-256 under a key of its own and bound to the derived
session identity, so it is valid for one session only. It is not encrypted, because the time of the
last access is not a secret. The binding writes it at most once per interval, so the idle deadline is
exact to within that interval. The binding keeps no per-session state, so the client decides how often
the cookie is written. A message authentication code has no per-key usage limit that such a client
could spend, which a cipher with a random nonce has. The sealed payload gains no field, so its format
version is unchanged. *The activity cookie fails closed.* A missing, forged, unreadable or foreign
activity cookie never extends a session. Without a usable one the idle deadline counts from the
login. The layout and the interval are in
link:../development/bff-cookie.adoc#activity-cookie[the cookie-based contributor guide].

== Alternatives rejected

*Resolve reserved paths through the ordinary route table.* One mechanism would resolve every path.
Rejected because a security-critical endpoint would then depend on route ordering and prefix breadth.
A legitimate broad prefix silently captures the callback, and the failure depends on configuration.
Precedence must be structural to be trustworthy.

*Make the accepted back-channel host configurable.* A key naming the internal host would keep the
gate. Rejected because its only correct value is whatever the IdP registered. The same fact would
live in two places, and any drift between them reproduces the silent `404`.

*Derive the accepted host from a full `backchannel_logout_url` instead of a path.* Rejected for the
same reason. It also adds a migration: every existing configuration declares a path, and each would
become incomplete while still having to agree with the IdP's registration.

*Keep the OIDC-host gate and require the IdP to reach the gateway by its public name.* The only
alternative that changes no code. Rejected because a provider on a private network often cannot
resolve the public name. Making it resolve means DNS or hairpin routing between two containers that
stand side by side.

*Make CSRF defence configurable, with a secure default.* Rejected because the option's existence is
the vulnerability. A defence that can be switched off will be switched off where the exposure is
least understood, and a secure default does not resist a deliberate override.

*Relax the binding cookie to `SameSite=None` and keep `form_post`.* It keeps the code out of the URL.
Rejected because it weakens the cross-site binding the cookie exists to provide. A binding cookie
sent cross-site no longer tells the browser that started the login from one that did not, which is
the check the callback's `403` performs. It would also contradict decision (ii). The code's exposure
is bounded on four axes; the binding has nothing behind it.

*Stay on `form_post` without the binding cookie on the callback.* Rejected because it is not a working
design: with the cookie absent the callback resolves no pending login. Making it work means dropping
the binding requirement, which is the previous alternative under another name.

*Expose the response mode as a key that defaults to `query`.* Rejected because the other value cannot
produce a working login while the binding cookie stays `Lax`. A setting whose alternative is always
wrong is a trap.

*Bind the login through `state` alone and drop the binding cookie.* Either transport would then work.
Rejected because `state` travels with the callback: any browser that presents the code also presents
it. It correlates a response to a request but cannot attest which browser received it. This removes
the replay-from-another-browser rejection, a larger loss than the URL exposure.

*Implement the two session modes as independent stacks.* Each could be tuned to its own shape.
Rejected because it doubles the surface where a security defect can occur. A fix to one stack does
not reach the other, and the two drift apart in what operators read as one feature.

*Resolve the session again just before the updating write.* It needs no store change. Rejected
because a second check followed by an unconditional write is the same check-then-act with a shorter
window. A destruction between the second resolve and the write is still undone.

*Make a logout wait for in-flight writers.* Serialising a logout with a refresh or a widening would
close the window from the other side. Rejected because a logout would then wait on an IdP round
trip. A back-channel logout also destroys by `sid` or `sub` without knowing which sessions have a
writer in flight. The store already serialises its own operations.

*Keep one upserting write and add a tombstone per destroyed session.* Rejected because it adds
per-session state that outlives the session and needs its own bound and expiry, to rebuild a fact the
store has at the moment of the write: whether the record is there.

*Give cookie mode a server-side list of logged-out sessions.* It would let `CookieSessionBinding`
report a termination. Rejected because it is server-side session state in the variant that exists to
have none, and it would have to be shared between instances to mean anything.

*Mint a new session identity at every step-up and widening.* It needs no handle beside the record.
Rejected because the identity is the key the rest of the runtime holds. The `sid` and `sub` indexes
would have to move in step, a refresh coalesced on the old identity would no longer exclude one on
the new identity, and the authentication time and absolute expiry would have to be carried across by
hand.

*Re-mint the cookie-mode nonce on a step-up or a widening.* Rejected because the identity is derived
from the nonce. A new nonce is a different session to everything keyed on the identity, and it
withdraws nothing: the earlier sealed cookie still unseals under the same key.

*Require a sealing key unconditionally in cookie mode.* Rejected because it imposes key management on
every deployment, single-node and development ones included. That pushes operators toward checked-in
or trivially derived keys, a worse outcome than a documented, deliberately scoped generated key.

*Derive the cookie-mode identity from the fixed material alone, without a nonce.* It needs no extra
sealed field. Rejected because stability and uniqueness are independent requirements and this meets
only the first. Two sessions of one subject within one login granule derive the same identity, which
cross-wires the coordination the identity keys. The defect is silent and appears only under
concurrency.

*Accept the previous sealed-cookie format beside the new one.* It would avoid a forced re-login on
upgrade. Rejected because an older cookie lacks an identity input, and any value supplied for it
changes the derived identity. That reintroduces the collision the nonce removes.

*Carry the last access as a field of the sealed session.* One cookie instead of two. Rejected for two
reasons. The field changes the sealed payload, which raises the format version and ends every
cookie-mode session at the upgrade. And every access becomes a re-seal of the whole session: a
full-size `Set-Cookie` carrying the tokens, each one racing the refresh's own write.

*No idle timeout in cookie mode.* It keeps the cookie-based BFF at one cookie. Rejected because the
two modes would then differ in a property operators read as one feature, the drift decision (iii)
prevents. The capability is achievable without server-side state.

The rejected options share one shape. Each buys a local convenience, such as a setting, less
abstraction or an easier upgrade, by removing a structural guarantee. Each pays with a failure that is
silent and shows only in the deployments least equipped to diagnose it.

== Consequences

*Positive.*

* Configuration cannot shadow a security-critical path: reserved-path precedence is structural.
* No deployment of this gateway runs without CSRF defence, because none can be expressed.
* A BFF capability is written once, against the seam, and both modes get it.
* A mode-specific limit surfaces as a capability signal with a defined answer, never as a silently
  missing behaviour.
* In server mode a logout or a back-channel logout is not undone by a refresh or a widening in flight.
* A step-up or a widening changes the server-mode cookie value and nothing else about the session.
* A session nobody uses ends at its idle deadline in both modes. A reader of a session does not keep
  it alive.
* Cookie mode works without key management. The multi-replica case works with a configured
  key.
* Single-flight refresh keys correctly in both modes, also for concurrent logins by one subject.

*Negative.*

* Six reserved paths occupy their configured paths on the OIDC host, and the back-channel logout and
  client JWKS paths on every host. An operator who needs such a namespace proxied relocates the
  reserved path.
* A truly cross-site SPA cannot be served, because the fixed cookie policy does not attach the session
  cookie cross-site. Such an SPA must be hosted under the gateway's site.
* The authorization code travels in the callback URL. The exposure is bounded by the four obligations
  of decision (ii) and never removed.
* Any change to the sealed field set raises the format version and ends every cookie-mode session on
  deploy. There is no rolling migration.
* The session record carries a component that only one mode uses. Every code path that rebuilds the
  record field by field must copy it.
* A server-mode request in flight with the previous handle during a re-issue gets one "no session"
  answer. Its next attempt succeeds.
* *Cookie mode cannot observe a termination.* A refresh or a widening in flight during a logout still
  produces a sealed `Set-Cookie`. If it reaches the browser after the logout, the browser again holds
  a session until its absolute lifetime. The mitigations are a short `ttl_seconds`, short access-token
  lifetimes, and the server-session variant where immediate termination is required
  (link:../security-threat-model.adoc#bff-09[BFF-09]).
* *Cookie mode cannot withdraw an earlier value.* A sealed cookie from before a step-up or a widening
  stays usable at its earlier privilege until the absolute expiry. It never gains the later scopes
  (link:../security-threat-model.adoc#bff-21[BFF-21]).
* In cookie mode a browser or intermediary that drops the activity cookie ends the session one idle
  period after login.

*Constraints on later change.* Each of the following reintroduces a defect this record removes:

* rebuilding the session record without the nonce, which changes the derived identity mid-session.
  The re-seal path fails loud instead of re-minting;
* reverting to `form_post`, adding an authorization-request seam that bypasses the query builder, or
  relaxing the binding cookie's `SameSite`;
* splitting an updating write into a check and a write across two store calls;
* using the session identity as a cookie value or a lookup key for a request;
* letting any caller other than the session stage call `recordAccess`.

*Accepted risks.*

* *An operator misreads the key default.* Omitting the key works on one replica, so a deployment can
  scale out before it finds its sessions are not portable. The trade-off is documented where the key
  is configured.
* *The cookie size ceiling.* The session size follows the token size. The gateway refuses to seal an
  over-budget session rather than emit a cookie the browser would drop.
* *Tools that record URLs record the code.* Browser-automation traces capture the code-bearing
  callback URL. The code is single-use, consumed by then, PKCE-bound and issued by a test realm, but
  the shape applies to any URL-carried secret.
* *Green tests over a broken login.* A test that builds the callback itself passes on either
  transport. Only a real-browser end-to-end path detects a return of the `form_post` defect.
