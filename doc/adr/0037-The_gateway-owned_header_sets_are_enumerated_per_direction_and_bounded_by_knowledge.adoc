= ADR-0037: The gateway-owned header sets are enumerated per direction and bounded by knowledge
:toc: left
:toclevels: 2
:sectnums:

// adr-metadata
// summary: The gateway owns three header sets — a request-direction never-forward set, a response-direction strip, and a gateway-understood protocol set that crosses without an operator entry — each enumerated in full per direction rather than derived from a sibling; membership answers "does the gateway know what this header means?" rather than "is it technically necessary", and the value- or mode-dependent behaviours (TE: trailers, the single re-admittable Authorization) live in the application rather than in a set literal. The browser Cookie is not a set member: a per-route cookies block (allow none | all | list, same_origin_check, additional_origins; four scopes, whole-block replacement, default none) decides which cookies reach the upstream and which upstream Set-Cookie lines reach the client, the gateway's own cookies never cross under any block (one GatewayCookies definition), and a cookie-forwarding route refuses a cross-site unsafe request that carries a forwarded cookie.
// tags: header-policy, forward-policy, connection-headers, zero-trust, rfc9110, rfc9113, conditional-requests, protocol-set, cookie-policy, csrf
// affects: api-sheriff

== Status

Accepted

== Context

Once a route can resolve a forward-all posture
(link:0036-Forward_filtering_is_a_three-mode_policy_inside_an_authorised_route.adoc[ADR-0036]),
the header names the gateway must never relay stop being a convenience and
become the thing that makes the permissive baseline defensible. Under an
allow-list-only model an omission from those sets was masked: the operator's
enumeration was the filter, and a name the gateway forgot to withhold simply
never appeared on anyone's allow-list. Under forward-all an omission crosses.

Three separate questions were being answered by scattered, partly-duplicated
logic.

**What must never be relayed, and in which direction?** The response direction
already had a set — the connection-specific and framing names an upstream may
propose but the gateway must not place on the client's connection. Issue #172
was exactly a failure of *scope* rather than of content: the proxy data plane
stripped `Connection` and the asset terminal action did not, so an origin's
routine `Connection: keep-alive` reached an HTTP/2 client, which is malformed
per RFC 9113 §8.2.2 and made a served asset arrive as nothing at all. Two
mirrored lists had let one drift. The request direction had no enumerated set
at all — it did not need one while the operator's allow-list was the filter.

**What should cross without anyone naming it?** With forward-all available the
enumeration burden is gone for permissive routes, but it remains for exactly the
routes that most want a positive-list: a route that names three application
headers still had to add `Accept`, `Content-Type` and `Range` before its backend
behaved normally. Those are HTTP mechanics, not application policy.

**What does the `not_modified` toggle actually govern?** Conditional requests
have two halves — the validators the client sends, and the `ETag` /
`Last-Modified` the upstream answers with. The request half enumerated two
validators; the response half stripped two headers. Whether those halves were
one decision or two had never been recorded, and the request half's membership
was demonstrably incomplete against RFC 9110 §13.

A fourth question sat inside the first and was answered too bluntly. **What
happens to the browser's `Cookie`?** It used to be an absolute member of the
request-direction set, withheld from every upstream on every route. That kept
the BFF's own session cookie away from backends, which is the property that
matters, but it also made the gateway unable to front an upstream that keeps its
own session in a cookie — a legacy application, an admin console, a framework
whose CSRF token travels as a cookie. Fronting such an upstream is a case the
gateway supports, so a strip that breaks every one of them is a gap, not a
safety margin. The response direction had the mirror-image gap: an upstream's
`Set-Cookie` was relayed with no policy at all, so one upstream could set a
cookie, with a `Domain` of its choosing, that the browser then sent to every
other upstream behind the same host.

A membership rule was needed that could be applied to a name mechanically, and
that would not quietly expand — and a cookie rule was needed that separates the
gateway's own cookies, which must never cross, from the application's, which an
operator may let through.

== Decision

**Three sets, each enumerated in full for the direction it serves, and none
derived from another. The browser `Cookie` is not a member of any of them: it is
governed per route by the `cookies` policy block, in both directions.**

=== The response-direction strip

The connection-specific and framing names the gateway never places on the
client's connection: the RFC 9113 §8.2.2 connection-specific names, the
remaining RFC 7230 §6.1 hop-by-hop names, and `Content-Length` — which is
framing rather than hop-by-hop and is stripped for a different reason, that it
is a claim about the *source's* body which neither relay writes verbatim in
every case.

It is declared **once** and read by **every path that answers a client** — the
proxy data plane's streamed relay and the asset terminal action's buffered
envelope. Those paths apply it differently, because one streams a body it does
not hold and the other lets the framework size a buffer it does. That difference
is in the application; the *set* is one rule about one protocol, so it has one
home.

=== The request-direction never-forward set

The names a client may send that the gateway never relays upstream, whatever
mode the route resolved. The members are listed once, in
xref:../configuration.adoc#_never_forward_set[the never-forward section of the
configuration reference]; this record states the rule that admits a name, not
the list. Membership answers one of five questions:

* **Credentials the gateway terminates or mediates** — the inbound
  `Authorization`, which the gateway validates and replaces with the mediated
  bearer. The browser `Cookie` is deliberately *not* here: it is not one
  credential but a jar holding the gateway's cookies and the application's side
  by side, and a set member can only withhold the jar whole. The gateway's own
  cookies are withheld by name instead, under every policy (see
  <<_the_browser_cookie_is_a_per_route_policy>>).
* **Hop-by-hop and connection-specific names** describing the hop the gateway
  terminates rather than the message it forwards.
* **Framing the gateway re-establishes** — the body length.
* **Names the gateway itself owns or regenerates** — the authority, the request's
  origin and referrer, and the date.
* **Spoofable provenance claims only the gateway is entitled to make** — the
  underscore spellings of the forwarding names and the vendor client-IP aliases.

**The forwarding-name equivalence class is split across two sets, by which
question each name answers.** The *canonical* forwarding names stay in the
regeneration skip, because that set enumerates what the gateway **emits** and is
read twice — as the client-copy skip and as the mask that hides inbound
forwarding headers from the resolver when the immediate peer is untrusted. The
gateway does not regenerate `X_Forwarded_For` or `X-Real-IP`, and the resolver
never queries either, so filing them there would assert a regeneration
relationship that does not exist and widen a mask with names nothing asks for.
What *is* true of them is this set's question: they are provenance claims the
gateway alone may make, so a client-sent copy is never relayed. `Forwarded`
contributes no variant: it carries no hyphen to fold, so adding it here would
duplicate the canonical name the regeneration skip already holds.

The threat is not that such a name corrupts the *regenerated* header — it cannot
— but that a backend reads it **as though** it were the canonical one: a
framework folding `-` and `_` into a single CGI-style variable resolves
`X_Forwarded_For` to the same `HTTP_X_FORWARDED_FOR` the real header produces.
Under the allow-list-only model these were dropped incidentally, because
everything unlisted was. Under forward-all the protection has to be *stated*, in
the gateway's own set rather than as a per-route `headers_deny` remedy, because
an equivalence class handled route-by-route stays incomplete. `set_headers` is
unaffected — the strip governs client input, and an operator fronting a backend
that reads `X-Real-IP` still sets it deliberately.

**The class is closed by folding, not by listing its members.** Both sets test
membership on the *separator-folded* name — lower-cased with every `_` mapped to
`-` — so each closes its own names across the whole `-`/`_` class. The literals
are not the closure and must not be read as one: a two-separator name has **four**
spellings (`X-Forwarded-For`, `X_Forwarded_For`, `X-Forwarded_For`,
`X_Forwarded-For`) that a CGI-folding backend resolves to one variable, so
enumerating them would mean four entries per name and a fix the first time one was
missed — which is the Traefik fix-chain itself, where each CVE closed one spelling
while a sibling survived. Folding also makes the closure *inherited*: a name added
to either set later is covered across every spelling without a second edit.

**The two sets are independent enumerations, not one derived from the other.**
That the request set currently contains every response-set name is an
*observation*, not an invariant. Each set is pinned exhaustively by its own test,
so a one-directional addition fails that set's assertion instead of propagating.

**Two behaviours ride on top of membership and deliberately do not live in the
set literal**, because both are value- or mode-dependent:

1. **`authorization` is the single re-admittable member**, honoured only when a
   route declares a positive-list naming it. Under a negative-list or forward-all
   there is no positive-list, so a permissive baseline can never leak an inbound
   credential. A re-admitted value is still overwritten by the mediated bearer,
   which is merged last.
2. **`te` crosses only when its value is exactly the `trailers` token.** RFC 9110
   admits that one value end-to-end; any other negotiates a transfer coding for
   the hop the gateway terminates.

**The `forward` block never decides about `Cookie`.** The mode copy skips the
name on every posture, and a `forward.headers_allow`, `forward.headers_deny` or
`forward.set_headers` entry naming `Cookie` is refused at boot: the `cookies`
block is the one place that decides which cookies cross, and a second place
would let two blocks disagree about the same header. `authorization` stays
re-admittable through a positive-list because it is one credential with one
owner; `Cookie` is governed by its own block because it is many.

[[_the_browser_cookie_is_a_per_route_policy]]
=== The browser `Cookie` is a per-route policy

**The gateway's own cookies never cross, under any policy and in either
direction.** One framework-free definition, `GatewayCookies`, holds them: every
cookie under the reserved `__Host-sheriff-` prefix — always, on a gateway with or
without a BFF, so a gateway cookie added later is covered by construction — plus
the configured `oidc.session.cookie_name` and its `-activity` sibling, in both
session modes. The boot rules, the request rebuild and the response predicate all
read that one definition, so the three cannot disagree about what the gateway
owns. How a name is matched is in
xref:../configuration.adoc#_never_forward_set[the never-forward section]. This is
the property the absolute strip existed for, kept on its own terms: the BFF's
sealed session cookie is the gateway's, never the backend's. A single definition
is what closes that class — a session cookie forwarded to the proxied
API (GHSA-vvg7-p7jw-8qr3) is the failure a second, hand-maintained list of
"cookies to drop" eventually produces, when one side learns a new cookie name and
the other does not.

**Which application cookies cross is the route's `cookies` block.** It names the
mode in `allow` — `none`, `all`, or a list of cookie names — and decides both
directions from that one declaration. It resolves like every policy block
(link:0067-Every_policy_block_is_one_declaration_resolved_nearest_declared_scope_wins_with_whole-block_replacement.adoc[ADR-0067]):
the nearest declared block wins and is taken whole. **The default is `none`**, the
nothing-crosses posture. An asset or a redirect route always resolves `none`: it
has no upstream to hand a cookie to or relay one from. The fields, the operator
examples, the request rebuild and the response predicate are specified in
xref:../configuration.adoc#_cookies[the `cookies` reference] and
xref:../user/endpoint-routes.adoc#_cookie_dependent_upstream[Fronting a
cookie-dependent upstream]. This record states what they decide:

* **Request.** The upstream receives a `Cookie` rebuilt from the admitted pairs on
  every dispatch path. The gateway's cookies are dropped first, always.
* **Response.** An upstream `Set-Cookie` line is relayed only when the route admits
  the cookie it names and the name is not one of the gateway's own. Its `Domain`
  attribute is removed, so an upstream can neither set a gateway cookie nor widen a
  cookie past the host the browser addressed. `Path` is relayed as sent: a cookie
  one upstream sets still reaches every route its path covers, and that route's
  upstream receives it only when its own policy admits the name — the accepted
  residual link:../security-threat-model.adoc#gw-15[GW-15 of the threat model]
  records.
* **The default relays nothing.** Under `none` no upstream `Set-Cookie` is relayed
  at all. That is a breaking change for every upstream that sets cookies today: its
  route has to declare the cookies it relies on.

**A cookie-forwarding route is guarded against cross-site requests by the
gateway.** Once a browser cookie can reach an upstream, a cross-site page can make
the browser send it there — the ambient-credential shape CSRF rests on. Every
non-WebSocket route whose block forwards a cookie therefore carries a same-origin
check. It trusts the origin the request was received on plus exactly the block's
`additional_origins`, and refuses `403` an unsafe request whose origin it cannot
prove, before authentication and before the upstream
(xref:../configuration.adoc#_cookies_same_origin_check[the same-origin check]).

**The check applies only to an unsafe request that carries at least one cookie
the route would forward.** It reads the request through the same reading the
rebuild uses, so the check and the rebuild cannot disagree about what
"forwarded" means. The reason is the threat itself: a request carrying no
forwardable cookie hands the upstream no ambient browser credential, so there is
nothing for a cross-site page to forge. A non-browser client — a gRPC service, a
server-to-server caller — that sends no `Origin` keeps working without one.
`same_origin_check: false` removes the check and logs a WARN (`ApiSheriff-139`):
defending that upstream against CSRF is then the upstream's own job, a choice the
operator makes visibly.

**A WebSocket route is settled differently.** Its upgrade is already gated by the
exact-match `websocket.allowed_origins` allowlist, which is stricter than the
same-origin check — an absent `Origin` is always refused. A second origin list on
the same upgrade would only add a way for the two to disagree. A cookie-forwarding
WebSocket route must instead declare a non-empty `websocket.allowed_origins`, and
boot is refused otherwise.

**A gateway-scope `allow: all` is refused at boot**, because a gateway-wide "every
cookie to every upstream" is the exposure the policy exists to scope. The other
boot refusals and the two WARNs are listed in
xref:../configuration.adoc#_cookies_boot_rules[the `cookies` boot rules].

=== The gateway-understood protocol set

The names that cross **without an operator entry**, in two tiers:

* **Unconditional** — `Accept`, `Accept-Encoding`, `Accept-Language`,
  `Content-Type`, `Range`: content negotiation and range requests.
* **Conditional** — the five RFC 9110 §13 validators `If-None-Match`,
  `If-Modified-Since`, `If-Match`, `If-Unmodified-Since`, `If-Range`, gated by
  the route's `not_modified` toggle.

**The membership rule is knowledge, not necessity.** A name is in the set when
the gateway knows what it means and can reason about the consequences of
relaying it; the "technically necessary" rule is rejected below. `User-Agent` is
deliberately out on the same test: widely expected, required for nothing, and a
backend that genuinely needs it can name it. The set is a fixed constant with no
configuration surface; an operator who wants one of these withheld denies it by
name.

**A `headers_deny` entry naming a protocol header wins.** The set is applied only
to names the mode copy did not already refuse. A *positive*-list is deliberately
not consulted — crossing without being named is the set's entire purpose — so the
only way to withhold one is to say so.

**The set is disjoint from the request-direction never-forward set**, and that
disjointness is load-bearing. The protocol set reads the raw client request after
the strip, so it bypasses the strip; that is safe only while the two sets share no
name. A test asserts the disjointness directly (see the first risk below).

=== The `not_modified` decision

**The toggle is kept, and its request-direction membership is widened from two
validators to five. The response direction is unchanged.**

Keeping it is the substantive half. The two halves are one decision: forwarding a
validator whose response counterpart is then stripped makes the gateway ask a
question it discards the answer to. Gating both halves on one flag stops that, and
a test that names both stages asserts the coupling.

Widening to five closes an incompleteness: RFC 9110 §13 defines five validators, a
route honouring conditional requests needs all of them, and two were a subset.

**One boundary is recorded rather than resolved.** The toggle gates the protocol
set's *admission path*; it is not a withholding rule applied to the mode copy. A
forward-all or negative-list route therefore forwards a validator with the flag
off, while the response half still strips the `ETag` that would answer it — the
asymmetry this toggle exists to prevent. It is pinned as characterization and
left open; the closing change is deferred below.

== Consequences

=== Positive

* The forward-all baseline is safe by construction: the names that must not
  cross are withheld structurally, not by operator diligence.
* An operator states application policy and the gateway supplies HTTP mechanics,
  so a positive-list route names three headers instead of eleven.
* One home per direction means a name cannot be present in one relay path and
  absent from another — the #172 failure mode is structurally excluded.
* A route honouring conditional requests now forwards all five validators, so
  `If-Range` and `If-Unmodified-Since` work where they previously did not.
* The membership rule is stateable in one sentence, so a future addition can be
  argued against it rather than judged ad hoc.
* The gateway can front an upstream that keeps its own session in a cookie, while
  its own cookies stay out of every upstream by one definition rather than by the
  strip.
* An upstream can no longer plant a cookie the gateway owns, or one scoped to a
  wider `Domain` than the host the browser addressed, and a cross-site page can no
  longer ride a forwarded cookie into a state-changing upstream request.

=== Negative

* Three sets are three surfaces to maintain, and the independence rule means a
  name relevant to both directions is written twice, deliberately.
* The protocol set is a fixed constant. An operator whose backend needs a name
  outside it must add a positive-list entry, and the gateway offers no way to
  extend the set itself.
* The knowledge rule requires a judgement per name. It is sharper than
  "necessary", but it is not mechanical, and `User-Agent` sits close enough to
  the line that its exclusion needs the rationale recorded.
* The default `none` relays no upstream `Set-Cookie`, so every upstream that sets
  a cookie today stops receiving it back until its route declares a `cookies`
  block — a breaking change made deliberately, because the alternative default
  relays cookies no one decided to relay.
* A cookie-forwarding route that serves a browser from a second origin needs that
  origin in `additional_origins`; the check names no wildcard and trusts nothing
  it was not told.

=== Risks

* **An addition to either enumerated set can break the disjointness the protocol
  set relies on.** The protocol set bypasses the strip; a name added to both
  lists would be withheld and then re-admitted. The disjointness test is the
  guard, and it must be understood as an invariant rather than a tidiness check.
* **The two-independent-lists rule looks like duplication and invites a
  refactor.** A future reader may "simplify" by deriving one set from the other,
  which silently couples the directions and makes a one-directional addition
  propagate. The rationale is recorded on the sets themselves for that reason.
* **The forward-all conditional asymmetry is a known open edge.** It is
  characterized by a test rather than fixed, so it will not surprise a reader of
  the suite — but it remains a route shape that forwards a precondition whose
  answer is discarded.
* **A permissive baseline makes every future omission from the request set a
  live defect** rather than a latent one. Adding a client-sendable,
  gateway-owned header to the protocol landscape now requires updating that set
  in the same change.
* **`allow: all` exposes every application cookie on the host to that route's
  upstream**, including cookies another upstream set. It is refused at the gateway
  scope for that reason and should stay rare below it; a list names exactly what
  one upstream needs.
* **A gateway cookie set outside `GatewayCookies` would cross.** The reserved
  prefix covers every cookie named under it, so the risk is confined to a cookie
  the gateway sets under a name of an operator's choosing — the session cookie
  and its activity sibling, which the definition reads from the same
  configuration key the session runtime does.

== Alternatives Considered

=== Derive the request set from the response set plus a delta

Define one core list and express the request direction as "the core plus these
extra names".

*Rejected because* it asserts a relationship the two directions do not have. The
sets answer different questions — one is about a connection the gateway is
terminating toward a client, the other about credentials and provenance the
gateway owns toward an upstream — and their present overlap is a coincidence of
the current membership rather than a rule. A derivation would make every future
addition to the response direction silently change request behaviour.

=== Make the protocol set configurable

Let an operator extend or replace the gateway-understood set per route or
globally.

*Rejected because* it reintroduces the enumeration it exists to remove, and adds
a way to get it wrong. The set's value is that it is the same everywhere and
needs no thought; a configurable version is just an allow-list with a default,
and the route-level `headers_allow` already covers the case where an operator
needs a name the gateway does not know.

=== Use "technically necessary for the backend" as the membership rule

Admit any header a backend commonly requires.

*Rejected because* the rule admits `Authorization` and the whole `Cookie` jar —
the inbound credential the gateway replaces, and a header carrying the cookies
whose withholding the BFF pattern depends on. A rule that contradicts the
gateway's own credential boundary at its most important names is not a rule.

=== Drop the `not_modified` toggle and always forward validators

Remove the flag, forward all five validators unconditionally, and always relay
`ETag` / `Last-Modified`.

*Rejected because* it removes the operator's ability to keep a route out of
conditional-request handling entirely, and the flag has a legitimate use: a route
whose upstream computes validators expensively, or whose responses must not be
cached by intermediaries, wants the whole exchange off. Removing the toggle also
removes the coupling that keeps the two halves consistent, so a later change to
one direction would have nothing to hold it to the other.

=== Widen the conditional tier but gate it on the mode copy as well

Extend the toggle so it also withholds validators a forward-all route would copy,
closing the asymmetry recorded above.

*Deferred, not rejected.* It is the change that would make the criterion "no
conditional validator crosses in either direction on a disabled route" true in
every mode. It is out of scope here because it changes what forward-all means:
forward-all currently says "the client's headers cross", and this would carve an
exception into that promise based on an unrelated flag. That is a decision about
mode semantics and belongs with ADR-0036's model, argued on its own terms.

=== Forward every cookie by default

Relay the browser `Cookie` and the upstream `Set-Cookie` untouched unless an
operator removes them — the default of Kong, Traefik, NGINX and Apache APISIX.

*Rejected because* the gateway terminates a browser session of its own. A
forward-everything default hands that session cookie to every upstream until
someone remembers to remove it, and lets any upstream set a cookie every other
upstream then receives. A gateway whose premise is that the backend never sees
the session cannot ship that default.

=== An all-or-nothing opt-in per endpoint

Let an endpoint switch cookie forwarding on or off as one flag — the shape of
KrakenD's `input_headers`, where naming `Cookie` forwards the whole header.

*Rejected because* the useful decision is per cookie, not per header. An
all-or-nothing switch forwards the gateway's own cookies alongside the
application's the moment it is on, and offers no way to give one upstream its
`SESSIONID` without the rest of the jar.

=== Keep the absolute strip

Withhold `Cookie` from every upstream and relay no upstream `Set-Cookie` — the
posture of Duende BFF and of a Spring Cloud Gateway route with
`RemoveRequestHeader=Cookie`.

*Rejected because* fronting a cookie-dependent upstream is a supported case, and
the strip makes every such upstream fail with no configuration that repairs it.
The strip's one real benefit — the gateway's session never reaches a backend — is
kept by `GatewayCookies` under every policy, so dropping the strip costs that
property nothing.

=== A comma-separated cookie list

Spell `allow` as one string, `allow: "SESSIONID,theme"`.

*Rejected because* it puts a second parser in front of a value YAML already
types. A comma is not a cookie-name character, so the format is unambiguous in
principle, but `all`, `none` and a one-name list become indistinguishable by type,
and a stray space or an empty segment becomes a boot error to explain instead of a
schema error the editor shows. The YAML scalar-or-list makes the three modes three
shapes.

=== A gateway-scope `allow: all`

Let one gateway-wide block forward every application cookie to every upstream.

*Rejected because* it is the forward-everything default re-entered through
configuration: every upstream, including ones added later, would receive cookies
the others set. `all` is accepted at the anchor, endpoint and route scopes, where
it names the upstreams it reaches; at the gateway scope it is refused at boot.

=== Forward `Origin` and leave CSRF to each upstream

Relay the browser's `Origin` and let every cookie-dependent upstream defend
itself.

*Rejected because* `Origin` is a member of the never-forward set — a name the
gateway owns — and re-admitting it for this purpose would carve the first
exception into that set for a job the gateway can do itself. It would also make
CSRF protection something each upstream has to get right individually, behind a
gateway that already knows the origin the request was received on. The check
runs once, at the edge; an upstream that wants to keep the job sets
`same_origin_check: false`, visibly.

=== Refuse every `Origin`-less unsafe request on a cookie-forwarding route

Apply the same-origin check to every unsafe request on such a route, whether or
not it carries a forwardable cookie.

*Rejected as the stricter variant.* It refuses the non-browser clients — gRPC
services, server-to-server callers — that send no `Origin` and no cookie, and so
carry no ambient credential to forge. The threat the check answers needs a
forwarded cookie to exist; a request without one is outside it, and the check
that applies only to cookie-carrying requests closes the threat without breaking
those clients.
