// adr-metadata
// summary: The gateway owns four header sets — a request-direction never-forward set, a response-direction strip, a response-direction identity set (UpstreamIdentityHeaders: Server, X-Powered-By, removed rather than rewritten on the HTTP relay, the gRPC relay and the upstream asset envelope unless the route sets keep_identity_headers: true), and a gateway-understood protocol set that crosses without an operator entry — each enumerated in full per direction rather than derived from a sibling; membership answers "does the gateway know what this header means?" rather than "is it technically necessary", and the value- or mode-dependent behaviours (TE: trailers, the single re-admittable Authorization) live in the application rather than in a set literal. With not_modified off the two 304 validators (If-None-Match, If-Modified-Since) are withheld from GET and HEAD under every forward mode (on every other method they cross: If-None-Match is a 412 write precondition, If-Modified-Since is ignored), so the toggle governs both halves of the exchange everywhere, while If-Match, If-Unmodified-Since and If-Range cross unchanged because withholding them would change the request rather than discard an answer. The browser Cookie is not a set member: a per-route cookies block (allow none | all | list, same_origin_check, additional_origins; four policy scopes, whole-block replacement, default none) decides which cookies reach the upstream and which upstream Set-Cookie lines reach the client, the gateway's own cookies never cross under any block (one GatewayCookies definition), and a cookie-forwarding route rejects a cross-site unsafe request that carries a forwarded cookie, answered as the unrouted 404 by default per ADR-0073.

== Status

Accepted

== Decision

=== The question

Once a route can resolve forward-all
(link:0036-Forward_filtering_is_a_three-mode_policy_inside_an_authorised_route.adoc[ADR-0036]), the names
the gateway never relays are what makes that default defensible. Under an allow-list-only model the
operator's enumeration masked an omission. Under forward-all an omitted name crosses. This record settles
four questions:

* What must never be relayed, and in which direction?
* What crosses without an operator naming it?
* What does the `not_modified` toggle govern?
* What happens to the browser's `Cookie`?

It also fixes a membership rule that applies to a name mechanically and does not quietly expand.

*The decision:* four sets, each enumerated in full for the direction it serves, and none derived from
another. `ConnectionHeaders`, `UpstreamIdentityHeaders` and `ForwardPolicyStage` hold them. The browser
`Cookie` belongs to none of them. The `cookies` policy block governs it per route, in both directions.

=== The response-direction strip

This set holds the connection-specific and framing names the gateway never places on the client's
connection:

* the RFC 9113 §8.2.2 connection-specific names;
* the remaining RFC 7230 §6.1 hop-by-hop names;
* `Content-Length`, which is framing rather than hop-by-hop. It goes because it claims something about the
  source's body, and neither relay writes that body verbatim in every case.

The gateway declares the set once, and every path that answers a client reads it: the proxy data plane's
streamed relay and the asset terminal action's buffered envelope. The two paths apply it differently,
because one streams a body it does not hold and the other lets the framework size a buffer. That difference
stays in the application. The set is one rule about one protocol, so it has one home.

One home is the lesson of an earlier failure. Two mirrored lists drifted: the proxy stripped `Connection` and
the asset terminal action did not. An origin's routine `Connection: keep-alive` then reached an HTTP/2 client.
That is malformed per RFC 9113 §8.2.2, and the asset arrived as nothing at all.

=== The response-direction identity set

`UpstreamIdentityHeaders` holds the upstream response headers that name the server software behind the
gateway: `Server` and `X-Powered-By`. It stays apart from the strip. The strip holds names that are wrong on
the client's connection. An identity header is well-formed and goes because it discloses the upstream's
fingerprint.

The gateway removes a member and never rewrites it to a neutral value. Removal is the default on every path
that relays upstream response headers: the HTTP relay, the gRPC relay and the upstream-backed asset envelope.
A route that sets `keep_identity_headers: true` keeps the members on all three. The boot refuses the key on a
route that relays no upstream response header.

=== The request-direction never-forward set

This set holds the names a client may send that the gateway never relays upstream, whatever the forward mode.
xref:../configuration.adoc#_never_forward_set[The never-forward section of the configuration reference] lists
the members once. This record states the rule that admits a name. Membership answers one of five questions:

* *Credentials the gateway terminates or mediates:* the inbound `Authorization`, which the gateway validates
  and replaces with the mediated bearer. The browser `Cookie` is deliberately not here. It is a jar holding the
  gateway's cookies and the application's side by side, and a set member can only withhold the jar whole. The
  gateway withholds its own cookies by name instead, under every policy
  (<<_the_browser_cookie_is_a_per_route_policy>>).
* *Hop-by-hop and connection-specific names:* they describe the hop the gateway terminates, not the message it
  forwards.
* *Framing the gateway re-establishes:* the body length.
* *Names the gateway owns or regenerates:* the authority, the request's origin and referrer, and the date.
* *Spoofable provenance claims only the gateway may make:* the underscore spellings of the forwarding names and
  the vendor client-IP aliases.

*Two sets split the forwarding names, by the question each name answers.* The canonical forwarding names stay in
the regeneration skip. That set enumerates what the gateway emits. The gateway reads it twice: as the client-copy
skip, and as the mask that hides inbound forwarding headers from the resolver when the immediate peer is
untrusted. The gateway does not regenerate `X_Forwarded_For` or `X-Real-IP`, and the resolver never queries
either. Filing them there would assert a false regeneration relationship and widen a mask with names nothing asks
for. They are provenance claims only the gateway may make, which is this set's question. `Forwarded` contributes
no variant: it has no hyphen to fold, so an entry here would duplicate the canonical name.

The threat is not a corrupted regenerated header, which such a name cannot cause. The threat is an upstream that
reads the name as the canonical one. A framework folding `-` and `_` into one CGI-style variable resolves
`X_Forwarded_For` to the same `HTTP_X_FORWARDED_FOR` as the real header. Under the allow-list-only model these
names dropped incidentally, because everything unlisted did. Under forward-all the gateway must state the
protection in its own set. A per-route `headers_deny` remedy leaves an equivalence class incomplete. `set_headers`
is unaffected: the strip governs client input, and an operator fronting an upstream that reads `X-Real-IP` still
sets it deliberately.

*Folding closes the class, not a list of members.* Both sets test membership on the separator-folded name: lower
case, with every `_` mapped to `-`. Each set therefore closes its own names across the whole `-`/`_` class. The
literals are not the closure. A two-separator name has four spellings (`X-Forwarded-For`, `X_Forwarded_For`,
`X-Forwarded_For`, `X_Forwarded-For`) that a CGI-folding upstream resolves to one variable. Enumerating them means
four entries per name and a fix each time one is missed. That is the Traefik fix-chain, where each CVE closed one
spelling and a sibling survived. Folding is also inherited: a later addition to either set covers every spelling
with no second edit.

*The request set and the response strip are independent enumerations.* The request set currently contains every
strip name. That is an observation, not an invariant. Each set has its own exhaustive test, so a one-directional
addition fails that set's assertion instead of propagating.

*Two behaviours ride on membership and stay out of the set literal*, because each depends on a value or a mode:

. *`authorization` is the single re-admittable member.* The gateway honours it only when a route declares a
  positive-list naming it. A negative-list or forward-all has no positive-list, so neither can leak an inbound
  credential. The mediated bearer, merged last, still overwrites a re-admitted value.
. *`te` crosses only when its value is exactly the `trailers` token.* RFC 9110 admits that one value end-to-end.
  Any other value negotiates a transfer coding for the hop the gateway terminates.

*The `forward` block never decides about `Cookie`.* The mode copy skips the name in every forward mode. The boot
refuses a `forward.headers_allow`, `forward.headers_deny` or `forward.set_headers` entry naming `Cookie`. The
`cookies` block is the one place that decides, and a second place would let two blocks disagree about one header.
`authorization` stays re-admittable through a positive-list because it is one credential with one owner. `Cookie`
has its own block because it is many.

=== The browser `Cookie` is a per-route policy

The absolute strip kept the BFF's session cookie away from upstreams. It also left the gateway unable to front an
upstream that keeps its own session in a cookie, which is a supported case. The response direction had the
mirror-image gap: one upstream could set a cookie, with a `Domain` of its choosing, that the browser then sent to
every other upstream behind the same host.

*The gateway's own cookies never cross, under any policy and in either direction.* One framework-free definition,
`GatewayCookies`, holds them:

* every cookie under the reserved `__Host-sheriff-` prefix, always, with or without a BFF, so the prefix covers a
  later gateway cookie by construction;
* the configured `oidc.session.cookie_name` and its `-activity` sibling, in both session modes.

The boot rules, the request rebuild and the response predicate all read that one definition, so the three cannot
disagree about what the gateway owns.
xref:../configuration.adoc#_never_forward_set[The never-forward section] states how a name is matched. The BFF's
sealed session cookie belongs to the gateway, never to the upstream. A session cookie forwarded to the proxied API
(GHSA-vvg7-p7jw-8qr3) is the failure a second, hand-maintained drop list eventually produces, when one side learns
a new cookie name and the other does not.

*The route's `cookies` block decides which application cookies cross.* It names the mode in `allow`: `none`, `all`
or a list of cookie names. That one declaration decides both directions. It resolves like every policy block
(link:0067-Every_policy_block_is_one_declaration_resolved_nearest_declared_scope_wins_with_whole-block_replacement.adoc[ADR-0067]):
the nearest declared block wins and is taken whole. The default is `none`. An asset route or a redirect route
always resolves `none`, because it has no upstream to give a cookie to or relay one from.
xref:../configuration.adoc#_cookies[The `cookies` reference] and
xref:../user/endpoint-routes.adoc#_cookie_dependent_upstream[Fronting a cookie-dependent upstream] specify the
fields, examples, rebuild and predicate. This record states what they decide:

* *Request.* The upstream receives a `Cookie` rebuilt from the admitted pairs on every dispatch path. The gateway
  drops its own cookies first, always.
* *Response.* The gateway relays an upstream `Set-Cookie` line only when the route admits the cookie it names and
  the name is not one of the gateway's own. The gateway removes its `Domain` attribute. An upstream therefore can
  neither set a gateway cookie nor widen a cookie past the host the browser addressed. `Path` crosses as sent. A
  cookie one upstream sets still reaches every route its path covers, and that route's upstream receives it only
  when its own policy admits the name. link:../security-threat-model.adoc#gw-15[GW-15 of the threat model] records
  this accepted residual.
* *The default relays nothing.* Under `none` the gateway relays no upstream `Set-Cookie` at all. Every upstream
  that sets cookies needs a route that declares the cookies it relies on.

*The gateway guards a cookie-forwarding route against cross-site requests.* Once a browser cookie can reach an
upstream, a cross-site page can make the browser send it there, which is the ambient-credential shape CSRF rests
on. Every non-WebSocket route whose block forwards a cookie therefore carries a same-origin check
(xref:../configuration.adoc#_cookies_same_origin_check[the same-origin check]). It trusts the origin the gateway
received the request on, plus exactly the block's `additional_origins`. It rejects an unsafe request whose origin
it cannot prove, before authentication and before the upstream.

The check runs before the trust boundary, so
link:0073-Untrusted_callers_get_the_unrouted_404_for_every_rejection_raised_before_the_trust_boundary.adoc[ADR-0073]
sets the answer. On the shipped default the rejection is answered as an unrouted address is: `404`, the routing
problem document, and the HTTP `404` on a gRPC route rather than a trailers-only status. The event stays
`CSRF_REJECTED`, and `sheriff_errors_total` still meters it. With `security_defaults.uniform_not_found: false` the
rejection answers `403`. Which requests the check rejects is the same either way.

*The check applies only to an unsafe request that carries at least one cookie the route would forward.* It reads
the request through the same reading the rebuild uses, so the two cannot disagree about "forwarded". A request with
no forwardable cookie hands the upstream no ambient browser credential, so a cross-site page has nothing to forge.
A non-browser client, such as a gRPC service or a server-to-server caller, keeps working without `Origin`.
`same_origin_check: false` removes the check and logs a WARN (`ApiSheriff-139`). Defending that upstream against
CSRF is then the upstream's own job, and the operator makes that choice visibly.

*A WebSocket route is settled differently.* The exact-match `websocket.allowed_origins` allowlist already gates its
upgrade. That gate is stricter than the same-origin check, because it always rejects an absent `Origin`. A second
origin list on one upgrade would only add a way for the two to disagree. A cookie-forwarding WebSocket route must
instead declare a non-empty `websocket.allowed_origins`, and the boot refuses it otherwise.

*The boot refuses a gateway-scope `allow: all`*, because "every cookie to every upstream" is the exposure the policy
exists to scope. xref:../configuration.adoc#_cookies_boot_rules[The `cookies` boot rules] list the other boot
refusals and the two boot WARNs.

=== The gateway-understood protocol set

These names cross without an operator entry, in two tiers:

* *Unconditional:* `Accept`, `Accept-Encoding`, `Accept-Language`, `Content-Type`, `Range`, `If-Range`, `If-Match`,
  `If-Unmodified-Since`. They carry content negotiation, range requests and the write and range preconditions.
* *Conditional:* `If-None-Match` and `If-Modified-Since`, the two RFC 9110 §13 validators a `304` answers. The
  route's `not_modified` toggle gates them.

*The membership rule is knowledge, not necessity.* A name belongs when the gateway knows what it means and can reason
about the consequences of relaying it. `User-Agent` stays out on the same test: widely expected, required for nothing,
and an upstream that needs it can name it. The set is a fixed constant with no configuration surface. An operator who
wants one of these withheld denies it by name.

*A `headers_deny` entry naming a protocol header wins.* The gateway applies the set only to names the mode copy did
not already withhold. It deliberately does not consult a positive-list, because crossing without being named is the
set's purpose. Denying a name is therefore the only way to withhold it.

*The set is disjoint from the never-forward set, and the disjointness is load-bearing.* The gateway applies the
protocol set after the strip, but it copies the names from the raw client request rather than from the stripped map.
The strip therefore does not filter it. That is safe only while the two sets share no name. A test asserts the
disjointness directly.

=== The `not_modified` decision

Conditional requests have two halves: the validators the client sends, and the `ETag` and `Last-Modified` the upstream
answers with. The toggle stays, gates only the two `304` validators, and with the flag off withholds both from `GET`
and `HEAD` in every forward mode. The response side is unchanged.

The two halves are one decision: forwarding a validator whose answer the gateway then strips asks a question it
discards. One flag gates both halves, and a test that names both stages asserts the coupling. `If-Match`,
`If-Unmodified-Since` and `If-Range` are not gated. Withholding them changes the request (a lost update, a
mixed-version `206`) rather than discarding an answer.

With the flag off, `ForwardPolicyStage` removes the two from a `GET` or `HEAD` after the mode copy. On other methods
they cross: `If-None-Match` is a `412` write precondition, and the origin ignores `If-Modified-Since`. `set_headers`
stays operator configuration. The mode decides which client headers cross, and only the toggle knows the answer is
stripped.

== Alternatives rejected

=== Derive the request set from the response set plus a delta

Define one core list and express the request direction as "the core plus these extra names".

*Rejected because* it asserts a relationship the two directions do not have. One set concerns a connection the gateway
terminates toward a client. The other concerns credentials and provenance the gateway owns toward an upstream. Their
present overlap is a coincidence of membership. A derivation would make every response-direction addition silently
change request behaviour.

=== Make the protocol set configurable

Let an operator extend or replace the gateway-understood set per route or globally.

*Rejected because* it reintroduces the enumeration it exists to remove, and adds a way to get it wrong. The set's value
is that it is the same everywhere and needs no thought. A configurable version is an allow-list with a default.
`headers_allow` already covers a name the gateway does not know.

=== Use "technically necessary for the upstream" as the membership rule

Admit any header an upstream commonly requires.

*Rejected because* the rule admits `Authorization` and the whole `Cookie` jar: the inbound credential the gateway
replaces, and a header carrying the cookies the BFF pattern withholds. A rule that contradicts the gateway's credential
boundary at its most important names is not a rule.

=== Drop the `not_modified` toggle and always forward validators

Remove the flag, forward both `304` validators unconditionally, and always relay `ETag` and `Last-Modified`.

*Rejected because* it removes the operator's ability to keep a route out of conditional-request handling. The flag has a
legitimate use: a route whose upstream computes validators expensively, or whose responses intermediaries must not
cache, wants the whole exchange off. Removing it also removes the coupling between the halves, so a later change to one
direction would have nothing to hold it to the other.

=== Rewrite identity headers to a neutral value

Replace `Server` and `X-Powered-By` with a fixed value such as `Server: gateway`.

*Rejected because* a rewritten banner is still a banner, now one the gateway asserts about itself. Removal discloses
nothing.

=== Add the identity names to the response-direction strip

*Rejected because* the strip holds names that are wrong on the client's connection, and no route may override it. An
identity header is well-formed, so merging the two would drop the per-route opt-out.

=== Forward every cookie by default

Relay the browser `Cookie` and the upstream `Set-Cookie` untouched unless an operator removes them. Kong, Traefik, NGINX
and Apache APISIX default to this.

*Rejected because* the gateway terminates a browser session of its own. This default hands that session cookie to every
upstream until someone remembers to remove it. It also lets any upstream set a cookie every other upstream then receives.
A gateway whose premise is that the upstream never sees the session cannot ship it.

=== An all-or-nothing opt-in per endpoint

Let an endpoint switch cookie forwarding on or off as one flag. KrakenD's `input_headers` has this shape, where naming
`Cookie` forwards the whole header.

*Rejected because* the useful decision is per cookie, not per header. Once on, the switch forwards the gateway's own
cookies beside the application's. It also cannot give one upstream its `SESSIONID` without the rest of the jar.

=== Keep the absolute strip

Withhold `Cookie` from every upstream and relay no upstream `Set-Cookie`. Duende BFF does this, as does a Spring Cloud
Gateway route with `RemoveRequestHeader=Cookie`.

*Rejected because* fronting a cookie-dependent upstream is a supported case, and the strip makes every such upstream fail
with no repairing configuration. `GatewayCookies` keeps the strip's one real benefit under every policy: the gateway's
session never reaches an upstream. Dropping the strip costs that property nothing.

=== A comma-separated cookie list

Spell `allow` as one string, `allow: "SESSIONID,theme"`.

*Rejected because* it puts a second parser in front of a value YAML already types. A comma is not a cookie-name character,
so the format is unambiguous in principle. But `all`, `none` and a one-name list become indistinguishable by type. A stray
space or an empty segment becomes a boot refusal to explain instead of a schema error the editor shows. The YAML
scalar-or-list makes the three modes three shapes.

=== A gateway-scope `allow: all`

Let one gateway-wide block forward every application cookie to every upstream.

*Rejected because* it is the forward-everything default re-entered through configuration. Every upstream, including later
ones, would receive cookies the others set. The anchor, endpoint and route policy scopes accept `all`, because there it
names the upstreams it reaches. At the gateway policy scope the boot refuses it.

=== Forward `Origin` and leave CSRF to each upstream

Relay the browser's `Origin` and let every cookie-dependent upstream defend itself.

*Rejected because* `Origin` is a member of the never-forward set, a name the gateway owns. Re-admitting it would carve the
first exception into that set for a job the gateway can do itself. Each upstream would also have to get CSRF protection
right individually, behind a gateway that already knows the origin it received the request on. The check runs once, at the
edge. An upstream that wants the job sets `same_origin_check: false`, visibly.

=== Reject every `Origin`-less unsafe request on a cookie-forwarding route

Apply the same-origin check to every unsafe request on such a route, whether or not it carries a forwardable cookie.

*Rejected as the stricter variant.* It rejects the non-browser clients, such as gRPC services and server-to-server callers,
that send no `Origin` and no cookie and so carry no ambient credential to forge. The threat needs a forwarded cookie to
exist. The check on cookie-carrying requests closes the threat without breaking those clients.

== Consequences

=== Properties of the design

* Forward-all is safe by construction: the sets withhold the dangerous names structurally, not by operator diligence.
* An operator states application policy and the gateway supplies HTTP mechanics. A positive-list route names three headers
  instead of eleven.
* One home per direction means a name cannot be present in one relay path and absent from another.
* With the toggle on, the `304` validators cross unless `headers_deny` names them. With it off, neither crosses a `GET` or
  `HEAD` in any mode, so the halves agree. `set_headers` is ungated.
* One sentence states the membership rule, so a future addition can be argued against it.
* The gateway can front an upstream that keeps its session in a cookie, and one definition keeps the gateway's own cookies
  out of every upstream.
* An upstream cannot plant a gateway cookie or widen a cookie's `Domain`. A cross-site page cannot ride a forwarded cookie
  into a state-changing upstream request.

=== Accepted costs

* Four sets are four surfaces to maintain. A name relevant to both directions is deliberately written twice.
* The protocol set is a fixed constant. An operator whose upstream needs another name adds a positive-list entry.
* The knowledge rule needs a judgement per name. It is sharper than "necessary" but not mechanical, and `User-Agent` sits
  close enough to the line to need its rationale recorded.
* The default `none` relays no upstream `Set-Cookie`. An upstream that sets a cookie does not get it back until its route
  declares a `cookies` block. The alternative default relays cookies no one decided to relay.
* A cookie-forwarding route that serves a browser from a second origin needs that origin in `additional_origins`. The check
  names no wildcard and trusts nothing it was not told.

=== Risks

* *An addition to either enumerated set can break the protocol set's disjointness.* The protocol set bypasses the strip, so
  a name on both lists would be withheld and then re-admitted. The disjointness test is the guard, and it protects an
  invariant, not tidiness.
* *The two-independent-lists rule looks like duplication and invites a refactor.* Deriving one set from the other silently
  couples the directions. The sets carry the rationale for that reason.
* *Forward-all makes every future omission from the request set a live defect.* A new client-sendable, gateway-owned header
  requires a set update in the same change.
* *`allow: all` exposes every application cookie on the host to that route's upstream*, including cookies another upstream
  set. It should stay rare below the gateway policy scope. A list names exactly what one upstream needs.
* *A gateway cookie set outside `GatewayCookies` would cross.* The reserved prefix covers every cookie under it. The risk is
  confined to a cookie under an operator-chosen name: the session cookie and its activity sibling. The definition reads those
  from the same configuration key the session runtime reads.
