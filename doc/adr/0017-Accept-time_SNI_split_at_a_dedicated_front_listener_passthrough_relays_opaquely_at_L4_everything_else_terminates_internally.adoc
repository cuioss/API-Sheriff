== Status

Accepted

== Decision

=== The question

An inbound TLS connection on the public port takes one of two mutually exclusive dispositions. Some hostnames relay opaquely at L4: the gateway never sees plaintext, and the backend presents its own certificate end to end. Every other hostname terminates at the gateway, with optional inbound mTLS.

Only the Server Name Indication in the TLS ClientHello tells the two apart, and it arrives before any handshake completes. A framework HTTPS listener exposes SNI only at its own handshake layer. By then it has committed to terminating the connection, so it offers no seam to divert a raw, still-encrypted stream. This record settles where the accept-time decision lives, how the two dispositions share one public port, and how an ambiguous hello stays off the more permissive path.

=== The front listener owns the public TLS port

`SniFrontListener` is a raw-TCP `NetServer` that terminates nothing. It buffers bytes until `ClientHelloSniParser` reports a complete ClientHello, reads the SNI and routes on it:

* *An SNI in `tls.passthrough_sni`*, compared case-insensitively: `PassthroughRelay` relays opaquely to the topology-resolved backend. The relay replays the buffered ClientHello and never speaks TLS, so the backend's own certificate reaches the client end to end.
* *Any other SNI, or none:* the same relay hands the still-encrypted stream to the internal terminated listener, which solely owns TLS termination and inbound mTLS.

=== Port ownership is split

The public port belongs to the front listener (`sheriff.tls.public-port`). A deployment that enables passthrough moves the terminated listener to the internal port (`sheriff.tls.internal-https-port`) through its own port variable. Termination and client-certificate verification belong to the terminated listener alone. The passthrough path never participates in a handshake.

=== SNI fails closed

The disposition is decided only after the full ClientHello is reassembled. A hello that carries no SNI, is malformed, is not a TLS handshake or passes the 32 KiB reassembly bound takes the terminated path and records `ApiSheriff-107`. It never takes a passthrough, and it never takes a path without the configured client-certificate requirement.

=== No overhead by default

`TlsEdgeProducer` creates the front listener only when `tls.passthrough_sni` is non-empty. Otherwise the terminated listener keeps the public port, unchanged. A bind failure of the front listener refuses the boot, so the gateway never serves on a half-open TLS edge.

== Alternatives rejected

=== A framework listener-level SNI seam

Let the framework's own HTTPS listener read SNI during its handshake and branch there.

*Rejected because* the framework exposes SNI only after it has committed to terminating the connection. There is no clean seam to divert a raw, still-encrypted TCP stream before termination. Reading SNI at that layer cannot yield an opaque L4 passthrough in which the backend presents its own certificate, because termination has already begun when SNI becomes visible.

=== One terminating listener that re-originates TLS to passthrough backends

Terminate every connection at the gateway and open a fresh TLS connection to the backend for passthrough hostnames.

*Rejected because* it breaks end-to-end certificate identity: the client sees the gateway's certificate, not the backend's. It also places the gateway on the plaintext path for traffic that is meant to stay opaque, which enlarges the trust boundary instead of preserving it.

Both alternatives place the SNI decision at or after the framework's termination commitment. Termination has then begun before the disposition is known, which is incompatible with opaque L4 passthrough and with a fail-closed, pre-handshake decision.

== Consequences

=== Properties of the design

* One public port serves both dispositions, and the gateway decides at the earliest possible point: accept time, before any handshake.
* A passthrough target keeps its end-to-end certificate identity, because the gateway never terminates it.
* The fail-closed rule is structural. An ambiguous hello cannot reach the permissive path, independent of any per-request check.

=== Accepted costs

* The listener topology has two tiers, front and internal. That is a permanent increase in moving parts and a port-ownership contract deployments must respect.
* The gateway owns ClientHello reassembly and SNI extraction, because the framework exposes no pre-termination seam. That parser is a security-relevant surface the project must test at handshake level, not by configuration assertion.

=== Risks

* A malformed or maximally fragmented ClientHello fails closed to the terminated path. A passthrough client that emits a pathological hello loses passthrough rather than risking a wrong disposition. This trades availability for a guaranteed-safe disposition.
