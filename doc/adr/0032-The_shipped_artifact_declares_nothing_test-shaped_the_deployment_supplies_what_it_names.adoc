== Status

Accepted

== Decision

=== The question

`api-sheriff/src/main/resources/application.properties` ships to every deployment. A framework profile makes it cheap to park context-specific configuration there: Quarkus resolves a `%profile.key=value` entry only under the named profile, so a test value lies dormant elsewhere. That cheapness is why the practice accumulates, and why the question is settled once and not per key.

Three costs make the practice wrong for this artifact:

* *Test material and test credentials ship inside the production artifact.* A profile prefix does not make a secret absent. It only makes it unread. An artifact that carries credentials it never uses is a supply-chain and disclosure liability with no benefit.
* *A profile branch can mask a defect in the unbranched profile.* The test suite exercises the branched profile, and nothing exercises the production path. A readiness probe that stays green because the test profile configures a namespace production never configures reports on the harness, not on the product. The more thorough the suite, the more confident the false negative.
* *The configuration stops describing the product.* A reader of the shipped file cannot tell product contract from harness scaffolding.

The rule cannot be stated over syntax. "No `%`-profile entries" names a shape, not the defect. An unprefixed `quarkus.tls.<name>.*` bucket with a benchmark-specific name is as much a test binding as its prefixed equivalent, and it satisfies the syntactic rule. A shape-level rule can be met by relocating the defect, which produces a green check over an unchanged problem.

*The decision:* the shipped artifact declares nothing test-shaped, and the deployment supplies what it names. No key in the packaged configuration is scoped to, or named for, a test, benchmark or development context, whether or not it carries a profile prefix. When the shipped configuration names a logical binding, the deployment that uses the binding supplies its material.

=== Removal takes one of three shapes

One question settles the shape: *does the product read this key?*

[cols="1,2,2", options="header"]
|===
| Shape | Applies when | Result

| *Delete outright*
| Nothing in the product reads the key.
| The key is removed and re-supplied nowhere. Relocating it would preserve the redundancy in a new place.

| *Relocate to the deployment that names it*
| Something reads the key, and the value is deployment-specific.
| The shipped file carries no anchor and no placeholder. The deployment supplies the whole binding from its own configuration source.

| *Flip the shipped default*
| Both contexts need a value, and the values differ.
| The artifact ships the value that is safe when nothing is configured. The deployment that wants the other value supplies it.
|===

Deleting a branch without flipping the default it overrode is a regression, not a removal. The branch existed because the default was wrong for the unbranched context, so the default and the branch are settled together. The link:../development/README.adoc#_artifact_purity[Artifact Purity] section of the contributor guide carries the worked example of each shape.

=== A binding the deployment supplies fails loudly when absent

Relocation is safe only because an unsupplied binding is a hard startup failure. link:0011-gatewayyaml_exposes_JWKS_trust_and_egress_as_neutral_names_bound_by_the_deployment.adoc[ADR-0011] owns that property for the JWKS trust surface, and it is a precondition of this decision. Without it, relocation would turn a visible test dependency into an invisible production misconfiguration.

=== Name-bearing configuration comes from a file source

A deployment supplies configuration whose *name* is itself discovered, such as a `quarkus.tls.<name>.*` bucket or an issuer namespace segment, through a mounted configuration file. Environment sources expose property names in mangled form, which does not satisfy the prefix scan that discovers the name, so the binding resolves as absent. Fixed-name properties, including the one that selects the mounted file, are safe as environment variables.

=== A guard enforces the prefix shape, and only that

`ShippedApplicationPropertiesTest` asserts over the packaged file that no key carries a profile prefix. The rule is stated over intent, so the guard is a partial mechanical proxy for it. The contributor guide states how the guard is built and what it does not cover.

=== An unconditional declaration made to satisfy this rule is not a violation of it

A key declared unconditionally *because* a profile-scoped declaration would be a branch is the rule working. The gateway ships two such keys. The key-less TLS bucket of the plain-HTTP management opt-out (`quarkus.tls.plain-management.reload-period`) is one. The bean-exclusion key that removes the extension's health beans (`quarkus.arc.exclude-types`, see link:0074-The_token-validation_extensions_metrics_collector_observes_the_gateway_validator_and_its_health_probes_stay_excluded.adoc[ADR-0074]) is the other. The extension's metrics collector is deliberately not excluded. Both keys carry a comment citing this rule. Neither is test-shaped: both are product configuration, inert until a deployment selects the behaviour it enables.

== Alternatives rejected

=== Relocate every context-specific key to deployment configuration, uniformly

Apply the relocation shape to all of them. This is the most mechanical rule, needs no per-key judgement and satisfies the artifact-purity goal completely.

*Rejected because* it preserves redundancy under a new name. Where nothing in the product reads a key, the deployment would maintain configuration with no consumer. That parallel declaration will drift, get copied into the next deployment and eventually read as evidence that the product needs it. Relocation is right only when something reads the key. When nothing does, the honest change is deletion.

=== Retain a material-free unprefixed anchor for the relocated map key

Keep the name in the shipped file with no path and no password, so the artifact declares the configuration map key and the deployment supplies only the material. This guarantees name discovery in every runtime and satisfies the profile-prefix guard completely.

*Rejected because* it bakes a context-specific *name* into product configuration: the same defect in different clothing, and one that evades the guard by carrying no prefix.

The key-less bucket of the management opt-out looks like the same construction, but the two have opposite intent. That bucket is a product feature whose emptiness *is* the mechanism: selecting it leaves the key-certificate options null, which performs the plain-HTTP downgrade. It must stay empty forever. A relocated trust anchor is a bucket whose purpose is to be populated with real material, and its name is specific to one non-production context. Declaring it empty does not make it inert. It makes it a promise the artifact cannot keep.

=== Supply the relocated name-bearing configuration as environment variables

Avoid a mounted file and pass the values as environment variables, which every deployment mechanism supports and which needs no volume.

*Rejected on mechanism, not on principle.* The mangled names do not satisfy the literal prefix scan that discovers a configuration map key. The name would never be discovered, the binding would resolve as absent and the boot would abort, which reproduces the failure the relocation was chosen to avoid.

=== Enforce the rule with a source-tree check instead of a packaged-config test

Scan `src/main/resources` at build time or in a linting step, rather than asserting over the build output.

*Rejected because* it does not test the delivered artifact. The source tree is the input to packaging, not its result. A change in resource filtering, profile handling or build layout could make the two disagree while the check keeps passing. Asserting over the packaged copy costs nothing extra: no new plugin, dependency or script.

Each rejected option optimises for the *check* rather than for the *property the check protects*. Uniform relocation, an unprefixed anchor and a source-tree scan all produce a green result over an artifact that still carries what this decision removes.

== Consequences

=== Properties of the design

* The released artifact carries no credentials, no test paths and no harness scaffolding.
* Production and every test context resolve the same configuration surface. A defect in the product's own configuration cannot hide behind a branch only the test suite takes.
* Name discovery behaves identically in JVM and native, because whatever must be discoverable is declared unconditionally in a file source.
* The shipped file is self-describing: every key in it is product contract.

=== Accepted costs

* A deployment that uses a named binding edits two places: the name in the product's configuration and the material in the deployment's. ADR-0011 accepts the same cost for portability and secret separation.
* A deployment that names a binding and forgets to supply it does not start. A class of failure moves from "silently wrong at runtime" to "loudly absent at boot".
* Test and benchmark harnesses carry configuration the artifact used to carry for them. The ownership moved, and the harness is now responsible for keeping it correct.

=== Risks

* *A green guard will be over-read.* This is the principal residual risk, and it is deliberately accepted. The guard enforces the profile-prefix shape, and the decision is stated over intent. An unprefixed but test-shaped key passes the guard while violating the rule. A green guard is not proof of a clean artifact. No automated check is proposed for the intent-level rule, because "is this name test-shaped?" is a judgement a reviewer makes and a regular expression cannot.
* *The three shapes can be misapplied by choosing the convenient one.* Relocation is always available and always looks like compliance, so a key that should be deleted can be relocated and still pass every check. The discriminating question has to be answered by tracing consumers.
