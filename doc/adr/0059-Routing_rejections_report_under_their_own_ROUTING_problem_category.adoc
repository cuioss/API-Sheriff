// adr-metadata
// summary: The three rejections that say "this request addresses nothing the gateway serves that way" — no route matched (404), a Host naming a hostname reserved for passthrough (404) and a method outside the route's allowlist (405) — report under a ROUTING category of their own (slug routing, type urn:api-sheriff:problem:routing, title Routing) instead of INPUT_VALIDATION, a breaking change to the public problem type with no alias; on an address no route serves the two 404s stay identical on the wire, and they are separated for the operator by a bounded event label, which changes the label set of sheriff_errors_total to {route,category,event} for every series; the verb-gate 405 and the smuggled-host 404 are eligible for the negotiated HTML error page; on the shipped default a verb-gate rejection before the trust boundary is answered as the unrouted 404 (ADR-0073).

== Status

Accepted

== Decision

Every rejection the gateway originates names a category. Three places read it: the `type` and `title` of the RFC 9457 problem document, the `category` label of the error metric, and `grpc-message` on a `protocol: grpc` route. A category therefore has to answer the first diagnostic question: where do I look?

Three rejections do not fit the category that names a malformed request. The request is well-formed in all three, and each is a statement about the route table:

* *No route matched.* The path is unknown, the endpoint is disabled, or the route is bound to a different host.
* *The `Host` names a hostname reserved for passthrough.* The accept-time L4 split serves that hostname, and the terminated listener never reaches it.
* *The method is outside the route's allowlist.* The route exists and does not serve that verb.

Reported as `Input Validation`, they send the reader to path encoding, headers and parameters before the route's `match` block. The cost is highest for a route that exists and is bound to another host.

*The decision:* a rejection that is a statement about the route table reports under a `ROUTING` category. On an address no route serves, the two `404`s are one answer on the wire. They are always two values on a bounded metric label.

=== The category

`EventCategory.ROUTING` carries the slug `routing`, the title `Routing` and the problem type `urn:api-sheriff:problem:routing`. It has four members:

[cols="2,1,3", options="header"]
|===
| Event | Status | Cause

| `NO_ROUTE_MATCHED` | `404` | no route matches the address (deny-by-default route selection)
| `PASSTHROUGH_HOST_SMUGGLED` | `404` | the `Host` of a terminated request names a `passthrough_sni` hostname
| `METHOD_NOT_ALLOWED` | `405` | the method is outside the route's effective `allowed_methods`
| `PRE_TRUST_INTERNAL_FAILURE` | `404` | an unexpected failure before the trust boundary, answered as the floored unrouted `404` so a failure on a routed address cannot be told from an absent one; the event itself has no HTTP mapping
|===

=== The three readers of the slug

The slug is defined once, on the category, and read in three places that hold no copy:

* *The problem document.* `type` is `urn:api-sheriff:problem:routing` and `title` is `Routing`.
* *The error metric.* `sheriff_errors_total` carries `category="routing"`.
* *`grpc-message`.* A rejection on a `protocol: grpc` route is trailers-only (link:0016-grpc-trailers-only-rejection-mapping.adoc[ADR-0016]), and its `grpc-message` is the category slug. The `grpc-status` mapping is unchanged: `NOT_FOUND` for the two `404`s, `UNIMPLEMENTED` for the `405`.

=== The smuggled host shares the category and the response

On an address no route serves, the response to `PASSTHROUGH_HOST_SMUGGLED` is the response of that unrouted address: the same status, problem type, title, headers and negotiation. A response that differed for a reserved hostname would let an anonymous caller enumerate the `passthrough_sni` set by comparing answers. The passthrough upstreams are deliberately unreachable through the terminated listener, and their names are part of what that guard protects.

The event's security relevance stays where the caller cannot read it. The rejection writes its `WARN` record, with a fixed disposition and never the raw `Host` value, and it is counted under its own event name.

=== The `event` label

`sheriff_errors_total` carries an `event` label whose value is the `EventType` name:

----
sheriff_errors_total{route,category,event}
----

An unrouted address is counted under `event="NO_ROUTE_MATCHED"` and a smuggled passthrough host under `event="PASSTHROUGH_HOST_SMUGGLED"`, both with `category="routing"`. The label is on every series of the metric.

The label is bounded. Its value is the name of an `EventType` constant, so its cardinality is fixed at the enum. It never carries request-derived input: no path, no `Host`, no method string. The `route` label follows the same rule with its fixed `<no-route>` value.

`SheriffMetrics` records the metric at four sites: a rejection raised in the pipeline, the pre-trust internal failure, the over-ceiling body of a reserved path, and a source block (`SOURCE_BLOCKED`), which is refused before route selection and so carries the `<no-route>` label. Three rejections are rendered directly and are not counted in it: the `405` for a request method the gateway cannot parse, the `404` for a reserved path on a gateway without an active session runtime, and the `404` of the client JWKS path in its withheld form. All three appear in the `4xx` bucket of `sheriff_requests_total` only. The two `404`s among them carry the routing problem document without being counted as routing errors.

=== HTML eligibility

`NO_ROUTE_MATCHED`, `PASSTHROUGH_HOST_SMUGGLED` and `METHOD_NOT_ALLOWED` classify as `HTML_ELIGIBLE` in `ErrorPageClassifier` and negotiate the HTML error page of link:0053-Portal_templates_render_on_a_standalone_Qute_engine_and_escape-bypass_constructs_are_refused_at_boot.adoc[ADR-0053]. `PRE_TRUST_INTERNAL_FAILURE` classifies as `KEEP_SHAPE`.

* *`PASSTHROUGH_HOST_SMUGGLED`.* An unrouted address answers a browser navigation with the HTML page. A smuggled host answering that navigation with a problem document would make the two `404`s distinguishable by body shape. Eligibility follows from wire identity.
* *`METHOD_NOT_ALLOWED`.* A `405` is reachable by navigation, for instance a link to an address that serves `POST` only. A browser shown a JSON document has no page to read.

The page title for a `405` is the fixed `Method Not Allowed`, derived from the status and never from a problem detail.

A `405` for a method the gateway cannot parse does not negotiate. It is answered before a pipeline request exists, so it is always `application/problem+json`.

=== The verb gate before the trust boundary

The verb gate runs before the trust boundary. On the shipped default, link:0073-Untrusted_callers_get_the_unrouted_404_for_every_rejection_raised_before_the_trust_boundary.adoc[ADR-0073] answers its rejection as an unrouted address is answered: `404`, no `Allow` header, the routing problem document, or the HTML page for a browser navigation. The wire identity of the two `404`s extends to that third answer. The event stays `METHOD_NOT_ALLOWED` in `ROUTING`, and the `event` label still separates it for the operator. The `405` with `Allow` and its HTML eligibility return with `security_defaults.uniform_not_found: false`. The `405` for an unparseable method is raised before route selection and is unaffected.

=== What stays elsewhere

* `RESERVED_BODY_TOO_LARGE` and `CONTENT_TOO_LARGE` are `INPUT_VALIDATION`. A body beyond a declared size is a property of the request (link:0023-The_declared_max_body_bytes_cap_is_the_effective_one_and_a_breach_is_the_gateways_413.adoc[ADR-0023]).
* The framing rejection is a `400` `SECURITY_FILTER_VIOLATION` in `INPUT_VALIDATION`, with the other inbound-filter, path-allowlist and parameter-limit rejections.
* `/auth/userinfo` is `Accept`-blind and answers JSON whatever the request accepts.

== Alternatives rejected

=== Leave the three in `INPUT_VALIDATION`

This changes no public surface.

*Rejected because* the category's job is to say where to look, and for these three it says the wrong place, most of all for a route that exists and is bound elsewhere.

=== Retitle `INPUT_VALIDATION` to something broad enough to cover them

A title such as "Request Rejected" would stop the category from being wrong.

*Rejected because* it removes the misdirection by removing the direction. Every `400`, `404`, `405` and `413` would share one word, and the reader would be back to the status code. It would also change the title of correctly named rejections and leave the slug and the URN describing something the title no longer does.

=== Give the smuggled host a category of its own

A security category would make the event prominent on a dashboard without a second label.

*Rejected because* what must be hidden from the caller cannot be carried in a field the caller receives. The distinction would sit in the problem `type`, the `title` and `grpc-message`.

=== Keep the smuggled host in `INPUT_VALIDATION` and move only the other two

*Rejected for the same reason.* The smuggled host would differ from an unrouted address by problem type, and an anonymous caller could tell them apart from the body alone.

=== Keep the old URN as an alias

A transition period with both URNs would spare clients an immediate change.

*Rejected because* a problem document has one `type`, so the alias would need a second response shape or a non-standard extension member, and every client would have to understand both. The gateway has not started API stability, and a clean change costs clients one edit.

=== Separate the two `404`s by a second metric

A dedicated counter for smuggle attempts would leave the label set unchanged.

*Rejected in favour of* one bounded label. A counter would solve one pair and leave every other pair of same-category events inseparable, each needing its own counter.

=== Put the request's host or path on the metric

This would make a misrouted request directly findable.

*Rejected because* it is request-derived input on a label: unbounded cardinality, and attacker-chosen strings in the metrics store. The access log is where a request's own values belong.

=== Leave the verb-gate `405` as JSON only

API clients produce most `405`s and keep the problem body anyway, because they send no explicit `text/html` range.

*Rejected because* keeping it JSON-only would affect only the browser that navigates into one, the one reader a JSON body does not serve. The negotiation rule already protects API clients, so the exclusion bought nothing.

One group of these options keeps the wire or the metric unchanged and pays with a category that misleads or a distinction that cannot be made. The other makes the distinction where the caller can read it. The decision separates the two audiences: on an address no route serves the caller gets one answer for both `404`s, and the operator gets a label the caller never sees.

== Consequences

=== Properties of the design

* The category answers the first diagnostic question. `Routing` sends the reader to the route table, the host binding and the verb allowlist, and `Input Validation` means what it says.
* On an address no route serves, the set of reserved passthrough hostnames is not readable from the answer. Status, type, title, headers and body shape are those of the unrouted address in both the JSON and the HTML answer.
* The operator loses nothing. The smuggle attempt is counted under its own `event` value and logged, so an alert is one label matcher.
* The `event` label separates every pair of events that share a category: the two `413`s, the two `401`s and the three upstream failures too.
* A browser that navigates into a `405` or a reserved hostname gets a page, under the explicit-`text/html` rule every other eligible exit follows.

=== Accepted costs

* *Two breaking changes to public surface.* A `404` or `405` that carried `urn:api-sheriff:problem:input-validation` carries `urn:api-sheriff:problem:routing`, and `sheriff_errors_total` carries a third label. A dashboard or alert that matches the exact label set, or aggregates without naming the labels it keeps, has to be updated. A query that sums by `category` keeps its result. Neither change has a compatibility form.
* *More series.* The metric has one series per route, category and event that occurred. The bound is the enum, so the growth is a small constant factor.
* *The category name does not separate the routine from the hostile.* `category="routing"` shows unrouted traffic and smuggle attempts as one number, and the operator reads the `event` label to tell them apart.
* *The metric is not the full count of `404`s and `405`s.* The three directly rendered rejections are outside it, so `sheriff_errors_total` and the `4xx` bucket of `sheriff_requests_total` differ by design.

=== Risks

* *Wire identity is a property of every response attribute.* A change that gives one of the two `404`s a header, a title or a negotiation rule of its own reopens the disclosure. The classification of both events has to move together.
* *An unbounded label by accident.* A recording site that passed a request-derived string would create a cardinality and log-injection problem. The recorder accepts an `EventType`, not a string, which makes that a compile-time question.
* *A reader assuming the label covers every rejection.* A dashboard that treats the metric as the complete rejection count undercounts the three directly rendered rejections.
