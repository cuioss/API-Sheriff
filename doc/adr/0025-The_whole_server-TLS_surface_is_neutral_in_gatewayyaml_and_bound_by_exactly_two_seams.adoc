= ADR-0025: The whole server-TLS surface is neutral in gateway.yaml and bound by exactly two seams

== Status

Accepted

== Decision

=== The question

link:0011-gatewayyaml_exposes_JWKS_trust_and_egress_as_neutral_names_bound_by_the_deployment.adoc[ADR-0011] settled the layering question for the JWKS egress and trust surface: the gateway configuration names intent, the deployment supplies material, and one component maps between them. It did not state a general rule. This record settles the gateway's own server-side TLS surface, which spans four concerns:

* *Policy:* the protocol floor, the cipher allowlist, the advertised ALPN protocols, inbound mTLS and whether the management interface serves over TLS. These are identical in every environment the same document is deployed into.
* *Key and trust material:* environment-specific, secret and already handled by the runtime's own loading, format and rotation support.
* *Ports:* environment-specific, and load-bearing for topology.
* *Build-time knobs:* fixed when the native image is built, so no runtime document can influence them.

Three structural facts sharpen the choice:

* *A neutral name that binds nothing is worse than a raw framework key.* The runtime consults its TLS-registry configuration only when the server certificate also comes through that registry. A gateway that supplies its certificate through the HTTP-SSL keys never passes that guard, so a declared floor and allowlist reach no listener. A declared TLS floor reads as enforcement to every reviewer and auditor, and a security gateway must not claim it falsely. Any policy surface must be bound, and the binding asserted.
* *The two listeners share no seam.* The runtime enumerates `HttpServerOptionsCustomizer` beans for the terminated listener after it has built the SSL options, so a customizer can observe and overwrite the result. The management interface initialises on a path that never enumerates those beans.
* *The management interface has exactly one port.* The runtime's management configuration declares no separate SSL port and no insecure-requests mode. A management TLS decision therefore covers health and metrics together.

*The decision:* every server-TLS knob belongs to exactly one of three classes, and its class determines where it lives. Policy lives in the gateway configuration under neutral names and reaches the runtime through exactly two seams. Ports and material stay deployment-supplied. Build-time knobs leave the runtime surface entirely.

This extends ADR-0011 to the whole server-TLS surface. ADR-0011 stays in force, and its JWKS mechanisms are unchanged.

=== The three-way classification

[cols="1,3", options="header"]
|===
| Class | Rule

| *Policy*
| Named neutrally in the gateway configuration. Covers the protocol floor, the cipher allowlist, ALPN, inbound mTLS and whether the management interface serves over TLS. No key, and no part of the JSON schema, names the runtime.

| *Deployment-bound*
| Supplied by the deployment and never promoted into the gateway configuration. Covers certificate and private-key material, trust material and every port. Neutral deployment-side names the product already owns stay where they are, and runtime keys keep their environment-variable contract.

| *Build-time*
| Lives in the build configuration and never appears in the runtime configuration surface.
|===

=== Policy reaches the runtime through exactly two seams

[cols="1,2,2", options="header"]
|===
| Listener | Seam | Why it is the only one available

| Terminated listener
| `HttpServerOptionsCustomizer` beans. `TlsServerCustomizer` maps the `tls` block onto the enabled protocol set, the cipher allowlist and the ALPN protocols, and `MtlsServerCustomizer` owns client-auth.
| The runtime enumerates customizer beans after building the SSL options, so a customizer is the last writer. The TLS-registry keys do not work on this gateway, because the registry is consulted only when the certificate also comes from it.

| Management interface
| `NeutralTlsConfigSource`, a SmallRye `ConfigSource` that parses the gateway configuration and projects the management TLS policy onto the runtime key that governs it.
| The management interface never enumerates customizers. The only lever left on that path is the configuration the recorder reads, so a config source is the seam by elimination.
|===

Neither seam can replace the other. A customizer cannot reach management, and a config source is the wrong instrument for the terminated listener, where a live bean can observe what the configuration produced.

The config source cannot read the bound configuration model. A `ConfigSource` is constructed while the configuration system is being built, long before CDI exists. It therefore re-reads `gateway.yaml` directly and parses only the block it projects from. That is a bounded duplication of a small slice of parsing, not a second configuration pipeline. The authoritative parse and validation still happen once, later. The source ignores a malformed or absent document on purpose: the loader meets the same failure moments later and reports it as a located error, and failing earlier would replace that with a context-free failure from inside configuration-system construction.

=== The projecting source is single-ordinal and projects policy keys only

The config source sits at an ordinal above the environment-variable source. A policy named in the gateway configuration must take effect, and an ordinal at or below the environment's would let a deployment variable silently win over the document.

The source projects *policy keys only*: never a port, never trust material, never key material. No deployment-bound knob is ever in the projected set, so nothing the deployment owns can be outranked by surprise. A single ordinal is therefore sufficient, and policy-keys-only is a standing invariant of the source.

One projected policy key is reachable from the environment as well, deliberately. The management TLS-configuration-name key is a policy key by class and also the deployment door onto the plain-HTTP opt-out, described in <<two-doors-onto-one-lever>>. When both doors set it, the gateway configuration wins, because the source sits above the environment. The surprise-freedom above is a statement about deployment-bound knobs, and the source never projects those.

*The source must never project key material into the default TLS registry bucket.* The management-interface lookup falls back to the default bucket when no configuration name is selected, and takes that fallback only when the bucket carries key material. This project's default bucket is empty, because the server certificate arrives through the HTTP-SSL keys. Populating it from anywhere would switch the management interface to HTTPS through a path no configuration file mentions. A test asserts this.

[#two-doors-onto-one-lever]
=== Management HTTPS is the default, and the opt-out is runtime-native

The management interface serves over TLS by default, on the deployment-bound management port. Taking it to plain HTTP stays possible, because running operations endpoints in the clear behind a trusted boundary is a legitimate deployment, but it stops being silent. Two doors lead onto one lever:

* *The neutral door:* `management.tls.enabled: false` in the gateway configuration. The config source projects it onto the runtime's management TLS-configuration-name key, selecting a named TLS bucket that carries no key material.
* *The deployment door:* setting that same runtime key as an environment variable.

The neutral key projects nothing when it is absent or set to the secure value, so the deployment door keeps working unchanged.

The mechanism is runtime-native. Selecting a bucket with no key material *is* a disable: the named lookup resolves, the key material is null-guarded, and the recorder swaps in the plain options. It is runtime configuration, so one native image serves both postures with no rebuild. An unresolvable name fails the boot with an error naming the missing property.

The downgrade is *audited, not refused*. `ManagementPlainHttpAudit` emits a loud `WARN` (`ApiSheriff-115`) at startup. The audit is keyed on the *observed effective state*, the TLS material the listener actually resolved, because an audit keyed on a configuration key reports a comfortable fiction once that key is renamed, superseded or reached by another route.

=== The neutral management block declares no port

The neutral management block carries TLS policy only. The boot refuses a port written there, with a message naming the runtime property and environment variable that own it. A management port in the gateway configuration could reach the runtime only through the projecting source, whose ordinal would silently override the deployment's own port variable. Refusing the key makes its deliberate absence discoverable.

=== Named consequences of the classification

* *The terminated listener's port and its plain-HTTP handling stay deployment-bound.* Promoting the SSL port would break the link:0017-Accept-time_SNI_split_at_a_dedicated_front_listener_passthrough_relays_opaquely_at_L4_everything_else_terminates_internally.adoc[ADR-0017] split, in which a deployment that enables SNI passthrough gives the public TLS port to the front listener and moves the terminated listener to an internal port through that variable.
* *The management port stays deployment-bound*, for the ordinal reason above.
* *The native-image SSL knob is build-time and leaves the runtime surface entirely.* It lives in the build's `native` profile, the configuration active exactly when the knob has meaning.

=== Policy applies to the terminated listener

The TLS floor, cipher allowlist and ALPN policy govern the terminated listener. The front listener terminates nothing, so it neither applies nor could apply a cipher allowlist. For an SNI passthrough hostname the backend's own TLS policy is the effective one. This is a statement of what the policy can mean, not a limit more code could lift.

=== Plain HTTP is declared, and a gate on the first seam refuses the rest

`quarkus.http.insecure-requests=enabled` is the explicit plain-HTTP opt-in, and the environment source outranks the properties file, so a deployment that means to serve cleartext says so and is obeyed. A missing certificate is not a request for cleartext. "Deliberately behind a TLS-terminating ingress" and "the certificate failed to mount" are the same observation, and absence cannot express intent.

`ServerTlsDeclarationGate` therefore refuses, on the terminated-listener seam. It changes no option. It reads the declared server-TLS keys and throws. It acts before the runtime's own guard, because that guard reports the same state with the wrong words: an `IllegalStateException` naming the exposure key to an operator who set another value, saying nothing about the missing certificate and offering no remedy. The customizer hooks run strictly before that test. A customizer failing the boot is this record's own pattern: `TlsServerCustomizer` refuses an unusable cipher allowlist the same way.

Five states are refused, and each refusal names the offending configuration and the ways out:

* *No key material is declared anywhere, and the exposure strategy is not `enabled`.*
* *A named TLS registry bucket is selected for which no key material is declared.* This is almost always a typo in the name, or a bucket nobody populated.
* *`enabled` together with declared server key material for that listener.* A listener cannot both serve cleartext and terminate TLS.
* *`enabled` together with `tls.mtls.enabled`.* A gateway that terminates no TLS can verify no client certificate, so the declared requirement would be silently inert.
* *`enabled` together with a non-empty `tls.passthrough_sni`.* The front listener claims the public TLS port, which a plain-HTTP application port contradicts.

An explicit `enabled` stands the first two refusals down, in silence. Those two are the absence cases, and absence is what the opt-in may declare. It does not stand the last three down: each names a second declaration that means something only on a listener that terminates TLS.

The gate decides from *declared* key material, the keys visible as configuration, because it runs before the listener is built. A declaration that later resolves to nothing usable passes the gate and is caught downstream: `TerminatedListenerTlsAudit` reports the *resolved* state as `ApiSheriff-121`. The gate never converts an absent declaration into a permissive posture, so this limit costs strictness, never confidentiality. The audits stay keyed on observed effective state. Only the gate, a boot refusal rather than an audit, keys on the declared view.

`DeclaredKeyMaterialKeys` is the one shared vocabulary of declared keys, and the gate and both audits read it. Every spelling the legacy `ssl.certificate.*` block accepts counts: the PEM chain, the PEM key, a keystore file and a credentials provider. A narrower set at any one site would report a plain-HTTP downgrade against a listener that terminates TLS correctly.

The two-seam count holds. The gate writes nothing to the default bucket and projects no material anywhere, and no third source exists.

== Alternatives rejected

=== Leave TLS policy in raw runtime keys

Keep the protocol floor and cipher allowlist in the runtime properties file under the runtime's own key names, with no neutral surface.

*Rejected because* those keys are inert on this gateway: the registry is consulted only when the certificate comes through it. Retaining them would preserve a surface that reads as enforcement while enforcing nothing, which is strictly worse than declaring no policy.

=== Reference the runtime's named TLS configuration directly from the gateway configuration

Let the gateway configuration carry the runtime's own TLS-configuration name, removing the projecting source.

*Rejected on the layering ground of ADR-0011.* It makes the product's configuration language depend on the framework beneath it, so a change of runtime invalidates documents the product told operators to write.

=== A second, lower-ordinal config source

Split the projection across two sources: one above the environment for keys the gateway configuration must win, one below it for keys the environment should still win.

*Rejected because* precedence then becomes a per-key property no operator can predict and no document can state without an exception table. With only policy keys projected, no key exists for which the environment ought to win, so a second source has nothing to carry.

=== Promote ports into the gateway configuration

Treat ports as part of the neutral surface, so one document describes the whole listener topology.

*Rejected on two grounds.* A projected port would outrank the deployment's own port variable at the single ordinal, which is the surprise the ordinal rule prevents. And the ADR-0017 split works by a deployment moving the terminated listener to an internal port through that variable, a topology a document-owned port could not express.

=== A bespoke key that disables management TLS by blanking the certificate

Introduce a product-specific acknowledgement key whose presence makes the projecting source emit blank management certificate paths, forcing the listener to start plain.

*Rejected because* it is a bespoke mechanism where a runtime-native one exists, and it inverts the audit relationship. The product would own a certificate-blanking trick that depends on internal runtime behaviour. The warning would key on the product's own declaration rather than on what the listener resolved, and would go quiet once the downgrade arrived by another route.

=== Refuse to boot on a management TLS downgrade

Treat plain-HTTP management as a configuration error.

*Rejected because* plain-HTTP management behind a trusted boundary is a legitimate deployment. Refusing it pushes operators toward a worse workaround: disabling the management interface entirely, which moves health and metrics onto the TLS-terminated main router and is build-time fixed besides. A loud, effective-state-keyed `WARN` keeps the deployment possible and removes its silence.

=== A validation rule for the refused management port

Reject a `management.port` key through the configuration validator rather than in the JSON schema.

*Rejected because* the rule would be unreachable. Loading returns on the first schema failure, so a validator rule for a key the schema already rejects can never run. Declaring the key in the schema solely to refuse it puts the actionable message at the key's own location, not on a generic unknown-key error against its parent.

=== A config source that projects plain HTTP when no certificate is declared

A policy-free `ConfigSourceFactory` reads the declared certificate keys and, finding none, projects `quarkus.http.insecure-requests=enabled`, turning the runtime's boot refusal into a running plain-HTTP gateway. This would have been a third seam.

*Rejected for two independent reasons.* It can only ever be inference. The opt-in already exists and already wins, so the one capability the source adds is deriving intent from the absence of a certificate. Resolving that ambiguity toward cleartext turns a mounting mistake into a silently unencrypted gateway, the one outcome that must never be reachable without someone asking for it. Invalid or unrecognised configuration is warned about or refused, never quietly compensated for.

A configuration source is also the wrong place to refuse from. A `ConfigSourceFactory` runs wherever configuration is assembled, including the build. Code generation and augmentation initialise application configuration from the module's own properties file, where no certificate is declared and none should be. A factory that threw would fail the build of every module carrying this artifact, over a state that is correct at build time.

=== The runtime's management TLS-configuration-name key, considered and adopted

This key was first rejected on two grounds: that it can only select a TLS configuration and never disable TLS, and that it would relocate deployment certificate material into a product-declared bucket.

Both objections fail against the mechanism as it behaves, so the key is adopted as the opt-out above. Selecting a bucket with no key material *is* a disable, and the selected bucket is empty by construction, so no certificate moves anywhere. The reversal is recorded because both objections are plausible readings of the key's name, and a future reader who re-derives them would otherwise re-reject a mechanism that works.

A configuration surface earns its neutrality by being *bound*, and it earns its precedence by being *narrow*. Options that add a name without a binding, or a binding without a bounded key set, fail in one of those two directions.

== Consequences

=== Properties of the design

* Declared TLS policy is in force. The floor and the cipher allowlist reach the listener through an asserted seam.
* One document states the gateway's TLS posture, in the product's vocabulary.
* The classification makes new knobs decidable before a key is named, so the surface grows by rule.
* A single ordinal keeps precedence explainable: the gateway configuration wins for policy, the environment wins for everything else.
* The secure default keeps a real escape hatch. The management downgrade is reachable, runtime-native, settable at container start and loud.
* Ports and material stay out of the committed document, so one gateway configuration moves across environments unedited and carries no secrets.
* Plain HTTP on the terminated listener is reachable only by declaring it.

=== Accepted costs

* Two different mechanisms bind the policy. A maintainer changing the surface must know which listener a key targets and therefore which seam carries it.
* The config source parses the gateway configuration a second time, before the authoritative loader. The duplication is bounded and silent on failure, but it is a second reader that must stay in step with the first.
* The management downgrade is all-or-nothing. Health and metrics leave TLS together.
* Two doors onto one decision mean a reader of the gateway configuration alone cannot tell whether a deployment variable has selected the downgrade. The startup `WARN` on observed effective state compensates.

=== Risks

* *A future key projected outside the policy class.* A single port or key-material addition to the source would silently invert the environment's precedence. Asserting the forbidden key classes absent by name, and pinning the projected set's cardinality, make an addition a visible diff.
* *Silent HTTPS inheritance on the management interface.* Declaring a default TLS registry bucket anywhere would make management inherit HTTPS through the registry fallback. An explicit assertion that no default bucket is declared mitigates this.
* *Drift between the two readers of the gateway configuration.* Keeping the early parse narrow keeps the overlap small.
* *An operator reaching for the wrong disable.* Disabling the management interface outright is build-time fixed and moves health and metrics onto the main TLS-terminated router, producing an HTTPS probe endpoint rather than a plain one. The documentation names the trap where it documents the opt-out.
