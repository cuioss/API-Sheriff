// adr-metadata
// summary: The forward block -- declarable at endpoint and route, the nearest declared one taken whole per ADR-0067 -- resolves one of three forward modes per dimension: a positive-list when headers_allow / query_allow is declared, a negative-list when headers_deny / query_deny is declared, and forward-all when neither is. The boot refuses both lists for one dimension. Deny-by-default lives at the URL layer rather than at the forward stage, and a @Nullable list per ADR-0033 carries the absent-versus-declared-empty distinction the three modes rest on.

== Status

Accepted

== Decision

=== The question

The forward stage decides which client headers and query parameters reach the upstream. It once
offered one mode: an allow-list, with an absent list meaning "nothing crosses". The documentation
called this the gateway's deny-by-default posture. This record settles where that guarantee lives
and how an operator states what crosses inside an authorised route.

Three facts force the decision:

* *The guarantee sat at the wrong layer in the documentation.* The URL layer enforces
  deny-by-default: a request that matches no route gets `NO_ROUTE` and reaches no upstream. The
  forward stage runs after route selection and authorisation. Loosening it moves the enumeration
  burden and leaves the boundary where it was.
* *The enumeration burden bought no security.* An operator with a normal REST upstream had to list
  `Accept`, `Accept-Encoding`, `Accept-Language`, `Content-Type`, `Range` and every conditional
  validator. None of them is a credential. Operators wrote long lists that drifted from what the
  upstream needed, or they listed broadly and hid the permissive intent.
* *Several modes need absence as a state.* "The operator declared no list" and "the operator
  declared a list naming nothing" select different behaviour. A model that normalises absent to
  empty cannot express the difference.

=== Three forward modes per dimension

The `forward` block resolves one forward mode for headers and one for query parameters, each from
its own keys:

* *Positive-list:* `headers_allow` or `query_allow` is declared. Only the named entries cross.
* *Negative-list:* `headers_deny` or `query_deny` is declared. Everything crosses except the named
  entries.
* *Forward-all:* neither key is declared for that dimension. Every client entry crosses.

The dimensions need not agree. A route may run a positive-list on headers and forward-all on query
in one block, because the two answer different questions.

Each mode selects among client-controlled entries only. "Everything" means everything the gateway
does not own itself:

* The gateway-owned header sets bound every mode, and no list re-admits a member, with one
  deliberate exception. Forward-all is safe only because these sets withhold the dangerous names
  structurally. They and their membership rule are the subject of
  link:0037-The_gateway-owned_header_sets_are_enumerated_per_direction_and_bounded_by_knowledge.adoc[ADR-0037].
* The gateway-understood protocol headers cross without being named.
* No mode decides about `Cookie`. It crosses only as the `cookies` policy block admits it.
* The client copy skips the regenerated forwarding headers in every mode. Forward-all therefore
  cannot carry a spoofed `X-Forwarded-For` to an upstream.

=== The boot refuses both lists for one dimension

The two lists are mutually exclusive. A route that names both has not expressed a stricter policy.
It has expressed an ambiguous one, and any resolution would guess at intent. `ForwardingRules`
reports the conflict, so the boot refuses before the gateway serves traffic. The operator sees a
boot refusal rather than a routing behaviour to infer.

=== Declarable at endpoint and route

[[amendment-a1]]
The block is declarable on a route and on an endpoint, and it follows the rule of every policy block
(link:0067-Every_policy_block_is_one_declaration_resolved_nearest_declared_scope_wins_with_whole-block_replacement.adoc[ADR-0067]).
A route runs its own `forward` block when it declares one, else its endpoint's. The winning block is
taken whole. A route block therefore replaces the endpoint block entirely: a route naming only
`headers_allow` drops an endpoint `query_deny`. With neither declared, both dimensions are
forward-all.

The block has no anchor or gateway policy scope. Forward filtering is upstream-specific, and the
endpoint is the policy scope that owns the upstream.

The boot applies both of its refusals at each policy scope:

* An endpoint block that declares both lists of one dimension is refused, as a route block is.
* A `token_relay: false` route whose effective block re-admits `Authorization` through
  `headers_allow` is refused, whether the block is the route's or the endpoint's.

The endpoint and route blocks live in one endpoint file with one owner. A route that replaces its
endpoint's block therefore gets no boot WARN.

=== Deny-by-default is documented where it lives

The forward stage's documentation, and the architecture and threat-model text about it, state two
facts. A request that matches no route reaches no upstream. The `forward` block chooses a forward
mode inside an authorised route.

The authorization boundary is unchanged: no request reaches an upstream it could not reach before.
Forwarding exposure inside that boundary did change. A route that relied on the old allow-list-only
default now sends an authorised request's headers and query parameters upstream. Relocating the
documentation is a correction. Broadening the default is a behavioural change, recorded under
<<_consequences>>.

=== Absent is not empty

The four list components of `ForwardConfig` are `@Nullable List<String>`:

* `null` means the operator declared no list for that dimension.
* A declared empty list exists and names nothing. `query_allow: []` is a positive-list that admits
  nothing, which is the opposite of an absent `query_allow`.

The canonical constructor deliberately does not normalise `null` to `List.of()`. Normalising would
erase the distinction and silently turn every "admit nothing" route into a forward-all route. Absence
is a `@Nullable` type rather than a stored `Optional`, following
link:0033-Absence_in_the_production_type_model_is_a_Nullable_type_not_a_stored_Optional.adoc[ADR-0033].
`set_headers` normalises absent to empty, because it carries no mode semantics and has no distinction
to lose.

=== The application order encodes a precedence rule

`ForwardPolicyStage` merges in this order:

. the mode copy, the never-forward strip and, where `not_modified` requires it, the withheld
  conditional validators;
. the rebuilt `Cookie`;
. the gateway-understood protocol set;
. `set_headers`;
. the regenerated forwarding headers;
. the mediated session bearer.

Two rules explain every step:

. *Operator configuration beats client input.* `set_headers` merges after everything sourced from
  the request, so a client value never overrides an operator's explicit one.
. *Gateway-owned transport truth beats operator configuration.* Regeneration and the mediated bearer
  merge after `set_headers`, with the bearer last. The upstream therefore sees the gateway's account
  of the connection and only the mediated credential.

The order needs a map that treats field names the way HTTP does. The outbound map is keyed
case-insensitively, matching RFC 9110 field-name semantics. A later step therefore replaces an earlier
value however either step spelled the field. Otherwise an inbound `content-type` and an operator's
`Content-Type` both reach the upstream, and a lookup by either spelling still finds a plausible value.

=== The boundary with ADR-0047

This record owns which client entries cross.
link:0047-The_security_filter_validates_the_raw_query_it_forwards.adoc[ADR-0047] owns the form in
which the query is validated and forwarded, and the spelling the query lists compare. The two records
stay apart. `query_allow` and `query_deny` select a pair under the forward mode this record defines,
and they compare the spelling ADR-0047 defines.

== Alternatives rejected

=== Keep the allow-list-only model and document it better

Leave the single mode in place and fix only the claim about where deny-by-default lives.

*Rejected because* it corrects the description and keeps the cost that motivated the review. The
operator still lists `Accept` and `Content-Type` to make an ordinary upstream work. The operator still
cannot say "everything except this one header".

=== Add a negative-list and let the two compose

Allow both `headers_allow` and `headers_deny` on one dimension. Apply the allow-list first, then
subtract the deny-list.

*Rejected because* the composition has no unambiguous reading. With disjoint lists the subtraction does
nothing. With overlapping lists it is the allow-list written with extra steps. A name on both lists is
exactly where two operators would predict different behaviour. A boot refusal turns that silent
ambiguity into a visible error.

=== Make forward-all an explicit opt-in keyword

Require `forward: all` rather than inferring forward-all from two absent lists.

*Considered seriously, and rejected on the migration.* An explicit keyword is more legible in isolation.
But the absent state must still mean something, and every candidate meaning is worse:

* Absent as the old deny-all keeps the enumeration burden on the routes that need it least, whose
  authors never wrote a forward block.
* Absent as an error forces a `forward` block onto every route of every existing configuration.

The chosen reading makes the common case free. Its documented cost is that omission selects the mode.

=== Model the absent list as an empty list plus a separate mode enum

Normalise `null` to `List.of()` and carry an explicit `headers_mode` enum beside it.

*Rejected because* it stores one fact twice and lets the two copies disagree. `headers_mode: allow` with
an empty list and `headers_mode: none` with a populated list are both representable. Neither has a
meaning, and a validator would have to forbid states the type model should not admit. The `@Nullable`
list has exactly the three states the behaviour has.

The rejected options fall into two classes: those that keep the enumeration burden, and those that add a
second representation of the mode. The decision keeps one representation and moves the burden to the
gateway.

== Consequences

=== Properties of the design

* An operator states a forward mode rather than enumerating HTTP mechanics. A normal upstream behind an
  authorised route needs no `forward` block.
* The negative-list expresses "everything except these", which is what an operator withholding one
  internal header means.
* A reader looking for the deny-by-default guarantee finds the mechanism that enforces it.
* A route need not over-constrain query parameters to constrain headers.
* An ambiguous route gets a boot refusal rather than a guessed behaviour.

=== Accepted costs

* Three modes are more surface than one. A reader must know which mode a route resolves, and absence
  selects the mode, which the declared YAML cannot show.
* Forward-all makes the gateway-owned header sets load-bearing. Under an allow-list-only model the
  operator's enumeration masked an omission from those sets. Under forward-all the omitted name crosses.
  The sets are therefore a security surface of their own.
* Every consumer of a `@Nullable` list must distinguish `null` from empty. A consumer that treats them
  alike silently reintroduces the bug the model prevents.

=== Risks

* *A configuration with no `forward` block means forward-all.* This changes behaviour for any route that
  relied on the old allow-list-only default. A search for identifiers cannot find it, because the route
  expresses its mode by omission. A review of fixtures and examples must check what they do not say.
* *A later normalisation re-collapses the model.* A `null`-to-empty normalisation anywhere in the
  configuration pipeline turns every declared-empty positive-list into forward-all. Tests assert the
  distinction at the record and at the stage.
* *A case-sensitive outbound map breaks precedence quietly.* The failure is a duplicate header at the
  upstream, not an exception, and a test of `get("Content-Type")` still passes. The tests therefore
  assert the cardinality of each field name.

=== The rule for similar surfaces

A default that is stricter than its layer needs costs operator effort and buys no safety. That cost shows
up as long configuration files rather than as incidents. Before loosening such a default, establish which
layer enforces the guarantee. If another layer does, the loosening corrects the documentation and adds a
convenience. If this layer does, it is a real trade and needs its own argument.

A three-state setting whose third state is absence needs a type that carries absence. Where a distinction
selects behaviour, it belongs in the type, and a test fails when a later normalisation removes it.
