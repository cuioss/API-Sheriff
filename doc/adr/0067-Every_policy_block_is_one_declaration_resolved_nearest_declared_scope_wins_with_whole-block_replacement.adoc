== Status

Accepted

This decision is the one resolution behind
link:0007-anchor-scoped-policy.adoc#_policy_block_resolution_rule[ADR-0007, one declared rule resolved by `PolicyBlock`]
and the endpoint scope of
link:0036-Forward_filtering_is_a_three-mode_policy_inside_an_authorised_route.adoc#_forward_block_scopes[ADR-0036, declarable at endpoint and route].

== Decision

=== The question

ADR-0007 states one inheritance rule for the gateway's policy blocks: `gateway -> anchor -> endpoint -> route`, every step replacing the whole block. A rule stated once and implemented once per block, with a second copy in the configuration validator, carries three costs:

* *Two resolutions can disagree.* A boot refusal judges a route through the validator's copy while the route runs the builder's. Nothing makes them agree, and a scope added to one would not reach the other.
* *Adding or widening a block is unmeasured work.* The record component, both JSON schemas, the native-image registration, the documented array-key inventory and the chain must all move together, with no list of the places.
* *A newly declarable scope can bypass a boot refusal.* Several boot rules do not resolve a block. They enumerate declarations (`route.forward()`, a stream over anchors and routes). A scope such a reader does not name is a scope at which a declaration is never checked.

Every existing chain already obeyed nearest-declared-wins with whole-block replacement. Normalising the blocks needed no scope removed and no change to what a booting configuration means. It needed one declaration per block, one resolver and an explicit decision per block about its scopes.

*The decision:* every policy block is one `PolicyBlock` descriptor, and one generic resolver applies the rule to every block.

=== One descriptor per block, one resolver for all of them

A descriptor carries:

* the YAML key the block is declared under;
* the scopes it is declarable at, each with the accessor reading the declaration there;
* the one "is declared" test every block shares: `null` and an empty list are both not declared;
* its fallback when no scope declares it: a fixed value, no block or a boot refusal;
* its override-WARN opt-in.

The resolver walks the scopes nearest first and returns the first declaration, and it never merges two. The route's anchor is resolved in one place too: the route's own `anchor`, else its endpoint's. The route-table builder and the configuration validator both resolve through the descriptors, so the posture a boot refusal judges and the posture the route table materializes come from the same code.

The descriptors live in the framework-free configuration package, so the offline validation resolves blocks as the boot does (link:0061-Offline_configuration_validation_is_a_pre-boot_flag_on_the_gateway_binary_over_the_boots_own_pipeline_seam.adoc[ADR-0061]).

=== The scope set of each block

The operator decided every block's scopes, each on the default recommended at outline:

[cols="2,3,2,6", options="header"]
|===
| Block | Declarable at | Change | Security consequence / why the set stops there

| `auth`
| anchor, endpoint, route
| none
| No gateway scope: a gateway-wide `auth` would hand every unanchored route a posture and turn the fail-closed "no auth resolvable = boot refusal" into a default.

| `allowed_methods`
| gateway, anchor, endpoint
| none
| No route scope: a route already narrows its verbs with `match.methods`, which must be a subset of the effective list. A route-level allowlist would be a second way to say the same thing.

| `security_filter`
| anchor, endpoint, route
| *+ endpoint*
| Removes per-route repetition inside an endpoint file. An endpoint block can replace and relax an anchor block whole. The override WARN announces that, and the `minimal` refusal bounds it. No gateway scope: `security_defaults` owns the gateway-wide profile and the pre-route baseline seeded from it.

| `security_headers`
| gateway, anchor
| none
| The browser response posture is a property of the namespace. A narrower block would let one endpoint or route drop HSTS or frame-deny for part of an anchor's namespace. `cors` stays in the gateway block alone (ADR-0007).

| `upstream_defaults`
| gateway, endpoint
| none
| Upstream behaviour belongs to the upstream, which the endpoint owns through its `base_url`. An anchor is a namespace, not an upstream. The route keeps its field-level toggles.

| `forward`
| endpoint, route
| *+ endpoint*
| One deny or allow list per upstream instead of per route. A route block replaces the endpoint block whole and can drop an endpoint `query_deny`. Both sit in one endpoint file with one owner, so the replacement is not announced. No anchor or gateway scope: forward filtering is upstream-specific (ADR-0036).

| `websocket`
| route
| none
| The block is valid on `protocol: websocket` routes only, and `allowed_origins` is a fail-closed per-route allowlist (link:0015-websocket-origin-failclosed-allowlist.adoc[ADR-0015]). An endpoint block would reach the endpoint's other routes.
|===

The table records the blocks this decision covered. A block added later declares its scopes in its own descriptor and appears in link:../user/anchors.adoc#_policy_block_scopes[the live scope table], which a contract test binds to the descriptors. `cookies` (link:0037-The_gateway-owned_header_sets_are_enumerated_per_direction_and_bounded_by_knowledge.adoc[ADR-0037]) is the first, declarable at all four scopes.

The net change was two endpoint-level keys. A configuration that booted before resolves as it did, because the boot refused both keys at the endpoint until then.

=== The boot readers of a widened block read the new scope

Every boot rule and boot-pipeline check that reads `security_filter` or `forward` covers the endpoint scope. Otherwise an endpoint-level declaration would bypass refusals that hold on a route. The three readers that enumerate declarations are extended, each pinned by a test:

* the token-relay conflict, a `token_relay: false` route whose `forward.headers_allow` names `Authorization`, reads the resolved forward block, so an endpoint-level list is refused like a route-level one;
* the forward mode-exclusivity rule also checks the endpoint-declared block;
* the framework body-size check counts every endpoint's own `max_body_bytes` as well as every anchor's and route's (link:0023-The_declared_max_body_bytes_cap_is_the_effective_one_and_a_breach_is_the_gateways_413.adoc[ADR-0023]).

The `profile: minimal` refusal needed no change, because it reads the route's resolved block through the shared resolver (link:0024-Inbound_filter_modes_minimal_is_a_partial_disable_retaining_the_body_cap_and_path_allowlist_and_is_refused_on_authenticated_and_BFF_routes.adoc[ADR-0024]).

=== The override WARN is derived from the descriptor

`ApiSheriff-101` is emitted for a block whose descriptor opts in when the route's anchor declares the block and a nearer scope, the route's endpoint or the route itself, declares it too. It is logged once per route and block.

The opt-in is the descriptor's `overrideWarn` flag. link:../user/anchors.adoc#_policy_block_scopes[The Override WARN column of the scope table] lists the blocks that set it: currently `allowed_methods`, `security_filter` and `cookies`. `auth` is excluded because weakening its floor is a boot refusal, which is stronger. `security_headers` has no scope nearer than the anchor, and `upstream_defaults`, `forward` and `websocket` have no anchor scope.

=== Two field-level fallbacks stay, as documented exceptions

* *`security_filter.profile` -> `security_defaults.profile` -> `strict`.* A resolved block that declares no `profile` takes the gateway-wide profile, never the profile of the broader block it replaced. The config side implements this once, in `RouteTableBuilder.effectiveProfile`, read by the boot posture log and the validator.
* *A route's `upstream.retry.enabled` and `upstream.not_modified.enabled`.* Each overrides that one field of the resolved `upstream_defaults` block.

=== What stays outside the rule

*The request-pipeline edge.* The edge reads the materialized route, seeds its pre-route baseline from `security_defaults` and keeps its own reading of the profile fallback for that baseline.

*The anchor auth floor.* An anchor declaring `require: bearer` or `require: session` refuses a member whose effective auth is `require: none`. The floor compares the anchor's declared `auth` block with the resolved one. `AnchorRules` reads the declared block through the anchor-scope accessor of `PolicyBlock.AUTH`. The access-to-auth matrix, the authenticated-anchor backing and the session-fallback refusal read the anchor's `auth` block from the anchor model directly.

== Alternatives rejected

=== Keep the per-block chains and add a contract test over them

A test can compare the chains with the schemas.

*Rejected because* it cannot make the validator and the route table call the same code. It guards the symptom and leaves two resolutions in place.

=== Merge blocks across scopes key by key

A nearer block would override only the keys it declares.

*Rejected for the reason ADR-0007 records:* every surveyed gateway that survived overrides whole blocks, and key-level merging makes a nearer scope unable to remove a broader key.

=== Give every block every scope

Uniform and simple to state.

*Rejected block by block in the table above.* A gateway-level `auth` turns a boot refusal into a default, an endpoint-level `security_headers` lets one team drop HSTS inside another's namespace, and an endpoint-level `websocket` block reaches routes that are not WebSocket routes.

=== Drop the two field-level fallbacks for a uniform rule

*Rejected because* each prevents a silent change. Dropping the profile fallback would make a block that declares no `profile` resolve `strict` whatever the gateway declares, which is tighter but a silent change to deployments, and would leave the route's profile disagreeing with the pre-route baseline. Folding the upstream toggles into a route-scope `upstream_defaults` block would, under whole-block replacement, reset the toggle the route did not mention.

== Consequences

=== Properties of the design

* The boot validator and the route table cannot resolve a block differently, because there is one resolution.
* Where a block is declarable is a fact recorded once, in its descriptor. A contract test binds it to both bundled schemas and the user-documentation scope table in either direction.
* Adding a block is a listed set of steps, each with the test that catches a missed one (link:../development/README.adoc#_adding_a_policy_block[Contributor guide, Adding a Policy Block]).
* One flag per block replaces a hand-kept list for the override WARN.

=== Accepted costs

* Two endpoint-level keys widen the configuration surface. An operator reading an endpoint file has one more place a route's filter or forward posture can come from.
* An endpoint-level `security_filter` can relax an anchor's posture for every route of the endpoint at once. The WARN makes that visible and does not refuse it.

=== Risks

* *A boot reader that enumerates declarations stays blind to a new scope.* A reader written later that enumerates instead of resolving would not be caught by any contract test. The contributor guide names the obligation.
* *Whole-block replacement drops what a broader block declared.* A route `forward` block naming only `headers_allow` drops an endpoint `query_deny`. That is the rule working as stated, accepted because a merge would make a nearer scope unable to relax a broader one.
