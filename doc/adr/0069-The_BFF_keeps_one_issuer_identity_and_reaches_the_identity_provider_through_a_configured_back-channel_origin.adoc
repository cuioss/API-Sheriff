== Status

Accepted

== Decision

=== The question

A BFF talks to its identity provider over two channels that need not reach it at one address. The *front channel* is the browser: it is redirected to the
authorization and end-session endpoints at the address the identity provider publishes to users. The *back channel* is the gateway: it fetches discovery, pushes
authorization requests, exchanges codes, and refreshes and revokes tokens. In a containerised or segmented deployment the gateway often cannot use the browser-facing
address, while an address it can reach is invisible to the browser.

The identity provider also has an identity, its issuer identifier. Three rules hold it to one exact string:

* RFC 8414 section 3.3: the `issuer` in the discovery document is identical to the identifier the discovery URL was built from.
* RFC 9068: the `iss` of an access token equals the discovered issuer.
* RFC 9207: the `iss` returned with the authorization response equals the metadata issuer, which FAPI 2.0 requires.

This record settles how a deployment whose two channels need two addresses satisfies three exact-match rules that admit one. A narrower question follows from
sender-constrained tokens (ADR-0058). A DPoP proof names the URL of its request (`htu`). When the gateway dials another address than the advertised one, the proof and the
identity provider's comparison must agree on the URL. Two further questions keep the answer verifiable: which Keycloak a deployment and the test stacks run against, and how a
release states it.

*The decision:* `oidc.issuer` is the one identity. The split is transport, not identity. The browser goes to the endpoints the identity provider advertises, and the gateway reaches
the identity provider's own origin through `oidc.back_channel_origin`. No issuer check is relaxed.

=== One issuer identity, two transport paths

The gateway compares the discovery `issuer`, the token `iss` and the authorization-response `iss` with `oidc.issuer`, the browser-facing identifier. The browser goes to the advertised
authorization and end-session endpoints, unchanged.

The gateway sends its own calls to `oidc.back_channel_origin` with path and query unchanged: discovery, the pushed authorization request, the token endpoint (code exchange and refresh) and
RFC 7009 refresh-token revocation. The `ApiSheriff-138` boot record names the same list. The gateway never dials the identity provider's userinfo endpoint: its own `oidc.user_info.path`
endpoint answers from the session's validated ID-token claims (`IdTokenClaimProjection`).

The mapping is the engine's single origin mapping, `token-sheriff-client`'s `backChannelOrigin` (introduced in 0.9.7, DPoP `htu` corrected in 0.9.8). The engine re-targets only an advertised
endpoint on the issuer's own origin. The value goes to the one client configuration every scoped variant reuses (ADR-0048), so all scope sets share it.

JWKS stays on `token_validation.issuers[].jwks.url`, which names the reachable key-set address directly. The 0.9.8 discovery-issuer enforcement in the validation library has no effect here. The
gateway sets the issuer identifier identically on the issuer configuration and the loader. Every JWKS source is a direct `jwks.url` or a file, never well-known discovery: `RetryingJwksLoader` reports its
delegate's JWKS type, and no production source is of the well-known kind.

=== Boot rules for the origin

* *Origin only.* An absolute `http` or `https` URI naming a host, with an optional port and at most one trailing `/`. The boot refuses a path, query, fragment or user-info component.
* *Fixed-text refusals.* A boot refusal never echoes the configured value, which may carry a credential in its user-info.
* *https only*, unless `oidc.back_channel_allow_insecure_http: true` is set. The boot refuses the opt-in when no origin is declared or the origin is `https`. An admitted `http` origin logs
  `ApiSheriff-138` at WARN, because the engine's `allowInsecureHttp` applies to the whole client, not only the mapped calls. This opt-in inherits that known limitation.
* *Configuration only.* The gateway never derives the origin from request data.
* The gateway contacts the mapped host under `egress_tls.oidc_verify_hostname` and `egress_tls.oidc_tls_profile`, which the engine evaluates against the host actually contacted (ADR-0045).

=== No private-address rule

The boot does not refuse an origin for naming a private, loopback or link-local address. The key exists to name an internal host. Construction closes server-side request forgery instead: the origin
comes from configuration alone, and the engine re-targets only endpoints advertised on the issuer's origin.

*Residual.* The gateway contacts an endpoint the metadata advertises on a foreign origin as advertised. That is the engine's existing behaviour, and this key does not widen it, except under the
cleartext opt-in.

=== The Keycloak side

The identity provider publishes one static identity: a full-URL `KC_HOSTNAME` (the published `https://localhost:1443` in this repository's stacks), no realm `frontendUrl` and no
`hostname-backchannel-dynamic`. Every advertised endpoint, revocation included, then lies on the issuer's origin and is mapped. A realm `frontendUrl` would override the static hostname for every
advertised URL, so no realm import declares one. `BackChannelOriginActivationWiringTest` asserts it.

=== The DPoP htu contract

A mapped call's DPoP proof names the URL the engine actually dialled (upstream ADR-0015, _DPoP htu names the back-channel URL actually contacted_, token-sheriff 0.9.8). For this gateway that is the
token endpoint's first attempt and its `use_dpop_nonce` retry, on the code exchange and the refresh. Upstream applies the same rule to the engine's userinfo call, which this gateway never makes. Keycloak
receives and compares that URL: it derives the URL it checks `htu` against from the request, not from its configured hostname.

*Known limitation (residual).* The contract does not cover an identity provider that compares `htu` with a configured public URL. `back_channel_origin` is issuer-wide and all-or-nothing, so such a
deployment must not set it for a DPoP-constrained client.

*How the contract was found.* The first attempt ran on the engine release that kept the advertised URL in `htu`. Every real-Keycloak BFF login in the Failsafe suite (79 tests) got a callback 400, and
Keycloak logged `CODE_TO_TOKEN_ERROR`, `invalid_dpop_proof`, `DPoP HTTP URL mismatch`. The stub identity providers stayed green because neither checked `htu`. Both now judge every proof's `htu` and `htm`
against the URL the request was received on (`StubIdentityProvider`, `StubIdentityProviderRig`). That regression class is now red in the stub suites too.

=== The Keycloak pin policy

* *One tag and one digest*, identical in `integration-tests/docker-compose.yml` and `deployment/compose-sample/docker-compose.yml`. `KeycloakImagePinWiringTest` guards the single pin and the Dependabot
  entry, and asserts no version number.
* *One Dependabot `docker-compose` group*, `keycloak`, moves both pins in one pull request. The organisation's sweeper auto-merges minor and patch bumps only once `integration-tests / conclusion` is
  green. It never auto-merges a major bump.
* The demo Playwright suite sees a bump only after merge. The compose sample sees it in the bump pull request: the `integration-tests` job brings the sample up after the integration suite and runs its BFF
  login check on the image built from the pull request.
* *Every release's notes name the Keycloak version* the release was verified against, derived from both pins at the release tag (the release runbook, Step 11).
* *Documentation names no Keycloak version number* for behaviour a suite pins. It names the pinned image (`integration-tests/docker-compose.yml`), because the Dependabot group moves the pin and a number in
  prose goes stale. Dated observations made on an earlier image stay dated.

=== Whether the gateway fronts the identity provider

That is not part of this decision. No shipped topology fronts the identity provider, and the gateway ships none. A variant serving it under an `/auth` prefix is held and has no implementation. If it lands, it
consumes the back-channel origin, because the gateway would otherwise dial its own listener for discovery. Its exposure must be an allowlist, never a catch-all: `/realms/`, `/resources/`, `/.well-known/` and
`/lb-check` are in, and `/admin/`, `/realms/master/`, `/metrics`, `/health` and the management port are out. That allowlist is the rule the variant must follow and is unproven here.

== Alternatives rejected

*Browser-side DNS overrides* (`--host-resolver-rules`, `/etc/hosts`) make the internal name resolve in the browser.
*Rejected because* they work only where the test rig controls the browser's resolver, so the suites would prove an arrangement no operator can deploy.

*Rewriting the discovery document in flight* replaces the advertised endpoints with internal ones.
*Rejected because* it breaks the RFC 8414 section 3.3 identity check by construction: the document the gateway validates is no longer the one the identity provider published.

*Two issuer values*, a public one for the browser and an internal one for the gateway.
*Rejected because* they break `iss` validation and RFC 9207, which is what the exact-match rules exist to prevent.

*A separate discovery URL or per-endpoint overrides.*
*Declined upstream because* one declared origin mapping covers discovery and every back-channel call with a single rule. A list of overrides is one setting per endpoint, each able to drift.

*Keycloak's dynamic back-channel hostname as the mechanism.*
*Rejected because* it leaves `revocation_endpoint` on the external origin (observed on Keycloak 26.5.7) and couples the gateway's correctness to identity provider behaviour the gateway cannot check.

*Validating `iss` against the internal URL while the browser uses the public one* was the previous arrangement, and the one that reads most plausible.
*Rejected because* the identity the gateway checks then differs from the identity the user authenticated against, the two-issuer failure in another form.

*A `Host`-header rewrite* keeps the advertised URL in `htu` and sends a `Host` header naming the public authority.
*Rejected because* the JDK HTTP client sends that restricted header only under the JVM-wide `jdk.httpclient.allowRestrictedHeaders` property. That process-global switch changes what every other client
in the process may send, lives in launch arguments no configuration review sees, and makes `Host` disagree with the TLS SNI and the verified certificate.

*An opt-in for the dialled-URL `htu`*, a setting that selects the advertised URL.
*Rejected upstream (ADR-0015) because* it adds configuration surface, documentation and a test matrix for a branch no known deployment needs. The primary target compares against the received request,
and RFC 9449 section 4.2 defines `htu` as the request's target URI. The unused branch is also a misconfiguration vector: selecting it against a request-comparing server reproduces the
`DPoP HTTP URL mismatch` it would exist to avoid.

*An unpinned or per-file Keycloak tag.*
*Rejected because* the two stacks could drift apart, and a release could not name what it was verified against.

*Gateway-side metadata resolution*: the gateway fetches and resolves the discovery document itself, for example from the internal URL, and hands the engine resolved endpoints as a stand-in for the
engine option.
*Rejected because* the engine owns discovery. `backChannelOrigin` already fetches discovery, keeps the RFC 8414 section 3.3 issuer check against `oidc.issuer`, re-targets only endpoints on the issuer's own
origin, and signs every mapped call's DPoP `htu` for the URL it dialled. A gateway-side resolver would re-implement that check and rule outside the engine, split one transport rule into two places
that can drift, and still leave the engine signing proofs for endpoints it did not choose.

The rejected options share one flaw. Each relaxes the identity the exact-match rules protect, or moves the transport rule somewhere the engine that applies the identity cannot see it.

== Consequences

=== Properties of the design

* One issuer identifier serves the browser, the tokens and the metadata, so every exact-match rule holds with no deployment-specific relaxation.
* A gateway that reaches the identity provider at an internal address needs one configuration key and no DNS trick. The test stacks run without resolver overrides, so the suites prove what an operator deploys.
* Every back-channel call, its TLS posture and its DPoP proof name the one host actually dialled.
* The Keycloak version a release was verified against is a derived, stated fact, and the two stacks cannot drift apart unnoticed.

=== Accepted costs

* The origin mapping is issuer-wide and all-or-nothing. A deployment cannot map some calls and not others.
* The cleartext opt-in widens the whole engine client, not only the mapped calls.
* An identity provider that compares `htu` with a configured public URL cannot use the mapping with a DPoP-constrained client.

=== Risks

* The gateway dials an endpoint advertised on a foreign origin as advertised.
* `.github/dependabot.yml` is on the organisation's docs-only ignore list. A change to it alone triggers neither workflow, so `KeycloakImagePinWiringTest` runs only locally or on the next build-triggering change.
* The on-demand APISIX comparison lane cannot validate tokens. `integration-tests/src/main/docker/apisix/apisix.yaml` discovers at `https://keycloak:8443/realms/benchmark/.well-known/openid-configuration` and
  validates through the discovered `jwks_uri`. Under a static external hostname that URI is `https://localhost:1443/...`, unreachable from the APISIX container. Every Keycloak 26.x line applies the static
  `KC_HOSTNAME`. `apisix.yaml` stays unchanged, restoring the check is follow-up work, and no gated suite is affected.
* A future Keycloak that compared `htu` with its configured hostname would turn the real-Keycloak BFF login suites red. That failure is loud, not silent.

=== Verified on

This section states what was observed, not the current pin, which `integration-tests/docker-compose.yml` holds. Verified on `quay.io/keycloak/keycloak:26.8.1@sha256:79c623a2...d244`, the local image label matching
the digest pinned in both compose files:

* *Failsafe* (`verify -Pintegration-tests`): green, 312 integration tests, no failure, error or skip. Every BFF suite named here ran: login (`BffSessionLoginIT`, `BffCookieSessionIT`), refresh (`BffTokenRefreshIT`,
  `BffCookieRefreshIT`), refresh-token reuse (`BffRefreshReuseIT`), logout (`BffLogoutIT`), back-channel logout (`BffBackchannelLogoutIT`), FAPI controls (`BffFapiControlsIT`, `BffGeneratedKeysIT`, `BffClientSecretModeIT`),
  scope parity (`BffSessionScopeParityIT`), TLS relaxation (`BffTlsRelaxationIT`) and bearer validation (`BearerValidationIT`), plus the stub-rig suites under the `htu` check.
* *Playwright* (the demo end-to-end suite): 28 passed, 14 session-server and 14 session-cookie, without `--host-resolver-rules`.
* *The compose sample* came up healthy from empty volumes and passed its readiness gate, with the documented local image override because the published gateway image is amd64-only and the host was arm64. A password-grant
  token carried `iss=https://localhost:1443/realms/sample`, exactly the configured issuer, while readiness implies the JWKS loaded from `keycloak:8443`.
* *Falsification of the `htu` case.* The unit-level proof that both token-request proofs of a re-targeted code exchange name the URL actually contacted compiles against token-sheriff 0.9.7 and goes red at its assertion. On
  0.9.8 it is green.

Observations made on Keycloak 26.5.7, among them that the dynamic back-channel hostname leaves `revocation_endpoint` on the external origin, stay dated as 26.5.7 observations. None was re-observed on 26.8.1.

Version strings in the documentation follow the pin policy above. A statement a green suite pins names the pinned image. A dated observation no test asserts stays dated: the client secret Keycloak generates for a client imported
without one, the realm settings first established on a throwaway 26.5.7 container, and the observations ADR-0058 links.
