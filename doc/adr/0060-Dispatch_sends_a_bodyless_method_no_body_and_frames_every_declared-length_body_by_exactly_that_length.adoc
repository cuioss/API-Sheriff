== Status

Proposed

== Context

The gateway settles HTTP framing at the edge because framing decides where one message ends and the
next begins, and a gateway that disagrees with its upstream about that boundary is the precondition
for request smuggling. The framing gate does this before route selection, and it can only decide on
what has arrived by then: the request line and the headers.

On HTTP/1.1 the headers are the whole framing story. A message body exists exactly when
`Content-Length` or `Transfer-Encoding` says so, so a gate that reads those two headers sees every
body the connection will carry. HTTP/2 breaks that equivalence. A body is carried by DATA frames,
and `content-length` is optional; when present, it asserts the content length but does not delimit
the DATA frames. A stream can carry body bytes that
no header announces, and a stream can also end with an empty final DATA frame that carries no bytes
at all. At the moment the gate runs, the two are indistinguishable: neither has declared anything,
and the frames that tell them apart have not arrived yet.

That puts the rule "a bodyless method carries no body" at a choice point. The gate cannot enforce it
for an undeclared body without guessing from absence, and the body is consumed long after the gate
has finished. The question is which component owns the guarantee that no body bytes reach the
upstream on a bodyless method.

A second, related question sits at the same seam. The client's `Content-Length` is in the gateway's
request-direction never-forward set: it is a claim about the client's message, and the dispatch path
re-establishes the framing of what it actually sends. When dispatch streams a body without a length,
the transport frames it as chunked. A request that arrived with an unambiguous declared length then
reaches the upstream in a different framing from the one the gateway validated, and the upstream
learns the message boundary from a mechanism the gateway never checked.

Both questions come down to the same thing: where the gateway's validated view of the body becomes
the upstream's view of it.

== Decision

*The framing gate decides on headers; dispatch owns what actually crosses to the upstream. A
bodyless method is sent with no body and refused on its first body byte, and a declared length
frames the forwarded body by exactly that length. One rule per question, on every protocol.*

=== A bodyless method is sent with no body, and its first body byte refuses it

A `GET` or `HEAD` without a positive declared `Content-Length` is dispatched with no body at all: the
inbound stream is never handed to the upstream request. A watcher consumes the inbound stream
instead. Its first chunk carrying at least one byte, whatever its size, records a
`SECURITY_FILTER_VIOLATION` and resets the upstream request. A zero-length chunk and the end of the
stream are not violations, so a stream ending with an empty final DATA frame is served normally.

The refusal takes the shape the gate's own framing rejection takes. While the dispatch is still
awaited, it is the dispatch's failure, answered `400` like any other framing rejection. On HTTP/2
only the offending stream ends, never the connection. If the first byte arrives after the upstream
response has been handed over for relay, the client stream is reset instead, never cleanly ended,
so a truncated response is not presented as complete. The upstream
exchange is aborted, and nothing was forwarded because the upstream request carried no body.

The rule does not test the protocol version. On HTTP/1.1 such a request carries no body bytes by
framing, so the watcher never fires there. The only effect on HTTP/1.1 is that the upstream request
carries no body instead of an empty streamed one. The property is stated once and holds everywhere:
a bodyless method never carries a body upstream, on any protocol.

A `GET` with a positive declared `Content-Length` admitted by the gateway-wide opt-in is not on this
path. It is a declared-length request and is framed as the next section describes. `HEAD` is refused
on every leg, as the gate already requires. The gateway-answered `GET` and `HEAD` actions (asset
serving, redirects, the portal and the reserved paths) never subscribe the inbound body, so they
have no body to forward and are unaffected.

=== A declared length frames the forwarded body, and the body is held to it

Every request that is not on the bodyless path and carries a checked declared `Content-Length` is
forwarded with that value as the upstream `Content-Length`. This covers the opt-in `GET`, `POST`,
`PUT`, `PATCH`, `DELETE` and a gRPC request that declares one. The transport therefore frames the
body by length and never re-frames it as chunked. "Checked" means the value the framing gate and
the `max_body_bytes` pre-check admitted. The client's own header is still never relayed: dispatch
writes the value it validated.

Because the upstream now takes its message boundary from that value, the forwarded body is held to
it exactly. The bound sits in the same streaming counter that enforces `max_body_bytes`, not in a
separate stage. A chunk that would carry the total past the declared length is not forwarded. It
records a `SECURITY_FILTER_VIOLATION` and resets the upstream request. An inbound body that ends
short of the declared length resets the upstream request as `INBOUND_BODY_ABORTED`. The upstream
never waits on, or completes, a message of another length.

A request that declares no length keeps the framing the transport chooses. The rule has no per-method
scope: one length rule covers every method.

=== Retry stays safe without special cases

A bodyless request never subscribes the inbound stream to an upstream attempt, so the stream-aware
retry gate sees it as bodyless and the request stays retryable for as long as no body byte has
arrived. A violation is a gateway rejection and is never retried.

== Consequences

=== Positive

* The bodyless-method property is a property of what crosses to the upstream, not an inference from
  headers. It holds for a body that no header declares, and it costs no false rejection of a stream
  that ends with an empty frame.
* The guarantee does not depend on a size limit. The first byte decides, so the configured body cap
  is a resource bound and not the safeguard for this rule.
* HTTP/1.1 and HTTP/2 obey one statement of each rule. There is no version branch for the two
  protocols to drift apart along.
* The length the upstream reads is one the gateway validated, and the bytes it receives match that
  length exactly. The gateway's and the upstream's view of the message boundary cannot diverge for a
  declared-length request.
* Upstreams that require a length-framed body, and the opt-in `GET` with body in particular, receive
  the framing the client sent instead of a chunked re-encoding of it.
* The framing gate keeps its pre-route, headers-only position and its HTTP/1.1 rules unchanged. The
  new guarantees are added behind it, not woven into it.

=== Negative

* The rule is split across two components. The gate refuses what the headers declare, and dispatch
  refuses what the stream carries. A reader of either component alone sees half of the property, so
  both carry the cross-reference.
* A late violation, one whose first body byte arrives after the response has been handed over for
  relay, is answered by a stream reset. The client sees a reset rather than a `400`.
* A declared-length request is now held to an exact byte count. A client whose body disagrees with
  its own declared length is refused rather than tolerated, on every route.
* Dispatch's signature carries the framing decision, so every dispatch entry point, the gRPC path
  included, has to state it explicitly.

=== Risks

* *Narrowing the rule to HTTP/2.* On HTTP/1.1 the watcher never fires and reads as dead code. A
  version check that skips it there would quietly reintroduce two rules where there is one, and the
  first transport change that lets an HTTP/1.1 request carry an undeclared body would find no guard.
* *Moving enforcement back to the gate.* A headers-time check looks simpler. It is the alternative
  rejected below, and reintroducing it as a simplification would refuse legitimate streams that end
  with an empty DATA frame while still deciding on information the gate does not have.
* *Decoupling the length header from the byte bound.* Writing the declared length upstream is safe
  only because the same stream enforces it. A refactor that keeps the header and drops the exact
  bound, for instance by moving the counter out of the forwarding stream, hands the upstream a
  boundary the gateway no longer enforces.
* *Treating the size cap as the safeguard.* A future change that admits small bodies on a bodyless
  method because the cap bounds them would trade the property for a resource limit.

== Alternatives Considered

*Reject at headers time in the framing gate.* Refuse a `GET` or `HEAD` whose HTTP/2 stream was not
ended together with its headers, keeping all framing decisions in one stage. Rejected because a
client may legally end the stream with an empty final DATA frame, so the check would refuse
conforming requests. It would also decide on absence, before the frames that tell a body from an
empty end have arrived. The gate's position before route selection is deliberate, and it is exactly
why the gate cannot see the body.

*Rely on the body cap to bound the harm.* Let an undeclared body through and treat `max_body_bytes`
as the limit on what it can do. Rejected because the cap bounds size, not presence. A bodyless method
carrying any body is the violation, whatever its size, and an upstream that receives one has already
been handed a message the gateway's framing model says does not exist.

*Apply the rule to HTTP/2 only.* Gate the no-body send on the protocol version, since only HTTP/2
can carry an undeclared body. Rejected because on HTTP/1.1 the unified rule costs nothing: the
watcher never fires, and the only change is that the upstream request carries no body. A version
branch would turn one property into two statements that can drift.

*Frame by declared length only for the opt-in `GET`.* Fix the re-framing where the opt-in introduced
the visible case and leave other methods to the transport. Rejected because the re-framing applies
to every declared-length request equally. Scoping the fix by method would leave the validated length
and the forwarded framing disagreeing for the most common body-bearing requests.

*Relay the client's own `Content-Length`.* Forward the header instead of writing a value at dispatch.
Rejected because the header is a claim about the client's message, and the gateway's header policy
withholds it for that reason. Writing the validated value and enforcing it on the stream makes the
upstream's boundary one the gateway has proven, not one it has passed along.

*Buffer the body to learn its length.* Read the whole body, then forward it with an exact length.
Rejected because the data plane streams request bodies and never buffers them. Buffering would trade
a framing guarantee for a memory exposure proportional to the body cap on every request.

The rejected options either decide too early, on headers that cannot see the body, or decide too
loosely, with a size limit, a protocol branch or a method scope standing in for the property. The
chosen position enforces each property at the one point where the gateway both knows the truth and
controls what the upstream receives.

== Generalisation

When a protocol lets a message carry content that its metadata does not announce, a check on the
metadata cannot enforce a rule about the content. It can only refuse what was announced. The
diagnostic question is: *at which point does the component both know what the message actually
carries and control what is passed on?* The rule belongs there. An earlier stage keeps the checks it
can make on what it sees. Likewise, when a component re-establishes a framing on the far side of a
trust boundary, the framing it writes should be the value it validated, and it should enforce that
value on the bytes it sends, so the downstream boundary is one the component has proven rather than
one it has only relayed.

== Amendment A1 (2026-10-14): a dispatch holding an upstream connection waits at most 10 s for request-body progress

*Dispatch owns what crosses to the upstream, and so it also owns how long it waits for the body it
forwards. A dispatch that holds its upstream connection and is reading the request body ends after
10 s without a forwarded body byte: the upstream request is reset, which frees the connection, and the
client is answered `408`.*

=== Context

A body-carrying dispatch hands the inbound body to its upstream request once the attempt has obtained
a pooled upstream connection, and it holds that connection until the exchange ends. A body that stops
arriving leaves the dispatch holding the connection while nothing crosses it: the upstream waits for
the rest of a message the gateway has no bytes for, and every upload queued behind it for a connection
of the same pool waits as well. The only bound was the upstream guard's fixed 30 s timeout
(link:0064-The_upstream_guard_is_fixed_in_the_gateway_and_a_route_declares_no_circuit_breaker_settings.adoc[ADR-0064]),
which then ended the dispatch as `UPSTREAM_TIMEOUT` (`504`). That outcome holds the connection for the
whole 30 s and attributes the wait to the upstream, which was given nothing to answer, so the breaker
counts it as an upstream failure.

=== Decision

. *What is measured.* One clock per body stream starts when the dispatch hands the body to its
  upstream request, which happens only once the attempt holds its connection, and every forwarded chunk
  restarts it. A single value therefore covers both the wait for the first body byte and every gap
  between chunks. When 10 s pass without progress, the dispatch ends as `REQUEST_BODY_TIMEOUT` (`408`,
  `INPUT_VALIDATION`) and the upstream request is reset, so its connection is free for the next
  dispatch at once.
. *What is not measured.* The wait for a pooled connection is the gateway's own queueing and comes
  before the clock starts. While the forwarding pipe has paused the body because the upstream is not
  taking data, the gap is not counted, and it restarts from the moment the pipe resumes, so the
  upstream's backpressure is never charged to the request. The clock stops when the upstream request's
  send completes, so it never runs once the response is handed over. A bodyless request never hands
  its body to an upstream request (see the decision above) and is not watched. A `protocol: grpc`
  route is not watched either: client-streaming and bidirectional calls legitimately pause between
  messages, and the forced-HTTP/2 upstream carries the call on a shared connection, so there is no
  pooled connection of its own to free.
. *How the answer ends.* The body behind the `408` was not read, so the answer ends what it arrived on,
  exactly as a framing refusal of this record does: on HTTP/2 the answer ends that stream, which is
  then reset with `NO_ERROR` through the one end rule of
  link:0066-An_HTTP2_response_answered_while_its_request_body_is_open_is_ended_once_request_data_stops_arriving_or_a_time_cap_passes_and_its_stream_is_then_reset_with_NO_ERROR.adoc[ADR-0066],
  and the connection carries on; on HTTP/1.x the answer carries `Connection: close` and the
  connection is closed once it has been written.
. *Breaker and retry.* The expiry takes the body stream's single abort claim, as a body over the cap or
  a body beyond its declared length does, and reaches the guard as a gateway rejection. The breaker
  skips it and records it as a success, and the retry predicate refuses it -- the treatment of every
  client-ended dispatch. Whichever abort claims the stream first is the outcome: a cap breach, a framing
  refusal, an inbound failure or the gateway's own reset that comes first stops the clock, and a later
  expiry changes nothing.
. *A fixed value, below the guard.* The 10 s value is a gateway constant with no configuration key or
  system property, following ADR-0064's line that the upstream guard it sits under is a fixed policy
  of the gateway. It is shorter than the guard's 30 s timeout, so a dispatch whose body stopped
  arriving is ended as the request's before the guard would end it as the upstream's, and it is long
  enough that a sender pausing between chunks on a slow link is not affected. The guard's 30 s timeout
  still bounds every dispatch as a whole, a steady upload included.
. *Recording.* `INFO` `ApiSheriff-23` records the expiry with the route id and the fixed timeout only,
  latched per route so the log holds one record per route; `sheriff_errors_total` counts every
  occurrence under `event="REQUEST_BODY_TIMEOUT"`.

=== Alternatives considered for the amendment

*Leave the guard timeout as the only bound.* Rejected because it holds the connection for 30 s per
stalled dispatch, answers the client `504`, and counts an upload that stopped as an upstream failure
in the breaker's window.

*Make the bound configurable.* Rejected for the reason ADR-0064 gives for the guard: the value has to
stay below a guard timeout no route can see or change, and no deployment choice makes a longer wait
on a body that is not arriving correct.

*Bound the whole body by a deadline.* Rejected because a slow but steady upload that keeps arriving
would be cut off, while the problem is a body that has stopped. Measuring progress ends only the
dispatch that waits for nothing.

*Start the clock with the dispatch.* Rejected because the wait for a pooled connection would then be
charged to the request, and a queue behind busy connections would end uploads that never had a chance
to send.

=== Consequences of the amendment

*Positive.*

* A dispatch whose body stopped arriving frees its upstream connection after 10 s instead of 30 s,
  and the uploads queued behind it obtain the connection then.
* The outcome is attributed to the request: the client is answered `408`, and the breaker no longer
  counts a stalled upload as an upstream failure.
* An upload that keeps arriving, however slowly, and an upload throttled by its upstream are never cut
  off by this bound.

*Negative.*

* A client that pauses its upload for longer than 10 s between two chunks, while the gateway is
  reading it, is answered `408`, and on HTTP/1.x it loses its connection.
* The body stream carries a timer and the state to judge it. One timer is pending per stream at a
  time; a forwarded chunk only records when it arrived.

*Risks.*

* *Moving the start of the clock.* Arming it before the attempt holds its connection charges the pool
  wait to the request.
* *Counting the pause.* Letting the clock run while the pipe has paused the body charges the upstream's
  backpressure to the request.
* *Arming it on the gRPC path.* A client-streaming call that pauses between messages would be ended.

The amendment supersedes no statement above: it adds the time bound to the dispatch side that this
record already makes the owner of what crosses to the upstream.
