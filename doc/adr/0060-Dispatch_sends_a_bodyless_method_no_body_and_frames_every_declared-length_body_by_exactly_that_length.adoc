== Status

Accepted

== Decision

The framing gate settles HTTP framing before route selection. It sees only the request line and the
headers. On HTTP/1.1 the headers are the whole framing story: a body exists exactly when
`Content-Length` or `Transfer-Encoding` says so. HTTP/2 breaks that equivalence. DATA frames carry the
body, and `content-length` is optional. A stream can carry body bytes that no header announces. A
stream can also end with an empty final DATA frame. When the gate runs, the two look the same.

A second gap sits at the same seam. The client's `Content-Length` is in the request-direction
never-forward set of
link:0037-The_gateway-owned_header_sets_are_enumerated_per_direction_and_bounded_by_knowledge.adoc[ADR-0037].
A body streamed without a length is framed as chunked by the transport. The upstream then learns the
message boundary from a mechanism the gateway never checked.

A third gap is time. A dispatch holds a pooled upstream connection while it forwards the body. Before
this decision only the upstream guard's fixed 30 s timeout
(link:0064-The_upstream_guard_is_fixed_in_the_gateway_and_a_route_declares_no_circuit_breaker_settings.adoc[ADR-0064])
bounded that hold. The guard bounds a dispatch only until the response head. It ended a stalled body
as `UPSTREAM_TIMEOUT` (`504`), which the breaker counts against an upstream that was given nothing to
answer. After the response head, nothing bounded a body that kept arriving.

The record settles one question: *where does the gateway's validated view of the body become the
upstream's view, and who bounds it?*

*Dispatch owns what crosses to the upstream, and it owns how long it waits for the body it forwards.
A bodyless method is sent with no body. A declared length frames the forwarded body exactly. A
forwarded body is bounded by an idle timeout and a deadline, and a gRPC call by a stream-idle bound.
Each rule holds on every protocol.*

The rule belongs where the gateway both knows what the message carries and controls what the upstream
receives. The gate keeps the checks it can make on headers. `DispatchStage` implements the rest.

*The boundary with ADR-0066.* This record owns what crosses to the upstream and the request-body
bounds. link:0066-An_HTTP2_response_answered_while_its_request_body_is_open_is_ended_once_request_data_stops_arriving_or_a_time_cap_passes_and_its_stream_is_then_reset_with_NO_ERROR.adoc[ADR-0066]
owns how a response ends and how the upstream connection closes. Every answer this record produces
ends through the one end rule of ADR-0066. Every upstream reset this record makes closes an HTTP/1.1
connection the way ADR-0066 decides.

[[bodyless-method]]
=== A bodyless method is sent with no body

A `GET` or `HEAD` without a positive declared `Content-Length` is dispatched with no body. The
inbound stream is never handed to the upstream request. A watcher (`BodylessMethodWatch`) consumes
it instead. The first chunk that carries at least one byte rejects the request as
`SECURITY_FILTER_VIOLATION`, whatever its size. The watcher then resets the upstream request. A
zero-length chunk and the end of the stream are not violations. A stream that ends with an empty
final DATA frame is served normally.

The rejection takes the shape of the gate's own framing rejection:

* *While the dispatch is awaited*, the rejection is the dispatch's failure and is answered `400`. On
  HTTP/2 only the offending stream ends.
* *After the response was handed over for relay*, the client stream is reset with `CANCEL`. It is
  never cleanly ended, so a truncated response does not look complete. The upstream request carried
  no body, so nothing was forwarded.

The rule does not test the protocol version. On HTTP/1.1 such a request carries no body bytes by
framing, so the watcher never fires. The only effect there is an upstream request with no body
instead of an empty streamed one.

A `GET` with a positive declared `Content-Length`, admitted by the opt-in of
link:0029-The_GET-with-body_opt-in_relaxes_only_the_Content-Length_leg_and_is_necessarily_gateway-wide.adoc[ADR-0029],
is not on this path. It is framed by its declared length. `HEAD` stays rejected on every leg. The
gateway-answered actions (asset, redirect, portal, reserved paths) never subscribe the inbound body.

[[declared-length]]
=== A declared length frames the forwarded body

Every other request with a checked declared `Content-Length` is forwarded with that value as the
upstream `Content-Length`. "Checked" means the value the framing gate and the body cap pre-check
admitted. This covers the opt-in `GET`, `POST`, `PUT`, `PATCH`, `DELETE` and a gRPC request that
declares a length. The transport frames the body by length and never re-frames it as chunked. The
client's own header is still never relayed: dispatch writes the value it validated.

The forwarded body is held to that length exactly. The bound sits in the streaming counter that
enforces the body cap (`ByteCappedBodyStream`,
link:0023-The_declared_max_body_bytes_cap_is_the_effective_one_and_a_breach_is_the_gateways_413.adoc[ADR-0023]).
A chunk that would carry the total past the declared length is not forwarded. It rejects the request
as `SECURITY_FILTER_VIOLATION` and resets the upstream request. A body that ends short of the
declared length resets the upstream request as `INBOUND_BODY_ABORTED`.

A request that declares no length keeps the framing the transport chooses. One length rule covers
every method.

[[request-body-idle-timeout]]
=== A body that stops arriving ends after 10 s

One clock watches each forwarded body. It starts when the attempt hands the body to its upstream
request, which happens only once the attempt holds its pooled connection. Every forwarded chunk
restarts it. One value therefore covers the wait for the first body byte and every gap between
chunks. After 10 s without progress, the dispatch ends as `REQUEST_BODY_TIMEOUT` (`408`,
`INPUT_VALIDATION`) and the upstream request is reset. The dispatch stops holding its pooled
connection at once.

The clock does not count:

* the wait for a pooled connection, which is the gateway's own queueing;
* a pause of the forwarding pipe while the upstream takes no data; the clock restarts when the pipe
  resumes;
* the time after the attempt's send completes;
* a bodyless request, which hands no body to the upstream;
* a `protocol: grpc` route. Client-streaming and bidirectional calls pause between messages, and the
  forced-HTTP/2 upstream shares its connection, so there is no pooled connection to free.

What becomes of the upstream connection depends on what was written to it. `DispatchStage` sends the
request head together with the first forwarded body chunk. On HTTP/1.1 the connection returns to the
pool only when no body chunk had been forwarded. A partly sent request closes its connection, and the
next dispatch obtains a new one. ADR-0066 decides how that connection closes. On an HTTP/2 upstream
the reset ends one stream, and the connection carries on.

[[request-body-deadline]]
=== A body that keeps arriving ends 25 s after its attempt started

A body that sends a chunk more often than every 10 s never trips the idle timeout. A body-carrying
dispatch therefore also carries a request-body deadline. The deadline is 25 s after the upstream
attempt started, which is the moment the guard's 30 s timeout starts too. The timer is set when the
attempt hands its body to the upstream request. The wait for a pooled connection counts towards the
25 s.

When the deadline passes while the gateway still reads the body, the upstream request is reset and
the body is rejected as `REQUEST_BODY_TIMEOUT`:

* *Before the response head* the dispatch fails as the request's: `408` (`INPUT_VALIDATION`).
* *After the response head* the reset fails the relay. The relayed response ends with the status the
  upstream sent, also when no upstream body byte had been relayed yet.

A passed deadline stays in force. Two cases reach the body only after the deadline. In the first, the
forwarding pipe has paused the body because the upstream takes no data. The deadline does not reset
the upstream request while the upstream holds the body back. It ends the body when the pipe resumes.
In the second, the attempt obtained its pooled connection only after the deadline. The body is ended
as soon as it starts to be read, before any byte crosses.

The deadline stops when the body ends and when another abort claims the stream first. It also stops
when the attempt ends without handing its response back: its send failed, the next attempt began, or
the dispatch failed. A stopped deadline reports nothing. A bodyless request and a gRPC route do not
arm it.

[[grpc-stream-idle-bound]]
=== A gRPC call silent for five minutes is ended

A gRPC call arms neither request-body bound. Until the upstream sends its response headers, the
guard's 30 s timeout bounds the call. After them the gRPC relay carries a stream-idle bound of five
minutes, the default stream idle timeout of Envoy. Every request frame the dispatch reads and every
upstream frame the relay writes restarts it. When five minutes pass with no frame in either
direction, the gateway resets the upstream request. It ends the client response with
`grpc-status: 4` (`DEADLINE_EXCEEDED`) and `grpc-message: stream-idle-timeout`. Connection-level
HTTP/2 `PING` frames are not frames of the call and do not count.

[[unread-upload-bodies]]
=== Unread HTTP/2 upload bodies give their credit back

An HTTP/2 stream whose body the gateway does not read returns no flow-control window while it stays
open. Two such streams were checked:

* An upload rejected `503` by the admission cap ends through the one end rule of ADR-0066. Its
  `NO_ERROR` reset closes the stream, and the credit its body held returns to the connection.
* An upload whose client resets it while its dispatch waits for a pooled connection is closed by that
  reset. Its credit returns, and its admission permit comes back at once.

Both held before this decision. Two tests in `GatewayEdgeEarlyResponseResetTest` pin them, and no
production code changed.

The inbound connection window stays derived: 100 streams times the 65,535-byte stream window,
6,553,500 bytes (`EdgeHardeningOptions`). A fixed 2 MiB window was measured and lost more throughput
than the 10% a change was allowed to cost. The protocol, the figures and the limits of the
measurement are in
link:../architecture/tls-and-inbound-security.adoc#_http2_connection_window_measurement[the architecture's connection-window
measurement].

=== Fixed values, retry and recording

The 10 s idle timeout, the 25 s deadline and the five-minute stream-idle bound are gateway constants.
No configuration key or system property reaches them. They follow ADR-0064: the guard they sit under
is a fixed policy of the gateway. Both request-body bounds are shorter than the guard's timeout, so
the gateway ends a stalled or trickling body as the request's before the guard would end it as the
upstream's. A gRPC call's `grpc-timeout` header is not honoured.

Every rejection of this record takes the body stream's single abort claim. The first abort to claim
the stream is the outcome; a later one changes nothing. Each rejection reaches the guard as a gateway
rejection. The breaker skips it and records it as a success, and the retry predicate does not retry it. A
bodyless request never subscribes the inbound stream to an attempt, so it stays retryable for as long
as no body byte has arrived.

`INFO` `ApiSheriff-23` records an idle timeout, `ApiSheriff-24` a passed deadline and `ApiSheriff-25`
a call the stream-idle bound ended. Each carries the route id and the fixed value only and is latched
per route. `sheriff_errors_total` counts both request-body bounds under
`event="REQUEST_BODY_TIMEOUT"`. No error counter counts a call the stream-idle bound ended.

== Alternatives rejected

*Reject at headers time in the framing gate.* Reject a `GET` or `HEAD` whose HTTP/2 stream did not
end together with its headers. Rejected because a client may legally end the stream with an empty
final DATA frame, so the check would reject conforming requests. It would also decide on absence,
before the frames that tell a body from an empty end have arrived. The gate's position before route
selection is deliberate, and that position is why it cannot see the body.

*Rely on the body cap to bound the harm.* Let an undeclared body through and treat the body cap as
the limit. Rejected because the cap bounds size, not presence. Any body on a bodyless method is the
violation. An upstream that receives one already holds a message the gateway's framing model says
does not exist.

*Apply the rule to HTTP/2 only.* Gate the no-body send on the protocol version. Rejected because on
HTTP/1.1 the rule costs nothing: the watcher never fires. A version branch would turn one property
into two statements that can drift.

*Frame by declared length only for the opt-in `GET`.* Rejected because the re-framing applies to every
declared-length request. A method scope would leave the validated length and the forwarded framing
disagreeing for the most common body-bearing requests.

*Relay the client's own `Content-Length`.* Rejected because the header is a claim about the client's
message, and the header policy withholds it for that reason. Writing the validated value and
enforcing it on the stream makes the upstream's boundary one the gateway has proven.

*Buffer the body to learn its length.* Rejected because the data plane streams request bodies and
never buffers them
(link:0006-body-streaming-vs-httpresult.adoc[ADR-0006],
link:0008-data-plane-transport.adoc[ADR-0008]). Buffering would trade a framing guarantee for a memory
exposure proportional to the body cap on every request.

*Leave the guard timeout as the only bound on a body.* Rejected for three reasons. It holds the
connection for 30 s per stalled dispatch. It answers `504` and counts the stall as an upstream failure.
And it bounds a dispatch only until the response head, so a body that kept arriving after an upstream
answered was bounded by nothing.

*Make the bounds configurable.* Rejected for the reason ADR-0064 gives for the guard. Each bound has
to stay below a guard timeout no route can see or change. No deployment choice makes a longer wait on
a body that is not arriving correct.

*Start the idle clock with the dispatch.* Rejected because the pool wait would then be charged to the
request. A queue behind busy connections would end uploads that never had a chance to send.

*Bound the whole body only by progress, not by a deadline.* The first form of this decision rejected a
whole-body deadline, because a slow but steady upload would be cut off. Two findings reversed that.
The guard bounds a dispatch only until the response head, so after it nothing bounded a body that
kept arriving. And where the guard did end a trickling body, it attributed the end to the upstream as
a `504` the breaker counts. The deadline was adopted.

*Arm the 25 s deadline on gRPC routes.* Rejected by operator decision. Long-lived client-streaming
calls are normal for gRPC. A call that keeps sending is not waiting for nothing; the stream-idle bound
ends a call that has gone quiet. A test pins that a gRPC call pausing longer than either request-body
bound is ended by neither.

*Bound a gRPC call by a request-side idle clock.* Rejected because it would end a bidirectional call
whose upstream keeps sending while its client is quiet, such as a watch or subscription call. A clock
that counts a frame in either direction, as Envoy's stream idle timeout does, ends only a call silent
on both sides. The bound therefore lives in the response relay.

*Honour the call's `grpc-timeout`.* Not adopted. The header is the client's statement about its own
call. The bound the gateway enforces stays one fixed constant.

*A fixed 2 MiB connection window.* Rejected on the measurement above. The fixed window would also
let more than 32 paused streams use up the whole connection window, the case the derivation prevents.

The rejected options decide too early, on headers that cannot see the body. Or they decide too
loosely: a size limit, a protocol branch, a method scope or a timeout owned by the upstream stands in
for the property.

== Consequences

*Positive.*

* The bodyless-method property is a property of what crosses to the upstream. It holds for a body no
  header declares, and it costs no false rejection of a stream that ends with an empty frame.
* The guarantee does not depend on a size limit. The first byte decides.
* HTTP/1.1 and HTTP/2 obey one statement of each rule.
* The length the upstream reads is one the gateway validated, and the bytes match it exactly.
  Upstreams that require a length-framed body, the opt-in `GET` in particular, receive that framing.
* A stalled body ends its hold on a pooled connection after 10 s instead of 30 s, and the uploads
  queued behind it obtain a connection then.
* A stalled or trickling body is attributed to the request: `408`, skipped by the breaker, never
  retried. A body that keeps arriving after the upstream answered is bounded.
* An upload that keeps arriving, however slowly, is not cut off by the idle timeout. An upload the
  upstream throttles is never charged for the pause.
* A gRPC call silent in both directions for five minutes ends with a status its client understands.
* The framing gate keeps its pre-route, headers-only position and its HTTP/1.1 rules unchanged.

*Negative.*

* The bodyless-method rule is split across two components. The gate rejects what the headers declare,
  and dispatch rejects what the stream carries. Each component carries the cross-reference.
* A late violation is answered by a stream reset. The client sees a reset rather than a `400`.
* A declared-length request is held to an exact byte count. A client whose body disagrees with its own
  declared length is rejected on every route.
* Dispatch's signature carries the framing decision, so every dispatch entry point states it,
  the gRPC path included.
* A client that pauses its upload for longer than 10 s while the gateway reads it is answered `408`.
  On HTTP/1.x it loses its connection.
* An upload whose body has not ended 25 s after its attempt started is ended, however steadily it
  arrives. The pool wait counts towards the 25 s. An upload that obtains its connection only after the
  deadline is answered `408` although its client sent the whole body in time.
* After the response head the client keeps the upstream's status, so a `200` can end before its body
  is complete.
* A gRPC call that legitimately stays silent in both directions for more than five minutes has to
  send messages to stay open.
* Each body stream carries a timer and the state to judge it. One timer is pending per stream at a
  time.

*Constraints on later change.* Each of the following reintroduces a defect this record removes:

* narrowing the bodyless-method rule to HTTP/2, which leaves the next transport change that lets an
  HTTP/1.1 request carry an undeclared body without a guard;
* moving enforcement back to the gate, which rejects legitimate streams that end with an empty frame;
* keeping the length header but dropping the exact byte bound, which hands the upstream a boundary
  the gateway no longer enforces;
* treating the body cap as the safeguard for a bodyless method;
* arming the idle clock before the attempt holds its connection, or letting it run while the pipe has
  paused the body;
* arming either request-body bound on the gRPC path, which ends a long client-streaming call;
* resetting the upstream request at the deadline while the upstream takes no data;
* dropping a passed deadline, or leaving the clocks of an ended attempt running;
* counting only one direction for the gRPC stream-idle bound.

`TerminalDispatchGrpcStreamIdleTest` runs a call through `TerminalDispatch.dispatchGrpc`, the overload
that takes the bound. It covers the hand-off of the watched request stream to the dispatch, and it
asserts the fixed five-minute value of `GrpcStreamIdleBound.on`. Only the public `dispatchGrpc`'s
one-line hand-over of that bound to the overload is asserted by no test (see
link:../security-threat-model.adoc#gw-07-request-body[GW-07 -- request-body bounds]).
