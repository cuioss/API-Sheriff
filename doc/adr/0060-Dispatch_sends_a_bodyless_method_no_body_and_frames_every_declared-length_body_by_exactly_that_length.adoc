== Status

Accepted

== Decision

The framing gate settles HTTP framing before route selection. It sees only the request line and the
headers. On HTTP/1.1 the headers are the whole framing story: a body exists exactly when
`Content-Length` or `Transfer-Encoding` says so. HTTP/2 breaks that equivalence. DATA frames carry the
body, and `content-length` is optional. A stream can carry body bytes that no header announces. A
stream can also end with an empty final DATA frame. When the gate runs, the two look the same.

A second gap sits at the same seam. The client's `Content-Length` is in the request-direction
never-forward set of
link:0037-The_gateway-owned_header_sets_are_enumerated_per_direction_and_bounded_by_knowledge.adoc[ADR-0037].
A body streamed without a length is framed as chunked by the transport. The upstream then learns the
message boundary from a mechanism the gateway never checked.

A third gap is time. A dispatch holds a pooled upstream connection while it forwards the body. Before
this decision only the upstream guard's fixed 30 s timeout
(link:0064-The_upstream_guard_is_fixed_in_the_gateway_and_a_route_declares_no_circuit_breaker_settings.adoc[ADR-0064])
bounded that hold. The guard bounds a dispatch only until the response head. It ended a stalled body
as `UPSTREAM_TIMEOUT` (`504`), which the breaker counts against an upstream that was given nothing to
answer. After the response head, nothing bounded a body that kept arriving.

The record settles one question: *where does the gateway's validated view of the body become the
upstream's view, and who bounds it?*

*Dispatch owns what crosses to the upstream, and it owns how long it waits for the body it forwards.
A bodyless method is sent with no body. A declared length frames the forwarded body exactly. A
forwarded body is bounded by an idle timeout and a deadline. A gRPC call is bounded by a message bound
and a pre-response deadline until its upstream answers, and by a stream-idle bound after that. Each
rule holds on every protocol.*

The rule belongs where the gateway both knows what the message carries and controls what the upstream
receives. The gate keeps the checks it can make on headers. `DispatchStage` implements the rest.

*The boundary with ADR-0066.* This record owns what crosses to the upstream and the request-body
bounds. link:0066-An_HTTP2_response_answered_while_its_request_body_is_open_is_ended_once_request_data_stops_arriving_or_a_time_cap_passes_and_its_stream_is_then_reset_with_NO_ERROR.adoc[ADR-0066]
owns how a response ends and how the upstream connection closes. Every answer this record produces
ends through the one end rule of ADR-0066. Every upstream reset this record makes closes an HTTP/1.1
connection the way ADR-0066 decides.

[[bodyless-method]]
=== A bodyless method is sent with no body

A `GET` or `HEAD` without a positive declared `Content-Length` is dispatched with no body. The
inbound stream is never handed to the upstream request. A watcher (`BodylessMethodWatch`) consumes
it instead. The first chunk that carries at least one byte rejects the request as
`SECURITY_FILTER_VIOLATION`, whatever its size. The watcher then resets the upstream request. A
zero-length chunk and the end of the stream are not violations. A stream that ends with an empty
final DATA frame is served normally.

The rejection takes the shape of the gate's own framing rejection:

* *While the dispatch is awaited*, the rejection is the dispatch's failure and is answered `400`. On
  HTTP/2 only the offending stream ends.
* *After the response was handed over for relay*, the client stream is reset with `CANCEL`. It is
  never cleanly ended, so a truncated response does not look complete. The upstream request carried
  no body, so nothing was forwarded.

The rule does not test the protocol version. On HTTP/1.1 such a request carries no body bytes by
framing, so the watcher never fires. The only effect there is an upstream request with no body
instead of an empty streamed one.

A `GET` with a positive declared `Content-Length`, admitted by the opt-in of
link:0029-The_GET-with-body_opt-in_relaxes_only_the_Content-Length_leg_and_is_necessarily_gateway-wide.adoc[ADR-0029],
is not on this path. It is framed by its declared length. `HEAD` stays rejected on every leg. The
gateway-answered actions (asset, redirect, portal, reserved paths) never subscribe the inbound body.

[[declared-length]]
=== A declared length frames the forwarded body

Every other request with a checked declared `Content-Length` is forwarded with that value as the
upstream `Content-Length`. "Checked" means the value the framing gate and the body cap pre-check
admitted. This covers the opt-in `GET`, `POST`, `PUT`, `PATCH`, `DELETE` and a gRPC request that
declares a length. The transport frames the body by length and never re-frames it as chunked. The
client's own header is still never relayed: dispatch writes the value it validated.

The forwarded body is held to that length exactly. The bound sits in the streaming counter that
enforces the body cap (`ByteCappedBodyStream`,
link:0023-The_declared_max_body_bytes_cap_is_the_effective_one_and_a_breach_is_the_gateways_413.adoc[ADR-0023]).
A chunk that would carry the total past the declared length is not forwarded. It rejects the request
as `SECURITY_FILTER_VIOLATION` and resets the upstream request. A body that ends short of the
declared length resets the upstream request as `INBOUND_BODY_ABORTED`.

A request that declares no length keeps the framing the transport chooses. One length rule covers
every method.

[[request-body-idle-timeout]]
=== A body that stops arriving ends after 10 s

One clock watches each forwarded body. It starts when the attempt hands the body to its upstream
request, which happens only once the attempt holds its pooled connection. Every forwarded chunk
restarts it. One value therefore covers the wait for the first body byte and every gap between
chunks. After 10 s without progress, the dispatch ends as `REQUEST_BODY_TIMEOUT` (`408`,
`INPUT_VALIDATION`) and the upstream request is reset. The dispatch stops holding its pooled
connection at once.

The clock does not count:

* the wait for a pooled connection, which is the gateway's own queueing;
* a pause of the forwarding pipe while the upstream takes no data; the clock restarts when the pipe
  resumes;
* the time after the attempt's send completes;
* a bodyless request, which hands no body to the upstream;
* a `protocol: grpc` route. Client-streaming and bidirectional calls pause between messages, and the
  forced-HTTP/2 upstream shares its connection, so there is no pooled connection to free. The message
  bound counts complete messages instead (<<grpc-message-bound>>).

What becomes of the upstream connection depends on what was written to it. `DispatchStage` sends the
request head together with the first forwarded body chunk. On HTTP/1.1 the connection returns to the
pool only when no body chunk had been forwarded. A partly sent request closes its connection, and the
next dispatch obtains a new one. ADR-0066 decides how that connection closes. On an HTTP/2 upstream
the reset ends one stream, and the connection carries on.

[[request-body-deadline]]
=== A body that keeps arriving ends 25 s after its attempt started

A body that sends a chunk more often than every 10 s never trips the idle timeout. A body-carrying
dispatch therefore also carries a request-body deadline. The deadline is 25 s after the upstream
attempt started, which is the moment the guard's 30 s timeout starts too. The timer is set when the
attempt hands its body to the upstream request. The wait for a pooled connection counts towards the
25 s.

When the deadline passes while the gateway still reads the body, the upstream request is reset and
the body is rejected as `REQUEST_BODY_TIMEOUT`:

* *Before the response head* the dispatch fails as the request's: `408` (`INPUT_VALIDATION`).
* *After the response head* the reset fails the relay. The relayed response ends with the status the
  upstream sent, also when no upstream body byte had been relayed yet.

*Amendment: an answer whose head was not yet written is unstorable.* It now carries
`Cache-Control: no-store` and none of the upstream's `Expires`, `Age`, `ETag` or `Last-Modified`, so no
cache keeps the empty answer as the upstream's response. Its status is kept rather than turned into a
`502`: the upstream has acted on the request, and a `502` would invite the client to send it again.

A passed deadline stays in force. While the upstream takes no data, the deadline does not reset the
upstream request; it ends the body when the forwarding pipe resumes. An attempt that obtains its
pooled connection only after the deadline has its body ended as soon as it starts to be read, before
any byte crosses. When the deadline stops is in
link:../architecture/tls-and-inbound-security.adoc#_request_body_deadline[Architecture -- request-body
deadline]. A bodyless request does not arm it. A gRPC route arms it only until its upstream answers,
and counts it from the hand-over instead (<<grpc-message-bound>>).

[[grpc-stream-idle-bound]]
=== A gRPC call silent for five minutes is ended

A gRPC call arms no request-body idle timeout. Until its upstream sends its response headers, the
call is bounded by the message bound and the pre-response deadline (<<grpc-message-bound>>). After
the response headers the gRPC relay carries a stream-idle bound of five minutes, the default stream
idle timeout of Envoy. Every request frame the dispatch reads and every upstream frame the relay
writes restarts it. When five minutes pass with no frame in either direction, the gateway resets the
upstream request. It ends the client response with `grpc-status: 4` (`DEADLINE_EXCEEDED`) and
`grpc-message: stream-idle-timeout`. Connection-level HTTP/2 `PING` frames do not count.

[[grpc-message-bound]]
=== Amendment: until its upstream answers, a gRPC call is bounded per complete request message and by a pre-response deadline, which is the client's unless the upstream stalled the request stream for the stall threshold

*The invariant.* A gRPC call ends as an upstream failure only when the upstream had everything the
client was going to send, never gave the client the time to send it, or stopped taking what the client
sent. Time the client holds its request open is the client's; time spent reaching the upstream is the
upstream's. The guard's timeout, which the breaker records as an upstream failure, is therefore reached
in two ways, both the upstream's: by an upstream that holds a complete, half-closed request it does
not answer, and by an upstream that stops taking data mid-request and takes no more within the guard's
30 s. A wait for an upstream connection or HTTP/2 stream slot ends earlier, at the connection wait
bound (<<upstream-connection-wait>>). Each holds only while the client stays: a client that leaves before the
upstream answers ends the call at once, as its own departure, on a gRPC route as on any other
(link:../architecture/tls-and-inbound-security.adoc#_client_departure[Architecture -- a client that
leaves before it is answered]). A flow-control pause is not a stall: a client that sends faster than a
healthy upstream reads is not given the upstream's breaker to open. The step-by-step behaviour of every
clock below is in
link:../architecture/tls-and-inbound-security.adoc#_grpc_message_bound[Architecture -- gRPC message
bound and pre-response deadline].

*Why a bound is needed at all.* The forced-HTTP/2 upstream request head is written only with the first
body chunk, and an upstream cannot act on a request message it holds only part of. A client that opens
a call and then sends nothing, half a message, or a complete message followed by silence would hold the
dispatch until the guard's 30 s timeout. The breaker would then count that timeout against a healthy
upstream.

*The message bound (10 s per complete message).* `GrpcDispatchStage` builds its dispatch with a fixed
message bound, `GRPC_MESSAGE_TIMEOUT_MILLIS` (10 s), counted from the hand-over of the body to the
upstream request. `ByteCappedBodyStream` reads each length-prefixed message as its bytes cross and
holds none of them. Only a complete message starts the wait for the next one again; a forwarded byte
of an incomplete message does not, and a pause while the upstream takes no data is not counted, though the
read time before it is (amended: a resume no longer starts the wait again). When
the bound passes before the next complete message, the expiry takes the body stream's single abort
claim with a `DispatchStage.RequestMessageTimeout` (`INBOUND_BODY_ABORTED`) and resets the upstream
request. The breaker does not count it, the retry predicate does not retry it, and the client receives
`INVALID_ARGUMENT` in a trailers-only answer
(link:0016-grpc-trailers-only-rejection-mapping.adoc[ADR-0016]).

*The pre-response deadline (25 s from the hand-over, held to a 29 s cap).* A message bound alone does
not hold the invariant for a steady sender. A client that sends a complete message every few seconds
and never ends its request stream stays inside the message bound and would still reach the guard. The
gRPC dispatch therefore also arms the request-body deadline as a pre-response deadline,
`GRPC_PRE_RESPONSE_DEADLINE_MILLIS` (25 s, equal to the HTTP request-body deadline). It counts from the
hand-over, like the message bound, so the wait for an upstream connection is never charged to the
client. Because the guard's 30 s counts from the start of the attempt, the deadline is held to a cap,
`GRPC_PRE_RESPONSE_CAP_MILLIS` (29 s from the start of the attempt, one second under the guard), and
passes at whichever comes first. A fixed hand-over grace, `GRPC_HAND_OVER_GRACE_MILLIS` (1 s), is the
least time the deadline ever leaves after the hand-over. An attempt that obtains its connection later
than 28 s is therefore ended at once, unsent, as `DispatchStage.UpstreamConnectionTooLate`, the same
`UPSTREAM_TIMEOUT` the guard would report a moment later, counted by the breaker. Without the grace, a
hand-over a fraction of a millisecond before the cap would arm a deadline that can pass before an end
the client already sent is delivered, and end that client as its own `REQUEST_BODY_TIMEOUT`, which the
breaker skips: a connection stall charged to the client. The deadline never runs after the upstream
answers, so a bidirectional stream the upstream has answered is never ended by it. When it passes while
the client holds the stream, the expiry takes the abort claim with a
`DispatchStage.RequestBodyDeadlineExceeded` (`REQUEST_BODY_TIMEOUT`, `408`) and resets the upstream
request. The client receives `DEADLINE_EXCEEDED` with `grpc-message: input-validation`
(link:0016-grpc-trailers-only-rejection-mapping.adoc#grpc-pre-response-deadline[ADR-0016]). The 4 s and
28 s windows the cap and the grace produce are in the architecture page.

[[grpc-upstream-stall-threshold]]
*Only a sustained upstream stall makes the deadline the upstream's.* A deadline that passes while the
request stream is being read is the client's `REQUEST_BODY_TIMEOUT` above, however long the upstream had
paused the stream earlier. A deadline that passes while the upstream's backpressure has the request
stream paused ends the call the moment the upstream takes data again, and the length the pause has
reached decides whose failure it is. A pause without a break of at least the upstream stall threshold,
`GRPC_UPSTREAM_STALL_MILLIS` (10 s), ends the call as a `DispatchStage.UpstreamStalledRequest`: the
breaker counts it, the failure mapper reports it as `UPSTREAM_TIMEOUT` (`504`), and the client receives
`DEADLINE_EXCEEDED` with `grpc-message: upstream`. A shorter pause leaves the deadline the client's. A
resume ends a pause, so a stall is always one unbroken pause, never a sum of short ones. Only the
attribution depends on the pause; when the call ends does not.

*Why a threshold, and why 10 s.* HTTP/2 flow control pauses a request stream whenever its sender gets
ahead of its reader. A client that sends large messages faster than a healthy upstream reads them, and
never ends its stream, sits paused for brief waits most of the time, so a deadline charged to whoever
held the stream at that instant would usually be charged to the upstream — and repeating such calls would
let one client open the route's breaker (`UPSTREAM_CIRCUIT_OPEN`) for every caller. A healthy upstream's
flow control returns window within a few round-trips, milliseconds, never seconds; only a pause of
seconds is an upstream that stopped reading. The threshold is the message bound,
`GRPC_MESSAGE_TIMEOUT_MILLIS` (10 s): the span the gateway already treats as no progress on the client's
side is the span it treats as no progress on the upstream's. It sits far above any flow-control pause and
well below the 25 s deadline, so a stall that starts within the call can reach it.

*ADR-0064 is unchanged.* The guard, its fixed 30 s timeout and its rule that the breaker skips a
gateway rejection are untouched. The guard's 30 s stays the bound for the three upstream cases the
invariant names. The request-side bounds end a call inside the guard, so the breaker sees the client's
own `GatewayException` (option (a); option (b) is rejected below). Both bounds, the cap, the grace and
the stall threshold are fixed constants of `GrpcDispatchStage` (see the fixed values below).

Every HTTP dispatch is built without the message bound, and so arms neither the message bound nor the
pre-response deadline.

[[upstream-connection-wait]]
=== Amendment: the wait for an upstream connection is bounded, and its saturation is the gateway's own

Each upstream client queues at most `max(admission_cap, 16)` attempts, dials within 5 s and handshakes TLS
within 4 s (`EgressClients`), and an attempt waits at most 10 s for its connection,
queue and dial together (`DispatchStage.UPSTREAM_CONNECTION_WAIT_MILLIS`). An attempt the full queue
refuses, or whose wait outlasts the 10 s, ends unsent inside the guard as `UPSTREAM_POOL_SATURATED`
(`503`): the gateway's own saturation, which the breaker does not count and the retry predicate refuses.
A refused connection and a dial or handshake past its timeout stay the upstream's failure; together they are
shorter than the wait bound but run from the dial's start, so an attempt that queued first can meet the wait
bound first. The wait still counts towards the HTTP
deadline (<<request-body-deadline>>), which must pass before the guard's timeout; the 10 s bound leaves a
body at least 15 s after its hand-over, and a gRPC call at least 19 s before its 29 s cap. The values are fixed; the derivation is in
link:../architecture/tls-and-inbound-security.adoc#_upstream_connection_wait[Architecture -- upstream connection wait].

[[unread-upload-bodies]]
=== Unread HTTP/2 upload bodies give their credit back

An HTTP/2 stream whose body the gateway does not read returns no flow-control window while it stays
open. Two such streams give their credit back. An upload rejected `503` by the admission cap ends
through the one end rule of ADR-0066, whose `NO_ERROR` reset returns its credit to the connection. An
upload whose client resets it while its dispatch waits for a pooled connection is closed by that
reset; its credit returns, and its admission permit comes back at once. Both held before this
decision. Two tests in `GatewayEdgeEarlyResponseResetTest` pin them, and no production code changed
(link:../architecture/tls-and-inbound-security.adoc#_http2_unread_upload_release[unread upload release]).

The inbound connection window stays derived: 100 streams times the 65,535-byte stream window,
6,553,500 bytes (`EdgeHardeningOptions`). A fixed 2 MiB window was measured and lost more throughput
than the 10% a change was allowed to cost
(link:../architecture/tls-and-inbound-security.adoc#_http2_connection_window_measurement[connection-window
measurement]).

=== Fixed values, retry and recording

The 10 s idle timeout, the 25 s deadline, the 10 s gRPC message bound, the 25 s gRPC pre-response
deadline with its 29 s cap, 1 s hand-over grace and 10 s upstream stall threshold, and the five-minute
stream-idle bound are gateway constants. No configuration key or system property reaches them. They
follow ADR-0064: the guard they sit under
is a fixed policy of the gateway. Both request-body bounds are shorter than the guard's timeout, so
the gateway ends a stalled or trickling body as the request's before the guard would end it as the
upstream's. A gRPC call's `grpc-timeout` header is not honoured.

Every rejection of this record takes the body stream's single abort claim. The first abort to claim
the stream is the outcome; a later one changes nothing. Each rejection reaches the guard as a gateway
rejection. The breaker skips it and records it as a success, and the retry predicate does not retry it. A
bodyless request never subscribes the inbound stream to an attempt, so it stays retryable for as long
as no body byte has arrived.

Each bound's end is recorded at `INFO`, latched per route. A gRPC message-bound end is recorded under the
`INBOUND_BODY_ABORTED` disposition `client-idle`. A pre-response deadline end the client held is also
counted on that disposition's `sheriff_inbound_body_aborts_total` series, beside its
`REQUEST_BODY_TIMEOUT` event. A pre-response deadline end the upstream stalled for
the threshold is recorded as an upstream timeout, never as a passed request-body deadline. The log
records, their latches and the counters are in
link:../architecture/tls-and-inbound-security.adoc#_request_body_bound_recording[Architecture --
recording of the request-body bounds].

== Alternatives rejected

*Reject at headers time in the framing gate.* Reject a `GET` or `HEAD` whose HTTP/2 stream did not
end together with its headers. Rejected because a client may legally end the stream with an empty
final DATA frame, so the check would reject conforming requests. It would also decide on absence,
before the frames that tell a body from an empty end have arrived. The gate's position before route
selection is deliberate, and that position is why it cannot see the body.

*Rely on the body cap to bound the harm.* Let an undeclared body through and treat the body cap as
the limit. Rejected because the cap bounds size, not presence. Any body on a bodyless method is the
violation. An upstream that receives one already holds a message the gateway's framing model says
does not exist.

*Apply the rule to HTTP/2 only.* Gate the no-body send on the protocol version. Rejected because on
HTTP/1.1 the rule costs nothing: the watcher never fires. A version branch would turn one property
into two statements that can drift.

*Frame by declared length only for the opt-in `GET`.* Rejected because the re-framing applies to every
declared-length request. A method scope would leave the validated length and the forwarded framing
disagreeing for the most common body-bearing requests.

*Relay the client's own `Content-Length`.* Rejected because the header is a claim about the client's
message, and the header policy withholds it for that reason. Writing the validated value and
enforcing it on the stream makes the upstream's boundary one the gateway has proven.

*Buffer the body to learn its length.* Rejected because the data plane streams request bodies and
never buffers them
(link:0006-body-streaming-vs-httpresult.adoc[ADR-0006],
link:0008-data-plane-transport.adoc[ADR-0008]). Buffering would trade a framing guarantee for a memory
exposure proportional to the body cap on every request.

*Leave the guard timeout as the only bound on a body.* Rejected for three reasons. It holds the
connection for 30 s per stalled dispatch. It answers `504` and counts the stall as an upstream failure.
And it bounds a dispatch only until the response head, so a body that kept arriving after an upstream
answered was bounded by nothing.

*Make the bounds configurable.* Rejected for the reason ADR-0064 gives for the guard. Each bound has
to stay below a guard timeout no route can see or change. No deployment choice makes a longer wait on
a body that is not arriving correct.

*Start the idle clock with the dispatch.* Rejected because the pool wait would then be charged to the
request. A queue behind busy connections would end uploads that never had a chance to send.

*Bound the whole body only by progress, not by a deadline.* The first form of this decision rejected a
whole-body deadline, because a slow but steady upload would be cut off. Two findings reversed that.
The guard bounds a dispatch only until the response head, so after it nothing bounded a body that
kept arriving. And where the guard did end a trickling body, it attributed the end to the upstream as
a `504` the breaker counts. The deadline was adopted.

*Arm the 25 s deadline on gRPC routes for the whole call.* Rejected by operator decision. Long-lived
client-streaming calls are normal for gRPC. A call the upstream has answered and that keeps sending is
not waiting for nothing; the stream-idle bound ends a call that has gone quiet. The deadline is armed
on a gRPC call only until its upstream answers (<<grpc-message-bound>>).

*Bound a gRPC call by a request-side idle clock for its whole life.* Rejected because it would end a
bidirectional call whose upstream keeps sending while its client is quiet, such as a watch or
subscription call. A clock that counts a frame in either direction, as Envoy's stream idle timeout
does, ends only a call silent on both sides. After the response headers the bound therefore lives in
the response relay. The message bound is a request-side clock only before the upstream answers, when
the upstream cannot yet be sending.

*Stop the gRPC bound at the first forwarded request byte.* The first form of the gRPC bound did this.
Rejected because one byte of an incomplete message gives the upstream nothing it can act on, so a
client that sent one byte held the call until the guard's timeout, which the breaker counts. The bound
now ends only at a complete length-prefixed message.

*Translate the guard's timeout into the client's abort (option (b)).* The first option considered was
to let the guard fire and then report a call whose request stream was still open as the client's abort.
Rejected because it is not available. SmallRye Fault Tolerance nests the circuit breaker outside the
timeout, as MicroProfile Fault Tolerance requires, so the breaker records the guard's
`TimeoutException` before `DispatchStage` sees the result of the guarded call. The breaker exempts only
a `GatewayException`, and `DispatchStage` translates a failure only after the guard has returned, by
which time the breaker has already counted it. The request-side bounds (option (a),
<<grpc-message-bound>>) end the call inside the guard instead.

*Bound a gRPC call by the message bound alone.* Rejected because a steady sender that never ends its
request stream stays inside the message bound and still reaches the guard. The pre-response deadline
closes that case.

*Honour the call's `grpc-timeout`.* Not adopted. The header is the client's statement about its own
call. The bound the gateway enforces stays one fixed constant.

*A fixed 2 MiB connection window.* Rejected on the measurement above. The fixed window would also
let more than 32 paused streams use up the whole connection window, the case the derivation prevents.

The rejected options decide too early, on headers that cannot see the body. Or they decide too
loosely: a size limit, a protocol branch, a method scope or a timeout owned by the upstream stands in
for the property.

== Consequences

*Positive.*

* The bodyless-method property is a property of what crosses to the upstream. It holds for a body no
  header declares, and it costs no false rejection of a stream that ends with an empty frame.
* The guarantee does not depend on a size limit. The first byte decides.
* HTTP/1.1 and HTTP/2 obey one statement of each rule.
* The length the upstream reads is one the gateway validated, and the bytes match it exactly.
  Upstreams that require a length-framed body, the opt-in `GET` in particular, receive that framing.
* A stalled body ends its hold on a pooled connection after 10 s instead of 30 s, and the uploads
  queued behind it obtain a connection then.
* A stalled or trickling body is attributed to the request: `408`, skipped by the breaker, never
  retried. A body that keeps arriving after the upstream answered is bounded.
* An upload that keeps arriving, however slowly, is not cut off by the idle timeout. An upload the
  upstream throttles is never charged for the pause.
* A gRPC call silent in both directions for five minutes ends with a status its client understands.
* A gRPC client that holds its request stream open — sending nothing, part of a message, or steady
  messages without ending the stream — is ended as the client's before the guard, so it cannot open an
  upstream's circuit breaker. That includes a client that sends faster than a healthy upstream reads:
  its flow-control pauses are far below the stall threshold, so its deadline stays its own.
* An upstream that stalls a request stream for at least 10 s across the pre-response deadline is
  counted by its breaker, rather than having its stall charged to its clients.
* The framing gate keeps its pre-route, headers-only position and its HTTP/1.1 rules unchanged.

*Negative.*

* The bodyless-method rule is split across two components. The gate rejects what the headers declare,
  and dispatch rejects what the stream carries. Each component carries the cross-reference.
* A late violation is answered by a stream reset. The client sees a reset rather than a `400`.
* A declared-length request is held to an exact byte count. A client whose body disagrees with its own
  declared length is rejected on every route.
* Dispatch's signature carries the framing decision, so every dispatch entry point states it,
  the gRPC path included.
* A client that pauses its upload for longer than 10 s while the gateway reads it is answered `408`.
  On HTTP/1.x it loses its connection.
* An upload whose body has not ended 25 s after its attempt started is ended, however steadily it
  arrives. The pool wait counts towards the 25 s. An upload that obtains its connection only after the
  deadline is answered `408` although its client sent the whole body in time.
* After the response head the client keeps the upstream's status, so a `200` can end before its body
  is complete; with no byte relayed, that answer is marked `no-store`.
* A gRPC call that legitimately stays silent in both directions for more than five minutes has to
  send messages to stay open.
* Before its upstream answers, a gRPC client must complete each request message within 10 s of the
  one before it, and a client stream the upstream answers only after the client ends it must end within
  25 s of the hand-over and before the 29 s cap, earlier than the guard's timeout that ended it before.
  Behind an upstream connection slower than 4 s that leaves the client less than 25 s, but never less
  than 19 s, since the connection wait is bounded at 10 s.
* An attempt whose upstream connection took longer than 28 s ends as `UPSTREAM_TIMEOUT` before the
  guard would have ended it, so an upstream that connects that slowly and would then answer within the
  last two seconds is not given them.
* An attempt that waits over 10 s for a pooled connection, or finds the wait queue full, is answered
  `503` unsent; a TCP connect over 5 s fails as the upstream's unless the attempt's wait bound, which
  counts its queue time too, passes first.
* An upstream stall shorter than the 10 s threshold across the pre-response deadline, or one of any
  length that ends before the deadline passes, leaves the deadline the client's `REQUEST_BODY_TIMEOUT`,
  which the breaker skips: an upstream that stops reading for several seconds at a time, but never for
  10 s across the deadline, is not counted for it, and its clients see `input-validation` where the wait
  was partly the upstream's.
* The gRPC body stream reads every message's length prefix as it crosses, which adds per-chunk work on
  the gRPC path. It copies no payload.
* Each body stream carries a timer and the state to judge it. One timer is pending per stream at a
  time.

*Constraints on later change.* Each of the following reintroduces a defect this record removes:

* narrowing the bodyless-method rule to HTTP/2, which leaves the next transport change that lets an
  HTTP/1.1 request carry an undeclared body without a guard;
* moving enforcement back to the gate, which rejects legitimate streams that end with an empty frame;
* keeping the length header but dropping the exact byte bound, which hands the upstream a boundary
  the gateway no longer enforces;
* treating the body cap as the safeguard for a bodyless method;
* arming the idle clock before the attempt holds its connection, or letting it run while the pipe has
  paused the body;
* arming the request-body idle timeout on the gRPC path, or letting the message bound or the
  pre-response deadline run after the upstream answered, which ends a long client-streaming call the
  upstream serves;
* stopping the gRPC message bound at a forwarded byte rather than at a complete message, or dropping
  the pre-response deadline or its cap, any of which lets a client's open request stream reach the
  guard and be counted against the upstream;
* counting the gRPC pre-response deadline from the start of the attempt, which charges a slow upstream
  connection to a client that had already sent its whole request;
* dropping the hand-over grace, or narrowing the refusal back to a connection that came past the cap,
  which dispatches a hand-over just short of the cap with a deadline too short for an end the client
  already sent to be delivered, and charges that connection stall to the client;
* resetting the upstream request at the deadline while the upstream takes no data;
* charging a passed pre-response deadline to the upstream for any pause shorter than the stall
  threshold, or for a sum of pauses a resume separated, which lets a client that out-sends a healthy
  upstream open its breaker;
* dropping a passed deadline, or leaving the clocks of an ended attempt running;
* handing a dispatch a decorator around the armed request body instead of the body itself, which hides
  a client's departure from the dispatch and leaves a call its client has left to the guard's timeout;
* counting only one direction for the gRPC stream-idle bound.
