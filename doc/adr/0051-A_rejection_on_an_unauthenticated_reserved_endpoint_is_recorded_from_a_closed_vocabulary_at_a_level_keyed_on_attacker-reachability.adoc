== Status

Accepted

== Decision

=== The question

A gateway mounts reserved paths that are reachable without a credential by protocol design. A protocol peer posts to them, and the endpoint decides from the
request's own content whether to act. The OIDC back-channel logout receiver is the archetype: any host that can reach the gateway can post to it. Only the
signature on the token in the body separates a genuine identity-provider delivery from noise.

Such an endpoint rejects far more often than it acts. Each rejection poses two questions: what may be said about it, and how loudly. Three failure modes frame
the answer:

* *Silence is indistinguishable from absence.* With every rejection at `DEBUG`, the path is invisible at the default log level. A delivery that never arrived and
  a delivery that was rejected look identical. "Did the identity provider even reach us?" has no answer short of raising the level and waiting for a cross-service
  condition to recur.
* *Volume is a denial-of-service surface.* With every rejection at `WARN`, anyone who can reach the gateway has an unbounded flood, with no session, credential or
  well-formed body. The cost lands on the operator's storage, alerting and ability to see anything else.
* *A reason string is a sink.* The tempting reason interpolates the claim that failed or the value that was wrong. On this path that detail is attacker-supplied and may
  bear identity: a `sub`, a `sid`, a token fragment. A free-text parameter is a general exfiltration channel into the log.

Which rejections an anonymous caller can drive is a property of each reason, not of the endpoint. Exactly one thing decides it: whether the request that produced the reason
can be presented again. The position of the signature check does not decide it. A token the configured issuer signed is not scarce, because every ID token and access token
of that issuer verifies. A rejected token is not remembered. A reason reached after verification can therefore recur at the hands of whoever holds one such token. A reason
is unrepeatable only when a repeat needs a fresh credential from the identity provider, such as a new authorization code.

=== The decision

A rejection on the back-channel logout path is recorded through one emitter type, from a closed enumerated vocabulary. Its level depends on whether a caller without a credential
of its own can make the reason occur again. `LogoutRejection` and `LogoutRejectionLog` realise this. Three coupled mechanisms carry it.

=== Where the rule applies

The back-channel logout path is the only path that uses `LogoutRejectionLog`. Two other records apply the same level rule through a latch and a closed reason set of their own:

* `PushedAuthorizationRequests` records `ApiSheriff-132` for a refused push, reachable through login initiation.
* `SealedSessionCookieCodec` records `ApiSheriff-113` for a cookie that fails to unseal.

`BoundTokenEndpointClient` records `ApiSheriff-134` on every occurrence, under the second arm of mechanism (2).

`CallbackEndpoint` does not apply the rule. It records a rejection ahead of the code exchange at `DEBUG` only, so the failure mode "silence is indistinguishable from absence" still
holds on the callback. A CSRF rejection is also `DEBUG` only, and its event counter carries the signal.

=== (1) The reason vocabulary is closed and carries no value

Every reason is a member of a fixed enumeration, and each member's only payload is a fixed lower-case token. It holds no token material, `sub`, `sid` or raw offending value. The
emitter's one recording method accepts a member of that enumeration and nothing else, and it is the only production code that uses the `ApiSheriff-112` record. The type of that method
carries the constraint, not a review convention.

The closure is the load-bearing half. A bounded-but-open vocabulary, a string the caller is asked to keep short, works until someone needs one more detail. The parameter then admits it.

=== (2) The level discriminator is attacker-reachability, per emission point

The discriminator is whether a caller without a credential of its own can make the reason occur again. It is answered once per emission point, for that point's whole vocabulary.

* *A reason such a caller can repeat is latched.* The first occurrence of each reason per emitter is recorded at `WARN`, and every repeat at `DEBUG`. On the back-channel logout path
  this is every reason. A request with no token or an unverifiable one is repeatable by anyone. A token whose signature verifies and whose claims are then rejected is repeatable too:
  it is not remembered, and any token of the same issuer reaches the same checks.
* *A reason is recorded at `WARN` on every occurrence* only when a repeat needs a fresh credential from the identity provider. A refused token response is the example. On the code-exchange
  leg it is reached by redeeming a single-use authorization code. On the refresh leg the refusal ends the session whose refresh token reached it, so a repeat needs a new login.

=== (3) The flood bound is a per-reason, per-emitter latch

The latch bounds the flood to one line per reason per emitter, while the first real occurrence of each reason still reaches the default log level. The operator learns that the condition
occurred, and the attacker does not control the volume.

The bound applies per assembled runtime. Each component that can reject holds its own emitter, bound to its own logger, so the record names the class that rejected the request.

=== What the latch does not give

Absence of a repeated `WARN` says nothing about the rate. An attacker who consumes a reason's latch early makes a later genuine occurrence `DEBUG`-only. Both are accepted costs. The `WARN`
channel answers "did this happen at all". The `DEBUG` channel answers "how often" and "is it still happening".

== Alternatives rejected

=== Record every rejection at `DEBUG`

The minimal-risk choice on volume, and it leaks nothing by level.

*Rejected because* it makes a protocol integration unobservable at the level operators run. "Nothing arrived" and "something arrived and was rejected" both render as silence. Only reproducing
a cross-service condition on demand recovers the distinction.

=== Record every rejection at `WARN`

This maximises signal and needs no per-reason classification.

*Rejected because* it gives anyone who can reach the gateway an unbounded, unauthenticated write into the operator's log sink. A defence an anonymous caller can turn into resource exhaustion is
not a defence. "The path is rarely hit" assumes no adversary.

=== Rate-limit the emission with a token bucket instead of a latch

This preserves the rate signal under load and still bounds the volume.

*Rejected as disproportionate.* It adds per-reason time state and a refill policy, two settings with no obviously correct values, to improve a channel that already carries the rate at `DEBUG`. The
latch is one concurrent-set insertion and states its limit plainly. The bucket promises a rate fidelity it only approximately keeps.

=== Discriminate on request origin instead of attacker-reachability

Use a trusted source address or an mTLS peer. This is the intuitive reading of "can an attacker drive this".

*Rejected because* the log policy would depend on deployment-supplied network trust, the input a reserved unauthenticated endpoint must not rely on for a security property. Whether a request can be
presented again is a property of the protocol exchange. Deriving the discriminator from it keeps the policy correct under every topology, including a directly reachable gateway.

=== Discriminate on the position of the signature check

Latch what precedes the check, and record what follows it unconditionally. This was the first form of this decision.

*Rejected because* a verified signature shows who issued a token, not that the request is scarce. The issuer's other tokens verify as well, and a rejected token can be presented again.

=== Keep a free-text reason parameter with a documented "no sensitive values" rule

This preserves full diagnostic detail and costs nothing to implement.

*Rejected because* it relocates a structural guarantee into a convention. The parameter's type admits a `sub`, a `sid` or a token fragment, and only each future caller's memory prevents it. A sink that is
safe by discipline is a sink.

=== Let each rejection site choose its own level

The most flexible shape, with no central emitter.

*Rejected because* the flood policy must hold everywhere to hold at all. One site choosing unconditional `WARN` for an attacker-reachable reason removes the bound for the whole endpoint, and nothing would
surface that it had.

The rejected alternatives divide cleanly. One group picks a single global level and sacrifices observability or the volume bound. The other keeps the distinction but grounds it in something weaker than
repeatability: network origin, the signature check's position, caller discipline or per-site judgement. The chosen position derives the discriminator from the one fact that decides attacker-reachability, carries
the vocabulary in the type system, and applies the level in one emitter type.

== Consequences

=== Properties of the design

* The back-channel logout path is observable. At the default log level an operator can tell a delivery that never arrived from one that was rejected, and can tell which rejection.
* Construction bounds the log volume an anonymous caller can drive on that path, at one line per reason per emitter.
* The record cannot leak identity-bearing or attacker-supplied data, because no parameter can carry it. Secure logging is a property of the type, not of each call site.
* The first occurrence of every reason reaches the default log level, including those that describe a real integration problem: a misconfigured audience, a clock outside the replay window, a token missing required
  claims.
* A new reason at a latched emission point needs no classification.
* The emitter type states the emission rule once. On the back-channel logout path the endpoint and the receiver each hold an emitter, and both apply it.

=== Accepted costs

* The `WARN` channel understates rate for latched reasons, permanently and by design. A volume question needs `DEBUG`.
* A latch an attacker consumes demotes a later genuine occurrence of that reason. The first occurrence is guaranteed, and the informative one is not.
* The closed vocabulary is a maintenance obligation. A rejection whose reason is not in the set cannot carry a reason until a deliberate change extends the set.
* The record is coarser than a free-text one. An operator learns the reason class, not the offending value.
* Latch state is per process and per assembled runtime. A restart re-arms every latch, and two runtimes in one process each emit their own first `WARN`.
* A rejected callback leaves no `WARN`. An operator who needs to know why a login callback failed raises the level to `DEBUG`.

=== Risks

* *The latch reads as a rate limiter.* It is a one-shot per reason. A reader expecting sampled `WARN`s under load sees exactly one and concludes the condition stopped.
* *The closed vocabulary erodes.* Each request to add "just this one value" is plausible, and together they rebuild the free-text sink. The closure is the limit.
* *An emission point is misclassified.* One wrongly judged unrepeatable records `WARN` without bound. The author makes the judgement where the point is written, and nothing computes it.
* *A verified signature reads as unrepeatable.* What makes a reason unrepeatable is that a repeat needs a fresh credential, and rejection does not use up a signed token.
