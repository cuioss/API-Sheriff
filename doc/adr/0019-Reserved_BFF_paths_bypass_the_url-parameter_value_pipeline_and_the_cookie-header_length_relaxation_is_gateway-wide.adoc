== Status

Accepted

== Decision

The gateway validates every request before routing: path canonicalisation, url-parameter validation
and header validation. Each check is fail-closed and echoes no offending value. The pipeline is tuned
to defend an upstream against traffic the gateway forwards. Two legitimate request classes do not fit
it.

* *A reserved path is not forwarded traffic.* The url-parameter value pipeline is an anti-injection
  defence for parameters that reach an upstream. A reserved BFF path ends at a handler the gateway
  owns. Some of its parameters carry structure the pipeline rejects: a same-origin return target is a
  path, with separators that look suspicious in a value bound for an upstream.
* *Some header values are long by design.* The cookie-mode BFF's sealed session cookie is designed to
  a multi-kilobyte budget. A bearer token with its `Bearer ` prefix routinely exceeds the `strict`
  preset's 1024-character value cap. Both fail the pre-route floor on every request.

The pre-route floor (`BasicChecksStage`) runs before route selection, so routing decides on
canonical, validated input. At that point no route or anchor exists to scope a relaxation to. That
is a structural property of the pipeline, not a shortcut.

*Both relaxations are granted. Each is scoped as narrowly as its position in the pipeline permits,
and each leaves every other validator in force.*

*The boundaries.*
link:0018-BFF_session_mode_is_one_SessionBinding_seam_behind_a_fixed_reserved-path_and_CSRF_model.adoc[ADR-0018]
owns the BFF structure these relaxations serve, the reserved-path model included. This record owns
the two inbound-validation relaxations.
link:0026-A_security_bound_declared_at_one_inbound-validation_stage_is_re-asserted_at_every_later_stage_that_re-validates_the_same_input.adoc[ADR-0026]
owns the principle that a bound declared at one stage is re-asserted at every later stage that
re-validates the same input. The post-route handling of the header carve-outs below applies that
principle; this record does not restate it.

[[reserved-path-parameters]]
=== (a) A matched reserved path never reaches the url-parameter value pipeline

A matched reserved path is answered by `ReservedPathHandler` before route selection. The url-parameter
name and value validation runs in the post-route stage (`ThoroughChecksStage`), under the route's
configuration and the inbound-filter profile gate of
link:0024-Inbound_filter_modes_minimal_is_a_partial_disable_retaining_the_body_cap_and_path_allowlist_and_is_refused_on_authenticated_and_BFF_routes.adoc[ADR-0024].
A reserved path therefore never reaches it. The exemption is a consequence of where reserved paths
end, not a predicate consulted per request. There is no second representation of the reserved-path
set that could disagree with the registry.

Validation of those parameters is not skipped. It moves to the reserved handler, which knows each
parameter's grammar. The handler validates a return target as a same-origin path and `state` as an
opaque correlator. Those checks are type-aware, so they are stricter than a generic value policy.

Everything else still constrains a reserved path. The pre-route floor still canonicalises the path
and yields the single canonical path every later stage reads. The parameter and header count caps
still apply, and so does every header validator. A gateway with no BFF matches no reserved path and is
unaffected.

[[header-carve-outs]]
=== (b) The header-value length cap is raised for two header names, gateway-wide

`BasicChecksStage` selects the value policy by header name, on three branches:

* *`Cookie` and `Set-Cookie`*, on an active cookie-mode BFF only. The budget is
  `oidc.session.max_cookie_size` plus 512 bytes for co-resident cookies. A bearer-only or server-mode
  gateway has no cookie carve-out.
* *`Authorization`*, on every gateway. The budget is
  `security_defaults.max_authorization_header_value_length`, default 8192, the `lenient` preset's own
  header-value cap. A declared value below the resolved baseline is a boot refusal: a relaxation key
  must not tighten.
* *Every other header* keeps the resolved baseline cap.

`SecurityPostures` builds both carve-out policies. Each is seeded component by component from the
resolved baseline and overrides the length cap alone. The null-byte, control-character and
injection-pattern validators, extended-ASCII handling and case sensitivity stay as the baseline sets
them. The seeding makes "only the length cap changes" a structural property: a carve-out admits a
longer value, never a differently shaped one.

The relaxation is gateway-wide because no anchor exists at the floor. The cookie budget sits on the
global `oidc.session` block and the `Authorization` budget on the gateway-wide `security_defaults`
block for that reason. Their placement must not be read as per-anchor enforcement.

*The post-route re-run honours both carve-outs.* `ThoroughChecksStage` re-validates every header under
the route's configuration whenever that configuration diverges from the baseline. A route that only
raises `max_body_bytes` already diverges. The re-run runs before authentication, so an
`Authorization` value is still present there. Without the carve-outs it would reject a bearer token
the floor had admitted. The re-run therefore uses the same three-way dispatch, seeds each carve-out
from the route's configuration and caps it at `max(route cap, budget)`. A route stricter than the
gateway keeps its strictness on the carved-out headers for every validator but length.

*No site may lower a cap.* Three sites derive a carved-out cap, and each only ever admits more
length:

[cols="1,2,3", options="header"]
|===
| Site | Cap | Mechanism

| Pre-route `Cookie` / `Set-Cookie`
| `max(baseline cap, budget + 512)`
| A silent `max`. The cookie budget is a codec transport property with its own range check, so a
  value below the baseline is a legitimate budget, and clamping it is correct. The shipped default,
  4019 plus 512, is 4531, below the `lenient` baseline of 8192.

| Pre-route `Authorization`
| The declared budget
| A boot refusal of a below-baseline value, not a silent `max`. The key is a relaxation key on a
  gateway-wide block, so a lower value is a misconfiguration and earns a boot diagnostic.

| Post-route re-run, both names
| `max(route cap, budget)`
| A silent `max`. A route that raised its own cap keeps it.
|===

The residual exposure is enumerable. On a cookie-mode gateway a client may send a longer `Cookie`
value, subject to every other content check and the transport limits. A value that is not a
resolvable sealed session is "no session" to the binding. On every gateway a client may send a longer
`Authorization` value, subject to the same checks, before bearer validation rejects an invalid token.
The configuration field contract is in
link:../configuration.adoc#_pre_route_header_carve_outs[Configuration Reference -- Pre-route
header-name carve-outs].

== Alternatives rejected

*Apply the url-parameter value pipeline to reserved paths unchanged.* One uniform policy with no
exception. Rejected because it rejects correct traffic and protects nothing. A path-shaped return
target fails a policy whose threat, reinterpretation by an upstream, does not apply to a request that
is never forwarded. The login return leg could not work.

*Loosen the url-parameter value policy globally so reserved paths pass.* Rejected because it weakens
the defence where it carries weight, on parameters that are forwarded, to accommodate requests that
are not. The narrow case must be the exception, not the new baseline.

*Keep a reserved-path predicate inside the pre-route stage.* The first form of decision (a) exempted
reserved paths by a host-and-path matcher threaded into the stage that then ran the value pipeline.
Rejected once the value pipeline moved post-route: the matcher was a second copy of the reserved-path
set that could drift from the registry, and the pipeline's shape now gives the exemption for free.

*Raise the header-value cap globally for all headers.* The simplest change. Rejected because it drops
the cap's protection on every other header to solve a problem confined to two. A relaxation must name
the header it applies to, or it is a removal.

*Make the cookie-header cap per-anchor.* The natural containment. Rejected because it cannot be built
at this position: no anchor exists before route selection. Moving the header check after routing
would route on unvalidated input, a worse exposure than the raised cap.

*Reject the cookie-mode variant instead of relaxing anything.* Rejected because the cookie-based BFF
answers a real deployment need. The relaxation it requires is bounded and reviewable.

*Leave bearer requests to fail the floor, or raise the route's `max_header_value_length` instead.*
Rejected because a gateway that cannot serve bearer traffic is not an option. Raising a route's own
cap relaxes every header on that route, the blunt widening the name-scoped carve-out exists to avoid.

*Seed the carve-out from the builder's defaults.* Rejected because the defaults are not the resolved
baseline. On a `strict` gateway that seeding also relaxed suspicious-pattern detection, extended ASCII
and case-sensitive comparison for cookie values, so the shipped behaviour broke the "only the length
cap changes" bound. Seeding from the resolved baseline is what makes the bound true.

*Measure the carved-out headers post-route at the route's own cap.* Rejected because it undoes the
carve-out one stage later on any route with a divergent `security_filter`: the floor admits a bearer
token and the re-run rejects it, still before bearer validation.

*Set the pre-route cookie cap outright from the budget.* Rejected because the shipped default budget
lies below the `lenient` baseline. The carve-out then lowered the cap for exactly the header it names
and rejected cookie values every other header could carry.

*Clamp a below-baseline `Authorization` budget silently, like the cookie budget.* Rejected because it
turns a misconfiguration into silent coercion. A boot refusal names the key that is wrong.

The rejected options fall into two classes. One widens a relaxation past the case that motivates it.
The other refuses a bounded relaxation at the cost of a legitimate capability. The chosen position is
the narrowest scope each enforcement point permits, and where that scope is coarser than wanted, the
limit is structural and stated.

== Consequences

*Positive.*

* Legitimate BFF and bearer traffic passes the edge: a login return leg with a path-shaped target, a
  cookie-mode request with a multi-kilobyte sealed cookie, and a bearer request with a long token.
* Reserved-path parameters are validated more precisely, by a handler that knows their grammar.
* The cookie carve-out is inert on a gateway that is not an active cookie-mode BFF.
* The carve-outs hold the same bound at every site that measures a header value, and no route's
  posture is weakened on any other axis.
* The residual exposure of each relaxation is enumerable, which makes it reviewable.

*Negative.*

* Reserved-path parameter validation is the reserved handlers' responsibility. A new handler that
  does not validate its own parameters has no generic backstop.
* Neither length relaxation can be scoped to the routes that need it. On a cookie-mode gateway the
  cookie carve-out applies to every request.
* The `Authorization` carve-out has no mode axis. It is present on every gateway, a larger residual
  than the cookie carve-out's, accepted because the alternative is a gateway that cannot serve bearer
  traffic.
* Two documented exceptions now exist to a uniform inbound policy, a cost in comprehensibility.

*Constraints on later change.*

* A new reserved handler must validate every parameter it reads.
* The limit now accepted is two header names, one validator (the length cap) and a mode axis that
  binds the cookie carve-out alone. Relaxing a different validator is a separate decision with its
  own record.
* A carve-out must stay seeded from the resolved configuration, and no site may lower a cap.
