== Status

Accepted

== Decision

=== The question

A session outlives the route that started it. Its login requested one route's OAuth scopes, and the session later reaches routes that need others.
link:0049-Route_scope_policy_bearer_routes_enforce_oidcscopes_union_endpointscopes_session_routes_only_request_them.adoc[ADR-0049] derives one set per route at boot, `neededScopes = oidc.scopes ∪ endpoint.scopes`. Without a comparison on a live session,
the gateway does not hold its own sessions to a declared requirement:

* *Under-check.* A session from a route needing fewer scopes reaches a route needing more, and its token crosses without them. Whether the request fails depends on an upstream that may not check.
* *Two answers for one route.* A bearer caller lacking the scope gets `403` before any upstream contact. A browser session lacking it is relayed. On a `session_fallback` route the two sit on one route.

A pre-check needs a way to widen a live session. A new login replaces the session, and RFC 6749 §6 forbids a refresh grant from widening the original grant. A pre-check that can only reject turns every mismatch into a dead end.

Two facts about a session's tokens make the mismatch recoverable:

* the *active scope set* `A`: the scopes the mediated access token was granted. A refresh response can narrow it.
* the *granted scope set* `S`: the scopes the identity provider is known to grant this session. It equals `A` at login and after a widening. A refresh never adds to it.

A scope missing from `A` but inside `S` needs no user: a refresh grant may name any subset of the original grant. A scope outside `S` needs a new authorization. This record settles what a session route does when `A` lacks a needed scope.

`S` is useful only while it is true. An identity provider can stop granting a scope during a session's life: an entitlement is removed, a consent withdrawn, a client scope unassigned. A set that still names such a scope sends every request for it into a recovery that cannot succeed. The decision therefore also says when a scope leaves `S`.

=== The decision

A session route never relays a session that lacks a scope the route needs. It compares on every request and obtains what is missing: by a refresh when it lies inside `S`, by widening the live session when not. It answers `403` when the identity provider refuses.

* *The comparison runs on every session request.* After session resolution and the near-expiry refresh, `SessionAuthenticationStage` computes `missing = neededScopes − A`. It does so whatever `auth.token_relay` says and before recording any bearer, so `token_relay: false` withholds the token from the upstream
  but not the check from the request. With nothing missing the request continues, and the gateway makes no identity-provider call.
* *Inside the grant, a refresh.* When every missing scope lies inside `S`, the stage makes exactly one call through the scope-driven leg of `TokenRefreshCoordinator`, requesting `A ∪ missing`. The leg shares the near-expiry leg's per-session single-flight, re-checks the re-resolved session under that exclusion, and
  never adds to `S`. The stage compares the returned session again, so no refresh outcome relays an under-scoped session. Navigations and API calls take this path alike.
* *`S` is kept truthful.* It records what the identity provider last showed it grants, not everything it ever granted. Exactly two events change it after login:
** *A widening replaces it.* The merge sets `S` to the scope of the new grant, not a union with the earlier set. A scope the identity provider no longer returns leaves `S`.
** *A processed scope refresh reduces it.* When the identity provider processes the scope-driven grant and its response `scope` lacks a requested member, every such member leaves `S` before the rotated session is persisted. Nothing else is removed, and nothing is added.

+
A response that omits `scope` refuses nothing (RFC 6749 §5.1), and an unprocessed grant proves nothing, so neither changes `S`. The near-expiry leg never changes `S`, even when its response narrows `A`: it asked for the session's current scopes, not for a scope a route needs. The first scope-driven refresh that asks settles the question.

* *Outside the grant, the live session is widened.* When a missing scope lies outside `S`, or the refresh did not obtain the set, the answer depends on what the caller can do:
** A *navigation* (its `Accept` offers `text/html`) gets a `302` into an authorization request for `S ∪ neededScopes` that returns to the requested URL. The first attempt carries `prompt=none`. If the identity provider answers `login_required`, `interaction_required`, `consent_required` or `account_selection_required`, exactly one interactive
   attempt follows. These are the four "interaction needed" errors OpenID Connect Core 1.0 §3.1.2.6 defines for a `prompt=none` request. Any error on the interactive attempt is terminal.
** Every other request gets `403` `application/problem+json`, with two RFC 9457 extension members. `missing_scopes` lists the missing names, sorted and taken from the route's boot-configured set, never from a token. `step_up_url` is the same-origin URL a browser follows to widen the session for that request, present only when `oidc.step_up.path` is
   configured. The answer carries no `WWW-Authenticate` challenge, which belongs to the bearer posture.
* *A widening merges into the session it started from.* The widening callback is bound to the browser like a login callback. It checks a pending record, the binding cookie and the `state` before anything else, an identity-provider error included, so a forged error cannot start a re-drive. The gateway merges a successful grant only when the new ID token's
  subject, the live session's subject and the subject recorded when the widening started are the same. The merge keeps the session's internal identity, its authentication time and its absolute expiry, takes the new tokens, and sets both `A` and `S` to the granted scope. It never mints a second session or moves a session to another identity.
* *The merged session takes the `sid` of the grant.* The merged tokens belong to the identity-provider session that answered. That need not be the session the gateway session came from: the original can have ended and the user authenticated again, which is what the interactive attempt produces. The merge takes the new ID token's `sid` when it carries one, and keeps the
  session's own otherwise. In the server-session BFF the store re-indexes the session on that write, so a back-channel logout for the answering identity-provider session destroys it.
* *A refusal is terminal.* Any other identity-provider error, any error on the interactive attempt, a subject mismatch, a missing live session, and a grant that still lacks a scope sought beyond `S` all answer `403`. The session stays unchanged and usable on every route it satisfies. No further redirect follows, so a scope the identity provider will not grant cannot loop the browser.
* *A scope the identity provider stopped granting reaches that refusal.* Because `S` is truthful, such a scope is sought beyond `S` by the time a widening callback checks its grant. When a scope refresh ran first and got a narrower grant, the scope has left `S`, so the following widening is refused. When no refresh ran (the session holds no refresh token, transparent refresh is off, or the near-expiry
  refresh had just re-bound the cookie), the first widening is merged, the merge takes the scope out of `S`, and the next round is refused. A navigation ends in the `403` after at most two rounds.
* *The step-up path is a reserved path that serves a live session only.* The key `oidc.step_up.path` registers it, and it matches like the other browser-facing reserved paths. Without a live session it answers `401` with no identity-provider redirect and no pending record. It validates its `returnUrl` as same-origin and falls back to the configured default. When the target route's needed scopes lie inside
  `S` it redirects straight back, because the route then refreshes by itself. Otherwise it starts the silent-first widening a navigation gets.
* *The session carries `S` in both BFF variants.* The session record and the sealed cookie payload hold the granted set next to the active set. The version gate refuses a sealed session cookie without the field, so its browser re-authenticates.

One case skips the refresh although everything missing lies inside `S`. When the near-expiry refresh has just re-bound the session under a new cookie, the request's `Cookie` header still names the rotated binding, and a second exchange from it would present a refresh token the identity provider has retired. Such a request takes the widening branch, and the next request carries the new cookie and refreshes normally.

With transparent refresh switched off, the scope-driven leg is bound to a pass-through that hands the session back unchanged, and the stage goes straight to widening.

=== A merge cannot revive a terminated session

The merge goes through the `SessionBinding` seam's updating write, which never creates a session (link:0018-BFF_session_mode_is_one_SessionBinding_seam_behind_a_fixed_reserved-path_and_CSRF_model.adoc[ADR-0018]). In the server-session BFF, a logout or back-channel logout that destroys the session after the callback resolved it is reported at that write. The gateway stores nothing, and the callback answers the same terminal `403`
with no `Location` and no `Set-Cookie`. The refusal is recorded with the reason `session-terminated`, and the refused grant's tokens drop as other refusals' do. The session stays terminated. The scope-driven refresh leg behaves the same way and ends the request as session-ended (link:0046-Refresh_failures_are_disposed_by_the_engines_failure_kind_and_refresh-token_reuse_detection_is_the_identity_providers_job.adoc[ADR-0046]).

In the cookie-based BFF the binding holds no state a logout could remove, so it cannot observe one and re-seals the merged session. That is a residual of the stateless variant.

[[widening-reissues-cookie]]
=== A merge re-issues the browser's cookie value

In the server-session BFF a widening merge gives the browser a new cookie value. The merge uses the variant of the updating write that also re-issues the value the browser holds
(link:0018-BFF_session_mode_is_one_SessionBinding_seam_behind_a_fixed_reserved-path_and_CSRF_model.adoc#cookie-reissue[ADR-0018, re-issuing the browser's handle]). The callback's response sets the new value, and the previous one stops resolving in the same step. The cookie-based BFF re-seals the merged session with its nonce unchanged.

The session's identity, authentication time and absolute expiry stay, and the merge never mints a second session. The session identity is internal and is not the cookie value. Only the cookie value changes.

=== How this relates to earlier decisions

* *ADR-0049.* This decision supersedes its session half. A widening merge meets the precondition that record deferred its pre-check on. The `neededScopes` derivation, the bearer check and the boot refusal of `endpoint.scopes` on an endpoint with only `none` routes stand. Requesting and checking still read one set, and a session route now does both.
* *ADR-0055.* The SESSION branch of a `session_fallback` route is exactly a session route, so it inherits all of the above. Both branches now enforce one set, each with its posture's answer.
* *ADR-0046.* The scope-driven leg keeps every per-kind disposition and adds one outcome that is not a refusal: the session is kept but lacks the requested set, because the identity provider granted a narrower scope, the session holds no refresh token, or the request coalesced with a refresh that did not ask for it. That outcome records no back-off and no warning, and the stage widens. An outright `invalid_scope` answer is not part of it (<<_accepted_costs>>).
* *ADR-0048.* The widening authorization flow is built on `ScopedEngineFlows` per call and never cached. The login-flow cache is bounded because a login set is fixed at boot, while `S ∪ neededScopes` contains scopes from the identity provider. A parameter-aware rewrite on the gateway side adds `prompt=none` to the rendered URL, which leaves the engine unchanged.

== Alternatives rejected

=== Relay and let the upstream refuse

This is the session half of ADR-0049. It needs no extra mechanism and never interrupts a request.

*Rejected because* a component the gateway does not control would enforce a gateway-declared scope, and a bearer caller and a browser session would get different answers on one route. A live session can now be widened.

=== Narrow the token per endpoint

Relay each route a token restricted to its scopes, through a scope-restricted refresh or RFC 8693 token exchange. This is ADR-0049's third alternative.

*Still excluded.* It addresses session-wide scope growth, a different problem: a session lacking a scope still lacks it after narrowing. It also costs a token-endpoint round trip per route or per-route token caching, and it needs identity-provider support that cannot be assumed.

=== Probe with a refresh instead of tracking `S`

Request `A ∪ missing` on every miss and treat a failure as "outside the grant". That removes the second scope set from the session.

*Rejected because* it replaces a local set comparison with a token-endpoint round trip for every request on a scope the user never granted. It also cannot read the answer reliably: a refused scope and an unreachable identity provider arrive as one failure kind, and the back-off for the second would throttle the first.

=== Reuse the RFC 9470 step-up coordinator

`StepUpCoordinator` already re-drives an authorization request for a live session.

*Rejected because* it is the `acr` leg. It builds its request from the static `oidc.scopes` through the engine's step-up handler, and its re-drive lands as a new session. A widening needs a per-request scope set and a merge into its starting session, which is the login re-drive's shape with a different landing. The two legs stay separate.

=== Let `S` only ever grow

Unite each widening's grant with the earlier set, and never change `S` on a refresh. Every scope the user once authorized stays available to a refresh.

*Rejected because* it also keeps a scope the identity provider has stopped granting. Nothing then seeks that scope beyond `S`: the refresh returns a narrower grant, the widening merges without the scope, and the browser goes round until its redirect limit, while every API call for the scope starts its own refresh grant. The terminal refusal depends on `S` being true.

=== Carry the route's needed set on the widening pending record

The callback could reject any grant lacking a needed scope and so end a navigation on the first round.

*Rejected in favour of fixing `S`.* `S` would still name a scope the identity provider no longer grants. API calls for it would refresh on every request, and the step-up path would still answer such a target with a direct redirect.

=== Refuse a widening whose ID token names another `sid`

This keeps a session bound to the identity-provider session it came from.

*Rejected because* it turns the interactive attempt into a dead end in the case it exists for: the original identity-provider session is gone and the user authenticated again. The subject check is what binds a widening to the session.

The rejected alternatives leave the decision to someone else, learn what the user granted by asking the identity provider each time, or keep an answer in the session that has stopped being true. The decision keeps the answer in the session and keeps it current: what the token carries, what the identity provider grants, and one comparison that picks the recovery.

== Consequences

=== Properties of the design

* The under-check is closed on session routes. The gateway enforces a scope declared on an endpoint for every authenticated caller of its routes, and no token lacking it reaches the upstream.
* A satisfied route costs nothing. The comparison is a set containment check on held values: no identity-provider call, no rotated token, no `Set-Cookie`.
* A mismatch is recoverable. A user reaches a scoped route from any session with at most one consent.
* The session stays the same session across a widening. A widening neither creates a second session nor extends its lifetime. In the server-session BFF a copy of the earlier cookie value does not carry the widened session.
* A navigation for a scope the identity provider stops granting ends in the terminal `403` after at most two widening rounds.
* A back-channel logout finds a widened session, because the session is indexed under the `sid` its tokens belong to.
* Logins stay minimal. A login requests only its route's scope set, and further scopes come when a route first needs them.
* One route gives one answer about a scope, whichever authentication branch the request takes.

=== Accepted costs

* *An API client cannot recover by retrying.* A widening needs a browser navigation to the identity provider. A script that gets the `403` must send the browser to `step_up_url`. With no step-up path configured, the response names the missing scopes and nothing to follow.
* *An `invalid_scope` refresh answer arms the refresh back-off.* The engine surfaces it as a transport failure without the OAuth error code, so it classifies as `PRE_REDEMPTION` like an outage and takes that kind's back-off and warning. The request is still never relayed short of a scope, because the stage compares again. The session's next near-expiry refresh waits out the same window. Telling the two apart needs the error code from the engine.
* *The first request for a new scope is slower.* It pays one token-endpoint round trip inside the grant, or a redirect through the identity provider outside it.
* *A session can lose a scope.* A widening whose grant no longer returns a member of `S`, and a scope refresh answered with a narrower grant, both take that scope out of `S`. A later route needing it is served by a widening, and the user may consent again. `S` is evidence about the identity provider, so inconsistent grants move a scope in and out of it.
* *A scope that left the grant can cost one merged round before the refusal.* When no scope refresh ran first, the callback cannot yet tell the scope is gone: it merges, sends the browser back once, and refuses on the next round. Telling it on the first round needs the route's needed set on the pending record.
* *A logout token for the previous identity-provider session no longer matches a widened session.* After a widening answered by a different identity-provider session, the session is indexed under the new `sid` only. A late logout for the earlier session destroys nothing.
* *A near-expiry refresh that narrows `A` leaves `S` untouched.* The scope stays in `S` until a route needs it and a scope refresh asks for it.
* *The sealed cookie format is not migrated.* The gateway refuses a cookie-based session sealed without the granted set, and its browser logs in again.

=== Risks

* *Session-wide scope growth is larger.* ADR-0049 accepts that every scope a session holds is relayed to every session-route upstream. Widening adds scopes to a live session, so a session that visited a scoped route presents those scopes everywhere afterwards. The bounds stand: the identity provider grants only what is requested, a widening requests only a route's boot-declared set with what was granted, and `token_relay: false` withholds the token. The threat model tracks it as BFF-15.
* *A cross-site navigation can start a widening.* A link to a scoped route or the step-up path makes the browser request more scopes for the user's session. It cannot choose them: the set is the target route's boot-declared set, the return URL is same-origin-validated, and consent stays with the identity provider.
* *A widening merge and a concurrent refresh race.* Both resolve the session and persist it, and the last writer wins. Either result is a fresh token set of one identity, and the gateway re-checks the subject on the resolved session, not from the pending record. The loss is one abandoned refresh token. The loser's `S` can be overwritten too, and a scope it wrongly keeps leaves again the next time it is asked for and not returned. In the server-session BFF a termination is not part of this race: both writers use the updating write, and a write that finds the session gone stores nothing.
* *In the cookie-based BFF a merge or a refresh can outlast a logout.* A widening callback or a refresh in flight when the browser logged out still re-seals a session cookie. If that response reaches the browser after the logout response, the gateway resolves the cookie again until the session's absolute lifetime. The mitigations are a short `ttl_seconds`, short access-token lifetimes, and the server-session BFF where immediate termination is required. The threat model tracks it as BFF-09.
* *A refresh inside the grant depends on the identity provider honouring it.* One that declines to restore a granted scope returns a narrower grant or refuses, and the session is widened instead. The outcome is slower, not wrong. A narrower grant also takes the scope out of `S`. An outright `invalid_scope` refusal does not: it arrives as an outage, leaves `S` unchanged and retries once per back-off window.
