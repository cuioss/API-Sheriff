== Status

Accepted

== Decision

=== The question

A BFF gateway requests OAuth scopes on two legs it drives through the confidential-client engine (`token-sheriff-client`):

* the *login leg*: the authorization request carries a `scope` parameter, and the identity provider grants at most what it names;
* the *refresh leg*: the refresh grant may carry a `scope` parameter, and RFC 6749 §6 lets it narrow, but never widen, the granted set.

The needed scope set is not one gateway-wide value. An endpoint declares additional OAuth scopes (`endpoint.scopes`), and each route materializes
`neededScopes = oidc.scopes ∪ endpoint.scopes` once at boot. A session route's login requests that route's set. A login through `/auth/login?returnUrl=` requests the
set of the route the target lands on. A refresh requests the session's active scope set, the one the identity provider granted, because a refresh that names a narrower
set silently narrows the session.

The engine has no per-call scope argument. On both legs it reads `scope` from `ClientConfiguration.getScopes()` alone:
`AuthorizationRequestBuilder.build(configuration, metadata, context)` renders it, and `RefreshFlow.refresh(metadata, refreshToken)` posts it. A flow fixes its
configuration at construction. This record settles how a gateway with per-request needs drives such an engine.

=== One configuration per scope set

The configuration carries the scope set, so the gateway builds one configuration per scope set and drives a flow over it. The engine stays unchanged.

`ScopedEngineFlows` is the seam. It is built once per runtime over the collaborators the base configuration uses: the shared `TokenEndpointClient`, the access-token and ID-token
validation bridges, the gateway's `response_mode=query` request builder, the client authentication and the one DPoP sender constraint. It also takes a factory that builds a
`ClientConfiguration` for a scope list.

* `authorize(metadata, scopes)` drives an `AuthorizationCodeFlow` whose configuration carries exactly `scopes`. The flow is cached under the canonical set (deduplicated, then
  sorted), so two requests for one set in a different order share one flow.
* `refresh(metadata, refreshToken, scopes)` builds a `RefreshFlow` for that one call and never caches it.
* `widen(metadata, scopes, silent)` builds an `AuthorizationCodeFlow` for that one call and never caches it. The set a session widening requests holds the session's granted scopes, so
  the identity provider decides its size, as on the refresh leg
  (link:0057-Session_routes_obtain_their_declared_scopes_by_refreshing_inside_the_grant_and_widening_the_live_session_outside_it.adoc[ADR-0057]).

=== The factory pins the posture

The runtime producer passes `backChannelConfiguration(oidc, scopes)` as the factory. That method applies the ADR-0045 posture: the `oidc_verify_hostname` passthrough on every build, the
`oidc_tls_profile` trust context, and the boot refusal of the two together. The scope list is the only input that varies. A scoped variant therefore cannot dial the identity provider with a
posture the base configuration lacks. The gateway reports a relaxed or replaced posture once per runtime, not once per variant.

=== What stays on the base configuration

Discovery, the callback's code exchange, RFC 9470 step-up and refresh-token revocation keep the base configuration with `oidc.scopes`. The exchange does not send `scope`, and discovery and revocation
do not read it. <<_risks>> covers step-up.

=== Who chooses the set

The login flow forwards whatever set its caller names:

* The session stage passes the selected route's `neededScopes` for an unauthenticated navigation.
* The login-initiation endpoint passes the set `ReturnTargetScopes` resolves for the return target. That is the `neededScopes` of the authenticated route the same-origin, canonicalized target path selects
  as a `GET` on the gateway host. It is `oidc.scopes` when the target is absent, cross-origin, non-canonical or unmatched, or lands on a `require: none` route. A route with `match.headers` is not selected,
  because a header matcher cannot be evaluated for a request that has not happened yet.

The refresh leg passes the session's active scope set.

== Alternatives rejected

=== Subclass the authorization request builder to rewrite `scope`

The gateway already supplies its own `AuthorizationRequestBuilder` for `response_mode=query`. It could override `build` and replace `scope` in the rendered URL with a value passed through a side channel.

*Rejected because* that covers the login leg only. `RefreshFlow` takes no request builder, so the refresh leg would still post the static `oidc.scopes` and narrow every session to it. The gateway would also parse
and re-encode a URL the engine produced, duplicating encoding the engine owns. It would need a thread-bound side channel to carry the set into `build`.

=== Release an engine version with a per-call scope argument

An `authorize(metadata, scopes)` and a `refresh(metadata, refreshToken, scopes)` on the engine would be the most direct shape.

*Rejected because* the engine already reads `scope` from the configuration on both legs, so the per-configuration seam reaches the same behaviour without changing the engine. An engine release is excluded for this
decision.

=== Cache refresh flows too

A cache keyed by the active scope set would save the per-refresh construction.

*Rejected because* its keys come from the identity provider's grants rather than from boot configuration, so its size would be set outside the gateway. The construction it saves is cheap.

All three change either who renders `scope` or what bounds a cache. The decision keeps both where they are: the engine renders `scope` from the configuration, and only boot configuration sizes a cache.

== Consequences

=== Properties of the design

* Per-request scope works on both legs with no engine release and no new dependency. The seam depends only on the engine's public API (`ClientConfiguration.builder()`, `AuthorizationCodeFlow`, `RefreshFlow`,
  `TokenEndpointClient`, `RotationResult.grantedScope()`).
* Requesting and checking read one derivation. The login request, the `/auth/login` resolution and the bearer route's `insufficient_scope` check all read the route's boot-derived `neededScopes`.
* The ADR-0045 posture holds on every scoped variant by construction.
* Scope encoding stays the engine's. The gateway never renders or rewrites a `scope` parameter.

=== Accepted costs

* The login-flow cache holds one `AuthorizationCodeFlow` per distinct login scope set. Construction bounds it: a login scope set is always a route's `neededScopes` or `oidc.scopes`, both fixed at boot.
* Every refresh constructs a `ClientConfiguration` and a `RefreshFlow`. With a named `oidc_tls_profile` that also resolves the profile's trust context. The cost falls once per token lifetime per session, and it is
  small next to the grant's round trip. No bounded cache is possible, because the active set comes from the identity provider.

=== Risks

* *The step-up leg still requests the static `oidc.scopes`.* `StepUpHandler.initiate` builds its authorization request from the base configuration, so an RFC 9470 re-drive requests `oidc.scopes` rather than the session's
  active set. The session-side lookup that re-drive uses is unwired, so no live path narrows a session through it. The step-up design owns this entry point. Until it is settled, the step-up pending record states the
  static set it requested.
* *Granted scopes accumulate across endpoints.* A session that logged in through one scoped route and later refreshes carries every scope granted to it, so a token relayed to one endpoint can carry another endpoint's
  scopes. Per-endpoint token narrowing is out of scope. The operator and threat-model documentation state the residual.
