== Status

Accepted

== Decision

API Sheriff scales with a virtual-thread-per-request model (link:../architecture/runtime-and-dependencies.adoc#_threading_model[Architecture, Threading Model]). Virtual threads help a gateway most when blocking work does not pin the carrier platform thread. Two JDK facts follow from that:

* *JEP 491 (JDK 24 and later)* removes carrier-thread pinning on `synchronized` blocks and methods. Before JDK 24, a virtual thread that blocked inside `synchronized` pinned its carrier. A gateway hits that hidden pin in third-party and JDK library code.
* *Java 25 is an LTS release* and includes the JEP 491 behaviour.

*The decision:* API Sheriff compiles and runs on Java 25. Java 21 is not a target.

* `maven.compiler-plugin.release` is `25`. Java 22 to 25 language features are permitted.
* Both shipping paths run on Java 25. In JVM mode the container base image is pinned to a JDK 25 runtime line. In native mode the distroless image from `Dockerfile.native` contains no JVM, and the JEP 491 behaviour comes from the Mandrel or GraalVM builder pinned to the JDK 25 line.
* The CI matrix builds and tests on Java 25 and every newer GA release it lists, as `.github/project.yml` declares (`maven-build.java-versions` is the matrix, `maven-build.java-version` the primary JDK). The 25 leg is primary: it produces the released artifacts and the Sonar and coverage analysis. A newer leg is a forward-compatibility guard. It must stay green and does not ship.
* Local development requires JDK 25 or newer. A newer toolchain compiles `--release 25` correctly.

== Alternatives rejected

=== Compile at Java 21 and run on Java 25

An earlier proposed form of this record separated the compile target from the runtime and raised only the runtime, out of caution about toolchain, CI-image and parent-POM readiness at release 25.

*Rejected because* API Sheriff ships and runs a Java 25 image only, and no earlier deployment target exists or is planned. Compiling at 21 for a 25-only runtime buys nothing. It forbids Java 22 to 25 language features, splits the toolchain story into "develop on 21, ship on 25", and keeps a version that plays no role in the delivered artifact. The parent POM and Quarkus support a Java 25 compile baseline, so the readiness gap that form waited for is closed.

== Consequences

=== Properties of the design

* Virtual threads reach full throughput under load without an audit of every dependency for `synchronized`-based pinning, and no compile and runtime split needs reasoning about.
* One toolchain runs end to end: the version you build with is the version you ship on.
* Java 22 to 25 language features are available to the pipeline and configuration code.
* The forward-compatibility legs surface regressions of newer JDKs (deprecations, behavioural changes, native-image breakage) before the next LTS forces the issue.

=== Accepted costs

* Every build, CI and native stage needs JDK 25 or newer, and no Java 21 fallback leg exists. A contributor on an older JDK must upgrade.
* Native-image builds depend on a Mandrel or GraalVM distribution for the JDK 25 line on the target platform. Verify that it is published before pinning, and re-verify when the Mandrel pin advances.
* A forward-compatibility leg can go red on a JDK the project does not ship on. Treat such a failure as a signal, pin or skip it with a tracked issue, and keep the leg present. It is not a release blocker.

=== When this is revisited

* A new LTS (Java 29, expected 2027) becomes the deploy baseline. The primary `java-version` and the Mandrel pin then rise, and the matrix re-anchors.
* A dropped dependency or a native-image constraint forces a specific JDK ceiling.
