== Status

Accepted

== Decision

A reverse proxy must convey the original client's IP, protocol and host to the upstream. Two header families exist: the de-facto trio `X-Forwarded-For`, `X-Forwarded-Proto` and `X-Forwarded-Host`, and the standardized `Forwarded` header (https://www.rfc-editor.org/rfc/rfc7239.html[RFC 7239]). The record settles which family the gateway reads, which it emits, and whom it trusts.

*The decision:* the gateway accepts both families behind a mandatory trust model and emits `X-Forwarded-*` by default.

=== Resolution through `cui-http`

The gateway writes no forwarded-header parsing of its own. It uses the `de.cuioss.http.forwarded` resolver, whose behaviour contract (precedence, sanitization, serialization) is `cui-http/doc/forwarded-header-resolution.adoc`. This record holds the posture decisions.

=== Both families on input

The gateway reads `Forwarded`, the `X-Forwarded-*` family and the NiFi `X-Proxy*` set. The resolver normalizes everything into one immutable model `{scheme, host, port, contextPath, clientIp}`.

Precedence is per field. For scheme, host, port and client IP, `X-Forwarded-*` is consulted first and RFC 7239 last. The context-path prefix comes from `X-ProxyContextPath` or `X-Forwarded-Prefix` only, because RFC 7239 defines no prefix directive.

Fixed precedence makes the highest-precedence family authoritative. Each trusted proxy must therefore manage `X-Forwarded-*`: it either appends to it or strips it. A proxy that appends only `Forwarded` and passes a client's spoofed `X-Forwarded-For` through would hand the spoofed chain the win. Where such a proxy cannot be fixed, the gateway must strip the unmanaged family before resolution.

=== A configurable canonical output

`forwarded.emit` is `x-forwarded` (the default) or `both`. `both` adds a strictly encoded `Forwarded` header in addition to `X-Forwarded-*`.

=== The trust model comes first

`forwarded.trusted_proxies` is a CIDR allowlist. Trust starts at the unspoofable TCP peer. The resolver walks the appended chain right to left and accepts entries only from allow-listed hops. The first entry from a non-trusted hop is the real client. If the immediate peer is not trusted, the gateway takes no client address from its headers. Where the gateway keys on the source, it uses the TCP peer (`SourceKeys`), and the regenerated set carries no `X-Forwarded-For`. The boot refuses a set of ranges that trusts everyone (link:0044-Trusted-proxy_breadth_is_warned_beyond_one_provisioned_network_and_refused_only_at_the_whole_address_space.adoc[ADR-0044]).

The right-to-left walk belongs to the resolver. The immediate-peer gate is gateway code, `TcpPeerGate`, because the transport-agnostic resolver consumes only a header accessor and never sees the peer. The gateway checks the peer before it consults the resolver. Without that gate, a direct client sending `X-Forwarded-For: 1.2.3.4` would have its spoofed entry honored.

=== Emission is regeneration

The gateway never appends to or forwards an inbound chain. It emits freshly generated headers from the resolved, sanitized facts, so the emitted `X-Forwarded-For` carries exactly the one resolved client. Malformed or sabotaged inbound values are dropped and logged at the gateway and never reach the upstream.

The gateway emits no `by=` parameter. The context-path prefix travels only as `X-Forwarded-Prefix`.

== Alternatives rejected

=== Emit `Forwarded` by default

The manifest lists RFC 7239 support as a requirement, and the competitive analysis framed it as a differentiator.

*Rejected because* emitting it by default buys nothing for real downstreams and adds parsing and encoding risk:

* *Inertia.* A forwarding header has value only when the downstream reads it. Rails, ASP.NET, CloudFront, AWS ELB and ALB, and Cloudflare read only `X-Forwarded-*`. A proxy emitting `Forwarded` must also emit `X-Forwarded-*` for anything to work.
* *No security payoff.* The hard problem is which hop to trust, and it is identical for both families (RFC 7239 section 8). The new syntax solves a syntax problem, not the trust problem.
* *Complexity and hazards.* RFC 7239 is a two-level, delimiter-rich grammar with conditional quoting, IPv6 bracket and port quoting, obfuscated nodes and arbitrary extensions. That yields naive comma-splitting, IPv6 mishandling, header injection through unquoted values and the "Forwarded header sabotage" class, where malformed syntax makes a strict parser discard the trustworthy entry.
* *Adoption.* nginx has no native support. Apache `mod_remoteip` reads XFF only. HAProxy has `option forwarded` only since 2.8. Envoy, Traefik and Kong use XFF, with RFC 7239 through plugins or long-open issues. CDNs and load balancers use XFF only.

=== A `Forwarded`-only emit mode

*Rejected because* XFF-only downstreams, the overwhelming majority, would silently lose client information.

=== A family accept setting

A setting could select which family the gateway accepts on input, for a proxy that does not manage `X-Forwarded-*`.

*Not implemented.* The record calls it a known, deliberate omission until a real deployment needs it.

=== Append to or forward the inbound chain

The conventional per-hop model appends to the chain it received.

*Rejected because* regeneration is the stronger defence: a malformed or sabotaged inbound value can never reach the upstream.

=== Emit `by=` with obfuscated identifiers

RFC 7239 section 6.3 suggests obfuscated identifiers to avoid leaking internal topology (sections 8.2 and 8.3).

*Rejected because* omitting the parameter avoids the leak more simply.

=== A gateway-owned parser and encoder

*Rejected because* `cui-http` already ships a spec-correct parser and encoder, hardened by the same header-value sanitization pipelines the inbound filter uses.

=== Consult RFC 7239 first

*Rejected because* consulting `X-Forwarded-*` first is consistent with the adoption reality above.

== Consequences

=== Properties of the design

* The default works with every real downstream, and the gateway can still emit RFC 7239 for a standards-conformant consumer that asks.
* The differentiator is a correct normalization of both families behind a strict trusted-proxy allowlist, and a configurable, sabotage-resistant canonical output. Competitors get this part wrong: the nginx `realip` and Kong too-broad-trust bug that breaks IP rate-limiting is the canonical example.
* The parser and encoder are not gateway code.

=== Accepted costs

* A trusted proxy that does not manage `X-Forwarded-*` hands a spoofed chain the win, and no setting covers that deployment.
