== Status

Accepted

== Decision

=== The question

The `token_validation.issuers[]` entries of the gateway configuration bind to a token-sheriff `HttpJwksLoaderConfig`. Its builder exposes about seventeen knobs. The gateway exposes a small subset, so every promoted knob is a decision, not a pass-through.

Two knobs are preconditions for the gateway working in its ordinary deployment shapes:

* *Egress.* `EgressPolicy.secureDefault()` refuses a JWKS URL that resolves to a loopback, link-local, site-local, any-local, multicast or unique-local address. Without a widening mechanism the gateway validates tokens only from a public-internet identity provider. It cannot reach a Kubernetes ClusterIP identity provider, a Docker-network deployment or an on-prem identity provider on RFC 1918 addresses. A gateway normally sits inside the same private network as the identity provider it trusts.
* *TLS trust.* The JWKS client verifies the identity provider's certificate against the JVM default trust store. An identity provider behind an internal or corporate CA, or a cluster-internal one under the cluster's own authority, fails PKIX path building. The key set never loads, and every bearer request is rejected. A trust failure then presents as a token failure.

Both must be configurable for production. This record settles how.

Two questions follow. Trust anchors live in the runtime's own named-TLS surface. If the gateway configuration referenced that surface, the product's configuration language would depend on the framework beneath it, and a change of runtime would invalidate documents operators wrote and committed. Trust material (store paths, passwords, rotation) must also live somewhere. In the gateway configuration it would put secrets in a committed document and force the gateway to re-implement key-store loading.

*The decision:* the gateway configuration names intent in API Sheriff's own vocabulary, the deployment supplies material, and exactly one component maps between them.

=== The issuer surface exposes egress and trust as neutral keys

`token_validation.issuers[].jwks` carries two production capabilities:

* `allowed_egress_hosts`: a host-exact SSRF egress allowance. It has no wildcard or suffix form.
* `tls_profile`: the name of a logical trust profile. Absent means the JVM default trust store.

Neither key, nor the JSON schema that validates them, names a runtime, a TLS registry, a truststore path or a password. `tls_profile` is a name in API Sheriff's vocabulary and carries no trust material.

[[_derived_egress_allowance]]
=== An absent `allowed_egress_hosts` derives the `jwks.url` host

The `http` issuer's allowance has two forms:

* *Absent or empty derives the allowance.* `TokenValidatorProducer` passes exactly one host to the loader's egress allowance: the host of the issuer's own `jwks.url`, spelled as the URL spells it, with any port dropped. The issuer's key endpoint is then reachable wherever it resolves.
* *A declared list is authoritative.* A non-empty list is passed entry by entry, and the `jwks.url` host is never merged into it. A list naming another host keeps the `jwks.url` host refused whenever it resolves to a private address. Declaring the list pins the allowance, so a later `jwks.url` edit to another host fails closed instead of moving the exemption.

The boot refuses a blank or whitespace-only entry and a `host:port` entry, naming the entry. It admits a bare IPv6 literal. An `http` issuer that declares no list and whose `jwks.url` names no host has nothing to derive from. It fails startup with a configuration error that names the issuer and never echoes the URL. A derived allowance never collapses into an empty one.

No dedicated key restores the no-exemption posture for an `http` issuer. An operator who wants a narrower allowance declares an explicit list. A key whose only purpose is to switch the derivation off was not added, because the explicit list already expresses every narrower posture that still loads a key set.

The derivation is not a local reversal of an upstream tightening. `EgressPolicy.secureDefault()` is unchanged, and the gateway does not replace or relax it. The gateway passes one host through the library's own `allowedEgressHost` seam, the seam a declared list uses. The link:../technical_aspects.adoc#_upstream_security_default_changes[policy on upstream security-default changes] is therefore not engaged: no upstream default changed and none is being worked around.

The field contract is in link:../configuration.adoc#_token_validation[the configuration reference].

=== Exactly one component knows the runtime binding

`JwksTrustProfileResolver` translates a logical `tls_profile` name into the runtime's named TLS configuration and then into an `SSLContext`, which it hands to the loader builder. It is the only place that knows the mapping exists. Every other collaborator, including the producer that assembles the validator, deals only in the logical name and the resulting `SSLContext`. Confining the binding to one seam keeps the gateway configuration portable: when the runtime changes, only that component follows.

=== Configuration neutral, diagnostics concrete

The neutrality rule has a deliberate scope:

* The gateway configuration and its JSON schema never name the runtime.
* Startup errors and user-facing documentation do name the concrete runtime key.

An operator who names an unbound profile needs the exact key to set. Neutrality protects the configuration contract. It is not a reason to make failures harder to diagnose.

=== An unresolvable profile refuses to start

The boot refuses a named-but-unbound profile on an `http`-sourced issuer. It never falls back to default trust. `TokenValidatorProducer.onStartup` forces the validator into existence at boot, so the failure surfaces at startup and not on the first bearer request. A `source: file` issuer opens no TLS connection and never resolves the profile, so it boots with an unbound name, and that name governs nothing (link:../configuration.adoc#_jwks_verify_hostname_profile_collision[configuration reference]).

[[_jwks_refresh_knobs]]
=== Two refresh knobs are exposed; the rest stay deferred

A knob is promoted under one discipline: a neutral key named for what API Sheriff means, with a default that preserves current behaviour. `jwks.refresh_interval_seconds` and `jwks.key_rotation_grace_period_seconds` are promoted under it:

* *Neutral names.* Both keys use the gateway configuration's snake-case vocabulary and state their unit. Neither the keys nor the schema name the library or its builder.
* *Current behaviour is preserved.* The gateway passes a key to the loader configuration only when it is declared. An omitted key leaves the builder untouched, so the library's own default applies and the gateway keeps no second copy of it.
* *Bounded at boot, by the gateway.* A value outside its range is a boot refusal naming the issuer, the key and the range. The ranges are the gateway's: the library admits every non-negative value, and the gateway refuses values the library would take.
* *Refused where they cannot act.* Either key on a `source: file` issuer is a boot refusal. A file source is read once and never refreshed, so the key would parse and change nothing.

The link:../configuration.adoc#_jwks_key_rotation[configuration reference] holds the ranges and defaults. link:0063-An_unknown_key_id_triggers_one_bounded_JWKS_refresh_per_issuer_and_the_refresh_cadence_is_configurable.adoc[ADR-0063] records the third, gateway-owned key exposed with them, the bounded refresh it governs, and why the grace period needs a gateway-side counterpart once the gateway replaces a loader itself.

Every other loader knob stays deferred, and link:../configuration.adoc#_jwks_deferred_knobs[the configuration reference lists them]. Several are production-significant, so their absence is a known gap and not an oversight. Exposing one is a separate decision under the same discipline.

== Alternatives rejected

=== Reference the runtime's named TLS configuration directly from the gateway configuration

The gateway configuration would carry the runtime's own configuration name, which removes the mapping component. This is the simplest option.

*Rejected because* it makes the product's configuration language depend on the identity of the framework beneath it. A change of runtime would break documents the product told operators to write. The mapping component is a small, bounded price for keeping the contract independent of its substrate.

=== Carry trust material inline in the gateway configuration

The gateway configuration would hold the truststore path and password, which makes the document self-contained and removes the two-place edit.

*Rejected because* it places secrets in a document meant to be reviewed and committed. It also obliges API Sheriff to re-implement key-store loading, format support and rotation the runtime already provides. That second implementation would be weaker than the first.

=== Fall back to default trust when a profile does not resolve

An unresolvable profile would log a warning and continue on the JVM default trust store.

*Rejected as the most dangerous option.* It either defers the failure to an obscure JWKS fetch error, or it succeeds quietly against anchors the operator never intended to trust when the identity provider happens to chain to a public CA. A trust decision that silently degrades is worse than one that refuses to start.

=== Expose the whole `HttpJwksLoaderConfig` builder

Every builder knob would appear in the gateway configuration mechanically.

*Rejected because* it makes the configuration surface a mirror of a dependency's API. Each promotion should be a deliberate decision about what API Sheriff means, with its own naming, defaulting and documentation. A mechanical pass-through forfeits that and freezes the dependency's vocabulary into the product's contract.

The unifying principle: the gateway configuration is the product's configuration language. Its keys are chosen for what API Sheriff means, not for what its dependencies or its runtime call things.

== Consequences

=== Properties of the design

* The gateway validates tokens against the identity providers it is placed next to: cluster-internal, Docker-network and on-prem behind an internal CA.
* Trust-store passwords never appear in the gateway configuration, so the committed document stays secret-free.
* API Sheriff consumes the runtime's key-store result and grows no second implementation.
* The same gateway configuration moves across environments that bind one profile name to different anchors, with no edit.
* A change of runtime invalidates one component, not every user's configuration.
* An issuer that omits `tls_profile` keeps the JVM default trust store, so that widening is never made by accident.
* A private-network identity provider loads its key set from the one `jwks.url` declaration.

=== Accepted costs

* *The derived entry exempts the `jwks.url` host in every deployment*, not only one whose identity provider lives on a private network. In a public-identity-provider deployment, a hostname that resolves to an internal address through a DNS change, a split-horizon resolver or a poisoned cache is dialled. The exemption is bounded to the one host the operator named as the key endpoint, and it widens nothing else. Certificate trust is untouched, so chain validation and hostname verification still refuse an endpoint that cannot prove it is that host. The threat analysis is under link:../security-threat-model.adoc#gw-05[GW-05] and link:../security-threat-model.adoc#bff-07[BFF-07].
* A private-network identity provider behind an internal CA needs an edit in two places: the profile name in the gateway configuration and the binding in deployment configuration. The indirection is the cost of portability and secret separation.
* A reader of the gateway configuration alone cannot tell which anchors a profile resolves to. The startup diagnostic and the configuration documentation compensate.

=== Risks

* *Operator confusion between the two keys.* `allowed_egress_hosts` answers "may I connect to this address?". `tls_profile` answers "do I trust the certificate I get back?". A private-network identity provider behind an internal CA needs a trust profile, and a missing one yields a failure that can look like the other. Documenting the pair together and their distinct error messages mitigate this.
* *Egress widening is a real attack-surface increase.* Each allowance entry exempts a host from an SSRF guard. Host-exactness mitigates this: a typo cannot broaden the widening.
