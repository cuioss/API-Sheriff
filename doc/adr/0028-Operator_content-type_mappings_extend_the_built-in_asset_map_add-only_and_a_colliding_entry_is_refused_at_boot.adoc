== Status

Accepted

== Decision

=== The question

The gateway-owned asset envelope sets the response `Content-Type` from the served filename's extension, through a map the gateway owns. A hostile or misconfigured upstream therefore cannot dictate how a browser interprets the bytes.

A finite map meets extensions it does not carry. An unmapped extension falls back to a generic default, which is safe but not useful: a deployment serving a font, an archive format or a domain-specific media type gets a download prompt. The set of media types is open-ended, so the deployment needs a way to name what the gateway does not know.

The obvious surface for a lookup table is an overlay: operator entries merge over the built-ins, and the last writer wins. That is wrong here, because the values in this table are security decisions. `svg` maps to `image/svg+xml` deliberately. SVG is an executable document format, and the difference between `image/svg+xml` and `text/html` is the difference between a rendered image and script executing in the gateway's own origin. Under an overlay, one line of operator configuration turns every served `.svg` into a stored-XSS delivery mechanism, through a key that looks innocuous in review.

This record settles in which direction an operator may move a security-relevant default the gateway already decided.

*The decision:* the built-in asset content-type map is immutable. The operator block extends it and never overlays it. The gateway honours a declared mapping only for an extension the built-in map does not carry, and the boot refuses an entry naming a built-in extension.

=== Built-in precedence at the lookup, not at merge time

`AssetResponseEnvelope.contentTypeFor` consults the built-in map first and returns its answer whenever one exists. It reaches the operator map only for an extension the built-in map does not carry. The two maps are never combined into one structure whose provenance is lost, so precedence holds for every extension without an exception list.

The caller passes the operator map explicitly, so the resolution holds no mutable static state and the native-image build has no build-time-snapshot hazard to reason about.

=== A colliding entry is a boot refusal

Lookup precedence alone would make a colliding entry inert, and an inert entry is worse than a refused one: the operator writes a mapping, the gateway starts, and the mapping does nothing. `AssetDefaultsRules.validateAssetContentTypesAddOnly` therefore refuses a `content_types` entry naming a built-in extension and names the offending extension. `AssetResponseEnvelope.builtInExtensions` exposes the built-in set for this check, so the validator and the lookup read one source of truth.

=== Keys are normalised and values are bounded

`AssetDefaultsConfig` lowercases declared extension keys at the model boundary, so a key's case cannot decide whether the refusal or the lookup recognises it. Otherwise `SVG` would pass the collision check, miss the built-in lookup and reintroduce the override through a spelling.

The gateway serves a mapping's value verbatim as the `Content-Type` header, so `AssetDefaultsRules.validateAssetContentTypeValues` refuses a value that is not a well-formed `type/subtype` media type.

An absent or empty block resolves every extension as an unconfigured gateway does.

== Alternatives rejected

=== Merge the operator map over the built-in defaults, last writer wins

The conventional shape for a defaults-plus-overrides block, understood by any operator and needing no special rule.

*Rejected because* it makes every gateway-decided content type a deployment-time decision, including the containment decisions. One line remapping `svg` turns a served asset into script running in the gateway's origin, and it looks unremarkable in a block whose purpose is naming unmapped formats. The surface cannot tell the two kinds of value apart, so admitting the useful override admits the dangerous one.

=== Allow override except for an explicit deny-list of security-relevant extensions

This keeps override ergonomics for the values that are formatting preferences and protects the others.

*Rejected because* the deny-list is the thing nobody maintains. It must be correct at the moment every new built-in is added, by an author thinking about a media type rather than an override surface, and an omission fails silently. It also has no principled boundary: whether a type is "active" depends on how the browser and the serving context treat it, which the gateway cannot enumerate once.

=== Allow override and mitigate at the response with `nosniff` and a `Content-Security-Policy`

This admits the full override surface and relies on the envelope's other controls to bound the damage.

*Rejected because* those controls answer a different question. `nosniff` stops the browser from disagreeing with the declared type, and it is silent when the declared type is itself the attack: an explicitly declared `text/html` is honoured as declared. A policy header narrows what the document may do, but it is a second control over a self-inflicted wound.

=== Ship no built-in map and require the operator to declare every mapping

With no defaults there is no override question, and the surface is uniform.

*Rejected because* it moves the security decision onto every deployment. The safe values are safe because the gateway chose them, and a surface where each deployment must arrive at `image/svg+xml` independently will produce deployments that do not.

The rejected options divide into two kinds. One hands a security decision to the deployment, by overlay, by omission or behind a list nobody maintains. The other keeps the decision but relies on a downstream control to blunt contradicting it. The chosen position keeps the decision where it was made, and lets the deployment add only where the gateway had no decision. A table can hold decisions and preferences that look identical at the configuration surface. Where they cannot be told apart at the point of override, the safe surface is additive.

== Consequences

=== Properties of the design

* Every gateway-decided content type is a fixed property of the gateway. A reviewer reading the built-in map reads the shipped behaviour.
* The stored-XSS lever an overlay surface would create does not exist, structurally.
* An unmapped extension can be named, which is the capability the deployment needed.
* The boot answers an operator's misunderstanding with a message naming the offending key.

=== Accepted costs

* An operator who disagrees with a built-in mapping has no configuration path, and the only route is a change to the gateway. This is intended, and a deployment with a legitimate disagreement will meet it.
* Every extension added to the built-in map narrows the operator surface: a mapping a deployment supplied for itself becomes a boot refusal on upgrade. Growing the map is a breaking change to configurations that anticipated it.
* There are two maps with an ordering rule between them, which is more to understand than one merged map.

=== Risks

* *A wrong built-in mapping is unfixable in the field.* The correction has to travel through a release.
* *A second resolution path could bypass the order.* Any path that consults the operator map without built-in-first ordering, such as a new asset source, reintroduces the override silently, because the entry it honours passed boot validation.
* *The refusal is only as good as the set it reads.* A built-in mapping added through a structure the validator does not consult would be overridable while appearing protected.
