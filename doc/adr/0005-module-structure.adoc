== Status

Superseded by link:0062-Platform_mechanisms_are_preferred_over_hand-rolled_equivalents_and_the_framework-agnostic_core_rule_is_retired.adoc[ADR-0062].

== Decision

=== The question

API Sheriff's production code lives in a single deployable Quarkus module (`api-sheriff`), alongside the `integration-tests` and `benchmarks` coordinator modules. As the request pipeline lands, that module gains a substantial body of logic that is not inherently Quarkus-specific: the immutable configuration model and validators, the event and counter system, the route table and matchers, the forward policy, and the boot-time assembly of per-route runtime objects. Only a thin outer layer is genuinely framework-bound: the CDI producers and observers, the Vert.x HTTP edge, the MicroProfile Config plumbing, and the Micrometer and SmallRye Health wiring.

This raises a question the CUI ecosystem has already answered once. Should the framework-agnostic logic move into a separate plain-Java core module, with a thin `-quarkus` binding module on top? `token-sheriff-validation` / `token-sheriff-validation-quarkus` and `token-sheriff-client` / `token-sheriff-client-quarkus` use exactly that split (`CLIENT-21`: the engine is pure Java, framework bindings sit outside it).

The heaviest framework-agnostic logic API Sheriff relies on, offline JWT validation and the entire OIDC confidential-client flow, already lives in those upstream pure-Java modules. API Sheriff consumes them and does not re-implement them. The hard parts therefore already honour the pure-core principle. What remains in the `api-sheriff` module is mostly configuration modelling plus framework glue.

*The decision:* keep a single `api-sheriff` Quarkus module for the initial releases. Do not extract a separate core module yet. Enforce a clean framework-agnostic seam by package discipline inside the one module, so extraction is cheap if and when a real second consumer appears.

=== No core module now

There is exactly one deployable, the gateway, and exactly one consumer of the framework-agnostic logic, that same deployable. The Static-mode gateway is one process, and the pure-Java engines it needs are already separate upstream modules.

=== Keep the seam clean by package layout

Framework-agnostic code lives in packages that must not import Quarkus, CDI (`jakarta.enterprise.*`, `jakarta.inject.*`), MicroProfile Config, Vert.x or Micrometer. Examples are `de.cuioss.sheriff.gateway.config.model`, `...config.validation`, `...events`, `...routing`, `...forward` and `...pipeline`. These types take their collaborators through constructor parameters, never through field or CDI injection. The boot assembles them once into the per-route `RouteRuntime`.

=== Confine framework wiring to an edge layer

CDI producers and observers, the Vert.x route handler, config-source plumbing, health and metrics binding, and the RFC 9457 exception edge live in dedicated packages (for example `...quarkus`, `...edge`). These packages may depend on the framework. They construct the framework-agnostic objects and hand them their dependencies.

=== Enforce the boundary mechanically

An ArchUnit rule (the Java arch-gate) asserts that the framework-agnostic packages import nothing from `io.quarkus..`, `io.vertx..`, `jakarta.enterprise..`, `jakarta.inject..`, `org.eclipse.microprofile..` or `io.micrometer..`. This is the single-module substitute for the compile-time guarantee a separate module would give. It is what makes a later extraction mechanical and not archaeological.

== Alternatives rejected

=== Extract a separate plain-Java core module with a thin `-quarkus` binding module now

This is the split `token-sheriff-validation` / `token-sheriff-validation-quarkus` and `token-sheriff-client` / `token-sheriff-client-quarkus` use. It would give the boundary a compile-time guarantee.

*Rejected because* a second Maven module would add a reactor node, a published artifact and a dependency edge for zero current reuse: cost without payoff. The pure-Java engines the gateway needs are already separate upstream modules, and API Sheriff's own code is predominantly configuration plus framework glue, the part that least benefits from its own module. This record is explicitly a "not yet", not a "never".

== Consequences

=== Properties of the design

* No premature module proliferation: one reactor node, one artifact, one place to build and reason about, matching the actual number of consumers (one).
* The arch-gate keeps the framework-agnostic core framework-agnostic. The day a second consumer appears (a non-Quarkus embedding, a shared offline config-lint or validate CLI, a native-image constraint that forces separation, or a reusable test harness), the extraction is a package-to-module move, not a detangling project.
* The design is consistent with the CUI precedent. The pure-Java engines are separate modules upstream.

=== Accepted costs

* An arch-gate rule enforces the boundary, not module compilation, so the boundary is only as strong as that rule. The rule must be present and part of the quality gate from the first pipeline change onward, or the seam silently erodes.
* If the framework-agnostic surface grows large and stable, the argument for a real module strengthens.

=== Revisit conditions

* A second consumer of the framework-agnostic logic materialises (a non-Quarkus host, a standalone `validate` or `lint` CLI for offline configuration checking, a portal or embedding adapter, or a shared cross-project test harness).
* Native-image or dependency constraints make the single-module layout costly.
* The arch-gate boundary proves insufficient in practice (repeated violations, or a need for the compile-time guarantee only a module split provides).

=== Shipped-surface snapshot -- 0.1.0

This section records the framework-agnostic surface as 0.1.0 actually ships it, so a later reversal has a measurable baseline and not a remembered one. It is a record of state, not a new decision.

==== The reactor at the cut

The question above names three modules. The shipped reactor carries five:

[cols="1,3", options="header"]
|===
| Module | Note

| `api-sheriff` | The one deployable Quarkus module.
| `integration-tests` | Coordinator module.
| `benchmarks` | Coordinator module.
| `demo-client` | Demo SPA plus its Playwright end-to-end suite. Added after this ADR was accepted. Carries no Java and contributes nothing to the default lane: every npm-touching execution sits inside its own `e2e-demo` profile.
| `deployment` | Deployment-shaped `docker-compose` sample. Added after this ADR was accepted. Carries no Java and builds no artifact.
|===

*The delta does not weaken the decision.* Both added modules are packaging and demonstration surfaces carrying no Java. Neither is a second consumer of the framework-agnostic logic, which is the condition the revisit conditions turn on. The count of deployables is still one.

==== The enforced package seam

`FrameworkAgnosticArchTest` enforces the boundary. It is a plain JUnit 5 test, deliberately not an ArchUnit `@AnalyzeClasses` runner, so it runs in both `test` and `verify -Ppre-commit` and is wired into the quality gate.

The agnostic set it protects at 0.1.0 is five packages:

* `de.cuioss.sheriff.gateway.config.model`
* `de.cuioss.sheriff.gateway.config.validation`
* `de.cuioss.sheriff.gateway.events`
* `de.cuioss.sheriff.gateway.forward`
* `de.cuioss.sheriff.gateway.pipeline`

[WARNING]
====
*`routing` is deliberately excluded from the enforced set, and the Decision still lists it.* That divergence is intentional and recorded here, not silently reconciled. By operator resolution of 2026-07-19, `routing.RouteRuntime` holds the shared Vert.x `HttpClient` reference and the per-route SmallRye Fault-Tolerance guard by design, so it is framework-coupled and must not be asserted framework-agnostic.

*The enforced set of five packages is the baseline, not the Decision's six.* A reader measuring the seam must read the gate, not the prose.
====

The framework set an agnostic package must never import is correspondingly wider than the Decision's list: `io.quarkus..`, `io.vertx..`, `io.smallrye..`, `io.netty..`, `org.jboss..`, `jakarta.enterprise..`, `jakarta.inject..`, `org.eclipse.microprofile..` and `io.micrometer..`. `io.smallrye..` is listed because the Fault-Tolerance guard is exactly the coupling that keeps `routing` out of the agnostic set, and leaving it unlisted would let an agnostic-core class acquire that same coupling unchecked. `io.netty..` and `org.jboss..` arrive transitively with the Quarkus and Vert.x stack and are framework by any reading of this ADR.

==== What the reversal measures against

* Five enforced agnostic packages, not six: `routing` is framework-coupled by resolution.
* One deployable, and five reactor modules, two of which carry no Java.
* A quality-gate test enforces the seam, not module compilation, so its strength is exactly the strength of that test.
