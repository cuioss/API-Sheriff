== Status

Accepted

== Decision

The gateway re-asserts HTTP framing integrity at the edge, ahead of route selection. Framing decides
where one request ends and the next begins. A gateway that disagrees with its upstream about that
boundary is the precondition for request smuggling. The framing gate (`FramingGate`) therefore
rejects several independently sufficient shapes. Among them are `Content-Length` together with
`Transfer-Encoding`, a body on a method defined as bodyless, and a `Connection` token naming a framing
or trust header. Its class documentation lists the full set.

The rejection of a body on a bodyless method is the one that meets legitimate traffic. `GET` is
defined as bodyless, but some upstream APIs accept a body on it. A search API that takes a structured
query document is the widely deployed case. A deployment in front of such an upstream sees a request
its backend understands rejected at the gateway. Its only workarounds are worse: rewriting the client
to another method, or disabling the framing defences wholesale.

The record settles what the escape hatch for that traffic looks like. Two properties of the gate make
the choice consequential.

First, the rejection is not one condition. It fires on three independently sufficient signals: an
observed body, a positive declared `Content-Length`, and `Transfer-Encoding`. As one disjunction they
look alike, and the obvious opt-in gates the whole disjunction. But the signals do not carry the same
risk. Chunked framing on a bodyless method is exactly the shape the desync defences exist to
constrain. A positive declared `Content-Length` is not: it is unambiguous framing that both ends parse
the same way. An opt-in over the disjunction buys a use case that needs one signal by admitting a
signal the use case never sends.

Second, the gate runs before route selection. Framing must be settled before the request is parsed
far enough to choose a route. So no route exists when the decision is taken, and any key at this stage
is gateway-wide whatever its configuration surface says.

*The opt-in admits exactly one thing: a positive declared `Content-Length` on `GET`. Every other leg
of the framing gate stays unconditional. The opt-in is gateway-wide because the gate runs before any
route exists to scope it to.*

=== The disjunction is split, and only one leg consults the opt-in

The gate evaluates the three signals as ordered, separate checks. It evaluates `Transfer-Encoding`
first and unconditionally: no configuration admits chunked framing on a bodyless method. Only the
declared-`Content-Length` leg consults the opt-in, and only for `GET`. `HEAD` is unaffected on every
leg. The residual leg, a body signalled without a positive declared `Content-Length`, falls through to
the rejection. So the opt-in admits nothing that is not `Content-Length`-framed.

The CL+TE rule and the framing-header-strip rule are separate checks. Scoping the opt-in to the
bodyless-method rejection cannot weaken either.

The split makes the bound structural. As one disjunction, "only the `Content-Length` case is relaxed"
would be a claim about the caller's inputs. As separate legs, it is a property of the gate.

=== The gate re-asserts its own bound

The residual leg matters even where the calling stage makes it unreachable. The gate re-checks the
body-present signal itself, so its stated bound holds under any input. This applies the principle of
link:0026-A_security_bound_declared_at_one_inbound-validation_stage_is_re-asserted_at_every_later_stage_that_re-validates_the_same_input.adoc[ADR-0026];
this record does not restate it.

=== The default is off, and the surface is gateway-wide

An omitted `security_defaults.allow_get_with_content_length_body` resolves to rejection, the behaviour
of a gateway that never declared it. The secure posture needs no configuration and cannot be reached
by accident. The key sits in the gateway-wide `security_defaults` block and is documented as
gateway-wide, because the stage it governs precedes route selection.
link:0019-Reserved_BFF_paths_bypass_the_url-parameter_value_pipeline_and_the_cookie-header_length_relaxation_is_gateway-wide.adoc[ADR-0019]
carries the other pre-route relaxation, and its gateway-wide scope has the same structural cause.

== Alternatives rejected

*Gate the whole disjunction with one opt-in.* This is the straightforward reading of "allow a body on
`GET`". It needs no split and no per-leg reasoning. Rejected because it pays for the use case in a
currency the use case never asked for. Admitting `Transfer-Encoding` on a bodyless method admits the
desync primitive itself, while the traffic being served sends a declared `Content-Length`. The
relaxation would be strictly larger than the problem for no benefit, the defining shape of an
over-broad security exception.

*Make the opt-in per-route.* This is the natural scope: only the route in front of the upstream that
needs it would relax. Rejected because it cannot be honoured where the check lives. The framing gate
runs before route selection, so no route exists to consult. Implementing it would mean either
deferring framing validation until after routing, which routes on input whose message boundaries are
not settled, a strictly worse exposure. Or it would mean a per-route key that silently behaves
gateway-wide, a surface that misstates its blast radius.

*Leave the rejection unconditional and require clients to use another method.* This is the strictest
option and keeps the gate free of configuration. Rejected because it makes the gateway unusable in
front of a class of upstream it otherwise serves correctly. The forced workaround is not neutral:
rewriting a query-bearing `GET` as `POST` discards idempotency and cacheability. A deployment that
cannot rewrite its clients is pushed toward disabling much broader protections.

*Detect the shape and admit it implicitly, with no configuration.* If a `Content-Length`-framed body on
`GET` is acceptable on request, the gate could simply accept it. Rejected because it changes the
default posture of every deployment to serve a few. It also removes the operator's declaration of
intent, the artefact that makes the wider surface reviewable. A relaxation nobody had to ask for is
one nobody knows they have.

The rejected options fall into two kinds. One kind widens the relaxation beyond the need, across
framing shapes or across every deployment by default. The other kind refuses the relaxation and pushes
the deployment toward a broader workaround. The chosen position cuts the exception to the exact shape
of the traffic, declares the scope the stage actually enforces, and keeps the default an unconfigured
gateway had.

*The diagnostic question.* When a rejection is a disjunction over several signals, an exception
against it is granted against all of them unless the disjunction is split. Before relaxing such a
rejection, ask which signals the motivating case actually produces, and what admitting each of the
others costs. Then ask where the check runs relative to the context the exception wants to be scoped
to. A key cannot be scoped to information its stage does not yet have.

== Consequences

*Positive.*

* No gateway setting admits chunked framing on a bodyless method. The desync primitive stays
  unreachable by configuration.
* The motivating traffic is served exactly, at no cost to the constraint: a client that sends a query
  document on `GET` sends it `Content-Length`-framed.
* The relaxation's stated blast radius is its enforced one, because each admitted and each refused
  shape is a separate branch.
* A deployment that does not need the capability is unaffected without acting. A deployment that
  enables it is told in the configuration surface that it did so gateway-wide.

*Negative.*

* The key is coarser than an operator would prefer. A deployment that needs a body on `GET` for one
  upstream enables it for every route. That widening is real and irreducible at this stage.
* One conceptual rule is now several branches: more code and more tests than the disjunction, on a
  rejection surface that used to be easy to check at a glance.
* An operator who reads "allow GET with body" may expect every body on `GET` to be admitted. The key's
  name and every document describing it must carry its real boundary.

*Accepted failure modes.*

* *A body that no header declares.* The gate decides on headers alone. On HTTP/2 a body can travel in
  DATA frames with no `content-length`; the gate does not see it. The upstream dispatch refuses such a
  body on its first byte, because it sends a bodyless method upstream with no body on every protocol
  (link:0060-Dispatch_sends_a_bodyless_method_no_body_and_frames_every_declared-length_body_by_exactly_that_length.adoc[ADR-0060]).

*Constraints on later change.*

* *Do not re-collapse the legs.* The split reads as redundancy: three branches with one rejection, one
  of them apparently unreachable. A simplification that merges them into a disjunction gated by the
  opt-in silently admits chunked framing, as a tidy-up with no behavioural intent.
* *Do not extend to `HEAD` by symmetry.* `HEAD` is excluded deliberately and will read as an
  oversight, because it is the other bodyless method and the change is one token. No use case needs
  it, and admitting it widens the surface for nothing.
* *Keep the boundary and its description together.* The boundary lives in one gate. Its description
  lives in the schema, the operator guide and the configuration reference. A narrowing applied to the
  gate alone leaves documents promising a wider relaxation, and the wider promise is the one an
  operator plans against.
