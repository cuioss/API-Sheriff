== Status

Accepted

== Decision

A gateway in BFF mode talks to its identity provider (IdP) directly over the back channel: discovery,
the pushed authorization request, the authorization-code exchange, refresh and refresh-token
revocation. Those calls leave the gateway over HTTPS unless the explicit cleartext opt-in
`oidc.back_channel_allow_insecure_http` is set. Boot validation admits that opt-in only together with an
`http` `oidc.back_channel_origin`; it then lets the whole OIDC client use cleartext, and it is reported
at boot as a WARN. The keys of this record act only on the HTTPS dial. All but discovery present the
client authentication credential, and the code exchange returns the material the gateway builds
sessions from.
The back channel is an egress leg in the sense of
link:0040-Upstream_hostname_verification_is_a_global_egress-TLS_knob_bound_at_client_construction.adoc[ADR-0040],
and this record applies ADR-0040's
link:0040-Upstream_hostname_verification_is_a_global_egress-TLS_knob_bound_at_client_construction.adoc#egress-tls-principle[egress-TLS principle]
to it.

A back channel whose posture the gateway does not set verifies hostnames only because the client
library defaults to it. An upstream default change would then move the posture of the leg that carries
the client credential, silently. And an operator whose IdP is reached through a name its certificate
does not carry, or presents a private-CA certificate, would have no configuration answer.

Three facts about the leg settle the mechanism.

* *The client library carries the passthrough.* The IdP client's configuration builder
  (`ClientConfiguration`) has `verifyHostname(boolean)`, which forwards to the same shared HTTP-handler
  builder the JWKS leg uses. It also has `sslContext(...)` for caller-supplied trust.
* *The library refuses the relaxation on a caller-supplied context*, for the reason
  link:0041-The_JWKS_hostname-verification_knob_is_the_librarys_own_passthrough_and_its_sslContext_collision_is_refused_at_boot.adoc[ADR-0041]
  records: the relaxation substitutes the trust manager on a context the handler derives, so a context
  the caller built has nothing to relax.
* *The leg is a different client from the JWKS back channel.* A different producer builds it, from a
  different library entry point, once per gateway rather than once per issuer, for a different endpoint
  set. That the two legs often reach the same IdP is a property of a deployment, not of the gateway.

*The BFF back channel is bound to `egress_tls` through two peer keys of its own,
`oidc_verify_hostname` and `oidc_tls_profile`. `BffRuntimeProducer` passes the hostname flag to the
library's own `verifyHostname` on every build, the `true` path included. A named profile supplies the
builder's `sslContext` and replaces the leg's anchors. The one combination the library refuses is a
boot refusal first, in the gateway's own vocabulary.*

=== Peer keys, following ADR-0040's surface rule

The keys sit beside `upstream_verify_hostname` and `jwks_verify_hostname` as peers. No bare
`verify_hostname` or `tls_profile` is introduced. Every key of the `egress_tls` block is named for its
leg. The JWKS leg's trust key stays per issuer in `jwks.tls_profile`.

The relaxation and the trust key ship together, per principle (1) of ADR-0040. The argument weighs most
on this leg: an operator who turns off hostname verification to fix a chain-trust failure has disabled a
control on the connection that carries the client credential, and still does not reach the IdP.

=== The passthrough is called on every build

`BffRuntimeProducer` resolves the global `egress_tls` block once, at bean construction. An absent block
resolves to the block's defaults, so "block omitted" and "key omitted" are the same posture:
verification on. An omitted `oidc_verify_hostname` inside a present block resolves to `true` through
ADR-0040's `EgressTlsDeserializer`. The producer passes the flag to `verifyHostname` on every build, the
`true` path included, per principle (4). The gateway writes no TLS code, per principle (2).

=== A named profile replaces the leg's anchors

`oidc_tls_profile` names a logical trust profile and carries no material. It resolves through the
mapping seam of
link:0011-gatewayyaml_exposes_JWKS_trust_and_egress_as_neutral_names_bound_by_the_deployment.adoc[ADR-0011],
through a leg-neutral entry point of `JwksTrustProfileResolver` that shares one resolution core with the
per-issuer JWKS resolution. Its refusals therefore apply to this leg exactly and cannot drift apart: an
unbound name, a trust-all profile (refused ahead of the anchor-free check), an anchor-free profile, and
material that cannot be loaded. Each refusal names `egress_tls.oidc_tls_profile`.

The resolved context replaces the JVM default trust store on this leg. A profile holding only a private
CA stops trusting public certificate authorities for the IdP.

=== The collision is refused before the builder is built

`oidc_verify_hostname: false` together with a named `oidc_tls_profile` is a boot refusal with a
`CONFIG_INVALID` naming both gateway keys, checked before the builder exists. Principle (3) of ADR-0040
and ADR-0041's reasoning carry over whole: the combination has no coherent meaning, and the library
would reject it one layer down. On this leg the collision is simpler than on the JWKS leg, because both
keys sit at the same scope.

=== Neither posture is silent

Each departure from the default that boots is a boot WARN, logged once from the single build and only on
the active BFF path. The refused pair above reports no WARN, because the refusal runs first. A
bearer-only gateway builds no IdP client. `ApiSheriff-125` reports a relaxed hostname check;
`ApiSheriff-126` reports a trust profile in effect and never carries a store path, password or anchor.
The wording of both is in link:../LogMessages.adoc[Log messages].

=== The scope claim is proven by a dial

The proof runs against a local HTTPS server that serves a discovery document under a certificate that
does not name the dialled address. It drives the producer's own configuration path:

* a *matched control* runs the same server, anchor and configuration twice, differing only in the flag;
  chain trust succeeds on both legs, so hostname verification is the only discriminator;
* an *omitted-block leg* proves that a document with no `egress_tls` resolves to verification on;
* an *untrusted-chain leg* dials a correctly named server under a root that is not an anchor, with the
  flag off, and must still be refused;
* the *collision refusal* has its own matched control: the same `false` flag without a profile
  assembles cleanly;
* a *profile leg* proves a named profile sets the context and is reported;
* *falsification checks*: deleting the `verifyHostname` call turns the relaxed leg red, and removing the
  pre-builder refusal turns the collision test red with the library's exception instead of
  `CONFIG_INVALID`.

*Deployment activation.* No shipped descriptor sets `oidc_verify_hostname`: verification on is the
shipped posture, so no deployed document has an activation for a wiring test to check. The integration
stack does name the trust profile. Its IdP serves a self-signed certificate, so every integration
descriptor with an `oidc` block declares `oidc_tls_profile`, naming the profile its JWKS issuers name. A
wiring guard pins that declaration and the profile's binding, and the stack's BFF login suites exercise
the leg through it. The same descriptors exercise the shared `egress_tls` record and its deserializer in
the native build.

=== A fitness function guards against an unbound leg

A hand-written leg enumeration does not notice the construction site it omits, so the standing guard is
a property instead: `EgressTlsPostureArchTest`, in the
four-leg shape of
link:0030-Comment-only_invariants_become_positively-phrased_fitness_functions_shipped_with_a_four-leg_control_set.adoc[ADR-0030],
fails the build when production code calls an egress TLS-client construction target without calling
that target's posture method in the same class. `ClientConfiguration#builder()` is one mapped target,
with `verifyHostname` as its posture method. Removing the call from the producer turns the rule red,
naming the producer.

== Alternatives rejected

*Leave the leg on the library default.* Bind nothing, and rely on the library keeping hostname
verification on. Rejected because it makes a security property of the gateway a property of a
dependency's release notes. ADR-0022 requires an upstream default change to be adopted deliberately,
and a posture the gateway never sets can only be inherited. It would also leave operators with a
private-CA or name-mismatched IdP no answer.

*Reuse `jwks_verify_hostname` for both IdP legs.* Treat "the identity provider" as one egress surface.
Rejected because the legs are different clients from different library entry points, and ADR-0040's
peer-key argument applies unchanged: an operator who relaxes one has no reason to relax the other. An
IdP whose discovery and token endpoints sit behind a name-mismatched ingress while its JWKS is served
from a correctly named host is an ordinary topology. A shared key would force a relaxation onto a leg
that does not need it, and its name would read narrower than it acts. It also has no coherent trust
counterpart, because the JWKS profile is per issuer and this leg's client is built once per gateway.

*Put the keys in a third vocabulary.* A nested `bff.tls` block, or keys under the `oidc` block.
Rejected because it splits egress TLS policy for one traffic direction across two places. That is the
merge of concerns ADR-0040 separated `egress_tls` from `tls` to avoid, in the opposite direction.

*Hand-roll the relaxation or a relaxed context in the gateway.* Build a delegating trust manager
locally, or derive a relaxed context from the named profile, so the relaxation and a profile could
combine. Rejected for the reasons ADR-0041 records against the same options on the JWKS leg. Passing a
caller-built context to defeat the library's guard satisfies its letter and defeats its purpose. It
moves security-critical trust-manager code into the gateway, where its failure mode, a forwarded
overload that validates nothing, is invisible in review.

*Add an integration instance per relaxation key.* A gateway instance that sets
`oidc_verify_hostname: false`, mirroring the upstream key's matched pair. Rejected because it proves
nothing the unit dial does not. The unit test performs a real TLS handshake through the producer's own
path, with a matched control and an untrusted-chain leg, and the existing descriptors already exercise
the native binding. An instance whose configuration no deployment ships would add stack start-up cost to
every integration run for a property already held twice.

Each rejected option either leaves the posture to a default, blurs which leg a key governs, or pulls TLS
code into the gateway. An egress leg's posture belongs to the gateway, is expressed in one block under a
key named for the leg, and is implemented by the library that owns the connection.

== Consequences

*Positive.*

* The leg that carries the client credential and the authorization codes has an explicit posture the
  gateway owns, independent of the library's default.
* An operator whose IdP is reached through a name-mismatched address has a narrow answer, and one whose
  IdP presents a private-CA certificate has a different, correct one.
* Every egress TLS posture key lives in one block, named for its leg.
* The trust-profile refusals are shared with the JWKS leg by construction, so the two IdP legs cannot
  diverge in how they fail closed.
* The incoherent combination fails at boot, naming keys the operator wrote.
* An unbound future leg fails the build, not a review.

*Negative.*

* *The block has five keys, and two of them usually point at the same IdP.* An operator who relaxes
  hostname verification for an IdP reached by both back channels sets two keys. That is the price of
  independently relaxable legs.
* *Two trust surfaces for one IdP sit at different scopes.* The JWKS profile is per issuer; this leg's
  is global. A deployment that binds one private CA for both names the same profile in two places.
* The gateway carries a check whose only reason is a constraint one layer down. If the library lifts
  the restriction, the refusal must be removed deliberately.

*Accepted failure modes.*

* *The relaxation is read as a general TLS disable.* The schema description, the model documentation,
  the operator pages and `ApiSheriff-125` state the hostname-only scope, and the untrusted-chain leg
  proves it.
* *The JVM can disable hostname verification below every gateway key.* The JDK system property
  `jdk.internal.httpclient.disableHostnameVerification` turns off hostname checks on every JDK-client
  leg: this one, the JWKS back channel and the asset-origin fetch. It is a start-up flag, so the
  fitness function, which reads bytecode, cannot see it. It is the deployment's responsibility and a
  named residual in the threat model.
* *A named profile silently drops public anchors.* An operator who names a profile for a private CA may
  still need a public root on the same leg. The replacement semantic is stated wherever the key appears,
  `ApiSheriff-126` included.
* *The fitness function reads per class.* A class that pins one client of a family and builds a second
  without its posture is not caught. Every class builds at most one client per family today.

*Constraints on later change.*

* A further egress leg follows ADR-0040's principle and needs no new rule: a correctly pinned leg passes
  `EgressTlsPostureArchTest` unchanged, and an unpinned one cannot land green.
