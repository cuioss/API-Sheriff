== Status

Accepted

== Decision

=== The question

The gateway validates every query parameter before it forwards a request, using the cui-http parameter
pipelines. Those pipelines expect the wire form. A character stage checks the characters a
request-target may carry. A decoding stage then percent-decodes the input once, and the decoded-form
rules run on the result: NUL, control characters, double encoding, malformed UTF-8 and injection
patterns.

The representation handed to the filter is therefore a security decision. This record settles which
representation that is. Three problems force the decision:

* *An already-decoded value gets decoded twice.* A transport that decodes for convenience turns `+`
  into a space, `%C3%BC` into `ü` and `%25` into `%`. The character stage rejects those characters. The
  decoding stage then reads a literal `%` as the start of an escape. Legitimate requests fail for reasons
  unrelated to their content.
* *What was validated is not what is forwarded.* `q=a%252F` decodes once at the transport to `a%2F`. The
  pipeline validates it as `a/`. The forward path re-encodes it to `a%252F`. The upstream receives a double
  encoding that the filter judged as a plain slash.
* *A name is input as well.* The value pipeline misses the name-specific rules: a name that decodes to a
  pair delimiter (`a%3Db`, `a%26b`) or a line break, and the name length cap. A name also has two spellings
  once the query stays encoded: the raw `%74oken` and the `token` the upstream decodes. The forward lists
  must compare the right one.

=== The filter validates the wire form, and the forward path emits it

* *The edge splits the raw request-target query, and nothing else.* It splits the query on `&` and each
  pair on its first `=`. It skips empty segments. Names and values stay percent-encoded, and `+` stays `+`.
  The pairs stay an ordered sequence in wire order (<<pair-sequence>>). A pair without `=` stays bare, so it
  crosses as `flag`, not `flag=`.
* *Names go through `PARAMETER_NAME`, values through `PARAMETER_VALUE`.* The post-route stage validates
  each raw name with the cui-http parameter-name pipeline. That pipeline rejects decoded delimiters and line
  breaks, and it enforces the name length cap. The stage validates each raw value with the parameter-value
  pipeline. Both pipelines decode once themselves, which is the input they were built for.
* *The validated pairs cross verbatim, with one exception.* The HTTP, WebSocket and gRPC dispatch paths
  append each raw name and raw value as they are, in sequence order. The validated form and the forwarded
  form are the same bytes in the same order, except that every raw `;` is written as `%3B`
  (<<semicolon-exception>>).
* *The forward lists compare the decoded name, and the raw pair crosses.* `query_allow` and `query_deny`
  match the percent-decoded name, with strict UTF-8 and `+` read as a space. The lists judge the sequence pair
  by pair and drop a pair where it stands, so the surviving pairs keep their order. Only two ASCII hex digits
  (RFC 3986 `HEXDIG`) form a percent-escape. An escape with any other digit, such as a full-width `７`, is
  malformed and is not decoded. A name with no well-formed decoding crosses only under forward-all: a
  positive-list cannot admit it, and a negative-list cannot prove it absent.
* *Consumers that need a meaning read it from the transport.* The reserved BFF parameters (`claims`,
  `returnUrl`, `state`) compare or redirect on the value's meaning, so they read the transport's decoded view.
  The reserved paths still bypass the parameter pipelines
  (link:0019-Reserved_BFF_paths_bypass_the_url-parameter_value_pipeline_and_the_cookie-header_length_relaxation_is_gateway-wide.adoc[ADR-0019]).
  The redirect and callback paths read the raw query string.

The pipeline query has exactly one representation: the wire-form pair sequence. A consumer that wants any
other form derives it at the point of use.

=== The boundary with ADR-0036

This record owns the form in which the query is validated and forwarded, and the spelling the query lists
compare.
link:0036-Forward_filtering_is_a_three-mode_policy_inside_an_authorised_route.adoc[ADR-0036] owns which
client entries cross. The two records stay apart. A forward mode from ADR-0036 selects the pairs, and the
pairs it selects cross in the form this record defines.

[[pair-sequence]]
=== Why an ordered pair sequence and not a name-keyed map

A map keyed by name cannot represent interleaved repeated names. Grouping `a=1&b=2&a=3` by name gives
`a → [1, 3], b → [2]`. Rendering that map forwards `a=1&a=3&b=2`. The filter never validated that
request-target. An upstream that reads the first or last `a` relative to `b` may also interpret it differently.

The query therefore stays an ordered sequence of raw `(name, value)` pairs from the edge split to the render
point. The filter validates each pair where it stands. The forward lists judge each pair on its own. The render
emits the surviving pairs in arrival order. A consumer that needs a lookup by name derives a grouped view at
the point of use. No security stage or forward stage does.

[[semicolon-exception]]
=== The `;` re-encoding: the single exception to verbatim forwarding

The edge splits pairs on `&` only, and the forward lists judge the decoded name of each `&`-split pair.
cui-http's query character set admits a raw `;` under every inbound-filter profile. To the gateway,
`?x=1;token=abc` is one pair named `x`. It passes `query_deny: [token]` and, under `strict`, the value pipeline.

An upstream that also splits on `;`, as some frameworks and legacy stacks do, reads a second parameter
`token=abc`. No list and no filter judged it. That is HTTP parameter smuggling (CWE-235), and forwarding the raw
pair verbatim would open it. The earlier forward path re-encoded through `URLEncoder`, which wrote `;` as `%3B`,
so verbatim forwarding without this exception would be a regression.

The forward path therefore writes every raw `;` of a forwarded name or value as `%3B`:

* The rewrite happens at the single render point, on every route, whatever the forward mode.
* The rewrite is lossless at the decoded level. The pair the upstream decodes is the pair the filter validated.
* Its spelling differs in one character, in the direction that keeps one pair one pair. Every other byte crosses
  verbatim.
* The `strict` parameter-name pipeline already rejects a `;` in a name. The rewrite covers a name on a `minimal`
  route and every value.

== Alternatives rejected

=== Keep the decoded transport view and add `%` to the query character set

Keep handing the pipeline the transport's decoded values, and add `%` to the query character set so that a decoded
literal percent passes the character stage.

*Rejected because* it treats a symptom of the double decode as its cause. Adding `%` admits only malformed
encodings, and the decoding stage still decodes the value a second time. It also leaves the forward path
re-encoding a form other than the one validated. That mismatch is the defect, and no character-set change closes it.

=== Decode once at the edge and skip the pipeline's decoding stage

Hand the pipeline decoded values and configure it not to decode again.

*Rejected because* the forward path would then have to re-encode the decoded value. A re-encoding cannot guarantee
the bytes the client sent: equivalent spellings collapse, and the upstream receives a request the client did not
make. Only the form that arrived can be validated and forwarded without a second transformation.

=== Match the forward lists against the raw name

Keep the forward policy's comparison on the name exactly as it arrived.

*Rejected because* it fails open. The upstream decodes the name before it acts on it. Encoding any character of a
listed name would therefore evade a deny list that compares raw spellings.

The rejected options share one shape: each lets the filter and the upstream see different forms of the same input.
The decision keeps one form end to end and derives any other form at the single point that needs it.

== Consequences

=== Properties of the design

* The filter's verdict describes the request the upstream receives. A value the filter rejects cannot reach the
  upstream under another encoding. The filter judges `%252F` as the double encoding it is, and rejects it.
* Legitimate values no longer fail for their encoding. A space, a `ü`, a timestamp with encoded colons and a
  literal `%` sent as `%25` all pass, because the pipeline sees the wire form it was designed for.
* The rules written for names validate names, including the length cap and the rejection of decoded delimiters.
* Percent-encoding a name cannot evade the forward lists.

=== Accepted costs

* Values that decode to `<`, `>` or `"` no longer fail merely for their spelling. The decoded-form rules and the
  injection patterns judge them, and output encoding for their context stays the upstream's job. The filter is an
  input-canonicalization and injection-pattern control, not an output-encoding one.
* Most Java APIs do not expect the pipeline query's form. A new consumer that reads it as decoded text silently gets
  the encoded spelling. The accessor and this record state the contract.

=== Risks

* *A future convenience decode at the edge reintroduces two failures at once.* The edge split is deliberately
  primitive. A transport helper that decodes brings back the double decode and the validated-versus-forwarded
  mismatch, and a happy-path test does not notice. The unit edge test asserts that the transport's decoded value
  differs from the forwarded raw value for the same request.
* *A forward-list match on the raw name reopens the evasion.* The decoded-name comparison is the fail-closed
  direction. Tests deny and admit a percent-encoded spelling of a listed name.
* *A lenient hex-digit test reopens it from the other side.* A digit test that admits non-ASCII digits (Java's
  `Character.digit`, for instance) decodes `%７４oken` to `token`. An allow list would then admit a name the raw pair
  does not spell (CWE-20). The decode accepts only `0-9`, `A-F` and `a-f`. A unit test pins that a full-width-digit
  escape crosses neither an allow list nor a deny list.
* *Regrouping the query by name breaks validated-equals-forwarded.* A map keyed by name reorders interleaved repeated
  names. The unit and edge tests pin `a=1&b=2&a=3` byte for byte under forward-all, an allow list and a deny list.
* *Dropping the `;` re-encoding reopens parameter smuggling.* A purer verbatim render hands a `;`-splitting upstream
  parameters the gateway never judged. The edge test pins `?x=1;token=abc` crossing as `x=1%3Btoken=abc` under
  forward-all, `query_deny` and `query_allow`. The native IT pins the same case against go-httpbin.
