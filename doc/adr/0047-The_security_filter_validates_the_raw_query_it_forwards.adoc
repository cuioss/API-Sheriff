== Status

Accepted

== Context

The gateway validates every query parameter before it forwards a request, and it
does so with the cui-http parameter pipelines. Those pipelines are built for the
*wire form*: a character-validation stage checks the characters a request-target
may carry, and a decoding stage percent-decodes the input exactly once before the
decoded-form rules (NUL, control characters, double encoding, malformed UTF-8,
injection patterns) run against it.

That contract makes the *representation handed to the filter* a security
decision in its own right, and two failure classes follow from getting it wrong.

**An already-decoded value is decoded a second time.** A transport that decodes
the query for convenience — `+` becomes a space, `%C3%BC` becomes `ü`, `%25`
becomes `%` — hands the pipeline characters that are not legal on the wire. The
character stage rejects them (a space, a `ü`, a `"`), and the decoding stage then
decodes what is left again: a literal `%` sent as `%25` arrives as `%` and is read
as the start of an escape. Legitimate requests are refused for reasons that have
nothing to do with their content.

**What was validated is not what is forwarded.** If the filter sees one form and
the forward path re-encodes another, the upstream receives bytes nobody checked.
`q=a%252F` is decoded once by the transport to `a%2F`, validated by the pipeline
as `a/`, and then re-encoded by the forward path to `a%252F` — the upstream is
handed a double encoding the filter judged as a plain slash. Any divergence
between the two forms is a place where the filter's verdict does not describe
the request the upstream actually processes.

A query also has *names*, and a name is input like any other. Validating names
with the value pipeline misses the name-specific rules — a name that decodes to a
pair delimiter (`a%3Db`, `a%26b`) or a line break — and ignores the name length
cap.

Finally, the forward policy matches query names against operator lists. Once the
query stays encoded, a name has two spellings — the raw `%74oken` and the
`token` the upstream decodes it to — and the list has to be compared against the
right one.

== Decision

**The security filter validates the query in its raw, still-percent-encoded wire
form, and the forward path emits exactly the pairs it validated.**

* **The edge splits the raw request-target query, and nothing else.** The query
  is split on `&` and each pair on its *first* `=`. Empty segments are skipped,
  names and values stay percent-encoded, `+` stays `+`, and pairs are grouped by
  raw name in first-seen order. A pair without `=` is kept bare, so it is
  forwarded as `flag`, not rewritten to `flag=`.
* **Names go through `PARAMETER_NAME`, values through `PARAMETER_VALUE`.** The
  per-route stage validates each raw name with cui-http's dedicated
  parameter-name pipeline — which rejects decoded delimiters and line breaks and
  enforces the name length cap — and each raw value with the parameter-value
  pipeline. Both pipelines decode once, themselves, which is the input they were
  built for.
* **The validated pairs are forwarded verbatim.** The HTTP, WebSocket and gRPC
  dispatch paths render the query by appending each raw name and raw value as-is.
  There is no re-encoding step on the forward path, so the validated form and the
  forwarded form are the same bytes.
* **The forward lists compare the decoded name; the raw pair crosses.**
  `query_allow` and `query_deny` entries are matched against the percent-decoded
  name (strict UTF-8, `+` read as a space), while the pair that crosses keeps its
  raw spelling. A name without a well-formed decoding crosses only under
  forward-all: it can neither be admitted by a positive-list nor proven absent
  from a negative one.
* **Consumers that need a meaning read it from the transport.** The reserved BFF
  parameters (`claims`, `returnUrl`, `state`) compare or redirect on the value's
  meaning, so they read the transport's decoded view rather than the pipeline
  map. The reserved paths still bypass the parameter pipelines (ADR-0019), and the
  redirect and callback paths already read the raw query string.

The pipeline map therefore has exactly one representation — the wire form — and a
consumer that wants anything else derives it at the point of use.

== Consequences

=== Positive

* The filter's verdict describes the request the upstream receives. A value the
  filter rejects cannot reach the upstream under a different encoding, and a
  double encoding such as `%252F` is judged — and rejected — as the double
  encoding it is.
* Legitimate values stop being refused for their encoding: a space, a `ü`, a
  timestamp with encoded colons and a literal `%` sent as `%25` pass, because the
  pipeline sees the wire form it was designed for.
* Names are validated by the rules written for names, including the length cap
  and the refusal of decoded delimiters.
* The forward lists cannot be evaded by percent-encoding a name.

=== Negative

* Values that decode to characters such as `<`, `>` or `"` are no longer refused
  merely for how they are spelled. They are judged by the decoded-form rules and
  the injection patterns, and output encoding for their context remains the
  upstream's job. The filter is an input-canonicalization and injection-pattern
  control, not an output-encoding one.
* The pipeline map is now in a form most Java APIs do not expect. Any new
  consumer that reads it as decoded text silently gets the encoded spelling; the
  contract is stated on the accessor and here so that the mistake is at least a
  documented one.

=== Risks

* **A future convenience decode at the edge reintroduces both failure classes at
  once.** The edge split is deliberately primitive; replacing it with a transport
  helper that decodes brings back the double decode and the validated-versus-
  forwarded mismatch without any test that exercises only the happy path noticing.
  The unit edge test pins the hand-off by asserting that the transport's decoded
  value differs from the forwarded raw value for the same request.
* **A forward-policy match on the raw name reopens the evasion.** The
  decoded-name comparison is the fail-closed direction and is pinned by tests
  that deny and admit a percent-encoded spelling of a listed name.

== Alternatives Considered

=== Keep the decoded transport view and add `%` to the query character set

Continue handing the pipeline the transport's decoded values, and widen the
query character set with `%` so that a decoded literal percent no longer fails
the character stage.

*Rejected because* it treats a symptom of the double decode as its cause. Adding
`%` to the allowed characters of an already-decoded value admits only malformed
encodings — the decoding stage would still decode the value a second time — and
it does nothing about the forward path re-encoding a different form than the one
validated. The mismatch between the two forms is the defect; no character-set
change closes it.

=== Decode once at the edge and skip the pipeline's decoding stage

Hand the pipeline decoded values and configure it not to decode again.

*Rejected because* the forward path would then have to re-encode the decoded
value, and a re-encoding is never guaranteed to reproduce the bytes the client
sent: equivalent spellings collapse, and the upstream receives a request the
client did not make. The only form that can be both validated and forwarded
without a second transformation is the one that arrived.

=== Match the forward lists against the raw name

Keep the forward policy's comparison on the name exactly as it arrived.

*Rejected because* it is fail-open. The upstream decodes the name before it acts
on it, so a deny list comparing raw spellings is evaded by encoding any character
of a listed name.

The rejected options share one shape: each lets the filter and the upstream see
different forms of the same input. The decision keeps one form end to end and
derives any other form at the single point that needs it.
