== Status

Accepted

== Decision

The gateway's standard rejection envelope is an `application/problem+json` response (link:../architecture/observability-and-errors.adoc#_error_contract[error contract]). A gRPC client's runtime does not surface an arbitrary HTTP response body. It surfaces the gRPC status in the response trailers (`grpc-status`, `grpc-message`). Two facts constrain the answer:

* A rejection may occur before the upstream is reached, so the gateway must originate a gRPC-shaped rejection, not merely relay one.
* The gateway cannot know at boot whether the upstream speaks HTTP/2. The upstream dial is forced to HTTP/2, but negotiation can still fail at dispatch.

*The decision:* a gateway-generated rejection on a `protocol: grpc` route is a trailers-only gRPC response: HTTP `200`, `content-type: application/grpc`, a HEADERS frame carrying `grpc-status` and `grpc-message`, no DATA frame and no body. `GrpcStatusMapper` maps the rejection by the HTTP status the same cause renders on an HTTP route:

[cols="1,1,2", options="header"]
|===
| gRPC status | Code | HTTP status of the same cause on an HTTP route

| `INVALID_ARGUMENT`   | 3  | `400`: inbound-filter violation
| `UNAUTHENTICATED`    | 16 | `401`: missing or invalid bearer token
| `PERMISSION_DENIED`  | 7  | `403`: valid credentials lacking an OAuth scope; failed CSRF check
| `NOT_FOUND`          | 5  | `404`: no route matched
| `UNIMPLEMENTED`      | 12 | `405`: method not in the route's effective `allowed_methods`
| `RESOURCE_EXHAUSTED` | 8  | `413`: body over the body cap
| `UNAVAILABLE`        | 14 | `502` and `503`: upstream connection failure or open circuit; also an HTTP/2 negotiation failure at the forced HTTP/2 dispatch
| `DEADLINE_EXCEEDED`  | 4  | `504`: upstream timeout
|===

Any other status maps to `UNKNOWN` (2). The trailers carry the category name only, never internal detail, the same no-leak rule the problem document enforces.

The `429` has no mapping. Every `429` the gateway sends answers a source blocked by per-source detection before route selection, so no route and no `protocol: grpc` is known when it is written. It is always the `rate-limiting` problem document (link:0076-One_per-source_detection_substrate_counts_pre-trust_rejections_and_answers_a_tripped_source.adoc[ADR-0076]).

[[_pre_trust_rejection_uniform_404]]
A rejection raised before the trust boundary does not get a trailers-only answer on the shipped default. A trailers-only status names the address as a gRPC route, and that is the disclosure link:0073-Untrusted_callers_get_the_unrouted_404_for_every_rejection_raised_before_the_trust_boundary.adoc[ADR-0073] closes. Every rejection of the link:0073-Untrusted_callers_get_the_unrouted_404_for_every_rejection_raised_before_the_trust_boundary.adoc#_the_closed_set[ADR-0073 closed set] raised after route selection and before the trust boundary gets the answer of an unrouted address: the HTTP `404`, never a `grpc-status` trailer. These are the verb gate, the `allowed_paths` check, the post-route-stage inbound filter, the declared-`Content-Length` fast-reject, the CSRF check and the missing or invalid bearer token. A gRPC client surfaces the HTTP `404` as `UNIMPLEMENTED`.

A pre-route-floor inbound-filter violation and `PARAMETER_LIMIT_EXCEEDED`, which only the pre-route floor raises today, are outside that rule. They are raised before route selection, so they are already identical whether a route exists or not. The table holds for every rejection past the trust boundary, such as `PERMISSION_DENIED` for a missing OAuth scope and `UNAVAILABLE` and `DEADLINE_EXCEEDED` at dispatch. It holds for every row when `security_defaults.uniform_not_found` is `false`.

== Alternatives rejected

=== An `application/problem+json` body on the gRPC route

*Rejected because* a gRPC client cannot use it. It surfaces as an opaque malformed-response or `INTERNAL` error that hides the real reason.

=== Only the HTTP status code, with no gRPC status

*Rejected because* a gRPC client keys on the trailers, not the HTTP status line. The caller would see `UNKNOWN`.

=== Close the stream or connection on rejection

*Rejected because* it is indistinguishable from a network failure and loses the reason entirely.

== Consequences

=== Properties of the design

* A gRPC client receives a rejection its runtime surfaces as a first-class `StatusRuntimeException` with the correct code.
* The forced HTTP/2 failure has a defined contract, `UNAVAILABLE`, so an upstream that cannot negotiate HTTP/2 fails predictably.
* The error contract governs the mapping, and unit tests cover it per row.

=== Accepted costs

* On the shipped default a gRPC client that fails before the trust boundary sees `UNIMPLEMENTED`, not the cause. That is the price of closing the disclosure.
