= API Sheriff -- FAPI 2.0 Next Steps
:toc: left
:toclevels: 3
:sectnums:
:sectnumlevels: 2

link:fapi_status.adoc[FAPI 2.0 Status] records what the BFF does today. In key mode it
implements the FAPI 2.0 controls (DPoP route). With `oidc.client_secret` configured the
client-authentication requirement is not met. This document carries only what remains open after
that. It scopes the items; it does not schedule them.

Each item states what is missing, why it is missing, and what would close it. Nothing listed here is
a control the gateway claims.

== Evidence That Is Still Owed

=== A conformance-suite run

No run of the profile's conformance test suite against the gateway exists. A suite run is the only
credible evidence for a conformance claim, and until one exists the gateway is described as
implementing the controls and nothing stronger. Deciding whether conformance is a product goal comes
first: it implies tracking the profile and repeating the run.

=== Keycloak's FAPI 2.0 client profiles

The integration realm sets its client attributes explicitly -- signed-assertion authentication, a
JWKS URL, required pushed requests, DPoP-bound tokens. It does not apply Keycloak's FAPI 2.0 client
profiles. Two things were therefore not established:

* whether those profiles enforce the issuer-only audience of the client assertion. The stack shows
  that Keycloak *accepts* the issuer as audience; it does not show that Keycloak refuses any other;
* whether those profiles enforce the algorithm list of FAPI 2.0 §5.4.1.

Running the stack with the profiles applied would settle both.

== Controls That Are Not Built

=== The mutual-TLS route

The profile permits mutual TLS in place of DPoP and `private_key_jwt`. The gateway does not offer it.
The route is alpha upstream, and at the pinned `token-sheriff-client` it is not constructible:
`MtlsClientAuth` throws in its constructor. This concerns the gateway as an OAuth client only. The
inbound client-certificate check of `tls.mtls` is a different control and is unaffected.

=== Client-secret mode

`oidc.client_secret` remains a supported configuration key, and configuring it selects
`client_secret_basic`. In that mode the client-authentication requirement stays unmet by operator
choice. The gateway reports the mode with `WARN` `ApiSheriff-133` at every boot. Nothing is planned
that would change the mode itself; closing the gap for a deployment means removing the secret and
registering the gateway's key set at the identity provider.

=== Overlapping-key rotation

Each signing key has exactly one active instance. A key is replaced by a restart, with no window in
which the old and the new key are both published or both accepted. An identity provider that does
not fetch the new client key in time refuses the calls in between. Overlap would need a second
published key and a second accepted proof key.

=== `EdDSA`

FAPI 2.0 §5.4.1 permits `EdDSA` with Ed25519. The gateway offers `PS256` and `ES256` only. For the
client-authentication key the reason is the engine: its client-assertion signer signs the `RS`, `PS`
and `ES` families and nothing else. For the DPoP proof key the reason is the gateway's own rule: the
engine's proof signer does sign `EdDSA`, and the gateway holds both keys to the same two key types
rather than adding a third for one purpose. An Ed25519 key file is refused at boot for either key.

=== Binding the authorization code to the proof key

The gateway sends no `dpop_jkt` with the pushed authorization request. FAPI 2.0 §5.3.3.1 NOTE 2 does
not require it of clients, and the engine's PAR transport attaches no proof. An authorization code
is therefore protected by PKCE and by the browser binding, and not additionally by the DPoP key.

=== Enforcing `cnf` on the gateway's own bearer routes

A `require: bearer` route validates the token offline and does not check a DPoP proof. The
validation pipeline runs DPoP checks only for an issuer that carries a DPoP configuration, and the
gateway configures none. A sender-constrained token presented without a proof is therefore accepted
on those routes. The same holds behind the gateway: the token forwarded upstream carries `cnf` and
no proof, and an upstream must not check it.

=== The step-up re-drive

The RFC 9470 step-up re-drive is assembled and its authorization request is pushed, but no edge code
calls it. Pushed requests on that seam are proven at unit level and are not reachable in a running
gateway. This is not the step-up *path* (`oidc.step_up.path`), which is live and starts a session
widening.

=== The pushed session widening on the integration stack

A session widening pushes its authorization request -- the silent attempt and the interactive
re-drive alike -- and its code exchange and the scope-driven refresh carry the DPoP proof and pass
the binding check. That is proven at unit level against a stub identity provider. The integration
suite of the widening has not been run against a realm client that requires pushed requests and
binds its tokens since the two features were combined.

== Gaps in the Engine

The following sit inside the pinned `token-sheriff-client`, below the seams the gateway wires.

=== The engine accepts an unbound token response

The engine accepts a token response of type `Bearer` to a request that carried a DPoP proof. It
compares neither the token type nor `cnf` with the sender constraint it sent. The gateway closes this
itself: `BoundTokenEndpointClient` refuses such a response at the gateway's own token-endpoint seam,
in both client-authentication modes. The check is owed upstream. There it would also do one thing
the gateway's check cannot: a refused refresh could name the refresh token to revoke. Today a
refresh token issued alongside a refused response is discarded and not revoked at the identity
provider.

=== The nonce retry resends the client assertion

The engine retries a token request once when a non-success response carries `DPoP-Nonce`. The retry
resends the same request, which in key mode includes the same client assertion. An authorization
server that enforces single use of an assertion refuses the retry.

=== A nonce on a successful response is not kept

A `DPoP-Nonce` delivered on a successful response is not carried into later requests (RFC 9449
§8.2), so the next request pays the retry again.

Whether Keycloak's token endpoint issues `DPoP-Nonce` at all was not established, so neither nonce
gap has been observed on the stack.

== Exposure That Came With the Controls

=== The login path triggers an outbound request

An unauthenticated request to the login path, or an unauthenticated navigation to a session route,
causes one authenticated outbound request from the gateway to the identity provider: the pushed
authorization request. It is signed in key mode and carries the client secret in client-secret mode.
It is bounded by the admission cap of the edge and by nothing narrower. A dedicated bound on login
initiation does not exist.

=== A client-hosted key-set URL

In key mode the identity provider fetches the client key from a URL its administrator registered.
No standards guidance was found on request forgery through a client-hosted key-set URL. The
mitigations that exist are on the identity-provider side: its fetch interval and its policy on
secure URIs. On the gateway side the endpoint publishes a public key and reads no input.

== A Follow-Up Outside the FAPI Controls

The following is not a FAPI item. It is a follow-up outside the plan that introduced the controls
above, and it is tracked separately.

=== Align the cookie sealing key with the file-based key model

The two signing keys are read from PEM files on a mount, named by path. The cookie sealing key,
`oidc.session.encryption_key`, is still a base64 value supplied through a variable. The follow-up is
to bring the sealing key in line with the file-based key model, so that all key material of a BFF
deployment is provisioned the same way.

== Out of Scope

* Authorization-server-side requirements -- the IdP's concern.
* FAPI 2.0 Message Signing (a separate profile from the Security Profile assessed here).
* Retiring the `response_mode=query` tradeoff, which is an independent decision on its own merits
  (see link:fapi_status.adoc[the status document]).
