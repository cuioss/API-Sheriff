= Build-Gate Discipline -- A Green Gate That Changed Your Files
:toc:
:toclevels: 2
:sectnums:

link:../../CLAUDE.md[`CLAUDE.md`] states the class, in its *Pre-Commit Process* section: a gate that
exits 0 can still have changed your files. This page is the detail behind that line -- which
mechanisms in this repository do it, what a contributor does about them, and the two neighbouring
rules about reading build output honestly. The class statement is not restated here; the
enforcement is named at the end.

== The three mechanisms that exit 0 while mutating the tree

Three distinct mechanisms in this repository mutate the working tree during a green
`verify -Ppre-commit` run. None of them is visible in the build result -- that is the whole
difficulty. `BUILD SUCCESS` is printed either way.

Where the tree stands today: a whole-reactor `verify -Ppre-commit` drives `rewrite:run` with the
full `pre-commit` recipe list in every module, produces *zero* `Changes have been made to`
attributions, and leaves the working tree clean. The repository is at the active recipes' fixed
point. That is a property of the tree at a point in time, not a guarantee -- the fixed point is
lost the moment a change lands that the recipes want to rewrite, and nothing announces the loss.
The three mechanisms below are what happens on that run. They are dormant, not retired, and every
rule on this page is written for the run on which they wake up.

=== OpenRewrite import-group churn

The `pre-commit` profile's `activeRecipes` override in the root `pom.xml` activates
`org.openrewrite.java.OrderImports` and `org.openrewrite.java.RemoveUnusedImports`. Against a tree
that is not already at their fixed point, they rewrite import blocks across roughly *170 files* --
almost all of them untouched by whatever branch is running the gate.

This one has a second-order effect that is easy to miss. The plan-marshall change-ledger stamps
`worktree_sha` at *build end*, so it records the *churned* tree. Reverting the churn restores the
pre-build sha, and the freshness check then reports `stale` for a commit whose gate has just
passed. A "the worktree was never verified" refusal immediately after a green gate is this
interaction, not a lost build.

*Update 2026-09-01:* this change lands the fixed point itself, so a gate run against an unmodified
`main` now rewrites nothing and neither the churn nor the freshness interaction above fires. Both
return the moment the tree drifts away from the fixed point again -- so the mechanism is documented
here as live, not retired. What changed is that the default state is now *at* the fixed point rather
than 180 files away from it, and -- per the corrected section below -- the churn a run does produce
converges in one pass, so it can be committed rather than reverted.

=== The pre-commit formatter converges in one pass (corrected 2026-09-01)

This section previously recorded the opposite -- that `org.openrewrite.java.format.AutoFormat` and
its companions "do not converge in one pass: a run takes A to B, and the next run takes B to C",
and that "run the formatter again and see if it settles" was not a diagnostic because "it will not
settle". That was measured against the *old* recipe list. It no longer holds.

*MEASURED (2026-09-01, two consecutive `verify -Ppre-commit -DskipTests` runs):* run 1 took a clean
tree to 180 changed files (113 insertions, 137 deletions). Run 2 was executed over that churned
tree *without reverting* and produced **no further change** -- the working diff against `HEAD` was
byte-identical, SHA-256 `e18290636a54e18a676d48407975840b9476e5deafb15f013603cbfb5bd5211f` on both
runs. The recipes reach their fixed point in a single pass, so running the formatter again *is* now
a valid diagnostic, and a converged tree is safe to commit.

*INFERRED, not established:* the earlier non-convergence was most likely caused by
`AutoFormat` running interleaved with the `UpgradeToJava8 -> ... -> UpgradeToJava25` migration
composite, which was removed from the recipe list in the same change that produced the measurement
above. The convergence was measured only *after* that removal, so the causal link between the two is
a hypothesis that fits the evidence, not a finding. Nobody re-ran the old list to confirm it.

The prior claim that "`main` is at the fixed point today" was also false at the time of writing:
`main` was 180 files away from it. That is what this change lands -- the fixed point itself, so the
claim becomes true rather than aspirational.

=== `SimplifyTestThrows` silently reverts an accepted narrowing

`org.openrewrite.java.testing.junit5.JUnit5BestPractices` -- also in the `pre-commit` profile's
recipe list -- reaches `SimplifyTestThrows`, which broadens a narrowed `throws` clause on a test
method back to `throws Exception`. When a review bot asks for a narrower clause and the narrowing
is implemented and then run through the gate, the recipe reverts it, and the gate exits 0 over the
reverted form. The change is gone and every visible signal says the work landed.

== The three operational consequences

=== Verify a review-bot suggestion by surviving the gate, not by implementing it

Implementing a suggestion is not evidence that the suggestion is in the tree. Run the gate, then
run `git status --porcelain`, and read the result: a file you edited that now shows as modified
against your own commit has been rewritten by the gate, and a file that shows nothing may have been
rewritten back to where it started. A suggestion is verified only by *surviving the gate*.

=== Attribute a post-gate dirty tree before reverting it

The reflex on a dirty tree is "the usual import churn, revert it and move on". That reflex is what
loses a `SimplifyTestThrows` reversion, because it discards the evidence unread.

OpenRewrite prints its attribution into the build log, as a
`Changes have been made to <file> by:` block followed by the recipe chain responsible. Read that
block before reverting anything: it distinguishes the three mechanisms above from each other and
from a genuine change of yours.

One trap in the tooling around that log: the `build-maven` rewrite-log parser can report
`verdict: not_observed` for a build in which `rewrite:run` demonstrably ran, because it keys on a
findings marker rather than on the recipe-attribution blocks. That verdict is *not* evidence that
OpenRewrite was inactive. When it disagrees with the log, the log wins.

=== Never hand-edit formatter-owned whitespace, wrapping or import order

Whitespace, line wrapping and import order belong to the formatter. Editing them by hand puts you
in a loop against a mechanism that is not idempotent: two rounds of "reformat by hand, re-run the
gate, get a different result" is not bad luck, it is a proof of the non-idempotency described
above. Stop at that point and revert the cosmetic edits rather than trying to find the arrangement
the formatter will accept -- there is not one.

== The revert rule, and the objection to it

*Revert unrelated churn; keep the rewrite only for files the branch itself authored.* A scoped pull
request carries the files its change is about.

The countervailing argument is real and should be stated rather than ignored: on a tree away from
the fixed point the reverted diff *will reappear on the next run*, so reverting it is work that has
to be repeated. That is true, and it is not a reason to commit the churn. Paying that cost once per
pull request is cheaper than polluting every scoped pull request with roughly 170 unrelated files
-- which destroys the reviewability of each one and buries the actual change.

The rule stands even though the tree is at the fixed point today, and it stands *because* of how
that fixed point is held: it is a property of the current tree rather than a guarantee about future
ones, and it is lost silently the first time a change the recipes want to rewrite lands. On that
run the churn is back and the revert-versus-commit question is live again, with the same answer.
Running `git status --porcelain` after the gate is what tells a contributor which kind of run they
are on -- there is no other signal, because the gate exits 0 either way.

== The recipe-scoping trap

A reproduction that drops the profile does not reproduce anything. `rewrite:run` *without*
`-Ppre-commit` reports `Using active recipe(s) []` and changes no file, because the recipe list
that reaches all three mechanisms is the `pre-commit` profile's `activeRecipes` override.

The failure mode is a false negative that reads as an exoneration: a narrower, faster invocation
comes back clean, and OpenRewrite appears to be innocent of a mutation it did in fact perform.
`-Ppre-commit` is load-bearing in every reproduction of anything on this page.

== The enforcement

All three mechanisms are invisible in the build result by construction, so the one thing that can
be done about them mechanically is to *report* them. link:../../.github/workflows/maven.yml[`.github/workflows/maven.yml`]
carries a `rewrite-report` job, named "OpenRewrite dirty-tree report (non-gating)", which runs the
rewriting gate itself and then prints, into the job summary, the post-gate `git status --porcelain`
listing and every `Changes have been made to <file> by:` block with its recipe chain.

The job *deliberately never fails the build on a dirty verdict*. The tree is observed clean at the
fixed point today, but that is not guaranteed to hold, and a hard fail-on-dirty gate would block
every pull request from the moment any drift lands -- including the pull requests that did not
cause it. So the job reports the dirty set and the recipe attribution and leaves the disposition to
the author. A genuine Maven or tooling failure still turns the check red; only the dirty verdict is
non-gating.

The condition under which the ADR-0030 fitness-function shape becomes the right call is a fixed
point that is *held* rather than merely observed: once drift is caught and corrected by the change
that introduces it, a positively-phrased "the tree is clean after the rewriting gate" assertion
stops being a blanket blocker and becomes an invariant worth asserting.

== A build whose output says it did nothing has verified nothing

This is the specific case of the general rule in link:../../CLAUDE.md[`CLAUDE.md`] -- a successful
build is not evidence that work happened -- applied to Maven's incremental compilation.

Maven's `testCompile` compares test-source timestamps against the compiled test classes. A change
confined to `src/main/java`, or a pure signature change, leaves every test source older than its
class file, so `testCompile` skips compilation entirely and prints
`Nothing to compile - all classes are up to date`. Plain `test` inherits the same defect, because
Surefire runs whatever is already sitting in `target/test-classes`.

*After any production-only or signature change, run `clean test-compile` -- or `clean verify`.*
That marker line in the output is the detection signal: a build that reports it has verified
nothing about the change, whatever its exit code says.

Two instances of this repository's own history are the evidence for the single rule, not two
separate rules: a production-only change that looked green and yielded *142 compilation errors*
under `clean test-compile`, and a signature change that yielded *26*.

== `-T1` reduces the flake rate; it does not cure the condition

`.mvn/maven.config` carries `-T1`. It is not a leftover, and the parallel form it replaced bought
nothing measurable. But the pin is a *measured rate reduction, not a cure*. The condition it was
introduced against is still live, and has since been measured to survive the pin four times: twice
before this investigation (both second-hand, recorded below), once by this investigation's own
31-run budget, with `-T1` re-read from `.mvn/maven.config` and confirmed in effect before the first
run -- the only instance first-hand to this document, and the strongest -- and a fourth time on
2026-09-02, by an unrelated plan's finalize gate on the same machine (recorded below; second-hand to
this document, but first-hand to the reporter rather than inherited from the destroyed artifacts).
This section was first written when the pin looked like the fix; that reading is corrected below
rather than quietly restated.

=== What the parallel form cost (MEASURED-but-second-hand)

The reactor has six modules and *one* dependency edge (`api-sheriff -> integration-tests`), so five
of the six sit in layer 0 and `-T1C` ran essentially all of them concurrently. `api-sheriff` is the
critical path at ~1886 tests; the other four finish well inside its shadow either way. The measured
wall-clock is the same to within noise -- 333-369s parallel against 359-373s serial -- so the
parallelism was not shortening the build, only loading the machine while `api-sheriff`'s
live-Vert.x-server tests were asserting over real sockets.

What it cost was determinism. Under `-T1C` the gate failed *five runs out of five*, and never twice
on the same test -- six distinct tests across those runs, all of them in
`de.cuioss.sheriff.gateway.edge`, the only package that drives live servers:

* `WebSocketRelayStageTest.mapsUnreachableUpstreamTo502` -- `TimeoutException`
* `WebSocketRelayStageTest.releasesOnceOnEstablishedRelayTeardown`
* `GatewayEdgePipelineTest.rejectsUnmodelledVerb` -- `TimeoutException` on a 15s *localhost* call
* `GatewayEdgePipelineTest.minimalRouteIsStillGovernedByThePreRouteFloor` -- `InvalidLineSeparatorException`
* `GatewayEdgePipelineTest.forwardsPostBody` -- `expected: <200> but was: <400>`
* `GrpcStatusMapperTest.appliesStageHeadersGatewayWins` -- `expected: <DENY> but was: <null>` in 34ms

Every one of them passes in isolation. The same gate on an untouched `main` fails the same way, so
this is a property of the build, not of any branch.

The symptom *shape* is what rules out the obvious readings. Timeouts alone would suggest CPU
starvation, but a malformed line separator, a spurious 400 and a response missing a header it was
handed are wire-level corruption -- bytes arriving that the client never expected -- which slowness
does not produce. Two tempting explanations were checked against the source and discarded rather
than left standing: the fixtures do *not* leak servers (`@AfterEach` closes server, client and the
`Vertx` instance, each awaited), and `Map.of()`'s randomised iteration order does not reach the one
functional failure, because `renderRejection` applies every stage header and only then overrides
`content-type`, which is order-independent.

Per the rule in "A build whose output says it did nothing has verified nothing", the serial greens
above were checked for vacuity before being believed: both runs show `Tests run: 1886, Failures: 0`
for `api-sheriff` in the reactor log, not merely a zero exit. The executor's `tests_run` field
reports only the *last* module's surefire summary (202, from `benchmarks`), so it cannot answer this
question -- read the reactor log.

=== The pin was measured insufficient, twice (MEASURED-but-second-hand)

*2026-08-31 recurrence.* The condition reproduced with `-T1` *verified in effect* -- the pin was
re-read from `.mvn/maven.config` before the runs, not assumed -- at *three runs out of three red*,
on pristine `main`. That is the measurement that retired the "the pin fixed it" reading: a fix that
is in effect and still red three times running is not a fix.

*2026-09-01 acceptance soak.* An `N=10` soak with the pin still in place returned *five RED and five
GREEN* -- a 50% per-run failure rate. Note the sample size travels with the rate: at `N=10` the 50%
figure is a coarse estimate, and it is quoted here with its `N` for exactly that reason.

The two together are why a small green streak must never be read as an all-clear on this condition.
A `4/4` green run under `-T1` was once read that way, and the 2026-08-31 recurrence is what that
reading cost.

=== The condition is macOS-local: a wildcard ephemeral bind collides with a foreign loopback listener

Two investigations feed this section and they are not interchangeable. The *2026-09-01* budget
measured the population -- how often the stall strikes, which methods, how long. The *2026-09-03*
work measured the *mechanism*, and refuted the reading 2026-09-01 had inferred. Every claim below
carries which of the two it came from, because the second one overturned a conclusion of the first
and a reader needs to be able to tell them apart.

*The mechanism, MEASURED 2026-09-03.* First-hand to the investigation that measured it, on macOS
26.6.2 (darwin 25.6.0) under JDK 25.0.1.

`.listen(0)` with no host argument binds the *dual-stack wildcard* `*:P`. Netty sets
`SO_REUSEADDR=true` on that socket, and macOS then permits the wildcard bind to take an ephemeral
port another process already holds as a `127.0.0.1`-specific listener. Both bindings coexist and
neither call fails. A client dialling `127.0.0.1:P` is then routed by BSD most-specific-match to the
*other* process, which accepts the connection and never answers it. Vert.x's acceptor sits in
`KQueue.poll` because nothing was ever queued on its listener -- it is idle *correctly*, not stuck.

Four controls establish that, and each states its own scope:

* *The live capture.* At the ceiling the JVM held only its own listener and its client socket, with
  *no server-side accepted socket*. A system-wide `lsof -iTCP:65034` named the owner: a VS Code
  helper process holding `127.0.0.1:65034 (LISTEN)` and the accepted connection, at
  `rxbytes=146 / txbytes=0` -- the request arrived and nothing was ever sent back. The system-wide
  query is the load-bearing part. A *per-process* `lsof` shows the same missing accepted socket, but
  it cannot name the foreign owner, so on its own it is suggestive rather than conclusive.
* *Deterministic reproduction (E1).* Squat `127.0.0.1:P` with a loopback-specific listener, then
  wildcard-bind Vert.x on the same `P`: the bind succeeds and the request stalls, *1 of 1*. That arm
  shows the mechanism reproduces on demand; at `N=1` it is not a rate estimate and is not quoted as
  one.
* *Matched negative control (E2).* `listen(P, "127.0.0.1")` against the same squatted port is refused
  with `BindException`. The loopback-specific bind *collides* exactly where the wildcard bind
  silently coexists, which is why the fix is a fix rather than a reshuffle.
* *The rate, with its denominator.* 179 foreign `127.0.0.1` listeners sat inside the 16384-port
  ephemeral range (49152-65535) on the machine under test, predicting *1.0925%* per `listen(0)`. A
  positive control over *20 000* ephemeral allocations measured *1.0931%*: the wildcard arm was
  handed all 179 occupied ports, and the loopback-bound arm was handed *0*. The three ports the bare
  reproducer stalled on -- 61547, 62911 and 65034 -- are all inside that occupied set.

*INFERRED.* A ~1.09% per-`listen(0)` collision rate and the ~26% per-run stall rate recorded below
are consistent rather than in tension, because a run performs many ephemeral binds and one collision
is enough to stall it. Nobody counted binds per run, so this is a consistency check between two
independently measured figures -- not a derivation of either, and not a claim that the arithmetic
closes.

*Provenance, stated because this page insists on it.* The 2026-09-03 probe sources, run logs and
population counts were working material under `.plan/temp/`, not a committed artifact. While they
exist the block above is re-checkable; once they are cleared it becomes recorded-but-not-re-checkable,
the same class as the `stabilize-edge-suite-awaits` figures further up this page. What survives the
probes is the fix, the guard and this write-up.

The 2026-09-01 investigation ran a pre-registered, non-extensible budget of *31 runs* (26 with only
`WebSocketRelayStageTest` selected, 5 whole-module), with `-T1` re-read and confirmed before the
first run. Everything attributed to that budget below is *first-hand* to it unless marked otherwise.

*MEASURED (2026-09-01).* A 30-second stall reproduced in *8 of the 31 runs* (25.8%) -- 5 of 26 on the
single-class arm, 3 of 5 on the whole-module arm. It struck *ten distinct test methods across five
classes* (`WebSocketRelayStageTest`, `GatewayEdgePipelineTest`, `GatewayEdgeRouteBffWiringTest`,
`GatewayEdgeRouteTest`, `PassthroughRelayTest`), always by hitting the fixtures' 30000 ms `Awaits`
ceiling essentially exactly -- 30004 to 30010 ms elapsed, i.e. no progress at all rather than slow
progress.

*MEASURED -- what this rules out.* Four readings are excluded by the data, not merely unsupported.
The first three are excluded by the 31-run budget; the fourth is excluded by the 2026-09-03
measurement above and carries its own provenance, because the budget could not have shown it:

* *Not reactor parallelism.* `-T1` was in effect for every one of the 31 runs.
* *Not cross-class co-tenancy inside the build.* Five of the stalls occurred on the arm that selected
  a *single* test class in a *single* Surefire fork, with no other test class in the reactor. Read
  the scope of that evidence exactly: it excludes a second test class in the same reactor as the
  disturber, and it says nothing about host CPU, I/O, file-descriptor or memory pressure originating
  outside the build. Machine load was excluded separately and later -- see the 2026-09-02
  corroboration below, which supplies the concurrent-load control this arm never carried.
* *Not connection establishment alone.* `PassthroughRelayTest.propagatesHalfCloseToBackend` stalled
  awaiting a half-close on an *already-established* connection, and the stall also strikes plain HTTP
  request/response exchanges (`timed out awaiting the edge response to GET /nowhere`), not just
  WebSocket upgrades.
* *Not an undelivered kqueue readiness event* -- MEASURED 2026-09-03, *not* by this budget. The E1/E2
  pair excludes the selector reading directly: a loopback-bound listener on a squatted port is
  *refused*, while a wildcard listener on that same port *succeeds and then stalls*. The
  discriminator is which bind the kernel accepts, not which notification the selector delivers. The
  entry sits in this list rather than in *What this run additionally eliminates* below because that
  list is scoped to what the 2026-09-02 run eliminated, and that run measured nothing about ports
  either; this elimination belongs to neither run and is attributed to the date that produced it.
+
It also resolves the bullet above it in the mechanism's favour rather than against it. A connection
that establishes and then never completes is exactly what acceptance by a *foreign* listener looks
like -- MEASURED at `rxbytes=146 / txbytes=0` in the live capture, INFERRED for the individual
`propagatesHalfCloseToBackend` occurrence, whose socket state was never captured.

*MEASURED -- the thread dumps.* On two independent occurrences, in two different fixtures, the
captured dump shows the awaiting thread parked in `Awaits` while the Vert.x acceptor thread *and all
three event-loop threads* sit simultaneously at `sun.nio.ch.KQueue.poll` via
`KQueueSelectorImpl.doSelect`. Every Vert.x thread is idle with nothing to do.

*What the dumps establish, and what they do not.* At each of the two captures, no sampled Vert.x
thread was executing. Two dumps are two instants, not a continuous observation of the stall. From
those two instants, saturation, deadlock and a blocked handler are excluded -- the work never
arrived rather than arriving late. That much still stands, and the measured mechanism agrees with
it: nothing was ever queued on the fixture's listener, so there was nothing for any of those threads
to do.

*SUPERSEDED (INFERRED 2026-09-01, refuted 2026-09-03) -- the kqueue-readiness reading.* The previous
revision of this section took the same two dumps one step further, to *a loopback readiness event
that the macOS kqueue selector never delivered*, and marked it an inference with good fit rather
than an established property. That step is now refuted. It is kept here rather than deleted because
how it failed is the useful part.

The observation was read correctly and the conclusion drawn from it was wrong. Turning "no thread
had work" into "a notification was lost" assumes the work had been queued somewhere a selector could
lose it, and it had not been queued at all. `KQueue` being the macOS-only selector implementation
then made the platform-local fit look like corroboration -- but the platform-local property is
really BSD most-specific-match routing plus what macOS permits `SO_REUSEADDR` to do, and `KQueue`
appears in the dumps only because it is where an idle acceptor waits on this platform. A component
that shows up in every stack trace of a stall is not thereby the component at fault; it may simply
be where correct idling looks the same as being stuck.

*MEASURED -- what the 2026-09-01 budget did not find.* Zero reproductions, in 31 runs, of the
separate *unexpected-upgrade-status* symptom the budget was actually sized against. That arm is
therefore *inconclusive with stated power*, never an all-clear -- see the power caveat below.

*Partly supersedes the earlier inferred mechanism -- and only partly.* The previous revision of this
section recorded a TIME_WAIT / ephemeral-port-reuse reading and this document then called it
*contradicted* by the 2026-09-01 data. That was itself an over-claim, and it is corrected here
rather than quietly softened, because the correction is to a sentence this investigation wrote.

The hypothesis has more than one form, and the evidence covers exactly one of them:

* *The listener form is contradicted.* The stall reproduced in fixtures that bind with `listen(0)`
  and *hold* the listening socket for the whole fixture lifetime. For those ports there is no
  release and no re-bind window to race, so port reuse of the *listener* cannot be the mechanism.
* *The accepted-socket and client-socket forms remain uninstrumented.* Nothing in the 31-run budget
  observed the ephemeral ports of the accepted connections or of the clients the fixtures drive --
  and those are the sockets the traffic actually crosses, and the ones that do churn ephemeral ports
  from run to run. TIME_WAIT on that side is neither confirmed nor excluded; it was never looked at.

Retiring a hypothesis on evidence that covers one of its forms is precisely the failure mode this
page exists to prevent -- "a plausible root cause is not the root cause" has a mirror image, which
is that a refuted sub-case is not a refuted case. The listener form is closed. The rest is open --
which is where this page stood until 2026-09-03, and is superseded by the paragraph that follows.

*Where that correction landed, in hindsight (2026-09-03).* The listener form was contradicted
correctly and for the right reason -- those fixtures hold the socket, so there is no release and no
re-bind window to race. The measured mechanism is nevertheless *on the listener socket*, by an
entirely different route: not reuse of a port this process released, but coexistence with a port
another process still holds. TIME_WAIT was never involved at all, and the accepted-socket and
client-socket forms left open above turned out not to be needed rather than to be the answer.

So the mirror image has a second edge. Refuting one listener-side story is what made the listener
socket look answered-for, and the passes that followed instrumented the client, the accepted socket
and the selector -- everything except the one bind call that decided the outcome. A refuted sub-case
is not a refuted case; it is also not a cleared *location*.

=== Corroboration from an unrelated plan (2026-09-02, MEASURED-but-second-hand)

A second, unrelated plan hit the same condition on the same machine while this one was in review,
and reported what it saw. It is recorded here because it adds *population and eliminations* --
nothing else. It instruments no mechanism, and it must not be read as narrowing any of the readings
left open above.

*Setup.* Branch `feature/configurable-context-path` at `4b487ec`, rebased onto `origin/main`
`82e44cc8`, so both #241 (the tiered `Awaits` ceilings) and #242 are present. Command
`verify -Ppre-commit` over the whole reactor, ~1907 tests. Six invocations, of which one is excluded
as *NO-VERDICT* -- the wrapper timed out at 522 s without producing a pass or a fail -- under the
same exclusion rule this investigation's own budget applied.

*Result.* *1 GREEN / 4 RED* across the `N=5` verdict-producing runs. The 95% interval on that is
roughly *28-99%*: consistent with the ~50% recorded above, and far too wide to refine it. This is
explicitly *not* an independent rate estimate. It was a finalize gate rather than a designed soak,
and the reporter said so.

*Post-rebase specifically.* Of the three runs after the rebase: *3 RED / 0 GREEN*, every one
carrying #241's own instrumented-ceiling wording, and every elapsed time in the *30004-30007 ms*
range against a 30000 ms ceiling. Two standing claims on this page reproduce independently there: the
stall *has never been observed to end*, and *widening a ceiling absorbs nothing* -- these runs were
red against the newer, wider instrumented ceiling exactly as earlier runs were against the older
one.

*A new site.* `GrpcStatusMapperTest.rendersUnknownMessageForNullCategory`. That class appears
earlier on this page only among the `-T1C` wire-corruption failures; neither it nor this method had
been recorded carrying the *stall* signature before.

That changes how the population reads. Eleven test classes in this repository construct a live
`Vertx.vertx()` -- verified first-hand against the tree at the time of writing:
`GatewayEdgePipelineTest`, `GatewayEdgeRouteBffWiringTest`, `GatewayEdgeRouteTest`,
`GrpcDispatchStageTest`, `GrpcStatusMapperTest`, `PassthroughRelayTest`, `ReservedBodyCeilingTest`,
`RouteRuntimeAssemblerTest`, `SniFrontListenerTest`, `TlsEdgeProducerTest` and
`WebSocketRelayStageTest`. *Seven of those eleven* have now carried the stall signature: the five
named above, plus `GrpcStatusMapperTest` by the method just named, plus `SniFrontListenerTest` --
which is counted on class timing alone (31.16 s locally against 0.944 s in CI, consistent with one
method reaching the ceiling) and is therefore *INFERRED*. Six of the seven are named down to the
method; the seventh is a class-timing inference and is not to be quoted as a measured site.

*INFERRED.* The set keeps recruiting new sites whose only shared property is `Vertx.vertx()` plus
`listen(0)` plus a fresh client. That fits a uniform per-attempt hazard -- every live-socket attempt
carrying the same probability -- better than any reading in which particular fixtures are special.
It is a reading of the accumulating population, not a measurement of the hazard.

*What this run additionally eliminates.* Two candidates that earlier passes had left standing:

* *Machine load, and with it gate cadence.* The control this page had been missing now exists. A
  parallel plan was running Maven builds in windows overlapping runs 4 and 5 *and* the single GREEN
  run (2026-09-01 23:24-23:31 local, against their 23:19-23:25 and 23:26-23:33). Concurrent load
  sits on both sides of the green/red split, so it does not separate them. Read the scope exactly:
  with one green and two reds inside the overlap this excludes concurrent-build load as *the
  discriminator* -- which is what "machine load explains the flake" requires -- and it is not a
  demonstration that host load has no effect at all.
* *The macOS application firewall.* Three settings, three separate queries -- `--getglobalstate`
  establishes only the global state, so the other two claims need their own evidence rather than
  being read off it:
+
[source,text]
----
socketfilterfw --getglobalstate   -> Firewall is disabled. (State = 0)
socketfilterfw --getblockall      -> Firewall has block all state set to disabled.
socketfilterfw --getstealthmode   -> Firewall stealth mode is off
----
+
None of the three is intercepting loopback connections.

Machine load therefore moves out of the "never formally excluded" column, and no candidate reading
on this page rests on load or on how often the gate is run.

*The CI contrast, re-confirmed at a newer commit.* Run 33596810317 on `main` at `82e44cc8`,
2026-09-02, compared same-for-same against the local run:

* `WebSocketRelayStageTest` -- 13 tests in 0.648 s in CI; 34.75 s locally, failed
* `GrpcStatusMapperTest` -- 3 tests in 0.978 s in CI; 30.59 s locally
* `ReservedBodyCeilingTest` -- 7 tests in 3.646 s in CI; 9.557 s locally
* `PassthroughRelayTest` -- 4 tests in 1.060 s in CI; 30.69 s locally
* `SniFrontListenerTest` -- 5 tests in 0.944 s in CI; 31.16 s locally

`ReservedBodyCeilingTest` is the one row that is merely slower rather than stalled -- 9.557 s is
nowhere near the ceiling -- and it is listed so the four that *are* at the ceiling are not read as
five. Alongside this, `gh run list --workflow=maven.yml --branch=main --limit=20` returned *20
successes out of 20*. The Linux lane still does not reproduce the condition.

*A trap worth its own warning: `Tests run: 0` in the CI log does not mean "skipped in CI".* The CI
log reports `Tests run: 0` for `WebSocketRelayStageTest` and `GrpcStatusMapperTest`. Taken at face
value that *inverts* the contrast above -- it reads as "these classes are not covered in CI at all",
which would make the comparison meaningless rather than damning. It is an artifact of nesting: those
lines are the outer `@Nested` containers, which carry no direct `@Test` methods, and the real tests
report under their nested display names, all green. Anyone re-deriving this contrast by grepping the
class name alone will get a false "not covered in CI" result. Match on the nested display names, or
read the surefire XML.

*One method count, stated without the conclusion it invites.*
`PassthroughRelayTest.relaysPrefixThenLiveBytes` now has a *third* recorded occurrence. That is the
count, and it is all that is being claimed: whether the method is genuinely over-represented or
merely the most-sampled one is *not* established -- no per-method sampling denominator was ever
recorded, so the two cannot be told apart from these counts.

=== State the limit of the finding precisely

What was measured in the original investigation is the causal link -- parallel fails, serial passes,
`n=7`. The mechanism is no longer inferred: it was *MEASURED* on 2026-09-03 and is recorded above
with its four controls. The chain of readings that preceded it is worth keeping in order, because
each was retired by evidence rather than by preference -- TIME_WAIT ephemeral port reuse,
contradicted in its listener form; an undelivered macOS kqueue readiness notification, refuted by
the E1/E2 pair; and finally a dual-stack wildcard ephemeral bind coexisting with a foreign
`127.0.0.1` listener, which is where the evidence now sits.

CPU and file-descriptor pressure were never formally excluded by the original work. The
all-threads-idle dumps argue against both, and the 2026-09-02 concurrent-load control recorded above
excludes machine load as the discriminator outright. File-descriptor pressure specifically still
rests on the dumps alone -- no control has ever been run against it, and the 2026-09-03 work did not
run one either. A measured mechanism for the occurrences that were captured is not an exclusion of
every other candidate; it says nothing about that one.

*Three things this does not settle.* None is closed by the fix, and none is to be quoted as closed:

* *The 5 s TEARDOWN-tier occurrence.*
  `ReservedBodyCeilingTest.retiresConnectionAfterDeclaredLengthRejection`, elapsed *5.036 s* against
  the 5000 ms teardown ceiling. A half-close against a connection a foreign process holds would
  plausibly produce it -- a conjecture with no measurement behind it. That class is also one of the
  fix sites, so its listener is now loopback-bound, which changes nothing here: binding the listener
  does not measure the teardown tier.
* *Why CI is clean.* The reading is that Linux runners hold no such `127.0.0.1`-specific listeners in
  the ephemeral range. That is *INFERRED*, and it is directly testable -- run the population probe on
  a runner and count what it finds. Nobody has.
* *Whether the mechanism accounts for every historical occurrence*, including the
  possibly-contaminated second-hand `p = 0.50` full-suite tally. The originating artifacts are
  destroyed, so that question is not merely unanswered; it is unanswerable from the record that
  survives.

*The re-opening that the previous revision said the fix did not depend on has happened.* That
sentence read "the fix does not depend on which of those it is; a re-opening of the question does",
and it was written on the premise that the pin was a fix. The 2026-08-31 recurrence retired that
premise, the question re-opened, and the mechanism turned out to matter a great deal -- the fix that
eventually landed acts on the bind call, which no reading before 2026-09-03 had pointed at.

Two power caveats travel with any green result here, and both are load-bearing:

* The `p = 0.50` rate behind the 2026-09-01 soak is *second-hand and possibly contaminated*. An
  unknown share of that historical `5 RED / 10` tally may have been this 30-second stall rather than
  the unexpected-status symptom, and the destroyed artifacts can no longer separate the two. Every
  power figure derived from it inherits that contamination.
* A zero-reproduction result is reported as *inconclusive with stated power*, carrying its `N`.
  It is never reported as an all-clear.

=== What a contributor does about it

The 2026-09-01 investigation changed no production or test code: the evidence pointed at a
host-level loopback condition and named no defect in any fixture or in the gateway, and fixing a
mechanism the evidence excludes would have been a third unmeasured fix. That restraint was correct
on the evidence then available, and the wording it produced was deliberate. The 31-run budget was
pre-registered against a *different* symptom -- an unexpected upgrade status -- and found the stall
instead; it audited no fixture and no gateway path. "Named no defect" is what was observed. "There
is no defect" is a universal negative the budget was never shaped to establish.

*That changed on 2026-09-03, and a fix has landed.* The defect was in the fixtures after all, and it
was one call. Every live-socket fixture bound its ephemeral server with the single-argument
`listen(0)` overload -- the dual-stack wildcard -- while the client in that same fixture dialled
`127.0.0.1`. All *20* such sites across *9* files now bind through `LoopbackHost.ADDRESS` in
`de.cuioss.sheriff.gateway.testsupport`, and every `Awaits` ceiling now folds a `SocketSnapshot`
capture of the kernel's own view -- `lsof` for this pid, plus `netstat` in whichever spelling the
platform takes (`-anv -p tcp` on macOS, `-ant` on Linux) -- into its timeout message. A future
occurrence therefore arrives with its evidence attached, instead of requiring another investigation
to go and obtain it.

[NOTE]
====
*The netstat half was macOS-only when it first landed, and CI is what caught it.* The original
invocation and the port pattern were both macOS spellings: Linux reads `-p` as _show-program_ rather
than as a protocol selector, and prints `127.0.0.1:59120` where macOS prints `127.0.0.1.59120`. The
half therefore produced nothing usable on Linux.

Two beliefs were wrong at once, which is why it survived local verification. The first was that
`netstat` is absent from `ubuntu-latest` -- it is present, so the capture's availability probe
returned true and the half ran rather than abstaining. The second was structural: the probe asserting
the capture had worked scanned the *combined* section, so `lsof` output satisfied it on a run where
`netstat` contributed nothing. Splitting that assertion per tool is what turned an invisible
degradation into a red build.

The general shape is the one this page keeps re-learning: a check whose green is satisfiable by a
neighbour is not a check on the thing it names.
====

*The condition is not thereby closed.* What landed removes the measured transport-level cause. No
post-fix rate has been measured, the quarter-of-runs figure below is a *pre-fix* rate, and the three
items under *State the limit of the finding precisely* are all still open. Read a post-fix green
streak the way this page has already had to learn to read one: as absence of evidence at some
unstated `N`, never as an all-clear.

* *A single red edge-suite run on macOS is not evidence of a branch defect.* Establish provenance
  before acting on it -- roughly a quarter of local runs of this suite carried the stall before the
  fix. If one appears after it, read the `SocketSnapshot` block in the timeout message first. Read
  it for what it can actually show: `lsof` runs with `-p <this pid>` and `netstat` is filtered to
  the ports that per-process view returned, so the block is *this JVM's socket state* and cannot
  name the foreign process that owns a colliding listener. A `SYN_SENT` with no established peer, or
  no socket for the port at all, is the shape that points back at this condition. To identify an
  owner you need a system-wide lookup the snapshot does not perform -- `lsof -nP -iTCP:<port>`
  without `-p`, run by hand while the stall is live.
* *Establish that provenance against CI, not against a local re-run.* For the 30-second stall
  signature specifically, the Linux lane is the authority: it has never reproduced that signature,
  so a red there is a real defect rather than this condition. It is *not* the authority for macOS
  behaviour in general -- this very section argues the condition under study is macOS-local, and a
  genuine macOS-only regression is exactly the case a green Linux lane cannot clear.
* *Do not widen the `Awaits` ceilings and do not retry-wrap or quarantine the affected fixtures.*
  The 30-second ceiling is what makes the condition visible and measurable; raising it would hide
  the phenomenon rather than address it. It is now also the *capture* point -- widening it delays
  the socket-state snapshot, on top of hiding the stall, so the one moment the kernel's own view of
  the stalled socket is recorded moves further from the event that prompted it.
* *Do not change `-T1`.* It is a measured rate reduction and is still worth having; it is simply not
  a cure.
* *Bind every new live-socket fixture through `LoopbackHost.ADDRESS`* -- never a bare `listen(0)` or
  `new ServerSocket(0)`. `LoopbackEphemeralBindArchTest` is the fitness function that enforces this
  and fails the build on either spelling. It rejects the bare overload outright and does *not* check
  whether the socket is later dialled, so "it is never dialled" is not a defence at review time; it
  is the reason a carve-out was granted, not a test the guard performs.
+
The carve-out is `TlsEdgeProducerTest` *as a class*, its nested classes included -- not a list of
individual sites. The guard therefore protects none of that class, and a new bare bind added
anywhere in it will pass. Its existing wildcard binds serve two different purposes: the collision
holders occupy a port so a *wildcard* production bind is refused, and `freePort()` wildcard-binds to
allocate a candidate and again to re-probe it against the bind scope production will use. Both are
recorded in place. A new fixture belongs outside this class unless it genuinely needs a wildcard
bind, because moving it inside silently removes it from the guard.
+
A companion source sweep in the same class catches the wildcard *host literal* -- `listen(0,
"0.0.0.0")` -- which the bytecode rule structurally cannot see, since that call and
`listen(0, LoopbackHost.ADDRESS)` are the same call target. The sweep is a net rather than a parser:
it reaches one level of nested parentheses in the port argument and no further, and that limit is
recorded next to the pattern.

== Two rules about reading a check's output

=== An ERROR from a guard is a statement about the guard, not about its subject

When a guard, gate or analysis step reports an error, the first reading is almost always "the thing
being checked is broken". Frequently the correct reading is "the check could not evaluate" -- a
missing input, an unresolvable path, a tool that never started.

Establish that the check actually ran before treating its output as a finding about its subject.
Establish the same before treating a *green* as evidence: a check that silently could not run
reports success indistinguishable from a real pass, and that is the more dangerous half of this
rule. An error at least draws attention to itself.

=== A plausible root cause is not the root cause

A story that explains every symptom is not thereby true. An explanation that fits all the available
facts is a hypothesis with good fit, and it survives exactly until someone re-derives it against
the implementing source -- at which point a comfortable, load-bearing explanation can turn out to
describe code that does not exist.

Before a diagnosis is acted on, read the implementation it claims to describe.
