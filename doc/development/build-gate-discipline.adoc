link:../../CLAUDE.md[`CLAUDE.md`] states the class, in its *Pre-Commit Process* section: a gate that
exits 0 can still have changed your files. This page is the detail behind that line -- which
mechanisms in this repository do it, what a contributor does about them, the BOM import order a
clean build cannot show to be wrong (<<quarkus-bom-first>>), and the two neighbouring rules about

port holders a contributor workstation can carry (<<foreign-loopback-port-holders>>). The class
statement is not restated here; the enforcement is named at the end.

== The three mechanisms that exit 0 while mutating the tree

Three distinct mechanisms in this repository mutate the working tree during a green
`verify -Ppre-commit` run. None of them is visible in the build result -- that is the whole
difficulty. `BUILD SUCCESS` is printed either way.

Where the tree stands today: a whole-reactor `verify -Ppre-commit` drives `rewrite:run` with the
full `pre-commit` recipe list in every module, produces *zero* `Changes have been made to`
attributions, and leaves the working tree clean. The repository is at the active recipes' fixed
point. That is a property of the tree at a point in time, not a guarantee -- the fixed point is
lost the moment a change lands that the recipes want to rewrite, and nothing announces the loss.
The three mechanisms below are what happens on that run. They are dormant, not retired, and every
rule on this page is written for the run on which they wake up.

What the same run did rewrite was *four test sources the branch had just authored* -- and that is the
distinction the paragraph above hides. "At the fixed point" is a property of the sources already in
the tree. Sources a branch adds have never been past the recipes, so the first gate run that sees
them pulls them in, and it does so by construction rather than by drift. The recipes involved are
named in <<junit5-best-practices>>. Read the practical consequence off the revert rule further down
rather than off the count: churn in files the branch itself authored is *kept*, and the fixed point
is regained by committing the normalized form -- which is a different disposition from the unrelated
churn the same rule says to revert.

=== OpenRewrite import-group churn

The `pre-commit` profile's `activeRecipes` override in the root `pom.xml` activates
`org.openrewrite.java.OrderImports` and `org.openrewrite.java.RemoveUnusedImports`. Against a tree
that is not already at their fixed point, they rewrite import blocks across roughly *170 files* --
almost all of them untouched by whatever branch is running the gate.

This one has a second-order effect that is easy to miss. The plan-marshall change-ledger stamps
`worktree_sha` at *build end*, so it records the *churned* tree. Reverting the churn restores the
pre-build sha, and the freshness check then reports `stale` for a commit whose gate has just
passed. A "the worktree was never verified" refusal immediately after a green gate is this
interaction, not a lost build.

A gate run against an unmodified `main` rewrites nothing today, so neither the churn nor the
freshness interaction fires by default. Both return the moment the tree drifts away from the fixed
point -- the mechanism is live, not retired -- and the churn a run does produce converges in one pass
(next section), so it can be committed rather than reverted.

=== The pre-commit formatter converges in one pass

`org.openrewrite.java.format.AutoFormat` and its companions reach their fixed point in a single pass,
so running the formatter again *is* a valid diagnostic, and a converged tree is safe to commit.

*MEASURED (two consecutive `verify -Ppre-commit -DskipTests` runs):* run 1 took a clean tree to 180
changed files (113 insertions, 137 deletions). Run 2 was executed over that churned tree *without
reverting* and produced **no further change** -- the working diff against `HEAD` was byte-identical,
SHA-256 `e18290636a54e18a676d48407975840b9476e5deafb15f013603cbfb5bd5211f` on both runs.

An older recipe list did *not* converge: a run took A to B and the next took B to C. *INFERRED, not
established:* that was most likely caused by `AutoFormat` running interleaved with the
`UpgradeToJava8 -> ... -> UpgradeToJava25` migration composite, which was removed from the recipe
list in the same change that produced the measurement above. Convergence was measured only *after*
that removal, and nobody re-ran the old list, so the causal link is a hypothesis that fits the
evidence, not a finding.

*MEASURED -- convergence re-confirmed, on a much smaller sample.* A branch adding four
test sources ran the gate four times in sequence. Run 1 rewrote all four and printed their
attribution blocks. The rewrite was kept, three further corrections were authored on top, and run 2
produced *zero* attribution blocks -- so one pass reached the fixed point here too. The normalized
form was then committed, and runs 3 and 4 over that committed tree each exited 0 and left
`git status --porcelain` *empty*. `rewrite:run` was confirmed active on every one of them
(`Using active recipe(s) [...]`, seventeen recipes, in every module), which is what separates a
converged tree from the `Using active recipe(s) []` false negative the
<<the-recipe-scoping-trap,recipe-scoping trap>> describes.

Read the sample for what it is -- four files rather than 180, and a different recipe set doing the
rewriting -- so it corroborates the 180-file measurement rather than re-establishing it.

[[junit5-best-practices]]
=== `JUnit5BestPractices` rewrites test sources, and one of its sub-recipes inverts an assertion

`org.openrewrite.java.testing.junit5.JUnit5BestPractices` -- also in the `pre-commit` profile's
recipe list -- is a composite, and three of the sub-recipes it reaches rewrite ordinary,
correctly-written test code. All three were *MEASURED (2026-09-21)* on one branch's four
newly-authored test sources, each read out of the gate log's own attribution blocks:

`SimplifyTestThrows`:: Broadens a narrowed `throws` clause on a test method back to
`throws Exception`. When a review bot asks for a narrower clause and the narrowing is implemented and
then run through the gate, the recipe reverts it, and the gate exits 0 over the reverted form. The
change is gone and every visible signal says the work landed. It also strands the Javadoc: an
`@throws TimeoutException` tag survives a signature the recipe has rewritten to `Exception`, and
nothing in the gate notices.

`TestsShouldNotBePublic`:: Drops `public` from a test class. Harmless where nothing outside the
package needs the type -- but it is a *visibility* change applied to source the author just wrote,
so it belongs on this page rather than in the surprise column.

`AssertionsArgumentOrder`:: *The one to watch.* It moves what it takes to be the expected value into
the first argument -- and it reads a *constant reference* as the expected value and a *method call*
as the actual. So `assertEquals(Duration.ofSeconds(5), SOME_CONSTANT)` is rewritten to
`assertEquals(SOME_CONSTANT, Duration.ofSeconds(5))`, which **inverts expected and actual** and
therefore inverts every failure message that assertion can produce. The assertion still passes, so
nothing draws attention to it; only a later failure shows the inversion, at the moment it is least
convenient. Write the assertion with a *literal* in the expected position -- `assertEquals(5,
SOME_CONSTANT.toSeconds(), "...")` -- which is already at the recipe's fixed point and keeps the
conventional order.

The general point is the one the revert rule makes: a branch's own new test sources get rewritten on
their first gate run, that rewrite is *kept* rather than reverted, and it is reviewed before it is
kept. `AssertionsArgumentOrder` is why the review is not a formality.

== The three operational consequences

=== Verify a review-bot suggestion by surviving the gate, not by implementing it

Implementing a suggestion is not evidence that the suggestion is in the tree. Run the gate, then
run `git status --porcelain`, and read the result: a file you edited that now shows as modified
against your own commit has been rewritten by the gate, and a file that shows nothing may have been
rewritten back to where it started. A suggestion is verified only by *surviving the gate*.

=== Attribute a post-gate dirty tree before reverting it

The reflex on a dirty tree is "the usual import churn, revert it and move on". That reflex is what
loses a `SimplifyTestThrows` reversion, because it discards the evidence unread.

OpenRewrite prints its attribution into the build log, as a
`Changes have been made to <file> by:` block followed by the recipe chain responsible. Read that
block before reverting anything: it distinguishes the three mechanisms above from each other and
from a genuine change of yours.

One trap in the tooling around that log: the `build-maven` rewrite-log parser can report
`verdict: not_observed` for a build in which `rewrite:run` demonstrably ran, because it keys on a
findings marker rather than on the recipe-attribution blocks. That verdict is *not* evidence that
OpenRewrite was inactive. When it disagrees with the log, the log wins.

=== Never hand-edit formatter-owned whitespace, wrapping or import order

Whitespace, line wrapping and import order belong to the formatter -- not in the sense that it
prefers them, but in the sense that it *writes* them, on every run, from its own rules. Editing
them by hand therefore puts you in a loop against ownership: the gate reasserts its own output and
your arrangement is reverted, so "reformat by hand, re-run the gate, get a different result" is the
mechanism working exactly as specified rather than a fault in it. Stop at that point and revert the
cosmetic edits rather than trying to find the arrangement the formatter will accept -- the only
arrangement it accepts is the one it produces itself.

== The revert rule, and the objection to it

*Revert unrelated churn; keep the rewrite only for files the branch itself authored.* A scoped pull
request carries the files its change is about.

The countervailing argument is real and should be stated rather than ignored: on a tree away from
the fixed point the reverted diff *will reappear on the next run*, so reverting it is work that has
to be repeated. That is true, and it is not a reason to commit the churn. Paying that cost once per
pull request is cheaper than polluting every scoped pull request with roughly 170 unrelated files
-- which destroys the reviewability of each one and buries the actual change.

The rule stands even though the tree is at the fixed point today, and it stands *because* of how
that fixed point is held: it is a property of the current tree rather than a guarantee about future
ones, and it is lost silently the first time a change the recipes want to rewrite lands. On that
run the churn is back and the revert-versus-commit question is live again, with the same answer.
Running `git status --porcelain` after the gate is what tells a contributor which kind of run they
are on -- there is no other signal, because the gate exits 0 either way.

[[the-recipe-scoping-trap]]
== The recipe-scoping trap

A reproduction that drops the profile does not reproduce anything. `rewrite:run` *without*
`-Ppre-commit` reports `Using active recipe(s) []` and changes no file, because the recipe list
that reaches all three mechanisms is the `pre-commit` profile's `activeRecipes` override.

The failure mode is a false negative that reads as an exoneration: a narrower, faster invocation
comes back clean, and OpenRewrite appears to be innocent of a mutation it did in fact perform.
`-Ppre-commit` is load-bearing in every reproduction of anything on this page.

== The enforcement

All three mechanisms are invisible in the build result by construction, so the one thing that can
be done about them mechanically is to *report* them. link:../../.github/workflows/maven.yml[`.github/workflows/maven.yml`]
carries a `rewrite-report` job, named "OpenRewrite dirty-tree report (non-gating)", which runs the
rewriting gate itself and then prints, into the job summary, the post-gate `git status --porcelain`
listing and every `Changes have been made to <file> by:` block with its recipe chain.

The job *deliberately never fails the build on a dirty verdict*. The tree is observed clean at the
fixed point today, but that is not guaranteed to hold, and a hard fail-on-dirty gate would block
every pull request from the moment any drift lands -- including the pull requests that did not
cause it. So the job reports the dirty set and the recipe attribution and leaves the disposition to
the author. A genuine Maven or tooling failure still turns the check red; only the dirty verdict is
non-gating.

The condition under which the
link:test-corpus-integrity.adoc#fitness-function-shape[fitness-function shape] becomes the right call is a fixed
point that is *held* rather than merely observed: once drift is caught and corrected by the change
that introduces it, a positively-phrased "the tree is clean after the rewriting gate" assertion
stops being a blanket blocker and becomes an invariant worth asserting.

== A build whose output says it did nothing has verified nothing

This is the specific case of the general rule in link:../../CLAUDE.md[`CLAUDE.md`] -- a successful
build is not evidence that work happened -- applied to Maven's incremental compilation.

Maven's `testCompile` compares test-source timestamps against the compiled test classes. A change
confined to `src/main/java`, or a pure signature change, leaves every test source older than its
class file, so `testCompile` skips compilation entirely and prints
`Nothing to compile - all classes are up to date`. Plain `test` inherits the same defect, because
Surefire runs whatever is already sitting in `target/test-classes`.

*After any production-only or signature change, run `clean test-compile` -- or `clean verify`.*
That marker line in the output is the detection signal: a build that reports it has verified
nothing about the change, whatever its exit code says.

Two instances of this repository's own history are the evidence for the single rule, not two
separate rules: a production-only change that looked green and yielded *142 compilation errors*
under `clean test-compile`, and a signature change that yielded *26*.

== `-T1` reduces the flake rate; it does not cure the condition

`.mvn/maven.config` carries `-T1`. It is not a leftover. The parallel `-T1C` form it replaced bought
nothing measurable and cost determinism, but the pin is a *measured rate reduction, not a cure*: the
local edge-suite stall it was introduced against survived it repeatedly, and its transport-level
cause turned out to be a single bind call in the test fixtures.

Some of the figures below are *second-hand*: they were measured by an earlier investigation whose
evidence artifacts no longer exist, so they are reported as recorded rather than as re-checkable.
The mechanism and its controls are first-hand to the investigation that measured them. Each claim
below carries its weight -- MEASURED, INFERRED or reported -- because the record contains readings
that were later refuted, and a reader needs to tell which kind a sentence is.

=== What the parallel form cost

The reactor has six modules and one dependency edge (`api-sheriff -> integration-tests`), so `-T1C`
ran nearly all of them concurrently. `api-sheriff` is the critical path; the measured wall-clock
was the same to within noise (333-369 s parallel against 359-373 s serial). The parallelism did not
shorten the build. It only loaded the machine while `api-sheriff`'s live-Vert.x-server tests were
asserting over real sockets.

Under `-T1C` the gate failed *five runs out of five*, never twice on the same test, and always in
`de.cuioss.sheriff.gateway.edge` or one of its sub-packages -- the only package tree that drives live
servers. Every failing test passed in isolation, and an untouched `main` failed the same way. The
symptom shape ruled out plain slowness: besides timeouts it included a malformed line separator, a
spurious `400` and a response missing a header it was handed -- wire-level corruption, which CPU
starvation does not produce. Fixture server leaks and `Map.of()` iteration order were checked
against the source and excluded.

*MEASURED-but-second-hand -- the pin is insufficient.* With `-T1` re-read from `.mvn/maven.config`
and confirmed in effect, the condition reproduced at three runs out of three on pristine `main`, and
an `N=10` soak returned five red and five green. A small green streak under `-T1` is therefore never
an all-clear; a `4/4` green run was once read that way, and the recurrence is what that reading cost.

A serial green was itself checked for vacuity before being believed: the reactor log shows the
`api-sheriff` test count with zero failures, not merely a zero exit. The executor's `tests_run`
field reports only the *last* module's Surefire summary, so it cannot answer that question -- read
the reactor log.

=== The mechanism: a wildcard ephemeral bind coexists with a foreign loopback listener

*MEASURED, on macOS under JDK 25.* `.listen(0)` with no host argument binds the *dual-stack
wildcard* `*:P`. Netty sets `SO_REUSEADDR=true` on that socket, and macOS then permits the wildcard
bind to take an ephemeral port another process already holds as a `127.0.0.1`-specific listener.
Both bindings coexist and neither call fails. A client dialling `127.0.0.1:P` is routed by BSD
most-specific-match to the *other* process, which accepts the connection and never answers it.
Vert.x's acceptor sits in `KQueue.poll` because nothing was ever queued on its listener -- it is
idle *correctly*, not stuck.

Four controls establish that, and each states its own scope:

* *The live capture.* At the ceiling the JVM held only its own listener and its client socket, with
  *no server-side accepted socket*. A system-wide `lsof -iTCP:<port>` named the owner -- a VS Code
  helper process holding `127.0.0.1:<port> (LISTEN)` and the accepted connection at
  `rxbytes=146 / txbytes=0`: the request arrived and nothing was sent back. The system-wide query is
  the load-bearing part; a per-process `lsof` shows the missing accepted socket but cannot name the
  foreign owner.
* *Deterministic reproduction (E1).* Squat `127.0.0.1:P` with a loopback-specific listener, then
  wildcard-bind Vert.x on the same `P`: the bind succeeds and the request stalls, *1 of 1*. That
  shows the mechanism reproduces on demand; at `N=1` it is not a rate estimate.
* *Matched negative control (E2).* `listen(P, "127.0.0.1")` against the same squatted port is refused
  with `BindException`. The loopback-specific bind *collides* exactly where the wildcard bind
  silently coexists, which is why the fix is a fix rather than a reshuffle.
* *The rate, with its denominator.* 179 foreign `127.0.0.1` listeners sat inside the 16384-port
  ephemeral range (49152-65535) on the machine under test, predicting *1.0925%* per `listen(0)`. A
  positive control over *20 000* ephemeral allocations measured *1.0931%*: the wildcard arm was
  handed all 179 occupied ports, the loopback-bound arm *0*. The ports the bare reproducer stalled on
  are all inside that occupied set.

*The population, MEASURED before the fix.* A pre-registered budget of 31 runs with `-T1` confirmed
in effect reproduced a 30-second stall in *8 of 31* (about 26%), across ten test methods in five
classes, always at the fixtures' 30000 ms `Awaits` ceiling to within 10 ms -- no progress at all,
rather than slow progress. Later gate runs extended it: seven of the eleven test classes that
construct a live `Vertx.vertx()` have carried the signature (one of them inferred from class timing
alone). *INFERRED:* a ~1.09% per-bind collision rate and a ~26% per-run stall rate are consistent,
because a run performs many ephemeral binds and one collision is enough -- a consistency check
between two measured figures, not a derivation of either.

*What the data excludes.* Reactor parallelism (`-T1` was in effect throughout); a second test class
as the disturber (stalls occurred with a single class in a single Surefire fork); connection
establishment alone (an already-established half-close and plain request/response exchanges stalled
too); concurrent build load as the discriminator (load sat on both sides of the green/red split,
which does not show load has no effect); the macOS application firewall (global state, block-all and
stealth mode each queried separately, all off); and an undelivered kqueue readiness event (the E1/E2
pair discriminates on which bind the kernel accepts, not on which notification the selector
delivers). Thread dumps at two stall instants showed the acceptor and every event loop parked in
`KQueue.poll`; that is consistent with the mechanism, and the live capture and E1/E2 carry the
conclusion.

*How the earlier readings were retired.* The record holds a chain of readings, each retired by
evidence rather than preference: TIME_WAIT ephemeral-port reuse, contradicted in its listener form
because the fixtures *hold* their listening sockets (its accepted-socket and client-socket forms were
never instrumented -- not refuted, only shown to be unnecessary); then an undelivered kqueue
readiness notification, refuted by E1/E2; then the wildcard bind, where the evidence sits. Two lessons
travel with that chain. A component that shows up in every stack trace of a stall is not thereby the
component at fault -- it may be where correct idling looks the same as being stuck. And a refuted
sub-case is neither a refuted case nor a cleared *location*: refuting one listener-side story made the
listener socket look answered-for, and the passes that followed instrumented everything except the one
bind call that decided the outcome.

*The Linux lane does not reproduce the wildcard-bind collision.* Same-for-same, the stalling classes
run in about a second in CI against 30 seconds or more locally, and `main`-branch runs stay green.
*INFERRED:* Linux runners hold no such `127.0.0.1`-specific listeners in the ephemeral range. That is
directly testable by running the population probe on a runner, and nobody has.

One trap in re-deriving that contrast: the CI log reports `Tests run: 0` for some of these classes.
That does not mean "skipped in CI". Those lines are the outer `@Nested` containers, which carry no
direct `@Test` method; the real tests report under their nested display names. Match on the nested
display names, or read the Surefire XML.

[[linux-relay-race-occurrence]]
=== The same symptom on Linux, from a different mechanism

"macOS-local" above describes the wildcard-bind mechanism, not the 30-second stall *symptom*. A Linux
CI run (35802987168, *reported by the plan spec* that opened the investigation; the CI abstraction
returned an empty failed-job log, so it was not re-checked) failed on a `WebSocketRelayStageTest`
relay await timeout with the same stall shape.

*It is not the wildcard-bind condition -- INFERRED.* By then `LoopbackEphemeralBindArchTest` already
failed the build on a bare wildcard bind outside its four named exemptions, so the relay test's
fixtures bound through `LoopbackHost.ADDRESS`, and E2 shows that a loopback-specific bind *collides*
with a foreign listener. The inference is sound for the bind; no capture of that run's socket state
exists.

*The mechanism -- MEASURED in the unit lane.* Vert.x delivers a WebSocket's inbound frames from the
moment the socket exists. `WebSocketRelayStage` installed its frame handlers only when the relay's
wiring ran, so a frame that reached either leg in between went to no handler and was lost. A lost
frame is never echoed, and the test's await runs to its ceiling. Two deterministic reproductions pin
the window with the wiring deferred by a fixed 500 ms -- the client writing its first frame inside its
own upgrade callback, and an upstream writing a greeting the instant it accepts. Both were red in 5 of
5 runs before the fix and green in 5 of 5 after it, with the delay still in place.

*The fix.* The relay hops onto the client connection's own context, which `GatewayEdgeRoute.handle()`
captures on the connection's event loop. It pauses each leg the instant that leg is acquired and
resumes both only after every handler is installed, so an early frame waits in Vert.x's own inbound
buffer.

*Production impact -- INFERRED.* Attributing the CI run to the window is itself inferred. Read as the
window, it was a unit-fixture executor divergence: the fixture dispatches the relay from a plain
virtual-thread executor that binds no Vert.x context, while Quarkus's context-preserving executor
binds the client connection's context before the relay runs (read from the executor bytecode, not
observed). Against the *unfixed* native gateway the early-frame integration test lost no first frame in
*N = 50* upgrades, which bounds the per-upgrade client-leg loss rate below about 6% at 95% confidence --
inconclusive with stated power, not an all-clear. The upstream leg hits the window whatever executor
calls the relay. It is reproduced only in the unit lane, because the integration lane's echo upstream
never speaks first, so no production measurement exists for it in either direction. The same pause
closes it.

=== The fix, and what it does not settle

The defect was in the fixtures, and it was one call: they bound their ephemeral server with the
single-argument `listen(0)` overload while the client in the same fixture dialled `127.0.0.1`. Within
the guarded set, 22 sites across 9 files now bind through `LoopbackHost.ADDRESS` in
`de.cuioss.sheriff.gateway.testsupport`. That is the guarded scope, not a tree-wide total: four named
sites in `TlsEdgeProducerTest` deliberately still bind the wildcard, because the TLS edge that class
exercises is the production listener, which binds the wildcard.

Every `Awaits` ceiling also folds a `SocketSnapshot` capture of the kernel's own view into its timeout
message -- `lsof` for this pid, plus `netstat` in whichever spelling the platform takes (`-anv -p tcp`
on macOS, `-ant` on Linux) -- so a future occurrence arrives with its evidence attached.

[NOTE]
====
*The netstat half was macOS-only when it first landed, and CI is what caught it.* Linux reads `-p` as
_show-program_ rather than as a protocol selector, and prints `127.0.0.1:59120` where macOS prints
`127.0.0.1.59120`. It survived local verification because the probe asserting the capture had worked
scanned the *combined* section, so `lsof` output satisfied it on a run where `netstat` contributed
nothing. Splitting that assertion per tool turned an invisible degradation into a red build. A check
whose green is satisfiable by a neighbour is not a check on the thing it names.
====

*The condition is not thereby closed.* The fix removes the measured transport-level cause. No post-fix
rate has been measured -- the quarter-of-runs figure is a pre-fix rate -- and four questions remain
open:

* *File-descriptor pressure* was never controlled for. It rests on the all-threads-idle dumps alone,
  and a measured mechanism for the captured occurrences is not an exclusion of every other candidate.
* *The 5 s TEARDOWN-tier occurrence.* `ReservedBodyCeilingTest.retiresConnectionAfterDeclaredLengthRejection`
  ran to 5.036 s against the 5000 ms teardown ceiling. A half-close against a connection a foreign
  process holds would plausibly produce it -- a conjecture with no measurement behind it.
* *Why CI is clean of the collision* is inferred and untested, as stated above.
* *Whether the mechanism accounts for every historical occurrence*, including the second-hand 50%
  soak tally, which may be contaminated by the stall itself. The originating artifacts are destroyed,
  so that question is unanswerable from the surviving record. Every power figure derived from that
  tally inherits the contamination.

A zero-reproduction result is reported as *inconclusive with stated power*, carrying its `N`, and never
as an all-clear.

=== What a contributor does about it

* *A single red edge-suite run on macOS is not evidence of a branch defect.* Establish provenance
  before acting on it. Read the `SocketSnapshot` block in the timeout message first, for what it can
  actually show: `lsof` runs with `-p <this pid>` and `netstat` is filtered to the ports that view
  returned, so the block is *this JVM's socket state* and cannot name a foreign owner. A `SYN_SENT`
  with no established peer, or no socket for the port at all, points back at this condition.
  Identifying the owner needs a system-wide `lsof -nP -iTCP:<port>` without `-p`, run by hand while
  the stall is live.
* *Establish that provenance against CI, not against a local re-run.* A Linux-lane stall is not the
  wildcard-bind condition; it is a defect to find, as the relay race was. A green Linux lane is *not*
  the authority for macOS behaviour in general -- a genuine macOS-only regression is exactly the case
  it cannot clear.
* *Do not widen the `Awaits` ceilings and do not retry-wrap or quarantine the affected fixtures.* The
  ceiling is what makes the condition visible and measurable, and it is the *capture* point: widening
  it hides the stall and moves the socket-state snapshot further from the event.
* *Do not change `-T1`.* It is a measured rate reduction and still worth having; it is not a cure.
* *Bind every new live-socket fixture through `LoopbackHost.ADDRESS`* -- never a bare `listen(0)` or
  `new ServerSocket(0)`.

`LoopbackEphemeralBindArchTest` is the fitness function that enforces the last rule. It rejects the
bare overload outright and does *not* check whether the socket is later dialled, so "it is never
dialled" is not a defence at review time -- it is the reason a carve-out was granted, not a test the
guard performs.

The carve-out is *four named sites* in `TlsEdgeProducerTest`, not the class; the rest of that class and
its nested classes is guarded like any other fixture. Three of the sites are collision holders that
occupy a port so a *wildcard* production bind is refused, and the fourth is the re-probe behind
`freePort()`, which tests a candidate against the bind scope production will use. The allocation socket
in `freePort()` binds `LoopbackHost.ADDRESS` like every other ephemeral listener. An exact-set control
pins the list: run without the exemption, the rule must report exactly those four code units, so a
stale entry and an unjustified new wildcard bind both fail.

A companion source sweep in the same class catches the wildcard *host literal* -- `listen(0,
"0.0.0.0")` -- which the bytecode rule structurally cannot see, since that call and
`listen(0, LoopbackHost.ADDRESS)` are the same call target. All four exempt sites are
`ServerSocket(int)` constructions, which the sweep never targets.

The sweep is an *allow-list*: the host argument must be exactly `LoopbackHost.ADDRESS`, and anything
else fails. A deny-list of known wildcard spellings was tried first, and each review round found
another spelling on no list -- a wrapped line, a variable port, a nested port call, a spaced selector,
a comment, a constant holding the literal, and finally `"0.0." + "0.0"`. An allow-list does not have to
recognise what an expression evaluates to in order to refuse it.

Two mechanics support it. Between the selector dot and `listen` the sweep accepts whitespace and
comments, so `server./* c */listen(...)` is not a way through. And the argument scanner walks
parenthesis depth to the top-level comma, so a port expression at any nesting depth still yields its
host argument. Depth-awareness is only sound if every parenthesis it counts is really a delimiter, so
the scanner lexes every construct in which a parenthesis is not one -- string literals, text blocks,
character literals, block comments and line comments -- each with a control. A scanner that lexed only
string literals let `server.listen(/* ) */ 0, "")` end the walk early; the call was *skipped rather
than judged*, and a skipped call passes. A guard that cannot parse an input can refuse it or ignore
it, and ignoring converts every gap in the lexer into a silent bypass. The scanner therefore fails
closed on the host text -- a comment inside the argument itself is refused even though the code is
correct.

[[foreign-loopback-port-holders]]
== Foreign loopback port holders on the workstation

Some local test failures are caused by the machine the suite runs on, not by the change under test.
One such class has been seen often enough to name: something on the contributor workstation
intermittently holds loopback ports that the test fixtures assume are free.

=== The symptom

A test that opens, probes or connects to a loopback port fails with a bind or connect error, or with a
control precondition that expected a port to be free and found it taken. The failure has three
recognisable properties:

* It is *unrelated to the change under test* -- the failing test sits in code the branch did not
  touch.
* It is *intermittent* -- a re-run of the same suite on the same tree passes, and CI passes on the
  same commit.
* It is *machine-local* -- the port is held by a process that is not part of the test run: another
  build, another plan's worktree, a local service, or a long-lived listener that happens to own a port
  in the ephemeral range.

The fixtures pick ports they expect to be free and assume nothing else claims them for the duration
of the test. On a busy workstation that assumption does not always hold.

=== Recorded sightings

Four sightings are recorded, each attributed to the environment by re-run or baseline evidence rather
than by assertion. The first two are the loopback stall and its wildcard-bind fix described above,
which share the symptom. The other two belong to this class alone: `TlsEdgeProducerTest` and
`SniFrontListenerTest` each failed once locally on a port-collision control precondition under a load
average of 119, and passed on re-run and in CI -- the contended machine and the port assumption met in
the same run, and neither alone explains it. Separately, machine-local port-collision failures cost
two full-suite re-runs in a single session, in tests the branch did not touch, with the re-runs
passing. Moving the `TlsEdgeProducerTest` allocation socket from the wildcard to loopback removed that
fixture's exposure to the wildcard mechanism and does nothing about a foreign holder.

[[not-the-wildcard-bind-class]]
=== This is not the wildcard-bind class

The two classes share a symptom and have different mechanisms. In the wildcard-bind class (fixed), the
fixture's own wildcard listener is handed a port a foreign process holds on `127.0.0.1`, and the
client is routed to that process. Binding through `LoopbackHost.ADDRESS` fixed it, and
`LoopbackEphemeralBindArchTest` keeps it fixed. In this class (open), a foreign process holds a port
the fixture assumes is free *before* the fixture asks for it, so the address the fixture binds makes
no difference. No test-side change removes the foreign holder -- the workstation owns it.

A failure of this shape is therefore not evidence that the wildcard-bind fix regressed, and not a
reason to reopen it.

=== Reading a failure of this shape

A local failure that matches the symptom is *presumptively environmental*. Attribute it with evidence
before attempting any code fix:

. *Check what the branch touched.* If the failing test and the code it exercises are outside the
  branch's changes, the branch is an unlikely cause.
. *Re-run the failing tests.* A pass on re-run, with no change in between, is the first piece of
  evidence.
. *Compare against a trusted baseline.* The same test green in CI on the same commit, or green on
  `main`, supports the environmental hypothesis but does not by itself establish that the tree is not
  the cause. Where possible, identify the foreign process holding the port first.
. *Look at the machine.* A high load average or a concurrent build in another worktree makes a
  contended-environment failure more likely.

Only a failure that survives this -- it reproduces on re-run, it touches code the branch changed, or
it fails on the baseline too -- is treated as a defect to fix in code. The convention has a precedent:
a branch ran eight gate rounds with two green and six red, eight different sets of failing tests,
every failing file untouched by the branch, and CI green at every pushed commit. Each round of code
changes aimed at those failures would have chased the workstation rather than the change.

The convention is not a licence to ignore a red test. It orders the investigation: establish where the
signal comes from first, then decide whether code is at fault.

[[quarkus-bom-first]]
== The Quarkus platform BOM is imported first

The root `pom.xml` imports more than one BOM into `<dependencyManagement>`. Maven resolves a
coordinate that two imports both pin by *declaration order*: the first import wins. So the order of
two BOM imports silently decides which Quarkus line the reactor resolves.

Quarkus is not an ordinary dependency. `quarkus-bom` pins one internally consistent version line for
the Quarkus extensions and their shared runtime libraries, and `io.smallrye.config` is the one that
carries the load: the build step that augments `@ConfigMapping` interfaces is compiled against a
specific smallrye-config API. A subordinate BOM built against another Quarkus release declares its own
versions for the same coordinates. If it wins one, the reactor can resolve two smallrye-config
versions, and config-mapping augmentation then fails at build time with an error that names neither
BOM. A new import placed ahead of `quarkus-bom` that pins one of those coordinates causes it.

*The rule.* `quarkus-bom` is declared first in `<dependencyManagement>` and owns the Quarkus and
`io.smallrye.config` version line for the whole reactor. Every other BOM import comes after it and
may only contribute versions for coordinates the platform does not pin. Two obligations are part of
the rule:

* *Import position is a contract, not formatting.* A new BOM import is added *after* the
  `quarkus-bom` import. Reordering the imports changes dependency resolution and is reviewed as such.
  `quarkus-bom` is restated locally although `cui-quarkus-parent` already imports it, because an
  inherited import is outranked by every import a child declares.
* *Convergence is checked against the resolved graph, not asserted in prose.* When a dependency floor
  moves, re-derive the resolved `io.smallrye.config` version from the reactor with `dependency:tree`
  scoped to the coordinate, and update the comment beside the `token-sheriff-bom` import to name the
  versions that actually resolve. That comment carries the exact command. A comment that names a
  convergence is evidence only until one of the two BOMs moves.

This is a rule about reading build output honestly: nothing in Maven's output reports which BOM won a
coordinate, so a misplaced import looks like a clean build until augmentation fails. Both mitigations
are conventions, not gates.

*What the rule costs.* A subordinate BOM's own Quarkus expectations are silently overridden. If that
BOM really needs a newer Quarkus API at runtime, the failure is a `NoSuchMethodError` at execution
rather than a resolution conflict at build time. And the Quarkus version moves for the whole reactor
at once; it cannot move for one subordinate's benefit.

*Three alternatives were rejected.*

* *Import the subordinate BOM first and let it own the shared coordinates.* This honours the
  subordinate's build-time expectations exactly. It is rejected because it inverts the dependency:
  the platform that defines the application's runtime becomes subordinate to a library that runs on
  it, and the resulting split breaks config-mapping augmentation for the whole application.
* *Pin `io.smallrye.config` explicitly and leave the BOM order unconstrained.* This makes the
  converged version explicit and immune to import order. It is rejected as the governing rule because
  it fixes one symptom rather than the ordering question: the same collision recurs for every other
  coordinate the two BOMs share, and each needs its own pin. An explicit pin stays available as a
  targeted fix once a real split is shown -- the `jackson-annotations` entry in the root `pom.xml` is
  one.
* *Import only one BOM and manage the other's artifacts by explicit version.* This removes the
  collision, but hand-maintains every version the dropped BOM would have supplied and gives up the
  internal consistency a BOM exists to provide. It is rejected as a disproportionate maintenance cost.

Each rejected option accepts an ambiguous or hand-maintained authority over the shared version line.
The rule names one authority, the platform, and makes every other BOM subordinate to it.

== Two rules about reading a check's output

=== An ERROR from a guard is a statement about the guard, not about its subject

When a guard, gate or analysis step reports an error, the first reading is almost always "the thing
being checked is broken". Frequently the correct reading is "the check could not evaluate" -- a
missing input, an unresolvable path, a tool that never started.

Establish that the check actually ran before treating its output as a finding about its subject.
Establish the same before treating a *green* as evidence: a check that silently could not run
reports success indistinguishable from a real pass, and that is the more dangerous half of this
rule. An error at least draws attention to itself.

=== A plausible root cause is not the root cause

A story that explains every symptom is not thereby true. An explanation that fits all the available
facts is a hypothesis with good fit, and it survives exactly until someone re-derives it against
the implementing source -- at which point a comfortable, load-bearing explanation can turn out to
describe code that does not exist.

Before a diagnosis is acted on, read the implementation it claims to describe.

== Recorded discard: the fully-qualified-refspec fix

A proposal to make the release tag check use fully-qualified refspecs is recorded here as
*discarded*, so it is not re-opened from memory.

It has nothing left to apply to. The project-local release skill's tag check now uses
`git fetch --tags --force` together with `git ls-remote --exit-code --tags`, and its only surviving
`merge-base` use is an ancestry assertion rather than a resolution against a prunable
remote-tracking ref -- which was the failure the refspec change existed to prevent.

Its companion prescription, "run the guard checks serially", is likewise *not* landed, and
deliberately so: it was refuted by the correction that followed it, which found that serial
execution merely hid the problem rather than fixing it.
