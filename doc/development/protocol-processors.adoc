= Protocol Processors -- the SPI and the edge dispatch seam
:toc: left
:toclevels: 3
:toc-title: Table of Contents
:sectnums:
:source-highlighter: highlight.js

A contributor-facing guide to how API Sheriff serves more than one wire protocol behind a single
data-plane edge: the `ProtocolProcessor` SPI, the boot-time registry that binds a protocol to its
processor, and the per-request *protocol-dispatch seam* in the edge that routes WebSocket and gRPC
requests down their specialised paths. It describes *how the code is organised* and *how to add a
processor*; the protocol semantics are defined once in
link:../architecture/terminal-actions-and-protocols.adoc#_protocol_support[Architecture -- Protocol Support], and the design
decisions in link:../adr/0015-websocket-origin-failclosed-allowlist.adoc[ADR-0015] and
link:../adr/0016-grpc-trailers-only-rejection-mapping.adoc[ADR-0016].

== The `ProtocolProcessor` SPI

`de.cuioss.sheriff.gateway.routing.ProtocolProcessor` is the small seam that carries the *verb
semantics* of a protocol -- which HTTP methods a route of that protocol may serve. It is
deliberately narrow:

* `id()` -- the stable processor identifier (`http`, `websocket`, `grpc`).
* `standardMethods()` -- the set of methods the protocol serves by default.
* `supports(HttpMethod)` -- whether a given verb is in scope for the protocol.

The three implementations live alongside it in `de.cuioss.sheriff.gateway.routing`:

[cols="1,3"]
|===
| Implementation | Verb scope

| `HttpProtocolProcessor`
| Every proxyable HTTP verb. Shared by `HTTP` and `GRAPHQL` routes -- GraphQL rides the standard
  HTTP path.

| `WebSocketProtocolProcessor`
| `GET` only -- a WebSocket route is entered by the HTTP upgrade handshake.

| `GrpcProtocolProcessor`
| `POST` only -- every gRPC call is an HTTP/2 `POST` to a service/method path.
|===

A processor carries *only* the verb semantics. The protocol-specific dispatch behaviour
(handshake, streaming, trailer relay, rejection rendering) lives in the edge stages described
below, not in the processor.

== The registry

`ProtocolProcessorRegistry` maps each supported `Protocol` to its processor at boot:

* `HTTP` and `GRAPHQL` share a single `HttpProtocolProcessor` instance.
* `WEBSOCKET` resolves a dedicated `WebSocketProtocolProcessor`.
* `GRPC` resolves a dedicated `GrpcProtocolProcessor`.

`require(Protocol, routeId)` resolves the processor for a route and fails the boot with a
`CONFIG_INVALID` `GatewayException` only when a protocol is genuinely unregistered. Every protocol
in the served set is registered, so boot fails only for an unsupported protocol -- never merely
because a route selects WebSocket or gRPC.

`RouteAssembler` (in `de.cuioss.sheriff.gateway.edge.assembly`) calls `require(...)` once per route
at assembly time and stores the resolved processor on the immutable `Route`.

== The edge protocol-dispatch seam

`GatewayEdgeRoute` runs every request through the fixed pipeline (stages 0--5) uniformly,
regardless of protocol. After stage 5 (the forward policy) it reaches the *protocol-dispatch
seam* and branches on the path `edge.assembly.DispatchPath` assigns the selected route's protocol --
the same split the assembler reads to decide which routes get a shared upstream client and guard:

[source,java]
----
Runnable dispatch = switch (DispatchPath.of(route.protocol())) {
    case WEBSOCKET_RELAY -> () -> terminalDispatch.dispatchWebSocket(ctx, admitted, route, forward);
    case GRPC_DISPATCH -> () -> terminalDispatch.dispatchGrpc(ctx, admitted, route, forward);
    case HTTP_DISPATCH -> () -> terminalDispatch.dispatchAndRelay(ctx, admitted, route, forward); // HTTP / GraphQL
};
dispatch.run();
----

The switch is an *expression* with no `default` arm, so a `DispatchPath` constant without an arm here is a
compile error rather than a request left unanswered.

Each arm is a method of `TerminalDispatch` in `de.cuioss.sheriff.gateway.edge.terminal`, which hands
the dispatch to the stages of `edge.upstream` and `edge.relay` (see
link:../architecture/README.adoc#_edge_package_structure[Architecture -- Edge Package Structure]):

=== WebSocket -- handshake and opaque relay

`dispatchWebSocket` validates the handshake `Origin` against the route's effective allowlist via
`OriginValidationStage` (a foreign or absent origin is rejected `403` *before* any upstream dial --
GW-09 / CSWSH). It then asks `WebSocketUpgradeGate` whether the request is a valid WebSocket opening
handshake, before the request is tracked with its session, takes a relay sub-permit or dials the
upstream. The gate reads only the request's method, version, request URI and headers -- among them
the declared `Content-Length` -- and no Vert.x internal API, in a fixed order: a method
other than `GET` is refused `405` with `Allow: GET` -- the route's effective `allowed_methods` falls
back to every standard method, so the router does not enforce this; a request that is not HTTP/1.1,
or does not carry the `Connection: upgrade` and `Upgrade: websocket` tokens, is refused `426` (on
HTTP/1.x with `Upgrade: websocket` and `Connection: Upgrade`, on HTTP/2 with neither); a
`Sec-WebSocket-Version` or `Sec-WebSocket-Key` sent on more than one header line is refused `400`
before either value is read (RFC 6455 §11.3.1, §11.3.5); a `Sec-WebSocket-Version` other than `13` is
refused `426` with `Sec-WebSocket-Version: 13`; a missing version, or a missing or malformed
`Sec-WebSocket-Key` -- anything but 24 characters of padded base64 (RFC 4648 §4) decoding to 16 bytes
-- is refused `400`; a declared `Content-Length` above 8192 bytes, or one that is no decimal number,
is refused `413` (reached only under `security_defaults.allow_get_with_content_length_body`: without
that opt-in the stage-1 framing gate refuses a `GET` declaring a body before route selection);
a request URI that does not parse as a `java.net.URI` is refused `400` (reached on a
`security_filter.profile: minimal` route; under every other profile the stage-3 url-parameter
validation refuses such a query first). Those last two complete the
mirror of the vertx-core 4.5.34 HTTP/1.1 upgrade path (`Http1xServerRequest.webSocket()` buffers at
most 8192 body bytes and answers `413` with a connection close beyond it;
`Http1xServerConnection.createHandshaker` answers `405`, `400` for an unparseable request URI and `426`
for an unsupported version, and refuses no `Host`), so a request the gate accepts is not refused by
the HTTP stack after the upstream was dialled. The rules decide the status in that order; the
declared length decides the connection on its own. Every refusal of an HTTP/1.x request declaring a
body above the bound -- the `413`, or an earlier `405`, `426` or `400` -- is a `Verdict.Refused` with
`retiresConnection` set, whose own headers name the `close` connection option (`Upgrade, close` on a
`426`), and the connection is retired with the answer
(`ConnectionRetirement.retireConnectionAfterResponse`), since the body behind it is never read. On
HTTP/2 a refusal ends only its own stream. A refusal is answered on the
event loop through `ResponseEnds.reject` with no body, carrying the route's security headers, its own
headers and the pipeline's `Set-Cookie` lines, as every response after route selection does -- the two
`503` refusals of an upgrade too -- and logged at `DEBUG` with the route id and the status only (see
link:../security-threat-model.adoc#gw-09[Threat model -- GW-09]).

A request the gate accepts is handed to `WebSocketRelayStage`. The relay stage dials the upstream,
completes the client upgrade, relays frames opaquely in both directions, and reclaims an established
relay that idles past the route's `idle_timeout_seconds` (closing both legs with WebSocket code
`1001`). When the upstream has confirmed `101` but the client upgrade fails, the relay stage closes
the upstream leg with `1011` and answers the client `502` through `ResponseEnds.endResponse`, unless
Vert.x has answered the request already -- it refuses an invalid HTTP/1.1 handshake itself with `400`,
`405`, `413` or `426` (none of them expected for a request the gate accepted, since the gate answers
each first), while it fails an HTTP/2 request, which cannot be upgraded, without answering. Every answer
the relay stage writes before an upgrade holds the connection is an ordinary response end and passes
the one end rule. No HTTP `ResponseStage` relay runs for a WebSocket route.

==== The admission-permit lifecycle

The WebSocket arm is the one dispatch path where the edge's ordinary permit-release site does not
work, and getting this wrong is not a leak that shows up in a test — it shows up as a gateway that
`503`s everything after enough upgrades.

Every request acquires an *admission permit* at the top of `handle()`, and the HTTP paths return it
from `ctx.addEndHandler`, which fires when the HTTP response ends. A *completed upgrade takes the
connection over*, so for a relayed WebSocket that handler never fires: the response never ends in the
HTTP sense. The end handler therefore cannot be the release site here, and the permit must be held
across the upgrade anyway — an established relay occupies edge capacity for its whole lifetime, so
releasing it at upgrade completion would under-count exactly the connections that cost the most.

`dispatchWebSocket` hands `WebSocketRelayStage` its own release callback instead, and the relay owns
the release from that point. The contract, in full:

* *Acquired* at admission in `handle()`, before the pipeline runs, and *held across the upgrade* for
  the relay's whole lifetime.
* A request the upgrade gate refuses releases the general permit *before* any sub-permit is taken,
  through the shared guard, and only then is answered; the end handler that fires when the refusal
  ends the response finds the permit already returned.
* An upgrade additionally acquires the *relay sub-permit* (`edge_hardening.websocket_relay_cap`)
  before the hand-off — taken *in addition to* the general permit, not instead of it, so long-lived
  relays cannot squeeze HTTP out of the admission pool. An upgrade beyond that cap is refused `503`
  and releases the general permit on the way out.
* *Released exactly once*, from whichever terminal path is reached first: `RelaySession.closeBoth`
  — the single idempotent teardown funnel every established-relay terminal path converges on (client
  close, upstream close, idle reclaim, relay error) — or the *client-upgrade-failure* branch, where
  the upstream connected but the client upgrade did not complete, so no session exists to tear down.
  That branch answers the request `502` unless Vert.x has answered it already, then releases the
  permit itself; where its `502` ends the response, the edge's end handler fires as well, and the
  shared CAS-guarded release keeps the permit returned exactly once.
  `closeBoth` releases *before* it closes either leg, which is what lets an integration test treat an
  observed close frame as proof the permit is already back.
* Both permits are returned *together*, each behind its own idempotence latch, so an upstream-dial
  failure — which *does* end the HTTP response, and so does reach the end handler — cannot strand the
  sub-permit while the general one is released by a different site.

The double-release risk is real and is handled by construction rather than by convention: the release
routes through the same CAS-guarded callback the end handler and the executor-rejection rollback use,
so every path can call it and only the first call counts.

=== gRPC -- forced-h2 dispatch and trailer relay

`dispatchGrpc` streams the request opaquely to the forced-HTTP/2 upstream via `GrpcDispatchStage`,
then relays the upstream response -- including its `grpc-status` / `grpc-message` trailers -- with
`ResponseStage.relayWithTrailers`. Three collaborators carry the gRPC deltas:

* *Forced-h2 upstream client.* gRPC requires HTTP/2 end-to-end, so the h2 protocol version joins
  the client-sharing tuple key: `edge.assembly.UpstreamTarget` carries a `forcedHttp2`
  flag, so a gRPC route to `host:port` holds a client distinct from an HTTP/1.1 route to the same
  `host:port`. `EgressClients.clientFor(...)` (in `edge.upstream`) builds that forced-h2 client (h2
  over TLS with ALPN, or prior-knowledge h2c in cleartext).
* *Opaque frame streaming.* `GrpcDispatchStage` reuses the byte-capped streaming dispatch of
  `DispatchStage`, so the request/response bodies stream as opaque length-prefixed frames (the
  gateway never inspects the protobuf payload) under the same body cap and stream-aware retry gate
  as the HTTP path. The HTTP/2 stream-abuse bounds of threat GW-08 hold on the gRPC path because
  they are bounds of the shared inbound transport, set by `EdgeHardeningOptions` on every listener
  rather than per protocol: at most 100 concurrent streams per connection, a decoded header block of
  at most 16 KiB (`CONTINUATION` frames included), and the Rapid-Reset guard pinned at 200
  client-sent `RST_STREAM` frames per 30-second window. The forced-h2 upstream leg opens at most one
  upstream stream per admitted inbound request, so its stream and reset rates inherit the inbound
  bounds (link:../security-threat-model.adoc#gw-08[Threat model -- GW-08]).
* *Trailer relay and rejection mapping.* `ResponseStage.relayWithTrailers` streams the body with
  the client response held open, then copies the upstream trailers onto the client and ends it, so
  the client observes the gRPC status. The branch order of a gateway-generated rejection on a gRPC
  route is fixed in `ErrorResponseWriter.renderRejection`: it consults `UniformNotFound` *before*
  `GrpcStatusMapper`. A rejection raised before the trust boundary is therefore answered to an
  untrusted caller as the unrouted HTTP `404` -- a trailers-only status would name the address as a
  gRPC route (link:README.adoc#_rejections_before_the_trust_boundary[Rejections Before the Trust
  Boundary]). `GrpcStatusMapper` renders every other gateway rejection as a *trailers-only* gRPC
  response (HTTP `200`, `application/grpc`, `grpc-status` / `grpc-message`) rather than
  problem+json -- an h2-negotiation failure maps to `UNAVAILABLE`. See
  link:../architecture/observability-and-errors.adoc#_grpc_error_contract[Architecture -- gRPC rejections].

=== HTTP / GraphQL -- streamed relay

`dispatchAndRelay` is the default path: it dispatches over `DispatchStage` and relays the streamed
upstream response with `ResponseStage.relay`. GraphQL uses this path unchanged.

== Adding a new protocol processor

To add a future protocol:

. *Implement the SPI.* Add a `ProtocolProcessor` in `de.cuioss.sheriff.gateway.routing` declaring the
  protocol's `id()` and its served verbs. Mirror `GrpcProtocolProcessor` /
  `WebSocketProtocolProcessor` for a single-verb protocol.
. *Register it.* Add the `Protocol` -> processor mapping in `ProtocolProcessorRegistry`. Registry
  registration is one required step, not the whole contract: the `Protocol` enum must already carry
  the value, and the per-route config-model support (schema/model fields plus their `ConfigValidator`
  rules) and — where the protocol needs it — the dispatch arm below must also be in place before a
  route of that protocol resolves and boots.
. *Add a dispatch arm only if needed.* Every protocol is mapped onto a path in
  `edge.assembly.DispatchPath.of`, whose switch has no default arm, so a new `Protocol` constant does
  not compile until it is mapped. If the protocol rides the standard HTTP path (like GraphQL), map it
  onto `HTTP_DISPATCH`; no other edge change is required, and it is served by `dispatchAndRelay`. If it needs a distinct
  dispatch (a handshake, a specialised upstream client, or a non-problem+json rejection), add a
  constant for it to `edge.assembly.DispatchPath` and map the protocol onto it in `DispatchPath.of`,
  add its arm to the protocol-dispatch seam in `GatewayEdgeRoute.process(...)`, and add the
  `dispatch*` method to `edge.terminal.TerminalDispatch`, following `dispatchWebSocket` /
  `dispatchGrpc`. A distinct upstream client shape joins the `edge.assembly.UpstreamTarget` tuple
  key so it is deduplicated correctly.
. *Test it.* Add a processor verb-semantics test (see `GrpcProtocolProcessorTest`) and a
  dispatch/edge test for any new stage (see `GrpcDispatchStageTest`,
  `WebSocketRelayStageTest`).
