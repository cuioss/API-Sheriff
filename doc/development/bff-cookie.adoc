= Cookie-Based BFF -- Contributor Guide
:toc:
:toclevels: 3
:sectnums:

A contributor-facing guide to the *cookie-based BFF* implementation (Variant 3): where its code
lives, how the sealed cookie is put together, and the rules that keep it correct. It describes how to
*work in* the code; the design rationale is in
link:../variants/03-bff-cookie.adoc[Variant 3 -- BFF, Cookie-based] and the architectural decision in
link:../adr/0018-BFF_session_mode_is_one_SessionBinding_seam_behind_a_fixed_reserved-path_and_CSRF_model.adoc[ADR-0018].

== The engine boundary rule (read first)

*The gateway re-implements no OAuth leg.* The confidential-client *engine* (`token-sheriff-client`)
owns retrieval and flow -- auth-code + PKCE, `state`/`nonce`/exact `redirect_uri`, mix-up defence,
refresh-with-rotation, RP-initiated logout, RFC 9470 step-up. The *BFF* (this code) owns only the
browser-facing part: the binding/session cookies, CSRF, request proxying, the curated user-info view,
logout receivers, and RFC 9457 rendering.

This rule is identical in both BFF variants -- cookie mode reaches the engine exactly as server mode
does. When you add or change a reserved handler, drive an engine seam; never hand-roll an OAuth
request, a token exchange, or a JWKS fetch inside the gateway.

== Where the code lives

The cookie-specific code is in the `api-sheriff` module under
`de.cuioss.sheriff.gateway.bff.cookie`:

[cols="1,2"]
|===
| Type | Responsibility

| `SealedSessionPayload`
| The plaintext that gets sealed: the mediated tokens, the identity/session claims, the login instant
  anchoring the TTL, the per-session identity nonce, and the session's active and granted scope sets.
  Owns the inner wire format (`encode()` /
  `decode(...)`) and redacts every credential from `toString()`.

| `SealedSessionCookieCodec`
| The AES-256-GCM seal/unseal, the outer value layout, the `FORMAT_VERSION` stamp, the key-id gate,
  the `Set-Cookie` hardening, and the seal-time size budget.

| `CookieSessionBinding`
| The `SessionBinding` implementation: `bind` (seal on login, mint the nonce), `resolve` (unseal,
  enforce the absolute TTL and the idle timeout server-side), `persist` and
  `persistReissuingCookie` (re-seal a refresh, respectively a widening merge), `recordAccess` (the
  activity cookie), and the derived session identity. Reports `IdpDestruction.UNSUPPORTED`.

| `SessionActivityCookieCodec`
| The HMAC-SHA-256 sign/verify of the activity cookie -- the last-access instant the idle timeout
  rests on -- with its own layout, its own `FORMAT_VERSION` and its own key. See
  <<activity-cookie>>.

| `CookieKeyMaterial`
| Resolves the one sealing key -- passed `encryption_key` versus generate-on-startup -- the
  derived per-gateway identity salt, and the activity cookie's codec over a key derived from the
  sealing key (`activityCodec(...)`).
|===

Everything else is shared with the server-session variant; see
link:bff-session.adoc#_where_the_code_lives[the server-session guide] for the `bff.*` package map.

== The SessionBinding seam

`SessionBinding` is the seam the whole BFF foundation binds to -- never a store directly. The
configured `session.mode` selects only *which implementation* `BffRuntimeProducer` assembles:
`ServerSessionBinding` over the in-memory store, or `CookieSessionBinding` over the sealing codec.

Every reserved endpoint, the CSRF defence, the refresh and step-up coordinators, and the
`require: session` stage-4 runtime are consequently *mode-neutral*: they are written against the
seam and are unaware of which binding is in force. That is why adding a cookie-mode capability
almost never means touching a reserved endpoint.

Where the modes genuinely differ, they differ in capability, and there are two such places. The
first carries a flag: `idpDestruction()` reports `UNSUPPORTED` for the cookie binding, and the
back-channel logout endpoint is *gated on that signal* rather than on the mode name -- it answers a
deliberate `404` instead of claiming a destruction that never happened.

The second has no flag, because the result carries it. `persist` is the seam's *updating* write: it
updates a session that already exists and never creates one, and it returns an empty result when
the binding observed that the session is gone. `ServerSessionBinding` reports that when a logout
destroyed the session after the caller resolved it. `CookieSessionBinding` holds nothing a logout
could have removed, so it always re-seals and never returns empty -- a refresh or a widening that
was in flight during a logout still produces a session cookie. Callers must handle the empty result
(`TokenRefreshCoordinator` ends the request as session-ended, `CallbackEndpoint` answers `403`);
`bind` stays the only creating write. See the updating-write amendment of
link:../adr/0018-BFF_session_mode_is_one_SessionBinding_seam_behind_a_fixed_reserved-path_and_CSRF_model.adoc#updating-write[ADR-0018].

The updating write has a second variant, `persistReissuingCookie`, which a widening merge uses. In
server mode it swaps the handle the browser holds. Here it does exactly what `persist` does: every
update of a sealed session already produces a new cookie value, so there is nothing further to
re-issue. *Do not re-mint the nonce in it.* The nonce is minted once, in `bind`, and the derived
session identity depends on it; a new nonce would be a different session to the refresh
coordinator's single-flight and to the activity cookie. It would also withdraw nothing: the cookie
sealed before the widening still unseals under the same key and stays usable at its earlier level
until the session's absolute lifetime
(link:../adr/0018-BFF_session_mode_is_one_SessionBinding_seam_behind_a_fixed_reserved-path_and_CSRF_model.adoc#cookie-reissue[ADR-0018]).

== The activity cookie

A session ends at its absolute lifetime and, earlier, at its idle timeout
(link:../adr/0018-BFF_session_mode_is_one_SessionBinding_seam_behind_a_fixed_reserved-path_and_CSRF_model.adoc#idle-deadline[ADR-0018]).
A stateless binding can keep the last access only in the browser, and it keeps it in a cookie of
its own. *The sealed session payload and its `FORMAT_VERSION` are unchanged*: no field was added,
and nothing in `SealedSessionPayload` or `SealedSessionCookieCodec` knows about the idle timeout.

*Name.* The session cookie's name followed by `SessionActivityCookieCodec.COOKIE_NAME_SUFFIX`
(`-activity`). A suffix, not a prefix, so the cookie keeps the `+__Host-+` prefix. Its attributes are
the session cookie's hardening set, and its `Max-Age` is the session's remaining absolute lifetime.

*Layout.* The value is base64url without padding, always 56 characters for 42 bytes:

[source]
----
version(1B) | key-id(1B) | last-access(8B, epoch milliseconds) | HMAC-SHA-256 tag(32B)

tag covers:  cookie name | version | key-id | session-identity(16B) | last-access
----

The version is this cookie's own counter (`SessionActivityCookieCodec.FORMAT_VERSION`, currently
`2`) and is independent of the sealed session's.

*Authenticated, not encrypted.* The value carries one fact, the time of the last access, and that
is not a secret. The codec therefore signs it with a message authentication code and does not
encrypt it. *Do not change this to an AEAD cipher with a random nonce.* The binding keeps no state
per session, so the client decides how often `recordAccess` writes a cookie: it can send requests in
parallel, and it can present an activity cookie again after it was given a newer one. One key may
protect only a limited number of values under such a cipher (2^32^ for AES-GCM with a random
96-bit nonce, NIST SP 800-38D), and a client could spend that limit. HMAC-SHA-256 has no such
limit, and `sign` is deterministic: the same session and instant give the same value.

*Its own key.* `CookieKeyMaterial.activityCodec(...)` derives a key for this cookie alone from the
sealing key, so one key serves one algorithm. A value produced by either codec is refused by the
other. Both keys go when `encryption_key` is replaced. The operator's replacement schedule in
link:../user/bff-cookie.adoc#key-rotation[the operator guide] depends on the session cookie alone.

*Bound to the derived identity.* The 16-byte derived identity of the session is part of what the
tag covers and is not part of the value. `CookieSessionBinding` passes the identity derived from the
session cookie of the same request to `read`, and a value signed for another session does not
verify, so an activity cookie cannot be moved to a second session to keep that one alive. The
identity is never sent to the browser.

*Fail-closed verification.* `verify` returns empty -- "no activity cookie", never an error -- for a
value that is malformed, truncated, of another version, signed under another key, for another
cookie name or for another session, or tampered with. The binding then takes the session's *login instant* as the last access.
An activity cookie can therefore only extend a session up to the idle timeout past a real access,
and its absence can only shorten the session. A last access in the future is clamped to the
reference instant, so a value from a gateway whose clock runs ahead is never worth more than an
access at this very moment. It is not rejected: replicas differ by some clock offset in every
deployment, and a rejection would fall back to the login instant and end sessions that are in use.
The idle deadline is therefore exact to within the clock difference between the replicas, in
addition to the re-issue interval. Every rejection
is logged at `DEBUG` only: any client can send a junk activity cookie on any request.

*The re-issue interval.* `CookieSessionBinding.recordAccess` returns a new activity cookie only when
the last access is at least one interval old, and nothing before that. The interval is the smaller
of `ACTIVITY_COOKIE_INTERVAL` (60 seconds) and half the idle timeout, so an idle timeout below
60 seconds can still be kept alive by accesses. Most responses therefore carry no `Set-Cookie`, and
the idle deadline is exact to within that interval. The interval has no configuration key of its
own. It limits the `Set-Cookie` traffic of a well-behaved client and is not a bound a client has to
honour (see "Authenticated, not encrypted" above). `recordAccess` never returns the session cookie:
an access does not re-seal the tokens and cannot race a refresh for the token-bearing cookie.

*Clearing.* `clearingSetCookieHeaders()` returns two values, one per cookie. Every caller that ends
a session or logs out emits the whole list.

When you change this code:

* A change to the activity cookie's layout increments `SessionActivityCookieCodec.FORMAT_VERSION`,
  not the sealed session's. Activity cookies of the earlier version are then ignored, so a session
  whose login is older than the idle timeout ends at its next request; a younger one continues.
* Do not move the last access into `SealedSessionPayload`. That is a field-set change, which forces
  a `FORMAT_VERSION` bump of the sealed session and ends every cookie-mode session at the upgrade.
* A response on which the stage adds the activity cookie is sent `Cache-Control: no-store`
  (`PipelineRequest.addResponseSetCookie` sets both in one call). Add a gateway cookie through that
  method and nothing else.

== The sealed-cookie wire format

`FORMAT_VERSION` is *2* -- the eleven-field layout described below -- and it is incremented by one on
every change to the sealed field set (see the rule below). The packaging pipeline has four stages, and the direction matters in both
readings:

[source]
----
seal:    encode -> deflate -> AES-256-GCM -> base64url
unseal:  base64url -> AES-256-GCM -> inflate -> decode
----

The cookie value is a base64url-encoded *outer envelope*:

[source]
----
version(1B) | key-id(1B) | GCM nonce(12B) | ciphertext | GCM tag(16B)
----

The `version` and `key-id` bytes are bound into the GCM *associated data*, so tampering with either
fails the tag check rather than silently selecting a different parse. The gateway holds exactly one
sealing key: a stamped id that does not match it is refused outright -- never a try-every-key
decrypt -- which is what makes withdrawing a key a clean, fail-closed break.

The *inner* plaintext (what `SealedSessionPayload.encode()` produces) is the eleven fields in
record-declaration order, each written as a *2-byte big-endian unsigned length followed by its raw
UTF-8 bytes* -- eleven fields, so 22 bytes of framing. A zero length stands for an absent optional.
The tenth field is the session's active scope set `A` (`activeScopes`, the scopes of the current
access token) and the eleventh its granted scope set `S` (`grantedScopes`, the scopes the identity
provider is known to grant the session). Each is written as its names sorted and joined by a single
space; an empty set is a zero-length field. The two are sealed as independent fields and never
derived from one another: a near-expiry refresh re-seals `S` unchanged, a scope-driven refresh
re-seals it without the scopes the grant did not return, and a widening replaces it with the scope
of its grant
(link:../adr/0057-Session_routes_obtain_their_declared_scopes_by_refreshing_inside_the_grant_and_widening_the_live_session_outside_it.adoc[ADR-0057]).
It is read only *after* the GCM tag has authenticated the bytes -- `decode(...)` is never a parser
for untrusted input.

Length prefixes rather than a separator character are the point of the format, and the reason it
replaced the earlier newline-joined layout. That layout joined the fields with a newline and
URL-safe-base64-armoured each one
so no value could collide with the separator; the whole sealed value was then base64url-encoded
again for transport. That is a ~33 % expansion applied to material -- three JWTs -- that is already
base64 text, and then a second expansion on top of it. Nothing can be confused with a delimiter when
the length is stated up front, so the field bytes stay raw and the only base64 left is the single
outer one transport requires.

Deflating the framed plaintext before sealing is what turns the saved expansion into fitting the
budget: base64 text carries about six bits of information per byte, so the header and payload
segments of a JWT compress well. The signature segments do not -- they are random -- and neither
does the 43-character session nonce, which is a fixed incompressible floor on any ratio this format
reports.

[NOTE]
====
*Compress-then-encrypt is safe here and is not a general licence.* The CRIME/BREACH class needs an
attacker who can inject chosen plaintext next to a secret in the same compression context and then
observe the compressed length. Neither half holds for this cookie: the plaintext is assembled by the
gateway from IdP-issued tokens, and the sealed value is written once per session change rather than
returned as a length-observable oracle. See
link:../adr/0043-Compress-then-encrypt_in_the_sealed_session_cookie_and_the_CRIME_BREACH_discriminator.adoc[ADR-0043]
for the full discriminator.
====

Inflation on the unseal leg runs only over bytes the GCM tag has already authenticated, so it is not
untrusted-input decompression. It is still bounded by `SealedSessionPayload.MAX_PLAINTEXT_BYTES`, so
a corrupt-but-authenticated buffer cannot drive an unbounded allocation; a malformed or over-long
stream takes the same `payload-format` rejection a malformed payload does -- "no session", never an
error.

[IMPORTANT]
====
*Any change to the inner field set increments `FORMAT_VERSION` by exactly one.* The current value is
`2`: the eleven-field layout whose tenth and eleventh fields are the session's active and granted
scope sets. It superseded version `1`, the same layout without the granted scope set. The field-count
guard is strict, the reader refuses trailing bytes after the eleventh field, and there is no
legacy-shape acceptance path: a cookie in the previous format must fail to unseal, not be admitted
with a synthesized value. Incrementing the version is what makes that failure clean, since the version byte
is authenticated and is read at an explicit gate *before* a `Cipher` is constructed -- so a cookie
stamped with any other version is refused without any decryption or inflation being attempted. An
increment forces every existing cookie-mode session to log in again, once -- call that out in the
operator documentation when you make one.
====

== The four routes to a session that fits, and where each one landed

A cookie-mode session that also *refreshes* is the largest this variant ever carries: the seal holds
a live access token, a refresh token and the ID token at once. Whether that fits is the question this
section settles, and it settles all four routes that were open rather than only the one that shipped
-- a route recorded as considered-and-declined is what stops it being re-proposed as new.

The bar is *4019 bytes of sealed cookie value*, and it does not move in any of the four. It is the
RFC 6265 section 6.1 per-cookie header guarantee of 4096 less the 77 bytes the default cookie name
and attribute run wrap around the value. The bar is a *floor every browser guarantees*, not a limit
any one browser enforces, and that distinction is what decides route 1.

=== Route 1 -- enlarge the budget: settled, NOT built

`oidc.session.max_cookie_size` is configurable up to 8192, so raising it is a one-line change. It is
declined because *it changes nothing about what a browser keeps.* The gateway's budget governs when
the gateway refuses to seal; the browser's limit governs when the browser silently drops the
`Set-Cookie` it was sent. Raising the first past the second does not buy space -- it converts a loud,
diagnosable, server-side failure into an invisible client-side one, and the session then simply never
exists. That is the exact failure this variant already shipped once, and the reason the shipped
default was moved down to 4019 rather than left at the round 4096.

The gateway does not leave that decision unmarked. `ConfigValidator` derives the *emitted header*
size from the resolved configuration -- the effective budget plus the actual cookie name and the
widest `Max-Age` -- and warns at boot (`COOKIE_BUDGET_EXCEEDS_BROWSER_GUARANTEE`) when it exceeds the
4096-byte guarantee, naming the value budget that would fit instead. An operator who raises the
budget anyway is doing so against a boot-time warning that says what it costs, which is the correct
place for that decision to sit: it is a deployment's to make, on its own knowledge of the browsers it
serves, and not one the gateway makes silently on everybody's behalf.

The measurement that would bound the headroom is now executable rather than assumed:
`demo-client/tests/05-cookie-size-budget.spec.js` bisects the storable size from inside a real
Chromium page over two arms, because the two specifications budget different things -- RFC 6265
section 6.1 counts the whole header, RFC 6265bis section 5.6 counts name and value only. Chromium
stores more than the floor, and the spec reports how much.

[WARNING]
====
*That spec has not been run against this change, so no Chromium threshold is quoted here.* It is
opt-in (`verify -Pe2e-demo -pl demo-client`) and gates nothing on a pull request. A number would have
to come from a run, and inventing one would turn an executable measurement into a claim -- which is
precisely the failure mode the spec exists to end. Run it deliberately and record the figure here.

The same restraint applies to the other engines. Firefox and WebKit each enforce a per-cookie limit
in the same ~4 KB region, and RFC 6265bis is the convergence point they are moving toward, but this
repository measures neither and no figure for them is stated. That gap does not weaken the verdict:
the gateway ships to every engine, so the bar is the floor all of them guarantee, and a measurement
above it in any single engine is *headroom observed*, never a bar relaxed.
====

=== Route 2 -- split across several cookies: settled, NOT built

The budget is per cookie, so a session too large for one could be carried in chunks and reassembled
on read. It is declined as a product decision on complexity, and the decisive detail is a property of
this gateway rather than a general objection: *the chunks do not arrive separately.* A browser
concatenates every cookie it holds for the origin into one `Cookie` request header value, so N chunks
arrive as one header value measured against one cap -- and that cap is
`GatewayEdgeRoute.cookieHeaderConfigurationFor`'s `max(baseline, budget + 512)`, derived from the
*single declared budget* and sized for one cookie plus co-resident cookies. Under the shipped default
that is 4531 bytes. Splitting the value therefore does not divide the problem; it moves it to a
pre-route header cap that the same one declared number drives, and making that cap chunk-aware means
teaching the edge how many chunks a session is allowed to be.

The rest is the ordinary cost of chunking: a partial arrival has no clean answer (a session missing
its third chunk is neither present nor absent), the `__Host-` prefix discipline has to hold for every
chunk independently, and the per-domain cookie count -- which nothing in this repository asserts --
becomes load-bearing.

The route is *reversible*, and the condition is worth stating: if the packaging route's headroom is
ever exhausted -- a claim set that grows past what deflation absorbs -- splitting is the next
structural option, and it is a smaller change then than reducing the payload would be.

=== Route 3 -- reduce the payload: settled, held in reserve

Two levers exist, and they are held rather than declined because each costs something the gateway
should not spend before it must.

*Trim the claims the IdP mints.* The access and ID tokens carry whatever the realm's mappers and
default client scopes put in them. The integration realm alone declares realm-role, group-membership,
audience and three user-property mappers, on top of the role, scope and origin material Keycloak adds
by default -- and every one of those bytes travels in the seal. All of it is chosen in Keycloak, not
in the gateway, which is exactly why it is not the gateway's lever to pull: it is a deployment-level
decision with consequences for every consumer of those tokens, not only for the cookie.

*Drop the ID token from the seal.* This is the single largest reclaimable component, and what makes
it a candidate at all is that the seal carries the *raw* token while every claim the gateway actually
uses from it has already been extracted. `CallbackEndpoint` reads the validated ID token at login and
stores `sub`, `sid`, `acr` and `auth_time` as their own payload components; the raw token itself has
exactly one consumer, `RpInitiatedLogout`, which sends it as the `id_token_hint` on the end-session
redirect. So dropping it costs precisely that one thing -- without the hint the IdP cannot reliably
identify which session to end, and RP-initiated logout degrades to best-effort -- and costs neither
the identity claims nor anything else. It stays in reserve because a logout that reliably ends the
IdP session is worth more than bytes the packaging route currently supplies for free.

=== Route 4 -- package and compress: settled and BUILT

This is the route that shipped, and it is the wire format the section above describes: length-prefixed
raw UTF-8 framing (which removes the inner base64 armouring entirely) followed by deflation before
the seal.

The measurement, from `SealedSessionCookieCodecTest`'s three-token fixture -- an access, refresh and
ID token built to the shape Keycloak issues for the `integration` realm, with random signature
segments of the right width for RS256 and HS512, because a repeating filler in the one part of a JWT
deflation cannot help with would report a ratio no real token reaches:

[cols="3,2"]
|===
| Quantity | Measured

| Framed plaintext (length-prefixed raw UTF-8)
| 3433 bytes -- measured before the tenth and eleventh fields, the active and granted scope sets,
  were added; each adds its scope names (`email openid profile` in this fixture, for both sets) plus
  one 2-byte prefix, so the rows below move by a few dozen bytes at most

| Sealed cookie value, as emitted
| 2700 bytes -- *78.6 %* of the framed plaintext

| Deflated ciphertext behind that value
| ~1995 bytes -- about *58 %* of the framed plaintext; the difference between the two rows is the
  14-byte envelope, the 16-byte GCM tag and the single 4/3 base64url transport expansion

| Margin under the 4019-byte bar
| *1319 bytes*, i.e. the seal uses 67.2 % of the budget and *32.8 % remains* for claim-set growth

| Against the 10 % headroom reserve (3617 bytes)
| clears it by 917 bytes
|===

The ratio has a floor that no compression level can beat: the 43-character session nonce is 32 random
bytes and is incompressible, as are the three signature segments. What deflation actually recovers is
the JWT header and claim segments, which are base64 text carrying about six bits per byte.

Read the margin as a budget for *growth*, not as spare capacity: the figures above are one realm's
claim set, and a deployment whose IdP mints larger tokens spends that 32.8 % first. The fast gate is
the unit measurement above, which fails before any browser is involved;
`BffCookieRefreshIT` is what measures the real thing against a running IdP.

The safety of compress-then-encrypt in this construction -- the CRIME/BREACH discriminator, the payload
components and who controls each -- is settled in
link:../adr/0043-Compress-then-encrypt_in_the_sealed_session_cookie_and_the_CRIME_BREACH_discriminator.adoc[ADR-0043]
and is not restated here.

=== What this settlement does not close

Four residuals survive it, and none is closed by any of the four routes:

* *The browser lane still gates nothing.* The Playwright suite runs on pushes to `main` and on demand,
  never on a pull request, so a change that pushes the seal past a browser's limit can merge with the
  measurement never having run. See
  link:cookie-deliverability-blindness.adoc[Cookie-Deliverability Blindness] for what that lane can
  and cannot observe.
* *The Chromium threshold is unmeasured here.* Route 1's spec exists and is lint-clean; it has not
  been executed, so the headroom above the floor is currently a shape rather than a figure.
* *Per-domain cookie count and aggregate per-domain size carry no assertion anywhere.* Both are real
  browser limits, both would bite a chunked session first (route 2), and neither the Java suite nor
  the browser suite observes either.
* *The other cookie properties stay unobserved on a pull request.* `SameSite`, `Secure` and the
  `__Host-` prefix are browser-enforced, so the Java integration suite structurally cannot prove them
  -- it replays a cookie map and applies no policy at all.

== The derived session identity

`SessionRecord.sessionId()` is the one identity model the seam defines, and it is the key the refresh
coordinator uses for single-flight coalescing. Cookie mode *discards* the id minted at login and
derives its own instead: a salted digest over the login instant, `sub`, and the per-session nonce.

Two constraints hold it together:

* *Stable across re-seals.* All three digest inputs are fixed for the life of the session, so a
  refresh reproduces the identity byte-identically. `persist` re-seals the nonce *verbatim* and
  fails loud rather than re-minting; `TokenRefreshCoordinator.rotate()` must copy the nonce onto the
  rotated record. `rotate()` rebuilds the record component-by-component, so *any component you add to
  `SessionRecord` needs a copy line there* or it is silently dropped. The widening merge in
  `CallbackEndpoint` rebuilds the live session the same way and carries the same obligation.
* *Unique.* The nonce is what makes two logins by the same subject inside one clock second resolve to
  distinct identities; without it they collided and cross-wired the single-flight keying.

The identity is never emitted to the browser -- only the sealed value crosses -- and the raw nonce is
never used as, or substituted for, the session id. Single-flight coalescing is necessarily *per
instance* here; a cross-instance duplicate refresh is this variant's documented, accepted trade-off.

== Build and test

The canonical build commands are the ones in the repository `CLAUDE.md` (invoked through the build
executor, never a raw `mvn`). Both the quality gate and full verify must pass with zero findings
before a commit.

Unit-test entry points:

* `SealedSessionPayloadTest` -- the inner wire format: round trips, absent optionals, values carrying
  bytes that would have collided with the retired separator, the strict field-count and
  trailing-byte guards, the `MAX_PLAINTEXT_BYTES` bound, and credential redaction.
* `SealedSessionCookieCodecTest` -- seal/unseal, the version and key-id header, fail-closed rejection
  of a tampered nonce/ciphertext/tag, unknown version or key id, a malformed compressed stream, the
  size budget, and the measured encoded length of a realistic three-token session.
* `CookieSessionBindingTest` -- bind/resolve/persist, the server-side TTL enforcement, the identity
  properties (stability across a re-seal, uniqueness within a clock second), the idle deadline
  (a missing, tampered, other-session or other-key activity cookie never extends a session), the
  re-issue interval of `recordAccess`, and the two clearing cookies.
* `SessionActivityCookieCodecTest` -- the activity cookie: round trip, the binding to the session
  identity, the absence of that identity from the value, the deterministic value, fail-closed
  verification, separation from the sealed session cookie in both directions, the exact
  `Set-Cookie` and the 56-character value.
* `TokenRefreshCoordinatorTest` -- its `CookieMode` group covers the stateless refresh: re-seal into
  a new `Set-Cookie` and nonce propagation across `rotate()`.

Integration tests live in the `integration-tests` module and run against the native image on the
Docker compose stack under the integration-tests Maven profile:

* `BffCookieSessionIT` -- the full login -> mediated call -> logout round trip through a real IdP.
* `BffCookieStatelessnessIT` -- the two-instance topology (ports `10445` and `10446`) sharing only
  the sealing key. It logs in against the *first* instance only, then exercises the second, which
  is what makes "the peer held no record of this session" the evidence rather than an assumption.
  That asymmetry is deliberate: it also documents the login-leg affinity boundary.

Both IT suites are behaviour-level and are *not* bound to the inner wire form. The one exception is
the leading version byte: `BffCookieSessionIT` asserts it by literal, because that module has no
`api-sheriff` class on its classpath to reference `FORMAT_VERSION` through, so an increment updates
that literal in the same change.

== How to extend

* *A new sealed field* -- add the record component, append it in `encode()` in declaration order,
  read it back in `decode(...)`, raise the field count (which raises the framing width with it), and
  *increment `FORMAT_VERSION` by one* (and the literal in `BffCookieSessionIT` with it). If it participates in identity, mind the stability constraint above.
  Budget the field by what it costs *after* deflation, not by its raw size: a random or
  already-compressed value costs close to its full length, while structured text costs much less.
* *A new session-runtime capability* -- write it against the `SessionBinding` seam so it stays
  mode-neutral; if it genuinely cannot work statelessly, gate it on a capability signal (as
  back-channel logout does) rather than on the mode name.
* *Anything touching an OAuth leg* -- drive an engine seam, per the boundary rule.
