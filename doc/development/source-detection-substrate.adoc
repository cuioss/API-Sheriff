= Per-Source Detection Substrate -- Contract
:toc:
:toclevels: 2
:sectnums:

The written contract of the gateway's one per-source detection substrate, the framework-free package
`de.cuioss.sheriff.gateway.detection`. It states what the substrate keys on, how it counts, when a
source trips, what it emits and what it deliberately does not do -- the terms a consumer builds on.
The first consumer is the edge's reconnaissance detection, configured by the `enumeration_detection`
block. The second is the per-source threat classification, configured by the `threat_classification`
block (<<_second_consumer>>).

== Shape

[cols="1,3"]
|===
| Type | Role

| `SourceKey`
| The key one bucket is tracked under: `(source, host)`.

| `SourceKeyResolver`
| Derives a `SourceKey` from the peer address, a trusted forwarded client address and the authority
  host.

| `SourceLedger`
| The substrate: one leaky bucket per key, weighted admission, the state machine, the query API and
  the cardinality bound.

| `SourceState`
| The snapshot the query API and an admission answer.

| `SourceTrip`
| The raw record a trip hands the trip listener.
|===

The package imports no Vert.x, CDI, Micrometer or other framework type. The clock is an injected
`LongSupplier` reading monotonic nanoseconds (`System::nanoTime` in production) and a trip is handed
to a plain `Consumer<SourceTrip>`. Metering, logging and the wire are the consumer's.

== Keying

A key is `(source, host)`, compared character for character. `SourceKeyResolver` is the producer and
canonicalizes both parts.

*The source* is the forwarded client address when the caller hands one over, otherwise the TCP peer
address. The resolver does not judge trust: the edge's source-key stage, `SourceKeys`, hands over a
forwarded address only for a peer `forwarded.trusted_proxies` trusts, resolved by the same resolver
the forward stage regenerates `X-Forwarded-For` from. A trusted peer's request whose forwarding
headers resolve to no client -- an absent or malformed header -- is keyed on the `unknown` source,
never on the trusted peer's own address (`SourceKeysTest`). `SourceKeys` resolves the key once per
request, on the event loop before admission, and stashes it on the request context for every
consumer, so both consumers key a request on the same source. The chosen address is canonicalized:

* an IPv4 address is kept whole, in dotted-decimal form;
* an IPv6 address is reduced to its `/64` prefix, written `a:b:c:d::/64`. An end site is routinely
  given a whole `/64`, so keying on the full address would let one host rotate through unbounded
  keys. The *residual*: a site holding a `/48` still controls 65,536 `/64` prefixes and can spread
  across that many keys. The bound below caps what that costs the gateway; it does not make such a
  source trip. An IPv4-mapped IPv6 address is an IPv4 address and is kept whole;
* an absent, blank or unparseable address folds to the one fixed source `unknown`. The text is parsed
  as an address literal only, so a host name is never resolved.

*The host* is the lower-cased authority host when it equals a `match.host` some route declares,
otherwise the fixed sentinel `*`. A caller rotating `Host` therefore cannot multiply its keys: one
source occupies at most as many keys as there are declared hosts, plus one.

== The Cardinality Bound

A ledger tracks at most `MAX_TRACKED_SOURCES = 65,536` keys, a fixed constant. Admitting a new key at
the bound first sweeps the map and removes every entry whose level drained to zero and that is not
blocked. A sweep runs at most once per `SWEEP_INTERVAL` (one second), so a flood of new keys cannot
turn every admission into a full scan. When the map is still full the key is not tracked: the
admission returns the state `UNTRACKED`, the event is not counted and the overflow is counted in
`untrackedCount()` for the consumer to report. A tripped or blocked key is never evicted.

The bound is *soft*. The size check and the insert are not one atomic step, so the map can exceed the
bound by at most the number of threads inserting new keys at the same moment.

== Weighted Admission and Tags

`admit(key, weight, tag)` adds one event of `weight` (at least `1`) to the key's bucket and returns
the post-admission `SourceState`. `tag` is a constant of an enum the consumer supplies, so the tag set
is bounded by construction. Per key the ledger keeps the weight each tag contributed since the bucket
was last empty and reports it in the state and the trip. Both consumers tag each event with its
`EventType`.

Which events a consumer admits, and with what weight, is the consumer's decision, not the
substrate's: `ReconEvents.weightOf` admits a pre-trust rejection of its closed recon set with weight
`1` and everything else with weight `0`, which is never admitted. `PRE_TRUST_INTERNAL_FAILURE` is
outside that set: an operator-side failure is not caller behaviour and carries no detection weight.
The threat consumer's weights are `ThreatWeights.weightOf` (<<_second_consumer>>).

== Bucket Semantics

Every admitted weight is added to the key's level. The level drains linearly at
`threshold / window` per second: a source that keeps exactly a threshold's worth of weight per window
holds a steady level just under the threshold, and a full bucket empties in one window. The drain is
computed lazily from the clock whenever the bucket is touched -- no timer and no thread run.

A leaky bucket *approximates* a sliding window. It is not one: a burst of the full threshold trips at
once, while the same count spread evenly over slightly more than a window never does. The exact
sliding window -- the count of events within the last `window` -- is deliberately not served, because
it needs per-event timestamps per key.

== Configuration

A ledger is built from `SourceLedger.Settings(threshold, window, action, blockDuration)`. The recon
consumer reads them from the top-level `enumeration_detection` block of `gateway.yaml`
(`EnumerationDetectionConfig`):

[cols="1,1,3"]
|===
| Key | Default | Meaning

| `enabled` | `true` | Whether detection runs at all.
| `threshold` | `100` | The level at which a source trips.
| `window_seconds` | `60` | The window over which a full threshold drains.
| `action` | `observe` | The response to a trip: `observe`, `delay` or `block`.
| `block_seconds` | `60` | How long a tripped source is blocked under `block`.
| `delay_millis` | `2000` | How long a tripped source's rejection answers are held under `delay`
  (`1` to `10000`). The edge counts one source's held answers against its share of the held-answer
  sub-budget, an eighth of it and at least one, and answers a request past that share before admission
  with the `block` answer, `Retry-After` the whole seconds of `delay_millis`.
|===

An omitted block resolves to every default: detection runs on every gateway and records a trip
without changing any answer. *`observe` is the default* because the gateway keys a source by its
address and cannot tell at boot whether one address stands for one client or for every client behind
a NAT or an untrusted load balancer; a default `block` or `delay` would refuse or slow all of them for
the probing of one. `block` and `delay` are operator opt-ins. `LimitRules.validateEnumerationDetection`
refuses an out-of-range value at boot.

The threat consumer reads its settings from the `threat_classification` block
(link:../configuration.adoc#_threat_classification[Configuration -- `threat_classification`]). Its
action is fixed to `observe`, and its block duration, which the substrate requires to be positive, is
set to the window and never used.

== State Machine and Query API

[cols="1,3"]
|===
| Transition | When

| `CLEAR -> TRIPPED`
| The admission whose weight brings the level to the threshold or above. It emits one `SourceTrip`.
  A source trips at most *once per `CLEAR` period*: the trip re-arms only after the level drained
  back to zero.

| `TRIPPED -> BLOCKED`
| Under action `block`, whenever the level is at or above the threshold and the source is not already
  blocked -- on the trip itself, and again on a later admission if the level is still or again at the
  threshold after a block expired. The block lasts `blockDuration`.

| `BLOCKED -> TRIPPED`
| The block expired while the level is above zero.

| `TRIPPED -> CLEAR`
| The level drained to zero and no block holds. The per-tag contributions are cleared.
|===

`observe` and `delay` never block; what a trip changes on the wire is the consumer's decision, taken
from the returned state. The query API answers without admitting an event:

* `state(key)` -- the key's `SourceState` after draining to now, or empty when the key is not tracked;
* `isBlocked(key)` -- whether the key is `BLOCKED`;
* `trackedSources()` and `untrackedCount()` -- the map size and the overflow count.

A `SourceState` carries the key, the status (`CLEAR`, `TRIPPED`, `BLOCKED` or `UNTRACKED`), the level,
the threshold, the monotonic instant the block ends (meaningful only while `BLOCKED`) and the per-tag
contributions.

== The Emit Shape and the Trip Listener

A trip hands one `SourceTrip` to the listener registered at construction: the key, the level right
after the admission that tripped, the threshold, the window, the per-tag contributions, the configured
action and the monotonic trip instant. It is a *raw* record: no log template, no ECS or OCSF field
names, no wire format. Every rendering is the consumer's.

The listener is called on the admitting thread, after the key's lock is released, and only by the
admission that performed the transition. It must not block.

== Threading

The ledger is thread-safe. Every read-modify-write of one key -- drain, add, trip, block -- runs inside
one `ConcurrentHashMap.compute`, so two concurrent admissions for one source cannot both perform the
`CLEAR -> TRIPPED` transition and exactly one trip is emitted per `CLEAR` period. The two races the
design accepts are named above: the soft cardinality bound, and the listener running after the lock is
released, so a later admission's state may already be visible when the listener runs.

== Single Node, In Memory

The state lives in one process. It is not shared across gateway instances -- a source scanning a
cluster spreads its count across the instances it reaches -- and it does not survive a restart. Both
are deliberate: a shared store is a new dependency and a new failure mode on the request path, and
the substrate's job is to bound what one instance spends on one source.

== Second Consumer: Threat Classification

The per-source threat classification builds a weighted anomaly score per source from several kinds
of rejection, and raises one structured ALERT when a source's score crosses its threshold
(link:../adr/0078-Per-source_threat_classification_raises_one_ECS_alert_per_episode_from_its_own_ledger.adoc[ADR-0078]).
What the substrate serves it:

* *Its own ledger.* `ThreatClassifier` builds a `SourceLedger` of its own, with the threshold and
  window of the `threat_classification` block and the action `observe`. Nothing is shared with the
  recon ledger except the key derivation.
* *The shared key.* `SourceKeys` resolves the key once and stashes it, and runs whenever either
  consumer is enabled. The threat score therefore does not depend on `enumeration_detection` being
  on.
* *Weighted admission.* `ThreatWeights.weightOf` gives each rejection the threat feed is handed the
  weight of its event category, judged on the true event, before and after the trust boundary alike.
  It gives `0` to the categories and events that are not caller behaviour and to a static resource,
  except a filter verdict on the content the caller sent (`ThreatWeights.STATIC_SCORED_EVENTS`), and a
  `0` is never admitted. The `ThreatWeights` Javadoc holds the exact sets, including the rejections
  that are answered without reaching the feed.
* *The recon trip as an input.* The recon ledger's `SourceTrip` is admitted to the threat ledger
  with the weight `weights.recon_trip` under the tag `SOURCE_TRIPPED`, for the tripped key. A recon
  trip raises the score; it is never an ALERT of its own.
* *Dedup.* A trip is emitted once per `CLEAR` period, so the ALERT tier, `ThreatAlerts`, raises one
  ALERT per episode, not per event.
* *The per-tag breakdown.* The trip's contributions become the `contributions` and `categories`
  breakdown of the ALERT document.
* *The overflow count.* An admission that returns `UNTRACKED` is reported to the ALERT tier, which
  counts it and logs the first one per process.

What the consumer does itself, because the substrate deliberately does not serve it:

* *ECS formatting* -- the `SourceTrip` is raw. `ThreatAlertDocument` renders it as the ECS-shaped
  ALERT document
  (link:../architecture/observability-and-errors.adoc#_threat_alert_document[Observability -- the
  threat ALERT document]). The OCSF mapping is documented, not emitted.
* *Cross-node correlation* -- the state is per process; a SIEM that receives every node's ALERTs
  owns it.

What neither the substrate nor the consumer serves:

* *An exact sliding window* -- the bucket approximates one.
* *Persistence across restarts* -- a restart clears every bucket.
