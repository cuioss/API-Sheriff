= API Sheriff -- Contributor Guide
:toc:
:toclevels: 2

The *contributor layer* of the API Sheriff documentation. These documents are written for the
people who *build* the gateway -- compiling and testing the modules, understanding the module
layout, and following the project conventions. They describe how the codebase is put together
and how to work in it, distinct from the link:../README.adoc[design documentation] (which
defines *what* is built) and the link:../user/README.adoc[operator guide] (which describes how
to *run* the finished gateway).

== Inbound Validation: Where the Code Lives and Why

The inbound filter is *two stages split across route selection*, not one. A contributor changing
anything in this area needs the four structural reasons below, because each one is a constraint that
looks arbitrary until you know it. The decision record is
link:../adr/0024-Inbound_filter_modes_minimal_is_a_partial_disable_retaining_the_body_cap_and_path_allowlist_and_is_refused_on_authenticated_and_BFF_routes.adoc[ADR-0024];
the operator-facing behaviour is in
link:../configuration.adoc#_security_defaults[Configuration Reference -- `security_defaults`].

=== The two stages

`BasicChecksStage` is the *pre-route floor*. It validates the raw path and every header name and
value, enforces the parameter- and header-*count* caps, and records the canonical path. It runs under
the *gateway-wide* resolved configuration, for every request, before route selection.

`ThoroughChecksStage` is the *post-route per-route stage*. It is *always dispatched*, but only part of
its work is switchable: it unconditionally enforces the route's `max_body_bytes` cap and its
`allowed_paths` allowlist, then returns early when the route's profile is `MINIMAL`, skipping the
url-parameter name/value validation and the divergent pipeline re-run.

=== Why the url-parameter validation was relocated post-route

It used to live in the pre-route floor. It moved into `ThoroughChecksStage` because the profile is a
*per-route* setting and no route is resolved until after the floor has run -- so a pre-route parameter
check cannot be gated on a route's profile, and cannot run under the route's own
`SecurityConfiguration` either. The relocation is what makes both possible.

The relocation also made the ADR-0019 reserved-BFF-path relaxation *structural*: a reserved path
terminates in `handleReservedPath` before route selection, so it never reaches `ThoroughChecksStage`
and never reaches the parameter pipeline. The `reservedPathMatcher` predicate that used to implement
that exemption is *gone* -- do not reintroduce it. `BasicChecksStage` deliberately takes no
reserved-path argument.

=== Why the pre-route floor cannot be made skippable

`BasicChecksStage.validatePath` produces the *single canonical path* that route selection consumes.
Route selection therefore hard-requires the floor to have run: a request whose profile suppressed the
floor would have no canonical path to match a route against -- and with no route, there is no profile
to read in the first place.

This is a circular dependency, not a policy preference. Any proposal to let `profile: minimal` reach the
floor is not merely undesirable, it is unimplementable in this pipeline shape. The parameter *count*
cap stays in the floor for the same reason it is safe there: a collection limit is a DoS guard that
needs no per-route policy.

=== Why the `minimal` branch lives inside `ThoroughChecksStage`, not at the dispatch site

It would be easy to test the profile at the call site and skip dispatching the stage at all. That is
wrong, and the current shape is deliberate: `max_body_bytes` and `allowed_paths` are enforced *inside*
the stage and must run under `minimal`, so skipping the dispatch would silently drop both.

Keeping the branch inside the stage means the *stage itself* owns the closed list of what the mode
disables, immediately adjacent to the unconditional checks it must not affect. A future contributor
adding a check to this stage has to make an explicit decision about which side of the `if` it belongs
on, rather than inheriting a skip decision made elsewhere. Do not "optimise" the dispatch away.

=== Where the profile value-range gate lives

In the *bundled JSON Schema*, at each of its three symmetric `profile` declaration sites -- *not* in
`ConfigValidator`. An out-of-range value fails when the document is bound.

`ConfigValidator` deliberately carries *no* profile-range rule. A second copy of the enumeration would
be a second thing to keep in sync, and the failure mode of drift is that the looser gate silently
wins. `SecurityProfile.parse` returns an `Optional` for the model layer and for tests; it is not the
boot gate. When you add a mode, update the schema's three enum sites -- adding a validator rule
instead is the wrong fix.

=== Why the boot refusal keys on the effective access level

The `minimal`-refusal rule, `LimitRules.validateSecurityProfileMinimal`, derives the access level
through `RouteTableBuilder.effectiveAccessLevel` -- the same seam the route table uses -- rather than
reading `AnchorConfig.access` directly.

Reading the anchor's declared `access` would *under-refuse* the case that most needs refusing. Per
link:../adr/0007-anchor-scoped-policy.adoc[ADR-0007] a route or endpoint may legally *strengthen* a
`public` anchor's auth floor (weakening is forbidden, strengthening is not), so a route adding its own
`require: bearer` under an `access: public` anchor is authenticated *in effect* while its anchor still
reads `public`. The naive check passes exactly that route -- and it reads as coverage while providing
none.

The rule resolves the route's `auth` and `security_filter` blocks through the `PolicyBlock`
descriptors for the same reason: they are the one implementation of the resolution rule the route
table also uses, and re-deriving the posture from raw config fields would reintroduce the divergence
the shared seam exists to prevent. `effectiveAccessLevel`, `globalProfile` and `effectiveProfile`
(the field-level `security_filter.profile` fallback) are `public static` on `RouteTableBuilder` solely
to serve as shared seams, following the existing `normalizePrefix` precedent -- they are not
general-purpose API.

== Adding a Policy Block

A policy block is a configuration block resolved per route by the one rule of
link:../user/anchors.adoc#_policy_block_resolution[Policy-block resolution]: the nearest declared
scope of `gateway -> anchor -> endpoint -> route` wins, whole
(link:../adr/0067-Every_policy_block_is_one_declaration_resolved_nearest_declared_scope_wins_with_whole-block_replacement.adoc[ADR-0067]).
Each block is one `PolicyBlock` descriptor naming the scopes it is declarable at, its "is declared"
test, its nothing-declared fallback and its override-WARN opt-in. Adding a block -- or widening an
existing block to a further scope -- touches the places below. Each step names what catches a
missed edit; where nothing does, it says so.

[cols="3,4,4", options="header"]
|===
| Step | What to change | What catches a missed edit

| 1. Record component
| The block's component on the record of every scope it is declarable at (`GatewayConfig`,
  `AnchorConfig`, `EndpointConfig`, `RouteConfig`), with a builder entry.
| The compiler, once the descriptor names the accessor in step 5.

| 2. JSON schemas
| The key at each scope's location in `schema/gateway.schema.json` and `schema/endpoint.schema.json`,
  through a shared `$ref` where the block already exists elsewhere.
| `PolicyBlockSchemaContractTest`: descriptor scopes and schema locations must agree in both
  directions.

| 3. Native-image reflection
| A new model type registered in `ConfigModelReflection`.
| `ConfigModelReflectionTest`, which walks the record graph from `GatewayConfig` and `EndpointConfig`.

| 4. Array-key inventory
| Every list-valued key the block brings, in the inventory of `doc/configuration.adoc` (the stated
  counts included).
| `DocumentedSetsContractTest`, which derives the sets from the schemas.

| 5. Descriptor
| A `PolicyBlock` constant with its scopes, fallback and `overrideWarn` flag, listed in
  `PolicyBlock.ALL`, and its expectations in `PolicyBlockTest`.
| `PolicyBlockSchemaContractTest` (against the schemas) and `PolicyBlockTest`.

| 6. User documentation
| The block's row in the scope table of `doc/user/anchors.adoc` (`_policy_block_scopes`).
| `PolicyBlockSchemaContractTest`, which parses that table against `PolicyBlock.ALL`.

| 7. Override WARN
| When the block has an anchor scope and a nearer one, a decision whether replacing the anchor's
  block is announced (`overrideWarn`); an opted-in block needs `ApiSheriff-101` in
  `doc/LogMessages.adoc` to name it.
| `RouteTableBuilderTest` WARN-present and WARN-absent cases per opted-in block.

| 8. Every boot reader at every scope
| See below.
| For a reader that takes its scopes from the descriptor, the compiler and the reader's refusal of an
  unmapped scope; for any other reader, nothing generic -- the reader's own tests.
|===

*Every boot rule and boot-pipeline check that reads a block must read it at every scope the block is
declarable at.* A reader that resolves the block through its descriptor (`PolicyBlock.X.resolve`)
gets this for free. A reader that *enumerates declarations* instead -- `route.forward()`, a stream
over anchors and routes -- silently skips any scope it does not name, and a newly declarable scope
then lets a declaration bypass a boot refusal.

An enumerating reader can still take its scopes from the descriptor. The framework body-size check
(`maxDeclaredBodyBytes` in `ConfigBootPipeline`) has to enumerate, because it counts every declared
cap rather than only the one a route resolves (ADR-0023). It iterates `PolicyBlock.SECURITY_FILTER.scopes()`
and maps each scope to the declarations it holds through an exhaustive switch over `PolicyBlock.Scope`.
A new scope constant therefore fails the compile there, and the one scope the switch has no
declaration for -- `GATEWAY` -- throws an `IllegalStateException` instead of being skipped. Widening
`security_filter` to the gateway scope cannot slip past that reader: a boot, which always supplies
the framework ceiling, fails until the `GATEWAY` arm reads the new declaration. The offline
`--validate-config` run is the exception: it passes no ceiling, reports the body-limit check as
NOT CHECKED and never reaches `maxDeclaredBodyBytes`, so it does not fail there.

The other two readers that had to cover the endpoint scope when `security_filter` and `forward` gained
it were extended by hand, both in `ConfigValidator`: the token-relay/`Authorization` conflict now
reads the resolved forward block, and the forward mode-exclusivity rule also checks the
endpoint-declared block. Before widening a block, find every production reader of its record
component that names its scopes itself, and give each one a test at the new scope; no contract test
does this for you.

== Artifact Purity: No Test-Shaped Configuration in the Shipped File

=== The invariant

*The shipped artifact declares nothing test-shaped; the deployment supplies what it names.*

"No `%`-profile keys in `application.properties`" is the mechanical half of that rule, not the rule
itself. The full form has two clauses, and the second is the one a contributor is more likely to
breach by accident:

* Nothing in `api-sheriff/src/main/resources/application.properties` may exist only to make a test,
  a benchmark or a dev run work -- whether it is written as a `%it.`/`%dev.` branch or as a plain
  unprefixed key that happens to carry a test-only value.
* Where the product's configuration *names* something, the shipped file names it neutrally and the
  deployment binds it. `gateway.yaml` says `tls_profile: corporate-idp`; the deployment supplies the
  trust store behind that name. The name is policy, the material is deployment.

=== Why it matters

A profile branch is not a harmless convenience:

* *It ships test material inside the production artifact.* The `%it` trust bucket this repository
  used to carry put an integration-test truststore path *and its password literal* into the file
  every production deployment receives. Secrets and test fixtures do not become invisible by being
  behind a profile prefix -- they are in the image either way.
* *It can mask a defect that only the unbranched production profile would expose.* A branch means
  the configuration the tests exercise is not the configuration production runs. Every green test is
  then evidence about the branch, not about the artifact. The `%dev` file-logging exemption was
  exactly this: it existed to hide a shipped default (`quarkus.log.file.enabled=true` with a path
  resolving to the filesystem root) that was wrong for any run which did not override it.

=== The guard, and what it does not cover

`ShippedApplicationPropertiesTest` (in `api-sheriff`) reads the *packaged*
`target/classes/application.properties` and fails when any *key* starts with `%`. Two details in it
are load-bearing and must survive any refactoring:

* It resolves the file by path, deliberately *not* through `getResourceAsStream`. On the Surefire
  classpath `target/test-classes` precedes `target/classes`, so the resource call returns the *test*
  properties file -- and the guard would pass green while the shipped artifact regressed.
* It keys on the *key*, not on "the line contains `%`". `quarkus.log.file.format` legitimately
  contains `%d`, `%-5p` and `%s%e%n` in its *value*; a contains-check would false-positive forever.

The guard is *necessary but not sufficient*, and this plan is its own worked example of the gap:

* It sees `%`-prefixed keys only. An *unprefixed* but test-shaped key passes it -- a
  `quarkus.tls.benchmark-idp.*` bucket carrying a benchmark-specific profile name violates the
  invariant while satisfying the guard. That is why that bucket was *relocated to the deployment*
  rather than merely un-prefixed.
* It sees one file. A stale `%it.` citation living in another file's *comment* is structurally
  outside its reach -- and one did survive in `integration-tests/docker-compose.yml` until it was
  found by reading, not by the guard.

A green guard therefore means "no `%`-prefixed key in the packaged properties file", never "the
artifact is clean". The second clause of the invariant is still enforced by review.

=== The three shapes a removal takes

When you find a test-shaped entry, the fix is one of three -- pick by asking what the product does
with the property, not by which is least work:

. *Plain deletion*, when the product never reads that surface at all. The `%it` token-issuer keys
  fed the token-sheriff extension's own `sheriff.token.issuers.*` namespace; the request path runs
  off `gateway.yaml`, so the keys were deleted outright and the issuer the integration stack needs
  was declared in the mounted `gateway.yaml` where it belongs.
. *Full relocation to the deployment that names it*, when the material is genuinely needed but is
  deployment-scoped. The `%it` `benchmark-idp` truststore path and password moved into
  `integration-tests/src/main/docker/certificates/benchmark-idp-trust.properties`, which the compose
  services load through `QUARKUS_CONFIG_LOCATIONS`. The shipped file now binds no trust profile in
  any profile.
. *A shipped-default flip*, when the branch existed only to correct a default that was wrong for the
  unconfigured case. `%dev.quarkus.log.file.enabled=false` disappeared by shipping
  `quarkus.log.file.enabled=false` and having deployments that want a log file set
  `QUARKUS_LOG_FILE_ENABLED=true` beside their `LOG_FILE_PATH`.

The trap to avoid is a fourth, non-shape: deleting the branch and leaving the default it was
correcting. That is a regression wearing the invariant's clothes -- deleting the `%dev` line alone
would have left `quarkus:dev` writing a log file at `/`.
