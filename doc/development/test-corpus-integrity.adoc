= Test-Corpus Integrity -- Assertions That Assert Nothing
:toc: left
:toclevels: 3
:toc-title: Table of Contents
:sectnums:
:source-highlighter: highlight.js

A test can call production code, stay green and prove almost nothing. This note is the method API
Sheriff uses to find assertions that *cannot support the behaviour their names claim*, the vocabulary
that method classifies them with, and the standing rules that came out of applying it: the
<<fitness-function-shape,fitness-function shape>> every machine-checked invariant ships with, the
<<awaits-reassertion-guard,until-then-re-assert guard>>, and the
<<_standard_for_a_strengthened_assertion,standard a strengthened assertion meets>>.

The method has been applied exhaustively. Both test lanes -- `api-sheriff/src/test/**` and
`integration-tests/src/test/**` -- were read in full, every flagged method received exactly one
verdict, and the strengthened methods were each proved by an inversion audit: the asserted behaviour
was inverted locally and the test had to turn red. Nothing remains censused-but-unclassified. The
per-file verdict tables are not carried here; what is carried is the part that stays true for the next
test somebody writes, plus the <<open-work-list,integration-lane verdicts that are still open>>.

The companion note link:declared-limit-assertion-coverage.adoc[Declared-Limit Assertion Coverage]
does the same job for declared gateway limits; this one does it for assertion *strength*. The third
sibling, link:cookie-deliverability-blindness.adoc[Cookie-Deliverability Blindness], answers the
question neither of them asks -- which properties the integration lane is *structurally incapable of
observing*, however strong its assertions. All three follow the same discipline: enumerate the whole
surface first, credit what already exists by name, and record the remainder as a *countable* list
rather than as "various remaining tests".

The three divide cleanly by what they can be wrong about. This note asks *does the assertion support
the claim?*; the declared-limit note asks *does the claim have an assertion at all?*; the blindness
note asks *could any assertion in this lane have seen it?* A test can pass all three questions and
still be worthless only if the claim itself is wrong, which is a review problem rather than a
measurable one.

== Why This Note Exists

A test that calls production code and asserts only `assertDoesNotThrow(...)` or
`assertNotNull(result)` reports as coverage while proving almost nothing. It stays green when the
behaviour its `@DisplayName` promises is deleted, inverted, or never implemented. The corpus is
large enough that "we read everything and it looked fine" is not a claim anyone can check -- so the
method is built from *mechanical censuses whose counts are reproducible* plus a *read of the
candidates*, and it says plainly which files were read and which were not.

== Method

Census-then-targeted-read, deliberately -- not a linear pass over the whole corpus. A linear pass over
a corpus of well over a hundred test files and more than a thousand test methods degrades into
spot-checks, which is precisely the apparent-vs-real-coverage failure the method exists to catch. The
three steps:

. *Mechanical census* over the module-attributed inventory (`architecture search --content`),
  recording occurrence counts and complete-coverage evidence (files scanned, unreadable, truncated,
  elided).
. *Targeted read* of the ranked candidate files (100% of them) plus a *control sample* of the
  un-ranked remainder, to measure whether the ranking actually selected the vacuous ones.
. *Classify* every flagged method with exactly one verdict, cite `file:line`, then strengthen
  highest-risk-first and count what is left.

[IMPORTANT]
====
*Coverage claims cite census counts.* Where a file was not read, the record says so and counts it.
A "the whole corpus was reviewed" assertion is never made without the census that backs it.
====

Three census rules travel with the method:

* *Count both annotations.* The test-method denominator is `@Test` *union* `@ParameterizedTest`. A
  `@Test`-only count under-states the population, and a re-census after converting `@Test` methods
  into parameterized form would report a phantom drop *in the very file that was strengthened* -- a
  measurement artefact read as a regression. The strict pattern is `@Test(?![A-Za-z0-9_])`; the loose
  one also matches `@TestProfile`.
* *Occurrences are not call sites.* The raw marker count includes each file's `import static` line
  and any prose occurrence; the call-site count uses `marker\(`. State which one a figure is.
* *A carried figure is not a census.* A count inherited from an earlier pass is re-measured, with its
  pattern, commit and coverage evidence, before it is quoted. A delta that cannot be reconciled is
  recorded as unreconciled rather than explained after the fact.

=== Where census-then-targeted-read does not reach

The ranking selects candidates by *marker density*, which presupposes that a weak assertion leaves a
textual trace. That presupposition is only sometimes true, and the exception is not marginal -- it is
the shape that motivated the cookie-deliverability work.

*Shape (e) is invisible to every marker the census counts.* Nine cookie tests carried
substantive-looking status and attribute assertions and not one vacuity marker between them, while
being green about a session no browser could hold. A density ranking would never have surfaced them,
and neither would a read that only opened the ranked files. *For shape (e) the census shortcut is
unavailable, and the only method that finds it is reading every file in the pool* -- which is why the
integration lane, small enough to afford it, was read linearly.

The rest of the method survives intact. Density remains a working screen for shapes (a)--(d) --
<<density-finding>> is the evidence for that and against over-trusting it -- and the linear pass is
warranted where the defect class carries no marker, not as a general replacement for ranking.

[[search-form-constraint]]
=== Search-form constraint (load-bearing)

Every symbol-reachability census searches *both* the call form `name(` *and* the method-reference
form `::name` before recording any "unused" / "unreached" verdict.

This is not a formality. A literal `unseal(` search once returned *no production consumer* for
`SealedSessionCookieCodec.unseal`, while the real production call site is `codec::unseal` inside
`CookieSessionBinding.resolve()`. A call-form-only census would have produced a false "dead API"
verdict and an unsafe removal -- the exact apparent-vs-real failure this note is about, turned on the
note's own method.

== Taxonomy

=== What counts as flagged

A test method is *flagged* when its assertions cannot support what it claims. Three classes:

F1:: *Wholly vacuous* -- the method's entire assert-block consists only of `assertDoesNotThrow`
and/or `assertNotNull`.
F2:: *Partially vacuous* -- the method mixes a substantive assertion with one or more additional
*distinct scenarios* whose only assertion is a vacuous marker.
F3:: *Substituted client* -- the assert-block is entirely substantive, and the defect is one level
down: the observation it asserts over was produced by a client that applies none of the policy the
method's claim depends on. F3 is the flagging class for shape (e), and it exists because F1 and F2
are both defined over *markers* -- so neither can reach a method whose assertions look, and are,
strong.

=== The five shapes

[cols="1,3",options="header"]
|===
| Shape | Description

| (a) | construction / wiring-only evidence -- the object was built, nothing about it was inspected
| (b) | call returned without inspecting the return value
| (c) | tautological given the arrange block -- the assertion is entailed by the setup
| (d) | *highest risk among the marker shapes* -- named or documented for a behaviour its assertions
       do not exercise
| (e) | *permissive substitute client* -- the assertions are substantive, but the client that produced
       the observation enforces none of the policy the claim rests on
|===

Shape (d) is ranked highest *among (a)--(d)* because it is the only one of them that actively
*misleads*: the `@DisplayName` reads as a specification and the green result reads as its proof.

[[shape-e]]
==== Shape (e) -- the permissive substitute client

Shapes (a)--(d) are all properties of an *assert-block*: read the assertions, and the defect is
there to see. Shape (e) is not. Its assert-block can be exemplary -- exact status codes, exact
attribute values, a matched negative control -- and the test can still be green about a state that
could not occur, because the *client* standing in for the real one applies none of the policy that
would have prevented it.

That makes it the only shape with no textual marker, and therefore the only one a density census
cannot rank. It is also the only shape whose fix is usually not in the test: an assert-block that is
already substantive is not made honest by strengthening it further.

*The diagnostic question* -- the shape-(e) analogue of the inversion test -- is: *if the real client
applied its policy, would the arrange step still have succeeded?* When the answer is no, every
assertion downstream is being made about a state the production client would never have reached, and
the strength of those assertions is beside the point.

*Two confirmed instances in this corpus,* both in the integration lane, both recorded in the
companion note link:cookie-deliverability-blindness.adoc[Cookie-Deliverability Blindness]:

  at all: no per-cookie budget, and no `SameSite` / `Secure` / `+__Host-+` enforcement. The helper's

  (`integration-tests/.../BffKeycloakLoginFlow.java`).

=== The three verdicts

strengthen:: The claim is not supported. Applies when the name promises a specific post-condition the
assertion cannot distinguish (d), when a value-returning call discards its return (b), or when the
assertion is entailed by the arrange block (c).
keep:: *Correctly scoped.* The named behaviour genuinely *is* "completes without throwing" or "is
constructible", AND the admission is *attributable* -- either a matched negative control exists (a
sibling test whose arrange differs in exactly the dimension under test and which fails), or the
fixture itself is neutralised so a wrong implementation would throw (e.g. a provider that raises when
resolved, proving a code path never reached it).
delete:: The test is fully subsumed by a strictly stronger sibling and carries no distinct arrange.

The *matched-control* requirement is what keeps `keep` from becoming a rubber stamp. It is the same
standard <<fitness-function-shape>> sets for machine-checked invariants -- that section names the
*always-passing assertion* as one of four vacuity sources ("a rule that asserts only the absence of something passes when the subject is
renamed, moved, or deleted") and requires a *negative control* leg before a gate may be trusted as
enforcement. This note applies the same two ideas to ordinary unit tests.

[[fitness-function-shape]]
== Comment-Only Invariants Become Fitness Functions

Some repository invariants cannot be expressed in the type system. They are recorded as prose beside
the value they constrain: a comment above a configuration list, a note in a Javadoc block. Prose
enforces nothing. Whoever happens to read it follows it, while the invariant must hold for every
future author. A comment can name the exact failure mode it exists to prevent and still fail to
prevent it.

Such an invariant is therefore converted into a *fitness function*: an executable assertion the build
runs. The conversion carries its own risk. An assertion can be *vacuous* -- green because the rule
matches nothing, inverts its own verdict, or asserts a property that cannot fail. A vacuous gate is
worse than the comment it replaces. It turns an unenforced invariant into an apparently-enforced one,
and it removes the reader's motive to check.

=== The vacuity sources

Vacuity has four distinct sources. Closing one leaves the others open.

Polarity inversion:: Under ArchUnit's `no...` phrasing the framework inverts the polarity of a
condition's events. A `satisfied()` event counts as a violation and a `violated()` event as a pass. A
hand-written `ArchCondition` whose `check()` reports offenders through
`SimpleConditionEvent.violated(...)` -- the natural way to write one -- then reports nothing. Every
offender is reclassified as compliance, and the rule stays green over an arbitrarily dirty codebase.
Empty selection:: A rule whose predicate matches zero classes finds zero violations and passes.
Nothing distinguishes "no offenders exist" from "the selector is wrong".
Always-passing assertion:: A rule that asserts only the absence of something passes when the subject
is renamed, moved or deleted. The property it believed it was checking is gone, and so is the check.
Wrong artifact:: A gate that reads shipped configuration through the classpath can resolve a
test-profile copy instead of the packaged one. It then asserts green against a file that does not
ship.

The question a fitness function must answer is therefore not "assert or comment". It is "what must
an assertion ship with before it may be trusted as enforcement".

=== Positive phrasing

A fitness function is phrased *positively*: `classes().should(condition)` or
`fields().should(condition)`, with the condition emitting `SimpleConditionEvent.violated(...)` for each
offender. The `no...` form is never used for a coverage assertion, because it inverts the very events
the condition reports. A source sweep that is not an ArchUnit rule follows the same principle: it
collects offenders and asserts the collection is empty.

=== The four control legs

Every fitness function ships four control legs. Each leg closes a distinct vacuity source.

. *Non-vacuity guard.* A direct assertion that the selection predicate resolves to at least one
  subject today, that any parsed input is non-empty, and that the configuration key the rule reads is
  present. This leg distinguishes "no offenders" from "no selection".
. *Negative control.* A deliberately non-compliant fixture, in a dedicated specimen package, that the
  rule must reject. The test proves it by asserting the rule throws against the fixture. This leg
  proves the rule is *capable of failing*.
. *Matched positive controls.* Real classes from the production tree that are near misses for the
  predicate and must not be selected. A positive control asserts that the near-miss property still
  holds *before* it asserts exclusion. Otherwise it passes when the class is renamed or deleted, which
  is the always-passing failure one level down.
. *Specimen carve-out.* The production selection excludes the specimen package *explicitly*, not only
  through a test-source import filter. No single incidental mechanism is then the only thing that
  keeps the deliberate violation out of the real rule.

=== Packaged-artifact resolution, properties and scan radius

Three further rules complete the shape:

* *Resolve the packaged artifact by path.* A gate that reads shipped configuration resolves it by
  path against the packaged output directory, guarded by a regular-file precondition. It does not use
  classpath resolution: test resources can precede packaged resources on the test classpath, and the
  gate would then assert against the wrong artifact.
* *Assert a property, never membership.* The rule asserts a property of the selected set. It never
  asserts that the set equals today's members. A frozen membership list brings back the maintenance
  burden the gate exists to remove, because every legitimate addition becomes a test edit.
* *Justify the radius against the scan.* A selection radius is justified against the rule's *scan*
  radius, not against today's known members. When a rule imports a wide tree but selects a narrow
  subtree, the difference is scanned-then-discarded surface on which the invariant is unenforced.

=== What the shape costs

An invariant that was enforced by attention is enforced by the build, and it fails in the fast local
gate rather than in a downstream packaging step. The control legs make the gate's own health
observable: a change that breaks the selector or neuters the condition fails the guard or the
negative control instead of passing silently. Because the rule asserts a property, a legitimate
addition to the constrained set needs no test edit.

The cost is size. A fitness function with four control legs is much larger than the comment it
replaces, and it includes a fixture whose only purpose is to be rejected. The specimen package is
production-shaped code that exists only as a control, and a reader who meets it without this section
can mistake it for a defect.

Two residual risks stay open:

* *A control leg can rot.* A matched positive control whose near-miss property silently disappears
  degrades to an always-passing assertion. That is why the control asserts the property before it
  asserts exclusion.
* *The carve-out must track the predicate.* A widened selection predicate that does not widen the
  specimen carve-out pulls the deliberate violation into the production rule.

=== Alternatives rejected

*Leave the invariant as an explanatory comment.* This costs nothing and reads well where the value is
defined. It loses because enforcement by reading does not reach authors who never read that place.
The comment can name the exact failure mode and still not prevent it.

*Widen the underlying configuration to a package prefix instead of asserting per class.* This removes
the invariant entirely, because the constrained set becomes structural. It loses because a prefix
imposes the constrained behaviour on the whole package, not only on the members that need it. That is
a much larger blast radius, not a like-for-like swap.

*Generate the configuration from the source set at build time.* This removes drift by construction,
which is stronger than any assertion. It loses on cost: it adds build machinery whose maintenance and
failure modes need separate ownership, where the assertion needs none.

*Assert that the selected set equals its current membership.* This detects any change. It loses
because it detects *legitimate* changes just as loudly, so every valid addition becomes a test edit --
the maintenance burden the gate was introduced to remove.

*Phrase the rule with `no...` and report offenders as violations.* This reads more naturally as
English. It loses because the framework inverts the condition's event polarity under that form, so
the rule reports nothing and stays green over an arbitrarily dirty codebase.

Each rejected option either moves the enforcement burden somewhere nobody carries it, or produces a
gate whose green is not evidence.
link:../adr/0025-The_whole_server-TLS_surface_is_neutral_in_gatewayyaml_and_bound_by_exactly_two_seams.adoc[ADR-0025]
is an example of an invariant carried structurally rather than by convention.

[[awaits-reassertion-guard]]
== The Until-Then-Re-Assert Fitness Function

`api-sheriff/src/test/java/de/cuioss/sheriff/gateway/arch/AwaitsReassertionArchTest.java` converts
one comment-only invariant into a guard: *a declared test that waits on a
condition with `Awaits.until(..)` must assert the state it waited for after the wait returns.*

=== Why a wait is not an assertion

`Awaits.until` polls and either returns or throws a `TimeoutException`. A test whose last word on the
awaited state is the poll therefore records only that the condition held at some instant *during*
polling -- never that it holds at the point the test finishes reasoning about it. Remove the
behaviour the test names and the poll can still be satisfied transiently by a neighbouring effect,
and the method still returns green. Re-asserting after the wait moves the evidence onto the
post-state, which is what the test's name actually claims.

`edge/relay/WebSocketRelayStageTest.awaitReleases`:469 is the corpus's own worked example: the
`Awaits.until(..)` is immediately followed by `assertEquals(1, releases.get(), message)`.

=== Why a source sweep rather than an ArchUnit rule

The discriminator is the *order* of two calls inside one method body, and whether the second is an
assertion. ArchUnit reads bytecode, where an assertion call and an await call are both method calls
from the same code unit with no recoverable ordering -- the bytecode rule that would express this
does not exist. The sweep therefore reads source text, the same shape
`LoopbackEphemeralBindArchTest`'s wildcard-host-literal sweep uses and for the same reason.

The sweep is phrased *positively*: it collects offenders and asserts the collection is empty, naming
each offender in the failure message. The inverted `no...should` spelling is deliberately not used --
ArchUnit inverts a condition's event polarity under it, so such a rule reports nothing and stays
green over an arbitrarily dirty corpus.

=== The four control legs of <<fitness-function-shape>>

Non-vacuity guard:: `guardIsNonVacuous` asserts the source root resolves, the selection is non-empty,
it contains declared test methods, and at least one of those methods really calls `Awaits.until`.
Without the last, "zero offenders" cannot be told apart from a sweep whose pattern stopped matching.

Negative control:: `arch/specimen/AwaitsWithoutReassertionSpecimen` carries *two* deliberate
violations the sweep must report -- a test that asserts nothing at all, and one that asserts *before*
the wait and not after. The second exists because a guard that asked only "does this test assert
anything?" would accept it, and the control's exact count of two is what keeps that guard honest.

Matched positive controls:: `arch/specimen/AwaitsWithReassertionSpecimen` carries the compliant shape
and the helper-tier near miss. Each control asserts its near-miss property *first* -- that the file
still carries an awaited test method, and that the helper-tier await is still un-reasserted -- and
only then that the sweep does not report it. Reversed, either control would pass just as happily over
a file that had quietly become compliant, which is the always-passing failure one level down.

Specimen carve-out:: the specimen package is excluded from the production selection *by name* in
`isCarvedOutSource`, not by relying on a package or import filter, and the carve-out has its own
control that first proves the specimen still violates the rule.

=== Accepted limits

The limits below are bounds on what the guard reaches, stated here rather than left to be
discovered from a green run.

The selection is declared test methods, not every method:: When the guard was introduced the lane
carried *10*
`Awaits.until` occurrences across *6* files. *Five* sit inside a declared test method and are the
guard's live population (`auth/RetryingJwksLoaderTest` ×3, `auth/TokenValidatorProducerTest` ×1,
`testsupport/AwaitsTest` ×1). The other five are *wait primitives* -- `RetryingJwksLoaderTest.awaitLog`,
`edge/GatewayEdgeRouteTest.connectWhenAdmitted` and `.awaitReleased`,

helpers whose re-assertion obligation belongs to whichever test calls them, and several of which
legitimately end with the await. Sweeping every method body would report four of those five, which is
a noisy guard rather than a finding, so the scope is the declared test. *The cost is real and is not
hidden*: a helper that both waits and never re-asserts is out of reach, and so is a test that
delegates its entire wait to such a helper.

The lane is `api-sheriff` only:: `integration-tests` depends on `api-sheriff`, not the reverse, so an
ArchTest living in `api-sheriff` structurally cannot see integration-lane sources. *Mirroring the
sweep into `integration-tests` is explicitly not taken.* The integration lane carries no
`Awaits.until` call at all today, so a second copy would guard an empty set -- a standing vacuous
guard, which is the defect this note exists to remove -- while doubling the maintenance surface of a
hand-rolled source scanner. If the integration lane ever adopts `Awaits`, that decision is the trigger
to revisit this, and nothing else is.

The assertion is related to the wait by position, not by subject:: The guard asks only whether an
assertion follows the wait in the same test body, never whether it asserts the awaited state. A test
that waits on one condition and asserts an unrelated value passes, so a clean verdict means every
awaited test carries _some_ post-wait assertion, not that each re-asserts what it waited for. Relating
the two needs expression-level analysis of an arbitrary `BooleanSupplier`, which a source sweep cannot
do. The matched control `sweepAcceptsAnUnrelatedPostWaitAssertion` pins this near miss.

== Findings

The findings below outlive the passes that produced them: each is a way a green suite can mislead
that the next test author can recognise.

[[density-finding]]
=== Density is a screen, not a verdict

Files that clear a density threshold can produce *zero* strengthen verdicts. In
`bff/runtime/SessionAuthenticationStageTest`, `bff/csrf/CsrfDefenceTest` and
`edge/GatewayEdgeRouteTest` the marker count is high because the *subject* is an admit/reject gate,
and every admission is paired with a matched rejection control in the same class. Counting markers
finds candidates; only reading finds vacuity. A sweep that ranks by density and then acts *without
reading* would have rewritten seventeen correctly-scoped tests in those three files alone.

The exhaustive passes say the same from the other direction. The integration lane flagged 10% of its
methods and recommended strengthening 7%; the unit lane recommended strengthening 0.7% -- the corpus
is markedly stronger than its marker census suggests.

[[census-evasion]]
=== Published marker counts are a lower bound

`assertTrue(x != null)` and `assertTrue(optional.isPresent())` are an `assertNotNull` in everything
but name, and no marker census can count them. Both lanes carry the spelling. One occurrence found is
not evidence that the shape is rare; it is evidence that nothing looks for it. Every published marker
figure is therefore a *lower bound* on the vacuous-shape population, not a measurement of it.

In the other direction, `assertDoesNotThrow` used as a value-returning unwrapper around a reflective
call that throws a checked exception is a legitimate idiom, not a claim about behaviour. It inflates
the primary marker's call-site count, so a census that treats every call site as a candidate ranks
files on sites that assert nothing either way.

[[structurally-unfailable]]
=== The structurally unfailable assertion

`assertNotNull(record.toString())` cannot fail: a record's generated `toString` never returns null.
That is strictly worse than shape (a). Under (a) the object was merely un-inspected and a wrong
implementation could still have produced a null; here no implementation could have failed the check.
It is the *always-passing assertion* of <<fitness-function-shape>> reached from the other direction --
not by the subject disappearing, but by the property being unfalsifiable in the first place.

It is deliberately not a sixth shape, and neither is the spelling it resembles:
`assertNull(Awaits.connect(future, ...))` over a `CompletableFuture<Void>` is equally unfalsifiable,
but there the load-bearing assertion is the *await*, which fails by timeout. That test is honest and
only its spelling is odd.

[[mirror-finding]]
=== The unguarded mirror -- a claim of lockstep that nothing checks

A value is defined in one file, restated in another, and the restating file's Javadoc *claims the
lockstep* -- "kept in lockstep with", "the variable the overlaid gateway.yaml resolves to". Nothing
compares the two. The test is green whether the mirror is accurate or not, and green in a way that
specifically disarms the guard it belongs to. Four integration-lane `strengthen` verdicts were this
one defect; two of them are still on <<open-work-list>>.

The shape generalises past tests. `LogMessagesCatalogueTest` checks identifier uniqueness and band
membership but never reconciles the declared records against `doc/LogMessages.adoc`, so those rows are
a hand-maintained mirror with no comparison behind them.

*The corpus already contains the fix, twice.* `BenchmarkRealmCredentialConsistencyTest` exists solely
to compare the k6 script's credential literals against the realm import that provisions them, and its
Javadoc says why the values are not generated: the coupling would be worse than the mirror, so the
mirror stays and is *asserted*. `DescriptorInventoryWiringTest` does the same for a document, deriving
its expectations from the note at run time rather than transcribing them. A mirror that cannot be
derived is still owed a reader's warning: `EgressVerifyActivationWiringTest` carries two port literals
it cannot derive, and its Javadoc names all three files that must agree and states that none can check
the others.

[[cumulative-finding]]
=== A per-request assertion cannot observe cumulative exhaustion

`WebSocketProxyIT`'s class Javadoc records a failure this note's taxonomy would not have caught, and
it belongs here because the taxonomy is defined over *single methods*. Seven tests were green while
the relay leaked its admission permit on every connection. None of the seven was vacuous: each
asserted a real status on a real handshake. The blindness was structural -- three leaked permits
against a 2048-permit pool, with no assertion anywhere reading the pool.

The rule it states is worth carrying: *detecting resource exhaustion needs an assertion of a
different shape -- one made after N operations, and made about the gateway rather than about any
single response.* An eighth per-request test would have left the leak equally invisible.

That is a *sixth* way a green suite can be dishonest, and it is deliberately not shape (f). Shapes
(a)--(e) classify a method against its own claim; this one is a property of a *set* of methods and has
no per-method row to sit on. It is recorded as a finding rather than a taxonomy entry so the taxonomy
keeps meaning one thing.

=== The `assertNotNull` companion pattern

`assertDoesNotThrow(() -> act())` followed by `assertNotNull(someAccessor())` reads as *two*
assertions and still proves only that an object exists. Under the F1 rule such a method is flagged
exactly as a single-marker method is.

=== Equality that hides the property under test

An `EgressPolicy` built with `allowedEgressHost("localhost")` compares *equal* to
`EgressPolicy.secureDefault()` -- both render as `EgressPolicy(allowLoopback=false)`, so the host
allowlist is invisible to `equals` / `toString`. `assertEquals(EgressPolicy.secureDefault(), ...)`
therefore cannot detect an unintended widening, and the inverse assertion cannot detect a dropped
allowlist at all. The tests that use it stay honest only by pairing the equality check with a
behavioural `policy.check(uri)` assertion; a new test asserts the behaviour. The type is third-party
(`de.cuioss.sheriff.token.commons.transport`).

== Standard for a Strengthened Assertion

Every strengthened method must satisfy the anti-vacuity contract <<fitness-function-shape>> sets for
fitness functions, applied to an ordinary unit test:

* the assertion must be *capable of failing* on the behaviour the method's name claims;
* it must not degrade to an always-passing form when the subject is renamed or moved;
* where the claim is an *admission*, the strengthening either inspects the post-state directly or is
  paired with a matched negative control that makes the admission attributable;
* where the claim depends on a *client policy* -- a cookie budget, a cookie attribute, a certificate
  chain -- the strengthening must either observe something the substitute client does enforce, or the
  claim must be narrowed to what the gateway *emits*. See <<shape-e>>: strengthening an assert-block
  that was already substantive does nothing for a defect that lives one level down.

Inverting the asserted behaviour locally must turn the strengthened test red. A strengthening that
survives its own inversion has not strengthened anything.

*And the same standard applies to a `keep`.* Every `keep` verdict names the thing that
makes the admission attributable -- a matched control, a neutralised fixture, a narrow scope, or a
fixture-level assertion elsewhere. A `keep` that names nothing is a `strengthen` that was not written
down.
