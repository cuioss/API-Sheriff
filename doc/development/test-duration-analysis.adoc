= Test-Cycle Duration -- Measured Baseline, Findings and Proposals
:toc:
:toclevels: 2
:sectnums:

Where the time of the test cycle goes in CI, why, and what can change without reducing what is
proven. This page is an analysis and a ranked proposal list. It changes no test, POM or workflow;
each proposal is implemented only after it has been picked.

The constraint every proposal is held to: test quality stays the same or improves. No test is
deleted or weakened unless another named test demonstrably proves the same behaviour, coverage does
not drop, no real wait is shortened into a flake, and no gating test moves to a non-gating lane. A
speed-up that works by running less is reported as a finding and marked as such, never presented as
a fix.

== Summary

[cols="2,1,1"]
|===
| Required check (pull request) | Median | p90

| `integration-tests/conclusion` -- trigger to conclusion
| 34.7 min
| 36.6 min

| `build/conclusion` -- trigger to conclusion
| 30.9 min
| 32.7 min
|===

Five facts explain almost all of it:

. *The unit suite runs four times per pull request.* `maven.yml` runs `verify` on Java 25, on Java
  26 and a third time for Sonar; the integration-test lane runs it a fourth time because its
  command carries `-am`. Each run is the same 5483 tests and costs about 790 s.
. *The Sonar build is serial.* `sonar-build` declares `needs: build`, so the required
  `build/conclusion` waits for two full `verify` runs back to back.
. *Every test class gets its own JVM.* The root `pom.xml` sets `reuseForks=false`. Surefire reports
  about 290 s of test time inside a 796 s plugin execution; the remainder is fork start-up and
  per-JVM warm-up, paid about 160 times.
. *Integration-test time is real waiting, run in sequence.* Twelve classes account for about 90% of
  the failsafe run. They sleep on real token and session lifetimes, one class after another.
. *A test fixture image costs two minutes per run.* The `grpc-echo` image runs Maven inside Docker
  with an empty local repository, for one IT class with four tests.

Duplicated assertions are *not* where the time goes: every genuine duplicate found is worth
milliseconds. Runner queueing (2 s median) and job set-up (about 40 s per job) are negligible.

With the first four proposals in <<proposals>> both required checks are expected to land at 15 to
20 minutes; with all of them, at roughly 10 to 12.

=== The critical path

A pull request can merge when both `build/conclusion` and `integration-tests/conclusion` are green.

* On a pull request the integration-test lane decides, at 34.7 min, but the build lane follows at
  30.9 min. Shortening only one of them moves the critical path to the other.
* In the merge queue the integration-test lane decides alone: 30.5 min against 14.8 min, because
  `sonar-build` does not run on `merge_group`.
* A change therefore waits about 35 minutes for its pull-request checks and about 30 more in the
  merge queue. The push to `main` then runs both lanes a third time on the tree the merge queue
  just tested.

=== The Java 25 and 26 matrix

Both legs run `./mvnw verify -Dmaven.compiler.release=<version>` on the matching JDK. The logs show
identical work: 5483 + 113 + 202 tests on each leg, zero skipped. No test in the repository is
conditional on the Java version (the only execution condition is one `@EnabledOnOs`).

What the Java 26 leg proves that nothing else does: the sources compile with `--release 26` under
`-Werror`, and the full suite passes on a Java 26 runtime. That is a real, distinct proof.

What is duplicated: `sonar-build` is a third full `verify` on Java 25. It repeats the Java 25 leg
test for test and adds only the 50 s `sonar:sonar` goal. Coverage data is already produced by the
Java 25 leg, because JaCoCo is bound in the plain build.

== Findings

=== A -- Technical and architectural problems

==== One JVM per test class

`pom.xml:216-218` and `:237-238` set `useSystemClassLoader=false` and `reuseForks=false` for surefire
and failsafe, under the comment "Fix for class loading issues". No `forkCount` is set and
`.mvn/maven.config` pins `-T1`, so about 160 forks run one after another.

* The setting arrived with commit `15850608` (2025-08-09) as scaffolding copied from another
  project and was moved verbatim by `eb01ab27`. Neither commit states a reason, and no document or
  ADR does.
* It has since become load-bearing in two places.
  `api-sheriff/src/test/java/de/cuioss/sheriff/gateway/auth/SanMismatchedJwksServer.java:82-90`
  swaps the JVM-global trust store and names fork isolation as its first line of defence.
  `integration-tests/src/test/java/de/cuioss/sheriff/gateway/integration/BffTokenRefreshIT.java:104-111`
  relies on failsafe running classes strictly one at a time.
* The same policy costs the `integration-tests` module 30 s for 113 tests that sum to under 7 s,
  and the IT lane about 100 s across 64 forks.

A global flip to `reuseForks=true` is not safe. Four sites block it:

[cols="1,3,3"]
|===
| # | Site | Why

| B1
| `auth/SanMismatchedJwksServer.java:172-174`, used by `TokenValidatorProducerTest:735` and
  `BffRuntimeProducerTest:1852`
| Replaces `javax.net.ssl.trustStore*` for a whole nested-class lifetime.

| B2
| `edge/GatewayEdgeRoute.java:2557-2561` with `testsupport/UnreachablePort.java:108-117`
| The circuit-breaker name is derived from host and port; `UnreachablePort.pick` is deterministic,
  so four test classes would share one breaker name in one JVM.
  `GatewayEdgeErrorPageTest.java:152-153` records that a reused name "was observed never to open".

| B3
| The nine `@QuarkusTest` classes
| A live Quarkus application and its log manager would sit under the 29 `@EnableTestLogger`
  classes. Inferred, not observed.

| B4
| `tls/DefaultTrustSourceAuditTest.java:162-269`
| Sets and clears trust-store system properties; an issue only in combination with B3.
|===

Nothing else blocks it: there are no fixed listen ports (all 96 `listen` calls bind port 0 on
loopback), no `Locale`, `TimeZone` or default-`SSLContext` mutation, and no class-loader
manipulation in the test sources. In-JVM parallel execution is blocked more broadly, by the global
test log handler shared by 29 classes.

==== The environments

The compose stack is started once per failsafe run and never restarted or reconfigured. All twelve
gateway instances start in parallel and are ready in 6 to 7 s. *Merging variants would save about
nothing*, and the conflicting keys are process-wide (`tls.mtls.enabled`, `oidc.session.mode`, the
admission caps, the matched `upstream_verify_hostname` pair, certificate present against absent).
The variants are controls that differ in exactly one thing; that design should stay.

* Seven instances serve a single IT class each; that is their purpose.
* `api-sheriff-passthrough-empty` (port 10449) and `prometheus` are contacted by no IT. The first
  is the benchmark arm; of the second only the configuration file is read. Removing them from the
  IT lane saves memory, not time.
* APISIX and the benchmark nginx live in overlay compose files the IT lane does not load.
* Four configuration directories are not mounted by compose at all; ITs start one-off containers
  from them (`sheriff-config-late-idp`, `-tls-relaxation`, `-jwks-egress-mismatch`,
  `reserved-path-overlap`).
* The one environment that costs real time is `grpc-echo`: its Dockerfile runs
  `./mvnw ... -Pgrpc-echo clean package` inside the build container with an empty repository
  (1419 artifact downloads in the inspected log), about 119 s, for `GrpcProxyIT` (4 tests, 1.2 s).
  api-sheriff is compiled a third time in that step.

==== Sleeps and waits

In the integration tests the waiting is the test. About 600 s per run is `Thread.sleep` on real
lifetimes:

* The refresh suites sleep 22 s to reach the refresh window (access-token lifespan 45 s minus
  leeway 30 s). That wait occurs about 15 times: `BffTokenRefreshIT` 4, `BffRefreshReuseIT` 4,
  `BffCookieRefreshIT` 3, and once each in `BffFapiControlsIT`, `BffClientSecretModeIT`,
  `BffTlsRelaxationIT` and `BffGeneratedKeysIT`.
* `BffSessionIdleTimeoutIT` waits 29 s in server mode and 158 s in cookie mode
  (`COOKIE_IDLE_SECONDS=90`).
* `BffSessionAbsoluteTtlIT` waits 43 s; `JwksLateIdpReadinessIT` waits out the JWKS retry back-off.
* `HtmlErrorPageIT.upstreamTimeout` sends two requests in sequence that each wait the gateway's
  30 s upstream timeout.

These prove that a declared limit acts on the native image, which is the point of
link:declared-limit-assertion-coverage.adoc[the declared-limit rule]. None of them should be
shortened. What is accidental is that they run one after another, and that several tests in one
class wait separately for the same event.

In the unit tests real waiting is about 25 s per run, of which 6 to 7 s is accidental:

* `testsupport/AwaitsTest.java:459` waits a full 5 s ceiling to prove delegation, not the ceiling.
* `auth/RetryingJwksLoaderTest.java:273` drains 4 x 250 ms where a sibling proves the same absence
  with 4 x 50 ms; the class's constructor already accepts an injectable scheduler.
* `bff/refresh/TokenRefreshCoordinatorTest` sleeps 100 ms at about 13 call sites marked "no
  observable hook".

Every other timeout in the unit tests is an upper bound that returns immediately on success.
Session TTL and idle tests already use a fixed clock.

==== Real sockets and TLS

About 400 unit-test invocations create a fresh `Vertx` and usually two HTTP servers per test. The
steady-state cost is 64 to 140 ms each, so this is tens of seconds, not minutes. Each socket-level
class has an in-memory sibling for the pure logic (`pipeline/*StageTest` under
`GatewayEdgePipelineTest`, `FramingGateTest` under the framing corpus, and so on) and adds the real
parser, metrics and response rendering on top; that layering is deliberate.

=== Why test quality is unchanged or better

. *Parallel Sonar build.* The same three `verify` runs and the same Sonar analysis execute; only
  their order changes. The quality gate still blocks `build/conclusion`. If the Sonar goal is
  folded into the Java 25 leg instead, the analysis consumes the coverage of that very run, and the
  duplicate third run disappears. Nothing proven is lost, because that third run repeats the Java
  25 leg test for test.
. *No unit suite in the IT lane.* This one *does* work by running less, and is listed for that
  reason as a finding to decide on, not as a neutral fix. What makes it defensible: the removed run
  executes the same 5483 tests, on the same commit, on the same Java 25, as `build (25)`, whose
  result gates the same merge through the required `build/conclusion` -- on the pull request, in
  the merge queue and on the push. What is lost is one of four identical executions, which today
  acts as an unintended flake detector. Coverage is unaffected: the nested native build runs
  `clean` on `api-sheriff/target`, so the IT lane's unit coverage data is discarded today.
. *Host-built fixture jar.* `grpc-echo` is an upstream fixture, not the system under test. The same
  profile builds the same jar; only the place of the build changes. `GrpcProxyIT` is untouched.
. *No `quarkus-jacoco` timeout.* No test is touched. The condition is that coverage does not move:
  `api-sheriff/target/site/jacoco/jacoco.xml` must show the same covered instructions and branches
  per class before and after, and the SonarCloud figure must not drop. If the comparison shows
  that `@QuarkusTest` coverage is *not* in `jacoco.exec` today, the right change is to align the
  extension with the agent's data file, which raises reported coverage.
. *Concurrent sleep-bound classes.* Every class, method and assertion stays. Quality *improves* if
  the preconditions are done properly, because each destructive suite then owns its Keycloak user
  and its log, which removes the cross-suite coupling that today is only held off by sequential
  execution. Done without the preconditions it would produce false reds (revoked sessions) and
  false greens (foreign log records); that is the stated risk.
. *Shared waits.* Every assertion is kept and still observes a real refresh, timeout or expiry of
  the declared length. No wait is shortened. The cost is coarser failure granularity where two
  test methods become two assertion groups behind one wait; that can be kept by holding two
  sessions through one wait in a class-level fixture and leaving the methods separate.
. *Two surefire executions.* The same tests run with the same assertions. The classes that need
  isolation keep it, and for the first time the need is declared in the build and enforced by a
  guard, where today it is an undocumented side effect two source files quietly rely on. The
  breaker-name collision (B2) must be removed first, which also removes a latent trap.
. *Accidental waits and fixtures.* Each test still proves the same behaviour: `AwaitsTest:459`
  proves delegation with any ceiling; `RetryingJwksLoaderTest` proves the absence of a retry
  deterministically instead of by elapsed time, which is a stronger proof.
. *Shared Quarkus fork.* Same tests, same assertions; four boots are the number of distinct
  configurations.
. *Hygiene.* A duplicate is removed only where the table under C names the surviving test and the
  assertion that covers it.

=== Findings that are not proposals

These would save time by running less. They are recorded, not recommended.

* *The push to `main` re-tests the tree the merge queue just tested.* Both lanes run a third time
  on the merge commit. Removing that would save about 30 minutes of runner time per merge and no
  merge latency.
* *The Java 26 leg* costs one full `verify`. It proves compilation at `--release 26` and the suite
  on a Java 26 runtime. With proposal 1 it is off the critical path.
* *Shortening `COOKIE_IDLE_SECONDS` from 90* would cut about 85 s. The schema allows it, but it
  shrinks the margins of a timing test on slow runners.
* *`reuseForks=true` globally* or *in-JVM parallel execution* -- blocked by B1 to B4 and by the
  global test log handler.

=== Errors and weaknesses

. *The headline medians mix two populations.* Of the last 25 successful pull-request runs of
  `maven.yml`, 12 are Dependabot runs, for which `sonar-build` is skipped. Their wall-clock is 580
  to 1159 s; the other runs are 1248 to 2998 s, median about 28 minutes. The reported "19m10s
  until all required checks are green" and "20m02s" for `maven.yml` sit in the gap between the two
  groups and describe neither. A contributor's pull request waits about 28 minutes, not 19. The
  document does note that only 12 runs carried `sonar-build`, but does not split the medians.
. *The saving of the Sonar change is stated for the wrong population.* "About 9.5 minutes per pull
  request" holds for the non-Dependabot half only; Dependabot pull requests gain nothing.
. *The expected end state contradicts the document's own numbers.* It gives "about 6 minutes" once
  Sonar runs in parallel. Its integration-test lane is 10m55s wall-clock today and about 6m10s of
  job time after its proposals P10 to P13, plus the chained helper jobs; its end-to-end lane is
  7m18s. The critical path cannot fall below the slowest required lane, so the floor is 9 to 11
  minutes until the IT lane is shortened as well.
. *The `quarkus-jacoco` finding omits a setting that bears on it.* The module sets
  `quarkus.jacoco.reuse-data-file=true` at `pom.xml:173` and in its test `application.properties`.
  Someone configured the extension deliberately. The document leaves the cause of the missing data
  file open and makes the fix conditional on a coverage comparison, which is the right safeguard,
  but the existing configuration should be part of that investigation.
. *An unsourced claim.* "`forkCount > 1` was evaluated and rejected earlier (timing flakes, JaCoCo
  data loss)" cites no commit, issue or document, and none was found in its `doc/` tree or POMs.
. *Most duplicate pairs are not named.* It counts 53 genuine duplicates across five areas, names a
  handful and refers to working notes for the rest. No removal is proposed, so nothing follows
  from it, but the list is not reviewable as written.
. *The overhead table adds numbers that are not additive.* Its 484 s of surefire time is summed
  across modules that the reactor runs in parallel (`-T1C`), and is set beside the 574 s wall-clock
  of the job. The listed components sum to 529 s.
. *One proposal shortens a real wait.* P11 cuts a token lifetime from 35 s to 10 s for an expiry
  test. The document rates it low to medium risk and names a floor; under the constraint that no
  real wait may be shortened into a flake, it is the weakest of its proposals.

None of these touches the document's central findings, which hold: the serial Sonar build, the
fork policy, the JaCoCo timeout and the retry backoff are each demonstrated from source and log.

Two cautions also carry over from the review:

* TokenSheriff measured p90 queue times of 60 to 312 s on the same organisation runners over two
  weeks. The 2 s median reported here comes from a two-day sample; queueing was negligible in that
  sample, not necessarily in general.
* The population mix that distorts TokenSheriff's medians was checked here and is absent: all 19
  built pull-request runs in this sample carried `sonar-build`.

== Not measured, not verified

Stated separately from what was measured and found fine.

* *No per-class unit timings from CI.* The build job publishes no surefire reports, and the log
  prints display names of nested classes, which cannot be mapped to classes reliably. The unit
  ranking above is a local reproduction that timed out after 97 of about 160 classes on a loaded
  host. It ranks only, and it is incomplete.
* *The split of the 500 s unit overhead* into fork start-up, class loading and fixture warm-up is
  inferred from local reports and from the gap between plugin time and reported time. No CI run
  with a different fork policy exists.
* *Every saving marked "estimated"*, in particular proposals 5, 7 and 9, has not been tried. The
  blocking sites B2 (a JVM-global breaker registry) and B3 are inferred from source, not observed
  failing.
* *Reading coverage.* The fork-policy, IT-infrastructure and BFF/TLS readings covered their
  files. The routing, configuration and framing reading covered the framing and configuration-boot
  tests and 17 ITs in full and the remaining unit classes of `edge`, `pipeline`, `config` and
  `auth` by outline (method names, display names, parameter sources). The overlap table for those
  areas is verified only where it names two tests; further duplicates there cannot be excluded.
  About 45 acceptance tests consisting of a single `assertDoesNotThrow` were flagged by a scan and
  not read individually.
* *Flakes.* Failed and re-run runs were counted, not attributed.
* *The release lane.* `release.yml` runs the same IT command. Whether its called release workflow
  runs the unit suite independently was not checked; proposal 2 therefore leaves the release
  command unchanged.
* *The key sizes* behind the 3 to 4.5 s key-material initialisation were not confirmed in the
  library source.
* *The `quarkus-jacoco` timeout* was confirmed from one CI log and one local run. Why the data
  file is never written, and whether `@QuarkusTest` coverage already reaches `jacoco.exec`, was
  not established; proposal 4 depends on it.
* *SonarCloud coverage numbers* were not read; no proposal changes which tests run in the build
  that feeds Sonar.
