= Test-Cycle Duration -- Measured Baseline, Findings and Proposals
:toc:
:toclevels: 2
:sectnums:

Where the time of the test cycle goes in CI, why, and what can change without reducing what is
proven. This page is an analysis and a list of proposals ordered by expected gain. It changes no test, POM or workflow;
each proposal is implemented only after it has been picked.

The constraint every proposal is held to: test quality stays the same or improves. No test is
deleted or weakened unless another named test demonstrably proves the same behaviour, coverage does
not drop, no real wait is shortened into a flake, and no gating test moves to a non-gating lane. A
speed-up that works by running less is reported as a finding and marked as such, never presented as
a fix.

== Summary

[cols="2,1,1"]
|===
| Required check (pull request) | Median | p90

| `integration-tests/conclusion` -- trigger to conclusion
| 34.7 min
| 36.6 min

| `build/conclusion` -- trigger to conclusion
| 30.9 min
| 32.7 min
|===

Six facts explain almost all of it:

. *The unit suite runs four times per pull request.* `maven.yml` runs `verify` on Java 25, on Java
  26 and a third time for Sonar; the integration-test lane runs it a fourth time because its
  command carries `-am`. Each run is the same roughly 5500 tests and costs about 790 s.
. *The Sonar build is serial.* `sonar-build` declares `needs: build`, so the required
  `build/conclusion` waits for two full `verify` runs back to back.
. *Every test class gets its own JVM.* The root `pom.xml` sets `reuseForks=false`. Of the 796 s the
  unit run takes, about 290 s is test time; 513 s passes *between* classes, in 163 fork changes.
. *Every `@QuarkusTest` JVM waits out a 10 s timeout on shutdown.* The `quarkus-jacoco` extension
  waits for a data file that is never written: nine classes, about 90 s per `verify`.
. *Integration-test time is real waiting, run in sequence.* Twelve classes account for about 90% of
  the failsafe run. They sleep on real token and session lifetimes, one class after another.
. *A test fixture image costs two minutes per run.* The `grpc-echo` image runs Maven inside Docker
  with an empty local repository, for one IT class with four tests.

Duplicated assertions are *not* where the time goes: every genuine duplicate found is worth
milliseconds. Job set-up is about 40 s per job, and runners did not queue in the sample.

The four small proposals in <<proposals>> -- parallel Sonar build, no unit suite in the
integration-test lane, host-built `grpc-echo` jar, no `quarkus-jacoco` timeout -- are expected to
bring the build lane to about 15 minutes and the integration-test lane to about 20. All twelve
together bring them to roughly 9 and 12.

=== The critical path

A pull request can merge when both `build/conclusion` and `integration-tests/conclusion` are green.

* On a pull request the integration-test lane decides, at 34.7 min, but the build lane follows at
  30.9 min. Shortening only one of them moves the critical path to the other.
* In the merge queue the integration-test lane decides alone: 30.5 min against 14.8 min, because
  `sonar-build` does not run on `merge_group`.
* A change therefore waits about 35 minutes for its pull-request checks and about 30 more in the
  merge queue. The push to `main` then runs both lanes a third time on the tree the merge queue
  just tested.

=== Between the test classes

the next one starting belongs to no test: it is JVM exit, JVM start, and for a `@QuarkusTest` class
the application boot and shutdown. Eight `build (25)` logs, 161 to 164 class changes per run:

[cols="3,1,1,1"]
|===
| Transition | Per run | Median gap (s) | Sum per run (s)

| plain class to `@QuarkusTest` class | 5 | 11.0 | 53

| `@QuarkusTest` class to `@QuarkusTest` class | 3 | 22.0 | 66

796 s of the plugin execution and the roughly 290 s of test time surefire reports.

=== The Java 25 and 26 matrix

Both legs run `./mvnw verify -Dmaven.compiler.release=<version>` on the matching JDK. The logs show
identical work: the same test counts on both legs of every run (for example 5483 + 113 + 202),
zero skipped. No test in the repository is
conditional on the Java version (the only execution condition is one `@EnabledOnOs`).

What the Java 26 leg proves that nothing else does: the sources compile with `--release 26` under
`-Werror`, and the full suite passes on a Java 26 runtime. That is a real, distinct proof.

What is duplicated: `sonar-build` is a third full `verify` on Java 25. It repeats the Java 25 leg
test for test and adds only the 50 s `sonar:sonar` goal. Coverage data is already produced by the
Java 25 leg, because JaCoCo is bound in the plain build.

== Findings

=== A -- Technical and architectural problems

==== One JVM per test class

`pom.xml:216-218` and `:237-238` set `useSystemClassLoader=false` and `reuseForks=false` for surefire
and failsafe, under the comment "Fix for class loading issues". No `forkCount` is set and
`.mvn/maven.config` pins `-T1`, so about 163 forks run one after another.

* The setting arrived with commit `15850608` (2025-08-09) as scaffolding copied from another
  project and was moved verbatim by `eb01ab27`. Neither commit states a reason, and no document or
  ADR does.
* It has since become load-bearing in two places.
  `api-sheriff/src/test/java/de/cuioss/sheriff/gateway/auth/SanMismatchedJwksServer.java:82-90`
  swaps the JVM-global trust store and names fork isolation as its first line of defence.
  `integration-tests/src/test/java/de/cuioss/sheriff/gateway/integration/BffTokenRefreshIT.java:104-111`
  relies on failsafe running classes strictly one at a time.
* The same policy costs the `integration-tests` module 30 s for 113 tests that sum to under 7 s,
  and the IT lane about 100 s across 64 forks.

A global flip to `reuseForks=true` is not safe. Four sites block it:

[cols="1,3,3"]
|===
| # | Site | Why

| B1
| `auth/SanMismatchedJwksServer.java:172-174`, used by `TokenValidatorProducerTest:735` and

==== The environments

The compose stack is started once per failsafe run and never restarted or reconfigured. All twelve
gateway instances start in parallel and are ready in 6 to 7 s. *Merging variants would save about
nothing*, and the conflicting keys are process-wide (`tls.mtls.enabled`, `oidc.session.mode`, the
admission caps, the matched `upstream_verify_hostname` pair, certificate present against absent).
The variants are controls that differ in exactly one thing; that design should stay.

* Seven instances serve a single IT class each; that is their purpose.
* `api-sheriff-passthrough-empty` (port 10449) and `prometheus` are contacted by no IT. The first
  is the benchmark arm; of the second only the configuration file is read. Removing them from the
  IT lane saves memory, not time.
* APISIX and the benchmark nginx live in overlay compose files the IT lane does not load.
* Four configuration directories are not mounted by compose at all; ITs start one-off containers
  from them (`sheriff-config-late-idp`, `-tls-relaxation`, `-jwks-egress-mismatch`,
  `reserved-path-overlap`).
* The one environment that costs real time is `grpc-echo`: its Dockerfile runs
  `./mvnw ... -Pgrpc-echo clean package` inside the build container with an empty repository
  (1419 artifact downloads in the inspected log), about 119 s, for `GrpcProxyIT` (4 tests, 1.2 s).
  api-sheriff is compiled a third time in that step.

==== Sleeps and waits

In the integration tests the waiting is the test. About 600 s per run is `Thread.sleep` on real
lifetimes:

* The refresh suites sleep 22 s to reach the refresh window (access-token lifespan 45 s minus
  leeway 30 s). That wait occurs about 15 times: `BffTokenRefreshIT` 4, `BffRefreshReuseIT` 4,
  `BffCookieRefreshIT` 3, and once each in `BffFapiControlsIT`, `BffClientSecretModeIT`,
  `BffTlsRelaxationIT` and `BffGeneratedKeysIT`.
* `BffSessionIdleTimeoutIT` waits 29 s in server mode and 158 s in cookie mode
  (`COOKIE_IDLE_SECONDS=90`).
* `BffSessionAbsoluteTtlIT` waits 43 s; `JwksLateIdpReadinessIT` waits out the JWKS retry back-off.
* `HtmlErrorPageIT.upstreamTimeout` sends two requests in sequence that each wait the gateway's
  30 s upstream timeout.

These prove that a declared limit acts on the native image, which is the point of
link:declared-limit-assertion-coverage.adoc[the declared-limit rule]. None of them should be
shortened. What is accidental is that they run one after another, and that several tests in one
class wait separately for the same event.

In the unit tests real waiting is about 25 s per run, of which 6 to 7 s is accidental:

* `testsupport/AwaitsTest.java:459` waits a full 5 s ceiling to prove delegation, not the ceiling.
* `auth/RetryingJwksLoaderTest.java:273` drains 4 x 250 ms where a sibling proves the same absence
  with 4 x 50 ms; the class's constructor already accepts an injectable scheduler.
* `bff/refresh/TokenRefreshCoordinatorTest` sleeps 100 ms at about 13 call sites marked "no
  observable hook".

Every other timeout in the unit tests is an upper bound that returns immediately on success.
Session TTL and idle tests already use a fixed clock.

==== Real sockets and TLS

About 400 unit-test invocations create a fresh `Vertx` and usually two HTTP servers per test. The
steady-state cost is 64 to 140 ms each, so this is tens of seconds, not minutes. Each socket-level
class has an in-memory sibling for the pure logic (`pipeline/*StageTest` under
`GatewayEdgePipelineTest`, `FramingGateTest` under the framing corpus, and so on) and adds the real
parser, metrics and response rendering on top; that layering is deliberate.

=== B -- Grouping and infrastructure restarts

==== The `quarkus-jacoco` shutdown timeout

`api-sheriff/pom.xml:158` declares the `quarkus-jacoco` extension while `jacoco:prepare-agent` is
active as well. The extension registers a shutdown hook that waits for
`target/jacoco-quarkus.exec` to change, polling for at most 10 s. The file is never written. After
a local run `api-sheriff/target/jacoco-report/error.txt` reads:

----
Timed out waiting for Jacoco data file .../api-sheriff/target/jacoco-quarkus.exec update,
file size before test run: did not exist, current file size: does not exist
----

Only `jacoco.exec` exists in `target/`. The CI logs show the signature after every `@QuarkusTest`
class: the next class starts 13 s later where a plain class takes 2 s. Nine classes, about 90 s per
`verify`.

Why the data file is never written was not established. The likely explanation is that the
instrumented classes resolve the agent `jacoco:prepare-agent` already installed, so the data lands
in `jacoco.exec`; if so, `@QuarkusTest` coverage is already in the report Sonar reads and the
Quarkus-side report is empty and unused. This build sets no `quarkus.jacoco.*` property.
TokenSheriff has the same defect and additionally sets `quarkus.jacoco.reuse-data-file=true`, which
did not prevent it there.

=== What the order does not show

The order is by gain alone. Three things matter when picking:

* *Both lanes gate.* Proposal 1 alone leaves the integration-test lane at 34.7 min; proposal 2
  alone leaves the build lane at 30.9 min. Neither shortens a pull request without the other.
* *The cheap ones are 1, 2, 6 and 7.* Together they are expected to bring the build lane to about
  15 min (one `verify` of about 14 min after 7, plus helper jobs) and the integration-test lane to
  about 20 min (2082 s minus 785 s minus 105 s).
* *Some gains overlap.* 3 takes most of what 5 would save. 4 takes most of what 8 would save, and
  it requires the circuit-breaker name collision (site B2) to be removed first. Proposals 4, 7, 8,
  9 and 10 act on every `verify`, so their effect on the critical path is counted once after
  proposal 1 and twice before it.

Expected end state with all twelve: build lane about 9 minutes, integration-test lane about 12. In
the merge queue only the integration-test lane changes, from 30.5 min to about the same 12.

=== Why test quality is unchanged or better

1 -- Parallel Sonar build::
The same three `verify` runs and the same Sonar analysis execute; only their order changes. The
quality gate still blocks `build/conclusion`. A failing build no longer prevents a Sonar run, which
costs runner minutes on broken builds. If the Sonar goal is folded into the Java 25 leg instead,
the analysis consumes the coverage of that very run and the duplicate third run disappears; nothing
proven is lost, because that run repeats the Java 25 leg test for test.

2 -- No unit suite in the IT lane::
This one *does* run less than today, and is marked as such. What makes it sound: the removed run
executes the same tests, on the same commit, on the same Java 25, as `build (25)`, whose result
gates the same merge through the required `build/conclusion` -- on the pull request, in the merge
queue and on the push. What is lost is one of four identical executions, which today acts as an
unintended flake detector. Coverage is unaffected: the nested native build runs `clean` on
`api-sheriff/target`, so the lane's unit coverage data is discarded today. Building the upstream
modules with tests skipped and running `verify` on the IT module alone is also the ordinary shape
of such a lane; TokenSheriff's is built that way.

3 -- Concurrent sleep-bound classes::
Every class, method and assertion stays. Quality *improves* if the preconditions are met, because
each destructive suite then owns its Keycloak user and its log, which removes the cross-suite
coupling that today is only held off by sequential execution. Done without the preconditions it
would produce false reds (revoked sessions) and false greens (foreign log records); that is the
stated risk.

4 -- Two surefire executions::
The same tests run with the same assertions. The classes that need isolation keep it, and for the
first time the need is declared in the build and enforced by a guard, where today it is an
undocumented side effect two source files quietly rely on. Removing the breaker-name collision
first also removes a latent trap.

5 -- Shared waits::
Every assertion is kept and still observes a real refresh, timeout or expiry of the declared
length. No wait is shortened. The cost is coarser failure granularity where two test methods become
two assertion groups behind one wait; holding two sessions through one wait in a class-level
fixture keeps the methods separate.

6 -- Host-built fixture jar::
`grpc-echo` is an upstream fixture, not the system under test. The same profile builds the same
jar; only the place of the build changes. `GrpcProxyIT` is untouched.

7 -- No `quarkus-jacoco` timeout::
No test is touched. The condition is that coverage does not move:
`api-sheriff/target/site/jacoco/jacoco.xml` must show the same covered instructions and branches
per class before and after, and the SonarCloud figure must not drop. If the comparison shows that
`@QuarkusTest` coverage is *not* in `jacoco.exec` today, the right change is to align the extension
with the agent's data file, which raises reported coverage. Disable the report; do not remove the
extension before the cause is understood.

8 -- Lazy key material::
The keys are fixtures. Generation on first use yields the same keys to the same tests. The change
must make the lookup atomic, which also removes a check-then-act race in the current code.

9 -- Shared Quarkus fork::
Same tests, same assertions; four boots are the number of distinct configurations.

10 -- Accidental waits and fixtures::
Each test still proves the same behaviour: `AwaitsTest:459` proves delegation with any ceiling;
`RetryingJwksLoaderTest` proves the absence of a retry deterministically instead of by elapsed
time, which is a stronger proof.

11 -- One repository restore::
Not test-related.

12 -- Hygiene::
A duplicate is removed only where the table under C names the surviving test and the assertion
that covers it.

=== Findings that are not proposals

These would save time by running less, or by narrowing a margin. They are recorded, not
recommended.

* *The push to `main` re-tests the tree the merge queue just tested.* Both lanes run a third time
  on the merge commit. Removing that would save about 30 minutes of runner time per merge and no
  merge latency.
* *The Java 26 leg* costs one full `verify`. It proves compilation at `--release 26` and the suite
  on a Java 26 runtime. With proposal 1 it is off the critical path.
* *A shorter access-token lifespan for the refresh clients* (45 s today, refresh window at 15 s,
  hence the 22 s waits) would cut about 10 s from each of about 15 waits. It narrows the margin of
  every "not yet refreshed" assertion on a slow runner; proposals 3 and 5 reach the same time
  without it.
* *Shortening `COOKIE_IDLE_SECONDS` from 90* would cut about 85 s. The schema allows it, but it
  shrinks the margins of a timing test on slow runners.
* *`reuseForks=true` globally* or *in-JVM parallel execution* -- blocked by sites B1 to B4 and by
  the global test log handler.
* *Fork reuse for failsafe* -- blocked by RestAssured global statics and system properties, and
  worth 60 to 90 s; proposal 3 is the better use of the effort.

== Relation to the TokenSheriff analysis

TokenSheriff, a sibling project built on the same scaffolding and the same organisation workflows,
was analysed the same way (`doc/development/test-duration-analysis.adoc` there). The two analyses
checked each other; what follows is where they meet.

Shared findings, reached independently in both repositories:

* The serial `sonar-build` is the largest single lever on the build lane. One change to the
  organisation workflow serves both projects, and so does the single `~/.m2` restore.
* `reuseForks=false` is copied scaffolding without a recorded reason, in both the surefire and the
  failsafe configuration.
* The `quarkus-jacoco` shutdown timeout exists in both builds with the same signature.
* The second Java leg proves something distinct; the Sonar run is the redundant one.
* Genuine duplicates exist and are worth less than a second.
* A JVM-mode replacement for the native integration tests cannot be shown to keep what the native
  run proves. Native-binary caching is possible but risky; Docker image caching is not worth it.
* The eager key generation in the `token-sheriff-validation` test generators costs 3 to 4.5 s per
  JVM. This repository pays it in 15 forks; the fix belongs to TokenSheriff.

What TokenSheriff found that has no counterpart here:

[cols="2,3"]
|===
| TokenSheriff finding | Here

| Retry back-off inside unit tests (five tests of 15 s)
| Not present; see the note on `RetryingJwksLoaderTest` in the unit ranking.

| JFR compiled into the IT native image
| `quarkus.native.monitoring=jfr` is set in the product's own `application.properties`. The IT lane
  tests the image the release publishes, so it is not a test-lane setting.

| Frontend chain in the IT build, identity-provider start order, a client-only IT job
| No counterpart in this build.
|===

What this analysis found that TokenSheriff took over: the blocker analysis before reusing forks,
the two-execution split with a guard test in place of a global switch, and sharing a wait instead
of shortening a lifetime.

== Not measured, not verified

Stated separately from what was measured and found fine.

=== Not measured

* *Per-class unit timings on CI.* The build job publishes no surefire reports, and the log prints
  display names of nested classes, which cannot be mapped to classes reliably. The unit ranking is
  a local reproduction that timed out after 97 of about 160 classes on a loaded host. It ranks
  only, and it is incomplete.
* *Every gain marked "estimated"*, in particular proposals 3, 4 and 9. None has been tried.
* *The split of in-test warm-up* (key material, configuration stack, Vert.x first use) inside the
  290 s of reported test time. The time *between* classes is measured; the warm-up inside the
  first test of each class is inferred from local reports.
* *Flakes.* Failed and re-run runs were counted, not attributed.
* *SonarCloud coverage numbers* were not read; no proposal changes which tests run in the build
  that feeds Sonar.

=== Not verified

* *Why `jacoco-quarkus.exec` is never written*, and therefore whether `@QuarkusTest` coverage
  already reaches `jacoco.exec`. Proposal 7 depends on it.
* *The blocking sites B2 and B3* -- a JVM-global breaker registry, and a live Quarkus application
  under the test log handler -- are inferred from source, not observed failing.
* *The unit-test wait inventory for classes that never ran locally.* Most of `bff/**` is missing
  from the local run. For those classes the statement that every other timeout is an upper bound
  that returns immediately rests on reading alone.
* *Reading coverage.* The fork-policy, IT-infrastructure and BFF/TLS readings covered their
  files. The routing, configuration and framing reading covered the framing and configuration-boot
  tests and 17 ITs in full and the remaining unit classes of `edge`, `pipeline`, `config` and
  `auth` by outline (method names, display names, parameter sources). The overlap table for those

  About 45 acceptance tests consisting of a single `assertDoesNotThrow` were flagged by a scan and
  not read individually.
* *The IT-specific findings have one reader.* The BFF refresh, idle and TTL waits, the twelve
  gateway variants and the `grpc-echo` fixture were not checked against the test sources by the

* *The release lane.* `release.yml` runs the same IT command. Whether its called release workflow
  runs the unit suite independently was not checked; proposal 2 therefore leaves the release
  command unchanged.
* *The key sizes* behind the 3 to 4.5 s key-material initialisation were not confirmed in the
  library source.
