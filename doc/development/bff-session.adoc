= Server-Session BFF -- Contributor Guide
:toc:
:toclevels: 3
:sectnums:

A contributor-facing guide to the *server-session BFF* implementation (Variant 2): where its code
lives, how to build and test it, and the one architectural rule that keeps it correct. It describes
how to *work in* the code; the design rationale is in
link:../variants/02-bff-session.adoc[Variant 2 -- BFF, Session-based] and the canonical seam
statement in link:../architecture.adoc#_bff_session_runtime[Architecture -- Server-session BFF runtime].

== The engine boundary rule (read first)

*The gateway re-implements no OAuth leg.* The confidential-client *engine* (`token-sheriff-client`)
owns retrieval and flow -- auth-code + PKCE, `state`/`nonce`/exact `redirect_uri`, mix-up defence,
the pushed-authorization-request transport, client authentication, the DPoP proof,
refresh-with-rotation, RP-initiated logout, RFC 9470 step-up -- and the server-side token lifecycle.
The *BFF* (this code) owns only the browser-facing part: the binding/session cookies, CSRF, request
proxying, the curated user-info view, logout receivers, and RFC 9457 rendering for gateway-raised
errors.

When you add or change a reserved handler, drive an engine seam -- never hand-roll an OAuth request,
a token exchange, or a JWKS fetch inside the gateway. If a capability seems to need a new OAuth leg,
that leg belongs upstream in the engine, not here. This boundary is enforced by review; keep it
intact.

== Where the code lives

All BFF code is in the `api-sheriff` module under `de.cuioss.sheriff.gateway`:

[cols="1,2"]
|===
| Package | Responsibility

| `bff.session`
| The session-resolution seam: `SessionBinding` and its server-mode implementation
  `ServerSessionBinding`, `SessionRecord`, `SessionStore` (`InMemorySessionStore`),
  `SessionCookieCodec` (the opaque `__Host-` session cookie), and `SessionEndListener` /
  `SessionRelayRegistry` (what is closed when a session ends). See <<session-store>>.

| `bff.pending`
| The pre-session transaction: `PendingAuthorizationRecord`/`Store` and `BindingCookieCodec` -- the
  browser-binding cookie that ties an in-flight login to one browser until the callback lands.

| `bff.client`
| `ClientSigningKey` -- one signing key of the confidential client, provided from a PEM file or
  generated at startup.

| `bff.login`
| `LoginFlow` -- auth-code initiation over the engine's authorization seam;
  `PushedAuthorizationRequests` -- the adapter that pushes every authorization request;
  `BoundTokenEndpointClient` -- the token-endpoint client that refuses an unbound token response;
  `ScopedEngineFlows` -- the per-scope-set engine flows;
  `SessionWidening` -- the widening of a live session, silent attempt and interactive re-drive.

| `bff.reserved`
| The reserved-endpoint handlers and the `ReservedPathRegistry`: `CallbackEndpoint`,
  `LoginInitiationEndpoint`, `StepUpEndpoint`, `UserInfoEndpoint` (+ `ClaimAllowlistFilter`),
  `LogoutEndpoint`, `BackchannelLogoutEndpoint`, `ClientJwksEndpoint`.

| `bff.csrf` / `bff.refresh` / `bff.logout`
| `CsrfDefence`; the `TokenRefreshCoordinator` / `StepUpCoordinator`; the logout token validator and
  RP-initiated / back-channel logout logic.

| `bff.runtime`
| `BffRuntime` (the single edge-facing collaborator), `SessionAuthenticationStage`, and
  `GatewayJson` -- the CDI bean that renders the JSON bodies the gateway authors through the
  platform's Jackson serializer.

| `quarkus.BffRuntimeProducer`
| The CDI producer that assembles the active runtime and binds the engine seams.
|===

The handlers and codecs under `bff.*` take raw request pieces and return a rendered response, so
each is unit-testable without a container. That is a testing convenience, not a package rule: the
`bff` packages are not framework-free and no gate checks them. Where the platform supplies a
mechanism, use it; a hand-written component needs a recorded reason
(link:../adr/0062-Platform_mechanisms_are_preferred_over_hand-rolled_equivalents_and_the_framework-agnostic_core_rule_is_retired.adoc[ADR-0062]).
`GatewayJson` is the example of the first, the session store of the second. The runtime is
assembled by `BffRuntimeProducer`, and the edge (`gateway.edge`) consults the `ReservedPathRegistry`
before the proxy route table and dispatches a matched reserved path through
`BffRuntime.dispatch(...)`.

== The session store and the session binding

`SessionBinding` is the contract; `ServerSessionBinding` implements it over a `SessionStore`. The
decisions are in
link:../adr/0018-BFF_session_mode_is_one_SessionBinding_seam_behind_a_fixed_reserved-path_and_CSRF_model.adoc[ADR-0018]
and its amendments. The store is hand-written because no platform session mechanism has what the
contract needs (ADR-0062), and the producer builds it, not the container, because a bearer-only
gateway must not have one.

=== One creating write, two updating writes

[cols="1,1,3", options="header"]
|===
| `SessionBinding` | `InMemorySessionStore` | Used by

| `bind`
| `create`
| `CallbackEndpoint.completeLogin`. Stores a new session under a new handle. It is the only write
  that consumes capacity and the only one that applies the two bounds.

| `persist`
| `replaceIfPresent`
| `TokenRefreshCoordinator`, on both refresh legs. Replaces the record and keeps the handle.

| `persistReissuingCookie`
| `replaceAndReissueHandle`
| `CallbackEndpoint.completeWidening`. Replaces the record and swaps the handle.
|===

Neither updating write stores anything when the session identity is no longer held. Both return an
empty result then, and the caller must treat the session as ended and must not hand out the new
tokens. A new caller that updates a session picks one of the two by one question: does the
privilege of the session change? If it does, re-issue.

=== The handle beside the record

The cookie value is a random handle, not `SessionRecord.sessionId()`. The store holds three things
per session -- the record, its current handle and its last-access instant -- and a second map from
handle to session identity. The handle is store-side state and not a component of the record. That
matters for one interleaving: a refresh that resolved the session before a re-issue and replaces
the record after it writes the record only, so it leaves the re-issued handle in place and cannot
put the previous one back.

Three rules follow for code that touches sessions:

* Never use the session identity as a lookup key for a request, and never write it into a cookie, a
  log record or a response. `SessionRecord.toString` redacts it.
* Key per-session work -- the refresh coordinator's single-flight, the relay registry -- on the
  session identity, never on the handle. The handle changes; the identity does not.
* A request that still carries the previous handle resolves nothing. Answer it as "no session for
  this request" (`TokenRefreshCoordinator`'s `NO_SESSION`, the stage's `RefreshResult.NoSession`)
  and send *no* clearing cookie: the browser may already hold the re-issued one.

=== Why every operation is one monitor-guarded method

Every public method of `InMemorySessionStore` runs under the instance monitor, and no operation is
split across two calls. The updating writes are the reason: "is the session still there" and "write
it" must be one step under the lock `destroyById`, `destroyBySid` and `destroyBySub` take, or a
logout between the two would be undone. Keep it that way when you add an operation: a
check-then-act across two store calls reopens that window. Three consequences:

* `recordAccess` writes the last-access instant alone, never the record, so it cannot overwrite
  token material a concurrent refresh has just stored.
* The `SessionEndListener` is called only after the monitor has been left. A listener must not call
  back into the store and must not throw.
* The store's monitor is never taken on an event loop. Callers run on a virtual thread.

=== The two deadlines and where the sweep is scheduled

A session is expired at the earlier of its absolute lifetime and its last access plus the idle
timeout. `resolve` evicts an expired session as it is looked up and extends nothing. The only
caller of `SessionBinding.recordAccess` is `SessionAuthenticationStage.relay`, for a request it
lets through; a reserved endpoint must not call it.

The store starts no thread and no timer. `BffRuntimeProducer.registerSessionSweep` registers a
Vert.x periodic timer at 60 000 ms in server mode, whose handler runs `sweepExpired` off the event
loop, and `cancelSessionSweep` cancels it at shutdown. A capacity-consuming `create` that finds the
store at `max_sessions` sweeps once more before it refuses. The resolved idle timeout is handed to
the store, not to the binding, because `resolve` and `sweepExpired` are store operations and the
sweep runs without the binding.

=== What ends with a session

Every path on which the store *ends* a session -- the three destroy methods, the lazy eviction in
`resolve`, the sweep and the per-subject eviction -- reports the session identity to the
`SessionEndListener`. `SessionRelayRegistry` is that listener: it closes the WebSocket relays
tracked under the identity. A write that replaces the record or re-issues the handle goes through
a removal that reports nothing, so a refresh or a widening closes no relay. If you add a path that
removes a session, decide which of the two it is.

== The engine seams the producer wires

`BffRuntimeProducer` is the one place the client credential, the sender constraint and the
pushed-request client are assembled
(link:../adr/0058-The_BFF_pushes_every_authorization_request_and_binds_its_tokens_with_DPoP_and_authenticates_with_private_key_jwt_unless_a_client_secret_is_configured.adoc[ADR-0058]).
Each exists once per runtime. Know these seams before you touch the login, the refresh or a reserved
handler.

=== The signing key type and its two modes

`ClientSigningKey.resolve(keyFile, purpose)` yields one key per `Purpose` --
`CLIENT_AUTHENTICATION` or `SENDER_CONSTRAINT`.

* *Provided.* A non-null `keyFile` is read once, bounded to 16 KiB. The file must hold exactly one
  unencrypted PKCS#8 `PRIVATE KEY` block and one `PUBLIC KEY` block. The key type is established by
  which JDK key factory accepts the blocks; no ASN.1 is parsed in the gateway. One sign-and-verify
  round proves the halves match.
* *Generated.* A `null` `keyFile` generates an EC P-256 key and logs `ApiSheriff-21`.

The type derives the algorithm from the key (`PS256` for RSA from 2048 bits, `ES256` for EC P-256)
and the key id from the public key (RFC 7638 thumbprint). It has no accessor for the private key:
the material leaves only through `clientAuthentication(...)` and `senderConstraint()`, which hand it
to the engine. Every refusal of a key file is an `IllegalStateException` whose message names the
configuration field and the defect, never the path and never key material; the producer translates it into
`CONFIG_INVALID`. Keep that property when you add a refusal: do not chain a JDK cause whose message
carries the path.

=== Key-based or client-secret authentication

The mode is read through one predicate, `OidcConfig.usesClientSecret()`. `ConfigValidator` and the
producer both call it, so validation and runtime cannot resolve the mode differently.

* *No secret* -- `selectClientCredential` resolves the client-authentication key and returns its
  `PrivateKeyJwtAuth` together with a publishing `ClientJwksEndpoint`.
* *A secret* -- it returns `ClientSecretBasicAuth` together with `ClientJwksEndpoint.withheld()`,
  resolves no client-authentication key, and logs `ApiSheriff-133`.

The authentication and the endpoint are returned as one value on purpose: the key the gateway signs
with and the key it publishes come from one decision. Do not add a second read of the mode.

=== The JWKS endpoint and its withheld form

`ClientJwksEndpoint` has two forms. The publishing form answers `GET` with one JWK and every other
method with `405`. The withheld form answers `404` to every method. The path is reserved in both
forms -- `ReservedPathRegistry` does not read the mode -- so that a proxied upstream can never answer
under a key-set URL the identity provider may hold. The constructor refuses a JWK that carries a
private member.

`CLIENT_JWKS` is one of the two kinds matched on every host, and it is registered last, after the
step-up path, so that boot validation sees a `jwks_path` another key also names as a collision. If you add a reserved kind the identity
provider dials server-to-server, add it to that set and say why in `match(...)`.

=== The PAR adapter

`PushedAuthorizationRequests` adapts the engine's `ParClient`. It does not build a request: it takes
the authorization URL the engine's builder rendered, splits it into its parameters, pushes them, and
returns the authorization endpoint with `client_id` and `request_uri`. The engine's `FlowContext` is
kept as it is. Every failure becomes a `GatewayException` with `UPSTREAM_ERROR` (`502`), recorded as
`ApiSheriff-132` under a per-reason latch, because the login path is reachable without a credential.
Every seam that builds an authorization request goes through it -- the login (`LoginFlow`), the
session widening (`SessionWidening`, silent attempt and interactive re-drive) and the RFC 9470
step-up re-drive; there is no other way to obtain a redirect to the identity provider. A new seam
that renders an authorization URL must be wrapped the same way in `BffRuntimeProducer`, and must
call its seam before it stores a pending record or sets a cookie, so that a refused push leaves
nothing half-started.

=== The shared sender constraint

One `SenderConstraint` is built from the sender-constraint key and handed to the base
`AuthorizationCodeFlow` and to `ScopedEngineFlows`, which passes it to every per-scope login flow,
every per-call widening flow and every refresh flow, near-expiry and scope-driven. A code exchange or a refresh sent without it would carry no proof, and
`BoundTokenEndpointClient` would refuse its response.

=== The bound token-endpoint client

`BoundTokenEndpointClient` extends the engine's `TokenEndpointClient` and overrides the one method
every token response passes. It accepts a response only when `token_type` is `DPoP` and the access
token's `cnf.jkt` equals the proof key's thumbprint.

*Why the refusal is the engine's `RedeemedResponseException`.* The check runs after the identity
provider answered with success, so the grant is already redeemed. The two callers read the exception
type, not the message:

* `CallbackEndpoint` answers any `TokenSheriffException` with `400` and no session -- and, on a
  widening callback, with nothing merged into the live session.
* `RefreshFlow.classify` reads `RedeemedResponseException` as a redeemed grant, and
  `TokenRefreshCoordinator` ends the session. A plain `TransportException` would be read as a grant
  the provider never processed, and the session would be kept on a refresh token that is already
  spent.

For the same reason nothing that goes wrong while reading the token may escape unclassified: every
failure of the read is the `unreadable-access-token` refusal.

=== The step-up coordinator

`StepUpCoordinator` is assembled with the same request builder and the same PAR adapter as the login
leg, so its re-drive is a pushed request. *No edge code calls it.* The path is proven at unit level
and is not reachable in a running gateway
(link:../quality-report/code-correctness.adoc[code-correctness report, BFF-1]).

== Build and test

The canonical build commands are the ones in the repository `CLAUDE.md` (invoked through the build
executor, never a raw `mvn`). For BFF work:

* *Unit and module tests* -- run the `api-sheriff` module tests; the `bff.*` suites cover each
  handler and codec directly, without a container, following the project AAA + CUI-generator
  conventions.
* *Quality gate + full verify* -- both must pass with zero findings before a commit (the
  link:../development/README.adoc[contributor guide] and `CLAUDE.md` state the pre-commit process).

Because the runtime is assembled by `BffRuntimeProducer` only when a global `oidc` block with
`session.mode=server` and a `redirect_uri` is configured, a bearer-only test fixture gets the
*inert* runtime and never touches the engine -- add a server-mode `oidc` fixture when a test needs
the active path.

Two test-support types matter for this code:

* `testsupport.StubIdentityProvider` scripts an identity provider for the producer tests -- discovery,
  the pushed-authorization-request endpoint and the token endpoint -- so a test can read the request
  the gateway actually sent.
* `testsupport.SheriffDebugCapture` is required by every test that asserts *nothing is disclosed* in
  the log. The shipped configuration pins the `de.cuioss.sheriff` loggers to `INFO` for every test
  class, so without the extension a `DEBUG` record is never captured and the assertion passes on
  nothing. Register it and call its control before the absence assertions.

== Entry points for integration and benchmarks

* *Integration tests* live in the `integration-tests` module and run against the native image on the
  Docker compose stack (Keycloak + upstream), under the integration-tests Maven profile. The BFF ITs
  exercise the full login -> mediated call -> logout round-trip through a real IdP; a
  `require: session` route is declared in the sheriff-config the IT container consumes.
  `BffFapiControlsIT` (key mode), `BffClientSecretModeIT` (client-secret mode) and
  `BffGeneratedKeysIT` (no key configured, restarted under a live session) prove the controls above
  against Keycloak. The shared login helper `BffKeycloakLoginFlow` follows one redirect more than a
  front-channel login needed: Keycloak 26.5.7 answers an authorization request that names a pushed
  `request_uri` with a `302` to its own `login-actions/authenticate`, and only that page is the
  login form.

* *Benchmark* -- `benchmarks/src/main/resources/k6-scripts/session_mediated.js` measures the
  steady-state mediation hot path (a pre-established session cookie replayed against a
  `require: session` route: cookie -> store lookup -> bearer injection -> upstream), the
  session-mediation peer of the `bearer` and plain-proxy baselines. `K6BenchmarkConverter` parses
  its result alongside those baselines so mediation overhead is comparable, and leads the report
  overview with the mediation figure when present. The login handshake is deliberately *not*
  benchmarked -- it is IdP-bound, not a gateway hot path.

== How to extend

* *A new reserved endpoint* -- add its kind to `ReservedPathRegistry.ReservedEndpoint`, register its
  path in `ReservedPathRegistry.from(...)`, write a handler in `bff.reserved` that takes raw request
  pieces and returns a rendered response,
  wire it in `BffRuntimeProducer`, and route its kind in `BffRuntime.dispatch(...)`. Document the new
  key in link:../configuration.adoc#_oidc[Configuration -- `oidc`] and grow the reserved-path list.
  A handler that sets a cookie needs nothing further for caching: `BffRuntime.dispatch` sends every
  reserved answer that carries a `Set-Cookie` with `Cache-Control: no-store`.
* *A new session-runtime capability* -- write it against `SessionBinding`, so both session modes get
  it; drive any OAuth interaction through an engine seam per the boundary rule above.
* *A new gateway cookie* -- add its name to the set `BffRuntimeProducer.gatewayCookieNames` computes,
  so an upstream `Set-Cookie` of that name is not relayed.
