= Cookie-Deliverability Blindness -- What the Integration Lane Cannot Observe
:toc:
:toclevels: 3
:sectnums:

Why nine cookie integration tests reported success against a session no real browser client could
hold, which of the nine would have reported success anyway, what else the same gap hides, and where
the integration/browser boundary belongs.

This note is the third sibling of an existing pair, and it is written to join them rather than to
start a second index. The companion note
link:declared-limit-assertion-coverage.adoc[Declared-Limit Assertion Coverage] answers *which
declared gateway limit has a boundary assertion* -- it indexes the descriptor surface and the test
that pins each limit. The companion note
link:test-corpus-integrity.adoc[Test-Corpus Integrity -- Assertions That Assert Nothing] answers
*whether a test's assertions are strong enough to support the behaviour its name claims* -- it
classifies assertion strength inside tests that do exercise the right thing. This note answers the
question neither of them asks: *which properties the integration lane is structurally incapable of
observing, however strong its assertions and however complete its limit index*. A limit can be
indexed and a test can assert hard, and both can still be green about something the lane cannot see.

All three follow the same discipline: enumerate the whole surface first, credit what already exists
by name, and record the remainder as a *countable* standing backlog.

== The Question

The interesting question is not why a test failed. It is why nine tests reported success on a
session a real browser client could not hold.

In cookie mode the session *is* the cookie. Storing the refresh token alongside the access and ID
tokens grew the sealed value to 5123 bytes
(`integration-tests/src/main/docker/sheriff-config-cookie/gateway.yaml:159-164`), and browsers are
only required to accept 4096 bytes per cookie
(`api-sheriff/src/main/java/de/cuioss/sheriff/gateway/bff/cookie/SealedSessionCookieCodec.java:118-122`).
A browser therefore drops the `Set-Cookie` silently: no error, no session, an anonymous SPA. The
same change raised the instance budget to 8192
(`integration-tests/src/main/docker/sheriff-config-cookie/gateway.yaml:171`), so the gateway's own
seal-time guard -- `if (encoded.length() > maxCookieValueBytes)` at
`api-sheriff/src/main/java/de/cuioss/sheriff/gateway/bff/cookie/SealedSessionCookieCodec.java:211`
-- no longer fired either.

Every one of the nine tests should have gone red the moment the payload crossed 4096. None did.

[NOTE]
====
*The nine* are `BffCookieSessionIT` (six tests) and `BffCookieStatelessnessIT` (three), both under
`integration-tests/src/test/java/de/cuioss/sheriff/gateway/integration/`. Both drive the dedicated
cookie-mode instance `api-sheriff-cookie` on port 10445
(`BffCookieSessionIT.java:83`, `BffCookieStatelessnessIT.java:68`).
====

== Why Each of the Nine Passed

=== The counterfactual this section measures against

"Would this test have gone red?" needs a precise counterfactual, so this note uses one throughout:

* the browser receives the callback's `Set-Cookie`, applies the per-cookie budget, and *refuses to
  store* the session cookie;
* it therefore sends no session cookie on any subsequent request;
* the short binding cookie is unaffected, so the login round trip itself still completes.

That last clause matters. The login chain in
`integration-tests/src/test/java/de/cuioss/sheriff/gateway/integration/BffKeycloakLoginFlow.java:236-283`
asserts only status codes -- `302`, `200`, `302`, `302` -- and never uses the session it just
established. A client that drops the session cookie still walks the whole chain green.

=== The mechanism, confirmed

The working hypothesis was that RestAssured enforces no per-cookie size limit. That is correct, and
for *deliverability* it is the whole mechanism -- but it is one leg of a two-leg blindness, and the
second leg is the one that turns a single defect into a class.

*Leg one -- no size policy anywhere on the path.* The helper takes the callback's cookies into a
plain `HashMap` (`BffKeycloakLoginFlow.java:233`, `:281`) and replays them with `.cookies(cookies)`
(`:308`). No length is read at any of those three points. The library applies no per-cookie limit and
the helper adds none, so the absence is doubly sourced rather than inherited.

*Leg two -- the jar is keyed by name and discards every attribute.* `Session.gatewayCookies()` is a
`Map<String, String>` (`BffKeycloakLoginFlow.java:156`), so `SameSite`, `Secure`, `Path`, `Domain`
and the `__Host-` prefix rules survive only as a *name and a value*. The helper's own class Javadoc
states this plainly: it "replays cookies from a `Map` it manages itself, so it applies no cookie
policy: `SameSite`, `Secure` and `__Host-` are attributes it records but never enforces"
(`BffKeycloakLoginFlow.java:40-48`). The same limitation is recorded independently in
link:../../demo-client/doc/playwright-suite.adoc[the Playwright suite note] at `:78-81`.

Leg one hides the size. Leg two hides everything else.

=== What did NOT mask it

Three specific maskers were checked and none is present. Recording the negatives is the point: a
single confirmed explanation is worth more than a plausible one.

A fixture that re-authenticates between steps:: Absent. Each test logs in exactly once, in its
Arrange (`BffCookieSessionIT.java:99`, `:119`, `:151`, `:178`, `:200`, `:218`;
`BffCookieStatelessnessIT.java:86`, `:111`, `:130`). The one mid-test re-login is at
`BffCookieSessionIT.java:235`, and it is the property that test exists to prove, not a fixture
smoothing over a failure.

A helper that re-seals rather than replaying:: Absent. `tamper`
(`BffCookieSessionIT.java:286-291`) and `restampKeyId` (`:266-271`) mutate decoded bytes and
re-encode them; neither constructs a cipher and neither re-seals. Both exist to produce a value the
gateway must *reject*, so neither sits on a green path. The green path replays the callback's value
verbatim.

An assertion that reads the response body rather than the session state:: Present, but not masking.
`sealedSessionMediatesAndStaysUsable` asserts against the go-httpbin echo body
(`BffCookieSessionIT.java:163-170`) -- but it only reaches that body through a request the session
had to authenticate, since the same call asserts `statusCode(200)` at `:161`. The body read is
downstream of a genuine session check, not a substitute for one.

=== Per-test verdict

Under the counterfactual above, *seven of the nine go red and two stay green*. The two that stay
green are structurally incapable of observing deliverability, and they would have been green against
any client at all.

[IMPORTANT]
.The two green rows are green for different reasons, and both are worth naming
====
`sealedSessionCookieIsHardened` asserts on the *emitted header* and nothing else. That is a
legitimate scope -- the gateway's compliance with the `__Host-` contract is exactly what the gateway
can be held to -- but it means the test is indifferent to whether any client accepts the result.

`rpInitiatedLogoutClearsTheSealedCookie` is the sharper case. `LogoutEndpoint` answers a logout
*without* a live session with a `302` to `final_redirect` carrying the same
`clearingSetCookieHeader()` the authenticated branch emits
(`api-sheriff/src/main/java/de/cuioss/sheriff/gateway/bff/reserved/LogoutEndpoint.java:96-100`
versus `:119-121`). That header is a fixed string --
`+__Host-sheriff-session=; Max-Age=0; Path=/; Secure; HttpOnly; SameSite=Lax+` at
`SealedSessionCookieCodec.java:296-298` -- so every one of the test's three assertions (a `Location`,
`Max-Age=0`, an empty value) holds identically on both branches. The test cannot distinguish
"logged out" from "was never logged in".
====

*Of the four rows that go red at the fixture*, the redness is real but arrives at an
`assertNotNull` in an Arrange step rather than at the assertion the test's name is about. That is
worth recording because it changes what a failure report would have said: the suite would have
reported "the login must establish a sealed session cookie", not "the cookie is too large for a
browser". The diagnosis would still have needed a human.

== When the Suite Stopped Being Honest

*The tests never changed. The payload grew.* That boundary is the whole answer to whether this is a
test defect or a missing invariant.

Before the refresh token was stored, `CallbackEndpoint` seeded a session carrying the access and ID
tokens only, and the sealed value sat under the 4096 default. The nine tests were measuring a round
trip that genuinely worked -- for RestAssured *and* for a browser. They were correct, not lucky.

Storing the refresh token is what moved the payload. `CallbackEndpoint` now seeds
`.refreshToken(result.refreshToken())` into the session record
(`api-sheriff/src/main/java/de/cuioss/sheriff/gateway/bff/reserved/CallbackEndpoint.java:239`, with
the mechanism documented in the comment at `:231-238`), and in cookie mode the session is the cookie
-- so access + ID + refresh seal to 5123 bytes on this instance
(`integration-tests/src/main/docker/sheriff-config-cookie/gateway.yaml:159-164`). The same change
raised `max_cookie_size` to 8192 (`:171`), which is what kept the gateway's own guard quiet.

So the suite became blind at one identifiable instant, without a line of test code being touched.

[CAUTION]
====
*The blindness predates that change and must not be recorded as its regression.* The cookie sat
under 4096 only because the refresh token was not being stored -- the very bug that was fixed is
what kept the suite accidentally honest. Removing the accident exposed a gap that was always there.

The conclusion follows directly: this is a *missing invariant*, not a test defect. No existing
assertion is wrong. What was never asserted is that the emitted value fits a budget the gateway does
not control.
====

The absence is verified rather than assumed: neither cookie suite asserts the sealed value's length
anywhere. The only length-shaped expressions in either class are byte-array indexing inside the
mutation helpers -- `raw[raw.length - 1]` at `BffCookieSessionIT.java:289` and
`BffCookieStatelessnessIT.java:174`.

== What Else the Same Gap Hides

Deliverability is one browser-enforced property. Leg two of the mechanism -- the attribute-discarding
jar -- hides a whole class, so the useful output is an enumerated surface with a verdict per member,
not a single fix.

=== The enumerated property surface

The surface is *six properties*: the per-cookie budget this note opens on, plus the five further
cookie properties the same jar hides. It is bounded by a simple rule -- a property belongs here when
*the client*, not the gateway, is the enforcing party. All six satisfy that rule, which is why the
budget sits in the table alongside the other five rather than outside it.

[cols="2,3,1,2",options="header"]
|===
| Property | Who enforces it | IT-lane verdict | Where the assertion is, if any

| Per-cookie size budget (~4096 bytes)
| The browser, by silently refusing to store an over-budget value.
| *Not covered*
| Nowhere in the IT lane. The gateway's own seal-time guard
  (`SealedSessionCookieCodec.java:211`) fires against the *configured* budget, not the browser's.

| `SameSite`
| The browser, by withholding a `Lax` cookie on a cross-site send.
| *Attribute asserted, policy unobservable*
| `BffCookieSessionIT.java:111-112` asserts `SameSite=Lax` on the emitted header.

| `__Host-` prefix rules
| The browser, by rejecting a `__Host-`-named cookie that violates the required combination.
| *Attribute asserted, policy unobservable*
| `BffCookieSessionIT.java:106-109` asserts the name, `Secure`, `Path=/` and the absence of
  `Domain` as one group.

| `Secure`-over-plain rejection
| The browser, by refusing to send a `Secure` cookie over plain HTTP.
| *Attribute asserted, policy unobservable*
| `BffCookieSessionIT.java:107` asserts the flag. The rejection itself is never exercised: every
  origin in the lane is HTTPS (`BaseIntegrationTest.java:58`; `BffKeycloakLoginFlow.java:76`,
  `:86`, `:97`, `:109`).

| Per-domain cookie count
| The browser, by evicting cookies past its per-domain cap.
| *Not covered*
| Nowhere. The gateway sets three `__Host-` cookies --
  `+__Host-sheriff-binding+` (`bff/pending/BindingCookieCodec.java:57`),
  `+__Host-sheriff-session+` (`bff/session/SessionCookieCodec.java:44`) and
  `+__Host-sheriff-logout+` (`bff/logout/RpInitiatedLogout.java:58`) -- and a `HashMap` has no cap
  to hit.

| Aggregate per-domain cookie size
| The browser, by evicting or refusing once the domain's total is exceeded.
| *Not covered*
| Nowhere. No test sums the bytes the gateway asks one origin to hold.
|===

=== The count

Of the six properties enumerated:

* *Three* carry an attribute assertion in the IT lane -- `SameSite`, the `__Host-` combination, and
  the `Secure` flag. All three live in one test, `sealedSessionCookieIsHardened`
  (`BffCookieSessionIT.java:97-113`).
* *Three* carry no assertion at all -- the per-cookie budget, per-domain count, and aggregate size.
* *Zero* have their browser-side enforcement exercised anywhere in the integration lane.

The last line is the finding. The gap between *asserting* an attribute and *enforcing* the policy
behind it is total here, not partial: three of six are asserted and none of six is enforced. A green
`Bff*IT` run is evidence about what the gateway emitted, never about what a browser does with it.

*Standing backlog: three properties with no assertion, and six with no enforcement observation, in
the integration lane.* One of the three -- the per-cookie budget -- is closed by this plan's
emitted-header assertion. The other two, and the enforcement half of all six, remain open and are
recorded here rather than in a rival index.

=== The one lane that does cover the class

link:../../demo-client/doc/playwright-suite.adoc[The Playwright suite] drives a real Chromium against
both session modes as two projects differing only in `baseURL` (`:43-46`), and it already generalises
this exact class: "any control whose enforcement lives in the browser -- `SameSite`, `Secure`, the
`__Host-` prefix, cookie partitioning, CORS, `Referrer-Policy`, CSP, and the navigation context a
response arrives in -- cannot be proven by a programmatic HTTP client, however faithful" (`:84-88`).

It also states its own limit, and the limit is the reason this plan exists: "This Playwright suite is
the only suite in this repository that covers that class -- and it gates nothing" (`:88-91`). The
workflow triggers on `push: branches: [main]` and `workflow_dispatch` only
(`.github/workflows/demo-client-e2e.yml:11-14`), so a pull request that breaks one of these controls
merges with the suite never having run.

Coverage and enforcement are separate things here, and only the first one exists.

== Why `[session-server]` Was Unaffected

The server-session variant never approaches the budget, because nothing large crosses to the browser.
`ServerSessionBinding` keeps the token material in the store and hands the browser only the opaque
`SessionRecord.sessionId()` in the hardened `__Host-` cookie
(`api-sheriff/src/main/java/de/cuioss/sheriff/gateway/bff/session/ServerSessionBinding.java:30-32`,
with the emission at `:66`). A handle is a handle whatever the claim set does, so the payload growth
that moved the cookie-mode seal past 4096 moved nothing at all in server mode.

This is a property of the variant, not of its tests. The server-mode suites are not better written;
they are testing something a browser was always going to accept.

=== A second permissive substitute in the same lane

The audit question -- whether any other suite substitutes a permissive client for a real one --
has one further answer, and it is the same shape rather than a different one.

*TLS certificate validation is disabled lane-wide.* `BaseIntegrationTest` calls
`RestAssured.useRelaxedHTTPSValidation()` for every suite that extends it
(`integration-tests/src/test/java/de/cuioss/sheriff/gateway/integration/BaseIntegrationTest.java:57`),
and the BFF helper's own request specs relax it independently
(`BffKeycloakLoginFlow.java:308`, `:323`). Certificate-chain validity is a *client*-enforced control,
so the lane cannot observe it -- exactly as it cannot observe `SameSite`.

That is a deliberate and correct choice, not a defect: the stack serves a self-signed `localhost`
bundle, and the browser lane handles it the same way with `--ignore-certificate-errors`
(link:../../demo-client/doc/playwright-suite.adoc[the Playwright suite note], `:299-321`). It is
recorded here because it is the second member of the class, and because the class is the thing worth
knowing. A wider sweep of the integration corpus for pro-forma tests belongs to
link:test-corpus-integrity.adoc[Test-Corpus Integrity], not here.

== Where the Integration/Browser Boundary Belongs

The rule that falls out of the analysis is a clean split by *enforcing party*, and it is worth
stating as a rule because it decides where the next assertion goes.

Belongs in the integration lane -- everything the gateway *decides and emits*::
The presence, name and exact attribute set of each `Set-Cookie`; the *size* of the emitted value;
status codes and redirect targets; the sealed wire format and its version gate; fail-closed rejection
of a tampered or unauthenticatable value; two-instance portability. A programmatic client observes
all of these faithfully, because they are facts about the response rather than about the client.

Genuinely needs a browser -- everything the *client applies*::
Whether a `Lax` cookie is withheld on a cross-site send; whether a `__Host-`-named cookie is accepted
or rejected; whether a `Secure` cookie is refused over plain HTTP; per-domain count and aggregate-size
eviction; and the navigation context a response arrives in. No programmatic client can stand in for
these, however faithful -- which is the generalisation
link:../../demo-client/doc/playwright-suite.adoc[the Playwright suite note] already records at
`:84-88`.

The size assertion sits on the *first* side of that line, and that is the load-bearing consequence.
The emitted `Set-Cookie` value's length is a fact about the gateway's own output, observable by any
client that can read a response header -- so it belongs on the pull request, in the integration lane,
even though the *consequence* of exceeding it is browser-side. Nothing about the browser needs to be
simulated to assert a number the gateway itself produced.

[CAUTION]
.The honest limit
====
Moving the size assertion onto the pull request closes one row of the six-row table. It does not
close the other five, and it does not change the standing structural gap: the only lane that
exercises browser-side enforcement still gates nothing
(link:../../demo-client/doc/playwright-suite.adoc[Playwright suite], `:88-91`;
`.github/workflows/demo-client-e2e.yml:11-14`).

Until that changes, the honest reading of a green pull request is: every property the gateway
*emits* has been checked, and every property the browser *applies* has not. This note exists so that
sentence is available to a reader before the next cookie-shaped control is added, rather than after.
====

An assertion pinned to a *configured* constant would close nothing at all. The configured budget is
the value that was wrong; a test comparing the seal against it would have stayed green at 8192
exactly as the nine did. The assertion has to name the browser's number, not the gateway's.
