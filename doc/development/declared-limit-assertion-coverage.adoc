= Declared-Limit Assertion Coverage
:toc:
:toclevels: 2
:sectnums:

Every limit-shaped value the integration-test descriptor surface declares, and the test that
asserts it -- or the record that none does.

The gateway's security posture is declared in configuration and enforced in code. A declared limit
that no test exercises is a value that can be silently weakened: the descriptor still reads
correctly, the build stays green, and the guard is gone. This note is the index that makes that
class countable.

It is a *human-readable index over machine-enforced guards, not the enforcement itself*. The
wiring guards named below (`BodyLimitActivationWiringTest`, `EgressAllowlistActivationWiringTest`,
`TlsEdgeActivationWiringTest`, and their siblings) are what actually fail on drift. This note tells
a contributor which limits have such a guard, which have only a runtime assertion, and which have
neither.

Two companion notes answer the questions this one does not.
link:test-corpus-integrity.adoc[Test-Corpus Integrity -- Assertions That
Assert Nothing] asks whether an indexed test's assertions are strong enough to support the behaviour
its name claims. link:cookie-deliverability-blindness.adoc[Cookie-Deliverability Blindness -- What
the Integration Lane Cannot Observe] asks whether the lane could observe the property *at all* --
a limit can be indexed here and asserted hard there while the client standing in for a browser
enforces none of the policy the limit exists for, which is exactly how nine cookie tests stayed green
against a session no browser could hold.

The first two questions apply to every limit in this index: it must be listed with a real assertion
behind it, and that assertion must not be vacuous. *The third is scoped, and applying it everywhere
over-reports.* Deliverability blindness is a property of *client-enforced* limits -- the ones the
gateway declares but a browser, not the gateway, has to honour: the per-cookie size guarantee,
`SameSite`, the `__Host-` prefix rules. A *server-enforced* limit -- a request-body cap, a route
allowlist, a TLS floor, an inbound header-block bound -- is rejected by the gateway on the wire, so
the integration client observes the enforcement directly whatever policy it does or does not
implement, and the third note has nothing to say about it. Marking those rows incomplete for
failing a test they are not subject to would inflate the gap this index exists to count. So: a
server-enforced limit is covered when it satisfies the first two questions; a client-enforced one
carries the third as well.

Only the base directory carries `endpoints/`, `portal/` and `topology.properties`; the nine overlay
directories replace `gateway.yaml` and nothing else, which is why the endpoints tree resolves
identically for every gateway instance the compose stack boots. Eight of the nine back a compose
service. The ninth, `sheriff-config-tls-relaxation/gateway.yaml`, backs none: `BffTlsRelaxationIT`
mounts it over the shared directory of a one-off gateway, in the way a compose instance mounts its
overlay, and it is described under the citation notation below.

`sheriff-config-late-idp/gateway.yaml` is one of the two descriptors that are *not* overlays -- the
other, `sheriff-config-jwks-egress-mismatch/gateway.yaml`, is built on the same shape and is
described under the citation notation below. It backs
`JwksLateIdpReadinessIT`, which boots it as a one-off container rather than as a compose service --
that gateway is `DOWN` by design until the test starts its identity provider, and the compose
readiness gate would refuse it. It is a standalone, deliberately minimal document: the test mounts it
beside exactly one shared endpoint file, `sheriff-config/endpoints/assets-secure.yaml`, and no
`topology.properties`, so its route set is that single bearer-gated directory asset route.

`reserved-path-overlap/auth-overlap.yaml` sits beside the surface, in a directory no gateway instance
mounts, and declares `allowed_methods`. `BffReservedPathPrecedenceIT` copies it into a configuration
directory it assembles and asserts that list on the wire: a `GET` on the routed path is refused
`405`. `DescriptorInventoryWiringTest` sweeps the `sheriff-config*` directories only, so this file is
outside its inventory by construction and is not counted in the twenty-nine.

`sheriff-config/portal/portal.html` and `sheriff-config/topology.properties` -- declare none.
That complement is the other half of the same claim, so asserting the eighteen exactly asserts both
halves at once.

`sheriff-config/endpoints/bff-unassigned-scope.yaml` is limit-free for the same reason as
`sheriff-config/endpoints/bff-scoped.yaml`, whose key set it shares: `endpoint`, `id`, `enabled`,
`base_url`, `anchor`, `scopes`, `routes`, `match`, `path_prefix`, `auth`, `require` and
`session_fallback`, none of which matches the sweep. Its two routes back `BffSessionScopeParityIT`'s
refusal rows -- an endpoint scope the realm defines but never assigns to the gateway's client, shown
on a `require: session` route and on the SESSION branch of a `session_fallback` route -- so the
assertion is about a scope the identity provider will not grant, not about a bound on the request.
A `forward` allow/deny list or a body cap there would make the file limit-bearing and owe a Coverage
Matrix row.

`sheriff-config/endpoints/origin-headers.yaml` is limit-free for the same structural reason as
`untrusted.yaml`: none of its seven routes bounds a request. Three back response-path assertions
(header precedence, `Location` rewriting, and `HtmlErrorPageIT`'s relayed-origin-error control
through go-httpbin's `/status`) and four are the two header-discriminated route pairs
`RoutingAndResponseHeadersIT` selects between, so they declare a match prefix, `match.headers`
matchers (`name`, `present`), an `upstream.path`, `rewrite_location` and a `profile`
-- none of which matches the sweep -- and deliberately no `forward` list, since the query parameters
that drive the origin must cross unfiltered.

`sheriff-config/endpoints/untrusted.yaml` is limit-free by construction rather than by accident: it is the egress hostname-verification pair's chain-trust
control (ADR-0040), and its single route declares only a match prefix, because the assertion it
backs is about whether the TLS dial completes at all. A `forward` allow/deny list or a body cap
there would be inert configuration that nonetheless made the file limit-bearing and owed a Coverage
Matrix row.

`sheriff-config/endpoints/upstream-fault.yaml` is limit-free because the limits it exists to reach
are not configuration at all. Its single route backs `HtmlErrorPageIT`'s upstream-timeout and
open-circuit legs, and the timeout and the circuit breaker those legs trip are fixed in the gateway
-- a 30-second timeout, and a breaker per upstream host and port with a 20-request window, a
50 percent failure ratio and a 5-second open delay -- so no key of a route can declare them. The
fault is injected from outside instead, by a Toxiproxy proxy the test creates in front of the echo
backend. The route declares a match prefix and an `upstream.path` and nothing else, and its alias in
`sheriff-config/topology.properties` is named `FAULT_UPSTREAM`, a name that matches no alternative
of the sweep, so neither file crosses the partition. Those fixed values are not Layer 2 rows either:
Layer 2 records the caps a declared profile *resolves* to, and these are resolved from nothing a
descriptor says.

*Both claims above are machine-checked against this note itself*, not merely asserted here in
prose. `DescriptorInventoryWiringTest` (in
`integration-tests/src/test/java/.../gateway/integration/`) reads the three marked blocks above at
runtime -- the inventory table, the sweep pattern and the eighteen limit-bearing paths -- and uses them
as its expected values. It hardcodes none of them, so editing the test's expectations without
editing this note is not possible: the note *is* the expectation. It then asserts the committed
inventory equals the parsed inventory as an *exact set* -- so an added descriptor fails as loudly
as a removed one, unlike the *at-least* floor the sibling wiring guards use -- and re-runs the
parsed sweep over that inventory, asserting the set of limit-declaring files equals the parsed
eighteen. If this note cannot be located, or a marked block is missing or empty, the guard fails loudly
rather than deriving an empty expectation and passing.

=== Citation notation

Paths below are relative to `integration-tests/src/main/docker/`. Because a key declared in all
four *independently authored* `gateway.yaml` documents sits at a different line in each, such rows
cite every line explicitly as `×4 -- base:N, cookie:N, mtls:N, ws:N`, where `ws` is
`sheriff-config-ws-admission`. A row citing a bare `sheriff-config/gateway.yaml:N` is declared in
the *base document only* and is inherited by the overlays as the omitted-key default. The
`allowed_methods` row does not fit that reading: every `gateway.yaml` in the surface declares the
key -- the nine overlays at the base's own values -- and the row cites the base document's five
declarations rather than each document's. The documents described below that copy the base, or
stand alone, declare further base-cited keys; each paragraph says which.

`sheriff-config-passthrough-empty/gateway.yaml` is deliberately *outside* that `×N` notation, and
the `×4` rows are **not** re-cited as `×5`. It is not an independently authored descriptor: it is a
verbatim copy of the base document with the `tls.passthrough_sni` block -- and only that block --
removed, so every key the base declares it also declares, at the base's own relative order.

The two `sheriff-config-egress-verify-*/gateway.yaml` overlays are outside it too, and the `×4` rows
are not re-cited as `×6` -- but *not* on the passthrough-empty reasoning, because neither is a copy
of the base document. Both are built on the reduced document the mTLS and ws-admission overlays
share: key for key, each is the ws-admission document without its `edge_hardening` block and with
the two upstream keys added to its `egress_tls` block. The ws-admission document declares that block
itself, as its last one and with `oidc_tls_profile` alone; the pair declares it in the position of
the removed `edge_hardening` block. Measured against the base, each therefore *omits*:

* the whole `security_defaults` block (`profile`, `max_authorization_header_value_length`,
  `allow_get_with_content_length_body`), so both resolve the shipped defaults;
* `tls.min_version` and `tls.cipher_suites` -- their `tls` block declares `alpn` only;
* `tls.passthrough_sni`;
* the `asset_defaults` block;
* the global `security_headers` block and the `api` anchor's `security_headers` block, which the
  base gained for `RoutingAndResponseHeadersIT` (the passthrough-empty and refresh overlays carry
  both);
* `oidc.step_up.path`, which the base gained for `BffSessionScopeParityIT` (only the
  passthrough-empty overlay mirrors it);
* the `portal` block the base gained for `PortalIT` / `HtmlErrorPageIT` (again mirrored by the
  passthrough-empty overlay only).

Some values differ as well, none of them the bound of a limit: `metadata.config_version` is each
overlay's own label, `oidc.logout.final_redirect` is `/` where the base names
`/assets/demo/landing.html`, and `oidc.redirect_uri`, `oidc.logout.post_logout_redirect_uri` and
`oidc.session.csrf.trusted_origins` name each instance's own published origin (10450 and 10451)
instead of 10443.

Row by row, that leaves the following. The keys of all seven `×4` rows are declared by both
overlays, at the values the four cited documents declare -- `csrf.trusted_origins` naming the
instance's own origin, as it does in each of those four -- so re-citing them would add two line
numbers to each of the seven rows and index no limit that is not indexed already. Of the ten rows
that cite the base document alone, exactly one has its key in both overlays: `allowed_methods`,
declared at the same five places with the same values. The other nine -- `security_defaults.profile`,
`allow_get_with_content_length_body`, `tls.passthrough_sni`, `asset_defaults.content_types`,
`security_headers.hsts.max_age`, `security_headers.cors`, `portal.cache_seconds`, G1 and G11 -- do
*not* derive onto the egress pair, because the pair does not declare their keys.

Their `egress_tls` block adds *no* limit-shaped key: none of its three keys --
`upstream_verify_hostname`, `upstream_tls_profile` and `oidc_tls_profile` -- matches any alternative
in the sweep pattern above. The same holds for the `egress_tls` block of every other descriptor that
carries an `oidc` block: each declares `oidc_tls_profile` alone, except
`sheriff-config-tls-relaxation/gateway.yaml`, which declares `oidc_verify_hostname` and
`jwks_verify_hostname` instead -- two keys the sweep does not match either. Both files are
limit-bearing purely on keys a row already cites -- `allowed_methods`,
`anchors.upload.security_filter.max_body_bytes`, the `benchmark-keycloak` issuer's
`jwks.allowed_egress_hosts`, `oidc.session.ttl_seconds`, `oidc.session.refresh.leeway_seconds` and
`oidc.user_info.allowed_claims` -- which is why they need no Coverage Matrix row of their own, and
why the omissions above move neither file across the limit-bearing partition. The pair is a
single-variable matched control: its two members differ in the value of `upstream_verify_hostname`,
a key the sweep does not match at all, and otherwise only in the `config_version` label and in the
published port inside the three origin-bearing `oidc` values.

`sheriff-config-refresh/gateway.yaml` is outside the `×N` notation on the passthrough-empty
reasoning -- it *is* a copy of the base document -- and the `×4` rows are **not** re-cited to include
it either. It is the base document with
`tls.passthrough_sni` removed and two per-instance values repointed -- `oidc.client_id` to
`refresh-client` and the gateway origin from 10443 to 10452 -- and with the one difference in client
authentication the stack keeps on purpose: it declares `oidc.client_secret` where the base declares
`oidc.client_authentication.key_file`, because this instance is the stack's proof of client-secret
authentication. Every *limit-shaped* key the base declares it also declares, at the base's own
relative order, except the base's `portal` block, which it does not carry; the `portal.cache_seconds`
row therefore does not derive onto it. It does not declare `oidc.step_up.path` either: like the
egress pair above it does not mirror that base key, which matches no alternative in the sweep
pattern and so affects no row. Neither repointed value is limit-shaped: `client_id`
matches no alternative in the sweep pattern, and the origin appears inside `redirect_uri`,
`post_logout_redirect_uri` and `csrf.trusted_origins`, whose *keys* are already cited against the
base. The client-authentication difference is not limit-shaped either: `client_secret`,
`client_authentication`, `sender_constraint` and `key_file` match no alternative in the sweep
pattern. It is limit-bearing purely on the base keys it inherits, so it needs no Coverage Matrix row
of its own.

What makes this overlay worth naming is that it is the fixture the `refresh.leeway_seconds`
row's boundary assertion needs -- the item it served stood in the standing remainder until this
overlay made it reachable, and the row is `COVERED` because of it. The shared realm mints a 900-second access token, which puts the
near-expiry window 870 seconds into a session and out of a test's reach; this overlay authenticates
as `refresh-client`, whose client-level `access.token.lifespan` is 45, moving that window to
15s--45s. The declared `refresh.leeway_seconds: 30` is unchanged here -- the overlay changes what the
leeway is measured *against*, never the leeway itself.

`sheriff-config-cookie-refresh/gateway.yaml` is outside the `×N` notation for the same reason, and it
is derived from the *cookie* document rather than the base one: it is
`sheriff-config-cookie/gateway.yaml` with three *behavioural* values repointed -- `oidc.client_id` to
`cookie-refresh-client`, `session.refresh.enabled` from `false` to `true`, and the gateway origin from 10445
to 10455 -- plus the `metadata.config_version` document label, which the overlay itself records as a
label rather than a fourth behavioural difference. No key is added, and exactly one is not carried
over: `oidc.login.default_return_url`, which the cookie document sets and this overlay leaves unset.
That key matches no alternative in the sweep pattern, so no row is affected. Apart from it the
overlay declares exactly the key set the cookie document declares, and the `×4` rows are **not**
re-cited to include it. None of the three repointed values is
limit-shaped: `client_id` and `enabled` match no alternative in the sweep pattern, and the origin
appears inside `redirect_uri`, `post_logout_redirect_uri` and `csrf.trusted_origins`, whose *keys*
are already cited. It is limit-bearing purely on the keys it shares with the cookie document, so it
needs no Coverage Matrix row of its own.

What makes this overlay worth naming is the one thing it deliberately does *not* declare:
`session.max_cookie_size`. Omitting it is what puts the instance on the lowered browser-safe default,
so the sealed-cookie size budget is *measured* against a session that also refreshes rather than
assumed. An override here would silently move that measurement's ceiling and make the row it feeds
report on a budget no browser enforces -- which is the deliverability blindness
link:cookie-deliverability-blindness.adoc[the companion note] describes, reintroduced through a
descriptor rather than through a client.

`sheriff-config-late-idp/gateway.yaml` is outside the `×N` notation too, but for a different
reason: it is independently authored, yet every limit-shaped key it declares is a key the matrix
already indexes -- the anchor method list and the header-value carve-out at the base document's
value, the global method list and the egress host differing by design. It declares exactly three:
`allowed_methods` (global `["GET"]`, and `["GET", "HEAD"]` on its single `assets-secure` anchor --
the base's anchor value), `security_defaults.max_authorization_header_value_length: 8192` (the *G1*
carve-out, at the base's value) and one issuer's `jwks.allowed_egress_hosts` (the *G2* allowlist,
naming exactly the host its own `jwks.url` fetches from). None of the three is a new limit, so none
owes a row of its own: *G2*'s `EgressAllowlistActivationWiringTest` discovers descriptors by glob
and holds this file to the same rule as every other -- a declared list must be exactly the
`jwks.url` host; and `JwksLateIdpReadinessIT` drives
a real Keycloak-minted bearer token -- longer than the strict preset's 1024-character header-value
cap -- through this instance's pre-route floor, and fetches the key set through the allowlisted
private address, so both keys are in effect on the positive leg. Their *boundaries* remain those the
*G1* and *G2* rows record against the base document.

`sheriff-config-jwks-egress-mismatch/gateway.yaml` is the second standalone descriptor, and it sits
outside the `×N` notation for the same reason as the late-idp document. It backs
`JwksEgressMismatchIT`, which boots it as a one-off container on the compose network rather than as
a compose service -- that gateway is `DOWN` by design for its whole life, and the compose readiness
gate would refuse it. It copies the late-idp shape: the single bearer-gated `assets-secure` anchor
beside `sheriff-config/endpoints/assets-secure.yaml`, no `topology.properties`, and exactly three
limit-shaped keys -- `allowed_methods` (global `["GET"]`, and the base's `["GET", "HEAD"]` on the
anchor), `security_defaults.max_authorization_header_value_length: 8192` (the *G1* carve-out, at the
base's value) and one issuer's `jwks.allowed_egress_hosts`. That last key is the one deliberate
inversion: its list names `not-the-jwks-host.invalid`, *not* the host its own `jwks.url` fetches
from, because the refusal that list produces is exactly what the *G2* row's runtime leg asserts. None
of the three is a new limit, so the file owes no row of its own; it is the fixture behind the *G2*
row's `COVERED` status. `EgressAllowlistActivationWiringTest` carves it out of its positive half by
name and asserts the inverse instead -- the list is non-empty and does *not* contain the `jwks.url`
host -- so the fixture cannot silently degrade into a matching or derived list and turn the refusal
it exists for into a pass.

`sheriff-config-tls-relaxation/gateway.yaml` is outside the `×N` notation as well, and the `×4` rows
are **not** re-cited to include it. It backs `BffTlsRelaxationIT`, which mounts it over the shared
directory of a one-off gateway on a dedicated network; no compose service loads it. It is built on
the shape of the refresh overlay -- server mode, `refresh-client` with its client secret, refresh
enabled, the base document's anchor set -- and differs from that overlay in five places:

* its `egress_tls` block declares `oidc_verify_hostname: false` and `jwks_verify_hostname: false`
  and no `oidc_tls_profile`;
* neither http-sourced issuer names a `jwks.tls_profile`;
* the gateway origin inside `redirect_uri`, `post_logout_redirect_uri` and `csrf.trusted_origins` is
  10463;
* its `security_defaults` block does not declare `allow_get_with_content_length_body`, because
  `GetWithBodyActivationWiringTest` admits that opt-in on the enumerated base copies only;
* `metadata.config_version` is its own label.

Every key it declares that a matrix row indexes -- every *limit-shaped* key it declares among them
-- is declared at the value the base document declares: `allowed_methods` at the base's five places, `security_defaults.profile` beside
`max_authorization_header_value_length` (*G1*), `tls.min_version` (*G11*),
`anchors.upload.security_filter.max_body_bytes`, `security_headers.hsts.max_age`, the four
`security_headers.cors` lists, `asset_defaults.content_types`, the `benchmark-keycloak` issuer's
`jwks.allowed_egress_hosts` (*G2*), `oidc.session.ttl_seconds` (*G9*),
`oidc.session.refresh.leeway_seconds` and `oidc.user_info.allowed_claims` (*G10*). None of them is a
new limit and none is asserted at its boundary on this instance, so the file is limit-bearing purely
on keys a row already cites and those rows are not re-cited. Three base-only rows do *not* derive
onto it, because it does not declare their keys: `allow_get_with_content_length_body`,
`tls.passthrough_sni` and `portal.cache_seconds`.

What the file adds is the one row that cites it alone: the two hostname relaxations. Neither key
matches the sweep pattern, so the row is not owed by the limit-bearing partition; it is in the matrix
because the pair is a declared security posture with a runtime boundary, in the way the
`tls.passthrough_sni` and `tls.mtls` rows are.

*Seventeen* Coverage Matrix rows cite the base document: the *seven* `×4` rows (`anchors.upload`,
`csrf.trusted_origins`, `refresh.leeway_seconds`, G2, G8, G9, G10) and the *ten* base-only
`sheriff-config/gateway.yaml:N` rows (`security_defaults.profile`,
`allow_get_with_content_length_body`, `allowed_methods`, `tls.passthrough_sni`,
`asset_defaults.content_types`, `security_headers.hsts.max_age`, `security_headers.cors`,
`portal.cache_seconds`, G1, G11).
Citing the passthrough-empty overlay per row would add a *fifth* line number to each of the seven
`×4` rows and a *second* to nine of the ten base-only rows -- *sixteen* rows, restating one fact
sixteen times where it is better stated once: *derive it from the base citation.*
The three remaining `gateway.yaml` rows in the matrix cite an overlay only

== The Two Declaration Layers

The matrix spans both layers, because only one of them is greppable:

Layer 1 -- *literal descriptor keys*:: A value written into a `gateway.yaml` or an
`endpoints/*.yaml`. It can be found by reading the file.

Layer 2 -- *the strict preset's resolved effective caps*:: `security_defaults.profile: strict`
resolves to a set of caps that apply to *every route that declares no `security_filter.profile`* --
a 1 MiB body cap, 20 query parameters, 1024-character header values, 1024-character parameter
values and 1024-character paths. *None of these numbers appears in any yaml file.* They are the
floor the whole suite is measured against, and a limit that appears nowhere in the descriptors is
exactly the limit most likely to lose its assertion unnoticed.

== Status Vocabulary

`COVERED`:: A test asserts the value *at its boundary* with a matched positive control -- proving
the cap rejects because of the value, not because the route refuses the shape outright.

`WIRED`:: A descriptor-parsing guard asserts the declaration is *present*, but no runtime boundary
is exercised.

`PARTIAL`:: One leg landed. Either the positive control or the negative boundary is missing, or the
declaration's *existence* is proven while its *boundary* is not.

`GAP`:: No test names or exercises it.

== The Gap Count and This Plan's Selection

*Real gap count when this sweep began: 12* -- eight outright `GAP` (G2--G9), three `PARTIAL`
(G1, G10, G11), plus one row this note had itself mis-recorded:
`oidc.session.refresh.leeway_seconds` was carried as `WIRED` while no descriptor-parsing guard
asserted it, so neither half of the `WIRED` definition held. The PR #148 review corrected that row
to `GAP`; it was a real gap at the sweep's start and is counted as one here.

The sweep's hard ceiling is five assertions, so *the cap bound at its ceiling*: **G1--G5 each
received one** (their rows above name the asserting test), ranked below by blast radius -- a limit
whose breach degrades the whole gateway outranks one that degrades a single request.

asserted at its boundary with a matched positive control. **G2 reached `WIRED` only**:

remainder rather than dropped -- until `JwksEgressMismatchIT` closed it (see the standing remainder
below and the G2 matrix row).

        ...
----

It therefore *never reaches `sheriff-config/endpoints/`* -- where `endpoints/httpbin.yaml:87`
already declares a `max_body_bytes: 1024`. That cap sits far below the framework floor, so nothing
is broken today. But a *future* endpoint-level cap declared above the floor would push its instance
into a fail-closed boot abort with the guard still green, because the guard never parsed the file
that declares it.

This is *reported, not fixed*: widening the glob is a change to a guard whose blast radius reaches
every committed descriptor, and it belongs in its own plan with its own verification rather than
riding a coverage sweep. It is recorded here so the hole is a known, countable item rather than a
latent surprise.

The same reasoning is why the bearer-protected `security_filter` route added by this plan declares
`allowed_paths` rather than `max_body_bytes` -- adding a body cap in the endpoints tree would
enlarge exactly the hole this note has chosen to report.

== Report-Only Finding: the inventory guard partitions files, not keys

`DescriptorInventoryWiringTest#limitShapedKeysLiveOnlyInTheRecordedSurfaces` builds a set of *file
paths* -- those for which `declaresLimitShapedKey` returns `true` -- and asserts it equals the
eighteen paths parsed from the `limit-bearing` block. `declaresLimitShapedKey` is a per-file
*boolean* predicate ("does this file declare at least one limit-shaped key"), not a key enumeration,
so the assertion's granularity is the file and never the key.

The consequence: adding a limit-shaped key to one of the *eighteen already limit-bearing* files
leaves the computed set identical to the parsed one. The build stays green and no Coverage Matrix
row is forced. Only a key that makes one of the remaining eleven --
`sheriff-config/endpoints/assets.yaml`, `sheriff-config/endpoints/assets-secure.yaml`,
`sheriff-config/endpoints/bff-scoped.yaml`, `sheriff-config/endpoints/bff-unassigned-scope.yaml`,
`sheriff-config/endpoints/origin-headers.yaml`,
`sheriff-config/endpoints/portal-hidden.yaml`, `sheriff-config/endpoints/secure-scoped.yaml`,
`sheriff-config/endpoints/untrusted.yaml`, `sheriff-config/endpoints/upstream-fault.yaml`,
`sheriff-config/portal/portal.html` or
`sheriff-config/topology.properties` -- limit-bearing crosses the partition and fails the build.
Eighteen of twenty-nine is the *majority* of the surface,
so this is the ordinary case rather than an edge one: for those eighteen files the "add its row here
in the same change" instruction that closes this note rests on contributor convention, not on the
guard. The routing plan that added the base document's `security_headers` block is a worked instance:
`hsts.max_age` and the CORS allow lists are limit-shaped, the base file was already limit-bearing, and
the guard stayed green -- their two Coverage Matrix rows above were added by hand.

This is *reported, not fixed*, for the same reason as the finding above. Closing it means deriving
the Coverage Matrix's own *qualified* keys and comparing them exactly against the descriptors --
again a change to a guard whose blast radius reaches every committed descriptor, and one carrying
real subtlety: YAML anchors resolve a single key literal to several qualified paths, this matrix's
key column is deliberately non-uniform (qualified-with-value, qualified-bare, bare key, two keys in
one row), and the Layer 2 rows document caps that appear in *no* yaml at all and could never be
derived. Key-level enforcement therefore belongs in its own plan with its own verification rather
than riding a coverage sweep. It is recorded here so the hole is a known, countable item rather than
a latent surprise.

== Keeping This Note Honest

This table is prose, and prose drifts the moment a descriptor changes. Three properties limit that:

. *Every Layer 1 row carries a `file:line` citation*, so a reviewer can check a row against the
  descriptor in one step rather than re-deriving the surface. The rule binds only to rows that have
  a descriptor location. The five Layer 2 rows -- one per resolved cap enumerated in "The Two
  Declaration Layers" -- carry the marker "Layer 2 -- resolved, in no yaml" in that slot instead,
  because there is no descriptor line to cite. That marker is a claim rather than an excuse: it
  asserts the value appears in *no* committed descriptor, which is precisely why such a limit is the
  one most likely to lose its assertion unnoticed. A row carrying neither a citation nor that marker
  is the drift this property exists to catch.
. *The enumerated surface is stated explicitly* (twenty-nine files, named) *and machine-checked against
  this note*. `DescriptorInventoryWiringTest` parses the marked blocks in "The Enumerated Surface"
  -- the inventory table, the sweep pattern and the eighteen limit-bearing paths -- and uses them as its
  expected values instead of carrying its own copy. Both of its assertions are *file-level set
  equalities*, and the guarantee is exactly that: a new descriptor directory or a new
  `endpoints/*.yaml` breaks the exact-inventory equality and fails the build until this note is
  updated, and a limit-shaped key fails the build *only when it makes a previously
  non-limit-bearing file limit-bearing* -- when it moves a file across the eighteen/eleven partition.
  Adding one to a file that already declares a limit changes neither set; see the report-only
  finding above. Updating the test alone cannot make the build green: the test has no expectation of
  its own to update.
. *The wiring guards are the machine-enforced half.* `BodyLimitActivationWiringTest` and
  `EgressAllowlistActivationWiringTest` both assert a `COMMITTED_DESCRIPTOR_COUNT` floor, so a
  vacuous or mis-rooted glob fails loudly instead of passing over an empty set. This note indexes
  those guards; it does not replace them.

When you add a limit-shaped key to any of the twenty-nine files, add its row here in the same change --
and give it a status that is honest, including `GAP`.

== Declared Is Not Asserted: Three Rules Behind the Matrix

The matrix answers *which declared limit has an asserting test*. These three rules are the *why*
behind that question -- what a key with no asserting test actually is, what happens the day it
acquires one, and which shape of test settles the question for an opt-in feature. Together they are
the reason this note counts gaps instead of trusting the descriptors.

=== The deletion discriminator

*A configuration key that parses is not a configuration key that acts.* A key that is spelled
correctly, passes schema validation and reads exactly like a security control can still have no
production consumer at all -- in which case it is a *silent security no-op*: the descriptor reads
correctly, the schema accepts it, the build is green, and the control it names applies to nothing.
Every visible signal agrees, and every one of them is about the declaration rather than the
behaviour.

The one-line test is: *if the key were deleted entirely, would any test go red?* If the answer is
no, the control is *not test-proven* -- and that is the whole of what the test settles. It does not
settle whether the control is in effect. Two shapes come back green and are still live: a key with a
production reader but no asserting test -- rows *G7* and *G8* of the matrix above are exactly
that, each naming an enforcer and `none` in the asserting-test column -- and a key whose default or
inherited value carries the same behaviour once the explicit declaration is gone. So the deletion
test is the first of two steps, not the verdict. Confirm production consumption separately, by
tracing the key to the reader that consumes it.

This note carries its own worked instance. The `tls.min_version` protocol floor and the
`tls.cipher_suites` restriction (row *G11*) were declared, valid and inert -- they had *zero*
production readers until `TlsServerCustomizer` became one, so they constrained no listener at all
while the descriptor, the schema and the build all reported health. Deleting either key at that
point would have turned nothing red. The deletion test is what raised the suspicion; the trace to a
production reader -- finding none -- is what settled it.

=== Wiring an inert key is a behavioural flip for every consumer

The day an inert key becomes live, every consumer that reads the surface it governs changes
behaviour at once. An existing test may fail, and the trap is to treat that one failure as the scope
of the change. Where the surface carries no asserting test at all -- rows *G7* and *G8* again
-- the flip lands with nothing going red, and the trap has no trigger to spring.

*The test that fails first is a sample of the dependant set, not the whole of it.* Fixing it closes
the investigation while the un-sampled dependants stay broken, and they surface later and further
from the change that caused them -- by which point the wiring commit no longer looks like a
suspect. Enumerate the dependants before declaring the wiring done, rather than letting the test
suite enumerate them for you one failure at a time.

When the contract needs a new assertion, *extend `SingleSourceTlsContractTest`* -- or its siblings
`CipherSuiteFixtureWiringTest` and `ManagementPlainHttpActivationWiringTest` -- rather than writing
a new contract test beside them. The guards already exist, and a second one splits the contract
across two files that then drift apart.

=== An opt-in runtime feature needs a deployment-activation test

Unit tests prove `config -> behaviour`: given this configuration, the component does this. They do
not prove that *the deployment sets that configuration*. An opt-in feature can be fully unit-tested
and entirely off in every running instance, and no unit test can see the difference.

The shape that closes the other half is the `*ActivationWiringTest` family this note already
indexes, with `TlsEdgeActivationWiringTest` as the reference: it asserts the *deployed descriptor
actually turns the feature on*. That is the assertion a unit test structurally cannot reach, and it
is why a feature landing without one is recorded here as a gap rather than as coverage.

==== Recorded rationale: the egress hostname relaxations owe no activation instance

The rule above has a precondition that is easy to read past: an activation test asserts that a
*shipped deployment turns the feature on*. Where no shipped deployment is meant to, there is nothing
for it to assert, and the absence is a recorded decision rather than a gap. Two keys sit in exactly
that position, and the reasoning is written down here so it is not re-litigated as a missing test:
`egress_tls.jwks_verify_hostname` and its peer on the BFF OIDC back-channel,
`egress_tls.oidc_verify_hostname`.

*Both are secure-by-default relaxations that no shipped deployment activates.* Each defaults to
`true`, an omitted key or an omitted block resolves to `true`, and the shipped posture *is* that
default. No descriptor a deployment boots -- no compose service of the integration stack, and nothing
in the compose sample -- declares either key, so there is no deployed document whose activation a
wiring test could check. An activation test here could only assert that the relaxation is *off*
everywhere, which is the property the default already states and the schema already carries.

*One committed descriptor does declare both, and it is a test fixture rather than a deployment.*
`sheriff-config-tls-relaxation/gateway.yaml` sets both keys to `false` so that `BffTlsRelaxationIT`
can show, on the native image and against a real identity provider, what each relaxation reaches and
what neither does; see its Coverage Matrix row. The rule in "What would reopen it" below applied to
that change in full, and the guard was extended in the same change.

*The two halves that are owed are both present.*

* *The behaviour half* -- `config -> behaviour` -- is a real TLS dial at unit level, through each
  producer's own configuration path rather than a test-built library configuration:
  `TokenValidatorProducerTest` for the JWKS leg and `BffRuntimeProducerTest` for the BFF leg. Each runs
  a matched control (the same server, certificate and trust anchor, differing only in the flag: the
  default refuses, the relaxation completes), an untrusted-chain leg that must still fail with the
  flag off, and a falsification check -- deleting the production passthrough turns the relaxed leg
  red. The BFF leg adds an omitted-block leg and the collision refusal against `oidc_tls_profile` with
  its own matched control.
* *The native binding half* -- that the shared `egress_tls` record and its dedicated deserializer
  survive the native build and bind a declared block -- is already exercised by the integration
  stack's `sheriff-config-egress-verify-{on,off}` instance pair, which binds the same record through
  the same deserializer for `upstream_verify_hostname`, and whose single-variable shape
  `EgressVerifyActivationWiringTest` pins. A further instance differing only in a key no deployment
  sets would add a multi-minute stack start to every integration run and prove nothing that pair and
  the unit dial do not.

`upstream_verify_hostname` is the contrast case, and it is not an inconsistency: that key's matched
pair exists because its scope claim needed a real upstream dial through the native edge, not because
the rule required one per relaxation key.

*What would reopen it.* The rationale holds only while no shipped descriptor declares either key. A
descriptor that starts declaring `jwks_verify_hostname`, `oidc_verify_hostname` or `oidc_tls_profile`
is a deployment activating a posture, and from that change on the rule above applies in full: add the
wiring guard in the same change.

*`oidc_tls_profile` is the member of that list a deployment does activate.* It is a trust profile and
not a relaxation, so the rationale above never covered it. Every integration descriptor that carries
an `oidc` block declares `egress_tls.oidc_tls_profile: benchmark-idp` -- every one but the
TLS-relaxation fixture, described below -- and
`ItProfileConfigBindingWiringTest` is the wiring guard the paragraph above requires. It derives the
descriptor set by directory glob with a floor, asserts that each such descriptor names the profile and
declares no `oidc_verify_hostname` beside it, asserts that every `QUARKUS_PROFILE=it` gateway instance
loads the properties file that binds the profile, and asserts that no gateway passes a
`-Djavax.net.ssl.*` argument on its command line.

*The one exemption, and what it is conditioned on.* `sheriff-config-tls-relaxation/gateway.yaml`
cannot name the profile: the gateway refuses a hostname relaxation together with a named profile at
boot, so a descriptor that relaxes hostname matching has to verify the chain against the JVM default
trust store, and `BffTlsRelaxationIT` supplies that store with `-Djavax.net.ssl.trustStore*` arguments
after the image. By operator decision the guard therefore exempts exactly two files, each by its
literal path: that descriptor from the per-descriptor assertion, and `BffTlsRelaxationIT.java` from
the launch-site assertion. Neither exemption is unconditional. Before it skips the descriptor the
guard asserts that the file exists, declares an `oidc` block, declares `oidc_verify_hostname: false`
and names no `oidc_tls_profile`; before it skips the test source it asserts that the file is in the
derived launch-site set and carries the `-Djavax.net.ssl.` prefix. Deleting the fixture, giving it a
profile, or dropping the trust-store argument therefore turns the guard red instead of leaving an
exemption that covers nothing. The assertion over the compose gateway services has no exemption.

The command-line assertion covers two populations: the
gateway services of the compose file, read from both their `entrypoint` and their `command` in either
compose form, and the one-off launch sites, the files under the module's `src/test/java` and
`scripts/` that name the gateway image -- by its literal or through the harness constant
`OneOffGatewayContainers.IMAGE`, qualified or statically imported -- which takes in the files that
start it with `docker run` and a few that only inspect it. The second population is derived with a
floor and two named members, so it cannot silently shrink; but the assertion over it is a source-text
scan for the contiguous `-Djavax.net.ssl.` prefix, so an argument whose prefix is split across literals
or computed would evade it, and so would a file
that reaches the image only through an alias of that constant declared under another name. The behaviour
half is the integration stack's BFF login suites: the Keycloak they dial serves a self-signed
certificate, so a login completes only when
the back-channel trusts it through the named profile.
