= Boot Validation Rules -- Where a New Rule Goes
:toc:
:toclevels: 2
:sectnums:

The cross-cutting configuration rules run at boot (pipeline step 7) and in the offline
`--validate-config` check. They judge what the bundled JSON Schemas cannot express: a relation
between two keys, a value checked against another file, a posture resolved through the
route -> endpoint -> anchor chain. This page describes how those rules are organised, which class
owns which rule, and what a contributor does to add one.

The code lives in
link:../../api-sheriff/src/main/java/de/cuioss/sheriff/gateway/config/validation/ConfigValidator.java[`ConfigValidator`]
and the package
link:../../api-sheriff/src/main/java/de/cuioss/sheriff/gateway/config/validation/rule/package-info.java[`config.validation.rule`].

== The model

`ConfigValidator` orchestrates. It holds *one* ordered list, `DEFAULT_RULES`, with one
entry per rule, and runs every entry in list order against the bound gateway document, the enabled
endpoints and the resolved topology. That list is the only place that decides the order in which
violations are reported.

Every entry is a
link:../../api-sheriff/src/main/java/de/cuioss/sheriff/gateway/config/validation/rule/ValidationRule.java[`ValidationRule`]:
a function of `(GatewayConfig, List<EndpointConfig>, ResolvedTopology, List<ConfigError>)` that
*appends* one `ConfigError` per violation to the shared list. A rule never throws for a
validation failure and never stops at the first problem.

A rule body lives in the *concern class* that owns the configuration block it judges. A concern
class is a stateless Lombok `@UtilityClass` named `{Concern}Rules` in the `rule` package, exposing
each rule as a `public static validateXxx(...)` method with the narrowest parameter list the rule
needs. `ConfigValidator` adapts each method with one lambda in `DEFAULT_RULES`. A concern class
publishes no rule list of its own: a per-class list would be a second place deciding the order,
and it would have no reader. `ConfigValidator` itself holds no rule body.

The helpers every rule shares live once, in
link:../../api-sheriff/src/main/java/de/cuioss/sheriff/gateway/config/validation/rule/RuleSupport.java[`RuleSupport`]:
the reporting file (`GATEWAY_FILE`, `endpointFile`), the `ENDPOINT_ROUTES_POINTER` and
`ANCHORS_POINTER`, the CWE-117-safe echo of a configured value (`renderForMessage`), the declared
anchor name (`declaredAnchorName`), which protocol a route rides (`effectiveProtocol`), which
`auth.require` a route resolves (`requireOf`), the wildcard-origin token (`WILDCARD_ORIGIN`), the
RFC 9110 media-type token (`MEDIA_TYPE_TOKEN`), anchor-namespace containment (`prefixContains`,
`strictlyContains`) and whether the gateway lacks a configured token issuer
(`lacksConfiguredIssuer`). A helper shared by two or more concern classes lives once in
`RuleSupport`; a helper used by one concern stays private to that class. A rule never resolves a
policy block or a route's anchor itself: it reads them through `PolicyBlock` and
`PolicyBlock.ScopeChain.of` (ADR-0067), so boot validation and the route table cannot disagree.

The `ValidationRule` seam is not widened. Every rule today has the shape above, and a rule that
logs does so as a side effect with its own logger. Change the interface only for a check this
shape genuinely cannot express, and record why.

== The concern map

Every rule in `DEFAULT_RULES` belongs to exactly one concern class below. The map names each rule's
owner; how many rules there are, and the order they run in, is read from `DEFAULT_RULES` itself,
which is the only record of both. "Extracted" means the concern class exists and owns the rule
bodies.

The map is written by hand, so it is bound to the list by a test:
link:../../api-sheriff/src/test/java/de/cuioss/sheriff/gateway/config/validation/BootValidationConcernMapContractTest.java[`BootValidationConcernMapContractTest`]
reads the registrations in `DEFAULT_RULES` and fails the build when a registration has no row
here, when its rule is missing from the row of the concern class it calls, or when a row names a
rule that `DEFAULT_RULES` does not register through that row's class.

== Adding a rule

. *Pick the concern by the configuration block the rule judges*, using the map above. A rule that
  compares a route's `forward` block against its `auth.token_relay` belongs to `ForwardingRules`,
  whichever of the two keys the refusal message names first.
. *Add the method to that concern class*: a `public static validateXxx(...)` method, with Javadoc
  stating the rule and why it exists.
. *Register it as one lambda line in `DEFAULT_RULES`*, at the position that keeps the reported
  order -- normally beside the rules of the same concern. Never concatenate whole class lists: one
  entry per rule, in one list.
. *Document the log message* if the rule logs, in `doc/LogMessages.adoc`, as for any other
  `LogRecord`.

A rule that fits no existing concern gets a new concern class, authored fresh as a stateless
`@UtilityClass` in the `rule` package with `public static validateXxx(...)` methods. Its rules are
registered one lambda each in `DEFAULT_RULES` at the position that keeps the reported order, a row
for the class is added to the concern map above, and a helper it shares with another concern class
goes into `RuleSupport`. The refusal texts and the reporting order of the existing rules are
untouched by it.

== Tests

A rule's tests live beside it, in the test source tree's `config/validation/rule` package, named
`{Concern}RulesTest` -- for example
link:../../api-sheriff/src/test/java/de/cuioss/sheriff/gateway/config/validation/rule/RouteMatchingRulesTest.java[`RouteMatchingRulesTest`]
and
link:../../api-sheriff/src/test/java/de/cuioss/sheriff/gateway/config/validation/rule/PortalRulesTest.java[`PortalRulesTest`].
Where a concern's cases already span several classes, each keeps its aspect in the name, as
`TokenValidationRulesJwksEgressTest` and `TokenValidationRulesJwksRefreshTest` do.

The tests drive the full default validator, `new ConfigValidator()`, rather than calling the
concern-class method directly. That is deliberate: a rule that is written but dropped from
`DEFAULT_RULES` -- or registered with the wrong arguments -- then fails its own tests, while a test
of the bare method would stay green over a rule that never runs.

`ConfigValidatorTest` holds the orchestration cases only: a well-formed configuration passes, the
structural `TRACE` and `CONNECT` rejection, and the single-pass aggregation of violations from
several rules. A rule's own cases never go there.

== Constraints every rule keeps

* *Pre-boot and framework-free.* The offline `--validate-config` check runs this validator before
  the framework starts
  (link:../adr/0061-Offline_configuration_validation_is_a_pre-boot_flag_on_the_gateway_binary_over_the_boots_own_pipeline_seam.adoc[ADR-0061]),
  so the validation packages carry no framework imports
  (link:../adr/0062-Platform_mechanisms_are_preferred_over_hand-rolled_equivalents_and_the_framework-agnostic_core_rule_is_retired.adoc#narrowed-pre-boot-rule[the narrowed pre-boot rule of ADR-0062]).
  `PreBootFrameworkFreeArchTest` enforces it.
* *All violations in a single pass.* A rule appends and returns; it never throws a validation
  failure and never stops at the first one, so the operator sees every violation in one boot attempt
  (link:../adr/0009-asymmetric-alias-resolution-failure.adoc[ADR-0009]).
* *Configured values must be echoed through `RuleSupport.renderForMessage`.* A refusal that names
  a configured scalar has to render it with control characters escaped and the length capped, so
  that a hostile value cannot forge a boot ERROR log line (CWE-117). Write every refusal that way,
  and keep that escaping in exactly one copy.
* *A rule that logs owns its logger.* A rule that emits a WARN declares its own `CuiLogger` in its
  concern class and keeps its `LogRecord` from `ConfigLogMessages`; the identifier and the text do
  not change when the rule moves, only the logger category does. A test asserting the absence of
  that message must then name the concern class, or it passes vacuously.
