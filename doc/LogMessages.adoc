== Overview

This document provides a reference for all structured log messages emitted by the
API Sheriff gateway. Structured messages carry the `ApiSheriff` prefix and a stable
numeric identifier, so they are greppable and assertable.

The build-time benchmark harness in the `benchmarks` module emits its own `K6Benchmark`-prefixed
records; they are catalogued in a separate section at the end of this document, since they are
not gateway runtime messages.

=== Log Message Format

All messages follow the format: `ApiSheriff-[identifier]: [message]`

The log message levels follow these identifier ranges:

* INFO Level: 1-99
* WARN Level: 100-199
* ERROR Level: 200-299

Note: Only log level INFO and above are documented in this file. `DEBUG` / `TRACE`
diagnostics use the logger directly and are not catalogued.

== INFO Level (1-99)

[cols="1,1,2,2", options="header"]
|===
|ID |Component |Message |Description
|ApiSheriff-1 |EDGE |Route table compiled: %s route(s) assembled |Logged once at startup after the route table is assembled; `%s` is the number of routes the request pipeline serves.
|ApiSheriff-2 |CONFIG |Configuration loaded successfully (config_version='%s') |Logged once at startup after the file-based configuration is read, validated and assembled into the route table.
|ApiSheriff-3 |CONFIG |Route '%s' effective posture: anchor='%s', auth.require='%s', auth.session_fallback=%s, filter='%s' |Logged once per route during route-table assembly with its effective posture (anchor, auth requirement, `auth.session_fallback`, filter profile); anchors vanish at runtime, so this line records what each route inherited (ADR-0007). `auth.session_fallback=true` marks a `require: bearer` route that also serves a session branch (ADR-0055).
|ApiSheriff-4 |EDGE |WebSocket relay established for route '%s' |Logged once when a WebSocket upgrade completes (101 Switching Protocols) and the bidirectional relay to the upstream begins.
|ApiSheriff-6 |EDGE |Passthrough relay established for SNI '%s' to upstream '%s' |Logged once per accepted connection whose SNI matched `tls.passthrough_sni`, when the L4 relay to the backend is established; the gateway does not handshake, so the backend certificate reaches the client end-to-end.
|ApiSheriff-7 |EDGE |Accept-time SNI front listener started on port %s (%s passthrough SNI mapping(s)) |Logged once at startup when the front listener binds the public TLS port; emitted only when `tls.passthrough_sni` is non-empty.
|ApiSheriff-10 |BFF |Server-side session established for a require:session route |Logged once when a `mode: server` BFF session is created after a successful IdP login; carries no session id, subject or IdP `sid`.
|ApiSheriff-11 |BFF |Server-side session destroyed (%s) |Logged when a server-side session is destroyed; `%s` is the disposition (`logout` / `backchannel-logout` / `expiry` / `refresh-failure`), never the session id, subject or `sid`.
|ApiSheriff-12 |BFF |Mediated tokens refreshed for a require:session route (single-flight) |Logged when the transparent single-flight token refresh rotates a session's mediated tokens; token material is never logged.
|ApiSheriff-13 |BFF |Back-channel logout accepted — %s session(s) destroyed |Logged when a valid back-channel `logout_token` is accepted; `%s` is the number of sessions destroyed. A count of `0` means the token was valid but its `sid` (or `sub`) matched no held session — a session-binding problem, not a delivery one; refusals are ApiSheriff-112.
|ApiSheriff-14 |BFF |RP-initiated logout completed for a require:session route |Logged when the RP-initiated logout return leg verifies its single-use logout-state cookie and redirects the browser to the configured `final_redirect`.
|ApiSheriff-15 |BFF |Cookie-mode session sealed (%s bytes) |Logged once per `mode: cookie` login when the new session is sealed into its `Set-Cookie`; re-seals after refresh, step-up or widening log at DEBUG only. `%s` is the sealed-value length, never the value, the key or any token material.
|ApiSheriff-16 |BFF |Cookie-mode sealing key generated at startup (%s) — sessions do not survive a restart |Logged once at startup when no `session.key_file` is configured and a cookie-mode sealing key is generated in memory, so sessions do not survive a restart; `%s` is the affected scope. Configure `session.key_file` for sessions that survive restarts.
|ApiSheriff-17 |CONFIG |Effective default trust source — legs holding a raw JDK TrustManager: %s; legs resolving through the Quarkus TLS registry: %s |Logged once at startup, naming the trust material outbound dials verify against for each of two disjoint tiers: legs holding a raw JDK `TrustManager` (set by `javax.net.ssl.trustStore`, including the BFF OIDC back-channel without `egress_tls.oidc_tls_profile`) and legs using the Quarkus `<default>` TLS bucket. Setting only one tier moves only half the outbound surface; never logs a password, alias or anchor bytes.
|ApiSheriff-18 |CONFIG |JWKS key set for issuer '%s' loaded after %s retry attempt(s) |Logged when an issuer's JWKS key set loads after one or more failed gateway retries, closing the episode ApiSheriff-129 opened; the issuer's tokens validate again and it no longer holds readiness DOWN. `%s` are the configured issuer name and the retry count, never the JWKS URL, a host or key material.
|ApiSheriff-19 |PORTAL |Application portal enabled at '%s' with %s active catalog entries, template: %s |Logged once at startup when a `portal` block is declared and its template passed the boot checks; the values are the `portal.path`, the number of active catalog entries (enabled endpoints with an `endpoint.catalog` block) and the template source (`built-in` or the `portal.html` path). See link:user/portal.adoc[Application Portal].
|ApiSheriff-20 |BFF |Live session widened for a require:session route — scopes added: %s |Logged when a widening callback merges the IdP's grant into the live session, keeping its identity and absolute expiry (ADR-0057). `%s` is the sorted, space-separated scopes the grant added (empty when none); no token, session id or subject is logged.
|ApiSheriff-21 |BFF |Signing key for %s generated at startup (%s) — the key is not shared with other instances and is replaced on every restart |Logged once per purpose at startup when no `key_file` is set for a signing key (`client-authentication` or `sender-constraint`) and an EC P-256 key is generated in memory (ADR-0058). The key is per process and replaced on restart, so a multi-replica deployment must provide a key file.
|ApiSheriff-22 |EDGE |Request body on route '%s' did not arrive whole (%s) — upstream request aborted; further occurrences of this disposition on this route stay at DEBUG |Logged when a proxied request's body fails mid-stream (`body-stream-failed`), the client leaves before the answer (`client-left`), or a gRPC call's client holds its request stream open without sending its next complete request message within the fixed 10 s message bound, before the first message or between any two (`client-idle`), and the upstream request is aborted; reported as `INBOUND_BODY_ABORTED` — `400` on an HTTP route, `INVALID_ARGUMENT` in a trailers-only HTTP `200` on a gRPC call — and not counted as a failure by the circuit breaker. Latched per route and disposition: the first end of each disposition on a route is its own INFO, a repeat of the same disposition there stays at DEBUG. The rate is `sheriff_errors_total{event="INBOUND_BODY_ABORTED"}`, split by disposition in `sheriff_inbound_body_aborts_total{route,disposition}`.
|ApiSheriff-23 |EDGE |Request body on route '%s' made no progress for %s seconds — upstream request reset; further occurrences on this route stay at DEBUG |Logged when a proxied request body makes no progress for the fixed idle timeout and the upstream request is reset; reported as `REQUEST_BODY_TIMEOUT` (`408`), never retried, not counted as a failure by the circuit breaker, and never applied to bodyless or `protocol: grpc` requests (a gRPC call is bounded per request message instead, ApiSheriff-22). Latched per route (first INFO, repeats DEBUG); the rate is `sheriff_errors_total{event="REQUEST_BODY_TIMEOUT"}`.
|ApiSheriff-24 |EDGE |Request body on route '%s' did not end within %s seconds — upstream request reset; further occurrences on this route stay at DEBUG |Logged when a proxied request body is still arriving 25 s after the upstream attempt started and the upstream request is reset — on a gRPC call, a request stream still open before the upstream answered 25 s after the attempt handed the body over, or 29 s after the attempt started if that comes first, rendered to the client as `DEADLINE_EXCEEDED`; reported as `REQUEST_BODY_TIMEOUT` and latched per route like ApiSheriff-23. A gRPC call ended at the 29 s cap had less than 25 s after the hand-over. A recurring rate on an HTTP route means its uploads need more than the fixed 25 s and must arrive faster or be split. On a gRPC route it means clients were still sending when the deadline passed, which has two causes: calls that keep their request stream open longer than 25 s, or an upstream connection slow enough that the cap left the clients less than 25 s after the hand-over — with an upstream connection wait of more than 4 s the client gets only what remains before the 29 s cap, at least 1 s. Check the route's upstream connection times before asking its clients to send faster.
|ApiSheriff-25 |EDGE |gRPC call on route '%s' carried no frame in either direction for %s seconds — upstream request reset, call ended with DEADLINE_EXCEEDED; further occurrences on this route stay at DEBUG |Logged when a gRPC call with response headers carries no frame either way for the fixed five-minute idle timeout; the call ends with `grpc-status: 4` (`DEADLINE_EXCEEDED`). Latched per route (first INFO, repeats DEBUG); a service whose calls legitimately stay silent longer must send messages within five minutes.
|===

== Benchmark Harness Messages (`K6Benchmark`)

These records are emitted by the k6 benchmark post-processor in the `benchmarks` module
(`de.cuioss.sheriff.gateway.k6.benchmark.K6BenchmarkLogMessages`), not by the gateway runtime.
They follow the format `K6Benchmark-[identifier]: [message]` and the same identifier ranges.

Toolchain-neutral messages (Prometheus collection, report availability) reuse the upstream
`Benchmarking`-prefixed catalogue from `benchmarking-common` and are not repeated here; this
section lists only the k6-specific records, whose upstream counterparts are wrk-branded.

=== INFO Level (1-99)
