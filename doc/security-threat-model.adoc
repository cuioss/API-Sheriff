= API Sheriff -- Threat Model & CVE-Derived Validation Baseline
:toc: left
:toclevels: 3
:sectnums:
:sectnumlevels: 2

This document is the security contract API Sheriff validates *against*. It has three
parts:

. *Trust boundaries and STRIDE* -- the assets, the boundaries a request crosses, and the
  threat categories per boundary.
. *Failure catalogue* -- every failure class that has produced a real, cited CVE in a
  comparable API gateway, reverse proxy, or OAuth/OIDC stack (the gateways surveyed in the
  link:features-analysis.adoc[competitive analysis] -- APISIX, Kong, Traefik,
  KrakenD, Tyk, Gravitee -- plus the canonical proxy/JOSE CVEs). Each class carries the
  transferable lesson, the API Sheriff control that defeats it, a *status*, and a *testable
  assertion*.
. *Validation matrix* -- every control mapped to the component that owns it and the assertion
  that proves it, so this document doubles as a release gate.

[IMPORTANT]
====
*How to use this document.* It is normative for the security posture, not for behaviour --
where a control's behaviour is specified, link:configuration.adoc[the configuration model]
and link:architecture.adoc[the architecture] govern; this document names the *threat* the
control exists to answer and the *assertion* that proves it still does. Every catalogue
entry's assertion is meant to become a test (unit, integration, or benchmark) so a
regression re-opens a known-historical hole loudly. Status values:

* *COVERED* -- an ADR, a library, or delivered code owns the control; the assertion has (or
  will have) a test.
* *PARTIAL* -- the control exists but the assertion is not fully pinned, or only one half of
  an equivalence class is closed.
* *GAP* -- nothing yet owns this control; the "Gaps to close" section collects these as
  recommended hardening work (the original goal: learn from others' failures *before*
  shipping the feature).
* *ELIMINATED* -- the failure class does not apply because a design decision removed the
  surface entirely (recorded so an audit can confirm the surface stays removed).
====

== Foundation libraries (what is already owned upstream)

API Sheriff is not implementing these controls from scratch -- two audited libraries own
large parts of the catalogue, and the residual gateway work is exactly the part they
deliberately leave to the application. Attribution below reflects a 2026-07-17 source review
of the local `cui-http` and `TokenSheriff` trees. The versions this project resolves are
`cui-http` 3.1 -- managed by `cui-java-bom` through `cui-quarkus-parent`, with no override in this
repository; 3.1 is the release carrying the parameter-value line-break switch the `strict` profile
sets (see <<gw-03>>) -- and `TokenSheriff` 0.9.6, read from the `version.token-sheriff` property in
the root `pom.xml`, which is the authoritative source this number mirrors. Its JWKS-loader and
client-configuration builders both carry the hostname-verification passthrough the gateway binds its
two identity-provider back-channels through (see <<gw-06>>).

*`cui-http` (inbound filtering + forwarded resolution) provides:* per-component path
canonicalization returning a *normalized* path (`URLPathValidationPipeline` -- decodes
percent-encoding, collapses `..`/dot-segments and duplicate slashes, rejects
traversal/`%00`/overlong/backslash *unconditionally*); header name/value CR/LF/NUL rejection
(`CharacterValidationStage`, unconditional); collection count + length limits
(`RequestCollectionValidator`, `LengthValidationStage`); the forwarded-header trust engine
(`ForwardedHeaderResolver` -- CIDR-validated `trustedProxies`, right-to-left drop-untrusted,
per-value sanitization, canonical `X-Forwarded-*`/RFC 7239 regeneration, NiFi aliases); the
shared `SecurityEventCounter`; and reusable attack corpora (OWASP/ZAP/ModSec-CRS/Apache/Nginx/
IIS-CVE databases + encoding/traversal generators) shipped in its *test-jar*.

*`cui-http` deliberately does NOT provide* (gateway/web-server owns): request-level *framing*
/ smuggling defence (CL vs TE, chunked, HEAD-with-body, hop-by-hop `Connection` abuse) --
explicitly "infrastructure layer"; a *streaming* body-size limiter (the `BODY` pipeline is
removed; `max_body_bytes` must be a gateway stream counter); *matrix-param (`;`) handling*;
an *encoded-slash policy* (`%2f` is decoded to `/`); and the *TCP-peer gate* (the resolver
trusts headers, not the socket -- it never sees the peer address). It also does not reject
`0.0.0.0/0`/`::/0` (the gateway's configuration validator does).

*`token-sheriff-validation` provides, fail-closed:* JWT algorithm pinning
(`SignatureAlgorithmPreferences` -- allow-list, `none`/HMAC/embedded-`jwk` rejected, so
RS256->HS256 key-confusion is structurally impossible), an *in-library* guard for the
CVE-2022-21449 ECDSA "psychic signature" (`r|s == 0` rejected before the JDK verifier) and a
<2048-bit RSA floor; `iss`/`aud`/`azp`/`exp`/`nbf`/`iat`(+skew)/`sub` validation; JWKS from
the configured/discovered endpoint *only* (token-supplied `jku`/`x5u`/`jwk` ignored) behind
an `EgressPolicy` that blocks loopback/link-local/cloud-metadata on the initial fetch *and
every refresh* (DNS-rebinding-safe), with TTL cache, rotation grace, and unknown-`kid` that
cannot drive a fetch storm; the 4-arg `AccessTokenRequest(token, headers, uri, method)` for
DPoP; server-side DPoP proof validation + replay cache; a Quarkus JWKS-readiness health
check; an RFC 9457 exception mapper that interpolates no secret/message. It ships a
`generators`-classifier test-jar with adversarial token/key corpora (`JkuX5uAttackTest`,
`PsychicSignatureAttackTest`, ...).

*`token-sheriff-client` (BFF engine) provides, fail-closed:* auth-code + PKCE (`S256` only,
`plain` not implementable); `FlowContext` bundling `state`+`nonce`+PKCE-verifier+`redirect_uri`
(+`acr_values`/`max_age`) with constant-time `state`/`nonce` verification; RFC 9207 `iss`
mix-up defence (incl. absent-`iss` rejection); the refresh grant with rotation (`RefreshFlow`)
and a classification of a refused refresh by what the provider did to the presented token
(`RefreshFlow.classify`), plus an RFC 7009 `RevocationClient`; RP-initiated logout with *exact-match* `post_logout_redirect_uri`
and state verify (`PostLogoutRedirectValidator`); RFC 9470 step-up parsing/re-drive;
callback HPP defence (`CallbackParameters.parse(rawQuery)` rejects duplicate `code`/`state`);
pushed authorization requests (`ParClient`, RFC 9126); `private_key_jwt` client authentication
(`PrivateKeyJwtAuth`); and DPoP sender-constraint *requesting* (`SenderConstraint`: the proof on the
token request and one retry on a `DPoP-Nonce` challenge). At the pinned version the engine does *not*
compare the token type or `cnf` of a token response with the constraint it sent -- a `Bearer` answer
to a request that carried a proof is accepted -- so the downgrade refusal is the gateway's
(<<bff-14>>). Its mutual-TLS client authentication is not constructible at that version.

*The engine/validation libs deliberately leave to the gateway* (the true BFF residual): the
*back-channel logout-token receiver and its `events`/`sub`/`sid`-required + `nonce`-forbidden
checks* (no library support at all -- signature reuse only); *persistence* of the
`FlowContext` (session-bound, single-use discard, return-URL -- the engine gives the DTO
shape, not the store); the *concrete `TokenStore`* (server session vs encrypted cookie);
*scope enforcement* (the lib exposes `providesScopes()`/`getScopes()` but enforces nothing);
and calling `CallbackParameters.parse(rawQuery)` on the *raw* query (the `of(Map)` path cannot
re-detect duplicates); the *disposition* of a classified refresh failure and the per-session
single-flight around the refresh (`TokenRefreshCoordinator`); the *refusal of a token response that
is not bound* to the proof key (`BoundTokenEndpointClient`, <<bff-14>>); and the *signing keys* --
reading or generating them, and publishing the client key (<<bff-18>>, <<bff-19>>).
*Refresh-token reuse detection* is
owned by neither the libraries nor the gateway: it is the identity provider's strict rotation
(<<bff-08>>).

This attribution is folded into the *Owner* column of the validation matrix and the per-entry
status below.

== Assets

What an attacker wants, ranked by blast radius:

[cols="1,3"]
|===
| Asset | Why it matters

| Upstream reachability
| The gateway is the only sanctioned path to the backends. Reaching an upstream *without*
  passing auth/filtering is the top-line failure -- every "auth bypass" CVE below is an
  attack on this asset.

| Mediated tokens (BFF variants)
| Access / refresh / ID tokens held server-side (session mode) or inside the encrypted
  cookie (cookie mode). Theft = account takeover; leakage to the browser defeats the entire
  BFF rationale.

| Session / flow secrets
| Session-id cookie, the pending-authorization record (`state`/`nonce`/PKCE verifier), the
  cookie encryption key(s). Forgery or replay = impersonation.

| Client credential and signing keys (BFF variants)
| What the gateway proves its own identity with at the identity provider, and what its access tokens are
  bound to. Two private keys: the client-authentication key and the DPoP proof key. Each is read by
  the gateway itself from a PEM file on a mount, or generated at startup and held in process memory
  only. In client-secret mode -- selected by configuring `oidc.client_secret` -- the secret takes
  the place of the client-authentication key and remains an asset of that mode. Theft of the
  client-authentication key or of the secret = the holder can act as the gateway's client at the
  identity provider (<<bff-18>>).

| Client identity signal
| The real client IP / scheme the gateway asserts to upstreams via regenerated forwarding
  headers. Spoofing it corrupts every downstream IP-based decision.

| Configuration integrity
| The immutable route table and policy. There is no runtime mutation surface by design (see
  GW-10); the boot-time config *is* the trust anchor.

| Availability
| A single process fronting everything. Resource-exhaustion classes (GW-07, GW-08) target
  this.
|===

== Trust boundaries

A request crosses these boundaries; each is a place a control must hold.

[cols="1,2,3"]
|===
| # | Boundary | What is untrusted across it

| B1
| Client -> TLS edge
| Everything: TLS ClientHello/SNI, all request bytes, framing, every header including
  `Forwarded`/`X-Forwarded-*`/`Connection`, the raw path and its encoding, the body.

| B2
| TLS edge -> pipeline (terminated L7)
| The normalized request. The boundary's job is to hand the pipeline *one* canonical form
  and reject ambiguity (framing, encoding) here.

| B3
| Pipeline -> upstream (data plane)
| The gateway is now the client. What it *emits* is trusted by the upstream, so the gateway
  must strip inbound trust signals and regenerate its own (forwarding headers, mediated
  bearer). The upstream's *response* is untrusted coming back.

| B4
| Gateway <-> IdP (control plane, BFF)
| OIDC discovery/JWKS/pushed-authorization-request/token/revocation/logout traffic. Tokens and
  logout tokens received here are untrusted until validated; JWKS key sources must be pinned (no
  token-supplied `jku`). In key mode the boundary is also crossed in the other direction: the
  identity provider fetches the gateway's client key set from the gateway's public port
  (<<bff-19>>).

| B5
| Browser <-> BFF session
| The session cookie and any BFF-API request it authenticates. Cross-site requests carry the
  cookie ambiently (CSRF); the cookie itself is a theft target.

| B6
| Operator -> configuration
| Config files are operator-authored (semi-trusted) but env-substituted values and secrets
  cross a boundary; a config that would serve traffic in a partially-valid state is a
  failure (fail-closed boot).

| B7
| Data-plane network -> management surface
| Health/metrics on the management port. Must not be reachable from, or confused with, the
  public data-plane port; there is no admin/mutation API to expose (GW-10).
|===

.Boundary geometry
----
        B1                B2                      B3
client ----> [ TLS edge ] --> [ L7 pipeline ] --------> upstream
  |          (terminate/         (normalize,      (regenerated
  |           SNI split)          filter, auth,     headers,
  |                               forward policy)    mediated bearer)
  |                                   |  ^
  |  B5 (session cookie / BFF API)    |  | B4 (OIDC: discovery/JWKS/token/logout)
  +-----------------------------------+  +--> IdP

  B6 operator --> [ immutable config, fail-closed boot ]
  B7 management port (health/metrics) -- never on the data-plane port, no mutation API
----

=== Residual risk: plain-HTTP termination behind an external hop (B1)

B1 is drawn assuming the gateway *is* the TLS edge. A deployment that sets
`QUARKUS_HTTP_INSECURE_REQUESTS=enabled` moves that edge outward onto a separate terminating hop, and
B1 splits in two: the client reaches the hop over TLS, and the hop reaches the gateway in
*cleartext*. This is a supported mode, and the split is the point of it -- but it relocates part of
the boundary's guarantee out of the gateway and into the surrounding topology, which is what makes it
a residual risk rather than a control.

*What the gateway no longer guarantees on the hop-to-gateway leg:* confidentiality and integrity of
every request and response byte, and the authenticity of the client-identity signal. The gateway
cannot observe tampering on a link it does not terminate, and its immediate TCP peer is the hop
rather than the client, so client-address attribution rests entirely on
`forwarded.trusted_proxies` naming that hop correctly.

*What the topology must guarantee in exchange:*

* The hop and the gateway share a network segment no untrusted party can observe or inject on. A
  cleartext leg across anything wider is an unencrypted gateway with extra steps.
* The hop terminates TLS itself, so the client-facing half of B1 is unchanged from a client's point
  of view.
* The hop's address is the one entry in `forwarded.trusted_proxies`, declared as a `/32`. A range
  wide enough to contain a client hands that client's own forwarding claim to every upstream
  IP-based decision -- the *Client identity signal* asset, spoofed at the boundary that was supposed
  to establish it.

The gateway does not merely document this posture; it refuses the combinations that cannot be part of
it. Inbound mTLS and an ADR-0017 passthrough topology are both rejected at boot alongside the opt-in,
as is declared server key material, because each would leave a declaration in force that the mode
makes meaningless. The BFF is likewise unavailable on a plain port a browser reaches directly: every
session and binding cookie carries `Secure` unconditionally. Both verdicts, and the two others this
mode carries, are enumerated in
link:user/tls-edge.adoc#_interactions_with_the_rest_of_the_edge[TLS edge -- What this mode does to
the rest of the edge]; they are not restated here.

== Gateway failure catalogue

Each class: the mechanism, the *cited real CVEs* that prove it is not theoretical, the API
Sheriff control, its status, and the assertion to test. CVE IDs marked *(unverified)* were
sourced from advisory aggregators but not confirmed on an NVD/GHSA primary page during
research -- cite the *class*, not the number, until confirmed.

[#gw-01]
=== GW-01 -- Path normalization / router-vs-enforcement desync (auth bypass)

*The single most recurrent gateway CVE class.* The router matches on one representation of
the path (raw, or partially decoded) while auth/block enforcement -- or the backend --
acts on a different one, so a request skips the control bound to the path it ultimately
reaches.

*Evidence.* Traefik: CVE-2025-47952, CVE-2025-66490, CVE-2026-40912 (StripPrefixRegex
Path/RawPath length desync), GHSA-xf64-8mw2-4gr2 (StripPrefix), GHSA-cxjq-mrr5-89rv
(ReplacePathRegex) -- six-plus advisories in ~14 months. APISIX CVE-2021-43557 (`uri-blocker`
checked raw `request_uri`, router matched normalized). Kong CVE-2021-27306 (JWT route bypass
via `/public/../api`) and the external-authz path-traversal (Kong forwards un-normalized
path, partial `%2E`/`%2F` decode). Envoy CVE-2021-29492 (`%2F`/`%5C` not decoded ->
RBAC/JWT bypass). Systematized by Orange Tsai, "Breaking Parser Logic" (Black Hat 2018).

*Control.* `cui-http`'s `URLPathValidationPipeline` already returns a *canonical* path
(percent-decoded, dot-segments and duplicate slashes collapsed, traversal/`%00`/overlong/
backslash rejected unconditionally). The gateway's residual job is the *invariant*: route,
the `allowed_methods` verb gate, auth selection, `allowed_paths` matching, *and* the upstream
remainder all consume that *same* canonical output -- byte-identical -- never the raw
request-URI. Two things cui-http leaves to the gateway and this control must add: an
*encoded-slash policy* (cui-http decodes `%2f` to a structural `/`; the gateway decides
reject-vs-accept and applies it before routing) and *matrix-param (`;`) handling* (not
touched by cui-http). This directly answers the code-review finding that the interim
`ProxyRoute` looks the route up on the raw URI but relies on the router's normalized match
(raw-vs-normalized divergence).

*Exact routes consume the same canonical path.* A `match.path` route compares its declared path
against that canonical output as an un-normalized string, and a prefix route matches it on a segment
boundary -- neither re-reads the raw request-URI. The one deliberate asymmetry is the trailing slash,
which an exact route treats as significant (`/a` and `/a/` are distinct addresses) and which the
canonical path preserves; the integration suite asserts both spellings of one address through the
real pre-route floor, the slash-less one answered by an exact redirect route and the slash form
falling through to the enclosing prefix route.

*And the enclosing route is bound to the same anchor.* That fall-through is the intended behaviour
only while the route it falls through to carries the same posture. The ADR-0007 rules that pair
routes with anchors are *declaration*-scoped -- they judge a route by where its own match key sits --
so a route sitting outside and *above* an anchor was judged by none of them, while selection still
let it answer addresses inside the namespace. With exact routes that gap is reachable: an anchor
whose only member is `path: /admin` claims exactly one address, and `/admin/` and `/admin/x` land on
whatever encloses it -- served with *its* auth posture and *its* `security_headers` block, which is
the router-vs-enforcement desync of this entry expressed in configuration rather than in parsing. The
boot now closes it with the mirror rule: a prefix route whose namespace strictly contains an anchor's
`path_prefix` without declaring that anchor fails the boot, unless a prefix route declared at the
anchor's own `path_prefix` covers the namespace -- in which case longest-prefix selection gives that
member every address inside it. Coverage requires the member to match its whole namespace and not
merely to name it: a member narrowing on a non-path `match` dimension is not accepted as covering, so
no address in an anchor namespace is served by a route outside the anchor.

*The mirror rule reaches every protocol, including `grpc`.* The two declaration-scoped rules waive
`protocol: grpc` routes, because a service-rooted gRPC method path can never nest inside a gateway
namespace on a segment boundary -- an argument about where the route's own match key sits. The mirror
rule asks the opposite question, and nothing constrains a gRPC route's declared match key to a bare
service path. Selection is protocol-blind (the route table looks a request path up on the path alone,
and the matcher carries no protocol dimension), so a gRPC route declaring a broad `path_prefix` would
answer plain HTTP requests inside the swallowed namespace with its own posture. Waiving it there
would reopen precisely this entry's desync in configuration, so it is not waived.

*Coverage requires an unnarrowed member.* The coverage exception was first written path-geometrically
-- prefix equality alone -- which left the bypass reachable one dimension over: a member declared at
the anchor prefix but narrowed to `methods: [GET]` marked the namespace covered while every other verb
matched no anchored route and fell through to the enclosing one, answered under *its* auth and
`security_headers`. A `host` or `headers` narrowing does the same, and the header case is the easiest
of the three to reach, since the complement is any request that simply does not send the header.
The rule therefore tests both halves: the member's normalized match key equals the anchor prefix *and*
it narrows on no dimension the route matcher ANDs with the path. The matcher is the declaring source
for what those dimensions are (`match.methods`, `match.host` and `match.headers` at present), and the
predicate deciding it lives on the match model beside them, with a contract test asserting that every
component of that model is classified -- so a dimension added later cannot silently reopen this.

*The query is held to the same one-form rule, in the other direction.* A path is canonicalized
because routing and enforcement must agree on it; a query is forwarded, so what the filter judged and
what the upstream receives must be the same bytes. Before
link:adr/0047-The_security_filter_validates_the_raw_query_it_forwards.adoc[ADR-0047] they were not:
the transport decoded the query, the parameter pipeline decoded it a second time, and the forward path
re-encoded a third form -- `q=a%252F` was validated as `a/` while the upstream received `a%252F`. The
security filter now receives the raw, still-percent-encoded pairs (names through `cui-http`'s
parameter-name pipeline, values through the parameter-value pipeline, each decoding once) and the
forward path appends exactly those pairs verbatim and in the order they arrived -- the query is an
ordered pair sequence, never a map grouped by name, so `a=1&b=2&a=3` is not regrouped into
`a=1&a=3&b=2` -- so *the validated form equals the forwarded form* and a double encoding is refused as
one. The forward policy's `query_allow` / `query_deny` lists are
the one consumer that needs the decoded name -- the upstream acts on it -- so they compare the
percent-decoded name while the raw pair crosses: a percent-encoded spelling such as `%74oken` can no
longer evade a `query_deny: [token]`. A percent-escape counts only when both digits are ASCII hex
digits, so an escape spelled with full-width digits (`%７４oken`) is malformed rather than decoded to
`token`: such a name has no decoded form and crosses neither a positive- nor a negative-list (CWE-20).
The one byte the forward path does *not* pass verbatim is a raw
`;`: the edge and the forward lists split pairs on `&` only while `cui-http` admits a raw `;` under
every profile, so `?x=1;token=abc` is one pair `x` to the gateway but two to an upstream that also
splits on `;` -- a `token` no list judged (HTTP parameter smuggling, CWE-235). The forward path
therefore writes every raw `;` in a forwarded name or value as `%3B`, on every route; the decoded
meaning is unchanged, so the validated form still equals the forwarded form at the decoded level.
All three properties are pinned: `GatewayEdgeQueryHandoffTest` over a
live edge (including a leg asserting the transport's decoded value differs from the forwarded raw
one, the `;` legs under forward-all, `query_deny` and `query_allow`, and legs keeping interleaved
repeated names in wire order) and `StrictQueryAcceptanceIT` against the native image assert every
accepted query reaches the upstream byte for byte -- `;` aside -- and every refused one reaches it
not at all; `ForwardPolicyStageTest` denies and admits a percent-encoded spelling of a listed name, withholds a
full-width-digit escape under both lists, and keeps interleaved repeated names in inbound order.

*Status:* PARTIAL. Pipeline stage 1 validates the raw path and stages 2-3 act on the
normalized path, and anchor prefixes are normalized before the disjointness check -- but the
*invariant* is not stated explicitly anywhere, nor is the divergence tested. The assertion
below is the outstanding hardening item (see Gaps). The query half above is delivered and tested and
does not hold this entry at PARTIAL.

*Assertion.* For every encoded-traversal / encoded-slash / mixed-encoding / trailing-slash /
matrix-param variant of a protected path: the request is either rejected at B2 or is
routed, authorized, and forwarded against the *same* canonical path -- never authorized as
public and dispatched to a protected upstream. Upstream request-count = 0 on every bypass
attempt. A configuration whose anchor namespace is left uncovered while a broader route encloses it
fails the boot, and the same configuration with a prefix route at the anchor prefix boots
(`ConfigValidatorTest.AnchorRules`, rule 4b -- including the partial-coverage case, where an anchored
route on a sub-path only is not coverage). The same pair holds with the enclosing route declared
`protocol: grpc` (`ConfigValidatorTest.GrpcNamespaceExemption`), alongside the controls proving the
two declaration-scoped directions are still waived for it. A query accepted by the filter reaches the
upstream byte for byte, a refused one (including the double encoding `%252F`) reaches it not at all,
and a percent-encoded spelling of a name on a route's `query_deny` list is withheld.

[#gw-02]
=== GW-02 -- HTTP request smuggling / desync

Front-end and back-end disagree on where a request ends (CL vs TE, bare-LF chunk
terminators, duplicate framing headers, HEAD-with-body, HTTP/2->1.1 downgrade), letting an
attacker's body become a second request on a pooled connection.

*Evidence.* HAProxy CVE-2021-40346 (htx integer overflow desync, all ACLs bypassed). Go
`net/http` CVE-2025-22871 (bare-LF chunk terminator). Node/llhttp CVE-2022-35256. OpenResty
`lua-nginx-module` CVE-2024-33452 (HEAD-with-body reinterpreted -- hit *both* Kong and
APISIX). Kong CVE-2026-6338 (CL.0: attacker lists `Content-Length` in `Connection:` so Kong
drops it). Netty CVE-2021-21295 (missing CL validation on h2->h1 downgrade). Context:
PortSwigger "HTTP/1.1 Must Die" (2025).

*Control.* Enforce a single unambiguous framing at B2: reject requests bearing both
`Content-Length` and `Transfer-Encoding`; admit `chunked` as the only transfer coding and
require RFC-9112 chunk parsing with CRLF terminators; reject a body on a bodyless method;
never let a `Connection` token remove a framing or trust header (see GW-03); process nothing
that follows a request with rejected framing on the same connection; never reuse an upstream
connection that carried a request whose inbound framing failed. Prefer end-to-end HTTP/2 where
possible.

The HTTP transport refuses what it cannot frame at all, with a bare `400` and a closed connection. The gateway's `FramingGate` refuses what the transport does frame
but two parsers could read differently, with a `400` problem document

enforces the body rules no header can decide: a bodyless method is sent upstream with no body and

The gate runs once, at stage 1, before route selection. No later stage changes the inbound
header set, so there is no mutated set to validate again: request headers are immutable, and
the headers sent upstream are a separate map that never carries the client's `Content-Length`
or `Transfer-Encoding` (the request-direction never-forward set, GW-03). The framing of the
forwarded body is written by dispatch, not relayed. A request that declares a length is forwarded
with the value the gate and the `max_body_bytes` pre-check admitted, and with exactly that many
bytes. A request that declares none keeps the framing the upstream client chooses. A `GET` or
`HEAD` without a positive declared length is sent with no body at all. Resetting an upstream
request closes its connection on HTTP/1.x, which is what the corpus pins; on HTTP/2 it resets the
stream.

The bodyless-method rule binds the proxy dispatch, the one terminal action that streams an
inbound body. The other terminal actions a `GET` or `HEAD` can reach forward no inbound body
either. An asset route is served by method and path alone, whether its source is a directory or
an upstream. A redirect, the portal and the gateway's reserved paths write answers the gateway
authors.

*Status:* PARTIAL. API Sheriff sits *behind* other proxies (the whole forwarded-header design
assumes it), so framing agreement is a first-class requirement, not an inherited default. The
gate and the edge's connection handling are gateway code. The transport rows are behaviour of
the HTTP stack the gateway runs on, and the corpus is what turns red if a transport default
starts admitting one of those shapes. Every HTTP/1.1 corpus entry writes raw bytes over a plain
socket, and every entry asserts both the status of each response and the exact list of requests
the upstream saw.

The row is off COVERED because the assertion below is not pinned in full. Over HTTP/2 the corpus
pins that a gate rejection ends only its own stream, that a declared body on `HEAD` is refused,
that a non-decimal `Content-Length` refuses only its own stream, the bodyless-method rule, and the
framing of a body with and without a declared length. The smuggling entries speak HTTP/1.1, and
the upstream side of the corpus is HTTP/1.1 throughout: no test drives the remaining gate clauses
or an inbound body failure after dispatch over HTTP/2, and none drives the upstream reset against
an HTTP/2 upstream. One clause is pinned by `FramingGateTest` alone and by no corpus entry: a
repeated or comma-separated `Content-Length`.

*Assertion.* A request with both `Content-Length` and `Transfer-Encoding`, a HEAD/GET with a
body, or a `Connection: Content-Length` cleanup attempt is rejected (400) and never produces
two upstream requests; a smuggling test corpus (CL.TE/TE.CL/TE.TE/CL.0) run through the
gateway produces zero desyncs; a request queued behind a rejected one is not processed; a `GET`
or `HEAD` without a positive declared `Content-Length` never carries a body upstream, on any
protocol; a request that declares a length reaches the upstream framed by exactly that length; an
upstream request whose inbound body failed is reset and its connection is not reused. That
failure is reported under the dedicated event `INBOUND_BODY_ABORTED`, attributed to the client,
and is not counted as a failure by the route's circuit breaker and is recorded by it as a success.

*Operator-relaxable leg (bounded).* The gateway-wide
`security_defaults.allow_get_with_content_length_body` opt-in (default `false`) admits a
`Content-Length`-framed body on `GET`, for upstreams whose API takes one (Elasticsearch `_search`).
It narrows the "GET with a body" clause of the assertion above *only* for that shape, and only when
explicitly enabled. The boundary is drawn where the smuggling risk is, not where the convenience is:

* `Transfer-Encoding` on a bodyless method stays rejected *unconditionally* -- chunked framing on an
  otherwise-bodyless method is the desync primer this control exists to constrain, and the motivating
  clients send `Content-Length`-framed bodies, so excluding it costs the use case nothing. No
  configuration can relax it.
* The CL+TE coexistence rule, the duplicate/comma-listed `Content-Length` rule and the
  `Connection`-list framing-strip rule are independent checks unaffected by the opt-in; the CL+TE
  check runs *before* the body-on-bodyless-method check, so a `GET` carrying both is still rejected.
* `HEAD` with a body remains rejected on every leg.
* A `GET` body that no `Content-Length` declares stays refused on every protocol: the opt-in admits
  a declared length, and the bodyless-method rule above refuses any other `GET` body on its first
  byte.

The residual exposure is therefore a well-framed, unambiguously-delimited `GET` body -- a shape both
front-end and back-end agree on, which is what makes it not a desync vector. It is forwarded framed
by its declared length, with exactly that many bytes, never re-framed as chunked. With the key omitted or
`false`, every rejection above is preserved bit-for-bit.

=== GW-03 -- Header injection (CRLF) and hop-by-hop header abuse

(i) CR/LF/NUL in a header name/value splits the message (response splitting). (ii) A client
names a *trust* header inside `Connection:` so the proxy strips it before the backend sees
it -- deleting the origin's client-IP or auth signal.

*Evidence.* Apache httpd CVE-2022-31813 (client `Connection` handling suppresses
`X-Forwarded-*` to origin, defeating backend IP-auth). Netty CVE-2022-41915 (`DefaultHttpHeaders`
iterator path skipped value validation -> CRLF response splitting). Traefik CVE-2024-45410
(client names Traefik's own `X-Forwarded-*` as hop-by-hop). Kong CVE-2026-6338 (framing-header
strip abuse, GW-02).

*Control.* cui-http's `CharacterValidationStage` rejects CR/LF/NUL in header names and values
*unconditionally* on the *ingress* path: every inbound header is fed through it before any stage
reads one. The response direction carries no equivalent re-validation, and saying so is the
honest statement of the control's reach -- the gateway does not re-run `CharacterValidationStage`
over upstream response headers. Both response paths (`edge.ResponseStage` for the streamed proxy
relay, `asset.AssetResponseEnvelope` for the buffered asset envelope) copy the source's remaining
headers through once the gateway-owned never-relay set below has been applied. That direction is
bounded by *which names* cross rather than by re-checking their characters, so the residual is
scoped to a configured upstream that is already inside the gateway's trust boundary rather than
to client-supplied input. Never let a client `Connection:` header steer stripping of framing or
trust headers.

*Line breaks in query-parameter values under `strict`.* A parameter value that decodes to CR or LF
is forwarded to an upstream that may splice it into a log line, a header or another line-oriented
protocol. `cui-http` admits decoded CR, LF and TAB in parameter values under every preset by default
-- a form-data textarea carve-out -- so the gateway's `strict` profile turns that carve-out off:
`SecurityProfile.STRICT` is the `cui-http` strict preset with exactly one component changed
(`allowLineBreaksInParameterValues(false)`), and a value carrying `%0D` or `%0A` is refused `400`
before it reaches the upstream. `lenient` keeps the library default, and `minimal` runs no
parameter validation at all; both are documented as such (see
link:configuration.adoc#_query_validation_raw_form[the configuration reference]). Because the
filter now judges the raw form it forwards (<<gw-01>>), the refusal covers exactly the bytes the
upstream would have received.

The hop-by-hop and trust-header lists are *gateway-owned and enumerated in full per direction*,
never derived from a sibling list and never taken from what a client names
(link:adr/0037-The_gateway-owned_header_sets_are_enumerated_per_direction_and_bounded_by_knowledge.adoc[ADR-0037]).
Two properties carry this control:

* *The request-direction never-forward set applies under every forward mode* -- including the
  permissive forward-all baseline. `Authorization` is its single re-admittable member (only on a
  route declaring a positive-list naming it); `Cookie` is absolute against client input. No route
  configuration re-admits the hop-by-hop, framing or gateway-owned names from the request. The one
  path around the set is an operator's *static* `set_headers` value, which is merged after the
  strip and carries no caller-supplied material.
* *The forwarded header set is built by regeneration, never by editing the client's map.* The
  client's `X-Forwarded-*` / `Forwarded` copies are skipped on *every* mode, forward-all
  included, so a permissive route is not a way to smuggle a spoofed chain upstream (GW-04).

*The equivalence class is carried in the set, not left to the operator.* The old allow-list-only
forward model dropped *everything* an operator did not enumerate, which incidentally also dropped
non-canonical spellings a client invented -- an `X_Forwarded_For`-style underscore variant that
cui-http does not canonicalize to the hyphenated name, or a vendor alias such as `X-Real-IP`.
Forward-all removes that incidental protection, so the protection is now stated: the vendor
aliases are members of the request-direction never-forward set in their own right, and both that
set and the regeneration skip match on the *separator-folded* name, so every `-`/`_` spelling of
either set's names is withheld under every mode without an operator entry (see
link:#gw-04[GW-04] for why the class is closed by folding rather than by enumeration). The
aliases sit in the never-forward set rather than beside the canonical names because the gateway
does not *regenerate* them -- the canonical names are what it emits, the aliases are
claims about provenance only the gateway is entitled to make. `set_headers` is unaffected: an
operator fronting a backend that reads `X-Real-IP` still sets it deliberately, because the strip
governs client input and configuration is not client input.

*Status:* PARTIAL. Header CR/LF/NUL is cui-http (COVERED); the per-direction gateway-owned sets
and the every-mode regeneration skip are pipeline stage 5 and are pinned exhaustively by their
own tests; the hop-by-hop-abuse-cannot-strip-framing property (the GW-02 tie-in) is pinned by
`GatewayEdgeFramingCorpusTest` (`connectionStripsContentLength`) and `FramingGateTest`
(`rejectsFramingHeaderStrip`, `rejectsTrustHeaderStrip`): a `Connection` token naming a framing
or trust header is rejected `400` before route selection. The one leg keeping this row off
COVERED is the response direction: the last clause of the assertion below is not delivered,
because response headers are bounded by which names cross and are not re-validated (see
*Control*).

*Assertion.* CR/LF in a header value is rejected; a query-parameter value decoding to CR or LF is
rejected on a `strict` route and never forwarded, while a `lenient` route still admits it (the
matched control, pinned by `GatewayEdgeQueryHandoffTest` and `SecurityProfileTest`); a client
`Connection: X-Forwarded-For` (or
`Content-Length`) is rejected `400` and never causes the gateway to drop the regenerated
forwarding header or the framing header; a client-sent `X-Forwarded-For`, `Cookie` or `Authorization` never reaches the
upstream on a forward-all route; response headers are validated before write.

=== GW-04 -- X-Forwarded / trusted-proxy spoofing

IP-based auth, rate limiting, or "internal caller" trust reads a client-settable forwarding
header as source identity. Any client sets `X-Forwarded-For: 127.0.0.1` and becomes
"internal".

*Evidence.* APISIX CVE-2022-24112 -- the flagship gateway RCE: the `batch-requests` plugin
let the caller set `X-Real-IP` on re-dispatched sub-requests, the Admin-API IP allowlist
trusted it, loopback was forged, chained with the default admin token (GW-10) to
unauthenticated RCE. ZooKeeper CVE-2024-51504 (`IPAuthenticationProvider` honors client
`X-Forwarded-For` by default). Traefik CVE-2026-35051 / CVE-2026-54764 / CVE-2026-39858 /
CVE-2026-54763 *(unverified)* -- a chain of *incomplete* forwarded-header-stripping fixes
(each patched one spelling/case/underscore/alias variant while a sibling survived).
OAuth2-Proxy CVE-2026-40575 *(unverified)*. The "too-broad-trust" bug the
link:features-analysis.adoc[feature analysis] already calls out.

*Control.* Never derive trust from a client-settable header. Gate `Forwarded`/`X-Forwarded-*`
on a *TCP-peer* check against an explicit trusted-proxy CIDR list (ADR-0003), parse the chain
right-to-left discarding untrusted entries, and *regenerate* canonical output -- never
append. Validate the CIDR list at boot (reject `0.0.0.0/0`, `::/0`, and split-range
trust-all equivalents like `0.0.0.0/1`+`128.0.0.0/1`; reject malformed CIDRs). Canonicalize
header names across the *whole* equivalence class (case, `-`/`_`, aliases) before stripping,
or the strip is incomplete -- the Traefik fix-chain is the cautionary tale.

*Status:* COVERED. ADR-0003 + pipeline stage 5 (TCP-peer gate, drop-and-regenerate) + the
configuration validator (CIDR parsing, split-range trust-all rejection). The client's canonical
`X-Forwarded-*` / `Forwarded` copies are skipped under every forward mode, forward-all included,
so the *emitted* chain is always the gateway's own.

*Trusted-proxy breadth below trust-all is warned, not refused, and the residual is chosen rather than
safe*
(link:adr/0044-Trusted-proxy_breadth_is_warned_beyond_one_provisioned_network_and_refused_only_at_the_whole_address_space.adoc[ADR-0044]).
The TCP-peer gate is only as narrow as the list it reads, and every host inside a trusted range that
can reach the gateway directly can spoof the client identity downstream decisions rely on. Three
outcomes cover the whole range of breadth. A range set whose members together cover an address
family is *refused at boot*, complementary halves included. A single entry spanning more than one
operator-provisioned network -- broader than an IPv4 `/16` or an IPv6 `/48` -- boots with
`WARN ApiSheriff-102`, which is what catches the realistic mistake: a whole private block such as
`10.0.0.0/8` or `172.16.0.0/12` pasted in. An IPv4 `/16` (65,536 addresses) or an IPv6 `/48` boots
with *no* signal. That is a recorded, accepted exposure -- a legible range an operator chose, left
un-warned so the warning keeps its meaning on the configurations that need it -- and it is not a
statement that such a range is safe.

*A range supplied through an environment variable meets exactly these rules.* The validator reads
the value after `${VAR}` substitution and cannot tell it from a literal, so a provenance-keyed
refusal is not expressible, and a source-blind stricter threshold would refuse legitimate pod-network
trust while stopping nothing the warning and the trust-all refusal do not already surface. The
residual therefore applies to the environment path unchanged, with one aggravation stated rather than
implied: a substituted range passed through no reviewed change to `gateway.yaml`, so the boot warning
is the only signal it ever gets. The thresholds are held by a parameterised test carrying a warning
row past each boundary and a silent row exactly at it, asserted by identifier and range.

*The equivalence class beyond the canonical names is covered too, and it is closed by a rule
rather than by a list.* Two sets hold the names, split by *which question each name answers*: the
regeneration skip holds the canonical spellings (`x-forwarded-for`, `-host`, `-proto`, `-port`,
`-prefix`, `forwarded`) -- what the gateway *emits* -- and the request-direction never-forward set
holds the names it does not emit but must never *relay*, the vendor aliases `X-Real-IP`,
`X-Client-IP`, `True-Client-IP` and `CF-Connecting-IP`. The split is deliberate: filing a name the
gateway does not regenerate beside the ones it does would assert a relationship that is not there,
and would widen the untrusted-peer resolver mask with names the resolver never queries.

*Both sets are then tested on the separator-folded name* -- lower-cased with every `_` mapped to
`-` -- so each set closes its own names across the whole `-`/`_` class instead of listing the
variants. This matters because the class is larger than it looks: a two-separator name such as
`X-Forwarded-For` has *four* spellings (`X-Forwarded-For`, `X_Forwarded_For`, `X-Forwarded_For`,
`X_Forwarded-For`), and every backend that maps header names to CGI-style variables -- CGI,
FastCGI, WSGI and Rack all do -- resolves all four to one `HTTP_X_FORWARDED_FOR`. Enumerating
spellings would mean four entries per name and a fix the first time one was missed, which is
exactly the shape of the Traefik fix-chain in the evidence above: each of those CVEs closed one
spelling while a sibling survived. Folding before the membership test closes the class at once and
keeps it closed for any name a later edit adds to either set. `Forwarded` contributes no variant
at all -- it carries no separator to fold, so its underscore spelling is the canonical name the
regeneration skip already holds.

*Assertion.* A spoofed inbound `X-Forwarded-For`/`X-Real-IP`/`Forwarded` from a non-trusted
peer never influences the gateway's resolved client identity; the emitted chain is regenerated,
not appended; the canonical `X-Forwarded-*` / `Forwarded` names are skipped from the client copy
under *every* forward mode, forward-all included; each underscore variant and vendor alias is
withheld from the upstream under *both* forward-all and a negative-list that does not name it,
each leg carrying a matched positive control; every *mixed* `-`/`_` spelling of a forwarding name
or a vendor alias is withheld under forward-all, a negative-list *and* a positive-list naming it,
so the equivalence class is asserted closed rather than sampled; an operator's `set_headers` still
places such a name deliberately; a `0.0.0.0/1`+`128.0.0.0/1` config is rejected at boot; an entry broader
than `/16` or `/48` emits `ApiSheriff-102` while an entry exactly at either boundary does not.

=== GW-05 -- SSRF via proxy features / upstream control

A proxy feature lets the attacker influence the upstream destination (path-injected target,
user-supplied upstream, followed cross-host redirect) -> the gateway makes requests from its
trusted position to internal services / cloud metadata.

*Evidence.* Apache httpd mod_proxy CVE-2021-40438 (crafted URI-path selects attacker origin;
CISA Known-Exploited). The Capital-One-class metadata SSRF pattern.

*Control.* The upstream is a *fixed, boot-resolved topology alias* -- never influenced by
request content (link:adr/0004-topology-indirection.adoc[ADR-0004]). Resolved alias URLs are
restricted to `http`/`https` at boot. Redirect following is disabled
(`followRedirects(NEVER)` -- an SSRF-limiting default in the interim proxy, to be preserved).
On the *control plane* (B4 -- OIDC discovery/JWKS/token), `token-sheriff-validation`'s
`EgressPolicy` already blocks loopback/link-local/site-local/cloud-metadata targets on the
initial fetch and every refresh (DNS-rebinding-safe), and it is widened only host by host, through
the library's own `allowedEgressHost` seam. The gateway feeds that seam from the per-issuer
`token_validation.issuers[].jwks.allowed_egress_hosts` list in `gateway.yaml`, in one of two forms
(link:adr/0011-gatewayyaml_exposes_JWKS_trust_and_egress_as_neutral_names_bound_by_the_deployment.adoc#amendment-a1[ADR-0011
Amendment A1]):

* *Absent or empty -- derived.* The gateway passes exactly one host: the host of the issuer's own
  `jwks.url`, port dropped. An `http` issuer whose `jwks.url` names no host is refused at boot
  (`CONFIG_INVALID`), so a derived allowance never collapses into an empty one by accident.
* *Non-empty -- authoritative.* Each entry exempts exactly one host (host-exact, no wildcard or
  suffix form), and the `jwks.url` host is never merged into the list. A blank or `host:port` entry
  is refused at boot.

*The trade-off the derived form accepts.* It exempts the `jwks.url` host from the private-address
refusal in *every* deployment -- not only one whose IdP lives on a private network. A public-IdP
deployment is affected too: a public IdP hostname that resolves to an internal address (a DNS
change, a split-horizon resolver, a poisoned cache) was refused before and is now dialled. The
exemption is bounded to the one host the operator already named as the key endpoint, and it widens
nothing else: certificate trust is unchanged, so chain validation and hostname verification
(<<gw-06>>) still refuse an endpoint that cannot prove it is that host. The trade-off was accepted
deliberately in exchange for a private IdP working without a second declaration of a host the
configuration already carries. `EgressPolicy.secureDefault()` itself is unchanged upstream; the
gateway passes one host through the library's seam, so this is not a local reversal of an upstream
tightening (link:adr/0022-Upstream_security-hardening_default_changes_are_adopted_and_documented_never_locally_reverted.adoc[ADR-0022]).

*Residual.* No dedicated key restores the no-exemption posture for an `http` issuer. An operator who
wants a narrower allowance declares an explicit list, which is authoritative -- naming a host other
than the `jwks.url` host keeps the `jwks.url` host refused whenever it resolves privately -- and an
explicit list also pins the allowance against a later `jwks.url` edit. Operators should
egress-restrict the gateway and avoid pointing a topology alias at link-local/metadata ranges.

The `source: upstream` asset action (link:adr/0014-asset-serving-terminal-action.adoc[ADR-0014])
reuses this exact posture rather than opening a parallel fetch stack: a fixed, boot-resolved
topology upstream (never selected by request content), the `http`/`https` scheme allowlist,
`followRedirects(NEVER)`, and a bounded response size and read/connect timeout. A hostile asset
upstream can therefore neither redirect the fetch to an internal address nor be chosen by the
client; its response metadata is additionally overridden by the gateway-owned asset envelope
(fixed content type, stripped `Set-Cookie`, forced `no-store` for authenticated access).

*Status:* COVERED (design). No request-controlled upstream exists; the scheme allowlist is
enforced by the configuration validator; redirect-follow-off is a documented default; the
upstream asset source reuses the same fixed-topology + scheme-allowlist + no-redirect controls
(ADR-0014).

*Assertion.* No request input (path, header, body) can change the resolved upstream host; a
topology alias with a non-http(s) scheme fails boot; the data-plane client does not follow
upstream 3xx to a new host; the upstream asset source honours the same no-redirect and
fixed-topology guarantees and bounds the response size and timeout. On the JWKS leg, an issuer whose
explicit `allowed_egress_hosts` names a host other than its `jwks.url` host keeps its key set refused
against a private-address IdP, and the same gateway with only that key removed loads the key set
through the derived allowance (`JwksEgressMismatchIT`, against the native image, with that
single-variable control); the derived host (with a control on another `jwks.url` host), the
explicit-list-wins rule, the hostless-`jwks.url` refusal, and a real dial against the local
SAN-mismatched JWKS fixture that an explicit list naming another host refuses while the derived
allowance reaches it, are pinned by `TokenValidatorProducerTest`; the blank / `host:port` boot
refusals by `ConfigValidatorJwksEgressTest`.

[#gw-06]
=== GW-06 -- TLS/SNI fail-open, upstream cert verification, mTLS bypass

Failure modes: empty/unresolved SNI falls back to a *permissive* default (mTLS not required);
a verify flag is silently inverted; SAN matching ignores SAN type or over-matches wildcards.

*Evidence.* Traefik CVE-2026-32305 (fragmented ClientHello -> empty SNI -> permissive default
TLS config, mTLS bypassed). Traefik CVE-2025-66491 (ingress-nginx `proxy-ssl-verify: on`
mapped to Go `InsecureSkipVerify: true` -- verification *off* for ~5 months). Envoy
CVE-2022-21656 (SAN type ignored -> wrong-CA cert matches), CVE-2020-15104 (wildcard SAN
matches nested subdomains). KrakenD CVE-2026-39821 (punycode `xn--example-.com` normalizes
to `example.com` -> host-based rule bypass).

*Control.* Fail *closed*: empty/unresolved SNI must take the strictest policy or reject,
never a permissive default. Reassemble the full ClientHello before routing on SNI (the
`NetServer` front must not decide on a partial record). For any security-gating
boolean (mTLS require, upstream verify), *test the behaviour* -- a real handshake fails when
it must -- not merely that the flag parsed. Verify upstream certs by default. Normalize
security-decision hostnames with a spec-conformant, tested routine.

*Status:* PARTIAL. The accept-time SNI split and mTLS are delivered
(link:adr/0017-Accept-time_SNI_split_at_a_dedicated_front_listener_passthrough_relays_opaquely_at_L4_everything_else_terminates_internally.adoc[ADR-0017]).
*Upstream certificate verification is delivered and behaviour-tested end to end* on the terminated
egress leg
(link:adr/0040-Upstream_hostname_verification_is_a_global_egress-TLS_knob_bound_at_client_construction.adoc[ADR-0040]):
verification is on by default, the `egress_tls.upstream_verify_hostname` relaxation is bound at all
three *Vert.x* egress client-construction sites, and `egress_tls.upstream_tls_profile` binds trust
anchors through a fail-closed resolver that refuses an unbound, trust-all or anchor-free profile at
boot; both postures are reported at boot by `WARN ApiSheriff-118` / `ApiSheriff-119` rather than
taking effect silently. One further terminated-egress leg -- the asset-origin fetch -- is outside
every key and is recorded below as a scope limit rather than folded into the claim. The
*assert-behaviour-not-flag* discipline this entry demands is discharged *for that key specifically*
-- an integration-stack matched pair of gateway instances differing in exactly that one boolean makes
a real handshake fail on one leg and succeed on the other. The *JWKS* half is now *delivered and
behaviour-proven* as well
(link:adr/0041-The_JWKS_hostname-verification_knob_is_the_librarys_own_passthrough_and_its_sslContext_collision_is_refused_at_boot.adoc[ADR-0041]):
`egress_tls.jwks_verify_hostname` is read by the token-validator producer and passed through to the
JWKS client's own hostname-verification setting on every `http` source, on both the true and the
false path, so the gateway's posture does not follow an upstream default change; the relaxed posture
is reported at boot by `WARN ApiSheriff-120`; and the one incoherent combination -- the relaxation
together with an *`http`-sourced* issuer's per-issuer `jwks.tls_profile`, which supplies an SSL
context the relaxation cannot act on -- is *refused at boot* with a configuration error naming both
keys and the issuer, rather than silently ignoring one of them. The refusal is scoped to `http`
sources because that is where the collision exists: a `file`-sourced issuer opens no TLS connection,
so there is nothing for either key to reach on that leg. The *BFF OIDC back-channel* is now
*pinned and behaviour-proven* too
(link:adr/0045-The_BFF_OIDC_back-channel_posture_is_pinned_through_the_librarys_own_passthrough_under_peer_egress-TLS_keys.adoc[ADR-0045]):
`egress_tls.oidc_verify_hostname` is passed through to the identity-provider client's own
hostname-verification setting on every build, the true path included, `egress_tls.oidc_tls_profile`
supplies that client's trust through the same fail-closed resolution core as the JWKS profiles, the
relaxed posture and a named profile are reported at boot by `WARN ApiSheriff-125` /
`ApiSheriff-126`, and the relaxation together with a profile is *refused at boot* naming both keys.
An explicit-posture fitness function now stands guard over every leg: it fails the build when
production code constructs an outbound TLS client without, in the same class, calling that client's
posture method, so a seventh leg cannot land unbound the way the sixth once sat unenumerated. The
*fail-closed-on-empty-SNI* rule and *full-ClientHello reassembly before routing* remain unpinned (see
Gaps), which is why this entry stays PARTIAL -- the verdict is unchanged and only its reason has
narrowed, from three outstanding items to two.

*The six TLS-terminating egress legs, re-derived from source.* Every claim in this entry is scoped
by this enumeration, which is taken from the client-construction sites rather than copied from an
earlier list. It is hand-written and can drift like the list it replaces; the fitness function above
is the guard that does not depend on it being complete.

Plain-TCP dials negotiate no TLS and are not legs here: the ADR-0017 passthrough relay and the
loopback health probe.

*Assertion.* A fragmented/empty-SNI ClientHello does not reach a passthrough or a
no-client-cert default -- it is terminated under the strict policy or rejected; enabling mTLS
causes a real no-cert handshake to fail (behaviour test); a punycode host that normalizes to
a passthrough SNI is caught by the same collision rule. On the egress leg, a terminated dial to an
upstream whose certificate does not name the dialled host *fails the handshake by default*, and
succeeds only on an instance that declares `egress_tls.upstream_verify_hostname: false` -- both
directions asserted by a real dial rather than by reading the flag back. A third dial pins the
*scope* of that relaxation: against the relaxed instance, an upstream whose certificate chains to no
trusted anchor is *still refused*, so the two mechanisms are proven uncoupled. The same three-legged
shape now covers `jwks_verify_hostname`: a JWKS fetch from an identity provider whose certificate
does not name the dialled host *fails by default* and succeeds only with the key set to `false` --
both directions by real handshake against one server, one certificate, one issuer and one key set,
with the flag as the single difference -- and a third dial pins the scope, refusing an IdP whose
chain reaches no trusted anchor while the flag is off. A falsification check backs the pair: removing
the production passthrough turns the relaxed leg red. The BFF OIDC back-channel carries the same
shape for `oidc_verify_hostname`: discovery against a server whose certificate does not name the
dialled host *fails by default* and completes only with the key set to `false`, a document declaring
no `egress_tls` at all resolves to the refusing posture, a correctly named certificate under an
untrusted root is still refused with the flag off, and the flag set to `false` together with a named
`oidc_tls_profile` fails with a configuration error naming both keys while the same flag without a
profile assembles cleanly. Removing the production passthrough turns the relaxed leg red, and
removing the pre-builder refusal turns the collision test red. Removing a posture call from a
construction site -- the asset-origin fetch's explicit context, the BFF
back-channel's hostname setting, the Vert.x options' host verification -- turns the fitness function
red naming that class.

*Residual risk (accepted).* `egress_tls.upstream_verify_hostname: false` is an operator-selectable
relaxation of a control this entry exists to defend, so the residual risk is recorded rather than
described away. What it gives up is bounded to *hostname matching on terminated egress*: chain trust
is unaffected, a self-signed or untrusted-CA upstream is still refused, and passthrough -- relayed at
L4 and never decrypted -- cannot be reached by the setting at all. What remains is real: with the
relaxation in force, an attacker who can both redirect the gateway's upstream connection *and*
present a certificate that chains to an anchor the gateway trusts is no longer stopped by the name
mismatch. That is a materially harder position to reach than serving any certificate, and it is the
whole of what the knob concedes. Three properties bound the exposure and are the basis of the
acceptance: the default is `true` and an omitted key resolves to `true` rather than to the type
default, so the relaxation is never reached by silence; it is global and therefore *visible* in one
place in `gateway.yaml` rather than buried per route; and the scope claim is proven by the untrusted
dial above rather than asserted. The mitigation for an operator who needs a private-CA upstream is
`egress_tls.upstream_tls_profile`, which is a different key and does not require this one -- shipping
both together is what keeps the hostname knob from being misused as a general trust disable.

*Residual risk (accepted) -- the JWKS leg.* `egress_tls.jwks_verify_hostname: false` is the same
class of operator-selectable relaxation on a different leg, and it is recorded separately because
what it concedes is not the same thing. What it gives up is bounded to *hostname matching on the JWKS
back-channel*: chain trust is unaffected and an IdP whose certificate reaches no trusted anchor is
still refused. What remains is more serious than its upstream sibling, and saying so is the point of
recording it. The JWKS document carries the *signing keys every bearer token is validated against*,
so an attacker who can both redirect the gateway's JWKS fetch *and* present a certificate chaining to
an anchor the gateway trusts can serve their own key set -- and every token the gateway then accepts
is one they minted. On the upstream leg the equivalent position yields one proxied connection; here
it yields the authentication decision itself. Four properties bound the exposure and are the basis of
the acceptance: the default is `true` and an omitted key resolves to `true`, so the relaxation is
never reached by silence; it is reported at boot by `WARN ApiSheriff-120`, so it cannot reach
production unremarked; where the fetch may go at all is still bounded, so redirecting it is not
merely a DNS answer away -- and that bound is *two* mechanisms rather than one, each enforcing a
different half: token-sheriff's `EgressPolicy` SSRF egress guard is applied to the *checked JWKS
URI* before the initial fetch and before each background refresh, constraining which host that URI
may name, while a *cross-origin redirect hop* off that URI is what the HTTP handler's
`RedirectPolicy.sameOrigin()` rejects; and the scope claim is proven by the untrusted-chain dial
above rather than asserted. One qualification applies to the first half of that bound: the
`jwks.url` host itself is exempt from the guard's private-address refusal -- through the allowance
derived from `jwks.url`, or through an explicit list naming it (<<gw-05>>) -- so a DNS answer that
points *that* host at an internal address is not refused by the guard. Every host the allowance
does not exempt -- one neither derived from `jwks.url` nor named in an explicit list -- still is,
and the chain-trust check is what stands between such an answer and an attacker's key set. The
mitigation for an operator whose IdP is behind an internal CA is
`jwks.tls_profile`, which is a different key answering the chain-trust question -- and, on an
`http`-sourced issuer, the two are *mutually exclusive* and the combination is refused at boot, so an
operator cannot reach for both at once and end up with neither. A `file`-sourced issuer opens no TLS
connection, so it reaches no such collision and none is refused there -- and its `jwks.tls_profile`
has no TLS leg to act on either.

*Residual risk (accepted) -- the BFF OIDC back-channel.* `egress_tls.oidc_verify_hostname: false` is
the same class of operator-selectable relaxation on the sixth leg, and what it concedes is recorded
on its own terms. It gives up *hostname matching on the back-channel the gateway uses for discovery,
the pushed authorization request, the authorization-code exchange, refresh and refresh-token
revocation*; chain trust is unaffected and an identity provider whose
certificate reaches no trusted anchor is still refused. What remains is serious in a different way
from the JWKS leg: this connection *carries the client credential* -- the signed client assertion by
default, the client secret when `oidc.client_secret` is configured -- and the authorization codes,
and its responses are the discovery document, the `request_uri` of a pushed request and the token
responses sessions are built from. An attacker who
can both redirect the gateway's back-channel *and* present a certificate chaining to an anchor the
gateway trusts receives that credential and can answer the token exchange -- and a discovery
document it serves can name the endpoints the gateway dials next. What the captured credential is
worth differs by mode: a client secret is reusable until the operator rotates it, while a client
assertion expires sixty seconds after it was issued and never carries the
key that signed it (<<bff-18>>). The exposure is bounded by the same
properties as its siblings: the default is `true` and an omitted key or an omitted block resolves to
`true`; the relaxed posture is reported at boot by `WARN ApiSheriff-125`; the key is a peer of
`jwks_verify_hostname` rather than shared with it, so relaxing this leg relaxes neither the JWKS fetch
nor any proxied upstream; and the scope claim is proven by the untrusted-chain dial rather than
asserted. The mitigation for an identity provider behind an internal CA is `oidc_tls_profile`, which
answers the chain-trust question instead -- and the two are *mutually exclusive*, refused together at
boot, so an operator cannot reach for both and end up with neither. A named profile *replaces* the JVM
default trust store on this leg, so a profile holding only a private CA stops trusting public
authorities for the identity provider; that replacement is reported by `WARN ApiSheriff-126` rather
than left to be discovered.

*No deployment-activation instance is owed for the relaxation keys -- recorded, not a gap.* The hostname
keys are proven at the level they are asserted at, and those levels differ.
`upstream_verify_hostname` is proven by an integration-stack matched pair, so a *deployed descriptor*
turns the relaxation on and the `*ActivationWiringTest` family pins that it does.
`jwks_verify_hostname` and `oidc_verify_hostname` are proven at *unit* level against a local server,
through the producers' own configuration paths. The deployment-activation question a unit test cannot
reach -- does a shipped deployment actually turn this on? -- has nothing to assert for either: both
are secure-by-default *relaxations* that no shipped descriptor activates, so there is no deployed
document whose activation a wiring test could check. The two halves that are owed are present: the
behaviour half is the real TLS dial with its matched control, untrusted-chain leg and falsification
check, and the native binding half -- that the shared `egress_tls` record and its deserializer survive
the native build -- is exercised by the integration stack's `sheriff-config-egress-verify-{on,off}`
pair, which binds the same record through the same deserializer. The reasoning is recorded in
link:development/declared-limit-assertion-coverage.adoc#_the_egress_relaxation_keys_owe_no_activation_instance[Declared-limit
assertion coverage]; the condition that would reopen it is a shipped descriptor that starts declaring
either key.

*Scope limit (recorded, not a residual risk).* `egress_tls`'s *upstream* settings govern the three
Vert.x egress clients, `jwks_verify_hostname` the JWKS back-channel and the two `oidc_*` keys the BFF
back-channel; no key reaches the *asset-origin* fetch, leg 5 of the enumeration above: an asset
route with an `https` origin is fetched through a JDK `java.net.http.HttpClient` that carries no
`egress_tls` setting. Its construction site pins the JDK's own default context explicitly -- no
behavioural change, and the reason the fitness function can see the leg's posture at all. This is recorded separately from the residual risk above because it does not cut in the
dangerous direction. Hostname verification there is *fail-safe*: the JDK client checks the name
whatever the key says, so `upstream_verify_hostname: false` cannot weaken the asset leg, and no
unverified dial exists to defend. The *trust* half is the real limit -- `upstream_tls_profile`
replaces anchors on the three governed clients only, leaving the asset leg on the JVM default trust
store, so an asset origin behind a private CA *fails closed* rather than succeeding unverified, and
the deployment binds those anchors into the JVM trust store instead. Governing the JDK client would
need an `SSLParameters` / `SSLContext` seam that ADR-0040 deliberately did not scope; the limit is
stated in the operator documentation and in the model rather than left to be discovered.

*The BFF OIDC back-channel -- pinned, with a relaxation and a trust profile.* This leg was previously
recorded here as a scope limit with a countable remainder: it verified hostnames only because the
identity-provider client library defaulted to doing so, and nothing in this repository would have gone
red had that default moved. Both entries are closed rather than carried. The `ClientConfiguration`
built in `BffRuntimeProducer` -- what `DiscoveryResolver`, `ParClient`, the token-endpoint client and
`RefreshFlow` dial with, every one but discovery presenting the client credential (a signed assertion under `private_key_jwt`
by default, the client secret under `client_secret_basic` when one is configured) -- now receives
`egress_tls.oidc_verify_hostname` on every build, so the posture is the gateway's and an upstream
default change cannot move it
(link:adr/0022-Upstream_security-hardening_default_changes_are_adopted_and_documented_never_locally_reverted.adoc[ADR-0022]).
A named `egress_tls.oidc_tls_profile` supplies the leg's trust through the four fail-closed
refusals the JWKS profiles use -- an unbound name, a `trust-all` profile, an anchor-free profile and
unloadable material each fail boot naming `egress_tls.oidc_tls_profile`. The observables are the two
boot records, `ApiSheriff-125` and `ApiSheriff-126`, the collision refusal naming both keys, and the
fitness function, which goes red naming `BffRuntimeProducer` if the hostname call is removed. The
residual the relaxation concedes is recorded above.

*Residual (named, not guarded) -- the JVM-level hostname-verification switch.* The JDK system
property `jdk.internal.httpclient.disableHostnameVerification` turns off hostname checks on *every*
leg built on the JDK HTTP client -- the JWKS back-channel, the BFF OIDC back-channel and the
asset-origin fetch -- beneath every `egress_tls` key and beneath every construction site. A gateway
key set to `true` does not override it, no boot record reports it, and the explicit-posture fitness
function cannot see it, because it is a start-up flag rather than bytecode. The Vert.x legs 1-3 do
not use that client and are unaffected. It is carried as a named remainder rather than refused at
boot: a JVM start-up flag sits below the gateway's configuration surface and is the deployment's
responsibility, in the same way the default trust store triple is. It is recorded here and in the
fitness function's own documentation so that its absence from the gateway's guards is a stated fact
an audit can check the start command against, rather than a discovery.

*Threat -- trust-root REPLACEMENT of the default store.* Every entry above asks whether a dial
verifies. This one asks a prior question: *which anchors is it verifying against, and what stopped
being trusted when the deployment supplied them.* Both levers that set the gateway's default trust --
the JDK's `-Djavax.net.ssl.trustStore` triple and the Quarkus TLS registry's default trust bucket --
*substitute for the platform trust bundle wholesale rather than adding to it*. An operator who
supplies a store holding only their private certificate authority has silently stopped trusting every
public root the platform shipped. The failure mode is what makes it a threat rather than a
misconfiguration: nothing refuses at boot, and the loss surfaces later as an opaque handshake
rejection against an endpoint that used to work -- so the natural reading is "that endpoint broke",
not "we removed its anchor". The reverse direction is the security-relevant one and is worse,
because it is silent in both directions: a store assembled from the platform bundle *plus* an
attacker-influenced anchor widens what every terminated-egress leg accepts, with no key in
`gateway.yaml` recording that it happened. The two levers are also *independent*, so moving one and
not the other leaves half the outbound surface on the platform bundle and half on the supplied store
-- a split posture no single configuration file states.

*Control.* Report the effective store at boot rather than requiring it to be derived, and document
the one supported route with the replacement hazard stated before the recipe.

*Status:* DELIVERED as a reporting-and-documentation control, and it is worth being exact about what
that does and does not buy. `ApiSheriff-17` names, per tier, the trust source actually in force --
the legs holding a raw JDK `TrustManager` and the legs resolving through the Quarkus TLS registry --
and `ApiSheriff-122` fires alongside it whenever an operator-supplied store is in effect on either
tier, stating the replacement hazard and naming which half was left behind when the two tiers
disagree. The split-posture case is therefore reported in the one place an operator could not have
computed it from. Neither record carries a password, an alias or any anchor material. The operator
recipe -- including that the native, distroless image has no `update-ca-trust`, that the JDK triple
must arrive as command-line `-D` arguments, that `JAVA_TOOL_OPTIONS` is not honoured by a native
runner, and how to build a store that keeps the public roots *and* adds a private CA -- is in
link:configuration.adoc#_default_trust_store_replaces[Supplying a default trust store REPLACES the
platform bundle].

*Assertion.* A boot with no operator-supplied store reports the platform bundle on both tiers and
emits no `ApiSheriff-122`; a boot with a store on either tier emits it, and a boot where the two
tiers disagree says which half stayed on the platform bundle.

*Residual risk (accepted) -- the two tiers are independently settable.* The control reports the
posture; it does not constrain it. Nothing refuses a deployment that moves one lever and not the
other, and nothing inspects what is *inside* the supplied store -- a store missing the public roots,
or carrying an anchor it should not, boots exactly like a correct one. This is accepted rather than
closed because both levers are deployment-bound by
link:adr/0025-The_whole_server-TLS_surface_is_neutral_in_gatewayyaml_and_bound_by_exactly_two_seams.adoc[ADR-0025]
and refusing a legitimate single-tier deployment would be wrong; the gateway cannot know which
anchors a deployment *intended*. What bounds the exposure is that the state is no longer silent: the
divergence is named in the boot log by the record that exists for this hazard, so it is observable at
the moment it is introduced rather than at the moment it breaks something.

[#gw-07]
=== GW-07 -- Slowloris / connection & body-size exhaustion / decompression bombs

Slow partial requests pin workers; unbounded body buffering or decompression exhausts
memory; config-file expansion bombs exhaust boot memory.

*Evidence.* Apache httpd CVE-2007-6750 (Slowloris, pre-`mod_reqtimeout`). Envoy CVE-2022-29225
(decompressor with no output cap -> OOM). KrakenD-triaged Go stdlib DoS CVEs (CVE-2026-42504
MIME quadratic, CVE-2025-61723 PEM quadratic). The code review's own finding: the interim
`ProxyRoute` buffers unbounded request *and* response bodies with no timeout in a 512 MB
container.

*Control.* Bound everything an attacker inflates: inbound header/line-size limits, an
inbound idle/read timeout (slowloris), a max-in-flight admission cap, `max_body_bytes` as a
*streaming* counter (never buffer the body -- link:adr/0006-body-streaming-vs-httpresult.adoc[ADR-0006]),
and streamed responses (never materialized). The gateway is an *opaque* passthrough -- it does
not decode `Content-Encoding`, so it is not itself a decompression-bomb target, but it must
still cap body bytes. Explicit YAML `StreamReadConstraints` are applied at config load.

*Status:* PARTIAL. Streaming + the `max_body_bytes` counter is ADR-0006 + pipeline
stage 6; edge limits, idle timeout, admission cap and graceful drain are delivered as the
edge-hardening bounds; YAML limits are applied at config load. The individual controls are
delivered, but the assertion below is not yet pinned across the whole set, which is what keeps
the entry at PARTIAL rather than COVERED.

*Assertion.* A slow-drip request is evicted at the idle timeout; a body exceeding
`max_body_bytes` aborts mid-stream without full buffering; concurrent large requests do not
grow heap without bound (admission cap holds); an oversized/alias-bomb config fails boot
gracefully.

[#gw-08]
=== GW-08 -- HTTP/2 & gRPC abuse (Rapid Reset, CONTINUATION flood, downgrade smuggling, h2c)

Cheap multiplexed actions become expensive server work: open-then-`RST_STREAM` loops,
endless CONTINUATION header frames, h2->h1 downgrade Content-Length smuggling, forwarded
`Upgrade: h2c` bypassing controls.

*Evidence.* CVE-2023-44487 (HTTP/2 Rapid Reset -- record DDoS, hit nginx/Envoy/Tomcat/Jetty/
Go/gRPC/HAProxy/Node). Node CVE-2024-27983 and the CERT VU#421644 CONTINUATION-flood set
(httpd CVE-2024-27316, Tomcat CVE-2024-24549, Envoy CVE-2024-27919, nghttp2 CVE-2024-28182,
Go CVE-2023-45288). CVE-2019-9513 (PRIORITY flood). Netty CVE-2021-21295 (h2->h1 CL smuggling).

*Control.* Rate-limit stream *creation and reset* per connection (not only concurrent
streams); bound total CONTINUATION/header frame size and count per stream and drop
over-limit connections; re-derive Content-Length on any downgrade; never forward client
`Upgrade`/`Connection` (h2c) headers to the backend. API Sheriff terminates h2 via ALPN and
proxies gRPC over upstream h2 -- both the terminated and forced-h2-upstream sides
inherit this requirement.

*Status:* GAP. Quarkus/Netty ship some Rapid-Reset mitigation, but stream-reset rate limiting
and CONTINUATION bounds must be verified and pinned, and h2c-upgrade non-forwarding asserted.
This spans both the terminated h2 edge and the forced-h2 gRPC upstream.

*Assertion.* A Rapid-Reset / CONTINUATION-flood load against the gateway does not exhaust
CPU/memory (bounded, connection dropped); client `Upgrade: h2c`/`Connection` headers are not
forwarded upstream; an h2->h1 path re-derives framing.

[#gw-09]
=== GW-09 -- WebSocket cross-site hijacking (CSWSH) / missing Origin check on upgrade

The WS handshake is an HTTP Upgrade the browser sends with ambient cookies, and the
Same-Origin Policy does *not* restrict cross-origin WebSocket connections -- only server-side
`Origin` validation does. Accept-any-origin upgraders let an attacker page open an
authenticated socket in the victim's context (CWE-1385).

*Evidence.* Nginx-UI CVE-2026-34403, Mailpit CVE-2026-22689, Dozzle CVE-2026-44985 *(2026,
GHSA-sourced; CVSS enrichment pending)* -- all `CheckOrigin -> true` on cookie-authenticated
WS endpoints.

*Control.* Validate `Origin` server-side on the upgrade handshake against an allowlist
(reject unknown origins) *before* the relay is established. The handshake runs the full
pipeline incl. auth, and `OriginValidationStage` checks the `Origin` against the route's
`websocket.allowed_origins` by exact match on every route that declares one. A
`protocol: websocket` route whose effective auth is `require: bearer` or `require: session`
is refused at boot unless it declares a non-empty allowlist, so an authenticated WebSocket
route always has one; only a `require: none` route may omit it
(link:adr/0015-websocket-origin-failclosed-allowlist.adoc[ADR-0015]). The session cookie is
`SameSite=Lax` in both session modes, a fixed attribute with no configuration key, so the
socket is not authenticated by ambient cookies alone.

*Status:* COVERED. The boot requirement is pinned for both authenticated postures by
`ConfigValidatorTest.WebSocketOriginAllowlist`: `shouldRefuseAbsentAllowlist` and
`shouldRefuseEmptyAllowlist` refuse a bearer and a session route, `shouldAcceptPopulatedAllowlist`
admits both, and `shouldAcceptUnauthenticatedRouteWithoutAllowlist` is the matched control for
`require: none`. The handshake check is pinned by `OriginValidationStageTest`; it does not read
the auth posture, so it holds a session route to its allowlist exactly as it holds a bearer
route. `SameSite=Lax` is pinned by `SessionCookieCodecTest.SetCookie.shouldEmitHardenedCookie`
(server mode) and `SealedSessionCookieCodecTest.SetCookieHeader.shouldEmitHardenedAttributes`
(cookie mode).

*Assertion.* A WebSocket upgrade with a foreign `Origin` on a session-authenticated route is
rejected before any upstream dial; only allowlisted origins complete the handshake; a bearer
or session WebSocket route without a non-empty allowlist fails the boot.

=== GW-10 -- Control-plane exposure / default credentials / config-driven code execution

An exposed admin API, a functional default credential, or config-driven scripting turns any
control-plane reachability into full compromise.

*Evidence.* APISIX CVE-2020-13945 (built-in default admin token
`edd1c9f0...`), CVE-2022-24112 (Admin-API IP bypass -> Lua `script` RCE), CVE-2021-45232

*Status:* ELIMINATED (by design -- immutability, no admin API, no scripting). Management-port
separation is in `application.properties`; a single auth choke-point (the pipeline) avoids

=== GW-11 -- Pre-auth / config input handling (injection, path-from-ID, XML round-trip)

Management-plane and pre-auth endpoints, and any path/identifier built from input, are the
softest targets: SQLi, path traversal from a client-supplied ID, template/HTML injection,
SAML XML round-trip.

*Evidence.* Tyk CVE-2023-42283 / CVE-2023-42284 (two blind SQLi from one missing
parameterization on analytics `api_id`/`api_version`), CVE-2021-23357 (APIID -> filesystem
path traversal), CVE-2021-23365 (SAML XML round-trip auth bypass in the identity broker).
Gravitee CVE-2019-25075 then CVE-2022-38723 (the *same* registration path-traversal, patched
twice -- incomplete first fix).

*Control.* API Sheriff has *no datastore* (no SQL surface -- ELIMINATED), *no registration/
management endpoints*, and does *not do SAML* (OIDC only, via the validated token-sheriff
stack). The residual surface is config-load input: never build a filesystem path from an
unvalidated value, canonicalize-then-confine config file references to the config root, and
enforce the secrets rule on the *pre-substitution* scalar. The Gravitee
double-patch is the lesson for the validator: close the whole *class* (canonicalize-then-
contain + a full traversal/encoding regression corpus), not one spelling.

The asset-serving action (link:adr/0014-asset-serving-terminal-action.adoc[ADR-0014]) *reopens*
this class with a second client-supplied file-path surface: the request-path remainder of a
`source: directory` or `source: upstream` asset route. Both sources close it through one shared
`PathConfinement`, applied *before* the backing store is touched: `cui-http`'s
`URLPathValidationPipeline` canonicalizes the untrusted remainder (rejecting encoded traversal,
encoded slash, mixed/double encoding, `%00`, overlong UTF-8, backslash, and `..;/`), then the
gateway confines the normalized path under the configured root/prefix and rejects any escape.
Honouring the Gravitee lesson, a generator-driven traversal/encoding regression corpus

spelling.

*Status:* COVERED. Part of the failure class is eliminated outright -- no SQL, no SAML, no
management endpoints -- and the surfaces that do exist are owned by code: config-path handling
and the secrets-on-raw-value rule are enforced by the configuration validator; the
asset-serving file-path surface (ADR-0014) is confined by the shared `PathConfinement` and
proven by the traversal/encoding corpus. The entry is COVERED rather than ELIMINATED because
those surviving surfaces carry the live assertion below.

*Assertion.* No SQL or SAML code path exists; config file resolution cannot escape the config
directory via `..`/encoding; a full traversal corpus is rejected; asset file resolution -- for
both the local-directory and upstream sources -- cannot escape the configured root/prefix via
`..`/encoding, proven by the same full corpus (`PathConfinementTest`); the secrets rule is
evaluated on the raw scalar (a literal secret is rejected even if it would substitute to a
valid value).

[#gw-13]
=== GW-13 -- Open redirect through a gateway-answered redirect (CWE-601)

A redirect answered *by the gateway* carries the gateway's own origin as its credential: a link to
`https://gw.example.com/moved` looks trustworthy, and whatever `Location` it answers with is where the
browser goes. If that target can name another origin -- an attacker-chosen one, or one reached
through a spelling the configuration reader did not recognise as foreign -- the gateway becomes a
phishing and token-leak relay (CWE-601).

*Evidence.* The failure class is the URL-parser disagreement the WHATWG URL Standard codifies for
the special schemes: a leading `//` is scheme-relative and names a host, a backslash is parsed as
`/` so `/\evil.example` is `//evil.example`, and user-info disguises the real host
(`https://trusted@evil.example`). The same redirect-target laxity is the class behind the
`redirect_uri` advisories in <<bff-01>> (Keycloak CVE-2024-8883, CVE-2026-3872), there on the IdP
side. No gateway-product CVE is cited for this entry: the surface is new in API Sheriff, and the
entry is recorded from the parser behaviour before it ships rather than after.

*Control.* The `redirect` terminal action
(link:adr/0014-asset-serving-terminal-action.adoc#amendment-a1[ADR-0014 Amendment A1]) takes no
target from the request: `location` is fixed configuration, written verbatim, with no placeholder --
only the raw query is appended under `keep_query`. The configuration validator reviews every
`location` *once, at boot*, and refuses the boot rather than serving a doubtful value:

* without the explicit `allow_external: true` opt-in, `location` must be a gateway path -- exactly one
  leading `/`, no backslash, no percent-encoded `/` or `\` (`%2F`, `%5C`, either case), no dot-segment
  (`.`, `..` or their `%2E` spellings), printable ASCII without whitespace or control characters (a
  CR/LF would forge a response header), and no `#` together with `keep_query`. The path is
  additionally put through cui-http's `URL_PATH` validation pipeline, which adds the classes a
  single-decoding spelling test cannot see: double encoding (`/%252F%252Fevil.example`), traversal
  reached through it, null bytes, overlong and malformed UTF-8, unicode-normalising escapes, and a
  1024-character length cap;
* with the opt-in, it may additionally be an absolute `http`/`https` URI with a non-empty host and no
  user-info; every other scheme (`javascript:`, `data:`, ...) stays refused, and the opt-in is
  reported at boot by `WARN ApiSheriff-128`, naming the route and never the target;
* refusal messages echo the value through the injection-safe renderer (CWE-117, see <<gw-12>>).

*Control -- the query is same-origin only.* The review above establishes that the *target* is a value
the operator wrote down. It establishes nothing about the *query*, which arrives with the request and
is therefore attacker-supplied. `keep_query` together with `allow_external` would opt every inbound
parameter out of the gateway origin: a request to `/go?code=...&state=...` produces a `Location` that
plants those values in the third party's access log, `Referer` chain and page analytics
(CWE-201 / CWE-598). The pair is refused at boot rather than warned about -- a warning cannot be
acted on per request, and there is no reviewable value to judge. Each flag alone is unaffected: a
gateway path may keep the query, and a fixed external target may be declared without it.

Two further properties bound what a redirect route discloses: the redirect is answered only *after*
authentication, so under an authenticated anchor an anonymous caller is challenged before any
`Location` is revealed; and the action is refused on every protocol but `http`, and together with an
`upstream` or `asset` block, so no configuration reaches it silently.

*Control -- the rewritten upstream `Location`.* The `redirect` action is not the only `Location` the
gateway authors. A route with `upstream.rewrite_location: true`
(link:user/endpoint-routes.adoc#_rewrite_location[Rewriting upstream `Location` headers]) replaces an
upstream `Location` pointing inside its own upstream with a *gateway-relative* value, and that value
carries the gateway origin exactly as a configured one does. The target is not attacker-supplied --
it comes from the configured backend -- but its *spelling* is, in every scenario where the backend
reflects a request parameter into its own redirect, and stripping the upstream authority is what makes
a spelling dangerous that was not: an absolute URI binds its authority before its path, so
`https://app1.internal:8443/%5Cattacker.com` keeps the browser on the upstream, while the mapping
`/%5Cattacker.com` is read as `/\attacker.com` once decoded and therefore, per the same WHATWG
backslash rule above, as `//attacker.com`. The rewrite therefore applies *the refusal set of the boot
review* to the candidate path and to the computed mapping alike, relaying the header unchanged rather
than mapping it: no leading `//`, no percent-encoded `/` or `\` (`%2F`, `%5C`, either case), no
dot-segment (`.`, `..` or their `%2E` spellings), and nothing the cui-http pipeline refuses -- a
literal backslash, double encoding, a null byte, a malformed escape, a path past the length cap. The
encoded-slash arm additionally closes a confinement hole the dot-segment test alone cannot see, since
that test splits on the literal `/`: `/app1/a%2f..%2f..%2fadmin` is one segment to it and decodes
outside the match key. The refusal is never a normalization -- the value is emitted to the browser,
so confinement proved against a normalized string the browser never sees would bound nothing. The
query and fragment are outside the refusal and carried verbatim: a separator after the `?` or `#`
cannot form an authority.

*Control -- one refusal set, not two.* "The refusal set of the boot review" above is a shared
implementation rather than a maintained agreement: both paths call
`http.LocationPathReview.refusalReason`, so the boot review of a configured target and the per-request
rewrite of an upstream one cannot drift apart. That class is also where the split between the library
and this project's own tests is decided, and the split is empirical rather than stylistic. cui-http's
`URL_PATH` pipeline is a *canonicalizer*: for the traversal family it throws only when the result
would escape above the root, and otherwise returns a fixed value. It therefore *admits* -- by
normalising them away -- `/%5Cattacker.com`, `/a/x%2fy`, `/%2f%2fattacker.com`, `/a/./b`, a `..` run
that stays inside the root, and a leading `//`. Every one of those is a value this gateway must
refuse rather than fix, because it is emitted verbatim and the client resolves the string it
receives. The pipeline is consulted for whether it *threw*, never for the value it returns, and the
spellings above keep their own tests. `LocationPathReviewTest.CuiHttpCoverageBoundary` asserts that
boundary directly -- that the library admits each spelling and that the review refuses it anyway --
so a future cui-http that starts refusing one turns the redundancy into a failing test instead of
silent duplication.

*Control -- the answer is not stored.* A redirect answer is an ordinary cacheable response, and `301`
and `308` are cacheable by default under RFC 9111 §4.2.2 heuristic freshness. Because the redirect is
answered after authentication, a `Set-Cookie` an earlier stage produced -- a re-sealed or rotated
cookie-mode session -- rides on it, so a shared cache between the client and the gateway could store
one client's session cookie and replay it to another (CWE-524 / CWE-525). The gateway therefore emits
`Cache-Control: no-store` on a redirect answer whenever the route's effective auth requires
authentication *or* any `Set-Cookie` is accumulated -- the same governance the asset terminal action
already applies to `AccessLevel.AUTHENTICATED` content. A public, cookie-less redirect stays
cacheable, which is what a settled `301`/`308` move is for. The header is not a `security_headers`
key, so `header_modes` does not reach it, and it is written after the stage headers so none can
displace it.

*Status:* COVERED. The review is boot-time configuration validation with a table-driven refusal
corpus (`ConfigValidatorRedirectTest`: `//host`, `/\host`, `\\host`, `/%2F%2Fhost`, `/%5chost`,
`/a/../b`, the double-encoded `%252F`/`%252e` spellings and an over-cap path, an external URI without
the opt-in, `javascript:` and user-info with it, `#` with
`keep_query`, the `keep_query` + `allow_external` pair, plus the accepted forms and each flag alone);
`LocationRewriterTest` carries the same refusal corpus for the rewritten upstream `Location`
(`/\host`, `/\\host`, `%5C`/`%5c`, `%2F`/`%2f`, a mixed spelling, the double-encoded and malformed
escapes, and each of them on an absolute
upstream URI -- the form in which the mapping would otherwise *create* the cross-origin value --
against the matched positive controls that must still map: an ordinary path, an absolute URI with an
ordinary path, the neighbouring non-separator encodings `%5B`/`%5D`/`%2D`, and an encoded separator in
the query or fragment);
`LocationPathReviewTest` pins the shared review itself, including the cui-http coverage boundary
described above;
the native boot refusal of an external location without the
opt-in is exercised by `verify-invalid-config-fails.sh`; `RedirectStageTest` pins the cacheability
verdict on both its conditions and on the public control; `GatewayEdgePipelineTest` asserts the
`no-store` on an authenticated redirect and its absence on a public one over a live server; and
`RoutingAndResponseHeadersIT` asserts the
served redirect against the native image, including the query kept under `keep_query` and no upstream
contact.

*Residual risk (accepted).* `allow_external: true` hands the operator a legitimate external redirect,
and with it the ability to point clients at another origin. The review proves the target is a
well-formed `http`/`https` URI; it cannot prove the operator meant that host. The exposure is bounded
by it being an explicit per-route opt-in, visible in the endpoint file and announced at every boot by
`ApiSheriff-128`, and by the target -- and now the whole `Location`, since the query hand-off is
refused -- being fixed configuration an attacker cannot influence through the request.

*Assertion.* Every refused spelling above fails the boot with the value escaped in the message; a
gateway path and, under the opt-in, a well-formed `http`/`https` URI boot; `keep_query` together with
`allow_external` fails the boot naming both keys and never the target, while either flag alone boots;
an upstream `Location` whose path carries any of those spellings is relayed unchanged rather than
rewritten, while a path free of them -- including one whose query or fragment carries an encoded
separator -- still maps onto the route's match key;
a redirect answer carries
exactly the configured status and `Location` (the raw query appended only under `keep_query`) and
causes no upstream request; an authenticated or cookie-bearing redirect answer carries
`Cache-Control: no-store` and a public cookie-less one does not; an unauthenticated request to a
redirect route under an authenticated anchor is challenged and receives no `Location`.

[#gw-14]
=== GW-14 -- Response security-header floor weakened (origin precedence, anchor replacement)

The gateway-owned response security headers -- `Strict-Transport-Security`,
`X-Content-Type-Options`, `X-Frame-Options`, `Content-Security-Policy` -- are a *floor* only if the
value on the wire is the gateway's. Two mechanisms let a configured header end up absent or weaker
than the operator believes: an *upstream* sending the same header with a more permissive value, and
a *narrower scope* replacing a wider one without carrying all of its headers along.

*Evidence.* NGINX's `add_header` is the canonical instance of the second mechanism and the cautionary
tale ADR-0007's research recorded: a `location` declaring any `add_header` inherits *none* of the
`server`-level ones, so adding one header at a lower level silently drops HSTS and the rest. The
first mechanism is the documented proxy behaviour of relaying origin headers verbatim. Neither is
tied to a single CVE; both are configuration-shaped, which is why the control is stated rather than
inherited.

*Control.* Two decisions, each explicit rather than implied
(link:adr/0007-anchor-scoped-policy.adoc#amendment-a1[ADR-0007 Amendment A1]):

* *Origin precedence is `set` by default.* A gateway-owned header overwrites the origin's value
  unless the block's `header_modes` names that header `default`, and an omitted `header_modes` block
  is the overwrite behaviour. `default` is a per-header, per-block opt-in; a mode for a header its
  block does not enable is refused at boot, and a gateway-authored response (rejection, redirect,
  asset, preflight) always carries the configured value.
* *Anchor replacement is wholesale and stated, not merged silently.* An anchor block replaces the
  global block for its routes -- the same no-merge rule as every anchor policy block -- and the
  operator documentation states the consequence at every place the key is described: a header the
  anchor block omits is absent under that anchor. Responses before route selection keep the global
  block, so no pre-route rejection loses it.

A third mechanism is closed at the boundary rather than here: because the anchor block is resolved
*per selected route*, an address inside an anchor namespace that a route *outside* the anchor answers
carries that route's block, not the anchor's -- the header floor escaped by routing rather than by
precedence or by replacement. The anchor-namespace coverage rule (<<gw-01>>) refuses that
configuration at boot, so "a routed response carries exactly its anchor block" extends beyond the
addresses the anchor's own routes happen to name.

That closure depends on what the coverage rule accepts as covering, and the rule requires the member
to match its whole namespace rather than merely to name it: a member narrowed on `match.methods`,
`match.host` or `match.headers` is not coverage, precisely because the complement it does not match
would fall through to the enclosing route and carry *that* route's header block. The rule and the
drift guard on the dimension set are described under <<gw-01>>; they bound this mechanism's closure
identically.

`content_security_policy` values are refused at boot when blank or carrying a CR, LF or other control
character, on every block, so the header cannot become an injection vector (<<gw-03>>).

*Status:* COVERED. `SecurityHeadersStageTest` and `ResponseStageTest` pin the map routing and the
set/default relay; `ConfigValidatorTest` pins the orphan-mode and CSP refusals; and
`RoutingAndResponseHeadersIT` asserts against the native image that the anchor block applies only
under its anchor, that it drops the global HSTS (wholesale), that a pre-route `404` and a preflight
keep the global block, that `default` keeps an origin `X-Frame-Options` and fills an absent one, and
that `set` overwrites an origin `Content-Security-Policy`.

*Residual risk (accepted) -- `default` mode.* Under `default` the upstream decides the header's final
value, including a weaker one: a permissive `Content-Security-Policy` or a laxer framing policy
passes through unchanged. That is the purpose of the mode -- a frontend keeping its own policy while
the gateway supplies a floor for responses that send none -- so it is accepted, bounded by being a
per-header opt-in the operator writes for a named block, never a default.

*Residual risk (accepted) -- wholesale anchor replacement.* An anchor block that omits a global header
drops it for that anchor's routes, and the boot does not warn about it: the dropped header is a
consequence of the block the operator wrote, not an ambiguity. It is accepted because a merge would
make an anchor unable to *remove* a global header and would reintroduce the merge-order ambiguity
ADR-0007 forbids; it is bounded by the documented rule and by the integration assertion that the
replacement is observable on the wire.

*Assertion.* A routed response carries exactly its anchor block (a global header the anchor omits is
absent); a pre-route rejection and a CORS preflight carry the global block; under `set` an origin
value is overwritten, under `default` it is kept and the configured value fills an absent one; a
gateway-authored response carries the configured value under either mode; an orphan mode and a
control-character CSP fail the boot.

== OAuth / OIDC / BFF failure catalogue

These bite the BFF variants (Variants 2 and 3). The confidential-client *engine*
(`token-sheriff-client`) and the *validation* library (`token-sheriff-validation`) own most
of the cryptographic and flow legs; API Sheriff owns the browser-facing side. Each entry
notes which side owns the control. Normative anchors: *RFC 9700* (OAuth 2.0 Security BCP,
Jan 2025), *OAuth 2.0 for Browser-Based Apps BCP*, *RFC 9207* (`iss`), *RFC 9449* (DPoP),
*RFC 9126* (pushed authorization requests), *RFC 7523* (`private_key_jwt`), *OIDC Core*,
*OIDC Back-Channel Logout 1.0*. The client requirements of the *FAPI 2.0 Security Profile* are
tracked row by row in link:fapi_status.adoc[FAPI 2.0 Status]; the entries below cite a clause where a
control answers one, and make no conformance claim.

[#bff-01]
=== BFF-01 -- `redirect_uri` validation (exact match)

Lax redirect-URI matching (wildcard, subdomain, path-prefix, traversal, parser discrepancy)
delivers the authorization `code` to an attacker endpoint -> account takeover.

*Evidence.* Keycloak CVE-2023-6927 (wildcard bypass), CVE-2024-8883 (`localhost` valid-URI ->
arbitrary redirect), CVE-2026-3872 (`..;/` traversal past the allowed path). pixiv HackerOne
#1861974 (path traversal leaked codes). RFC 9700 §2.1/§4.1: *exact string match*, no
wildcards.

*Control.* The BFF redirect URI is a single fixed server endpoint -- trivially exact-matchable.
Register it statically, never templatize/wildcard it, canonicalize-and-reject
`..`/`..;`/encoded traversal before matching. Engine constructs the authorization request;
gateway config supplies the exact URI.

*Status:* COVERED. Reserved-path exact-match registration; one fixed `oidc.redirect_uri`.

*Assertion.* Wildcard/subdomain/path-prefix/`..;/` variants of the redirect URI are all
rejected; only the exact registered URI is accepted.

[#bff-02]
=== BFF-02 -- `state` / CSRF on the callback

Without an unguessable, session-bound, single-use `state`, the callback can't prove it
matches a flow this browser started -> login CSRF / code injection.

*Evidence.* HedgeDoc GHSA-6wm6-3vpq-6qvv, PolarLearn GHSA-fhhm-574m-7rpw (missing `state` ->
login CSRF). RFC 9700 §4.1.

*Control.* The engine's `FlowContext` generates the `state` (32-byte SecureRandom) and
verifies it constant-time on callback, fail-closed -- but it is an *in-memory DTO the gateway
must persist and discard*: single-use is a *caller contract*, not enforced by the type. The
*pending-authorization record* is the gateway's job: persist the `FlowContext`,
short TTL, add the return-URL (the engine's DTO has none), and *bind it to the initiating
browser* with a short-lived `HttpOnly` `__Host-` binding cookie (a record retrievable by
`state` alone can be delivered to a *different* browser -- the callback must require the
matching binding cookie, not just a valid `state`). PKCE does not replace login-CSRF
protection -- keep both.

*Status (mode-split -- the single-use guarantee differs):*

* *Server mode:* COVERED. The record is server-side; the gateway *discards it on first
  callback* (true single-use) and the binding cookie ties it to the browser.
* *Cookie mode:* PARTIAL (accepted risk). The record travels only in the sealed short-lived
  `__Host-` login cookie -- there is no server store to mark it consumed -- so within the
  cookie's short TTL a captured login cookie *could* be replayed. Mitigation and accepted risk:
  the TTL is minutes, the cookie is `HttpOnly`+`Secure`+`__Host-` (not JS-readable, HTTPS-only,
  origin-locked), the browser binding still holds, and the exposure window is the login round
  trip only. This is an explicit risk acceptance of the stateless variant -- choose server mode
  if strict single-use of the login step is required.

*The return URL is bound to the gateway origin, and only the query is carried along.* A
session-route navigation records its return URL as the canonical request path plus the raw
query, byte for byte -- the query is re-emitted from the raw wire pairs the security filter
already validated (ADR-0047), never re-encoded or reordered, so the page the user lands on is the
page they asked for. The target is still same-origin checked on the way into the pending record:
a gateway path with a single leading `/`, or an absolute URL on the `oidc.redirect_uri` origin.
An absent, cross-origin or unparseable target falls back to `oidc.login.default_return_url` (or
`/`), and that fallback is itself refused at boot unless it passes the same check
(`PendingAuthorizationRecord.sameOrigin`, the single predicate for both). Preserving the query adds
no redirect surface: it can change which gateway page loads, never which origin.

*Assertion.* A callback with a missing/foreign/re-used `state` is rejected; the record is
single-use (a replayed callback fails); return-URL is same-origin validated (no open
redirect); a navigation to `/x?tab=a&b` records exactly `/x?tab=a&b`; a cross-origin
`oidc.login.default_return_url` fails the boot.

=== BFF-06 -- JWT / ID-token validation (alg confusion, `alg:none`, `kid`, aud/iss/exp)

The verifier honors the token's own `alg`/`kid` (RS256->HS256 key confusion, `alg:none`,
`kid` path/SQL injection) or skips audience/issuer/expiry.

*Evidence.* `jsonwebtoken` CVE-2015-9235 (`alg:none`) / CVE-2016-10555 (RS256->HS256)
*(IDs unverified; the class is canonical)*, CVE-2022-23539 (unrestricted key type). Java
CVE-2022-21449 "Psychic Signatures" (ECDSA `(0,0)` accepted -- forge any ES256 JWT/ID

`aud`/`azp`/`exp`/`nbf`/`iat`(+skew)/`sub` are validated by the pipeline. Keys come only from
configured/discovered JWKS (BFF-07). The gateway's residual is to *configure* the expected

=== BFF-07 -- JWKS handling (`jku`/`x5u` SSRF, rotation races, unbounded fetch)

Trusting a per-token key URL fetches attacker keys (and is an SSRF primitive); naive
"refresh on unknown `kid`" is a DoS/amplifier; no cache caps.

*Evidence.* `jku`/`x5u` header-injection auth-bypass writeups (PortSwigger JWT). Rotation-race
and unbounded-fetch discussions.

*Control.* `token-sheriff-validation` owns this and is strong: token-header `jku`/`x5u`/`jwk`
are ignored (they appear nowhere in its key resolution; embedded `jwk` is actively rejected);
`HttpJwksLoader` fetches only from the configured/discovered endpoint behind an `EgressPolicy`
that blocks internal/metadata ranges on the initial fetch *and every background refresh*
(DNS-rebinding-safe, GW-05 tie-in); it caches with a TTL, keeps a bounded rotation grace
window, and `getKeyInfo(kid)` never triggers an on-demand fetch -- so a flood of unknown
`kid`s cannot drive a fetch storm. Gateway residual: the egress policy is widened only host by host,
through the library's own `allowedEgressHost` seam, fed from the per-issuer
`token_validation.issuers[].jwks.allowed_egress_hosts` list in `gateway.yaml` (see <<gw-05>>). When
the list is absent or empty the gateway derives exactly one entry, the host of the issuer's own
`jwks.url`; a non-empty list is authoritative, host-exact and never merged with that host; a blank or
`host:port` entry, and a hostless `jwks.url` with no list, are refused at boot. The derived default
is an accepted trade-off, recorded in full under <<gw-05>>: it exempts the `jwks.url` host from the
private-address refusal in every deployment -- a public IdP host that resolves to an internal address
included, which was refused before and now is not -- while certificate trust (chain and hostname
verification) is unchanged. No dedicated key restores the no-exemption posture for an `http` issuer;
an operator who wants it declares an explicit list, which is authoritative. The key set itself is
still fetched only from the configured `jwks.url`; the allowance decides which *addresses* that one
URL may resolve to, never which URL is fetched.

*Key-set availability is the gateway's -- readiness and a bounded retry.* The library's own
JWKS-readiness health check does not serve this gateway: its extension beans are excluded
(link:adr/0027-The_token-validation_extensions_unqualified_beans_are_excluded_not_accommodated.adoc[ADR-0027]),
and its loader status is not truthful after a failed first fetch -- an HTTP loader whose first fetch
failed never reports `OK`, even once a background refresh has installed keys, and its issuer cache
re-admits an issuer only on `OK`. A gateway that booted before its identity provider answered
therefore reported ready while it could validate no token, and retried the fetch only after a whole
refresh interval. The gateway now installs its own loader for every issuer through the library's
public loader seam. The wrapper records the outcome of each load attempt itself and reports `OK`
exactly when a key set is loaded, which also repairs the library's re-admission path. Readiness is
`DOWN` while any configured issuer has no key set, with a non-disclosing payload -- a fixed `jwks`
status token and the bounded counts `issuers` / `issuers_loaded`, never an issuer name, URL or host --
so an orchestrator holds traffic back from an instance that would reject every bearer token. A failed
load is retried after 1 s, doubling per attempt and capped at 30 s (never above the refresh
interval), driven by a scheduler only: neither bearer requests nor the readiness probe can trigger a
fetch, and at most one attempt is in flight per issuer, so the retry cannot be turned into a fetch
storm. Each scheduled retry logs `WARN ApiSheriff-129` and a recovery logs `INFO ApiSheriff-18`,
both carrying the issuer's configured name only. The upstream defect -- no `UNDEFINED` to `OK`
transition -- is reported to the library rather than depended on.

*Status:* COVERED (validation lib, fail-closed, SSRF-guarded with the `jwks.url` host exempted as
recorded under <<gw-05>>; key-set availability owned by the gateway's loader wrapper and readiness
check).

*Assertion.* A token-supplied `jku`/`x5u` is ignored; JWKS is fetched only from the
configured endpoint; a flood of unknown-`kid` tokens does not cause unbounded outbound
fetches; rotation across overlapping keys keeps validation working. Readiness is `DOWN` while an
issuer has no key set and names no issuer, URL or host; a status read issues no fetch; a failed
first fetch is retried on the bounded backoff and the key set arrives well inside the refresh
interval (`RetryingJwksLoaderTest`, `SheriffMetricsTest`); against the native image, a gateway whose
identity provider appears only after boot reports `DOWN`, turns `UP` within a minute of the provider
appearing, and then accepts that provider's token (`JwksLateIdpReadinessIT`). The egress allowance
is proven in both directions against the native image: an explicit list naming another host keeps
the key set refused and a real token rejected `401`, and the same gateway with only that key removed
loads the key set through the derived allowance and accepts the same token (`JwksEgressMismatchIT`).

[#bff-08]
=== BFF-08 -- Refresh-token rotation / reuse-detection under concurrency

A stolen refresh token is a long-lived bearer credential. Rotation without correct reuse
detection either fails to revoke the family or forks it so attacker and victim both persist.

*Evidence.* better-auth GHSA-392p-2q2v-4372 (concurrent redemption *forks the token family*).
RFC 9700 §4.14 (rotate with reuse detection -> revoke the whole family on reuse).

*Control -- reuse detection is the identity provider's, not the gateway's.* The gateway cannot
recognise a replayed refresh token: a confidential client only ever sees the refresh tokens it
presents itself, and a stateless cookie-mode instance keeps no token family, so there is no
gateway-side family and no engine-side one either (ADR-0046, option D). The control is *strict
refresh-token rotation at the identity provider* -- on Keycloak `revokeRefreshToken: true` with
`refreshTokenMaxReuse: 0` -- shipped on in both the integration realm and the compose-sample
realm. The provider refuses a replayed token with `invalid_grant`; the engine classifies that as
`CREDENTIAL_REJECTED`, and the gateway ends the session, clears the session cookie and records
`ApiSheriff-111` (`credential-rejected`). The other refresh failures are disposed per kind (see
link:configuration.adoc#_refresh_failure_dispositions[the configuration reference]): a failure
before the provider processed the grant keeps the session with a fixed back-off; a redeemed
response the gateway refused, or a rotated session it could not persist, ends the session and
revokes best-effort the one live refresh token it can name -- which is none when the response was
refused for not being bound to the proof key (<<bff-14>>). In server mode one more case ends the
same way without being a failure of the refresh: a logout or a back-channel logout destroyed the
session while its refresh was in flight. The rotated session is then not written back
(<<bff-09>>), the request is answered as session-ended, the refresh token the exchange returned is
revoked best-effort, and `ApiSheriff-111` records `session-terminated`. The gateway's own part in the
concurrency half is `TokenRefreshCoordinator`'s single-flight *per session, per instance*: concurrent
requests on one session share one redemption, so one instance never presents the same token twice
and never forks the family itself.

*Observed Keycloak behaviour (Keycloak 26.5.7, pinned by `BffRefreshReuseIT`).* On a detected replay
Keycloak refuses the replayed token *and revokes the successor refresh token*, so the legitimate
holder's session ends along with the attacker's -- a replay burns the whole grant, which is the
RFC 9700 §4.14 outcome. The Keycloak *user session* the login created survives, with the client still
attached: the revocation is scoped to the refresh grant, not a logout of the whole SSO session. Both
halves are assertions, so an upgrade that changes either turns the suite red.

*Residual.* Without strict rotation at the provider there is *no* reuse detection on either side --
the provider accepts a replayed refresh token and refreshes it. Strict rotation in turn costs
availability: a duplicate refresh from two instances (or two parallel cookie-mode requests landing on
different instances) presents the same token twice and the second ends the session, a forced
re-login. Enabling a reuse count or grace window at the provider trades that back for exactly the
detection signal rotation exists to provide -- an operator decision, never a gateway default.

*Status (mode-split -- the reachable attack differs):*

* *Server mode:* COVERED (IdP strict rotation). The refresh token never leaves the server-side
  store, so a gateway-side replay is unreachable from the browser; the attack that remains is a
  token stolen from elsewhere and redeemed directly at the provider. Strict rotation detects *reuse*,
  not that first redemption, so detection is bounded by the gateway's refresh cadence rather than
  immediate. If the attacker redeems first, the provider issues the attacker a successor and nothing
  is detected until the gateway presents its now-spent token on the session's next refresh; the
  provider then refuses it, the gateway ends the session as `credential-rejected`, and on Keycloak
  the successor grant is revoked too -- the attacker holds a working grant up to that gateway
  refresh. If the gateway refreshes first, the attacker's later presentation of the spent token is
  the detected reuse, the provider revokes the successor, and the gateway session ends on its next
  refresh. The path by which an IdP-side revocation reaches a server-mode gateway session is that next
  refresh, which ends it as `credential-rejected` (`BffRefreshReuseIT`, targeted grant revocation
  ending exactly one of two sessions).
* *Cookie mode:* COVERED (IdP strict rotation), with the duplicate-refresh residual accepted. A
  replay *is* reachable -- an attacker holding a copied pre-refresh cookie makes the gateway present
  the spent refresh token -- and the provider rejects it, ending that session and, on Keycloak, the
  successor's (`BffRefreshReuseIT`, cookie-mode replay and IdP-revoked cookie session). Because a
  cookie-mode session end destroys nothing server-side, a retained or replayed ended cookie would
  otherwise re-drive a refresh grant and a `WARN ApiSheriff-111` on every near-expiry request until
  the absolute TTL -- amplification and log flooding, not an authentication bypass. The refresh
  coordinator therefore marks the presented refresh token (a per-instance salted digest, never the
  token or cookie) when it ends a cookie-mode session, for whichever reason
  link:LogMessages.adoc#apisheriff-111[`ApiSheriff-111`] records, until the session's absolute
  lifetime, and refuses a marked token locally with no IdP call, no revocation and no warning.
  Keyed on the token, a successor cookie still reaches the provider once. *Residual:* the marker is
  per instance (each other instance makes one IdP call before
  marking), in memory (a restart forgets it, one IdP call again), bounded (a full store records
  nothing, so replays degrade to one IdP call per request), not set by RP logout, and unused in
  server mode.

*Assertion.* A replayed pre-refresh cookie is answered `401` with a clearing cookie and a
`credential-rejected` record; Keycloak's successor revocation and surviving user session are pinned;
a targeted IdP revocation ends exactly one server-mode session while its sibling keeps refreshing;
concurrent refreshes on one session within an instance make one redemption; cookie mode never
exposes the refresh token to the browser.

[#bff-09]
=== BFF-09 -- Logout (back-channel token validation, RP-initiated open redirect, fixation)

Under-validated back-channel logout tokens allow forged logout (DoS) or accepting an ID token
as a logout token; a lax `post_logout_redirect_uri` is an open redirect; incomplete session
destruction leaves a fixated session.

*Evidence.* OIDC Back-Channel Logout 1.0: logout token MUST carry `events` (with the
back-channel member) and `sub`/`sid`, and MUST NOT carry `nonce`; validate sig/`iss`/`aud`/
`iat`. Keycloak redirect CVEs (CVE-2023-6927/8883/2026-3872) apply to the post-logout URI.

*Control.* Validate logout tokens strictly: signature+`iss`+`aud`, require `events`, require
`sub`/`sid`, *reject any token containing `nonce`*, short `iat` window; destroy via the
`sid`/`sub` secondary index. Exact-match `post_logout_redirect_uri`. Destroy the
server session and rotate/clear the cookie on any logout; revoke the RT family. Cookie-mode
disables the back-channel endpoint (`404`) -- no session to destroy.

*The `sid` index names the identity-provider session the tokens belong to.* A session is indexed
under the `sid` of its login's ID token. A widening (<<bff-17>>) merges tokens that a different
identity-provider session may have issued, so it re-indexes the session under the `sid` of that
grant's ID token when the token carries one. Without that, a logout token for the session that
answered the widening would be accepted, destroy nothing (`ApiSheriff-13` with a count of `0`) and
leave the gateway session usable.

*A termination wins over an in-flight write (server mode).* Two writers update a session that
already exists: the token refresh, on both of its legs (<<bff-08>>), and the widening callback
(<<bff-17>>). Each resolves the session, calls the identity provider and writes the result back. A
logout or a validated back-channel logout can destroy the session between that resolve and that
write, and an unconditional write would then store the session again, holding newly issued tokens,
after it was ended. The `SessionBinding` seam therefore has one creating write, used by the login,
and one updating write that never creates
(link:adr/0018-BFF_session_mode_is_one_SessionBinding_seam_behind_a_fixed_reserved-path_and_CSRF_model.adoc#updating-write[ADR-0018]).
In server mode the store checks for the session and replaces its record as one atomic step, under
the lock every destroy operation takes, so a destruction either precedes the check -- and nothing is
written -- or follows the replacement and removes it. A write that finds the session gone is
answered as the session having ended: the refresh returns its session-ended outcome to the request
and to every request coalesced with it, revokes best-effort the refresh token the exchange returned,
and records `ApiSheriff-111` with `session-terminated`; the widening callback answers `403` with no
`Location` and no `Set-Cookie`, stores nothing, and records `ApiSheriff-131` with
`session-terminated`. The tokens of a refused widening grant are dropped unstored and are not
revoked, as with the callback's other refusals.

*A logout token is typed, unexpired and acts once.* After the signature the receiver checks, in this
order: the `typ` header, `iss`, `aud`, `iat` inside a two-minute window, `exp`, `events`, the absence
of `nonce`, `sub` or `sid`, and `jti`. A token whose `typ` header is present must name `logout+jwt`
(compared without case, with or without the `application/` prefix); a token without a `typ` header
passes that one check. `exp` must be present and in the future, and `jti` must be present. An accepted
token is then admitted once: the receiver remembers a digest of its `jti` for as long as its `iat`
window can still accept it, and a second delivery inside that window destroys nothing. The memory is
taken before any session is destroyed, so two deliveries arriving together cannot both act. It holds
10 000 entries per gateway instance and is not shared between instances; an entry leaves only when
its window has closed, and a token that finds the memory full of live entries is refused rather than
acted on unremembered. Every refusal is the `400` of a rejected logout token, served `no-store`, with
`ApiSheriff-112` naming the reason. Each component that can refuse a token records each reason at
`WARN` once and at `DEBUG` afterwards, because a refused token can be presented again at will.

*An RP-initiated logout ends the gateway session whatever the identity provider offers.* The logout
endpoint destroys the session and clears its cookies first and builds the redirect to the provider's
`end_session_endpoint` afterwards. When that redirect cannot be built -- the provider publishes no
endpoint, publishes one that is not an absolute `http` or `https` URI, its metadata cannot be
obtained, or the session holds no ID token -- the browser is sent to `oidc.logout.final_redirect`.
No such condition answers a logout with an error, and none leaves the session in place.
`ApiSheriff-135` records once per process that the provider offers no usable endpoint.

*Status:* COVERED in server mode. Both channels, the logout-token checks -- `typ`, `iss`, `aud`,
`iat`, `exp`, `events`, `nonce`, `sub`/`sid`, `jti` and the single use of a token -- and the
logout-`state` cookie are delivered, cookie mode disables the back-channel receiver, an RP-initiated
logout ends the gateway session with or without the provider's endpoint, and a server-mode
termination is not undone by a refresh or a widening that was in flight. Cookie mode carries one
accepted residual.

*Not delivered: token revocation at logout.* The control names revoking the refresh-token family.
RP-initiated logout hands the session to a token-revocation seam that the shipped runtime binds to a
no-op, and the back-channel receiver calls no revocation at all, so in both session modes the
gateway sends no RFC 7009 request on a logout. Whether the session's tokens stop being valid at the
identity provider is decided by the provider -- by how it handles the `end_session_endpoint`
redirect, or by the termination it announces over the back-channel -- not by the gateway. The
refresh path is separate and does send a best-effort revocation request (<<bff-08>>).

*Residual risk (accepted) -- cookie mode: a response in flight can outlast the logout.* The stateless
binding holds no session state, so its `destroy` removes nothing and its updating write cannot
observe a logout: it always re-seals. What the logout endpoint does is resolve the session from the
request, hand it to a token-revocation seam, answer with the clearing `Set-Cookie`, and redirect to
the identity provider's `end_session_endpoint`. The shipped runtime binds that seam to a no-op, so
the gateway itself revokes nothing at the identity provider on logout. A near-expiry refresh, a
scope-driven refresh or a widening callback that was already running for the same browser still
answers with a re-sealed session cookie. If that response reaches the browser after the logout response, the
browser again holds a cookie the gateway resolves as a session, until the session's absolute
lifetime. The exposure needs a request of the same browser in flight at the moment of the logout.
Beyond that it is bounded by the identity provider, not by the gateway: where the provider ends its
own session on the logout, the refresh token in the re-sealed cookie is refused at that session's
next transparent refresh and the session ends there, as for any IdP-side termination in this
variant; until then the gateway mediates the access token the cookie carries. The mitigations are the ones
link:variants/03-bff-cookie.adoc#_logout[Variant 3 -- Logout] names for a termination the stateless
variant cannot enforce at once: a short `ttl_seconds`, short access-token lifetimes, and the
session-based variant where immediate termination is a hard requirement.

*Assertion.* A logout token missing `events`/`sub`/`sid`, or *containing* `nonce`, or an ID
token replayed as a logout token -> rejected; a non-registered `post_logout_redirect_uri` ->
rejected; post-logout the session is gone and the cookie cleared; cookie-mode back-channel ->
`404`. In server mode a session destroyed by its identity, by `sid` or by `sub` is not written back
by the conditional store write, which replaces a stored record only and consumes no capacity
(`InMemorySessionStoreTest`, `ServerSessionBindingTest`); a session destroyed in each of those three
ways between a widening callback's resolve and its write ends in `403` with no `Location` and no
`Set-Cookie`, stays unresolvable and is recorded as `session-terminated`, while the same callback
merges when nothing destroys the session (`CallbackEndpointTest`); a session destroyed in each of
those ways during the provider exchange, on the near-expiry leg and on the scope-driven leg, is not
written back, the request and a coalesced waiter are answered as session-ended, and the rotated
refresh token is handed to revocation (`TokenRefreshCoordinatorTest`). The cookie-mode residual is
pinned rather than hidden: the stateless update re-seals after every destroy form
(`CookieSessionBindingTest`, `TokenRefreshCoordinatorTest`). A logout token typed other than
`logout+jwt`, without `exp` or at or past it, or without `jti` is refused, and an untyped one with
every other claim valid is accepted (`LogoutTokenValidatorTest`); each of those refusals is a `400`
that destroys nothing (`BackchannelLogoutEndpointTest`, `RefusedSignedTokens`). The same token
delivered twice destroys once, sixteen deliveries arriving together act once, and a full replay
memory refuses and remembers nothing (`LogoutTokenReplayGuardTest`; `BackchannelLogoutReceiverTest`,
`SingleUse`). The session is destroyed before the redirect to the provider is built; a logout
against a provider without a usable `end_session_endpoint`, with failing discovery, or for a session
without an ID token ends the session, clears the cookies and lands on `final_redirect`, and
`ApiSheriff-135` is recorded once (`RpInitiatedLogoutTest`, `NoUsableEndSessionEndpoint`;
`LogoutEndpointTest`). The redirect that carries the ID token is answered with
`Cache-Control: no-store` and `Referrer-Policy: no-referrer`, and a refused back-channel delivery
with `no-store` (`GatewayEdgeGatewayCookieTest`, `ServerMode`).

[#bff-10]
=== BFF-10 -- Cookie hardening & token-leakage-to-browser

Tokens reaching JS, or a weakly-flagged session cookie, defeat the BFF rationale; session
fixation on login lets a pre-seeded session be adopted.

*Evidence.* Browser-Based Apps BCP (BFF keeps tokens server-side). BFF cookie guidance
(`__Host-`+`HttpOnly`+`Secure`+`SameSite`). Session-fixation guidance.

*Control.* The access token and the refresh token never reach the browser in a readable form:
server-mode holds them in the store; cookie-mode
seals them in an `HttpOnly` AES-GCM cookie decrypted per request. Session cookie:
`__Host-` + `HttpOnly` + `Secure` + `SameSite=Lax`, opaque id only (see the variant
docs). Regenerate the session id on login and privilege change; destroy on logout.

*The `__Host-` guarantee cannot be configured away.* The prefix is what makes a browser *enforce*
`Secure`, `Path=/` and no `Domain` rather than merely receive them, and the session cookie's name is
operator-configurable through `oidc.session.cookie_name`. A declared name is therefore *refused at
boot*, in both session modes, unless it starts with the case-sensitive `+__Host-+` prefix followed by
a name, is a non-empty RFC 9110 token -- the name is written verbatim into `Set-Cookie`, so a `;`,
`=`, whitespace or control character would be response-header injection -- and differs from the
gateway-owned binding and logout-state cookies, which a colliding session cookie would silently
overwrite. The offending value is escaped before it is echoed (CWE-117). The refusal is the only guard:
the runtime consumes the name verbatim and the schema declares the key an unrestricted string. An
omitted key resolves to the gateway's own `+__Host-sheriff-session+`.

*The ID token is delivered to the browser once, at logout.* RP-initiated logout answers with a
`302` to the identity provider's `end_session_endpoint`, and the redirect URL carries the session's
ID token as `id_token_hint` beside `post_logout_redirect_uri` and `state`. The access token and the
refresh token are in no answer. A URL is recorded where a request body is not: the ID token is
readable in the browser's history, in the identity provider's access log, and by any intermediary
that terminates TLS in front of the identity provider. Three things bound that. The redirect is
followed over TLS to the provider that issued the token. An ID token is not an API credential: the
gateway accepts it on no route and relays it to no upstream, so its holder learns the claims it
carries and can present it as a logout hint, nothing more. And it is valid only until its own `exp`.
The gateway's answer carries `Cache-Control: no-store` and `Referrer-Policy: no-referrer`; the
latter governs the request the browser makes when it follows the redirect. Whether the identity
provider's own pages pass their URL on as a `Referer` is decided by the provider's referrer policy,
not by the gateway. The gateway session is ended and its cookies are
cleared before the redirect is built; when no end-session redirect can be built -- the provider
publishes no usable `end_session_endpoint`, its metadata cannot be obtained, or the session holds
no ID token -- the logout is completed at the gateway and the browser is sent to
`oidc.logout.final_redirect`, with no token in any URL.

*The origin need not see the token either.* A route that only has to know the user is logged in
declares `auth.token_relay: false`: the session is still required, refreshed and held to the route's
scopes (<<bff-15>>), but no `Authorization` header is relayed, so a static app or asset origin never holds an access token it
could log, leak or replay. The opt-out cannot be undone by the forward configuration: a route
resolving `token_relay: false` while its `forward.headers_allow` names `Authorization` (any case) is
refused at boot, because that list would re-admit the browser's own `Authorization` header to the
same origin. The cookie-mode seal also carries the session's active and granted scope sets; scope
names are not credentials and are printed as-is where the payload's `toString()` redacts the tokens.

*Status:* COVERED.

*Assertion.* No response carries an access token or a refresh token to the browser in a readable
form, and the ID token appears only as `id_token_hint` in the RP-initiated logout redirect; the
session cookie has
`__Host-`+`HttpOnly`+`Secure`+`SameSite`; the session id is regenerated at login (fixation
test); a configured `session.cookie_name` that lacks the prefix (or carries it in the wrong case, or
as `+__Secure-+`), is the bare prefix, is blank, carries a `;` or a space, or names either
gateway-owned cookie fails boot at `/oidc/session/cookie_name` with the value escaped, while the
default name and a well-formed custom `+__Host-+` name boot cleanly; a live session on a
`token_relay: false` route reaches the upstream with no `Authorization` header while a missing
session is still redirected (`302`) or challenged (`401`); `token_relay: false` together with
`headers_allow: [Authorization]` fails the boot.

*Evidence.* BFF security writeups repeatedly name this as the pattern's #1 gap.

=== BFF-12 -- Encrypted-cookie AES-GCM nonce / key rotation (stateless variant)

AES-256-GCM nonce reuse under one key is catastrophic (leaks the GHASH subkey -> tag forgery;
keystream reuse -> plaintext recovery); mis-selecting a key drops or forges sessions.

*Evidence.* "Nonce-Disrespecting Adversaries" (practical GCM nonce-reuse attacks). RFC 9700 /
crypto guidance.

*Control.* Fresh random 96-bit nonce per seal from a CSPRNG (never counter/derived); cookie
= `version‖key-id‖nonce‖ciphertext‖tag` with version+key-id+cookie-name in the GCM AAD
(deterministic key-id gate, replay-across-format prevention); tamper -> treated as no
session; exactly one sealing key, so withdrawing it is a fail-closed clean break (unknown key
id -> no session -> re-authentication) with no decrypt-only companion key to mis-select; ~4 KB
size budget enforced at seal (fail login loudly, no silent truncation).

*Status:* COVERED.

*Assertion.* Each seal uses a unique random nonce; a flipped byte in ciphertext/nonce/tag ->
unauthenticated (never `500`); a cookie stamped with a key id the gateway does not hold ->
no session, and the browser completes a full re-authentication; an oversized token set fails
login with a clear error; key material never logged.

=== BFF-13 -- Callback response hygiene (HPP duplicate params, code reuse, error reflection)

=== BFF-14 -- Sender-constraining (DPoP): the binding, an identity provider that ignores the proof, and where the binding ends

Plain bearer tokens are replayable if stolen (logs, proxies, XSS, MITM). Sender-constraining
binds a token to a client key. Three things go wrong with it at a BFF: the client asks for a bound
token and the identity provider answers with an unbound one that the client accepts (a silent
downgrade); the binding is assumed to protect the token everywhere, when it protects only the hops
that check a proof; and a resource server accepts a bound token as a plain bearer.

*Evidence.* RFC 9449 (DPoP: `cnf` binding, `jti` replay cache, `htu`/`htm`/`iat` checks),
RFC 8705 (mTLS-bound). FAPI 2.0 Security Profile §5.3.3.1 (the client shall support
sender-constrained access tokens). Misuse = not validating `cnf`, no `jti` cache, accepting bound
and bearer interchangeably (downgrade).

*Control -- the gateway requests a bound token on every token leg.* `BffRuntimeProducer` resolves
one sender-constraint key and builds one `SenderConstraint` from it. That one instance serves the
code exchange -- of a login callback and of a session-widening callback (<<bff-17>>) alike -- every
per-scope login and widening flow, and every refresh grant, near-expiry and scope-driven, so each
token request carries a DPoP proof signed with the same key. This holds in both
client-authentication modes (<<bff-18>>).
Mutual TLS binding (RFC 8705) is not offered.

*Control -- an identity provider that ignores the DPoP proof is refused.* The engine does not judge
the answer: at the pinned version it accepts a token response of type `Bearer` to a request that
carried a proof. The gateway therefore checks every token response itself, at the code exchange and
at every refresh, in `BoundTokenEndpointClient` -- the runtime's one token-endpoint client. A
response is accepted only when its `token_type` is `DPoP` (compared without regard to case) *and*
the access token carries a `cnf.jkt` equal to the RFC 7638 thumbprint of the gateway's own proof
key. Anything else is refused:

* at the code exchange the callback answers `400` and creates no session and no session cookie; on a
  widening callback it answers the same `400` and merges nothing into the live session, which is
  left as it was;
* at a refresh -- near-expiry or scope-driven -- the session ends (`ApiSheriff-111`, reason
  `redeemed-response-refused`), the session cookie is cleared and `oidc.session.refresh.on_failure`
  applies;
* the refusal is recorded as `WARN ApiSheriff-134` with two bounded tokens -- the leg
  (`code-exchange`, `refresh`, `other`) and the reason (`token-type`, `unreadable-access-token`,
  `cnf-absent`, `cnf-mismatch`). Neither the record nor the exception carries the access token, the
  refresh token, the ID token, a claim value, the received `jkt` or the received token type;
* an identity provider that issues opaque access tokens is refused the same way
  (`unreadable-access-token`): there is no `cnf` to read.

The `cnf` claim is read from the unverified payload of the access token. No trust decision rests on
that read: the engine validates the signature over the same bytes directly afterwards, nothing is
accepted unless both pass, and a refusal on an unverified payload only refuses. The record is not
latched, because the refusal is reached only on a success answer of the token endpoint, which needs
an authorization code or a refresh token the identity provider issued -- a caller without one cannot
produce it. A response that carries no access token at all does not reach the check: it is
refused one step earlier by the engine, with the same outcome and without the `ApiSheriff-134`
record.

*Control -- where the binding ends.* A proof is checked at the identity provider's token
endpoint and nowhere else:

* *The forwarded token.* A `require: session` route forwards the mediated access token upstream as
  `Authorization: Bearer`, with no proof. That token carries `cnf.jkt`. The upstream contract is
  that an upstream *must not check `cnf`*: a `cnf`-blind upstream accepts the token unchanged, and a
  DPoP-aware upstream would have to reject it for want of a proof. `auth.token_relay: false` forwards
  no token at all (<<bff-10>>).
* *Nothing downstream of the identity provider checks a proof when the token is used.* The binding
  is established and checked between the identity provider and the gateway. A copy taken on the upstream hop
  is as usable against that upstream as a bearer token is, so the control on that hop is transport
  security.
* *The gateway's own bearer routes accept a bound token without a proof.* A `require: bearer` route
  validates the token offline. The validation library runs its DPoP checks -- the proof validation
  and the `jti` replay cache the foundation section names -- only for an issuer that carries a DPoP
  configuration, and the gateway configures none. The hook exists (the 4-arg
  `AccessTokenRequest(token, headers, uri, method)` supplies the URI and method a proof check needs);
  the enforcement does not.

*Status:* PARTIAL. The request for a bound token and the refusal of an unbound answer are delivered
and tested. Enforcement of the binding at the point of use -- on the gateway's own bearer routes and
at the upstream -- is absent, and is recorded as an accepted residual rather than as a gap in the
delivered control.

*Residual risk (accepted) -- a refused response leaves a refresh token behind.* A refresh token
issued alongside a refused response is discarded and *not revoked* at the identity provider. The
refusal carries no token, the engine classifies it as a redemption whose rotation is unknown, and
the refresh coordinator has nothing to name in a revocation request. The token stays valid at the
identity provider until it expires or is revoked there. Its holder would have to be the gateway --
the response never left the back channel -- so the residual is an orphaned grant, not a leaked one.

*Residual risk (accepted) -- the binding does not reach the point of use.* A token stolen from the
upstream hop, from an upstream's log or from the gateway's memory is usable wherever a bearer token
is accepted. What the binding does deliver is narrower: an identity provider or resource server that
does check proofs refuses the token from any holder that cannot sign with the gateway's proof key.

*Residual risk (accepted) -- the authorization code is not bound to the proof key.* The gateway
sends no `dpop_jkt` with the pushed authorization request. The code stays protected by PKCE and by
the browser binding (<<bff-02>>, <<bff-03>>).

*Assertion.* A token response of type `Bearer`, one whose access token carries no `cnf`, one whose
`cnf.jkt` names another key and one whose access token is not a readable JWT are each refused with
the matching `ApiSheriff-134` reason, and no record or exception carries token material
(`BoundTokenEndpointClientTest`, and `BffRuntimeProducerTest` for the assembled runtime, where the
code exchange of a login and of a widening callback and both refresh legs are each driven against an
unbound answer). Against
Keycloak 26.5.7 and the native image, the token forwarded upstream carries the `jkt` of the
gateway's proof key and arrives as `Authorization: Bearer` with no proof beside it, for an EC and
for an RSA proof key, and a token rotated by a refresh carries the same `jkt`
(`BffFapiControlsIT`); in client-secret mode the token of the code exchange and the token of the
refresh grant both carry that `jkt` (`BffClientSecretModeIT`). A *refused* response is not observed on the
stack -- Keycloak binds every access token of these clients -- so the refusal is proven at unit level only.

=== BFF-15 -- Scope over-request, under-check and session-wide scope growth

Scopes are the coarse authorization a token carries. Three things go wrong with them at a gateway:
every login asks for every scope any endpoint could need (the token is over-privileged everywhere
it is relayed); a route that needs a scope forwards a token lacking it (the check is left to an
upstream that may not make it); and a refresh names a different set than was granted, silently
narrowing -- or trying to widen -- the session.

*Evidence.* RFC 6749 §3.3 (scope is requested, the AS decides what is granted) and §6 (a refresh
may narrow, never widen, the original grant); RFC 6750 §3.1 (`insufficient_scope`); RFC 9700 §2.3
(privilege restriction -- request only the scopes needed); OWASP API Security Top 10 2023 API5
(broken function-level authorization). The validation library exposes `providesScopes()` and enforces
nothing, so the check is the gateway's (see the foundation section above).

*Control.* One boot-time derivation per route, `neededScopes = oidc.scopes ∪ endpoint.scopes`,
drives every leg, so requesting and checking cannot drift apart
(link:adr/0048-Per-request_OIDC_scope_rides_a_per-scope-set_client_configuration_on_the_unchanged_engine.adoc[ADR-0048],
link:adr/0057-Session_routes_obtain_their_declared_scopes_by_refreshing_inside_the_grant_and_widening_the_live_session_outside_it.adoc[ADR-0057]):

* *Login scope minimization.* A login requests the `neededScopes` of the route it is for -- the
  session route a navigation hit, or the authenticated route a `/auth/login?returnUrl=` target
  lands on -- and `oidc.scopes` alone otherwise. An endpoint's extra scopes are asked for only when
  a login is for that endpoint, not on every login. `endpoint.scopes` is additive: an endpoint
  cannot remove a global scope, and declaring scopes on an all-`require: none` endpoint is refused
  at boot.
* *Bearer `insufficient_scope`.* A bearer route refuses a valid token missing any needed scope with
  `403` and `WWW-Authenticate: Bearer error="insufficient_scope", scope="<missing>"`, before any
  upstream contact. The challenge names come from boot configuration, never from the token. Because
  the set includes `oidc.scopes`, a BFF-mode gateway also rejects a bearer token lacking them (a
  `client_credentials` token, for example) -- a deliberate, documented tightening.
* *Session scope enforcement.* A session route, and the SESSION branch of a `session_fallback` route
  (<<bff-16>>), compares the session's active scope set `A` against `neededScopes` on every request,
  after the session is resolved and before any bearer is recorded -- whatever `auth.token_relay`
  says. A satisfied session costs no identity-provider call. A scope missing from `A` but inside the
  session's granted scope set `S` is obtained by a refresh requesting `A ∪ missing`, and
  the returned session is compared again, so no outcome of that refresh relays a session short of a
  scope. Any other shortfall redirects a navigation into a widening of the live session
  (<<bff-17>>) and refuses every other request `403` `application/problem+json`, naming the missing
  scopes from boot configuration, never from the token. The session answer carries no
  `WWW-Authenticate` challenge.
* *Refresh with the active set.* The session records the scope set of its current token (`A`) and
  every near-expiry refresh requests exactly `A`, never the static `oidc.scopes`; an omitted response
  `scope` leaves `A` unchanged (RFC 6749 §5.1), a narrowed response narrows it. The granted set `S`
  is equal to `A` at login, no refresh ever adds to it, and a near-expiry refresh never changes it,
  so the scope-driven refresh above can ask only for what the identity provider granted this session
  before (RFC 6749 §6).
* *The granted set is kept truthful.* `S` records what the identity provider last showed it grants,
  not everything it ever granted. A widening replaces `S` with the scope of its grant, and a
  scope-driven refresh the provider processed removes every requested scope the response did not
  return. A scope the provider has stopped granting therefore leaves `S` the first time the gateway
  asks for it (<<bff-17>>).

*Status:* PARTIAL (accepted residuals).

* *Session-wide scope growth (accepted).* A session gives a scope back only when the identity
  provider itself stops returning it; the token relayed to every session route carries every scope
  the session holds. A session that logged in through, or was widened for, a
  scoped endpoint therefore presents that endpoint's scopes to every other session-route upstream,
  and a widening adds to that set during the session's life. Per-endpoint token narrowing (token
  exchange, audience-restricted tokens) is out of scope. The exposure is bounded by the IdP granting
  only requested scopes (endpoint scopes configured as *optional*, not *default*, client scopes), by
  a widening requesting only a route's boot-declared set united with what was already granted, and
  by `token_relay: false` for origins that need no token at all.
* *An `invalid_scope` refresh answer is not told apart from an outage (accepted).* The engine
  surfaces that answer without the OAuth error code, so the scope-driven refresh disposes it as a
  pre-redemption failure: the session is kept and its next refresh waits out the back-off. The
  request is still never relayed short of a scope, because the stage compares again and widens or
  refuses.
* *RFC 9470 step-up leg.* An RFC 9470 step-up re-drive still requests the static `oidc.scopes`
  (recorded in ADR-0048); the session-side lookup that re-drive uses is currently unwired. This is
  the `acr` leg, not the `oidc.step_up.path` scope widening of <<bff-17>>.

*Assertion.* A navigation login on a scoped session route carries exactly `oidc.scopes ∪
endpoint.scopes`, and `/auth/login?returnUrl=` to an unauthenticated target carries exactly
`oidc.scopes` (`BffEndpointScopesIT`, `ReturnTargetScopesTest`); a bearer token lacking an endpoint
scope is `403 insufficient_scope` with no upstream contact while one covering it is `200`
(`BearerScopeIT`, `AuthenticationStageTest`); a refresh after a scoped login keeps the endpoint scope
in the refreshed token (`BffTokenRefreshIT`, `TokenRefreshCoordinatorTest`). On a session route and
on the SESSION branch of a `session_fallback` route, a session lacking a needed scope never reaches
the upstream: an XHR is `403` `application/problem+json` naming exactly the missing scope, a
navigation is redirected into a widening, and a satisfied session is relayed twice with a
byte-identical bearer and no `Set-Cookie` (`BffSessionScopeParityIT`,
`SessionAuthenticationStageScopeEnforcementTest`). The refresh branch is asserted at unit level
only (`SessionAuthenticationStageScopeEnforcementTest`, `TokenRefreshCoordinatorTest`): the two
scope sets are equal after a login and after a widening, so the integration suite cannot produce a
session whose `A` is narrower than its `S`. For the same reason the truthful granted set is asserted
at unit level only: a scope-driven grant that does not return a requested scope removes exactly that
scope from `S` in both session modes, an omitted response `scope` and an unprocessed grant leave `S`
unchanged, and a near-expiry refresh that narrows `A` leaves `S` unchanged
(`TokenRefreshCoordinatorTest`); with the stage, the coordinator and the callback assembled, API
calls for a scope the provider no longer grants are refused `403` and the scope leaves `S`, while a
scope it still grants is restored by a refresh and relayed (`SessionScopeTruthfulnessFlowTest`).

=== BFF-16 -- Authentication-branch downgrade on a dual-posture route (`session_fallback`)

A `require: bearer` route with `auth.session_fallback: true` carries two authentication branches:
BEARER for API clients and SESSION for BFF browsers. Whenever one route accepts two credentials, the
rule that picks the branch is itself an attack surface. If an attacker can steer a request onto the
weaker or more ambient branch, they can reach it with a credential the stronger branch refuses: an
invalid token "falling back" to a session cookie, or a cross-site request riding the cookie past a
CSRF check that only one branch performs.

*Evidence.* Authentication-downgrade and "fallback on failure" defects recur wherever a server
accepts more than one credential type. RFC 6750 §3.1 defines a failed bearer as a terminal `401`,
not a cue to try another mechanism. The OAuth 2.0 for Browser-Based Apps BCP treats the cookie as
the ambient credential that makes the CSRF defence necessary (<<bff-11>>).

*Control.* Branch selection is keyed on one input only: whether the request carries an
`Authorization` header. What the header contains is not consulted
(link:adr/0055-A_session_fallback_route_carries_two_authentication_branches_selected_by_Authorization_header_presence.adoc[ADR-0055]):

* *No downgrade.* Any `Authorization` header, whatever its scheme or value, an empty one included,
  selects BEARER. A malformed, foreign-scheme (`Basic`) or empty credential is therefore a `401` with
  `WWW-Authenticate: Bearer`, never a login redirect, and a valid session cookie sent alongside it
  never rescues it. The only way onto the session branch is to send no `Authorization` at all, which
  gains an attacker nothing a `require: session` route does not already offer.
* *CSRF where the credential is ambient.* The fixed CSRF defence (<<bff-11>>) runs on the SESSION
  branch only. The BEARER branch carries no ambient credential: a browser never attaches
  `Authorization` by itself, and a cross-origin script cannot set it without a CORS preflight. One
  resolver (`AuthBranch.resolve`) serves both the CSRF gate and the authentication stage, so the two
  cannot disagree about which branch a request is on.
* *No session on the bearer branch.* The BEARER branch looks up no session and writes no
  `Set-Cookie`, and the browser `Cookie` is withheld upstream by the gateway-owned never-forward set,
  as on every route. The upstream receives exactly the validated client token through the
  mediated-bearer seam, not a re-admitted inbound header (ADR-0037).
* *Both branches enforce the same scope set.* The BEARER branch is exactly a `require: bearer` route,
  including the `403 insufficient_scope` check over `neededScopes` (<<bff-15>>, ADR-0049). The
  SESSION branch is exactly a `require: session` route, including its comparison of the session's
  active scope set against the same `neededScopes`
  (link:adr/0057-Session_routes_obtain_their_declared_scopes_by_refreshing_inside_the_grant_and_widening_the_live_session_outside_it.adoc[ADR-0057]):
  a session lacking a scope is refreshed inside its grant, widened (<<bff-17>>) or refused `403`,
  and is never relayed short of one. A request is admitted on a `session_fallback` route only if one
  of those two routes would admit it, so enabling the key on a bearer route does not lower that
  route's authorization for browser users: either caller must carry `neededScopes`. The two answers
  differ in form only -- the BEARER `403` carries the RFC 6750 challenge, the SESSION `403` carries
  `missing_scopes` in a problem body and no `WWW-Authenticate`.
* *Discoverable and refused when meaningless.* The key is refused at boot on a posture other than
  `require: bearer` and on a gateway without an `oidc` block. The per-route boot posture line
  (`ApiSheriff-3`) reports `auth.session_fallback` for every route, and
  `sheriff_auth_branch_total{route,branch}` counts the branch each request took, on such routes only.

*Status:* COVERED.

*Assertion.* On a `session_fallback` route, with and without a live session cookie: a valid bearer is
`200` with exactly the client's token upstream, no upstream `Cookie` and no `Set-Cookie`; a token
lacking a needed scope is `403 insufficient_scope`; an invalid, `Basic` or empty `Authorization` is
`401 WWW-Authenticate: Bearer` with no `Location`, even for a navigation. Without `Authorization`, a
live session is served with its mediated token, a navigation is redirected into the IdP, an XHR is
`401`, and an unsafe method under a foreign `Origin` is CSRF-rejected while a bearer unsafe method
without any `Origin` is admitted (`BffSessionFallbackIT`, `AuthBranchTest`, `AuthenticationStageTest`,
`GatewayEdgeRouteBffWiringTest`). A live session lacking a needed scope is widened or refused `403`
on the SESSION branch exactly as on a `require: session` route, and never relayed
(`BffSessionScopeParityIT`, which runs each of its rows on both kinds of route). Both boot refusals
are asserted (`ConfigValidatorSessionFallbackTest`, `verify-invalid-config-fails.sh`), and the meter
records only on `session_fallback` routes (`MetricsIT`, `SheriffMetricsTest`).

=== BFF-17 -- Widening a live session (identity swap, attacker-driven authorization, refusal loop)

A session route does not relay a session that lacks a needed scope; it sends the browser back to the
identity provider to have the *live* session widened (<<bff-15>>). Adding to an existing session is a different
operation from starting one, and it fails in its own ways. The grant can land in a session that
belongs to someone else. A request the user never made -- a cross-site link -- can start the
authorization, and the question is then who chose the scopes and the landing URL. A refusal can send
the browser round again, or be answered by relaying anyway. The entry point that starts a widening
on demand, `oidc.step_up.path`, is a new reserved path with a URL parameter of its own.

*Evidence.* No gateway-product CVE is cited: the surface is new in API Sheriff, and the entry is
recorded from the mechanism. The classes are established ones: session fixation and identity
confusion (CWE-384), open redirect through a return parameter (CWE-601, as in <<bff-02>>), and log
injection through an error parameter (CWE-117). OpenID Connect Core §3.1.2.1 defines `prompt=none`
and §3.1.2.6 the `login_required`, `interaction_required`, `consent_required` and
`account_selection_required` answers to it.
RFC 6749 §6 forbids a refresh grant from widening the original grant, which is why a widening is an
authorization request at all.

*Control.*
(link:adr/0057-Session_routes_obtain_their_declared_scopes_by_refreshing_inside_the_grant_and_widening_the_live_session_outside_it.adoc[ADR-0057])

* *The widening callback is bound to the browser like a login callback.* It runs on the same pending
  record, binding cookie and `state` (<<bff-02>>), and all three are checked before anything else --
  an identity-provider error response included. An error without the binding cookie, or with a
  foreign `state`, is `403` and starts nothing, so a forged `login_required` cannot drive a
  re-drive.
* *No identity swap.* A grant is merged only when the new ID token's subject, the live session's
  subject and the subject recorded when the widening started are the same. The subject is checked on
  the session the callback resolves from the request, never taken from the pending record alone. A
  mismatch is `403`, the session is unchanged, and `ApiSheriff-130` is logged with no value at all.
  The merge keeps the session's identity, its authentication time and its absolute expiry, so a
  widening neither mints a second session nor extends the first.
* *The merged session follows the identity-provider session that answered.* The tokens a widening
  merges belong to the identity-provider session that issued the grant, which is not necessarily the
  one the gateway session was created from: the original may have ended and the user authenticated
  again, which is what the interactive attempt produces. The merge therefore takes the `sid` of the
  new ID token when it carries one, and keeps the session's own otherwise. In server mode the store
  re-indexes the session on that write, so a back-channel logout for the answering session destroys
  the gateway session (<<bff-09>>) instead of matching nothing and leaving it usable until its next
  refresh or its absolute expiry. A logout token that names the previous `sid` no longer matches.
* *The caller does not choose the scopes.* A widening requests `S ∪ neededScopes`: the session's
  granted set united with the boot-declared set of the target route. A cross-site navigation to a
  scoped route, or to the step-up path, can therefore make a user's browser *start* a widening, but
  it can only request a set an operator declared, consent stays with the identity provider, and the
  first attempt carries `prompt=none`. `missing_scopes` in the `403` answer is read from boot
  configuration, and `step_up_url` is the configured path plus the refused request's own path and
  query, percent-encoded.
* *The step-up path serves a live session only.* It is matched exactly, on the OIDC host, before the
  route table, like the other browser-facing reserved paths. Without a live session it answers `401`
  `application/problem+json` with no redirect to the identity provider, no pending record and no
  cookie, so it is not a second login entry point. That rejection is logged as one fixed-text `DEBUG`
  line that interpolates no value: an anonymous caller can drive no default-level log volume through
  it and can place nothing in the log.
* *The return URL cannot leave the origin.* `returnUrl` is validated by
  `PendingAuthorizationRecord.sameOrigin`, the predicate a login target passes (<<bff-02>>), and an
  absent, cross-origin, scheme-relative or unparseable target is replaced by the boot-checked
  `oidc.login.default_return_url`. This check is load-bearing rather than defence in depth: as a
  matched reserved path the step-up request terminates before route selection, so its parameter
  values never reach the per-route url-parameter pipeline
  (link:adr/0019-Reserved_BFF_paths_bypass_the_url-parameter_value_pipeline_and_the_cookie-header_length_relaxation_is_gateway-wide.adoc[ADR-0019]).
  The pre-route floor still applies to the request.
* *A refusal is terminal.* A silent attempt answered `login_required`, `interaction_required`,
  `consent_required` or `account_selection_required` is followed by exactly one interactive attempt.
  Every other outcome short of a
  full grant -- another identity-provider error, any error on the interactive attempt, a grant that
  lacks a scope sought beyond `S`, a subject mismatch, a callback without the live session -- is
  `403` with no `Location` and no `Set-Cookie`. The session stays usable on every route it
  satisfies. Nothing redirects again, so a scope the identity provider will not grant cannot loop
  the browser, and the request that started it is never relayed. An identity-provider error and a
  grant lacking a sought scope are logged as `ApiSheriff-131` with a reason from a closed set; an
  unknown error code is logged as `other`, never as the text the identity provider or an attacker
  supplied. A refusal can also come one step earlier: the request of a widening is pushed
  (<<bff-20>>), and a push the identity provider refuses is answered `502` before any redirect,
  with no pending record and no cookie. That answer does not redirect either.
* *A terminated session is not brought back by the merge.* The callback resolves the live session
  and writes the merge later in the same call. In server mode a logout or a validated back-channel
  logout that destroys the session in between wins: the merge is the seam's updating write, which
  never creates a session (<<bff-09>>), so nothing is stored, the callback answers the same `403`
  with no `Location` and no `Set-Cookie`, and `ApiSheriff-131` records `session-terminated`. The
  session stays terminated, and the tokens of the refused grant are held nowhere. In cookie mode the
  binding cannot observe a logout and re-seals the merged session; that residual is recorded under
  <<bff-09>>.
* *A scope the provider stopped granting reaches that refusal.* "Sought beyond `S`" is only a
  terminal check if `S` is true. A scope that is still named in `S` after the provider has stopped
  granting it -- an entitlement removed mid-session, a consent withdrawn -- would be sought by
  nobody: the refresh would return a narrower grant, the widening would be merged without the
  scope, and the browser would be sent back to the route and round again, one refresh grant, one
  authorization request and one code exchange per turn. `S` is therefore kept truthful (<<bff-15>>).
  A processed narrower scope refresh removes the scope from `S` before the widening starts, so the
  widening seeks it beyond `S` and a grant lacking it is refused. Where no refresh ran -- the
  session holds no refresh token, transparent refresh is off, or the near-expiry refresh had just
  re-bound the cookie -- the widening is merged once, the merge sets `S` to what was granted, and
  the following round is the refused one. A navigation therefore ends in the `403` after at most two
  rounds. An outright `invalid_scope` answer to the refresh is different: it is not told apart from
  an outage (<<bff-15>>), proves nothing about the scope and leaves `S` unchanged, so the refresh is
  retried once per back-off window rather than once per request.

*Status:* COVERED, with three accepted residuals.

* *A cross-site navigation can start a widening.* The link makes the browser ask for more scopes for
  the user's session. It cannot choose them or the landing origin, as above.
* *A widening merge and a concurrent refresh race.* Both resolve the session and then persist it,
  and the last writer wins. Either result is an identity-provider-fresh token set of the same
  identity; the loss is one abandoned refresh token. This race between the two writers is unchanged
  by the updating write above: that write settles a writer against a *termination*, in server mode,
  and says nothing about two writers.
* *The interactive re-drive is asserted at unit level only.* In the integration suite the browser
  that just logged in holds a live SSO session, so the silent attempt always succeeds there.

*Assertion.* On the widening callback: an error response without the binding cookie or with a
foreign `state` is `403` and re-drives nothing; `login_required`, `interaction_required`,
`consent_required` and `account_selection_required` on the silent attempt each re-drive exactly one
interactive attempt with the same scopes and return URL, and the same error on that interactive
attempt is `403` with no further redirect;
`invalid_scope` and `access_denied` are `403` with the session unchanged; a grant for another
subject, a widening issued for another subject, a callback without the live session and a grant
lacking a sought scope are each `403` with no `Location` and no `Set-Cookie`; a granted widening
keeps the session's id, authentication time and expiry in both session modes, sets both scope sets
to the granted scope and takes the `sid` of the new ID token; a session whose `S` names a scope the
grant no longer returns is merged once with the scope gone from `S` and refused `403` on the next
round, while the same session is merged round after round when the grant still returns it; after a
widening the production back-channel receiver destroys the session for a logout token naming the
new `sid` and matches nothing for one naming the previous `sid`, and a grant whose ID token carries
no `sid` leaves the session reachable under the one it had; a server-mode session destroyed by its
identity, by `sid` or by `sub` between the callback's resolve and its write is `403` with no
`Location` and no `Set-Cookie`, is recorded as `session-terminated` and stays unresolvable, while
the same callback merges when nothing destroys the session; an unknown
error code is logged as `other` (`CallbackEndpointTest`). With the stage, the refresh coordinator
and the callback assembled, a navigation for a scope the provider no longer grants is widened once
and its callback is `403` with no `Location`, and a session without a refresh token is merged once
and refused on the second round (`SessionScopeTruthfulnessFlowTest`). On the step-up path: no session, an
unknown session and an expired session are `401` with no authorization request built; an
off-origin, scheme-relative, backslash or blank `returnUrl` lands on the configured default; a
target whose scopes lie inside `S` is a direct `302`, decided on `S` and not on `A`; any other
target starts one silent widening for `S ∪ neededScopes` (`StepUpEndpointTest`). Against the live
edge and Keycloak: a navigation needing a grantable scope is redirected with `client_id` and
`request_uri` only, is answered from the realm SSO session without a login form, and lands back on
the route with a token carrying the scope; an XHR is `403` with a `step_up_url` and is relayed after
that URL was followed; a navigation needing a scope the realm assigns to no client is answered `502`
with no redirect and no cookie, because Keycloak refuses the pushed request (<<bff-20>>), and the
session is still served; the step-up path without a session is `401` and never redirects
(`BffSessionScopeParityIT`). The request is pushed, so that suite cannot read `prompt=none` or the
scope set; both are asserted on the pushed request at unit level (`BffRuntimeProducerTest`). The
terminal `403` of a callback that carries an identity-provider error is therefore asserted at unit
level only.

=== BFF-18 -- Client authentication: the signing keys, and the client secret an operator can still select

The gateway is a confidential client, and whatever it authenticates with at the identity provider
is the gateway's own identity there. A shared secret is a reusable bearer credential: it crosses the
back channel on every authenticated call, and whoever sees it once -- in a log, an environment dump, an
intercepted connection -- can act as the client until it is rotated. An asymmetric credential keeps
the private key inside the client and sends only signed, short-lived assertions, which moves the
risk from the wire to wherever the key is stored.

*Evidence.* RFC 9700 §2.5 (asymmetric client authentication -- mutual TLS or a signed JWT -- is
recommended over a shared secret). RFC 7523 (`private_key_jwt`). FAPI 2.0 Security Profile §5.3.3.1
(client authentication by mutual TLS or `private_key_jwt` only) and §5.4.1 (the permitted signing
algorithms).

*Control -- key mode, the default.* With no `oidc.client_secret` configured the gateway
authenticates with `private_key_jwt`. One `PrivateKeyJwtAuth` instance serves every pushed
authorization request (login, session widening, step-up re-drive), the code exchange of a login and
of a widening, both refresh legs and RFC 7009 revocation. Each assertion
carries a unique `jti`, expires after sixty seconds and names the
configured issuer as its only audience. The signing algorithm follows the key and cannot be set: an
RSA key of at least 2048 bits signs `PS256`, an EC key on curve P-256 signs `ES256`; no key type
reaches the `RS256` family, and an Ed25519 key is refused.

*The private keys are assets, and the gateway reads them itself.* There are two: the
client-authentication key (`oidc.client_authentication.key_file`) and the DPoP proof key
(`oidc.sender_constraint.key_file`, <<bff-14>>). Each has two modes:

* *Provided.* The key names a PEM file on a mount. The gateway reads the file itself when the BFF
  runtime is assembled: at most 16384 bytes, exactly one unencrypted PKCS#8 `PRIVATE KEY` block and
  exactly one `PUBLIC KEY` block. The two halves must belong to the same key, and the key must sign
  and verify once before it is used. Every defect refuses the boot -- the process exits without
  serving -- with a message that names the configuration key and the defect and never any key
  material. The value of the key is a *path*, not a secret, so it is not held to the secrets rule
  and may be written as a literal or through a placeholder.
* *Generated.* An omitted key is generated at startup (EC P-256) and reported once by
  `INFO ApiSheriff-21`. A generated key is held in process memory only. It is never written to a
  file, it is replaced on every restart, and it cannot be shared between instances.

The key id of either key is its RFC 7638 thumbprint. It is derived from the key and cannot be set, so
a published key id always identifies exactly the key in use.

*Control -- client-secret mode, an operator choice.* Configuring `oidc.client_secret` selects
`client_secret_basic`. There is no switch: the presence of the key is the selection, so *a copied
descriptor that carries a secret selects the mode*.

[WARNING]
====
Client-secret authentication is not FAPI 2.0 conformant and may weaken security.
====

What holds in that mode, and what does not:

* The client-authentication requirement of the FAPI 2.0 Security Profile is not met. Pushed
  authorization requests (<<bff-20>>) and the DPoP sender constraint (<<bff-14>>) stay in effect, and
  `oidc.sender_constraint.key_file` is handled exactly as in key mode.
* The secret stays an asset and its exposure stays a threat of this mode. It is sent as an HTTP Basic
  credential on every authenticated back-channel call, so the hostname and trust posture of that leg carries it
  (<<gw-06>>). The secrets rule still applies -- a literal value is refused at boot, the value must
  arrive through an environment placeholder -- and the configuration model redacts it (<<gw-12>>).
* The gateway announces the mode at every boot with `WARN ApiSheriff-133`. The record names the mode
  and never the secret. It is silenced only by removing `oidc.client_secret`.
* `oidc.client_secret` together with `oidc.client_authentication.key_file` is refused at boot, with a
  message naming both keys and no value. A blank secret is refused as well, so an empty variable
  cannot select the mode by accident.
* The client key-set endpoint answers `404` (<<bff-19>>).

*Status:* COVERED in key mode. In client-secret mode the weaker credential is an accepted residual,
selected by the operator and reported at every boot.

*Residual risk (accepted) -- the key files are unencrypted at rest.* An encrypted PEM block is
refused, so a provided key is protected by the mount and by nothing in the gateway: the gateway
checks that the file is readable and well-formed and refuses nothing on account of its permissions
or owner. Whoever can read the client-authentication key file can act as the gateway's client at
the identity provider; whoever can read the proof key file can sign proofs for the tokens bound to
it.

*Residual risk (accepted) -- no overlapping rotation.* Each key has exactly one active instance. A
key is replaced by a restart, with no window in which the old and the new key are both published or
both accepted. A compromised key is therefore withdrawn by replacing the file and restarting; the
identity provider's fetch interval bounds how long the old key is still honoured there
(<<bff-19>>).

*Residual risk (accepted) -- a client assertion can be replayed by a party that reads it.* The
engine retries a token request once when the answer carries `DPoP-Nonce`, and the retry resends the
same assertion. An identity provider that enforces single use of an assertion refuses that retry;
one that does not would also accept the assertion from anyone who captured it within its sixty
seconds. Capturing it needs the position <<gw-06>> describes.

*Assertion.* Every key-file defect -- a missing block, mismatched halves, an encrypted or
traditional-format block, an unsupported curve, an Ed25519 key, an RSA key below the floor, an
absent or unreadable file -- refuses the key with a message naming the configuration key and no key
material (`ClientSigningKeyTest`); a native gateway given
a defective key file exits without serving, and one given a secret together with a
client-authentication key file fails the boot (`verify-invalid-config-fails.sh`). Against Keycloak
26.5.7, a token request that presents a client secret for the key-authenticated client is refused
(`BffFapiControlsIT`); a client-secret instance logs `ApiSheriff-133` and never the secret value,
while a key-authenticated instance logs no such record (`BffClientSecretModeIT`); a gateway with no
key configured logs `ApiSheriff-21` once per key and completes a login (`BffGeneratedKeysIT`).

=== BFF-19 -- The client key-set endpoint (JWKS)

In key mode the identity provider verifies the gateway's client assertions against a key set it
fetches from the gateway. That makes one gateway path part of the gateway's own authentication:
whoever can answer that URL towards the identity provider chooses the key the identity provider
trusts for this client. It is also an unauthenticated path on the public port, and a URL an
identity provider dials on a client's say-so.

*Evidence.* RFC 7591 (`jwks_uri` client metadata). FAPI 2.0 Security Profile §5.4.2 (a client's key
set is served over TLS). No standards guidance on request forgery through a client-hosted key-set
URL was found; the concern is recorded here from the mechanism.

*Control -- what the endpoint discloses.* `ClientJwksEndpoint` answers `GET` on
`oidc.client_authentication.jwks_path` (default `/auth/jwks`) with one JSON Web Key: the public
members of the client-authentication key, `use: sig`, the algorithm and the key id. It never
publishes a private member, and it never publishes a separate DPoP proof key. It reads no request input.
The response is `Cache-Control: no-store`; every other method is `405`.

*Control -- reachability.* The path is reserved on *every* host, not only on the OIDC host, and is
answered without a credential -- the identity provider has none to present. It is bounded by the
admission cap of the edge and by nothing narrower. What an anonymous caller obtains is a public key
and its id.

*Control -- substitution of the client key.* The gateway cannot prove to the identity provider that
an answer came from the gateway; only the transport can. The registered URL must therefore be an
`https` URL, and the identity provider must trust the gateway's certificate *by name*. The gateway
does not enforce TLS on the path: it cannot see how a request reached a terminator in front of it.
And the URL is set by the identity provider's administrator, not by the gateway -- the gateway
cannot check what was registered. On the gateway side two things keep the path the gateway's own. The
reserved path is answered by the gateway itself, on every host, so a route whose match covers the
path does not answer it and no proxied upstream can. And a `jwks_path` -- declared, or the default
it resolves to -- that another reserved OIDC endpoint already claims is refused at boot, naming
both keys: the registry keeps the first registration for a path, so the collision would otherwise
drop the key-set endpoint without a diagnostic; a `jwks_path` that is not a canonical gateway path is
refused at boot as well, since a request that spells it as configured would never be matched and
the canonical path that request resolves to would be left unreserved.

*Control -- request forgery through the URL.* The fetch is made by the identity provider to an
address its administrator entered. The mitigations are on the identity-provider side: its fetch
interval, and its policy on which URLs it accepts (a secure-URI policy). The gateway contributes
nothing to that leg beyond a response that depends on no input.

*Control -- client-secret mode.* There is no key to publish. The endpoint is assembled in its
withheld form and answers `404` to every method, and the path is *not released to the route table*:
it stays reserved. An identity provider that still holds a key-set URL from an earlier key-mode
registration therefore cannot be answered by a proxied upstream under that URL.

*Status:* COVERED, with the residuals below accepted.

*Residual risk (accepted) -- a generated key behind more than one replica.* Each replica generates
its own key and publishes its own key set. The identity provider fetches the key set from whichever
replica answers that fetch and then trusts that replica's key only. An assertion signed by another
replica is refused until the identity provider fetches again and happens to reach the signer, so
client authentication fails intermittently. The control is operational and stated in the operator documentation: every replica
behind one identity-provider client is given the same key files. The gateway cannot see its
siblings and does not detect the condition.

*Residual risk (accepted) -- a key replacement is not instantaneous.* The identity provider learns
of a new key when it meets an unknown key id, and fetches at most once per its fetch interval (ten
seconds by default in Keycloak). A call inside that interval can be refused. What a restart with new
keys does to a live session was observed once, under stated limits: in cookie mode with a passed
sealing key and generated keys, the session established before the restart was refreshed, the
refresh succeeded and the new access token was bound to the new proof key. Replacing a *provided*
key file was not run, and a server-mode session does not survive a restart at all. The documented
worst case is that sessions fail their next refresh and follow `oidc.session.refresh.on_failure`.

*Residual risk (accepted) -- TLS on the path is the deployment's.* A gateway behind a plain-HTTP
hop (<<gw-06>>, the B1 residual above) serves the key set over whatever that hop offers. Registering
an `http` URL, or an `https` URL whose certificate the identity provider does not verify by name,
hands the client identity to anyone on that path.

*Assertion.* The publishing form answers `GET` with exactly one key carrying no private member and
`405` to other methods; the withheld form answers `404` to every method (`ClientJwksEndpointTest`);
the path is matched on every host and stays reserved in both forms (`ReservedPathRegistryTest`).
Against the native image: `GET /auth/jwks` answers, without a credential, one key with `use: sig`,
the algorithm `PS256`, no private member and a `kid` equal to the thumbprint computed from the key
file, and `POST` answers `405` (`BffFapiControlsIT`); in client-secret mode `GET` and `POST` answer
`404` (`BffClientSecretModeIT`); a generated key is published with `alg: ES256`, Keycloak fetches it
over TLS and a login completes, and after a restart the published `kid` has changed
(`BffGeneratedKeysIT`).

=== BFF-20 -- Login initiation causes an authenticated outbound request (pushed authorization request)

Pushing the authorization request (RFC 9126) keeps its parameters off the browser URL, and it
changes what an anonymous caller can make the gateway do. Before, starting a login was local work
and a redirect. Now *an unauthenticated request to the login path, or an unauthenticated navigation
to a session route, causes one authenticated outbound request from the gateway to the identity
provider*. The caller needs no credential; the gateway supplies its own.

*Evidence.* RFC 9126 (pushed authorization requests; the endpoint is a client-authenticated
back-channel endpoint). FAPI 2.0 Security Profile §5.3.3.2 (the client shall use pushed
authorization requests). The amplification is recorded from the mechanism; no CVE is cited.

*Control.* `PushedAuthorizationRequests` sits on every authorization-request seam: the login, the
session widening (<<bff-17>>) -- its silent attempt and its one interactive re-drive alike -- and the
RFC 9470 step-up re-drive. It pushes the parameters of the request the engine rendered -- for a
silent widening including `prompt=none` -- and
redirects the browser with `client_id` and `request_uri` only -- on that leg scope, `state`, the PKCE
challenge and the redirect URI appear in no browser URL, `Referer` header or front-channel log. The
push is authenticated with the gateway's client credential: a signed assertion in key mode, the
client secret in client-secret mode (<<bff-18>>). A widening needs a live session, so unlike a login
it is not reachable by an anonymous caller; a cross-site navigation of a signed-in browser can start
one (<<bff-17>>) and so cause one push. It rides the pinned back-channel posture
(<<gw-06>>). There is no front-channel fallback, so a caller cannot force the parameters back onto
the URL:

* every failure refuses the login or the widening with `502`: an identity provider that advertises no
  pushed-authorization endpoint (`no-par-endpoint`, no network call), a rendered request that cannot
  be split into uniquely named parameters (`invalid-request`, no network call), and every failure of
  the push itself -- a transport failure, a timeout, a non-success answer, an unparsable answer, an
  answer without a `request_uri` (`push-failed`);
* the refusal happens *before* the pending-authorization record is stored and before the binding
  cookie is set, so a failed push leaves no login or widening state behind in the gateway, and a
  live session that was to be widened is left as it was;
* the refusal is recorded as `WARN ApiSheriff-132` with that bounded reason on its first occurrence
  only. Every repeat of a reason is a `DEBUG` line for the rest of the process, so a stream of
  failing anonymous logins does not flood the log. Neither the record nor the refusal carries the
  authorization URL, a parameter value or the `request_uri`.

*Status:* PARTIAL (accepted residual). The control is delivered; the outbound request it adds is
bounded by the admission cap of the edge and by nothing narrower.

*Residual risk (accepted) -- no dedicated bound on login initiation.* Every admitted anonymous
login request costs the identity provider one authenticated request and one stored `request_uri`,
and costs the gateway one signature in key mode. In client-secret mode it also sends the secret
once more. The admission cap limits how many are in flight; nothing limits their rate per caller.
An operator who needs a tighter bound places it in front of the gateway. A successful push is
followed by a pending-authorization record, whose store is bounded and whose records expire after
five minutes, as before (<<bff-02>>).

*Residual risk (accepted) -- the RFC 9470 step-up seam has no live caller.* The RFC 9470 re-drive
(`StepUpCoordinator`) is assembled and its request is pushed, but no edge code calls it. On that
seam the control is proven at unit level only (<<bff-15>>). It is not the step-up *path*
(`oidc.step_up.path`, <<bff-17>>), which is live and starts a session widening.

*Residual risk (accepted) -- parts of the pushed widening are proven at unit level only.* What the
pushed request of a widening carries, the interactive re-drive, and that a refused push stores
nothing are asserted against a stub identity provider. The integration stack's widening suite
(`BffSessionScopeParityIT`) drives the silent attempt against a realm client that requires pushed
requests; it cannot read the pushed request, and it never reaches the interactive re-drive
(<<bff-17>>).

*Assertion.* The redirect carries exactly `client_id` and `request_uri`; a provider without a
pushed-authorization endpoint, an unsplittable rendered request and a failed push each raise the
upstream error with its bounded reason, recorded once per reason
(`PushedAuthorizationRequestsTest`). On the assembled runtime, the silent widening of a session-route
navigation and of the step-up path and the interactive re-drive each push their request -- the
silent one with `prompt=none` in the pushed body -- and redirect with `client_id` and `request_uri`
only; a refused push on either attempt is the `502` event with no pending record stored and the
session unchanged (`BffRuntimeProducerTest`). Against Keycloak 26.5.7, a hand-built
front-channel authorization request for the gateway's client that carries its parameters in the URL
is refused while the gateway's own redirect completes a login (`BffFapiControlsIT`), and the same
holds for a client authenticated with a secret (`BffClientSecretModeIT`). `BffSessionScopeParityIT`
asserts the same redirect shape on a widening started by a session route and by the step-up path,
completes both, and asserts the `502` and the `ApiSheriff-132` record of a push Keycloak refuses.

=== BFF-21 -- Session identifier, session lifetime and the gateway's own cookies

The entries above cover how a session is obtained and how its tokens are kept. This entry covers the
session itself: the value the browser holds, how long that value is honoured, and what happens to
the cookies the gateway sets. The failure classes are an identifier that can be guessed, read or
planted; a session that never ends, or that any request keeps alive; a cookie the browser keeps
after the session is over; a cookie that reaches an origin behind the gateway; and, where the
gateway holds no state, a browser that supplies its own idea of when it was last active.

*Evidence.* OWASP ASVS 5.0 chapter V7 and the OWASP Session Management Cheat Sheet (an unguessable
identifier that is exchanged in a cookie only, a new identifier at authentication, an idle and an
absolute timeout enforced by the server). `draft-ietf-httpbis-rfc6265bis` (the `+__Host-+` prefix
and its conditions). Envoy OAuth2 filter CVE-2025-55162 *(unverified)*: a sign-out that deleted a
prefixed cookie without `Secure`, so the browser kept it. Duende BFF GHSA-vvg7-p7jw-8qr3
*(unverified)*: the session cookie forwarded to the proxied API. mod_auth_openidc CVE-2024-24814
*(unverified)*: unauthenticated processing cost driven by the shape of a session cookie.

*Control.*

* *The cookie value is not the session id.* In server mode the browser holds a random handle of 256
  bits from `SecureRandom`, minted by `ServerSessionBinding`; the store resolves it to the session
  id, which is a second random value that never leaves the gateway and is not a lookup key. In
  cookie mode the browser holds the sealed value (<<bff-12>>); the session identity derived from it
  is used inside the gateway only. The value travels in the cookie and nowhere else: no endpoint
  reads it from a URL, and no answer carries it.
* *A login never adopts a value the browser presents.* The callback creates a session with a new id
  and binds it under a new handle (server mode) or a new nonce (cookie mode). A cookie that was in
  the browser before the login decides nothing about the session the login creates.
* *In server mode a widening re-issues the cookie value.* The write that merges a widening
  (<<bff-17>>) replaces the record and swaps the handle in one step under the lock every destroy
  takes. The previous value resolves nothing from then on. It is the same session: same id, same
  authentication time, same absolute expiry, still ended by a back-channel logout. The re-issued
  cookie carries the session's remaining lifetime as `Max-Age`. A refresh keeps the handle, and a
  refresh that resolved the session before a re-issue cannot put the previous handle back.
* *Two deadlines, enforced when the session is resolved, in both modes.* A session ends at its
  absolute lifetime (`oidc.session.ttl_seconds`, counted from the login) and after the idle timeout
  (`oidc.session.idle_timeout_seconds`) without an access, whichever comes first. Neither rests on
  the cookie's `Max-Age`: a browser that keeps a cookie past it is still answered as having no
  session. Only a request that is let through to a session route counts as an access. A request
  that is refused or redirected, the user-info endpoint and the portal's session lookup do not
  extend a session. A declared idle timeout below 1 or above the effective lifetime is refused at
  boot.
* *Cookie mode keeps the last access in a cookie of its own.* The activity cookie
  (`<session cookie name>-activity`) is authenticated with HMAC-SHA-256 under a key that exists
  for it alone, derived from the sealing key. The value is the time of the last access and is not
  encrypted; the identity of the session it belongs to is part of what the tag authenticates and is
  not in the value. An activity cookie that is missing, tampered with, signed under another key or
  for another cookie name, or bound to another session counts as absent, and the session is then measured from its
  login. Withholding or swapping the cookie can therefore only end a session sooner. No activity
  cookie extends the absolute lifetime, and an instant later than the gateway's clock counts as
  now, so replicas whose clocks differ can lengthen the idle deadline by at most that difference. A new activity cookie is written only when the last access is at least one re-issue interval
  old -- the smaller of 60 seconds and half the idle timeout, so an access can be recorded before
  every idle deadline -- and writing it never rewrites the session cookie. A session therefore ends
  no later than the idle timeout after its last access, and at most one interval earlier. The
  gateway keeps no state per session in this mode, so the client decides how often the cookie is
  written: parallel requests, or requests that present an older activity cookie again, each receive
  a new one. Writing it consumes no key budget, because a message authentication code has no limit
  on the number of values one key may protect, and the same session and instant always give the
  same value.
* *An expired server-mode session leaves memory.* A periodic task removes expired and idle sessions
  every 60 seconds whether or not anything looks them up.
* *A cookie is cleared with the attributes it was set with.* Every clearing `Set-Cookie` the
  gateway writes -- for the session cookie, the activity cookie, the binding cookie and the
  logout-state cookie -- carries `Path=/` and `Secure` and no `Domain`, the conditions a browser
  demands before it accepts any write to a `+__Host-+` cookie. A logout and a session ended by a
  refresh clear every cookie the active binding sets.
* *The gateway's cookies do not reach an upstream.* `Cookie` is a member of the request-direction
  never-forward set and no route configuration re-admits it (<<gw-03>>). This holds for the HTTP,
  the gRPC and the WebSocket dispatch.
* *Reading a cookie costs bounded work before anything is authenticated.* The `Cookie` header is
  capped before any session code runs. A value that is not a sealed cookie costs one base64 decode
  and at most one authenticated decryption; a payload is inflated only after its tag verified, up
  to a fixed size; the activity value has one fixed length. A rejected session cookie is recorded
  once per kind of rejection and a rejected activity cookie at `DEBUG` only, so a stream of junk
  cookies does not flood the log.
* *A login ends the session the browser presented.* A login callback that has passed its checks --
  the binding cookie, `state`, the code exchange and the subject -- destroys the session the
  request's own cookie resolves, whoever it belongs to, and binds the new session afterwards. In
  server mode the earlier session is gone from the store and its cookie value resolves nothing. A
  callback that is refused touches no session, and a widening keeps the session it widens.
* *One subject holds a bounded number of server-mode sessions.* The store ends the oldest session
  of a subject -- the one created first, whatever its last access -- before it stores a login that
  would take the subject past `oidc.session.max_sessions_per_subject`. The order is the order of
  logins, which the holder of a session cannot influence. The bound is applied before the store-wide
  `max_sessions`, so a subject at its own bound is not refused by a full store, and with the bound
  below `max_sessions` one account cannot hold the whole store against every other. A value below
  1 or above the effective `max_sessions` is refused at boot, and so is the key in cookie mode,
  where no store exists to enforce it.
* *A response the gateway sets a cookie on is not cacheable.* Whenever a pipeline stage adds a
  `Set-Cookie` to a response, the response is written with `Cache-Control: no-store`, on a relayed
  upstream response in place of whatever `Cache-Control` the upstream sent. Every answer of a
  reserved path that sets a cookie, and a gateway-rendered page that sets one, carry the same. A
  response the gateway adds no cookie to keeps the upstream's cache policy.
* *An upstream cannot set a gateway cookie.* On the HTTP and the gRPC relay an upstream `Set-Cookie`
  line naming a cookie the gateway owns -- the session cookie, the activity cookie, the binding
  cookie, the logout-state cookie -- is dropped; every other line is relayed unchanged. The name is
  compared exactly, the `+__Host-+` and `+__Secure-+` prefixes without case, and a nameless line
  whose value starts with an owned name is dropped as well. A WebSocket upgrade and an asset answer
  relay no upstream `Set-Cookie` at all.
* *A WebSocket relay ends with its session.* A relay opened for a request a session was let through
  with is closed on both legs, with close code `1008` and the reason `session ended`, at the
  session's absolute expiry. In server mode it is also closed when the session is destroyed or
  removed: by a logout, a back-channel logout, the login that replaces it, the per-subject bound, or
  the removal of an expired or idle session. The relays are tracked under the session id, not under
  the cookie value, so a re-issued cookie value closes nothing. At most 10 000 such relays are
  tracked; an upgrade beyond that is refused `503` before anything is opened, and no relay of a
  session is opened untracked. Frames on a relay do not extend the session. In cookie mode the
  gateway holds no session whose end it could observe, so there a relay is closed at the absolute
  expiry and not by a logout (<<bff-09>>).

*Status:* COVERED, with two statements of the controls above that no test asserts; the end of the
assertion names them. The limits of the
stateless variant are recorded where they arise and are not repeated here: a sealed cookie cannot be
withdrawn before its deadlines (<<bff-09>>), and its replay after a refresh is the identity
provider's to refuse (<<bff-08>>).

*Residual risk (accepted) -- cookie mode: a cookie sealed before a step-up or a widening stays
usable as it was sealed.* A step-up or a widening answers with a newly sealed session cookie. The
stateless binding holds nothing with which it could withdraw the cookie the browser held before, so
a copy of that earlier cookie keeps resolving a session until its own deadlines, at the
authentication level and with the scope sets sealed into it. It never gains what the step-up or the
widening obtained: a route that needs the new scope refuses it or sends it into a widening of its
own (<<bff-15>>). The exposure is that of any copied session cookie in this variant, held to the
earlier level. In server mode the same step re-issues the cookie value, and the previous value
resolves nothing.

[[_html_surface_failure_catalogue]]
== HTML surface failure catalogue

The optional application portal (link:user/portal.adoc[operator guide],
link:adr/0053-Portal_templates_render_on_a_standalone_Qute_engine_and_escape-bypass_constructs_are_refused_at_boot.adoc[ADR-0053])
gives the gateway an HTML surface of its own. Two responses are gateway-authored HTML: the overview
page on the reserved `portal.path`, and, with `portal.error_pages`, the negotiated HTML error page of
a gateway-originated error. Without a `portal` block neither exists and every entry below is
ELIMINATED for that deployment.

HTML adds a class of failure the JSON surfaces never had: a value the gateway writes into a page is
interpreted by a browser *in the gateway's origin*. The inputs that reach the page are catalog values
(operator configuration), the `notice` query parameter (attacker-controlled), the signed-in user's
`preferred_username` (identity-provider-controlled, and user-controlled wherever the IdP lets users
edit it), the HTTP status of an error, and the template itself (operator-authored). Three boundaries carry
them: the client edge (B1) for `notice` and the `Accept` header, the browser session (B5) for the
username, and the operator configuration (B6) for the catalog and the template.

The shared control is the rendering path. One standalone Qute engine renders every portal page. It
HTML-escapes every value it writes, has no resolver for the escape-bypass constructs, has no namespace
resolver, and sees a fixed map of plain values rather than domain objects. A template is parsed and
walked at boot, and the boot is refused rather than serving a template that could bypass that path.
Every portal response carries the fixed policy
`Content-Security-Policy: default-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`
and `X-Content-Type-Options: nosniff`, which `security_headers` cannot weaken.

[#html-01]
=== HTML-01 -- Stored and reflected XSS via catalog values, the `notice` parameter and the username

A value written into the page without HTML escaping runs as script in the gateway's origin. Stored
XSS arrives through a catalog `title` or `description`, reflected XSS through the `notice` query
parameter, and identity-driven XSS through a `preferred_username` the attacker chose at the identity
provider.

*Evidence.* Reflected and stored XSS through an echoed query parameter or an unescaped
administrator-supplied label is the most common web-application weakness class (CWE-79, OWASP A03).
No gateway-product CVE is cited: the surface is new in API Sheriff, and the entry is recorded from the
mechanism before it ships.

*Control.* Escaping is structural, not per-template. The engine's result mapper HTML-escapes every
value for the `text/html` variant every template is parsed with, and the raw-value resolver is
absent, so no expression resolves to unescaped output. `notice` is never echoed: it is mapped by exact,
case-sensitive comparison onto a closed vocabulary (`logged-out`), and every other value is dropped
before rendering. Only the vocabulary word reaches the page. The username is read from the
*validated* ID-token claims only, and escaped like every other value. The portal CSP carries no
`'unsafe-inline'`, so an injected inline script would not run even if escaping were bypassed.

*Status:* COVERED. `PortalRendererTest` pins the escaping of every model value and the absence of
`raw`/`safe`; `PortalNoticeTest` pins the closed vocabulary; `PortalEndpointTest` pins that an unknown
or HTML-bearing `notice` is dropped; `PortalIT` asserts against the native image that a catalog title
carrying `<`, `&`, `"` and `'` is escaped on the page and that `notice=<script>` renders nothing of it.

*Assertion.* No catalog value, username or `notice` value appears unescaped in a rendered page; a
`notice` outside the vocabulary never reaches the page; every portal response carries the fixed
portal CSP.

[#html-02]
=== HTML-02 -- Template injection by an operator template (SSTI)

A template engine that can reach application objects, configuration or the class loader turns a
template into code execution or a secret-disclosure channel. The template author is the operator,
but the template file is also a place where an attacker with write access to the configuration
volume, or an inattentive copy-and-paste, can escalate. A template construct that parses a *value*
as template code (`eval`) would make the username or a catalog value an injection vector as well.

*Evidence.* Server-side template injection is an established class (CWE-1336), with CVE-2022-22954
(FreeMarker template injection leading to remote code execution in VMware Workspace ONE Access) as a
canonical instance. The Quarkus-managed Qute engine carries `cdi:`, `config:` and `inject:`
namespace resolvers that would expose beans and configuration to a template.

*Control.* The portal never renders through the Quarkus-managed engine. It builds a standalone engine
with no namespace resolver, no template locator and no reflection resolver, over a data model limited
to `String`, `Boolean`, `Integer`, `List` and `Map`. Only the `if`, `for`/`each`, `let`/`set` and
`when`/`switch` sections exist: `eval` is absent, and `include`/`insert` have nothing to resolve
against. A second, independent layer walks every expression at boot, including section parameters and
virtual-method arguments, and refuses any `raw`, `safe` or namespaced expression with
`ApiSheriff-202`, naming the file and line. A template that is missing, unreadable or unparseable is
refused the same way. The template is read once at boot and never reloaded.

*Status:* COVERED. `PortalRendererTest` pins every refusal (each `raw`/`safe` spelling, namespaces,
unsupported sections, parse errors, a missing file) and the line reported; `PortalIT` asserts that a
runtime-parsed operator template renders in the native image.

*Residual risk (accepted).* An operator template is trusted markup. It can link to any origin, and it
can lay out the page misleadingly. It cannot execute code, reach configuration or unescape a value,
and the portal CSP confines what the page loads and where its forms submit. Write access to the
configuration directory is already equivalent to control of the gateway (see <<gw-10>>).

*Assertion.* A template using `raw`, `safe`, a namespace, `eval`, `include` or `insert` fails the
boot with `ApiSheriff-202`; a model value containing template syntax renders as escaped text.

[#html-03]
=== HTML-03 -- Cache leakage of session data

A page rendered for an authenticated session that a shared or browser cache stores can be served to
a different user, or to the same browser after sign-out. The reverse also leaks: an anonymous page cached across
a sign-in hides the session state.

*Evidence.* The failure class is web cache deception and misconfigured caching of personalised
responses (CWE-524, CWE-525). It is configuration-shaped rather than tied to one CVE.

*Control.* The cache policy follows what the body carries, not configuration alone. A page rendered
for an authenticated session is `Cache-Control: no-store` whatever `cache_seconds` says, whether or
not the session carries a usable `preferred_username`. Every HTML error page and
the `405` are `no-store`. Only a session-free page is cacheable (`max-age=<cache_seconds>`, default
`0`), and with an active BFF runtime it carries `Vary: Cookie`, merged into any existing `Vary`, so a
cache keys it on the session cookie. A portal response never sets a cookie. Error pages are always
rendered anonymously, so they carry no session data at all.

*Status:* COVERED. `PortalResponseEnvelopeTest` pins the per-class headers and the `Vary` merge;
`PortalEndpointTest` pins the session-bearing `no-store`; `PortalIT` asserts `max-age` and `Vary: Cookie` on the
anonymous page against the native image; `HtmlErrorPageIT` asserts `no-store` on every error page.

*Assertion.* A response rendered for an authenticated session is `no-store`; a session-free page carries
`Vary: Cookie` whenever the BFF runtime is active; no portal response carries `Set-Cookie` of its
own.

[#html-04]
=== HTML-04 -- Open redirect via a catalog `entry`

A catalog link names where a trusted gateway page sends the browser. If `entry` can name another
origin, directly or through a spelling the reader did not recognise as foreign, the portal becomes a
phishing relay (CWE-601), exactly as a gateway-answered redirect would (<<gw-13>>).

*Evidence.* The same URL-parser disagreement <<gw-13>> records: a leading `//` is scheme-relative, a
backslash is parsed as `/` by browsers, and percent-encoded separators are decoded by intermediaries.

*Control.* `entry` is fixed configuration, never request-derived, and is reviewed once at boot. The
schema requires a single leading `/` and refuses `//`, backslashes and control characters. The
validator additionally refuses a percent-encoded `/` or `\` and a path part the cui-http URL path
review refuses, for every enabled endpoint. The refusal names the endpoint and never echoes the value.
The rendered `href` is HTML-escaped (<<html-01>>). The portal's own login link carries the portal path
as a fixed `returnUrl`, which the login endpoint's same-origin rule governs (<<bff-02>>).

*Status:* COVERED. `ConfigValidatorPortalTest` pins every refused spelling and the admitted forms.

*Assertion.* A catalog `entry` that is not an origin-relative path on the gateway's own origin fails
the boot.

[#html-05]
=== HTML-05 -- Information disclosure in HTML error pages

A rendered error page has room for detail a problem body never had: an exception message, a problem
detail, an upstream address or a stack trace. An error page that resolves the session would also put
the user's identity on a failure path.

*Evidence.* The same class as <<gw-12>>, which cites APISIX CVE-2022-29266 for a secret surfaced in an
error body.

*Control.* An error page's only request-derived input is the status code. The title comes from a fixed
per-status table, and the page never receives a problem detail, an exception message or an upstream
address, because the data model has no key for them. No session is resolved on a failure path, so the
page is always anonymous. A render failure falls back to the exit's current, detail-free shape and is
logged at debug level only.

*Status:* COVERED. `ErrorPageClassifierTest` pins the fixed title table; `PortalEndpointTest` pins
the anonymous error model; `HtmlErrorPageIT` asserts status, content type, the portal CSP and
`no-store` per reachable error class against the native image.

*Assertion.* An HTML error page carries the unchanged status and the fixed title only; it never names
a user, an upstream or an internal detail.

[#html-06]
=== HTML-06 -- Origin-response interception and content-negotiation confusion

If the gateway replaced an *origin's* error response with its own HTML page, it would hide the
upstream's contract from the client and could change what an API client parses. If negotiation keyed
on wildcards, a `fetch()` or REST client sending `+*/*+` would receive HTML instead of the
`application/problem+json` it expects, and a script could be handed markup it then inserts into a
page.

*Evidence.* Error-page interception at a proxy is a documented source of broken API contracts and of
masked upstream diagnostics. It is configuration-shaped rather than tied to one CVE.

*Control.* Only gateway-originated errors are eligible, and eligibility is an exhaustive,
compile-checked classification. A new event type or exit fails compilation until it is classified. The
eligible set is a missing scope or failed CSRF check (`403`), an unrouted address, a `Host`
reserved for passthrough or a `source: directory` asset miss (`404`), a method outside the route's
allowlist (`405`), a body over the route cap (`413`), an upstream failure, an
open circuit or an upstream timeout (`502`/`503`/`504`), and a failed OIDC callback. On an address
no route serves, the two `404`s of the unrouted address and of a reserved `Host` negotiate alike,
so the body shape does not tell them apart
(link:adr/0059-Routing_rejections_report_under_their_own_ROUTING_problem_category.adoc[ADR-0059]). Every relayed
origin response, the `source: upstream` asset relay, the gRPC and WebSocket relays, a relay that failed
after the response head, the admission `503`, gRPC trailers-only rejections and unexpected internal
failures keep their shape. HTML is offered only when `Accept` lists `text/html` explicitly with a
quality above zero; wildcards never qualify. The status is identical either way.

*Status:* COVERED. `ErrorPageClassifierTest` pins the classification and the `Accept` parsing;
`GatewayEdgeErrorPageTest` pins the negotiation at every error writer; `HtmlErrorPageIT` asserts
against the native image that `Accept: application/json` keeps the problem body with the same status
and that a relayed origin error with `Accept: text/html` passes through unchanged.

*Assertion.* A relayed origin response is never replaced; a request without an explicit
`text/html` range never receives an HTML error page; the status is the same for HTML and JSON
answers.

== Gaps to close

The GAP/PARTIAL rows are where a *documented, real-world* failure class is not yet nailed
down. Closing them is the whole point of this exercise. Each is a small, additive change:

. *GW-01 -- make the single-canonical-path invariant explicit and tested.* cui-http
  already hands back a canonical path; the gateway's job is to route, verb-gate, auth-select,
  `allowed_paths`-match, and forward on *that same* value (never the raw URI), plus decide the
  encoded-slash policy and handle matrix `;` params (both left open by cui-http). Assertion: an
  encoded-traversal/encoded-slash/matrix-param corpus proves no authorize-as-public /
  dispatch-to-protected divergence (upstream count = 0). Dominant gateway CVE class; the
  direct fix for the code-review raw-vs-normalized finding.
. *GW-08 -- pin HTTP/2 abuse bounds.* Verify and assert stream-creation/reset
  rate limiting (Rapid Reset), CONTINUATION frame count/size bounds, and non-forwarding of
  client `Upgrade: h2c`/`Connection` to the upstream.
. *GW-06 -- fail-closed SNI + behaviour tests.* Make explicit: empty/fragmented SNI
  takes the strict policy or rejects (never a permissive default); the full ClientHello is
  reassembled before SNI routing; every security-gating boolean has a *behaviour* test (a real
  handshake fails when it must), not just a flag-read. The upstream-verify boolean is *done* --
  `egress_tls.upstream_verify_hostname` is proven by a matched pair of gateway instances plus an
  untrusted-upstream leg that pins the relaxation's scope
  (link:adr/0040-Upstream_hostname_verification_is_a_global_egress-TLS_knob_bound_at_client_construction.adoc[ADR-0040]).
  `egress_tls.jwks_verify_hostname` is likewise *done* -- read by the token-validator producer and
  proven by the same three-legged shape at unit level, with its collision against an
  `http`-sourced issuer's per-issuer `jwks.tls_profile` refused at boot
  (link:adr/0041-The_JWKS_hostname-verification_knob_is_the_librarys_own_passthrough_and_its_sslContext_collision_is_refused_at_boot.adoc[ADR-0041]).
  `egress_tls.oidc_verify_hostname` is *done* on the same terms for the BFF back-channel, with its
  `oidc_tls_profile` collision refused at boot
  (link:adr/0045-The_BFF_OIDC_back-channel_posture_is_pinned_through_the_librarys_own_passthrough_under_peer_egress-TLS_keys.adoc[ADR-0045]),
  and every outbound TLS client is held to an explicit posture by a standing fitness function.
  What remains under this heading is the mTLS-require boolean and the two SNI rules above.
. *BFF-13 -- pin the callback parsing *usage rule* with a test.* The engine already rejects
  HPP and the gateway already calls `CallbackParameters.parse(rawQuery)` on the raw query
  (never the duplicate-blind `of(Map)`); what is missing is a test asserting a
  duplicate-`code` callback is rejected. Scope enforcement is likewise the gateway's -- the
  validation lib exposes `providesScopes()` but enforces nothing; the gateway's bearer and session
  checks and their accepted residuals are recorded under <<bff-15>>.
. *Cross-cutting -- adopt this document as a release gate.* A security-audit sweep validates
  that every COVERED/PARTIAL assertion has a passing test and every GAP is closed or
  explicitly risk-accepted; consider a short ADR recording "CVE-derived validation baseline
  is a 1.0 release gate".

None of these change the architecture; they are hardening assertions on features that already
exist (mostly *wiring* audited library controls correctly), sourced from failures other
gateways and OAuth stacks actually shipped.
