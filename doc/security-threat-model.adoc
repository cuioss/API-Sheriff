= API Sheriff -- Threat Model & CVE-Derived Validation Baseline
:toc: left
:toclevels: 3
:sectnums:
:sectnumlevels: 2

This document is the security contract API Sheriff validates *against*. It has three
parts:

. *Trust boundaries and STRIDE* -- the assets, the boundaries a request crosses, and the
  threat categories per boundary.
. *Failure catalogue* -- every failure class that has produced a real, cited CVE in a
  comparable API gateway, reverse proxy, or OAuth/OIDC stack (the gateways surveyed in the
  link:features-analysis.adoc[competitive analysis] -- APISIX, Kong, Traefik,
  KrakenD, Tyk, Gravitee -- plus the canonical proxy/JOSE CVEs). Each class carries the
  transferable lesson, the API Sheriff control that defeats it, a *status*, and a *testable
  assertion*.
. *Validation matrix* -- every control mapped to the component that owns it and the assertion
  that proves it, so this document doubles as a release gate.

[IMPORTANT]
====
*How to use this document.* It is normative for the security posture, not for behaviour --
where a control's behaviour is specified, link:configuration.adoc[the configuration model]
and link:architecture.adoc[the architecture] govern; this document names the *threat* the
control exists to answer and the *assertion* that proves it still does. Every catalogue
entry's assertion is meant to become a test (unit, integration, or benchmark) so a
regression re-opens a known-historical hole loudly. Status values:

* *COVERED* -- an ADR, a library, or delivered code owns the control; the assertion has (or
  will have) a test.
* *PARTIAL* -- the control exists but the assertion is not fully pinned, or only one half of
  an equivalence class is closed.
* *GAP* -- nothing yet owns this control; the "Gaps to close" section collects these as
  recommended hardening work (the original goal: learn from others' failures *before*
  shipping the feature).
* *ELIMINATED* -- the failure class does not apply because a design decision removed the
  surface entirely (recorded so an audit can confirm the surface stays removed).
====

== Foundation libraries (what is already owned upstream)

API Sheriff is not implementing these controls from scratch -- two audited libraries own
large parts of the catalogue, and the residual gateway work is exactly the part they
deliberately leave to the application. Attribution below reflects a 2026-07-17 source review
of the local `cui-http` and `TokenSheriff` trees. The versions this project resolves are
`cui-http` 3.0 -- overridden in the root `pom.xml` above the parent-managed 2.2 -- and
`TokenSheriff` 0.9.5, the release whose JWKS-loader and client-configuration builders both carry the
hostname-verification passthrough the gateway binds its two identity-provider back-channels through
(see <<gw-06>>).

*`cui-http` (inbound filtering + forwarded resolution) provides:* per-component path
canonicalization returning a *normalized* path (`URLPathValidationPipeline` -- decodes
percent-encoding, collapses `..`/dot-segments and duplicate slashes, rejects
traversal/`%00`/overlong/backslash *unconditionally*); header name/value CR/LF/NUL rejection
(`CharacterValidationStage`, unconditional); collection count + length limits
(`RequestCollectionValidator`, `LengthValidationStage`); the forwarded-header trust engine
(`ForwardedHeaderResolver` -- CIDR-validated `trustedProxies`, right-to-left drop-untrusted,
per-value sanitization, canonical `X-Forwarded-*`/RFC 7239 regeneration, NiFi aliases); the
shared `SecurityEventCounter`; and reusable attack corpora (OWASP/ZAP/ModSec-CRS/Apache/Nginx/
IIS-CVE databases + encoding/traversal generators) shipped in its *test-jar*.

*`cui-http` deliberately does NOT provide* (gateway/web-server owns): request-level *framing*
/ smuggling defence (CL vs TE, chunked, HEAD-with-body, hop-by-hop `Connection` abuse) --
explicitly "infrastructure layer"; a *streaming* body-size limiter (the `BODY` pipeline is
removed; `max_body_bytes` must be a gateway stream counter); *matrix-param (`;`) handling*;
an *encoded-slash policy* (`%2f` is decoded to `/`); and the *TCP-peer gate* (the resolver
trusts headers, not the socket -- it never sees the peer address). It also does not reject
`0.0.0.0/0`/`::/0` (the gateway's configuration validator does).

*`token-sheriff-validation` provides, fail-closed:* JWT algorithm pinning
(`SignatureAlgorithmPreferences` -- allow-list, `none`/HMAC/embedded-`jwk` rejected, so
RS256->HS256 key-confusion is structurally impossible), an *in-library* guard for the
CVE-2022-21449 ECDSA "psychic signature" (`r|s == 0` rejected before the JDK verifier) and a
<2048-bit RSA floor; `iss`/`aud`/`azp`/`exp`/`nbf`/`iat`(+skew)/`sub` validation; JWKS from
the configured/discovered endpoint *only* (token-supplied `jku`/`x5u`/`jwk` ignored) behind
an `EgressPolicy` that blocks loopback/link-local/cloud-metadata on the initial fetch *and
every refresh* (DNS-rebinding-safe), with TTL cache, rotation grace, and unknown-`kid` that
cannot drive a fetch storm; the 4-arg `AccessTokenRequest(token, headers, uri, method)` for
DPoP; server-side DPoP proof validation + replay cache; a Quarkus JWKS-readiness health
check; an RFC 9457 exception mapper that interpolates no secret/message. It ships a
`generators`-classifier test-jar with adversarial token/key corpora (`JkuX5uAttackTest`,
`PsychicSignatureAttackTest`, ...).

*`token-sheriff-client` (BFF engine) provides, fail-closed:* auth-code + PKCE (`S256` only,
`plain` not implementable); `FlowContext` bundling `state`+`nonce`+PKCE-verifier+`redirect_uri`
(+`acr_values`/`max_age`) with constant-time `state`/`nonce` verification; RFC 9207 `iss`
mix-up defence (incl. absent-`iss` rejection); the refresh grant with rotation (`RefreshFlow`)
and a classification of a refused refresh by what the provider did to the presented token
(`RefreshFlow.classify`), plus an RFC 7009 `RevocationClient`; RP-initiated logout with *exact-match* `post_logout_redirect_uri`
and state verify (`PostLogoutRedirectValidator`); RFC 9470 step-up parsing/re-drive;
callback HPP defence (`CallbackParameters.parse(rawQuery)` rejects duplicate `code`/`state`);
DPoP/mTLS sender-constraint requesting with downgrade rejection.

*The engine/validation libs deliberately leave to the gateway* (the true BFF residual): the
*back-channel logout-token receiver and its `events`/`sub`/`sid`-required + `nonce`-forbidden
checks* (no library support at all -- signature reuse only); *persistence* of the
`FlowContext` (session-bound, single-use discard, return-URL -- the engine gives the DTO
shape, not the store); the *concrete `TokenStore`* (server session vs encrypted cookie);
*scope enforcement* (the lib exposes `providesScopes()`/`getScopes()` but enforces nothing);
and calling `CallbackParameters.parse(rawQuery)` on the *raw* query (the `of(Map)` path cannot
re-detect duplicates); the *disposition* of a classified refresh failure and the per-session
single-flight around the refresh (`TokenRefreshCoordinator`). *Refresh-token reuse detection* is
owned by neither the libraries nor the gateway: it is the identity provider's strict rotation
(<<bff-08>>).

This attribution is folded into the *Owner* column of the validation matrix and the per-entry
status below.

== Assets

What an attacker wants, ranked by blast radius:

[cols="1,3"]
|===
| Asset | Why it matters

| Upstream reachability
| The gateway is the only sanctioned path to the backends. Reaching an upstream *without*
  passing auth/filtering is the top-line failure -- every "auth bypass" CVE below is an
  attack on this asset.

| Mediated tokens (BFF variants)
| Access / refresh / ID tokens held server-side (session mode) or inside the encrypted
  cookie (cookie mode). Theft = account takeover; leakage to the browser defeats the entire
  BFF rationale.

| Session / flow secrets
| Session-id cookie, the pending-authorization record (`state`/`nonce`/PKCE verifier), the
  cookie encryption key(s). Forgery or replay = impersonation.

| Client identity signal
| The real client IP / scheme the gateway asserts to upstreams via regenerated forwarding
  headers. Spoofing it corrupts every downstream IP-based decision.

| Configuration integrity
| The immutable route table and policy. There is no runtime mutation surface by design (see
  GW-10); the boot-time config *is* the trust anchor.

| Availability
| A single process fronting everything. Resource-exhaustion classes (GW-07, GW-08) target
  this.
|===

== Trust boundaries

A request crosses these boundaries; each is a place a control must hold.

[cols="1,2,3"]
|===
| # | Boundary | What is untrusted across it

| B1
| Client -> TLS edge
| Everything: TLS ClientHello/SNI, all request bytes, framing, every header including
  `Forwarded`/`X-Forwarded-*`/`Connection`, the raw path and its encoding, the body.

| B2
| TLS edge -> pipeline (terminated L7)
| The normalized request. The boundary's job is to hand the pipeline *one* canonical form
  and reject ambiguity (framing, encoding) here.

| B3
| Pipeline -> upstream (data plane)
| The gateway is now the client. What it *emits* is trusted by the upstream, so the gateway
  must strip inbound trust signals and regenerate its own (forwarding headers, mediated
  bearer). The upstream's *response* is untrusted coming back.

| B4
| Gateway <-> IdP (control plane, BFF)
| OIDC discovery/JWKS/token/revocation/logout traffic. Tokens and logout tokens received
  here are untrusted until validated; JWKS key sources must be pinned (no token-supplied
  `jku`).

| B5
| Browser <-> BFF session
| The session cookie and any BFF-API request it authenticates. Cross-site requests carry the
  cookie ambiently (CSRF); the cookie itself is a theft target.

| B6
| Operator -> configuration
| Config files are operator-authored (semi-trusted) but env-substituted values and secrets
  cross a boundary; a config that would serve traffic in a partially-valid state is a
  failure (fail-closed boot).

| B7
| Data-plane network -> management surface
| Health/metrics on the management port. Must not be reachable from, or confused with, the
  public data-plane port; there is no admin/mutation API to expose (GW-10).
|===

.Boundary geometry
----
        B1                B2                      B3
client ----> [ TLS edge ] --> [ L7 pipeline ] --------> upstream
  |          (terminate/         (normalize,      (regenerated
  |           SNI split)          filter, auth,     headers,
  |                               forward policy)    mediated bearer)
  |                                   |  ^
  |  B5 (session cookie / BFF API)    |  | B4 (OIDC: discovery/JWKS/token/logout)
  +-----------------------------------+  +--> IdP

  B6 operator --> [ immutable config, fail-closed boot ]
  B7 management port (health/metrics) -- never on the data-plane port, no mutation API
----

=== Residual risk: plain-HTTP termination behind an external hop (B1)

B1 is drawn assuming the gateway *is* the TLS edge. A deployment that sets
`QUARKUS_HTTP_INSECURE_REQUESTS=enabled` moves that edge outward onto a separate terminating hop, and
B1 splits in two: the client reaches the hop over TLS, and the hop reaches the gateway in
*cleartext*. This is a supported mode, and the split is the point of it -- but it relocates part of
the boundary's guarantee out of the gateway and into the surrounding topology, which is what makes it
a residual risk rather than a control.

*What the gateway no longer guarantees on the hop-to-gateway leg:* confidentiality and integrity of
every request and response byte, and the authenticity of the client-identity signal. The gateway
cannot observe tampering on a link it does not terminate, and its immediate TCP peer is the hop
rather than the client, so client-address attribution rests entirely on
`forwarded.trusted_proxies` naming that hop correctly.

*What the topology must guarantee in exchange:*

* The hop and the gateway share a network segment no untrusted party can observe or inject on. A
  cleartext leg across anything wider is an unencrypted gateway with extra steps.
* The hop terminates TLS itself, so the client-facing half of B1 is unchanged from a client's point
  of view.
* The hop's address is the one entry in `forwarded.trusted_proxies`, declared as a `/32`. A range
  wide enough to contain a client hands that client's own forwarding claim to every upstream
  IP-based decision -- the *Client identity signal* asset, spoofed at the boundary that was supposed
  to establish it.

The gateway does not merely document this posture; it refuses the combinations that cannot be part of
it. Inbound mTLS and an ADR-0017 passthrough topology are both rejected at boot alongside the opt-in,
as is declared server key material, because each would leave a declaration in force that the mode
makes meaningless. The BFF is likewise unavailable on a plain port a browser reaches directly: every
session and binding cookie carries `Secure` unconditionally. Both verdicts, and the two others this
mode carries, are enumerated in
link:user/tls-edge.adoc#_interactions_with_the_rest_of_the_edge[TLS edge -- What this mode does to
the rest of the edge]; they are not restated here.

== Gateway failure catalogue

Each class: the mechanism, the *cited real CVEs* that prove it is not theoretical, the API
Sheriff control, its status, and the assertion to test. CVE IDs marked *(unverified)* were
sourced from advisory aggregators but not confirmed on an NVD/GHSA primary page during
research -- cite the *class*, not the number, until confirmed.

[#gw-01]
=== GW-01 -- Path normalization / router-vs-enforcement desync (auth bypass)

*The single most recurrent gateway CVE class.* The router matches on one representation of
the path (raw, or partially decoded) while auth/block enforcement -- or the backend --
acts on a different one, so a request skips the control bound to the path it ultimately
reaches.

*Evidence.* Traefik: CVE-2025-47952, CVE-2025-66490, CVE-2026-40912 (StripPrefixRegex
Path/RawPath length desync), GHSA-xf64-8mw2-4gr2 (StripPrefix), GHSA-cxjq-mrr5-89rv
(ReplacePathRegex) -- six-plus advisories in ~14 months. APISIX CVE-2021-43557 (`uri-blocker`
checked raw `request_uri`, router matched normalized). Kong CVE-2021-27306 (JWT route bypass
via `/public/../api`) and the external-authz path-traversal (Kong forwards un-normalized
path, partial `%2E`/`%2F` decode). Envoy CVE-2021-29492 (`%2F`/`%5C` not decoded ->
RBAC/JWT bypass). Systematized by Orange Tsai, "Breaking Parser Logic" (Black Hat 2018).

*Control.* `cui-http`'s `URLPathValidationPipeline` already returns a *canonical* path
(percent-decoded, dot-segments and duplicate slashes collapsed, traversal/`%00`/overlong/
backslash rejected unconditionally). The gateway's residual job is the *invariant*: route,
the `allowed_methods` verb gate, auth selection, `allowed_paths` matching, *and* the upstream
remainder all consume that *same* canonical output -- byte-identical -- never the raw
request-URI. Two things cui-http leaves to the gateway and this control must add: an
*encoded-slash policy* (cui-http decodes `%2f` to a structural `/`; the gateway decides
reject-vs-accept and applies it before routing) and *matrix-param (`;`) handling* (not
touched by cui-http). This directly answers the code-review finding that the interim
`ProxyRoute` looks the route up on the raw URI but relies on the router's normalized match
(raw-vs-normalized divergence).

*Exact routes consume the same canonical path.* A `match.path` route compares its declared path
against that canonical output as an un-normalized string, and a prefix route matches it on a segment
boundary -- neither re-reads the raw request-URI. The one deliberate asymmetry is the trailing slash,
which an exact route treats as significant (`/a` and `/a/` are distinct addresses) and which the
canonical path preserves; the integration suite asserts both spellings of one address through the
real pre-route floor, the slash-less one answered by an exact redirect route and the slash form
falling through to the enclosing prefix route.

*And the enclosing route is bound to the same anchor.* That fall-through is the intended behaviour
only while the route it falls through to carries the same posture. The ADR-0007 rules that pair
routes with anchors are *declaration*-scoped -- they judge a route by where its own match key sits --
so a route sitting outside and *above* an anchor was judged by none of them, while selection still
let it answer addresses inside the namespace. With exact routes that gap is reachable: an anchor
whose only member is `path: /admin` claims exactly one address, and `/admin/` and `/admin/x` land on
whatever encloses it -- served with *its* auth posture and *its* `security_headers` block, which is
the router-vs-enforcement desync of this entry expressed in configuration rather than in parsing. The
boot now closes it with the mirror rule: a prefix route whose namespace strictly contains an anchor's
`path_prefix` without declaring that anchor fails the boot, unless a prefix route declared at the
anchor's own `path_prefix` covers the namespace -- in which case longest-prefix selection gives that
member every address inside it. Coverage requires the member to match its whole namespace and not
merely to name it: a member narrowing on a non-path `match` dimension is not accepted as covering, so
no address in an anchor namespace is served by a route outside the anchor.

*The mirror rule reaches every protocol, including `grpc`.* The two declaration-scoped rules waive
`protocol: grpc` routes, because a service-rooted gRPC method path can never nest inside a gateway
namespace on a segment boundary -- an argument about where the route's own match key sits. The mirror
rule asks the opposite question, and nothing constrains a gRPC route's declared match key to a bare
service path. Selection is protocol-blind (the route table looks a request path up on the path alone,
and the matcher carries no protocol dimension), so a gRPC route declaring a broad `path_prefix` would
answer plain HTTP requests inside the swallowed namespace with its own posture. Waiving it there
would reopen precisely this entry's desync in configuration, so it is not waived.

*Coverage requires an unnarrowed member.* The coverage exception was first written path-geometrically
-- prefix equality alone -- which left the bypass reachable one dimension over: a member declared at
the anchor prefix but narrowed to `methods: [GET]` marked the namespace covered while every other verb
matched no anchored route and fell through to the enclosing one, answered under *its* auth and
`security_headers`. A `host` or `headers` narrowing does the same, and the header case is the easiest
of the three to reach, since the complement is any request that simply does not send the header.
The rule therefore tests both halves: the member's normalized match key equals the anchor prefix *and*
it narrows on no dimension the route matcher ANDs with the path. The matcher is the declaring source
for what those dimensions are (`match.methods`, `match.host` and `match.headers` at present), and the
predicate deciding it lives on the match model beside them, with a contract test asserting that every
component of that model is classified -- so a dimension added later cannot silently reopen this.

*Status:* PARTIAL. Pipeline stage 1 validates the raw path and stages 2-3 act on the
normalized path, and anchor prefixes are normalized before the disjointness check -- but the
*invariant* is not stated explicitly anywhere, nor is the divergence tested. The assertion
below is the outstanding hardening item (see Gaps).

*Assertion.* For every encoded-traversal / encoded-slash / mixed-encoding / trailing-slash /
matrix-param variant of a protected path: the request is either rejected at B2 or is
routed, authorized, and forwarded against the *same* canonical path -- never authorized as
public and dispatched to a protected upstream. Upstream request-count = 0 on every bypass
attempt. A configuration whose anchor namespace is left uncovered while a broader route encloses it
fails the boot, and the same configuration with a prefix route at the anchor prefix boots
(`ConfigValidatorTest.AnchorRules`, rule 4b -- including the partial-coverage case, where an anchored
route on a sub-path only is not coverage). The same pair holds with the enclosing route declared
`protocol: grpc` (`ConfigValidatorTest.GrpcNamespaceExemption`), alongside the controls proving the
two declaration-scoped directions are still waived for it.

[#gw-02]
=== GW-02 -- HTTP request smuggling / desync

Front-end and back-end disagree on where a request ends (CL vs TE, bare-LF chunk
terminators, duplicate framing headers, HEAD-with-body, HTTP/2->1.1 downgrade), letting an
attacker's body become a second request on a pooled connection.

*Evidence.* HAProxy CVE-2021-40346 (htx integer overflow desync, all ACLs bypassed). Go
`net/http` CVE-2025-22871 (bare-LF chunk terminator). Node/llhttp CVE-2022-35256. OpenResty
`lua-nginx-module` CVE-2024-33452 (HEAD-with-body reinterpreted -- hit *both* Kong and
APISIX). Kong CVE-2026-6338 (CL.0: attacker lists `Content-Length` in `Connection:` so Kong
drops it). Netty CVE-2021-21295 (missing CL validation on h2->h1 downgrade). Context:
PortSwigger "HTTP/1.1 Must Die" (2025).

*Control.* Enforce a single unambiguous framing at B2: reject requests bearing both
`Content-Length` and `Transfer-Encoding`; require strict CRLF and RFC-9112 chunk parsing;
reject a body on a bodyless method; re-derive/validate framing after any header mutation
(the `Connection`-list hop-by-hop cleanup must never remove `Content-Length`/
`Transfer-Encoding` -- see GW-03); never pool an upstream connection whose framing wasn't
fully validated. Prefer end-to-end HTTP/2 where possible.

*Status:* GAP. Quarkus/Vert.x/Netty reject much of this by default, but API Sheriff sits
*behind* other proxies (the whole forwarded-header design assumes it), so framing agreement
is a first-class requirement, not an inherited default. Nothing asserts it yet.

*Assertion.* A request with both `Content-Length` and `Transfer-Encoding`, a HEAD/GET with a
body, or a `Connection: Content-Length` cleanup attempt is rejected (400) and never produces
two upstream requests; a smuggling test corpus (CL.TE/TE.CL/TE.TE/CL.0) run through the
gateway produces zero desyncs.

*Operator-relaxable leg (bounded).* The gateway-wide
`security_defaults.allow_get_with_content_length_body` opt-in (default `false`) admits a
`Content-Length`-framed body on `GET`, for upstreams whose API takes one (Elasticsearch `_search`).
It narrows the "GET with a body" clause of the assertion above *only* for that shape, and only when
explicitly enabled. The boundary is drawn where the smuggling risk is, not where the convenience is:

* `Transfer-Encoding` on a bodyless method stays rejected *unconditionally* -- chunked framing on an
  otherwise-bodyless method is the desync primer this control exists to constrain, and the motivating
  clients send `Content-Length`-framed bodies, so excluding it costs the use case nothing. No
  configuration can relax it.
* The CL+TE coexistence rule, the duplicate/comma-listed `Content-Length` rule and the
  `Connection`-list framing-strip rule are independent checks unaffected by the opt-in; the CL+TE
  check runs *before* the body-on-bodyless-method check, so a `GET` carrying both is still rejected.
* `HEAD` with a body remains rejected on every leg.

The residual exposure is therefore a well-framed, unambiguously-delimited `GET` body -- a shape both
front-end and back-end agree on, which is what makes it not a desync vector. With the key omitted or
`false`, every rejection above is preserved bit-for-bit.

[#gw-03]
=== GW-03 -- Header injection (CRLF) and hop-by-hop header abuse

(i) CR/LF/NUL in a header name/value splits the message (response splitting). (ii) A client
names a *trust* header inside `Connection:` so the proxy strips it before the backend sees
it -- deleting the origin's client-IP or auth signal.

*Evidence.* Apache httpd CVE-2022-31813 (client `Connection` handling suppresses
`X-Forwarded-*` to origin, defeating backend IP-auth). Netty CVE-2022-41915 (`DefaultHttpHeaders`
iterator path skipped value validation -> CRLF response splitting). Traefik CVE-2024-45410
(client names Traefik's own `X-Forwarded-*` as hop-by-hop). Kong CVE-2026-6338 (framing-header
strip abuse, GW-02).

*Control.* cui-http's `CharacterValidationStage` rejects CR/LF/NUL in header names and values
*unconditionally* on the *ingress* path: every inbound header is fed through it before any stage
reads one. The response direction carries no equivalent re-validation, and saying so is the
honest statement of the control's reach -- the gateway does not re-run `CharacterValidationStage`
over upstream response headers. Both response paths (`edge.ResponseStage` for the streamed proxy
relay, `asset.AssetResponseEnvelope` for the buffered asset envelope) copy the source's remaining
headers through once the gateway-owned never-relay set below has been applied. That direction is
bounded by *which names* cross rather than by re-checking their characters, so the residual is
scoped to a configured upstream that is already inside the gateway's trust boundary rather than
to client-supplied input. Never let a client `Connection:` header steer stripping of framing or
trust headers.

The hop-by-hop and trust-header lists are *gateway-owned and enumerated in full per direction*,
never derived from a sibling list and never taken from what a client names
(link:adr/0037-The_gateway-owned_header_sets_are_enumerated_per_direction_and_bounded_by_knowledge.adoc[ADR-0037]).
Two properties carry this control:

* *The request-direction never-forward set applies under every forward mode* -- including the
  permissive forward-all baseline. `Authorization` is its single re-admittable member (only on a
  route declaring a positive-list naming it); `Cookie` is absolute against client input. No route
  configuration re-admits the hop-by-hop, framing or gateway-owned names from the request. The one
  path around the set is an operator's *static* `set_headers` value, which is merged after the
  strip and carries no caller-supplied material.
* *The forwarded header set is built by regeneration, never by editing the client's map.* The
  client's `X-Forwarded-*` / `Forwarded` copies are skipped on *every* mode, forward-all
  included, so a permissive route is not a way to smuggle a spoofed chain upstream (GW-04).

*The equivalence class is carried in the set, not left to the operator.* The old allow-list-only
forward model dropped *everything* an operator did not enumerate, which incidentally also dropped
non-canonical spellings a client invented -- an `X_Forwarded_For`-style underscore variant that
cui-http does not canonicalize to the hyphenated name, or a vendor alias such as `X-Real-IP`.
Forward-all removes that incidental protection, so the protection is now stated: the vendor
aliases are members of the request-direction never-forward set in their own right, and both that
set and the regeneration skip match on the *separator-folded* name, so every `-`/`_` spelling of
either set's names is withheld under every mode without an operator entry (see
link:#gw-04[GW-04] for why the class is closed by folding rather than by enumeration). The
aliases sit in the never-forward set rather than beside the canonical names because the gateway
does not *regenerate* them -- the canonical names are what it emits, the aliases are
claims about provenance only the gateway is entitled to make. `set_headers` is unaffected: an
operator fronting a backend that reads `X-Real-IP` still sets it deliberately, because the strip
governs client input and configuration is not client input.

*Status:* PARTIAL. Header CR/LF/NUL is cui-http (COVERED); the per-direction gateway-owned sets
and the every-mode regeneration skip are pipeline stage 5 and are pinned exhaustively by their
own tests; the hop-by-hop-abuse-cannot-strip-framing property (the GW-02 tie-in) is not
asserted, which is the one leg keeping this row off COVERED.

*Assertion.* CR/LF in a header value is rejected; a client `Connection: X-Forwarded-For` (or
`Content-Length`) does not cause the gateway to drop the regenerated forwarding header or the
framing header; a client-sent `X-Forwarded-For`, `Cookie` or `Authorization` never reaches the
upstream on a forward-all route; response headers are validated before write.

[#gw-04]
=== GW-04 -- X-Forwarded / trusted-proxy spoofing

IP-based auth, rate limiting, or "internal caller" trust reads a client-settable forwarding
header as source identity. Any client sets `X-Forwarded-For: 127.0.0.1` and becomes
"internal".

*Evidence.* APISIX CVE-2022-24112 -- the flagship gateway RCE: the `batch-requests` plugin
let the caller set `X-Real-IP` on re-dispatched sub-requests, the Admin-API IP allowlist
trusted it, loopback was forged, chained with the default admin token (GW-10) to
unauthenticated RCE. ZooKeeper CVE-2024-51504 (`IPAuthenticationProvider` honors client
`X-Forwarded-For` by default). Traefik CVE-2026-35051 / CVE-2026-54764 / CVE-2026-39858 /
CVE-2026-54763 *(unverified)* -- a chain of *incomplete* forwarded-header-stripping fixes
(each patched one spelling/case/underscore/alias variant while a sibling survived).
OAuth2-Proxy CVE-2026-40575 *(unverified)*. The "too-broad-trust" bug the
link:features-analysis.adoc[feature analysis] already calls out.

*Control.* Never derive trust from a client-settable header. Gate `Forwarded`/`X-Forwarded-*`
on a *TCP-peer* check against an explicit trusted-proxy CIDR list (ADR-0003), parse the chain
right-to-left discarding untrusted entries, and *regenerate* canonical output -- never
append. Validate the CIDR list at boot (reject `0.0.0.0/0`, `::/0`, and split-range
trust-all equivalents like `0.0.0.0/1`+`128.0.0.0/1`; reject malformed CIDRs). Canonicalize
header names across the *whole* equivalence class (case, `-`/`_`, aliases) before stripping,
or the strip is incomplete -- the Traefik fix-chain is the cautionary tale.

*Status:* COVERED. ADR-0003 + pipeline stage 5 (TCP-peer gate, drop-and-regenerate) + the
configuration validator (CIDR parsing, split-range trust-all rejection). The client's canonical
`X-Forwarded-*` / `Forwarded` copies are skipped under every forward mode, forward-all included,
so the *emitted* chain is always the gateway's own.

*Trusted-proxy breadth below trust-all is warned, not refused, and the residual is chosen rather than
safe*
(link:adr/0044-Trusted-proxy_breadth_is_warned_beyond_one_provisioned_network_and_refused_only_at_the_whole_address_space.adoc[ADR-0044]).
The TCP-peer gate is only as narrow as the list it reads, and every host inside a trusted range that
can reach the gateway directly can spoof the client identity downstream decisions rely on. Three
outcomes cover the whole range of breadth. A range set whose members together cover an address
family is *refused at boot*, complementary halves included. A single entry spanning more than one
operator-provisioned network -- broader than an IPv4 `/16` or an IPv6 `/48` -- boots with
`WARN ApiSheriff-102`, which is what catches the realistic mistake: a whole private block such as
`10.0.0.0/8` or `172.16.0.0/12` pasted in. An IPv4 `/16` (65,536 addresses) or an IPv6 `/48` boots
with *no* signal. That is a recorded, accepted exposure -- a legible range an operator chose, left
un-warned so the warning keeps its meaning on the configurations that need it -- and it is not a
statement that such a range is safe.

*A range supplied through an environment variable meets exactly these rules.* The validator reads
the value after `${VAR}` substitution and cannot tell it from a literal, so a provenance-keyed
refusal is not expressible, and a source-blind stricter threshold would refuse legitimate pod-network
trust while stopping nothing the warning and the trust-all refusal do not already surface. The
residual therefore applies to the environment path unchanged, with one aggravation stated rather than
implied: a substituted range passed through no reviewed change to `gateway.yaml`, so the boot warning
is the only signal it ever gets. The thresholds are held by a parameterised test carrying a warning
row past each boundary and a silent row exactly at it, asserted by identifier and range.

*The equivalence class beyond the canonical names is covered too, and it is closed by a rule
rather than by a list.* Two sets hold the names, split by *which question each name answers*: the
regeneration skip holds the canonical spellings (`x-forwarded-for`, `-host`, `-proto`, `-port`,
`-prefix`, `forwarded`) -- what the gateway *emits* -- and the request-direction never-forward set
holds the names it does not emit but must never *relay*, the vendor aliases `X-Real-IP`,
`X-Client-IP`, `True-Client-IP` and `CF-Connecting-IP`. The split is deliberate: filing a name the
gateway does not regenerate beside the ones it does would assert a relationship that is not there,
and would widen the untrusted-peer resolver mask with names the resolver never queries.

*Both sets are then tested on the separator-folded name* -- lower-cased with every `_` mapped to
`-` -- so each set closes its own names across the whole `-`/`_` class instead of listing the
variants. This matters because the class is larger than it looks: a two-separator name such as
`X-Forwarded-For` has *four* spellings (`X-Forwarded-For`, `X_Forwarded_For`, `X-Forwarded_For`,
`X_Forwarded-For`), and every backend that maps header names to CGI-style variables -- CGI,
FastCGI, WSGI and Rack all do -- resolves all four to one `HTTP_X_FORWARDED_FOR`. Enumerating
spellings would mean four entries per name and a fix the first time one was missed, which is
exactly the shape of the Traefik fix-chain in the evidence above: each of those CVEs closed one
spelling while a sibling survived. Folding before the membership test closes the class at once and
keeps it closed for any name a later edit adds to either set. `Forwarded` contributes no variant
at all -- it carries no separator to fold, so its underscore spelling is the canonical name the
regeneration skip already holds.

*Assertion.* A spoofed inbound `X-Forwarded-For`/`X-Real-IP`/`Forwarded` from a non-trusted
peer never influences the gateway's resolved client identity; the emitted chain is regenerated,
not appended; the canonical `X-Forwarded-*` / `Forwarded` names are skipped from the client copy
under *every* forward mode, forward-all included; each underscore variant and vendor alias is
withheld from the upstream under *both* forward-all and a negative-list that does not name it,
each leg carrying a matched positive control; every *mixed* `-`/`_` spelling of a forwarding name
or a vendor alias is withheld under forward-all, a negative-list *and* a positive-list naming it,
so the equivalence class is asserted closed rather than sampled; an operator's `set_headers` still
places such a name deliberately; a `0.0.0.0/1`+`128.0.0.0/1` config is rejected at boot; an entry broader
than `/16` or `/48` emits `ApiSheriff-102` while an entry exactly at either boundary does not.

[#gw-05]
=== GW-05 -- SSRF via proxy features / upstream control

A proxy feature lets the attacker influence the upstream destination (path-injected target,
user-supplied upstream, followed cross-host redirect) -> the gateway makes requests from its
trusted position to internal services / cloud metadata.

*Evidence.* Apache httpd mod_proxy CVE-2021-40438 (crafted URI-path selects attacker origin;
CISA Known-Exploited). The Capital-One-class metadata SSRF pattern.

*Control.* The upstream is a *fixed, boot-resolved topology alias* -- never influenced by
request content (link:adr/0004-topology-indirection.adoc[ADR-0004]). Resolved alias URLs are
restricted to `http`/`https` at boot. Redirect following is disabled
(`followRedirects(NEVER)` -- an SSRF-limiting default in the interim proxy, to be preserved).
On the *control plane* (B4 -- OIDC discovery/JWKS/token), `token-sheriff-validation`'s
`EgressPolicy` already blocks loopback/link-local/site-local/cloud-metadata targets on the
initial fetch and every refresh (DNS-rebinding-safe); keep its secure defaults and only widen
via `allowedEgressHost` for a trusted IdP. The gateway exposes that widening as the per-issuer
`token_validation.issuers[].jwks.allowed_egress_hosts` list in `gateway.yaml`: absent or empty
keeps `EgressPolicy.secureDefault()`, and each entry exempts exactly one host (host-exact, no
wildcard form). Operators should egress-restrict the gateway and
avoid pointing a topology alias at link-local/metadata ranges.

The `source: upstream` asset action (link:adr/0014-asset-serving-terminal-action.adoc[ADR-0014])
reuses this exact posture rather than opening a parallel fetch stack: a fixed, boot-resolved
topology upstream (never selected by request content), the `http`/`https` scheme allowlist,
`followRedirects(NEVER)`, and a bounded response size and read/connect timeout. A hostile asset
upstream can therefore neither redirect the fetch to an internal address nor be chosen by the
client; its response metadata is additionally overridden by the gateway-owned asset envelope
(fixed content type, stripped `Set-Cookie`, forced `no-store` for authenticated access).

*Status:* COVERED (design). No request-controlled upstream exists; the scheme allowlist is
enforced by the configuration validator; redirect-follow-off is a documented default; the
upstream asset source reuses the same fixed-topology + scheme-allowlist + no-redirect controls
(ADR-0014).

*Assertion.* No request input (path, header, body) can change the resolved upstream host; a
topology alias with a non-http(s) scheme fails boot; the data-plane client does not follow
upstream 3xx to a new host; the upstream asset source honours the same no-redirect and
fixed-topology guarantees and bounds the response size and timeout.

[#gw-06]
=== GW-06 -- TLS/SNI fail-open, upstream cert verification, mTLS bypass

Failure modes: empty/unresolved SNI falls back to a *permissive* default (mTLS not required);
a verify flag is silently inverted; SAN matching ignores SAN type or over-matches wildcards.

*Evidence.* Traefik CVE-2026-32305 (fragmented ClientHello -> empty SNI -> permissive default
TLS config, mTLS bypassed). Traefik CVE-2025-66491 (ingress-nginx `proxy-ssl-verify: on`
mapped to Go `InsecureSkipVerify: true` -- verification *off* for ~5 months). Envoy
CVE-2022-21656 (SAN type ignored -> wrong-CA cert matches), CVE-2020-15104 (wildcard SAN
matches nested subdomains). KrakenD CVE-2026-39821 (punycode `xn--example-.com` normalizes
to `example.com` -> host-based rule bypass).

*Control.* Fail *closed*: empty/unresolved SNI must take the strictest policy or reject,
never a permissive default. Reassemble the full ClientHello before routing on SNI (the
`NetServer` front must not decide on a partial record). For any security-gating
boolean (mTLS require, upstream verify), *test the behaviour* -- a real handshake fails when
it must -- not merely that the flag parsed. Verify upstream certs by default. Normalize
security-decision hostnames with a spec-conformant, tested routine.

*Status:* PARTIAL. The accept-time SNI split and mTLS are delivered
(link:adr/0017-Accept-time_SNI_split_at_a_dedicated_front_listener_passthrough_relays_opaquely_at_L4_everything_else_terminates_internally.adoc[ADR-0017]).
*Upstream certificate verification is delivered and behaviour-tested end to end* on the terminated
egress leg
(link:adr/0040-Upstream_hostname_verification_is_a_global_egress-TLS_knob_bound_at_client_construction.adoc[ADR-0040]):
verification is on by default, the `egress_tls.upstream_verify_hostname` relaxation is bound at all
three *Vert.x* egress client-construction sites, and `egress_tls.upstream_tls_profile` binds trust
anchors through a fail-closed resolver that refuses an unbound, trust-all or anchor-free profile at
boot; both postures are reported at boot by `WARN ApiSheriff-118` / `ApiSheriff-119` rather than
taking effect silently. One further terminated-egress leg -- the asset-origin fetch -- is outside
every key and is recorded below as a scope limit rather than folded into the claim. The
*assert-behaviour-not-flag* discipline this entry demands is discharged *for that key specifically*
-- an integration-stack matched pair of gateway instances differing in exactly that one boolean makes
a real handshake fail on one leg and succeed on the other. The *JWKS* half is now *delivered and
behaviour-proven* as well
(link:adr/0041-The_JWKS_hostname-verification_knob_is_the_librarys_own_passthrough_and_its_sslContext_collision_is_refused_at_boot.adoc[ADR-0041]):
`egress_tls.jwks_verify_hostname` is read by the token-validator producer and passed through to the
JWKS client's own hostname-verification setting on every `http` source, on both the true and the
false path, so the gateway's posture does not follow an upstream default change; the relaxed posture
is reported at boot by `WARN ApiSheriff-120`; and the one incoherent combination -- the relaxation
together with an *`http`-sourced* issuer's per-issuer `jwks.tls_profile`, which supplies an SSL
context the relaxation cannot act on -- is *refused at boot* with a configuration error naming both
keys and the issuer, rather than silently ignoring one of them. The refusal is scoped to `http`
sources because that is where the collision exists: a `file`-sourced issuer opens no TLS connection,
so there is nothing for either key to reach on that leg. The *BFF OIDC back-channel* is now
*pinned and behaviour-proven* too
(link:adr/0045-The_BFF_OIDC_back-channel_posture_is_pinned_through_the_librarys_own_passthrough_under_peer_egress-TLS_keys.adoc[ADR-0045]):
`egress_tls.oidc_verify_hostname` is passed through to the identity-provider client's own
hostname-verification setting on every build, the true path included, `egress_tls.oidc_tls_profile`
supplies that client's trust through the same fail-closed resolution core as the JWKS profiles, the
relaxed posture and a named profile are reported at boot by `WARN ApiSheriff-125` /
`ApiSheriff-126`, and the relaxation together with a profile is *refused at boot* naming both keys.
An explicit-posture fitness function now stands guard over every leg: it fails the build when
production code constructs an outbound TLS client without, in the same class, calling that client's
posture method, so a seventh leg cannot land unbound the way the sixth once sat unenumerated. The
*fail-closed-on-empty-SNI* rule and *full-ClientHello reassembly before routing* remain unpinned (see
Gaps), which is why this entry stays PARTIAL -- the verdict is unchanged and only its reason has
narrowed, from three outstanding items to two.

*The six TLS-terminating egress legs, re-derived from source.* Every claim in this entry is scoped
by this enumeration, which is taken from the client-construction sites rather than copied from an
earlier list. It is hand-written and can drift like the list it replaces; the fitness function above
is the guard that does not depend on it being complete.

[cols="1,2,2", options="header"]
|===
| Leg | Posture governed by | Proof

| 1. Vert.x default HTTP client
| `upstream_verify_hostname`, `upstream_tls_profile`

| 2. Vert.x forced-HTTP/2 (gRPC) client

Plain-TCP dials negotiate no TLS and are not legs here: the ADR-0017 passthrough relay and the
loopback health probe.

*Assertion.* A fragmented/empty-SNI ClientHello does not reach a passthrough or a
no-client-cert default -- it is terminated under the strict policy or rejected; enabling mTLS
causes a real no-cert handshake to fail (behaviour test); a punycode host that normalizes to
a passthrough SNI is caught by the same collision rule. On the egress leg, a terminated dial to an
upstream whose certificate does not name the dialled host *fails the handshake by default*, and
succeeds only on an instance that declares `egress_tls.upstream_verify_hostname: false` -- both
directions asserted by a real dial rather than by reading the flag back. A third dial pins the
*scope* of that relaxation: against the relaxed instance, an upstream whose certificate chains to no
trusted anchor is *still refused*, so the two mechanisms are proven uncoupled. The same three-legged
shape now covers `jwks_verify_hostname`: a JWKS fetch from an identity provider whose certificate
does not name the dialled host *fails by default* and succeeds only with the key set to `false` --
both directions by real handshake against one server, one certificate, one issuer and one key set,
with the flag as the single difference -- and a third dial pins the scope, refusing an IdP whose
chain reaches no trusted anchor while the flag is off. A falsification check backs the pair: removing
the production passthrough turns the relaxed leg red. The BFF OIDC back-channel carries the same
shape for `oidc_verify_hostname`: discovery against a server whose certificate does not name the
dialled host *fails by default* and completes only with the key set to `false`, a document declaring
no `egress_tls` at all resolves to the refusing posture, a correctly named certificate under an
untrusted root is still refused with the flag off, and the flag set to `false` together with a named
`oidc_tls_profile` fails with a configuration error naming both keys while the same flag without a
profile assembles cleanly. Removing the production passthrough turns the relaxed leg red, and
removing the pre-builder refusal turns the collision test red. Removing a posture call from a
construction site -- the asset-origin fetch's explicit context, the BFF
back-channel's hostname setting, the Vert.x options' host verification -- turns the fitness function
red naming that class.

*Residual risk (accepted).* `egress_tls.upstream_verify_hostname: false` is an operator-selectable
relaxation of a control this entry exists to defend, so the residual risk is recorded rather than
described away. What it gives up is bounded to *hostname matching on terminated egress*: chain trust
is unaffected, a self-signed or untrusted-CA upstream is still refused, and passthrough -- relayed at
L4 and never decrypted -- cannot be reached by the setting at all. What remains is real: with the
relaxation in force, an attacker who can both redirect the gateway's upstream connection *and*
present a certificate that chains to an anchor the gateway trusts is no longer stopped by the name
mismatch. That is a materially harder position to reach than serving any certificate, and it is the
whole of what the knob concedes. Three properties bound the exposure and are the basis of the
acceptance: the default is `true` and an omitted key resolves to `true` rather than to the type
default, so the relaxation is never reached by silence; it is global and therefore *visible* in one
place in `gateway.yaml` rather than buried per route; and the scope claim is proven by the untrusted
dial above rather than asserted. The mitigation for an operator who needs a private-CA upstream is
`egress_tls.upstream_tls_profile`, which is a different key and does not require this one -- shipping
both together is what keeps the hostname knob from being misused as a general trust disable.

*Residual risk (accepted) -- the JWKS leg.* `egress_tls.jwks_verify_hostname: false` is the same
class of operator-selectable relaxation on a different leg, and it is recorded separately because
what it concedes is not the same thing. What it gives up is bounded to *hostname matching on the JWKS
back-channel*: chain trust is unaffected and an IdP whose certificate reaches no trusted anchor is
still refused. What remains is more serious than its upstream sibling, and saying so is the point of
recording it. The JWKS document carries the *signing keys every bearer token is validated against*,
so an attacker who can both redirect the gateway's JWKS fetch *and* present a certificate chaining to
an anchor the gateway trusts can serve their own key set -- and every token the gateway then accepts
is one they minted. On the upstream leg the equivalent position yields one proxied connection; here
it yields the authentication decision itself. Four properties bound the exposure and are the basis of
the acceptance: the default is `true` and an omitted key resolves to `true`, so the relaxation is
never reached by silence; it is reported at boot by `WARN ApiSheriff-120`, so it cannot reach
production unremarked; where the fetch may go at all is still bounded, so redirecting it is not
merely a DNS answer away -- and that bound is *two* mechanisms rather than one, each enforcing a
different half: token-sheriff's `EgressPolicy` SSRF egress guard is applied to the *checked JWKS
URI* before the initial fetch and before each background refresh, constraining which host that URI
may name, while a *cross-origin redirect hop* off that URI is what the HTTP handler's
`RedirectPolicy.sameOrigin()` rejects; and the scope claim is proven by the untrusted-chain dial
above rather than asserted. The mitigation for an operator whose IdP is behind an internal CA is
`jwks.tls_profile`, which is a different key answering the chain-trust question -- and, on an
`http`-sourced issuer, the two are *mutually exclusive* and the combination is refused at boot, so an
operator cannot reach for both at once and end up with neither. A `file`-sourced issuer opens no TLS
connection, so it reaches no such collision and none is refused there -- and its `jwks.tls_profile`
has no TLS leg to act on either.

*Residual risk (accepted) -- the BFF OIDC back-channel.* `egress_tls.oidc_verify_hostname: false` is
the same class of operator-selectable relaxation on the sixth leg, and what it concedes is recorded
on its own terms. It gives up *hostname matching on the back-channel the gateway uses for discovery,
the authorization-code exchange, refresh and refresh-token revocation*; chain trust is unaffected and an identity provider whose
certificate reaches no trusted anchor is still refused. What remains is serious in a different way
from the JWKS leg: this connection *carries the client secret* and the authorization codes, and its
responses are the discovery document and the token responses sessions are built from. An attacker who
can both redirect the gateway's back-channel *and* present a certificate chaining to an anchor the
gateway trusts receives the client credential and can answer the token exchange -- and a discovery
document it serves can name the endpoints the gateway dials next. The exposure is bounded by the same
properties as its siblings: the default is `true` and an omitted key or an omitted block resolves to
`true`; the relaxed posture is reported at boot by `WARN ApiSheriff-125`; the key is a peer of
`jwks_verify_hostname` rather than shared with it, so relaxing this leg relaxes neither the JWKS fetch
nor any proxied upstream; and the scope claim is proven by the untrusted-chain dial rather than
asserted. The mitigation for an identity provider behind an internal CA is `oidc_tls_profile`, which
answers the chain-trust question instead -- and the two are *mutually exclusive*, refused together at
boot, so an operator cannot reach for both and end up with neither. A named profile *replaces* the JVM
default trust store on this leg, so a profile holding only a private CA stops trusting public
authorities for the identity provider; that replacement is reported by `WARN ApiSheriff-126` rather
than left to be discovered.

*No deployment-activation instance is owed for the relaxation keys -- recorded, not a gap.* The hostname
keys are proven at the level they are asserted at, and those levels differ.
`upstream_verify_hostname` is proven by an integration-stack matched pair, so a *deployed descriptor*
turns the relaxation on and the `*ActivationWiringTest` family pins that it does.
`jwks_verify_hostname` and `oidc_verify_hostname` are proven at *unit* level against a local server,
through the producers' own configuration paths. The deployment-activation question a unit test cannot
reach -- does a shipped deployment actually turn this on? -- has nothing to assert for either: both
are secure-by-default *relaxations* that no shipped descriptor activates, so there is no deployed
document whose activation a wiring test could check. The two halves that are owed are present: the
behaviour half is the real TLS dial with its matched control, untrusted-chain leg and falsification
check, and the native binding half -- that the shared `egress_tls` record and its deserializer survive
the native build -- is exercised by the integration stack's `sheriff-config-egress-verify-{on,off}`
pair, which binds the same record through the same deserializer. The reasoning is recorded in
link:development/declared-limit-assertion-coverage.adoc#_the_egress_relaxation_keys_owe_no_activation_instance[Declared-limit
assertion coverage]; the condition that would reopen it is a shipped descriptor that starts declaring
either key.

*Scope limit (recorded, not a residual risk).* `egress_tls`'s *upstream* settings govern the three
Vert.x egress clients, `jwks_verify_hostname` the JWKS back-channel and the two `oidc_*` keys the BFF
back-channel; no key reaches the *asset-origin* fetch, leg 5 of the enumeration above: an asset
route with an `https` origin is fetched through a JDK `java.net.http.HttpClient` that carries no
`egress_tls` setting. Its construction site pins the JDK's own default context explicitly -- no
behavioural change, and the reason the fitness function can see the leg's posture at all. This is recorded separately from the residual risk above because it does not cut in the
dangerous direction. Hostname verification there is *fail-safe*: the JDK client checks the name
whatever the key says, so `upstream_verify_hostname: false` cannot weaken the asset leg, and no
unverified dial exists to defend. The *trust* half is the real limit -- `upstream_tls_profile`
replaces anchors on the three governed clients only, leaving the asset leg on the JVM default trust
store, so an asset origin behind a private CA *fails closed* rather than succeeding unverified, and
the deployment binds those anchors into the JVM trust store instead. Governing the JDK client would
need an `SSLParameters` / `SSLContext` seam that ADR-0040 deliberately did not scope; the limit is
stated in the operator documentation and in the model rather than left to be discovered.

*The BFF OIDC back-channel -- pinned, with a relaxation and a trust profile.* This leg was previously
recorded here as a scope limit with a countable remainder: it verified hostnames only because the
identity-provider client library defaulted to doing so, and nothing in this repository would have gone
red had that default moved. Both entries are closed rather than carried. The `ClientConfiguration`
built in `BffRuntimeProducer` -- what `DiscoveryResolver`, `TokenEndpointClient` and `RefreshFlow` dial
with, presenting the client secret under `CLIENT_SECRET_BASIC` -- now receives
`egress_tls.oidc_verify_hostname` on every build, so the posture is the gateway's and an upstream
default change cannot move it
(link:adr/0022-Upstream_security-hardening_default_changes_are_adopted_and_documented_never_locally_reverted.adoc[ADR-0022]).
A named `egress_tls.oidc_tls_profile` supplies the leg's trust through the four fail-closed
refusals the JWKS profiles use -- an unbound name, a `trust-all` profile, an anchor-free profile and
unloadable material each fail boot naming `egress_tls.oidc_tls_profile`. The observables are the two
boot records, `ApiSheriff-125` and `ApiSheriff-126`, the collision refusal naming both keys, and the
fitness function, which goes red naming `BffRuntimeProducer` if the hostname call is removed. The
residual the relaxation concedes is recorded above.

*Residual (named, not guarded) -- the JVM-level hostname-verification switch.* The JDK system
property `jdk.internal.httpclient.disableHostnameVerification` turns off hostname checks on *every*
leg built on the JDK HTTP client -- the JWKS back-channel, the BFF OIDC back-channel and the
asset-origin fetch -- beneath every `egress_tls` key and beneath every construction site. A gateway
key set to `true` does not override it, no boot record reports it, and the explicit-posture fitness
function cannot see it, because it is a start-up flag rather than bytecode. The Vert.x legs 1-3 do
not use that client and are unaffected. It is carried as a named remainder rather than refused at
boot: a JVM start-up flag sits below the gateway's configuration surface and is the deployment's
responsibility, in the same way the default trust store triple is. It is recorded here and in the
fitness function's own documentation so that its absence from the gateway's guards is a stated fact
an audit can check the start command against, rather than a discovery.

*Threat -- trust-root REPLACEMENT of the default store.* Every entry above asks whether a dial
verifies. This one asks a prior question: *which anchors is it verifying against, and what stopped
being trusted when the deployment supplied them.* Both levers that set the gateway's default trust --
the JDK's `-Djavax.net.ssl.trustStore` triple and the Quarkus TLS registry's default trust bucket --
*substitute for the platform trust bundle wholesale rather than adding to it*. An operator who
supplies a store holding only their private certificate authority has silently stopped trusting every
public root the platform shipped. The failure mode is what makes it a threat rather than a
misconfiguration: nothing refuses at boot, and the loss surfaces later as an opaque handshake
rejection against an endpoint that used to work -- so the natural reading is "that endpoint broke",
not "we removed its anchor". The reverse direction is the security-relevant one and is worse,
because it is silent in both directions: a store assembled from the platform bundle *plus* an
attacker-influenced anchor widens what every terminated-egress leg accepts, with no key in
`gateway.yaml` recording that it happened. The two levers are also *independent*, so moving one and
not the other leaves half the outbound surface on the platform bundle and half on the supplied store
-- a split posture no single configuration file states.

*Control.* Report the effective store at boot rather than requiring it to be derived, and document
the one supported route with the replacement hazard stated before the recipe.

*Status:* DELIVERED as a reporting-and-documentation control, and it is worth being exact about what
that does and does not buy. `ApiSheriff-17` names, per tier, the trust source actually in force --
the legs holding a raw JDK `TrustManager` and the legs resolving through the Quarkus TLS registry --
and `ApiSheriff-122` fires alongside it whenever an operator-supplied store is in effect on either
tier, stating the replacement hazard and naming which half was left behind when the two tiers
disagree. The split-posture case is therefore reported in the one place an operator could not have
computed it from. Neither record carries a password, an alias or any anchor material. The operator
recipe -- including that the native, distroless image has no `update-ca-trust`, that the JDK triple
must arrive as command-line `-D` arguments, that `JAVA_TOOL_OPTIONS` is not honoured by a native
runner, and how to build a store that keeps the public roots *and* adds a private CA -- is in
link:configuration.adoc#_default_trust_store_replaces[Supplying a default trust store REPLACES the
platform bundle].

*Assertion.* A boot with no operator-supplied store reports the platform bundle on both tiers and
emits no `ApiSheriff-122`; a boot with a store on either tier emits it, and a boot where the two
tiers disagree says which half stayed on the platform bundle.

*Residual risk (accepted) -- the two tiers are independently settable.* The control reports the
posture; it does not constrain it. Nothing refuses a deployment that moves one lever and not the
other, and nothing inspects what is *inside* the supplied store -- a store missing the public roots,
or carrying an anchor it should not, boots exactly like a correct one. This is accepted rather than
closed because both levers are deployment-bound by
link:adr/0025-The_whole_server-TLS_surface_is_neutral_in_gatewayyaml_and_bound_by_exactly_two_seams.adoc[ADR-0025]
and refusing a legitimate single-tier deployment would be wrong; the gateway cannot know which
anchors a deployment *intended*. What bounds the exposure is that the state is no longer silent: the
divergence is named in the boot log by the record that exists for this hazard, so it is observable at
the moment it is introduced rather than at the moment it breaks something.

=== GW-07 -- Slowloris / connection & body-size exhaustion / decompression bombs

Slow partial requests pin workers; unbounded body buffering or decompression exhausts
memory; config-file expansion bombs exhaust boot memory.

*Evidence.* Apache httpd CVE-2007-6750 (Slowloris, pre-`mod_reqtimeout`). Envoy CVE-2022-29225
(decompressor with no output cap -> OOM). KrakenD-triaged Go stdlib DoS CVEs (CVE-2026-42504
MIME quadratic, CVE-2025-61723 PEM quadratic). The code review's own finding: the interim
`ProxyRoute` buffers unbounded request *and* response bodies with no timeout in a 512 MB
container.

*Control.* Bound everything an attacker inflates: inbound header/line-size limits, an
inbound idle/read timeout (slowloris), a max-in-flight admission cap, `max_body_bytes` as a
*streaming* counter (never buffer the body -- link:adr/0006-body-streaming-vs-httpresult.adoc[ADR-0006]),
and streamed responses (never materialized). The gateway is an *opaque* passthrough -- it does
not decode `Content-Encoding`, so it is not itself a decompression-bomb target, but it must
still cap body bytes. Explicit YAML `StreamReadConstraints` are applied at config load.

*Status:* PARTIAL. Streaming + the `max_body_bytes` counter is ADR-0006 + pipeline
stage 6; edge limits, idle timeout, admission cap and graceful drain are delivered as the
edge-hardening bounds; YAML limits are applied at config load. The individual controls are
delivered, but the assertion below is not yet pinned across the whole set, which is what keeps
the entry at PARTIAL rather than COVERED.

*Assertion.* A slow-drip request is evicted at the idle timeout; a body exceeding
`max_body_bytes` aborts mid-stream without full buffering; concurrent large requests do not
grow heap without bound (admission cap holds); an oversized/alias-bomb config fails boot
gracefully.

=== GW-08 -- HTTP/2 & gRPC abuse (Rapid Reset, CONTINUATION flood, downgrade smuggling, h2c)

Cheap multiplexed actions become expensive server work: open-then-`RST_STREAM` loops,
endless CONTINUATION header frames, h2->h1 downgrade Content-Length smuggling, forwarded
`Upgrade: h2c` bypassing controls.

*Evidence.* CVE-2023-44487 (HTTP/2 Rapid Reset -- record DDoS, hit nginx/Envoy/Tomcat/Jetty/
Go/gRPC/HAProxy/Node). Node CVE-2024-27983 and the CERT VU#421644 CONTINUATION-flood set
(httpd CVE-2024-27316, Tomcat CVE-2024-24549, Envoy CVE-2024-27919, nghttp2 CVE-2024-28182,
Go CVE-2023-45288). CVE-2019-9513 (PRIORITY flood). Netty CVE-2021-21295 (h2->h1 CL smuggling).

*Control.* Rate-limit stream *creation and reset* per connection (not only concurrent

*Status:* GAP. Quarkus/Netty ship some Rapid-Reset mitigation, but stream-reset rate limiting
and CONTINUATION bounds must be verified and pinned, and h2c-upgrade non-forwarding asserted.
This spans both the terminated h2 edge and the forced-h2 gRPC upstream.

*Assertion.* A Rapid-Reset / CONTINUATION-flood load against the gateway does not exhaust
CPU/memory (bounded, connection dropped); client `Upgrade: h2c`/`Connection` headers are not
forwarded upstream; an h2->h1 path re-derives framing.

=== GW-09 -- WebSocket cross-site hijacking (CSWSH) / missing Origin check on upgrade

The WS handshake is an HTTP Upgrade the browser sends with ambient cookies, and the
Same-Origin Policy does *not* restrict cross-origin WebSocket connections -- only server-side
`Origin` validation does. Accept-any-origin upgraders let an attacker page open an
authenticated socket in the victim's context (CWE-1385).

*Evidence.* Nginx-UI CVE-2026-34403, Mailpit CVE-2026-22689, Dozzle CVE-2026-44985 *(2026,
GHSA-sourced; CVSS enrichment pending)* -- all `CheckOrigin -> true` on cookie-authenticated
WS endpoints.

*Control.* Validate `Origin` server-side on the upgrade handshake against an allowlist
(reject unknown origins) *before* the relay is established; the handshake already runs the
full pipeline incl. auth, and Origin validation joins it for session-authed WS routes.
Require `SameSite` on the session cookie and do not rely on ambient cookies alone to
authenticate a socket.

*Status:* GAP for session-authed routes. The handshake runs auth, and
`websocket.allowed_origins` is enforced fail-closed on *bearer* WebSocket routes
(link:adr/0015-websocket-origin-failclosed-allowlist.adoc[ADR-0015]); the equivalent
`Origin` check for `require: session` WebSocket routes is not yet pinned (see Gaps).

*Assertion.* A WebSocket upgrade with a foreign `Origin` on a session-authenticated route is
rejected before any upstream dial; only allowlisted origins complete the handshake.

[#gw-13]
=== GW-13 -- Open redirect through a gateway-answered redirect (CWE-601)

A redirect answered *by the gateway* carries the gateway's own origin as its credential: a link to
`https://gw.example.com/moved` looks trustworthy, and whatever `Location` it answers with is where the
browser goes. If that target can name another origin -- an attacker-chosen one, or one reached
through a spelling the configuration reader did not recognise as foreign -- the gateway becomes a
phishing and token-leak relay (CWE-601).

*Evidence.* The failure class is the URL-parser disagreement the WHATWG URL Standard codifies for
the special schemes: a leading `//` is scheme-relative and names a host, a backslash is parsed as
`/` so `/\evil.example` is `//evil.example`, and user-info disguises the real host
(`https://trusted@evil.example`). The same redirect-target laxity is the class behind the
`redirect_uri` advisories in <<bff-01>> (Keycloak CVE-2024-8883, CVE-2026-3872), there on the IdP
side. No gateway-product CVE is cited for this entry: the surface is new in API Sheriff, and the
entry is recorded from the parser behaviour before it ships rather than after.

*Control.* The `redirect` terminal action
(link:adr/0014-asset-serving-terminal-action.adoc#amendment-a1[ADR-0014 Amendment A1]) takes no
target from the request: `location` is fixed configuration, written verbatim, with no placeholder --
only the raw query is appended under `keep_query`. The configuration validator reviews every
`location` *once, at boot*, and refuses the boot rather than serving a doubtful value:

* without the explicit `allow_external: true` opt-in, `location` must be a gateway path -- exactly one
  leading `/`, no backslash, no percent-encoded `/` or `\` (`%2F`, `%5C`, either case), no dot-segment
  (`.`, `..` or their `%2E` spellings), printable ASCII without whitespace or control characters (a
  CR/LF would forge a response header), and no `#` together with `keep_query`. The path is
  additionally put through cui-http's `URL_PATH` validation pipeline, which adds the classes a
  single-decoding spelling test cannot see: double encoding (`/%252F%252Fevil.example`), traversal
  reached through it, null bytes, overlong and malformed UTF-8, unicode-normalising escapes, and a
  1024-character length cap;
* with the opt-in, it may additionally be an absolute `http`/`https` URI with a non-empty host and no
  user-info; every other scheme (`javascript:`, `data:`, ...) stays refused, and the opt-in is
  reported at boot by `WARN ApiSheriff-128`, naming the route and never the target;
* refusal messages echo the value through the injection-safe renderer (CWE-117, see <<gw-12>>).

*Control -- the query is same-origin only.* The review above establishes that the *target* is a value
the operator wrote down. It establishes nothing about the *query*, which arrives with the request and
is therefore attacker-supplied. `keep_query` together with `allow_external` would opt every inbound
parameter out of the gateway origin: a request to `/go?code=...&state=...` produces a `Location` that
plants those values in the third party's access log, `Referer` chain and page analytics
(CWE-201 / CWE-598). The pair is refused at boot rather than warned about -- a warning cannot be
acted on per request, and there is no reviewable value to judge. Each flag alone is unaffected: a
gateway path may keep the query, and a fixed external target may be declared without it.

Two further properties bound what a redirect route discloses: the redirect is answered only *after*
authentication, so under an authenticated anchor an anonymous caller is challenged before any
`Location` is revealed; and the action is refused on every protocol but `http`, and together with an
`upstream` or `asset` block, so no configuration reaches it silently.

*Control -- the rewritten upstream `Location`.* The `redirect` action is not the only `Location` the
gateway authors. A route with `upstream.rewrite_location: true`
(link:user/endpoint-routes.adoc#_rewrite_location[Rewriting upstream `Location` headers]) replaces an
upstream `Location` pointing inside its own upstream with a *gateway-relative* value, and that value
carries the gateway origin exactly as a configured one does. The target is not attacker-supplied --
it comes from the configured backend -- but its *spelling* is, in every scenario where the backend
reflects a request parameter into its own redirect, and stripping the upstream authority is what makes
a spelling dangerous that was not: an absolute URI binds its authority before its path, so
`https://app1.internal:8443/%5Cattacker.com` keeps the browser on the upstream, while the mapping
`/%5Cattacker.com` is read as `/\attacker.com` once decoded and therefore, per the same WHATWG
backslash rule above, as `//attacker.com`. The rewrite therefore applies *the refusal set of the boot
review* to the candidate path and to the computed mapping alike, relaying the header unchanged rather
than mapping it: no leading `//`, no percent-encoded `/` or `\` (`%2F`, `%5C`, either case), no
dot-segment (`.`, `..` or their `%2E` spellings), and nothing the cui-http pipeline refuses -- a
literal backslash, double encoding, a null byte, a malformed escape, a path past the length cap. The
encoded-slash arm additionally closes a confinement hole the dot-segment test alone cannot see, since
that test splits on the literal `/`: `/app1/a%2f..%2f..%2fadmin` is one segment to it and decodes
outside the match key. The refusal is never a normalization -- the value is emitted to the browser,
so confinement proved against a normalized string the browser never sees would bound nothing. The
query and fragment are outside the refusal and carried verbatim: a separator after the `?` or `#`
cannot form an authority.

*Control -- one refusal set, not two.* "The refusal set of the boot review" above is a shared
implementation rather than a maintained agreement: both paths call
`http.LocationPathReview.refusalReason`, so the boot review of a configured target and the per-request
rewrite of an upstream one cannot drift apart. That class is also where the split between the library
and this project's own tests is decided, and the split is empirical rather than stylistic. cui-http's
`URL_PATH` pipeline is a *canonicalizer*: for the traversal family it throws only when the result
would escape above the root, and otherwise returns a fixed value. It therefore *admits* -- by
normalising them away -- `/%5Cattacker.com`, `/a/x%2fy`, `/%2f%2fattacker.com`, `/a/./b`, a `..` run
that stays inside the root, and a leading `//`. Every one of those is a value this gateway must
refuse rather than fix, because it is emitted verbatim and the client resolves the string it
receives. The pipeline is consulted for whether it *threw*, never for the value it returns, and the
spellings above keep their own tests. `LocationPathReviewTest.CuiHttpCoverageBoundary` asserts that
boundary directly -- that the library admits each spelling and that the review refuses it anyway --
so a future cui-http that starts refusing one turns the redundancy into a failing test instead of
silent duplication.

*Control -- the answer is not stored.* A redirect answer is an ordinary cacheable response, and `301`
and `308` are cacheable by default under RFC 9111 §4.2.2 heuristic freshness. Because the redirect is
answered after authentication, a `Set-Cookie` an earlier stage produced -- a re-sealed or rotated
cookie-mode session -- rides on it, so a shared cache between the client and the gateway could store
one client's session cookie and replay it to another (CWE-524 / CWE-525). The gateway therefore emits
`Cache-Control: no-store` on a redirect answer whenever the route's effective auth requires
authentication *or* any `Set-Cookie` is accumulated -- the same governance the asset terminal action
already applies to `AccessLevel.AUTHENTICATED` content. A public, cookie-less redirect stays
cacheable, which is what a settled `301`/`308` move is for. The header is not a `security_headers`
key, so `header_modes` does not reach it, and it is written after the stage headers so none can
displace it.

*Status:* COVERED. The review is boot-time configuration validation with a table-driven refusal
corpus (`ConfigValidatorRedirectTest`: `//host`, `/\host`, `\\host`, `/%2F%2Fhost`, `/%5chost`,
`/a/../b`, the double-encoded `%252F`/`%252e` spellings and an over-cap path, an external URI without
the opt-in, `javascript:` and user-info with it, `#` with
`keep_query`, the `keep_query` + `allow_external` pair, plus the accepted forms and each flag alone);
`LocationRewriterTest` carries the same refusal corpus for the rewritten upstream `Location`
(`/\host`, `/\\host`, `%5C`/`%5c`, `%2F`/`%2f`, a mixed spelling, the double-encoded and malformed
escapes, and each of them on an absolute
upstream URI -- the form in which the mapping would otherwise *create* the cross-origin value --
against the matched positive controls that must still map: an ordinary path, an absolute URI with an
ordinary path, the neighbouring non-separator encodings `%5B`/`%5D`/`%2D`, and an encoded separator in
the query or fragment);
`LocationPathReviewTest` pins the shared review itself, including the cui-http coverage boundary
described above;
the native boot refusal of an external location without the
opt-in is exercised by `verify-invalid-config-fails.sh`; `RedirectStageTest` pins the cacheability
verdict on both its conditions and on the public control; `GatewayEdgePipelineTest` asserts the
`no-store` on an authenticated redirect and its absence on a public one over a live server; and
`RoutingAndResponseHeadersIT` asserts the
served redirect against the native image, including the query kept under `keep_query` and no upstream
contact.

*Residual risk (accepted).* `allow_external: true` hands the operator a legitimate external redirect,
and with it the ability to point clients at another origin. The review proves the target is a
well-formed `http`/`https` URI; it cannot prove the operator meant that host. The exposure is bounded
by it being an explicit per-route opt-in, visible in the endpoint file and announced at every boot by
`ApiSheriff-128`, and by the target -- and now the whole `Location`, since the query hand-off is
refused -- being fixed configuration an attacker cannot influence through the request.

*Assertion.* Every refused spelling above fails the boot with the value escaped in the message; a
gateway path and, under the opt-in, a well-formed `http`/`https` URI boot; `keep_query` together with
`allow_external` fails the boot naming both keys and never the target, while either flag alone boots;
an upstream `Location` whose path carries any of those spellings is relayed unchanged rather than
rewritten, while a path free of them -- including one whose query or fragment carries an encoded
separator -- still maps onto the route's match key;
a redirect answer carries
exactly the configured status and `Location` (the raw query appended only under `keep_query`) and
causes no upstream request; an authenticated or cookie-bearing redirect answer carries
`Cache-Control: no-store` and a public cookie-less one does not; an unauthenticated request to a
redirect route under an authenticated anchor is challenged and receives no `Location`.

[#gw-14]
=== GW-14 -- Response security-header floor weakened (origin precedence, anchor replacement)

The gateway-owned response security headers -- `Strict-Transport-Security`,
`X-Content-Type-Options`, `X-Frame-Options`, `Content-Security-Policy` -- are a *floor* only if the
value on the wire is the gateway's. Two mechanisms let a configured header end up absent or weaker
than the operator believes: an *upstream* sending the same header with a more permissive value, and
a *narrower scope* replacing a wider one without carrying all of its headers along.

*Evidence.* NGINX's `add_header` is the canonical instance of the second mechanism and the cautionary
tale ADR-0007's research recorded: a `location` declaring any `add_header` inherits *none* of the
`server`-level ones, so adding one header at a lower level silently drops HSTS and the rest. The
first mechanism is the documented proxy behaviour of relaying origin headers verbatim. Neither is
tied to a single CVE; both are configuration-shaped, which is why the control is stated rather than
inherited.

*Control.* Two decisions, each explicit rather than implied
(link:adr/0007-anchor-scoped-policy.adoc#amendment-a1[ADR-0007 Amendment A1]):

* *Origin precedence is `set` by default.* A gateway-owned header overwrites the origin's value
  unless the block's `header_modes` names that header `default`, and an omitted `header_modes` block
  is the overwrite behaviour. `default` is a per-header, per-block opt-in; a mode for a header its
  block does not enable is refused at boot, and a gateway-authored response (rejection, redirect,
  asset, preflight) always carries the configured value.
* *Anchor replacement is wholesale and stated, not merged silently.* An anchor block replaces the
  global block for its routes -- the same no-merge rule as every anchor policy block -- and the
  operator documentation states the consequence at every place the key is described: a header the
  anchor block omits is absent under that anchor. Responses before route selection keep the global
  block, so no pre-route rejection loses it.

A third mechanism is closed at the boundary rather than here: because the anchor block is resolved
*per selected route*, an address inside an anchor namespace that a route *outside* the anchor answers
carries that route's block, not the anchor's -- the header floor escaped by routing rather than by
precedence or by replacement. The anchor-namespace coverage rule (<<gw-01>>) refuses that
configuration at boot, so "a routed response carries exactly its anchor block" extends beyond the
addresses the anchor's own routes happen to name.

That closure depends on what the coverage rule accepts as covering, and the rule requires the member
to match its whole namespace rather than merely to name it: a member narrowed on `match.methods`,
`match.host` or `match.headers` is not coverage, precisely because the complement it does not match
would fall through to the enclosing route and carry *that* route's header block. The rule and the
drift guard on the dimension set are described under <<gw-01>>; they bound this mechanism's closure
identically.

`content_security_policy` values are refused at boot when blank or carrying a CR, LF or other control
character, on every block, so the header cannot become an injection vector (<<gw-03>>).

*Status:* COVERED. `SecurityHeadersStageTest` and `ResponseStageTest` pin the map routing and the
set/default relay; `ConfigValidatorTest` pins the orphan-mode and CSP refusals; and
`RoutingAndResponseHeadersIT` asserts against the native image that the anchor block applies only
under its anchor, that it drops the global HSTS (wholesale), that a pre-route `404` and a preflight
keep the global block, that `default` keeps an origin `X-Frame-Options` and fills an absent one, and
that `set` overwrites an origin `Content-Security-Policy`.

*Residual risk (accepted) -- `default` mode.* Under `default` the upstream decides the header's final
value, including a weaker one: a permissive `Content-Security-Policy` or a laxer framing policy
passes through unchanged. That is the purpose of the mode -- a frontend keeping its own policy while
the gateway supplies a floor for responses that send none -- so it is accepted, bounded by being a
per-header opt-in the operator writes for a named block, never a default.

*Residual risk (accepted) -- wholesale anchor replacement.* An anchor block that omits a global header
drops it for that anchor's routes, and the boot does not warn about it: the dropped header is a
consequence of the block the operator wrote, not an ambiguity. It is accepted because a merge would
make an anchor unable to *remove* a global header and would reintroduce the merge-order ambiguity
ADR-0007 forbids; it is bounded by the documented rule and by the integration assertion that the
replacement is observable on the wire.

*Assertion.* A routed response carries exactly its anchor block (a global header the anchor omits is
absent); a pre-route rejection and a CORS preflight carry the global block; under `set` an origin
value is overwritten, under `default` it is kept and the configured value fills an absent one; a
gateway-authored response carries the configured value under either mode; an orphan mode and a
control-character CSP fail the boot.

== OAuth / OIDC / BFF failure catalogue

These bite the BFF variants (Variants 2 and 3). The confidential-client *engine*
(`token-sheriff-client`) and the *validation* library (`token-sheriff-validation`) own most
of the cryptographic and flow legs; API Sheriff owns the browser-facing side. Each entry
notes which side owns the control. Normative anchors: *RFC 9700* (OAuth 2.0 Security BCP,
Jan 2025), *OAuth 2.0 for Browser-Based Apps BCP*, *RFC 9207* (`iss`), *RFC 9449* (DPoP),
*OIDC Core*, *OIDC Back-Channel Logout 1.0*.

[#bff-01]
=== BFF-01 -- `redirect_uri` validation (exact match)

Lax redirect-URI matching (wildcard, subdomain, path-prefix, traversal, parser discrepancy)
delivers the authorization `code` to an attacker endpoint -> account takeover.

*Evidence.* Keycloak CVE-2023-6927 (wildcard bypass), CVE-2024-8883 (`localhost` valid-URI ->
arbitrary redirect), CVE-2026-3872 (`..;/` traversal past the allowed path). pixiv HackerOne
#1861974 (path traversal leaked codes). RFC 9700 §2.1/§4.1: *exact string match*, no
wildcards.

*Control.* The BFF redirect URI is a single fixed server endpoint -- trivially exact-matchable.
Register it statically, never templatize/wildcard it, canonicalize-and-reject
`..`/`..;`/encoded traversal before matching. Engine constructs the authorization request;
gateway config supplies the exact URI.

*Status:* COVERED. Reserved-path exact-match registration; one fixed `oidc.redirect_uri`.

*Assertion.* Wildcard/subdomain/path-prefix/`..;/` variants of the redirect URI are all
rejected; only the exact registered URI is accepted.

[#bff-02]
=== BFF-02 -- `state` / CSRF on the callback

Without an unguessable, session-bound, single-use `state`, the callback can't prove it
matches a flow this browser started -> login CSRF / code injection.

*Evidence.* HedgeDoc GHSA-6wm6-3vpq-6qvv, PolarLearn GHSA-fhhm-574m-7rpw (missing `state` ->
login CSRF). RFC 9700 §4.1.

*Control.* The engine's `FlowContext` generates the `state` (32-byte SecureRandom) and
verifies it constant-time on callback, fail-closed -- but it is an *in-memory DTO the gateway
must persist and discard*: single-use is a *caller contract*, not enforced by the type. The
*pending-authorization record* is the gateway's job: persist the `FlowContext`,
short TTL, add the return-URL (the engine's DTO has none), and *bind it to the initiating
browser* with a short-lived `HttpOnly` `__Host-` binding cookie (a record retrievable by
`state` alone can be delivered to a *different* browser -- the callback must require the
matching binding cookie, not just a valid `state`). PKCE does not replace login-CSRF
protection -- keep both.

*Status (mode-split -- the single-use guarantee differs):*

* *Server mode:* COVERED. The record is server-side; the gateway *discards it on first
  callback* (true single-use) and the binding cookie ties it to the browser.
* *Cookie mode:* PARTIAL (accepted risk). The record travels only in the sealed short-lived
  `__Host-` login cookie -- there is no server store to mark it consumed -- so within the
  cookie's short TTL a captured login cookie *could* be replayed. Mitigation and accepted risk:
  the TTL is minutes, the cookie is `HttpOnly`+`Secure`+`__Host-` (not JS-readable, HTTPS-only,
  origin-locked), the browser binding still holds, and the exposure window is the login round
  trip only. This is an explicit risk acceptance of the stateless variant -- choose server mode
  if strict single-use of the login step is required.

*Assertion.* A callback with a missing/foreign/re-used `state` is rejected; the record is
single-use (a replayed callback fails); return-URL is same-origin validated (no open
redirect).

[#bff-03]
=== BFF-03 -- PKCE downgrade / authorization-code injection

Code injected into a victim session, or PKCE stripped/downgraded to `plain`, lets the client
redeem an attacker-influenced code.

*Evidence.* RFC 9700 §4.5 (prevent code injection; PKCE `S256`). Documented code-injection
technique writeups.

*Control.* Always PKCE `S256` (reject `plain`); fail closed if a token response arrives for a
flow whose verifier the gateway did not store (the pending-authorization record binds it);
single-use codes, revoke-on-reuse. Engine performs the exchange; the record provides the
verifier binding.

*Status:* COVERED (engine + the pending-authorization record's verifier binding).

*Assertion.* A token response with no matching stored verifier is rejected; `plain` PKCE is
refused; a code redeemed twice fails and revokes issued tokens.

[#bff-04]
=== BFF-04 -- Missing / unvalidated `nonce` -> ID-token replay

A `nonce` sent but never checked (or never sent) lets a captured ID token from another
session be replayed -- it verifies cryptographically.

*Evidence.* roadiz GHSA-3gx8-q682-38mx (nonce generated, never validated). OIDC Core
§3.1.3.7.

*Control.* Random `nonce` stored in the pending-authorization record; on ID-token validation
require present-and-equal, then discard (single use). `token-sheriff-validation` performs the
check; the record supplies the expected value.

*Status:* COVERED (validation lib + the pending-authorization record supplying the expected
value).

*Assertion.* An ID token whose `nonce` is absent or unequal to the stored value is rejected;
replay of an ID token from another flow fails.

[#bff-05]
=== BFF-05 -- IdP mix-up (multi-issuer) and the `iss` defence

A client federating multiple IdPs can be confused about which AS a response came from and
send a code to the wrong (attacker) endpoint.

*Evidence.* RFC 9207 (`iss` response param; reject mismatched/missing `iss`). RFC 9700 §4.4.

*Control.* API Sheriff is *single-IdP by design* (one global `oidc` block), which structurally
removes mix-up. Still verify `iss` on the callback if the engine
supports RFC 9207 (defence-in-depth). If multi-IdP is ever added, per-IdP distinct redirect
URIs + `iss` verification become mandatory.

*Status:* ELIMINATED (single-IdP) + engine `iss` check where available.

*Assertion.* Only one issuer is configurable; a callback carrying a mismatched `iss` is
rejected.

[#bff-06]
=== BFF-06 -- JWT / ID-token validation (alg confusion, `alg:none`, `kid`, aud/iss/exp)

The verifier honors the token's own `alg`/`kid` (RS256->HS256 key confusion, `alg:none`,
`kid` path/SQL injection) or skips audience/issuer/expiry.

*Evidence.* `jsonwebtoken` CVE-2015-9235 (`alg:none`) / CVE-2016-10555 (RS256->HS256)
*(IDs unverified; the class is canonical)*, CVE-2022-23539 (unrestricted key type). Java
CVE-2022-21449 "Psychic Signatures" (ECDSA `(0,0)` accepted -- forge any ES256 JWT/ID
token/SAML). pac4j CVE-2026-29000 *(dependency relationship unverified)* (PlainJWT-in-JWE
accepted via public key). Original: Auth0 "Critical vulnerabilities in JWT libraries".

*Control.* `token-sheriff-validation` owns this fail-closed: `SignatureAlgorithmPreferences`
is an *allow-list* (RS/PS/ES/EdDSA), with `none` and *all* HMAC algorithms globally rejected
-- so RS256->HS256 key-confusion is structurally impossible, not merely checked. It also
rejects an embedded-`jwk` header (CVE-2018-0114), enforces a <2048-bit RSA floor, and carries
an *in-library* guard for the CVE-2022-21449 ECDSA "psychic signature" (`r|s == 0` rejected
before the JDK verifier) -- defence-in-depth on top of the patched Java 25 runtime. `iss`/
`aud`/`azp`/`exp`/`nbf`/`iat`(+skew)/`sub` are validated by the pipeline. Keys come only from
configured/discovered JWKS (BFF-07). The gateway's residual is to *configure* the expected
audience/issuer and, if desired, a narrower per-issuer `alg` list.

*Status:* COVERED (validation lib, fail-closed, incl. in-library psychic-signature guard;
patched JVM is belt-and-braces). The wired issuer config sets `expectedAudience` from
`token_validation.issuers[].audience`.

*Assertion.* Tokens with `alg:none`, RS256->HS256 confusion, a `kid` that resolves outside
the configured JWKS, wrong `aud`/`iss`, or expired -> all rejected; the running JVM is a
Psychic-Signatures-patched release.

[#bff-07]
=== BFF-07 -- JWKS handling (`jku`/`x5u` SSRF, rotation races, unbounded fetch)

Trusting a per-token key URL fetches attacker keys (and is an SSRF primitive); naive
"refresh on unknown `kid`" is a DoS/amplifier; no cache caps.

*Evidence.* `jku`/`x5u` header-injection auth-bypass writeups (PortSwigger JWT). Rotation-race
and unbounded-fetch discussions.

*Control.* `token-sheriff-validation` owns this and is strong: token-header `jku`/`x5u`/`jwk`
are ignored (they appear nowhere in its key resolution; embedded `jwk` is actively rejected);
`HttpJwksLoader` fetches only from the configured/discovered endpoint behind an `EgressPolicy`
that blocks internal/metadata ranges on the initial fetch *and every background refresh*
(DNS-rebinding-safe, GW-05 tie-in); it caches with a TTL, keeps a bounded rotation grace
window, and `getKeyInfo(kid)` never triggers an on-demand fetch -- so a flood of unknown
`kid`s cannot drive a fetch storm. Its Quarkus JWKS-readiness health check already gates the
ITs. Gateway residual: keep the secure egress defaults; widen only via `allowedEgressHost` for
a trusted IdP -- surfaced in `gateway.yaml` as the per-issuer
`token_validation.issuers[].jwks.allowed_egress_hosts` list (see <<gw-05>>), which defaults to
the secure policy when absent or empty.

*Status:* COVERED (validation lib, fail-closed, SSRF-guarded). Nothing for the gateway to
build.

*Assertion.* A token-supplied `jku`/`x5u` is ignored; JWKS is fetched only from the
configured endpoint; a flood of unknown-`kid` tokens does not cause unbounded outbound
fetches; rotation across overlapping keys keeps validation working.

[#bff-08]
=== BFF-08 -- Refresh-token rotation / reuse-detection under concurrency

A stolen refresh token is a long-lived bearer credential. Rotation without correct reuse
detection either fails to revoke the family or forks it so attacker and victim both persist.

*Evidence.* better-auth GHSA-392p-2q2v-4372 (concurrent redemption *forks the token family*).
RFC 9700 §4.14 (rotate with reuse detection -> revoke the whole family on reuse).

*Control -- reuse detection is the identity provider's, not the gateway's.* The gateway cannot
recognise a replayed refresh token: a confidential client only ever sees the refresh tokens it
presents itself, and a stateless cookie-mode instance keeps no token family, so there is no
gateway-side family and no engine-side one either (ADR-0046, option D). The control is *strict
refresh-token rotation at the identity provider* -- on Keycloak `revokeRefreshToken: true` with
`refreshTokenMaxReuse: 0` -- shipped on in both the integration realm and the compose-sample
realm. The provider refuses a replayed token with `invalid_grant`; the engine classifies that as
`CREDENTIAL_REJECTED`, and the gateway ends the session, clears the session cookie and records
`ApiSheriff-111` (`credential-rejected`). The other refresh failures are disposed per kind (see
link:configuration.adoc#_refresh_failure_dispositions[the configuration reference]): a failure
before the provider processed the grant keeps the session with a fixed back-off; a redeemed
response the gateway refused, or a rotated session it could not persist, ends the session and
revokes best-effort the one live refresh token it can name. The gateway's own part in the
concurrency half is `TokenRefreshCoordinator`'s single-flight *per session, per instance*: concurrent
requests on one session share one redemption, so one instance never presents the same token twice
and never forks the family itself.

*Observed Keycloak behaviour (Keycloak 26.5.7, pinned by `BffRefreshReuseIT`).* On a detected replay
Keycloak refuses the replayed token *and revokes the successor refresh token*, so the legitimate
holder's session ends along with the attacker's -- a replay burns the whole grant, which is the
RFC 9700 §4.14 outcome. The Keycloak *user session* the login created survives, with the client still
attached: the revocation is scoped to the refresh grant, not a logout of the whole SSO session. Both
halves are assertions, so an upgrade that changes either turns the suite red.

*Residual.* Without strict rotation at the provider there is *no* reuse detection on either side --
the provider accepts a replayed refresh token and refreshes it. Strict rotation in turn costs
availability: a duplicate refresh from two instances (or two parallel cookie-mode requests landing on
different instances) presents the same token twice and the second ends the session, a forced
re-login. Enabling a reuse count or grace window at the provider trades that back for exactly the
detection signal rotation exists to provide -- an operator decision, never a gateway default.

*Status (mode-split -- the reachable attack differs):*

* *Server mode:* COVERED (IdP strict rotation). The refresh token never leaves the server-side
  store, so a gateway-side replay is unreachable from the browser; the attack that remains is a
  token stolen from elsewhere and redeemed directly at the provider. Strict rotation detects *reuse*,
  not that first redemption, so detection is bounded by the gateway's refresh cadence rather than
  immediate. If the attacker redeems first, the provider issues the attacker a successor and nothing
  is detected until the gateway presents its now-spent token on the session's next refresh; the
  provider then refuses it, the gateway ends the session as `credential-rejected`, and on Keycloak
  the successor grant is revoked too -- the attacker holds a working grant up to that gateway
  refresh. If the gateway refreshes first, the attacker's later presentation of the spent token is
  the detected reuse, the provider revokes the successor, and the gateway session ends on its next
  refresh. The path by which an IdP-side revocation reaches a server-mode gateway session is that next
  refresh, which ends it as `credential-rejected` (`BffRefreshReuseIT`, targeted grant revocation
  ending exactly one of two sessions).
* *Cookie mode:* COVERED (IdP strict rotation), with the duplicate-refresh residual accepted. A
  replay *is* reachable -- an attacker holding a copied pre-refresh cookie makes the gateway present
  the spent refresh token -- and the provider rejects it, ending that session and, on Keycloak, the
  successor's (`BffRefreshReuseIT`, cookie-mode replay and IdP-revoked cookie session). Because a
  cookie-mode session end destroys nothing server-side, a retained or replayed ended cookie would
  otherwise re-drive a refresh grant and a `WARN ApiSheriff-111` on every near-expiry request until
  the absolute TTL -- amplification and log flooding, not an authentication bypass. The refresh
  coordinator therefore marks the presented refresh token (a per-instance salted digest, never the
  token or cookie) when it ends a session as `credential-rejected`, `redeemed-response-refused` or
  `persist-failure`, until the session's absolute lifetime, and refuses a marked token locally with
  no IdP call, no revocation and no warning. Keyed on the token, a successor cookie still reaches the
  provider once. *Residual:* the marker is per instance (each other instance makes one IdP call before
  marking), in memory (a restart forgets it, one IdP call again), bounded (a full store records
  nothing, so replays degrade to one IdP call per request), not set by RP logout, and unused in
  server mode.

*Assertion.* A replayed pre-refresh cookie is answered `401` with a clearing cookie and a
`credential-rejected` record; Keycloak's successor revocation and surviving user session are pinned;
a targeted IdP revocation ends exactly one server-mode session while its sibling keeps refreshing;
concurrent refreshes on one session within an instance make one redemption; cookie mode never
exposes the refresh token to the browser.

[#bff-09]
=== BFF-09 -- Logout (back-channel token validation, RP-initiated open redirect, fixation)

Under-validated back-channel logout tokens allow forged logout (DoS) or accepting an ID token
as a logout token; a lax `post_logout_redirect_uri` is an open redirect; incomplete session
destruction leaves a fixated session.

*Evidence.* OIDC Back-Channel Logout 1.0: logout token MUST carry `events` (with the
back-channel member) and `sub`/`sid`, and MUST NOT carry `nonce`; validate sig/`iss`/`aud`/
`iat`. Keycloak redirect CVEs (CVE-2023-6927/8883/2026-3872) apply to the post-logout URI.

*Control.* Validate logout tokens strictly: signature+`iss`+`aud`, require `events`, require
`sub`/`sid`, *reject any token containing `nonce`*, short `iat` window; destroy via the
`sid`/`sub` secondary index. Exact-match `post_logout_redirect_uri`. Destroy the
server session and rotate/clear the cookie on any logout; revoke the RT family. Cookie-mode
disables the back-channel endpoint (`404`) -- no session to destroy.

*Status:* COVERED. Both channels, the logout-token checks and the logout-`state` cookie are
delivered, and cookie mode disables the back-channel receiver.

*Assertion.* A logout token missing `events`/`sub`/`sid`, or *containing* `nonce`, or an ID
token replayed as a logout token -> rejected; a non-registered `post_logout_redirect_uri` ->
rejected; post-logout the session is gone and the cookie cleared; cookie-mode back-channel ->
`404`.

[#bff-10]
=== BFF-10 -- Cookie hardening & token-leakage-to-browser

Tokens reaching JS, or a weakly-flagged session cookie, defeat the BFF rationale; session
fixation on login lets a pre-seeded session be adopted.

*Evidence.* Browser-Based Apps BCP (BFF keeps tokens server-side). BFF cookie guidance
(`__Host-`+`HttpOnly`+`Secure`+`SameSite`). Session-fixation guidance.

*Control.* No token ever reaches the browser: server-mode holds them in the store; cookie-mode
seals them in an `HttpOnly` AES-GCM cookie decrypted per request. Session cookie:
`__Host-` + `HttpOnly` + `Secure` + `SameSite=Lax`, opaque id only (see the variant
docs). Regenerate the session id on login and privilege change; destroy on logout.

*The `__Host-` guarantee cannot be configured away.* The prefix is what makes a browser *enforce*
`Secure`, `Path=/` and no `Domain` rather than merely receive them, and the session cookie's name is
operator-configurable through `oidc.session.cookie_name`. A declared name is therefore *refused at
boot*, in both session modes, unless it starts with the case-sensitive `+__Host-+` prefix followed by
a name, is a non-empty RFC 9110 token -- the name is written verbatim into `Set-Cookie`, so a `;`,
`=`, whitespace or control character would be response-header injection -- and differs from the
gateway-owned binding and logout-state cookies, which a colliding session cookie would silently
overwrite. The offending value is escaped before it is echoed (CWE-117). The refusal is the only guard:
the runtime consumes the name verbatim and the schema declares the key an unrestricted string. An
omitted key resolves to the gateway's own `+__Host-sheriff-session+`.

*Status:* COVERED.

*Assertion.* No response ever carries a token to the browser; the session cookie has
`__Host-`+`HttpOnly`+`Secure`+`SameSite`; the session id is regenerated at login (fixation
test); a configured `session.cookie_name` that lacks the prefix (or carries it in the wrong case, or
as `+__Secure-+`), is the bare prefix, is blank, carries a `;` or a space, or names either
gateway-owned cookie fails boot at `/oidc/session/cookie_name` with the value escaped, while the
default name and a well-formed custom `+__Host-+` name boot cleanly.

[#bff-11]
=== BFF-11 -- CSRF on the cookie-authenticated BFF API (the classic BFF gap)

Once auth is a cookie, every cross-site request carries it; `SameSite` alone is insufficient
(Lax GET gaps, same-site subdomain attackers, browser inconsistencies). *Highest-probability
real BFF bug.*

*Evidence.* BFF security writeups repeatedly name this as the pattern's #1 gap.

*Control.* Fixed CSRF defence on unsafe methods: `Origin` exact-match against
`session.csrf.trusted_origins`; `Sec-Fetch-Site: same-origin` accepted when `Origin` absent;
else `403` + `CSRF_REJECTED`. Lock CORS to the SPA origin. This composes with the WebSocket
Origin check (GW-09).

*Status:* COVERED (fixed behaviour, no knob).

*Assertion.* An unsafe-method request with a foreign `Origin` -> `403`; `Sec-Fetch-Site`
variants behave per spec; CORS is limited to the configured origin.

[#bff-12]
=== BFF-12 -- Encrypted-cookie AES-GCM nonce / key rotation (stateless variant)

AES-256-GCM nonce reuse under one key is catastrophic (leaks the GHASH subkey -> tag forgery;
keystream reuse -> plaintext recovery); mis-selecting a key drops or forges sessions.

*Evidence.* "Nonce-Disrespecting Adversaries" (practical GCM nonce-reuse attacks). RFC 9700 /
crypto guidance.

*Control.* Fresh random 96-bit nonce per seal from a CSPRNG (never counter/derived); cookie
= `version‖key-id‖nonce‖ciphertext‖tag` with version+key-id+cookie-name in the GCM AAD
(deterministic key-id gate, replay-across-format prevention); tamper -> treated as no
session; exactly one sealing key, so withdrawing it is a fail-closed clean break (unknown key
id -> no session -> re-authentication) with no decrypt-only companion key to mis-select; ~4 KB
size budget enforced at seal (fail login loudly, no silent truncation).

*Status:* COVERED.

*Assertion.* Each seal uses a unique random nonce; a flipped byte in ciphertext/nonce/tag ->
unauthenticated (never `500`); a cookie stamped with a key id the gateway does not hold ->
no session, and the browser completes a full re-authentication; an oversized token set fails
login with a clear error; key material never logged.

[#bff-13]
=== BFF-13 -- Callback response hygiene (HPP duplicate params, code reuse, error reflection)

Duplicate `code`/`state`/`iss` (HTTP parameter pollution) exploit parser disagreement; a
reused code; a reflected `error_description`.

*Evidence.* Keycloak CVE-2026-9689 (HPP in the OIDC redirect URI). OAuth parameter-pollution
research. RFC 9700 §4.5.3 (single-use codes, revoke on reuse).

*Control.* The engine's `CallbackParameters.parse(rawQuery)` already *rejects* duplicate
security-relevant params (`code`/`state`, RFC 9700 §4.7.3 defence) rather than last-wins,
`IssValidator` checks `iss` (incl. absent-`iss` rejection) and `CallbackHandler` verifies
`state` *before* code redemption, and `InboundErrorNormalizer` sanitizes `error`/
`error_description` (never reflected). The single load-bearing *gateway* obligation: feed the
*raw* query string to `parse(rawQuery)` -- the `of(Map)` overload cannot re-detect duplicates
because the map already collapsed them. Single-use codes/revoke-on-reuse are the AS's.

*Status:* COVERED (engine), with a mandatory usage rule: the callback endpoint calls
`CallbackParameters.parse(rawQuery)`, never `of(Map)`. Asserting a duplicate-`code` callback
is rejected remains an outstanding test item (see Gaps).

*Assertion.* A callback with duplicate `code`/`state` reaches `parse(rawQuery)` and is
rejected; `state`/`iss` are verified before `code`; `error_description` is never reflected.

[#bff-14]
=== BFF-14 -- Sender-constraining (DPoP / mTLS)

Plain bearer tokens are replayable if stolen (logs, proxies, XSS, MITM). Sender-constraining
binds a token to a client key.

*Evidence.* RFC 9449 (DPoP: `cnf` binding, `jti` replay cache, `htu`/`htm`/`iat` checks),
RFC 8705 (mTLS-bound). Misuse = not validating `cnf`, no `jti` cache, accepting bound and
bearer interchangeably (downgrade).

*Control.* Optional hardening, not a required control for the base threat model. The
architecture already carries the hook: the 4-arg `AccessTokenRequest(token, headers, uri,
method)` supplies the URI+method DPoP needs. Where the threat model warrants, issue DPoP/mTLS
-bound access *and refresh* tokens, enforce the `cnf` binding and `jti` replay cache, and do
not accept the same token as a plain bearer (no downgrade). Neutralizes RT theft (BFF-08)
even with imperfect rotation.

*Status:* PARTIAL (hook present; full enforcement post-1.0 unless prioritized). A deliberate
future hardening, not a base requirement.

*Assertion.* If enabled: a bound token presented without its key -> rejected; a replayed DPoP
`jti` -> rejected; the same token is not accepted as a plain bearer.

== Gaps to close

The GAP/PARTIAL rows are where a *documented, real-world* failure class is not yet nailed
down. Closing them is the whole point of this exercise. Each is a small, additive change:

. *GW-01 -- make the single-canonical-path invariant explicit and tested.* cui-http
  already hands back a canonical path; the gateway's job is to route, verb-gate, auth-select,
  `allowed_paths`-match, and forward on *that same* value (never the raw URI), plus decide the
  encoded-slash policy and handle matrix `;` params (both left open by cui-http). Assertion: an
  encoded-traversal/encoded-slash/matrix-param corpus proves no authorize-as-public /
  dispatch-to-protected divergence (upstream count = 0). Dominant gateway CVE class; the
  direct fix for the code-review raw-vs-normalized finding.
. *GW-02 -- add explicit HTTP-framing rejection.* cui-http is explicitly out of
  scope here, so this is entirely gateway/web-server: CL+TE both present, body on a bodyless
  method, and `Connection`-list framing-strip attempts are rejected; a smuggling corpus
  produces zero desyncs. Justified because API Sheriff runs behind other proxies by design.
. *GW-08 -- pin HTTP/2 abuse bounds.* Verify and assert stream-creation/reset
  rate limiting (Rapid Reset), CONTINUATION frame count/size bounds, and non-forwarding of
  client `Upgrade: h2c`/`Connection` to the upstream.
. *GW-09 -- extend WebSocket `Origin` validation to session-authenticated routes.* The
  fail-closed allowlist already gates *bearer* WebSocket routes (ADR-0015); the equivalent
  check before the relay is established is load-bearing once `require: session` WS routes
  exist (CSWSH).
. *GW-06 -- fail-closed SNI + behaviour tests.* Make explicit: empty/fragmented SNI
  takes the strict policy or rejects (never a permissive default); the full ClientHello is
  reassembled before SNI routing; every security-gating boolean has a *behaviour* test (a real
  handshake fails when it must), not just a flag-read. The upstream-verify boolean is *done* --
  `egress_tls.upstream_verify_hostname` is proven by a matched pair of gateway instances plus an
  untrusted-upstream leg that pins the relaxation's scope
  (link:adr/0040-Upstream_hostname_verification_is_a_global_egress-TLS_knob_bound_at_client_construction.adoc[ADR-0040]).
  `egress_tls.jwks_verify_hostname` is likewise *done* -- read by the token-validator producer and
  proven by the same three-legged shape at unit level, with its collision against an
  `http`-sourced issuer's per-issuer `jwks.tls_profile` refused at boot
  (link:adr/0041-The_JWKS_hostname-verification_knob_is_the_librarys_own_passthrough_and_its_sslContext_collision_is_refused_at_boot.adoc[ADR-0041]).
  `egress_tls.oidc_verify_hostname` is *done* on the same terms for the BFF back-channel, with its
  `oidc_tls_profile` collision refused at boot
  (link:adr/0045-The_BFF_OIDC_back-channel_posture_is_pinned_through_the_librarys_own_passthrough_under_peer_egress-TLS_keys.adoc[ADR-0045]),
  and every outbound TLS client is held to an explicit posture by a standing fitness function.
  What remains under this heading is the mTLS-require boolean and the two SNI rules above.
. *BFF-13 -- pin the callback parsing *usage rule* with a test.* The engine already rejects
  HPP and the gateway already calls `CallbackParameters.parse(rawQuery)` on the raw query
  (never the duplicate-blind `of(Map)`); what is missing is a test asserting a
  duplicate-`code` callback is rejected. Scope enforcement is likewise the gateway's -- the
  validation lib exposes `providesScopes()` but enforces nothing.
. *Cross-cutting -- adopt this document as a release gate.* A security-audit sweep validates
  that every COVERED/PARTIAL assertion has a passing test and every GAP is closed or
  explicitly risk-accepted; consider a short ADR recording "CVE-derived validation baseline
  is a 1.0 release gate".

None of these change the architecture; they are hardening assertions on features that already
exist (mostly *wiring* audited library controls correctly), sourced from failures other
gateways and OAuth stacks actually shipped.
