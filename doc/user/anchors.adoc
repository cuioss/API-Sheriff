= API Sheriff -- Anchors (Namespace-Scoped Policy)
:toc:
:toclevels: 2

How to declare and operate *anchors* -- the namespace-scoped policy scopes configured in
`gateway.yaml`. The decisions behind them are recorded in
link:../adr/0007-anchor-scoped-policy.adoc[ADR-0007] and
link:../adr/0013-anchor-type-access-axes.adoc[ADR-0013]; this page describes how to use them.
The field-level contract for every key mentioned here lives in the
link:../configuration.adoc[Configuration Reference].

[[_anchors]]
== Anchors -- Namespace-Scoped Policy

Anchors (decision: link:../adr/0007-anchor-scoped-policy.adoc[ADR-0007]) are *named policy scopes
that own a URL path namespace*. They are declared in `gateway.yaml` and answer one question the
per-endpoint model cannot: "how is an invariant like _every call under `/api` presents a valid
bearer token_ declared once and *enforced*, instead of restated in every endpoint file?"

Semantics -- deliberately few rules:

* *Ownership.* Each anchor declares a `path_prefix`; anchor prefixes are pairwise disjoint
  (no anchor prefix is a prefix of another). The anchor owns everything under its prefix.
* *Membership: at most one anchor per route, declared, never derived.* An endpoint file
  declares `anchor: <name>` as the default for its routes; a route may override it. Membership is
  mandatory exactly where a namespace claims the route, never universally. When any `anchors`
  block is configured, membership and namespace must agree *both ways*: a route whose declared
  anchor does not contain its match key (`match.path_prefix`, or the exact `match.path`) fails the
  boot, and a route whose path falls
  inside an anchor namespace without declaring that anchor fails the boot. A route whose path
  lies outside every anchor namespace declares no anchor at all and is unaffected. No `anchors`
  block => this section does not apply. `protocol: grpc` routes are exempt from *these two*
  directions -- a gRPC method path is service-rooted on a single opaque segment and can never
  nest inside a gateway path namespace on a segment boundary -- but still declare an anchor for
  the classification axes and the auth floor. The exemption stops here: the namespace-coverage
  rule below judges what a route's prefix *contains* rather than where its own match key sits,
  and applies to `grpc` routes unchanged.
* *Namespace coverage: nothing outside the anchor may serve the namespace.* The two directions
  above judge a route by where its *own* match key sits, which leaves the opposite geometry --
  a route sitting outside and *above* an anchor, whose `path_prefix` swallows the anchor's --
  for this rule. A prefix route whose namespace strictly contains an anchor's `path_prefix`,
  and which does not declare that anchor, fails the boot *unless* a route under the anchor
  covers the namespace: a prefix route whose `path_prefix` is the anchor prefix itself *and which
  declares no further `match` dimension*. By longest prefix that covering route wins every address in
  the namespace, so a broader route alongside it is the ordinary topology, not a bypass. Without one, only the addresses the
  anchor's own routes name are protected and every other address falls through to the broader
  route -- served with *its* auth posture and *its* `security_headers`. The case this closes is
  an anchor whose only member is an exact `match.path` route: `path: /admin` claims exactly
  `/admin`, so `/admin/` and `/admin/x` would land on the enclosing route. See
  link:endpoint-routes.adoc#_route_ordering[Route ordering] for the selection rules this follows
  from. Exact routes are not judged here -- an exact route serves one address, which is the
  previous rule's case -- but `protocol: grpc` routes *are*: route selection is protocol-blind, so
  a gRPC route declaring a broad `path_prefix` swallows a namespace exactly as an `http` one does.
  Naming a namespace is not covering it: a candidate narrowed by any further dimension the route
  matcher applies (`match.methods`, `match.host` and `match.headers` today) serves only part of the
  namespace, so it does not count as coverage and the enclosing route is refused just as if the
  anchor had no covering member. Declaring `methods: [GET]` on the covering route is the easiest way
  to trip this: the anchor looks covered, but a `POST` would have fallen through.
* *Policy blocks.* An anchor may carry `auth`, `security_filter`, `security_headers`,
  `allowed_methods` and `cookies`. Every policy block is resolved by one rule -- the nearest declared scope of
  *gateway -> anchor -> endpoint -> route* wins and replaces every broader declaration *whole,
  never merged* -- and each block is declarable at a fixed set of those scopes. The rule and the
  per-block scope table are in <<_policy_block_resolution>> below.
* *`security_headers` is declarable at gateway and anchor only* -- endpoints and routes cannot
  override it. How the block takes effect, and what it does *not* merge, is set out in
  <<_anchor_security_headers>> below.
* *The auth floor cannot be weakened.* Where the anchor declares `require: bearer` or
  `require: session`, a member whose *effective* auth resolves to `require: none` fails the
  boot. Replacing one non-`none` posture with another (anchor `bearer`, route `session`) is
  allowed. An endpoint or route replacing an anchor's `allowed_methods`, `security_filter` or
  `cookies` block is allowed and logged as a boot WARN (see <<_policy_block_override_warn>>).
* *Anchored endpoints may omit `auth`.* The endpoint-level `auth` block becomes optional when
  the endpoint's anchor declares one; every route must still resolve to an unambiguous
  effective auth (route, else endpoint, else anchor) or the boot fails.
* *Anchors vanish at runtime.* They are resolved during route-table assembly into the
  materialized per-route *effective* values (auth, `allowed_methods`, filter, headers, `cookies`); the
  request pipeline never consults an anchor. The boot log reports the effective posture per
  route.

The one modelling consequence: a service exposed on two surfaces -- the same upstream reachable
under `/api` with bearer *and* under `/bff` with a session -- is *two routes* (in the same
endpoint file, sharing the `base_url` alias), one per anchor. Multi-anchor membership does not
exist; it would reintroduce merge-order ambiguity.

[[_policy_block_resolution]]
=== Policy-block resolution -- one rule for every block

Every policy block -- one row each in the scope table below (<<_policy_block_scopes>>) -- is
resolved for a route by the same rule (decision:
link:../adr/0067-Every_policy_block_is_one_declaration_resolved_nearest_declared_scope_wins_with_whole-block_replacement.adoc[ADR-0067]):

. *Four scopes, broadest first: `gateway -> anchor -> endpoint -> route`.* `gateway` is the root of
  `gateway.yaml`; `anchor` is the route's anchor -- the route's own `anchor:`, else its endpoint's;
  `endpoint` is the `endpoint` block of the route's endpoint file; `route` is the route itself.
. *The nearest declared scope wins.* The route's effective block is the one declared at the scope
  nearest the route.
. *Whole-block replacement.* The winning block replaces every broader declaration wholesale. No
  field of a broader block is merged into it: a key the winning block omits takes that key's own
  default, never the value a broader block declared.
. *An empty list is not a declaration.* A scope that omits the block, or declares it as an empty
  list (`allowed_methods: []`), does not declare it, and the next broader scope is consulted.
. *A block is declarable only at its own scopes* (the table below). The bundled schemas refuse it
  at any other scope when the document is loaded.
. *When no scope declares the block*, its nothing-declared fallback in the table applies.
. *The auth floor stays a floor.* Resolution decides which `auth` block a route gets; it never
  permits a weakening. Under an anchor declaring `require: bearer` or `require: session`, an
  effective `require: none` still fails the boot.

The route table and the boot validator resolve every block through the same code, so the posture
the boot validator judges is the posture the route runs.

*An example: `cookies` declared at three scopes.* The `cookies` block is the one block declarable at
all four scopes, so it shows the whole chain:

[source,yaml]
----
# gateway.yaml
cookies: { allow: none }                     # gateway scope
anchors:
  app:
    path_prefix: /app
    type: proxy
    access: public
    cookies: { allow: [SESSIONID, theme] }   # anchor scope

# endpoints/legacy.yaml
endpoint:
  id: legacy
  base_url: LEGACY
  anchor: app
  auth: { require: none }
  routes:
    - id: legacy-admin
      match: { path_prefix: /app/admin }
      cookies: { allow: [ADMINSESSION] }     # route scope
    - id: legacy-app
      match: { path_prefix: /app }
----

`legacy-admin` forwards `ADMINSESSION` alone: its block replaces the anchor's list rather than adding
to it, and the replacement is announced by `ApiSheriff-101`. `legacy-app` declares no block and its
endpoint declares none either, so the anchor's `[SESSIONID, theme]` applies. A route outside every
anchor whose endpoint declares no block resolves the gateway's `allow: none`, which is also what a
route resolves when no scope declares the block at all. What each mode forwards and relays is in
link:../configuration.adoc#_cookies[the `cookies` reference].

[[_policy_block_scopes]]
.Where each policy block is declarable
[cols="2,3,4,3,6", options="header"]
|===
| Block | Declarable at | Nothing declared | Override WARN | Why the scopes stop where they do

| `auth`
| anchor, endpoint, route
| The boot fails: every route must resolve an auth posture from its route, its endpoint or its
  anchor.
| No
| No gateway scope: a gateway-wide `auth` would hand every unanchored route a posture and turn the
  refused boot for a route without one into a silent default. No WARN: weakening an anchor's floor
  is refused at boot, which is stronger than a warning.

| `allowed_methods`
| gateway, anchor, endpoint
| Every standard method: `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`.
| Yes -- an endpoint list replacing the anchor's
| No route scope: a route narrows its verbs with `match.methods`, which must be a subset of the
  effective list.

| `security_filter`
| anchor, endpoint, route
| No block: the route runs the `security_defaults.profile` preset (`strict` when omitted).
| Yes -- an endpoint or route block replacing the anchor's
| No gateway scope: `security_defaults` owns the gateway-wide profile. The endpoint scope is
  *new and breaking* (see <<_policy_block_breaking_changes>>).

| `security_headers`
| gateway, anchor
| No block: no gateway-owned response security header is emitted.
| No
| No endpoint or route scope: the browser response posture is a property of the namespace, and a
  narrower block would let one endpoint drop HSTS or frame-deny for part of an anchor's namespace.
  `cors` is declarable in the gateway block only.

| `upstream_defaults`
| gateway, endpoint
| Both toggles enabled: `retry.enabled: true`, `not_modified.enabled: true`.
| No
| No anchor scope: upstream behaviour belongs to the upstream, which the endpoint owns through its
  `base_url`; an anchor is a namespace, not an upstream. A route overrides single toggles instead
  (see <<_policy_block_field_level_exceptions>>).

| `forward`
| endpoint, route
| Forward-all on both dimensions, bounded by the gateway-owned sets no configuration re-admits (see
  link:../configuration.adoc#_never_forward_set[the never-forward set]).
| No
| No anchor or gateway scope: forward filtering is upstream-specific
  (link:../adr/0036-Forward_filtering_is_a_three-mode_policy_inside_an_authorised_route.adoc[ADR-0036]).
  The endpoint and the route block live in the same endpoint file, so a route replacing the
  endpoint block is one owner's choice and is not announced. The endpoint scope is *new and
  breaking* (see <<_policy_block_breaking_changes>>).

| `websocket`
| route
| No block: an empty `allowed_origins` and an idle timeout of 300 seconds on a `protocol: websocket`
  route.
| No
| Route only: the block is valid on `protocol: websocket` routes alone, and `allowed_origins` is a
  fail-closed per-route allowlist
  (link:../adr/0015-websocket-origin-failclosed-allowlist.adoc[ADR-0015]); an endpoint block would
  reach the endpoint's other routes.

| `cookies`
| gateway, anchor, endpoint, route
| `allow: none`: no browser cookie reaches the upstream and no upstream `Set-Cookie` reaches the
  browser. The gateway's own cookies never cross under any block.
| Yes -- any endpoint or route block replacing the anchor's
| Every scope, because which cookies an upstream may receive is decided per upstream but may be
  set once for a namespace or the whole gateway. An asset or redirect route has no upstream: it
  always resolves `allow: none`, and a route-level block on one is refused. `allow: all` is refused
  at the gateway scope.
|===

[[_policy_block_override_warn]]
==== The override WARN

Replacing an anchor's block from a nearer scope is allowed, and for the blocks marked *Yes* above it
is announced: `ApiSheriff-101` is logged during route-table assembly when the route's anchor
declares the block *and* the route's endpoint or the route itself declares it too. The record is
logged once per route and block -- an anchor block replaced at both the endpoint and the route is
announced once -- and names the route, the endpoint owning it, the anchor, the block and the
replacing scope (`endpoint` or `route`, the nearest scope declaring the block, so a block replaced
at both names `route`). A block marked *No* is not
announced: `auth` because weakening its floor is refused outright, the others because no anchor
declaration sits under a nearer one (`security_headers`) or because the block has no anchor scope
at all. See link:../LogMessages.adoc[Log Messages].

[[_policy_block_field_level_exceptions]]
==== Documented exceptions -- two field-level fallbacks

Two fallbacks act on a single field rather than on a whole block. They are deliberate exceptions to
the rule above, not a merge:

* *`security_filter.profile`.* A resolved `security_filter` block that declares no `profile` takes
  `security_defaults.profile`, and `strict` when that is omitted too -- never the profile of the
  broader block it replaced. Dropping the field fallback would make such a block resolve `strict`
  whatever the gateway's baseline declares, and would leave the route's profile disagreeing with
  the pre-route baseline the gateway applies before any route is selected.
* *A route's `upstream.retry.enabled` and `upstream.not_modified.enabled`.* Each toggle the route
  declares overrides that one field of the effective `upstream_defaults` block; a toggle the route
  omits keeps the block's value. A route-level `upstream_defaults` block replaced wholesale would
  reset the toggle the route did not mention to its default.

[[_policy_block_breaking_changes]]
==== Breaking changes: `security_filter` and `forward` at the endpoint scope

The endpoint scope of these two blocks is a breaking change to what an endpoint document may
declare, and what it takes over is stated here:

* *An endpoint may declare `security_filter`.* It governs every route of the endpoint that declares
  no block of its own, and it replaces the anchor's block wholesale -- announced by
  `ApiSheriff-101`. The `profile: minimal` refusal on authenticated and BFF routes, and the boot
  check against the framework body-size floor, read the endpoint block too.
* *An endpoint may declare `forward`.* It governs every route of the endpoint that declares no block
  of its own; a route block replaces it wholesale, so a route block naming only `headers_allow`
  drops an endpoint `query_deny`. Both list pairs are refused at the endpoint exactly as on a route
  (allow and deny for one dimension together), and a `token_relay: false` route whose effective
  `forward.headers_allow` -- endpoint-level included -- names `Authorization` is refused.

A configuration without either key at the endpoint resolves exactly as it did before the scope
existed: the schema refused both keys there, so no existing endpoint document declares them.

[[_anchor_security_headers]]
=== Anchor `security_headers`

An anchor's `security_headers` block sets the gateway-owned *response* security headers for every
route under the anchor (decision:
link:../adr/0007-anchor-scoped-policy.adoc#amendment-a1[ADR-0007 Amendment A1]). It carries the same
response-header keys as the global block -- `hsts`, `content_type_nosniff`, `frame_deny`,
`content_security_policy` and `header_modes` -- and nothing else:

[source,yaml]
----
# gateway.yaml
security_headers:                  # GLOBAL block: seeded onto every response
  hsts: { max_age: 31536000, include_subdomains: true }
  content_type_nosniff: true
  cors:                            # CORS lives here, and only here
    enabled: true
    allowed_origins: [https://app.example.com]

anchors:
  portal:
    path_prefix: /portal
    type: proxy
    access: public
    security_headers:              # ANCHOR block: replaces the global block for /portal routes
      hsts: { max_age: 31536000, include_subdomains: true }   # restated -- not inherited
      content_type_nosniff: true                              # restated -- not inherited
      frame_deny: true
      content_security_policy: "default-src 'self'"
      header_modes:
        content_security_policy: default   # the frontend's own CSP wins when it sends one
----

*When it applies: right after route selection.* The request pipeline seeds the *global* block at its
first stage, before anything else runs. Once a route is selected, the route's resolved block -- the
anchor's block when its anchor declares one, the global block otherwise -- *replaces* the
gateway-owned security headers on the response. Every response produced after that point carries the
route's block: a proxied response, an asset, a redirect, the verb gate's `405`, an authentication
`401`, a gRPC trailers-only rejection and a failed WebSocket handshake alike. Every response produced
*before* a route is selected carries the global block, because no anchor is known yet: a stage-1
rejection, the `404` for a path no route matches, and a CORS preflight answer.

[IMPORTANT]
.The anchor block replaces the global block wholesale -- there is no merge
====
An anchor block is not layered on top of the global block key by key. It *replaces* it: any key the
anchor block does not declare is simply *absent* for that anchor's routes, even when the global block
declares it. An anchor declaring only `frame_deny: true` therefore drops the global
`Strict-Transport-Security` and `X-Content-Type-Options` for every route under it, and an anchor block
without `content_security_policy` drops the global policy. The same holds for `header_modes`: the
anchor's modes replace the global ones, and a header the anchor block enables without a mode entry is
in `set` mode whatever the global block says.

*To keep a global header under an anchor, restate it in the anchor block* -- as `hsts` and
`content_type_nosniff` are restated in the example above. This is the wholesale-replacement rule every
policy block follows (see <<_policy_block_resolution>>), not a special case for headers.
====

*`content_security_policy`.* The value is served *verbatim* as the `Content-Security-Policy` header;
the gateway does not parse or compose it. Omitting the key emits no policy. A value that is blank or
carries a CR, LF or any other control character fails the boot, on the global block and on every
anchor block, because it would inject a response header.

*`header_modes` -- precedence against the origin's own header.* By default the gateway *overwrites*
a gateway-owned header the upstream also sent. `header_modes` changes that per header, with one
optional key per gateway-owned header of the same block -- `hsts`, `content_type_nosniff`,
`frame_deny`, `content_security_policy`:

[cols="1,3"]
|===
| Mode | Behaviour on a proxied response

| `set` _(the default)_
| The gateway value *replaces* the origin's value.

| `default`
| The origin's value is *kept* when the upstream sent that header; the gateway value is emitted only
  when it did not.
|===

An absent key means `set`, and an omitted `header_modes` block is exactly the overwrite behaviour. A
response the gateway authors itself -- a rejection, a redirect, an asset, a preflight -- has no origin
header to defer to, so both modes emit the configured value there. A mode naming a header its own
block does not enable (for example `frame_deny: default` while `frame_deny` is absent or `false`) fails
the boot: it would configure a header the gateway never emits.

`default` is the tool for a frontend that manages its own policy: the gateway sets a *floor* for pages
that send no `Content-Security-Policy`, and a frontend that sends one keeps it. It is also a
deliberate weakening of the gateway's guarantee -- under `default`, an upstream decides the header's
final value, including a more permissive one. Use it only for upstreams trusted to set that header;
see link:../security-threat-model.adoc#gw-14[GW-14] for the threat this trade-off accepts.

*CORS stays global.* CORS is evaluated before route selection and authentication -- a browser
preflight must be answered without credentials -- so no anchor can scope it. A `cors` key inside an
anchor's `security_headers` block *fails the boot* at schema load rather than being accepted and
ignored; declare CORS in the global `security_headers` block. The global CORS policy is applied to
every route, the anchor's included.

[[_type_and_access_axes]]
=== Type and access axes

Every anchor carries two *mandatory* classification axes (decision:
link:../adr/0013-anchor-type-access-axes.adoc[ADR-0013]), orthogonal to one another and to the
policy blocks above:

* *`type`* -- what terminal behaviour the anchor's routes expose: `proxy` (a reverse-proxy
  surface), `bff` (a Backend-For-Frontend surface), or `asset` (a static-asset surface, see
  link:endpoint-routes.adoc#_asset_terminal_action[Asset terminal action]). The anchor-`type`
  value space is entirely unrelated to the TLS-L4 `tls.passthrough_sni` surface, despite the
  adjacent vocabulary.
* *`access`* -- the audience the anchor admits: `public` (an anonymous surface, no
  authentication) or `authenticated` (requires a fully-backed auth posture).

The two axes are enforced fail-closed at boot by the *access -> auth matrix*, which aggregates
every violation in the single validation pass (never fails fast):

* A `type: bff` anchor *must* declare `access: authenticated` -- a BFF surface is authenticated
  by construction.
* An `access: authenticated` anchor *must* declare a non-`none` auth floor whose backing block is
  present: a `bearer` floor needs `token_validation` with at least one issuer; a `session` floor
  needs an `oidc` block.
* An `access: public` anchor *must not* declare an `auth` block at all -- public is the *absence*
  of auth, so the `require: none` posture lives on the endpoint (or route) rather than the anchor.

These rules, and every other anchor rule on this page that fails the boot, can be checked before a
gateway boots the configuration: `--validate-config` runs the boot's own validation offline and
reports each violation with the file and pointer the boot would name. See
link:offline-config-validation.adoc[Offline Configuration Validation].

Like the policy blocks, the axes vanish at runtime: `type` selects the route's terminal action
during route-table assembly and `access` is materialized onto each asset route's response
envelope; the request pipeline never consults an anchor.
