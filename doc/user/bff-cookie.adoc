= Cookie-Based BFF -- Operator Setup
:toc: left
:toclevels: 3
:toc-title: Table of Contents
:sectnums:
:source-highlighter: highlight.js

A task-oriented guide for operators standing up the *cookie-based BFF* (Variant 3): API Sheriff as
an OIDC confidential client that keeps no server-side session store and hands the browser a sealed
cookie that *is* the session. It tells you *how* to configure and run the variant; the field-by-field
contract lives in the link:../configuration/authentication-and-oidc.adoc#_oidc[Configuration Reference (`oidc`)] and the
design rationale in link:../variants/03-bff-cookie.adoc[Variant 3 -- BFF, Cookie-based].

== When to choose this variant

Choose the cookie-based BFF when you need a *stateless* gateway: multiple replicas with no shared
session store and no sticky routing for ordinary traffic. Tokens still never reach the browser in
readable form -- they are sealed with AES-256-GCM and the cookie is `HttpOnly`. It is the stateless
alternative to sticky sessions: once every replica shares the sealing key and the two signing keys
(with a client secret: the secret and the proof key), any replica serves any session, and a replica that restarts takes no session with it.

Choose the link:../variants/02-bff-session.adoc[server-session variant] instead when server-side-only
token custody is a hard requirement (the token must never leave the gateway, not even encrypted), or
when you need IdP-driven back-channel logout.

== Before you start

The client setup this variant shares with the server-session one -- the prerequisites, the two
signing keys, registering the client at the identity provider, the login exchange, client-secret
authentication, strict refresh-token rotation and a private-CA identity provider -- is walked through
in link:bff-oidc-common.adoc[BFF Confidential Client: Shared Setup]. Check its prerequisites first.
Its key, registration and login checkpoints need a gateway running with the `oidc` block and session
route configured below, so return to it once those are in place. This guide covers what the sealed
cookie adds: the sealing key, the cookie size budget and the limits of
a gateway that keeps no session state.

== Configure the confidential client

Add an `oidc` block to `gateway.yaml` and set at least one route's effective auth to
`require: session`. A minimal cookie-based configuration:

[source,yaml]
----
# gateway.yaml
oidc:
  issuer: https://idp.example.com/realms/main
  client_id: api-sheriff
  # no client_secret and no client_authentication.key_file: the gateway authenticates with
  # private_key_jwt and a key it generates on startup
  redirect_uri: https://gw.example.com/bff/callback   # registered exactly at the IdP
  scopes: [openid, profile]                   # requested on every login; endpoints add their own
  session:
    mode: cookie                              # sealed cookie, no store (this variant)
    cookie_name: __Host-sheriff               # optional; must stay a __Host- name -- see "Session cookie name"
    key_file: /run/secrets/session.key        # optional -- see "Key material" below
    max_cookie_size: 4019                     # seal-time VALUE budget; see "Cookie size budget"
    ttl_seconds: 3600                         # absolute lifetime from login
    idle_timeout_seconds: 1800                # optional: ends a session nobody uses; see "Idle timeout"
    csrf:
      trusted_origins: [https://app.example.com]
    refresh: { enabled: true, leeway_seconds: 30, on_failure: reauthenticate }
----

The BFF runtime is built from exactly two inputs: a recognised `session.mode` (`server` or `cookie`)
*and* a configured `redirect_uri`. Route auth is not part of that decision -- `require: session`
routes are what *use* the runtime once it exists, not what turns it on. With no recognised
`session.mode` the runtime stays inert, so a bearer-only deployment is unaffected.

*A runnable starting point.* The compose sample runs a working BFF -- in *server* mode:
`deployment/compose-sample/docker/sheriff-config/gateway.yaml` with its Keycloak realm, its signing
keys and a login check (see link:compose-sample.adoc#_logging_in_through_the_bff[Compose Sample --
Log in through the BFF]). Everything in it but the `oidc.session` block carries over to this variant
unchanged -- the client, its signing keys, `back_channel_origin`, the redirect and logout URLs. To run
it in cookie mode, replace that block: `mode: cookie` instead of `mode: server`, drop `store`, and
settle the two decisions only this variant has -- whether to provide a sealing key file (<<_key_material>>)
and the cookie size budget (<<_cookie_size_budget>>). The `0.2.4` image the sample pins predates
`back_channel_origin` and the `/bff/*` reserved paths and refuses its `gateway.yaml` at boot, so run
it on a gateway release after `0.2.4` or on a locally built image
(link:compose-sample.adoc#_route_b_a_locally_built_image[Route B]).

*An identity provider the gateway reaches at a different address.* Keep `oidc.issuer` the
browser-facing identity, set `oidc.back_channel_origin` to the internal origin the gateway dials, and
point `token_validation.issuers[].jwks.url` at the internal host. The setup is the same in both BFF
variants; see link:bff-oidc-common.adoc#idp-different-address[Shared Setup -- An identity provider
the gateway reaches at a different address].

*Next: the signing keys and registration.* Give the gateway its two signing keys and register it at
the identity provider as link:bff-oidc-common.adoc#key-material[Shared Setup -- Key material]
describes, or choose link:bff-oidc-common.adoc#client-secret[client-secret authentication] instead.
The exhibit above names no signing-key file and therefore runs on generated keys, which fits one
replica: every replica that shares a sealing key must be given the same two signing-key files --
or, with a client secret, the same proof-key file and no client-authentication key file.

[[_key_material]]
== Key material: the sealing key

This variant holds three keys. This section covers the *sealing key*, which encrypts the session
cookie. The two *signing keys* -- one for client authentication, one for DPoP -- are covered in
link:bff-oidc-common.adoc#key-material[Shared Setup -- Key material]. All three follow the same idea: provide the key, or leave it out and let the
gateway generate one for a single replica.

The sealing key has *two modes*, selected by whether you declare `session.key_file`.

[cols="1,2,2"]
|===
| Mode | How to select | Trade-off

| Provided key file
| Declare `session.key_file` with the path of a key file that holds the AES-256 key.
| Sessions survive a gateway restart and are shareable across replicas. Requires you to create,
  distribute and safeguard the file.

| Generate on startup
| Omit `session.key_file` entirely.
| No operator input at all -- the gateway mints a key at boot. But *sessions are dropped on every
  restart* (users re-authenticate) and the key *cannot be shared* with another replica, so each
  replica can only unseal its own cookies.
|===

Use generate-on-startup for a single-replica deployment or a development environment. Use a provided
key file for anything multi-replica or restart-sensitive, and give every replica the same file. The
gateway raises a startup diagnostic naming the active key mode -- it never logs the path or key
bytes.

The key file applies to cookie mode only. The server-session variant never reads a sealing key, so
declaring `session.key_file` with `mode: server` stops the boot.

=== Create the key file

The key file holds *one line of base64* that decodes to *exactly 32 bytes*, the AES-256 key. The
alphabet is the standard one of RFC 4648 section 4, the one `openssl` writes. ASCII whitespace before
and after the line is fine, in any amount -- space, tab, line feed (LF), vertical tab, form feed and
carriage return (CR), so blank lines and a trailing newline written as LF or CRLF are included -- and
the gateway strips it. Nothing else may be in the file, and no whitespace may appear inside the line.

One command creates a valid file:

[source,bash]
----
openssl rand -base64 32 > session.key
----

The gateway reads the file once, at startup, and accepts a file of at most 256 bytes. It reads at
most 257 bytes of it: the one byte past the limit is how a larger file is detected. A 32-byte key is
one base64 line of 44 characters, so a valid file is far below that bound.

=== Mount the file and name it

Mount the key file read-only, on every replica, and name it by its path. Write the path literally, or
supply it through a variable -- the path is a location, not a secret, so both forms are accepted:

[source,yaml]
----
# gateway.yaml
oidc:
  session:
    mode: cookie
    key_file: /run/secrets/session.key        # a literal path
    # key_file: ${SHERIFF_SESSION_KEY_FILE}   # or a path supplied by the deployment
----

The file content is the secret. Restrict the mount to the gateway: the gateway reads the file as it
finds it and does not check its permissions. Every replica that serves the same sessions is given the
same file.

=== What stops the gateway from starting

A sealing-key file the gateway cannot use stops the boot. It never falls back to a generated key. The
boot log names `oidc.session.key_file` and the defect. It never prints the path, a line of the file
or a decoder message.

[cols="2,3,3", options="header"]
|===
| What is wrong | What the log says after the key name | What to do

| The file is not there
| `names a file that does not exist`
| Mount it, or correct the path.

| The path names a directory or another non-file
| `does not name a regular file`
| Name the key file itself.

| The file cannot be read
| `names a file that cannot be read`
| Make it readable by the gateway's user.

| The value is not a usable path
| `does not name a usable file path`
| Correct the value. Check what a placeholder resolves to.

| The file is larger than 256 bytes
| `names a file larger than the 256 byte limit`
| Write the key file again with the command above.

| The file is empty, or holds whitespace only
| `holds no key`
| Write the key into it.

| The content is not one line of base64 -- a line break or space inside it, a character outside
  the alphabet, a PEM block
| `is not one line of base64`
| Write the key file again with the command above.

| The content decodes to another length
| `decodes to 16 bytes; it must decode to exactly 32 bytes (AES-256)` (with the length found)
| Use a 32-byte key: `openssl rand -base64 32`.
|===

In server mode the configuration check refuses a declared key file at `/oidc/session/key_file`
before anything is read: `oidc session key_file is declared in server session mode, which never
reads the cookie sealing key`. Remove the line, or use cookie mode.

=== Changing the key

There is exactly *one* sealing key. The gateway holds no decrypt-only companion key, so there is no
rotation window and nothing to stage: replacing the key is a clean break. Every cookie sealed under
the withdrawn key carries a key id the gateway no longer holds, is refused as "no session", and
those users simply log in again. Moving the same key into another file, or to another path, changes
nothing.

The gateway reads the key file only at startup. Replacing the file alone changes nothing: a running
gateway keeps the key it read at boot, so cookies sealed under the withdrawn key stay valid until it
restarts. To change the key:

. Generate *one* new key file, once, with `openssl rand -base64 32`, and replace the mounted file
  on *every* replica with that same file. Do not run the command per replica: each run creates a
  different key, and replicas holding different keys refuse each other's cookies for good.
. *Restart every replica.* The key changes when a replica restarts, not when its file changes.
  Until the last replica has restarted, replicas hold different keys and refuse each other's
  cookies, so keep that window short.

Treat a key change as a scheduled forced re-login -- operationally the same event as the
format-version change described in <<_upgrading_forced_re_login_on_a_format_change>>.

[[key-rotation]]
=== When to replace a provided key

A provided key has to be replaced on a schedule. The schedule follows from how often the gateway
seals a session cookie with it.

The gateway seals the session cookie with AES-256-GCM and a random 96-bit nonce, and NIST SP
800-38D bounds one key used that way at 2^32^ (4 294 967 296) seals. A session cookie is sealed at
a login, at a token refresh and at a widening, and at no other time. Each of the three follows a
successful response from the identity provider's token endpoint, so the gateway does not seal more
often than the identity provider answers it.

The activity cookie (see <<idle-timeout>>) does not count towards the bound. It is not encrypted.
It is authenticated with HMAC-SHA-256 under a key of its own, and that has no limit of this kind.
How often it is written does not affect the schedule, whatever a client does.

The rule: *replace the key in `session.key_file` before this many days have passed since the key
was first used.*

[source]
----
days = 4 294 967 296 / session-cookie seals per day
----

The seals per day are the successful token-endpoint responses your identity provider gives the
gateway's client per day, counted across all replicas that share the key. Read that number from the
identity provider; it is the authoritative one.

Where you have no such number yet, estimate it. A session in continuous use is refreshed once per
access-token lifetime, which is `86 400 / access-token lifetime in seconds` seals per session per
day: 288 at a lifetime of five minutes. Logins and widenings add to it. The table gives the
estimate for a five-minute access token and sessions that are in use around the clock.

[cols="1,1", options="header"]
|===
| Peak concurrent sessions | Replace the key at least every

| 10 000 | 1 491 days
| 50 000 | 298 days
| 100 000 | 149 days
| 500 000 | four weeks (the bound is 29.8 days, so a calendar month is too long)
|===

Replacing the key resets the count, and it ends every session, as described above. A *generated*
key needs no schedule beyond this: it is replaced at every restart, so restart the gateway within
the same interval.

== Session cookie name

`session.cookie_name` is optional. Omit it and the session cookie is `+__Host-sheriff-session+`. If you
declare a name, the gateway checks it at boot -- in this variant and in the server-session one alike --
and *refuses to start* unless the name meets all three of these rules:

. *It starts with `+__Host-+`, in exactly that case, followed by a name.* The prefix is not
  decoration. A browser accepts a `+__Host-+` cookie only when it is `Secure`, scoped to `Path=/` and
  carries no `Domain`, so the prefix is what turns those attributes into something the browser
  *enforces* -- a subdomain cannot plant or shadow the cookie. `sheriff-session`, `+__host-sheriff+`
  and `+__Secure-sheriff+` are all refused, and so is the bare prefix on its own.
. *It is a valid cookie token.* The name is written verbatim into the `Set-Cookie` header, so it must
  be a non-empty RFC 9110 token: no spaces, no control characters, no separators such as `;` or `=`.
  Any of those would let the configured name rewrite the header the gateway emits.
. *It is not one of the gateway's own cookies.* The login leg sets `+__Host-sheriff-binding+` and
  logout sets `+__Host-sheriff-logout+`. A session cookie with either name would silently overwrite
  that cookie in the browser, so both names are refused.

A refused name fails the boot with one error at `/oidc/session/cookie_name` listing every rule the
name broke, with the value escaped before it is printed. Nothing later in the gateway re-checks the
name -- the BFF runtime uses it exactly as written -- which is why the check happens at boot rather
than on the first login.

[[_cookie_size_budget]]
== Cookie size budget

Because the session travels in the cookie, its sealed value has a size budget --
`session.max_cookie_size`, defaulting to *4019* bytes. That default is not a round number by
accident: it is the largest value budget whose emitted `Set-Cookie` header still fits the ~4 KB per
cookie a browser is required to keep, under the default cookie name and TTL. A larger value risks
being *silently dropped* by the browser, leaving a session that can never be resolved.

[IMPORTANT]
.The budget key and the browser's 4 KB measure different things
====
`max_cookie_size` is a *value* budget -- the sealed cookie value alone. The ~4096 bytes RFC 6265
6.1 asks a browser to keep is a *header* budget: the cookie's name, its value *and* its attributes
summed together. Under the default cookie name the difference is 77 bytes -- 23 for
`+__Host-sheriff-session=+` plus 54 for the attributes the gateway always appends
(`+; Max-Age=3600; Path=/; Secure; HttpOnly; SameSite=Lax+`).

So the largest value budget that still emits a browser-safe header is *4019* (4096 - 77), not 4096 --
which is why 4019 is the shipped default, and the number `ApiSheriff-124` warns above, *under the
default cookie name and TTL*. A custom `session.cookie_name` or a `ttl_seconds` past 9999 moves the
overhead by its own length difference, and the warning threshold moves with it: the gateway derives
the overhead from the values you configured, so a longer name means a lower browser-safe budget than
4019 and `ApiSheriff-124` fires from there.

*Omitting the key does not opt out of that warning.* The gateway emits the same header whether the
number was written down or left to the default, so the check reads the *effective* budget. It stays
quiet on a default configuration -- 4019 plus the default 77 bytes lands exactly on the guarantee --
and it fires on a gateway that omitted the key while running a longer cookie name or a wider TTL.
====

The gateway therefore refuses to seal an over-budget session rather than truncating it, and logs a
warning naming the offending length. If you hit the budget, *reduce the token set* -- trim `scopes`
so the IdP issues a smaller access token, and cut `user_info.allowed_claims` -- or *run the
link:../variants/02-bff-session.adoc[server-session variant]*, where token size is irrelevant
because nothing crosses to the browser.

Raising the budget above 4019 is permitted -- the validated range runs to 8192 -- and the gateway
warns once at boot when you do (`ApiSheriff-124`). Treat that boot line as the last signal you will
get: it fires precisely because raising the budget switches off the seal refusal described above,
and what the refusal was protecting you from then happens in the browser instead, which reports
nothing to anyone.

*The name check and the budget work together.* The budget's range is validated at boot in every
session mode, `ApiSheriff-124` derives its threshold from the name and TTL you actually configured,
and the seal is refused rather than truncated. The name check only narrows *which* names reach that
derivation. A longer `+__Host-+` name still costs budget exactly as described above.

[IMPORTANT]
.Refresh is supported in cookie mode, with a measured and finite margin
====
*Enabling `session.refresh` still costs a third token in the seal.* The refresh token has to be
stored in the session -- it is the only thing that re-contacts the IdP -- and in cookie mode the
session *is* the cookie. An access + ID + refresh session is therefore the largest this variant ever
carries; the question is only how much room is left over.

Measured in the project's integration suite, against the pinned Keycloak image and its `integration`
realm, with refresh enabled and DPoP-bound access tokens that carry their `cnf` claim: the
`ApiSheriff-15` records of the cookie-refresh stack show sealed cookie values of *2572 to 2580
bytes* for a three-token session. Against the 4019-byte budget the largest leaves *1439 bytes*
unused, *35.8 %* of the budget.

*Read that margin as a budget for growth, not as spare capacity.* It is one realm's claim set, and
two independent things spend it:

* *A larger claim set.* Every mapper the IdP adds -- realm roles, group membership, audiences, user
  properties -- travels inside the seal. A deployment whose IdP mints fatter tokens spends the
  35.8 % first, and the gateway cannot trim what the IdP put there.
* *A longer `session.cookie_name`, or a `ttl_seconds` past 9999.* These do not grow the payload;
  they lower the bar. Both widen the per-header overhead, so the browser-safe value budget falls
  below 4019 and the margin closes from the other side.

When the margin does run out the failure is honest: the seal is refused (`ApiSheriff-114`) and login
answers `500` -- loud, server-side and diagnosable. *Raising `max_cookie_size` past the browser-safe
budget is not the remedy.* It silences that refusal without making the cookie deliverable, and moves
the failure into the browser, which drops the oversized header silently and reports it to no one.
The remedies that work are the ones above -- trim `scopes` and `user_info.allowed_claims` so the IdP
issues less -- and, where those do not cover it, the
link:../variants/02-bff-session.adoc[server-session variant], where token size is irrelevant because
nothing crosses to the browser.

*The seal also carries the session's two scope sets.* To refresh with the scopes of the current
token -- rather than narrowing the session back to `oidc.scopes` -- the session remembers its active
set, and to tell a scope a refresh can restore from one that needs a new authorization it remembers
the scopes the IdP is known to grant it (see link:bff-session.adoc#scopes[Scopes]). In this variant
the session is the cookie, so both travel in it, as the tenth and eleventh length-prefixed fields:
each is its scope names sorted and joined by single spaces, so each costs 2 bytes of framing plus the
names themselves, before deflate. For a handful of short scope names that is a few dozen bytes of the
budget per set. Both grow with what the session was granted: a login on a route whose endpoint
declares its own `scopes` seals `oidc.scopes` plus those names, a later widening for another
endpoint adds that endpoint's names, and the session keeps them for as long as the IdP keeps
granting them, so a
deployment with many long `endpoint.scopes` names spends the margin above faster. The budget check
covers the fields like any other -- an oversize seal is still refused, never truncated. A widening
whose merged session would no longer fit answers `500` on the callback and leaves the session as it
was.

The measurement, and the four routes weighed before this one shipped, are recorded in
link:../development/bff-cookie.adoc[the contributor guide]. Note what the 4019 bar is: the floor
every browser guarantees, not a limit measured in any particular browser.
====

[[idle-timeout]]
== Idle timeout and the activity cookie

A session ends at its absolute lifetime (`session.ttl_seconds`) and, earlier, when
`session.idle_timeout_seconds` have passed without a request the gateway let through on a session
route. The default is `1800`, or `ttl_seconds` when that is lower; a declared value below `1` or
above `ttl_seconds` stops the boot. What counts as a request is the same as in the server-session
variant (see link:bff-session.adoc#session-lifetime[How long a session lives]).

A stateless gateway has nowhere to keep the time of the last request but the browser. It keeps it
in a second cookie, the *activity cookie*.

[cols="1,3", options="header"]
|===
| Property | Value

| Name
| The session cookie's name followed by `-activity`: `+__Host-sheriff-session-activity+` under the
  default name. There is no key for it.

| Attributes
| The session cookie's: `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, no `Domain`. Its `Max-Age`
  is the session's remaining absolute lifetime.

| Content
| The time of the last request, authenticated under a key of its own and bound to the one session
  it belongs to. It is not encrypted and carries no token. Its value is always 56 characters.

| When it is set
| On the response to a request let through on a session route, once the recorded last request is
  *one interval old*. The interval is 60 seconds, or half the idle timeout where that is shorter.
  Requests that arrive in parallel with the same activity cookie each receive a new one, and so
  does a request that presents an older activity cookie again. The cookie is first set one interval or more after the login; until then the login itself is the last
  request.

| When it is cleared
| At logout, and whenever the gateway ends the session: both cookies are cleared together.
|===

*The session cookie is not set again on a request.* Only a login, a token refresh and a widening
write the session cookie. An ordinary response carries at most the small activity cookie.

*The deadline is exact to within one interval.* Because the cookie is written only once the
recorded time is one interval old, that time can be up to one interval older than the latest request. With an idle
timeout of 1800 seconds the interval is 60 seconds and a session ends between 1740 and 1800 seconds
after its last request. With an idle timeout of 30 seconds the interval is 15 seconds and a session
ends between 15 and 30 seconds after its last request. Where several replicas share the key, their
clock difference adds to that range, so keep the replicas' clocks synchronised.

*The cookie can only shorten a session.* A missing, altered or unreadable activity cookie, and one
that belongs to another session, is ignored, and the idle timeout is then measured from the login.
A browser extension, proxy or client that drops the cookie therefore ends the session one idle
period after login, whatever the user does. If sessions end after exactly `idle_timeout_seconds`
despite activity, check that the second cookie reaches the browser and comes back.

*A response that sets it is not cacheable.* Whenever the gateway sets or clears one of its cookies
on a response, it sends that response with `Cache-Control: no-store`, replacing the upstream's
value. In this variant that includes the session-route response that carries the activity cookie
-- for a browser, about one response per session per interval -- and every response that re-seals the session
cookie. All other responses keep the upstream's cache policy.

*It shares the `Cookie` header headroom.* The inbound `Cookie` header cap is unchanged:
`max_cookie_size` plus 512 bytes. The activity cookie takes 88 of those 512 bytes under the default
name. The application cookies a route forwards travel in the same header, and the upstream receives
only those pairs -- but they may still be larger than the upstream's own header limits accept (see
link:../configuration/routing-and-forwarding.adoc#_cookies_size[Forwarded cookies and the cookie-size cap]).

*A WebSocket or a streamed response counts once, when it starts.* An open WebSocket does not keep
the session alive. On a session route the gateway closes a WebSocket at the session's absolute
expiry, with close code `1008` and the reason `session ended`; in this variant nothing closes it
earlier (see <<_what_is_unavailable_in_this_variant>>).

[[_what_is_unavailable_in_this_variant]]
== What is unavailable in this variant

A stateless gateway holds no session index and cannot reach another browser's cookie, so
IdP-driven destruction is *unsupported*:

* *Back-channel logout answers `404`.* The reserved path stays wired and deliberately returns `404`
  rather than falling through to the proxy route table -- it never claims a destruction that did not
  happen.
* *No destroy-by-`sid` / destroy-by-`sub`.* Nothing can be revoked centrally with *immediate*
  effect. The one IdP-side lever that reaches a cookie session is revoking its grant at the IdP
  (deleting the user's session there): with `session.refresh` enabled, the cookie keeps working
  until its access token enters the refresh window, and that refresh is then rejected and ends the
  session (`ApiSheriff-111`, `credential-rejected`). With refresh disabled it keeps working until
  `ttl_seconds` expires.

RP-initiated logout (the user logging themselves out) works normally: the browser's cookie is
cleared, and an expired cookie the browser keeps anyway is still refused server-side by the absolute
TTL check. Where instant central revocation is a hard requirement, use the server-session variant.
Mitigate in this variant with a short `ttl_seconds` and short access-token lifetimes.

*A logout does not stop a response that is already in flight.* The gateway keeps nothing a logout
could mark, so a token refresh or a session widening that was already running for the same browser
when it logged out still answers with a re-sealed session cookie. If that response reaches the
browser after the logout response, the browser holds a session cookie again. It lasts until
`ttl_seconds` at the latest; where the logout ended the session at the IdP as well, it ends earlier,
when the session's next refresh is refused there. The window needs a request of the same browser in
flight at the moment of the logout, and the mitigations are the two above. The server-session
variant does not have this window: there a logout wins over a refresh or a widening that was in
flight, and the session stays ended.

*A cookie sealed before a widening stays usable as it was sealed.* A granted widening re-seals the
session cookie with the new tokens and scopes. The cookie the browser held before still unseals: it
resolves the session at its earlier level, without the scopes the widening added, until the
session's absolute lifetime. It never gains the new scopes. The gateway keeps nothing that could
withdraw it. In the server-session variant the previous cookie value stops working at the moment of
the widening.

*A new login does not withdraw the earlier cookie either.* The login's `Set-Cookie` replaces the
earlier session cookie in the browser. A copy of the earlier cookie taken before that stays usable
until its own lifetime ends.

*A logout does not close an open WebSocket.* A WebSocket on a session route is closed at the
session's absolute expiry and at no earlier session event: not at a logout, and not at the idle
timeout. The route's own WebSocket idle timer and either peer can still close it. In the
server-session variant a logout closes it (see
link:bff-session.adoc#websocket-sessions[WebSockets and streamed responses]).

*No per-user session bound.* `session.max_sessions_per_subject` counts sessions in a store, and
this variant has none. Declaring the key in cookie mode stops the boot.

== Session affinity for the login leg

The variant is stateless once a session is *established*, but not during the login exchange. The
pending authorization held between the login redirect and the OIDC callback is per-instance and
never shared, so a login *begun* on one replica must *complete* on that replica. A session widening
holds its pending authorization the same way: a widening callback that lands on another replica is
refused.

*Configure session affinity for the login leg and for each widening* -- the redirect through to the
callback, an interactive retry included. Every other request may be balanced freely across replicas
with no affinity.

== Upgrading: forced re-login on a format change

A release that changes the sealed-cookie format forces every cookie-mode user to log in again, once.
The format carries a version that is bound into the cookie's authenticated data and read before any
cipher is constructed. A cookie carrying any other version is refused rather than mis-parsed --
logged once as `ApiSheriff-113` with disposition `unknown-version` -- and treated as no session:
navigations are redirected to login and API calls answer `401`. There is no rolling migration, so
schedule such a deploy as a forced re-login.

The current format is version *2*: the sealed payload is length-prefixed raw UTF-8, deflated before
encryption, and carries eleven fields -- the tokens, the identity and session claims, and the
session's active and granted scope sets.

The activity cookie has a format version of its own, currently *2*. A change to it leaves the sealed
session cookie valid: the gateway ignores every activity cookie written before, and measures the
idle timeout of those sessions from their login. A session whose login is older than
`idle_timeout_seconds` at that moment ends at its next request and the user logs in again; a younger
session continues.

== Operate

* *Absolute TTL.* `ttl_seconds` is counted from login and is never extended by a refresh; the
  deadline is recomputed from the original login on every re-seal, so an endlessly-refreshed session
  still dies on time.
* *Idle timeout.* `idle_timeout_seconds` ends a session nobody uses. It rests on the activity cookie;
  see <<idle-timeout>>.
* *Refresh re-seals the cookie.* A transparent token refresh emits a new `Set-Cookie` -- that is the
  whole of "persisting" in this variant. A granted widening of the session re-seals it the same way.
  An ordinary request does not: it sets at most the activity cookie.
* *Logout clears two cookies.* The session cookie and the activity cookie are cleared together, at
  logout and whenever the gateway ends a session. Logout itself behaves as in the server-session
  variant: the cookies are cleared first, and an IdP without a usable end-session endpoint lands the
  browser on `oidc.logout.final_redirect` with `ApiSheriff-135` logged once (see
  link:bff-session.adoc#logout[Logout]).
* *Replace a provided sealing key on schedule.* See <<key-rotation>>.
* *The gateway's cookies stay at the gateway.* The session cookie and the activity cookie are
  gateway cookies, as are `+__Host-sheriff-binding+` and `+__Host-sheriff-logout+`: none of them
  reaches an upstream under any `cookies` policy, and an upstream `Set-Cookie` naming one is dropped.
  The application's own cookies cross only as the route's `cookies` block admits them (see
  link:bff-session.adoc#gateway-cookies[The gateway's cookies and your application] and
  link:../configuration/routing-and-forwarding.adoc#_never_forward_set[the never-forward set]).
* *Scopes are enforced as in the server-session variant.* A session lacking a scope the route needs
  is refreshed, widened or refused `403` exactly as
  link:bff-session.adoc#scope-enforcement[the server-session guide] describes. One case is specific
  to this variant: when the near-expiry refresh of a request has just issued a new cookie, that
  request does not also refresh for a missing scope -- its own `Cookie` header names a refresh token
  the IdP has already retired -- and is widened or refused instead. The next request carries the new
  cookie and is refreshed normally.
* *Refresh failures, IdP reachability and a private-CA IdP* are the same in both variants; see
  link:bff-oidc-common.adoc#_operate[Shared Setup -- Operate],
  link:bff-oidc-common.adoc#_configure_strict_refresh_token_rotation_at_the_idp[strict refresh-token
  rotation at the IdP] -- a must in this variant, where a copied cookie is a copied refresh token --
  and link:bff-oidc-common.adoc#_private_ca_self_signed_idp[Private-CA / self-signed IdP].
