= Cookie-Based BFF -- Operator Setup
:toc:
:toclevels: 3
:sectnums:

A task-oriented guide for operators standing up the *cookie-based BFF* (Variant 3): API Sheriff as
an OIDC confidential client that keeps no server-side session store and hands the browser a sealed
cookie that *is* the session. It tells you *how* to configure and run the variant; the field-by-field
contract lives in the link:../configuration.adoc#_oidc[Configuration Reference (`oidc`)] and the
design rationale in link:../variants/03-bff-cookie.adoc[Variant 3 -- BFF, Cookie-based].

== When to choose this variant

Choose the cookie-based BFF when you need a *stateless* gateway: multiple replicas with no shared
session store and no sticky routing for ordinary traffic. Tokens still never reach the browser in
readable form -- they are sealed with AES-256-GCM and the cookie is `HttpOnly`.

Choose the link:../variants/02-bff-session.adoc[server-session variant] instead when server-side-only
token custody is a hard requirement (the token must never leave the gateway, not even encrypted), or
when you need IdP-driven back-channel logout.

== Prerequisites

* An OIDC provider (IdP) where you can register a *confidential client*. The gateway asks three
  things of that client, in every configuration:
** it accepts *pushed authorization requests* (RFC 9126) -- the gateway sends no other kind;
** it binds access tokens with *DPoP* (RFC 9449) -- the gateway refuses a token that is not bound;
** it issues access tokens as JWTs.
* In the default setup the client authenticates with a *signed JWT* (`private_key_jwt`), and the IdP
  fetches the gateway's public key from the gateway's JWKS endpoint. The IdP must be able to reach
  that endpoint server-to-server, over `https`. See <<signing-keys>>.
* A registered *redirect URI* pointing at the gateway's own callback path (`oidc.redirect_uri`),
  matched exactly at the IdP.
* A session sealing key, if you pass one, available as an environment variable (never written
  inline -- secrets in `oidc` must be `${ENV_VAR}` references).

No client secret is needed. A client secret remains possible as an operator choice; it is described,
with its warning, in <<client-secret>>.

== Configure the confidential client

Add an `oidc` block to `gateway.yaml` and set at least one route's effective auth to
`require: session`. A minimal cookie-based configuration:

[source,yaml]
----
# gateway.yaml
oidc:
  issuer: https://idp.example.com/realms/main
  client_id: api-sheriff
  # no client_secret and no client_authentication.key_file: the gateway authenticates with
  # private_key_jwt and a key it generates on startup
  redirect_uri: https://gw.example.com/auth/callback   # registered exactly at the IdP
  scopes: [openid, profile]                   # requested on every login; endpoints add their own
  session:
    mode: cookie                              # sealed cookie, no store (this variant)
    cookie_name: __Host-sheriff               # optional; must stay a __Host- name -- see "Session cookie name"
    encryption_key: ${SHERIFF_SESSION_KEY}    # optional -- see "Key material" below
    max_cookie_size: 4019                     # seal-time VALUE budget; see "Cookie size budget"
    ttl_seconds: 3600                         # absolute lifetime from login
    csrf:
      trusted_origins: [https://app.example.com]
    refresh: { enabled: true, leeway_seconds: 30, on_failure: reauthenticate }
----

The BFF runtime is built from exactly two inputs: a recognised `session.mode` (`server` or `cookie`)
*and* a configured `redirect_uri`. Route auth is not part of that decision -- `require: session`
routes are what *use* the runtime once it exists, not what turns it on. With no recognised
`session.mode` the runtime stays inert, so a bearer-only deployment is unaffected.

[[_key_material]]
== Key material: the sealing key

This variant holds three keys. This section covers the *sealing key*, which encrypts the session
cookie. The two *signing keys* -- one for client authentication, one for DPoP -- are covered in
<<signing-keys>>. All three follow the same idea: provide the key, or leave it out and let the
gateway generate one for a single replica.

The sealing key has *two modes*, selected by whether you declare `session.encryption_key`.

[cols="1,2,2"]
|===
| Mode | How to select | Trade-off

| Passed key
| Declare `session.encryption_key` as an `${ENV_VAR}` reference holding an AES-256 key.
| Sessions survive a gateway restart and are shareable across replicas. Requires you to generate,
  distribute and safeguard the key.

| Generate on startup
| Omit `session.encryption_key` entirely.
| No operator input at all -- the gateway mints a key at boot. But *sessions are dropped on every
  restart* (users re-authenticate) and the key *cannot be shared* with another replica, so each
  replica can only unseal its own cookies.
|===

Use generate-on-startup for a single-replica deployment or a development environment. Use a passed
key for anything multi-replica or restart-sensitive. The gateway raises a startup diagnostic naming
the active key mode -- it never logs key bytes.

=== Changing the key

There is exactly *one* sealing key. The gateway holds no decrypt-only companion key, so there is no
rotation window and nothing to stage: replacing `session.encryption_key` is a clean break. Every
cookie sealed under the withdrawn key carries a key id the gateway no longer holds, is refused as
"no session", and those users simply log in again.

Treat a key change as a scheduled forced re-login -- operationally the same event as the
format-version change described under "Upgrading" below.

=== Migrating from a configuration that declared `previous_key`

[WARNING]
====
`oidc.session.previous_key` *has been removed*, and the configuration schema rejects unknown keys.
A `gateway.yaml` that still declares `previous_key` therefore *fails at boot* -- the gateway does
not start, and the failure names the offending key.

*Remedy: delete the `previous_key` line* from `oidc.session`. Nothing replaces it. The environment
variable it referenced (commonly `SHERIFF_SESSION_KEY_PREVIOUS`) becomes unused and can be retired
from the deployment.

If you were mid-rotation when you upgrade, the cookies still sealed under the retired key are
refused as "no session" and those users log in again -- so prefer to finish the rotation (or accept
the re-login) before rolling this version out.
====

[[signing-keys]]
== Key material: the two signing keys

This is the default setup. Besides the sealing key the gateway signs with two keys, one per purpose:

[cols="2,3,2", options="header"]
|===
| Configuration key | What the key signs | Who needs the public half

| `oidc.client_authentication.key_file`
| The client assertion the gateway authenticates with on every call to the identity provider
  (`private_key_jwt`).
| The identity provider. It fetches it from the gateway's JWKS endpoint.

| `oidc.sender_constraint.key_file`
| The DPoP proof on every token request. Every access token is bound to this key.
| Nobody in advance. The public half travels inside each proof, so this key is not registered
  anywhere.
|===

Each key is optional. Each names a PEM file on a mount. The two may name the same file, but use two
keys: one key per purpose is what the FAPI 2.0 profile asks for.

=== The two modes, and when to use which

Each key is in one of two modes. Both are supported in production.

* *Generated* -- leave `key_file` out. The gateway generates an EC P-256 key when it starts and logs
  `ApiSheriff-20` once for that purpose. Nothing has to be provisioned. The key lives in one process:
  it is replaced on every restart, and no other replica has it. *The generated mode is for a single
  replica.*
* *Provided* -- name a key file. The key survives a restart and can be given to every replica.

*Every replica that shares a sealing key must be given the same two key files.* The cookie variant
exists to run several replicas without sticky routing, and the signing keys are part of what those
replicas must share:

* A replica with a different *client-authentication key* signs assertions the identity provider
  cannot verify against the key set it fetched from another replica. Authentication then fails on
  some requests and not on others.
* A replica with a different *proof key* presents a DPoP proof of a key the session's tokens are not
  bound to when it refreshes a session another replica logged in.

So a deployment that passes a sealing key for more than one replica passes both key files as well.
The exhibit above names no key file and therefore runs on generated keys, which fits one replica.

=== Produce a key file

A key file holds *exactly one* unencrypted PKCS#8 `PRIVATE KEY` block *and exactly one* `PUBLIC KEY`
block, and nothing else but whitespace:

[source,text]
----
-----BEGIN PRIVATE KEY-----
...
-----END PRIVATE KEY-----
-----BEGIN PUBLIC KEY-----
...
-----END PUBLIC KEY-----
----

*The `PUBLIC KEY` block is mandatory for every key type, RSA included.* The gateway publishes the
public half and embeds it in its proofs, and it does not derive it from the private key. At startup
it checks that the two blocks belong together.

Produce the file with OpenSSL. For an RSA key:

[source,bash]
----
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out client-auth.pem
openssl pkey -in client-auth.pem -pubout -out client-auth.pub
cat client-auth.pub >> client-auth.pem
rm client-auth.pub
----

For an EC key:

[source,bash]
----
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -pkeyopt ec_param_enc:named_curve \
  -out dpop.pem
openssl pkey -in dpop.pem -pubout -out dpop.pub
cat dpop.pub >> dpop.pem
rm dpop.pub
----

Check the result: the file must begin with `-----BEGIN PRIVATE KEY-----` and contain
`-----BEGIN PUBLIC KEY-----`.

=== Key types, sizes and algorithms

[cols="1,2,1", options="header"]
|===
| Key type | Minimum | The gateway signs with

| RSA | a modulus of 2048 bits | `PS256`
| EC | curve P-256, no other curve | `ES256`
|===

The key type selects the signing algorithm. There is no algorithm setting, and no other algorithm
can be chosen. Ed25519 keys are not accepted.

*The key id cannot be set.* The gateway derives it from the key (the RFC 7638 thumbprint of the
public half), so it changes exactly when the key changes.

=== Mount the file and name it

Mount the key files read-only, on every replica, and name each by its path. Write the path
literally, or supply it through a variable -- a path is a location, not a secret, so both forms are
accepted:

[source,yaml]
----
# gateway.yaml
oidc:
  client_authentication:
    key_file: /etc/sheriff/keys/client-auth.pem     # a literal path
  sender_constraint:
    key_file: ${SHERIFF_DPOP_KEY_FILE}              # or a path supplied by the deployment
----

The file content is the secret. Restrict the mount to the gateway: the gateway reads the file as it
finds it and does not check its permissions.

=== What stops the gateway from starting

A key file the gateway cannot use stops the boot. It never falls back to a generated key. The boot
log names the configuration key -- `oidc.client_authentication.key_file` or
`oidc.sender_constraint.key_file` -- and the defect. It never prints the path or a line of the file.

[cols="2,3,3", options="header"]
|===
| What is wrong | What the log says after the key name | What to do

| The file is not there
| `names a file that does not exist`
| Mount it, or correct the path.

| The file cannot be read
| `names a file that cannot be read`
| Make it readable by the gateway's user.

| The `PUBLIC KEY` block is missing
| `holds no PUBLIC KEY block`
| Append the public half, as in the commands above.

| The two blocks belong to different keys
| `holds a PRIVATE KEY block and a PUBLIC KEY block that do not belong to the same key`
| Write the public block from this private key.

| The private key is encrypted
| `holds an ENCRYPTED PRIVATE KEY block; an encrypted key is not supported`
| Convert it with `openssl pkcs8 -topk8 -nocrypt`.

| A traditional `RSA PRIVATE KEY` or `EC PRIVATE KEY` block
| `holds a block labelled RSA PRIVATE KEY; that key format is not supported` (or `EC PRIVATE KEY`)
| Convert it with `openssl pkcs8 -topk8 -nocrypt`.

| An EC key on another curve
| `holds an EC key on a curve other than P-256`
| Generate the key on P-256.

| An Ed25519 key
| `holds an EdDSA key; EdDSA is not offered`
| Use an RSA key of at least 2048 bits or an EC P-256 key.

| An RSA key that is too small
| `holds an RSA key with a modulus below 2048 bits`
| Generate a key of at least 2048 bits.
|===

The remaining refusals -- a directory instead of a file, a file above 16 KiB, a second block of the
same kind, any other PEM block, text outside a block -- are listed in
link:../configuration.adoc#_oidc_signing_keys[Configuration Reference -- Signing keys].

=== Register the client at the identity provider

The identity provider learns the client-authentication key from the gateway. Register the
gateway's JWKS URL at the client; do not paste the public key into the identity provider.

* *The JWKS URL* is `https://<gateway address the identity provider can reach>/auth/jwks`. The path
  is `oidc.client_authentication.jwks_path`; `/auth/jwks` is its default. The endpoint answers a
  `GET` without a credential, on every host name the gateway answers on, so an internal service name
  works. It publishes the public half of the client-authentication key and nothing else.
* *The identity provider dials the gateway.* It must reach that URL server-to-server and must trust
  the gateway's certificate for the name it dials. Behind a load balancer every replica must answer
  with the same key, which is one more reason to provide the key file.
* *The DPoP key needs no registration.* It is never published.

On Keycloak 26.5.7 the clients of this project's integration stack carry these settings (shown as
they appear in a realm export):

[cols="2,3", options="header"]
|===
| Setting | Value

| `clientAuthenticatorType` | `client-jwt` (signed JWT)
| `use.jwks.url` | `true` (_Use JWKS URL_)
| `jwks.url` | the gateway's JWKS URL
| `token.endpoint.auth.signing.alg` | `PS256` for an RSA key, `ES256` for an EC or a generated key
| `require.pushed.authorization.requests` | `true`
| `dpop.bound.access.tokens` | `true`
|===

The identity provider needs the public key only. Keycloak nevertheless generates and stores a secret
for every client that is imported without one. With the authenticator above it refuses that secret
at the token endpoint. This was seen on Keycloak 26.5.7; no test asserts it.

=== What the browser sees at login

The gateway pushes the authorization request to the identity provider and redirects the browser with
two parameters only, `client_id` and `request_uri`. No scope, no `state` and no redirect URI travel
through the browser. Keycloak 26.5.7 answers that redirect with a further `302` to its own
`login-actions/authenticate` page before it shows the login form.

If the identity provider offers no pushed-authorization-request endpoint, or the push fails, the
login is refused with `502`. The gateway logs `WARN` `ApiSheriff-132` with the reason, once per
reason; repeats stay at `DEBUG`.

=== When the identity provider does not bind the token

The gateway accepts a token response only when it is bound to the proof key: its type must be `DPoP`,
and the access token must carry a `cnf.jkt` claim that names the gateway's proof key. Otherwise:

* *At login* the callback answers `400`. No session is created and no session cookie is set.
* *At a refresh* the session ends, its cookie is cleared, and the request is answered as
  `oidc.session.refresh.on_failure` says.
* *In the log* the gateway writes `WARN` `ApiSheriff-131`, naming the leg and the reason and no token
  material.

An identity provider that issues *opaque* access tokens is refused the same way: there is no `cnf`
to read. The fix is at the identity provider: require DPoP-bound tokens for the client. This holds
in both client-authentication modes.

[[replacing-a-key]]
== Replacing a signing key

* *A generated key* is replaced by every restart.
* *A provided key* is replaced by replacing the file on every replica and restarting them. The file
  is read once, at startup.

Nothing is changed at the identity provider. The key id changes with the key, and the identity
provider fetches the new client key from the JWKS endpoint when it meets the unknown key id. It does
so at most once per fetch interval -- ten seconds by default in Keycloak -- so a request that falls
inside that interval can fail. There is no overlap: the old key is not published or accepted next to
the new one. While replicas are restarted one after another, those still on the old key and those
already on the new one disagree for as long as the roll takes.

*What a replacement does to live sessions.* On Keycloak 26.5.7 a session survives it. The integration
suite restarts a gateway whose two keys are generated, under a live session. The next refresh of
that session succeeds, the session continues, and the new access token is bound to the new proof
key.

That observation has limits, and they are stated here so that it is not read as more than it is:

* It was made in this variant, with a *passed* sealing key, so the session cookie stayed readable
  across the restart. With a generated sealing key a restart drops every session whatever the
  signing keys do.
* Only generated keys were replaced. Replacing a provided key file was not run.
* It holds for the identity provider and the version named. Another identity provider may refuse a
  refresh that presents a proof of a new key.

Plan for the worst case: sessions whose tokens were bound to the old key fail their next refresh,
end, and follow `oidc.session.refresh.on_failure` -- with the default, the user is sent through the
login again.

[[client-secret]]
== Client-secret authentication: an operator choice

[WARNING]
====
Client-secret authentication is not FAPI 2.0 conformant and may weaken security.
====

The gateway can authenticate to the identity provider with a client secret instead of a key. It is a
supported configuration, and it is your decision to make.

*How it is selected.* By configuring `oidc.client_secret`. There is no switch: the key being present
is the selection, and removing it selects key-based authentication again.

[source,yaml]
----
# gateway.yaml
oidc:
  issuer: https://idp.example.com/realms/main
  client_id: api-sheriff
  client_secret: ${SHERIFF_CLIENT_SECRET}     # must be a bare ${ENV_VAR} reference
  sender_constraint:
    key_file: /etc/sheriff/keys/dpop.pem      # optional, exactly as in key mode
----

*What changes, and what does not.*

* Only the client credential changes. The gateway sends the secret as `client_secret_basic` on every
  call to the identity provider.
* Pushed authorization requests stay on.
* DPoP stays on. `oidc.sender_constraint.key_file` is handled exactly as in key mode -- every replica
  needs the same file -- and a token response that is not bound to the proof key is still refused.

*What is refused.* `oidc.client_secret` together with `oidc.client_authentication.key_file` does not
boot. The message names both keys and carries neither the secret nor the path:
`oidc.client_secret and oidc.client_authentication.key_file are both declared`. Remove one of them.

*What the gateway logs.* At every boot it writes `WARN` `ApiSheriff-130`:

[source,text]
----
ApiSheriff-130: The BFF authenticates to the identity provider with oidc.client_secret. Client-secret authentication is not FAPI 2.0 conformant and may weaken security. Pushed authorization requests and the DPoP sender constraint stay in effect. Removing oidc.client_secret selects private_key_jwt
----

The one way to silence it is to remove `oidc.client_secret`.

*What the JWKS path answers.* `404`. There is no client-authentication key in this mode, so there is
no key set for the identity provider to fetch. The path stays reserved and is not handed to the
route table.

*What to register at the identity provider.* A client that authenticates with a secret, requires
pushed authorization requests and binds its tokens with DPoP. Register no key-set URL. On Keycloak:
`clientAuthenticatorType: client-secret`, `require.pushed.authorization.requests: true`,
`dpop.bound.access.tokens: true`.

*A copied configuration selects this mode.* A `gateway.yaml` taken from another deployment that
carries `client_secret` authenticates with the secret without anyone having decided it. Check the
boot log for `ApiSheriff-130`.

== Session cookie name

`session.cookie_name` is optional. Omit it and the session cookie is `+__Host-sheriff-session+`. If you
declare a name, the gateway checks it at boot -- in this variant and in the server-session one alike --
and *refuses to start* unless the name meets all three of these rules:

. *It starts with `+__Host-+`, in exactly that case, followed by a name.* The prefix is not
  decoration. A browser accepts a `+__Host-+` cookie only when it is `Secure`, scoped to `Path=/` and
  carries no `Domain`, so the prefix is what turns those attributes into something the browser
  *enforces* -- a subdomain cannot plant or shadow the cookie. `sheriff-session`, `+__host-sheriff+`
  and `+__Secure-sheriff+` are all refused, and so is the bare prefix on its own.
. *It is a valid cookie token.* The name is written verbatim into the `Set-Cookie` header, so it must
  be a non-empty RFC 9110 token: no spaces, no control characters, no separators such as `;` or `=`.
  Any of those would let the configured name rewrite the header the gateway emits.
. *It is not one of the gateway's own cookies.* The login leg sets `+__Host-sheriff-binding+` and
  logout sets `+__Host-sheriff-logout+`. A session cookie with either name would silently overwrite
  that cookie in the browser, so both names are refused.

A refused name fails the boot with one error at `/oidc/session/cookie_name` listing every rule the
name broke, with the value escaped before it is printed. Nothing later in the gateway re-checks the
name -- the BFF runtime uses it exactly as written -- which is why the check happens at boot rather
than on the first login.

If an older `gateway.yaml` of yours declares a name without the prefix, rename it to a `+__Host-+`
name (or delete the line to take the default). Existing sessions under the old name are not carried
over: browsers keep sending the old cookie, the gateway no longer reads it, and those users log in
again.

== Cookie size budget

Because the session travels in the cookie, its sealed value has a size budget --
`session.max_cookie_size`, defaulting to *4019* bytes. That default is not a round number by
accident: it is the largest value budget whose emitted `Set-Cookie` header still fits the ~4 KB per
cookie a browser is required to keep, under the default cookie name and TTL. A larger value risks
being *silently dropped* by the browser, leaving a session that can never be resolved.

[IMPORTANT]
.The budget key and the browser's 4 KB measure different things
====
`max_cookie_size` is a *value* budget -- the sealed cookie value alone. The ~4096 bytes RFC 6265
6.1 asks a browser to keep is a *header* budget: the cookie's name, its value *and* its attributes
summed together. Under the default cookie name the difference is 77 bytes -- 23 for
`+__Host-sheriff-session=+` plus 54 for the attributes the gateway always appends
(`+; Max-Age=3600; Path=/; Secure; HttpOnly; SameSite=Lax+`).

So the largest value budget that still emits a browser-safe header is *4019* (4096 - 77), not 4096 --
which is why 4019 is the shipped default, and the number `ApiSheriff-124` warns above, *under the
default cookie name and TTL*. A custom `session.cookie_name` or a `ttl_seconds` past 9999 moves the
overhead by its own length difference, and the warning threshold moves with it: the gateway derives
the overhead from the values you configured, so a longer name means a lower browser-safe budget than
4019 and `ApiSheriff-124` fires from there.

*Omitting the key does not opt out of that warning.* The gateway emits the same header whether the
number was written down or left to the default, so the check reads the *effective* budget. It stays
quiet on a default configuration -- 4019 plus the default 77 bytes lands exactly on the guarantee --
and it fires on a gateway that omitted the key while running a longer cookie name or a wider TTL.
That case used to pass in silence, because the default was 4096 and an omitted key was skipped
outright.
====

The gateway therefore refuses to seal an over-budget session rather than truncating it, and logs a
warning naming the offending length. If you hit the budget, *reduce the token set* -- trim `scopes`
so the IdP issues a smaller access token, and cut `user_info.allowed_claims` -- or *run the
link:../variants/02-bff-session.adoc[server-session variant]*, where token size is irrelevant
because nothing crosses to the browser.

Raising the budget above 4019 is permitted -- the validated range runs to 8192 -- and the gateway
warns once at boot when you do (`ApiSheriff-124`). Treat that boot line as the last signal you will
get: it fires precisely because raising the budget switches off the seal refusal described above,
and what the refusal was protecting you from then happens in the browser instead, which reports
nothing to anyone.

*The session-cookie-name check changed nothing here.* The budget key was re-examined when the name
check above was added, and it needed no further change: its range is still validated at boot in
every session mode, `ApiSheriff-124` still derives its threshold from the name and TTL you actually
configured, and the seal is still refused rather than truncated. The name check only narrows *which*
names reach that derivation. A longer `+__Host-+` name still costs budget exactly as described above.

[IMPORTANT]
.Refresh is supported in cookie mode, with a measured and finite margin
====
*This supersedes earlier guidance.* Previous releases of this guide said that access + ID + refresh
together commonly exceeded the budget, and pointed you at the server-session variant as the answer
whenever both refresh and browser-safe cookies were required. That is no longer the position: the
sealed payload is now framed as length-prefixed raw UTF-8 and deflated before it is encrypted,
which is what made the three-token session fit.

*Enabling `session.refresh` still costs a third token in the seal.* The refresh token has to be
stored in the session -- it is the only thing that re-contacts the IdP -- and in cookie mode the
session *is* the cookie. An access + ID + refresh session is therefore the largest this variant ever
carries; the question is only how much room is left over.

Measured on a three-token fixture built to the shape Keycloak issues for the `integration` realm:
the framed plaintext is *3433 bytes*, and the sealed cookie value that leaves the gateway is *2700
bytes* -- 78.6 % of the framed plaintext. Against the 4019-byte budget that leaves *1319 bytes*
unused, *32.8 %* of the budget.

*Read that margin as a budget for growth, not as spare capacity.* It is one realm's claim set, and
two independent things spend it:

* *A larger claim set.* Every mapper the IdP adds -- realm roles, group membership, audiences, user
  properties -- travels inside the seal. A deployment whose IdP mints fatter tokens spends the
  32.8 % first, and the gateway cannot trim what the IdP put there.
* *A longer `session.cookie_name`, or a `ttl_seconds` past 9999.* These do not grow the payload;
  they lower the bar. Both widen the per-header overhead, so the browser-safe value budget falls
  below 4019 and the margin closes from the other side.

When the margin does run out the failure is honest: the seal is refused (`ApiSheriff-114`) and login
answers `500` -- loud, server-side and diagnosable. *Raising `max_cookie_size` past the browser-safe
budget is not the remedy.* It silences that refusal without making the cookie deliverable, and moves
the failure into the browser, which drops the oversized header silently and reports it to no one.
The remedies that work are the ones above -- trim `scopes` and `user_info.allowed_claims` so the IdP
issues less -- and, where those do not cover it, the
link:../variants/02-bff-session.adoc[server-session variant], where token size is irrelevant because
nothing crosses to the browser.

*The seal also carries the session's active scope set.* To refresh with the scopes the IdP actually
granted -- rather than narrowing the session back to `oidc.scopes` -- the session remembers that set
(see link:bff-session.adoc#scopes[Scopes]), and in this variant the session is the cookie. The set
travels as a tenth length-prefixed field: the scope names sorted and joined by single spaces, so it
costs 2 bytes of framing plus the names themselves, before deflate. For a handful of short scope names
that is a few dozen bytes of the budget. It grows with the scope set the login requested: a login on
a route whose endpoint declares its own `scopes` seals `oidc.scopes` plus those names, and keeps them
for the life of the session, so a deployment with many long `endpoint.scopes` names spends the margin
above faster. The budget check covers the field like any other -- an oversize seal is still refused,
never truncated.

The measurement, and the four routes weighed before this one shipped, are recorded in
link:../development/bff-cookie.adoc[the contributor guide]. Note what the 4019 bar is: the floor
every browser guarantees, not a limit measured in any particular browser.

[[_configure_strict_refresh_token_rotation_at_the_idp]]
== Configure strict refresh-token rotation at the IdP

In this variant the refresh token travels inside the sealed cookie, so a copied cookie is a copied
refresh token. Once the gateway has refreshed a session, the *older* cookie still unseals -- the
gateway keeps no state to tell it apart from the current one -- and replaying it makes the gateway
present the already-spent refresh token again. *The gateway cannot detect that*: it keeps no token
family, and a stateless instance could not share one if it did. Detection is your identity
provider's job, so turn it on for the client's realm or tenant:

* *Keycloak:* *Revoke Refresh Token* on and *Refresh Token Max Reuse* `0` (`revokeRefreshToken: true`,
  `refreshTokenMaxReuse: 0` in a realm export). The project's integration and compose-sample realms
  ship with exactly this.
* *Other providers:* refresh-token rotation with reuse detection and no reuse grace window.

With it on, the replay is refused with `invalid_grant`, the gateway ends that session, clears the
cookie and records `ApiSheriff-111` with reason `credential-rejected`. Keycloak additionally revokes
the successor token, so the session the legitimate browser holds ends on its next refresh as well,
while the Keycloak user session survives -- a replay costs the attacker and the user the whole grant.
*Without strict rotation, neither side detects reuse*: the provider refreshes the replayed token and
the copied cookie becomes a working session.

Once the gateway has ended a session this way, it remembers the refresh token that session presented
(as a salted digest, in memory, until the session's absolute lifetime), so further requests with that
same cookie are refused locally -- cookie cleared, no call to your IdP, no further `ApiSheriff-111`.
That memory is per instance and does not survive a restart, so another instance, or the same one after
a restart, asks the IdP once more before it remembers the token too.

*The trade you accept.* Strict rotation cannot tell a replay from a benign duplicate. Each instance
single-flights refreshes per session, but two parallel requests carrying the same cookie that land on
*different* instances inside the refresh window both present the same refresh token, and the second
ends the session -- a forced re-login. Allowing a reuse count or grace window at the IdP avoids that
at the price of the detection itself; see
link:../variants/03-bff-cookie.adoc#_transparent_refresh_and_step_up[the concurrent-refresh race].

*How a failing refresh is answered.* Only the failure kinds above end the session. If the IdP is
unreachable or answers `5xx`, the session is kept: requests keep using the current access token until
it expires, then are answered as unauthenticated *without* the cookie being cleared, and the next
attempt waits five seconds (`ApiSheriff-127`, per instance). `on_failure` picks how a failing request
is answered -- `reauthenticate` redirects navigations to login and answers API calls `401`, `reject`
answers `401` to everything. See link:../configuration.adoc#_refresh_failure_dispositions[the
per-kind table].

== What is unavailable in this variant

A stateless gateway holds no session index and cannot reach another browser's cookie, so
IdP-driven destruction is *unsupported*:

* *Back-channel logout answers `404`.* The reserved path stays wired and deliberately returns `404`
  rather than falling through to the proxy route table -- it never claims a destruction that did not
  happen.
* *No destroy-by-`sid` / destroy-by-`sub`.* Nothing can be revoked centrally with *immediate*
  effect. The one IdP-side lever that reaches a cookie session is revoking its grant at the IdP
  (deleting the user's session there): with `session.refresh` enabled, the cookie keeps working
  until its access token enters the refresh window, and that refresh is then rejected and ends the
  session (`ApiSheriff-111`, `credential-rejected`). With refresh disabled it keeps working until
  `ttl_seconds` expires.

RP-initiated logout (the user logging themselves out) works normally: the browser's cookie is
cleared, and an expired cookie the browser keeps anyway is still refused server-side by the absolute
TTL check. Where instant central revocation is a hard requirement, use the server-session variant.
Mitigate in this variant with a short `ttl_seconds` and short access-token lifetimes.

== Session affinity for the login leg

The variant is stateless once a session is *established*, but not during the login exchange. The
pending authorization held between the login redirect and the OIDC callback is per-instance and
never shared, so a login *begun* on one replica must *complete* on that replica.

*Configure session affinity for the login leg only* -- the redirect through to the callback. Once
the session cookie is issued, requests may be balanced freely across replicas with no affinity.

== Upgrading: forced re-login on a format change

The sealed-cookie format carries a version that is bound into the cookie's authenticated data. The
version is incremented by one on every change to the set of fields the cookie seals, and a cookie
carrying any other version fails to unseal rather than being mis-parsed -- there is deliberately no
backward-compatible acceptance path.

*Plan for it*: on an upgrade that changes the format version, all existing cookie-mode sessions are
invalidated at deploy time and users must log in again, once. There is no rolling migration --
schedule the deploy accordingly.

The current format is `FORMAT_VERSION` *1*: the sealed payload is length-prefixed raw UTF-8, deflated
before encryption, and carries ten fields -- the tokens, the identity and session claims, and the
session's active scope set. The numbering restarted at 1 with the change that added the active scope
set, so *cookies sealed before this change are refused*: they carry a different version byte, fail the
explicit version gate *before* decryption (logged once as `ApiSheriff-113` with disposition
`unknown-version`), and are treated as no session -- navigations are redirected to login and API
calls answer `401`. Existing cookie sessions therefore log in again once after the upgrade.

The gate reads and compares the version byte before any cipher is constructed. The version an
accepted cookie carries is authenticated in turn -- AES-GCM binds it into the associated data -- but
that happens after the gate, not at it. So a retired format is never mis-parsed.

== Operate

* *Absolute TTL.* `ttl_seconds` is counted from login and is never extended by a refresh; the
  deadline is recomputed from the original login on every re-seal, so an endlessly-refreshed session
  still dies on time.
* *Refresh re-seals the cookie.* A transparent token refresh emits a new `Set-Cookie` -- that is the
  whole of "persisting" in this variant.
* *IdP reachability.* Provider metadata is discovered lazily on first use, so the gateway boots
  without the IdP -- but logins fail until the issuer is reachable. The reverse direction matters as
  well in the default setup: the IdP must reach the gateway's JWKS endpoint, or it cannot verify the
  gateway's client assertion and every login fails (see <<signing-keys>>).

== Private-CA / self-signed IdP

If your IdP presents a certificate from a *private CA*, name a trust profile for the gateway's
back-channel to it -- discovery, the pushed authorization request, the authorization-code exchange,
refresh and refresh-token revocation -- with
`egress_tls.oidc_tls_profile`, and bind the profile's anchors in the deployment. The profile
*replaces* the JVM default trust store on that one leg, so include a public root in it if the IdP
still needs one. The per-issuer `jwks.tls_profile` is a separate key for the JWKS fetch; an IdP
behind the same private CA needs both. Alternatively, add the CA to the JVM default truststore and
name no profile. See link:bff-session.adoc#_private_ca_self_signed_idp[the server-session guide]
for both routes; they are identical in both variants.
