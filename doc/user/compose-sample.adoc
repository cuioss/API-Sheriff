= Compose Sample -- a Deployment-Shaped Stack You Can Run
:toc:
:toclevels: 3
:sectnums:

A runnable Docker Compose stack that shows the *shape* of an API Sheriff deployment: the published
image pulled by tag, all configuration supplied through read-only mounts, and the runtime-hardening
directives a real deployment should set, set explicitly rather than left to a default. It is a
teaching artifact, not a deployment you should run as-is -- see
<<_what_must_change_before_this_is_real>>.

*The scope of that hardening claim, stated so it is not read wider than it holds.* The *security*
directives -- non-root, `cap_drop: ALL`, `no-new-privileges`, `read_only` with explicitly sized
`tmpfs`, and read-only configuration mounts -- are set on *all three* services. *Resource limits are
set on the gateway only*, and that asymmetry is deliberate rather than an omission: an unvalidated
memory cap on a third-party image is a crash loop in an operator's face rather than a hardening win,
and the right ceiling for the identity provider follows from the database and realm size a real
deployment runs, which this sample cannot know. Size those for your own stack -- do not copy a
number from here.

It lives at `deployment/compose-sample/` and is a *sample*, not a test harness. It carries three
services and nothing else -- the gateway, an identity provider whose realm mints the tokens the
gateway validates and signs browser users in, and a stand-in upstream that the gateway proxies to.
The gateway serves that upstream twice: as a public API at `/api`, and behind a *server-session
BFF* at `/app`, where a browser logs in through the identity provider and the gateway holds the
tokens. See <<_logging_in_through_the_bff>>. The
link:../development/compose-sample.adoc[contributor guide] explains why it is a separate stack from
the one `integration-tests` brings up, and draws the topology.

IMPORTANT: The sample's BFF needs the gateway release *after* `0.2.4`. The image the sample pins,
`0.2.4`, predates `oidc.back_channel_origin` and the `/bff/*` reserved paths, so it refuses the
sample's `gateway.yaml` at boot. Until that release is cut and the pin moves to it, run the sample
with a locally built image -- <<_route_b_a_locally_built_image>>.

An optional override file adds a fourth service, a TLS-terminating hop in front of the gateway, to
demonstrate the ingress / sidecar deployment shape in which the gateway itself serves plain HTTP.
It carries the same *security* directives as the three above -- non-root, `cap_drop: ALL`,
`no-new-privileges`, `read_only` with explicitly sized `tmpfs` -- and, like the identity provider and
the upstream and unlike the gateway, declares *no resource limits*, for the reason given just above.
See <<_the_plain_http_variant>>.

WARNING: Every credential and every piece of key material in this sample is a placeholder. Read
<<_what_must_change_before_this_is_real>> before this stack is reachable by anything you care about.

== Before you start

You need Docker with Compose v2 (`docker compose version` must succeed), and a gateway image. There
are two routes to the image; pick one.

The image must be the gateway release after `0.2.4` or a local build of the current source. The
sample's `gateway.yaml` carries the BFF's `oidc` block, and `0.2.4` -- the image the sample still
pins -- predates `oidc.back_channel_origin` and the `/bff/*` reserved paths and refuses that document
at boot. Until the next release moves the pin, Route B is the route that works.

=== Route A -- the published image (the default)

The sample defaults to the pinned published image and needs nothing from you but the ability to
reach `ghcr.io` -- once the pin names a release after `0.2.4`; see above:

[source,bash]
----
docker pull ghcr.io/cuioss/api-sheriff:0.2.4
----

The bring-up script pulls it for you if it is missing, so this step is optional. From the first
release the two-platform lane cuts, Route A works on `linux/amd64` and `linux/arm64` hosts alike,
Apple Silicon and AWS Graviton included: the published tag names an index over one image per
platform, and the pull selects the image for your host. Tags up to and including `0.2.4` predate that
lane and are `linux/amd64` only, so on an arm64 host use Route B while the pin names such a tag. For
what the published image contains, how it is tagged, and how to verify its signatures and SBOMs, see
link:container-image.adoc[Container Image -- Pulling, Running and Verifying]; this guide does not
restate any of it.

[[_route_b_a_locally_built_image]]
=== Route B -- a locally built image

You need Route B in exactly four cases: the pin is still `0.2.4` or earlier, which predates the
sample's BFF configuration and refuses it at boot; your host is an arm64 machine and the pin is still
a tag that predates the two-platform lane (`0.2.4` or earlier, which is `linux/amd64` only); your host's
CPU is below the baseline the published image is compiled for -- an x86-64 CPU without AVX2, or an
older AArch64 core such as Graviton 1 or the Raspberry Pi 4, as listed in
link:../../README.adoc#_known_limitations[the README's Known Limitations]; or you want to run the
sample against local changes. A local build compiles for the host it runs on, so it starts where the
published image does not.

To run the sample against your own build, produce the image and point the sample at it:

[source,bash]
----
python3 .plan/execute-script.py plan-marshall:build-maven:maven run \
  --command-args "clean install -Pnative -pl api-sheriff -am -DskipTests"
docker compose -f integration-tests/docker-compose.yml build api-sheriff
export API_SHERIFF_IMAGE=api-sheriff:distroless
----

Both commands run from the repository root. `API_SHERIFF_IMAGE` is the single knob: the compose file
references it with no inline fallback, its default lives once in `deployment/compose-sample/.env`
(which Compose auto-loads), and the bring-up script's image preflight reads the value back out of the
resolved Compose model instead of restating it. Exporting the variable therefore steers the preflight
and the stack that actually starts as one -- they cannot disagree.

If neither route has produced the image, the bring-up fails immediately -- naming the reference it
looked for and both routes -- rather than starting a partial stack.

== Bringing the stack up

=== 1. Generate the sample certificates

The stack serves TLS everywhere, and *no key material is committed*. Generate it once:

[source,bash]
----
./deployment/compose-sample/docker/certificates/generate-certificates.sh
----

This writes five files next to the script, all git-ignored:

* `localhost.crt` and `localhost.key` -- a self-signed certificate and its key, served by the
  gateway and by Keycloak alike;
* `sample-idp-truststore.p12` -- a truststore holding that one certificate and no key;
* `client-auth.pem` -- the BFF's RSA client-authentication key. The gateway signs the
  `private_key_jwt` assertion it authenticates to Keycloak with using it (PS256);
* `dpop.pem` -- the BFF's EC P-256 DPoP key. The gateway signs the DPoP proofs that bind every
  access token it holds to itself using it (ES256).

The two signing keys need no change in the realm when you regenerate them: Keycloak holds no copy of
the client key and fetches its public half from the gateway, and a DPoP proof carries its own public
key.

The certificate's SAN list names every host a TLS client in the stack dials: `localhost` for the
browser; `keycloak`, because the gateway reaches the identity provider by its compose service name
and a certificate without that name would fail hostname verification on the token-key fetch and the
BFF back channel; and `api-sheriff` and `tls-terminator`, because Keycloak in turn fetches the BFF's
public client key from the gateway -- directly in the base sample, through the terminating hop in
<<_the_plain_http_variant>>.

The truststore is how the gateway comes to trust Keycloak at all. The issuer in
`docker/sheriff-config/gateway.yaml` names the trust profile `jwks.tls_profile: sample-idp`, and the
committed `docker/certificates/sample-idp-trust.properties` binds that name to the generated store;
the compose file loads it through `QUARKUS_CONFIG_LOCATIONS`. The BFF's back channel to Keycloak --
discovery, the pushed authorization request, the code exchange -- names the same profile through
`egress_tls.oidc_tls_profile`. Without that binding the token-key
fetch would fail certificate validation against the self-signed identity provider, and the gateway
would never report ready. Nothing is relaxed to make it work: chain and hostname are both verified,
against exactly the one certificate Keycloak serves.

Trust runs the other way too. Keycloak verifies the gateway's certificate when it fetches the client
key, against the same certificate, which the compose file anchors through `KC_TRUSTSTORE_PATHS`.
Hostname verification stays on there as well.

If you generated the material before the truststore or the signing keys existed, run the script
again -- the bring-up refuses to start with an incomplete set and says so. Run with no argument, the
script always replaces the whole set; `--if-missing` replaces it only when a file of the set is
missing, and is what the Maven profile below calls.

=== 2. Start it

[source,bash]
----
./deployment/compose-sample/scripts/start-sample.sh
----

The script preflights the image, brings the three services up, and then gates on the stack being
genuinely usable rather than merely started. The gate has two layers: it waits on each service's own
health signal -- for the gateway, the `HEALTHCHECK` baked into its image -- and then polls the
readiness endpoint with a bounded budget, composed beneath the management context path the compose
file publishes as the `de.cuioss.sheriff.management-root-path` label. It polls rather than asking
once because readiness includes the identity provider's token keys: Keycloak's own health signal
only proves its port accepts, so the gateway can start while the realm is still importing and has to
retry its first key fetch. The budget covers that retry; a gateway still not ready when it runs out
fails the gate. The script
restates that path nowhere; it derives it, because the path is build-time fixed in the image and a
gateway built with a different one serves its probes elsewhere
(link:context-path.adoc[The Context Path]). The second layer is not redundant with the
first; <<_reading_the_container_health_signal>> explains what each one proves. Either layer failing
exits non-zero, printing the container log and the full health payload.

Alternatively, run it through the build as an opt-in Maven profile. It generates the certificate
material and signing keys first when any file of the set is missing (a complete set is left
untouched), brings the stack up, gates on readiness, logs in through the BFF with the login check
described in <<_logging_in_through_the_bff>>, and tears the stack down again:

[source,bash]
----
python3 .plan/execute-script.py plan-marshall:build-maven:maven run \
  --command-args "verify -Pcompose-sample -pl deployment -am"
----

`-Dcompose-sample.image=IMAGE` runs the profile against another gateway image: it exports
`API_SHERIFF_IMAGE=IMAGE` into the bring-up, exactly as Route B does by hand. CI uses it to run the
sample against the image it has just built -- see <<_after_a_keycloak_update>>.

Without `-Pcompose-sample` the `deployment` module is a no-op: the default build starts no container
and costs no measurable time.

=== 3. Drive a request through the gateway

[source,bash]
----
curl -k https://localhost:8443/api
----

[source,json]
----
{"service":"demo-api","message":"Reached the upstream through API Sheriff."}
----

That response came from the `demo-api` container, which publishes no host port at all -- the gateway
is the only way to reach it. `-k` is required because the certificate is self-signed; that is the
point of a sample, not a defect.

Two other endpoints are published:

[cols="1,3"]
|===
| Address | What it is

| `https://localhost:9000`, beneath the published management context path
| The gateway's management interface -- HTTPS, because the sample supplies management certificates.
  Its readiness endpoint is what the readiness gate probes; the path it sits beneath comes from the
  compose file's `de.cuioss.sheriff.management-root-path` label rather than from anything this page
  restates. <<_reading_the_container_health_signal>> composes the probe from it.

| `https://localhost:1443`
| Keycloak: the login page the BFF sends a browser to, and the admin console for inspecting the
  realm. No token is minted here by hand any more: `sample-client` has no secret and no password
  grant, so a user signs in through the BFF instead. It is also the identity provider's one
  identity: Keycloak's `KC_HOSTNAME` is this published URL, so the sample realm's issuer is
  `https://localhost:1443/realms/sample` whichever address a request arrives on, and that is the
  issuer the gateway validates tokens against. The gateway does not dial it: its key-set fetch and
  its BFF back channel (`oidc.back_channel_origin`) stay on `keycloak:8443` on the internal network.
|===

[[_logging_in_through_the_bff]]
=== 4. Log in through the BFF

Open `https://localhost:8443/app` in a browser. The browser warns about the self-signed certificate
twice -- once for the gateway on `8443`, once for Keycloak's login page on `1443` -- because both
serve the generated certificate. Sign in as `sample-user`, with the password from
`docker/keycloak/sample-realm.json` (`CHANGE-ME-BEFORE-PRODUCTION`). The browser lands back on
`/app`, which answers with the same `demo-api` document `/api` serves. The difference is how it got
there: the gateway holds the user's tokens and forwards the access token upstream, and the browser
holds only the gateway's `+__Host-sample-session+` cookie.

`/app` is a `type: bff` anchor with a `require: session` floor (see
link:anchors.adoc[Anchors -- Namespace-Scoped Policy]), and its one route,
`endpoints/demo-app.yaml`, inherits that floor rather than declaring one (see
link:endpoint-routes.adoc[Endpoint Route Configuration]). A browser navigation without a session is
redirected to the login page; an API request without one gets `401`.

To sign out, open `https://localhost:8443/bff/logout`. The gateway ends its session, sends the
browser to Keycloak to end the realm session too, and lands it on the public page
`/pages/signed-out.html` rather than back on `/app`, which would only start the next login.

The same login, without a browser:

[source,bash]
----
./deployment/compose-sample/scripts/check-bff-login.sh
----

This is a real login flow, not a smoke test. It drives the whole authorization-code round trip with
one cookie jar and asserts every leg: a session-less API request to `/app` must be refused with
`401` (without that control a public route would make the rest of the check vacuous), the browser
navigation must be redirected with a pushed authorization request, Keycloak's login form is read and
the credentials posted, the redirects lead back through the gateway's callback, and `/app` must
finally answer `200` with the `demo-api` document while the jar holds the session cookie. Every
request verifies TLS against the generated certificate, and a failure prints the failing step, the
status and the response headers with cookie values and URL queries removed. `--help` lists the
options -- base URL, path, user, password and cookie name.

For the token exchange, Keycloak authenticates the gateway by fetching the BFF's public client key
from the gateway's `/bff/jwks`. That fetch runs server-to-server, so the realm names the URL through
a placeholder, `${SAMPLE_GATEWAY_JWKS_URL}`, which each variant's compose file sets to the address it
can actually dial: `https://api-sheriff:8443/bff/jwks` in the base sample, and
`https://tls-terminator:8443/bff/jwks` in <<_the_plain_http_variant>>, where the gateway itself
serves no TLS.

=== 5. Stop it

[source,bash]
----
./deployment/compose-sample/scripts/stop-sample.sh
----

This removes the containers, the network and the volumes, so the next bring-up starts from a known
state and re-imports the realm.

[[_after_a_keycloak_update]]
=== After a Keycloak update

The sample's Keycloak image is pinned by tag and digest, and that pin is updated automatically: one
Dependabot group moves it in the same pull request as the integration-test stack's Keycloak, and a
build-time test keeps the two pins identical. The image line in
`deployment/compose-sample/docker-compose.yml` is the record of the version the sample runs.

CI brings the base sample up on every pull request. After the integration suite has torn its own
stack down, the `integration-tests` workflow runs the `compose-sample` profile against the native
image that job has just built from the pull request's source
(`-Dcompose-sample.image=api-sheriff:distroless`), so the sample's Keycloak is started and a real
login through the BFF is checked. A Keycloak bump pull request reaches the sample through that job
and no other; the configuration-validation workflow still validates only the gateway configuration
set. CI does *not* bring up <<_the_plain_http_variant>> -- check that one by hand after a bump that
touches it.

So after pulling a Keycloak bump, tear the sample down with `stop-sample.sh` before the next start.
The script runs `down -v`, and that matters here: the `keycloak-quarkus` named volume holds
`/opt/keycloak/lib/quarkus`, and Docker seeds a named volume from the image only on first use. A
volume left over from the previous image would keep serving that image's Quarkus libraries to the new
one.

[[_the_plain_http_variant]]
== The plain-HTTP variant -- TLS terminated in front of the gateway

Everything above runs the gateway as its own TLS edge. The variant in
`deployment/compose-sample/docker-compose.plain-http.yml` takes that away: the gateway serves plain
HTTP on the internal network only, and a TLS-terminating nginx hop in front of it owns the public
HTTPS listener. That is the shape a deployment behind an ingress controller, a service mesh sidecar
or a load balancer already has, and it is the shape in which re-terminating TLS inside the gateway
would be duplicated work and a second, separately-configured trust decision.

It is an *override file*, layered on the base rather than replacing it:

[source,bash]
----
./deployment/compose-sample/scripts/start-sample.sh --plain-http
----

which composes exactly this:

[source,bash]
----
cd deployment/compose-sample
docker compose -f docker-compose.yml -f docker-compose.plain-http.yml up -d --wait
----

Stopping is unchanged -- `./deployment/compose-sample/scripts/stop-sample.sh` tears the variant down
too, because it runs `down -v --remove-orphans` and the terminator is an orphan with respect to the
base file.

The request you drive through it is the same one, at the same address: the terminator publishes the
port the gateway used to publish, so `curl -k https://localhost:8443/api` still works. What changed
is which component answers the handshake. The BFF login is unchanged too: `/app` logs a browser in
the same way, and `check-bff-login.sh` runs against this variant without an argument.

=== Requires Docker Compose 2.24.4 or newer

The override drops the gateway's published `8443` using the Compose-Spec `!override` merge tag.
Releases older than 2.24.4 do not implement *that* tag, and they *do not reject the file* -- the tag
is ignored and the base's value survives the merge. The gateway would then keep publishing `8443`
alongside the terminator's binding on the same host port, which surfaces as an opaque port conflict
or as a published container port that answers nothing.

NOTE: 2.24.0 is not enough, and the difference is easy to miss. The sibling `!reset` tag arrived in
2.24.0; `!override` -- the one this override actually uses, because `!reset` would also drop the
loopback management publication the readiness gate is derived from -- arrived in 2.24.4. On 2.24.0
through 2.24.3 the file parses, the tag is silently ignored, and the collision above is what you get.

`start-sample.sh --plain-http` checks the version first and refuses with that explanation rather than
letting you debug the collision. Check yours with `docker compose version`.

=== Switching between the variants needs a teardown first

Bring the *other* variant up without stopping the current one and the terminator fails to start, with
a daemon message that names neither the variant nor the cause:

....
user specified IP address is supported only when connecting to networks with user configured subnets
....

A Docker network's IPAM is fixed when the network is created, and Compose does *not* reconfigure a
network that already exists. The base sample declares the network with no subnet at all; the
plain-HTTP override declares `10.89.0.0/24`, because the terminator holds a static address on it and
the gateway's trusted-proxy entry is that address as an exact `/32`. Layering the override onto a
network the base already created therefore reuses the subnet-less one, and the static address cannot
be honoured.

So tear the stack down between variants -- which removes the network along with the containers:

[source,bash]
----
./deployment/compose-sample/scripts/stop-sample.sh
----

`start-sample.sh --plain-http` preflights this too: if the network is already there without the
required subnet, it refuses with that explanation and names the teardown command, rather than letting
the terminator die on the daemon's message.

=== Why values are cleared rather than omitted

Compose *merges* an override into the base; it does not replace it. Omitting a key leaves the base's
value standing, which is the opposite of what "this deployment does not do that" needs. So the
override clears the gateway's certificate variables to the empty value:

[source,yaml]
----
- QUARKUS_HTTP_INSECURE_REQUESTS=enabled
- QUARKUS_HTTP_SSL_CERTIFICATE_FILES=
- QUARKUS_HTTP_SSL_CERTIFICATE_KEY_FILES=
----

A key that is present but blank declares nothing, which is exactly what is wanted here -- and it is
required rather than cosmetic. Leaving those two out would inherit the base's certificate paths, and
a declared server certificate alongside the plain-HTTP opt-in is one of the combinations the gateway
refuses to boot on. The management interface's certificates are deliberately *not* cleared: that is
a separate listener, so port 9000 stays HTTPS and the readiness gate is unaffected.

=== The trusted proxy is the terminator, and nothing else

`SHERIFF_TRUSTED_PROXIES` in the variant names one address as an exact `/32` host route -- the
terminator's, and no other:

[source,yaml]
----
- SHERIFF_TRUSTED_PROXIES=10.89.0.10/32
----

That is why the override declares an explicit subnet for the sample's network and pins the
terminator to a static address on it: without one, Docker assigns from a pool and the entry could
not be written as an exact host route at all. It would have to widen to a range -- and every other
container on that network, `keycloak` and `demo-api` included, holds an address in the same range,
so a range here would let any of them state its own client address in `X-Forwarded-For`. Change the
subnet if it collides with your own routing, and change the terminator's address and the `/32` with
it; the three values are one decision.

For what this mode does to the rest of the edge -- how it interacts with passthrough SNI, inbound
mTLS, the management interface and the forwarded-header handling -- see
link:tls-edge.adoc#_interactions_with_the_rest_of_the_edge[the interaction verdicts in TLS Edge].
They are stated once there rather than restated here.

[[_reading_the_container_health_signal]]
== Reading the container health signal

The gateway image carries its own `HEALTHCHECK`, so the container runtime tracks a health state for
`api-sheriff` with no host-side tooling involved. That state is what the bring-up script's first gate
layer blocks on, and it stays visible afterwards through ordinary Docker commands.

=== What `docker compose ps` reports

[source,bash]
----
docker compose -f deployment/compose-sample/docker-compose.yml ps
----

....
NAME          STATUS
api-sheriff   Up 45 seconds (healthy)
demo-api      Up 45 seconds
keycloak      Up 46 seconds (healthy)
....

Three things in that column are worth reading deliberately:

* *`(healthy)` on `api-sheriff`* is the image's baked probe reporting success. It is not something
  this compose file computes.
* *`(health: starting)`* is what the same container reports for the first 20 seconds. That is the
  probe's start period, during which a failing check does not count against the retry budget and the
  container is not yet marked unhealthy. Seeing it briefly after bring-up is normal.
* *No suffix at all on `demo-api`* means that service declares no health check. It is not a failure
  and not a degraded state -- there is simply nothing being measured.

An `(unhealthy)` gateway means the probe failed three consecutive times after the start period
elapsed. Read the probe's own output before anything else -- see <<_inspecting_the_probe_output>>.

=== What `healthy` proves, and what it does not

The baked probe opens a TCP connection to the management port inside the container, closes it again,
and reports success when the port accepted. Nothing is written to or read from that socket.

*It proves* the process is up and its management interface is bound and accepting -- a *liveness*
fact.

*It does not prove* readiness. A healthy container has not told you that the gateway's configuration
document was accepted, that its token validator resolved, that TLS terminates correctly on 8443, or
that a request will reach the upstream. All of those can be false while the container reports
healthy.

The probe is deliberately protocol-blind, and that is why it cannot make the larger claim: the
management interface speaks HTTPS in this sample but plain HTTP in a deployment that opts out, so a
probe that spoke either one would be wrong against the other. It measures the one thing that is true
under both.

Readiness has its own answer, and it is one request away -- addressed beneath the *management context
path*, which is fixed when the image is built and published to the host side by the compose file's
`de.cuioss.sheriff.management-root-path` label. Read it from there rather than assuming it, exactly as
the readiness gate does:

[source,bash]
----
# Read the label off the RUNNING gateway container. Docker's own --format is used rather than a
# JSON parser so this step needs nothing beyond the Compose v2 the guide already asks for.
MGMT_ROOT=$(docker inspect \
  --format '{{ index .Config.Labels "de.cuioss.sheriff.management-root-path" }}' \
  "$(docker compose -f deployment/compose-sample/docker-compose.yml ps -q api-sheriff)")

# Drop any trailing separator before composing. The suffix below already begins with `/`, so a label
# of `/` would compose `//health/ready` and a label of `/ops/` would compose `/ops//health/ready` --
# neither is served. The shipped label is `/q`, where this line is a no-op; it matters exactly when
# you follow the instruction above and READ the label rather than assuming it.
MGMT_ROOT="${MGMT_ROOT%"${MGMT_ROOT##*[!/]}"}"

curl -k "https://localhost:9000${MGMT_ROOT}/health/ready"
----

That normalisation is the same rule the rest of the project applies to this label, and the project
keeps exactly one implementation of it per language boundary: `RootPaths.normalize` on the Java side,
`normalize_root_path` in `integration-tests/scripts/lib-docker-compose.sh` on the shell side -- which
both `start-integration-container.sh` and `demo-client/scripts/start-dev-environment.sh` source
rather than re-implement -- and the k6 resolver. All of them collapse the whole trailing run before
composing. The line above is the sample's own inline copy, kept deliberately: this stack is shipped
to be read and adapted standalone, so it sources nothing from `integration-tests/`.

The endpoint names beneath that path (`/health`, `/health/ready`, `/health/live`, `/metrics`) are
Quarkus' own fixed suffixes, so those alone stay spelled out. What the path itself can be, and why
moving it costs a rebuild rather than an environment variable, is in
link:context-path.adoc[The Context Path].

That endpoint answers `503` while the gateway is not ready, which is what makes it a readiness signal
rather than a second liveness one. Use it -- not the health column -- before concluding the stack is
usable. A monitoring system that treats the container health state as readiness has drawn a
conclusion the signal does not support.

[[_inspecting_the_probe_output]]
=== Inspecting the probe output

The full health record, including what the last few probe runs printed, is on the container:

[source,bash]
----
docker inspect --format '{{json .State.Health}}' $(docker compose -f deployment/compose-sample/docker-compose.yml ps -q api-sheriff)
----

The `ps -q` indirection is worth keeping: Compose prefixes container names with the project, so the
container is not simply called `api-sheriff` on the Docker side.

The JSON carries three things you will actually use:

`Status`:: `starting`, `healthy` or `unhealthy` -- the same state the `ps` column renders.

`FailingStreak`:: How many consecutive checks have failed. A success resets it to `0`, so a non-zero
value means the most recent checks are failing -- not that the container recovered. It can be
non-zero while `Status` still reads `healthy`, and that combination is the useful early warning:
Docker holds the healthy state until the streak reaches `--retries` (3, per the baked probe), so a
`1` or a `2` is a container that is failing its probe right now but has not yet been declared
unhealthy.

`Log`:: The last few probe runs, each with `Start`, `End`, `ExitCode` and `Output`.

`ExitCode: 1` is the probe reporting that the management port did not accept, and `Output` then
carries the one line the probe writes for exactly this purpose:

....
health-probe: 127.0.0.1:9000 not accepting: java.net.ConnectException: Connection refused
....

That line names the port it tried and the reason it failed, which distinguishes the two cases that
look identical from outside: the application has not finished starting (connection refused, and the
next check will likely succeed), versus the application is running but its management interface is
bound somewhere else (which is a configuration problem -- see
link:container-image.adoc[Container Image -- Pulling, Running and Verifying] for the port override
constraint). An empty `Output` with a non-zero `ExitCode` means the probe process itself was killed
by the runtime's own `--timeout`, which is a different failure again.

[[_what_must_change_before_this_is_real]]
== What must change before this is real

The sample is deliberately loud about being a sample. Every item below is a placeholder that is
*wrong* for any deployment reachable by something you care about.

[cols="1,2"]
|===
| Sample-only value | What a real deployment does instead

| *The generated certificate and key* -- self-signed, with no CA behind it, and written
  world-readable so the gateway's and Keycloak's differing non-root uids can both read it.
| Supplies certificate and key from its own PKI, with ownership matched to the runtime uid, mounted
  at the same two paths. The gateway does not care where they came from.

| *The `sample-idp` trust binding* -- `sample-idp-trust.properties` points the profile at the
  generated truststore, which anchors the sample's own self-signed certificate, under a sample
  password.
| Binds the profile (under this name or its own) to a truststore holding its identity provider's CA,
  supplied by the deployment with a password that is not in a repository. `gateway.yaml` keeps
  naming only the logical profile.

| *The BFF signing keys* -- `client-auth.pem` and `dpop.pem`, generated next to the certificate,
  unencrypted and world-readable, in the `certificates/` directory the gateway mounts. Keycloak and
  the plain-HTTP variant's terminator mount only `localhost.crt` and `localhost.key` out of it, file
  by file, so the signing keys reach the gateway alone.
| Supplies its own client-authentication and DPoP keys, with ownership matched to the gateway's
  runtime uid, and keeps them in the *gateway only*, as the sample does. The identity provider needs
  no key file: it fetches the public client key from the gateway's JWKS endpoint.

| *The Keycloak realm client* -- `sample-client` in `docker/keycloak/sample-realm.json`, registered
  for `https://localhost:8443` and for a JWKS URL on the sample's internal network.
| Registers its own confidential client against its own gateway address -- see <<_adapting_it>>.

| *The Keycloak bootstrap admin credentials* -- `admin` / `admin` in `docker-compose.yml`.
| Sets real credentials, and does not publish the admin console at all unless it means to.

| *The sample realm user* -- `sample-user` with a placeholder password.
| Deletes it. It exists only so you can log in through the BFF while trying the stack out.

| *`start-dev`* -- Keycloak runs in development mode.
| Runs Keycloak in production mode against a real database. The sample's realm lives in a volume and
  is discarded on teardown.
|===

The gateway's own configuration under `docker/sheriff-config/` needs less adaptation than the rest
of the stack: it declares the `strict` inbound filter profile explicitly, a TLS floor of 1.2, and
three namespaces -- the public proxy namespace `/api`, the BFF namespace `/app` with its
`require: session` floor, and the public `/pages` namespace serving the signed-out page. It declares
one token issuer, whose egress allowance is pinned by an explicit, host-exact `allowed_egress_hosts`
list rather than left to the allowance derived from its JWKS URL (see the comment on that key), and
one `oidc` block: a server-session client with no secret, authenticating with `private_key_jwt`,
pushing every authorization request and binding its tokens with DPoP, keeping the browser-facing
issuer identity while dialling Keycloak at `oidc.back_channel_origin`. The public `/api` endpoint is
`auth: require: none`, which is the first thing to change when adapting the sample -- switch it to
`require: bearer` and the route is gated on a token from the declared issuer.

[[_the_sample_realm_enables_strict_refresh_token_rotation]]
== The sample realm enables strict refresh-token rotation

One realm setting is *not* a placeholder, and it is worth keeping when you adapt the sample: the
`sample` realm sets `"revokeRefreshToken": true` and `"refreshTokenMaxReuse": 0` in
`docker/keycloak/sample-realm.json`. That is strict refresh-token rotation -- every refresh returns a
new refresh token, and the one it replaced is spent the moment it is redeemed.

*It is the refresh-token replay defence, and it lives at the identity provider.* The gateway cannot
recognise a replayed refresh token: a confidential client only ever sees the tokens it presents
itself, and a stateless cookie-mode instance keeps no token family to compare against. An identity
provider enforcing strict rotation refuses the replay with `invalid_grant`, and the gateway disposes
that refusal as a credential rejection -- it ends the session and records `ApiSheriff-111` with reason
`credential-rejected` (see link:../configuration.adoc#_oidc[`session.refresh.on_failure`]). Against
Keycloak the defence reaches further than the replayed copy: the integration suite
`BffRefreshReuseIT` observed that a detected replay also revokes the successor refresh token, so the
legitimate holder's session ends too, while the Keycloak user session survives.

The sample gateway's BFF mediates server-mode sessions with refresh enabled
(`oidc.session.refresh`), so the setting acts on the sample itself: every refresh the gateway performs
for an `/app` session rotates the refresh token, and a replayed one ends the session. The sample's
client is the kind such a session needs -- it accepts pushed authorization requests, binds its
access tokens with DPoP and fetches the gateway's key set (see
link:bff-session.adoc#key-material[Server-Session BFF -- Key material]) -- and the rotation setting
is shipped on so the realm you copy already carries the defence.

*The cost you take on.* With no reuse permitted, a *duplicate* refresh of the same refresh token is
indistinguishable from theft, and it ends the session. The gateway single-flights refreshes per
session within one instance, so two requests on one instance never present the same token twice. It
cannot coordinate across instances: two gateway instances refreshing the same session, or -- in
cookie mode -- two parallel requests carrying the same cookie that land on different instances, can
both present the same token, and the second one logs the user out. That is the concurrent-refresh
trade link:../variants/03-bff-cookie.adoc#_transparent_refresh_and_step_up[the cookie variant]
describes; with rotation strict, its residual effect is a rare forced re-login.

*What your own identity provider needs.* Configure strict refresh-token rotation on the client's
realm or tenant -- on Keycloak, *Revoke Refresh Token* on with *Refresh Token Max Reuse* `0`; on other
providers, refresh-token rotation with reuse detection and no reuse grace window. *Without it neither
side detects reuse*: the gateway never could, and the provider accepts the replayed token and simply
refreshes it. Allowing a reuse count or grace window instead buys back availability under the
duplicate-refresh race at the price of exactly the detection signal rotation exists to provide.

== Where configuration comes from

The shipped artifact declares nothing about where its configuration or key material lives; the
deployment supplies both. In this sample that happens entirely through the `environment:` block of
the `api-sheriff` service, which is the same door the release smoke test drives.

For which knobs the deployment owns versus which `gateway.yaml` owns -- the three-way policy /
deployment-bound / build-time classification and the precedence rule -- see
link:environment-variable-overrides.adoc[Environment-Variable Overrides]. This guide does not
restate that classification.

One value comes from outside that block: `API_SHERIFF_IMAGE`, which selects the gateway image itself
rather than configuring the gateway. Its default is written once in `deployment/compose-sample/.env`,
the file Compose auto-loads from the sample directory. That file is the only place the published
image reference appears -- `docker-compose.yml` references the variable with no inline fallback, and
`scripts/start-sample.sh` derives the effective value from the resolved Compose model. An exported
`API_SHERIFF_IMAGE` wins over the file, which is how Route B above works, and how the Maven
profile's `-Dcompose-sample.image` works.

The BFF's two key files arrive through that `environment:` block like every other deployment fact:
`gateway.yaml` names them only as the bare placeholders `${SHERIFF_CLIENT_AUTH_KEY_FILE}` and
`${SHERIFF_DPOP_KEY_FILE}`, and the compose file points them at the generated files on the
already-mounted `certificates/` directory. An unset variable fails the boot rather than starting a
BFF without a key.

One deliberate absence is worth naming, because it differs from the integration stack:
`QUARKUS_HTTP_SSL_PORT` is *not* set here. The integration stack moves its terminated listener off
8443 because its configuration claims that port for an SNI front listener. This sample declares no
passthrough SNI, so the gateway terminates directly on 8443 and an override would only mis-address
it.

[[_adapting_it]]
== Adapting it

The sample is meant to be copied. The `deployment/compose-sample/` directory is self-contained --
nothing in it reaches into `integration-tests/` or into the `api-sheriff` module -- so copying the
directory gives you a working starting point. From there the usual first four changes are:

. Point the `UPSTREAM` alias in `docker/sheriff-config/topology.properties` at your real backend, or
  override `TOPOLOGY_UPSTREAM` in the environment. It is the one place a backend address is written
  down.
. Switch `docker/sheriff-config/endpoints/demo-api.yaml` to `auth: require: bearer`. You will
  usually need no `forward` block at all: with none declared, every client header and query
  parameter crosses except the gateway-owned never-forward set (`Cookie` absolutely, an inbound
  `Authorization` on any route declaring no positive-list naming it, and the hop-by-hop and
  framing names), and the HTTP mechanics -- `Accept`, `Accept-Encoding`, `Accept-Language`,
  `Content-Type` and `Range` -- cross without being listed, joined by the five conditional
  validators when the route's `not_modified` toggle is enabled. Add a `forward` block only to
  *narrow* that: `headers_deny` / `query_deny` to withhold specific names, or
  `headers_allow` / `query_allow` for a strict positive-list. See
  link:../configuration.adoc#_forward[the `forward` reference].
+
[IMPORTANT]
====
*This is a behaviour change if you are upgrading.* `forward` used to be allow-list-only, so a
route that declared no block forwarded nothing. Declaring neither list now means *everything
crosses*, and an existing route that omitted the block -- or omitted one of its two dimensions --
starts forwarding client input it previously withheld.

The bound is worth stating precisely: this changes what crosses *within* routes you had already
exposed, never *which* routes are reachable (route matching is unchanged and still
deny-by-default), and it leaks no credentials -- `Cookie` crosses under no mode at all, and an
inbound `Authorization` only where a route declares a positive-list naming it. *Mitigation is one
line:* declare a positive-list on any route whose previous no-block posture you relied on.

This sample is unaffected: `demo-api.yaml` declares `headers_allow: []` / `query_allow: []`, and a
*declared-empty* list is a positive-list naming nothing -- not the absent state. Its behaviour is
exactly what it always was.
====
. Replace the identity provider with your own, updating the issuer URL, the JWKS URL and the
  `allowed_egress_hosts` entry in `docker/sheriff-config/gateway.yaml` together -- the issuer value
  must match the `iss` your tokens actually carry, or every request fails with a 401 that looks like
  a signature problem and is not. The `allowed_egress_hosts` list is authoritative: the exemption
  does not follow the JWKS URL to a new host, so a provider on a private address whose host the list
  still does not name is refused and its key set never loads. Update the entry, or delete the list to
  take the allowance derived from the JWKS URL's host. Rebind the `jwks.tls_profile` it names to your provider's CA at the
  same time: the gateway refuses to boot on a profile it cannot load, and it will not report ready
  until it has fetched the provider's keys over a verified connection. The `oidc` block moves with
  it: `oidc.issuer` takes the same identity, and `oidc.back_channel_origin` the address the gateway
  dials -- or drop that key when the gateway reaches the provider at its public identity.
. Register your own BFF client at the identity provider, and point the `oidc` block at it. The
  realm's `sample-client` shows every setting the gateway asks for: client authentication by signed
  JWT (`client-jwt` on Keycloak) with the provider fetching the key from your gateway's JWKS URL as
  the provider can reach it, pushed authorization requests required, DPoP-bound access tokens, and
  your gateway's callback and post-logout return URLs registered exactly. On Keycloak, keep the
  `basic` client scope among the client's default scopes: it carries the `sub` claim, and the gateway
  refuses a login whose token has none. Then set `oidc.client_id`, `oidc.redirect_uri` and the logout
  URLs to match. link:bff-session.adoc[Server-Session BFF -- Operator Setup] is the full guide;
  link:bff-cookie.adoc[Cookie-Based BFF -- Operator Setup] covers switching the session to cookie
  mode.
