= Server-Session BFF -- Operator Setup
:toc: left
:toclevels: 3
:toc-title: Table of Contents
:sectnums:
:source-highlighter: highlight.js

A task-oriented guide for operators standing up the *server-session BFF* (Variant 2): API Sheriff
as an OIDC confidential client that holds tokens server-side and hands the browser only an opaque
session cookie. It tells you *how* to configure and run the variant; the field-by-field contract
lives in the link:../configuration/authentication-and-oidc.adoc#_oidc[Configuration Reference (`oidc`)] and the design
rationale in link:../variants/02-bff-session.adoc[Variant 2 -- BFF, Session-based].

== When to choose this variant

Choose the server-session BFF when server-side-only token custody is a hard requirement: the token
never leaves the gateway, not even encrypted. It is *stateful* -- it keeps an in-memory session
store -- so it fits a single node, or several replicas behind sticky sessions (see
<<multi-replica>>). A multi-node non-sticky deployment, or one that must avoid server-side session
state, is the link:../variants/03-bff-cookie.adoc[cookie-based variant]'s job instead.

== Before you start

The client setup this variant shares with the cookie-based one -- the prerequisites, the two signing
keys, registering the client at the identity provider, the login exchange, client-secret
authentication, strict refresh-token rotation and a private-CA identity provider -- is walked through
in link:bff-oidc-common.adoc[BFF Confidential Client: Shared Setup]. Check its prerequisites first.
Its key, registration and login checkpoints need a gateway running with the `oidc` block and session
route configured below, so return to it once those are in place. This guide covers what the
server-side session store adds.

== Configure the confidential client

Add an `oidc` block to `gateway.yaml` and set at least one route's effective auth to
`require: session`. A minimal server-session configuration:

[source,yaml]
----
# gateway.yaml
oidc:
  issuer: https://idp.example.com/realms/main
  client_id: api-sheriff
  client_authentication:
    key_file: /etc/sheriff/keys/client-auth.pem   # optional: omit to generate a key on startup
  sender_constraint:
    key_file: /etc/sheriff/keys/dpop.pem          # optional: omit to generate a key on startup
  redirect_uri: https://gw.example.com/bff/callback   # registered exactly at the IdP
  scopes: [openid, profile]                   # requested on every login; see "Scopes" below
  login:
    path: /bff/login                          # optional: gateway-owned login-start URL
    default_return_url: /app/                 # optional: landing page when a login has no target (default /)
  user_info:
    path: /bff/session                        # optional: curated identity view for the SPA
    allowed_claims: [sub, name, email]        # disclosure ceiling; empty discloses nothing
    default_view: [sub, name]                 # subset of allowed_claims
  session:
    mode: server                              # server-side token store (this variant)
    store: memory                             # REQUIRED for server mode; only initial option
    max_sessions: 10000                       # DoS guard on the in-memory store
    max_sessions_per_subject: 10              # optional: live sessions one user may hold
    cookie_name: __Host-sheriff
    ttl_seconds: 3600                         # absolute lifetime from login
    idle_timeout_seconds: 1800                # optional: ends a session nobody uses
    csrf:
      trusted_origins: [https://app.example.com]   # SPA origins allowed on unsafe methods
    refresh: { enabled: true, leeway_seconds: 30, on_failure: reauthenticate }
----

*A working configuration to start from.* The compose sample runs this variant end to end:
`deployment/compose-sample/docker/sheriff-config/gateway.yaml` is a complete server-session
configuration -- signing keys from files, `back_channel_origin`, a `__Host-` session cookie,
refresh and logout -- and its Keycloak realm carries exactly the client settings
link:bff-oidc-common.adoc#_register_the_client_at_the_identity_provider[Shared Setup -- Register the
client at the identity provider] lists. A browser can log in through it, and a
script proves the login; see
link:compose-sample.adoc#_logging_in_through_the_bff[Compose Sample -- Log in through the BFF]. The
`0.2.4` image the sample pins predates `back_channel_origin` and the `/bff/*` reserved paths and
refuses this `gateway.yaml` at boot, so run it on a gateway release after `0.2.4` or on a locally
built image (link:compose-sample.adoc#_route_b_a_locally_built_image[Route B]).

The gateway drives no login unless a route's effective auth is `require: session` or a
`require: bearer` route declares `session_fallback: true` (see <<session-fallback>>). One part of the
block does reach bearer routes, though: `oidc.scopes` joins the scope set every bearer route checks
(see <<bearer-oidc-scopes>>), so adding an `oidc` block to a gateway that also
serves bearer routes tightens those routes.

*The `/bff/*` paths are reserved paths, not an anchor.* Every path the block names -- the callback,
`/bff/login`, the curated identity view at `/bff/session`, and the logout, back-channel, step-up and
client JWKS paths when you declare them -- is an exact-match carve-out answered by the gateway *ahead
of the route table*. The carve-out applies on the OIDC host (the host of `redirect_uri`), with two
exceptions: the back-channel logout and client JWKS paths are reserved on *every* host, because the
identity provider dials them server-to-server at whatever address the client registered, often an
internal one. So on another host those two paths still never reach your routes. Each claims its one path and
nothing beneath it: `/bff/other` is not reserved and is routed like any other request. Nothing
validates the `/bff/` spelling either; it is a naming convention, and any canonical path works. Keep
your application's own routes under an anchor of their own -- `/app` in the examples below -- so the
two namespaces stay visibly apart.

*An identity provider the gateway reaches at a different address.* Keep `oidc.issuer` the
browser-facing identity and set `oidc.back_channel_origin` to the internal origin the gateway dials;
see link:bff-oidc-common.adoc#idp-different-address[Shared Setup -- An identity provider the gateway
reaches at a different address].

*Next: keys and registration.* Give the gateway its two signing keys and register it at the identity
provider as link:bff-oidc-common.adoc#key-material[Shared Setup -- Key material] describes, or
choose link:bff-oidc-common.adoc#client-secret[client-secret authentication] instead.

== Protect a route with a session

Mark the endpoint (or an anchor) `require: session`; the mediated `Authorization: Bearer` is then
injected automatically from the stored token, and any inbound `Authorization` from the browser is
stripped:

[source,yaml]
----
# endpoints/app1.yaml
endpoint:
  id: app1
  base_url: APP1
  auth: { require: session }
  scopes: [orders.read]                       # needed on every route of this endpoint, in addition to oidc.scopes
  routes:
    - id: orders-api
      match: { path_prefix: /api/orders }
      upstream: { path: /orders }
----

`scopes` names what a login for this endpoint *asks* the IdP for, and what every session request to
its routes is held to: a session whose token lacks one of these scopes is not relayed. The gateway
obtains the scope when the IdP grants it and answers `403` when it does not. See <<scopes>> and
<<scope-enforcement>>.

[[token-relay]]
== Enforce login without handing the origin a token

By default a session route relays the session's access token to the upstream as
`Authorization: Bearer`. Some origins need to know only that the user is logged in -- a static
single-page app, an asset server -- and have no use for the token. Set `token_relay: false` in the
route's `auth` block (or the endpoint's, or an anchor's) to keep the token at the gateway:

[source,yaml]
----
# endpoints/spa.yaml
endpoint:
  id: spa
  base_url: SPA
  auth: { require: session, token_relay: false }
  routes:
    - id: spa-shell
      match: { path_prefix: /app }
----

The session is still resolved, refreshed, scope-checked and required exactly as before: a navigation
without a session is redirected to login, an XHR gets `401`, an ended session still clears the
cookie, and a session lacking a scope the route needs is refreshed, widened or refused `403` (see
<<scope-enforcement>>). The only difference is that the gateway mediates no `Authorization` header:
the session's token never reaches the upstream. The only `Authorization` that could still cross is a static value the route
itself configures in `forward.set_headers` -- operator configuration, which `token_relay` does not
filter. `token_relay` acts on
`require: session` routes and on the session branch of a <<session-fallback,`session_fallback`>>
route. It has no effect on a plain `require: bearer` route, where the client's own `Authorization`
crosses only when `forward.headers_allow` names it, nor on the bearer branch of a `session_fallback`
route, which always forwards the validated client token.

Because the point of `token_relay: false` is that no access token reaches the origin, the gateway
refuses at boot a route that sets it while its effective `forward.headers_allow` names
`Authorization` (in any letter case) -- that would let the browser's own `Authorization` header back
in. Remove `Authorization` from `headers_allow`, or drop `token_relay: false`.

[[session-fallback]]
== Serving API clients and browsers on one route

A backend path that serves both API clients presenting their own bearer token and browsers logged in
through the gateway would otherwise need two routes on one prefix, told apart by an
`Authorization` header matcher. `session_fallback: true` on a `require: bearer` route folds the pair
into one route with two authentication branches:

[source,yaml]
----
# endpoints/orders.yaml
endpoint:
  id: orders
  base_url: ORDERS
  auth:
    require: bearer
    session_fallback: true          # a request without Authorization takes the session branch
  scopes: [orders.read]
  routes:
    - id: orders-api
      match: { path_prefix: /api/orders }
----

*The branch is picked from one thing only: whether the request carries an `Authorization` header.*

[cols="2,3"]
|===
| Request | What happens

| Valid bearer token, with or without a session cookie
| Admitted when the token carries every scope the route needs; the upstream receives exactly that
  token as `Authorization: Bearer`. No session is looked up, the fixed CSRF defence does not run, the
  gateway does not set a session cookie, and the session cookie is not forwarded (see <<gateway-cookies>>). The route's cookie
  same-origin check is not a session check and still applies: an unsafe request carrying a cookie the
  route's `cookies` policy forwards is checked before authentication (see
  link:../configuration/routing-and-forwarding.adoc#_cookies_same_origin_check[Configuration Reference -- The same-origin
  check]). `headers_allow` does not need to name `Authorization`.
| Bearer token lacking a needed scope
| `403` with `WWW-Authenticate: Bearer error="insufficient_scope", scope="<missing>"`.
| Invalid token, a `Basic` credential or an empty `Authorization`, with or without a session cookie
| The unrouted `404`, with no `WWW-Authenticate` challenge, metered as `TOKEN_MISSING` or
  `TOKEN_INVALID` (see link:edge-security.adoc#_uniform_not_found_operator_note[Why an existing
  route answers 404]); `401` with `WWW-Authenticate: Bearer` when
  `security_defaults.uniform_not_found` is `false`. Never a login redirect, and a valid session
  cookie does not rescue it -- the bearer branch was chosen the moment the header was sent.
| No `Authorization`, live session
| Served exactly as on a `require: session` route. The session's scopes are compared with the set
  the route needs. A session that carries them is relayed: its token goes upstream (unless
  `token_relay: false`) and is refreshed near expiry, and the session cookie is dropped from what
  the upstream receives (see <<gateway-cookies>>). A session
  lacking one is not relayed: a scope inside its granted set is obtained by a refresh, any other is
  obtained by widening the session on a navigation, and an XHR or API call gets `403`
  `application/problem+json` naming the `missing_scopes` and, when `oidc.step_up.path` is
  configured, a `step_up_url` (see <<scope-enforcement>>). Both branches enforce the same set; the
  `insufficient_scope` challenge of the second row is the answer to bearer clients only.
| No `Authorization`, no session, navigation
| `302` into the login. The login requests the route's scope set, `oidc.scopes` plus the endpoint's
  `scopes`.
| No `Authorization`, no session, XHR or API call
| `401` `application/problem+json`.
|===

*CSRF.* The fixed CSRF defence runs on the session branch only: an unsafe method without
`Authorization` needs a trusted `Origin` (or `Sec-Fetch-Site: same-origin`) exactly as on a session
route (see <<csrf>>). The bearer branch skips it, because a browser never attaches `Authorization`
by itself and a cross-origin script cannot send one without a CORS preflight.

*What the gateway needs.* The route is held to both backing blocks: a `token_validation` block with
at least one issuer for the bearer branch, and an `oidc` block for the session branch. Setting
`session_fallback: true` on a `require: none` or `require: session` posture, or on a gateway with no
`oidc` block, is refused at boot with a fixed `ApiSheriff-200` message. The boot log's per-route
posture line reports `auth.require='bearer', auth.session_fallback=true` for such a route.

*What to watch.* `sheriff_auth_branch_total{route,branch}` counts every request on a
`session_fallback` route by the branch it took, `bearer` or `session`. Routes without the key record
no series. A route expected to serve mostly API clients whose `session` series climbs is receiving
requests without `Authorization` -- typically a client that dropped its header.

The full key contract is in
link:../configuration/authentication-and-oidc.adoc#_auth_session_fallback[Configuration Reference -- `auth.session_fallback`]
and the design rationale in
link:../adr/0055-A_session_fallback_route_carries_two_authentication_branches_selected_by_Authorization_header_presence.adoc[ADR-0055].

[[return-url]]
== Where the browser lands after login

When a navigation without a session is redirected to login, the gateway records the URL the browser
asked for and sends it back there after the callback. The recorded URL is the canonical request path
*plus the raw query string, byte for byte*: `/orders?tab=open&sort` returns to exactly
`/orders?tab=open&sort`, repeated and interleaved parameters in their original order, bare names and
percent-encoding kept as sent. A request without a query returns to the path alone.

A login started through `oidc.login.path` (`/bff/login?returnUrl=...`) returns to its `returnUrl`
target. Either way the target must be *same-origin* with `oidc.redirect_uri`: a gateway path
starting with a single `/`, or an absolute URL on that origin. An absent, cross-origin or unparseable
target is replaced by `oidc.login.default_return_url`, or by `/` when that key is unset. The default
itself is checked at boot against the same rule -- a cross-origin `default_return_url` is refused, so
it can never turn a login into an open redirect.

[[scopes]]
== Scopes

*Terminology.* `oidc.scopes` and `endpoint.scopes` are scopes the gateway *requests* from the IdP.
They are not pre-approved: the IdP decides what it grants, and the token carries only that.

*Syntax.* Every entry of either list must be an RFC 6749 §3.3 `scope-token`: one or more printable
ASCII characters (`0x21`-`0x7E`) other than the double quote and the backslash -- so no space, no
control character and no non-ASCII. `orders:read`, `orders.read` and `k_beispiel_token_permissions`
are fine; `orders read` is two scopes written as one and is refused at boot, naming the offending
entry.

*Additivity.* The scope set a route needs is worked out once at boot:

[source]
----
needed(route) = oidc.scopes ∪ endpoint.scopes     (endpoint.scopes alone when no oidc block exists)
----

`endpoint.scopes` sits at endpoint level, outside `auth`, and only ever *adds*: an endpoint cannot
remove a global scope. Declaring `scopes` on an endpoint whose every route resolves `require: none`
is refused at boot, since scopes act only on authenticated routes.

*What a login requests.*

* A navigation to a session route without a session requests exactly that route's `needed` set.
* A login through `/bff/login?returnUrl=X` requests the `needed` set of the authenticated route `X`
  would land on -- matched as a `GET` on the gateway host, the query ignored. A route with a
  `match.headers` condition is never selected here, because a header cannot be evaluated for a
  request that has not happened yet. When `X` is absent, cross-origin or unparseable, matches no
  route, or lands on a `require: none` route, the login requests `oidc.scopes` alone.

*Session-wide scope growth.* A login requests only the scope set of the route it is for; further
scopes are requested when a route first needs them (see <<scope-enforcement>>). A session gives a
scope back only when the IdP itself stops granting it: one that logged in through, or was widened
for, a route of `orders` holds the `orders.read` grant for as long as the IdP returns it, and the
token it relays to every other session route
carries that scope too -- per-endpoint token narrowing is not offered. Set `token_relay: false` on
routes whose origin needs no token (see <<token-relay>>).

*Optional client scopes at the IdP.* The IdP grants a requested scope only when the client is allowed
to request it. On Keycloak, attach an endpoint scope to the client as an *Optional* client scope, so it
is granted only when a login or a widening asks for it. A *Default* client scope is granted on every
login whether requested or not, which defeats the per-endpoint request.

*The two scope sets a session keeps.* The session remembers the scope set of its current access
token (its *active* set): after login, the token's `scope` claim (or the requested set when the token
carries none); after a refresh, the `scope` the token endpoint returns, or the requested set when
the response omits it. It also remembers the scopes the IdP is known to grant it (its *granted*
set). That set equals the active set at login. A successful widening replaces it with the scopes of
the widening's grant. A near-expiry refresh never changes it, and no refresh ever adds to it. The
one refresh that can reduce it is the scope-driven refresh of <<scope-enforcement>>: a scope it asks
for and the IdP does not return leaves the granted set. The granted set therefore says what the IdP
last showed it grants, not everything it ever granted (see <<scope-revoked>>).

*Refresh keeps the active set.* A near-expiry refresh requests exactly the active set, never the
static `oidc.scopes`, so a refresh does not silently narrow a session that logged in on a scoped
route. The one refresh that requests more is the scope-driven refresh of <<scope-enforcement>>,
which asks for the active set plus scopes the session was granted before.

[[bearer-oidc-scopes]]
*Bearer routes check `oidc.scopes` too.* A `require: bearer` route checks the same `needed` set against
the token the client presents, and a token missing any member is refused `403` with
`WWW-Authenticate: Bearer error="insufficient_scope", scope="<missing>"`, naming only the missing
scopes. Because the set includes `oidc.scopes`, a gateway running in BFF mode rejects a bearer token
that lacks them -- a `client_credentials` token issued without `openid` and the other `oidc.scopes`,
for example, is answered `403 insufficient_scope` even on a bearer route whose endpoint declares no
`scopes`. Have such clients request the `oidc.scopes` as well, or serve them from a gateway without an
`oidc` block.

[[scope-enforcement]]
== When a session lacks a scope the route needs

A session outlives the route that started it, so it can reach a route whose `needed` set (see
<<scopes>>) it does not carry. A session route never relays such a session. On every request the
gateway compares the session's active set with the route's `needed` set -- after the session is
resolved and any near-expiry refresh has run, and before anything is relayed. This holds on
`require: session` routes and on the session branch of a <<session-fallback,`session_fallback`>>
route, and it holds whatever `token_relay` says: `token_relay: false` withholds the token from the
upstream, not the check from the request.

[cols="2,3"]
|===
| The session's scopes | What happens

| Nothing is missing
| The request continues. The comparison is local: no call to the IdP, no rotated token, no cookie.
| Every missing scope lies inside the session's granted set
| A refresh, requesting the active set plus the missing scopes. Navigations and API calls take this
  path alike.
| A missing scope lies outside the session's granted set, or the refresh did not obtain it
| The session has to be *widened*. A navigation is redirected to the IdP; any other request is
  refused `403`.
|===

=== A refresh for a scope granted before

When every missing scope lies inside the session's granted set, the gateway makes a refresh that
requests the active set plus the missing scopes. A session that then carries the `needed` set is
relayed. A session that is kept but still lacks a scope -- the IdP granted less than requested, or
the refresh is backing off -- is widened or refused as described below; it is never relayed short of
a scope. When the IdP granted less than requested, the scopes it did not return also leave the
session's granted set (see <<scope-revoked>>).
A refresh that ends the session, or leaves the request without a valid token, is answered
exactly as a failed near-expiry refresh is (see
link:../configuration/authentication-and-oidc.adoc#_refresh_failure_dispositions[the per-kind table]).

The refresh is skipped, and the request goes straight to widening, in two cases:

* The session holds no refresh token: `oidc.session.refresh.enabled` is `false`, or the IdP issued
  none.
* Cookie mode only: the near-expiry refresh of the same request has just issued a new session
  cookie. The request's own `Cookie` header then names a refresh token the IdP has already retired,
  so no second exchange is started from it. The next request carries the new cookie and is refreshed
  normally.

*An `invalid_scope` answer to the refresh arms the refresh back-off.* The gateway cannot tell that
answer from an IdP that never processed the grant, so it is recorded as a pre-redemption failure
(`ApiSheriff-127`): the session is kept, the request is widened or refused, and the session's next
refresh -- a near-expiry one included -- waits out the five-second back-off.

=== Widening the live session

A widening asks the IdP for the session's granted set plus the route's `needed` set and merges the
grant into the *same* session. What the gateway answers depends on whether the caller can follow a
redirect to the IdP.

*A navigation* (its `Accept` offers `text/html`) is redirected `302` into that authorization request
and comes back to the URL it asked for, path and raw query (see <<return-url>>). The request is
pushed like a login's, so the gateway adds `client_id` and `request_uri` only to the redirect; the
scopes and `prompt` travel in the pushed request. The first attempt
carries `prompt=none`, so an IdP that can answer from its own SSO session does so without showing
the user anything. If the IdP answers `login_required`, `interaction_required`,
`consent_required` or `account_selection_required`, the gateway starts exactly one interactive
attempt for the same scopes and the same return URL.

*Any other request* (XHR / `fetch`, an API client) is refused `403` `application/problem+json`. The
body carries two RFC 9457 extension members (shown formatted; the gateway writes it compact):

[source,json]
----
{
  "type": "urn:api-sheriff:problem:authorization",
  "title": "Authorization",
  "status": 403,
  "missing_scopes": ["orders.read"],
  "step_up_url": "/bff/step-up?returnUrl=%2Fapi%2Forders%3Ftab%3Dopen"
}
----

* `missing_scopes` lists the scope names the session lacks, sorted. Every name comes from the
  route's configured `needed` set, never from a token.
* `step_up_url` is a relative, same-origin URL: `oidc.step_up.path` with the refused request's path
  and query as its percent-encoded `returnUrl` parameter. It is present only when
  `oidc.step_up.path` is configured. Without it the answer names the missing scopes and nothing to
  follow.
* The answer carries no `WWW-Authenticate` header. That challenge belongs to bearer clients.
* On a `protocol: grpc` route the refusal is a trailers-only gRPC status, which carries neither
  member.

*Following `step_up_url`.* A script cannot complete a widening by retrying: the widening needs a
browser navigation to the IdP. Send the browser to `step_up_url` as a top-level navigation, not as a
`fetch`. After a granted widening the browser is redirected to the `returnUrl` -- the refused
request's own path and query -- and a repeated call is relayed.

*What a granted widening changes.* The session stays the same session. It keeps its identity, its
authentication time and its absolute expiry, so a widening does not extend `ttl_seconds`. It takes
the new tokens, and both its active set and its granted set become the scopes of the new grant. A
scope of the earlier granted set that the IdP no longer returned is therefore gone from the session.
The gateway logs `ApiSheriff-20`, naming only the scopes added.

*The browser gets a new cookie value.* The callback of a granted widening sets the session cookie
again with a new value, and the previous value stops working at once. The new cookie's `Max-Age` is
the session's remaining lifetime, not a full `ttl_seconds`. A request that was already on its way
with the previous value is answered once as unauthenticated -- `401` for an API call, the redirect
into login for a navigation -- without a clearing cookie, and succeeds when it is sent again. A
back-channel logout still finds the session. Because the value changes, nothing outside the
gateway may treat it as a stable name for the session (see <<multi-replica>>).

*A widening also moves the session to the IdP session that answered it.* The new tokens belong to
the IdP session that issued the grant. That is usually the one the login used, but not always: if
the IdP session ended and the user signed in again -- which is what the interactive attempt does --
it is a new one. The gateway session takes the `sid` of the new ID token when the token carries one,
and keeps its own otherwise. In server mode a back-channel logout for that IdP session, delivered
to `oidc.logout.backchannel_path`, then destroys the gateway session. A logout token that names the
earlier `sid` no longer matches it.

*When the widening is refused.* The callback answers `403`, redirects nowhere and sets no cookie,
and the session is left as it was: it stays usable on every route whose `needed` set it satisfies.
That is the answer to:

* an IdP error on the silent attempt other than the four named above, and any IdP error on the
  interactive attempt;
* a grant that still lacks a scope the widening sought beyond the granted set;
* a grant for a different user (`sub`) than the session's -- a session is never moved to another
  identity;
* a callback that arrives without the live session.

The first two are logged as `ApiSheriff-131` with a bounded reason, the identity mismatch as
`ApiSheriff-130` (see link:../LogMessages.adoc[Log Messages]). Because nothing redirects again, a
scope the IdP will not grant cannot loop the browser. The gateway keeps no record of a refusal: a
later navigation to the route starts a new attempt.

Three refusals are not answered by that `403`. An IdP that refuses the *pushed* request -- some refuse
a scope there that the client may not request -- never sees the browser: the navigation, or the
request to the step-up path, is answered `502` and `ApiSheriff-132` is logged (see
link:bff-oidc-common.adoc#_what_the_browser_sees_at_login[Shared Setup -- What the browser sees at login]).
A widening started while the gateway holds its maximum of unfinished logins is answered `503` with
`Retry-After: 30` (see <<pending-logins>>). A grant whose token is not bound to the proof key is
answered `400` on the callback and logged as `ApiSheriff-134`. In all three cases the session is left
as it was.

*A logout during a widening wins.* If the user logs out, or the IdP delivers a back-channel logout,
after the callback has found the live session and before it stores the merged one, the grant is not
merged and nothing is stored: the session stays logged out. The callback answers the same `403`,
and the refusal is logged as `ApiSheriff-131` with the reason `session-terminated`.

[[scope-revoked]]
=== When the IdP stops granting a scope

An IdP can stop granting a scope during a session's life: a role or entitlement is removed, a
consent is withdrawn, a client scope is unassigned. The session's granted set then still names a
scope the IdP will not return. The gateway corrects the granted set the first time it asks:

* *A refresh is answered with fewer scopes than it asked for.* The scopes the IdP did not return
  leave the granted set. A navigation is then widened once, and when that grant lacks the scope too
  the callback answers the terminal `403` above. An API call is refused `403`.
* *No refresh ran* -- the session holds no refresh token, refresh is switched off, or (cookie mode)
  the near-expiry refresh had just issued a new cookie. The widening's grant is merged, which takes
  the scope out of the granted set, and the browser is sent back to the route once. The next
  widening is the one that ends in the terminal `403`.

Either way the session is kept and stays usable on every route it still satisfies. A navigation ends
in the `403` after at most two round trips to the IdP.

One case is not corrected this way. An IdP that answers the refresh with an outright `invalid_scope`
error gives the gateway nothing to learn from (see the back-off note above): the granted set is left
as it was and the refresh is tried again once per back-off window.

[[step-up-path]]
=== The step-up path

`oidc.step_up.path` is an optional gateway-owned reserved path (see
<<_gateway_owned_reserved_paths>>). It is the
target of `step_up_url`: a browser holding a live session navigates to
`<path>?returnUrl=<target>` to have that session widened for the route behind `<target>`.

[source,yaml]
----
# gateway.yaml
oidc:
  step_up:
    path: /bff/step-up               # optional; absolute gateway path
----

* *It serves a live session only.* Without one it answers `401` `application/problem+json` with
  `Cache-Control: no-store`: no redirect to the IdP, no cookie. It widens a session and never
  starts one; a login is started through a session route or `oidc.login.path`.
* *The return URL must be same-origin.* `returnUrl` is checked by the rule a login's target is
  checked by (see <<return-url>>). An absent, cross-origin, scheme-relative or unparseable target is
  replaced by `oidc.login.default_return_url`, or by `/` when that key is unset.
* *It requests what the target's route needs.* The target is resolved to a `needed` set exactly as
  for `/bff/login?returnUrl=` (see <<scopes>>): matched as a `GET` on the gateway host, the query
  ignored, a route with a `match.headers` condition never selected, and `oidc.scopes` alone when no
  authenticated route matches.
* *It redirects straight back when no widening is owed.* When that set already lies inside the
  session's granted set, the answer is a `302` to the target and nothing else: the route itself then
  obtains the scope by a refresh. Otherwise the path starts the same widening a navigation gets,
  `prompt=none` first.

Because the target is matched as a `GET` without headers, a refused request on a route that such a
`GET` would not select -- a route matching `methods: [POST]` only, or one selected by a header
matcher -- gets a `step_up_url` that widens for whatever route the `GET` selects instead, or not at
all.

The path's presence alone registers the endpoint. `oidc.step_up.enabled` and
`oidc.step_up.honor_upstream_challenge` govern the RFC 9470 upstream-challenge leg and do not gate
it. See link:../configuration/authentication-and-oidc.adoc#_oidc[Configuration Reference -- `oidc`] and
link:../adr/0057-Session_routes_obtain_their_declared_scopes_by_refreshing_inside_the_grant_and_widening_the_live_session_outside_it.adoc[ADR-0057].

=== What the integration realm showed

The project's integration suite runs these paths against the pinned Keycloak image
(`integration-tests/docker-compose.yml`) with one realm. Two observations from it, each about that
image and that realm and not a statement about identity providers in general:

* A `prompt=none` authorization request from a browser that holds the realm's SSO cookies is
  answered with a code, without a page.
* A refresh that asks again for a scope of the original grant, after an earlier refresh narrowed it
  away, is issued a token carrying that scope.

[[_gateway_owned_reserved_paths]]
== Gateway-owned reserved paths

The gateway carves out its own exact paths *before* the proxy route table, so a proxy prefix can
never swallow them. Six of them are answered on the OIDC host only (the host of
`oidc.redirect_uri`). The last two in the table are answered on *every* host, because the identity
provider calls them server-to-server. Configure them so they do not collide with a proxied namespace
you need:

[cols="1,2"]
|===
| Path | Purpose

| `oidc.redirect_uri` (path) | Auth-code callback that lands a login.
| `oidc.login.path` | Login-initiation entry point that starts a login (optional).
| `oidc.step_up.path` | Step-up entry point that widens the live session for the URL it is given (optional).
| `oidc.user_info.path` | Curated identity view served to the SPA (optional).
| `oidc.logout.path` | RP-initiated logout.
| `oidc.logout.post_logout_redirect_uri` (path) | Logout-return verification leg.
| `oidc.logout.backchannel_path` | Back-channel logout receiver (server mode only). Every host. See <<backchannel-logout>>.
| `oidc.client_authentication.jwks_path` | The client JWKS endpoint; default `/bff/jwks`, reserved
  even when the key is not declared. Every host. Publishes the client-authentication public key; with
  `oidc.client_secret` configured it answers `404`.
|===

== Serve a curated identity view to the SPA

If the SPA needs profile fields, expose `oidc.user_info.path` rather than forwarding raw tokens.
Disclosure is *closed by default*: list exactly the claims you are willing to reveal in
`allowed_claims`, and set `default_view` (a subset) for the no-claims-requested case. A claim
absent from `allowed_claims` is never returned.

*Every disclosed claim keeps the JSON type it has in the validated ID token.* An array stays an
array, an object stays an object, and numbers and booleans stay numbers and booleans; only claims
that are strings in the token are strings in the response. The claims are read from the payload of
the ID token the gateway has just validated, so the view never carries a value the token does not.
Two consequences are worth planning for in the SPA:

* *Date claims are numbers.* Under `claims`, `exp`, `iat` and `auth_time` are the token's numeric
  epoch seconds, not strings. The separate `session` member is the gateway's own bookkeeping, not a
  token claim: its `expires_at` and `auth_time` are ISO-8601 timestamp strings.
* *Multi-valued claims are arrays.* A `groups` claim arrives as a JSON array you can iterate, never
  as a string rendering of one.

`allowed_claims` caps disclosure whatever the claim's type: a structured claim outside the list is
never returned, and explicitly requesting one is refused `403`. With
`allowed_claims: [sub, name, email, groups]`, a request for `?claims=sub,groups` answers:

[source,json]
----
{
  "claims": {
    "sub": "8f2c0c1e-4b0a-4a57-9d0e-2f1f6f3a9b21",
    "groups": ["orders-readers", "support"]
  },
  "session": {
    "expires_at": "2026-09-18T11:00:00Z",
    "auth_time": "2026-09-18T10:00:00Z"
  }
}
----

[[csrf]]
== CSRF for a cross-origin SPA

Every `require: session` route, and the session branch of every `session_fallback` route, enforces
origin verification on unsafe methods (non-GET/HEAD/OPTIONS) -- this is fixed, not a knob. If your SPA is served from a different origin than the gateway, list
its origin in `oidc.session.csrf.trusted_origins` *and* enable `security_headers.cors` with
`allow_credentials: true`. This works only for *same-site* origins (same registrable domain); a
truly cross-site SPA never gets the `SameSite=Lax` cookie attached -- host it under the gateway's
site. See link:../variants/02-bff-session.adoc#_csrf_defence[CSRF Defence].


[[session-lifetime]]
== How long a session lives

A session has two deadlines, and it ends at whichever comes first.

* *The absolute lifetime*, `oidc.session.ttl_seconds`, is counted from the login. Nothing extends
  it: not a request, not a token refresh, not a widening.
* *The idle timeout*, `oidc.session.idle_timeout_seconds`, ends a session that has gone that long
  without a request the gateway let through on a session route. The default is `1800`, or
  `ttl_seconds` when that is lower. A declared value below `1` or above `ttl_seconds` stops the boot.

*What counts as a request.* Only a request that is let through to a `require: session` route, or to
the session branch of a `session_fallback` route. A request the gateway refuses, challenges or
redirects into a login or a widening does not count, and neither does a call to the user-info path
or any other reserved path. A page that only polls `oidc.user_info.path` therefore does not keep
its session alive.

*What the user sees.* A request on a session past either deadline is answered like a request
without a session: a navigation is redirected into login, an XHR or API call gets `401`.

*Expired sessions leave the store within a minute.* The gateway removes a session past either
deadline when its cookie is next presented, and otherwise in a sweep that runs once a minute. An
expired session therefore does not hold one of the `max_sessions` slots until the store fills.

[[websocket-sessions]]
=== WebSockets and streamed responses

A long-lived connection counts as *one* request, when it starts. The frames of an open WebSocket
and the bytes of a streamed response do not move the idle deadline. A browser that holds a
WebSocket and sends no other request to a session route lets its session go idle.

*A WebSocket on a session route is closed when its session ends.* The gateway closes both legs with
close code `1008` and the reason `session ended`. That happens:

* at the session's absolute expiry;
* at a logout through `oidc.logout.path`, and at a back-channel logout;
* when a new login in the same browser replaces the session (see <<login-replaces>>);
* when the session is ended by the per-user bound (see <<login-replaces>>);
* when the sweep removes the session -- so also after the idle timeout, within a minute of it.

It does *not* happen when a widening gives the browser a new cookie value: the session is the same
session, and its WebSockets stay open.

A client should treat `1008` with that reason as "authenticate again, then reconnect". It differs
from the `1001` a route's own WebSocket idle timer sends.

*Streamed HTTP and gRPC responses are not ended.* A response that is already streaming when its
session ends runs until it finishes or a transport timeout ends it.

*The gateway tracks at most 10 000 session-bound WebSockets per instance.* An upgrade beyond that is
refused `503` before anything is opened, like an upgrade beyond the WebSocket relay budget (see
link:protocol-routes.adoc[Protocol routes]). WebSockets on bearer routes and on
`require: none` routes are not session-bound and do not count.

[[login-replaces]]
== A new login, and how many sessions a user may hold

*A login ends the session the browser presents.* When a login completes in a browser that still
carries a session cookie, the gateway ends that session before it creates the new one, whoever it
belonged to. An earlier session does not live on beside the new one, and its cookie value stops
working. A widening is not a login and keeps its session.

*One user holds a bounded number of sessions.* `oidc.session.max_sessions_per_subject` bounds the
live sessions of one subject (`sub`). The default is `10`, or `max_sessions` when that is lower.
Each browser, browser profile and private window is a session of its own. A login beyond the bound
ends the user's *oldest* session -- the one created first -- and is then admitted; that browser is
answered as unauthenticated on its next request. Raise the key for an account that more than ten
browsers use at once. The range is `1` to `max_sessions`, and a value outside it stops the boot.

Neither event revokes tokens at the IdP, and neither is logged above `DEBUG`.

[[pending-logins]]
== When too many logins are unfinished

Every login the gateway starts leaves a *pending login* in its memory until the browser comes back
to the callback or five minutes pass: a navigation to a session route without a session, a request
to `oidc.login.path`, a widening started by a navigation or by the step-up path, and the interactive
second attempt of a widening. Starting a login needs no credential, so the gateway limits how many
it holds and how the room is shared. A gateway instance holds at most 10,000 pending logins, and
neither number is configurable.

*Each source holds at most 256.* A pending login is counted under the address it came from: the
client address the forwarding headers name when the request arrives through a proxy listed in
`forwarded.trusted_proxies`, otherwise the address of the TCP connection. Behind the gateway's own
SNI front listener (`tls.passthrough_sni` set), that connection is the client's connection to the
front listener, not the internal hop the gateway relays it over. An IPv6 address counts by
its `/64`. Requests through a trusted proxy whose forwarding headers name no client, and requests
without a usable address, are all counted as one source, `unknown`. When a source starts its 257th
pending login, its oldest one is dropped; that user's callback is refused `403` and the login has to
be started again. Other sources are not touched.

*A full gateway refuses new logins and keeps the started ones.* When all 10,000 places hold logins
that have not expired, a further login, widening or step-up start is answered `503` with
`Retry-After: 30`, unless its source already holds 256 -- that one replaces its own oldest as above.
The body is `application/problem+json` of type `urn:api-sheriff:problem:rate-limiting`; a browser
navigation gets the HTML error page instead when `portal.error_pages` is on (see
link:portal.adoc[Portal]). The browser is not redirected and gets no cookie, and a live session that
was to be widened stays as it was. No login already started is dropped to make room, so users who
are on the IdP's login page can still complete it. The `503` ends once logins are completed or
expire, at most five minutes after the logins that filled the gateway were started.

The gateway has already pushed the refused login's authorization request to the IdP when it finds
no room, so a refused login still costs the IdP one request.

*What you see.* The first refusal logs `WARN` `ApiSheriff-145` once; every further refusal stays at
`DEBUG` until fewer than half of the places -- fewer than 5,000 -- hold pending logins. The next full
period after that logs it once more. A gateway that frees a few places and fills them again is still
in the same period and logs nothing new. The record names no address and no login. Every refusal is
counted on `sheriff_errors_total{event="PENDING_AUTHORIZATION_SATURATED"}` (see
link:../LogMessages.adoc[Log Messages] and
link:../architecture/observability-and-errors.adoc[Observability and error handling]).

*What it means.* A sustained count means many sources are starting logins they do not finish -- a
login flood. No setting raises the limits: the gateway does not enforce `rate_limit`, so place a
rate limit on the login and session paths in front of the gateway. If many real users share one
address -- a corporate NAT, or a proxy you have not listed in `forwarded.trusted_proxies` -- more than
256 of them logging in within the same five minutes drop each other's logins; list the proxy so
each user's own address counts. The threat analysis is in
link:../security-threat-model.adoc#bff-20[Threat model -- BFF-20].

Each replica counts its own pending logins (see <<multi-replica>>).

[[logout]]
== Logout

A logout through `oidc.logout.path` *always ends the gateway session first*: the session is
destroyed and its cookie cleared before anything is asked of the IdP. What follows depends on the
IdP.

* *The IdP publishes an end-session endpoint.* The browser is redirected there with
  `id_token_hint`, `post_logout_redirect_uri` and `state`, comes back to
  `oidc.logout.post_logout_redirect_uri`, and lands on `oidc.logout.final_redirect`. This is a
  redirect, so the ID token travels in the URL of that one request. The response that carries it
  has `Referrer-Policy: no-referrer`.
* *The IdP publishes no usable end-session endpoint* -- none, or a value that is not an absolute
  `http` or `https` URL. The browser lands on `oidc.logout.final_redirect` directly. The gateway
  logs `WARN` `ApiSheriff-135` once; repeats stay at `DEBUG`. *The session at the IdP is not ended*:
  a user who logs in again may be signed in without a prompt. If you see `ApiSheriff-135`, check
  the IdP's discovery document for `end_session_endpoint`.
* *Discovery fails at that moment*, or the session holds no ID token. The browser lands on
  `oidc.logout.final_redirect` as well, and the IdP is asked again at the next logout.

*What the logout revokes.* In each of these cases, after the session is destroyed and before
the browser is redirected, the gateway tries to revoke the session's refresh token at the IdP's
`revocation_endpoint` (RFC 7009). It revokes the token the session held when it was destroyed, so a
refresh that rotated the token while the logout was running is covered. When something else ended
the session after the logout found it and before it destroyed it, the gateway revokes the refresh
token of the session the logout found instead. When discovery fails, the
revocation's own metadata read fails too: the attempt is reported as `ApiSheriff-147` and nothing is revoked. Where the revocation
succeeds, a refresh token stolen from the session can no longer mint access tokens. What it does
not revoke:

* *The access token.* It stays valid at a resource server until it expires. Keep access-token
  lifetimes short.
* *Other tokens of the same grant*, unless the IdP invalidates them on its own when the refresh token
  is revoked.
* *Anything, when there is nothing to revoke with.* A session without a refresh token
  (`oidc.session.refresh.enabled: false`, or the IdP granted none) sends no request. Neither does an
  IdP whose discovery document names no `revocation_endpoint`; that is logged at `DEBUG` only, so
  check the discovery document if you rely on the revocation.

The revocation waits for the IdP, so a slow IdP delays the logout answer. Each request to the IdP is
bounded by the back channel's 5-second connect and 10-second read timeouts, and the revocation needs
at most two: a discovery request when the IdP's metadata is not yet known, and the revocation itself
(see
link:../adr/0080-RP-initiated_logout_revokes_the_sessions_refresh_token_at_the_identity_provider_before_the_end-session_redirect.adoc[ADR-0080]).
The session is already gone during that wait. A failed
revocation never changes the answer the browser gets. The first failure logs `WARN` `ApiSheriff-147`
once; repeats stay at `DEBUG`. If you see `ApiSheriff-147`, check that the gateway can reach the
IdP's revocation endpoint over its back channel and that the IdP accepts the gateway's client
authentication there -- until then, logouts leave refresh tokens valid until they expire.

A logout without a live session answers the same redirect to `oidc.logout.final_redirect` and
clears the cookie. There is no session token to revoke, so no revocation request is sent. A logout
that found a live session which something else -- a new login of the same user, the expiry sweep, a
back-channel logout -- ended before the logout destroyed it is different: the gateway revokes the
refresh token of the session it found, as described above, and the browser is still redirected to
the IdP's end-session endpoint where one is usable. Revoking a token that is already invalid does no
harm; the IdP answers it with success.

[[backchannel-logout]]
=== Back-channel logout: what the identity provider must send

The IdP ends a gateway session by posting a logout token to `oidc.logout.backchannel_path`. The
gateway acts on a token only when all of this holds:

[cols="1,3", options="header"]
|===
| Part of the token | Requirement

| Signature | Verifies against the IdP's JWKS.
| `typ` header | Optional. When present it must be `logout+jwt` (`application/logout+jwt` is read as
  the same). A token typed anything else, `JWT` included, is refused.
| `iss`, `aud` | The configured `oidc.issuer` and `oidc.client_id`.
| `iat` | Within two minutes of the gateway's clock.
| `exp` | Required, and not yet passed. There is no clock-skew allowance on `exp`.
| `jti` | Required.
| `events` | Contains the back-channel logout event.
| `nonce` | Absent.
| `sub` or `sid` | At least one. `sid` ends the sessions of that IdP session, `sub` alone every
  session of the user.
|===

*A token acts once.* The gateway remembers the `jti` of every token it acted on until the token's
two-minute window has passed, and refuses a second delivery of the same token.

*A back-channel logout revokes no token.* It destroys the matching sessions only; the IdP that sent
the logout token has already ended its own session.

*That memory is per gateway instance.* It is held in memory, is not shared between instances and
does not survive a restart. It holds 10 000 tokens; when it is full of tokens still inside their
window, a further token is refused until one leaves it, and the IdP's retry then succeeds.

Every refused token is answered `400` and logged as `ApiSheriff-112` with the reason (see
link:../LogMessages.adoc[Log Messages]). An IdP whose logout tokens carry no `exp` or no `jti`, or a
`typ` other than `logout+jwt`, cannot end sessions on this gateway. The pinned Keycloak image
(`integration-tests/docker-compose.yml`) sends `typ` `logout+jwt`, `exp` and `jti`.

[[gateway-cookies]]
== The gateway's cookies and your application

*A response that carries a gateway cookie is not cacheable.* Whenever the gateway sets or clears
one of its cookies on a response, that response is sent with `Cache-Control: no-store`, replacing
the upstream's value. In this variant that is the login, logout and step-up answers and the answer
that ends a session. Every other response keeps the cache policy the upstream sent.

*The gateway's cookies never reach an upstream, under any policy.* The session cookie -- the
configured `oidc.session.cookie_name` -- its `-activity` sibling, and every cookie under the
reserved `+__Host-sheriff-+` prefix, `+__Host-sheriff-binding+` and `+__Host-sheriff-logout+` among
them, are dropped from the
`Cookie` header on every route, whatever the route's `cookies` block admits; naming one in
`cookies.allow` is refused at boot.

*An application behind the gateway cannot set a gateway cookie.* A `Set-Cookie` in an upstream
response that names one of those cookies is dropped under every policy, on the HTTP relay and on the
gRPC leading headers and trailers alike. Nothing is logged. Do not use those names in the
application.

*Your application's own cookies cross only as its route admits them.* Under the default
`cookies.allow: none` the upstream receives no browser cookie and no upstream `Set-Cookie` reaches
the browser. A route whose upstream needs its own cookies names them in a `cookies` block, and every
`Set-Cookie` the gateway then relays has its `Domain` attribute removed. See
link:../configuration/routing-and-forwarding.adoc#_never_forward_set[the never-forward set] and
link:../configuration/routing-and-forwarding.adoc#_cookies[the `cookies` reference].

[[multi-replica]]
== Running more than one replica

The session store is in the memory of one gateway process. Several replicas work only with *sticky
sessions*: the load balancer or ingress in front of them sends every request of one browser to the
replica that holds its session.

* *Base the affinity on a cookie of the load balancer or ingress itself.* Let it set its own
  affinity cookie and route on that.
* *Never derive the affinity from the gateway's session cookie.* Its value changes when a session
  is widened (see <<scope-enforcement>>). A balancer that hashes that value sends the browser to
  another replica after the change, where the session does not exist.
* *The login leg needs the same affinity.* The pending login between the redirect to the IdP and
  the callback is held by the replica that started it.
* *A replica that restarts or fails over ends the sessions it held.* Those users log in again.
  Nothing is replicated.
* *Give every replica the same two signing key files* (see
  link:bff-oidc-common.adoc#key-material[Shared Setup -- Key material]).

Where replicas must be interchangeable, use the
link:../variants/03-bff-cookie.adoc[cookie-based variant]: once every replica shares the sealing key
and the two signing keys, any replica serves any session.

== Operate

* *Sessions are in-memory.* A gateway restart drops all sessions and users re-authenticate. Size
  `max_sessions` for expected concurrency; it caps memory against a login flood. Expired sessions
  are removed within a minute, so only live sessions hold the ceiling.
* *Unfinished logins are bounded separately.* At most 10,000 per instance and 256 per source; a full
  gateway answers new logins `503` and logs `ApiSheriff-145`. See <<pending-logins>>.
* *Two deadlines.* `ttl_seconds` is counted from login and is not extended by refresh or by use;
  `idle_timeout_seconds` ends a session nobody uses. On either the user re-authenticates. See
  <<session-lifetime>>.
* *A logout is not undone by a request that was already running.* A logout through
  `oidc.logout.path`, or a back-channel logout, can arrive while a token refresh or a widening for
  the same session is in flight. The logout wins: the refreshed or widened session is not stored,
  the refreshing request is answered as unauthenticated with the session cookie cleared, and the
  refresh token the IdP had just issued is revoked best-effort. The log shows `ApiSheriff-111` with
  the reason `session-terminated` for a refresh and `ApiSheriff-131` with the same reason for a
  widening. Neither is a fault; `persist-failure` is the reason to look into.
* *Refresh failures, IdP reachability and a private-CA IdP* are the same in both variants; see
  link:bff-oidc-common.adoc#_operate[Shared Setup -- Operate],
  link:bff-oidc-common.adoc#_configure_strict_refresh_token_rotation_at_the_idp[strict refresh-token
  rotation at the IdP] and link:bff-oidc-common.adoc#_private_ca_self_signed_idp[Private-CA /
  self-signed IdP].
