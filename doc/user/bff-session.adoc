= Server-Session BFF -- Operator Setup
:toc:
:toclevels: 3
:sectnums:

A task-oriented guide for operators standing up the *server-session BFF* (Variant 2): API Sheriff
as an OIDC confidential client that holds tokens server-side and hands the browser only an opaque
session-id cookie. It tells you *how* to configure and run the variant; the field-by-field contract
lives in the link:../configuration.adoc#_oidc[Configuration Reference (`oidc`)] and the design
rationale in link:../variants/02-bff-session.adoc[Variant 2 -- BFF, Session-based].

== When to choose this variant

Choose the server-session BFF when server-side-only token custody is a hard requirement: the token
never leaves the gateway, not even encrypted. It is *stateful* -- it keeps an in-memory session
store -- so it fits single-node or sticky-session deployments. A multi-node non-sticky deployment,
or one that must avoid server-side session state, is the
link:../variants/03-bff-cookie.adoc[cookie-based variant]'s job instead.

== Prerequisites

* An OIDC provider (IdP) where you can register a *confidential client* and obtain a
  `client_id` / `client_secret`.
* A registered *redirect URI* pointing at the gateway's own callback path (`oidc.redirect_uri`),
  matched exactly at the IdP.
* The client secret and any session-related secrets available as environment variables (never
  written inline -- `client_secret` must be an `${ENV_VAR}` reference).

== Configure the confidential client

Add an `oidc` block to `gateway.yaml` and set at least one route's effective auth to
`require: session`. A minimal server-session configuration:

[source,yaml]
----
# gateway.yaml
oidc:
  issuer: https://idp.example.com/realms/main
  client_id: api-sheriff
  client_secret: ${SHERIFF_CLIENT_SECRET}     # must be an ${ENV_VAR} reference
  redirect_uri: https://gw.example.com/auth/callback   # registered exactly at the IdP
  scopes: [openid, profile]                   # requested on every login; see "Scopes" below
  login:
    path: /auth/login                         # optional: gateway-owned login-start URL
    default_return_url: /app/                 # optional: landing page when a login has no target (default /)
  user_info:
    path: /auth/userinfo                      # optional: curated identity view for the SPA
    allowed_claims: [sub, name, email]        # disclosure ceiling; empty discloses nothing
    default_view: [sub, name]                 # subset of allowed_claims
  session:
    mode: server                              # server-side token store (this variant)
    store: memory                             # REQUIRED for server mode; only initial option
    max_sessions: 10000                       # DoS guard on the in-memory store
    cookie_name: __Host-sheriff
    ttl_seconds: 3600                         # absolute lifetime from login
    csrf:
      trusted_origins: [https://app.example.com]   # SPA origins allowed on unsafe methods
    refresh: { enabled: true, leeway_seconds: 30, on_failure: reauthenticate }
----

The gateway drives no login unless a route's effective auth is `require: session` or a
`require: bearer` route declares `session_fallback: true` (see <<session-fallback>>). One part of the
block does reach bearer routes, though: `oidc.scopes` joins the scope set every bearer route checks
(see <<bearer-oidc-scopes>>), so adding an `oidc` block to a gateway that also
serves bearer routes tightens those routes.

== Protect a route with a session

Mark the endpoint (or an anchor) `require: session`; the mediated `Authorization: Bearer` is then
injected automatically from the stored token, and any inbound `Authorization` from the browser is
stripped:

[source,yaml]
----
# endpoints/app1.yaml
endpoint:
  id: app1
  base_url: APP1
  auth: { require: session }
  scopes: [orders.read]                       # needed on every route of this endpoint, in addition to oidc.scopes
  routes:
    - id: orders-api
      match: { path_prefix: /api/orders }
      upstream: { path: /orders }
----

`scopes` names what a login for this endpoint *asks* the IdP for, and what every session request to
its routes is held to: a session whose token lacks one of these scopes is not relayed. The gateway
obtains the scope when the IdP grants it and answers `403` when it does not. See <<scopes>> and
<<scope-enforcement>>.

[[token-relay]]
== Enforce login without handing the origin a token

By default a session route relays the session's access token to the upstream as
`Authorization: Bearer`. Some origins need to know only that the user is logged in -- a static
single-page app, an asset server -- and have no use for the token. Set `token_relay: false` in the
route's `auth` block (or the endpoint's, or an anchor's) to keep the token at the gateway:

[source,yaml]
----
# endpoints/spa.yaml
endpoint:
  id: spa
  base_url: SPA
  auth: { require: session, token_relay: false }
  routes:
    - id: spa-shell
      match: { path_prefix: /app }
----

The session is still resolved, refreshed, scope-checked and required exactly as before: a navigation
without a session is redirected to login, an XHR gets `401`, an ended session still clears the
cookie, and a session lacking a scope the route needs is refreshed, widened or refused `403` (see
<<scope-enforcement>>). The only difference is that the gateway mediates no `Authorization` header:
the session's token never reaches the upstream. The only `Authorization` that could still cross is a static value the route
itself configures in `forward.set_headers` -- operator configuration, which `token_relay` does not
filter. `token_relay` acts on
`require: session` routes and on the session branch of a <<session-fallback,`session_fallback`>>
route. It has no effect on a plain `require: bearer` route, where the client's own `Authorization`
crosses only when `forward.headers_allow` names it, nor on the bearer branch of a `session_fallback`
route, which always forwards the validated client token.

Because the point of `token_relay: false` is that no access token reaches the origin, the gateway
refuses at boot a route that sets it while its effective `forward.headers_allow` names
`Authorization` (in any letter case) -- that would let the browser's own `Authorization` header back
in. Remove `Authorization` from `headers_allow`, or drop `token_relay: false`.

[[session-fallback]]
== Serving API clients and browsers on one route

A backend path that serves both API clients presenting their own bearer token and browsers logged in
through the gateway would otherwise need two routes on one prefix, told apart by an
`Authorization` header matcher. `session_fallback: true` on a `require: bearer` route folds the pair
into one route with two authentication branches:

[source,yaml]
----
# endpoints/orders.yaml
endpoint:
  id: orders
  base_url: ORDERS
  auth:
    require: bearer
    session_fallback: true          # a request without Authorization takes the session branch
  scopes: [orders.read]
  routes:
    - id: orders-api
      match: { path_prefix: /api/orders }
----

*The branch is picked from one thing only: whether the request carries an `Authorization` header.*

[cols="2,3"]
|===
| Request | What happens

| Valid bearer token, with or without a session cookie
| Admitted when the token carries every scope the route needs; the upstream receives exactly that
  token as `Authorization: Bearer`. No session is looked up, no CSRF check runs, no cookie is set, and
  the session cookie is not forwarded. `headers_allow` does not need to name `Authorization`.
| Bearer token lacking a needed scope
| `403` with `WWW-Authenticate: Bearer error="insufficient_scope", scope="<missing>"`.
| Invalid token, a `Basic` credential or an empty `Authorization`, with or without a session cookie
| `401` with `WWW-Authenticate: Bearer`. Never a login redirect, and a valid session cookie does not
  rescue it -- the bearer branch was chosen the moment the header was sent.
| No `Authorization`, live session
| Served exactly as on a `require: session` route: the session's token is relayed upstream (unless
  `token_relay: false`), refreshed near expiry, and the session cookie is stripped. As on every
  session route, *no scope check runs*: any live session is admitted, even one whose login never
  requested the route's scopes. The `403 insufficient_scope` row above applies to bearer clients
  only, so a route whose `scopes` are its authorization boundary is not a `session_fallback`
  candidate.
| No `Authorization`, no session, navigation
| `302` into the login. The login requests the route's scope set, `oidc.scopes` plus the endpoint's
  `scopes`.
| No `Authorization`, no session, XHR or API call
| `401` `application/problem+json`.
|===

*CSRF.* The fixed CSRF defence runs on the session branch only: an unsafe method without
`Authorization` needs a trusted `Origin` (or `Sec-Fetch-Site: same-origin`) exactly as on a session
route (see <<csrf>>). The bearer branch skips it, because a browser never attaches `Authorization`
by itself and a cross-origin script cannot send one without a CORS preflight.

*What the gateway needs.* The route is held to both backing blocks: a `token_validation` block with
at least one issuer for the bearer branch, and an `oidc` block for the session branch. Setting
`session_fallback: true` on a `require: none` or `require: session` posture, or on a gateway with no
`oidc` block, is refused at boot with a fixed `ApiSheriff-200` message. The boot log's per-route
posture line reports `auth.require='bearer', auth.session_fallback=true` for such a route.

*What to watch.* `sheriff_auth_branch_total{route,branch}` counts every request on a
`session_fallback` route by the branch it took, `bearer` or `session`. Routes without the key record
no series. A route expected to serve mostly API clients whose `session` series climbs is receiving
requests without `Authorization` -- typically a client that dropped its header.

The full key contract is in
link:../configuration.adoc#_auth_session_fallback[Configuration Reference -- `auth.session_fallback`]
and the design rationale in
link:../adr/0055-A_session_fallback_route_carries_two_authentication_branches_selected_by_Authorization_header_presence.adoc[ADR-0055].

[[return-url]]
== Where the browser lands after login

When a navigation without a session is redirected to login, the gateway records the URL the browser
asked for and sends it back there after the callback. The recorded URL is the canonical request path
*plus the raw query string, byte for byte*: `/orders?tab=open&sort` returns to exactly
`/orders?tab=open&sort`, repeated and interleaved parameters in their original order, bare names and
percent-encoding kept as sent. A request without a query returns to the path alone.

A login started through `oidc.login.path` (`/auth/login?returnUrl=...`) returns to its `returnUrl`
target. Either way the target must be *same-origin* with `oidc.redirect_uri`: a gateway path
starting with a single `/`, or an absolute URL on that origin. An absent, cross-origin or unparseable
target is replaced by `oidc.login.default_return_url`, or by `/` when that key is unset. The default
itself is checked at boot against the same rule -- a cross-origin `default_return_url` is refused, so
it can never turn a login into an open redirect.

[[scopes]]
== Scopes

*Terminology.* `oidc.scopes` and `endpoint.scopes` are scopes the gateway *requests* from the IdP.
They are not pre-approved: the IdP decides what it grants, and the token carries only that.

*Syntax.* Every entry of either list must be an RFC 6749 §3.3 `scope-token`: one or more printable
ASCII characters (`0x21`-`0x7E`) other than the double quote and the backslash -- so no space, no
control character and no non-ASCII. `orders:read`, `orders.read` and `k_beispiel_token_permissions`
are fine; `orders read` is two scopes written as one and is refused at boot, naming the offending
entry.

*Additivity.* The scope set a route needs is worked out once at boot:

[source]
----
needed(route) = oidc.scopes ∪ endpoint.scopes     (endpoint.scopes alone when no oidc block exists)
----

`endpoint.scopes` sits at endpoint level, outside `auth`, and only ever *adds*: an endpoint cannot
remove a global scope. Declaring `scopes` on an endpoint whose every route resolves `require: none`
is refused at boot, since scopes act only on authenticated routes.

*What a login requests.*

* A navigation to a session route without a session requests exactly that route's `needed` set.
* A login through `/auth/login?returnUrl=X` requests the `needed` set of the authenticated route `X`
  would land on -- matched as a `GET` on the gateway host, the query ignored. A route with a
  `match.headers` condition is never selected here, because a header cannot be evaluated for a
  request that has not happened yet. When `X` is absent, cross-origin or unparseable, matches no
  route, or lands on a `require: none` route, the login requests `oidc.scopes` alone.

*Session-wide scope growth.* A login requests only the scope set of the route it is for; further
scopes are requested when a route first needs them (see <<scope-enforcement>>). A session never
gives a scope back: one that logged in through, or was widened for, a route of `orders` holds the
`orders.read` grant for the rest of its life, and the token it relays to every other session route
carries that scope too -- per-endpoint token narrowing is not offered. Set `token_relay: false` on
routes whose origin needs no token (see <<token-relay>>).

*Optional client scopes at the IdP.* The IdP grants a requested scope only when the client is allowed
to request it. On Keycloak, attach an endpoint scope to the client as an *Optional* client scope, so it
is granted only when a login or a widening asks for it. A *Default* client scope is granted on every
login whether requested or not, which defeats the per-endpoint request.

*The two scope sets a session keeps.* The session remembers the scope set of its current access
token (its *active* set): after login, the token's `scope` claim (or the requested set when the token
carries none); after a refresh, the `scope` the token endpoint returns, or the requested set when
the response omits it. It also remembers every scope the IdP has granted it so far (its *granted*
set): equal to the active set at login, extended by each successful widening, and never changed by a
refresh.

*Refresh keeps the active set.* A near-expiry refresh requests exactly the active set, never the
static `oidc.scopes`, so a refresh does not silently narrow a session that logged in on a scoped
route. The one refresh that requests more is the scope-driven refresh of <<scope-enforcement>>,
which asks for the active set plus scopes the session was granted before.

[[bearer-oidc-scopes]]
*Bearer routes check `oidc.scopes` too.* A `require: bearer` route checks the same `needed` set against
the token the client presents, and a token missing any member is refused `403` with
`WWW-Authenticate: Bearer error="insufficient_scope", scope="<missing>"`, naming only the missing
scopes. Because the set includes `oidc.scopes`, a gateway running in BFF mode rejects a bearer token
that lacks them -- a `client_credentials` token issued without `openid` and the other `oidc.scopes`,
for example, is answered `403 insufficient_scope` even on a bearer route whose endpoint declares no
`scopes`. Have such clients request the `oidc.scopes` as well, or serve them from a gateway without an
`oidc` block.

[[scope-enforcement]]
== When a session lacks a scope the route needs

A session outlives the route that started it, so it can reach a route whose `needed` set (see
<<scopes>>) it does not carry. A session route never relays such a session. On every request the
gateway compares the session's active set with the route's `needed` set -- after the session is
resolved and any near-expiry refresh has run, and before anything is relayed. This holds on
`require: session` routes and on the session branch of a <<session-fallback,`session_fallback`>>
route, and it holds whatever `token_relay` says: `token_relay: false` withholds the token from the
upstream, not the check from the request.

[cols="2,3"]
|===
| The session's scopes | What happens

| Nothing is missing
| The request continues. The comparison is local: no call to the IdP, no rotated token, no cookie.
| Something is missing, and the IdP granted it to this session before
| Exactly one refresh, requesting the active set plus the missing scopes. Navigations and API calls
  take this path alike.
| Something is missing that the session was never granted, or the refresh did not obtain it
| The session has to be *widened*. A navigation is redirected to the IdP; any other request is
  refused `403`.
|===

=== One refresh for a scope granted before

When every missing scope lies inside the session's granted set, the gateway makes one refresh that
requests the active set plus the missing scopes. A session that then carries the `needed` set is
relayed. A session that is kept but still lacks a scope -- the IdP granted less than requested, or
the refresh is backing off -- is widened or refused as described below; it is never relayed short of
a scope. A refresh that ends the session, or leaves the request without a valid token, is answered
exactly as a failed near-expiry refresh is (see
link:../configuration.adoc#_refresh_failure_dispositions[the per-kind table]).

The refresh is skipped, and the request goes straight to widening, in two cases:

* The session holds no refresh token: `oidc.session.refresh.enabled` is `false`, or the IdP issued
  none.
* Cookie mode only: the near-expiry refresh of the same request has just issued a new session
  cookie. The request's own `Cookie` header then names a refresh token the IdP has already retired,
  so no second exchange is started from it. The next request carries the new cookie and is refreshed
  normally.

*An `invalid_scope` answer to the refresh arms the refresh back-off.* The gateway cannot tell that
answer from an IdP that never processed the grant, so it is recorded as a pre-redemption failure
(`ApiSheriff-127`): the session is kept, the request is widened or refused, and the session's next
refresh -- a near-expiry one included -- waits out the five-second back-off.

=== Widening the live session

A widening asks the IdP for the session's granted set plus the route's `needed` set and merges the
grant into the *same* session. What the gateway answers depends on whether the caller can follow a
redirect to the IdP.

*A navigation* (its `Accept` offers `text/html`) is redirected `302` into that authorization request
and comes back to the URL it asked for, path and raw query (see <<return-url>>). The first attempt
carries `prompt=none`, so an IdP that can answer from its own SSO session does so without showing
the user anything. If the IdP answers `login_required`, `interaction_required` or
`consent_required`, the gateway starts exactly one interactive attempt for the same scopes and the
same return URL.

*Any other request* (XHR / `fetch`, an API client) is refused `403` `application/problem+json`. The
body carries two RFC 9457 extension members (shown formatted; the gateway writes it compact):

[source,json]
----
{
  "type": "urn:api-sheriff:problem:authorization",
  "title": "Authorization",
  "status": 403,
  "missing_scopes": ["orders.read"],
  "step_up_url": "/auth/step-up?returnUrl=%2Fapi%2Forders%3Ftab%3Dopen"
}
----

* `missing_scopes` lists the scope names the session lacks, sorted. Every name comes from the
  route's configured `needed` set, never from a token.
* `step_up_url` is a relative, same-origin URL: `oidc.step_up.path` with the refused request's path
  and query as its percent-encoded `returnUrl` parameter. It is present only when
  `oidc.step_up.path` is configured. Without it the answer names the missing scopes and nothing to
  follow.
* The answer carries no `WWW-Authenticate` header. That challenge belongs to bearer clients.
* On a `protocol: grpc` route the refusal is a trailers-only gRPC status, which carries neither
  member.

*Following `step_up_url`.* A script cannot complete a widening by retrying: the widening needs a
browser navigation to the IdP. Send the browser to `step_up_url` as a top-level navigation, not as a
`fetch`. After a granted widening the browser is redirected to the `returnUrl` -- the refused
request's own path and query -- and a repeated call is relayed.

*What a granted widening changes.* The session stays the same session. It keeps its identity, its
`sid`, its authentication time and its absolute expiry, so a widening does not extend
`ttl_seconds`. It takes the new tokens, its active set becomes the scopes of the new grant, and its
granted set grows by them. The gateway logs `ApiSheriff-20`, naming only the scopes added.

*When the widening is refused.* The callback answers `403`, redirects nowhere and sets no cookie,
and the session is left as it was: it stays usable on every route whose `needed` set it satisfies.
That is the answer to:

* an IdP error on the silent attempt other than the three named above, and any IdP error on the
  interactive attempt;
* a grant that still lacks a scope the widening sought beyond the granted set;
* a grant for a different user (`sub`) than the session's -- a session is never moved to another
  identity;
* a callback that arrives without the live session.

The first two are logged as `ApiSheriff-131` with a bounded reason, the identity mismatch as
`ApiSheriff-130` (see link:../LogMessages.adoc[Log Messages]). Because nothing redirects again, a
scope the IdP will not grant cannot loop the browser. The gateway keeps no record of a refusal: a
later navigation to the route starts a new attempt.

[[step-up-path]]
=== The step-up path

`oidc.step_up.path` is an optional gateway-owned reserved path (see
<<_gateway_owned_reserved_paths>>). It is the
target of `step_up_url`: a browser holding a live session navigates to
`<path>?returnUrl=<target>` to have that session widened for the route behind `<target>`.

[source,yaml]
----
# gateway.yaml
oidc:
  step_up:
    path: /auth/step-up              # optional; absolute gateway path
----

* *It serves a live session only.* Without one it answers `401` `application/problem+json` with
  `Cache-Control: no-store`: no redirect to the IdP, no cookie. It widens a session and never
  starts one; a login is started through a session route or `oidc.login.path`.
* *The return URL must be same-origin.* `returnUrl` is checked by the rule a login's target is
  checked by (see <<return-url>>). An absent, cross-origin, scheme-relative or unparseable target is
  replaced by `oidc.login.default_return_url`, or by `/` when that key is unset.
* *It requests what the target's route needs.* The target is resolved to a `needed` set exactly as
  for `/auth/login?returnUrl=` (see <<scopes>>): matched as a `GET` on the gateway host, the query
  ignored, a route with a `match.headers` condition never selected, and `oidc.scopes` alone when no
  authenticated route matches.
* *It redirects straight back when no widening is owed.* When that set already lies inside the
  session's granted set, the answer is a `302` to the target and nothing else: the route itself then
  obtains the scope by a refresh. Otherwise the path starts the same widening a navigation gets,
  `prompt=none` first.

Because the target is matched as a `GET` without headers, a refused request on a route that such a
`GET` would not select -- a route matching `methods: [POST]` only, or one selected by a header
matcher -- gets a `step_up_url` that widens for whatever route the `GET` selects instead, or not at
all.

The path's presence alone registers the endpoint. `oidc.step_up.enabled` and
`oidc.step_up.honor_upstream_challenge` govern the RFC 9470 upstream-challenge leg and do not gate
it. See link:../configuration.adoc#_oidc[Configuration Reference -- `oidc`] and
link:../adr/0056-Session_routes_obtain_their_declared_scopes_by_refreshing_inside_the_grant_and_widening_the_live_session_outside_it.adoc[ADR-0056].

=== What the integration realm showed

The project's integration suite runs these paths against Keycloak 26.5.7 with one realm. Three
observations from it, each about that version and that realm and not a statement about identity
providers in general:

* An authorization request naming a scope the realm assigns to no client is answered
  `invalid_scope`, so the widening ends in the terminal `403`.
* A `prompt=none` authorization request from a browser that holds the realm's SSO cookies is
  answered with a code, without a page.
* A refresh that asks again for a scope of the original grant, after an earlier refresh narrowed it
  away, is issued a token carrying that scope.

[[_gateway_owned_reserved_paths]]
== Gateway-owned reserved paths

On the OIDC host (the host of `oidc.redirect_uri`) the gateway carves out its own exact paths
*before* the proxy route table, so a proxy prefix can never swallow them. Configure them so they do
not collide with a proxied namespace you need:

[cols="1,2"]
|===
| Path | Purpose

| `oidc.redirect_uri` (path) | Auth-code callback that lands a login.
| `oidc.login.path` | Login-initiation entry point that starts a login (optional).
| `oidc.step_up.path` | Step-up entry point that widens the live session for the URL it is given (optional).
| `oidc.user_info.path` | Curated identity view served to the SPA (optional).
| `oidc.logout.path` | RP-initiated logout.
| `oidc.logout.post_logout_redirect_uri` (path) | Logout-return verification leg.
| `oidc.logout.backchannel_path` | Back-channel logout receiver (server mode only).
|===

== Serve a curated identity view to the SPA

If the SPA needs profile fields, expose `oidc.user_info.path` rather than forwarding raw tokens.
Disclosure is *closed by default*: list exactly the claims you are willing to reveal in
`allowed_claims`, and set `default_view` (a subset) for the no-claims-requested case. A claim
absent from `allowed_claims` is never returned.

*Every disclosed claim keeps the JSON type it has in the validated ID token.* An array stays an
array, an object stays an object, and numbers and booleans stay numbers and booleans; only claims
that are strings in the token are strings in the response. The claims are read from the payload of
the ID token the gateway has just validated, so the view never carries a value the token does not.
Two consequences are worth planning for in the SPA:

* *Date claims are numbers.* Under `claims`, `exp`, `iat` and `auth_time` are the token's numeric
  epoch seconds, not strings. The separate `session` member is the gateway's own bookkeeping, not a
  token claim: its `expires_at` and `auth_time` are ISO-8601 timestamp strings.
* *Multi-valued claims are arrays.* A `groups` claim arrives as a JSON array you can iterate, never
  as a string rendering of one.

`allowed_claims` caps disclosure whatever the claim's type: a structured claim outside the list is
never returned, and explicitly requesting one is refused `403`. With
`allowed_claims: [sub, name, email, groups]`, a request for `?claims=sub,groups` answers:

[source,json]
----
{
  "claims": {
    "sub": "8f2c0c1e-4b0a-4a57-9d0e-2f1f6f3a9b21",
    "groups": ["orders-readers", "support"]
  },
  "session": {
    "expires_at": "2026-09-18T11:00:00Z",
    "auth_time": "2026-09-18T10:00:00Z"
  }
}
----

[[csrf]]
== CSRF for a cross-origin SPA

Every `require: session` route, and the session branch of every `session_fallback` route, enforces
origin verification on unsafe methods (non-GET/HEAD/OPTIONS) -- this is fixed, not a knob. If your SPA is served from a different origin than the gateway, list
its origin in `oidc.session.csrf.trusted_origins` *and* enable `security_headers.cors` with
`allow_credentials: true`. This works only for *same-site* origins (same registrable domain); a
truly cross-site SPA never gets the `SameSite=Lax` cookie attached -- host it under the gateway's
site. See link:../variants/02-bff-session.adoc#_csrf_defence[CSRF Defence].

== Configure strict refresh-token rotation at the IdP

The gateway does *not* detect refresh-token reuse, and cannot: it keeps no token family and only
ever sees the refresh tokens it presents itself. Reuse detection is your identity provider's job, so
turn it on there for the client's realm or tenant:

* *Keycloak:* *Revoke Refresh Token* on and *Refresh Token Max Reuse* `0` (`revokeRefreshToken: true`,
  `refreshTokenMaxReuse: 0` in a realm export). The project's integration and compose-sample realms
  ship with exactly this.
* *Other providers:* refresh-token rotation with reuse detection and no reuse grace window.

*What strict rotation detects is reuse* -- a second presentation of a refresh token that was already
redeemed. It cannot recognise the first redemption of a live stolen token, so the order of the two
redemptions decides when the theft surfaces:

* *The attacker redeems the stolen token first.* The provider treats it as a normal rotation and
  issues the attacker a successor; nothing is detected yet. The gateway's copy is now spent, and the
  reuse is detected only when the gateway presents it on the session's next refresh: the provider
  refuses it, the gateway ends the session (`ApiSheriff-111`, reason `credential-rejected`), and on
  Keycloak the successor grant is revoked as well, cutting the attacker off too. Until that gateway
  refresh the attacker holds a working grant -- the window is bounded by the gateway's refresh cadence,
  not closed immediately.
* *The gateway refreshes first.* The attacker's later presentation of the now-spent token is the
  detected reuse; the provider revokes the successor grant, and the gateway session ends on its next
  refresh as `credential-rejected`.

Either way the Keycloak user session survives: the revocation is scoped to the refresh grant.
*Without it, neither side detects reuse* -- the provider simply refreshes a replayed token.

*The trade.* With no reuse permitted, a duplicate refresh of one token ends the session. In this
variant the gateway single-flights refreshes per session, and a single-node or sticky deployment
routes every request of a session to one instance, so the duplicate does not arise from the gateway
itself; it would take two instances refreshing the same session. Allowing a reuse count or grace
window buys that back at the cost of exactly the detection signal rotation provides.

== Operate

* *Sessions are in-memory.* A gateway restart drops all sessions and users re-authenticate. Size
  `max_sessions` for expected concurrency; it caps memory against a login flood. Expired sessions
  release their slot when the bound is reached -- a login arriving at a full store sweeps the
  expired entries first, so only genuinely live sessions hold the ceiling.
* *Absolute TTL.* `ttl_seconds` is counted from login and is not extended by refresh; on expiry the
  user re-authenticates.
* *Refresh failures do not all end the session.* If the IdP is unreachable or answers `5xx`, the
  session is *kept*: requests keep using the current access token until it expires, then are
  answered as unauthenticated without the session being destroyed, and the next refresh attempt
  waits five seconds (`ApiSheriff-127`). A refresh the IdP rejects, or one the gateway cannot
  complete after the IdP redeemed it, ends the session (`ApiSheriff-111`). `on_failure` only picks
  how the failing request is answered: `reauthenticate` redirects navigations to login and answers
  API calls `401`, `reject` answers `401` to everything. See
  link:../configuration.adoc#_refresh_failure_dispositions[the per-kind table].
* *IdP reachability.* Provider metadata is discovered lazily on first use, so the gateway boots
  without the IdP -- but logins fail until the issuer is reachable. Confirm egress to the issuer
  (and its JWKS) is permitted.

== Private-CA / self-signed IdP

If your IdP presents a certificate from a *private CA* (or a self-signed cert), the gateway's own
back-channel to it -- discovery, the authorization-code exchange, refresh and refresh-token
revocation -- has to trust that CA,
or logins fail with a PKIX/TLS trust error even though JWKS validation succeeds. The per-issuer
`jwks.tls_profile` does *not* cover this leg; it governs the JWKS fetch only. RP-initiated logout is
not part of the back-channel: it hands the browser an `end_session_endpoint` redirect and opens no
gateway connection to the IdP -- see
link:tls-edge.adoc#_operator_consideration_outbound_trust_material_replaces_the_platform_bundle[TLS
Edge]. There are two routes.

*Name a trust profile for the back-channel (recommended).* Set `egress_tls.oidc_tls_profile` to a
logical profile name and bind the anchors in the deployment:

[source,yaml]
----
# gateway.yaml
egress_tls:
  oidc_tls_profile: corporate-idp
----

[source,properties]
----
quarkus.tls.corporate-idp.trust-store.p12.path=/etc/sheriff/corporate-ca.p12
quarkus.tls.corporate-idp.trust-store.p12.password=${TRUSTSTORE_PASSWORD}
----

The profile *replaces* the JVM default trust store on this leg rather than adding to it, so a
profile holding only your private CA stops trusting public authorities for the IdP. An unbound,
`trust-all` or empty profile is refused at boot, and the boot log confirms a profile in effect with
`ApiSheriff-126`. The same IdP's JWKS fetch still needs its own `jwks.tls_profile`. Do not combine the
profile with `egress_tls.oidc_verify_hostname: false` -- the pair is refused at boot. See
link:../configuration.adoc#_oidc_back_channel_posture[The BFF OIDC back-channel] for the full
contract.

*Or add the CA to the JVM default truststore* and name no profile. That store covers every leg that
names no profile of its own, and it replaces the platform bundle wholesale, so build it from the
platform bundle plus your CA (see
link:../configuration.adoc#_default_trust_store_replaces[Supplying a default trust store REPLACES the
platform bundle]). Point the JVM default truststore at your CA store with system properties on the
runner command line (a native runner does not honour `JAVA_TOOL_OPTIONS` — pass `-D` on the command
line):

[source]
----
-Djavax.net.ssl.trustStore=/app/certificates/idp-truststore.p12
-Djavax.net.ssl.trustStorePassword=<password>
-Djavax.net.ssl.trustStoreType=PKCS12
----

A publicly-trusted IdP needs none of this — the JDK's built-in truststore already trusts it.
