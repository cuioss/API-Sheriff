= API Sheriff -- Endpoint Route Configuration (`endpoints/*.yaml`)

How to author the `endpoints/*.yaml` files: the route schema, the three terminal actions (proxy,
asset, redirect), exact and prefix routes and their ordering, how `upstream.path` builds the upstream
URI, what an omitted block resolves to, and the transport bounds at the edge. The field-level
contract for every key mentioned here lives in the
link:../configuration.adoc[Configuration Reference]; anchors are covered in
link:anchors.adoc[Anchors].

== Endpoint Configuration Files (`endpoints/*.yaml`)

One file per endpoint (service / host / app) or logical group. The file lists its routes and, when
at least one of them proxies, binds to a single `base_url` alias. *No concrete upstream host appears
here* -- the `base_url` alias is resolved from the topology at startup. An endpoint whose routes are
all `asset` or `redirect` routes contacts no endpoint upstream and omits `base_url` (see
<<_base_url_only_with_proxy_routes>>).

[source,yaml]
----
# endpoints/app1.yaml
endpoint:
  id: app1                         # unique endpoint name (mandatory); a duplicate id across
                                   #   endpoint files fails the boot
  enabled: ${ENDPOINT_APP1_ENABLED:-true}   # default true. false => this endpoint is inert:
                                   #   its routes are not added to the table and its base_url
                                   #   alias need not resolve. The ${VAR:-default} placeholder
                                   #   makes the env override visible in-file (ADR-0004 A1);
                                   #   a plain literal (enabled: true) is equally valid
  base_url: APP1                   # alias; resolved from topology.properties / env. Mandatory
                                   #   because this file carries a proxy route; an endpoint of
                                   #   asset and redirect routes only omits it
  anchor: api                      # anchor membership (see "Anchors" in anchors.adoc): default
                                   #   for every route in this file, overridable per route; the
                                   #   route paths must lie inside the anchor's path_prefix.
                                   #   Mandatory for routes inside a configured anchor namespace
  auth:                            # default auth posture for every route in this file; a route
    require: bearer                #   may override it (below). MANDATORY unless the endpoint's
                                   #   anchor declares an auth block (see "Anchors" in
                                   #   anchors.adoc)
  allowed_methods: [GET, POST]     # optional per-endpoint verb allowlist; REPLACES the
                                   #   anchor/global allowed_methods wholesale for this
                                   #   endpoint (no inheritance, no merge). Omit => the
                                   #   anchor's list applies, else the global list
  routes:                          # merged into one table across all endpoint files
                                   #   (see "Route ordering"); no match => 404
    - id: orders-api
      protocol: http               # http | grpc | graphql | websocket (see "protocol" in
                                   #   ../configuration.adoc)
      match:
        path_prefix: /api/orders   # prefix route; `path: /api/orders` would declare an EXACT
                                   #   route instead -- exactly one of the two (see "Route ordering")
        methods: [GET, POST]
        host: ${GATEWAY_PUBLIC_HOST:-api.example.com}
                                   # matches the INBOUND request's Host header -- the gateway's
                                   #   own public vhost, not an upstream location. It is
                                   #   therefore environment-specific: express it as a ${VAR}
                                   #   placeholder rather than a literal
        headers:                   # optional header matchers (presence or exact value)
          - { name: X-Tenant, present: true }
      auth:                        # route-level override of endpoint.auth (whole block
        require: bearer            #   replaces, no merge)
        required_scopes: [orders.read]
      security_filter:             # "basic filtering -- NOT a WAF"; the field-level contract is
                                   #   "security_filter" in ../configuration.adoc
        profile: strict
        allowed_paths: ["/api/orders", "/api/orders/{id}"]   # quoted: {} is YAML syntax
        max_header_count: 50
        max_header_value_length: 8192   # characters (cui-http unit)
        max_query_params: 20
        max_param_value_length: 2048    # characters
        max_body_bytes: 1048576
      forward:                     # OPTIONAL. Omit the whole block for FORWARD-ALL, the
                                   #   baseline. Per dimension, declaring *_allow selects a
                                   #   positive-list and *_deny a negative-list; declaring BOTH
                                   #   for one dimension is REFUSED AT BOOT
        headers_allow: [x-tenant]  # positive-list. The gateway-understood protocol headers
                                   #   (Accept, Accept-Encoding, Accept-Language, Content-Type,
                                   #   Range, + the conditional validators) cross WITHOUT being
                                   #   listed -- do not enumerate HTTP mechanics here
        query_deny: [debug]        # negative-list on the OTHER dimension: every other client
                                   #   parameter crosses. The two dimensions are independent
        set_headers:               # additional STATIC gateway-set headers only; the mediated
          x-gateway: api-sheriff   #   Authorization (session routes) and the forwarding-
                                   #   header set are injected automatically, never configured.
                                   #   set_headers WINS over a client header of the same name
                                   #   (case-insensitively) -- operator config beats client input
      upstream:
        path: /orders              # APPENDED to the alias base path; the request-path
                                   #   remainder after the match key follows it (see
                                   #   "Upstream path" below)
        rewrite_location: false    # default false. true maps an upstream Location pointing
                                   #   inside this route's upstream back onto /api/orders
        connect_timeout_ms: 2000
        read_timeout_ms: 5000
        retry: { max_attempts: 3, idempotent_only: true }
        circuit_breaker: { failures: 5, reset_ms: 30000 }
      rate_limit: { requests_per_second: 100, burst: 20 }   # reserved; feature deferred
----

The manifest's `/auth` -> IdP and `/token` -> IdP mappings are just another endpoint file bound to
the `KEYCLOAK` alias:

[source,yaml]
----
# endpoints/keycloak.yaml
endpoint:
  id: keycloak
  base_url: KEYCLOAK
  auth: { require: none }          # endpoint default: the login flow is necessarily
                                   #   unauthenticated; inherited by both routes
  routes:
    - id: auth
      match: { path_prefix: /auth }
      forward:                     # a POSITIVE-list, chosen deliberately: this route reaches an
                                   #   IdP authorization endpoint, so only the OIDC request
                                   #   params should cross
        query_allow: [client_id, redirect_uri, response_type, scope, state, nonce,
                      code_challenge, code_challenge_method]
      upstream: { path: /realms/main/protocol/openid-connect/auth }
    - id: token
      match: { path_prefix: /token, methods: [POST] }
                                   # no forward block: FORWARD-ALL. Content-Type would cross
                                   #   even under a positive-list -- it is gateway-understood
      upstream: { path: /realms/main/protocol/openid-connect/token }
----

[[_upstream_path]]
=== Upstream path

A proxy route's upstream URI is built from three parts: the resolved alias, the route's
`upstream.path`, and the *remainder* -- the request path with the route's match key stripped. The
alias contributes its scheme, host, port *and base path*; `upstream.path` is *appended* to that base
path, joined on exactly one `/` (decision:
link:../adr/0004-topology-indirection.adoc#_amendment_a2[ADR-0004 Amendment A2]):

----
upstream URI = alias base path + upstream.path + remainder
----

An omitted or blank `upstream.path` keeps the alias base path unchanged. Aliases carry the
environment, routes carry paths: a route never restates the part of the location that belongs to
the deployment.

[cols="2,1,1,2"]
|===
| Alias (`topology.properties`) | `upstream.path` | Request | Upstream URI

| `APP1=https://app1.internal:8443/app1`
| `/orders`
| `/api/orders/42` on `path_prefix: /api/orders`
| `https://app1.internal:8443/app1/orders/42`

| `APP1=https://app1.internal:8443/app1`
| _(omitted)_
| `/api/orders/42` on `path_prefix: /api/orders`
| `https://app1.internal:8443/app1/42`

| `KEYCLOAK=https://kc.internal:8443`
| `/realms/main/protocol/openid-connect/token`
| `/token` on `path_prefix: /token`
| `https://kc.internal:8443/realms/main/protocol/openid-connect/token`
|===

*Migrating a route written for the former replace semantics.* Before Amendment A2 a declared
`upstream.path` *replaced* the alias base path, so a route behind an alias with a base path had to
repeat that base path. Drop the repeated part from the route:

[source,yaml]
----
# topology.properties: UPSTREAM=http://go-httpbin:8080/anything

# before (replace): the route restated the alias base path
upstream: { path: /anything/graphql }     # reached /anything/graphql

# after (append): the route names only its own segment
upstream: { path: /graphql }              # still reaches /anything/graphql
----

A route behind an alias *without* a base path (`GRPC_ECHO=http://grpc-echo:9000`) resolves to the same
URI under both semantics and needs no change.

[[_rewrite_location]]
==== Rewriting upstream `Location` headers (`upstream.rewrite_location`)

An upstream that redirects to its own absolute path -- `Location: /login` from an application
mounted behind `/api/orders` -- sends the browser off the gateway namespace, and an absolute
`Location` naming the upstream's internal host sends it off the gateway altogether. Setting
`upstream.rewrite_location: true` maps such a value back onto the route:

* *Candidates* are a relative path-absolute value (`/orders/login`) and an absolute URI whose scheme,
  host and effective port equal the route's upstream.
* A candidate whose path equals the *effective upstream base path* (alias base path +
  `upstream.path`) or continues it on a segment boundary is rewritten to the route's match key plus
  the remainder, emitted as a *gateway-relative* path, so the browser stays on the gateway origin.
  Query and fragment are kept verbatim.
* Everything else is relayed *unchanged*: a foreign origin, a scheme-relative `//host` value, an
  unparseable value, and a path outside the effective base path.

With the alias `APP1=https://app1.internal:8443/app1` and `upstream.path: /orders` on
`path_prefix: /api/orders`, the effective base path is `/app1/orders`: an upstream
`Location: https://app1.internal:8443/app1/orders/login?next=42` becomes
`/api/orders/login?next=42`, while `Location: https://idp.example.com/auth` passes through untouched.

The key defaults to `false` -- `Location` is relayed exactly as the upstream sent it. It is valid on
`http` and `graphql` routes only; declaring it on a `grpc` or `websocket` route fails the boot, since
neither protocol carries a redirect the gateway could rewrite.

[[_base_url_only_with_proxy_routes]]
=== `base_url` is mandatory only with a proxy route

A route that declares neither an `asset` nor a `redirect` block is a *proxy route*: it reaches the
endpoint's upstream. An endpoint must declare `base_url` *exactly when* it carries at least one proxy
route; an endpoint made only of asset and redirect routes omits it. The rule is enforced at boot, not
by the schema:

* an endpoint with a proxy route and no `base_url` fails the boot
  (`endpoint '<id>' declares proxy route(s) but no base_url`);
* a `base_url` that *is* declared must resolve in the topology even when no route uses it -- a
  declared alias is never silently ignored.

[[_terminal_actions]]
=== Terminal actions

A route carries *exactly one terminal action* -- what the gateway does with a request once it has
passed route selection, the verb gate, the thorough checks and authentication:

[cols="1,1,3"]
|===
| Action | Declared by | What answers the request

| *proxy*
| neither `asset` nor `redirect` (an optional `upstream` block tunes it)
| The endpoint's upstream, reached through the streamed data plane (every example above).

| *asset*
| an `asset` block
| The gateway itself, serving static content (see <<_asset_terminal_action>>).

| *redirect*
| a `redirect` block
| The gateway itself, with a status and a `Location` and no upstream contact (see
  <<_redirect_terminal_action>>).
|===

Declaring two of them on one route fails the boot: a `redirect` block beside an `asset` block, or
beside an `upstream` block, is refused rather than resolved by a silent precedence (decisions:
link:../adr/0014-asset-serving-terminal-action.adoc[ADR-0014] and its
link:../adr/0014-asset-serving-terminal-action.adoc#amendment-a1[Amendment A1]).

[[_asset_terminal_action]]
=== Asset terminal action

An asset route serves static content through an `asset` block instead of proxying. It rides a
`type: asset` anchor: declaring an `asset` block on a route under a `proxy` or `bff` anchor (or on an
unanchored route) fails the boot, and a route under an asset anchor must declare either an `asset` or
a `redirect` block.

The `asset` block selects one of two sources:

[source,yaml]
----
# endpoints/assets.yaml -- ROUTE FRAGMENT: the routes: list of an endpoint file whose anchor
#   is type: asset. The enclosing endpoint: block (id, base_url, anchor, auth) has the same
#   shape as the complete files above -- this fragment on its own is not a valid endpoint file.
routes:
  - id: bundle                       # a local directory / volume mount
    match: { path_prefix: /static/app }
    asset:
      source: directory              # directory | upstream
      directory: /srv/app-bundle     # the configured root; the request sub-path is confined
                                     #   UNDER this root and any escape is a 404. No
                                     #   classpath-embedded resources.
  - id: cdn                          # a secondary origin
    match: { path_prefix: /static/cdn }
    asset:
      source: upstream               # reuses the existing upstream model -- the resolved
      upstream: ASSET_ORIGIN         #   base_url + remainder -- the shared data-plane client and
                                     #   the SSRF controls (scheme allowlist, followRedirects
                                     #   NEVER, bounded size/timeout). No parallel fetch stack.
----

Two cross-cutting rules govern *both* sources:

* *Canonicalize-and-confine, before the source is touched.* The request sub-path is canonicalized
  through cui-http's `URLPathValidationPipeline` (percent-decoding, `..`/dot-segment and
  duplicate-slash collapse, unconditional traversal / `%00` / overlong / backslash rejection),
  then confined to the configured root / synthetic base; any escape is a `404`. No file is opened
  and no upstream is fetched for a rejected path.
* *Auth before source resolution.* The route's effective auth (materialized from its `access`
  axis and auth floor) is enforced at stage 4 *before* the source is resolved, so an unauthorized
  request to an `access: authenticated` asset is rejected `401` and never triggers a directory
  read or an upstream fetch.

Every served response passes through the *gateway-owned response envelope*, so the gateway -- never
the backing directory or upstream -- governs the response metadata: the `Content-Type` is set from
the gateway's own extension map (overriding whatever the source claimed), `X-Content-Type-Options:
nosniff` is always added, any source `Set-Cookie` is stripped, and an `access: authenticated`
asset is forced to `Cache-Control: no-store` even when the source sent `Cache-Control: public`.
Only `GET` and `HEAD` are served; any other verb is rejected `405`.

An operator may *teach* the gateway an extension it does not already map -- but never *restate* one
it does. See link:../configuration.adoc#_asset_defaults[`asset_defaults`] for the add-only block
and the security rationale behind that asymmetry.

[[_asset_index_and_fallback]]
==== Directory index and single-page-application fallback

A `source: directory` asset block may name two files the source answers with when the request does
not address an existing file directly:

[source,yaml]
----
- id: spa
  match: { path_prefix: /static/app }
  asset:
    source: directory
    directory: /srv/app-bundle
    index: index.html                # answers a DIRECTORY address
    fallback: index.html             # answers an unknown EXTENSIONLESS path
----

* *`index`* -- a request addressing a directory (the bare route prefix, a sub-path ending in `/`, or
  a sub-path naming an existing directory) is answered with that file *from the addressed directory*.
  A directory without the file is a `404`. Without `index`, every directory address is a `404`.
* *`fallback`* -- a request whose target does not exist *and whose last path segment carries no `.`
  extension* is answered with that file from the *root* of the directory. This is the client-side
  routing case: `/static/app/orders/42` serves the application shell. A missing file *with* an
  extension -- `/static/app/app.js`, `/static/app/logo.png` -- stays a `404`, so a broken asset
  reference is never masked by an HTML page.

Both files are served through the same canonicalize-and-confine chain as any other asset: the
traversal, symlink and special-file protections are reused, never bypassed, and the `Content-Type`
follows the *served* file's name. Each value must be a single file-name segment -- no `/`, no `\`, no
`..`, no control characters, not empty -- and both keys are refused on a `source: upstream` asset
block; either violation fails the boot.

[[_redirect_terminal_action]]
=== Redirect terminal action

A `redirect` block makes the gateway answer the request itself with a redirect status and a
`Location` header -- no upstream is contacted, no body is sent. The typical use is steering an entry
address without a trailing slash to its slash form, so relative URLs inside the application resolve
under it:

[source,yaml]
----
routes:
  - id: k-beispiel-entry
    match:
      path: /KIDICAP.Gateway/app/K.Beispiel      # EXACT route: this one address only
    redirect:
      location: /KIDICAP.Gateway/app/K.Beispiel/ # written verbatim into Location
      status: 308                                # mandatory: 301 | 302 | 303 | 307 | 308
      keep_query: true                           # default false: append the raw query
      # allow_external: false                    # default false: see "External targets"
  - id: k-beispiel-app                            # the slash form and everything below it
    match:
      path_prefix: /KIDICAP.Gateway/app/K.Beispiel
    # proxy route (or an asset route) serving the application itself
----

Because `/KIDICAP.Gateway/app/K.Beispiel` and `/KIDICAP.Gateway/app/K.Beispiel/` are different
addresses to an exact route (see <<_route_ordering>>), the redirect claims the slash-less entry while
the prefix route keeps serving the slash form and every path below it.

*Choosing the status.* `status` has no default, because permanence must be an explicit choice:

[cols="1,1,3"]
|===
| Status | Method on follow | Use it when

| `301`
| may change to `GET`
| The address moved for good and the old one only ever received `GET`. *Browsers cache it*, often
  indefinitely -- a wrong `301` outlives its configuration.

| `308`
| preserved
| The address moved for good and may receive other methods. *Cached like `301`.* The usual choice for
  a canonical trailing-slash redirect.

| `302`
| may change to `GET`
| The move is temporary and only `GET` matters. Not cached by default.

| `307`
| preserved
| The move is temporary and the method and body must be kept. Not cached by default.

| `303`
| always `GET`
| The client should fetch the target with `GET` regardless of the method it sent (post/redirect/get).
|===

Start with `302` or `307` while an address change is being tried out and switch to `301` / `308` once
it is settled; a permanent status is hard to take back from browser caches.

*`keep_query`.* With `keep_query: true` the raw inbound query string is appended to `location` --
joined with `?`, or with `&` when `location` already carries a query. Nothing else from the request is
copied: there are no request placeholders, and without `keep_query` the query is dropped. A `location`
containing `#` cannot be combined with `keep_query` (a query appended after a fragment never reaches
the server) and fails the boot.

*The context path.* `location` is written into `Location` *verbatim*. It is a raw gateway path written
the same way `match.path_prefix` is written, and the gateway never prefixes it with the application
context path (see link:context-path.adoc[The Context Path]).

*Answered after authentication.* A redirect route runs the same pipeline as any other route up to its
terminal action: route selection, the verb gate, the thorough checks and *authentication* all come
first. Under an anchor or endpoint that requires authentication, an unauthenticated request is
challenged (`401`, or the login redirect on a `require: session` navigation) *before* any `Location` is
disclosed -- the configured target is itself information an anonymous caller does not get. A public
entry redirect declares `auth: { require: none }` like any other public route. The redirect answer
carries the route's resolved security headers (see link:anchors.adoc#_anchors[Anchors]) and any
`Set-Cookie` an earlier stage produced; the route's `forward` block is not consulted, because nothing is
forwarded.

*Where a redirect is allowed.* A `redirect` block is admitted under every anchor type -- `proxy`,
`bff` and `asset` -- and on unanchored routes, since it serves nothing an anchor type governs. It is
refused on a `grpc`, `websocket` or `graphql` route: those clients do not follow an HTTP redirect, so
the route would be dead configuration.

[[_redirect_external_targets]]
==== External targets and the open-redirect review

`location` is checked *once, at boot* -- at request time it is written verbatim, so the boot review is
the only place a target is judged. Without `allow_external`, the value must be a *gateway path*:

[cols="2,3"]
|===
| Refused spelling | Why a client reads it as another origin, or as a different path

| `//evil.example/x`
| A leading `//` is scheme-relative: it names another host.

| `/\evil.example`, `\\evil.example`
| Browsers read a backslash as `/`.

| `/%2F%2Fevil.example`, `/%5cevil.example`
| A percent-encoded `/` or `\` (either case) is decoded by intermediaries.

| `/a/../b`, `/a/./b`, `/a/%2e%2e/b`
| A dot-segment is normalized away by clients.

| a value with whitespace or a control character
| A CR/LF would forge a response header; whitespace is never a valid `Location`.

| `https://elsewhere.example/`, `javascript:...`
| Not a gateway path -- only admitted under `allow_external` (below), and `javascript:` never.
|===

`allow_external: true` additionally admits an *absolute `http` or `https` URI with a non-empty host
and no user-info* (`https://user@evil.example` disguises the real host and stays refused). Every other
scheme stays refused. Opting in is legitimate -- a moved site, a hand-off to another application -- but
it is never silent: the boot logs `WARN ApiSheriff-125` naming the route id (never the target), see
link:../LogMessages.adoc[Log Messages]. A refused `location` fails the boot with a message that echoes
the value in escaped form, so a hostile value cannot forge log lines.

[[_route_ordering]]
=== Route ordering

The routes of *all* endpoint files are merged into a single immutable route table at startup. A route
declares exactly one path matcher:

* *`match.path_prefix`* -- a *prefix route*: it matches the prefix itself and every path continuing it
  on a segment boundary (`/api` matches `/api/orders`, never `/apifoo`).
* *`match.path`* -- an *exact route*: it matches exactly one address, by an un-normalized string
  comparison against the canonical request path. The trailing slash is significant: `/a` and `/a/` are
  two different addresses, and an exact `path: /a` matches neither `/a/` nor `/a/b`.

Declaring both, or neither, fails the boot. Matching is then a two-step rule:

. *Candidates* are the routes whose *entire* matcher set holds for the request (path AND methods AND
  host AND headers). A route whose path matches but whose `host` or `methods` do not is simply not a
  candidate -- other routes are still considered.
. Among the candidates, *every exact route precedes every prefix route*; exact routes are ordered by
  path length, longest first, and prefix routes by the *longest* `path_prefix`. The first candidate in
  that order wins.

So for the *same address* an exact route always beats a prefix route, and an exact route can sit
inside a prefix route's namespace to override that one address (the redirect example above does
exactly that) while the prefix route keeps serving every other path.

So that the winner is never ambiguous, any two routes with an *identical* `path_prefix`, or any two
exact routes with an *identical* `path` -- in the same file or across files -- must be *statically
disjoint*. Prefixes are compared normalized (`/api` and `/api/` are the same prefix); exact paths are
compared verbatim (`/a` and `/a/` are different paths and never collide). An exact route and a prefix
route never collide, even for the same string, because the exact route is selected first by design.
Two same-key routes are disjoint when one of these holds:

* *both* declare `host`, with different values (a route that omits `host` matches every host,
  so a declared-host route paired with a host-less route at the same prefix is *not* disjoint
  and is rejected -- there is deliberately no "specific host + any-host fallback at the same
  prefix" pattern; give the fallback a different prefix or declare hosts on both);
* their `methods` sets do not overlap (an omitted `methods` means all methods and overlaps
  everything); or
* both declare a matcher on the *same header name* that cannot both hold -- either different
  exact values (e.g. `X-Tenant: a` vs `X-Tenant: b`), or *opposite presence assertions*
  (`present: true` on one and `present: false` on the other, which no single request satisfies
  at once). A lone `present: true`, with no opposing `present: false` at the same prefix and
  header, establishes nothing.

Any same-key pair that fails all three tests is rejected at boot; precedence never depends
on file-system or declaration order. This keeps the canonical virtual-hosting case
expressible: `/api` on `a.example.com` -> `APP_A` and `/api` on `b.example.com` -> `APP_B`
live in two endpoint files and are disjoint by host.

A request that matches no route is rejected with `404`.

*Reserved gateway paths.* The gateway's own OIDC endpoints are matched *exactly, before the
route table*, but only on the *OIDC host* (the host of `oidc.redirect_uri`). The keys that
register them, and the field-level contract for each, are owned by
link:../configuration.adoc#_oidc[`oidc`] -- the list below names which of those keys carve out a
path, not what the keys mean. Up to *six* paths are carved out:

. the `oidc.redirect_uri` path -- the auth-code *callback*, reached by a top-level `GET` with
  `code` and `state` in the query string (`response_mode=query`) and carrying no request body;
. `oidc.logout.path` -- RP-initiated *logout*;
. its return path (`oidc.logout.post_logout_redirect_uri`) -- the *logout-return* leg;
. `oidc.logout.backchannel_path` -- the *back-channel logout* receiver (`mode: server` only);
. `oidc.user_info.path` -- the session/*user-info* endpoint serving the curated identity view;
. `oidc.login.path` -- the gateway-owned *login-initiation* entry point that starts a login.

Each is registered only when its configuration key is present, so a deployment that omits
`oidc.user_info` or `oidc.login` carves out fewer than six. A proxy route such as
`path_prefix: /auth` therefore never swallows the `/auth/callback` callback, while other virtual
hosts (e.g. machine-to-machine API hosts with `bearer` routes) keep their full path namespace.
Routes remain free to use neighbouring prefixes; only the exact reserved paths on that one host
are carved out.

[[_defaults_for_omitted_blocks]]
=== Defaults for omitted blocks

What an omitted block resolves to, and where the resolution comes from. Most rows are
fail-closed -- an omitted `auth` inherits a declared posture rather than inventing one, and an
omitted `security_filter` lands on `strict`. The `forward` row is the deliberate exception,
and is explained in its own cell:

[cols="1,3"]
|===
| Omitted block | Effect

| `auth` (route level)
| The route inherits the *endpoint's* `auth` block (or, when the endpoint omits one, its
  *anchor's* -- see link:anchors.adoc#_anchors[Anchors]). The authentication posture is defined per
  endpoint file -- `endpoint.auth` is *mandatory unless the endpoint's anchor declares an
  `auth` block*, and anonymous access is `auth: { require: none }`, written out; there is no
  implicit default. A route-level `auth` block *replaces* the endpoint/anchor default
  wholesale (no field merging). An endpoint file with neither its own nor an anchor-provided
  `auth` block fails the boot.

| `enabled` (endpoint level)
| The endpoint is *active* (`enabled: true`). Set `false` -- or the env override
  `ENDPOINT_<ID>_ENABLED=false` -- to make the endpoint inert (see
  link:../configuration.adoc#_endpoint_identity[`endpoint`]).

| `allowed_methods` (endpoint level)
| The *anchor's* `allowed_methods` applies if the route's anchor declares one, else the
  *global* `gateway.allowed_methods` (which itself defaults to the standard verb set when
  omitted). A *declared* endpoint list is the first choice and *replaces* the anchor/global list
  wholesale for that endpoint -- the omission above is what hands the choice on. No
  inheritance/merge at any step -- see
  link:../configuration.adoc#_allowed_methods[`allowed_methods`].

| `security_filter`
| The block is resolved by *wholesale replacement* down the chain
  `route` -> `anchor` -> `security_defaults`, never merged: the first level that declares a
  `security_filter` block supplies it entirely. (The endpoint level carries no `security_filter`
  block and is not part of this chain.) A route declaring a block that omits `profile` falls back to
  `security_defaults.profile`, not to its anchor's profile; an omitted `security_defaults` block --
  or one omitting `profile` -- resolves to `strict`. The resolved profile's preset supplies the
  limits, and any explicit limit keys in the winning block override them individually.

| `forward`
| *Forward-all* on both dimensions: every client request header and query parameter crosses,
  minus the gateway-owned request-direction never-forward set (`Authorization`, `Cookie`, the
  hop-by-hop and connection-specific names, `Content-Length`, `Host`, `Origin`, `Referer`,
  `Date`), which no configuration can re-admit apart from the single `Authorization` carve-out.
  The *automatic* injections apply as always: the mediated `Authorization: Bearer` on session
  routes and the regenerated forwarding-header set. A route that wants a stricter posture
  declares it -- see link:../configuration.adoc#_forward[`forward`]. Note this is the one
  omitted-block default that
  is *permissive*: it filters within a route the request is already authorised for, so the
  deny-by-default guarantee is unaffected (it lives at route matching).

| `rate_limit`
| No rate limiting (the feature is out of scope regardless; the field is reserved).
|===

[[_edge_hardening_defaults]]
=== Edge hardening (transport) defaults

The public data-plane HTTP listener is bounded on two axes, and they are governed differently.

The *transport bounds* — the framing limits and the drain window — are fixed secure defaults applied
in code (`EdgeHardeningOptions`) and are not operator-configurable. They fail fast on abusive framing
before a request is admitted to the pipeline. These values are recorded here doc-first: they are the
contract the edge-hardening code implements, and any change to a constant must be reflected in this
table.

The *admission budgets* — how many requests, and how many WebSocket relays, may be in flight at once
— are operator-facing and configurable through the optional
link:../configuration.adoc#_edge_hardening[`edge_hardening`] block in `gateway.yaml`. Their sizing
depends on the
deployment's traffic shape rather than on protocol safety, which is why they are the two bounds the
operator owns. Omitting the block, or either key, resolves to the defaults in the table below, so a
deployment that never writes it keeps the behaviour shown here.

[cols="2,1,3"]
|===
| Bound | Default | Effect

| Maximum request header block
| 16 KiB
| An over-large header block is rejected by the Vert.x codec before the request reaches the pipeline.

| Maximum HTTP/1.x request-line length
| 8 KiB
| An over-long `METHOD SP request-target SP HTTP/x` line is rejected at the transport.

| Maximum chunked-transfer chunk size
| 16 KiB
| An over-large single chunk is rejected at the transport.

| Reserved-path request body
| 16 KiB
| The cumulative body the edge buffers for a gateway-terminated reserved `POST` path -- in practice
  the back-channel logout receiver, which is reached before authentication and never meets a
  per-route body cap. A larger body is rejected `413`. Defined as the header-block bound rather than
  as a second constant.

| Idle-connection reap
| 60 s
| An idle connection is closed after this window, so a slow-loris / h2 abuse load cannot pin
  connection slots.

| Admission cap (in-flight requests) +
  [`edge_hardening.admission_cap`]
| 2048
| Requests beyond the cap are rejected `503` *before* a virtual thread is dispatched, so a flood
  cannot spawn unbounded virtual threads. Operator-configurable; minimum 1.

| WebSocket relay cap (established relays) +
  [`edge_hardening.websocket_relay_cap`]
| 512 +
  (a quarter of the effective `admission_cap`)
| A sub-budget acquired *in addition to* the general admission permit, never instead of it. An
  established relay holds both permits for the connection's whole lifetime rather than for one
  round-trip, so without this second bound a modest number of long-lived relays would consume the
  general pool and starve ordinary HTTP traffic. An upgrade beyond the cap is refused `503` and
  releases the general permit on the way out. Operator-configurable; minimum 1, and must not exceed
  `admission_cap`. Omitting it takes a quarter of the *effective* `admission_cap` rather than a fixed
  `512`, so the three-quarters-for-HTTP reservation holds at every admission cap.

| Graceful-drain timeout
| 25 s
| The bounded wait for in-flight requests to complete on `SIGTERM`; kept below the Quarkus default
  shutdown timeout so the drain completes within the shutdown window rather than being cut short.
|===
