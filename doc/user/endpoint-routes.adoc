= API Sheriff -- Endpoint Route Configuration (`endpoints/*.yaml`)

:source-highlighter: highlight.js

How to author the `endpoints/*.yaml` files: the route schema, the three terminal actions (proxy,
asset, redirect), exact and prefix routes and their ordering, how `upstream.path` builds the upstream
URI, what an omitted block resolves to, and the transport bounds at the edge. The field-level
contract for every key mentioned here lives in the
link:../configuration.adoc[Configuration Reference]; anchors are covered in
link:anchors.adoc[Anchors].

== Endpoint Configuration Files (`endpoints/*.yaml`)

One file per endpoint (service / host / app) or logical group. The file lists its routes and, when
at least one of them proxies, binds to a single `base_url` alias. *No concrete upstream host appears
here* -- the `base_url` alias is resolved from the topology at startup. An endpoint whose routes are
all `asset` or `redirect` routes contacts no endpoint upstream and omits `base_url` (see
<<_base_url_only_with_proxy_routes>>).

The endpoint files are validated at boot together with `gateway.yaml` and `topology.properties`:
a schema violation, an unresolvable alias or a broken cross-file rule -- a duplicate id, a
route outside its anchor -- refuses the start. The same validation runs offline,
before any gateway boots the files: see link:offline-config-validation.adoc[Offline Configuration
Validation].

[source,yaml]
----
# endpoints/app1.yaml
endpoint:
  id: app1                         # unique endpoint name (mandatory); a duplicate id across
                                   #   endpoint files fails the boot
  enabled: ${ENDPOINT_APP1_ENABLED:-true}   # default true. false => this endpoint is inert:
                                   #   its routes are not added to the table and its base_url
                                   #   alias need not resolve. The ${VAR:-default} placeholder
                                   #   makes the env override visible in-file (ADR-0004 A1);
                                   #   a plain literal (enabled: true) is equally valid
  base_url: APP1                   # alias; resolved from topology.properties / env. Mandatory
                                   #   because this file carries a proxy route; an endpoint of
                                   #   asset and redirect routes only omits it
  anchor: api                      # anchor membership (see "Anchors" in anchors.adoc): default
                                   #   for every route in this file, overridable per route; the
                                   #   route paths must lie inside the anchor's path_prefix.
                                   #   Mandatory for routes inside a configured anchor namespace
  auth:                            # default auth posture for every route in this file; a route
    require: bearer                #   may override it (below). MANDATORY unless the endpoint's
                                   #   anchor declares an auth block (see "Anchors" in
                                   #   anchors.adoc)
  scopes: [orders.read]            # optional, OUTSIDE auth, ADDITIVE: every route of this
                                   #   endpoint needs oidc.scopes ∪ these. A bearer route
                                   #   answers 403 insufficient_scope to a token missing one;
                                   #   a session route requests them at login and holds every
                                   #   live session to them (see "Endpoint scopes" below).
                                   #   Refused at boot when every route of the endpoint
                                   #   resolves require: none
  allowed_methods: [GET, POST]   # optional per-endpoint verb allowlist; nearest declared
                                   #   scope wins, so it REPLACES the anchor/global list
                                   #   wholesale for this endpoint. Omit => the anchor's list,
                                   #   else the global one (see "Policy-block resolution" in
                                   #   anchors.adoc)
  security_filter:                 # optional endpoint default for every route that declares no
    profile: strict                #   security_filter of its own; REPLACES the anchor's block
    max_body_bytes: 1048576        #   wholesale (boot WARN ApiSheriff-101 when the anchor
                                   #   declares one). A route block replaces this one wholesale
  forward:                         # optional endpoint default for every route that declares no
    headers_deny: [x-internal]     #   forward block of its own; a route block REPLACES it
                                   #   wholesale -- no list of it survives under the route block
  routes:                          # merged into one table across all endpoint files
                                   #   (see "Route ordering"); no match => 404
    - id: orders-api
      protocol: http               # http | grpc | graphql | websocket (see "protocol" in
                                   #   ../configuration.adoc)
      match:
        path_prefix: /api/orders   # prefix route; `path: /api/orders` would declare an EXACT
                                   #   route instead -- exactly one of the two (see "Route ordering")
        methods: [GET, POST]
        host: ${GATEWAY_PUBLIC_HOST:-api.example.com}
                                   # matches the INBOUND request's Host header -- the gateway's
                                   #   own public vhost, not an upstream location. It is
                                   #   therefore environment-specific: express it as a ${VAR}
                                   #   placeholder rather than a literal
        headers:                   # optional header matchers. The name is lower-cased
                                   #   (Locale.ROOT) at boot, so ASCII names match
                                   #   case-insensitively; present: true requires the
                                   #   header, present: false requires its ABSENCE; value
                                   #   requires that exact, case-sensitive value. The fields
                                   #   of one matcher AND together; present: false together
                                   #   with value can never match and fails the boot, and so
                                   #   do two matchers of one route that name the same
                                   #   header and can never both hold (see "Route ordering")
          - { name: X-Tenant, present: true }
      auth:                        # route-level override of endpoint.auth (whole block
        require: bearer            #   replaces, no merge); scopes are NOT part of auth, so
                                   #   overriding auth never drops endpoint.scopes
        token_relay: true          # default true; governs the SESSION branch -- a require:
                                   #   session route, including the session branch of a
                                   #   session_fallback route. false keeps the session's
                                   #   access token away from this upstream (no Authorization
                                   #   header is relayed) while still requiring the login and
                                   #   the route's scopes.
                                   #   Refused at boot together with an effective
                                   #   forward.headers_allow (endpoint- or route-level)
                                   #   naming Authorization
        # session_fallback: false  # default false; valid only with require: bearer and a
                                   #   gateway oidc block. true adds a session branch: a
                                   #   request WITHOUT Authorization takes the SESSION branch
                                   #   (login, CSRF, mediated token), one WITH it the BEARER
                                   #   branch. See "auth" in ../configuration.adoc
      security_filter:             # "basic filtering -- NOT a WAF"; the field-level contract is
                                   #   "security_filter" in ../configuration.adoc. REPLACES the
                                   #   endpoint block above wholesale for this route: a limit
                                   #   not restated here takes the preset, not the endpoint value
        profile: strict
        allowed_paths: ["/api/orders", "/api/orders/{id}"]   # quoted: {} is YAML syntax
        max_header_count: 50
        max_header_value_length: 8192   # characters (cui-http unit)
        max_query_params: 20
        max_param_value_length: 2048    # characters
        max_body_bytes: 1048576
      forward:                     # OPTIONAL. REPLACES the endpoint block above wholesale, so
                                   #   its headers_deny does NOT apply to this route. With no
                                   #   block here or at the endpoint: FORWARD-ALL, the baseline.
                                   #   Per dimension, declaring *_allow selects a positive-list
                                   #   and *_deny a negative-list; declaring BOTH for one
                                   #   dimension is REFUSED AT BOOT at either scope
        headers_allow: [x-tenant]  # positive-list. The gateway-understood protocol headers
                                   #   (Accept, Accept-Encoding, Accept-Language, Content-Type,
                                   #   Range, If-Range, If-Match, If-Unmodified-Since, + the
                                   #   two 304 validators when not_modified is on) cross
                                   #   WITHOUT being listed -- do not enumerate HTTP mechanics here
        query_deny: [debug]        # negative-list on the OTHER dimension: every other client
                                   #   parameter crosses. The two dimensions are independent
        set_headers:               # additional STATIC gateway-set headers only. Injected
          x-gateway: api-sheriff   #   automatically, never configured: the regenerated
                                   #   forwarding-header set (always) and the mediated
                                   #   Authorization: Bearer -- on a session route and the
                                   #   session branch of a session_fallback route only when
                                   #   the effective token_relay is true; on the bearer branch
                                   #   of a session_fallback route always (the validated client
                                   #   token); never on a plain require: bearer route.
                                   #   set_headers WINS over a client header of the same name
                                   #   (case-insensitively) -- operator config beats client input
      # keep_identity_headers: true  # OPTIONAL, route only. Absent => the upstream's Server and
                                   #   X-Powered-By are stripped from its responses; true keeps
                                   #   them (see "Keeping an upstream's identity headers" below)
      upstream:
        path: /orders              # APPENDED to the alias base path; the request-path
                                   #   remainder after the match key follows it (see
                                   #   "Upstream path" below)
        rewrite_location: false    # default false. true maps an upstream Location pointing
                                   #   inside this route's upstream back onto /api/orders
        connect_timeout_ms: 2000   # INERT today: parsed, read by nothing -- every
        read_timeout_ms: 5000      #   dispatch runs under the guard's fixed 30 s timeout
        retry: { max_attempts: 3, idempotent_only: true }
                                   # INERT today: only retry.enabled acts (two retries,
                                   #   100 ms apart); max_attempts and idempotent_only are
                                   #   read by nothing. All four keys are open decisions --
                                   #   see ADR-0064 "What this decision does not settle"
                                   # no circuit_breaker key: the breaker is the gateway's fixed
                                   #   policy (20-call window, ratio 0.5, 5 s open) and a route
                                   #   declares none -- the key is refused at boot (ADR-0064)
      rate_limit: { requests_per_second: 100, burst: 20 }
                                   # planned, not implemented, no 429 today: parsed,
                                   #   enforced by nothing, and named at boot by the
                                   #   WARN ApiSheriff-140
----

The manifest's `/auth` -> IdP and `/token` -> IdP mappings are just another endpoint file bound to
the `KEYCLOAK` alias:

[source,yaml]
----
# endpoints/keycloak.yaml
endpoint:
  id: keycloak
  base_url: KEYCLOAK
  auth: { require: none }          # endpoint default: the login flow is necessarily
                                   #   unauthenticated; inherited by both routes
  routes:
    - id: auth
      match: { path_prefix: /auth }
      forward:                     # a POSITIVE-list, chosen deliberately: this route reaches an
                                   #   IdP authorization endpoint. The gateway's login redirect
                                   #   carries two parameters only -- the authorization request
                                   #   itself is pushed to the IdP over the back channel -- so
                                   #   only those two should cross
        query_allow: [client_id, request_uri]
      upstream: { path: /realms/main/protocol/openid-connect/auth }
    - id: token
      match: { path_prefix: /token, methods: [POST] }
                                   # no forward block: FORWARD-ALL. Content-Type would cross
                                   #   even under a positive-list -- it is gateway-understood
      upstream: { path: /realms/main/protocol/openid-connect/token }
----

[[_upstream_path]]
=== Upstream path

A proxy route's upstream URI is built from three parts: the resolved alias, the route's
`upstream.path`, and the *remainder* -- the request path with the route's match key stripped. The
alias contributes its scheme, host, port *and base path*; `upstream.path` is *appended* to that base
path, joined on exactly one `/` (decision:
link:../adr/0004-topology-indirection.adoc#_amendment_a2[ADR-0004 Amendment A2]):

----
upstream URI = alias base path + upstream.path + remainder
----

An omitted or blank `upstream.path` keeps the alias base path unchanged. Aliases carry the
environment, routes carry paths: a route never restates the part of the location that belongs to
the deployment.

[cols="2,1,1,2"]
|===
| Alias (`topology.properties`) | `upstream.path` | Request | Upstream URI

| `APP1=https://app1.internal:8443/app1`
| `/orders`
| `/api/orders/42` on `path_prefix: /api/orders`
| `https://app1.internal:8443/app1/orders/42`

| `APP1=https://app1.internal:8443/app1`
| _(omitted)_
| `/api/orders/42` on `path_prefix: /api/orders`
| `https://app1.internal:8443/app1/42`

| `KEYCLOAK=https://kc.internal:8443`
| `/realms/main/protocol/openid-connect/token`
| `/token` on `path_prefix: /token`
| `https://kc.internal:8443/realms/main/protocol/openid-connect/token`
|===

*Migrating a route written for the former replace semantics.* Before Amendment A2 a declared
`upstream.path` *replaced* the alias base path, so a route behind an alias with a base path had to
repeat that base path. Drop the repeated part from the route:

[source,yaml]
----
# topology.properties: UPSTREAM=http://go-httpbin:8080/anything

# before (replace): the route restated the alias base path
upstream: { path: /anything/graphql }     # reached /anything/graphql

# after (append): the route names only its own segment
upstream: { path: /graphql }              # still reaches /anything/graphql
----

A route behind an alias *without* a base path (`GRPC_ECHO=http://grpc-echo:9000`) resolves to the same
URI under both semantics and needs no change.

[[_rewrite_location]]
==== Rewriting upstream `Location` headers (`upstream.rewrite_location`)

An upstream that redirects to its own absolute path -- `Location: /login` from an application
mounted behind `/api/orders` -- sends the browser off the gateway namespace, and an absolute
`Location` naming the upstream's internal host sends it off the gateway altogether. Setting
`upstream.rewrite_location: true` maps such a value back onto the route:

* *Candidates* are a relative path-absolute value (`/orders/login`) and an absolute URI whose scheme,
  host and effective port equal the route's upstream.
* A candidate whose path equals the *effective upstream base path* (alias base path +
  `upstream.path`) or continues it on a segment boundary is rewritten to the route's match key plus
  the remainder, emitted as a *gateway-relative* path, so the browser stays on the gateway origin.
  Query and fragment are kept verbatim.
* On an *exact* route (`match.path`) the rewrite only happens when the mapping is *equal to* the match
  key. An exact route answers one address and nothing below it (see <<_route_ordering>>), so a mapping
  below the match key would name a path this gateway answers with `404`; such a candidate is relayed
  unchanged instead. A prefix route is unaffected -- it serves the whole subtree, so every mapping
  under its match key is routable.
* Everything else is relayed *unchanged*: a foreign origin, a scheme-relative `//host` value, an
  unparseable value, a path outside the effective base path, a path carrying a `.` or `..`
  segment in either its literal or its percent-encoded spelling (`/app1/orders/../login`,
  `/app1/orders/%2e%2e/login`), a path carrying an *ambiguous separator* -- a backslash, or a
  percent-encoded `/` or `\` (`%2F`, `%5C`, either case) -- and a path carrying a *double-encoded or
  malformed escape*: `%252F`, `%252e`, a null byte, an overlong UTF-8 sequence, or a path longer than
  1024 characters. The base-path test is made on the path as
  received, so any of those constructs would survive into the mapping and the browser would resolve it
  *outside* the match key -- the same reason a `redirect` target may not carry one (see
  <<_redirect_external_targets>>). The refused set is *literally* the one the boot review applies to a
  configured `redirect` target -- one shared implementation, not two lists kept in step -- so the two
  cannot disagree about which paths are dangerous.
* The ambiguous-separator refusal also covers the one case where the rewrite would *create* a
  cross-origin redirect out of a value that did not carry one. An absolute URI binds its authority
  before its path, so `Location: https://app1.internal:8443/%5Cattacker.com` keeps the browser on the
  upstream; the gateway-relative mapping `/%5Cattacker.com` does not, and a client that decodes before
  resolving reads `/\attacker.com`, which the WHATWG URL Standard parses as `//attacker.com` -- a
  foreign origin. A percent-encoded `/` is the same class from the other side: it hides a `..`
  traversal from the dot-segment test, which splits on the literal `/` only.
* The double-encoded and malformed-escape classes come from cui-http's `URL_PATH` validation
  pipeline, the same library the inbound request filter uses. It is consulted only for *whether it
  rejected* the path; the canonical value it returns is discarded, because the `Location` is emitted
  to the browser and a confinement proved against a normalised string the browser never sees would
  bound nothing. That is also why the dot-segment and encoded-separator refusals above are not left to
  the library: it *normalises* those spellings away -- `/a/x%2fy` becomes `/a/x/y`, `/a/./b` becomes
  `/a/b`, `/%5Cattacker.com` becomes `/\attacker.com` -- rather than rejecting them.
* The query and fragment are *not* covered by that refusal: they are carried verbatim, and a separator
  after the `?` or `#` cannot form an authority, so `Location: /app1/orders/login?next=%2Fhome` still
  maps to `/api/orders/login?next=%2Fhome`.

With the alias `APP1=https://app1.internal:8443/app1` and `upstream.path: /orders` on
`path_prefix: /api/orders`, the effective base path is `/app1/orders`: an upstream
`Location: https://app1.internal:8443/app1/orders/login?next=42` becomes
`/api/orders/login?next=42`, while `Location: https://idp.example.com/auth` passes through untouched.

The key defaults to `false` -- `Location` is relayed exactly as the upstream sent it. It is valid on
`http` and `graphql` routes only; declaring it on a `grpc` or `websocket` route fails the boot, since
neither protocol carries a redirect the gateway could rewrite.

[[_keep_identity_headers]]
=== Keeping an upstream's identity headers (`keep_identity_headers`)

By default the gateway removes the upstream's `Server` and `X-Powered-By` headers -- the two
standard software banners -- before a response reaches the client. Only these two are removed: any
other header an upstream sets still reaches the client, so an upstream that discloses its software
elsewhere (a framework header such as `X-AspNet-Version`, or its body) must be configured not to. The strip applies to proxied HTTP responses, to gRPC leading headers and trailers, and to an
asset route with `source: upstream`. The headers are dropped, not replaced with a neutral value.

Set `keep_identity_headers: true` on a route only when a client of that upstream depends on its
banner -- for example a monitoring probe or a legacy client that branches on the `Server` value:

[source,yaml]
----
- id: legacy-portal
  match: { path_prefix: /legacy }
  keep_identity_headers: true      # this route only; every other route keeps the default strip
  upstream: { path: /portal }
----

* *Default.* Leave the key out. An absent key strips, and so does `false`.
* *Per route only.* There is no endpoint, anchor or gateway form: the exception is scoped to the one
  upstream that needs it.
* *Refused where it cannot act.* A `redirect` route, an asset route with `source: directory` and a
  `protocol: websocket` route relay no upstream response header, so declaring the key there -- with
  either value -- fails the boot.

The field reference is link:../configuration.adoc#_keep_identity_headers[`keep_identity_headers`].
Removing the banner does not hide the TLS and HTTP/2 fingerprint of the gateway itself; see
link:tls-edge.adoc#_tls_and_http2_fingerprints[TLS and HTTP/2 fingerprints].

[[_base_url_only_with_proxy_routes]]
=== `base_url` is mandatory only with a proxy route

A route that declares neither an `asset` nor a `redirect` block is a *proxy route*: it reaches the
endpoint's upstream. An endpoint must declare `base_url` *exactly when* it carries at least one proxy
route; an endpoint made only of asset and redirect routes omits it. The rule is enforced at boot, not
by the schema, and only over *enabled* endpoints -- validation and topology resolution are both
handed the enabled set, so a disabled endpoint is outside both bullets below (see
link:../configuration.adoc#_endpoint_identity[`enabled`]):

* an *enabled* endpoint with a proxy route and no `base_url` fails the boot
  (`endpoint '<id>' declares proxy route(s) but no base_url`);
* a `base_url` that *is* declared by an *enabled* endpoint must resolve in the topology even when no
  route uses it -- a declared alias is never silently ignored. A disabled endpoint may keep a
  `base_url` naming an alias the environment does not define, which is what lets a config set ship an
  endpoint whose backend is absent here and switch it off.

[[_terminal_actions]]
=== Terminal actions

A route carries *exactly one terminal action* -- what the gateway does with a request once it has
passed route selection, the verb gate, the thorough checks and authentication:

[cols="1,1,3"]
|===
| Action | Declared by | What answers the request

| *proxy*
| neither `asset` nor `redirect` (an optional `upstream` block tunes it)
| The endpoint's upstream, reached through the streamed data plane (every example above).

| *asset*
| an `asset` block
| The gateway itself, serving static content (see <<_asset_terminal_action>>).

| *redirect*
| a `redirect` block
| The gateway itself, with a status and a `Location` and no upstream contact (see
  <<_redirect_terminal_action>>).
|===

Declaring two of them on one route fails the boot: a `redirect` block beside an `asset` block, or
beside an `upstream` block, is refused rather than resolved by a silent precedence (decisions:
link:../adr/0014-asset-serving-terminal-action.adoc[ADR-0014] and its
link:../adr/0014-asset-serving-terminal-action.adoc#amendment-a1[Amendment A1]).

[[_asset_terminal_action]]
=== Asset terminal action

An asset route serves static content through an `asset` block instead of proxying. It rides a
`type: asset` anchor: declaring an `asset` block on a route under a `proxy` or `bff` anchor (or on an
unanchored route) fails the boot, and a route under an asset anchor must declare either an `asset` or
a `redirect` block.

The `asset` block selects one of two sources:

[source,yaml]
----
# endpoints/assets.yaml -- ROUTE FRAGMENT: the routes: list of an endpoint file whose anchor
#   is type: asset. The enclosing endpoint: block (id, base_url, anchor, auth) has the same
#   shape as the complete files above -- this fragment on its own is not a valid endpoint file.
routes:
  - id: bundle                       # a local directory / volume mount
    match: { path_prefix: /static/app }
    asset:
      source: directory              # directory | upstream
      directory: /srv/app-bundle     # the configured root; the request sub-path is confined
                                     #   UNDER this root and any escape is a 404. No
                                     #   classpath-embedded resources.
  - id: cdn                          # a secondary origin
    match: { path_prefix: /static/cdn }
    asset:
      source: upstream               # reuses the existing upstream model -- the resolved
      upstream: ASSET_ORIGIN         #   base_url + remainder -- the shared data-plane client and
                                     #   the SSRF controls (scheme allowlist, followRedirects
                                     #   NEVER, bounded size/timeout). No parallel fetch stack.
----

Two cross-cutting rules govern *both* sources:

* *Canonicalize-and-confine, before the source is touched.* The request sub-path is canonicalized
  through cui-http's `URLPathValidationPipeline` (percent-decoding, `..`/dot-segment and
  duplicate-slash collapse, unconditional traversal / `%00` / overlong / backslash rejection),
  then confined to the configured root / synthetic base; any escape is a `404`. No file is opened
  and no upstream is fetched for a rejected path.
* *Auth before source resolution.* The route's effective auth (materialized from its `access`
  axis and auth floor) is enforced at stage 4 *before* the source is resolved, so an unauthorized
  request to an `access: authenticated` asset is rejected and never triggers a directory read or an
  upstream fetch. On a bearer route the caller sees the unrouted `404` rather than a `401` (see
  <<_uniform_not_found_operator_note>>).

Every served response passes through the *gateway-owned response envelope*, so the gateway -- never
the backing directory or upstream -- governs the response metadata: the `Content-Type` is set from
the gateway's own extension map (overriding whatever the source claimed), `X-Content-Type-Options:
nosniff` is always added, any source `Set-Cookie` is stripped, and an `access: authenticated`
asset is forced to `Cache-Control: no-store` even when the source sent `Cache-Control: public`.
Only `GET` and `HEAD` are served; any other verb that the route's `allowed_methods` admits is
rejected `405` by the asset action. A verb outside `allowed_methods` is refused earlier, by the verb
gate, and an unauthenticated caller sees that refusal as the unrouted `404` (see
<<_uniform_not_found_operator_note>>).

An operator may *teach* the gateway an extension it does not already map -- but never *restate* one
it does. See link:../configuration.adoc#_asset_defaults[`asset_defaults`] for the add-only block
and the security rationale behind that asymmetry.

[[_asset_index_and_fallback]]
==== Directory index and single-page-application fallback

A `source: directory` asset block may name two files the source answers with when the request does
not address an existing file directly:

[source,yaml]
----
- id: spa
  match: { path_prefix: /static/app }
  asset:
    source: directory
    directory: /srv/app-bundle
    index: index.html                # answers a DIRECTORY address
    fallback: index.html             # answers an unknown EXTENSIONLESS path
----

* *`index`* -- a request addressing a directory (the bare route prefix, a sub-path ending in `/`, or
  a sub-path naming an existing directory) is answered with that file *from the addressed directory*.
  A directory without the file is a `404`. Without `index`, every directory address is a `404`.
* *`fallback`* -- a request whose target does not exist *and whose last path segment carries no `.`
  extension* is answered with that file from the *root* of the directory. This is the client-side
  routing case: `/static/app/orders/42` serves the application shell. A missing file *with* an
  extension -- `/static/app/app.js`, `/static/app/logo.png` -- stays a `404`, so a broken asset
  reference is never masked by an HTML page.

Both files are served through the same canonicalize-and-confine chain as any other asset: the
traversal, symlink and special-file protections are reused, never bypassed, and the `Content-Type`
follows the *served* file's name. Each value must be a single file-name segment -- no `/`, no `\`, no
`..`, no control characters, not empty -- and both keys are refused on a `source: upstream` asset
block; either violation fails the boot.

[[_redirect_terminal_action]]
=== Redirect terminal action

A `redirect` block makes the gateway answer the request itself with a redirect status and a
`Location` header -- no upstream is contacted, no body is sent. The typical use is steering an entry
address without a trailing slash to its slash form, so relative URLs inside the application resolve
under it:

[source,yaml]
----
routes:
  - id: k-beispiel-entry
    match:
      path: /KIDICAP.Gateway/app/K.Beispiel      # EXACT route: this one address only
    redirect:
      location: /KIDICAP.Gateway/app/K.Beispiel/ # written verbatim into Location
      status: 308                                # mandatory: 301 | 302 | 303 | 307 | 308
      keep_query: true                           # default false: append the raw query (same-origin only)
      # allow_external: false                    # default false, and never with keep_query: see
      #                                          # "External targets"
  - id: k-beispiel-app                            # the slash form and everything below it
    match:
      path_prefix: /KIDICAP.Gateway/app/K.Beispiel
    # proxy route (or an asset route) serving the application itself
----

Because `/KIDICAP.Gateway/app/K.Beispiel` and `/KIDICAP.Gateway/app/K.Beispiel/` are different
addresses to an exact route (see <<_route_ordering>>), the redirect claims the slash-less entry while
the prefix route keeps serving the slash form and every path below it.

*Choosing the status.* `status` has no default, because permanence must be an explicit choice:

[cols="1,1,3"]
|===
| Status | Method on follow | Use it when

| `301`
| may change to `GET`
| The address moved for good and the old one only ever received `GET`. *Browsers cache it*, often
  indefinitely -- a wrong `301` outlives its configuration.

| `308`
| preserved
| The address moved for good and may receive other methods. *Cached like `301`.* The usual choice for
  a canonical trailing-slash redirect.

| `302`
| may change to `GET`
| The move is temporary and only `GET` matters. Not cached by default.

| `307`
| preserved
| The move is temporary and the method and body must be kept. Not cached by default.

| `303`
| always `GET`
| The client should fetch the target with `GET` regardless of the method it sent (post/redirect/get).
|===

Start with `302` or `307` while an address change is being tried out and switch to `301` / `308` once
it is settled; a permanent status is hard to take back from browser caches.

*`keep_query`.* With `keep_query: true` the raw inbound query string is appended to `location` --
joined with `?`, or with `&` when `location` already carries a query. Nothing else from the request is
copied: there are no request placeholders, and without `keep_query` the query is dropped. A `location`
containing `#` cannot be combined with `keep_query` (a query appended after a fragment never reaches
the server) and fails the boot.

`keep_query` is *same-origin only*: declaring it together with `allow_external` fails the boot. The
query is the one part of a redirect the caller controls, so carrying it to another origin puts
whatever the caller sent -- `?code=`, `?access_token=`, a session-ish identifier -- into the target's
access log, `Referer` chain and page analytics, and no boot review can vet a value that does not exist
until the request arrives. Keep whichever of the two the route actually needs and drop the other; a
gateway path with `keep_query` and a fixed external target without it are both fine.

*The context path.* `location` is written into `Location` *verbatim*. It is a raw gateway path written
the same way `match.path_prefix` is written, and the gateway never prefixes it with the application
context path (see link:context-path.adoc[The Context Path]).

*Answered after authentication.* A redirect route runs the same pipeline as any other route up to its
terminal action: route selection, the verb gate, the thorough checks and *authentication* all come
first. Under an anchor or endpoint that requires authentication, an unauthenticated request is
rejected *before* any `Location` is disclosed -- the configured target is itself information an
anonymous caller does not get. On a bearer route it receives the unrouted `404` (see
<<_uniform_not_found_operator_note>>); on a `require: session` route a navigation is redirected into
the login and any other request receives `401`. A public
entry redirect declares `auth: { require: none }` like any other public route. The redirect answer
carries the route's resolved security headers (see link:anchors.adoc#_anchors[Anchors]) and any
`Set-Cookie` an earlier stage produced; the route's `forward` block is not consulted, because nothing is
forwarded.

*Caching of the answer.* A redirect is a normal cacheable response -- `301` and `308` are stored by
browsers and by any shared cache on the path, indefinitely if nothing says otherwise. The gateway
therefore adds `Cache-Control: no-store` to a redirect answer whenever either of two things holds:

* the route's *effective auth* requires authentication (`bearer` or `session`) -- the answer was
  produced for one caller's credentials, so a shared cache must not replay it to another; or
* the answer carries any *`Set-Cookie`* -- the redirect is answered after authentication, so a
  re-sealed or rotated session cookie can ride on it, and a cached copy would hand that cookie to the
  next client.

A public redirect that sets no cookie is left cacheable, which is the point of using `301`/`308` for a
settled move. Nothing is configurable here: it is a fixed property of the answer, not a
`security_headers` key, so `header_modes` does not reach it.

*Where a redirect is allowed.* A `redirect` block is admitted under every anchor type -- `proxy`,
`bff` and `asset` -- and on unanchored routes, since it serves nothing an anchor type governs. It is
refused on a `grpc`, `websocket` or `graphql` route: those clients do not follow an HTTP redirect, so
the route would be dead configuration.

[[_redirect_external_targets]]
==== External targets and the open-redirect review

`location` is checked *once, at boot* -- at request time it is written verbatim, so the boot review is
the only place a target is judged. Without `allow_external`, the value must be a *gateway path*:

[cols="2,3"]
|===
| Refused spelling | Why a client reads it as another origin, or as a different path

| `//evil.example/x`
| A leading `//` is scheme-relative: it names another host.

| `/\evil.example`, `\\evil.example`
| Browsers read a backslash as `/`.

| `/%2F%2Fevil.example`, `/%5cevil.example`
| A percent-encoded `/` or `\` (either case) is decoded by intermediaries.

| `/a/../b`, `/a/./b`, `/a/%2e%2e/b`
| A dot-segment is normalized away by clients.

| `/%252F%252Fevil.example`, `/a/%252e%252e/b`, `/a%00b`
| A double-encoded or malformed escape reaches the refused spellings above after a second decode.
  Refused by cui-http's `URL_PATH` pipeline, together with overlong UTF-8, unicode-normalising escapes
  and a path longer than 1024 characters.

| a value with whitespace or a control character
| A CR/LF would forge a response header; whitespace is never a valid `Location`.

| `https://elsewhere.example/`, `javascript:...`
| Not a gateway path -- only admitted under `allow_external` (below), and `javascript:` never.
|===

The backslash and percent-encoded-separator rows are checked against the *whole* value, query and
fragment included -- a fixed configured target has no reason to encode a separator anywhere. The
remaining path rows are checked against the path portion, and are the same shared review the
`upstream.rewrite_location` mapping applies to an upstream `Location` (see <<_rewrite_location>>), so
a spelling refused at boot in a configured target is refused at runtime in a rewritten one.

`allow_external: true` additionally admits an *absolute `http` or `https` URI with a non-empty host
and no user-info* (`https://user@evil.example` disguises the real host and stays refused). Every other
scheme stays refused. Opting in is legitimate -- a moved site, a hand-off to another application -- but
it is never silent: the boot logs `WARN ApiSheriff-128` naming the route id (never the target), see
link:../LogMessages.adoc[Log Messages]. A refused `location` fails the boot with a message that echoes
the value in escaped form, so a hostile value cannot forge log lines.

`allow_external` cannot be combined with `keep_query`; the boot refuses the pair, naming the route and
the two keys and never the target. The review above proves the *target* is a well-formed foreign
origin the operator wrote down -- it says nothing about the *query*, which arrives with the request.
See `keep_query` above for what the combination would disclose.

[[_route_ordering]]
=== Route ordering

The routes of *all* endpoint files are merged into a single immutable route table at startup. A route
declares exactly one path matcher:

* *`match.path_prefix`* -- a *prefix route*: it matches the prefix itself and every path continuing it
  on a segment boundary (`/api` matches `/api/orders`, never `/apifoo`).
* *`match.path`* -- an *exact route*: it matches exactly one address, by an un-normalized string
  comparison against the canonical request path. The trailing slash is significant: `/a` and `/a/` are
  two different addresses, and an exact `path: /a` matches neither `/a/` nor `/a/b`.

Declaring both, or neither, fails the boot. Matching is then a two-step rule:

. *Candidates* are the routes whose *entire* matcher set holds for the request (path AND methods AND
  host AND headers). A route whose path matches but whose `host` or `methods` do not is simply not a
  candidate -- other routes are still considered.
. Among the candidates, *every exact route precedes every prefix route*; exact routes are ordered by
  path length, longest first, and prefix routes by the *longest* `path_prefix`. The first candidate in
  that order wins.

So for the *same address* an exact route always beats a prefix route, and an exact route can sit
inside a prefix route's namespace to override that one address (the redirect example above does
exactly that) while the prefix route keeps serving every other path.

So that the winner is never ambiguous, any two routes with an *identical* `path_prefix`, or any two
exact routes with an *identical* `path` -- in the same file or across files -- must be *statically
disjoint*. Prefixes are compared normalized (`/api` and `/api/` are the same prefix); exact paths are
compared verbatim (`/a` and `/a/` are different paths and never collide). An exact route and a prefix
route never collide, even for the same string, because the exact route is selected first by design.
Two same-key routes are disjoint when one of these holds:

* *both* declare `host`, with different values (a route that omits `host` matches every host,
  so a declared-host route paired with a host-less route at the same prefix is *not* disjoint
  and is rejected -- there is deliberately no "specific host + any-host fallback at the same
  prefix" pattern; give the fallback a different prefix or declare hosts on both);
* their `methods` sets do not overlap (an omitted `methods` means all methods and overlaps
  everything); or
* both declare a matcher on the *same header name* -- compared after `Locale.ROOT`
  lower-casing, as the runtime reads the name, so `X-Tenant` and `x-tenant` (ASCII) name one
  header -- that cannot both hold: either different exact values (e.g. `X-Tenant: a` vs
  `X-Tenant: b`; values compare case-sensitively), or one matcher *requires* the header while
  the other *forbids* it. A matcher requires the header when it
  declares `present: true` or a `value`, and forbids it with `present: false`, so both
  `present: true` vs `present: false` and an exact `value` vs `present: false` are disjoint --
  no single request satisfies both at once. An exact `value` vs `present: true` is *not*
  disjoint (a request carrying that value satisfies both), and neither are two `present: true`
  or two `present: false` matchers. A lone `present: true`, with no opposing `present: false`
  at the same prefix and header, establishes nothing.

Any same-key pair that fails all three tests is rejected at boot; precedence never depends
on file-system or declaration order -- and the runtime matcher evaluates each header matcher
exactly as this rule assumes, so a certified-disjoint pair selects the same route whichever
of the two is declared first. This keeps the canonical virtual-hosting case
expressible: `/api` on `a.example.com` -> `APP_A` and `/api` on `b.example.com` -> `APP_B`
live in two endpoint files and are disjoint by host.

The same "cannot both hold" test also guards a *single* route. Every header matcher of a route
must hold, so a route declaring two matchers on the same header name (compared after
`Locale.ROOT` lower-casing) that cannot both hold -- two different exact values, or one matcher
requiring the header (`present: true` or a `value`) while the other forbids it
(`present: false`) -- could never match any request. Such a route fails the boot, naming the route and both matchers, with one
error per conflicting pair. Redundant but compatible pairs on one route stay valid: an exact
`value` with `present: true`, two identical values, two `present: true` or two `present: false`
matchers. The pair that makes two *different* same-key routes disjoint -- an exact `value` on one
and `present: false` on the other -- is exactly the pair that makes a single route dead.

A request that matches no route is rejected with `404`.

*Reserved gateway paths.* The gateway's own OIDC endpoints are matched *exactly, before the
route table*. The keys that register them, and the field-level contract for each, are owned by
link:../configuration.adoc#_oidc[`oidc`] -- the list below names which of those keys carve out a
path, not what the keys mean. Up to *eight* paths are carved out. The first six are matched only on
the *OIDC host* (the host of `oidc.redirect_uri`); the last two are matched on *every* host, because
the identity provider calls them server-to-server at whatever address was registered with it:

. the `oidc.redirect_uri` path -- the auth-code *callback*, reached by a top-level `GET` with
  `code` and `state` in the query string (`response_mode=query`) and carrying no request body;
. `oidc.logout.path` -- RP-initiated *logout*;
. its return path (`oidc.logout.post_logout_redirect_uri`) -- the *logout-return* leg;
. `oidc.user_info.path` -- the session/*user-info* endpoint serving the curated identity view;
. `oidc.login.path` -- the gateway-owned *login-initiation* entry point that starts a login. The
  redirect it answers carries `client_id` and `request_uri` only: the authorization request itself
  is pushed to the identity provider over the back channel;
. `oidc.step_up.path` -- the *step-up* entry point that widens a live session for the route
  behind its `returnUrl`. A widening it starts is pushed in the same way, so its redirect carries
  `client_id` and `request_uri` only as well;
. `oidc.logout.backchannel_path` -- the *back-channel logout* receiver (`mode: server` only);
. `oidc.client_authentication.jwks_path` -- the *client JWKS* endpoint, at which the identity
  provider fetches the gateway's client-authentication public key. With `oidc.client_secret`
  configured there is no such key and the path answers `404`; it stays carved out all the same.

The first seven are registered only when their configuration key is present, so a deployment that
omits `oidc.user_info`, `oidc.login` or `oidc.step_up.path` carves out fewer. The client JWKS path
is the exception: it needs no declaration, and an `oidc` block with a `redirect_uri` that names none
reserves the default `/bff/jwks`. A proxy
route such as `path_prefix: /bff` therefore never swallows the `/bff/callback` callback, while
other virtual hosts (e.g. machine-to-machine API hosts with `bearer` routes) keep their full path
namespace -- except for the two every-host paths, which no virtual host can proxy. Routes remain free
to use neighbouring prefixes; only the exact reserved paths are carved out. A reserved path is a
carve-out, not an anchor: it claims its one path and nothing beneath it, so `/bff/other` is routed by
the route table like any other request, and the `/bff/*` spelling the samples use is a naming
convention nothing validates.

[[_uniform_not_found_operator_note]]
=== Why an existing route answers 404

A request to a route that exists can be answered `404`, exactly as an address without any route is
answered. That is deliberate. When a caller has not authenticated yet, every rejection a route
raises before authentication completes is answered as the unrouted `404`: a missing or invalid
bearer token, a method outside `allowed_methods`, a path outside `allowed_paths`, a refusal of the
route's `security_filter`, a declared `Content-Length` over `max_body_bytes`, and a CSRF or
same-origin refusal. Without this, an unauthenticated scanner would learn which addresses name
routes from the `401`, `405`, `400`, `413` or `403` it receives. The answer is the same in every
detail: status, body, `Content-Type`, response headers -- no `WWW-Authenticate`, no `Allow` -- and
the time it takes. A `protocol: grpc` route answers with the HTTP `404` too, not with a gRPC status
(link:../adr/0073-Untrusted_callers_get_the_unrouted_404_for_every_rejection_raised_before_the_trust_boundary.adoc[ADR-0073]).

*How to tell the true cause apart.* The gateway reports the real reason even though the caller does
not see it:

* `sheriff_errors_total{event}` on the management port counts the true event --
  `TOKEN_MISSING`, `TOKEN_INVALID`, `METHOD_NOT_ALLOWED`, `PATH_NOT_ALLOWED`,
  `SECURITY_FILTER_VIOLATION`, `CONTENT_TOO_LARGE` or `CSRF_REJECTED` -- with the route id and the
  category, never `NO_ROUTE_MATCHED`. A rising `NO_ROUTE_MATCHED` count is a request for an address
  that has no route; any of the others is a request a route refused.
* The WARN and INFO lines the gateway logs for a rejection name the true event as well (see
  link:../LogMessages.adoc[Log Messages]).

*Who still gets the honest code.* The uniform `404` is for callers that have not passed
authentication. A client with a valid token keeps every answer raised after authentication: the
`403 insufficient_scope` of a token lacking a scope, the dispatch `408` and `413`, and upstream
`5xx`. A session route keeps its own answers too: a navigation without a session is redirected into
the login, and any other request receives `401` `application/problem+json`. Rejections raised before
authentication -- a wrong method, for example -- answer `404` to every caller, because the gateway
has not looked at a credential at that point. An authenticated client that receives an unexpected
`404` from a route it knows exists has therefore sent a request that route refuses; the metric above
names which refusal.

*Turning it off.* `security_defaults.uniform_not_found: false` in `gateway.yaml` restores the honest
`401`, `405`, `400`, `413` and `403` for every caller, and the gRPC trailers-only status on a gRPC
route. The default is `true`. See
link:../configuration.adoc#_uniform_not_found[Configuration -- The uniform 404].

[[_endpoint_scopes]]
=== Endpoint scopes (`endpoint.scopes`)

`scopes` is an endpoint-level list, declared beside `auth` rather than inside it. It is *additive*:
every route of the endpoint needs

----
needed(route) = oidc.scopes ∪ endpoint.scopes
----

worked out once at boot (`endpoint.scopes` alone when the gateway declares no `oidc` block). Because
it sits outside `auth`, a route that overrides `auth` still needs the endpoint's scopes, and no
endpoint can remove a member of `oidc.scopes`. What the set does depends on the route's effective
auth:

* *`require: bearer`* -- the presented token must carry every member. A token missing one is answered
  `403` with `WWW-Authenticate: Bearer error="insufficient_scope", scope="<missing>"`, naming only the
  missing scopes (sorted), and the upstream is never contacted. Because the set includes
  `oidc.scopes`, a gateway that also runs the BFF rejects a bearer token lacking them -- a
  `client_credentials` token among them. An empty set skips the check. On a route with
  `session_fallback: true` this answer is the *bearer branch's* (requests carrying
  `Authorization`); its session branch enforces the same set as `require: session` below.
* *`require: session`* -- the set is what a login started on the route *requests* from the IdP, and
  what every live session is compared against on each request, whatever `token_relay` says. A
  session whose token carries every member is relayed with no call to the IdP. A missing scope inside
  the session's granted set costs a refresh; any other missing scope redirects a navigation to
  the IdP to widen the live session, and answers every other request `403`
  `application/problem+json` naming the `missing_scopes` and, when `oidc.step_up.path` is
  configured, a `step_up_url`. A session short of a scope is never relayed. See
  link:bff-session.adoc#scope-enforcement[Server-Session BFF -- When a session lacks a scope the
  route needs] for the full behaviour and
  link:bff-session.adoc#scopes[Server-Session BFF -- Scopes] for session-wide scope growth. The
  same applies to the *session branch* of a `session_fallback` route (requests without
  `Authorization`): both branches of such a route enforce the one set, each with its own answer.
* *`require: none`* -- the set has no effect. An endpoint declaring `scopes` whose every route
  resolves `require: none` is refused at boot.

The `auth` block carries no scope list of its own; the schema refuses one, so endpoint scopes are
declared here or not at all.

[[_cookie_dependent_upstream]]
=== Fronting a cookie-dependent upstream (`cookies`)

By default no browser cookie reaches an upstream and no upstream `Set-Cookie` reaches the browser.
An upstream that keeps its own state in a cookie -- a legacy application's `SESSIONID`, a framework's
CSRF token cookie, a preference -- therefore needs its route to name those cookies in a `cookies`
block:

[source,yaml]
----
# endpoints/legacy.yaml
endpoint:
  id: legacy
  base_url: LEGACY
  auth: { require: none }
  routes:
    - id: legacy-app
      match: { path_prefix: /legacy }
      cookies:
        allow: [SESSIONID]           # only this cookie crosses, in both directions
----

What the route then does with cookies:

* *Request.* The upstream receives a `Cookie` header holding the browser's `SESSIONID` pair and
  nothing else. Every other browser cookie is dropped, and so are the gateway's own cookies -- the
  BFF session cookie among them -- which no `cookies` block can admit.
* *Response.* An upstream `Set-Cookie: SESSIONID=...` line reaches the browser with its `Domain`
  attribute removed, so the cookie stays bound to the host the browser addressed. A `Set-Cookie`
  naming any other cookie is not relayed.
* *Cross-site requests.* Because the route forwards a cookie, the gateway checks the origin of every
  unsafe request (`POST`, `PUT`, `PATCH`, `DELETE`, ...) that carries `SESSIONID`. A request sent by
  a page on another site -- its `Origin` is neither the origin the gateway was reached on nor one the
  block lists in `additional_origins` -- is refused before the upstream sees it. The refusal is
  raised before authentication, so the browser sees the unrouted `404` (see
  <<_uniform_not_found_operator_note>>), and `403` on a gateway that sets
  `security_defaults.uniform_not_found: false`. The same
  cross-site request *without* a `SESSIONID` cookie carries no credential to forge and is
  forwarded, so a server-to-server client that sends no cookie and no `Origin` keeps working. A `GET`
  is never checked.

If the application is served to browsers from a second origin, list that origin in
`additional_origins`. Behind a TLS-offloading proxy the gateway is reached over `http` while the
browser sends an `https` `Origin`; list the public `https` origin there as well. `allow: all`
forwards every cookie except the gateway's own and is refused at the gateway scope; prefer a list
naming exactly what one upstream needs.

*Upgrading from a gateway without the `cookies` block is a breaking change.* Such a gateway relayed
every upstream `Set-Cookie` line; under the default `allow: none` none is relayed, so an upstream
that sets cookies stops having them reach the browser until its route, endpoint or anchor names them.
The full contract -- the three modes, the four scopes, the same-origin check, the WebSocket rule and
every boot refusal -- is the link:../configuration.adoc#_cookies[`cookies` reference]; which headers
the gateway withholds in either direction is the
link:../configuration.adoc#_never_forward_set[never-forward set].

[[_defaults_for_omitted_blocks]]
=== Defaults for omitted blocks

What an omitted block resolves to. Every policy block follows one rule -- the nearest declared
scope of `gateway -> anchor -> endpoint -> route` wins and replaces every broader declaration
wholesale -- and the scopes each block is declarable at, with its nothing-declared fallback, are
tabulated once in link:anchors.adoc#_policy_block_resolution[Policy-block resolution]; the rows
below do not restate the chain. Most rows are fail-closed -- an omitted `auth` inherits a declared
posture rather than inventing one, and an omitted `security_filter` lands on `strict`. The
`forward` row is the deliberate exception, and is explained in its own cell:

[cols="1,3"]
|===
| Omitted block | Effect

| `auth` (route level)
| The route takes the nearest declared `auth` block -- its endpoint's, else its anchor's (see
  link:anchors.adoc#_policy_block_resolution[Policy-block resolution]). The authentication posture
  is defined per endpoint file -- `endpoint.auth` is *mandatory unless the endpoint's anchor
  declares an `auth` block*, and anonymous access is `auth: { require: none }`, written out; there
  is no implicit default. An endpoint file with neither its own nor an anchor-provided `auth` block
  fails the boot.

| `auth.token_relay`
| `true`: a `require: session` route -- and the session branch of a `session_fallback` route --
  relays the session's access token upstream as `Authorization: Bearer`. The key travels with its
  `auth` block, so it is resolved with the block, never on its own. On the
  bearer branch of a `session_fallback` route the validated client token is forwarded through the
  mediated-bearer seam independent of `token_relay`. It has no effect on plain `require: bearer`
  routes or on `none` routes.

| `auth.session_fallback`
| `false`: a `require: bearer` route has one authentication branch and is a plain bearer route. The
  key travels with its `auth` block exactly as `token_relay` does, so a route-level block that omits it
  resolves to `false` whatever the endpoint or anchor declares. See
  link:../configuration.adoc#_auth_session_fallback[`auth.session_fallback`].

| `scopes` (endpoint level)
| Empty: the endpoint's routes need `oidc.scopes` alone (nothing at all when the gateway has no
  `oidc` block). See <<_endpoint_scopes>>.

| `enabled` (endpoint level)
| The endpoint is *active* (`enabled: true`). Set `false` -- or the env override
  `ENDPOINT_<ID>_ENABLED=false` -- to make the endpoint inert (see
  link:../configuration.adoc#_endpoint_identity[`endpoint`]).

| `allowed_methods` (endpoint level)
| A declared endpoint list is the nearest scope and wins. With none, the *anchor's* list applies if
  the route's anchor declares one, else the *global* `gateway.allowed_methods`, else the standard
  verb set. There is no route-level list -- a route narrows its verbs with `match.methods` -- see
  link:../configuration.adoc#_allowed_methods[`allowed_methods`].

| `security_filter`
| The route takes the nearest declared block -- its endpoint's, else its anchor's -- whole; with
  none declared it runs `security_defaults.profile`. A resolved block that omits `profile` falls
  back to `security_defaults.profile`, *not* to the profile of the block it replaced, and an
  omitted `security_defaults` block -- or one omitting `profile` -- resolves to `strict` (one of the
  two link:anchors.adoc#_policy_block_field_level_exceptions[documented field-level exceptions]).
  The resolved profile's preset supplies the limits, and any explicit limit keys in the winning
  block override them individually.

| `forward`
| The endpoint's `forward` block when the endpoint declares one, taken whole. With none at either
  scope: *forward-all* on both dimensions: every client request header and query parameter crosses,
  minus the gateway-owned link:../configuration.adoc#_never_forward_set[never-forward set], which
  no configuration can re-admit apart from the single `Authorization` carve-out. The `Cookie`
  header is not decided here at all: it crosses only as the route's `cookies` block admits it (see
  the `cookies` row below). The *automatic* injections apply as always. The regenerated forwarding-header set is always
  injected. The mediated `Authorization: Bearer` is injected on a session route and on the
  session branch of a `session_fallback` route only when the effective `token_relay` is `true`,
  and on the bearer branch of a `session_fallback` route always (the validated client token,
  independent of `token_relay`); a plain `require: bearer` route never receives one. A route that wants a stricter posture
  declares it -- see link:../configuration.adoc#_forward[`forward`]. Note this is the one
  omitted-block default that
  is *permissive*: it filters within a route the request is already authorised for, so the
  deny-by-default guarantee is unaffected (it lives at route matching).

| `cookies`
| The nearest declared block -- the route's, else its endpoint's, else its anchor's, else the
  gateway's -- taken whole. With none declared: `allow: none`, fail-closed -- no browser cookie
  reaches the upstream and no upstream `Set-Cookie` reaches the browser. An asset or redirect route
  resolves `allow: none` whatever is declared. See <<_cookie_dependent_upstream>>.

| `rate_limit`
| No rate limiting, whether the block is declared or not: rate limiting is planned, not
  implemented, and no `429` is produced today. A declared block is parsed and enforced by nothing,
  and every route that declares one is named at boot by the WARN `ApiSheriff-140` -- see
  link:../configuration.adoc#_rate_limit[`rate_limit`].
|===

[[_edge_hardening_defaults]]
=== Edge hardening (transport) defaults

The public data-plane HTTP listener is bounded on two axes, and they are governed differently.

The *transport bounds* — the framing limits, the HTTP/2 connection window, the request-body idle
timeout and deadline, the gRPC stream-idle timeout, the unrouted-`404` response floor and the drain
window — are fixed secure defaults applied in code (`EdgeHardeningOptions`, the gRPC relay for the
stream-idle timeout, and `UniformNotFound` for the response floor) and are not
operator-configurable. The framing limits fail fast on abusive framing before a request is
admitted to the pipeline. These values are recorded here doc-first: they are the
contract the edge-hardening code implements, and any change to a constant must be reflected in this
table.

The *admission budgets* — how many requests, and how many WebSocket relays, may be in flight at once
— are operator-facing and configurable through the optional
link:../configuration.adoc#_edge_hardening[`edge_hardening`] block in `gateway.yaml`. Their sizing
depends on the
deployment's traffic shape rather than on protocol safety, which is why they are the two bounds the
operator owns. Omitting the block, or either key, resolves to the defaults in the table below, so a
deployment that never writes it keeps the behaviour shown here.

[cols="2,1,3"]
|===
| Bound | Default | Effect

| Maximum request header block
| 16 KiB
| An over-large header block is rejected by the Vert.x codec before the request reaches the pipeline.

| Maximum HTTP/1.x request-line length
| 8 KiB
| An over-long `METHOD SP request-target SP HTTP/x` line is rejected at the transport.

| Maximum chunked-transfer chunk size
| 16 KiB
| An over-large single chunk is rejected at the transport.

| Reserved-path request body
| 16 KiB
| The cumulative body the edge buffers for a gateway-terminated reserved `POST` path -- in practice
  the back-channel logout receiver, which is reached before authentication and never meets a
  per-route body cap. A larger body is rejected `413`. Defined as the header-block bound rather than
  as a second constant.

| Idle-connection reap
| 60 s
| An idle connection is closed after this window, so a slow-loris / h2 abuse load cannot pin
  connection slots.

| HTTP/2 concurrent streams per connection
| 100
| The `SETTINGS_MAX_CONCURRENT_STREAMS` value every listener announces. A listener whose own setting
  is unbounded or larger is lowered to 100; a lower setting is kept. Not configurable.

| HTTP/2 connection window
| 6,553,500 bytes +
  (100 streams × 65,535-byte initial stream window)
| Each stream is bounded by its own window; the connection window is large enough that streams the
  gateway is not yet reading cannot hold back the ones it forwards. Derived from the 100-stream bound
  above times the initial stream window, capped at 2^31^-1 and never below one stream window. Not
  configurable.

| Request-body idle timeout
| 10 s
| A proxied request whose body makes no progress for this long while the gateway reads it is
  answered `408` and stops holding its upstream connection. On an HTTP/1.1 upstream that connection
  is reused only when no body chunk had been forwarded; otherwise it is closed and the next request
  opens a new one. Not applied to bodyless requests or
  `protocol: grpc` routes; not configurable. Shorter than the upstream guard's 30 s timeout, which
  bounds the dispatch until the upstream's response head. See
  link:../architecture/tls-and-inbound-security.adoc#_request_body_idle_timeout[Architecture -- request-body idle timeout].

| Request-body deadline
| 25 s +
  (from the start of the upstream attempt)
| A proxied request whose body has not ended this long after its upstream attempt started is ended,
  however steadily the body arrives: answered `408` when the upstream has not answered yet, and
  otherwise its relayed response is ended -- on HTTP/2 the stream is then reset, on HTTP/1.x the
  connection is closed. The time spent waiting for a pooled upstream connection counts towards the
  25 s: a request that obtains its connection only after the deadline is answered `408` as soon as its
  body is read. The deadline does not reset an upstream that is not taking data, but a body that
  upstream reads again after the deadline is ended then. Not applied to bodyless requests or
  `protocol: grpc` routes; not configurable. See
  link:../architecture/tls-and-inbound-security.adoc#_request_body_deadline[Architecture -- request-body deadline].

| gRPC stream-idle timeout
| 5 min
| A `protocol: grpc` call whose upstream has sent its response headers and that then carries no frame
  in either direction for this long is ended with `grpc-status: 4` (`DEADLINE_EXCEEDED`) and
  `grpc-message: stream-idle-timeout`. A frame in either direction keeps the call open; HTTP/2 `PING`
  frames do not count, and the call's `grpc-timeout` is not honoured. Before the response headers the
  upstream guard's 30 s timeout bounds the call instead. Not configurable. See
  link:../architecture/tls-and-inbound-security.adoc#_grpc_stream_idle_bound[Architecture -- gRPC stream-idle bound].

| Unrouted-`404` response floor
| 50 ms + a random jitter below 20 ms +
  (from admission)
| While `security_defaults.uniform_not_found` is on, every answer rendered as the unrouted `404` is
  written no earlier than this after the request was admitted, so the answer time does not tell an
  existing route from an absent one (<<_uniform_not_found_operator_note>>). A Vert.x timer holds the
  answer; no thread waits. The answer keeps its admission permit until it is written. Not
  configurable.

| Admission cap (in-flight requests) +
  [`edge_hardening.admission_cap`]
| 2048
| Requests beyond the cap are rejected `503` *before* a virtual thread is dispatched, so a flood
  cannot spawn unbounded virtual threads. Operator-configurable; minimum 1.

| WebSocket relay cap (established relays) +
  [`edge_hardening.websocket_relay_cap`]
| 512 +
  (a quarter of the effective `admission_cap`)
| A sub-budget acquired *in addition to* the general admission permit, never instead of it. An
  established relay holds both permits for the connection's whole lifetime rather than for one
  round-trip, so without this second bound a modest number of long-lived relays would consume the
  general pool and starve ordinary HTTP traffic. An upgrade beyond the cap is refused `503` and
  releases the general permit on the way out. Operator-configurable; minimum 1, and must not exceed
  `admission_cap`. Omitting it takes a quarter of the *effective* `admission_cap` rather than a fixed
  `512`, so the three-quarters-for-HTTP reservation holds at every admission cap.

| Graceful-drain timeout
| 25 s
| The bounded wait for in-flight requests to complete on `SIGTERM`; kept below the Quarkus default
  shutdown timeout so the drain completes within the shutdown window rather than being cut short.
|===
