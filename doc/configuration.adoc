== Principles

Configuration is *static, file-based, and immutable*. It is read once at startup, validated
in full, frozen into immutable value objects, and never mutated at runtime. The gateway
refuses to boot on invalid configuration.

Two structural principles shape the layout:

* *Endpoint config is portable; topology is environment-specific.* Route definitions never name
  a concrete *upstream* host. They reference an abstract alias (`APP1`, `KEYCLOAK`, ...); a
  separate topology file binds each alias to a real location. Moving a deployment changes only
  the topology, never the endpoint files. (The claim is about the backend leg. A `match.host`
  matcher is a different thing -- it matches the *inbound* request's `Host` header, the
  gateway's own public vhost, and is environment-specific.)
* *Deny-by-default at the URL layer.* Nothing is routed or trusted unless it is explicitly
  configured: a request matching no route reaches no upstream at all, and an authentication
  posture is written out rather than inferred. Within a route the request is already authorised
  for, the `forward` block then chooses a *filtering posture* -- permissive by default, strict
  by opt-in -- bounded by gateway-owned sets no configuration can override (see
  link:#_forward[`forward`]).

The model rests on a small set of adopted patterns:

* *Endpoint-centric routes* with per-route timeout and circuit breaker.
* *Composable, bounded matchers* (path, method, host, header).
* *Validated-then-immutable, atomic config.*
* *Three-mode forward filtering* (positive-list, negative-list, or forward-all per dimension),
  bounded by gateway-owned never-forward sets.
* *Alias -> URL indirection with an explicit in-file env placeholder* -- a single-URL alias,
  decomposed on read, whose value an environment variable may supply or override only through an
  explicit `${VAR}` placeholder written in the file -- never an automatic lookup (see
  link:adr/0004-topology-indirection.adoc[ADR-0004]).

The provenance of these patterns -- what was adopted from which evaluated product and why -- is
recorded in the link:features-analysis.adoc[Feature Analysis] and the ADRs, not here.

The schema is intentionally declarative; there is no rule language and no runtime mutation API.

== Configuration Layout

Configuration is three kinds of artifact:

[cols="1,3"]
|===
| Artifact | Purpose

| `gateway.yaml`
| *Global* settings: schema version, TLS, security-response headers, filter defaults, the
  link:user/anchors.adoc#_anchors[`anchors`] (namespace-scoped policy), the `forwarded`-header policy, and the
  `oidc` block (BFF variants). No routes.

| `endpoints/*.yaml`
| *One file per endpoint* -- a service / host / app, or a logical group. Each file binds to one
  `base_url` *alias* and declares the routes for that endpoint. These files are
  *environment-independent* in their backend leg -- they never contain a real *upstream* host.
  (An inbound `match.host` matcher names the gateway's own public vhost and is
  environment-specific; write it as a `${VAR}` placeholder.)

| `topology.properties`
| Maps each `base_url` alias to a concrete location (one URL per alias). Overridable per alias by
  an environment variable. This is the *only* file that changes between environments.
|===

[source,text]
----
config/
  gateway.yaml              # global settings
  endpoints/
    app1.yaml               # base_url: APP1     -> routes for /api/orders ...
    keycloak.yaml           # base_url: KEYCLOAK -> routes for /auth, /token
  topology.properties       # APP1=..., KEYCLOAK=...   (explicit ${VAR} placeholders let env vars override)
----

The configuration directory is selected by the `sheriff.config.dir` property (a Quarkus
configuration property; default `config`). Under it, `gateway.yaml` and `topology.properties`
are read by exact name, and every *`.yaml`* file directly under `endpoints/` is loaded as an
endpoint file in filename-sorted order -- files with any other extension, and nested
subdirectories, are ignored.

== Loading, Resolution and Validation

* `gateway.yaml`, every file under `endpoints/`, and `topology.properties` are read once at
  startup.
* Each endpoint's `base_url` alias is *resolved* against the topology (an explicit in-file
  `${VAR}` placeholder lets an environment value win over the placeholder's default, see
  link:user/environment-variable-overrides.adoc#_topology_and_endpoint_enablement[Topology]); the resolved URL is *decomposed once* into
  `{scheme, host, port, base-path}` (see link:adr/0004-topology-indirection.adoc[ADR-0004]).
* The document set is validated as a whole; unknown keys, unknown `version`, an unresolved alias,
  a malformed topology URL, or a route referencing a missing endpoint all *fail the boot*.
* Secrets are never inlined: they are `${ENV_VAR}` references, so the config artifacts are safe to
  commit. Topology values may be literal (they are locations, not secrets) but are still
  overridable through an explicit in-file `${VAR}` placeholder.
* *Environment override mechanism* (link:adr/0004-topology-indirection.adoc#_amendment_a1[ADR-0004
  Amendment A1]): every override point is a *visible in-file placeholder*, resolved once, before
  schema validation, uniformly across `gateway.yaml`, `endpoints/*.yaml`, and
  `topology.properties`. The grammar is fixed: `${NAME}` (required -- the variable must be set or
  the boot fails, the secrets semantics) or `${NAME:-default}` (optional -- the literal
  `default`, everything between the first `:-` and the closing brace, applies when the variable
  is unset; an environment value wins over it). `NAME` matches `[A-Za-z_][A-Za-z0-9_]*`; several
  placeholders may appear in one scalar; there is *no nesting and no escape syntax* -- a scalar
  carrying a `${` that is not a well-formed placeholder *fails the boot* (a loud failure is
  always preferred over a silently un-substituted literal). The `TOPOLOGY_<ALIAS>` /
  `ENDPOINT_<ID>_ENABLED` names used throughout this document are the *conventional variable
  names* written inside those placeholders, not invisible code-level lookups: an environment
  value reaches a topology or enablement field only through an explicit in-file `${VAR}`
  reference.
* On any validation error the process exits non-zero and logs the offending file/alias -- it does
  not start a degraded gateway.

== Schemas

Both configuration artifacts are validated against bundled *JSON Schema* documents (Draft
2020-12) before binding, so a structurally malformed file is rejected with a precise
file-and-JSON-pointer error before any immutable value object is built:

[cols="1,3"]
|===
| Schema | Validates

| `schema/gateway.schema.json`
| The global `gateway.yaml` document -- `version` (the only required key), `metadata`, `tls`,
  `management`, `security_headers`, `security_defaults`, `allowed_methods`, `anchors`,
  `upstream_defaults`, `asset_defaults`, `forwarded`, `edge_hardening`, `token_validation` and
  `oidc`.

| `schema/endpoint.schema.json`
| A single `endpoints/*.yaml` file -- the `endpoint` block (`id`, `enabled`, `base_url`,
  `anchor`, `auth`, `allowed_methods`, `upstream_defaults`) and its `routes[]`, each route's
  `id`, `protocol`, `anchor`, `match`, `auth`, `security_filter`, `forward`, `upstream`, `asset`,
  the WebSocket-route `websocket` block (which holds `allowed_origins` and
  `idle_timeout_seconds`), and reserved `rate_limit`.
|===

Both schemas set `additionalProperties: false` at *every* object level, so an *unknown key* -- a
typo or a stale field -- fails the boot rather than being silently ignored. The schemas mirror
this document field-for-field and are the *structural* gate only. The *cross-cutting* rules a
schema cannot express are enforced in code and listed under
link:#_configuration_validation_rules_summary[Configuration Validation Rules]: endpoint- and
route-`id` uniqueness across files, `upstream_defaults` and `allowed_methods` wholesale-replacement,
`allowed_methods` verb membership, topology-alias resolvability, and same-prefix disjointness. Every
violation the schema gate and the configuration-validator rules detect is collected in a single
pass and reported together, rather than one at a time, and any violation refuses the boot. The one
deliberate exception is an unresolvable `base_url` alias of an *enabled* endpoint: the topology
resolver runs *before* the aggregating validator and *throws* on it
(link:adr/0009-asymmetric-alias-resolution-failure.adoc[ADR-0009]), so that single failure aborts
the boot on its own rather than joining the aggregated report. An unresolvable `passthrough_sni`
alias, by contrast, is deferred to the validator and aggregated with the rest.

== Gateway Configuration (`gateway.yaml`)

[source,yaml]
----
version: 1                         # config schema version; unknown values are refused

metadata:
  config_version: "2026-07-10.1"   # audit stamp only (see "Configuration Mode")

tls:                               # TLS POLICY for the terminated listener. Neutral names only:
                                   #   ports and certificate/key material stay deployment-supplied
                                   #   and never appear here (ADR-0025). One named exception:
                                   #   mtls.client_ca below REFERENCES a trust anchor by path --
                                   #   see "the client_ca carve-out"
  min_version: "1.3"
  cipher_suites: []                # OPTIONAL allowlist, e.g.
                                   #   [TLS_AES_256_GCM_SHA384, TLS_AES_128_GCM_SHA256].
                                   #   Omit/empty => the runtime's own suite selection
  alpn: [h2, http/1.1]             # HTTP/2 (also carries gRPC) + HTTP/1.1
  passthrough_sni: {}              # SNI hostname -> topology alias, relayed at L4 without
                                   #   decryption, e.g. { legacy.example.com: LEGACY }
  mtls:
    enabled: false
    client_ca: /etc/sheriff/ca.pem

management:                        # TLS policy for the management interface (health/metrics on
                                   #   their own port). POLICY ONLY -- this block declares NO
                                   #   port; the port is deployment-bound (see "management")
  tls:
    enabled: true                  # HTTPS is the default and the shipped posture. false takes
                                   #   the WHOLE management surface to plain HTTP and emits a
                                   #   loud boot WARN (ApiSheriff-115)

security_headers:                  # response-header middleware (global default)
  hsts: { max_age: 31536000, include_subdomains: true }
  content_type_nosniff: true
  frame_deny: true
  cors:                            # disabled unless configured; a cross-origin SPA (see
    enabled: true                  #   oidc.session.csrf below) needs this enabled WITH
    allowed_origins: [https://app.example.com]   # credentials, or the browser blocks the calls
    allowed_methods: [GET, POST]
    allowed_headers: [content-type]
    allow_credentials: true

security_defaults:                 # baseline inbound filter mode; overridable per route/anchor
  profile: strict                  # strict | lenient | minimal   (omitted block => strict)
                                   # 'minimal' is a PARTIAL disable, not an off switch:
                                   # see "The `minimal` mode" below for the closed definition
  allow_get_with_content_length_body: false   # OPTIONAL, default false. Admits a Content-Length-
                                   #   framed body on GET (for upstreams like Elasticsearch
                                   #   _search). PARTIAL: Transfer-Encoding on GET stays REJECTED
                                   #   unconditionally, and HEAD is unaffected on every leg.
                                   #   See "The `GET`-body opt-in" below.

allowed_methods: [GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS]   # positive HTTP-verb allowlist
                                   #   (global default). An anchor or endpoint may REPLACE this
                                   #   wholesale (no inheritance -- see endpoint.allowed_methods).
                                   #   A routed request whose method is not in the EFFECTIVE list
                                   #   is rejected 405. TRACE and CONNECT are never permitted and
                                   #   cannot be listed. Omit => the standard set shown here.

anchors:                           # OPTIONAL namespace-scoped policy (see "Anchors" in
  api:                             #   user/anchors.adoc); each anchor OWNS a disjoint path
    path_prefix: /api              #   namespace and carries the policy floor for every route
                                   #   inside it
    type: proxy                    # MANDATORY classification axis (proxy | bff | asset); see
                                   #   "Type and access axes" in user/anchors.adoc. Unrelated to
                                   #   tls.passthrough_sni.
    access: authenticated          # MANDATORY audience axis (public | authenticated); a bearer
                                   #   floor is what `authenticated` requires
    auth: { require: bearer }      # every /api route presents a bearer token; a member route
                                   #   may replace this block but never weaken it to `none`
    security_filter: { profile: strict }
  bff:
    path_prefix: /bff
    type: bff                      # a bff surface MUST declare access: authenticated
    access: authenticated
    auth: { require: session }     # the BFF surface: mediated OIDC session per the oidc block
  static:                          # an asset surface (see "Asset terminal action" in
                                   #   user/endpoint-routes.adoc)
    path_prefix: /static
    type: asset
    access: public                 # a public anchor declares NO auth block (public is the
                                   #   absence of auth); an auth block here fails the boot

asset_defaults:                    # OPTIONAL. ADD-ONLY extension of the gateway's built-in asset
                                   #   content-type map. Omit the block to let the built-in map
                                   #   govern alone.
  content_types:                   # extension (lowercase, no dot) -> Content-Type
    webmanifest: application/manifest+json   # an extension the gateway does NOT map
                                   #   An entry naming a BUILT-IN extension (html, css, js, svg,
                                   #   png, ... -- 21 in total) is REFUSED AT BOOT, naming the
                                   #   offending extension. The built-ins are immutable because
                                   #   remapping one -- svg away from image/svg+xml, or any
                                   #   built-in to text/html -- is a stored-XSS lever on a
                                   #   security gateway.

forwarded:                         # resolved by cui-http (de.cuioss.http.forwarded)
  trusted_proxies: [10.0.0.5/32, 10.0.0.6/32]   # MANDATORY; the exact proxy addresses --
                                   #   keep as narrow as possible; empty => forwarding
                                   #   headers are never trusted; TCP peer is the client
                                   #
                                   # OR, supplied whole from the environment:
                                   #   trusted_proxies: "${SHERIFF_TRUSTED_PROXIES}"
                                   #   with SHERIFF_TRUSTED_PROXIES=10.0.0.5/32,10.0.0.6/32
                                   #
                                   #   ONE variable carries the WHOLE list, comma-separated
                                   #   and stripped, so the number of proxies is fixed by the
                                   #   deployment rather than by this file -- which is the
                                   #   point, since the trusted set differs per environment
                                   #   while the mounted document is copied unchanged.
                                   #   Use the BARE ${VAR}: a ${VAR:-default} form would let
                                   #   the gateway boot with a trust set nobody chose, so an
                                   #   empty resolution FAILS THE BOOT instead. Writing an
                                   #   explicit [] here still means "trust no proxy" and
                                   #   stays valid -- the refusal is of an emptied
                                   #   SUBSTITUTION, never of a list you wrote empty.
                                   #   The PRESENCE of the forwarded block still requires a
                                   #   file edit; only the value is environment-supplied.
  trust_scheme_host: false         # honor sanitized scheme/host/port/prefix from proxies
                                   #   (ForwardedResolverConfig.trustAll)
  emit: x-forwarded                # x-forwarded (default) | both (adds RFC 7239 Forwarded)

edge_hardening:                    # OPTIONAL admission budget for the public data-plane edge.
                                   #   Omit the block, or either key, to take the defaults shown.
  admission_cap: 2048              # max concurrently in-flight requests across the whole edge;
                                   #   a request beyond it is refused 503. Minimum 1.
  websocket_relay_cap: 512         # max concurrently ESTABLISHED WebSocket relays. A sub-budget
                                   #   acquired IN ADDITION TO the general permit above, never
                                   #   instead of it, because a relay holds its permit for the
                                   #   connection's whole lifetime rather than one round-trip.
                                   #   Minimum 1, and must not exceed admission_cap -- a larger
                                   #   value could never bind. Omitting this key alone takes a
                                   #   QUARTER of the effective admission_cap (>= 1), so lowering
                                   #   admission_cap alone stays valid. See "Sizing the WebSocket
                                   #   relay budget" in the protocol-routes guide.

token_validation:                  # offline bearer validation (routes with auth.require: bearer)
  issuers:                         # one entry per accepted identity provider
    - name: main
      issuer: https://idp.example.com/realms/main   # expected iss claim
      audience: api-sheriff                          # expected aud claim
      jwks:
        source: http               # http | file
        url: https://idp.example.com/realms/main/protocol/openid-connect/certs
        # file: /etc/sheriff/jwks.json   (air-gapped deployments)
        # allowed_egress_hosts: [idp.internal]   # SSRF egress allowlist; OMIT unless needed.
                                   #   Absent/empty keeps the secure default (private-address
                                   #   JWKS targets refused). Host-exact, no wildcard; widen
                                   #   only for a trusted IdP on a private network (GW-05).
        # tls_profile: corporate-idp             # logical trust profile; OMIT for a public-CA
                                   #   IdP. Names trust anchors without carrying them; the
                                   #   deployment binds the name. See "Trust profiles" below.

oidc:                              # only used by the BFF variants (2 and 3)
  issuer: https://idp.example.com/realms/main
  client_id: api-sheriff
  client_secret: ${SHERIFF_CLIENT_SECRET}
  scopes: [openid, profile]
  redirect_uri: https://gw.example.com/auth/callback
                                   # register at the IdP as a plain GET redirect target: the
                                   #   gateway drives response_mode=query (fixed in code, no knob)
  login:
    path: /auth/login              # gateway-owned login-initiation entry point (reserved path)
  user_info:
    path: /auth/userinfo           # gateway-served curated identity view (reserved path)
    allowed_claims: [sub, name, email]   # operator allowlist; empty (default) discloses nothing
    default_view: [sub, name]      # returned when the caller requests no explicit claims;
                                   #   every entry must lie within allowed_claims
  logout:
    path: /logout                  # gateway-served; triggers RP-initiated logout at the IdP
    post_logout_redirect_uri: https://gw.example.com/logout/done   # gateway-owned return leg,
                                   #   pre-registered, exact match; verifies the logout state
    final_redirect: https://app.example.com/   # where the browser lands after verification
    backchannel_path: /logout/backchannel   # back-channel receiver (mode: server only)
  session:                         # NOTE: exhibit shows the fields of BOTH modes; store is
                                   #   server-mode-only, the encryption key cookie-mode-only
    mode: cookie                   # cookie (Variant 3) | server (Variant 2)
    store: memory                  # REQUIRED for server mode; memory is the only initial option
    max_sessions: 10000            # server mode only: upper bound on concurrently stored
                                   #   sessions -- a DoS guard on the in-memory store. Reaching
                                   #   the bound sweeps the expired sessions and admits the login
                                   #   if that freed a slot; no scheduler or periodic sweep exists
    cookie_name: __Host-sheriff
    encryption_key: ${SHERIFF_SESSION_KEY}   # cookie mode only (AES-256-GCM); OPTIONAL -- omit to
                                   #   generate a key on startup (sessions die on restart)
    max_cookie_size: 4096          # cookie mode only: sealed cookie-value size budget in bytes.
                                   #   40..8192, default 4096. Drives BOTH the seal budget and the
                                   #   gateway's pre-route Cookie header-value cap
    ttl_seconds: 3600              # absolute session lifetime from login
    csrf:
      trusted_origins: [https://app.example.com]   # app origins allowed on unsafe methods;
                                   #   defaults to the origin of redirect_uri
    refresh:
      enabled: true
      leeway_seconds: 30           # refresh this long before expiry
      on_failure: reauthenticate   # reauthenticate | reject
  step_up:                         # RFC 9470
    enabled: true
    honor_upstream_challenge: true

== Field Reference

[[_endpoint_identity]]
=== `endpoint` (identity and enablement)

Every `endpoints/*.yaml` file declares exactly one `endpoint` block. Its identity and
enablement fields:

[cols="1,3"]
|===
| Field | Meaning

| `id`
| The endpoint's *unique name* (mandatory). It labels the endpoint in logs and metrics and is
  the key for the `enabled` env override (below). *`id` must be unique across all endpoint
  files* -- two endpoints sharing an `id` (in one file or across files) *fail the boot*. This
  is distinct from, and additional to, route-`id` uniqueness. Pattern: `[a-z][a-z0-9-]*`.

| `enabled`
| Whether this endpoint is active. *Defaults to `true`*. When `false`, the endpoint is *inert*:
  its routes are *not* merged into the route table (requests to those paths get the ordinary
  `404`), it does not participate in route disjointness / passthrough-collision checks, and its
  `base_url` alias *need not resolve* -- so an endpoint whose backend is absent in a given
  environment can be shipped in the config set and simply switched off there. A disabled
  endpoint is still *schema-validated* (typos are caught), it is just not activated. Overridable
  per environment via the in-file placeholder form -- `enabled: ${ENDPOINT_ORDER_API_ENABLED:-true}`
  -- where the environment variable *wins over the placeholder default* (ADR-0004 Amendment A1,
  the same mechanism link:user/environment-variable-overrides.adoc#_topology_and_endpoint_enablement[topology] uses). By convention `<ID>` in the variable name
  is the upper-cased `id` with hyphens mapped to underscores (endpoint `order-api` ->
  `ENDPOINT_ORDER_API_ENABLED`).
|===

The endpoint's other fields are documented under their own headings: `base_url`
(link:user/environment-variable-overrides.adoc#_topology_and_endpoint_enablement[Topology] / link:adr/0004-topology-indirection.adoc[ADR-0004]), `anchor`
(link:user/anchors.adoc#_anchors[Anchors] -- the normative reference for both the gateway `anchors` block and
the endpoint/route `anchor` membership field), `auth` (link:#_auth[`auth`]),
`allowed_methods` (link:#_allowed_methods[`allowed_methods`]), and
`routes` (link:user/endpoint-routes.adoc#_route_ordering[Route ordering] + the per-route field headings).

=== `tls`

[cols="1,3"]
|===
| Field | Meaning

| (termination)
| The gateway terminates TLS (new certificate) for every connection whose SNI is *not* listed
  in `passthrough_sni`, decrypts, and applies all L7 features (filtering, routing, auth,
  mediation). Termination is not configurable per se -- it is the behaviour of everything that
  is not passthrough. Required for the BFF variants and for L7 gRPC/WebSocket.

| `passthrough_sni`
| A map of *SNI hostname -> topology alias*: connections whose SNI matches a key are relayed
  as opaque TCP (L4), without decryption, to the `host:port` the alias resolves to via
  link:user/environment-variable-overrides.adoc#_topology_and_endpoint_enablement[`topology.properties`] / `TOPOLOGY_<ALIAS>` -- the same indirection routes
  use, so passthrough targets are relocatable per environment too. The alias must resolve at
  boot, and its URL must carry *no base-path* (an L4 relay has no concept of one); either
  violation fails the boot. Passthrough is declared *here, per SNI* -- never on a route. No L7
  feature (filtering, auth, header injection, gRPC/WebSocket/GraphQL handling) applies to a
  passthrough connection. Hostname comparison is *case-insensitive* (RFC 6066). Two guards
  keep the L4/L7 split unambiguous: a route whose `match.host` equals a passthrough SNI
  *fails the boot* (the two declarations contradict each other), and a *terminated* request
  whose `Host` header names a passthrough SNI is rejected with `404` before routing --
  otherwise a client could reach a "passthrough-only" backend at L7 by completing a terminated
  handshake and smuggling the hostname in the `Host` header. Termination (everything else) and
  passthrough (mapped SNIs) coexist on the same listener.

| `min_version`
| Minimum negotiated TLS version for the *terminated* listener; `1.3` recommended, `1.2` floor.
  A `1.2` floor enables TLSv1.2 and TLSv1.3; a `1.3` floor enables TLSv1.3 only. Any other value
  fails the boot rather than being silently dropped. Omit the key to leave the runtime's own
  default protocol set untouched.

| `cipher_suites`
| *Optional* cipher allowlist for the *terminated* listener, given as JSSE suite names (e.g.
  `TLS_AES_256_GCM_SHA384`). Each listed suite is enabled; an omitted or empty list leaves the
  runtime's own suite selection untouched, which is the recommended default -- an allowlist is a
  commitment to maintain it as suites are deprecated. Two operator errors are refused at boot rather
  than producing a listener that binds and then fails every handshake: a suite name this JDK does not
  support, and a list that leaves one of the protocols enabled by `min_version` with nothing to
  negotiate. The second is easy to hit -- a `1.2` floor also enables TLSv1.3, so an allowlist of only
  TLS 1.2 suites (or only TLS 1.3 suites) strands one of them. Keep the list consistent with
  `min_version`, or the boot aborts naming the stranded protocol.

| `alpn`
| Advertised ALPN protocols for the *terminated* listener. `h2` also carries gRPC ("gRPCS" when
  TLS-terminated). Accepted values are `h2`, `http/1.1` and `http/1.0`; any other identifier fails
  the boot. An omitted or empty list leaves ALPN as the runtime configured it.

| `mtls.*`
| Require and verify client certificates against the given CA (terminated connections only --
  on passthrough the gateway never participates in the handshake).
|===

[[_client_ca_carve_out]]
*The `client_ca` carve-out.* `mtls.client_ca` is the one key in this block that points at trust
material, so it needs stating precisely rather than being waved past. What `gateway.yaml` carries is
a *reference* -- a filesystem path naming where the deployment mounted its CA bundle -- never the
material itself. The bundle is deployment-supplied, deployment-mounted and deployment-rotated; the
document commits only to the location, which is why it still moves between environments unedited as
long as the mount point is stable.

link:adr/0025-The_whole_server-TLS_surface_is_neutral_in_gatewayyaml_and_bound_by_exactly_two_seams.adoc[ADR-0025]'s
three-way rule classifies trust *material* as deployment-bound and does not, as written, distinguish
a path reference to that material from the material itself. This carve-out is therefore recorded here
as an explicitly named exception rather than as a rule the ADR already carries. Note the contrast with
the JWKS surface, where
link:adr/0011-gatewayyaml_exposes_JWKS_trust_and_egress_as_neutral_names_bound_by_the_deployment.adoc[ADR-0011]
has `tls_profile` name a *profile* the deployment binds to material, keeping the path out of the
document entirely; `mtls.client_ca` does not currently have that indirection.

[[_tls_scope_limit]]
*Scope limit -- these keys govern the terminated listener only.* `min_version`, `cipher_suites`
and `alpn` are applied to the listener the gateway itself terminates. They do *not* and cannot
apply to a passthrough connection: the SNI front listener terminates nothing -- it reassembles the
ClientHello, reads the SNI, and either relays the still-encrypted stream at L4 or hands it to the
terminated listener (link:adr/0017-Accept-time_SNI_split_at_a_dedicated_front_listener_passthrough_relays_opaquely_at_L4_everything_else_terminates_internally.adoc[ADR-0017]).
For a passthrough hostname the *backend's* own TLS policy is the effective one, end to end. This is
a statement of what the policy can mean, not a limitation more configuration could lift.

[[_tls_precedence]]
*These keys are the effective source when they are declared.* Each of the three policy keys above is
bound onto the terminated listener by a customizer that runs after the runtime has built its SSL
options, so what is written here is what the listener starts with. The binding is *per key*, and the
customizer is a no-op for any key `gateway.yaml` omits -- so an omitted key leaves the runtime's own
resolution in force, including a deployment-supplied environment variable naming the same runtime
knob. Declaring `tls.min_version` makes it authoritative over `QUARKUS_HTTP_SSL_PROTOCOLS`; omitting
it leaves that variable effective. This is not theoretical: the `api-sheriff-mtls` integration
instance pins TLS 1.2 exactly that way today.

Read that as a statement about *precedence*, not as a retraction of the single-source claim. There is
deliberately no raw `quarkus.tls.*` policy key left in `application.properties` -- that remains true,
and it is what removed the inert shipped surface. The route that can still compete is a
deployment-supplied `quarkus.http.ssl.*` variable, which is a different mechanism from a shipped key.
See link:#_server_tls_key_verdicts[Server-TLS key verdicts] for the disposition of every key that
used to live there, and
link:adr/0025-The_whole_server-TLS_surface_is_neutral_in_gatewayyaml_and_bound_by_exactly_two_seams.adoc[ADR-0025]
for the classification rule that decides where a new knob belongs.

*How SNI selection works.* Server Name Indication (RFC 6066) is the hostname the client sends
in the *TLS ClientHello* -- in cleartext, before any encryption is established -- precisely so that a server
fronting multiple hosts can decide how to handle the connection without decrypting anything.
API Sheriff reads it at accept time and splits there:

* *SNI mapped in `passthrough_sni`* -> the gateway stops participating: the entire encrypted
  byte stream, ClientHello included, is relayed to the `host:port` resolved from the SNI's
  topology alias. The
  *backend* completes the handshake and presents its own certificate; the client gets true
  end-to-end TLS. The price is total L7 blindness: the gateway cannot terminate mTLS, choose
  ALPN, inspect paths, inject forwarding headers, or authenticate anything on that connection.
* *Any other SNI, or no SNI at all* -> the gateway terminates: it completes the handshake with
  its own certificate (enforcing `min_version`, `alpn`, `mtls`) and the full L7 pipeline
  applies. A ClientHello *without* SNI (rare; old clients or IP-address dialing) can never
  match a passthrough entry and is therefore always terminated.

Matching is *exact and case-insensitive* (hostnames are case-insensitive per RFC 6066/RFC 952);
wildcard entries (`*.internal.example.com`) are *not* supported initially -- list each host.
Note the two guards described under `passthrough_sni` above: the boot-time route/`match.host`
collision check and the runtime rejection of terminated requests whose `Host` header names a
passthrough SNI.

*Encrypted ClientHello (ECH).* ECH hides the true (inner) hostname; the outer ClientHello
carries the ECHConfig's `public_name` as its cleartext SNI, and that outer name is the *only*
thing SNI-based selection can ever act on. Two consequences: passthrough keyed on the
`public_name` is ECH-*compatible* -- the intact ClientHello is relayed and the backend holding
the ECH key completes the handshake (that is the fronting model). Conversely, hosts the
gateway *terminates* must not publish ECHConfigs pointing at it: the gateway holds no ECH key,
so an ECH client would treat the handshake as ECH rejection (it authenticates the
`public_name`, refuses to send the real request, and retries or aborts). Listing an *inner*
hostname in `passthrough_sni` does nothing -- it never appears in the outer SNI.

[[_tls_active]]
*Status -- active.* The `tls.passthrough_sni` and `tls.mtls` blocks are *enforced at runtime*, not
merely parsed: an accept-time front listener reads the SNI from the reassembled ClientHello and
splits each connection at L4 (passthrough) or L7 (terminated); terminated connections apply
`mtls` client-certificate verification; and the runtime Host-vs-SNI smuggle guard rejects a
terminated request whose `Host` names a passthrough SNI with `404` before route selection. Before
each match the runtime normalizes both sides: the SNI is lower-cased and one trailing FQDN dot is
removed, and the terminated request's `Host` additionally has a single `:port` suffix stripped -- so
`Backend.Example.Com.`, `backend.example.com`, and `backend.example.com:8443` all resolve to the same
passthrough key. Three
constraints an operator must keep in mind, all stated above and restated here because they are the
common configuration mistakes: SNI matching is *exact* -- *no wildcard* entries; a passthrough
alias URL carries *no base path*; and `mtls` applies to *terminated connections only* (the gateway
never participates in a passthrough handshake). Operating these keys -- including the emergency
trust-root-replacement blast radius -- is covered in the link:user/tls-edge.adoc[operator TLS-edge
topic]; the front-listener architecture and the fail-closed (GW-06) rationale are covered in the
link:development/tls-edge.adoc[developer TLS-edge topic].

[[_management]]
=== `management`

The optional global `management` block carries the TLS policy of the *management interface* -- the
separate port serving health and metrics. It follows the same rule as `tls`: neutral names for
*policy*, nothing else.

[cols="1,3"]
|===
| Field | Meaning

| `tls.enabled`
| Whether the management interface serves over TLS. *Defaults to `true`*, which is also the shipped
  posture -- HTTPS on the management port is the secure default and stays the default. Setting it to
  `false` selects a key-less named TLS bucket, so the management listener starts on plain HTTP.

| (no `port` key)
| *This block declares no port, deliberately.* A `management.port` written in `gateway.yaml` is
  *refused at boot* with a message naming `quarkus.management.port` /
  `QUARKUS_MANAGEMENT_PORT` -- the property that does own it -- and
  link:adr/0025-The_whole_server-TLS_surface_is_neutral_in_gatewayyaml_and_bound_by_exactly_two_seams.adoc[ADR-0025].
  The refusal is implemented in `schema/gateway.schema.json`: the `port` property is declared solely
  in order to fail, so the actionable sentence lands at the `/management/port` JSON pointer rather
  than surfacing as a generic unknown-key error against the parent object. The port default is
  `9000`.

| (no context-path key)
| *This block declares no root path either, and for a different reason from the port.* The
  management context path is `quarkus.management.root-path` (shipped default `/q`), and it is a
  *build-time* key: it is fixed at augmentation, so no runtime source could project it whatever
  ordinal that source had -- unlike the port, which is deployment-bound and merely omitted. Moving it
  is a rebuild, through `api-sheriff/pom.xml`'s `-Dsheriff.management-context-path` seam. It is also
  an *independent absolute* key: moving the *application* context path does not move the probes with
  it. Both properties, the seam that sets them and the mechanism that makes the seam act are in
  link:user/context-path.adoc[The Context Path].
|===

*Why there is no port here.* The management block reaches the runtime through a configuration
source whose ordinal sits deliberately above the environment's, so a policy named in `gateway.yaml`
is not silently overridden by a deployment variable. A *port* projected at that ordinal would in
turn silently override `QUARKUS_MANAGEMENT_PORT` -- the operator surprise the ordinal rule exists to
prevent -- and the only way to let the environment win would be a second, lower-ordinal source that
ADR-0025 rejects. The omission is therefore structural, and it is made discoverable by refusing the
key rather than ignoring it.

*The single-port constraint: a downgrade takes the whole surface.* Unlike the main HTTP listener,
the management interface has exactly *one* port -- there is no management `ssl-port` and no
management `insecure-requests` mode, so there is no simultaneous HTTPS listener to fall back to.
`tls.enabled: false` therefore takes health *and* metrics to plain HTTP in their entirety, and every
consumer probing that port over HTTPS breaks. That is why the downgrade is *audited with a loud
boot `WARN`* (`ApiSheriff-115`, see link:LogMessages.adoc[Log Messages]) rather than passing
silently -- and why it is a `WARN` and never a boot refusal: plain-HTTP management behind a trusted
network boundary is a legitimate deployment.

*Two doors, one lever.* The neutral key above and the deployment-level
`QUARKUS_MANAGEMENT_TLS_CONFIGURATION_NAME` environment variable land on the *same* runtime key.
`tls.enabled: true` and an omitted block both project *nothing*, which is exactly what keeps the
deployment variable a working route. The operator guidance -- when the downgrade is legitimate, and
why `quarkus.management.enabled=false` is *not* the way to get a plain probe endpoint -- lives in
the link:user/tls-edge.adoc[operator TLS-edge topic].

*The container-level health signal is not a `gateway.yaml` key.* The image bakes its own
`HEALTHCHECK` -- what `docker ps` renders as `(healthy)` -- and that is a property of the *artifact*,
not of the configuration document. There is no `health_check` block, no cadence key and no enable
toggle for it anywhere in this file; the whole declaration lives in
`api-sheriff/src/main/docker/Dockerfile.native`. It is also not the same signal as the readiness
endpoint the port above serves beneath the configured management context path
(link:user/context-path.adoc[The Context Path]), and the two are routinely conflated: the baked
probe is a protocol-blind TCP accept and therefore reports *liveness*, whereas readiness is
`GatewayReadinessCheck`'s answer over the management interface. One constraint follows from the
probe being configuration-free: it targets `9000` as a compiled-in constant and does not follow
`QUARKUS_MANAGEMENT_PORT`, so a deployment that moves the management port makes the baked check fail
closed -- never healthy -- and the only remedy is an image rebuilt against the new port. Overriding
the `HEALTHCHECK` does not reach it, because the override still names the one executable the image
carries and that binary probes the constant it was built with
(link:adr/0039-The_distroless_images_health_check_is_answered_by_the_application_binary_before_boot.adoc[ADR-0039]).
What that state does and does not prove for an operator is covered in
link:user/compose-sample.adoc#_reading_the_container_health_signal[Reading the container health signal].

[[_server_tls_key_verdicts]]
=== Server-TLS key verdicts

`gateway.yaml` is the effective source of server-TLS *policy* for every policy key it declares; a key
it omits falls back to the runtime's own resolution, which a deployment-supplied environment variable
can still reach (see link:#_tls_precedence[the precedence rule above]). The table below records the
disposition of every raw `quarkus.*` server-TLS key that used to live in `application.properties`,
classified by
link:adr/0025-The_whole_server-TLS_surface_is_neutral_in_gatewayyaml_and_bound_by_exactly_two_seams.adoc[ADR-0025]'s
three-way rule -- *policy* (neutral in `gateway.yaml`), *deployment-bound* (ports and material,
supplied by the deployment), *build-time* (fixed when the image is built, never in the runtime
surface). The two exceptions to the "no raw server-TLS policy key remains" bar are named explicitly;
an undocumented exception would be a silent trim.

|===
| Key | Class | Disposition | Reason and destination

| `quarkus.tls.protocols`
| policy
| deleted
| Replaced by `tls.min_version`. The key never reached the listener: the runtime consults its TLS
  registry only when the certificate also comes from the registry, and this gateway supplies its
  certificate through `quarkus.http.ssl.certificate.*` -- so the declared floor was inert.

| `quarkus.tls.cipher-suites`
| policy
| deleted
| Replaced by `tls.cipher_suites`, inert for the same reason.

| `quarkus.tls.alpn`
| policy
| deleted
| Replaced by `tls.alpn`, inert for the same reason.

| `quarkus.http.ssl.client-auth`
| policy
| deleted
| Replaced by `tls.mtls`, which was already bound programmatically -- the customizer runs after the
  runtime builds the SSL options and overwrites whatever this key had set, so `gateway.yaml` was
  already the effective source and the key was misleading.

| `quarkus.ssl.native`
| *build-time*
| *exception 1 -- relocated*
| Declared in `api-sheriff/pom.xml`'s `native` profile. It is a GraalVM knob fixed when the image is
  built, so `gateway.yaml` could never make it take effect and `application.properties` would only
  make it look like a runtime key. It lives with the other build-time native properties, in the
  profile that is active exactly when the knob has meaning.

| `quarkus.http.ssl-port`
| *deployment-bound*
| *exception 2 -- retained*
| Stays in `application.properties` as the default (`8443`), overridden per deployment by

  could not express.

| `quarkus.http.insecure-requests`
| *deployment-bound*
| *exception 2 -- retained*
| Same class: a port/exposure knob the deployment owns, not TLS policy.

promoted into `gateway.yaml` -- it arrives through `quarkus.http.ssl.certificate.*` and the
`QUARKUS_*` environment contract, exactly as the JWKS trust profiles of
link:adr/0011-gatewayyaml_exposes_JWKS_trust_and_egress_as_neutral_names_bound_by_the_deployment.adoc[ADR-0011]
do. The full operator-facing split of what stays deployment-bound versus what `gateway.yaml` owns is
in link:user/environment-variable-overrides.adoc[Environment-variable overrides].

[[_protocols]]
=== `protocol`

Each route declares the protocol it serves: `http` (the default), `graphql`, `grpc`, or
`websocket`. All four are supported *from the start* (link:adr/0002-initial-scope.adoc[ADR-0002]);
HTTP/3 is deferred. The value selects handshake/streaming behaviour only (WebSocket upgrade,
gRPC streaming); the semantics of each protocol -- and what the security filter does and does
not inspect -- are defined once in
link:architecture.adoc#_protocol_support[Architecture -- Protocol Support].

A `protocol: websocket` route carries one additional per-route block --
link:#_websocket[`websocket`] -- holding both WebSocket keys:
link:#_allowed_origins[`allowed_origins`] (a mandatory `Origin` allowlist on bearer WebSocket
routes) and `idle_timeout_seconds` (the established-relay idle-timeout bound). Both are
documented immediately below.

[[_allowed_origins]]
=== `websocket.allowed_origins` (WebSocket routes)

A per-route `Origin` allowlist for a `protocol: websocket` route whose *effective* auth is
`require: bearer`. It is declared *inside the route's `websocket` block* -- `allowed_origins` is
not a route-level key, and writing it as a sibling of `websocket` fails the boot as an unknown
key. It is *`security_headers`-adjacent* -- an `Origin`-header check performed at the handshake,
not a routing matcher -- but, unlike the gateway/anchor-scoped
link:#_security_headers[`security_headers`] block, it is scoped *per route*: the set of browser
origins allowed to open a socket is a property of the individual bearer WebSocket route. The
check runs on the HTTP upgrade request, *before* the upstream is dialled.

[cols="1,3"]
|===
| Attribute | Value

| Type
| A *list* of origin strings, each `scheme://host[:port]`.

| Default
| *None.* There is deliberately no "any origin" default. On a bearer WebSocket route the field
  is *mandatory and non-empty* (see Fail-closed).

| Allowed values / matching
| *Exact match*, compared as full origins (scheme + host + port). The *host* is compared
  *case-insensitively* (hostnames are case-insensitive per RFC 6066); the *scheme and port* are
  compared exactly. There are *no wildcards*, no suffix forms, and no regular expressions -- list
  each permitted origin in full.

| Fail-closed / validation
| The upgrade request's `Origin` header must *exactly match* a listed origin or the *handshake is
  rejected* before any upstream dial. An *absent or empty* `websocket.allowed_origins` on a bearer
  WebSocket route *fails the boot* -- deny-by-default: a bearer socket with no allowlist would
  otherwise admit every origin, which is never the intended posture. A `websocket` block on a
  non-`websocket` route, or `allowed_origins` on a WebSocket route whose effective auth is not
  `require: bearer`, is a configuration error and fails the boot.
|===

[source,yaml]
----
# a bearer WebSocket route (endpoints/*.yaml)
- id: live-updates
  protocol: websocket
  match: { path_prefix: /api/stream, host: api.example.com }
  auth: { require: bearer }
  websocket:                       # BOTH WebSocket keys live inside this block
    allowed_origins:               # MANDATORY, non-empty on a bearer WS route; exact origins
      - https://app.example.com    #   (scheme+host+port), host case-insensitive, no wildcards
    idle_timeout_seconds: 300      # optional; default 300 (see "websocket" below)
  upstream: { path: /stream }
----

[[_websocket]]
=== `websocket` (WebSocket routes)

The per-route WebSocket block. It carries *both* WebSocket keys -- the
link:#_allowed_origins[`allowed_origins`] allowlist documented above and the idle-timeout bound
below. It is valid only on a `protocol: websocket` route.

[cols="1,3"]
|===
| Field | Meaning

| `allowed_origins`
| The fail-closed `Origin` allowlist -- *mandatory and non-empty* on a bearer WebSocket route.
  Documented in full under link:#_allowed_origins[`websocket.allowed_origins`] above.

| `idle_timeout_seconds`
| *Per-route integer, default `300`.* Bounds an established bidirectional relay: when *no frame
  travels in either direction* for this many seconds, the relay is closed. WebSocket
  *ping/pong counts as activity*, so an application- or gateway-level heartbeat keeps the socket
  open. When declared it must be a *positive integer*; when omitted, the default `300` applies. It
  is valid *only* on a `protocol: websocket` route.
|===

[[_security_filtering]]
=== `security_filter`

The explicit *not-a-WAF* boundary: allowlists and limits, no attack-signature matching. Maps onto
`cui-http`'s `SecurityConfiguration` and pipelines:

[cols="2,2,2"]
|===
| Config field | cui-http mapping | Notes

| `profile`
| `SecurityConfiguration.strict()` / `lenient()`; `minimal` maps to *no preset*
| The inbound-filter mode. `strict` and `lenient` are baseline presets that the limits below
  override individually. `minimal` is a *dispatch mode*, not a preset: it carries no
  `SecurityConfiguration` of its own and inherits its limits from the nearest non-`minimal` profile in
  the fallback chain (landing on `strict` when the whole chain is `minimal`), which is what keeps its
  retained `max_body_bytes` cap concrete. See link:#_the_minimal_mode[The `minimal` mode].

| `max_body_bytes`
| *(gateway-enforced, under a framework floor)*
| DoS guard, and the *effective* cap for the route: a request whose body exceeds it is rejected
  *413*, carrying an `application/problem+json` envelope whenever the request reaches gateway
  enforcement (see "Shadowing at the boundary" below -- a `Content-Length` breach of the framework
  floor is answered by the framework with a bare `413` instead). `cui-http` removed its BODY validation
  pipeline ("body content validation should be handled at application layer"), so the gateway
  enforces the cap itself while reading the request body; `SecurityConfiguration.maxBodySize` is
  not wired. The cap only takes effect *below the framework floor* described immediately below.

| `max_header_count` / `max_query_params`
| `maxHeaderCount` / `maxParameterCount` (`RequestCollectionValidator`)
| Hash-collision / resource-exhaustion guards.

| `max_header_value_length` / `max_param_value_length`
| `maxHeaderValueLength` / `maxParameterValueLength`
| Per-item length caps (a single header value / parameter value, not the whole header block),
  measured in *characters* -- the `cui-http` unit -- not bytes.

| (path safety)
| `URLPathValidationPipeline`
| Traversal / encoding / character / pattern checks. Run twice under different policies: once in the
  *non-skippable pre-route floor* under the gateway-wide baseline (this is the run that produces the
  canonical path), and again *post-route* under the route's own configuration when that configuration
  diverges from the baseline. Only the second, divergent run is switched off by `profile: minimal`; the
  floor's run cannot be switched off by any profile value.

| `allowed_header_names` / `blocked_header_names`
| `allowedHeaderNames` / `blockedHeaderNames`
| Optional header-name allow/block lists.

| `allowed_content_types`
| `allowedContentTypes`
| Optional `Content-Type` allowlist for request bodies.
|===

[[_preset_limits]]
==== Preset limits

The two presets are not just "tight" and "loose" labels -- they carry concrete numbers, and a route
that declares no limit key of its own lands exactly on them. Because an omitted `security_defaults`
block resolves to `strict`, the `strict` column is what an undeclared deployment actually enforces.

[cols="3,1,1"]
|===
| Limit | `strict` | `lenient`

| `max_body_bytes` (`maxBodySize`)
| 1 MiB (1048576)
| 10 MiB (10485760)

| `max_query_params` (`maxParameterCount`)
| 20
| 500

| `max_header_count` (`maxHeaderCount`)
| 20
| 100

| `max_param_value_length` (`maxParameterValueLength`)
| 1024
| 8192

| `max_header_value_length` (`maxHeaderValueLength`)
| 1024
| 8192

| path length (`maxPathLength`)
| 1024
| 8192

| parameter / header / cookie *name* length
| 64
| 256

| cookie value length / cookie count
| 1024 / 10
| 8192 / 50
|===

All length limits are measured in *characters* -- the `cui-http` unit -- not bytes. The presets also
differ in their non-length validators: `strict` normalizes Unicode, compares case-sensitively, fails
on suspicious patterns, and permits neither double encoding, control characters, nor extended ASCII;
`lenient` inverts each of those. Neither preset ever permits null bytes.

[[_pre_route_header_carve_outs]]
==== Pre-route header-name carve-outs

The *non-skippable pre-route floor* measures every inbound header value against the resolved
baseline `max_header_value_length` above. Two header names are carved out of that cap, each by a
dedicated value pipeline selected on the header *name*. Both carve-outs are declared on gateway-wide
blocks, because the floor runs *before route selection* -- no anchor is resolved at that point, so
neither relaxation can be scoped per route or per anchor
(link:adr/0019-Reserved_BFF_paths_bypass_the_url-parameter_value_pipeline_and_the_cookie-header_length_relaxation_is_gateway-wide.adoc[ADR-0019]).

[cols="1,2,2"]
|===
| Header | Budget key | Bound

| `Cookie` / `Set-Cookie`
| `oidc.session.max_cookie_size` (plus a fixed cookie-header overhead)
| Present *only* in an active cookie-mode BFF; a bearer-only or server-mode gateway keeps the
  resolved baseline on every header. A sealed session cookie is designed to a multi-kilobyte budget
  the baseline would otherwise reject on every authenticated request.

| `Authorization`
| `security_defaults.max_authorization_header_value_length` (default `8192`)
| *Unconditional* -- every gateway is bearer-capable, so there is no mode that switches it off. A
  bearer token plus its `Bearer ` prefix routinely exceeds the `strict` baseline of 1024 characters,
  which would reject every bearer request `400` before bearer validation ever runs.
|===

*Only the length cap changes.* Each carve-out configuration is seeded from the resolved baseline and
overrides `max_header_value_length` alone, so every non-length validator -- null-byte,
control-character, extended-ASCII and injection-pattern checks -- still applies to the carved-out
value exactly as to any other header. That bound is enforced *structurally* by the seeding, not by
convention.

*Both carve-outs survive the post-route re-run.* A route whose `security_filter` resolves to a
configuration differing from the gateway baseline -- a route declaring nothing more than a raised
`max_body_bytes` already qualifies -- has its headers re-validated after route selection under that
route's own configuration. That re-validation applies the *same* two carve-outs, so the raised cap
reaches `Authorization` and `Cookie` / `Set-Cookie` values on *every* route, not only on routes
without a `security_filter` block. The post-route cap is `max(route max_header_value_length, budget)`:
a route that raises its own cap above the budget keeps its higher cap, and the carve-out never lowers
a route's own cap. Everything else is unchanged -- the re-run seeds each carve-out from the *route's*
configuration, so every non-length validator stays on the route's setting, and the two header names
are the only ones affected.

*The framework body-size floor.* `max_body_bytes` is a cap the gateway applies *on top of* an
underlying HTTP-framework limit, `quarkus.http.limits.max-body-size`. The framework limit is the
floor every declared cap sits under: a route cannot accept more than the floor allows, whatever it
declares. API Sheriff ships the floor at *`64M`* (67108864 bytes) in `application.properties`,
matching the largest `max_body_bytes` in the shipped topology. Without that declaration Vert.x
applies its own 10 MiB default and silently clips every larger declared cap, so the route's own
limit never fires.

The relationship is *boot-enforced*: a deployment that declares a `max_body_bytes` larger than the
floor fails fast at startup rather than running with a cap that cannot be honoured. Raising a
declared cap therefore means raising `quarkus.http.limits.max-body-size` in the same change.

*Shadowing at the boundary.* When the floor is set *equal to* the largest declared cap, the
framework's own `Content-Length` pre-check answers a breach of that largest cap with a bare `413`
(`Connection: close`, empty body) *before the gateway's request handling runs* — so the RFC 9457
`application/problem+json` envelope is rendered only for routes capped strictly *below* the floor.
An operator who wants the gateway's own envelope on the largest-capped route sets the floor *above*
that cap rather than equal to it. The integration stack does exactly this: it overrides the floor to
`128M` so the gateway, not the framework, renders the rejection.

*Chunked requests.* A chunked request carries no `Content-Length`, so it passes the framework's
pre-check untouched and is capped by the gateway's streaming byte counter instead — it always
receives the gateway's `application/problem+json` envelope, regardless of where the floor sits.

*Whitelisting.* `cui-http` has no path allow-list knob, so path whitelisting is enforced at the
gateway layer by `allowed_paths`: a request whose validated, normalized path matches no entry is
rejected -- the manifest's "WAF via path white-listing". Header-name and content-type allow/block
are configured via `allowed_header_names` / `blocked_header_names` / `allowed_content_types`
above, wired to the corresponding `cui-http` knobs. *What reaches the upstream is a separate,
later question* answered by the route's link:#_forward[`forward`] block, which offers a
positive-list (`headers_allow` / `query_allow`), a negative-list (`headers_deny` / `query_deny`)
or the forward-all baseline -- do not read `forward` as an inbound admission control; a request
that got this far was already admitted.

*`allowed_paths` matching semantics.* An entry is a literal path in which `{name}` placeholders
each match *exactly one* path segment (any characters except `/`). There are no wildcards, no
regular expressions, and no multi-segment placeholders. Matching runs *after* the `cui-http`
validation pipeline has decoded and normalized the path, so encoding tricks (`%2e%2e`, overlong
UTF-8, doubled slashes) cannot bypass the allowlist. `/api/orders/{id}` matches
`/api/orders/42` but neither `/api/orders` nor `/api/orders/42/items`.

=== `auth`

Whether authentication is required is defined *per endpoint file*: `endpoint.auth` is
mandatory (unless the endpoint's anchor declares an `auth` block -- see
link:user/anchors.adoc#_anchors[Anchors]) and is the default posture for every route in the file. A route-level `auth` block
replaces the endpoint default wholesale for that route (no field merging). "Effective auth"
below means the route's own block if present, else the endpoint's. `required_scopes` is valid
at either level; because override is wholesale, a route-level block that omits it *drops*
endpoint-level scope enforcement for that route. Weakening overrides (lower `require`, dropped
scopes) are legal -- a health route under a bearer endpoint is the normal case -- but every one
is called out in the boot log, so weakening is always an explicit, audited choice.

[cols="1,3"]
|===
| Value | Behaviour

| `require: none`  | No authentication (e.g. `/health`). Must be written explicitly at the endpoint (or route) level -- an endpoint file without an `auth` block, and without an anchor-provided one, fails the boot (see link:user/endpoint-routes.adoc#_defaults_for_omitted_blocks[Defaults for omitted blocks]).
| `require: bearer`| Offline-validate the incoming `Authorization: Bearer` via `token-sheriff-validation` against the issuers in link:#_token_validation[`token_validation`]; enforce `required_scopes`. link:variants/01-base-gateway.adoc[Variant 1].
| `require: session`| Require a valid mediated OIDC session per the link:#_oidc[`oidc`] block; inject the token upstream. The BFF variants. An unauthenticated *navigation* request (one that accepts `text/html`, i.e. a browser page load) is redirected into the auth-code flow; any other unauthenticated request (XHR/`fetch`, API clients) receives `401` `application/problem+json` -- redirecting a JSON call is useless to its caller. The distinction is content negotiation, not per-route configuration. `required_scopes` on a session route are enforced against the *mediated* access token's granted scopes -- so they must be requested in `oidc.scopes` at login, or every request on the route fails with `403`.
|===

Routes with different `require` values may coexist in one deployment; the canonical statement
of the variants-are-route-postures rule is in link:variants/README.adoc[Variants].

[[_token_validation]]
=== `token_validation`

Configures offline bearer validation for `require: bearer` routes; it materializes the
`token-sheriff-validation` `IssuerConfig`/`TokenValidator` wiring described in
link:variants/01-base-gateway.adoc[Variant 1]. Required when any route's *effective* auth is
`require: bearer`.

[cols="1,3"]
|===
| Field | Meaning

| `issuers[].name`
| Unique label, used in logs and metrics.

| `issuers[].issuer`
| The expected `iss` claim (maps to `IssuerConfig.issuerIdentifier`). Multiple issuers are
  supported; the validator selects by the token's `iss`.

| `issuers[].audience`
| The expected `aud` claim (maps to `IssuerConfig.expectedAudience`). *The `aud` claim is
  required once an audience is configured*: `IssuerConfig.azpAudienceFallbackEnabled` is `false`,
  so a matching `azp` does *not* substitute for a missing `aud` -- an `azp`-only token is
  rejected. If your IdP issues `azp`-only tokens, either configure it to emit `aud`, or omit
  the `audience` key entirely -- omitting it disables audience validation wholesale.

| `issuers[].jwks`
| Key material for signature verification: `source: http` with a `url` (cached, periodically
  refreshed), or `source: file` -- the latter for air-gapped deployments.

| `issuers[].jwks.allowed_egress_hosts`
| SSRF egress allowlist for `source: http`, applied on the initial JWKS fetch *and* every
  background refresh. *Omit it unless you must.* Absent or empty keeps
  `EgressPolicy.secureDefault()`, which refuses a JWKS URL resolving to a loopback,
  link-local, site-local, any-local, multicast, or unique-local address. Each entry exempts
  exactly one host from that check -- the match is host-exact, with no wildcard or suffix
  form -- so widen it only for a trusted IdP that genuinely lives on a private network, and
  name that one host. See link:security-threat-model.adoc#gw-05[GW-05] and
  link:security-threat-model.adoc#bff-07[BFF-07].

| `issuers[].jwks.tls_profile`
| Name of the logical *trust profile* used to verify the IdP's server certificate when fetching
  the JWKS over `source: http`. Omit it for an IdP presenting a publicly-trusted certificate --
  the JWKS client then uses the JVM default trust store. Name a profile when the IdP presents a
  certificate from an internal or corporate CA. See link:#_jwks_trust_profiles[Trust profiles]
  below for how a name is bound to concrete anchors.
|===

The BFF variants do *not* read this block: they validate the tokens they retrieve against the
issuer configured in link:#_oidc[`oidc`].

[[_jwks_trust_profiles]]
==== Trust profiles (`jwks.tls_profile`)

By default the JWKS client verifies the IdP's certificate against the JVM's default trust store.
That is correct when the IdP presents a certificate from a public CA, and wrong in two common
deployments: an IdP fronted by an *internal or corporate CA*, and a *cluster-internal IdP* whose
certificate is issued by the cluster's own authority. In both cases the fetch fails PKIX path
building, the key set never loads, and every bearer request is rejected -- a failure that looks
like a token problem but is a trust problem.

`tls_profile` fixes that by naming the trust anchors to use:

[source,yaml]
----
token_validation:
  issuers:
    - name: corporate
      issuer: https://idp.corp.internal/realms/main
      jwks:
        source: http
        url: https://idp.corp.internal/realms/main/protocol/openid-connect/certs
        allowed_egress_hosts: [idp.corp.internal]   # private address -> widen egress (GW-05)
        tls_profile: corporate-idp                  # internal CA -> name the trust anchors
----

===== The name is not the material

`tls_profile` is a *logical* name in API Sheriff's own vocabulary. It carries no trust store path,
no password, and no runtime detail. The deployment binds the name to concrete trust material:

[source,properties]
----
quarkus.tls.corporate-idp.trust-store.p12.path=/etc/sheriff/corporate-ca.p12
quarkus.tls.corporate-idp.trust-store.p12.password=${TRUSTSTORE_PASSWORD}
----

So the mapping runs `gateway.yaml` name -> deployment binding -> trust anchors -> JWKS client.
`gateway.yaml` expresses *intent* ("verify this IdP against the corporate anchors"); the
deployment supplies *material*. That split is deliberate, and it buys three things:

* *Secrets stay out of `gateway.yaml`.* A trust-store password never appears in the document you
  edit, review, and commit.
* *No second key-store implementation.* Loading, formats, reloads, and rotation are already solved
  on the deployment side; API Sheriff consumes the result rather than growing a weaker copy.
* *Portability.* The same `gateway.yaml` moves between environments that bind the same profile
  name to different anchors -- dev, staging, production -- with no edit.

NOTE: `gateway.yaml` and its JSON schema deliberately never name the mechanism that binds the
profile; that binding is an implementation detail behind a single seam. Startup *diagnostics*
deliberately do name it, because an operator staring at an unbound profile needs the exact knob to
set, not an abstraction.

===== When the profile is not bound

A named profile that the deployment does not define is a *startup failure*, not a fallback:

[source,text]
----
Issuer 'corporate' names jwks.tls_profile 'corporate-idp' but no such trust profile is
configured — define it via quarkus.tls.corporate-idp.trust-store.*
----

The gateway refuses to start, consistent with how every other configuration violation is handled.
Falling back to default trust would be worse than failing: it would either surface later as an
obscure JWKS fetch error, or -- if the IdP happens to chain to a public CA -- quietly succeed
against anchors the operator never intended to trust.

===== When the profile is bound but carries no anchors

A profile that exists but supplies no trust material is refused too -- for exactly the same reason,
and this is the case that is easy to reach by accident. The runtime registers a named bucket as
soon as *any* `quarkus.tls.<name>.*` key is present, so a bucket that sets only, say, a reload
period is a real, resolvable profile with nothing in it:

[source,properties]
----
# a bound profile with no anchors -- refused, not silently accepted
quarkus.tls.corporate-idp.reload-period=24H
----

[source,text]
----
Issuer 'corporate' names jwks.tls_profile 'corporate-idp' but that profile carries no trust
material — it would verify the IdP against the JVM default trust store instead of the anchors
the name promises; define it via quarkus.tls.corporate-idp.trust-store.*
----

Without this check the deployment would start and the JWKS client would verify the IdP against the
JVM default trust store -- the very fallback the previous section refuses -- while `gateway.yaml`
still reads as though corporate anchors were in force. A named profile therefore means *these
anchors*, never *whatever the JVM happens to trust*.

===== When the profile disables verification entirely

A profile that sets `trust-all` is refused as well. It is the same failure one step worse: the
bucket resolves, it does carry trust options, and the SSL context it yields accepts *any*
certificate.

[source,properties]
----
# a bound profile that verifies nothing -- refused, not silently accepted
quarkus.tls.corporate-idp.trust-all=true
----

[source,text]
----
Issuer 'corporate' names jwks.tls_profile 'corporate-idp' but that profile sets
quarkus.tls.corporate-idp.trust-all — the JWKS client would accept any certificate, so a machine
on the path to the IdP could serve its own signing keys; bind the profile to real anchors via
quarkus.tls.corporate-idp.trust-store.*
----

This is a man-in-the-middle vector on the JWKS path rather than a merely weakened check. The key
set fetched over that connection is what every bearer token is validated against, so an on-path
machine free to serve its own JWKS chooses the signing keys the gateway will accept -- and
certificate verification is the only thing standing in its way.

The check runs *before* the anchor-free check above, and that order is load-bearing rather than
incidental. A `trust-all` bucket carries trust material -- the runtime binds it to a
trust-everything configuration -- so it satisfies the anchor-free guard and would slip past it
undetected. Testing for it first is what keeps the worse failure from hiding behind the weaker
one. A named profile means *these anchors*; it never means *no verification at all*.

An issuer that omits `tls_profile` is unaffected: no trust configuration is applied at all, and
the JWKS client keeps the JVM default trust store. That is the one supported way to ask for default
trust -- by saying nothing, not by naming an empty profile.

===== Relationship to `allowed_egress_hosts`

The two settings are independent and frequently needed together, because they solve different
halves of the same deployment. `allowed_egress_hosts` answers *"may I connect to this address?"*
(the SSRF egress guard, which refuses private addresses by default); `tls_profile` answers *"do I
trust the certificate I get back?"*. A cluster-internal IdP on a private address behind an internal
CA needs both; a public-internet IdP behind a public CA needs neither.

[[_oidc]]
=== `oidc`

The confidential-client block used by the BFF variants
(link:variants/02-bff-session.adoc[Variant 2] and link:variants/03-bff-cookie.adoc[Variant 3]);
ignored when no route's effective auth is `require: session`.

[cols="1,3"]
|===
| Field | Meaning

| `issuer`, `client_id`, `client_secret`, `scopes`, `redirect_uri`
| The OIDC confidential-client identity. `client_secret` must be an `${ENV_VAR}` reference.
  `redirect_uri` is the gateway's own callback route, registered exactly at the IdP.
  *Register it as a plain redirect target reached by a `GET`*: the gateway drives the
  authorization request with `response_mode=query`, so the IdP must be free to answer a `302`
  carrying `code` and `state` in the query string. An IdP client pinned to force `form_post`
  breaks the flow. *There is no configuration knob for the response mode* -- it is fixed in code
  (see link:architecture.adoc#_oidc_callback_response_mode[Architecture -- OIDC callback response
  mode]), deliberately, because it is coupled to the `SameSite=Lax` browser-binding cookie.

| `login.path`
| Gateway-owned *login-initiation* entry point -- the reserved path a browser navigates to in
  order to *start* a login (the mirror of the `redirect_uri` callback that *lands* it). A caller
  that already holds a live session is redirected straight to the same-origin-validated return
  URL (no fresh auth-code flow); an unauthenticated caller is driven into the authorization-code
  flow. Optional -- omit it and the deployment simply has no gateway-owned login-start URL.
  Registered as a reserved gateway path when present.

| `user_info.path`
| Gateway-served *user-info* endpoint returning the curated identity view assembled from the
  session's tokens -- never a passthrough of the raw ID/userinfo claims. Registered as a
  reserved gateway path when present; omit it and no user-info endpoint is exposed.

| `user_info.allowed_claims`
| The operator claim *allowlist* bounding what `user_info.path` may ever disclose. The secure
  default is *closed*: an empty (or omitted) allowlist discloses *nothing*, so the operator --
  never the browser client -- widens disclosure. A claim absent from this list is never returned,
  regardless of what the caller requests.

| `user_info.default_view`
| The claim selector returned when the caller requests no explicit claims. Every entry *must* lie
  within `user_info.allowed_claims` (a default-view claim outside the allowlist fails the boot),
  so the curated default can never exceed the disclosure ceiling.

| `logout.path`
| Gateway-served logout endpoint (default `/logout`): revokes the held tokens (RFC 7009),
  destroys the local session/cookie, and redirects to the IdP `end_session_endpoint` with
  `id_token_hint`, `post_logout_redirect_uri`, and a *session-bound `state`* (per `CLIENT-13`).
  Because the session is already destroyed at that point, the `state` is sealed into a
  short-lived (60 s), single-use `+__Host-sheriff-logout+` cookie set alongside the redirect;
  the return leg verifies against that cookie and clears it -- stateless, so it works
  identically in both session modes.

| `logout.post_logout_redirect_uri`
| The return leg from the IdP. It must be a *gateway-owned* path -- the gateway has to see the
  return to verify the session-bound `state` -- pre-registered at the IdP and compared by
  *exact string match*, never pattern or prefix (open-redirect defence). After verification the
  browser is redirected to `logout.final_redirect`.

| `logout.final_redirect`
| The application URL the browser lands on after the verified logout round-trip. Optional;
  defaults to `/`.

| `logout.backchannel_path`
| Receiver for OIDC back-channel logout tokens from the IdP. Meaningful in `mode: server`
  only, where a validated logout token destroys the matching session; in `mode: cookie` the
  endpoint is *disabled* (`404`) -- there is no server-side state a logout token could
  destroy. See the statelessness limitation in link:variants/03-bff-cookie.adoc[Variant 3].

| `session.csrf.trusted_origins`
| The browser origins allowed to make *unsafe-method* (non-GET/HEAD/OPTIONS) calls to
  `require: session` routes -- i.e. the origins the SPA is served from. Defaults to the origin
  of `redirect_uri`. The `Origin` header carries the *calling page's* origin, so an
  application served from a different host than the gateway must be listed here.
  Compared as full origins (scheme + host + port), exact match. A *cross-origin* SPA needs
  *both* halves configured: this list (what the gateway *accepts* -- CSRF) and
  `security_headers.cors` enabled with `allow_credentials: true` (what the browser *permits*).
  This works only for *same-site* origins -- a different origin under the same registrable
  domain, e.g. `app.example.com` calling `gw.example.com` -- because the session cookie is
  fixed at `SameSite=Lax`: a truly *cross-site* SPA (different registrable domain) never gets
  the cookie attached to its calls, by design. Host the application under the same site as the
  gateway. See link:variants/02-bff-session.adoc#_csrf_defence[CSRF Defence].

| `session.mode`
| `cookie` (Variant 3, encrypted-cookie state) or `server` (Variant 2, server-side store).
  Global -- one deployment runs one BFF shape.

| `session.store`
| *Required* when `session.mode: server` -- the boot fails if a server-mode session omits it; it is
  unused in `cookie` mode. `memory` (single-node or sticky-session deployments) is the only initial
  value; a shared external store is deliberately unsupported for now (see the trade-off in
  link:variants/02-bff-session.adoc[Variant 2]). There is no implicit default -- server mode must
  name its store explicitly.

| `session.max_sessions`
| *Server mode only.* Upper bound on the number of concurrently stored sessions -- a
  denial-of-service guard on the in-memory store, so an unbounded stream of logins cannot exhaust
  node memory. Unused in `cookie` mode (there is no server-side store to bound). Optional; omit it
  to leave the store unbounded.

  The bound counts *live* sessions, not accumulated ones. An expired session keeps its slot until
  something reclaims it, and reaching the bound is that trigger: a login arriving at a full store
  sweeps the sessions expired at that instant and is admitted if the sweep freed a slot. A store
  still full afterwards is genuinely full of live sessions and the login is refused fail-closed.
  Nothing schedules that sweep -- there is no scheduler, timer thread or periodic task, and no knob
  configures one -- so size this against expected peak concurrency. Re-storing an id already held
  (how a rotated session is persisted) consumes no new capacity and is admitted at the bound
  without consulting it.

| `session.cookie_name`
| Cookie name; the `+__Host-+` prefix (implying `Secure`, `Path=/`, no `Domain`) is the default
  and recommended.

| `session.encryption_key`
| `cookie` mode only. AES-256-GCM key as an `${ENV_VAR}` reference. Both key-material modes are
  fully supported production options:

  * *Passed key* -- `encryption_key` is set. Sessions survive a restart and the key can be shared
    across replicas. This is the mode a multi-replica deployment must use.
  * *Generate on startup* -- `encryption_key` is omitted. A fresh AES-256 key is generated at boot.
    Two consequences the operator must accept: *all sessions are dropped on every restart*, and
    *the key cannot be shared across replicas*, so a load-balanced deployment would reject every
    cookie sealed by another instance.

  There is exactly *one* sealing key -- no decrypt-only companion key and no rotation window.
  Replacing it is a clean break: cookies sealed under the withdrawn key carry a key id the gateway
  no longer holds, are refused as "no session", and those users log in again.

| `session.max_cookie_size`
| *Cookie mode only.* The sealed cookie-value size budget in bytes. Optional; range `40`--`8192`,
  default `4096` (browsers are only required to accept 4096 bytes per cookie, so the default sits
  there rather than at the gateway's transport ceiling). A value outside the range fails the boot
  with a message naming this key: below the floor no structurally valid sealed value could ever be
  emitted, and above the ceiling the derived header cap would exceed what the inbound
  request-header block (16 KiB, shared with every other header) will carry.

  This is *one declared number driving two limits*. It is both the seal-time budget -- a sealed
  value over it fails the seal with a logged warning, never a silent truncation -- *and* the source
  of the gateway's pre-route `Cookie` header-value cap (the budget plus a fixed 512-byte headroom
  for the cookie name and any co-resident cookies). Encoding the two limits independently is what
  previously made cookie mode unusable: the pre-route filter rejected every request carrying a live
  sealed cookie with `400` before any BFF logic ran.

  The raised cap is scoped twice, and is *not* a general widening of inbound header validation:

  * *By mode* -- only a gateway that resolves an active cookie-mode BFF raises it. A bearer-only or
    `session.mode: server` gateway keeps the resolved baseline `max_header_value_length` on every
    header, unchanged (see <<_preset_limits>> for the per-preset figure).
  * *By header* -- within a cookie-mode gateway only `Cookie` and `Set-Cookie` header *values* use
    the raised cap. Every other header keeps the resolved baseline, and every non-length validator
    (null-byte, control-character, injection-pattern) still applies to the cookie value. The
    `Authorization` carve-out described in <<_pre_route_header_carve_outs>> is the one other
    exception, and it is independent of session mode.

  [IMPORTANT]
  ====
  *Enforcement is gateway-wide, not per-anchor.* The key sits on the global `oidc.session` block,
  but the cap it drives is applied by the pre-route stage that runs *before* route selection --
  at which point no anchor is resolved. Do not read the key's placement as per-anchor scoping;
  a cookie-mode gateway raises the `Cookie` cap for every route it serves. The per-anchor
  `security_filter.max_header_value_length` knob is a different control, applied post-route.
  ====

| `session.ttl_seconds`
| *Absolute* session lifetime, counted from a login timestamp stored inside the session record
  (server mode) or the encrypted cookie payload (cookie mode) -- enforcement is server-side,
  since cookie attributes are client-advisory. It is not an idle timeout, and token refresh
  does not extend it. On each `Set-Cookie` (including re-seals after refresh) the cookie
  `Max-Age` is set to the *remaining* lifetime, so re-sealing never extends the session. On
  expiry the user re-authenticates via the login flow.

| `session.refresh.enabled` / `leeway_seconds`
| Transparent refresh: when the access token is within `leeway_seconds` of expiry, refresh it
  (with rotation) during the request.

| `session.refresh.on_failure`
| What happens to the *request during which* refresh fails; the session is destroyed either
  way. `reauthenticate` (default): treat the request as unauthenticated -- navigation requests
  are redirected into a fresh authorization-code flow, others get `401` (the same content
  negotiation as `require: session`). `reject`: always answer `401` `application/problem+json`,
  even for navigations -- for deployments whose SPA handles re-login entirely itself.

| `step_up.*`
| RFC 9470: honour an upstream `401` + `insufficient_user_authentication` challenge by silent
  refresh, then re-authorization with elevated `acr_values`/`max_age`. See
  link:variants/02-bff-session.adoc[Variant 2].
|===

| Field | Meaning

| `path_prefix`

[[_forward]]
=== `forward`

*A filter inside a route the request is already authorised for* -- not the gateway's
deny-by-default boundary. That boundary is route matching: a request matching no route is
rejected `404` and reaches no upstream at all (see link:user/endpoint-routes.adoc#_route_ordering[Route ordering]). By
the time `forward` runs, the route has been selected and the auth posture enforced, so this
block decides only *which of the client's own headers and query parameters survive the trip*
(link:adr/0036-Forward_filtering_is_a_three-mode_policy_inside_an_authorised_route.adoc[ADR-0036]).

==== The three modes

Headers and query parameters are *independent dimensions*. Each resolves exactly one of three
modes from what the route declares -- and a route may mix them, e.g. a positive-list on headers
with forward-all on query.

[cols="1,2,2"]
|===
| Mode | Selected by | Behaviour

| *Positive-list*
| `headers_allow` / `query_allow` declared
| Only the named entries cross.

| *Negative-list*
| `headers_deny` / `query_deny` declared
| Every client entry crosses *except* the named ones.

| *Forward-all*
| Neither list declared for that dimension
| Every client entry crosses. This is the baseline: omit the `forward` block entirely and both
  dimensions are forward-all.
|===

*Declaring both lists for one dimension fails the boot.* `headers_allow` together with
`headers_deny` (or `query_allow` with `query_deny`) is not a stricter policy but an ambiguous
one, so the configuration validator refuses it rather than resolving it to a guess. The two
dimensions are judged separately -- `headers_allow` plus `query_deny` is legal.

*An absent list is not an empty one.* `query_allow: []` is a *positive-list admitting nothing*;
an omitted `query_allow` is *forward-all*. The two are opposite behaviours, so the distinction
is carried in the model and never normalised away
(link:adr/0033-Absence_in_the_production_type_model_is_a_Nullable_type_not_a_stored_Optional.adoc[ADR-0033]).

Header names match *case-insensitively* on both list modes, as RFC 9110 field names require.
Query-parameter names match *case-sensitively* on both modes -- query names are case-sensitive
in HTTP, and making only one side insensitive would let a route's two lists disagree about what
a name is.

==== What crosses regardless of the mode

Three gateway-owned sets bound every mode, and they are what makes the forward-all baseline safe
to offer
(link:adr/0037-The_gateway-owned_header_sets_are_enumerated_per_direction_and_bounded_by_knowledge.adoc[ADR-0037]).

*The never-forward set.* These client headers are withheld under *every* mode, whatever a route
declares: `Authorization`, `Cookie`, `Connection`, `Proxy-Connection`, `Keep-Alive`,
`Proxy-Authenticate`, `Proxy-Authorization`, `TE`, `Trailer`, `Transfer-Encoding`, `Upgrade`,
`Content-Length`, `Host`, `Origin`, `Referer` and `Date` -- credentials the gateway terminates
or mediates, the hop the gateway terminates rather than the message it forwards, the framing the
gateway re-establishes, and the names the gateway itself owns.

The set also holds the *spoofable provenance claims* only the gateway is entitled to make: the
vendor client-IP aliases `X-Real-IP`, `X-Client-IP`, `True-Client-IP` and `CF-Connecting-IP`, and
the underscore spellings of the forwarding names. Every name in the set is matched on its
*separator-folded* spelling -- lower-cased with each `_` mapped to `-` -- so `X_Real_IP` and
`X-Real_IP` are withheld exactly as `X-Real-IP` is, and a backend that folds header names into
CGI-style variables cannot be reached by respelling one.

Two members carry value- or mode-dependent behaviour:

* *`Cookie` is absolute against client input.* No mode and no list re-admits a client's `Cookie`.
  The BFF pattern's premise is that the backend never sees the sealed `__Host-` session cookie,
  and that absoluteness is exactly what makes a permissive baseline defensible. The one way a
  `Cookie` header reaches an upstream at all is an operator writing a *static* value in
  `set_headers` (see below) -- gateway configuration, never the caller's session cookie.
* *`Authorization` is the single re-admittable member*, and only where the route declares a
  *positive*-list naming it -- a legitimate choice for a pure-proxy route. Under a negative-list
  or forward-all there is no positive-list, so a permissive route can never leak an inbound
  credential. On a `require: session` route the mediated bearer is merged *last* and overwrites
  it regardless, so the upstream still sees only the mediated credential.
* *`TE` crosses only as the exact `trailers` token* -- the one value RFC 9110 admits end-to-end,
  and what gRPC-over-HTTP/2 requires. Any other value negotiates a transfer coding for the hop
  the gateway terminates and is withheld.

*The gateway-understood protocol set.* These cross *without* being named, so a route never
enumerates HTTP mechanics to make an ordinary backend work:

* *Unconditional* -- `Accept`, `Accept-Encoding`, `Accept-Language`, `Content-Type`, `Range`.
* *Conditional* -- the five RFC 9110 §13 validators `If-None-Match`, `If-Modified-Since`,
  `If-Match`, `If-Unmodified-Since`, `If-Range`, admitted only when the route's
  link:#_upstream_defaults[`not_modified`] toggle is enabled.

Membership answers *"does the gateway know what this header means?"*, not "does a backend need
it" -- the latter rule would admit `Cookie` and `Authorization`. `User-Agent` is deliberately
outside the set on that test; a backend that genuinely needs it names it in `headers_allow`. The
set is a fixed constant with no configuration surface: to withhold one of these, *deny it by
name*. A `headers_deny` entry naming a protocol header wins; a `headers_allow` is deliberately
not consulted, since crossing without being named is the set's whole purpose.

*The regenerated forwarding headers.* The client's `X-Forwarded-*` / `Forwarded` copies never
cross under any mode -- the gateway emits its own freshly regenerated set per the
link:#_forwarded_headers[`forwarded`] policy, so forward-all is not a way to smuggle a spoofed
`X-Forwarded-For` upstream.

==== `set_headers`, and what wins

`set_headers` adds *static*, gateway-controlled headers. Two injections are never written here
and never listed in `headers_allow`: the mediated `Authorization: Bearer` on `require: session`
routes (set from the session's access token), and the regenerated forwarding-header set.

*`set_headers` is not bounded by the never-forward set, and that is deliberate.* The strip governs
*client input*; an operator's static value is gateway configuration and is merged after it, so
`set_headers` can place any header name at all -- including `Authorization` for a backend behind a
static credential, `Host` for a backend expecting a particular vhost, or `X-Real-IP` for one that
reads it. What this cannot do is leak the *caller's* value: the entry is a fixed string from the
route's YAML, so a client's `Cookie`, credential or provenance claim still never crosses. Two
consequences follow. A hop-by-hop or framing name set here (`Transfer-Encoding`, `Content-Length`,
`Connection`, `Upgrade`) is written onto a request whose framing the gateway otherwise owns and is
never a sensible entry -- it is not refused at boot, so do not write one. And declaring the same
field twice under different casing (`Content-Type` and `content-type`) leaves which value wins
unspecified; declare each field once.

The stage merges in a pinned order -- the mode copy with the never-forward strip, then the
protocol set, then `set_headers`, then the regenerated forwarding headers, then the mediated
bearer -- and that order is one rule stated twice:

. *Operator configuration beats client input.* `set_headers` merges after everything sourced
  from the request, so an operator's `Content-Type` *replaces* a client's `content-type` rather
  than riding alongside it. The outbound map is keyed case-insensitively, so the replacement
  happens whatever either side spelled.
. *Gateway-owned transport truth beats operator configuration.* The regenerated forwarding
  headers and the mediated bearer merge after `set_headers`, the bearer last.

=== `upstream`

The target is `resolved(endpoint.base_url) + upstream.path + remainder`, where *remainder* is
the request path after stripping the matched `match.path_prefix` -- so path parameters survive
the mapping (`/api/orders/42` -> `.../orders/42`), and `upstream.path` *replaces* the matched
prefix rather than prepending to the full request path. The query parameters the route's
link:#_forward[`forward`] mode admits are appended unchanged.
`connect_timeout_ms` / `read_timeout_ms` are
millisecond-precision options on the shared per-upstream-tuple data-plane client
(link:adr/0008-data-plane-transport.adoc[ADR-0008]). `retry` and `circuit_breaker` map to the
per-route resilience guard assembled at boot (SmallRye Fault Tolerance, programmatic --
ADR-0008): retry applies to idempotent methods only (`idempotent_only` -- GET, HEAD, OPTIONS,
PUT, DELETE; never POST or PATCH) *and* only while no request-body byte has been sent
upstream; the breaker is stateless per node, opens after `failures` consecutive failures and
half-opens after `reset_ms`
(see link:architecture.adoc#_downstream_client[Architecture -- Downstream Client]). The upstream host is never
written literally here -- only the alias-relative `path`.

[[_upstream_defaults]]
=== `upstream_defaults`

Two upstream behaviour toggles -- upstream *retry* and HTTP *304 Not Modified* handling --
declarable at two scopes, `gateway.yaml` (global) and per `endpoint`, and overridable per route.
Each route's effective value is materialized *once* at boot into the route table, so the request
pipeline reads a single resolved `true`/`false` and never re-derives the inheritance.

[cols="1,3"]
|===
| Field | Meaning

| `retry.enabled`
| Whether idempotent upstream calls for the route are retried. This toggle only *gates* retry;
  the retry *policy* (attempt count, idempotent-only) lives in the route's `upstream.retry` --
  see link:#_upstream[`upstream`].

| `not_modified.enabled`
| End-to-end conditional-request *pass-through* for the route
  (link:adr/0008-data-plane-transport.adoc[ADR-0008],
  link:adr/0037-The_gateway-owned_header_sets_are_enumerated_per_direction_and_bounded_by_knowledge.adoc[ADR-0037]).
  *Enabled* (default): the five RFC 9110 §13 validators (`If-None-Match`, `If-Modified-Since`,
  `If-Match`, `If-Unmodified-Since`, `If-Range`) are admitted by the gateway-understood protocol
  set -- they cross without appearing in any `forward` list -- and upstream `304` responses plus
  the validator response headers (`ETag`, `Last-Modified`) relay untouched. *Disabled*: the
  response half strips `ETag` / `Last-Modified`, and the request half withholds the five
  validators from the protocol set, deliberately forcing full `200` exchanges -- for upstreams
  whose ETags are inconsistent across nodes or leak inode/version detail. Gating both halves on
  one flag is what stops the gateway asking a question whose answer it then discards. In
  *neither* state does the gateway cache response bodies or answer `304` from a cache --
  gateway-side response caching is rejected by design (ADR-0008).

  *One boundary is recorded rather than resolved.* The toggle gates the *protocol set's
  admission path*; it is not a withholding rule applied to the mode copy. A forward-all or
  negative-list route therefore still carries a client's `If-None-Match` upstream with the flag
  off -- the header crosses on the route's declared posture -- while the response half strips the
  `ETag` that would answer it. Closing that gap means changing what forward-all means for a
  class of client headers, which is wider than the decision that introduced the modes, so it is
  pinned by a characterization test and left as an open question rather than resolved silently.
  A route that must withhold the validators under a permissive posture names them in
  `headers_deny`.
|===

*Resolution (wholesale, no merge).* Each route's effective `retry` / `not_modified` toggle is,
in precedence order:

* the route's own `upstream.retry.enabled` / `upstream.not_modified.enabled` if declared; else
* the *endpoint-level* `upstream_defaults` block if the endpoint declares one -- it *replaces*
  the global block wholesale for that endpoint's routes (the same no-merge rule `auth` and
  link:#_allowed_methods[`allowed_methods`] use); else
* the *global* `gateway.upstream_defaults` block if declared; else
* the built-in default -- both toggles *enabled*.

Both `upstream_defaults` blocks (global and per endpoint) share one shape; an omitted toggle
defaults to `true`:

[source,yaml]
----
upstream_defaults:
  retry: { enabled: true }
  not_modified: { enabled: false }
----

[[_asset_defaults]]
=== `asset_defaults`

The operator's *add-only* extension of the gateway's built-in asset content-type map, declarable
only at the global scope (`gateway.yaml`). It solves one problem: an asset whose extension the
gateway does not know is served as `application/octet-stream`, which browsers download rather than
render. Declaring the extension here gives it the right `Content-Type`.

[cols="1,3"]
|===
| Field | Meaning

| `content_types`
| A map of *lowercase extension* (without the dot) to the `Content-Type` served for it. Keys are
  constrained to lowercase alphanumerics by the schema and lowercased on binding, so a key's case
  can never decide whether a mapping applies. Values are bounded twice: the schema caps them at 255
  characters and refuses anything that is not a control-character-free `type/subtype…` shape, and the
  configuration validator then enforces the precise RFC 9110 media-type grammar, naming the offending
  extension and value. Both bounds *fail the boot* -- the value is served verbatim as the asset's
  `Content-Type` response header, so a CR/LF or non-media-type value would be a response-header
  injection vector. Omitted (or an empty map) means the built-in map governs alone.
|===

[source,yaml]
----
asset_defaults:
  content_types:
    webmanifest: application/manifest+json
    avif: image/avif
----

*Add-only -- and the built-ins are refused, not ignored.* The gateway's own 21-entry extension map
(`html`, `htm`, `css`, `js`, `mjs`, `json`, `map`, `xml`, `txt`, `svg`, `png`, `jpg`, `jpeg`,
`gif`, `webp`, `ico`, `woff`, `woff2`, `ttf`, `pdf`, `wasm`) is consulted *first* and always wins.
An `asset_defaults.content_types` entry naming any of those extensions *fails the boot*, with a
message naming the offending extension; it collects with every other violation in the same
single-pass report rather than failing on the first. An extension *neither* map carries still falls
back to `application/octet-stream`.

The refusal is deliberate, and it is a *security* bound rather than an ergonomic one. The built-in
map is precisely what makes an asset's `Content-Type` gateway-governed instead of source-dictated.
Permitting an override would hand an operator (or anyone who can edit the mounted descriptor) a
*stored-XSS lever* on a security gateway: remapping `svg` away from `image/svg+xml`, or pointing
any built-in extension at `text/html`, turns a file served from a directory mount or a secondary
origin into a script-executing document on the gateway's own origin. Add-only removes that lever
while still solving the stated problem. Refusing at boot -- rather than silently ignoring the entry
at request time -- is what makes the bound *visible*: the operator learns the mapping did not take
effect instead of shipping a descriptor that reads as though it did.

[[_edge_hardening]]
=== `edge_hardening`

The two operator-facing admission budgets for the public data-plane edge, declarable only at the
`gateway.yaml` (global) scope — the pools they bound are process-wide, so there is no per-endpoint or
per-route form. The block and both members are optional; each omission resolves to its default, so a
deployment that never writes the block keeps the shipped behaviour. The remaining edge bounds
(framing limits, idle reap, drain window) are *not* configurable — see
link:user/endpoint-routes.adoc#_edge_hardening_defaults[Edge hardening defaults] for the full table.

[cols="1,3"]
|===
| Field | Meaning

| `admission_cap`
| The maximum number of concurrently in-flight requests the edge admits, across every route
  (default `2048`, minimum `1`). A request beyond the cap is refused `503` *before* a virtual thread
  is dispatched, so a flood cannot spawn unbounded virtual threads. Size it to the concurrency the
  deployment's upstreams can absorb: too high defers the backpressure to the upstream, too low
  refuses traffic the gateway could have served.

| `websocket_relay_cap`
| The maximum number of concurrently *established* WebSocket relays (minimum `1`; when omitted, a
  quarter of the effective `admission_cap` — `512` at the default `admission_cap` of `2048`).
  This is a *sub-budget acquired in addition to* the general permit, never instead of it, because an
  established relay holds its permit for the connection's whole lifetime rather than for one
  request/response round-trip. Without the second bound, a modest number of long-lived relays would
  consume the general pool and starve ordinary HTTP traffic. An upgrade beyond the cap is refused
  `503`, releasing the general permit on the way out. Must not exceed `admission_cap` — a larger
  value could never bind, so it is refused at boot rather than silently ignored. For sizing guidance
  see link:user/protocol-routes.adoc[Protocol routes].
|===

=== `rate_limit`

Reserved schema for per-node, in-memory token-bucket rate limiting
(`requests_per_second`, `burst`). *The feature is not implemented*; the field is documented only
so the schema need not change should that decision ever be revisited. It is accepted and ignored,
and no `429` is ever produced.

=== `metadata`

`config_version` is an audit stamp only -- logged at boot, exposed for operational
traceability, no runtime behaviour. Retained so the model need not change if dynamic
discovery is added later (link:adr/0002-initial-scope.adoc[ADR-0002]).

=== `security_headers`

Response-header middleware applied to every response the gateway returns. Resolved at
*gateway -> anchor* scope only (an anchor may replace the block wholesale for its namespace --
see link:user/anchors.adoc#_anchors[Anchors]); endpoints and routes can neither override nor disable it.
Responses emitted before route selection (CORS preflight, pre-routing rejections) use the
anchor block when the request path lies inside an anchor namespace, else the gateway block.

[cols="1,3"]
|===
| Field | Meaning

| `hsts`
| `Strict-Transport-Security` with `max_age` and `include_subdomains`.

| `content_type_nosniff`
| `X-Content-Type-Options: nosniff`.

| `frame_deny`
| `X-Frame-Options: DENY`.

| `cors`
| CORS preflight/response handling. Disabled by default. `allowed_origins` are exact origins;
  a wildcard origin combined with `allow_credentials: true` is rejected at boot (credential
  leak). Preflight `OPTIONS` requests are answered by the CORS layer *before* authentication --
  preflights carry no cookies by spec, so routing them into the auth stage would break every
  credentialed cross-origin call. Responses to CORS requests carry `Vary: Origin` (shared-cache
  poisoning guard). When disabled, no CORS headers are emitted and cross-origin browser calls
  fail -- the secure default.
|===

=== `security_defaults`

The gateway-wide inbound-filter baseline. `profile` selects the *inbound-filter mode*, and the mode
set has exactly three members:

[cols="1,4"]
|===
| Value | Meaning

| `strict`
| The tightest posture, backed by `SecurityConfiguration.strict()`.

| `lenient`
| The relaxed posture, backed by `SecurityConfiguration.lenient()`. Even this preset never permits
  null bytes, and path traversal is blocked regardless of configuration.

| `minimal`
| A *partial* disable of the per-route validation. It is not an off switch -- see
  link:#_the_minimal_mode[The `minimal` mode] for the closed definition of what it does and does not
  turn off.
|===

*An omitted `security_defaults` block -- or a block omitting `profile` -- resolves to `strict`*, the
fail-closed choice. A deployment wanting a looser baseline must declare `lenient` explicitly. The
concrete numbers each mode carries are tabulated under link:#_preset_limits[Preset limits].

The block carries two further keys:

[cols="1,4"]
|===
| Key | Meaning

| `allow_get_with_content_length_body`
| *Boolean, default `false`.* Admits a `Content-Length`-framed request body on `GET`. It exists for
  upstreams whose API genuinely takes a body on `GET` -- Elasticsearch's `_search` is the motivating
  case. It is a *partial* relaxation of the framing gate, scoped to exactly one rejection leg and
  only for `GET`: the declared-`Content-Length` leg. A `GET` whose body is signalled without a
  declared `Content-Length` is not `Content-Length`-framed and stays rejected. See
  link:#_the_get_body_opt_in[The `GET`-body opt-in] below for the closed definition of what stays
  enforced.

| `max_authorization_header_value_length`
| *Integer, minimum `1`, default `8192`.* The budget for the `Authorization` header-value carve-out
  (see link:#_pre_route_header_carve_outs[Pre-route header-name carve-outs]). It raises the
  header-value cap for `Authorization` values *only*; every other header stays on the resolved
  baseline. The default is the `lenient` preset's own header-value ceiling, so the carve-out never
  admits a value the loosest shipped profile would itself reject. It sits on the gateway-wide
  `security_defaults` block because the floor that first enforces it runs before route selection --
  its placement must not be read as per-anchor enforcement. The same budget is applied by the
  post-route re-run, so the raised cap reaches `Authorization` values on every route, including one
  declaring its own `security_filter`.
|===

[[_the_get_body_opt_in]]
==== The `GET`-body opt-in

`allow_get_with_content_length_body: true` relaxes the anti-smuggling framing gate by exactly one
leg -- the declared-`Content-Length` leg -- and only for `GET`. Everything else the gate enforces is
untouched. What *stays rejected* is the closed list:

* *A body-present `GET` with no declared `Content-Length` -- rejected.* The opt-in admits a
  `Content-Length`-framed body and nothing else, so a body signalled by any other means falls
  outside it. The gate asserts this itself rather than relying on an upstream stage to have ruled
  the shape out (ADR-0026).
* *`Transfer-Encoding` on `GET` -- rejected unconditionally.* No configuration relaxes it. Chunked
  framing on an otherwise-bodyless method is precisely the shape the request-smuggling defences exist
  to constrain, and excluding it costs the motivating use case nothing: an Elasticsearch `_search`
  client sends a `Content-Length`-framed body, never a chunked one. The relaxation is therefore
  drawn at the boundary where the security value is, not where the convenience is.
* *Any body on `HEAD` -- rejected on every leg.* The opt-in never applies to `HEAD`.
* *`Content-Length` and `Transfer-Encoding` both present -- rejected.* The CL+TE coexistence rule is
  a separate check that runs *before* the body-on-bodyless-method check, so a `GET` carrying both is
  refused regardless of this key.
* *Multiple `Content-Length` headers, or a comma-separated `Content-Length` value -- rejected.*
* *A `Connection` header naming a framing or trust header -- rejected.* The framing-header-strip
  defence is independent of this key.

The key is *gateway-wide* rather than per-route by necessity, not convenience: the framing gate runs
at stage 1, before route selection, so no route is resolved yet to scope it to.

*The blast radius is therefore the whole gateway, not the one upstream that needed it.* Because the
key cannot be scoped, enabling it for a single Elasticsearch-shaped upstream simultaneously admits a
`Content-Length`-framed `GET` body on *every* other route -- including `require: bearer` routes and
every route under a `type: bff` anchor. RFC 9110 section 9.3.1 notes that content on `GET` has no
defined semantics, and the practical consequences on those other routes are caches that key on the
URL while ignoring the body, and any component that authorizes on the URL while the application
reads the body. Keep the key `false` unless every route on the gateway can tolerate a `GET` body.

An omitted key resolves to `false`, which is bit-for-bit the behaviour of a gateway that never had
this key: every framing rejection is preserved.

[IMPORTANT]
====
The mode set is *closed*: `strict`, `lenient`, `minimal`, and nothing else. Any other value -- at
any of the three declaration sites (`security_defaults`, an anchor's `security_filter`, a route's
`security_filter`) -- makes the gateway *fail to boot*. There is no fallback and no
warning-and-continue.

The value range is enforced by the bundled JSON Schema, not by the configuration validator, so an
out-of-range value is rejected when the document is bound.

`auth.require: none` is a *different* key in a different value space and is unrelated to this set.
====

*The mode is resolved per route*, by wholesale replacement down the chain
`route.security_filter` -> `anchor.security_filter` -> `security_defaults`. A route declaring a
`security_filter` block that omits `profile` falls back to `security_defaults.profile`, *not* to its
anchor's profile -- the block is replaced whole, never merged. Any explicit limit keys in the winning
block override the resolved preset's limits individually.

*Fail-closed rule.* A route whose *effective* profile resolves to `minimal` *fails the boot* when either

* its effective access level is `authenticated`, or
* its resolving anchor's `type` is `bff`.

The access level is the *effective* one, not the anchor's declared `access`: a route or endpoint may
legally strengthen a `public` anchor's auth floor (link:adr/0007-anchor-scoped-policy.adoc[ADR-0007]
forbids weakening a floor, not strengthening one), and such a route is authenticated in effect while
its anchor still reads `access: public`. The refusal collects into the all-violations pass with every
other configuration error and names the route, the refusing dimension, and the remedy. A
`security_defaults.profile: minimal` that reaches such a route through the fallback chain is refused
identically -- there is no separate global exemption.

[[_the_minimal_mode]]
==== The `minimal` mode

`minimal` is a statement about *validation*, never about *limits*. The following two lists are the
*normative closed definition* of the mode, not illustrative examples: anything absent from the
disabled list keeps running.

*Still enforced under `minimal` -- without exception:*

* The entire *non-skippable pre-route floor*: raw-path canonicalisation and validation, header name
  and value validation, and the query-parameter and header *count* caps. The floor cannot be made
  skippable because route selection consumes the canonical path it produces -- so an encoded path
  separator, an over-cap parameter count and an oversized header value are all still rejected `400`
  on a `minimal` route.
* `max_body_bytes` -- a resource guard against exhaustion, not an injection defence.
* `allowed_paths` -- a surface restriction, not an injection defence.
* The verb gate (`allowed_methods`), authentication and the auth floor, CSRF, the route's
  link:#_forward[`forward`] mode and the gateway-owned never-forward set it cannot override, the
  terminal-action rules, and the response-side security-header envelope.

*Disabled under `minimal` -- exactly these two, and nothing else:*

. The *url-parameter name and value validation* (the post-route run under the route's own
  configuration).
. The *per-route pipeline re-run* -- the second pass of the path and header pipelines that a route
  whose configuration diverges from the gateway baseline would otherwise perform.

Because `minimal` carries no preset of its own, a `minimal` route resolves its limits from the nearest
non-`minimal` profile in its fallback chain, landing on `strict` when the whole chain is `minimal`.
That is what gives the retained `max_body_bytes` cap a concrete number to enforce.

The rationale for each bound -- and the alternatives rejected, including a wholesale skip of the
post-route stage -- is recorded in
link:adr/0024-Inbound_filter_modes_minimal_is_a_partial_disable_retaining_the_body_cap_and_path_allowlist_and_is_refused_on_authenticated_and_BFF_routes.adoc[ADR-0024].

[[_allowed_methods]]
=== `allowed_methods`

A *positive allowlist of HTTP verbs*, declarable at three scopes -- `gateway.yaml` (global),
per link:user/anchors.adoc#_anchors[anchor], and per `endpoint` -- with *explicit no-inheritance semantics*.
It is a coarse, defence-in-depth verb gate that sits *above* the per-route `match.methods`
matcher: `match.methods` selects which route serves a verb; `allowed_methods` decides whether
the gateway will serve the verb *at all* for that endpoint.

*Resolution (no inheritance).* Each route's *effective* `allowed_methods` is materialized once
at boot:

* the *endpoint's* `allowed_methods` if the endpoint declares one -- it *replaces* the
  anchor/global list wholesale for that endpoint (no merge, no union, no intersection --
  exactly the wholesale-replace rule the `auth` block uses); else
* the *anchor's* `allowed_methods` if the route's anchor declares one; else
* the *global* `gateway.allowed_methods` if declared; else
* the standard set `{GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS}`.

Because the endpoint list *replaces* rather than narrows, an endpoint may permit a verb the
global default omits (global `[GET, POST, PUT]`, endpoint `[PUT, DELETE, HEAD]` -> that
endpoint serves `DELETE`/`HEAD` and *not* `GET`/`POST`; other endpoints keep the global list).

*Runtime.* After route selection, a request whose method is not in the matched route's
effective `allowed_methods` is rejected with `405 Method Not Allowed` and an `Allow` header
listing the effective set (`INPUT_VALIDATION` event); the upstream is never called. `TRACE` and
`CONNECT` are *never* permitted -- they are not proxyable through the data plane and cannot
appear in any `allowed_methods` list (listing either fails the boot).

*Boot validation.* The check applies only to *explicitly declared* `match.methods`: every method
*listed* in a route's `match.methods` must be a member of that route's effective
`allowed_methods` -- a route that matches a verb its endpoint forbids is a contradiction and
*fails the boot* (fail-fast, rather than a route that can never fire). A route that *omits*
`match.methods` (so it would match all methods) does *not* fail the boot against a narrower
`allowed_methods`; it simply serves the effective set and the verb gate returns `405` at runtime
for the rest. So `allowed_methods` is the way to blanket-restrict verbs across an endpoint's
routes without restating `match.methods` on each.

[[_forwarded_headers]]
=== `forwarded`

Forwarded-header handling is *delivered by `cui-http`'s `de.cuioss.http.forwarded` package*
(`ForwardedHeaderResolver` -> immutable `ResolvedForwarding`, configured by a
`ForwardedResolverConfig`); the gateway wires configuration in and consumes the resolved
result -- it implements no parsing of its own. The authoritative behaviour specification is
`cui-http/doc/forwarded-header-resolution.adoc`; the design rationale (why `X-Forwarded-*` is
the sane emission default) is link:adr/0003-forwarded-headers.adoc[ADR-0003].

[cols="1,3"]
|===
| Field | Meaning

| `trusted_proxies`
| *Required whenever a `forwarded` block is present* (the `forwarded` block itself is optional) --
  a CIDR allowlist (IPv4 + IPv6), mapped to `ForwardedResolverConfig.trustedProxies`.
  It drives the *client-IP trust walk*: the `X-Forwarded-For` (or RFC 7239 `for`) chain is
  walked right-to-left, skipping trusted hops; the first non-trusted, well-formed address is
  the client. An *empty* list means no client IP is ever resolved from headers -- the TCP peer
  is the client (fail-safe). The gateway additionally consults forwarding headers only when
  the *immediate TCP peer* is in this list -- a *gateway-side* gate: the transport-agnostic
  resolver consumes only a header accessor and never sees the peer, so this check is API
  Sheriff code, and without it a direct client's spoofed `X-Forwarded-For` would be honored.
  Never trust-all (`0.0.0.0/0` or its IPv6 twin `::/0`) -- the canonical footgun -- and keep the list as *narrow* as
  possible (the exact proxy addresses, not a whole RFC 1918 block): every host inside a listed range
  that can reach the gateway directly can spoof forwarding headers. Each listed proxy must
  also *manage* the `X-Forwarded-*` family (append or strip) -- see the mixed-family
  requirement in link:adr/0003-forwarded-headers.adoc[ADR-0003].

  *A broad entry warns at boot.* An entry shorter than `/16` (IPv4) or `/48` (IPv6) emits
  `ApiSheriff-102` during startup validation -- a WARN, not a boot failure. The thresholds mark
  the point at which one entry spans more than a single operator-provisioned network: `/16` is
  the widest single IPv4 network in routine use (an AWS VPC's maximum, Docker's default bridge
  `172.17.0.0/16`, the RFC 1918 `192.168.0.0/16` block), and `/48` is the canonical IPv6 site
  allocation. So `172.16.0.0/12` and `10.0.0.0/8` warn, and `2001:db8::/32` warns.

  *What is deliberately left un-warned*: an IPv4 `/16` (65,536 addresses) and an IPv6 `/48`.
  Both are still real exposure -- every host inside them that can reach the gateway directly
  can spoof forwarding headers -- and they are un-warned because they are *legible* exposures
  an operator chose, not because they are safe. Warning on a routine, correct configuration is
  how a guard gets trained into background noise. Narrow the list regardless of whether it warns.

  *The whole list can be supplied by one `${VAR}`.* Because this field declares an `array`, a
  placeholder written as its value is typed from that destination and split on `,`, with each
  element stripped -- so `trusted_proxies: "${SHERIFF_TRUSTED_PROXIES}"` with
  `SHERIFF_TRUSTED_PROXIES=10.0.0.5/32,10.0.0.6/32` binds the two-element list. This is the
  deployment-bound case the mechanism exists for: the trusted set genuinely differs per
  environment while the mounted document does not. Use the *bare* `${VAR}` form. An *empty
  resolution* -- an unset-and-defaulted `${VAR:-}`, or a variable resolving to an empty value or
  carrying an empty comma-separated element -- is *refused at the substitution site* and fails
  the boot, naming this pointer and never echoing the resolved value. That refusal is deliberate
  and cannot be delegated to validation: this field declares no `minItems`, so an explicit `[]`
  is legal and a validator reading the bound list cannot tell a list you wrote empty from one a
  variable emptied. Writing `trusted_proxies: []` yourself therefore remains valid and still
  means *no proxy is trusted*.

| `trust_scheme_host`
| Maps to `ForwardedResolverConfig.trustAll`: honor the *sanitized* forwarded scheme / host /
  port / context-path prefix. Off by default (secure default: nothing is honored); enable only
  when the gateway sits fully behind trusted proxies. cui-http's finer-grained
  `allowedContextPaths` (honor specific prefixes without `trustAll`) is deliberately not
  exposed initially.

| `emit`
| Canonical output: `x-forwarded` (default) or `both`. `x-forwarded` emits the
  `ResolvedForwarding` serialization `toXForwardedHeaders()`
  (`X-Forwarded-Proto/-Host/-Port/-Prefix/-For`, present fields only); `both` additionally
  emits `toForwardedHeader()` -- a single strictly encoded RFC 7239 `Forwarded` value. There is
  deliberately no `Forwarded`-only mode: XFF-only downstreams would silently lose client
  information (link:adr/0003-forwarded-headers.adoc[ADR-0003]).
|===

*Inbound header family and precedence.* The resolver understands `X-Forwarded-Proto/-Host/
-Port/-Prefix/-For`, RFC 7239 `Forwarded` (`proto`, `host`, `for` -- the RFC defines no prefix
directive), and the NiFi-proprietary `X-ProxyScheme/-Host/-Port/-ContextPath`. Precedence is
*per field*, first present non-blank value wins:

[cols="1,4"]
|===
| Field | Precedence

| scheme      | `X-Forwarded-Proto` -> `X-ProxyScheme` -> RFC 7239 `proto`
| host        | `X-Forwarded-Host` -> `X-ProxyHost` -> RFC 7239 `host`
| port        | `X-Forwarded-Port` -> `X-ProxyPort` -> port carried by the resolved host
| prefix      | `X-ProxyContextPath` -> `X-Forwarded-Prefix` (RFC 7239: none)
| client IP   | `X-Forwarded-For` chain -> RFC 7239 `for` chain
|===

*The `prefix` field is not this gateway's context path.* It is an *inbound* hint a trusted proxy
sends about where it published the gateway, honored only under `trust_scheme_host` and used only when
composing forwarded values -- it never moves where this gateway itself serves; the gateway's own
application and management context paths (`/` and `/q/...` by default) are build-time and are moved
only by rebuilding, see link:user/context-path.adoc[The Context Path].

*Sanitization (fail-safe, never throws).* Every honored value passes the `cui-http`
header-value pipeline (CR/LF, NUL, control characters, over-length, suspicious patterns; the
pipeline is configured from the *gateway-wide* `security_defaults` profile -- forwarded-header
handling is gateway-wide, so no per-route `profile`, `minimal` included, changes it), plus fixed
fail-secure field guards that no profile can relax: scheme must be `http`/`https`, port `1..65535`, host
must carry no path separators or whitespace, and the context-path rejects protocol-relative
(`//host`) and backslash values on the *raw* value, before the sanitization pipeline -- whose
normalization would otherwise collapse `//host` to `/host` and mask the attack (honoring
`//attacker.com` would compose into a protocol-relative URL and exfiltrate the request).
Rejected values are *dropped, never honored*: pipeline sanitization failures increment the
shared `SecurityEventCounter` feeding the gateway metrics, the raw-value guards log
`HTTP-120`..`HTTP-123` WARNs, and plain trust misses (e.g. a forwarded host with
`trust_scheme_host: false`) are simply not honored, without noise.

*Emission is regeneration, never propagation.* The gateway does not append to or forward
inbound chains: it emits freshly generated headers from the *resolved, sanitized* facts --
`X-Forwarded-For` carries exactly the one resolved client IP. Any sabotage payload smuggled
into inbound headers therefore dies at the gateway instead of reaching the upstream. Because
emission carries *present fields only*, what appears depends on the trust config: under the
secure default (`trust_scheme_host: false`) only the client IP resolves, so only
`X-Forwarded-For` / `Forwarded: for=...` are emitted. The example below assumes
`trust_scheme_host: true` and a trusted proxy that sent `X-Forwarded-Host: gw.example.com` /
`X-Forwarded-Proto: https` for client `192.0.2.60`, with `emit: both`:

[source,text]
----
X-Forwarded-For: 192.0.2.60
X-Forwarded-Host: gw.example.com
X-Forwarded-Proto: https
Forwarded: for=192.0.2.60;host=gw.example.com;proto=https
----

RFC 7239 encoding is strict (IPv6 client addresses bracketed *and* quoted; other values quoted
only when not a valid token). Two asymmetries are inherent: `Forwarded` cannot carry the
context-path prefix (the RFC defines no directive -- the prefix travels only as
`X-Forwarded-Prefix`), and no `by=` parameter is emitted at all, which avoids the internal
topology leak RFC 7239 §8.2/§8.3 warn about more simply than the obfuscation the RFC suggests.

== Configuration Validation Rules (summary)

* `version` must be a known value.
* Every `endpoint.id` is unique across all endpoint files (in one file or across files); a
  duplicate endpoint `id` fails the boot.
* Every route has a unique `id` (across all endpoint files) and a resolvable `endpoint.base_url`.
* An endpoint is *enabled* unless its resolved `enabled` value is `false` (file literal, or a
  `${ENDPOINT_<ID>_ENABLED:-...}` placeholder resolved against the environment -- ADR-0004
  Amendment A1). A *disabled* endpoint is schema-validated but otherwise inert: its routes are
  not merged into the table, its `base_url` alias is *exempt* from the resolution requirement
  below, and it takes no part in the disjointness / passthrough-collision checks.
* Every `base_url` alias *of an enabled endpoint* resolves (after placeholder substitution)
  to a well-formed URL; otherwise boot fails.
* Every endpoint file declares an `auth` block (the default posture for its routes) *unless*
  its anchor declares one (see link:user/anchors.adoc#_anchors[Anchors]); an endpoint with neither fails the
  boot. Routes may override it per route (see
  link:user/endpoint-routes.adoc#_defaults_for_omitted_blocks[Defaults for omitted blocks]).
* Anchor `path_prefix` values are pairwise disjoint -- no anchor prefix is a prefix of another;
  overlap fails the boot.
* When an `anchors` block is configured: every enabled route's `match.path_prefix` lies inside
  its *declared* anchor's `path_prefix`, and every enabled route whose path lies inside any
  anchor's namespace declares exactly that anchor. A membership/namespace mismatch, a missing
  declaration inside an anchor namespace, or a reference to an undefined anchor fails the boot.
* Where a route's anchor declares `auth.require` of `bearer` or `session`, the route's
  *effective* auth must not resolve to `require: none` -- the anchor floor cannot be weakened;
  violation fails the boot. Non-auth overrides that relax anchor limits are logged as boot
  WARNs (weakening-override convention).
* A route whose *effective* auth is `require: bearer` requires a `token_validation` block with
  at least one issuer.
* A route whose *effective* auth is `require: session` requires an `oidc` block.
* Any two routes with an identical `match.path_prefix` -- same file or not -- must be statically
  disjoint (both declare different `host` values, or non-overlapping `methods`, or same-name
  header matchers with different exact values or opposite presence assertions -- `present: true`
  on one and `present: false` on the other; a lone `present: true` establishes nothing);
  otherwise the boot fails (see link:user/endpoint-routes.adoc#_route_ordering[Route ordering]).
* `allowed_methods` (global, anchor, or endpoint) may list only `GET`, `HEAD`, `POST`, `PUT`,
  `PATCH`, `DELETE`, `OPTIONS`; listing `TRACE` or `CONNECT` fails the boot. An endpoint
  `allowed_methods` *replaces* the anchor/global list wholesale, an anchor's replaces the
  global (no inheritance).
* Every method in a route's `match.methods` must be a member of that route's *effective*
  `allowed_methods` (the endpoint's list if declared, else the anchor's, else the global list,
  else the standard set); a route matching a verb its endpoint forbids fails the boot (see
  link:#_allowed_methods[`allowed_methods`]).
* A route whose `match.host` equals (case-insensitively) a key in `tls.passthrough_sni`
  fails the boot -- the route and the passthrough declaration contradict each other
  (see the `tls` field reference).
* Every `tls.passthrough_sni` alias resolves via the topology, and the resolved URL carries no
  base-path; otherwise the boot fails.
* The `forwarded` block is optional; when present, `forwarded.trusted_proxies` must be present
  within it (may be empty = forwarding headers are never trusted); the trust-all CIDRs `0.0.0.0/0`
  *and* `::/0` are rejected as unsafe.
* A `forwarded.trusted_proxies` entry shorter than `/16` (IPv4) or `/48` (IPv6) emits the
  `ApiSheriff-102` boot WARN -- it does *not* fail the boot. The thresholds mark the point at
  which one entry spans more than a single operator-provisioned network; an IPv4 `/16` and an
  IPv6 `/48` are deliberately left un-warned (see the
  link:#_forwarded_headers[`trusted_proxies`] field reference).
* A `${VAR}` written at a *list-valued* key supplies the whole list: the placeholder is typed from
  the destination's declared `array` and split on `,`, each element stripped. An *empty resolution*
  at such a key -- a value resolving to empty, the defaulted `${VAR:-}` shape, or any empty
  comma-separated element -- *fails the boot*, reported at the value's own pointer and never
  echoing the resolved value. The refusal happens at the substitution site rather than in
  validation, because these keys declare no `minItems`: an explicit `[]` you write is legal, so a
  validator reading the bound list cannot distinguish it from a list a variable emptied, whereas
  substitution can. Writing `[]` yourself is therefore unaffected. This rule is scoped to `array`
  destinations: a `${VAR}` resolving to empty at a *scalar* key behaves as it always has.
* *The list-valued rule is uniform, and its radius is the declared type alone.* It carries no key
  name and no pointer test, so it reaches *every* `array`-typed key the bundled schemas declare --
  not only the one the compose sample uses. *Both* schemas are in radius: the loader runs the same
  substitution pass over `gateway.yaml` against the gateway schema and over each
  `endpoints/*.yaml` against the endpoint schema, so an endpoint document's array keys are reached
  on identical terms. The authoritative sets are the `array`-typed nodes of
  `schema/gateway.schema.json` and `schema/endpoint.schema.json`; the enumerations below name them
  as of this writing and are checked against those files, not maintained independently of them.
+
--
In `gateway.yaml` the schema declares 18 such keys. Seventeen declare string items and are the
usable set: `allowed_methods` (global, anchor and endpoint), `auth.required_scopes`, the
`security_filter` lists `allowed_paths` / `allowed_header_names` / `blocked_header_names` /
`allowed_content_types`, the `security_headers.cors` lists `allowed_origins` / `allowed_methods` /
`allowed_headers`, `tls.cipher_suites`, `tls.alpn`, `forwarded.trusted_proxies`,
`token_validation.issuers[].jwks.allowed_egress_hosts`, `oidc.scopes`,
`oidc.session.csrf.trusted_origins`, `oidc.user_info.allowed_claims` and
`oidc.user_info.default_view`.

An `endpoints/*.yaml` document reaches `auth.required_scopes`, `allowed_methods` and the four
`security_filter` lists through the same shared definitions, and adds six further string-item keys
of its own: `routes[].match.methods`, the `routes[].forward` lists `headers_allow` /
`headers_deny` / `query_allow` / `query_deny`, and `routes[].websocket.allowed_origins`.
--
+
Three of the reachable keys are arrays of *objects* rather than strings -- `token_validation.issuers`
in `gateway.yaml`, and `endpoint.routes` and `routes[].match.headers` in an endpoint document. At
each the mechanism *reaches* the key rather than silently skipping it, produces scalars where the
schema requires objects, and the schema-validation pass then *refuses the document* -- a loud
failure, not a wrong value. `tls.passthrough_sni` is *not* a member at all: it is an object map of
SNI hostname to topology alias, not an array, so the rule never matches it and it cannot be
supplied this way.
* *Reachable is not recommended.* Per
  link:adr/0025-The_whole_server-TLS_surface_is_neutral_in_gatewayyaml_and_bound_by_exactly_two_seams.adoc[ADR-0025],
  `forwarded.trusted_proxies` is *deployment-bound* -- genuinely different per environment -- and is
  the intended user of this mechanism. `tls.cipher_suites` and `tls.alpn` remain *policy*: the
  uniform rule makes them mechanically reachable by a `${VAR}`, and that reachability is not an
  endorsement. A decision that is the same in every environment belongs in `gateway.yaml` under a
  neutral name; supplying it from the environment is discouraged.
+
The same caution applies with more force to the endpoint-document keys, because several of them are
*security controls*: the `routes[].forward` header and query allow/deny lists and
`routes[].websocket.allowed_origins` decide what crosses the gateway and which origins may open a
socket. They are reachable by a `${VAR}` on the same uniform terms as any other list, so an
environment variable can widen or empty them. Treat them as policy that belongs in the committed
endpoint document -- note that an *empty* resolution fails the boot rather than silently opening the
control, which is the rule above doing exactly the work it was added for.
* `upstream.connect_timeout_ms` / `read_timeout_ms` must be positive integers; they are
  millisecond-precision options on the data-plane client
  (link:adr/0008-data-plane-transport.adoc[ADR-0008] dropped the former whole-second
  restriction, which existed only for the `cui-http` `HttpHandler` builder).
* Secrets in `oidc` (`client_secret`, the session encryption key) must be *bare* `${ENV_VAR}`
  references -- not literals, and not the defaulted `${ENV_VAR:-...}` form, whose default would
  itself be a literal secret in a committed document. Both shapes fail the boot.
* `session.mode: cookie` does *not* require `session.encryption_key` -- omitting it selects the
  generate-on-startup key mode (sessions are dropped on restart and the key is not shareable
  across replicas). `session.mode: server` requires an explicit `session.store` (only `memory` is
  valid) and uses no encryption key.
* `security_headers.cors` with a wildcard origin and `allow_credentials: true` is rejected.
* A `protocol: websocket` route whose *effective* auth is `require: bearer` must declare a
  *non-empty* link:#_allowed_origins[`websocket.allowed_origins`] list; an absent or empty
  allowlist *fails the boot* (fail-closed -- there is no "any origin" default). Each entry is an
  exact origin (`scheme://host[:port]`, host compared case-insensitively, scheme and port exact);
  wildcards, suffix forms, and regular expressions are rejected. Both WebSocket keys live inside
  the route's `websocket` block -- `allowed_origins` written as a route-level sibling of
  `websocket` fails the boot as an unknown key. A `websocket` block on a non-`websocket` route,
  or `allowed_origins` on a WebSocket route whose effective auth is not `require: bearer`, fails
  the boot.
* `websocket.idle_timeout_seconds`, when declared, must be a *positive integer* (default `300`
  when omitted); it is valid only on a `protocol: websocket` route.
* The `edge_hardening` block is optional, and so is each of its members. An omitted `admission_cap`
  resolves to `2048`; an omitted `websocket_relay_cap` resolves to a *quarter of the effective*
  `admission_cap` (never below `1`), which is `512` at the default `admission_cap` -- so an operator
  who lowers `admission_cap` alone gets a proportionally lowered relay sub-budget rather than a
  boot-time rejection. When declared, each cap must be at least `1` -- a cap of zero would refuse
  every request (or every relay) and is always a misconfiguration rather than a deliberate posture.
* `edge_hardening.websocket_relay_cap` must not exceed `edge_hardening.admission_cap`. The relay
  budget is a *sub-budget of* the admission pool -- a relay takes a permit from both -- so a larger
  value could never bind and would silently disable the sub-cap the operator meant to impose. The
  comparison uses the *effective* values; because an omitted relay cap is derived from the admission
  cap it can only be tripped by an *explicitly declared* relay cap.
* `security_defaults.max_authorization_header_value_length`, when declared, must not be *below* the
  resolved baseline `max_header_value_length` (1024 under `strict`, 8192 under `lenient`). The key
  exists to *raise* the pre-route cap for `Authorization` values; a lower value is not a carve-out at
  all but a per-header *tightening* expressed through the one key that cannot express one, and it
  would silently make `Authorization` the single most-restricted header while reading like a
  relaxation key. The refusal offers no downward path because none exists: a route's
  `security_filter` cannot lower the `Authorization` cap (the post-route re-run floors it back up to
  `max(route max_header_value_length, budget)` for that header name), and `security_defaults.profile`
  cannot either (the budget is this key or its fixed `8192` default, and does not track the profile).
  Both bound *general* header values instead. The comparison uses the *resolved* profile, which is
  why it is a boot rule rather than a schema range; the schema owns only the `integer` /
  `minimum: 1` range. An omitted key is never refused -- it resolves to the default `8192`.
* `asset_defaults.content_types` is *add-only*: an entry naming one of the gateway's 21 built-in
  asset extensions is *refused at boot*, with the message naming the offending extension. The
  built-in mappings are immutable because permitting an override -- remapping `svg` away from
  `image/svg+xml`, or pointing any built-in at `text/html` -- is a stored-XSS lever on a security
  gateway. Refusing (rather than silently ignoring the entry at request time) is what makes the
  operator aware the mapping never took effect. Entries for extensions the gateway does *not* map
  are always accepted, and an omitted or empty block is never refused. See
  link:#_asset_defaults[`asset_defaults`].
